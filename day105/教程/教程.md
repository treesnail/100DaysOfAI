## 今日目标

day104 的结语说："`__all__` 读起来永远像一份已经兑现的清单。"
今天再换一个资产——把 **471 个模块里 2430 条模块级常量** 编成一份可核对的台账：

```text
问题① 100 天之后，仓库里第五个没有被利用的资产是什么？
问题② "这个仓库把哪些名字钉成了什么值"这件事，现在靠什么回答？
问题③ 一份常量台账的判据应该是什么？
```

今天的答案：

```text
问题① 是那 2430 条 UPPER_CASE = 右端：它们被写在几百份 .py 里，却从来没有人横向摆在一起看过
问题② 现在只能靠 grep 与 IDE 搜索——它没有"同名表"，也没有"取值表"
问题③ 判据不是"这份台账全不全"，而是"每一个常量能不能被定值、
       报出来的同名与冲突是不是真的、同一批文件能不能编出同一份台账"——
       **可复算 + 可定值才是这份台账的全部价值**
```

本日要建立的四件事：

1. **一份扫描**：`parse.scan_all()` → 471 个模块、2430 条常量、两类取值形态，
   **只用 `ast` + `literal_eval`，一行 `import` 都没有**；
2. **一份台账**：`ledger.build_ledger()` → 471 行 / 常量 2430 / 可取值 1848 / 读不出 582 /
   跨模块同名 164 组 / **冲突 38 组** / 摘要 `e7760a45ad90967c`；
3. **一张同名表**：`ledger.name_groups()` → unique 1884 / consistent 70 / conflict 38 / incomparable 56；
4. **一套判据**：七条性质、三类判据、六个失败族。

最终产出：`constant_ledger` 包七个文件（729 语句 / 162 分支）、
`tests/test_constant_ledger.py`（54 个用例，100% 覆盖）、`docs/constant_ledger.md`（12 节）、
`scripts/constant_ledger_demo.py`（7 节）。现场读数：

```text
扫描 471 个模块 | 重复赋值的模块 0 个
```

## 第一章：为什么"字""名字""关系""承诺"之后要编"取值"

day101 编的是**字**，day102 编的是**错误名字**，day103 编的是**模块关系**，day104 编的是**承诺**。
今天编的是**取值**：

```text
每个模块各把一些名字钉成值            "我这里的 EPSILON 是 1e-5"
没人把这几十个 EPSILON 摆在一起看过   "这两个包里的 EPSILON 是不是同一个数？"
```

这件事有一个天然的好处：**它依然不依赖模型能力**——
它只依赖"把文件收齐、把取值离线算出来、把顺序定死"。

因此今天的四个读数是扫描 / 台账 / 同名 / 性质，而且它们**共用同一份台账**
（`study_lines(ledger=...)`、`check_all(ledger=...)` 读的是同一时刻的状态）。

## 第二章：收料——先说清"哪些文件必须进得来"，再说清"什么算常量"

```text
被扫描的       smart_research_agent/**/*.py                    471 份
算常量的       UPPER_CASE = 单个 Name 目标（模块级）            2430 条
不算常量的     解包赋值 / 小写名 / 以 _ 开头 / 写在 def 或 class 里
```

一条纪律与 day101 ~ day104 逐字相同：**一份没进台账的模块，与"这个模块一个常量都没定义"读起来完全一样。**

```python
ALPHA = 1                ⇒ 收
BETA: int = 2            ⇒ 收（带注解）
GAMMA += 3               ⇒ 收，但取值记 opaque（它没有可比较的右端）
DELTA, EPS = 1, 2        ⇒ **不收**（一个右端对两个名字，取值说不清）
lower = 1 / _PRIVATE = 1 ⇒ **不收**（不是全大写 / 以 _ 开头）
def f(): INSIDE = 1      ⇒ **不收**（不在模块级作用域）
```

"模块级"这条边界与 day104 同源：`class C:` 里的 `KAPPA = 9` 与函数体里的 `INSIDE = 1`
都是**那一层的实现细节**，不是被钉死在外面的数。本课里这条规则写在 `iter_module_scope` 里，
并且有一条测试专门钉住它。

## 第三章：两类取值形态——以及"我承认我算不出来"

```text
literal   EPSILON = 1e-5 / TOLERANCE = 1e-9 / NAMES = ("a", "b")   ⇒ literal_eval 求得出
opaque    ROOT = Path(__file__).resolve().parents[2]               ⇒ 求不出来，记"读不出来"
```

现场读数是 **literal 1848 / opaque 582**。两类必须分开记，理由很具体：

> **把 opaque 当成"空值"去和别的模块比，会让两个根本无关的常量"看起来一致"。**

`literal_eval` **不执行代码、不 import、不联网**，因此"这个值是什么"有一个离线、确定的答案。
本课绝不用 `eval`：那会把"编一份台账"变成"跑一遍整个仓库"。

## 第四章：四类同名关系——判定顺序写死

```text
unique          只在一个模块里出现                              ⇒ 1884 组
consistent      跨模块，且能比较的字面值全都相同                 ⇒   70 组
conflict        跨模块，且能比较的字面值不止一个（**读数**）      ⇒   38 组
incomparable    跨模块，但至少一侧是 opaque（**拒绝下结论**）     ⇒   56 组
```

```python
if len({item.module for item in members}) < 2:      return RELATION_UNIQUE
if any(item.value_kind == VALUE_OPAQUE ...):        return RELATION_INCOMPARABLE
if len({item.literal for item in members}) == 1:    return RELATION_CONSISTENT
return RELATION_CONFLICT
```

顺序不能换：**先判"能不能比"，再判"比出来是什么"**。
把 `incomparable` 并进 `conflict`，会让"我算不出来"被读成"它们对不上"——
一个没人说得清归属的名字，比一个报错更难被发现（day102 / day104 说过两次了）。

## 第五章：一个读数，不是一次失败

现场读数里，**38 组名字在不同包里取值不同**。它们分两类：

```text
"同一件事的不同参数"   DEFAULT_BATCH_SIZE 2 vs 32、DEFAULT_ALPHA 0.5 vs 0.99
                       —— 每个包给自己的模型挑了一个合理的批大小 / 权重
"结构性的同名"         FAMILY_OUTCOMES（25 个模块各写一份自己的处置表）、
                       ABSENT_FAMILY / RETURNED_FAMILY（每个包各写一次"今天谁缺席"）
```

本课**不**写一条"同名必须同值"的性质去把它们"处理掉"。理由是：

```text
它们是一处**读数**，不是一次失败
  - 把它们做成"必须一致"的性质 ⇒ 这条性质会在仓库合理地变化时变红，
    最后一定会被人关掉——而一条被关掉的性质，等于不存在
  - 于是本课把整张印出来（conflicts()），只对"它是不是真的"做一条相等判据（③）
```

**但"读数"不等于"没有出口"：** `require_consistent(ledger)` 是那条"拒绝交付"的路，
它在**调用点显式要求**"这些同名常量必须一致"时才抛 `ConflictError`。
这与 day103 对"环"、day104 对"幽灵"的处理是同一个立场：
**一个读数不该被一条性质静默地删掉，但它可以成为一次显式拒绝交付的理由。**

## 第六章：真的撞到的一堵墙——集合字面量的 `repr`

本课写完后，第一次跑全量构建时得到一个**不稳定的摘要**：同一批文件，两次运行给出两个数字。
原因在取值指纹的第一版：

```python
return repr(ast.literal_eval(node))          # 对 set 而言，这一步随进程变化
```

一个模块级常量若写成集合字面量：

```python
LETTERS = {"a", "b", "c"}
```

`literal_eval` 给出的是一份 **`set`**，而 `set` 的迭代序随进程（`PYTHONHASHSEED`）变化，
于是 `repr` 也就随之变化——**台账照样编得出来、同名表照样算得出来，
只有第 ② 条性质（两次构建逐位相同）会被它顶破。**

修法是把"集合 → 字符串"这一步显式定序：

```python
if isinstance(value, (set, frozenset)):
    return "{" + ", ".join(sorted(canonical_value(item) for item in value)) + "}"
```

这与 day101 的"倒排表文档名必须排序"、day102 的"族按包名升序 × 源码顺序排"、
day103 的"候选按 `(-len, name)` 排"、day104 的"模块按名字排序"是同一条纪律的**第五次**应用。
区别在于：这次它藏在一个"看起来完全合理"的 `repr` 里。

为了让它再也不能悄悄坏掉，这一课的测试里有一条**子进程测试**：
两个不同的 `PYTHONHASHSEED` 必须给出同一个摘要。

## 第七章：可复算——把"并列"的不确定性显式消掉

台账的可复算口径只有两行：

```text
comparable() = (modules, ((模块, ((名字, 行号, 注解, 形态, 取值), ...)), ...))
digest()     = sha256(repr(comparable()))[:16]        ⇒ 实测 e7760a45ad90967c
```

`comparable()` 里**一个集合、一个字典、一个绝对路径都没有**。三处显式排序：

```text
模块        按名字升序
常量        （名字, 行号）升序
同名组      按（-出现模块数, 名字）升序
```

## 第八章：七条性质、六个失败族与五条边界

### 8.1 七条性质（三类判据齐全）

```text
1. ledger_covers_all_modules              | [equality   ] | 读数 0 ✓ | 模块 471 个 / 期望 471 个
2. ledger_is_reproducible                 | [equality   ] | 读数 0 ✓ | 摘要 …967c / …967c
3. conflicts_are_sound                    | [equality   ] | 读数 0 ✓ | 冲突组 38 个 / 不成立 0 个
4. shared_constants_are_sound             | [equality   ] | 读数 0 ✓ | 同名组 164 个 / 不成立 0 个
5. duplicate_assignments_within_module    | [upper_bound] | 读数 0 ✓ | 重复 0 个 ≤ 上界 0
6. constants_are_numerous                 | [lower_bound] | 读数 2430 ✓ | 常量 2430 ≥ 下界 500
7. shared_constants_exist                 | [lower_bound] | 读数 164 ✓ | 同名组 164 ≥ 下界 1
合计：7/7 条通过
```

**四条相等、一条上界、两条下界**。三条判据各自的"方向"要跟这个量的方向一致：

```text
③ ④ 是"真的吗"型判据：报出来的每一组冲突 / 每一个同名组，都要**独立复核**一遍
⑤ 重复赋值的模块数：越少越好的量 ⇒ 兜的是上限
⑥ ⑦ 是**存在性**断言：只能从下面兜住（写成 == 某个精确数会在仓库合理地变化时误报失败）
```

第 ③ 条的独立复核很具体：它不看取值指纹，而是**重新读源码**，
把该名字在每个成员模块里的**右端源码片段**取出来（`parse.value_segments`）；
这一组必须至少有两种不同的片段才算冲突。因此它能抓住"取值指纹算错了 / 少了归一化"。

### 8.2 六个失败族

| 族 | 该谁去修 |
|----|----------|
| `ParseError` | 改解析：某份 `.py` 读不到或语法错时，先把它补进扫描范围或修好它 |
| `AssignError` | 改赋值：常量右端读不下来时，把它写成字面量，或显式排除在台账之外 |
| `LedgerBuildError` | 改台账实现：两次构建不一致或同一模块同名列两次时，去掉没有固定的量 / 重复项 |
| `ConflictError` | 改数据或改调用：同名常量取值不一致时，要么统一取值，要么别要求它们一致 |
| `NumericError` | 改数据或改实现：非有限读数与非法上下界都属于"数值不可用" |
| `ParameterError` | 改调用：值形态 / 同名关系 / 性质名 / 上限都是调用点的一次决定 |

`FAMILY_OUTCOMES` 与 `_FAMILY_CLASSES` 逐键对齐，导入期断言。两条族常量：

```text
RETURNED_FAMILY = "ShapeError"
  day075 的 transformer_core 第一次给它命名，此后被十来个包各写一遍——它是 day102 那份台账里
  跨包重名之最（34 个模块同时导出它）。day103（编图）与 day104（编承诺清单）都没有它；
  day105 换了一个对象，问的却是同一个问题："同一个名字在不同包里**长成了什么形状**？"
  ——一个 EPSILON 在 A 包是 1e-5、在 B 包是 1e-8，正是一次形状对不上。于是它**回来**了。

ABSENT_FAMILY = "GradientError"
  本课是纯静态分析：不但没有反向，连一次 import 都不执行。
```

### 8.3 五条边界

```text
1. 不新增任何第三方依赖：解析只用标准库 ast 与 ast.literal_eval。
2. 不改动任何既有模块、既有测试、pyproject 与 docs 下的既有文件——只新增文件。
3. 不做 import、不执行被扫描的表达式：Path(__file__) 这类右端被记成 opaque，而不是被求值。
4. 全部读数离线、确定性：只读文件系统与 ast，不联网、不读密钥。
5. 不判断常量取值的好坏：只如实记录"谁把哪个名字钉成了什么值"，不评价该不该是这个值。
```

## 结语：三条可以带走的工程结论

1. **先把"哪些文件必须进得来"说清，再谈读了什么。**
   本课的第一条性质是覆盖（471/471），它排在所有结构性质之前。
   一份没进台账的模块，与"这个模块一个常量都没定义"在结果里读起来完全一样。

2. **"同名不同值"是一个读数，不是一次错误。**
   38 组同名不同值里有"每个包给自己的模型挑了不同的批大小"这类**合理**的差异。
   正确做法是把它整张印出来，并给调用点一条**显式**的拒绝交付之路（`require_consistent`），
   而不是让一条"必须一致"的性质替你把它删掉。

3. **集合字面量必须先排序。**
   `repr({1, 2, 3})` 的顺序随进程变化——它与 day101 的 `dict` 插入序、day103 的排序键并列
   是同一条纪律；差别只是这次它藏在一个"看起来完全合理"的 `repr` 里。

> **诚实的说明**：本课是**离线、确定性**的——它不调用任何模型、不做任何推理，
> 也不测量"这个常量取得对不对"。它给的是**一套能带走的取值纪律**：
> 当你真的要为一个代码库建一份常量台账时，知道该先收齐什么、
> 该怎么离线定值、该怎么处理"同名不同值"、该断言哪七件事。
