## 第一部分：选择题

### 第 1 题

**答案：C**

**解析：** LangGraph 节点的返回值语义是**部分更新（partial update）**：返回的 dict 按字段合并进当前状态，没提到的字段保持原值。对未声明 reducer 的字段（如 `thought`），合并方式就是**覆盖**——新值替换旧值。

逐项排除：

- A 错：节点不需要也不应该返回完整状态，只返回它负责更新的字段即可。我们的 think 节点在有最终答案时只返回 `thought/final_answer/done` 三个字段。
- B 错：追加语义需要显式声明 reducer，如 `history: Annotated[list, operator.add]`。普通字段默认是覆盖。
- D 错：这是最容易产生的误解。引擎做的是字段级合并，不是整体替换——否则 think 节点返回一次，task、steps 就全丢了。

### 第 2 题

**答案：A**

**解析：** `add_conditional_edges(source, path_func, path_map)` 三参数职责分明：

- `source`（`"think"`）：条件边从哪个节点出发；
- `path_func`（`route_after_think`）：读状态、做业务判断、返回一个字符串**键**（如 `"act"` 或 `"end"`）；
- `path_map`（`{"act": "act", "end": END}`）：键 → 目标节点的映射表。

判断逻辑与拓扑走向因此解耦：路由函数只管"done 了吗"，映射表只管"done 了去哪"。B 的"条件表达式字符串"、C 的"目标节点列表"、D 的"异常处理表"都不是该 API 的形态。注意这是 langgraph 1.x 的签名，网上一些 0.x 时代教程的写法已经过时。

### 第 3 题

**答案：B**

**解析：** `graph.invoke(None, config=同样的config)` 是断点恢复的标准写法。第一个参数传 `None` 表示"不提供新输入，从检查点继续"；引擎根据 config 里的 thread_id 找到暂停时的快照，从 `snapshot.next` 指向的节点接着执行。

逐项排除：

- A 错：传入 `initial_state(task)` 是**重新开始**——它会被当作一条新的输入写入该 thread，而不是恢复暂停的现场。
- C 错：LangGraph 没有 `resume()` 方法（那是某些工作流引擎的 API）。
- D 错：`{"resume": True}` 不是 langgraph 1.2 的合法输入形态。

关键前提是 config 必须相同：恢复的依据就是 thread_id 对应的检查点，换一把"钥匙"就没有现场可恢复。

### 第 4 题

**答案：B**

**解析：** `Annotated[list[dict], operator.add]` 声明了 reducer：节点返回的 `history` 值不直接覆盖，而是执行 `旧值 + 新值`。`operator.add` 作用在列表上就是拼接，所以第一次 act 后 `history == [记录A]`，第二次返回 `[记录B]` 后变为 `[记录A, 记录B]`。

这就是"累积集合"字段的正确写法。对照记忆口诀：**字段是"最新值"用默认覆盖，是"累积集合"用 reducer。** 如果忘了声明 reducer，history 每步都会被覆盖成单元素列表，"越跑越短"——这是 LangGraph 新手最高发的 bug 之一。

## 第二部分：判断题

### 第 5 题

**答案：错**

**解析：** `MemorySaver` 的字面意思就是"存在内存里"——检查点保存在进程的字典中，**进程退出即全部丢失**。同一个 thread_id 只能在同一进程生命周期内恢复状态。

需要跨进程、跨重启的持久化时，要换成 `SqliteSaver` 或 `PostgresSaver` 等后端。值得记住的是：因为 checkpointer 是 `compile()` 时注入的，换后端**不需要改动任何节点代码**——这正是"编译期注入"设计的回报。MemorySaver 的适用场景是开发调试、单元测试、单次运行的脚本。

### 第 6 题

**答案：对**

**解析：** `snapshot.next` 是"待执行节点"元组。图运行到 END 后没有下一步，返回空元组 `()`；而断点暂停时返回如 `("act",)`。我们的测试同时断言了两种情况：

```python
assert snapshot.next == ()        # TestCheckpoint：已跑完
assert graph.get_state(config).next == ("act",)  # TestInterrupt：断点暂停
```

这两个值是程序判断"图跑完了还是停在半路"的标准方法，写审批系统、进度条时都会用到。

### 第 7 题

**答案：错**

**解析：** `interrupt_before` 是在节点**执行前**暂停——这是它全部价值所在。暂停时 act 尚未运行，`observation` 仍是初始空串 `""`（测试里专门断言了这一点），但 think 写入的 `action="calculator"` 已经可见。

这个"将发未发"的窗口正是审批危险操作的最佳时机：人能看到 Agent **打算**做什么（action 已写入状态），同时副作用还**没有发生**（工具尚未执行），可以否决、可以改参数。如果是在执行后暂停（`interrupt_after`），邮件已经发出去了，审批就失去了意义。

## 第三部分：问答题

### 第 8 题

**参考答案：**

放在 think 之后时，流程变为：

```text
think → act → think → act → think → act → think(第4次) → 路由发现 steps>=3 → END
```

LLM 共被调用 **4 次**。第 4 次调用产出的思考注定被丢弃——路由紧接着就把图导向 END，这次调用的输出没有任何消费者。

而我们放在 act 之后的实现：

```text
think → act → think → act → think → act → 路由发现 steps>=3 → END
```

LLM 恰好调用 3 次，与 max_steps 语义对齐（也和 day006 `ReactAgent` 的行为一致）。

浪费的实质：LLM 调用是 Agent 系统里**最贵、最慢的资源**（真实 API 按 token 计费，延迟以秒计），工具执行通常近乎免费。路由位置决定了最后一次循环以哪个节点收尾——以 think 收尾就多烧一次注定无用的调用。推而广之：**设计条件边时，要把终止检查放在"昂贵操作之前"，而不是之后。**

### 第 9 题

**参考答案：**

`values` 是空字典 `{}`。thread-b 从未运行过，checkpointer 里不存在它的任何快照。

这个实验说明的特点是：**编译后的图对象本身是无状态的执行引擎，全部运行状态都存放在 checkpointer 中，并以 thread_id 为边界相互隔离。**

类比 Web 架构：这就像"应用无状态、会话存 Redis"——同一个 Flask/FastAPI 应用可以服务成千上万个用户，会话数据互不串扰。带来的直接好处：

1. **天然并发安全**：一张图服务任意多会话，无需加锁；
2. **状态可外部化**：换 PostgresSaver 后，状态脱离进程存在，图进程可以随便重启、扩容；
3. **可审计**：任意会话的完整状态历史按 thread_id 即可取回。

## 第四部分：编程题

### 第 10 题

**参考实现**（追加到 `tests/test_graph.py`）：

```python
class TestHumanApproval:
    """危险操作人工审批：断点暂停 → 审批人否决并改参 → 恢复执行."""

    def test_reject_dangerous_action_at_breakpoint(self, registry: ToolRegistry):
        llm = MockLLM(
            responses=[
                "Thought: 需要超大计算\nAction: calculator\nAction Input: 999999**999999",
                "Thought: 已拿到结果\nFinal Answer: 已完成",
            ]
        )
        graph = build_react_graph(llm, registry, interrupt_before=["act"])
        config = _config("t-approval")

        # ① 图在 act 前暂停：危险操作将发未发
        graph.invoke(initial_state("做一次危险计算"), config=config)
        assert graph.get_state(config).next == ("act",)

        # ② 审批人否决：把危险入参改成无害计算
        graph.update_state(config, {"action_input": "1+1"})

        # ③ 恢复执行：按审批后的参数运行
        final = graph.invoke(None, config=config)

        assert final["observation"] == "2"          # 算的是 1+1，不是超大数
        assert final["final_answer"] == "已完成"
```

**解析：**

- ① 第一次 `invoke` 只执行了 think 节点：LLM 弹出第一段脚本，action 写入状态，图在 act 前停住。此时超大计算**尚未执行**——断言 `next == ("act",)` 确认了暂停位置。
- ② `update_state` 对 `action_input` 是覆盖式更新（该字段没有 reducer），审批人的修改直接替换掉危险参数。这一步就是 Human-in-the-Loop 的"否决/修正"动作。
- ③ `invoke(None, config)` 从检查点恢复：act 读到的是修正后的 `"1+1"`，算出 `"2"`；随后 route_after_act 判断 `steps(1) < max_steps(5)`，回到 think；MockLLM 弹出第二段脚本给出 Final Answer，图走 END。

**评分要点：** 暂停位置断言（`next == ("act",)`）、`update_state` 的正确调用、`invoke(None, ...)` 恢复、对 `observation` 与 `final_answer` 的双重断言。常见错误：第一段脚本忘了带 `Action Input`（解析器会抛 `ReActParseError`）；第二段脚本忘了带 `Thought:`（同样解析失败）；恢复时误传 `initial_state(...)` 导致从头重跑而非续跑。
