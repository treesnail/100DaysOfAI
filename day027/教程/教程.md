## 第一章：为什么运行期输出需要质检 —— 评估的最后一公里

### 1.1 现状：Final Answer 无人把关

回顾 day006 的 ReAct 循环，终止条件是"模型自己觉得信息够了"：

```text
Thought: 已得到结果
Final Answer: 2+3 等于 5     ←── 这句话直接返回给用户，中间没有任何检查
```

模型说"可以收场了"，循环就收场。但"模型觉得够了"和"答案真的对"是两回事。真实的翻车现场五花八门：

- **格式失控**：下游系统期待 JSON，模型返回了一段散文；
- **数字幻觉**：Observation 明明返回 `56.0`，Final Answer 写成"结果是 100"；
- **答非所问**：用户问"对比三个框架"，答案只分析了第一个就收尾；
- **空话套话**："这是一个很好的问题，综上所述……"，没有实质内容。

离线评估（day025 的 Harness 批量跑数据集）能发现**系统性问题**，但它有两个盲区：一是只能在发版前跑，拦不住线上每一次输出；二是数据集覆盖不了用户真实提问的长尾分布。**运行期质检补的正是这最后一公里**——每一次输出都被评估，每一次评估都被记录。

### 1.2 离线评估 vs 在线评估

| 维度 | 离线评估（day025 Harness） | 在线评估（今天） |
|------|---------------------------|------------------|
| 时机 | 发版前 / 回归时批量跑 | 每次 Agent 输出时实时跑 |
| 输入 | 固定评估数据集 | 真实用户任务 |
| 对比基准 | 通常有 expected 参考答案 | 没有参考答案，只有过程证据 |
| 成本敏感度 | 低（反正离线跑） | 高（每次输出多一次 LLM 调用） |
| 产出 | 通过率、平均分报告 | 逐条质量日志、趋势告警 |
| 回答的问题 | "这个版本能不能发？" | "线上质量有没有劣化？" |

注意第三行：**在线评估没有标准答案可比对**，这是它设计上最难的地方。我们能用的证据只有三样：任务本身、循环过程中的 Observation、以及最终输出。今天的数字一致性检查，正是"用过程证据替代标准答案"的典型手法。

### 1.3 评估器在架构中的位置

```text
用户任务
   │
   ▼
┌────────────────────────────────────────────┐
│ ReactAgent.run()                            │
│   ReAct 循环：Thought/Action/Observation    │
│        │                                    │
│        ▼ Final Answer 产出                  │
│   ┌──────────────────────┐                 │
│   │ OutputEvaluator       │  ← 双通道打分   │
│   │  规则通道 + 模型通道   │                 │
│   └──────────┬───────────┘                 │
│              ▼ OutputScore                  │
│   ┌──────────────────────┐                 │
│   │ OutputQualityLogger   │  ← 追加写 jsonl │
│   └──────────────────────┘                 │
└────────────────────────────────────────────┘
   │
   ▼ 答案照常返回给用户（评估不阻断主流程）
```

两个关键设计原则，第四章会展开：

1. **评估是旁路，不是闸门**：评估失败、日志写失败，都不影响答案返回。
2. **接入是可选的**：不传 `output_evaluator`，Agent 行为与之前完全一致——评估能力是"挂载件"，不是"侵入改造"。

> 思考题：为什么不让评估器"拦截"低分答案、要求 Agent 重试？提示：想一想延迟、成本，以及"谁来保证重试后更好"。自我修正机制是后续阶段的课题。

## 第二章：三个指标的操作化定义 —— 从形容词到函数

### 2.1 什么叫"操作化"

"答案要有用、要准确、格式要对"——这是三个**形容词**，形容词没法写进代码。操作化（operationalization）就是给每个形容词配一个**可计算的判定函数**：

```text
有用性   → helpfulness(output, task) -> 0~1 分
准确性   → accuracy(output, observations) -> 0~1 分
格式合规 → format_compliance(output, spec) -> 0~1 分
```

操作化做的好不好，看两点：**可重复**（同一输入同一分数）和**可解释**（扣分能说出原因）。我们统一用 0~1 连续分数而非"通过/不通过"二元判定，因为趋势监控（第四章）需要连续值才能看出"缓慢劣化"。

### 2.2 格式合规（format_compliance）：最适合规则化的指标

操作化定义：**输出是否满足事先声明的结构约定与长度约束**。

这是三个指标里最"硬"的一个——"是不是合法 JSON"没有见仁见智的空间，`json.loads` 说了算。我们的实现（[evaluation/output_eval.py](../源码/smart-research-agent/smart_research_agent/evaluation/output_eval.py) 的 `_check_format`）覆盖两类约束：

- **结构约定**：`expected_format="json"` 时用权威解析器判定；`expected_format="markdown"` 时检查是否含标题（`#`）或列表（`-` / `1.`）标记；
- **长度约束**：`min_length` / `max_length`，防空答案也防失控的长篇。

计分方式是**扣分制**：满分 1.0，每违反一项扣 0.5，下限 0。同时把每条违例写进 `issues`——**分数用于聚合，问题清单用于诊断**，两者缺一不可。

注意一个细节：JSON 校验先剥离 ```` ```json ```` 代码块围栏再解析。这和 day010 `parse_plan` 的防御式解析是同一哲学——**模型的格式漂移是常态，判定逻辑要按"最宽容的合法形态"来写**。

### 2.3 准确性（accuracy）：用过程证据做粗检

操作化定义：**输出中的关键事实能否在循环证据（Observation）中找到来源**。

在线评估没有标准答案，但 ReAct 架构给了我们一份天然的过程证据：所有工具返回的 Observation。于是我们实现了一条朴素但有效的规则——**数字一致性粗检**（`_check_numeric`）：

1. 用正则从输出中抽出全部数字；
2. 用同样的方法从全部 Observation 中抽出数字集合；
3. 输出里的每个数字若不在 Observation 集合中，记一条 issue（"疑似编造"）；
4. 得分 = 命中数 / 输出数字总数。

为什么只查数字？因为数字是**可以精确比对的最小事实单元**：字符串匹配 `5.0` 几乎不会误判，而"框架 A 比框架 B 快"这种语义断言用规则根本无法核对。这是规则通道的能力边界，也预示了模型通道存在的必要性（第三章）。

两个"按满分放行"的边界设计值得记住：

- 没有 Observation（Agent 一步直接作答）→ 无法核对，满分；
- 输出中没有数字 → 没有可核对对象，满分。

**规则检查的原则是"不误伤"**：宁可漏报，不可错杀。一条天天误报的检查规则，下场就是被团队关掉，那时它连漏报的价值都没有了。

### 2.4 有用性（helpfulness）：必须交给模型的指标

操作化定义：**答案是否完整、直接地回应了任务**。

试着用规则定义"有用"：长度达标？空话也可以很长。包含任务关键词？答非所问也包含。你会发现**有用性本质是语义判断，规则写不出来**。这类指标的唯一现实方案是 LLM-as-a-judge——让另一个（或同一个）LLM 按评分量规（rubric）打分：

```python
RUBRIC_PROMPT = """你是一个输出质量评审员。请根据任务要求评审助手的最终答案。
...
从两个维度打分（1~5 的整数，5 最好）：
- helpfulness：答案是否完整、直接地回应了任务，对用户有实际帮助
- accuracy：答案中的论断是否合理、无明显事实错误
严格输出 JSON，不要输出其他内容：
{"helpfulness": 4, "accuracy": 5, "issues": ["问题描述，没有则为空数组"]}
"""
```

三个设计细节：

- **rubric 要具体**："1~5 分，5 最好"之外还给了每个维度的判定标准，评分才有锚点；
- **要求输出 issues**：评审模型不只给分，还要写下理由，这些理由直接进入日志，是可解释性的来源；
- **`temperature=0.0`**：评分任务求稳不求活，关掉采样随机性，同一输出尽量得同一分数——呼应 2.1 的"可重复"要求。

### 2.5 每个指标"谁来判断"：决策表

| 指标 | 操作化定义 | 规则能判吗 | 模型能判吗 | 我们的分工 |
|------|-----------|-----------|-----------|-----------|
| 格式合规 | 结构约定 + 长度约束 | 完全能（确定、廉价） | 能但浪费 | **纯规则** |
| 准确性 | 事实与证据一致 | 数字能，语义不能 | 能（但可能也被骗） | **规则粗检 + 模型复核，各 50%** |
| 有用性 | 是否回应了任务 | 不能 | 能 | **纯模型** |

这张表是第三章"互补性"讨论的浓缩：规则吃"确定性高、形式化"的部分，模型吃"语义化、开放式"的部分，准确性恰好横跨两边，所以双通道各占一半权重。

## 第三章：双重评估 —— 规则与模型的互补性

### 3.1 为什么不二选一

先做个思想实验：只用其中一种通道会怎样。

**只用规则**：格式和数字查得很准，但"答案是 `{"result": "我不知道"}`"——JSON 合法、长度达标、没有数字可核——满分通过。规则看不见语义层面的坏。

**只用模型**：`helpfulness`、`accuracy` 都能评，但三个问题无解：

1. **成本**：每条输出多一次 LLM 调用。格式是否合法这种一行 `json.loads` 的事也花一次调用，是拿牛刀杀鸡；
2. **一致性**：模型评分有方差，今天 4 分明天 3 分，趋势监控的噪声变大；
3. **盲区**：评审模型和被评模型如果是同一家，系统性盲区（比如都倾向于过度自信的措辞）会互相包庇。

### 3.2 互补性：成本 / 一致性 / 覆盖面三维权衡

| 维度 | 规则通道 | 模型通道 |
|------|---------|---------|
| 单次成本 | 几乎为零（CPU 正则） | 一次 LLM 调用（真金白银） |
| 一致性 | 完全确定，同输入同输出 | 有采样方差，需 temperature=0 压制 |
| 覆盖面 | 只能查可形式化的性质 | 语义层面几乎无边界 |
| 可解释性 | 违例可精确定位到规则 | 理由由模型生成，可能含糊 |
| 失效模式 | 漏报（查不出来的坏） | 误判（评分漂移、与被评模型同盲区） |

**没有任何一个维度上两者同强，也没有任何一个维度上两者同弱**——这就是互补的严格含义，也是"双重评估"不是冗余而是必要的数学原因。

### 3.3 加权合成：overall 怎么算

`OutputEvaluator.evaluate()` 的合成逻辑：

```python
helpfulness = model_scores["helpfulness"] / 5            # 纯模型，1~5 归一化
accuracy = 0.5 * numeric_score + 0.5 * (model_scores["accuracy"] / 5)  # 规则模型各半
format_compliance = rule_format_score                     # 纯规则
overall = 0.4 * helpfulness + 0.4 * accuracy + 0.2 * format_compliance
```

权重 `(0.4, 0.4, 0.2)` 的理由：有用性与准确性直接决定用户价值，格式是"接口契约"——重要但可自动修复（下游可以做格式适配），所以权重减半。权重是业务决策不是技术决策，我们把它做成构造参数 `weights`，就是承认**不同业务该有不同的答案**。

### 3.4 降级策略：评估器自身永远可用

模型通道可能失败：网络超时、返回乱码、分数越界。这时评估器怎么办？我们的选择是**降级为纯规则评估**而不是抛异常：

```python
model_scores = self._model_score(output, task)
if model_scores is not None:
    ...  # 双通道合成
else:
    logger.warning("模型打分失败，降级为纯规则评估")
    helpfulness = 1.0 if len(output.strip()) >= self.min_length else 0.0
    accuracy = numeric_score
```

设计依据：**评估是可观测性设施，可观测性设施的可用性要求必须高于被观测对象**。监控系统的座右铭是"我可以看不清，但我不能不在"。`_model_score` 内部同样走防御式解析（`find("{")` / `rfind("}")` + 类型与取值范围校验），任何一层不过都返回 `None` 触发降级——day010 的四道防线思想，第三次复用。

> 思考题：降级分支里 `helpfulness` 用"长度达标即满分"的启发式，这个启发式会高估还是低估真实有用性？为什么这种偏差方向（高估）对告警系统是危险的？

## 第四章：质量日志 —— 从单次打分到线上监控

### 4.1 单次打分的价值为零

一个 `overall=0.6` 说明不了什么——也许是任务本身难。评估数据的价值在**纵向聚合**：

- 昨天平均分 0.82，今天 0.61 → 有人改了提示词？换了模型？
- 最近 50 条里"数字疑似编造"出现了 12 次 → 幻觉率在上升；
- 改版前后各跑一周，对比均分 → 这次 Prompt 优化到底是好是坏？

这些都要求**每次评估被持久化**，这就是 `OutputQualityLogger`（[evaluation/quality_logger.py](../源码/smart-research-agent/smart_research_agent/evaluation/quality_logger.py)）的职责。

### 4.2 为什么选 jsonl 格式

```python
record = {
    "ts": datetime.now(timezone.utc).isoformat(),
    "task": task[:200],
    "output_preview": output[:200],
    **score.to_dict(),
}
with self.log_path.open("a", encoding="utf-8") as f:
    f.write(json.dumps(record, ensure_ascii=False) + "\n")
```

jsonl（JSON Lines，每行一条独立 JSON）是运行期日志的事实标准，原因：

- **追加写 O(1)**：不需要读取、解析、重写旧内容，写路径极快；
- **单行损坏不传染**：某一行写一半进程崩了，只损失这一行，其余记录完好（对比：一个巨大的 JSON 数组少个逗号就全废）；
- **天然可被流式工具消费**：`tail -f`、`jq`、pandas 都认这个格式，日后接 ELK/Loki 零成本。

另外两个细节：`task` 与 `output` 截断到 200 字符（日志是证据不是存档，全文会撑爆磁盘）；时间戳用 UTC ISO 格式（跨时区部署时不用猜"这是哪个时区的时间"）。

### 4.3 aggregate()：趋势判定与回归告警的雏形

`aggregate()` 返回的摘要有三块：

1. **总量指标**：各维度均分（`avg_overall` 等），回答"整体水位在哪"；
2. **趋势判定**：最近 `recent_window` 条（默认 10 条）的均分 vs 之前记录的均分，差值超过 0.05 判为 `improving` / `degrading`；
3. **高频问题**：`top_issues` 用 `Counter` 统计出现最多的 issue，回答"坏在哪里"。

趋势判定的逻辑极简：

```python
recent = records[-self.recent_window :]
earlier = records[: -self.recent_window]
diff = recent_avg - earlier_avg
trend = "improving" if diff > 0.05 else "degrading" if diff < -0.05 else "stable"
```

0.05 是**死区（dead band）**：模型通道的评分方差意味着 ±0.02 的波动是噪声不是信号，死区防止告警系统对噪声过敏——这和工业监控里"连续 N 次超阈值才告警"是同一种防抖思想，只是维度不同。

`insufficient_history` 这个状态也值得一提：记录不足一个窗口时，我们**拒绝**给出趋势结论。监控系统最危险的行为是在数据不足时装作有结论——宁可说"不知道"，不能说错。

## 第五章：接入 ReactAgent —— 可选挂载与失败隔离

### 5.1 两个可选参数，不改默认行为

```python
def __init__(
    self,
    llm: BaseLLM,
    registry: ToolRegistry,
    max_steps: int = 10,
    output_evaluator: OutputEvaluator | None = None,
    quality_logger: OutputQualityLogger | None = None,
):
```

这是**可选依赖注入**：评估器和日志器都是 `None` 默认值，旧代码 `ReactAgent(llm, registry)` 原样可跑。为什么选择"可选挂载"而不是"默认开启"？三个理由：

1. **评估有成本**（一次额外 LLM 调用），调用方应该显式选择付费；
2. **向后兼容**：day006~day026 的所有测试、所有调用方一行不用改；
3. **可组合**：只传 `output_evaluator` 可以"只打分不落盘"，只传 `quality_logger` 没有意义（没分可记），两者的依赖关系一目了然。

### 5.2 评估时机与失败隔离

`run()` 里唯一的改动是在 `Final Answer` 产出时插了一个旁路调用：

```python
if step.final_answer is not None:
    logger.info("得出最终答案")
    self._evaluate_output(task, step.final_answer, observations)
    return step.final_answer
```

注意 `observations` 是这次循环里收集的全部工具返回——它就是数字一致性检查要的"过程证据"。而 `_evaluate_output` 内部：

```python
try:
    score = self.output_evaluator.evaluate(answer, task=task, observations=observations)
except Exception as exc:  # noqa: BLE001
    logger.warning("输出质量评估异常（已跳过）: %s", exc)
    return
```

宽捕获 `Exception` 在别处是坏味道，在这里是刻意的：**评估器是旁路设施，它的任何故障都不配打断用户正在等的答案**。这条原则比"优雅"重要——`tests/test_output_eval.py` 里的 `test_evaluator_exception_does_not_break_run` 用一个必然抛异常的 BrokenEvaluator 固化了这条保证。

## 第六章：今日总结 —— 输出质量评估的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 三指标操作化 | 形容词无法编程，每个指标配判定函数 | `OutputScore` 三维度 + overall |
| 格式合规纯规则 | 确定性问题用确定性工具，成本为零 | `_check_format` |
| 数字一致性粗检 | 在线评估无标准答案，用 Observation 过程证据替代 | `_check_numeric` |
| 规则"不误伤"原则 | 无证据时按满分放行，宁漏报勿错杀 | `_check_numeric` 两个提前返回 |
| 有用性纯模型 | 语义判断规则写不出来 | `RUBRIC_PROMPT` + `_model_score` |
| 双重加权合成 | 规则与模型在成本/一致性/覆盖面上互补 | `evaluate()` 权重 (0.4, 0.4, 0.2) |
| 模型通道失败降级 | 可观测性设施的可用性必须高于被观测对象 | `evaluate()` else 分支 |
| jsonl 追加写 | O(1) 写路径、单行损坏不传染、流式工具友好 | `OutputQualityLogger.log` |
| 趋势死区 0.05 | 评分方差是噪声，告警系统不能对噪声过敏 | `aggregate()` |
| 可选挂载 + 失败隔离 | 评估是旁路不是闸门，向后兼容零改动 | `ReactAgent.__init__` / `_evaluate_output` |

今天埋下的伏笔：

- **自我修正**：低分答案目前是"记录后放行"，未来可以让 Agent 拿 issues 作为反馈重试；
- **告警闭环**：`aggregate()` 是手动调用的，day032 会把它接进 CI/CD 流水线做自动回归告警；
- **RAG 评估**：day029 的检索评估（召回率、MRR）会复用今天的 Harness 与日志设施。
