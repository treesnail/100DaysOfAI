## 第一章：为什么需要 subword 分词 —— 词表大小 vs OOV 的权衡

### 1.1 两种朴素方案都走不通

把文本变成模型能处理的数字序列，最朴素的想法是按现成的语言单位切：

**方案一：按词切（word-level）**。`"unbelievable"` 是一个词表项。问题：英语有词形变化（`believe/believes/believed/believing`）、复合词、拼写错误、新造词——词表要覆盖一切就得无限大。词表每大一分，模型最后一层的输出矩阵（词表大小 × 隐层维度）就大一分，cl100k_base 的 10 万词表已经占 GPT-3 级别模型相当比例的参数量。更要命的是 **OOV（out-of-vocabulary，未登录词）**：词表里没有的词只能记成 `<UNK>`，信息彻底丢失。用户ID、URL、新梗、"ChatGPT" 这种 2022 年才出现的词，全是 OOV。

**方案二：按字符切（character-level）**。词表只要几百个符号，永不 OOV。但代价是序列长度爆炸：`"unbelievable"` 从 1 个单位变成 12 个。序列长度直接决定注意力的计算量（随长度平方增长）与上下文窗口的消耗速度，而且单字符几乎不携带语义，模型要从头学"字符怎么拼成词"，学习负担剧增。

### 1.2 subword：两头好处都要

subword（子词）分词的核心观察是：**常见词应该整体成为一个 token，罕见词应该拆成有意义的片段**。`"unbelievable"` 切成 `un + belie + vable` 三片——每片都是常见片段，模型既能理解 "un-" 是否定前缀，又永远可以用片段拼出任何没见过的词，OOV 在事实上消失了。

```text
词表大小:   词级 >> 子词级 > 字符级
序列长度:   字符级 >> 子词级 > 词级
OOV 风险:   词级 >> 子词级 ≈ 字符级(≈0)
```

子词级在三个维度上都落在两个极端之间的甜点位：几万到几十万大小的词表、接近词级的序列长度、近乎为零的 OOV。剩下的问题是：**哪些片段该进词表？** 三种主流算法给出了三种答案，这是第二、三章的主题。

## 第二章：BPE —— 贪心合并的艺术

### 2.1 从数据压缩到分词

BPE（Byte Pair Encoding，字节对编码）本是 1994 年的数据压缩算法：反复把数据里最常见的相邻字节对替换成一个新符号。2016 年 Sennrich 等人把它搬到分词上：初始符号是字符，反复合并最高频的相邻对，合并历史就是一张"片段建造图纸"。

核心循环只有三步：

```text
重复 num_merges 轮:
    ① 统计：数一遍当前所有相邻符号对的出现频率（按词频加权）
    ② 选择：挑频率最高的那一对
    ③ 合并：全局替换成一个新符号，记下这条合并规则
```

伪代码（与我们的实现一一对应）：

```text
vocab = {词 → (字符序列 + </w>): 词频}
merges = []
for i in 1..num_merges:
    counts = 统计 vocab 中所有相邻符号对的频率
    best   = counts 中频率最高的对（并列取字典序最小者）
    vocab  = 把 vocab 里所有 best 替换为拼接后的新符号
    merges.append(best)
return merges   # 合并规则表 = 学到的"词表建造顺序"
```

两个设计细节值得停下来想：

- **词尾标记 `</w>`**：把 `est` 与词尾的 `est</w>` 区分开，保留词边界信息——"est" 在词中（如 "estimate"）和词尾（如 "newest"）的语义角色不同。
- **合并规则有顺序**：编码新词时按规则产生的先后套用，先产生的规则优先级高。顺序就是模型学到的"构词法优先级"。

我们的实现（`../源码/smart-research-agent/smart_research_agent/llm/bpe_demo.py`）用 Sennrich 论文的经典演示语料 `{"low": 5, "lower": 2, "newest": 6, "widest": 3}`。三步各对应一个函数：


在这份语料上跑 `train_bpe(corpus, 10)`，前四轮合并（测试 `test_first_merges_are_deterministic` 精确断言了它们）：

```text
第 1 轮: ("e", "s")   -> "es"      频率 9 = newest(6) + widest(3)
第 2 轮: ("es", "t")  -> "est"     频率 9
第 3 轮: ("est","</w>")-> "est</w>" 频率 9：词尾 est 先学成，因为它最高频
第 4 轮: ("l", "o")   -> "lo"      频率 7 = low(5) + lower(2)
```

10 轮后的最终词表里，`low</w>` 和 `newest</w>` 已经各自合并成**单个符号**——高频整词进入词表，这正是 1.2 节"常见词整体成 token"的承诺被算法自动兑现。

### 2.3 BPE 如何解决 OOV：编码一个没见过的词

训练只产生规则表，真正的威力在编码阶段。`encode("lowest", merges)`——语料里**没有** "lowest"：

```text
初始: l o w e s t </w>
套用 ("l","o")     : lo w e s t </w>
套用 ("lo","w")    : low e s t </w>
套用 ("e","s")     : low es t </w>
套用 ("es","t")    : low est </w>
套用 ("est","</w>"): low est</w>
结果: ["low", "est</w>"]   ← 未知词被拆成两个已知片段
```

没见过 "lowest"，但见过 "low" 和词尾 "est"，于是拼出语义合理的切分（"低" + 最高级后缀）。**OOV 没有靠任何特殊机制解决，它是贪心合并的自然副产品**——这是 BPE 最优雅的一点。对应测试 `test_unseen_word_decomposes_into_known_subwords`。

### 2.4 从教学版到工业版还差什么

`bpe_demo.py` 为了讲清原理做了三处简化，知道差距在哪才算真懂：

1. **字符级起步 vs 字节级起步**：工业 BPE（GPT-2 起）以 256 个字节为初始符号，任何 Unicode 文本都能编码，彻底无 OOV；教学版以字符起步，遇到训练时没见过的字符仍会失败。
2. **预切分**：tiktoken 先用正则把文本切成"词片"（数字、单词、标点分开），BPE 只在词片内部合并，避免跨词边界学到 "the quick" 这种无意义片段。
3. **规模**：cl100k_base 有 100,256 个 token（5 万条合并规则 + 字节与特殊符号），语料是整个互联网量级；我们的演示是 4 个词、10 轮合并。

核心循环则一模一样——你写的 30 行代码和 tiktoken 跑的是同一个算法。

## 第三章：WordPiece 与 SentencePiece —— 另外两种答案

### 3.1 WordPiece：把"频率最高"换成"提升似然最大"

WordPiece（Google，BERT 的分词器）的循环骨架与 BPE 相同——逐轮挑一对符号合并——区别只在**第②步的选择标准**：

```text
BPE:       选出现频率最高的对
WordPiece: 选 score = freq(pair) / (freq(a) * freq(b)) 最高的对
```

这个分数是点互信息的变体：分子是"两个符号一起出现的频率"，分母是"它们各自独立出现时期望的共现频率"。**分数高意味着这对符号的结合比偶然更紧密**——`("un", "##able")` 可能频率不如 `("e", "d")`，但 "un" 后面跟 "able" 的确定性远高于平均，这种"强结合"的片段语言学上更有意义。等价的说法是：每次合并选择能让训练语料的**似然（likelihood）提升最大**的那对。工程直觉：BPE 问"哪对最常见"，WordPiece 问"哪对最出乎意料地黏在一起"。

### 3.2 SentencePiece：把"分词"变成语言的无关前置

BPE 与 WordPiece 都假设输入**已经按空格分成词**——这对英语成立，对中文、日文、泰文等无空格语言直接失效。SentencePiece（Google，ALBERT/T5/LLaMA 系使用）做了两个关键改动：

1. **直接从原始字符流训练**：空格不被当分隔符，而是当作普通字符（用 `▁` 表示）参与合并。中文没有空格也能学，反过来还统一了所有语言的处理管线。
2. **支持 Unigram 算法**：与 BPE"从字符往上合并"相反，Unigram 从**大词表往下裁剪**——先假设一个很大的候选词表，用 EM 算法估计每个片段的概率，反复删掉"删掉它语料总似然下降最小"的片段，直到词表收缩到目标大小。

Unigram 相对 BPE 的独特能力是**一个句子可以有多种合法切分并各自带概率**，这让训练时可以采样不同切分做数据增强（subword regularization），提升鲁棒性；BPE 的切分是唯一确定的。

### 3.3 三种算法一页对照

| 维度 | BPE | WordPiece | Unigram（SentencePiece） |
|------|-----|-----------|--------------------------|
| 构造方向 | 自底向上合并 | 自底向上合并 | 自顶向下裁剪 |
| 选择标准 | 共现频率最高 | 似然提升最大（互信息） | 删除后总似然下降最小 |
| 切分结果 | 唯一确定 | 唯一确定 | 可概率采样多种切分 |
| 典型使用者 | GPT 系（tiktoken） | BERT | T5、LLaMA（经 SentencePiece） |
| 对无空格语言 | 需字节级兜底 | 需预处理 | 原生支持（空格即字符） |

## 第四章：tiktoken 实战 —— TokenCounter

### 4.1 中英 token 效率差异：实测数字

先用 tiktoken 看看真实世界的 token 长什么样（cl100k_base，GPT-4/3.5 的词表）：

```text
'unbelievable'  -> 3 tokens: ['un', 'belie', 'vable']
'tokenization'  -> 2 tokens: ['token', 'ization']
'你好，世界'     -> 6 tokens（部分汉字被拆到字节级）
```

一句英文与它的中文翻译对比，差异是数量级的：

```text
英文 "The quick brown fox jumps over the lazy dog": 43 字符 ->  9 tokens
中文 "敏捷的棕色狐狸跳过了懒惰的狗":                 14 字符 -> 27 tokens
```

**同样一段信息，中文消耗的 token 约是英文的 3 倍**（cl100k_base 下）。原因：词表训练语料以英文为主，汉字覆盖面不足，许多汉字要退回字节级编码（一个 UTF-8 汉字 3 字节，最差情况 1 字 = 2~3 tokens）。新一代词表在明显改进——o200k_base（GPT-4o）下同一句中文从 27 tokens 降到 16，`你好，世界` 从 6 降到 3。对成本与上下文窗口规划的直接推论：**中文场景的 token 预算要打英文的 2~3 倍余量，且新模型对中文更便宜**。

### 4.2 TokenCounter：精确计数 + 体面降级

实现位于 `../源码/smart-research-agent/smart_research_agent/llm/tokenizer.py`。三个方法对应三个工程问题：

```python
counter = TokenCounter()
counter.backend                        # "tiktoken"（本机实测）或 "fallback"
counter.count_tokens("你好世界", "gpt-4o")   # 按模型的 encoding 精确计数
counter.count_messages(messages)       # 一组 chat 消息 + 每条 4 token 元数据开销
counter.estimate_cost(prompt, "gpt-4o-mini", expected_completion_tokens=100)
```

设计上值得讲的点：

- **模型名 → encoding 的显式映射**（`MODEL_TO_ENCODING`）：`gpt-4o*` 用 o200k_base，更早的模型用 cl100k_base，未知模型回退 cl100k_base 而不是报错——词表错一点不影响"预估"，报错却会阻断流程。`count_messages` 的每条 4 token 开销沿用 OpenAI 官方 cookbook 的口径（角色标记与分隔符），余量规划足够准。
- **降级是功能不是异常**：`_load_encoding` 把 import 失败、词表下载失败等一切异常吞掉返回 `None`，计数自动落到 `estimate_tokens_chars`——CJK 字符按 1 token/字、其余按 4 字符/token 的中英感知估算。`backend` 属性把当前路径**显式暴露**，教程和测试都能断言自己走在哪条路上。对比 day005 `mock.py` 的"全文 4 字符 1 token"：那个估算对中文低估 3 倍以上，兜底的 `estimate_tokens_chars` 修正了这一点。
- **成本预估在调用发生之前**：`estimate_cost` 直接消费 day032 `DEFAULT_PRICE_TABLE` 格式的价格表，返回明细字典（输入/输出各多少 token、各多少钱、合计），模型不在价格表中抛 `KeyError`——与 `CostTracker.record` 同款"宁可报错不可漏算"策略。

```python
def estimate_cost(self, prompt_text, model, price_table=None, expected_completion_tokens=0):
    ...
    prompt_tokens = self.count_tokens(prompt_text, model)
    price = table[model]
    input_cost = prompt_tokens * price["input"] / 1000.0
    output_cost = expected_completion_tokens * price["output"] / 1000.0
    return {"prompt_tokens": prompt_tokens, ..., "total_cost_usd": ...}
```

### 4.3 与 CostTracker 的分工：事前预估 vs 事后记账

现在工具链闭环了，两个工具各管一段时间轴：

```text
调用前: TokenCounter.estimate_cost  → 这段话大概多少钱？超预算就压缩/换模型
调用中: LLM.chat                    → 真实生成
调用后: CostTracker.record_from_llm → 按真实 usage 记账归因（day032）
```

预估与记账用同一份价格表、同一种 token 计数口径，事前预算与事后账单才能对得上——这是"可观测性"在成本维度上的完整形态。

## 第五章：token 数 × 上下文窗口 × 成本 —— 三个实际推论

1. **上下文窗口按 token 计，不按字符计**。128K 窗口对英文是约 9.6 万词，对中文只有约 4~5 万字。RAG 系统塞检索结果（day020）时，中文场景的截断点比直觉早得多——`count_tokens` 是塞之前必做的检查。
2. **成本 = token 数 × 单价，单价输出远高于输入**。day033 解释了输出更贵的原理（串行解码）；今天有了精确计数，`estimate_cost` 能在调用前把"这条提示词 + 预计回复"折成美元数字。
3. **max_tokens 设小的省钱思路对中文尤其危险**。中文回答的 token 消耗是英文的 2~3 倍，按英文经验设的 max_tokens 会把中文回答拦腰截断——截断的 JSON 无法解析，Agent 被迫重试，重试的成本远超省下的输出 token（day033 习题第 8 题的"省小钱亏大钱"在中文场景被放大）。

### 5.4 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| subword 分词取代词级/字符级 | 词表大小、序列长度、OOV 三者不可兼得，subword 是甜点位 | 第一章 |
| BPE 贪心合并最高频对 | 常见片段自然进入词表，OOV 是副产品式解决 | `train_bpe` 核心循环 |
| 词尾标记 `</w>` | 词中/词尾的同一片段语义角色不同 | `END_OF_WORD` |
| 合并规则按序套用 | 规则顺序 = 构词法优先级 | `encode` |
| 并列时取字典序最小者 | 训练结果与遍历顺序无关，测试可精确断言 | `train_bpe` 的 `sorted` key |
| WordPiece 用似然提升选对 | "结合出乎意料地紧密"的片段更有语言学意义 | 第三章对照表 |
| SentencePiece 空格当字符 | 无空格语言（中日泰）无需预处理 | 3.2 节 |
| 未知模型回退 cl100k_base | 预估场景容错优先于精确 | `encoding_name_for` |
| tiktoken 失败自动降级字符估算 | 计数功能永不可用词表缓存绑架 | `_load_encoding` / `fallback` |
| CJK 按 1 token/字估算 | 修正"4 字符 1 token"对中文的 3 倍低估 | `estimate_tokens_chars` |
| 模型不在价格表抛 KeyError | 宁可报错不可漏算（与 day032 同策略） | `estimate_cost` |
| 预估与记账共用价格表 | 事前预算与事后账单口径一致 | `DEFAULT_PRICE_TABLE` |
