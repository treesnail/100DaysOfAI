```text

② 精度   把权重从 32 位压到 8/4 位   —— 省显存、花精度
```

三个问题：

1. **缓存为什么不改变结果？** 因为它存的 K/V 与整段路径用的是**同一批数**——

## 第一章：从"跑得通"到"跑得省"

### 1.1 前十六天各交出了一件事，今天是第一次**在推理上做减法**

```text
day079   三个子层拼成一个块          回答"一块怎么造"
day080   把那个块复制 N 份           回答"一摞怎么接"

```

前十六天一直在**加法**（加层、加头、加数据、加接口），今天第一次**做减法**。
而减法有一个与前十六天完全不同的性质：

```text
做加法时    错了会报错，或者至少指标会变差
做减法时    错了**什么都不报**——结果只是"偏了"或"慢了一点"
```

因此今天每一条读数都带**方向**（`higher` / `lower` / `neutral`），
而"越大越好"这种话一句都不写。

### 1.3 四条纪律

```text
① 三笔账必须能被逐项相加    权重 + 缓存 + 激活 = 总量；Σ 每步增量 = 总缓存
```

因为它有一个**方向**；而"误差很小"这种话是无法被反驳的。

## 第二章：缓存里存的是什么

### 2.1 存的不是 hidden state，而是投影之后的 K/V

```python
keys[index]   = project(ln_1(x), w_key)      # (T, hidden)，**已投影**
values[index] = project(ln_1(x), w_value)
```

存**投影结果**而不是归一化之后的输入，是这一课最省事的一处收益：
每步只投影**新的一行**（`(1,h) × (h,h)`），而不是把 T 行再投影一遍。

它带来第二条纪律：**归一化之后才投影**（pre-LN 块里注意力吃的是 `ln_1(x)`）。
在归一化之前缓存，形状一模一样、数值全变——而它只在多层堆叠后变得明显。

### 2.2 prefill 就是一次普通的整段前向

```text
prefill     把提示词一次算完，顺手把每一层的 K/V 存下来
decode      每次一个 token：每层投影一行、注意力读缓存、把新的 K/V 追加进去
```

因此 prefill 的输出必须与**不缓存时**的整段前向**逐位相同**——
这条等式是"我的缓存接对了"的最强证据。本包的写法是"两件事共用同一个 `normed`"：

```python
_normed, keys, values = _norm_and_project(card, weights, index, current)
for row_k, row_v in zip(keys, values, strict=True):
    cache.append(index, row_k, row_v)
current = run_one_block(card, weights, index, current, causal=card.causal)
```

缓存里的行与整段路径里用到的行**来自同一次投影**，因此"逐位相同"不是巧合。

### 2.3 缓存的账：`2 · L · T · h · bytes`

```text
缓存里存的是**两**张表（K 与 V），因此每一条缓存公式前面都有一个 2。
```

演示读数（`L=2, h=16, fp32` ⇒ 每步 256 字节）：

```text
第 0 步（prefill，位置 4）：缓存 1280 字节（+1280）
第 1 步（decode，位置 5）：缓存 1536 字节（+256）
第 2 步（decode，位置 6）：缓存 1792 字节（+256）
……
```

而"总步数 × 每步 == 总量"要在**几个长度上各核一次**：

```text
T=0   总量 0       == 每步 256 × 0
T=1   总量 256     == 每步 256 × 1
T=5   总量 1280    == 每步 256 × 5
T=16  总量 4096    == 每步 256 × 16
T=32  总量 8192    == 每步 256 × 32
```

只核一次的话，"把 K 与 V 只算了一份"（差一半）与"漏乘层数"（差一个整数倍）
都只会在**某一个长度**上碰巧对。

### 2.4 缓存不是"变快"，而是"换"

```text
打分次数        重算 T(T+1)/2 = 45     缓存 T = 9        （T=9）
显存            0                     2·L·T·h·bytes
```

45 与 9 都是整数，因此"省了多少"是一个能被算出来、而不是被形容出来的数。
但代价那一栏是**O(T) 的显存**：

```text
缓存把每步的计算量从 O(T) 降到 O(1)，代价是 O(T) 的显存。
⇒ 显存紧的时候，"缓存一定更好"是错的。
```

## 第三章：两条路径必须逐位相同

这是本课最强的一条对账，而它的强度来自"两条路径的算术**逐字相同**"：

```text
整段路径    hf_attention：K/V 从输入现场投影出来
缓存路径    attend_projected：K/V 从参数传进来（老的行来自缓存、新的行刚算出来）
```

七个阶段（投影 / 分头 / 打分 / 缩放 / softmax / 混合 / 拼回 + 输出投影）一个不少，
因此：

```python
cached, full = compare_with_recompute(card, weights, prompt_ids, new_token)
assert cached == full          # **逐位**，不是容差
```

它抓的错法有两类，而两类都**不会报错**：

```text
在归一化之前取 K/V     形状全对、数值全变
K 与 V 弄反            形状全对、数值全变
```

### 3.1 一条"没有掩码参数"的设计

`attend_projected` 刻意**不接受掩码**：缓存路径上的每一次调用都发生在
"最后一个位置"，而它能看到前面所有位置——因果性由"缓存里只有过去"自动成立。

想给一个**中间位置**算输出（例如逐 token 的 prefill）请走整段路径——
day086 的 `block_causal_mask` 就是为那种情形准备的。
把两种情形混进同一个入口，就会出现"掩码给宽了没人报错"这一类问题
（day086 第 8 章那条教训的同一个形状）。

## 第四章：位置必须由缓存长度决定（本课最容易踩的坑）

### 4.1 第一版实现撞上的那一下

decode 一步只喂**一个** token。第一版实现复用了 day086 的 `embed_tokens`，
而那个函数按行内下标编号位置：

```python
position_rows = gather_rows(weights.position, tuple(range(len(row))), name="position")
#                                                      ↑ 一步只有一行 ⇒ 永远是 (0,)
```

于是这个新 token 被当成**位置 0**。形状完全合法、不报错，
而这一步的输入**整块被换掉了**（本机实测：位置 5 与位置 0 的嵌入最大差 `3.658558e-01`），
两条路径的 logits 立刻分家。

### 4.2 修法：把"位置"变成一个必须显式给出的参数

```python
def _embed_at(card, weights, token_id, position):
    if not 0 <= position < card.positions:
        raise CacheError(f"位置 {position} 超出位置表长度 {card.positions}：本包不静默回绕、也不截断。")
    row = gather_rows(weights.word, (int(token_id),), name="word")
    offset = gather_rows(weights.position, (position,), name="position")
    ...
```

而那个 `position` 来自**缓存长度**：

```python
position = cache.length          # ← 它就是"你在第几位"
```

这条纪律在真实实现里的说法是"**缓存必须带一个 `position_ids`**"。
本课把它写成一个只服务于单行的函数，是因为"一行"与"一整段"在这里**必须分开**——
共用一个入口正是那个 bug 的来源。

## 第五章：量化只有两件事，打包不是第三件

```text
① 定标     找一个 scale（对称）或 scale + zero（非对称），把浮点映射到整数格
② 取整     q = round(x / scale) —— **误差只发生在这一步**
③ 打包     int4 两个数挤进一个字节 —— **无损的位运算**，一位都不丢
```

把"打包"和"取整"混在一起说，就会出现"4 位量化精度是 8 位的一半"这种话——
而真正决定精度的是**格数**：8 位 256 格、4 位 16 格。

### 5.1 两条定标式子

```text
对称（absmax）      scale = max|x| / (2^(b-1) − 1)      0 精确映到 0，没有零点偏移
非对称（zero_point） scale = (max − min) / (2^b − 1)     把动态范围用满，0 要靠 zero 找回来
```

非对称那一支的写法是"先平移再定标"：`q = round(x/scale) + zero`，
然后**把格号夹在 `[0, 2^b-1]` 内**。夹哪一个很重要：

```text
夹的是"格号"（x̂ = (q − zero)·scale 里的那个 q），而不是"格号减去零点"——
后者在区间不跨 0 的时候会整体错位一个零点（形状全对、数值全偏）。
```

`zero` 于是**可以是负的**——当整个区间都在 0 的同一侧时（例如权重全是正数），
0 本来就不在这个动态范围里。本课在演示里印了这一个读数：

```text
手算锚点（对称、一行 1.0 / −0.5 / 0.0）：
  scale = 7.874e-03 = 1/127 ⇒ 格号 [127, -64, 0]
  非对称（一行 0.5 / 1.5 / 2.5）：格号 [0, 128, 255]、zero = −64（**负的，且正确**）
```

### 5.2 一条可推导的上界（今天新出现的一类判据）

```text
|x − x̂| = |x − round(x/scale)·scale| ≤ 0.5 · scale = scale/2
```

它不是经验，是推导。它有**两条前提**，而两条都要当场检查：

```text
前提 ①  每个元素都落在 [-max_abs, max_abs] 内   ⇒ 出现 inf/nan 时前提就破了
前提 ②  scale ≠ 0                             ⇒ 整块同值时 scale = 0（本包当场拒绝）
```

第 ② 条值得单独说：`scale = 0` 出现在**整块权重都是同一个值**的时候
（例如一个刚初始化、或者被剪枝剪空的层）。那时反量化会把整块还原成 0，
而"误差很大"与"这一层本来就没东西"读起来不一样——因此本包在**定标**那一步就拒绝。

### 5.3 判据必须分两类

前十七天的判据都是"两个数相等"，今天多了一类"实测 ≤ 上界"。
本课的 `CrossCheck` 因此多了一个字段：

```python
@dataclass(frozen=True)
class CrossCheck:
    reading: float | int
    expected: float | int
    exact: bool = True
    upper_bound: float | None = None      # ← 有它时判据是 "≤"，没有时才是 "=="

    @property
    def passed(self) -> bool:
        if self.upper_bound is not None:
            return float(self.reading) <= float(self.upper_bound) + 1e-12
        if self.exact:
            return self.reading == self.expected
        return abs(float(self.reading) - float(self.expected)) <= 1e-12
```

把两类混成一个判据的后果是：一个**实测恰好为 0** 的读数（因为输入全是 0）
会在"相等"那一支里通过，而它其实什么都没证明。

### 5.4 粒度买精度、位宽买空间

```text
per_tensor   整块共用一个 scale ⇒ 一个离群值抬高所有人的台阶
per_channel  每一行一个 scale   ⇒ 离群值只抬高它自己那一行
```

演示读数（样本**带离群值**：只有一行有一个放大 80 倍的元素）：

```text
int8  absmax     per_tensor 8.016e-04 vs per_channel 4.143e-04 ⇒ 1.9 倍
int8  zero_point per_tensor 4.179e-04 vs per_channel 1.984e-04 ⇒ 2.1 倍
int4  absmax     per_tensor 1.605e-02 vs per_channel 7.427e-03 ⇒ 2.2 倍
对照（每行分布相同的权重）：int8 的收益只有 1.2 倍
```

三条值得单独指出的：

```text
① 这个收益只在**行与行的动态范围差得很大**时才出现（对照组只有 1.2 倍）
② 表里用**均值**误差而不是最大值：最大值被那个离群的那一行占住，
   而两种粒度下它都是同一行 ⇒ 最大值会把收益完全掩盖
③ 粒度与位宽不能互换：粒度买精度、位宽买空间
```

第 ① 与 ② 条都是**被量出来**的，而不是想出来的——这也解释了
`study.skewed_matrix()` 为什么必须专门造一份带离群值的样本。

## 第六章：int4 的打包是无损的

```text
int4 的 4 位装不满一个字节，因此它**必须**打包（两个数一个字节）。
顺序固定：先低 4 位、再高 4 位。
```

负数的处理是这一族最容易错的地方：

```text
同一个字节 120 → 有符号解出 0、无符号解出 120     （补码的两个端点）
```

因此"样本里必须出现 `-8` 与 `7`"是一条纪律：**"负数的低 4 位会串到高位"
这类错误只在负数上出现**——用一组非负样本试，永远试不出来。

而打包本身**无损**：它省的是**空间**，不是精度。精度损失发生在 `round` 那一步。

## 第七章：批的账

```text
静态批       把请求按 max_batch 分好组，一组一起跑到底 ⇒ 总步数 = Σ 每组的最长
连续批       一条算完就把它那个位置让给新的一条
```

演示读数（长度 `[9, 2, 5, 1, 7]`、批大小 3）：

```text
组 [0, 1, 2]：宽 9 ⇒ 9 步；组 [3, 4]：宽 7 ⇒ 7 步
静态批 16 步 / 连续批下界 9 步 | 槽位效率 50.0%（有效 24 / 机会 48）
连续批的处理表：10 步 × 3 槽位 = 30 | 占用 24（80.0%）
每条请求在表里出现的次数 [9, 2, 5, 1, 7] == 各自的长度 [9, 2, 5, 1, 7] ✓
```

### 7.1 三个必须写下来的细节

```text
① "连续批的总步数 = 最长的那条"只在 len(lengths) <= max_batch 时成立；
   请求比槽位多时实际步数会更长（上面 10 > 9 就是这一条）
② 每一条请求在表里必须出现**恰好它的长度**次——这是"它每一步都在算"的唯一证据
③ 槽位效率的分母是"总步数 × max_batch"（**有机会**算的 token 数）
```

第 ② 条是本课抓到的一个真实错误：第一版处理表忘了把 `remaining` 减 1，
于是**没有一条请求会结束**——表看起来完全合法（槽位都占着、步数也对），
而第 5 条请求只出现了 6 次而不是 7 次。抓住它的正是这条不变量。

### 7.2 槽位效率的两个分母

```text
BatchPlan.efficiency    有效 token / (步数 × max_batch)      按"这一批总共算了多少"
occupancy(schedule)     占位槽位 / 总槽位                     按"每一步有几个位置有人"
```

两者之差就是"请求在跑但位置被填"。两个数都要印，因为它们的**分母不是同一件事**。

## 第八章：预算的账

```text
权重       参数量 × 每元素字节          —— 与序列长度**无关**
缓存       2·L·T·h·bytes               —— 与序列长度**线性相关**
激活       一次前向最宽的那个中间张量    —— 与批大小**线性相关**
```

第三样的口径必须**写死**，否则它会变成一个可以随便取值的数：

```text
换成 hidden        会小 ffn/h 倍
换成"所有层一起"   会大 L 倍
```

两个方向的差别都是数量级，而三种取法看起来都"合理"。

演示读数（同一个 64 KiB 预算、同一个 32 个位置）：

```text
fp32  | 权重 46144 + 缓存  8192 + 激活  8192 =  62528 / 65536 ✓ | 余量  3008 | T_max 37
fp16  | 权重 23072 + 缓存  4096 + 激活  4096 =  31264 / 65536 ✓ | 余量 34272 | T_max 165
int8  | 权重 11536 + 缓存  2048 + 激活  2048 =  15632 / 65536 ✓ | 余量 49904 | T_max 421
int4  | 权重  5768 + 缓存  1024 + 激活  1024 =   7816 / 65536 ✓ | 余量 57720 | T_max 933
```

### 8.1 一个能被整除算出来的答案

缓存与激活都线性于序列长度，因此"预算内最长能做多少 token"是一个一次方程的整数解：

```text
weights + T·(batch·ffn·bytes + 2·L·h·bytes) ≤ budget
⇒ T_max = ⌊(budget − weights) / (batch·ffn·bytes + 2·L·h·bytes)⌋
```

而且**两侧都要查**：

```text
fp32 下最多 37 个位置：T=37 合计 65088 ✓、T=38 合计 65600 ✗
fp16 下最多 165 个位置：T=165 合计 65312 ✓、T=166 合计 65568 ✗
int8 下最多 421 个位置：T=421 合计 65424 ✓、T=422 合计 65552 ✗
int4 下最多 933 个位置：T=933 合计 65480 ✓、T=934 合计 65544 ✗
```

只查"放得下"的话，一个**偏小**的最大值也会通过——而"保守"与"算错"读起来一样。

### 8.2 为什么三项必须能被逐项相加

因为放不下的时候要能回答**"是哪一项放不下"**：

```text
权重放不下       ⇒ 换更小的精度 / 换更小的模型
缓存放不下       ⇒ 缩短上下文 / 换能分页的路线
激活放不下       ⇒ 减小批大小
```

三种出路完全不同。把总量当成一个数（而不是三项之和）的后果是：
"显存不够"这句话没有任何下一步动作，而**偷偷把上下文截短**
会看起来像一个正常的选择。

## 第九章：七条性质与三类对账

```text
逐位（==）    缓存路径 vs 整段路径（prefill 与 decode 两条）、int4 打包往返
整数相等      每步字节增量 vs 2·L·h·bytes、预算三项之和、占用槽位数
上界判定      反量化误差 ≤ scale/2                     ← **今天新出现的一类**
两侧都查      预算里 T_max 放得下、T_max+1 放不下
```

三条对账，两条跨天：

```text
缓存 vs 整段      cache.compare_with_recompute ↔ day086 的 forward.logits（**逐位**）
prefill vs 整段    cache.prefill 的 hidden states ↔ day086 的 hidden_states（**逐位**）
量化 vs 上界       量化 → 反量化后的实测误差 ↔ scale/2（**上界**，不是相等）
```

今天的七条性质里**没有一条会走到"不适用"**——这与前一天不同。
理由是：这一课的每一条判据都只依赖"卡片 + 权重"，而它们在任何一张卡片上都有定义
（前一天的"参数量对账"需要一份**库读数**，而库读数只有两个模型有）。

### 9.1 六张表

```text
缓存步表      每一步的缓存字节数（prefill 一步到位、之后每步一个固定增量）
缓存公式表    长度 × 每步 == 总量（五个长度各核一次）
量化表        2 个位数 × 2 个方案 × 2 种粒度 = 8 行的误差与 SNR
粒度收益表    只换粒度：同样位数下两种粒度的均值误差之比
批表          静态 vs 连续的步数、占用率与吞吐（含逐行的处理表）
预算表        四种精度下的三项之和、余量、T_max
```

## 第十章：失败族的第三次换理由

```text
day075~081   有手写反向            ⇒ 有 GradientError 那一族
day082~087   没有手写反向          ⇒ 这一族连续缺席六天
```

今天的理由比前两天**更硬**：

```text
量化是不可微的：round(x/scale) 的导数几乎处处为 0、在跳变点不存在。
真实世界的做法是前向用量化权重、反向用直通估计（STE）——而那是**训练**的事。
本课只做推理，因此连"该不该用 STE"都不需要回答。
```

而今天新增的四个族，各自要改的东西都不同：

```text
CacheError    "这一次的生成策略不成立"      缓存满了 ⇒ 换容量、换更短的上下文
QuantError    "这份数据配这个方案不成立"    整块同值 ⇒ scale = 0，除了 0 什么都没有
BudgetError   "这一次放不下"                换卡、换精度、换路线——**不是偷偷截断上下文**
AssemblyError "两份各自的合法东西拼不起来"  缓存与卡片不是同一次装载
```

`BudgetError` 值得单独说一句：把它归进 `ParameterError` 的后果是——
有人会去把 `context_length` 偷偷调小，而"上下文被截断"与"上下文够用"
在生成结果上**不一定看得出来**。

## 第十一章：一个真实的命名坑

包入口再导出一个叫 `quantize` 的函数，会把子模块 `inference_optim.quantize`
**同名遮掉**：

```python
from smart_research_agent.inference_optim import quantize   # ← 拿到的是函数，不是模块
quantize.measure(matrix, spec)                              # AttributeError: 'function' object has no attribute 'measure'
```

因此本包把那个函数叫 `quantize_matrix`。这不是风格问题：
Python 的 import 系统在 `from package import name` 时**优先取包的属性**，
而 `__init__.py` 里 `from .quantize import (...)` 那一行会把子模块的属性覆盖掉。

同源的还有一处：`cache` 与 `batching` 这两个模块名**没有**被同名导出，
因此它们可以照常用 `from ... import cache as cache_module`。
本课的测试文件里有一条断言看着每个子模块的 `__all__` 都是包导出集合的子集——
它抓的是"某个名字被重复导出"这一类问题。

## 第十二章：边界与后续

### 12.1 五条边界（**本课明确不承诺的事**）

```text
① 本包复现的是账（字节数、误差上界、吞吐计数），不是真实推理引擎的性能
② 本包不做真正的 8 位/4 位算术：量化是"量化 → 反量化"，用浮点算出误差
③ 本包不安装、也不调用 bitsandbytes / accelerate
④ 本包的批处理是**静态**批；连续批处理只在计数层面被算出来
⑤ 本包的缓存不跨请求复用（没有前缀共享），也没有分页
```

第 ② 条是这一课最需要说清的一条：**它能量误差，不能量真实的加速比**。
真实的 int8 kernel 之所以快，是因为它在**整数**上算——而本课把
"量化 → 反量化"放在浮点上，因此只留下误差那一半。

### 12.2 两个悬念（它们都是推理优化里最赚钱的两块）

```text
连续批        真正的收益来自"不等"——而本课只算出了"省了几步"
前缀共享      多条请求共用同一段前缀时，缓存可以只存一份——本课不做
```

### 12.3 与后续的接缝

```text

        "为什么这个模型在我的卡上跑不起来"，答案就是那三项之和
day099  结业项目：预算表会直接变成部署前的第一张检查单
```

今天最值得带走的三句话，与前十七天那几句对着看：

```text
day085  "分头"发生在**投影内部**                     —— 读源码读出来的结构事实
```
