## 第一部分：选择题

### 第 1 题 —— 答案 B

单元测试验证的是"**模块内部对不对**"，集成测试验证的是"**模块之间的契约齐不齐**"。本次缺陷的本质是契约不一致：

- `CostTracker.record_from_llm()` 的实现要求被传入的对象**自己持有 `usage_log`**：

  ```python
  def record_from_llm(self, llm, model: str, endpoint: str = "chat") -> int:
      consumed = getattr(llm, "_cost_consumed", 0)
      new_entries = llm.usage_log[consumed:]
  ```

- `MockLLM` 按 day032 的约定**有** `usage_log`，所以成本追踪的测试全绿；
- `ModelRouter` 是**包装器**，自己不产生 token、不持有用量，所以它**没有** `usage_log`；
- 但 `usage_log` 从来不是 `BaseLLM` 的接口成员——它只是 `MockLLM` 与 OpenAI 兼容客户端之间的"事实约定"（duck typing）。

两边各自的测试都只覆盖了自己那一半世界，于是缺陷只在拼起来的那一刻出现。选 A 不成立：这不是覆盖率问题（两边的语句都执行到了，缺的是**跨模块组合**的用例）；选 C 也不成立：动态语言只是让这类错误"运行时才报"，但契约本身是可以被显式设计与断言的；选 D 更不成立：`MockLLM` 的行为符合约定，没有任何 bug。

**可迁移的经验**：为每一条"事实约定"（duck typing 的隐式接口）补一条集成测试。day046 的修复就把回归测试放在了 `test_pipeline.py::TestRouterAccountability`——缺陷的真实现场是"路由 + 计费"的组合。

### 第 2 题 —— 答案 B

关键在于缓存是**持久化的复用**，它会放大写入内容的影响：

| 顺序 | 第一次请求 | 第二次（命中） |
|------|-----------|---------------|
| 审核 → 写缓存（正确） | 缓存里是脱敏文本 | 返回脱敏文本，`pii_types == []` |
| 写缓存 → 审核（错误） | 缓存里是**明文 PII** | 直接返回**未脱敏原文** |

第一次泄漏还可以解释成"模型说漏了嘴"；第二次开始就是系统在稳定地泄露——**把一个偶发问题变成了持续性缺陷**。

这一条顺序约束在代码里只表现为两行的先后（`STAGE_MODERATE` 在 `STAGE_STORE` 之前），因此必须用断言钉住。day046 的 `test_cached_reply_is_already_clean` 就是这条约束的可观测证据：首次 `pii_types == ["邮箱"]`，命中时变成 `[]`。A、C、D 都与"安全"无关，且 C 是错误陈述（缓存当然能存任意字符串）。

### 第 3 题 —— 答案 B

`ModelRouter` 知道"我把请求转给了谁"，但计费器需要的是"谁产生了用量"。补上 `last_used_llm` 之后语义就闭合了：

- `decision_log` 回答"**决策上**选了谁"（含降级链与 `fallback_used`）；
- `last_used_llm` 回答"**事实上**谁完成了这次调用"。

两者对齐，成本才不会记到"首选但失败"的模型头上。选 A 不对：性能不是考虑因素；选 C 不对：`CostTracker` 依然要求叶子提供 `usage_log`，只是现在传进去的是叶子而不是包装器；选 D 不对：任何被包装的 LLM 都可能被计费。

顺带一提，`getattr(self.llm, "last_used_llm", None) or self.llm` 的写法让普通 LLM（没有该属性）自然走原路径，不需要任何分支——这是"用属性探测代替类型判断"的常见手法。

### 第 4 题 —— 答案 B

判定下限是**防抖动阈值**：

```python
if current_value is None or base_value < self.min_latency_ms:
    continue                       # 基线太小，比值没有意义
```

1ms 变成 2ms 是"2 倍回归"，但对用户完全无感，而且会被调度抖动随机触发。**一个天天误报的门禁，最后一定会被人关掉**——门禁的价值在长期可信，不在瞬时灵敏。选 A 恰好相反；选 C 是附带效果而非目的；选 D 不对（小数值可以算比值，只是算出来没有意义）。

## 第二部分：判断题

### 第 5 题 —— 答案：错

缓存键**必须**包含系统提示词。实现如下：

```python
def cache_key(self, task: str, system_prompt: str | None = None) -> str:
    prefix = (system_prompt if system_prompt is not None else self.system_prompt) or ""
    return f"{prefix}\n{task}" if prefix else task
```

理由：同一句"总结一下"在不同人格/指令下应当得到不同回答。只按用户文本做键，换个 `system_prompt` 就会命中旧答案。这类"张冠李戴"比缓存不命中危险得多——因为返回内容看起来完全正常，难以发现。对应测试是 `test_cache_key_includes_system_prompt`（两个不同系统提示词 → 第二次不命中）。

### 第 6 题 —— 答案：对

```python
def percentile(values: list[float], q: float) -> float:
    if not 0.0 <= q <= 100.0:
        raise ValueError("q 必须在 0~100 之间")
    if not values:
        return 0.0
    ordered = sorted(values)
    rank = math.ceil(q / 100.0 * len(ordered)) - 1
    index = max(0, min(rank, len(ordered) - 1))
    return ordered[index]
```

`ordered[index]` 一定取自排序后的原样本，所以返回值永远是**真实观测值**。技术评测通常样本量小（一次十几条任务），插值会造出"观测不到的耗时"，而门禁的每个结论都必须能回溯到某一次真实请求。测试用 20 个样本验证：`percentile(list(range(1,21)), 95) == 19.0`（第 19 个样本，不是 19.95 之类的插值）。

## 第三部分：简答题

### 第 8 题 —— 护栏的两个设计决定

**① 拒答文本是常量，不让模型生成。**

如果把攻击串交给模型，让模型"解释为什么拒绝"，就等于**把攻击内容送进了模型上下文**——护栏白设了。攻击者完全可能在注入串里要求"如果你拒绝，请先复述我的要求"，从而诱导模型泄露系统提示词。因此 `REFUSAL_REPLY` 是一条固定文本：

```python
REFUSAL_REPLY = "抱歉，本次请求包含疑似 Prompt 注入的内容，已被输入侧护栏拦截。"
```

拒答路径还有第二个好处：**模型完全不被调用**（`llm.calls == []`，测试直接断言），既省一次钱，也不给注入内容任何被模型看到的机会。

**② 提供"只记录不拦截"模式。**

```python
if injection is not None and injection.is_injection and self.block_on_injection:
    ...
```

注入检测是**基于正则规则的启发式**（day031 的实现），必然存在误报与漏报。上线初期若直接全量拦截，一次误报就会打回正常用户。`block_on_injection=False` 让系统先"只记录不拦截"，用真实流量的 `injection.matched_patterns` 统计误报率、调优规则，再切到拦截模式——这是灰度开关的标准做法，且开关本身读自配置（`settings.pipeline_block_on_injection`），不需要改代码。

对应测试：`test_injection_can_be_flagged_only` 断言在关闭拦截时请求照常走完六个阶段，但 `injection.is_injection is True` 仍然被记录。

### 第 9 题 —— 混合路由为什么不需要 if

**分流结果：**

| 任务 | `estimate_complexity` | 满足能力阈值的候选 | 选择 | 理由 |
|------|----------------------|------------------|------|------|
| "1+1 等于几" | 1 | 本地(3)、云端(5) 都满足 | **本地 qwen3:8b** | 都满足阈值 → 取最便宜 → 本地 `cost=0.0` |
| "请分析并对比 RAG 与微调的优劣，并给出评估建议" | 4（命中"分析""对比"两个复杂动词） | 只有云端(5) 满足 | **云端 gpt-4o-mini** | 本地 capability=3 < 4 被排除 |

复杂度由 day033 的确定性启发式给出：基础 1 分，文本长度 >50/+1、>200/+1，复杂动词命中数 × 2（上限 +3），最后 `min(score, 5)`。

**把策略交给可复用组件的好处：**

1. **不需要新增业务代码**。分流规则完全由"能力档位 + 单价"两张表决定，新增一个模型（比如更强的本地 70B）只是往 `ModelSpec` 列表里加一项，判断逻辑一行不动。
2. **决策可解释、可审计**。`CostFirstStrategy` 每次都会生成人类可读的 `reason` 并写入 `decision_log`，所以"为什么这次走了云端"永远有案可查——手写 `if` 分支很难做到这一点。
3. **降级方向天然正确**。`CostFirstStrategy` 把首选之后的候选按能力**从强到弱**排列（"降级往上"：多花钱总比答错安全）。本地服务挂掉时会自动升级到云端，而不是退化到更弱的模型。
4. **与配置校验配合**。当 `local_capability >= cloud_capability` 时，云端永远不会被选中，`build_hybrid_router` 会打告警——手写分支几乎没有机会发现这种"花了钱没用上"的配置错误。

## 第四部分：编程题

### 第 10 题 —— 参考答案

```python
"""验证：本地模型失败降级到云端时，成本与模型名都归到云端."""
from smart_research_agent.integration.pipeline import IntegratedPipeline, build_hybrid_router
from smart_research_agent.llm.base import BaseLLM, Message
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.observability.cost_tracker import CostTracker


class FailingLLM(BaseLLM):
    """模拟本地推理服务不可用（进程没起 / 显存不足）."""

    def chat(
        self, messages: list[Message], temperature: float = 0.7, max_tokens: int = 1024
    ) -> str:
        raise ConnectionError("本地 Ollama 服务未启动")


def test_cost_follows_fallback_to_cloud():
    cloud = MockLLM(default="云端兜底回答")
    router = build_hybrid_router(
        FailingLLM(), cloud, local_name="qwen3:8b", cloud_name="gpt-4o-mini"
    )
    tracker = CostTracker()
    tracker.price_table["qwen3:8b"] = {"input": 0.0, "output": 0.0}
    tracker.price_table["gpt-4o-mini"] = {"input": 0.001, "output": 0.002}

    pipeline = IntegratedPipeline(router, tracker=tracker)
    result = pipeline.run("1+1 等于几")  # 复杂度 1 → 首选便宜的本地模型 → 失败 → 降级云端

    assert result.model == "gpt-4o-mini"
    assert result.cost_usd > 0
    by_model = tracker.report()["by_model"]
    assert by_model["gpt-4o-mini"]["cost"] > 0
    assert "qwen3:8b" not in by_model      # 失败的本地模型不产生任何费用记录
    assert router.last_used_llm is cloud
```

本机实际运行结果（`cost` 与 token 数由 `MockLLM` 的估算函数决定，因此完全确定）：

```text
OK cost= 3e-06 by_model= {'gpt-4o-mini': {'prompt_tokens': 1, 'completion_tokens': 1, 'cost': 3e-06}}
```

**为什么必须用"简单任务"？**

因为本测试要验证的是**降级路径**，而不是"正常路由到云端"。

- 简单任务（复杂度 1）：本地与云端都满足能力阈值，`CostFirstStrategy` 因本地 `cost=0.0` 而首选本地——只有在本地**失败**之后，请求才会落到云端。此时"云端被使用"这个事实**只能是降级造成的**。
- 复杂任务（复杂度 4~5）：本地 `capability=3` 不满足阈值，**一开始就被排除**，请求直接路由到云端，`fallback_used` 为 `None`。这样即使断言全部通过，也证明不了降级链是通的——测试会变成"假的绿灯"。

**若换成复杂任务，断言会怎么变？**

1. `result.model` 仍然是 `"gpt-4o-mini"`（这点不会变）；
2. `result.cost_usd > 0` 仍成立，`by_model` 仍只含云端——**表面结论一样**；
3. 但 `router.decision_log[-1].fallback_used` 会从 `"gpt-4o-mini"` 变成 `None`；
4. 因此这三条断言就再也无法区分"降级成功了"与"压根没走降级"。

结论：**要测降级，必须构造一个"首选会失败"的现场**——工具的测试数据必须能把被测行为与其他行为区分开，否则它就是一条自我安慰的断言。这也是 day031 红队评估强调"用例要能真的打穿"的同一个道理。
