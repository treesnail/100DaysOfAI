## 第一部分：选择题

### 第 1 题

**答案：B**

解析：安全性是**实测**出来的，不是声明出来的。Prompt 里写"禁止泄露系统提示词"是软约束——模型的服从是概率性的，一句构造精巧的注入（"忽略之前的指令……"）就可能绕过。安全性必须用攻击用例集实测检出率（这正是 day031 红队评估的核心）。A 是两大维度的正确定义；C 正确，成本 = 钱（token 折算）+ 时间（延迟分位数）；D 正确，维度是全集、权重由场景定（决策表的第一心法：先找否决项再排权重）。

### 第 2 题

**答案：B**

解析：这是模板方法模式的教科书应用。`run()` 冻结四步骨架（顺序、异常处理、汇总逻辑所有评估共享），子类只实现两个抽象方法：`execute`（怎么调被测对象）和 `score`（怎么打分）。收益是**复用与一致性**：day029 的 RAG 评估、day030 的 Agent 评估各自实现两个方法就拥有完整流水线，且所有评估的行为模型一致、报告格式一致。A 错，基类不改变执行性能；C 错，调用次数由评分器内部决定，与骨架无关；D 恰好相反——骨架把"数据集显式加载"固化下来，正是为了数据集可独立版本化、可冻结比较。

### 第 3 题

**答案：B**

解析：根本原理是认知上的不对称——**评估比生成容易**。判断"这份报告是否对比了至少 3 个框架"只需验证，写出一份优秀报告需要创造。人类如此，模型也如此，所以够强的模型当裁判在统计上可靠。A 错且危险：实践要求是裁判**不弱于**被测对象，而不是天然成立；用弱模型评强输出会系统性打低分。C 错：LLM 裁判有位置偏差、冗长偏差、自偏好三大已知偏差，必须显式缓解。D 错：裁判每次评估都消耗 token，这正是"能用规则判的不用模型判"的成本动机。

### 第 4 题

**答案：C**

解析：偏爱与出现顺序相关的答案是**位置偏差（Position Bias）**，标准缓解是**交换顺序各评一次**：两次结论一致才采信，或取两次平均。A 描述的是冗长偏差（分数随长度上升）的缓解；B 描述的是自偏好偏差（给自己的输出打高分）的缓解；D 的"输出 JSON"只解决解析问题，与位置无关。三大偏差与缓解手段要成对记忆：位置→换序重评，冗长→rubric 声明长度不加分，自偏好→异模型/盲评。

### 第 5 题

**答案：B**

解析：这是双重评估的第一原则——**按错误的确定性分层**：确定性契约问题（合法 JSON、必填字段、长度区间）用规则判定，100% 可复现、零 LLM 成本、毫秒级；语义问题（有用性、准确性）才交给模型。用模型判确定性问题，等于为每次评估付一次 LLM 调用的钱，还引入概率波动（这次判合规下次判不合规）。A、D 是附带好处而非根本理由；C 错，LLM 当然"看得懂" JSON，问题是用它判不值、不稳。这个原则与 day010 `parse_plan` 四道防线同构：越接近语义的检测越贵，能在外层拦下的别放进来。

## 第二部分：判断题

### 第 6 题

**答案：错**

解析：混淆了两件事。**同一次比较之内**，数据集必须冻结——今天 82 分、改动后 85 分，跑的是同一批用例，这 3 分才可信。但**跨时间**，评估集是活资产：每个线上 bad case 修复后必须进评估集（"事故变资产"），否则同一个坑会掉第二次。正确做法是**版本化演进**：用例集 v1.0 → v1.1（新增 10 条边界用例），每次评估报告记录用的是哪个版本。冻结的是"单次比较的基准"，不是"数据集本身"。

### 第 7 题

**答案：错**

解析：Prompt 评估只检查"指令本身写得好不好"（清晰、一致、无歧义），不保证"模型听懂了、产出好"。一个清晰度满分的 Prompt 也可能因为超出模型能力、或与任务不匹配而产出糟糕结果。两者的关系类似 lint 与单元测试：**Prompt 评估是廉价的预筛，端到端输出评估（day027）才是终审**。预筛能花小钱拦掉明显有毛病的 Prompt，但终审不可省略——质量最终由输出说了算。

### 第 8 题

**答案：对**

解析：先给理由再给分数，本质是把 CoT（思维链）用在裁判身上：显式推理过程约束了最终判断，分数显著更稳定、更少漂移。直接要分数等于让模型"凭直觉猜"，同一输出在不同上下文下可能差 2 分以上。工程上还有第二个好处：理由文本让分数**可审计**——低分用例能拿着理由去归因（是内容错了还是格式问题），理由也是调 rubric 的依据。实现细节：分数要求单独成行、格式固定（如 `分数: 4`），方便程序正则解析——又是"程序消费的 LLM 输出必须锁定格式"的老原则。

### 第 9 题

**答案：错**

解析：只存分数的质量日志无法归因——看到 case_17 得了 0.2 分，没有输入输出原文，你永远不知道是问题难、模型错还是裁判误判。**分数是索引，原文才是证据**，两者缺一不可。正确的顾虑方向是另外两条：① 原文可能含用户隐私，PII 脱敏必须在落盘前完成（呼应 day015 安全模块）；② 磁盘与保留策略用滚动/归档解决，而不是砍掉证据。顺带记住：选 JSONL 格式的原因之一就是行级容错与追加写友好，天然适合这种流水记录。

## 第三部分：填空题

### 第 10 题

**答案**：（1）**数据集**　（2）**执行（运行）**　（3）**评分（打分）**　（4）**汇总（聚合）**　（5）**bad case（失败案例）**

解析：四步流水线是 Harness 的模板方法骨架，顺序固定且理由充分：先加载（基准冻结、独立于代码）→ 再执行（被测对象跑一遍，子类实现 `execute`）→ 再评分（子类实现 `score`）→ 最后汇总（决策要均分、归因要明细，两者在汇总层分离）。用例来源排序的逻辑：真实 bad case 直接消灭已发生的线上问题，价值最高；人工边界用例覆盖想不到的长尾；happy path 防回归基本盘，价值最基础。只放 happy path 的评估集会退化成走过场。

### 第 11 题

**答案**：（1）**有用性**　（2）**准确性**　（3）**格式合规**　（4）**格式合规**　（5）**硬门槛**

解析：三维是 day025 四大维度在单次输出粒度上的具体化——有用性≈相关性，准确性≈正确性，格式合规是输出特有的契约检查（Agent 的输出常被下游程序消费）。格式合规是唯一纯规则可判的维度（合法 JSON、字段齐全、长度区间都是确定性问题），因此它归规则通道；有用性、准确性涉语义，归 LLM 裁判。"不合规直接 0 分"是**硬门槛**：它表达"这个维度具有一票否决权"，与"各维加权平均"是两种不同的合成策略——下游程序消费输出时格式错了内容再好也没用，硬门槛正是这种业务现实的数学表达，注意别和加权混用（加权后 0 分只是拉低均值，不叫否决）。

## 第四部分：问答题

### 第 12 题

**参考答案**：

**系统①：对外客服问答机器人**

- **一票否决项：安全性**。对外暴露意味着会被真实攻击者尝试注入、套话、诱导产出有害内容；一次泄露事故摧毁的是整个产品的信任，正确性再高也补不回来。
- **核心指标：相关性、正确性**（延迟为重要辅助）。客服场景用户最在意"有没有回答我的问题"（相关性），其次是答案对不对。
- **评估器组合**：规则通道必须在线——敏感词、PII 泄漏、注入检出都是确定性检查，零成本必须做满；LLM 裁判按 rubric 评相关性与正确性。
- **用例集要点**：注入/越狱攻击用例必含且占大头（否决项决定用例集结构）；含多轮上下文用例（客服天然多轮）；含"超出知识范围应拒答/转人工"的负例。

**系统②：内部批处理报告生成器（JSON 供下游消费）**

- **一票否决项：格式合规**。下游是程序不是人，JSON 缺字段、结构漂移直接让管道崩掉——内容再好也没用。
- **核心指标：正确性、成本**。报告内容要事实准确；批处理量大，token 成本敏感；**延迟几乎不敏感**（离线跑，慢点无所谓）。
- **评估器组合**：规则为主——schema 校验（JSON Schema 或字段断言）做一票否决；LLM 裁判**抽检**语义质量即可（不必每条都评，成本意识）。
- **用例集要点**：边界格式用例为主（嵌套结构、空值、超长输出、Markdown 代码块包裹的 JSON）；含事实性断言用例。

**共同要点**：先找否决项再排权重（顺序反了是本末倒置）；否决项决定"哪些评估器必须在线、用例集以什么为主"；评估器成本与被测场景匹配——② 可以抽检，① 的规则通道必须全量。

### 第 13 题

**参考答案**：

一条输出的旅程分五个环节（对照 Harness 四步骨架 + 日志落盘）：

1. **加载冻结数据集**：从版本化的 JSONL 黄金集读出用例（input/expected/tags）。**冻结的意义**在于可比性——本次与下次评估跑同一批用例，分数差才可归因于系统改动而非用例漂移；数据集独立版本化，每次报告记录所用版本。
2. **逐条执行**：`execute(case)` 调被测系统产出 output。Harness 通过抽象方法调用，不认识 Agent——换 RAG 链路只需换子类。
3. **逐条评分（双通道分工）**：规则通道判确定性契约问题（格式、长度、关键词），100% 可复现、零成本；裁判通道按 rubric 判语义问题（有用性、准确性），先理由后分数。分工原则是"能用代码判的绝不用模型判"——既是可靠性原则也是成本原则。
4. **质量日志落盘**：每条记录（输入、输出、各维分数、时间戳）追加一行 JSONL。它的**两个消费出口**：一是汇入评估报告，支撑"能否发版"的决策（分数不得低于基线）；二是低分记录成为 bad case 清单，回流到评估数据集与 Prompt 修订——事故变资产，评估集因此生长。
5. **汇总成报告**：各维均分、通过率、按 tags 分组、失败清单。决策发生在汇总层，归因发生在明细层。

**为什么换裁判后历史分数不可直接比**：裁判模型是评估系统的一部分，相当于度量衡本身。同一个输出，GPT-4 裁判可能给 4 分，换一个裁判可能给 3 分——分数差来自"秤"变了，而非系统变了。正确做法：评估报告中记录裁判模型版本；更换裁判时用同一冻结数据集重跑一遍，建立新基线，新旧基线之间只能间接折算，不能直接混排。这与"换数据集版本要重新建档"是同一个道理：**基准的任何组成部分变化，都意味着一次重新标定。**

### 第 14 题

**参考实现**：

```python
"""迷你评估 Harness：模板方法四步骨架的最小落地."""
import json
from dataclasses import dataclass


@dataclass
class EvalCase:
    id: str
    input: str
    expected: str


@dataclass
class CaseResult:
    case: EvalCase
    output: str
    passed: bool


def load_dataset(text: str) -> list[EvalCase]:
    """从 JSONL 文本解析用例集；坏行抛带行号的 ValueError."""
    cases = []
    for lineno, line in enumerate(text.strip().splitlines(), start=1):
        try:
            obj = json.loads(line)
            cases.append(EvalCase(id=obj["id"], input=obj["input"], expected=obj["expected"]))
        except (json.JSONDecodeError, KeyError, TypeError) as exc:
            raise ValueError(f"数据集第 {lineno} 行解析失败: {exc}") from exc
    return cases


def run(dataset: list[EvalCase], system) -> tuple[float, list[str]]:
    """四步骨架的执行+评分+汇总：逐条跑、按"包含 expected"判定、汇总通过率."""
    results = []
    for case in dataset:
        output = system(case.input)
        results.append(CaseResult(case=case, output=output, passed=case.expected in output))
    total = len(results)
    pass_rate = sum(r.passed for r in results) / total if total else 0.0
    failed = [r.case.id for r in results if not r.passed]
    return pass_rate, failed


def qa_system(question: str) -> str:
    return {"1+1 等于几": "2", "中国的首都是哪": "北京"}.get(question, "不知道")
```

```python
# tests/test_mini_harness.py
import pytest
from mini_harness import load_dataset, run, qa_system

GOOD_JSONL = (
    '{"id": "c1", "input": "1+1 等于几", "expected": "2"}\n'
    '{"id": "c2", "input": "中国的首都是哪", "expected": "北京"}\n'
    '{"id": "c3", "input": "火星的首都是哪", "expected": "奥林帕斯"}'
)


def test_load_dataset_parses_good_jsonl():
    cases = load_dataset(GOOD_JSONL)
    assert [c.id for c in cases] == ["c1", "c2", "c3"]
    assert cases[0].expected == "2"


def test_load_dataset_bad_line_raises_with_lineno():
    bad = '{"id": "c1", "input": "q", "expected": "a"}\n这不是JSON'
    with pytest.raises(ValueError, match="第 2 行"):
        load_dataset(bad)


def test_run_all_pass():
    cases = load_dataset(GOOD_JSONL)[:2]  # 只取两条能答对的
    pass_rate, failed = run(cases, qa_system)
    assert pass_rate == pytest.approx(1.0)
    assert failed == []


def test_run_partial_failure():
    cases = load_dataset(GOOD_JSONL)  # c3 会答"不知道"，失败
    pass_rate, failed = run(cases, qa_system)
    assert pass_rate == pytest.approx(2 / 3)
    assert failed == ["c3"]
```

**解析**：

- `load_dataset` 用 `enumerate(..., start=1)` 拿行号，把 `JSONDecodeError`（语法坏）、`KeyError`（缺字段）、`TypeError`（非对象）统一转成带行号的 `ValueError`，并用 `from exc` 保留异常链——这是 day010 `parse_plan` 防御式解析的同一套手法：**权威解析器判语法、业务契约显式校验、语义化异常向上抛**。
- "包含匹配"（`expected in output`）是正确性判定的最简形态：比精确匹配宽松（允许模型多说几句），比 LLM 裁判便宜（零成本）。真实系统里三种判定并存，按场景选。
- `run()` 返回 `(通过率, 失败清单)` 体现了汇总层的双产出：**决策要均分（能不能发版），归因要明细（差在哪里）**。
- 边界：`total == 0` 时通过率定义为 0.0 而非抛错或 1.0——空数据集没有证明任何东西，给 1.0 会制造虚假信心。

```python
"""双重评估练习：规则通道 + MockLLM 驱动的裁判通道."""
import re

from smart_research_agent.llm.base import Message
from smart_research_agent.llm.mock import MockLLM

JUDGE_PROMPT = """你是一位严格的评估裁判。请按以下评分细则评估回答质量：
1 分 = 答非所问或完全错误；3 分 = 部分相关但遗漏要点；5 分 = 完整准确且无冗余。
注意：回答长度不构成加分项。

请先输出分析理由，然后在最后一行单独输出：分数: X（X 为 1~5 的整数）

问题：{question}
被评回答：{output}
"""


def rule_score(output: str) -> float:
    """规则通道：确定性契约检查."""
    return 1.0 if output.startswith("Final Answer:") and len(output) <= 200 else 0.0


def judge_score(llm, question: str, output: str) -> float:
    """裁判通道：组装 rubric Prompt，解析最后一行分数并归一化."""
    prompt = JUDGE_PROMPT.format(question=question, output=output)
    reply = llm.chat([Message(role="user", content=prompt)])
    matches = re.findall(r"分数[:：]\s*([1-5])", reply)
    if not matches:
        raise ValueError(f"裁判回复中未找到分数行: {reply!r}")
    return int(matches[-1]) / 5.0  # 取最后一次出现，对应"最后一行"约定


def evaluate(llm, question: str, output: str) -> float:
    return 0.4 * rule_score(output) + 0.6 * judge_score(llm, question, output)
```

```python
# tests/test_dual_eval.py
import pytest
from smart_research_agent.llm.mock import MockLLM
from dual_eval import rule_score, judge_score, evaluate

GOOD_OUTPUT = "Final Answer: 上海人口的两倍约为 4800 万。"
BAD_OUTPUT = "上海人口的两倍约为 4800 万。"  # 缺少规定前缀，不合规
QUESTION = "上海人口的两倍是多少？"


def test_full_score_when_compliant_and_judge_gives_5():
    llm = MockLLM(responses=["理由：回答完整准确，直接给出数值。\n分数: 5"])
    assert evaluate(llm, QUESTION, GOOD_OUTPUT) == pytest.approx(1.0)


def test_rule_fail_and_judge_3():
    llm = MockLLM(responses=["分数: 3"])
    # rule=0.0, judge=3/5=0.6 → 0.4*0 + 0.6*0.6 = 0.36
    assert evaluate(llm, QUESTION, BAD_OUTPUT) == pytest.approx(0.36)


def test_judge_reply_without_score_raises():
    llm = MockLLM(responses=["我觉得这个回答还行。"])
    with pytest.raises(ValueError, match="分数"):
        judge_score(llm, QUESTION, GOOD_OUTPUT)


def test_judge_prompt_contains_question_and_output():
    llm = MockLLM(responses=["分数: 4"])
    judge_score(llm, QUESTION, GOOD_OUTPUT)
    sent = llm.calls[0][0].content
    assert QUESTION in sent
    assert GOOD_OUTPUT in sent
    assert "评分细则" in sent  # rubric 必须进入裁判 Prompt
```

**解析**：

- **规则通道的确定性**：`rule_score` 是纯函数，同样输入永远同样输出，零成本——这就是"格式类问题必须走规则"的全部理由。测试里 `BAD_OUTPUT` 只差一点（缺前缀）就被判 0，体现硬门槛语义：契约就是契约。
- **裁判 Prompt 的三要件**齐了：rubric（每档分的判据 + "长度不加分"的冗长偏差缓解）、参照物（原始问题与被评输出）、分数格式锁定（`分数: X` 单独成行）。注意 rubric 里显式写"长度不构成加分项"——这是第 4 题考过的冗长偏差缓解的落地。
- **解析取 `matches[-1]`** 而非 `[0]`：裁判按要求"先理由后分数"，分数在末尾；取最后一次出现对"理由里意外提到分数字样"更鲁棒。解析失败抛 `ValueError` 而非返回 0——静默兜底会污染统计数据（呼应 day002 的 Fail Fast 与 day010 的防御式解析）。
- **`MockLLM.calls` 验证 Prompt 组装**：`test_judge_prompt_contains_question_and_output` 不断言分数，而断言"裁判收到了什么"——评分解析逻辑和 Prompt 组装逻辑是两条独立的故障线，要分开测。这正是 MockLLM 记录入参的价值（day005 设计的兑现）。
- 权重 0.4/0.6 只是示例；真实场景里格式若是否决项，应该改用硬门槛（`rule == 0 → total = 0`）而非加权——第 11 题填空考的正是这个区别。
