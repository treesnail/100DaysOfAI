## 今日目标

day099 的结语留了三句话，今天必须逐条兑现：

```text
① "装上了"与"接上了"是两件事：一条元组比较就能证明"接上了"（SystemRun.is_identical_to）
② 清单要能被程序核对，而不是被人抄（importlib 说了算）
③ 读数必须现场算出，且要能跟一个界比较（三条判据：相等 / 上界 / 下界）
```

day099 是在**链**上兑现这三句话的。今天把它们抬到**交付**这一层：

```text
① → 剧本要能被重放：replay() 跑两次，diff_count 必须 == 0
② → 清单要能被重扫：发现集合 == 记录集合（52 == 52）
③ → 自评要能落到证据上：等级由三项证据推出，且挂在量程里
```

本日要建立的四件事：

1. **一份剧本**：`demo.build_transcript()` → `DemoTranscript`（九段读数 + 汇总 + 归档 + 摘要）；
2. **一份名册**：`inventory.build_inventory()` 用 `pkgutil` 数遍全部子包，
   `importlib` 逐个解析，产出 52 行读数；
3. **一组评级**：`assessment.assess()` → 8 行"评级 + 三项证据"，评级**只能由证据推出**；
4. **一份规划**：`roadmap.plan()` 从真实缺口推出 5 条下一步，**缺口集合 == 规划项集合**。

最终产出：`graduation` 包十个文件（901 语句 / 170 分支）、`tests/test_graduation.py`

## 第一章：交付的定义——四份产物，各回答一个问题

"项目做完了"这句话在工程上几乎不携带信息。把"做完了"换成一个可被反驳的问题，
它会立刻变成四句话：

```text
1. 这一次端到端运行，能不能被别人原样重放？        → 演示剧本
2. 这门课到底交付了哪些子包，各有多少东西？          → 课程清单 + 课程总结
3. 八项能力分别建到了哪一步，各自的证据是什么？       → 能力自评
4. 按真实缺口排，下一步该补什么？                    → 后续规划
```

这四句话被写进代码（`types.DELIVERABLE_ORDER`），并在导入期做
`set(...) == set(...)` 的闭合断言。**为什么值得写进代码**：交付物清单如果只存在于教程里，
那么"少交了一份"这件事在报告里就看不出来——报告仍然完整，只是少了那一节。

四份交付物各自回答一个独立的问题，合起来**不重不漏**：

```text
demo        | 演示剧本 | 它回答：这一次端到端运行，能不能被别人原样重放？
summary     | 课程清单 | 它回答：这门课到底交付了哪些子包，各有多少东西？
assessment  | 能力自评 | 它回答：八项能力分别建到了哪一步，各自的证据是什么？
roadmap     | 后续规划 | 它回答：按真实缺口排，下一步该补什么？
```

第 ② 条性质就是这件事：**四份交付物全部非空**，读数 = 空白了几份。
"没写"与"这一份不需要"在文本上长得一样，只有把"非空"写成判据，
这份遗漏才会当场变红。

## 第二章：演示剧本——展示，而不是宣称

`demo.build_transcript()` 做一件很简单的事：把一次 `capstone.assembly.run()` 的
九段读数、汇总行与归档行折成一份**文本**。它不生产任何新读数。

```text
# 演示剧本 · 100 天 AI 学习计划 · 结业里程碑
# 问题：向量维度不一致该怎么处理
1. [guard   ] ✓ | 读数 0 | 护栏：放行 | 注入 0 / 敏感 0 / PII 0 | 检查 12 字
2. [plan    ] ✓ | 读数 3 | 规划：3 条子任务 拆解问题、检索语料、核对引用 | 工具自检 2 + 3 * (4 - 1) = 11 ✓
3. [retrieve] ✓ | 读数 3 | 检索：3 条（k-3=+0.0328、k-2=+0.0320、k-6=+0.0320）| empty_reason=hits
4. [pack    ] ✓ | 读数 3 | 打包：147/600 字 | 引用 3 条 | 截断 0 / 丢尾 0
5. [generate] ✓ | 读数 1 | 生成：模型已调用 | 回退 （无） | 32 字
6. [ground  ] ✓ | 读数 0 | 接地：通过 | 有效 1 / 幻觉 0 / 未引用 2 | 覆盖 33.3%
7. [evaluate] ✓ | 读数 1 | 评估：召回 1.0000 | 精确 0.3333 | MRR 1.0000 | NDCG 1.0000 | 金标准 ['k-3']
8. [account ] ✓ | 读数 3.78e-05 | 记账：2 次调用 | token 210（196+14） | 费用 $0.00003780（gpt-4o-mini）
9. [trace   ] ✓ | 读数 9 | 追踪：9 个 span（root=capstone.run）
汇总：阶段 9 段全通过=True | 召回 1.0000 | 费用 $0.00003780 | token 210 | span 9 | 摘要 f052e4a7dd78d232
里程碑：100 天 AI 学习计划 · 结业里程碑 | 第 100 天 | 运行摘要 f052e4a7dd78d232 | 阶段 9 段全通过=True
# 剧本摘要：78c8ba8284c3ba99
```

**剧本里没有一个字是形容词**：每一行都是真算出来的读数（第几段、成没成、读数多少、摘要多少）。
这正是它作为交付物的价值——读者可以自己跑一遍对照，而不必相信任何一句话。

这里有两个**不同**的摘要，必须分清：

```text
运行摘要 f052e4a7dd78d232   = sha256(问题 + 九段记录 + 答案 + 指标 + 费用 + token + span 条数)
剧本摘要 78c8ba8284c3ba99   = sha256(问题 + 九段读数 + 汇总行 + 归档行)
```

前者由 day099 定义（覆盖四条指标、费用与 token），后者由今天定义（覆盖**剧本的文本**）。
它们各管一段：**"运行没变"与"剧本没变"是两件事**。
如果今天直接复用运行摘要，那么"有人改了剧本的抬头"这种变化就看不见了。

`DemoTranscript.__post_init__` 里有三条护栏，其中一条值得单独说：

```text
stage_lines 的条数必须等于 len(ASSEMBLY_STAGES)（9 段）
    —— 缺段或多段的剧本读起来依然通顺，因此它必须被当成一次失败（DemoError）。
```

## 第三章：重放——一次 `==` 就够

剧本要能被重放，做法最省力也最严格：**跑两次、逐位比**。

```python
first = demo.build_transcript(capstone_assembly.run())
second = demo.build_transcript(capstone_assembly.run())
report = demo.ReplayReport(first=first, second=second)
report.identical      # diff_count == 0
```

实测：

```text
重放：第一次摘要 78c8ba8284c3ba99 / 第二次摘要 78c8ba8284c3ba99 | 逐位相同=True | 差异 0 项
```

重放口径（`DemoTranscript.comparable`）**只含四样东西**：

```text
参与比较：问题 / 九段读数 / 汇总行 / 归档行
不参与：  时间戳、uuid、耗时、日志文本
```

**"不参与"这一列才是本节的要点**：把它们放进读数，"两次重放逐位相同"这条性质会
**永远失败**——而失败的原因与剧本本身无关，于是这条性质就会被人关掉。
day096 把时钟做成可注入、day099 把时间移出复算口径，都是同一条纪律：
**可复现的前提是先把"不确定的东西"从读数里挪出去。**

此外还有一条工程细节（`capstone` 里已经定下的）：

```text
run() 每次新建一份底座（build_substrate）⇒ 两次运行的 MockLLM 脚本从同一条起跑线出发
```

这不是"为了测试才这样"：复用一个被上一次请求改过状态的模型对象，
正是"两次运行读数不同"最常见的病因。今天把这条纪律从"一次运行"推到了"一份产物"。

## 第四章：课程清单——数出来，不是抄出来

"学习总结"最容易写成一段散文。今天把它变成一份**名册**：

```python
names  = inventory.discover_subpackages()   # pkgutil.iter_modules，不 import
report = inventory.build_inventory()        # 对每个子包 importlib 一次
```

本仓库当前的读数（`python scripts/graduation_demo.py` 第 4 节）：

```text
子包 52 个 | 在场 52 | 公开名字 4767 | 内部文件 379
```

名册的前几行长这样：

```text
agent                | 在场 | 公开   11 个名字 | 文件  11 | __all__ 无
alignment            | 在场 | 公开   73 个名字 | 文件   6 | __all__ 有
api                  | 在场 | 公开    1 个名字 | 文件   4 | __all__ 有
arch_variants        | 在场 | 公开  155 个名字 | 文件   8 | __all__ 有
...
graduation           | 在场 | 公开  130 个名字 | 文件   9 | __all__ 有   ← 今天新增的包
```

两列分工明确：

```text
公开名字数   这个包对外面**公开了几个名字**（有 __all__ 就信它，否则按目录数子模块）
内部文件数   这个包里面有**几个文件**（子模块与子包都算）
```

`_public_symbol_count` 为什么在无 `__all__` 时要按目录数？day099 已经解释过一次，
今天再钉一遍：**确定性与导入顺序无关**。按 `vars()` 数，随着别的模块把子模块 import 进来，
包命名空间会"长"出新名字，于是同一次运行里"先数"与"后数"会给出两个数。

`InventoryReport.__post_init__` 有一条闭合检查：

```text
发现集合 == 记录集合
    → 漏项（有子包没进名册）与重复（同一个包数了两遍）都会当场变红
```

一个被漏掉的包既不会出现在名册里，也不会被任何人负责——这正是
day098 记下的那条风险（"哪一项没被碰到，答案必须写在报告里"）的可执行版本。

## 第五章：课程总结——两条路径，同一个数

名册是给程序读的；总结是给人读的。总结有八个计数：

```text
总结：100 天 | 子包 52 | 文件 379 | 名字 4767 | 能力 8 | 阶段 9 | 性质 7 | 交付物 4
```

**前四个数与后四个数的来源完全不同**，这一点必须分清：

```text
100 天         MILESTONE_TOTAL_DAYS（一个**声明**：这个仓库里没有日期，100 天是里程碑的定义）
52 / 379 / 4767  数出来的（来自 InventoryReport）
8 / 9 / 7 / 4    折出来的（分别来自 capstone.types 与 graduation.types）
```

因此 `summary_matches_inventory` 只对账**三个可数计数**：

```text
(subpackages, len(inventory.rows))   52 == 52
(modules, inventory.total_modules)   379 == 379
(symbols, inventory.total_symbols)   4767 == 4767
→ 差异项数 0（0 = 一致）
```

**为什么这值得单独做成一条性质**：总结给人读、清单给程序读，
**两条独立路径给出同一个数**，才叫"总结被核对过"。
这与 day099 第 ⑥ 条性质"记账（走价格表）vs 手算（走公式）"是同一套纪律：

```text
同一个量由两条独立路径算出，两条都对上 → 这个量可信
只有一个来源 → 你只是在复述那个来源
```

`CourseSummary.__post_init__` 里有一条特别的天数护栏：

```text
days 必须逐位等于 MILESTONE_TOTAL_DAYS（100）
    → 否则"我们走完了 100 天"与"我们走了 98 天"在报告里读起来一样
```

## 第六章：能力自评——评级只由证据推出

自评不是"我们做完了"这一句，而是 8 行**带证据**的评级。每一行的评级由三条证据推出：

```text
证据① 承担子包在场数 / 承担数       security、llm …… 全部解析得到吗
证据② 公开名字数（对门槛 SYMBOL_FLOOR = 8）
证据③ 端到端链上那一段 ok            这一项能力在 day099 的九段链里真的跑通了吗
```

三级门槛把评级切成四档（`types.LEVELS`）：

```text
0 未建     有承担子包不在场
1 已建     全部在场，但公开名字数 < 门槛
2 可用     前两项成立，但链上那一段 ok=False
3 已交付   三项全过
```

实测（`python scripts/graduation_demo.py` 第 6 节）：

```text
L3 已交付 ✓ | input_guard            | 承担 2/2 | 名字  20 | 阶段 guard ok=True
L3 已交付 ✓ | task_planning          | 承担 2/2 | 名字  23 | 阶段 plan ok=True
L3 已交付 ✓ | hybrid_retrieval       | 承担 2/2 | 名字 219 | 阶段 retrieve ok=True
L3 已交付 ✓ | context_packing        | 承担 1/1 | 名字 124 | 阶段 pack ok=True
L3 已交付 ✓ | grounded_generation    | 承担 2/2 | 名字 136 | 阶段 generate ok=True
L3 已交付 ✓ | offline_evaluation     | 承担 1/1 | 名字  20 | 阶段 evaluate ok=True
L3 已交付 ✓ | cost_and_tracing       | 承担 2/2 | 名字  20 | 阶段 account ok=True
L1 已建  · | tool_execution         | 承担 1/1 | 名字   5 | 阶段 plan ok=True
```

七个数字相加可以逐条核对（"名字"这一列就是承担子包的公开名字数之和）：

```text
input_guard        security(8)  + llm(12)        = 20
task_planning      agent(11)   + llm(12)        = 23
hybrid_retrieval   retrieval(124) + vectorstore(95) = 219
context_packing    retrieval(124)                = 124
grounded_generation retrieval(124) + llm(12)     = 136
offline_evaluation evaluation(20)                = 20
cost_and_tracing   observability(8) + llm(12)    = 20
tool_execution     tools(5)                      =  5   ← 低于门槛 8
```

**唯一的 L1 是 `tool_execution`**：它的承担子包 `tools` 公开面只有 **5** 个名字，
低于门槛 8。这不是缺陷，而是**自评的诚实**——它给出一个 1 分，
并说明为什么（`公开名字 5（门槛 8）`），然后把这件事交给后续规划。

`CapabilityScore.__post_init__` 有两条闭合检查，第二条是关键：

```text
① evidence 至少一条（否则 AssessmentError）
② level 必须**等于**由同一批证据重算出来的那一档
```

第 ② 条让"手写一个 3 分"不可能悄悄通过：

```python
# 证据说 L0（有一个承担子包不在场），却写了 3 分 → 当场拒绝
CapabilityScore(..., owners_present=0, owners_total=2, symbols=100, stage_ok=True, level=3)
# AssessmentError: 评级 3 与证据重算出的 0 不一致……
```

**一个没有证据的满分，与"我猜的满分"在报告里长得一模一样**——这就是这条护栏存在的理由。

最后，有一条**更严但刻意分开**的路：

```python
assessment.require_delivered()   # 有任意一项没到 L3 就抛 AssessmentError
```

本课的真实状态是"7 项 L3 + 1 项 L1"，因此它会抛。
而**七条性质**（`verify.check_all`）是全部通过的——两条路刻意分开：
把"七条性质全过"与"八项都到 L3"绑在一起，会让"有一条能力在 L1 **且已被规划**"
这种合法状态被当成失败，从而逼着人把自评的分数往上写。

## 第七章：后续规划——从缺口推出

后续规划最容易写成许愿：一串"下一步要做 X、Y、Z"，读起来很完整，
却没有任何一处能对上"我们到底缺什么"。今天把它反过来做：
**先算缺口，再让每一条缺口对应一个规划项**。

缺口只有两种，两种都来自一次真实读数：

```text
unclaimed_package   无人认领的子包     已交付、但不属于这 8 项能力清单（来自清单）
capability_below    没到最高级的能力   在场 / 符号 / 阶段三项里有一项没过（来自自评）
```

实测（`python scripts/graduation_demo.py` 第 7 节）：

```text
1. [unclaimed_package] indexing       | 理由：索引清单与版本：已交付，但不属于这 8 项能力 | 下一步：评估是否纳入主线能力清单；若纳入，补一条端到端阶段与一组读数
2. [unclaimed_package] mcp_server     | 理由：MCP 服务端：已交付，但不属于这 8 项能力清单   | 下一步：同上
3. [unclaimed_package] finetune       | 理由：微调数据管线：已交付，但不属于这 8 项能力     | 下一步：同上
4. [unclaimed_package] api            | 理由：HTTP 端点：已交付，但不属于这 8 项能力（外壳） | 下一步：同上
5. [capability_below ] tool_execution | 理由：L1 已建 · | 承担 1/1 | 名字 5 | 阶段 plan ok=True | 下一步：把这一项能力的证据补齐到 L3
规划：5 项（unclaimed_package 4 / capability_below 1）
```

**"无人认领"为什么也算一种缺口**：

```text
indexing / mcp_server / finetune / api 都是真的写出来了的包，
但它们不在这 8 项能力的清单里——它们不是"坏了的包"，而是"还没被纳进主线的能力"。
"要不要纳进来"是一个真实的待决问题；把它列进规划，比假装看不见更诚实。
```

`Roadmap` 与 `gaps()` 之间有一条可断言的对应关系：

```text
缺口集合 == 规划项集合
    missing(gap_keys)   → 有缺口没有规划（应当为空）
    ignored(gap_keys)   → 规划指向不存在的缺口（应当为空）
```

第 ④ 条性质就是它们的和 == 0。一份对不上的规划读起来更完整，但它不可反驳——
这正是 day099 那句"清单要能被程序核对"在**规划**上的翻版。

## 第八章：七条性质、七个失败族与五条边界

### 8.1 七条性质（三类判据齐全）

```text
1. demo_replays_identically     | [equality   ] | 读数 0 ✓ | 差异项数 0（0 = 逐位相同）；摘要 78c8ba8284c3ba99 / 78c8ba8284c3ba99
2. deliverables_are_complete    | [equality   ] | 读数 0 ✓ | 交付物 4/4 份非空；空白的：无
3. inventory_accounts_for_all   | [equality   ] | 读数 0 ✓ | 子包 52 个 / 发现 52 个 | 重复 0 / 漏项 0
4. roadmap_covers_every_gap     | [equality   ] | 读数 0 ✓ | 缺口 5 个 / 规划 5 项 | 未覆盖 0 / 多余 0
5. assessment_within_scale      | [upper_bound] | 读数 3 ✓ | 最高 L3 ≤ 上界 L3
6. assessment_has_evidence      | [lower_bound] | 读数 3 ✓ | 最少证据 3 条 ≥ 下界 1
7. summary_matches_inventory    | [equality   ] | 读数 0 ✓ | 差异项数 0（0 = 一致）
合计：7/7 条通过
```

**五条相等、一条上界、一条下界**——判据类型是性质的一部分，
它们与 `types.GRADUATION_PROPERTIES` 逐名对齐，并在导入期做闭合断言。

第 ⑥ 条是**下界**：每一项能力至少挂一条证据。这一条**只能从下面兜住**——
证据越多越好，到 3 条、4 条都不会"超过"某个上限；写成相等判据会在报告补了一条证据时误报失败。

第 ⑤ 条是**上界**：最高评级不超过量程。它**不是相等**：8 项能力不可能都恰好是 3 分才是合格的，
本课的真实状态就是"7 项 L3 + 1 项 L1"，而这一项已经被第 ④ 条兜住了。

### 8.2 七个失败族

| 族 | 该谁去修 |
|----|----------|
| `MilestoneError` | 改里程碑定义或改数据：天数与归档对不上时，先把那份可复算的读数补上 |
| `DemoError` | 改剧本生成：重放不一致或剧本缺段时，先让两次重放给出同一份剧本 |
| `InventoryError` | 改扫描：重复发现或漏项时，先让"发现"与"记录"是同一个集合 |
| `AssessmentError` | 改自评规则：未知能力、没有证据或评级越界时，先把证据补齐 |
| `RoadmapError` | 改规划：有缺口没有下一步时，先让缺口集合与规划项逐键对上 |
| `NumericError` | 改数据或改实现：非有限读数与非法上下界都属于"数值不可用" |
| `ParameterError` | 改调用：交付物名 / 缺口类型 / 阈值 / 序号都是调用点的一次决定 |

`FAMILY_OUTCOMES` 与 `_FAMILY_CLASSES` 逐键对齐，导入期断言。两条族常量：

```text
RETURNED_FAMILY = "VersionError"
  它第一次出现是 day065 的 indexing.errors.VersionError（"索引版本对不上"）；
  此后各课都只把它当工具函数。今天把"100 天里程碑"归档成一个**可复算的版本事件**
  （剧本摘要即这份产物的指纹），于是这个名字**回来**了——但基类从 Exception
  换成 GraduationError(ValueError)：它要能被同一条 except ValueError 兜住，与其余六族同源。

ABSENT_FAMILY = "GradientError"
  本课是交付与归档，一个新式子都没有写；本课连一次反向都没有触发。
  唯一的"梯度事件"仍是被调用的 finetune 那一侧——它属于被调用的代码，不属于交付层。
```

### 8.3 五条边界

```text
1. 不新增任何第三方依赖：四份交付物用到的每一个读数都来自快照内的既有子系统。
2. 不改动任何既有模块、既有测试、pyproject 与 docs 下的既有文件——只新增文件。
3. 交付的是产物与判据，不是新的模型能力：不重写检索器、生成器或指标。
4. 全部读数离线、确定性：复用 day099 的固定底座，不联网、不读密钥。
5. 能力自评是**基于证据的评级**，不是对真实世界效果的承诺——
   它衡量的是"这一项能力在本仓库里被建到哪一步"，不是"它在生产环境里有多强"。
```

第 5 条是本课最需要说清的一条：一个 8×4 的评级表很容易被读成"我们的能力评估结果"，
但它**不是**。它是"按本仓库的代码事实，这一项建到哪一步"，证据只有三样
（在场 / 符号 / 阶段）。把它读成效果评估，是使用它时最危险的一种误读。

## 结语：三条可以带走的工程结论

1. **交付的判据是"别人能复算"，不是"我们能跑通"。**
   剧本要能被重放（`replay().diff_count == 0`）、清单要能被重扫
   （发现集合 == 记录集合）、总结要能与清单对账（差异项数 == 0）。
   "我这台机器跑过"不是一份产物。

2. **每一个数都要能回答"它从哪来"。**
   自评的等级由三项证据推出、并由一条闭合检查拒绝"手写的分"；
   总结的八个计数里，四个数出来、四个折出来，来源被写进两列不同的话。
   一个没有来源的数，与"我猜的数"在报告里长得一模一样。

3. **交付要敢把不完美写出来。**
   本课的最终自评是 **7 项 L3 + 1 项 L1**：`tool_execution` 停在"已建"，
   因为 `tools` 包的公开面只有 5 个名字（低于门槛 8）。
   它没有被写成 3 分，而是被写成 1 分并交给规划。
   **一份把 1 分写成 3 分的交付，会让后面所有的规划都失去意义。**

> **诚实的说明**：本课是**离线、确定性**的——模型是 `MockLLM` 的剧本、
> 语料是 6 条写死的记录、编码器是确定性字符 n-gram，因此它**不测量任何真实模型的质量**。
> 第 6 节的自评量的是"这一项能力在本仓库里被建到哪一步"，不是效果；
> 第 5 节的费用来自**价格表折算**，不是账单；第 4 节的清单是 `importlib` 数出来的符号数，
> 不是代码质量。本课**没有** `import` 任何新依赖、**没有** GPU、**没有**真实向量库、
> **没有**部署与服务化——它给的是**一套能带走的交付纪律**：
> 当你在真实项目里收尾时，知道该交哪四份、各断言哪几件事。

## 100 天到此收束

这是这门课的第 100 天，也是 G2（结业项目整合（二））的收尾。
回头看这条主线：`smart-research-agent` 从一个空目录，长成
**52 个子包 / 379 个文件 / 4767 个公开名字**，全量回归 **14950 个用例**一路全绿。

最后一天做的事，是把"这条路走完了"变成一个**别人能复核**的说法：

```text
一份能重放的剧本（78c8ba8284c3ba99）
一份能被 importlib 核对的名册（52 == 52）
一份挂证据的自评（7 × L3 + 1 × L1）
一份从缺口推出的规划（5 == 5）
```

这四份东西里没有任何一行是新的模型能力——它们全部由前 99 天的读数折出来。
**这正是"结业交付"该有的样子：不新增能力，只让已有的能力变得可被信任。**
