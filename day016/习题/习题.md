### 第 1 题（MCP 解决的核心问题）

MCP 协议要解决的本质问题是：

- A. 提升 LLM 的推理速度

### 第 2 题（架构角色）

在 MCP 架构中，关于 Host、Client、Server 三个角色，以下说法**正确**的是：

- A. 一个 Host 只能连接一个 Server
- B. Client 与 Server 是一对多的关系，一个 Client 可以服务多个 Server

- D. Server 需要持有 LLM 连接，以便主动为模型提供上下文

### 第 3 题（三类原语的控制权）

Resources、Tools、Prompts 三类原语中，**由模型自主决定何时触发**的是：

- A. Resources
- B. Tools

- D. 三者都是

### 第 4 题（JSON-RPC 2.0 消息）

以下 JSON 消息中，属于**通知（Notification）**的是：

- A. `{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {}}`

## 第四部分：编程题

### 第 10 题（实现 CapabilityRegistry）

教程第六章给出了 SmartResearch Agent 的目标能力清单，但今天的 `protocol.py` 只有单个描述符的建模，还没有"把一批描述符聚合成 Server 能力清单"的设施。请新建 `smart_research_agent/mcp_server/capabilities.py`，实现一个 `CapabilityRegistry`，要求：

**功能要求**：

1. 提供 `register_resource(desc: ResourceDescriptor)`、`register_tool(desc: ToolDescriptor)`、`register_prompt(desc: PromptDescriptor)` 三个注册方法。
2. 同类能力**按 name 判重**（Resource 按 uri 判重）：重复注册抛出 `ValueError`，错误信息包含冲突的名字。
3. 提供 `to_initialize_capabilities() -> dict` 方法，返回可直接放进 initialize 响应 `result["capabilities"]` 的字典，格式为：
   ```python
   {
       "resources": {"listChanged": False, "count": <资源数>},
       "tools": {"listChanged": False, "count": <工具数>},
       "prompts": {"listChanged": False, "count": <提示词数>},
   }
   ```
4. 提供 `list_all() -> dict[str, list]` 方法，返回 `{"resources": [...], "tools": [...], "prompts": [...]}`，各列表包含已注册的描述符对象。

**测试要求**：新建 `tests/test_mcp_capabilities.py`，至少覆盖：

- 三类能力各注册一个后，`to_initialize_capabilities()` 的 count 全为 1；
- 重复注册同名 Tool 抛 `ValueError`；
- 重复注册同 uri 的 Resource 抛 `ValueError`；
- 空注册表的 `to_initialize_capabilities()` 三个 count 全为 0。

**提示**：

- 内部用三个 dict 存描述符（key 分别是 uri / name / name），判重和计数都自然解决。
- `to_initialize_capabilities` 不需要序列化描述符本体——能力声明只报告"我支持这类能力、有几个"，描述符的细节由后续的 `resources/list`、`tools/list` 方法提供。想一想为什么这样分层。
