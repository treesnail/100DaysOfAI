## 今日目标

1. **理解 Function Calling 的机制与参数 schema 设计**——模型如何"说出"工具调用、JSON Schema 的描述质量为什么直接决定选参正确率。
2. **将 Agent 工具调用迁移到 LLM 原生 function calling 接口**——`FunctionCallingAgent` 用 tool_calls 结构走 ReAct 等价循环，工具结果以 `tool` 角色消息回填。
3. **处理函数调用失败与重试逻辑**——三类错误（schema 校验失败 / 工具不存在 / 执行异常）的分类处置与反馈回路设计。

day006 以来，我们的 Agent 一直走"文本协议"：模型按 `Thought/Action/Action Input` 格式输出自由文本，`parser.py` 用正则把它解析成结构化调用。这条路能用，但每一环都依赖模型的"自觉"。今天换成主流厂商的原生方案：**function calling**——把"怎么表达一次工具调用"从提示词约定升级为协议级的结构化输出。

## 第一章：文本解析 vs Function Calling —— 两条路线的本质差异

### 1.1 ReAct 文本协议在做什么

回顾 ReactAgent 的循环（`agent/react_agent.py`）：系统提示词用自然语言约定输出格式，模型输出自由文本，`parse_react_output` 用四个正则提取 `Thought`、`Action`、`Action Input`。这条链路上有三个不可靠来源：

```text
模型输出 "Action: calc"（工具名写错）     -> parser 解析成功，执行时才发现工具不存在
模型输出 "Action Input: 1+1。"（多个句号）-> 参数带噪声直接传给工具
模型输出 "Thought: ... Action: ... Final Answer: ..."（同步两个都写）-> 格式违例
```

每一个都要靠提示词约束（day026 v2 的四条约束）、解析器容错、执行时校验层层兜底。**格式正确性是被"求"出来的**——求模型遵守约定。

### 1.2 Function Calling 把格式约束机器化

Function calling 的思路相反：**不让模型用自然语言约定格式，而是给它一个结构化的输出通道**。

```text
请求侧:  tools = [{"type": "function", "function": {name, description, parameters(JSON Schema)}}]
                ↓ 随请求下发，模型在训练/推理时就知道"可调用的函数清单及其参数规格"
响应侧:  {"tool_calls": [{"id", "function": {"name": "calculator", "arguments": "{\"expression\": \"1+1\"}"}}]}
                ↓ 模型决定调工具时填充 tool_calls，直接回答时填充 content
执行侧:  解析 tool_calls -> schema 校验 -> 执行 -> 以 role="tool" 消息回填结果 -> 再调模型
```

关键差异在于：**arguments 是一段 JSON，由模型以"结构化输出"模式生成**。现代厂商在解码层面就对输出做约束（受约束解码/微调对齐），工具名只能来自下发清单、参数必须符合 schema 的概率被大幅拉高——格式正确性从"提示词求来的"变成"协议保证的"。

### 1.3 三条路线维度对照

| 维度 | ReAct 文本解析 | Function Calling |
|------|---------------|------------------|
| 输出通道 | 自由文本，正则解析 | 结构化 tool_calls，协议解析 |
| 格式可靠性 | 靠提示词约束 + 解析容错，会漏 | 解码层约束，近似强保证 |
| 模型要求 | 任何能跟指令的模型 | 需厂商训练/接口支持 |
| 可调试性 | 思考过程（Thought）天然可见 | 推理过程不强制外露 |
| 成本 | 提示词要内嵌格式说明与约束（长） | schema 随 tools 字段下发（也占 token，但格式约束不再占提示词） |
| 并行调用 | 一步一个 Action | 一次响应可返回多个 tool_calls |

两者不是替代关系而是**演进关系**：function calling 的循环骨架（调模型 → 得到调用意图 → 执行 → 回填结果 → 再调模型）与 ReAct 完全同构，`FunctionCallingAgent` 就是 ReactAgent 在结构化通道上的等价物。文本路线在"模型不支持 function calling"或"需要强制外露推理过程"时仍然是正确的 fallback——这也是 `BaseLLM.chat_with_tools` 默认抛 `NotImplementedError` 并提示"请改用 chat 走文本协议"的原因。

## 第二章：JSON Schema 设计要点 —— 描述质量即选参正确率

### 2.1 schema 是模型选参的唯一依据

模型决定"调用哪个函数、传什么参数"时，能看到的信息**只有** tools 字段里的 name / description / parameters。schema 写得好不好，直接决定调用质量：

```python
# 差：模型只能猜 expression 该传什么
{"properties": {"expression": {"type": "string"}}}

# 好：类型 + 自然语言描述 + 可选示例，模型选参有明确依据
{"properties": {"expression": {
    "type": "string",
    "description": "要计算的数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'"
}},
 "required": ["expression"]}
```

三个要点：

1. **description 写给模型看，不是写给人看**。它是模型的"参数说明书"：取值范围、格式约定、单位、示例都应该在这里。模糊描述（"输入数据"）几乎等于没写。
2. **required 显式声明**。缺了它，模型可能漏传关键参数——我们的 `validate_arguments` 把"缺必填"列为第一类拦截对象，线上观察到的模型选参错误绝大多数就是缺必填与类型不符两类。
3. **schema 与工具实现必须同源**。`FunctionSpec.from_tool` 直接引用 `BaseTool` 的 `name`/`description`/`parameters` 元数据（测试断言 `spec.parameters == tool.parameters`）——如果 schema 手写一份、工具实现一份，两者必然漂移，模型按旧 schema 传的参数会被新实现拒绝。**一份元数据，两种用途（执行 + 下发），漂移在结构上被消除。**

### 2.2 我方仍需校验：信任但要验证

即使厂商在解码层做了约束，"模型给出的参数一定合法"也不成立——小模型、长上下文、对抗输入都会让约束失效。所以 `validate_arguments` 在执行前做一道独立的 schema 校验（`llm/function_calling.py`）：

```python
def validate_arguments(spec: FunctionSpec, arguments: dict) -> None:
    missing = [key for key in schema.get("required", []) if key not in arguments]
    if missing:
        raise SchemaValidationError(f"调用 {spec.name} 缺少必填参数: {', '.join(missing)} ...")
    # properties 中声明了 type 的字段逐一做类型校验（string/number/integer/boolean/array/object）
```

两个实现细节值得一提：

- **只实现 JSON Schema 的子集**（required + type），零依赖、离线可跑。这两类覆盖了绝大多数真实错误，是收益/成本比最高的拦截点。
- **bool 不是 number**：Python 里 `bool` 是 `int` 的子类，`isinstance(True, int)` 为真，但 JSON Schema 里 boolean 与 number/integer 互不相容——不特判的话，模型传 `true` 给数字参数会漏过校验（测试 `test_bool_rejected_for_number` 专门守这个坑）。

## 第三章：FunctionCallingAgent —— 循环、回填与重试回路

### 3.1 ReAct 等价循环

实现位于 `../源码/smart-research-agent/smart_research_agent/agent/fc_agent.py`。主循环三步：

```python
for step_no in range(1, self.max_steps + 1):
    response = self.llm.chat_with_tools(messages, tools_payload)
    messages.append(Message(role="assistant", content=...))   # 决策入史
    calls = parse_tool_calls(response)
    if not calls:                      # 模型直接回答 -> 循环终止
        return response["content"]
    for call in calls:
        result, failed, counts_retry = self._execute(call, spec_map)
        messages.append(Message(role="tool", content=f"[{call.name}] {result}"))  # 结果回填
```

对照 ReactAgent 的变化只有两处：**"模型想做什么"从解析文本变成读取结构**，**"观察结果"从 user 消息（`Observation: ...`）变成 `tool` 角色消息**。`tool` 角色是 OpenAI 协议的专用角色，把工具输出与"用户说的话"区分开——模型据此知道"这段文本是函数返回的事实，不是用户的新指令"，这对抵抗经工具结果注入的间接提示词攻击（day031）也有结构性帮助。

### 3.2 错误分类：三类失败，三种处置

`llm/function_calling.py` 把 `ToolCallError` 分成三个子类，因为它们的最优处置完全不同：

| 错误类型 | kind | 含义 | 处置 |
|----------|------|------|------|
| SchemaValidationError | `schema` | 模型给错参数（缺必填/类型错/坏 JSON） | 错误详情回填，**占重试预算** |
| UnknownToolError | `unknown_tool` | 模型编了不存在的函数 | 附可用清单回填，**占重试预算** |
| ToolExecutionError | `execution` | 参数合法但工具内部异常 | 作为观察结果回填，**不占重试预算** |

分类的逻辑：**前两类是"模型的错"**——把错误信息喂回去，模型有能力自我修正（缺 `expression`？下次补上）；**第三类是"环境的错"**——参数没问题，重试模型无意义，应把失败事实告诉模型，由它决定换工具、换参数策略或放弃。`_execute` 返回的三元组 `(结果文本, 是否失败, 是否占重试预算)` 把这个决策显式化了。

### 3.3 反馈回路的设计

重试回路必须回答两个问题：

**反馈里放什么？** 放模型能据此修正的信息。schema 错误的反馈不只是"错了"，而是：

```text
参数校验失败：调用 calculator 缺少必填参数: expression（schema 要求: expression）。请修正参数后重新调用。
```

错误类型 + 缺失字段名 + schema 期望——模型拿到这条消息就知道下一步该传什么。这与 day036 的"约束要素"同理：**反馈越具体，修正越准**。测试 `test_schema_error_fed_back_and_retried` 验证了完整回路：第一轮缺参 → 反馈回填 → 第二轮修正 → 第三轮给出最终答案。

**什么时候放弃？** 连续失败计数超过 `max_retries`（默认 2）即终止。注意是**连续**失败：一次成功的调用会把计数清零。不设上限的反馈回路是烧 token 的死循环——模型可能在"缺参 → 反馈 → 还是缺参"上空转，每轮都是真金白银。坏 JSON（连工具名都不可信、无法回填 tool 消息）降级为 user 消息反馈，这是协议无法配对时的体面兜底。

### 3.4 MockLLM 的 function calling 模拟

离线测试需要"会调工具的 LLM"。`MockLLM.chat_with_tools` 接受 `tool_call_responses` 脚本：

```python
llm = MockLLM(tool_call_responses=[
    {"tool_calls": [{"name": "calculator", "arguments": {"expression": "2 + 3 * 4"}}]},  # 第 1 轮调工具
    {"content": "2 + 3 * 4 = 14"},                                                        # 第 2 轮直接回答
])
```

返回前脚本被规整为 OpenAI 兼容格式：arguments 序列化为 JSON 字符串、自动补 `id` 与 `type` 字段（`_normalize_tool_response`）。**为什么连 Mock 都要走线上格式**？因为 `parse_tool_calls` 要处理的就是线上格式——Mock 输出与线上一致，测试覆盖的才是真实协议路径而非玩具路径。脚本用尽后兜底返回 `{"content": ...}`，与既有 `responses`/`candidates` 机制共存，旧测试零改动。

## 第四章：迁移策略 —— 不是替换，是并存与切换

`FunctionCallingAgent` 落地后，系统里有了两条并存的 Agent 路线，选择依据是能力检测而非一刀切：

```text
LLM 支持 function calling（chat_with_tools 可用）?
   ├─ 是 -> FunctionCallingAgent：结构化可靠性优先（生产默认）
   └─ 否 -> ReactAgent：文本协议兜底（小模型/自研模型/需外露推理过程时）
```

`BaseLLM.chat_with_tools` 的默认实现抛 `NotImplementedError` 并把退路写进错误信息，就是这个切换逻辑的落点。两条路线共享同一套工具注册表、同一份工具元数据（`BaseTool.parameters` 一处定义，`to_schema()` 供文本提示词、`FunctionSpec.from_tool` 供 function calling），迁移成本只在 Agent 壳层。

### 4.1 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| tool_calls 结构化通道替代文本解析 | 格式正确性由协议保证，不靠提示词"求" | `chat_with_tools` / `parse_tool_calls` |
| schema 与工具实现同源 | 一份元数据两种用途，漂移在结构上被消除 | `FunctionSpec.from_tool` |
| description 写给模型看 | 模型选参的唯一依据就是 schema 文本 | 第二章 2.1 |
| 执行前独立 schema 校验 | 信任但要验证：解码约束可能失效 | `validate_arguments` |
| bool 特判不属于 number | Python isinstance 语义与 JSON Schema 语义冲突 | `validate_arguments` |
| 错误三分类（schema/unknown/execution） | "模型的错"喂回去重试，"环境的错"只反馈不占预算 | `ToolCallError` 子类 / `_execute` 三元组 |
| 反馈含错误类型+缺失字段+期望 | 反馈越具体，模型修正越准 | `_execute` 的反馈文本 |
| 连续失败超限即放弃 | 无上限反馈回路 = 烧 token 死循环 | `max_retries` / `consecutive_failures` |
| 成功调用清零失败计数 | 重试预算约束的是"连续犯错"而非"历史总和" | `run` 主循环 |
| 坏 JSON 降级为 user 消息反馈 | 无合法 id 时 tool 消息无法配对，体面兜底 | `run` 的 parse 异常分支 |
| tool 角色回填结果 | 工具输出与用户指令在协议层分离，抗注入 | `Message(role="tool", ...)` |
| Mock 输出走线上格式 | 测试覆盖真实协议路径而非玩具路径 | `_normalize_tool_response` |
| BaseLLM 默认抛 NotImplementedError | 能力检测即路线切换点，错误信息自带退路指引 | `BaseLLM.chat_with_tools` |

至此 M4 的 Prompt 与 Function Calling 专题完成：day036 解决"怎么把问题问进模型"，day037 解决"怎么让模型可靠地把工具调用说出来"。两者合流后的 SmartResearch Agent 同时具备提示词版本化管理与结构化工具调用能力。
