## 第一章：为什么这一课不是"再写一个评估器"

day025 有 `EvaluationHarness`（批量跑用例、打分、汇总），day029 有 `RagEvaluator`（四个检索指标 + 忠实度评审）。今天为什么还要一层？

### 1.1 三件 day025/day029 做不到的事

```text
① 它们评的是**一段名单**或**一次答案**，而今天要评的是**整条链路跑完一次**
   检索 → 打包 → 生成 → 核对，四步里任何一步的降级都必须进同一份报告
② 它们的指标没有"方向"，因此**不能进回归门禁**：
   "召回率 0.83"这个数字本身不告诉你"降到 0.78 算不算事故"
③ 它们没有"这一条为什么不好"的归因：
   一份写着 retrieval_recall=0.83 的报告，读的人不知道下一步该动哪个旋钮
```

### 1.2 链路顺序 = 排查顺序

day070 的第三章把"哪一层先坏了"写成了一张人工诊断表。今天的归因函数**照抄那张表的顺序**，这不是巧合：链路上每一层都在为下一层提供输入，而"下游的症状"总是比"上游的原因"更显眼。

```
库为空 → 检索为空 → 检索没抓到 → 重排切掉 → 没进提示词 → 排太后 →
片段被截断 → 走了回退 → 幻觉引用 → 没有有效引用 → 覆盖率低 → 忠实度低
```

一条坏例往往同时满足多个判据（检索没抓到的时候，答案当然也没有引用），但**因果顺序是固定的**。因此归因只给**一个**标签：先修因，再修果。给出全部标签会把因果关系摊平成一张清单，而读的人只会去修那个最显眼的（最后一个）。

### 1.3 评估器在架构中的位置

```text
                        ┌─────────────────────────────────────────┐
   评测集（6 条用例）      │              RagEvalSuite               │
   语料（6 条记录）        │  装载 → 灌库 → 装配（按变体） → 跑 → 归因  │
                        └───────────────┬─────────────────────────┘
                                        ▼
                    RagPipeline.answer()   ← 与线上完全同一条链路
                                        ▼
        RagAnswer →（runner 搬运）→ CaseOutcome   ← 一份扁平、可比较的账
                                        ▼
        diagnose → BadCase（标签 + 原因 + 动作）  ← 调试的那一半
                                        ▼
        build_report → RagEvalReport（11 指标 + 逐条证据 + 坏例 + 动作）
                                        ▼
        to_baseline → RagBaseline  ──→ save() ──→ data/eval/rag_baseline.json
                                        ▼
        RagBaselineGuard.compare() → 回归结论（或"不下结论"）
```

**两处设计原则**（后面每章都会回到它们）：

1. **指标口径只有一份实现**：四个检索指标直接复用 `retrieval.rerank` 与 `evaluation.rag_metrics` 的纯函数，忠实度复用 `evaluation.rag_eval` 的提示词与解析。今天只向 `evaluation/rag_eval.py` 加了**一个公开转发函数**（`parse_faithfulness`，只增不改），没有重写任何指标。
2. **评估不改变任何产物**：`rag_debug` 只读，配置组 `rag_eval_*` 只决定"怎么评"，不重建索引、不影响线上任何一次回答。

## 第二章：把"召回"拆成两段 —— 这一课的核心新指标

### 2.1 一个被忽略的漏斗

在此之前，"召回"只有一个数字。但链路上有两个**不同的名单**：

```text
① 检索器交出的名单      recall@k          ← day066~day068 的全部努力都在这里
        │
        │   ② 打包（pack_context）：预算 max_context_chars、单块上限 per_hit_chars
        │      从**尾部**丢掉放不下的、把超长的**截断**
        ▼
③ 真正进了提示词的名单   packed_recall@k    ← 模型唯一看得到的那一份
```

`RetrievalResult` 存在，`PackedContext` 也存在，`RagAnswer.context` 还带着 `dropped_hits` / `truncated_hits`——但**没有人把这两段放在一起算过一次召回率**。

### 2.2 "抓到了但没进提示词"是一门独立的失败

```text
检索抓对了        → 不是检索的错
模型没机会用它    → 不是生成的错
它是**预算的错**   → 处置动作：调 retrieval_max_context_chars / retrieval_per_hit_chars
```

合成一个召回率之后，这门失败会消失在均值里。而它的处置动作与另两种（改检索、改提示词）完全不同——这就是本层把 `StageMetrics` 分成两段的原因（`types.py`）：

```python
#: 检索器交出的那份名单（day066~day068 的账）.
STAGE_RETRIEVED = "retrieved"

#: 真正进了提示词的那份名单（day069 的账：预算丢尾之后剩下的）.
STAGE_PACKED = "packed"
STAGES: tuple[str, ...] = (STAGE_RETRIEVED, STAGE_PACKED)
```

`CaseOutcome` 上还多了一个把差额换成**条数**的属性——比例适合进报告，条数适合当待办：

```python
@property
def packed_away(self) -> int:
    """金标准里"被预算丢掉"的条数（**这一课的核心新指标**）."""
    lost = (self.retrieved.recall - self.packed.recall) * len(self.relevant)
    return int(round(lost))
```

### 2.3 四个检索指标：复用，不重写

`types.measure_ids` 是唯一的指标计算入口（纯函数）：

```python
def measure_ids(ids, relevant, k, *, grades=None) -> dict[str, float]:
    head = list(ids)[:k]
    graded = dict(grades or {})
    return {
        "recall": recall_at_k(ids, relevant, k),          # day068 的纯函数
        "precision": retrieval_precision(head, relevant), # day029 的纯函数
        "reciprocal_rank": reciprocal_rank(ids, relevant),# day068 的纯函数
        "ndcg": ndcg(head, graded) if graded else ndcg_at_k(ids, relevant, k),
    }
```

三处口径值得写清楚：

- **`precision` 只吃前 k 条**：不然一个 20 条的名单会因为"分母大"而拿到更低的精确率，而它其实只是"给得多"；
- **NDCG 有两个口径，按标注形态选一个**：有分级标注走 `evaluation.rag_metrics.ndcg`（分级增益 `2^rel - 1`，理想排序由等级表自己算），没有分级标注走 `retrieval.rerank.ndcg_at_k`（二值增益，理想排序由金标准条数算）。两个函数都是既有实现，本层不重写任何一个——但**同一批用例的标注形态必须一致**，否则 `mean_ndcg` 会变成两个口径的平均，而报告里看不出这件事（这一条由 `RagEvalSuite` 在装配期校验，见 6.3）。
- **金标准与等级表是两张表**：项目自带的评测集里 `relevant_ids` 是 `["rag-001"]` 而 `relevance_grades` 里还带着 `{"rag-002": 1}`——等级 1 表示"部分相关"，它不进 recall 的二值口径，却参与 NDCG 的位置折损。第一版实现把它们强行对齐，结果**拒绝了仓库里那份真实标注**；正确的读法是把两张表分别喂给各自的指标。

### 2.4 十一个质量指标（`baseline.QUALITY_METRICS`）

| 指标 | 方向 | 谁来管 |
|------|------|--------|
| `retrieval_recall` / `retrieval_precision` / `retrieval_ndcg` | higher_better | 检索（day066~day068） |
| `packed_recall` / `packed_ndcg` | higher_better | **打包预算**（这一课新增） |
| `grounded_rate` / `mean_coverage` | higher_better | 生成与核对（day069） |
| `hallucination_rate` | lower_better | 生成 |
| `llm_call_rate` | **neutral** | 描述性指标，不判方向 |
| `fallback_rate` / `bad_case_rate` | lower_better | 生成 / 全部 |

**为什么 `llm_call_rate` 没有方向**：它下降既可能是好事（检索为空时按护栏不调模型——那是设计如此），也可能是坏事（该调没调）。给它硬安一个方向，报告里会多出一类"看起来像回归、其实是护栏生效"的告警——那正是误报的来源。它仍然进基线、进报告、进差值表，只是不参与回归判定；真正的异常由 `fallback_rate` / `bad_case_rate` 如实报出来。

**比例类指标按用例取均值，不按"总条数"取**：一条有 3 个幻觉引用的用例与一条有 1 个的，在 `hallucination_rate` 上贡献相同——因为这个指标回答的是"这一批里多少条答案不可信"，而不是"总共有几个幻觉引用"（后者是 `tag_counts` 与 `CaseOutcome.hallucinated` 的账）。

## 第三章：归因 —— 一个标签、一句话、一个动作

### 3.1 三张封闭表

`types.py` 里定义了三张必须逐键对齐的表，**在导入期就校验一致性**：

```python
BAD_CASE_TAGS = (no_data, retrieval_empty, retrieval_miss, rerank_cut, packed_away,
                 rank_bad, truncated_chunk, generation_fallback,
                 hallucinated_citation, ungrounded, low_coverage, weak_faithfulness)
BAD_CASE_DESCRIPTIONS   # 每一类"是什么问题"（一句话，进报告）
BAD_CASE_ACTIONS        # 每一类"下一步做什么"（可执行动作，**只动一个旋钮**）
BAD_CASE_PRIORITY = BAD_CASE_TAGS   # 排列 = 归因优先级 = 链路的顺序
```

```python
if set(BAD_CASE_DESCRIPTIONS) != set(BAD_CASE_TAGS) or set(BAD_CASE_ACTIONS) != set(BAD_CASE_TAGS):
    raise DiagnosisError("坏例标签的三张表不一致：……"
                         "否则某一类坏例会在报告里只有名字、没有解释、也没有下一步。")
```

这条校验的价值在**它防的是沉默**：少一个键不会让任何测试变红，只会让报告里某一类坏例缺少动作——而"缺一行"与"这一类没问题"在读的时候长得一样。

第六种回退那张表（`FALLBACK_ACTIONS`）同样与 `generation.FALLBACK_REASON_DESCRIPTIONS` 逐键对齐：六种回退对应六种动作（改检索 / 查提供方 / 查 max_tokens / 改提示词 / 换模型），合成一个布尔之后就再也分不出来。

### 3.2 优先级是这样落地的

`diagnose.diagnose` 是纯函数（不读文件、不碰网络、不看 `settings`），它逐条判、命中即返回：

```python
# ① 库是空的：它不是模型问题，而是这次评估的前置条件没满足。
if outcome.empty_reason == EMPTY_REASON_NO_DATA:
    return BadCase(query=query, tag=TAG_NO_DATA, reason=…, action=BAD_CASE_ACTIONS[TAG_NO_DATA], …)

# ② 检索为空（其余三种原因）：处置动作看那一个原因本身。
if outcome.empty_reason:
    …

# ③ 一条金标准都没抓到：这是检索侧的问题（编码器 / 分块 / 索引版本）。
if retrieved.recall == 0.0:
    …

# ④ 有金标准被重排阈值切掉（第四道减法）——它有自己的旋钮。
if outcome.dropped_by_rerank > 0 and retrieved.recall < 1.0:
    …

# ⑤ 抓到了但没进提示词：这一课独有的那一门失败（预算的错）。
if packed.recall < retrieved.recall:
    return BadCase(..., tag=TAG_PACKED_AWAY, reason=(
        f"金标准被预算丢在了提示词之外：检索召回 {retrieved.recall:.4f}，"
        f"进了提示词之后只剩 {packed.recall:.4f}（丢掉 {outcome.packed_away} 条依据，"
        f"dropped_hits={outcome.dropped_hits}）——检索是对的，模型却看不到那一条"), …)
```

⑤ 那一段的措辞是刻意的：它同时给出**两个比例**（检索召回 / packed 召回）、**一个条数**（丢掉几条依据）与**一个字段**（`dropped_hits`）——读的人因此可以立刻判断"是预算太小，还是打包逻辑有问题"。

### 3.3 归因是"读账"，不是"再算一次账"

每一条 `reason` 里出现的数字全部来自 `CaseOutcome` 上**已有**的字段，归因不做任何新的计算（`packed_away` 除外，它是一次显式的换算）。理由：

```text
如果归因内部重算一遍召回率，那么报告里的"召回 0.5"与"归因说召回为 0"
就有可能是两个数（一次算法改动、一次参数不同）——
而两个互相矛盾的读数比一个错读数更坏。
```

### 3.4 判据的阈值是函数参数

```python
def diagnose(outcome, *, min_coverage=0.5, min_reciprocal_rank=0.5,
             min_faithfulness=0.5, require_grounded=True) -> BadCase | None:
```

四个阈值都有缺省值，且都可以逐次覆盖。**它们不是"质量的定义"，而是"这一批实验的判据"**——换一套更严的判据本身就该是一次显式决定，因此它们进的是函数参数（可被实验记录），而不是散落在代码里的字面量。

`require_grounded=False` 的用法只有一种：**先量一次"不做接地要求时的可核对率"**（day069 把 `retrieval_require_citation` 的缺省设成关闭，理由正是"先让默认可核对率跑一段时间"）。这条开关存在的意义是"能复现那次测量"，而不是"放宽质量"。

## 第四章：质量基线 —— 与性能基线方向相反

### 4.1 两处根本差别

day046 的 `PerformanceGuard` 已经交过一份基线。今天是它的质量侧对应物，而两者有一处必须写清楚的差别：

| | 性能基线（day046） | 质量基线（今天） |
|---|---|---|
| 指标 | 延迟 / token / 费用 | 召回 / 接地 / 覆盖率 |
| 好坏方向 | **越大越差** | **越小越差** |
| 判定口径 | **比值** `current / baseline > tolerance` | **差值** `delta < -tolerance` |
| 基数为 0 | 跳过该指标（0 的倍数无意义） | 照样可判（`0 → 0.05` 就是 5 个百分点） |

若两块共用一份"比值 > 阈值"的实现，质量侧的**每一次改善都会被判成回归**——而一个把好事报成坏事的门禁会在第一天被人关掉。

### 4.2 质量侧必须用差值：三条理由

1. **方向反转**：性能指标的"变差"是变大，质量指标的"变差"是变小。
2. **基数为 0 是常态**：`hallucination_rate` 与 `fallback_rate` 在健康系统上的基线值**就是 0**。比值在 0 基数下没有定义（day046 的处理是跳过这条指标），而差值在 0 基数下照样可判。**跳过一条指标会让"从零变坏"这种事永远不被发现**——那是这一课最想避免的一类静默失效。
3. **量纲可比**：11 个指标全是 `[0, 1]` 里的比例，差值就是"几个百分点"，可以直接写进报告给人读。

### 4.3 方向表与三张表的一致性

```python
DIRECTION_HIGHER_BETTER = "higher_better"
DIRECTION_LOWER_BETTER = "lower_better"
DIRECTION_NEUTRAL = "neutral"
DIRECTIONS = (DIRECTION_HIGHER_BETTER, DIRECTION_LOWER_BETTER, DIRECTION_NEUTRAL)

METRIC_DIRECTIONS: dict[str, str] = { … 11 项 … }
DEFAULT_TOLERANCES: dict[str, float] = { … 11 项，单位是百分点 … }
METRIC_DESCRIPTIONS: dict[str, str] = { … 11 项，人话说明 … }

if set(METRIC_DIRECTIONS) != set(QUALITY_METRICS) or set(DEFAULT_TOLERANCES) != set(QUALITY_METRICS) …:
    raise BaselineError("质量指标的三张表不一致：…否则某个指标会静默地不被判定——"
                        "而「静默地不判」与「判了没问题」在报告里长得一样。")
```

**第三种方向（`neutral`）是刻意存在的**：它是"只做描述"的那一类指标（今天的 `llm_call_rate`）。有了它，报告才能把"这个数不参与判定"写成一条明确声明，而不是靠"它恰好没超阈值"。

### 4.4 三档判定的完整规则

`baseline.deltas_between` 是判定的**唯一实现**（守卫与 A/B 对比都读它）：

```python
if direction != DIRECTION_NEUTRAL and abs(delta) > float(dead_band):
    tolerance = float(table[metric])
    better = delta > 0.0 if direction == DIRECTION_HIGHER_BETTER else delta < 0.0
    if better:
        verdict = "improved"
    elif abs(delta) > tolerance:
        verdict = "degraded"
```

```text
|delta| <= dead_band（缺省 0.02）        → unchanged（噪声）
方向是 neutral                            → unchanged
变化方向是「好」                          → improved
变化方向是「差」且 |delta| > 容忍度       → degraded
变化方向是「差」但 |delta| <= 容忍度      → unchanged（**允许变差多少**的语义）
```

最后一行是这套规则里最容易写错的一处：容忍度的语义是**"允许变差多少"**，因此它只对"变差"生效。第一版实现写成了 `degraded if delta < -tolerance else improved`——那会把"掉了 0.3、但容忍度是 0.4"记成 **improved**，也就是**符号反了的报告**。测试里为此留了一条用例（`test_custom_tolerances_and_dead_band`）。

### 4.5 三道"能不能比"的检查

`RagBaselineGuard.compare` 先查三件事，**任何一条不过就不给结论**：

```python
if current.k != self.baseline.k:
    reasons.append("口径变了：k 从 {…} 变成 {…}（前 3 条与前 5 条不是同一件事）")
if current.index_version != self.baseline.index_version:
    reasons.append("条件变了：索引版本从 {…} 变成 {…}（换了索引/编码器之后，历史数字立刻作废）")
if current.samples < self.min_samples or self.baseline.samples < self.min_samples:
    reasons.append("样本不足：…（两条用例不足以宣告回归）")
```

"不下结论" **不等于"通过"**：

```python
@property
def conclusive(self) -> bool:
    return not self.reasons

@property
def ok(self) -> bool:
    """**下了结论且没有回归**才算通过（不结论时返回 ``False``）."""
    return self.conclusive and not self.regressions
```

因此样本不足时 `ok=False` 而 `regressions=()`——读报告的人看到的是 `inconclusive`，而不是一个会让人放松警惕的绿灯。**门禁最危险的行为是在数据不足时装作有结论。**

`prompt_version` 的待遇刻意**不同**：它是 A/B 的**自变量**（day069 留下的伏笔），两边不同不影响可比性，只会进 `variables` 被记下来。

## 第五章：变体 —— 一次只改一个旋钮

day070 第七章写下过三条整理纪律，第一条是"一次只改一个旋钮"。变体就是这条纪律的数据形状（`suite.Variant`）：

```python
@dataclass(frozen=True)
class Variant:
    name: str
    prompt_version: str | None = None      # None = 去读 settings
    require_citation: bool = False
    top_k: int | None = None
    max_context_chars: int | None = None
    note: str = ""                          # **它改了什么**（报告里回显）
```

四个内置变体：

```text
baseline       当前默认配置（提示词 v2、不强制引用）
prompt-v1      只换提示词版本 v2 → v1（day069 留下的 A/B 伏笔）
cite-gate      只开 require_citation 闸门（不可核对的答案会被整条丢掉）
tight-budget   只收紧上下文预算（用来量 packed_away）
```

`prompt_version` 的取值被限制在**受管模板**里（`PROMPT_VERSIONS`）：自由文本会让"我换了哪一版"这件事无法复现；要换自定义模板得注入 `RAGGenerator`（那种覆盖不进提示词版本的分组，day069 已经写过）。

`compare_variants` 与守卫**共用同一份判定实现**，但**不产出回归结论**：

```text
A/B 回答"哪个变体更好"     → RagEvalReport / VariantComparison
门禁回答"这次能不能发"      → BaselineComparison（regressions + ok）
```

把两件事合成一个函数，会让一次实验的结果被读成一次发版评审。

逐条实测（`retrieved` 那一段，用同一个脚本把 6 条用例逐条打印出来）：

| 用例 | 金标准 | 检索名单（前 5 条） | recall | precision | RR | nDCG |
|------|--------|---------------------|--------|-----------|-----|------|
| 什么是检索增强生成 | rag-001 | 001, 004, 003, 006, 002 | 1.0000 | 0.3333 | 1.0000 | 0.9173 |
| 向量检索如何工作 | 002, 004 | 002, 005, 001, 003, 006 | **0.5000** | 0.3333 | 1.0000 | 0.7872 |
| 文档切块的常见策略 | rag-003 | 003, 001, 002, 005, 004 | 1.0000 | 0.3333 | 1.0000 | 1.0000 |
| Embedding 模型的作用 | rag-004 | 004, 003, 005, 006, 001 | 1.0000 | 0.3333 | 1.0000 | 0.9173 |
| 检索质量有哪些评估指标 | rag-005 | 005, 003, 001, 004, 006 | 1.0000 | 0.3333 | 1.0000 | 1.0000 |
| 如何评估生成答案的忠实度 | rag-006 | 006, 001, 003, 004, 005 | 1.0000 | 0.3333 | 1.0000 | 1.0000 |

三处读数值得单独解释，因为它们都是"数字对了、结论别读错"的典型：

- **`retrieval_recall = 0.9167` 的来历**：6 条里只有"向量检索如何工作"一条不满分（它标了 2 条金标准，而第 2 条没进名单）→ `(1+0.5+1+1+1+1) / 6 = 0.9167`。**单看这个均值会漏掉"有一条用例只召回一半"**——这正是报告里要同时保留 `per_case` 逐条证据的原因。
- **`retrieval_precision = 0.3333` 是 `k=3` 的算术结果**：前 3 条里恰好各有 1 条金标准 → 每条都是 `1/3`（连那条有 2 个金标准的用例也是 `1/3`：它的前 3 条里只落进 1 个）。它提醒我们：**精确率的分母是"端上来的盘子里有几条"，不是"库里有多少相关的"**——所以它低并不等于"检索给错了"，而"给多给少"正是 `k` 这个旋钮。
- **`retrieval_ndcg = 0.9370` 是四个指标里唯一带位置折损的**：金标准总在第 1 名（`RR` 全是 1.0000），但等级表里的"部分相关"文档（例如 `rag-002` 等级 1）落在后面，理想排序与实际的差就体现在 NDCG 上。

A/B 对照（同一索引、同一批用例，只差一个旋钮）：

```text
A/B baseline:baseline → baseline:prompt-v1（变量：提示词版本 v2 → v1）：改善 0 项、退化 0 项、未变 11 项
A/B baseline:baseline → baseline:cite-gate：改善 0 项、退化 0 项、未变 11 项
A/B baseline:baseline → baseline:tight-budget：改善 0 项、退化 0 项、未变 11 项
```

**"未变 11 项"是一个结论，不是一次失败**：在这份只有 6 条短片段的小语料上，换提示词版本、开引用闸门、把预算收紧到 200 字，都没有改变任何一个质量指标。A/B 的价值恰恰在于它能把"我以为改了会变好"变成一个**有数字的否定**。

第 8 节做了两个"把系统弄坏"的实验，用来验证归因链路：

```text
空库那一次        检索召回 0.0000 → packed 召回 0.0000 | 接地率 0.0000 | 坏例 6 条
                 坏例标签分布：{'no_data': 6}
                 llm_call_rate = 0.0000 与回退分布 {'no_context': 6}
                 ← 检索为空时**一次模型都没调**（护栏生效），因此那段兜底答复不是模型编的

幻觉引用那一次     检索召回 0.9167 → packed 召回 0.9167 | 接地率 0.0000 | 覆盖率 0.2000
                 幻觉率 1.0000 | 坏例 6 条，标签分布：{'hallucinated_citation': 6}
                 ← 一个引用了 [9] 的答案即使"其余部分看起来都对"，接地判定也只能是否定的
```

两次实验的**检索指标完全相同**（0.9167 与 1.0000），而结论完全相反。这正是"多指标 + 归因"要解决的问题：**任何单一数字都不足以说明这一批答案能不能交付**。

### 6.4 一个真实的陷阱：同名导入

写这一课的两个端点时踩到一个**不报错的坑**，值得单独记一笔。`rag_debug` 的装配入口叫 `build_suite`，而 `routes.py` 顶部**已经**从 `finetune_eval` 导入了同名的 `build_suite`（微调评估套件的装配器，被 `/finetune/eval/*` 两个端点调用）：

```python
from smart_research_agent.finetune_eval import (   # 顶部第 319 行：微调评估的
    …
    build_suite,
    …
)
…
from smart_research_agent.rag_debug import (       # 本层再加一行：RAG 评估的
    …
    build_suite,                                   # ← 这会把上面那个名字重新绑定！
)
```

**Python 不报错**：后导入的名字覆盖先导入的，于是 `/finetune/eval/*` 会静默地拿到一份 RAG 评估套件——而它的症状只是"返回的字段都不认识"。这类 bug 的表现形式是"另一个端点的响应结构不对"，与本次改动毫无表面联系。

这一课里唯一能发现它的手段是**静态检查**（`ruff` 的 F811 `redefinition of unused`）：

```text
smart_research_agent\api\routes.py:670:5: F811 Redefinition of unused `build_suite`
                                        from line 324: `build_suite` redefined here
```

修法是改名导入，并把理由写在代码里：

```python
from smart_research_agent.rag_debug import build_suite as build_rag_eval_suite
```

三条可以带走的结论：

1. **"导入不报错"不等于"导入是对的"**——名字冲突是 Python 里最安静的一类错误；
2. **跨模块重名是设计问题**：`rag_debug.build_suite` 与 `finetune_eval.build_suite` 回答的是不同的问题（一个装 RAG 评估套件，一个装微调评估套件），名字都"对"，冲突来自**同一个宿主文件**需要同时用两个；
3. **修完之后要跑相邻模块的测试**（这一次跑了 `test_rag_debug_api.py` 与两个 `test_finetune_eval_*.py`，416 个用例）——只跑自己新写的测试是发现不了这个坑的。

## 第七章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 召回拆成两段 | "抓到了但没进提示词"是预算的错，处置动作与另两种不同 | `STAGE_RETRIEVED` / `STAGE_PACKED` |
| `packed_away` 用条数 | 比例进报告，条数当待办 | `CaseOutcome.packed_away` |
| 指标复用不重写 | 两份实现一定会分家，而分家没有报错指向它 | `measure_ids` / `parse_faithfulness` |
| NDCG 按标注形态选口径 | 分级版与二值版不能混在一个均值里 | `measure_ids` + `RagEvalSuite` 的装配期校验 |
| 金标准与等级表分开 | 强行对齐会毁掉一份真实的标注 | `RagEvalCase` 的取舍说明 |
| 12 类标签的三张表逐键对齐 | 少一个键 = 某一类坏例没有动作，而这与"没问题"长得一样 | `types.py` 的导入期校验 |
| 优先级 = 链路顺序 | 因果有先后，只给一个标签才能先修因 | `BAD_CASE_PRIORITY` |
| 归因只读账 | 重算一遍就有两个可能矛盾的读数 | `diagnose` |
| 判据是函数参数 | 换判据是一次显式决定，必须可被记录 | `diagnose` / `RagEvalRunner` 的四个阈值 |
| 质量侧用差值不用比值 | 方向反转 + 0 基数是常态 | `deltas_between` |
| 容忍度只对"变差"生效 | 否则"差得不多"会被记成 improved（符号反了） | `deltas_between` 的 `better` 分支 |
| `neutral` 是第三种方向 | 把"不参与判定"写成明确声明 | `METRIC_DIRECTIONS` |
| 不下结论 ≠ 通过 | 门禁最危险的行为是在数据不足时装作有结论 | `BaselineComparison.ok` |
| 三道可比性检查 | 一份条件变了的评估看起来就像一次质量劣化 | `RagBaselineGuard.compare` |
| `prompt_version` 是自变量 | A/B 要能改它，而不能被它阻塞 | `variables` vs `reasons` |
| 变体一次只改一个旋钮 | 无法归因的实验与没有实验的信息量相同 | `Variant` + `note` |
| 基线与报告分开存 | 基线要进 git、要 diff；报告是排查用的全套证据 | `RagBaseline.save` / `RagEvalReport.save` |
| 基线缺失时给 null | "没有基线"与"基线全是零"是两回事 | `/rag/eval/status` |
| 报告自述适用范围 | 不说清边界等于让实验室结论冒充生产结论 | `RagEvalReport.limitations` |
| 降级必须留痕 | 评审失败时 `faithfulness=None` + `notes`，否则均值里多一个看不见的空洞 | `RagEvalRunner._faithfulness` |
| 端点跑注入的库 | 评估对象必须与服务对象是同一套 | `/rag/eval/run` |
| 跨模块同名导入必须改名 | Python 不报错，只会让另一个端点静默拿到错的套件 | `routes.py` 的 `build_rag_eval_suite` |

### 今天埋下的伏笔

```text
11 个质量指标 + RagBaseline
    day072（M6-D10 RAG 生产化部署）要把它接进定时评估："索引增量更新之后质量变了吗"
    这个问题今天已经有判据了——缺的只是"谁来定期跑、跑完通知谁"
RagEvalReport.save 与 outputs/rag_eval/report.json
    生产化部署那一课会把报告落盘接到发布流程里（发布前跑一次，基线不降才放行）

    定时评估要换评测集/换判据时，改配置而不是改代码；
```
