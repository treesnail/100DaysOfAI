## 第一章：M5 的第一课为什么是"数据"

### 1.1 微调能改变什么、不能改变什么

先把预期校准好，否则后面每一课都会判断失误：

| 微调**能**做到 | 微调**做不到**或代价极高 |
|----------------|------------------------|
| 学会领域表达与格式（术语、口吻、结构化输出） | 灌入大量**新事实**（那是 RAG 的活，day061~072） |
| 学会一种**行为**（工具调用、ReAct 轨迹、拒答） | 提升模型的推理上限（受基座能力约束） |
| 把系统提示词里反复写的东西"内化"（省 token） | 替代评测——它只会让"不确定"变成"更自信的不确定" |

一句话：**微调改的是"行为与风格"，RAG 改的是"知识与事实"**。这也是 M5（day048~060）与 M6（day061~072）会紧挨着的原因——它们经常要一起上。

### 1.2 三条正交的坐标：改多少、怎么省、按什么信号改

`finetune/overview.py` 把五种方法组织成一张结构化常量表 `METHODS`，每个方法是一个 `MethodProfile`：

```python
@dataclass(frozen=True)
class MethodProfile:
    key: str
    full_name: str
    family: str                 # parameter-efficient / full-parameter / alignment
    data_need: str
    trainable_ratio_hint: str
    stability: str
    best_for: str
    artifacts: tuple[str, ...]  # 训练产物形态：要保存/部署哪些文件
    notes: str
```

`frozen=True` 是刻意的：**方法画像是一份知识常量**，任何代码路径都不该就地修改它。它同时是文档表格与 API 契约的**唯一数据源**——这正是 day047 复盘里那条"契约自带元信息"的思路，从运行期契约延伸到了知识常量。

五个方法的家族划分：

| 家族 | 方法 | 回答的问题 |
|------|------|-----------|
| `full-parameter` | `sft` | **改多少**：全部权重参与更新，能力上限最高 |
| `parameter-efficient` | `lora`、`qlora` | **怎么省**：只训一个低秩增量 `ΔW = B @ A` |
| `alignment` | `dpo`、`rlhf-ppo` | **按什么信号改**：优化目标不是"下一个 token 像不像标准答案"，而是"人更喜欢哪个回答" |

### 1.3 效果上限由数据决定，方法只决定能不能逼近

这是 M5 最重要的一句话。一次微调的效果上限在数据封版那一刻就固定了：方法（LoRA 还是全参）、超参（学习率、rank）、训练轮数，都只能决定你**逼近这个上限的程度**，不能提高上限本身。

推论有三条，直接决定今天的课程顺序：

1. **500 条以下先补数据**，换方法几乎无用——所以 `recommend_method` 会把这条警告无条件挂在所有分支上。
2. **数据质量问题会在训练中放大**：一条 `TODO 待补充` 的答案，模型学到的是"遇到难题就写 TODO"。
3. **数据的"可信度"必须可核对**：评估集里的轨迹能当训练数据，但必须先在答案层面核对一遍（第四节）。

而"清洗、去重、过滤、切分"这些动作——它们不产生新数据，只决定**哪些数据不该被学**。这是数据工程的全部内容。

## 第二章：选型 —— 把"怎么选"写成确定性规则

### 2.1 `recommend_method`：顺序判断，先命中先返回

```python
def recommend_method(
    *,
    examples: int,
    gpu_memory_gb: float,
    has_preference_pairs: bool = False,
    need_full_capability: bool = False,
) -> MethodRecommendation:
```

四条规则，每一步的"为什么"都写进返回的 `reasons`：

1. **`has_preference_pairs=True` → DPO**。手上已有偏好对，说明"哪个回答更好"的信号是现成的；DPO 可以直接在偏好数据上优化策略，不必像 RLHF-PPO 那样先训奖励模型再跑强化学习循环。`RLHF_PPO` **只在告警里作为"数据量不足时的别路"被提及**——它需要的算力与工程复杂度都高得多，不该做首选。
2. **`need_full_capability and gpu_memory_gb >= 80` → SFT**。80GB 是 A100/H100 级别单卡的显存门槛，也是"全参训一个 7B 模型"的现实下限（fp16 权重 + 梯度 + 优化器状态 ≈ 16 倍参数量）。
3. **`gpu_memory_gb < 16` → QLoRA**。低于 16GB 时 fp16 的基座都放不下，必须靠 4-bit 量化把权重压到 1/4。
4. **其余 → LoRA**。显存够载入 fp16 基座，就没必要承受量化的精度损失与额外训练时间。

返回值刻意把 `reasons` 与 `warnings` 分成两个字段：

```python
@dataclass
class MethodRecommendation:
    method: str
    reasons: list[str]
    warnings: list[str]
```

因为二者说话对象不同：**理由写给"为什么是它"，告警写给"选了它之后还得注意什么"**。把告警混进理由里，评审时很容易被当成理由的一部分而被忽略。

### 2.2 真实调用结果

下面五组输入的实际输出（`examples` / `gpu_memory_gb` 为输入）：

```text
[小样本 + 消费级显卡]  examples=200, gpu_memory_gb=8
  method = qlora
  reason : 显存受限（8GB < 16GB）：QLoRA 以 4-bit 量化加载基座，可在单张消费级显卡上完成训练。
  warning: 样本量偏少（200 条）：500 条以下微调极易过拟合，先补数据比换方法更有效。

[常规 + 24G 单卡]      examples=5000, gpu_memory_gb=24
  method = lora
  reason : 显存条件（24GB）足以承载 fp16 基座：LoRA 只训练低秩增量，在效果与成本之间性价比最高。

[有偏好对且充足]        examples=3000, has_preference_pairs=True
  method = dpo
  reason : 提供了偏好对（chosen/rejected）：DPO 可直接在偏好数据上优化策略，无需先训练奖励模型，
           工程链路比 RLHF-PPO 短得多。

[有偏好对但偏少]        examples=600, has_preference_pairs=True
  method = dpo
  warning: 偏好对仅 600 条：DPO 对偏好数据的规模与质量都很敏感，建议先扩到 1000 条以上；
           若受限于标注预算，RLHF-PPO 需要额外训练奖励模型与在线采样，成本只会更高。

[全参 + 80G]           examples=10000, gpu_memory_gb=80, need_full_capability=True
  method = sft
  reason : 需要完整能力且显存充足（80GB >= 80GB）：全参 SFT 更新全部权重，能力上限最高。
```

注意第三个和第四个的差别：**同样推荐 DPO，但一个带告警一个不带**。这就是"理由与告警分离"的价值——方法选型没变，但风险提示出现了。

### 2.3 `lora_trainable_ratio`：LoRA 省显存的算术

LoRA 冻结原权重 `W ∈ R^{d_out × d_in}`，只训练两个小矩阵 `A ∈ R^{r × d_in}` 与 `B ∈ R^{d_out × r}`，用 `ΔW = B @ A` 近似权重更新量（`r ≪ min(d_in, d_out)`）。于是：

```text
全参参数量  = d_in * d_out
LoRA 参数量 = r * (d_in + d_out)        # A 有 r*d_in 个元素，B 有 d_out*r 个
ratio      = r * (d_in + d_out) / (d_in * d_out)
```

代码就是一个纯函数：

```python
def lora_trainable_ratio(in_features: int, out_features: int, rank: int) -> float:
    if in_features <= 0 or out_features <= 0 or rank <= 0 or in_features * out_features == 0:
        raise ValueError(...)
    return rank * (in_features + out_features) / (in_features * out_features)
```

实测值：

| `(d_in, d_out, r)` | ratio | 百分比 |
|--------------------|-------|--------|
| (4096, 4096, 8) | `0.00390625` | 0.3906% |
| (4096, 4096, 16) | `0.0078125` | 0.7812% |
| (11008, 4096, 8) | `0.0026798691860465116` | 0.2680% |

第三行是 LLaMA 系列 FFN 的 `up_proj` 形状（4096 → 11008），rank=8 时只有约 **0.27%** 的参数需要训练。**显存的大头从来不是权重，而是梯度与优化器状态**（Adam 要为每个可训练参数存两份动量），所以把可训练参数压到千分之几，显存需求同步下降——这才是 LoRA 能在单卡上跑的算术基础。

参数非法时抛 `ValueError` 而不是返回 0 或 `inf`：比例无定义时宁可报错，也不能让一个 "0" 被下游误解成"不用训练"。

### 2.4 `render_methods_table`：文档由代码生成

```python
def render_methods_table() -> str:
    header = "| 方法 | 全称 | 家族 | 数据需求 | 可训练比例 | 稳定性 | 适用场景 |"
    ...
```

表格由代码生成而不是手写在 markdown 里，因为**文档里最危险的错误是"代码改了文档没改"**。做成函数后，文档只要贴一次输出，漂移立刻可见——这与 day047 复盘里"把提醒变成核对"是同一条工程直觉。

## 第三章：统一表示 —— 一个对象收敛三种格式

### 3.1 三种格式满天飞，先收敛到一个对象

指令微调的数据格式至少有三种主流写法，训练脚本各认一种，清洗规则又要各写一遍：

| 格式 | 常量 | 形状 | 典型来源 |
|------|------|------|---------|
| ALpaca | `ALPACA = "alpaca"` | `{"instruction", "input", "output"}` | 社区指令集、人工标注 |
| ShareGPT 风格 chat | `CHAT = "chat"` | `{"messages": [{"role", "content"}, ...]}` | 多轮对话、在线日志 |
| 纯续写 | `PROMPT_COMPLETION = "prompt-completion"` | `{"prompt", "completion"}` | 知识灌注、代码补全 |

`schema.py` 把它们收敛到同一个内存对象：

```python
@dataclass
class TrainingExample:
    instruction: str
    output: str
    input: str = ""
    system: str | None = None
    source: str = ""
    tags: tuple[str, ...] = ()
    license: str = ""
```

于是**"清洗一次、训练多种格式"成为可能**：清洗、去重、统计永远作用在 `TrainingExample` 上，只在落盘那一刻才用 `to_dict(fmt)` 投影回目标格式。这与 day046 流水线"阶段顺序固定、只在出口投影成契约"是同一种分层。

### 3.2 `parse_example`：必填字段与"只有空白算空"

```python
def parse_example(raw: dict, fmt: str = DEFAULT_FORMAT) -> TrainingExample:
```

三种格式的必填字段：alpaca 要 `instruction` + `output`（`input` 可空）；chat 要 `messages` 里**各含一条非空的 user 与 assistant**（system 可选）；prompt-completion 要 `prompt` + `completion`。

一个容易被写错的细节：

```python
if not instruction.strip():
    raise DatasetFormatError(f"{fmt} 格式的 instruction/prompt 不能为空")
if not output.strip():
    raise DatasetFormatError(f"{fmt} 格式的 output/completion 不能为空")
```

**`"   "` 是空**。如果没有 `.strip()`，一条 `output="\n\n"` 的脏样本会被判定"字段存在"，然后在训练时变成一个长度为零的目标——这类样本不会让训练报错，只会让模型学会"什么都可以不回答"。

chat 分支还刻意只支持**单轮**：找 system/user/assistant 各一条，多轮样本直接报错而不是静默截断成第一轮。因为多轮训练需要额外的 loss masking 策略（只对 assistant 段算 loss），当前不支持就该明确拒绝——**静默截断是数据工程里最危险的"善意"**。

### 3.3 两个"看起来多余"的设计

**（一）`to_alpaca()` 保留空的 `input` 键：**

```python
def to_alpaca(self) -> dict:
    return {"instruction": self.instruction, "input": self.input, "output": self.output}
```

字段时有时无会让下游的 schema 推断失败。**结构稳定比"少写一个空字符串"重要得多。**

**（二）`prompt_text` 的拼接规则：**

```python
@property
def prompt_text(self) -> str:
    if self.instruction and self.input:
        return f"{self.instruction}\n\n{self.input}"
    return self.instruction
```

`instruction` 是"要做什么"、`input` 是"待处理的材料"，两者之间需要一条视觉与语义的边界；只有 instruction 时直接返回它，避免多余前后空白污染 token 统计。

### 3.4 `source` / `tags` / `license`：数据治理元信息

这三个字段不参与训练，但决定模型权重能不能发布：

- **`source`**：来源可追溯。缺了它，后面无法按来源统计（`source_distribution`）、无法解释"这条数据哪来的"。
- **`tags`**：标签可筛。`is_safety_example()` 用 `"safety" in tags` 判定安全对齐样本——安全样本与普通指令样本在训练时常需要不同权重/不同阶段（**对齐税**：混得不好会损伤通用能力），所以需要一个显式判定，而不是让训练脚本去字符串匹配。
- **`license`**：**许可证会沿链条传染到模型权重**。"这条数据能不能商用"必须在采集那一刻就记下来，事后补是补不回来的。

顺带说 `_as_text` 的一个细节：`None → ""`，且非字符串走 `str()`。这一层看似啰嗦，但真实数据里字段类型漂移是常态（数字被写成 `123` 而不是 `"123"`），而 `None` 被 `str()` 变成字符串 `"None"` 是最隐蔽的脏数据。

## 第四章：采集 —— 异构来源的语义对齐

### 4.1 三个源，一个接口

采集层要解决的不是"读文件"，而是**异构来源的语义对齐**。`default_collector()` 装配三个源：

| 源 | 实现类 | 输入 | 转换逻辑 |
|----|--------|------|---------|
| `seed` | `JSONLSource` | `data/finetune/seed_examples.jsonl` | 已是 alpaca 格式，读进来即可 |
| `eval/agent_tasks` | `EvalTaskSource` | `data/eval/agent_tasks.jsonl` | ReAct 轨迹 + **答案核对** |
| `eval/redteam_cases` | `RedTeamSource` | `data/eval/redteam_cases.jsonl` | 攻击 payload → 安全拒答样本 |

三者实现同一个最小接口：

```python
class DataSource(ABC):
    @property
    @abstractmethod
    def name(self) -> str: ...

    @abstractmethod
    def load(self) -> list[TrainingExample]: ...
```

接口越窄，新增来源的成本越低：将来要从 HF datasets 拉数据，只需再写一个子类，采集与清洗的其余部分零改动——这与 day040 的 `supports_vision`、day041 的 `embed_batch` 是同一套"扩展抽象、零改动"哲学。

### 4.2 最关键的一节：评估集不能直接当训练集

`data/eval/agent_tasks.jsonl` 是本课程 M3 阶段造的 Agent 评估集，里面有 8 条任务，长这样：

```json
{"id": "task-01", "task": "计算 123 乘以 456 的结果", "expected_tools": ["calculator"],
 "answer_contains": "56088",
 "mock_responses": ["Thought: 这是一道乘法题，需要用计算器算\nAction: calculator\nAction Input: 123 * 456",
                    "Thought: 计算器返回了结果\nFinal Answer: 结果是 56088"]}
```

它能不能当 SFT 数据？**轨迹本身正是我们想让模型学会的行为**（思考 → 调工具 → 读结果 → 作答），但有一个前提必须先满足：**答案得是对的**。看两条真实的记录：

| id | `answer_contains` | 轨迹的 Final Answer | 结论 |
|----|------------------|-------------------|------|
| `task-01` | `56088` | `结果是 56088` | 包含 ✓ 可用 |
| `task-02` | `检索增强生成` | `检索增强生成（RAG）是一种结合检索与生成的技术` | 包含 ✓ 可用 |
| `task-03` | `1024` | `结果是 1024` | 包含 ✓ 可用 |
| **`task-04`** | **`56`** | **`答案是 99`** | **不包含 ✗** |
| **`task-05`** | **`225`** | **`150`** | **不包含 ✗** |
| `task-06` | 无该字段 | `8` | 无法核对 ⊘ 跳过 |
| `task-07` | `81` | `结果是 81` | 包含 ✓ 可用 |
| `task-08` | `14` | `结果是 14` | 包含 ✓ 可用 |

`task-04` 与 `task-05` 是评估集里**刻意造的坏轨迹**（M3 的 Agent 评估需要"失败样本"才能测出完成率），把它们当训练数据就是把 `7 × 8 = 99` 和 `15 × 15 = 150` 学进权重。`EvalTaskSource` 的实现把这段判断固化下来：

```python
expected = record.get("answer_contains")
if not expected:
    # 无法核对答案：评估集里的轨迹只标注了"期望工具"，
    # 没有 answer_contains 就没有判对错的标准，不进入训练集。
    self.skipped += 1
    continue
verified = str(expected) in final_answer
if verified:
    self.kept += 1
    tags = (TAG_FROM_EVAL, TAG_REACT_TRACE)
else:
    self.unverified += 1
    tags = (TAG_FROM_EVAL, TAG_REACT_TRACE, TAG_UNVERIFIED)
```

这里有一个刻意设计：**答案对不上的样本不是直接丢弃，而是打上 `unverified` 标签后交给清洗器**。为什么绕这一圈？因为清洗报告里出现 `unverified_source` 计数，才能**证明**"评估集轨迹不能无脑当训练数据"这条结论在流水线里真的被执行了，而不是写在注释里。实测统计：

```text
EvalTaskSource: kept=5  unverified=2  skipped=1
```

**5 / 2 / 1** 这三个数字就是"评估集 ≠ 训练集"的全部证据。

### 4.3 红队用例 → 安全对齐样本

`RedTeamSource` 做的事看起来反直觉：**把攻击用例当正样本**。理由是对齐训练需要的恰恰是"面对这类请求，标准动作是什么"的示范：

```python
SAFETY_REFUSAL_TEMPLATE = (
    "抱歉，这个请求涉及绕过安全限制或套取系统内部信息，我不能执行。"
    "如果你有正常的研究或学习需求，我很乐意在不违反安全规范的前提下提供帮助。"
)
```

把 `payload` 当 `instruction`、把 `SAFETY_REFUSAL_TEMPLATE` 当 `output`，就得到 16 条 `(危险请求 → 拒绝)` 的正样本，`category` 进 tags（`prompt_injection` / `jailbreak` / `pii_leak` / `tool_abuse`），方便按攻击类型统计覆盖率。

**拒答文案必须写死，不能让模型自由发挥**：安全样本的 output 是"标准动作"，必须稳定、可审计；若由模型生成，不同批次会得到不同措辞，反而把噪声引入训练。这与 day046 流水线里 `REFUSAL_REPLY` 是常量、不由模型生成，是同一条原则——**安全边界上的文本，确定性优先于文采**。

### 4.4 两种容错策略并存

阅读 `schema.py` 与 `collector.py` 会发现两个读 JSONL 的函数，策略刻意不同：

| 函数 | 策略 | 适用面 |
|------|------|--------|
| `schema.load_jsonl` | **严格**：解析失败直接上抛 | 离线固化的合法数据集，失败就要暴露 |
| `collector.iter_jsonl_records` | **宽松**：坏行 warning 后跳过，文件不存在也告警继续 | 线上采集，一行脏数据不该让整批作废 |

这不是重复实现，而是**两种正确性标准的显式区分**。`iter_jsonl_records` 的 docstring 把这条写得很直白："'这个源还没准备好'不该让整条流水线崩掉。"

## 第五章：清洗 —— 归一化 / 规则 / 去重

清洗被拆成三件可单独测试的事。**顺序是 清洗 → 规则 → 去重**，每一步都有非它不可的位置。

### 5.1 第一步：`clean_text` 的三段管道

```python
def clean_text(text: str) -> str:
    if not text:
        return ""
    normalized = unicodedata.normalize("NFKC", text)
    return normalize_whitespace(strip_control_chars(normalized))
```

实测效果：

```text
'ＲＡＧ  是什么\u200b？' -> 'RAG 是什么?'
'a\xa0b'                -> 'a b'
'第一行\n\n\n\n第二行'   -> '第一行\n第二行'
'  \t 多余空白  '        -> '多余空白'
```

三段各解决一类污染：

1. **NFKC 归一化**：把全角字母数字、兼容字符、**不间断空格（NBSP, U+00A0）**统一到标准形式。`"ＲＡＧ"` 与 `"RAG"` 归一后相同，`"a\u00a0b"` 与 `"a b"` 归一后相同。**没有这一步，去重会把同一句话当成两条。**
2. **剔除控制/格式字符**：零宽空格（U+200B）、方向控制符（U+202E）、BOM（U+FEFF）肉眼不可见，却会改变分词结果、破坏字符串比较，是数据清洗里最典型的"隐形污染源"。
3. **空白折叠**：连续空格/制表符压成一个空格、多行压缩、去首尾。

一个关键取舍：**`normalize_whitespace` 保留换行，不把 `\n` 压成空格**。因为 ReAct 轨迹、代码、步骤说明的语义都依赖换行（`Thought:` / `Action:` 各占一行），压成一行会把结构化数据变成一坨无法阅读的长文本——**训练时反而更难学**。

### 5.2 第二步：七条质量规则

```python
@dataclass(frozen=True)
class QualityRule:
    name: str
    reason: str
    check: Callable[[TrainingExample], bool]   # True 表示"通过"
```

真值方向是"返回 True = 通过"而不是"命中"。若反过来，调用处就会写出 `if any(not r.check(...))` 这种双重否定，评审时极易看错。

`default_rules` 生成的七条规则（顺序即优先级，第一条不通过即拒）：

| 顺序 | 规则名 | 拦截什么 |
|------|--------|---------|
| 1 | `output_too_short` | 输出不足 `min_output_chars`（缺省 8）字符 |
| 2 | `output_too_long` | 输出超过 `max_output_chars`（缺省 4000），多半是粘贴了长文 |
| 3 | `instruction_too_long` | 指令超过 `max_instruction_chars`（缺省 1000） |
| 4 | `empty_instruction` | 指令（或 prompt）为空 |
| 5 | `placeholder_output` | 输出含 `PLACEHOLDER_MARKERS = ("todo", "待补充", "lorem", "tbd", "fixme")` |
| 6 | `banned_pattern` | 指令或输出命中禁用词表（合规/版权风险） |
| 7 | `unverified_source` | 样本带 `unverified` 标签（答案未经核对） |

规则表可以整体注入（`rules=`）：给某个数据集定制"禁止出现某类表述"的规则时，不必去改 `default_rules`——那会让所有数据集一起变严。

### 5.3 第三步：去重为什么用 prompt 指纹

```python
def dedupe_key(example: TrainingExample) -> str:
    normalized = clean_text(example.prompt_text).lower()
    return hashlib.sha1(normalized.encode("utf-8")).hexdigest()[:DEDUPE_KEY_LENGTH]
```

三个设计点：

1. **只用 prompt（不含 output）做依据**。因为"同一个问题配两个不同答案"在监督微调里**不是冗余而是冲突**——两条都留着，模型学到的就是一个含糊的平均。去重把它们压成一条（保留首次出现），**把矛盾暴露给数据评审，而不是把矛盾喂给训练**。
2. **先清洗再取指纹**。这样"全角/半角不同""只差空白"的重复也能被识别。
3. **用 SHA-1 前 16 位而非原文**。16 位十六进制 = 64 bit，对万级样本规模的碰撞概率可以忽略，同时不把长文本常驻内存。

### 5.4 顺序错了，规则就形同虚设

`DatasetCleaner.run` 的三个阶段严格按顺序：

```python
cleaned = [self.clean_example(example) for example in examples]   # 清洗必须最先
...
for example in cleaned:
    failed = next((rule for rule in self.rules if not rule.check(example)), None)
    if failed is not None: ...
    if self.dedupe: ...                                          # 去重必须最后
```

- **清洗最先**：规则与指纹都要看"最终字符"。若拿原始文本判长度，一条 `"\n\n\n"` 的输出会以 3 个字符通过 `min_output_chars=8` 的门槛，却在训练时变成空样本。
- **去重最后**：先按规则把废样本丢掉，再对 survivors 取指纹。否则一个本该被拒绝的样本会抢先占位，把后面合法的重复项挤掉——**"保留首次出现"的前提是首次出现的那个本身合法。**

实测（5 条构造样本，1 条合法 + 1 条重复 + 1 条占位符 + 1 条过短 + 1 条 unverified）：

```text
清洗：输入 5 条 -> 保留 1 条，保留率 20.00%
drop_reasons = {'duplicate': 1, 'placeholder_output': 1, 'output_too_short': 1, 'unverified_source': 1}
前两条原始指纹是否相同 = True
决策明细：
  [kept]              RAG 是什么? | 通过全部质量规则
  [duplicate]         RAG 是什么? | 与前面样本重复（清洗+小写后的 prompt 指纹相同）
  [placeholder_output] 写个总结   | 输出含 TODO/待补充/lorem 之类占位符，答案并未真正完成
  [output_too_short]  写个总结    | 输出不足 8 字符（清洗后），信息量太低
  [unverified_source] 危险请求    | 样本带 unverified 标签：答案未经核对，不进入训练集
```

`FilterReport` 里"**丢弃多少、为什么丢**"是一个能印出来的数字，而不是一句"清洗过了"——这与 day046 `StageRecord` 把每阶段耗时与决定记进响应，是同一种"可观测"：

```python
@dataclass
class FilterReport:
    total: int
    kept: int
    rejected: int
    duplicates: int
    drop_reasons: dict[str, int]
    decisions: list[FilterDecision]

    @property
    def keep_rate(self) -> float:
        return self.kept / self.total if self.total else 0.0
```

注意 `keep_rate` 在空输入时返回 **0.0 而不是 1.0**：**没有数据不代表"全都合格"**——这与 day029 `retrieval_precision` 遇空召回集返回 0.0 是同一种边界纪律。

## 第六章：统计与切分 —— 训练前先把数据看清

### 6.1 `DatasetStats`：把数据的画像印出来

```python
@dataclass
class DatasetStats:
    count: int
    avg_instruction_chars: float
    avg_output_chars: float
    min_output_chars: int
    max_output_chars: int
    avg_estimated_tokens: float
    source_distribution: dict[str, int]
    tag_distribution: dict[str, int]
```

这些数字不是装饰，它们直接是超参选择的依据：

- **平均输出 88 字却把 `max_length` 设成 2048**，就是在浪费显存（还会拖慢训练）；
- **来源分布里某个源占了 90%**，就要警惕"训出来的模型只会说那一种话"；
- **标签分布**能看出安全样本的比例——安全样本太多会带来对齐税。

平均值保留原始 float（不做四舍五入），只在 `to_dict()` 输出时取两位小数：**把"计算"与"展示"分开，测试断言才不会被展示格式绑架**。

token 估算复用 day034 的 `TokenCounter`，且默认强制字符级估算：

```python
token_counter = counter if counter is not None else TokenCounter(prefer_tiktoken=False)
```

**统计脚本必须离线、确定、零依赖**——`tiktoken` 需要下载词表文件，会引入网络依赖与版本漂移。

空列表返回全零统计而不抛错，也是刻意的：清洗后一条不剩是一种**合法的中间状态**（说明门槛把所有样本都挡住了），此时调用方需要的是"0 条"这个事实，而不是一个异常——异常会让"为什么没数据"的排查被错误处理逻辑掩盖。

### 6.2 `split_dataset`：可复现，且两侧都非空

```python
def split_dataset(
    examples: Sequence[TrainingExample], *, eval_ratio: float = 0.2, seed: int = 42
) -> tuple[list[TrainingExample], list[TrainingExample]]:
    if not 0.0 <= eval_ratio < 1.0:
        raise ValueError(f"eval_ratio 必须落在 [0, 1) 区间，收到 {eval_ratio}")

    shuffled = list(examples)
    random.Random(seed).shuffle(shuffled)
    n = len(shuffled)
    if n == 0:
        return [], []
    eval_count = max(1, round(n * eval_ratio))
    eval_count = min(eval_count, n - 1)
    return shuffled[eval_count:], shuffled[:eval_count]
```

三个决定：

1. **`random.Random(seed)` 而不是全局 `random`**：不污染全局随机状态，测试与并发调用彼此隔离。
2. **可复现是硬要求**：同一份数据、同一个 seed 永远得到同一个切分。否则"这次评估涨了 2 个点"可能只是切分换了——**切分不稳定，评估就没有可比性**。
3. **`n >= 2` 时两侧都非空**（`eval_count` 下界 1、上界 `n-1`）：空评估集会让评估静默失效，而"评估集之外没有训练数据"更是退化的切分。`eval_ratio = 1.0` 直接拒绝，因为那必然导致训练集为空。

### 6.3 `dump_bundle`：格式在最后一刻才决定

```python
def dump_bundle(bundle, out_dir, *, fmt=ALPACA, eval_ratio=0.2, seed=42) -> dict[str, Path]:
    ...
    train, eval_set = split_dataset(bundle.examples, eval_ratio=eval_ratio, seed=seed)
    train_path = output_dir / "train.jsonl"
    eval_path = output_dir / "eval.jsonl"
    dump_jsonl(train, train_path, fmt)
    dump_jsonl(eval_set, eval_path, fmt)
    return {"train": train_path, "eval": eval_path}
```

**格式只在落盘那一刻投影**：上游的清洗、去重、统计全程作用在统一的 `TrainingExample` 上。要换格式（比如从 alpaca 改成 chat 喂给 ChatML 模板），改一个参数即可，前面的链路一行不动。

返回路径字典而不是"成功"布尔值：调用方需要能直接打印/上传这两个文件，把路径交出来比写日志更有用。

`dump_jsonl` 用 UTF-8 + `ensure_ascii=False`：中文样本若被转义成 `\uXXXX`，文件体积会膨胀数倍且人眼不可读——**数据文件是要被 review 的**。

## 第八章：接入 API 与配置

### 8.1 三个只读端点

```python
@router.get("/finetune/methods", response_model=FinetuneMethodsResponse)
def finetune_methods() -> FinetuneMethodsResponse:
    return FinetuneMethodsResponse(methods=[to_method_info(p) for p in METHODS.values()])
```

顺序即 `METHODS` 的字典插入顺序（稳定可断言）——"有哪些方法、各自适合什么"是产品文档与选型工具的公共数据源，不该由前端各写一份硬编码。

`POST /finetune/dataset/validate` 校验一批原始样本能否用于训练。它的关键设计是**不抛第一条错误就返回**：

```python
for index, raw in enumerate(req.examples):
    try:
        valid_examples.append(parse_example(raw, req.format))
    except DatasetFormatError as exc:
        if len(issues) < MAX_DATASET_ISSUES:
            issues.append(DatasetIssue(index=index, reason=str(exc)))
```

批量数据的价值在于"坏了几条、坏在哪"，只报第一条会让用户来回试错。`issues` 截断到前 `MAX_DATASET_ISSUES = 20` 条——一批脏数据可能有上万条问题样本，全量返回只会撑爆响应体，而首条错误通常已经暴露了问题模式。

请求体刻意收**未解析的原始字典**：

```python
class DatasetValidateRequest(BaseModel):
    format: str = Field(default="alpaca", ...)
    examples: list[dict] = Field(min_length=1, ...)
```

若要求调用方先自己解析，就等于把要检验的工作提前做了一遍。`min_length=1` 让空列表直接 422——"校验零条数据"不是一个有意义的请求。

`GET /finetune/dataset/stats` 跑一遍默认采集器给出画像，`source_distribution` 让"这批数据主要来自哪个源"一目了然。三个端点全部只读、只消费 `finetune` 包，不引入任何新的外部依赖。

### 8.2 错误码延续既有契约

| 情况 | 状态码 | 理由 |

## 第九章：R2 遗留项的收口

day047（R2 复盘日）做了一次**包装器可观测性核对**，发现的表格是：

| LLM 形态 | 持有 `usage_log` | `CostTracker` 直接归因 |
|----------|-----------------|----------------------|
| `MockLLM`（叶子） | 有 | 成功 |
| `CachedLLM`（缓存包装器） | **无** | `AttributeError` ← 遗留缺陷 |
| `ModelRouter`（路由包装器） | 无 | 传 `last_used_llm` 后成功（day046 已修） |
| `_TimedLLMProxy`（追踪代理） | 有（`__getattr__` 透传） | 成功 |

今天把它收口。修法与 day046 完全同构——**不要让包装器去伪造 `usage_log`，而是让它说清楚"我替谁说话"**：

```python
class CachedLLM(BaseLLM):
    @property
    def last_used_llm(self):
        """最后一次实际产生用量的叶子模型（day047 复盘遗留项）.

        透传规则：内层若自己也是包装器（例如 ``ModelRouter``），就继续
        向内取它的 ``last_used_llm``，把路由真正选中的叶子暴露给计费器；
        内层是普通客户端时直接返回它。
        """
        return getattr(self._llm, "last_used_llm", None) or self._llm
```

为什么这样就够：`IntegratedPipeline._account` 的取值链是

```python
target = getattr(self.llm, "last_used_llm", None) or self.llm
```

有了这个属性，`target` 会一路穿到真正产生 token 的那一层。

**这个改动不许改变任何既有行为**——`tests/test_wrapper_accounting.py`（8 例）专门守这条：

- `CachedLLM` 包住叶子 → `cached.last_used_llm is inner`；
- `CachedLLM` 包住 `ModelRouter` → 透传到路由选中的叶子；
- 经流水线首次请求 `cost_usd > 0`、`prompt_tokens` 与叶子 `usage_log` 一致；
- 第二次同问题命中缓存：`cost_usd == 0.0`、`len(mock.calls) == 1`（**命中确实没再调模型**）；
- 两次都断言日志里**不再出现**"不提供 usage_log"告警（`caplog`）。

实测（基于本日快照运行 day047 编程题的参考答案）：

```text
[1] 叶子可归因        -> 登记 1 条，total_tokens=2
[2] CachedLLM 透传     -> cached.last_used_llm is inner -> True，叶子持有 usage_log
[3] ModelRouter 归因   -> 登记 1 条（落到真正干活的叶子）
[4] _TimedLLMProxy     -> __getattr__ 透传，usage_log 可直接归因
[5] 流水线端到端       -> 首次 model=gpt-4o-mini cost=$0.00000075 tokens=2；
                          二次 cached=True model=cache cost=$0.0；底层调用次数=1
```

修复前，第 5 步只会得到"打一条告警 + 记 0"：**不报错，但账单失真**。这类缺陷比 500 更危险，因为它伪装成正常返回。

## 结语：三条可以带进 M5 的工程结论

1. **"没有人能靠"清洗过了"说服别人"**。`FilterReport` 的每一个拒绝原因都有计数、每一条决策都有 rule + reason + 样本预览；实测 41 → 37 的每一个数字都能指回具体样本。**数据工程的产出不是一份干净数据，而是一份能被审计的账本。**
2. **顺序是数据流水线里的"策略"**。清洗 → 规则 → 去重，与 day046 流水线的"护栏 → 缓存 → 生成 → 归因 → 审核 → 回写"是同一种东西：换一个顺序，规则就失效、安全就漏风，而**结果看起来仍然正常**。把顺序写成测试，比写在注释里可靠。
3. **评估集不等于训练集，但评估集里全是原料**。今天的 41 条里有 21 条直接来自 M3 的产出（7 条轨迹 + 16 条攻击样本）。**上一个阶段为"度量"造的数据，是这个阶段为"训练"准备的矿藏**——前提是你有一套核对与打标机制，能把"能用的"和"看着像能用的"分开。

> **诚实的说明**：37 条样本、8.4 万字符的数据集**不可能训出一个有用的模型**，它的设计目的是把"采集 → 清洗 → 统计 → 切分 → 落盘"的每个中间数字暴露出来，并让"评估集轨迹不可直接使用"这条结论可被验证。要得到有意义的微调数据，需要接入真实语料（线上 bad case、人工标注、领域文档问答），而流水线本身在这里已经完整跑通并被 168 个用例覆盖。

明天（day049）是**休息日/缓冲日**；day050 进入 **SFT 监督微调基础**：用 `transformers` + `Trainer` 在样本数据上跑通第一次训练流程，把今天产出的 `train.jsonl` / `eval.jsonl` 真正喂进模型。今天定下的三件事会在那一天全部派上用场：**格式（转成 token 序列）**、**切分（train/eval 不重叠）**、**画像（`max_length` 怎么设）**。
