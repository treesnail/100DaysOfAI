## 第一章：为什么"求导"这件事要写两遍

### 1.1 数值差分的两个优点与一个死穴

数值差分的思想简单到不需要推导：

```text
f'(x) ≈ (f(x+h) − f(x−h)) / (2h)
```

它的优点是**不依赖任何推导**——你只要会算函数值，就能算导数。
这使它成为唯一能独立验证"你的解析梯度对不对"的工具。

死穴有两个：

```text
① 贵        n 维梯度要 2n 次函数求值（中心差分）——10 万参数的模型不可行
② 只准到 1e-9   分辨率下限是 eps·|f|/(2h)（第三章会给它一个精确的表达式）
```

### 1.2 解析梯度的两个优点与一个死穴

解析式（手推的 `d(exp)/dx = exp`、`∂L/∂z = p − y`）精确、快、一次求值能拿到全部参数
的偏导数。它的死穴是**推导可能写错**，而且写错之后往往不报错：

```text
少乘一个因子        训练仍然在下降，只是慢一点（看起来像 lr 设小了）
符号写反            某些任务上仍然收敛（方向"大致"还对）
softmax 雅可比漏项  交叉熵的梯度**仍然是 p − y**（恰好抵消，见第十章）
```

### 1.3 于是这一课的架构是"两套 + 一次对照"

```text
calculus.py     数值差分：差分 / 梯度 / 方向导数 / 雅可比 / 步长误差实验
autograd.py     解析式 + 自动微分：把链式法则自动跑一遍
optim.py        更新公式：三个优化器 + 四种调度 + 两种裁剪 + 训练回路
gradcheck.py    对照：六项「解析 vs 数值」，逐点比较、容差由分辨率决定
```

**"两套实现"+ "一次对照"**是这一课与"一本数学书"的差别：
书里只需要正确，而工程里需要**能被证明正确**。

> 思考题：为什么 `gradcheck` 的六项里有一项（`autograd_chain`）与生产代码无关？
> 提示：前五项都在验证"某个公开函数的导数"，而这一项验证的是**我们自己的求导机制**。

## 第二章：三种差分与误差阶数——把结论量出来

### 2.1 三个式子，一次泰勒展开

```python
def forward_difference(function, x, *, step=DEFAULT_STEP) -> float:
    h = _checked_step(step)
    point = _checked_point(x)
    return (_evaluate(function, point + h) - _evaluate(function, point)) / h
```

中心差分是缺省，理由可以算出来：把两条泰勒展开相减，

```text
f(x+h) = f(x) + h f'(x) + h² f''(x)/2 + h³ f'''(x)/6 + O(h⁴)
f(x−h) = f(x) − h f'(x) + h² f''(x)/2 − h³ f'''(x)/6 + O(h⁴)
──────────────────────────────────────────────────────────────── 相减
f(x+h) − f(x−h) = 2h f'(x) + O(h³)            → 误差 O(h²)
```

**`h f''(x)` 这一项被减掉了**——这就是"多算一次函数值换一个数量级"的全部内容。

### 2.2 演示脚本第 1 节的实测（手算真值）

```text
  函数        点           真导数                  前向                  后向                  中心
  exp     1.0    2.71828183           1.359e-06           1.359e-06           1.635e-10
  sin     1.0    0.54030231           4.207e-07           4.208e-07           2.772e-11
  log     2.0    0.50000000           1.249e-07           1.250e-07           1.438e-11
  x³      2.0   12.00000000           6.002e-06           6.001e-06           7.892e-10
  1/x     4.0   -0.06250000           1.562e-08           1.561e-08           5.142e-12
```

后三列是**误差**（不是结果）：中心差分的误差比前向小 3 个数量级左右。
注意不同函数列的绝对量级不同（`sin` 的前向误差 4.2e-7、`x³` 是 6.0e-6）——
它由 `h·|f''|/2` 决定，而不是由 `h` 单独决定。

### 2.3 误差阶数：从"记住 O(h²)"到"量出 2.00"

`step_size_study(function, x, exact_derivative)` 对一串步长各算三种方法的误差，
`observed_order(method)` 用相邻两条读数算实测阶数：

```python
return math.log(error_first / error_second) / math.log(first.step / second.step)
```

演示脚本第 2 节（`f = exp` 在 `x = 1` 处）：

三行读数各自说明一件事：


### 2.4 阶数只在"截断误差主导区"有意义

把 `observed_order` 在**每两条相邻读数**上都算一遍（第 3 题的实测数据）：

```text
h = 1e-1 → 1e-2   前向 1.013    中心 2.000
h = 1e-2 → 1e-3   前向 1.001    中心 2.000
h = 1e-3 → 1e-4   前向 1.000    中心 1.888
h = 1e-5 → 1e-6   前向 0.987    中心 0.446
h = 1e-9 → 1e-10  前向 -0.856   中心 -1.247
h = 1e-12 → 1e-14 前向 -0.667   中心 -0.824
```

**末尾那些负数不是"阶数变负了"**，而是"误差不再随 h 单调下降"——
那里是舍入误差主导区，两条读数之比是一个随机量。

这就是为什么 `observed_order` 缺省只看**前两条**读数（`index=0`）：
在一个"混了两种机制"的区间上取平均，得到的数字既不是 1 也不是 2，
而是一个**看起来像结果**的中间值。

> 这一条比"记住 O(h²)"值钱得多：它说的是一件可迁移的事——
> **当一个量的行为由两种机制共同决定时，任何"总体统计"都不如"分段读"**。

## 第三章：步长、分辨率与"容差该取多少"

### 3.1 两类误差方向相反

```text
h 变小   截断误差下降（O(h) 或 O(h²)）
         舍入误差上升：f(x+h) − f(x−h) 是两个几乎相等的数相减，
         有效位被丢掉，而丢掉多少与 f 的量级成正比、与 h 成反比
```

交点就是实践最优步长。`best_step_for_central` 给出理论值：

```python
return (FLOAT_EPSILON / curvature) ** (1.0 / 3.0)
```

`f = exp` 在 `x = 1` 处曲率是 `e`，于是 `(2.22e-16 / 2.718)^{1/3} = 4.34e-6`——
与实测最优区间（1e-5 ~ 1e-7）一致。

### 3.2 一个真实的坑：`f''` 是量出来的，而测量有噪声

`best_step_for_central` 第一版写成"`|f''| <= eps` 就当作 0"。
跑测试时发现它对**直线函数**返回了 `6.3e-5`——比正确的 `eps^{1/3} = 6.06e-6` 大 10 倍。

原因很具体：`second_difference` 的分母是 `h²`，**舍入误差被放大 `1/h²` 倍**：

```text
f(x) = 3x + 1（真 f'' = 0），h = 1e-6
量出来的 |f''| ≈ 1.8e-3     ← 比真值大 15 个数量级，全是噪声
```

修法是把量出来的曲率与**它的噪声地板**比较，而不是与 `eps` 比较：

```python
noise_floor = 4.0 * FLOAT_EPSILON * max(magnitude, 1.0) / (DEFAULT_STEP * DEFAULT_STEP)
if curvature <= noise_floor:
    return FLOAT_EPSILON ** (1.0 / 3.0)
```

这条经验值得单独记：**一个"测量出来的量"必须与"它的分辨率"比较，
而不是与"理论上的 0"比较**。测试里把这件事直接断言下来：

```python
def test_measured_curvature_of_a_line_is_pure_noise(self):
    measured = abs(second_difference(lambda value: 3.0 * value + 1.0, 2.0))
    assert measured > 1e-6   # 真值是 0，量出来却不是
    assert measured < 1e-2   # 但它仍然落在噪声地板的量级内
```

### 3.3 二阶差分的步长必须更大（同一个道理的第二次应用）

`test_second_difference_of_cubic` 显式传了 `step=1e-4`：

```text
x³ 在 2 处，真 f'' = 12
h = 1e-6 → 量出 12.002843    （误差 2.8e-3，全是舍入）
h = 1e-4 → 量出 12.000000    （误差 < 1e-5）
```

分母是 `h²` 意味着"同样的相对舍入被放大 1e12 倍"。
用缺省步长写这条断言，测试会变成一条**在测浮点噪声**的测试。

### 3.4 分辨率公式：容差不能再拍脑袋了

`gradcheck.difference_resolution(magnitude, step)` 把上面这条链条写成一行：

```text
分辨率下限 = eps·|f| / (2h)

|f| ≈ 1      h = 1e-6   →  1.11e-10
|f| ≈ 30     h = 1e-6   →  3.33e-09
|f| ≈ 100    h = 1e-6   →  1.11e-08
```

于是 `GRADIENT_TOLERANCE = 1e-8` 这个数字**有出处了**：

```text
① 它比最坏那个案例（打分量级 10 → 分辨率 1.1e-9）高一个数量级
② 而"真的写错了"通常差 1e-3 以上——中间隔着五个数量级，区分度充足
```

第一版的容差是 `1e-9`，它在 `log_sigmoid`（`|f| ≈ 30`，分辨率 3.3e-9）上
报出了一条 `differs`：**两边都没错，是容差低于测量手段的分辨率**。

> 这一条是这一课最重要的工程结论：
> **低于分辨率阈值的容差只会产出假警报**，而假警报比"漏报"更坏——
> 它会让人去改一份本来正确的代码。

## 第四章：链式法则——在正确的点上取值

### 4.1 只有一条公式，只有一个易错点

```text
(f∘g)'(x) = f'(g(x)) · g'(x)
                     ↑ 最容易写错的地方：**在 g(x) 处取值**，不是 x
```

`calculus.chain_rule` 把两条路并排实现：

```python
overall = central_difference(composed, point)     # 整体：对复合函数做差分
product = 1.0
current = point
for function in reversed(tuple(functions)):
    product *= central_difference(function, current)   # 局部导数：在**此刻的点**上取
    current = _evaluate(function, current)             # 再把点向前推一层
```

演示脚本第 4 节（`d/dx sin(exp(2x))` 在 `x = 0`）：

```text
    整体（对复合函数做差分）      1.080604611736
    局部导数之积（从外往内乘）    1.080604611763
    手算   2·cos(1)·e⁰ = 2cos1 =  1.080604611736
```

第三条读数是**手算**的：三段局部导数分别是 `2`（内层的 `2x`）、`e^{2x}=1`（中间的 `exp`）、
`cos(e^{2x})=cos 1`（外层的 `sin`），乘起来恰好 `2cos 1`。

### 4.2 `compose` 的方向必须写下来

```python
def compose(*functions):
    def composed(value):
        result = value
        for function in reversed(functions):
            result = function(result)
        return result
    return composed
```

```text
compose(f, g)(x) == f(g(x))     与数学上的 f ∘ g 同一个方向（右到左）
```

写成"从左到右"也"看起来对"，而两种读法的数值结果完全不同——
因此这条约定必须写在 docstring 里，并且有一条测试钉住它。

## 第五章：反向传播——把链式法则自动跑一遍

### 5.1 每个节点记三样东西

```python
class Scalar:
    value        它现在的值
    grad         损失对它有多敏感（从 0 开始，用 += 累积）
    _parents     它的父节点（图的边）
    _propagate   局部导数规则：接收**本节点的梯度**，往父节点推
```

`d(x·x)/dx = 2x` 不是"记住的"，而是从"乘法的局部导数是另一个乘数"这条规则里
自己长出来的：`x·x` 的两条边都会把 `x` 的梯度各加一份，于是得到 `2x`。

演示脚本第 5 节把整张图打印出来（`y = x·x`，`x = 3`）：

```text
  节点                运算                 值          梯度
  x                 leaf         +3.0000     +6.0000
  nodemul           mul          +9.0000     +1.0000
```

**`x` 的梯度是 6，不是 3。** 这是全课最值钱的一行。

### 5.2 这一课真的踩到的那个 bug

第一版 `_from` 是这么写的（错误版本）：

```python
propagate=lambda: _accumulate((self, other_node), (self.grad, self.grad))
```

`self` 在闭包里指向**左操作数**，而不是"刚刚造出来的这个加法节点"。
于是加法把左操作数的旧梯度当作上游梯度传下去。

危险的形状是这样的：

```text
只有一条链、且左操作数是叶子时，它**恰好算出正确结果**
（叶子的 grad 初值 0，而 `x + 1` 的上游梯度正好等于……不，等等——
正确结果来自 0 被覆盖，因此单链上"看不出来"，而分支上立刻错）
```

在冒烟测试里，复合表达式 `(x·y + e^y) / (1 + x²)` 的梯度是 `(0.4, 1.049)`，
而手算应当是 `(-0.568, 0.772)`——**两个分量都错**。

修法是把 `propagate` 的签名改成接收上游梯度：

```python
propagate=lambda upstream: _accumulate((self, other_node), (upstream, upstream))
# backward() 里：
for node in topological_order(self):
    node._propagate(node.grad)
```

这条 bug 的教训不是"要小心"，而是**它的护栏必须是"与独立方法对照"**——
`gradcheck` 的 `autograd_chain` 那一项（`autograd` 的梯度 vs 数值差分）
在第一时间就会报 `differs`，误差 `2.88`（而不是 1e-10）。

### 5.3 拓扑序：为什么必须用迭代

```python
stack: list[tuple[Scalar, bool]] = [(root, False)]
while stack:
    node, expanded = stack.pop()
    if expanded:
        order.append(node)
        continue
    ...
```

一条 2000 层的加法链在**递归**实现下会直接撞上 Python 的缺省递归上限（1000），
而 `RecursionError` 与"模型太大"在日志里长得不一样、在直觉里却容易被归成一类。
测试里有一条专门的用例（`test_deep_chain_does_not_hit_the_recursion_limit`）。

### 5.4 累积：写成 `=` 会给出一个"可以解释得通"的错值

```python
def _accumulate(nodes, contributions):
    for node, contribution in zip(nodes, contributions):
        if node.requires_grad:
            node.grad += contribution       # ← 全模块唯一写梯度的地方
```

三条"不报错但结果错"的形状：

```text
x · x           两条边 → 6    （写成 = 会得到 3，看起来像 lr 设小了）
x + x           两条边 → 2    （写成 = 会得到 1）
x·x·x           三条边 → 12   （写成 = 会得到 4）
```

全模块只有 `_accumulate` 一处写梯度，就是为了让"用 `+=` 而不是 `=`"这条纪律
**只有一处可能被写错**。

### 5.5 定义域拒绝：不是安静地给 inf/nan

演示脚本第 7 节的实测：

```text
  log(0)     → NumericError: log 的自变量必须为正，收到 0.0：x = 0 时对数是 −inf…
  sqrt(0)    → NumericError: sqrt 的自变量必须为正，收到 0.0：0 处的导数是 1/(2·0)…
  1/0        → NumericError: 除数是 0：除法在这个点没有定义…
  0^0.5      → NumericError: 0 的 0.5 次幂没有定义：导数公式 n·x^(n−1)…
  (−2)^0.5   → NumericError: 负数的 0.5 次幂在实数范围内没有定义…
```

每一条消息都包含"下一步该走哪"。这与 day073 的 `errors.py` 是同一种写法：
**报错的目的不是拦住调用方，而是让它知道该做什么。**

## 第六章：优化器——三种更新公式，两种地形

### 6.1 一行公式，三个问题

```text
θ_{t+1} = θ_t − lr · g_t
             └┬─┘   └┬┘
          走多远   往哪走
```

```text
① 方向不只是梯度       动量把历史梯度累成"速度"，冲过平坦区、压住抖动
② 步长不该人人相同     Adam 用二阶动量给每个参数各自的等效步长
③ 步长不该一成不变     学习率调度：先热身、后退火（第八章）
```

### 6.2 三个更新公式（口径表里的原文）

```text
sgd        g = ∇f(θ);  θ ← θ − lr·g
momentum   g = ∇f(θ);  v ← β·v + g;  θ ← θ − lr·v
adam       m ← β₁m + (1−β₁)g;  v ← β₂v + (1−β₂)g²;
           m̂ = m/(1−β₁ᵗ);  v̂ = v/(1−β₂ᵗ);  θ ← θ − lr·m̂/(√v̂ + ε)
```

`OPTIMIZER_UPDATE_FORMULAS` 这张表是"可复核"的来源：
报告里能读到**这一层实际执行的是哪一行**，而不是"它大概是个 Adam"。

### 6.3 动量：累加型 vs EMA 型（一个不能混的地方）

本实现用**累加型**（Polyak 原始形式）：`v ← β·v + g`，速度的稳态幅度是 `g/(1−β)`。
`β = 0.9` 时是梯度的 **10 倍**（第 19 题的实测：`v` 收敛到 10、`β = 0.99` 时收敛到 100）。

另一种常见写法是 EMA 型：`v ← β·v + (1−β)g`。两者可以通过
"把 lr 除以 (1−β)"互相换算，但**不能混着用**：

```text
混用的后果    等效学习率差一个 1/(1−β) = 10 倍的因子
它看起来像     "换了优化器之后需要重新调 lr"
```

### 6.4 演示脚本第 8 节：同一批优化器，两种地形

```text
碗形 (x−1)² + 4(y+2)²，100 步             峡谷 x² + 20y²，60 步
SGD    lr=0.05  →  损失 0.000000          SGD    lr=0.01  →  损失 0.796841
动量    lr=0.05  →  损失 0.002793          动量    lr=0.01  →  损失 0.002437
Adam   lr=0.20  →  损失 0.000131          Adam   lr=0.10  →  损失 0.029205
```

读法**不是**"Adam 最好"：

```text
碗形（曲率相同）   三者差别很小，SGD 甚至最快——它没有额外状态要维护
峡谷（曲率差 20 倍）SGD 明显最差（在陡方向反复横跳），动量与 Adam 都把它压住了
```

**"哪个优化器更好"这个问题离开地形就没有意义。**
这也解释了为什么 `minimize` 的 `notes` 里要写清"梯度由数值差分给出"——
否则"优化器对不对"与"梯度算得对不对"两件事会混在一起。

### 6.5 `minimize` 的三个长度（刻意不一致）

```text
losses          长度 steps + 1    含**初始损失**
learning_rates  长度 steps        第 i 个是第 i+1 步真正用的 lr
params          长度 steps + 1    含初始参数
```

`losses[0]` 是"还没迈步时的损失"——没有它，"下降了多少"就没有参照点。
`TrainingTrace.__post_init__` 会拒绝任何其他长度组合：

```python
if len(self.learning_rates) != len(self.losses) - 1:
    raise NumericError("学习率比损失**少一个**（初始损失没有对应的学习率）。")
```

## 第七章：Adam 的偏差修正

### 7.1 两个动量都从 0 出发，于是前几步都偏小

```text
m₁ = (1−β₁)g = 0.1g          只有真值的 1/10
v₁ = (1−β₂)g² = 0.001g²      只有真值的 1/1000
```

不做修正时第一步的更新量：

```text
lr·0.1g / (√0.001·|g|) = lr·3.16      ← 比设定值大 3 倍
```

### 7.2 修正之后恰好是 `lr·sign(g)`

演示脚本第 12 节的实测：

```text
  梯度 g =    +1.0  →  第一步位移 -0.099999999   lr·sign(g) = -0.100000000
  梯度 g =    -1.0  →  第一步位移 +0.099999999   lr·sign(g) = +0.100000000
  梯度 g =   +0.01  →  第一步位移 -0.099999900   lr·sign(g) = -0.100000000
```

三行合起来说明一件事：**第一步的位移与 `|g|` 无关**。
`test_adam_first_step_is_lr_times_sign` 把这条结论断言下来，
`test_unbiased_first_step_would_be_over_three_times_larger` 把它**没有修正时**的样子
也断言下来——两个数字并排，修正的必要性就不需要再解释了。

### 7.3 推论：为什么后期需要退火

梯度恒定时每步位移都是 `lr`（推导：`m̂/√v̂ = sign(g)`，两个修正因子恰好抵消）。
好处是"不同尺度的参数走得一样快"，副作用是**后期会在最优点附近来回抖**：
在凸问题上 Adam 不保证收敛，因此有了第八章的退火。

### 7.4 两个修正因子的速度差 10 倍

```text
β₁ = 0.9     第 1 步 1 − 0.9   = 0.1      第 50 步 ≈ 0.995    基本到位
β₂ = 0.999   第 1 步 1 − 0.999 = 0.001    第 50 步 ≈ 0.049    还很远
```

`0.999^1000 ≈ 0.37`——"二阶动量的偏差修正在前 1000 步内一直重要"
不是一句经验之谈，而是这条衰减曲线的直接读数。

## 第八章：学习率调度——一个"先升后降"的形状

### 8.1 两个方向相反的需求

```text
前期 lr 太大   随机初始化时梯度方向信息量很低，一大步就把参数推到坏区域
               → 热身（warmup）：把 lr 从 0 附近线性拉到 base_lr
后期 lr 太大   已经接近谷底，大步会来回横跳（loss 曲线开始震荡）
               → 退火（cosine / step_decay）：把步长收小
```

两种需求方向相反，因此"一个调度同时满足两者"的唯一形式是**先升后降**——
`warmup_cosine` 就是它的最小实现。

### 8.2 四种调度（`step` 一律 1-based）

```python
def step_decay_schedule(step, *, base_lr, drop_every, gamma=0.1):
    ...
    return base * gamma ** ((current - 1) // drop_every)
```

演示脚本第 9 节的实测（`base_lr = 0.1`）：

```text
  调度              t=1      t=2      t=3      t=4      t=5      t=10
  constant      0.100000  0.100000  0.100000  0.100000  0.100000  0.100000
  step_decay    0.100000  0.100000  0.100000  0.050000  0.050000  0.012500
  cosine        0.100000  0.096985  0.088302  0.075000  0.058682  0.000000
  warmup_cosine 0.025000  0.050000  0.075000  0.100000  0.093301  0.000000
```

### 8.3 三处"写掉一个字符就错"的地方

```text
① ⌊(t−1)/drop_every⌋ 里的 −1
   写掉它会让第 drop_every 步**提前一步**掉档——任何曲线上都看不出来

② cosine 的分母用 T−1 而不是 T
   用 T 时第 10 步是 0.002447（手算 0.1·(1+cos(0.9π))/2），永远到不了 min_lr

③ warmup 的第 1 步是 base_lr/warmup，**不是 0**
   写成 0 时第一次更新完全不发生，日志里表现为
   "第 1 步的 loss 与初始 loss 一模一样"——看起来像"梯度算错了"
```

第 ③ 条特别值得记：它把一个"看起来只是保守一点"的选择，
变成了一个**会被误诊为 bug 的现象**。

### 8.4 常数调度是基线，不是旧方案

```text
没有常数调度，"调度有没有用"这个问题无法回答——两条曲线必须能对比
```

这与 day073 里"零向量的三种约定"是同一种工程判断：
一个方案的价值往往由**它被拿来对比的那个基线**决定。

## 第九章：梯度裁剪——"生效"必须可读

### 9.1 两个原语，行为不同

```python
def clip_by_global_norm(grads, max_norm) -> tuple[Vector, float]:
    length = math.sqrt(math.fsum(value * value for value in checked))
    if length <= limit:
        return checked, 1.0
    scale_factor = limit / length
    return tuple(value * scale_factor for value in checked), scale_factor
```

演示脚本第 10 节：

```text
  原始梯度 (100.0, 1.0)   ‖g‖ = 100.0050
  整体范数裁剪到 10：(9.9995, 0.099995)  缩放系数 0.099995
    方向不变（整体缩放）——这是"这一步走多长"的约束
  逐分量裁剪到 ±1：(1.0, 1.0)
    方向**变了**：从几乎水平变成 45°——它只适合"个别分量爆炸"的场景
```

### 9.2 为什么返回缩放系数

```text
只给梯度的话，一串"看起来正常"的数既可能是没裁剪，也可能已经被缩了 50 倍
```

这与 day073 的"每种变体都在报告里记下自己的 scale 与温度"是同一条纪律：
**一个改变了行为的开关，必须在输出里留下痕迹。**

## 第十章：六项梯度对照——公式只有一份真相

### 10.1 与 `bridge` 的关系

```text
bridge（day073）    我们的 cosine/softmax/sigmoid 与生产实现的**值**是否逐位一致
gradcheck（今天）   我们的**解析梯度**与对生产实现的**数值差分**是否逐点一致
```

演示脚本第 11 节的实测：

```text
  梯度对照 6 项：一致 6、分歧 0 | 最大误差 1.04e-08
    [agrees] softmax 39 个点，最大误差 1.82e-10（相对 1.82e-10）
    [agrees] cross_entropy 13 个点，最大误差 5.73e-10（相对 5.73e-10）
    [agrees] sigmoid 7 个点，最大误差 6.28e-11（相对 6.28e-11）
    [agrees] log_sigmoid 7 个点，最大误差 1.03e-09（相对 1.03e-09）
    [agrees] perplexity 5 个点，最大误差 1.04e-08（相对 1.46e-10）
    [agrees] autograd_chain 8 个点，最大误差 1.99e-10（相对 1.99e-10）
```

注意 `perplexity` 那一行的两个数字：**绝对误差 1.04e-8 而相对误差 1.46e-10**。
它的分量量级是 100，所以同样的绝对误差只相当于 1e-10 的相对误差。
这正是判据要按量级缩放（`max_scaled_gap`）的理由。

### 10.2 这一课最想讲清的性质：雅可比会被抵消

对 `L = −log p_y`，链式法则给出

```text
∂L/∂z_j = (∂L/∂p_y) · (∂p_y/∂z_j) = (−1/p_y) · p_y(δ_{yj} − p_j) = p_j − onehot(y)_j
```

第 32 题的实测（`z = (1, 2)`、`y = 1`、`p = (0.268941, 0.731059)`）：

```text
雅可比          (0.196612, -0.196612)
                (-0.196612, 0.196612)      每一行之和恰好为 0
−J[:,y]/p_y     (0.268941, -0.268941)
p − onehot(y)   (0.268941, -0.268941)      ← 与上一行逐位相同
```

于是得到一个反直觉的结论：

```text
**雅可比写错时，交叉熵的梯度看起来仍然正确**（只要实现走的是 p − onehot 这条路）。
```

因此"softmax 的雅可比"必须**单独比一次**——否则它没有任何护栏。
测试 `TestSoftmaxJacobianCancellation` 把这条等式直接断言下来，
而不是只在教程里说一句"它会被抵消"。

### 10.3 为什么只有两种结论

```text
bridge     三种：agrees / differs / rejected
gradcheck  两种：agrees / differs
```

`rejected` 的含义是"一边拒绝了这个输入、另一边给了值"——
那是两个**不同用途**的实现之间的约定差异（例如零向量的归一化）。

本模块两侧都是我们自己算的、输入由我们选定，因此不存在这种情况。
一个具体的例子：`perplexity` 的定义域是 `[0, ∞)`，最初把 `L = 0.0` 放进了样本，
中心差分去取 `−1e-6` 时生产实现（正确地）抛了 `SFTLossError`。
正确的处理是**换掉这个样本**（改成 `0.25`），而不是记一条"记录的差异"：

```python
#: 为什么没有 0.0：中心差分要在两侧各取一个点，而 perplexity 的定义域是 [0, ∞)……
PERPLEXITY_INPUTS: Vector = (0.25, math.log(2.0), 1.0, math.log(100.0), 3.0)
```

### 10.4 六项里唯一"与生产代码无关"的一项

`autograd_chain` 比的是**我们自己的求导机制**：5 个复合表达式（含 1~3 个输入、
含 `sqrt`/`sin`/`tanh`/`relu`/`log`/`exp`），逐点比较自动微分与数值差分。

其中两个表达式**故意**写成"同一个输入走两条路径"：

```text
x·x 与 tanh(x)·relu(x+1)     漏了累积的实现会在这里少算一半
```

这正是第五章那个 bug 的护栏——它在第一版实现上给出的误差是 `2.88`，
而不是 `1e-10`。

## 第十二章：这一课踩到的四个坑

### 12.1 `propagate` 读错了梯度（第五章 5.2）

第一版闭包写成 `self.grad`，加法把左操作数的旧梯度当上游梯度传下去。
冒烟测试里 `(x·y + e^y)/(1+x²)` 的梯度是 `(0.4, 1.049)`，手算应是 `(-0.568, 0.772)`。
**两个分量都错**，而且没有任何异常。

修好之后，`autograd_chain` 那一项的最大误差从 `2.88` 降到 `1.99e-10`。

### 12.2 容差低于分辨率（第三章 3.4）

第一版 `GRADIENT_TOLERANCE = 1e-9`，它在 `log_sigmoid`（`|f| ≈ 30`）上报了 `differs`，
而两边都对。修法是**把容差由分辨率算出来**，并把这条理由写进常量注释：

```python
#: 为什么不是 1e-9：中心差分自身的误差下限是 eps·|f|/(2h)……
```

### 12.3 `f''` 的噪声（第三章 3.2）

`best_step_for_central` 对直线函数返回 `6.3e-5`（正确值 `6.06e-6`）。
根因是"二阶差分的噪声被 `1/h²` 放大"。修法是**与噪声地板比较**而不是与 0 比较。

### 12.4 三个"测试自己有问题"的例子

这一课有三条断言的**第一版是错的**，而错在测试而不是实现：

```text
① 后向差分"在 log 的左端点可用"      log 在 0 处没有定义，f(0) 先炸——换成正弦？
                                    最终改成 √(1−x) 在右端点 x = 1（只有左侧有定义）
② 温度案例的"最优步长 = 6.06e-6"      那是 |f''| = 1 时的值；exp 在 1 处曲率是 e，
                                    正确值是 (eps/e)^{1/3} = 4.34e-6（手算可得）
③ 拓扑序"x 必须是最后一个"            图上还有两个常量节点，它们的拓扑位置与 x 不可比；
                                    改成"x 在两个中间节点之后"
```

带走的结论：**测试的价值在于它独立于实现**——
因此"期望值"要么是手算的，要么来自一条能写下来的公式；
"上一次跑出来的值"不是期望值，它是**实现的影子**。

## 第十三章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 三种差分并存，中心为缺省 | 误差阶数 1 → 2 的代价只是多一次求值 | `calculus.py` |
| 求和一律 `fsum` | 顺序累加的误差随维度线性累积（day073 的延续） | 全部算子 |
| 误差必须量出来 | `observed_order` 给出实测 1.01 / 2.00，而不是"记住 O(h²)" | `StepSizeStudy` |
| 阶数只在截断主导区算 | 混了两种机制的区间上取平均得到一个没有意义的数 | `observed_order(index=0)` |
| 曲率与**噪声地板**比较 | 量出来的 `f''` 在直线上是 1.8e-3（全是噪声） | `best_step_for_central` |
| 容差由分辨率决定 | 低于分辨率的容差只产出假警报（比漏报更坏） | `GRADIENT_TOLERANCE` |
| 判据按量级缩放 | 导数为 100 的量不该被绝对阈值卡死 | `max_scaled_gap` |
| 链式法则"在正确的点取值" | 局部导数吃的是**推进后的点** | `chain_rule` |
| 梯度 `+=` 累积 | 一个值走 k 条路径，梯度是 k 份之和 | `_accumulate` |
| `propagate` 吃上游梯度 | 闭包里的 `self` 是左操作数——**这一课真的踩了** | `Scalar._from` |
| 拓扑序用迭代 | 2000 层链会撞上递归上限，而报错容易被归成"模型太大" | `topological_order` |
| 定义域当场拒绝 | `inf`/`nan` 会一路污染到报告里的均值 | `log` / `sqrt` / `div` / `pow` |
| 动量用累加型并写明 | EMA 型混用会让等效 lr 差 10 倍，看起来只是"风格不同" | `MomentumOptimizer` |
| Adam 偏差修正 | 不修正时第一步是 `lr·3.16`，看起来只是"前期有点抖" | `AdamOptimizer` |
| 修正后第一步 = `lr·sign(g)` | 两个修正因子恰好抵消，可逐位断言 | `test_adam_first_step_...` |
| 调度 1-based 并写下来 | 0/1-based 混用时热身少一步、退火早一步 | `_checked_step_number` |
| warmup 第 1 步不是 0 | 写成 0 的现象会被误诊为"梯度算错了" | `warmup_cosine_schedule` |
| 裁剪返回缩放系数 | "生效"必须在输出里留下痕迹 | `clip_by_global_norm` |
| 三长度刻意不一致 | `losses[0]` 是"下降了多少"的参照点 | `TrainingTrace` |
| 两种对照结论 | 两侧都是自己算的，不存在"一边拒绝一边放行" | `GRADIENT_STATUSES` |
| 雅可比单独比一次 | 它在交叉熵的梯度里会被抵消 | `check_softmax_jacobian` |
| 本课不加配置项 | 判据进函数参数，进配置会让"改了容差=改了结论" | `types.FLOAT_EPSILON` |
