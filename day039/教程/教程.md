## 第一章：为什么需要流式 —— 一次性与流式的本质区别

### 1.1 正确的同一性，体验的鸿沟

先澄清一个容易误解的点：**流式不改变回复的内容**。同一个模型、同一次调用，`stream=False` 拿到的是完整文本，`stream=True` 拿到的是按 token 顺序到达的一串增量，两者按序拼接后**完全相等**。我们的实现把这一点固化为协议契约（见第二章）——流式是一次性的**另一种传输方式**，不是另一种模型。

那为什么还值得做？因为体验差距出现在**时间**上。衡量交互式 AI 体验有两个关键指标：

- **TTFT（Time To First Token，首字延迟）**：从用户发出请求到屏幕上出现第一个字的时间；
- **总耗时**：从请求到完整回复结束的时间。

流式对这二者影响截然不同。假设模型生成 500 字需要 5 秒，且这 5 秒均匀分布（每秒 100 字）：

```text
一次性：TTFT = 5 秒（最后一个字也没比第一个字早），总耗时 = 5 秒
流  式：TTFT ≈ 0.5~1 秒（首个 token 到达即可渲染），总耗时 ≈ 5 秒
```

总耗时几乎没变，但 **TTFT 从 5 秒降到 1 秒以内**。对用户来说，"1 秒后开始看到字、边看边等"与"盯 5 秒空白再看到全部"，是两种完全不同的产品。学术界和业界把这类优化概括为**感知性能**：实际耗时不变，但用户**感觉到**快了。

### 1.2 流式靠什么实现：自回归生成天然是可流式拆分的

day034 讲过 GPT 类模型是**自回归**的：每生成一个 token，就把它拼回输入、预测下一个，直到输出结束符。这个机制带来一个天然属性——**输出是逐个 token 产生的**。流式只是把这个属性透传了出来：上游每产出一个 token，就往下游推一块，而不是攒满整段再一起返回。

因此流式的实现不需要"把一个完整回答切成碎块"（那是 MockLLM 用来**模拟**的简化做法），而是把模型自回归的中间产物**原样转发**。第二章会看到，OpenAI 兼容接口通过 `stream=True` 直接拿到这些增量。

### 1.3 流式要付出的代价

流式不是免费午餐，代价有三处，今天都要面对：

1. **协议更复杂**：一次性是"一个请求一个 JSON"，流式是"一个请求一串事件"，客户端要从解析 JSON 改成解析事件流；
2. **错误语义更难**：一次性失败返回 4xx/5xx；流式可能已推了一半才失败，客户端要能处理"半截流"；
3. **部分流程不适合流式**：需要"一次成型、整体可用"的场景（如 function calling 返回结构化工具调用、Agent 的执行轨迹）流式收益很小甚至有害。

这解释了为什么我们**只给 `/chat` 加流式**，而不给 `/agent/run` 加：Agent 的每次 LLM 调用要么是决策（要完整的 tool_calls 才能执行）、要么是最终答案，且响应里还带 `steps`/`tool_calls` 审计轨迹，中途往下推没有意义。**流式适配的是"纯文本、人直接消费"的对话场景**。

## 第二章：分层实现流式 —— `BaseLLM.stream` 协议

### 2.1 协议：片段按序拼接必须等于一次 chat 的完整回复

流式的改动首先发生在 LLM 抽象层，而不是 API 层。在 `llm/base.py` 里给抽象基类加一个方法（关键契约写在注释里）：

```python
def stream(
    self,
    messages: list[Message],
    temperature: float = 0.7,
    max_tokens: int = 1024,
) -> Iterator[str]:
    """逐片段流式返回文本回复.

    默认实现把 chat 的完整回复作为**一个**片段 yield——对不支持真
    流式的实现而言，协议上仍是流式、内容不缺失。支持逐 token 增量返回
    的客户端覆写本方法。

    子类覆写契约：yield 出的片段按顺序拼接，必须等于一次 chat 的完整回复。
    """
    yield self.chat(messages, temperature=temperature, max_tokens=max_tokens)
```

理解这个设计的三层含义：

1. **默认实现是"降级安全"的**：任何只实现了 `chat` 的旧 LLM（比如只重写 `chat` 的测试桩、某些不支持流式的厂商），调用 `stream` 会自动退化成"把完整回复当一片 yield"。协议上是流式，内容一个不少。这一条让流式能力**向后兼容**——加流式不需要所有实现立即跟进。
2. **返回类型是生成器**（`Iterator[str]`）：函数体含 `yield`，调用时**不执行**，只有遍历时才真正调用 `chat`。这个惰性降到 Router 层时至关重要（见第四章的降级语义）。
3. **契约为测试提供不变量**："拼接 == chat" 是流式正确性的唯一判据。所有流式测试都可以写成：`"".join(llm.stream(...)) == llm.chat(...)`。

### 2.2 真流式：`OpenAICompatibleLLM.stream`

`llm/openai_compatible.py` 覆写了 `stream`，接的是 OpenAI SDK 的流式接口：

```python
def stream(self, messages, temperature=0.7, max_tokens=1024):
    stream = self._client.chat.completions.create(
        model=self._model,
        messages=[m.to_dict() for m in messages],
        temperature=temperature,
        max_tokens=max_tokens,
        stream=True,          # 关键：声明要增量响应
    )
    for chunk in stream:
        delta = chunk.choices[0].delta.content
        if delta:
            yield delta
```

两个细节值得单独说：

- **`stream=True` 让 HTTP 连接以 SSE/sse 形式持续推送**：SDK 返回一个可迭代对象，每次迭代是一个 chunk，而不是一个完整响应体。真正的网络层差别是——非流式是"一次 request-response 拿到全部"，流式是"保持连接、上游推一块我收一块"。
- **为何要 `if delta:` 过滤**：流式响应的首个 chunk 通常只有 `role` 字段（`delta.content` 为 `None`），后续 chunk 才带 `content` 增量，最后一个可能是空 content 的结束标记。直接把 `None` 或空串推给上层，会造成"首片是噪音、尾部有脏数据"。过滤后，上层拿到的**每一片都是有用文本**。

### 2.3 模拟流式：`MockLLM.stream`

离线测试不能发网络请求，所以 `llm/mock.py` 用确定性方式模拟流式，且严格满足第二章的契约：

```python
_CHUNK_SIZE = 4

def stream(self, messages, temperature=0.7, max_tokens=1024):
    self.calls.append(messages)
    reply = self._take_reply(temperature)      # 与 chat 完全相同的取词逻辑
    self._record_usage(messages, reply, max_tokens)  # usage 统计也一致
    for i in range(0, len(reply), _CHUNK_SIZE):
        yield reply[i : i + _CHUNK_SIZE]       # 按固定宽度切分，模拟 token 到达
```

注意它与 `chat` **共享** `_take_reply` 和 `_record_usage` 两个入口：取哪条脚本回复、怎么记 token，逻辑与一次性完全一致。这一致性有两个回报——一是"流式/一次性在相同脚本下语义等价"可以直接被测试断言；二是 usage 统计不会因为走流式就变口径（day043 的成本追踪会依赖这一点）。分块宽度 4 个字符是任意的，只为了制造"多片增量到达"的节奏感，让 SSE 端点测试能断言"确实分成了多片"。

## 第三章：SSE 协议与 `StreamingResponse` —— 把生成器接到 HTTP 上

### 3.1 SSE 是什么：HTTP 上的单向事件流

SSE（Server-Sent Events）是跑在普通 HTTP 之上的**单向**流式协议：服务器向客户端持续推送文本事件，客户端通过 `EventSource` 自动重连、自动解析。它比 WebSocket 简单得多——**不需要升级协议，不需要双向通信，天然兼容 HTTP 代理与缓存**。

我们只用一个最简子集：每条消息一行 `data: <payload>`，两个事件之间用**空行**分隔。报文长这样（`routes.py` 里的 `_sse_event`）：

```text
data: {"delta": "你好，我"}\n\n
data: {"delta": "是智研助"}\n\n
data: {"delta": "手"}\n\n
data: [DONE]\n\n
```

- 每个 JSON 对象携带一个 `delta` 片段，客户端按序拼接；
- `[DONE]` 是**约定的结束哨兵**（对齐 OpenAI 流式协议的惯例），客户端据此判定流结束。协议上 SSE 也可以靠"服务器关闭连接"来结束，但显式哨兵让客户端能区分"正常结束"与"连接异常中断"。

顺便说明：这里的 JSON 包装是**自选的**。OpenAI 的 SSE 每片就是一个裸 JSON（`data: {"choices":[...]}`）；我们选择 `{"delta": "..."}` 这种最简包装，因为客户端只需要拼接文本，不需要把厂商的完整响应结构都透传出去。

### 3.2 `StreamingResponse` 接线

`routes.py` 里的流式端点：

```python
@router.post("/chat/stream")
def chat_stream(req, llm=Depends(get_llm), models=Depends(get_models)):
    target = resolve_model(req.model, llm, models)

    def event_stream():
        for chunk in target.stream(
            [Message(role="user", content=req.message)], temperature=req.temperature
        ):
            yield _sse_event(json.dumps({"delta": chunk}, ensure_ascii=False))
        yield _sse_event("[DONE]")

    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )
```

几个关键点：

1. **`event_stream()` 是一个生成器函数**：`StreamingResponse` 接受的正是这样一个可迭代对象，Starlette 边迭代边把每段字节刷给客户端——这就是"流"的来源。
2. **`media_type="text/event-stream"`**：这个 Content-Type 是浏览器 `EventSource` 认可 SSE 的标志，客户端靠它决定用事件解析器而非 JSON 解析器。
3. **两个头部**：`Cache-Control: no-cache` 禁止中间代理缓存流（流是一次性的，缓存会带来灾难）；`X-Accel-Buffering: no` 是给 Nginx 的信号，让它关掉响应缓冲、把字节**实时**转发——否则 Nginx 会攒满一坨再吐，流式退化回一次性。
4. **端点声明为 `def` 而非 `async def`**：与 day038 第三章的线程池机制完全一致。`target.stream` 里的 `chat` 是同步阻塞调用，由 Starlette 在**线程池里迭代**生成器；事件循环不被阻塞。这是把同步生成器接到异步框架的正确姿势。

### 3.3 测试如何消费流式响应

`test_api.py` 用 `_parse_sse_deltas` 把响应体解析回 delta 列表，再断言拼接结果：

```python
def _parse_sse_deltas(body: str) -> list[str]:
    deltas = []
    for line in body.splitlines():
        if not line.startswith("data: "):
            continue
        payload = line[len("data: "):]
        if payload == "[DONE]":
            continue
        deltas.append(json.loads(payload)["delta"])
    return deltas
```

`TestClient` 会**把整条流收完再返回**（它在进程内完整消费生成器），所以测试拿到的是完整的 SSE 报文，再逐行解析。两个核心断言：`content-type` 以 `text/event-stream` 开头、`"".join(deltas) == 完整回复且 len(deltas) > 1`（证明真的分了多片）。

## 第四章：多模型路由的扩展 —— 让路由器成为完整替身

### 4.1 回顾 day033 的已有基础

day033 就已经建立了 `ModelRouter`（`llm/router.py`）：用 `estimate_complexity` 估算任务复杂度（1~5），`CostFirstStrategy` 据此选"满足能力要求的最便宜模型"，失败沿降级链向上切换，每次决策连同理由记入 `decision_log`。核心原则是**失败安全方向向上**——宁可降级到更贵更强的模型，也不降级到更弱可能答错的模型。

但当时的路由器只实现了 `chat` 一个方法。这意味着：**流式请求、function calling 请求走不了路由**——用一个只有一半能力的对象去替换单一 LLM，是不完整的替换。

### 4.2 补齐 `stream`：流式也透明路由

`ModelRouter.stream` 与 `chat` 对称，只是把"取完整回复"换成"迭代片段"：

```python
def stream(self, messages, temperature=0.0, max_tokens=1024):
    decision, chain = self.route(self._last_user_task(messages))
    for spec in chain:
        try:
            for chunk in spec.llm.stream(messages, temperature=temperature, max_tokens=max_tokens):
                if spec.name != decision.chosen:
                    decision.fallback_used = spec.name
                yield chunk
            return
        except Exception as exc:
            continue
    raise RuntimeError("所有候选模型均调用失败")
```

这里有一个**依赖第二章那个"惰性"设计的微妙点**：`BaseLLM.stream` 是生成器，调用时不执行、遍历才执行。所以当首选模型 `stream` 首片还没产出就抛异常时，异常发生在 `for chunk in ...` 的**迭代过程**里，会被 `try` 捕获，于是降级链得以生效。反过来，如果 `stream` 是个"调用即出完整结果"的普通函数，异常会在 `spec.llm.stream(...)` 这一行就抛出——一样能被捕获，只是失败点不同。两种情况下，"首选失败 → 换下一个重新流式"的语义都成立。

一个诚实的局限：**流式中途降级会重头再来**。如果首选模型已经推了 10 片、第 11 片才失败，路由器不会接着推第 11 片而会换模型**重新生成**（前面 10 片对客户端是"已收到但作废"）。是否要在流式里做"从断点续传"是更复杂的产品决策，本日不展开——对绝大多数场景，模型流式失败是极罕见的，简化为"重头再来"的代价可接受。

### 4.3 补齐 `chat_with_tools`：function calling 也纳入路由

与 `stream` 同理，`chat_with_tools` 也走"路由 → 降级链"，只是转发的是结构化协议。这样 `FunctionCallingAgent`（day037）无论收到的是单模型还是 `ModelRouter`，都能透明享受路由——`ModelRouter` 实现了 `BaseLLM` 的**全部**接口（`chat` / `stream` / `chat_with_tools`），是一个名副其实的完整替身。`test_router.py` 里的 `test_router_is_base_llm_for_agent`（day033 已有）与新增的 `TestRouterChatWithTools` 分别从文本协议与结构化协议两侧守护了这个可替换性。

### 4.4 补齐 `get_model`：为"显式切换"预留的查询口

```python
def get_model(self, name: str) -> BaseLLM | None:
    for spec in self.models:
        if spec.name == name:
            return spec.llm
    return None
```

这是本章向下一章（显式切换）过渡的桥：路由解决的是"**自动**帮我选模型"，下一章的 `model` 参数解决的是"调用方**点名**用哪个"。`get_model` 提供按名查客户端的原语，`None` 表示查不到。

## 第五章：模型切换 —— 自动路由与显式点名是两条正交能力

### 5.1 先分清两个概念

容易把"多模型路由"和"模型切换"混为一谈，其实它们是**两条正交的轴**：

| 维度 | 自动路由（Router） | 显式切换（model 参数） |
|---|---|---|
| 决策者 | 路由器按任务复杂度/成本/可用性 | 调用方（人/上游系统） |
| 何时生效 | 每次调用自动 | 请求显式携带时 |
| 典型场景 | 服务端替用户省钱且保证质量 | 用户在 UI 里选"用高级模型"、A/B 测试、调试 |

二者可以叠加：`model` 未指定时走路由器自动选，指定时**绕开路由器直接点名**。这正是 `resolve_model` 的语义（见 5.2）。

### 5.2 `model` 参数与注册表

`ChatRequest` 增加一个可选字段：

```python
model: str | None = Field(default=None, description="显式指定模型名；缺省使用默认模型/路由")
```

`routes.py` 里的解析逻辑：

```python
def resolve_model(model, llm, models) -> BaseLLM:
    if model is None:
        return llm                        # 未点名：走默认（单模型或 Router）
    target = models.get(model)
    if target is None:
        raise HTTPException(404, detail=f"未知模型: {model}，可用模型: ...")
    return target
```

`app.state.models` 是模型注册表（`dict[str, BaseLLM]`），由 `create_app(models=...)` 注入，缺省用 `default_models()`（无密钥时只含 `mock`，配了密钥则额外注册 `settings.default_model`）。`/models` 端点列出所有可显式切换的模型名，调用方不至于盲猜。

### 5.3 为什么未知模型是 404 而不是 422

这是对 day038"错误也是契约"的具体延伸。回顾 day038：**422 表示"请求语义不合法"**——字段类型错了、缺必填、超范围。而 `model="nope"` 是一个**合法字符串**，只是这个字符串**指向的资源不存在**。

"合法但不存在"是典型的**资源不存在（404）**语义，而非"请求格式有问题（422）"。客户端据此分支：422 是"我发错了，改请求"；404 是"这个名字不在候选集，查 /models 换一个"。`test_unknown_model_returns_404` 同时断言状态码 404 与 `detail` 里带了 `未知模型` 和可用的模型名——错误信息本身要给出**下一步行动**（有哪些可选），这是好的错误契约。

### 5.4 `/models` 端点：可发现性

```python
@router.get("/models")
def list_models(models=Depends(get_models)) -> dict:
    return {"models": sorted(models)}
```

端点存在的意义是**可发现性**：调用方不需要翻文档就知道能点名哪些模型。`sorted(models)` 保证输出顺序稳定（注册表是 dict，遍历顺序依赖插入序，排序让响应可预测、易测试）。这跟 day038 讲的"契约即文档"一脉相承——可用模型清单也是一份由代码派生的、永不漂移的"活文档"。

## 第六章：选型与呼应 —— 何时流式、何时不流式

### 6.1 SSE vs WebSocket vs 一次性

| 维度 | 一次性 JSON | SSE | WebSocket |
|---|---|---|---|
| 通信方向 | 请求→响应 | 服务器→客户端单向流 | 双向全双工 |
| 协议复杂度 | 最低 | 低（普通 HTTP + text/event-stream） | 高（协议升级、帧、心跳） |
| 自动重连 | 无 | 有（EventSource 内建） | 需自己实现 |
| 适用场景 | 一次性查询结果 | 服务器单向持续推送（模型生成、进度） | 双向交互（聊天室、协作编辑） |

我们的对话流是**服务器单向生成、客户端只读**，SSE 是最契合的选择——用最少的协议复杂度换到流式体验。WebSocket 的双向能力在这里是浪费（客户端没有要推给服务器的东西）。

### 6.2 与 day038 的呼应：线程池机制复用

本日流式端点没有引入任何新的并发处理——`StreamingResponse` 消费同步生成器时，Starlette 沿用了 day038 第三章讲的**线程池迭代**。这不是巧合：我们所有"同步阻塞生成器接到异步框架"的地方，靠的都是同一套 `run_in_threadpool` 机制。理解透 day038 第三章，这里的接线是顺水推舟。

### 6.3 与 day033 / day037 的呼应：一条完整的能力链

- **day033（路由）+ day039（补齐流式与工具路由）**：让 `ModelRouter` 从"只能 chat 的半成品"变成 `BaseLLM` 的完整替身，Agent 无论走哪条协议都能透明路由。
- **day037（Function Calling）+ day039（chat_with_tools 路由）**：结构化工具调用也能享受多模型路由与降级，能力链闭合。
- **day038（FastAPI）+ day039（SSE + 模型切换）**：服务层从"能对话"升级为"流式对话 + 可点名模型"，向真实产品再进一步。

### 6.4 今日总结

1. **流式解决的是感知性能（TTFT），不是总耗时**：自回归生成天然可拆分，流式只是把它透传出来；正确的同一性由"拼接 == 完整回复"的协议契约保证。
2. **流式能力分层实现而后向兼容**：`BaseLLM.stream` 默认退化为单片段，真流式（OpenAI 兼容）与模拟流式（MockLLM）各自覆写，未覆写的旧实现不必改动。
3. **SSE 是最简的单向流协议**：`data:` 帧 + 空行分隔 + `[DONE]` 哨兵，配 `text/event-stream` 与两个反缓冲头，由 `StreamingResponse` 消费同步生成器（复用 day038 线程池）。
4. **路由与切换是两条正交能力**：路由自动选型、`model` 参数显式点名；`resolve_model` 里 `None` 走默认、点名未命中 404——"合法但不存在"与"请求不合法"要用不同状态码区分。
5. **流式有边界**：只适配"纯文本、人消费"的对话场景，不适配需要整体可用的结构化输出（Agent 轨迹、function calling）。
