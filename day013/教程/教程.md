## 第一章：为什么需要状态图 —— while 循环编排的天花板

### 1.1 先回顾：day006 的 ReAct 是怎么跑起来的

day006 的 `ReactAgent.run()` 核心是一个 for 循环：

```python
for step_no in range(1, self.max_steps + 1):
    raw = self.llm.chat(messages)
    step = parse_react_output(raw)
    if step.final_answer is not None:
        return step.final_answer
    observation = self._execute_tool(step)
    messages.append(...)
return "达到最大步数限制，未能得出最终答案"
```

这段代码清晰、好读，对于"单线程跑到底"的场景完全够用。但它把四样东西**揉进了函数栈的局部变量里**：当前思考（`step`）、历史消息（`messages`）、步数（`step_no`）、终止判断（`if final_answer`）。这个"揉"字，就是一切问题的根源。

### 1.2 隐式编排的四个痛点

**痛点一：状态不可见。** 循环跑到第 3 步时，外部代码想知道"现在思考到哪了、刚才工具返回了什么"——做不到。状态活在 `run()` 的栈帧里，外人无法读取，除非打断点调试器附上去。Agent 的行为成了黑盒。

**痛点二：状态不可持久化。** 进程崩了、机器重启了、用户关掉了网页——循环中的一切付诸东流。真实产品里，一个调研任务可能跑十分钟，用户中途去喝了杯咖啡回来，期望看到的是"接着刚才继续"，而不是从头再来。

**痛点三：不可中断、不可介入。** 工具调用是**有副作用的**：发邮件、删文件、调付费 API。生产级 Agent 的标准要求是"危险操作前必须人工确认"。但 while 循环一旦启动就一路跑到黑，没有"在调用工具前暂停一下，等人审批"的机制。

**痛点四：流程不可重组。** 想加一步"每三步自我反思一次"？想在工具失败后重试两次再放弃？这些在 while 循环里意味着往函数体里塞更多 if/else，循环很快变成谁也不敢动的泥潭。流程结构应该是一种**可以独立演化的资产**，而不是埋在控制流里的潜规则。

### 1.3 把循环拆开看：它本来就是一张图

如果把 `run()` 的控制流画出来，它其实是这样的：

```text
        ┌─────────────┐
        │    START    │
        └──────┬──────┘
               ▼
        ┌─────────────┐     已有最终答案
   ┌──▶ │    think    │ ───────────────▶ END
   │    │ (调 LLM)    │
   │    └──────┬──────┘
   │           │ 决定调用工具
   │           ▼
   │    ┌─────────────┐     达到最大步数
   └────│     act     │ ───────────────▶ END
        │ (执行工具)   │
        └─────────────┘
```

`think` 和 `act` 是两个**节点（Node）**，箭头是**边（Edge）**，"已有最终答案吗 / 达到最大步数吗"是**条件边（Conditional Edge）** 的路由判断，而 `step`、`messages` 这些局部变量合在一起，就是在节点之间流转的**状态（State）**。

看出门道了吗？**while 循环只是这张图的一种"内联写法"**。LangGraph 做的事情，就是把这张图从代码的控制流里"提"出来，变成显式的数据结构——你声明节点、声明边、声明状态长什么样，引擎替你驱动整张图的执行。

### 1.4 显式化之后，四个痛点各自有了出路

| 痛点 | while 循环里 | 状态图里 |
|------|-------------|----------|
| 状态不可见 | 局部变量藏在栈帧 | 状态是显式对象，`graph.get_state()` 随时可读 |
| 不可持久化 | 进程死则状态亡 | checkpointer 每步自动存档，按 thread_id 取回 |
| 不可中断 | 一跑到底 | `interrupt_before` 在任意节点前暂停，人可介入 |
| 不可重组 | 改控制流 = 改函数体 | 加节点、改边即可，节点函数不动 |

这就是今天的核心论点：**编排逻辑显式化不是炫技，而是把"流程"从不可维护的控制流升级为可操作、可观测、可持久化的数据。**

> 思考题：既然图这么好，day006 为什么不一开始就上图？提示：想想"先学会爬再学会走"——手写循环让我们理解了 ReAct 的每一步在做什么，这个理解是使用任何编排框架的前提。框架是杠杆，不是拐杖。

### 1.5 LangGraph 在生态中的位置

LangGraph 是 LangChain 团队出的**低层编排框架**，定位是"Agent 的状态机引擎"。它不替你写提示词、不内置 Agent 逻辑，只提供三样东西：状态模型、图执行引擎、持久化/中断基础设施。这和我们项目的哲学完全一致——前面十二天我们亲手实现了 ReAct、记忆、规划，今天用 LangGraph 接管的只是**控制流与状态管理**这一层，提示词（`SYSTEM_PROMPT`）、解析器（`parse_react_output`）、工具注册表全部原样复用。

## 第二章：LangGraph 核心模型 —— State、Node、Edge

### 2.1 State：图中流转的唯一数据载体

LangGraph 的状态用 `TypedDict` 声明。我们的定义（[graph/state.py](../源码/smart-research-agent/smart_research_agent/graph/state.py)）：

```python
class AgentState(TypedDict):
    task: str                       # 用户任务，整个运行期间不变
    thought: str                    # 当前步的思考
    action: str | None              # 当前步决定调用的工具名
    action_input: str | None        # 工具入参
    observation: str                # 最近一次工具执行结果
    steps: int                      # 已执行的工具调用次数
    final_answer: str | None        # 最终答案（done=True 时有值）
    done: bool                      # 是否已得出最终答案
    history: Annotated[list[dict[str, Any]], operator.add]  # 已完成的步骤轨迹
```

对照 day006 的局部变量：`step` 拆成了 `thought/action/action_input/final_answer`，`step_no` 变成了 `steps`，终止标志显式化为 `done`。原来隐式的东西，现在全有了名字。

**为什么用 TypedDict 而不是 pydantic BaseModel？** 项目里配置用 pydantic（day001），后续 MCP 协议建模也会用 pydantic（day016），为什么这里换了？因为 LangGraph 的状态更新语义是**字典式的部分更新**——节点返回一个 `dict`，引擎把它合并进状态。TypedDict 就是这个语义的原生表达：它本质是带类型标注的 dict，不做运行时校验，不实例化对象，合并开销为零。状态在引擎手里高频读写，轻量比严格更重要。这是"按场景选工具"的又一个实例。

### 2.2 状态更新的两种语义：覆盖与 reducer

这是 LangGraph 新手最容易踩的坑，必须讲透。

**默认语义是覆盖（overwrite）**：节点返回 `{"thought": "新思考"}`，引擎直接替换 `state["thought"]`。对 `thought`、`steps` 这类"只保留最新值"的字段，覆盖正是我们要的。

但 `history` 不一样。act 节点每执行一次，都想**追加**一条记录，而不是把历史清空。如果按覆盖语义，第 2 步的 act 返回 `[第2步记录]`，第 1 步的记录就丢了。

解决办法是 **reducer**——在类型标注里告诉引擎"这个字段的更新要这样合并"：

```python
history: Annotated[list[dict[str, Any]], operator.add]
```

`Annotated[类型, 合并函数]` 的意思是：节点返回的 `history` 值不直接替换，而是执行 `旧值 + 新值`（`operator.add` 对列表就是拼接）。于是 act 节点只需返回 `{"history": [本条记录]}`，引擎自动追加到已有轨迹之后。

```text
act 第1步返回 {"history": [记录A]}  →  state["history"] = [] + [记录A] = [记录A]
act 第2步返回 {"history": [记录B]}  →  state["history"] = [记录A] + [记录B] = [记录A, 记录B]
```

记住判断口诀：**字段是"最新值"用语义覆盖，是"累积集合"用 reducer。** LangChain 生态里的 `add_messages` 就是一个预置的 reducer，专门合并消息列表，等我们接入对话消息模型时会用到。

### 2.3 Node：一个普通的 Python 函数

节点就是签名形如 `def node(state: AgentState) -> dict` 的函数：

- **输入**：当前完整状态（引擎自动注入）；
- **输出**：一个 dict，作为对状态的部分更新；
- **注册**：`builder.add_node("think", think)`，名字 + 函数。

节点的设计原则和我们 day003 讲工具时一样：**单一职责、无副作用扩散**。think 只调 LLM 和解析，绝不碰工具；act 只执行工具写回 observation，绝不调 LLM。职责边界清晰了，断点、重试、替换实现才有着力点。

### 2.4 Edge：固定边与条件边

固定边无条件走：`builder.add_edge(START, "think")` 表示图从 think 开始；`START` 和 `END` 是 LangGraph 预置的两个虚拟节点，代表图的入口与出口。

条件边是图的灵魂。langgraph 1.2 的签名是：

```python
builder.add_conditional_edges(source, path_func, path_map)
```

三个参数各管一件事：

- `source`：从哪个节点出发；
- `path_func`：一个路由函数，读状态、返回一个**键**；
- `path_map`：键到目标节点的映射表。

我们的两处条件边：

```python
def route_after_think(state: AgentState) -> str:
    """思考后的路由：已有最终答案则终止，否则去执行工具."""
    return "end" if state["done"] else "act"

def route_after_act(state: AgentState) -> str:
    """行动后的路由：达到最大步数则终止，否则回去继续思考."""
    return "end" if state["steps"] >= max_steps else "think"

builder.add_conditional_edges("think", route_after_think, {"act": "act", "end": END})
builder.add_conditional_edges("act", route_after_act, {"think": "think", "end": END})
```

**为什么路由函数只返回字符串键，而不直接返回节点名？** 多一层 `path_map` 间接映射看起来啰嗦，实际是刻意设计：路由函数专注"判断业务条件"（done 与否、步数与否），映射表专注"条件对应的拓扑走向"。将来把 `END` 换成一个 `summarize` 汇总节点，只改 `path_map` 一行，路由函数的逻辑不动——判断与拓扑解耦。

**为什么要有 `path_map` 而不是让路由函数返回任意节点名？** 因为有了映射表，LangGraph 能在编译期静态分析图的可达性，画出完整的拓扑图（`graph.get_graph().draw_mermaid()` 能出流程图靠的就是它）。如果路由函数返回任意字符串，拓扑就只能在运行期动态发现，可视化和静态检查都无从谈起。

### 2.5 一个关键设计决策：max_steps 检查放在哪条边上

注意我们把"超步数 → END"放在了 **act 之后**的条件边里，而不是 think 之后。这不是随手放的：

- 若放在 think 之后：流程是 `act → think → (步数够了?) → END`。也就是说，最后一次 act 完成后**还要再调一次 LLM**，模型输出了一段注定被丢弃的思考，白白烧掉一次调用的 token。
- 放在 act 之后：流程是 `act → (步数够了?) → END`。第 max_steps 次工具执行完立刻终止，LLM 恰好被调 max_steps 次——和 day006 `ReactAgent` 的语义完全对齐。

```text
对比两种放置（设 max_steps=3）：

检查在 think 后:  think→act→think→act→think→act→think✗   LLM 调 4 次（浪费 1 次）
检查在 act 后:    think→act→think→act→think→act→END      LLM 恰调 3 次
```

**路由判断的位置决定资源消耗。** 这在真实 API 按 token 计费的背景下，是实打实的成本问题。

> 思考题：如果路由函数抛出异常（比如状态里字段缺失），图会怎样？查一下 LangGraph 文档的 `RetryPolicy`，想想生产环境该怎么防御。

## 第三章：动手重构 —— 从 ReactAgent 到 react_graph

### 3.1 组件映射表

重构的第一步不是写代码，而是把旧实现的每个零件找到新家的位置：

| day006 `ReactAgent` | day013 状态图 | 变化 |
|---------------------|--------------|------|
| `messages` 局部变量 | `history` 字段（reducer 追加） | 从栈帧搬进显式状态 |
| `for step_no in ...` | think→act→think 循环边 | 控制流显式化 |
| `self.max_steps` 循环上界 | `route_after_act` 里的比较 | 上界变成路由条件 |
| `if final_answer: return` | `route_after_think` → END | 终止变成路由条件 |
| `_execute_tool()` | `act` 节点 | 一行不改，逻辑平移 |
| `SYSTEM_PROMPT` | think 节点内复用 | 原样 import |
| `parse_react_output()` | think 节点内复用 | 原样 import |

最后两行是重点：**重构的是编排，不是能力。** 提示词工程（day006）、输出解析（day006）、工具系统（day003~004）这些"内功"全部保留，LangGraph 只接管它们之间的调度。这也是为什么我们坚持把每层做成可独立测试的模块——今天它们成了图节点的现成零件。

### 3.2 think 节点：重建对话上下文

完整代码见 [graph/react_graph.py](../源码/smart-research-agent/smart_research_agent/graph/react_graph.py)。think 节点里有一段值得细看：

```python
for item in state["history"]:
    messages.append(
        Message(
            role="assistant",
            content=(
                f"Thought: {item['thought']}\n"
                f"Action: {item['action']}\n"
                f"Action Input: {item['action_input']}"
            ),
        )
    )
    messages.append(Message(role="user", content=f"Observation: {item['observation']}"))
```

day006 的 `messages` 列表随循环自然累积，每步的原始输出都留在里面。状态图里 think 节点每次拿到的都是全新状态，所以要从 `history` **重建**对话历史：把每个已完成步骤重新拼成 assistant/user 消息对，喂给 LLM。

这里有一个"重建"与"累积"的权衡：我们选择了**存储结构化字段（thought/action/observation），用时再拼回文本**，而不是直接存 LLM 原始输出字符串。好处是状态里的数据既可被 LLM 消费（拼回文本），也可被程序消费（比如统计"调了几次 calculator"）；代价是拼回的文本和原始输出可能有细微格式差异。对 MockLLM 无所谓，对真实模型，实测影响可忽略——ReAct 提示词对历史格式的容错本来就建立在解析器之上。

### 3.3 act 节点：一次更新三个字段

```python
return {
    "observation": observation,
    "steps": state["steps"] + 1,
    "history": [
        {
            "thought": state["thought"],
            "action": state["action"],
            "action_input": state["action_input"],
            "observation": observation,
        }
    ],
}
```

三个字段、两种更新语义同框：

- `observation`、`steps` 是覆盖式更新——`steps` 取旧值加一，读的是注入进来的 `state`；
- `history` 是 reducer 追加——返回单元素列表，引擎拼到尾部。

一个节点同时演示两种语义，这就是把这段代码放在教程正文的原因。**看节点返回值时，先问自己每个字段用的是哪种语义**，就不会写出"history 越跑越短"的 bug。

工具执行逻辑（查注册表、取必填参数、try/except 兜底）与 `ReactAgent._execute_tool` 逐行对应，连"工具不存在返回错误文本而非抛异常"的容错策略都保留——**错误也是信息**，把错误写回 observation 让模型下一步自己纠错，比让图崩溃更符合 Agent 的韧性设计。

### 3.4 组装与编译

```python
builder = StateGraph(AgentState)
builder.add_node("think", think)
builder.add_node("act", act)
builder.add_edge(START, "think")
builder.add_conditional_edges("think", route_after_think, {"act": "act", "end": END})
builder.add_conditional_edges("act", route_after_act, {"think": "think", "end": END})
return builder.compile(
    checkpointer=MemorySaver(),
    interrupt_before=interrupt_before or [],
)
```

四步生命周期：**声明状态 → 注册节点 → 连边 → 编译**。`compile()` 是分水岭：之前是可变的 builder，之后是不可变的 `CompiledStateGraph`。编译时 LangGraph 会做校验（所有条件边映射的目标存在吗？有从 START 出发的边吗？），并在这里注入两样运行时设施：

- `checkpointer=MemorySaver()`：检查点存储后端，每执行完一个节点就把状态快照存一份；
- `interrupt_before=["act"]`：声明在 act 节点执行**前**暂停——断点。

两者都是编译期注入而非节点内硬编码，意味着**同一张图可以编译出不同运行形态**：测试要断点、生产不带断点、换个 checkpointer 就能从内存换到数据库。行为差异不下沉到节点代码里。

### 3.5 run_graph：把 config 仪式封装起来

LangGraph 的 `invoke` 需要一个 `config` 参数指定会话：

```python
graph.invoke(state, config={"configurable": {"thread_id": "..."}})
```

`thread_id` 是检查点的命名空间钥匙：同一把钥匙对应同一条状态时间线。这个细节每次调用都要写，所以封装成便捷函数：

```python
def run_graph(graph: Any, task: str, thread_id: str = "default") -> str:
    config = {"configurable": {"thread_id": thread_id}}
    final = graph.invoke(initial_state(task), config=config)
    return final["final_answer"] or "达到最大步数限制，未能得出最终答案"
```

`invoke` 的返回值是图运行到 END 后的**最终完整状态**，我们从中取出 `final_answer`。兜底字符串与 `ReactAgent` 完全一致——对外行为对齐，重构才算"等价重构"。

## 第四章：状态持久化与断点调试 —— LangGraph 的杀手锏

### 4.1 checkpointer：每个节点后的自动存档

`MemorySaver` 的工作方式：图每执行完一个节点，就把当时的完整状态按 `thread_id` 存进一个内存字典。于是一条 thread_id 对应一串状态快照序列：

```text
thread "t1":
  快照0: {task, steps:0, ...}            ← invoke 入口
  快照1: {..., thought:"需要用计算器", action:"calculator"}   ← think 执行完
  快照2: {..., observation:"5", steps:1, history:[...]}      ← act 执行完
  快照3: {..., final_answer:"2+3 等于 5", done:True}         ← think 执行完 → END
```

`graph.get_state(config)` 取回的是**最新快照**（一个 `StateSnapshot`，`.values` 是状态字典，`.next` 是待执行节点元组）。这就是"痛点二：状态不可持久化"的解法——不过注意，**MemorySaver 是内存实现，进程退出即丢失**。它适合开发、测试、单机脚本；生产环境要换 SqliteSaver 或 PostgresSaver，接口完全一样，换的是后端。这正是"编译期注入"设计的回报。

### 4.2 thread_id：会话隔离的边界

为什么 `get_state` 也要传 config？因为一张编译好的图可以被成千上万个会话共享，checkpointer 靠 thread_id 区分"你问的是哪次对话的状态"。我们的测试 `test_threads_are_isolated` 验证了这一点：thread-a 跑完了，thread-b 的状态依然是空 `{}`。**图是无状态的执行引擎，状态全部在 checkpointer 里**——这个"引擎与状态分离"的架构，和 Web 框架里"应用无状态、会话存 Redis"是同一个思想。

### 4.3 interrupt_before：在副作用发生前按下暂停键

断点的用法分三步：

```python
graph = build_react_graph(llm, registry, interrupt_before=["act"])
config = {"configurable": {"thread_id": "t-bp"}}

paused = graph.invoke(initial_state(TASK), config=config)   # ① 跑到 act 前停住
assert graph.get_state(config).next == ("act",)             # ② 检查：下一步是 act
final = graph.invoke(None, config=config)                   # ③ 传 None = 从检查点恢复
```

逐句理解：

- **① 暂停时机**：interrupt_before 是"在节点**执行前**停"。此时 think 已把 `action="calculator"` 写进状态，但工具还没执行——这正是审批危险操作的最佳窗口。
- **② `snapshot.next`**：返回待执行节点元组 `("act",)`。如果图已跑到 END，`next` 是空元组。这两个值是程序判断"图停在哪"的标准方法。
- **③ `invoke(None, config)`**：第一个参数传 `None` 是 LangGraph 的恢复语义——"不给新输入，从该 thread 的检查点继续"。引擎从快照里捞出状态，接着执行 `next` 指向的节点。为什么必须传同一个 config？因为恢复的依据就是 thread_id 对应的快照，换了 thread_id 就没有可恢复的现场。

### 4.4 update_state：人在回路（Human-in-the-Loop）

断点的价值不止"暂停看状态"，更在于**改了再放行**：

```python
graph.invoke(initial_state(TASK), config=config)        # 停在 act 前
graph.update_state(config, {"action_input": "10*10"})   # 人工修正参数
final = graph.invoke(None, config=config)               # 按修正后的状态继续
assert final["observation"] == "100"                    # 计算器算的是 10*10
```

`update_state` 把新值写进检查点快照（字段合并语义与节点返回相同——history 走 reducer，其余覆盖）。恢复执行时 act 节点读到的就是被修正后的状态。

这就是 HITL 的完整闭环：**机器跑到关键节点 → 暂停 → 人审查/修改状态 → 机器接着跑**。我们的测试 `test_edit_state_at_breakpoint` 把这个流程固化成了回归用例。生产中它对应的场景是：Agent 要发邮件前暂停，运营人员检查正文、改两个措辞，点"确认"，流程继续。

### 4.5 断点 vs 异常：两种"停下来"的本质区别

对比一下两种中断：

| 维度 | 异常崩溃 | interrupt 断点 |
|------|---------|---------------|
| 意图 | 意外 | 计划内 |
| 状态 | 栈帧销毁，现场丢失 | 完整存入 checkpointer |
| 恢复 | 不可能，只能重跑 | `invoke(None, config)` 精确续跑 |
| 可介入 | 只能看 traceback | 可读状态、可改状态 |

Agent 系统的特殊性在于：**LLM 调用和工具执行都又贵又慢**，"崩了重跑"的代价远高于普通程序。断点 + 检查点把"暂停-审查-恢复"变成一等公民，是 Agent 框架区别于普通任务编排库（如 Airflow）的核心能力。

> 思考题：`update_state` 修改 history 字段时走什么语义？如果想在断点处**替换**掉某条历史记录而不是追加，该怎么办？提示：reducer 是声明在类型标注上的，`update_state` 也遵守它——可以考虑传一个特殊的覆盖标记，或查文档了解 `__pregel_` 通道机制。本题只需想清楚语义即可。

### 5.2 测试怎么做到离线且确定

和之前每一天一样，全部测试用 MockLLM 按脚本驱动：

```python
THINK_CALC = "Thought: 需要用计算器\nAction: calculator\nAction Input: 2+3"
FINAL = "Thought: 已得到计算结果\nFinal Answer: 2+3 等于 5"

llm = MockLLM(responses=[THINK_CALC, FINAL])
graph = build_react_graph(llm, registry)
answer = run_graph(graph, TASK, thread_id="t-full")
```

think 节点第一次调用弹出 `THINK_CALC`（→ 走 act），第二次弹出 `FINAL`（→ 走 END）。图的真实引擎在跑，只有 LLM 是替身——**编排逻辑是真测，外部依赖是真 mock**，这正是 day005 依赖注入设计在图时代的延续。

注意 fixture 里注册了真实的 `CalculatorTool`，所以 `observation == "5"` 是真算出来的，断言的是端到端结果而非中间桩。

### 5.3 三个测试组的覆盖逻辑

`tests/test_graph.py` 分三组：

- **TestReActGraph（4 个）**：端到端行为——完整流程、max_steps 熔断（用 `MockLLM(default=THINK_CALC)` 让模型"永远不收手"）、未知工具容错、直达答案不经过 act。覆盖了图的两条条件边的所有走向。
- **TestCheckpoint（2 个）**：`get_state` 取回最终状态、`snapshot.next == ()` 表示已到 END；不同 thread_id 状态隔离。
- **TestInterrupt（2 个）**：断点暂停 + `next == ("act",)` + `invoke(None)` 恢复；断点处 `update_state` 改参后恢复。

**每条边、每种状态访问方式都有对应的测试**——图的拓扑只有 2 节点 3 条边，但行为组合不少，测试按"走向"而非"代码行"组织，才能漏不掉。

## 第六章：今日总结 —— 从循环到图

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| TypedDict 而非 pydantic | 状态是高频字典式部分更新，轻量优先 | `graph/state.py` |
| `history` 用 `operator.add` reducer | "累积集合"字段需要追加语义而非覆盖 | `AgentState.history` |
| 节点 = 普通函数返回 dict | 部分更新合并，节点互不感知 | `think` / `act` |
| 路由函数 + path_map 分离 | 业务判断与拓扑走向解耦 | 两个 `route_after_*` |
| max_steps 检查放 act 之后 | 避免最后一次注定被丢弃的 LLM 调用 | `route_after_act` |
| checkpointer 编译期注入 | 同一张图可换存储后端、可开关断点 | `builder.compile(...)` |
| thread_id 会话隔离 | 引擎无状态，状态全在 checkpointer | `run_graph` 的 config |
| `invoke(None, config)` 恢复 | 断点现场在检查点里，恢复即续跑 | TestInterrupt |
| `update_state` 人工改状态 | Human-in-the-Loop 的审批闭环 | `test_edit_state_at_breakpoint` |

今天埋下的伏笔，后续会回收：

- **多 Agent 状态图**：今天的图只有两个节点，但 `add_node` 没有上限——day012 的多 Agent 协作（研究员、分析师、撰稿人）本质上就是一张更大的状态图，每个 Agent 是一个节点。
- **持久化到数据库**：MemorySaver 换 SqliteSaver，配合 day009 的长期记忆，Agent 将拥有跨进程、跨重启的完整状态。

```text
day006  手写 while 循环        （理解 ReAct 的每一步）
day013  LangGraph 状态图       （把流程变成可观测、可持久、可介入的图）← 今天
后续    多 Agent 图 + 生产持久化 （图的规模与可靠性升级）
```
