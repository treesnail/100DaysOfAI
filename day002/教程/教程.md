## 第一章：Git 的本质 —— 分布式版本控制的对象模型

### 1.1 为什么需要版本控制

先想一个问题：如果没有 Git，100 天的学习项目会遇到什么麻烦？

- 昨天写的代码今天改坏了，想回退，但没有备份。
- 想同时尝试两种实现方案，只能复制两份文件夹，命名成 `project_v1/`、`project_v2_final/`、`project_v2_final_final/`。
- 一段代码三天前还能跑，现在报错，但你完全想不起改了哪里。

版本控制系统（VCS）解决的核心问题是：**让代码的每一次变化都有记录、可回溯、可并行**。

### 1.2 Git 的对象模型：一切皆是内容寻址

很多教程从命令开始教 Git，结果学习者只记住了 `add / commit / push`，遇到 rebase、冲突就束手无策。正确的姿势是先理解 Git 的底层模型——它其实非常简单优雅。

Git 的对象库里只有四种对象：

| 对象 | 内容 | 类比 |
|------|------|------|
| **blob** | 文件内容（不含文件名） | 一张纯内容卡片 |
| **tree** | 目录结构（文件名 → blob/tree 的映射） | 一个文件夹清单 |
| **commit** | 指向某个 tree + 父 commit + 作者/时间/信息 | 一次快照的元数据 |
| **tag** | 指向某个 commit 的标注 | 里程碑标签 |

每个对象的内容经过 SHA-1 哈希得到唯一 ID（如 `f263097...`）。这带来两个重要性质：

1. **内容寻址（Content-Addressable）**：对象 ID 由内容决定。内容相同 → ID 相同；内容变 → ID 变。Git 因此天然能检测重复内容、校验数据完整性。
2. **不可变性（Immutability）**：对象一旦创建永不修改。"修改文件"实际上是创建新 blob，新 tree，新 commit。

> 思考题：为什么"不可变性"让 Git 如此可靠？  
> 因为历史永远不会被悄悄篡改——任何改动都会产生新的对象 ID，旧对象依然存在。这和函数式编程中的不可变数据结构是同一个思想。

### 1.3 快照模型，而非差异模型

Git 存储的是**快照（snapshot）**，不是差异（diff）。每次 commit 都指向一个完整的 tree，tree 完整地描述了当时整个项目的样子。

```
commit C3 ──→ tree T3 ──→ blob: README.md 内容
     │                └─→ tree: src/ ──→ blob: main.py 内容
     │
     └── parent: commit C2 ──→ tree T2 ──→ ...
```

为什么不用差异存储？

- **读取任意版本快**：不需要从最初版本逐个打补丁，直接取出对应 tree 即可。
- **未变的文件只存一份**：如果 `config.py` 在 C2 和 C3 中没变，两个 tree 指向同一个 blob，空间并不浪费。

理解了快照模型，就理解了为什么 `git checkout <commit>` 能瞬间切换项目状态——它只是把工作区换成对应 tree 描述的内容。

### 1.4 三个区域：工作区、暂存区、仓库

Git 日常操作在三个区域之间流动：

```
工作区(Working Directory)      暂存区(Staging Area)         本地仓库(Repository)
   你正在编辑的文件  ──add──▶   准备提交的快照  ──commit──▶   永久保存的 commit
        ▲                                                     │
        └─────────────────  checkout / restore  ──────────────┘
```

**暂存区为什么存在？** 这是 Git 区别于 SVN 等老式 VCS 的关键设计。

暂存区让你可以**精细控制一次 commit 包含哪些改动**：

```bash
# 你只改了 config.py 的一个字段，但顺便修了 logger.py 的注释
# 你想把这两件事分成两个 commit
git add smart_research_agent/config.py
git commit -m "feat(config): 新增 max_retry_count 字段"
git add smart_research_agent/utils/logger.py
git commit -m "docs(logger): 修正注释笔误"
```

**原子提交（Atomic Commit）**原则：一个 commit 只做一件事。好处：

- 代码评审时容易理解意图；
- 出问题时 `git revert` 可以精确回滚某一个改动而不误伤其他；
- `git bisect` 二分查找引入 bug 的提交时，粒度越细定位越准。

### 1.5 分支的本质：只是一个指针

这是 Git 最重要也最容易被误解的概念。**分支不是文件夹，不是代码副本，只是一个指向 commit 的指针（41 字节的文本文件）。**

```
        A ── B ── C  ← main (指针)
                  ↑
                HEAD (指向当前分支)
```

创建分支：

```bash
git checkout -b day002-git-workflow
```

Git 做的事仅仅是：新建一个指针文件 `refs/heads/day002-git-workflow`，内容是当前 commit 的 ID，然后把 HEAD 指过去。**没有任何文件被复制**，所以 Git 建分支是 O(1) 的瞬时操作。

```
        A ── B ── C  ← main
                  ↑
                day002-git-workflow  ← HEAD
```

理解这一点后，很多"分支很重"的心理障碍就消失了——在 Git 里，创建、切换、删除分支的成本几乎为零。这正是"分支驱动开发"得以成立的基础。

### 1.6 merge 与 rebase 的区别

两种整合分支的方式：

- **merge**：保留真实历史。创建合并提交，两个父 commit 都在。
- **rebase**：改写历史。把你的提交"摘下来"，依次重放到目标分支最新提交之后，形成直线历史。

```
merge:                          rebase:
A ── B ── C ────── M  (main)    A ── B ── C ── D'── E' (main)
         \       /                            (D,E 被重写为 D',E')
          D ── E  (feature)
```

本项目约定：**学习项目用 merge（`--no-ff`）**，因为我们要保留"每天的学习是一个完整阶段"的边界感。rebase 更适合向开源项目提交 PR 前整理提交历史。

> 黄金法则：**永远不要 rebase 已经推送到共享分支的提交**。rebase 会生成新 commit ID，等于改写了公共历史，别人 pull 时会陷入混乱。

### 1.7 Conventional Commits：为什么提交信息要有格式

回顾项目里的提交信息：

```text
init: 100天AI学习计划项目骨架与day001工程化基础
chore: 完善 .gitignore，防止敏感文件和临时文件入库
```

格式是 `type(scope): subject`。这不是形式主义，而是让**提交历史成为可解析的结构化数据**：

- 日后可以用脚本自动统计"这 100 天里 feat / fix / docs 各占多少"；
- CI 工具可以基于 type 自动生成 CHANGELOG、自动判断版本号（feat → minor、fix → patch）；
- 检索历史时 `git log --grep="^feat"` 就能过滤出所有功能提交。

完整规范见 `源码/smart-research-agent/docs/git_workflow.md`。

## 第二章：pytest 与测试 —— 从"跑一次看看"到"可重复验证"

### 2.1 测试金字塔

软件测试按粒度分三层：

```
        ╱  E2E  ╲        少量：端到端测试（慢、脆、贵）
       ╱ 集成测试 ╲       适量：模块间协作测试
      ╱  单元测试  ╲      大量：单个函数/类的行为测试（快、稳、准）
     ╱──────────────╲
```

今天我们建立的 `tests/` 目录属于最底层的**单元测试**。单元测试的定义：在隔离环境中验证一个最小代码单元（函数/类）的行为是否符合预期。

为什么单元测试要"多"？因为它是反馈最快的测试：毫秒级运行，改一行代码立刻知道有没有破坏其他逻辑。AI 项目迭代快，快速反馈的价值会被放大。

### 2.2 好测试的 FIRST 原则

| 原则 | 含义 | 本项目落地 |
|------|------|-----------|
| **F**ast | 快 | 单元测试不访问网络、不调用 LLM，毫秒级 |
| **I**ndependent | 独立 | 每个测试可单独运行，互不依赖顺序 |
| **R**epeatable | 可重复 | 任何机器、任何时间跑结果一致 |
| **S**elf-validating | 自验证 | 断言自动判断通过/失败，不需人眼看输出 |
| **T**imely | 及时 | 与功能代码同步编写（而非事后补） |

对照 day001 的第一个测试：

```python
def test_settings_default_values():
    settings = Settings()
    assert settings.project_name == "智研 AI 助手"
```

- Fast：只是实例化一个类。
- Independent：不依赖其他测试。
- Repeatable：默认值固定，任何环境结果一致。
- Self-validating：assert 自动判定。
- Timely：和功能代码同一天写。

### 2.3 fixture：测试的依赖注入

测试经常需要"准备环境"：创建对象、设置临时状态、最后清理。pytest 用 **fixture** 机制解决这个需求，本质上是**依赖注入（Dependency Injection）**：

```python
# tests/conftest.py
import pytest
from smart_research_agent.config import Settings


@pytest.fixture
def default_settings() -> Settings:
    """提供一个默认 Settings 实例，每次测试新建，避免状态泄漏."""
    return Settings()
```

使用时只需在测试函数签名里声明需要它：

```python
def test_default_values(default_settings: Settings):
    assert default_settings.debug is False
```

pytest 看到参数名 `default_settings`，自动去 fixture 注册表里找同名函数，执行并把返回值注入进来。

为什么这比在每个测试里手写 `settings = Settings()` 好？

1. **复用**：10 个测试都需要 Settings，写一次 fixture 而不是复制 10 遍。
2. **隔离**：fixture 默认每个测试执行一次（function 作用域），测试之间互不影响——这正是 FIRST 原则中 Independent 的保障。
3. **可组合**：fixture 可以依赖其他 fixture，形成依赖链，复杂测试环境的搭建也能保持清晰。

`conftest.py` 是 pytest 的约定文件：放在其中的 fixture 对整个目录下的测试自动可见，无需 import。

### 2.4 monkeypatch：隔离环境变量

测试配置类时最大的坑：**真实环境变量会污染测试结果**。如果你本机恰好设置了 `DEBUG=true`，测试默认值断言就会莫名其妙地失败。

pytest 内置的 `monkeypatch` fixture 专门解决这个问题：

```python
def test_debug_override(monkeypatch: pytest.MonkeyPatch):
    monkeypatch.setenv("DEBUG", "true")
    assert Settings().debug is True
```

`monkeypatch.setenv` 做的事：

1. 设置环境变量 `DEBUG=true`；
2. 测试结束后**自动恢复原值**（无论你写的是 pass 还是 fail）。

这保证了 Repeatable：测试不会改变系统状态，测试之间也不会通过环境变量互相影响。

### 2.5 parametrize：一个测试逻辑，多组输入

Pydantic 会把字符串 `"true"`、`"1"`、`"false"` 都正确转换成布尔值。要验证这个行为，传统写法是复制粘贴 5 个几乎一样的测试函数。`@pytest.mark.parametrize` 用**数据驱动**的方式消除重复：

```python
@pytest.mark.parametrize(
    ("raw", "expected"),
    [
        ("true", True),
        ("True", True),
        ("1", True),
        ("false", False),
        ("0", False),
    ],
)
def test_debug_accepts_common_bool_strings(
    monkeypatch: pytest.MonkeyPatch, raw: str, expected: bool
):
    monkeypatch.setenv("DEBUG", raw)
    assert Settings().debug is expected
```

pytest 会为每组数据生成一个独立测试用例，运行结果里你能看到 5 条独立记录：

```text
test_debug_accepts_common_bool_strings[true-True] PASSED
test_debug_accepts_common_bool_strings[True-True] PASSED
...
```

好处不只是少写代码：当某组数据失败时，测试名里直接带着输入值 `[false-True]`，**失败定位零成本**。

### 2.6 覆盖率：意义与陷阱

`pyproject.toml` 中的配置：

```toml
[tool.coverage.run]
branch = true
source = ["smart_research_agent"]

[tool.coverage.report]
fail_under = 80
```

先理解两个指标：

- **行覆盖率（Line Coverage）**：被执行过的代码行占总行数的比例。
- **分支覆盖率（Branch Coverage）**：每个 `if/else`、`for/while` 的所有分支是否都被执行过。

`branch = true` 开启分支覆盖率，它严格得多——100% 行覆盖可能只有 50% 分支覆盖：

```python
def greet(debug: bool) -> str:
    if debug:
        return "debug on"   # 行 A
    return "debug off"      # 行 B
```

只测 `greet(True)`：行 A、B 中 A 被执行、B 被执行过吗？没有——B 在 else 分支。等等，这段代码里 `return "debug off"` 没被执行，行覆盖率 50%。

换个例子：

```python
def safe_divide(a: float, b: float) -> float:
    if b == 0:
        raise ValueError("b 不能为 0")
    return a / b
```

只测 `safe_divide(4, 2)` → 行覆盖率 100%（if 判断行执行了，return 也执行了），但 `b == 0` 为 True 的分支从未走过。**行覆盖 100%，分支覆盖 50%**。这就是为什么我们开启 `branch = true`。

### 2.7 为什么 fail_under 设 80 而不是 100

这是一个反直觉但重要的工程判断：

1. **边际收益递减**：从 0% 到 80%，每提升一个百分点都能抓到真实 bug；从 95% 到 100%，往往在为 `raise NotImplementedError`、防御性兜底代码写无意义的测试。
2. **覆盖率 ≠ 质量**：覆盖率只说明"代码被执行过"，不说明"断言验证了正确行为"。一个只调用函数不做断言的测试也能提高覆盖率，但它什么也证明不了。
3. **100% 目标会扭曲行为**：团队为了指标写"覆盖式测试"，反而稀释了测试的价值。

正确心态：**覆盖率是发现"哪些代码完全没测试"的工具，不是质量本身。** 我们用 `fail_under = 80` 作为底线闸门，防止测试缺失，但绝不为凑数字写测试。

## 第三章：环境脚本完善 —— 幂等性与可移植性

### 3.1 day001 脚本的三个缺陷

回顾 day001 的 `setup_env.sh`：

```bash
python3 -m venv "$VENV_DIR"
```

问题一：**不幂等**。重复执行会重建 venv，虽然无害但浪费时间，且没有向用户说明。

问题二：**不可移植**。只认 `python3`，但 Windows 上 Python 常常只有 `python` 命令（比如你装的 Anaconda）。venv 的激活路径在 Windows 是 `Scripts/activate`，Unix 是 `bin/activate`，原脚本在 Windows Git Bash 下会直接失败。

问题三：**不防御**。没有 Python 时错误信息不友好；非 Git 仓库时 `pre-commit install` 会报错中断。

### 3.2 幂等性（Idempotency）：运维脚本的第一美德

幂等：**同一个脚本执行 1 次和执行 100 次，系统最终状态相同。**

新版脚本的幂等设计：

```bash
if [ -d "$VENV_DIR" ]; then
    echo "venv 已存在，跳过创建"
else
    "$PYTHON_CMD" -m venv "$VENV_DIR"
fi
```

为什么幂等如此重要？

- **容错重试**：网络抖动导致 pip 安装失败，修复后直接重跑脚本即可，不用担心"venv 已经建了一半"的脏状态。
- **CI/CD 友好**：流水线可能重复执行同一脚本，幂等性保证行为可预期。
- **认知负担低**：用户不需要记住"这个命令只能跑一次"。

幂等是自动化脚本区别于"操作手册"的本质特征——操作手册假设人按顺序执行，幂等脚本对执行次数和时机鲁棒。

### 3.3 可移植性：探测而非假设

```bash
if command -v python3 >/dev/null 2>&1; then
    PYTHON_CMD="python3"
elif command -v python >/dev/null 2>&1; then
    PYTHON_CMD="python"
else
    echo "错误：未找到 python3 或 python，请先安装 Python 3.10+"
    exit 1
fi
```

设计思想：**探测环境，而非假设环境**。

- `command -v` 是 POSIX 标准命令，检查某命令是否存在且可执行，比 `which` 更可靠（`which` 在不同 shell 下行为不一致）。
- 逐级回退（python3 → python → 报错），兼容 Linux/macOS/Windows。
- 最后兜底给出明确错误信息和修复建议，而不是让脚本报一个看不懂的 "command not found"。

venv 激活同样探测：

```bash
if [ -f "$VENV_DIR/Scripts/activate" ]; then
    source "$VENV_DIR/Scripts/activate"   # Windows
else
    source "$VENV_DIR/bin/activate"       # Linux / macOS
fi
```

### 3.4 verify_env.py 的分层检查设计

新版验证脚本按**从底层到上层**的顺序检查：

```
Python 版本 → 第三方包 → 项目配置 → Git 仓库 → Docker
```

这个顺序有讲究：**依赖关系决定检查顺序**。Python 版本不对，后面的包检查毫无意义；包没装好，项目配置必然加载失败。前置检查失败时尽快暴露根因，避免用户被一连串级联错误淹没。

每个检查返回布尔值，最后统一汇总：

```python
results = [
    check_python_version(),
    check_packages(),
    check_project_config(),
    check_git(),
    check_docker(),
]
if all(results):
    ...
```

同时用退出码表达结果：`0` 成功、`1` 失败。这使得脚本可以被其他脚本或 CI 流水线直接消费（`if python scripts/verify_env.py; then ...`）。

注意 Git 和 Docker 两项**只警告不阻塞**（始终返回 True）。这是"严格核心、宽松外围"的策略：没有 Git 仓库不影响写代码，没有 Docker 在 P 阶段也完全没问题，不应该让可选项打断初始化流程。

## 第四章：README 与 docs —— 文档即接口

### 4.1 README 的定位

README 是项目的**第一张脸**，读者（包括三个月后的你自己）会在 30 秒内决定要不要继续看下去。好 README 回答三个问题：

1. 这是什么？（一段话说清定位）
2. 怎么跑起来？（快速开始，命令可直接复制）
3. 结构是什么样的？（目录树，让人知道东西在哪）

day001 的 README 已包含这三部分，day002 新增了 Docker 使用方式和当前阶段说明的更新。

### 4.2 docs/ 目录的职责边界

README 放"快速上手"，`docs/` 放"深入规范"。分工：

## 第五章：Docker 基础 —— 容器化的原理

### 5.1 容器 vs 虚拟机

为什么需要容器？先看它解决什么问题——**"在我机器上能跑"问题**。你的代码依赖 Python 3.10、特定版本的 pydantic、特定的环境变量。换一台机器，换一个队友，部署到服务器，环境就可能不一致。

传统方案是虚拟机（VM）：虚拟出整个操作系统。问题是太重——每个 VM 都要跑完整 OS 内核，GB 级镜像，分钟级启动。

容器的思路完全不同：**共享宿主机内核，只隔离进程的运行环境**。

```
虚拟机：                        容器：
┌─────────────┐                ┌─────────────┐
│   App A     │                │   App A     │
│  依赖库     │                │  依赖库     │
│  Guest OS   │ ← 完整内核      │  隔离命名空间 │ ← 共享宿主机内核
├─────────────┤                ├─────────────┤
│ Hypervisor  │                │ Docker 引擎  │
├─────────────┤                ├─────────────┤
│  Host OS    │                │  Host OS    │
└─────────────┘                └─────────────┘
```

结果：容器镜像是 MB 级，启动是秒级甚至毫秒级，而隔离性（文件系统、网络、进程空间）依然保留。

### 5.2 镜像分层：Dockerfile 为什么那样写

我们的 Dockerfile：

```dockerfile
FROM python:3.11-slim

WORKDIR /app

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

COPY smart_research_agent/ ./smart_research_agent/
COPY pyproject.toml ./
RUN pip install --no-cache-dir -e .

CMD ["python", "-m", "smart_research_agent.main"]
```

关键设计：**先 COPY requirements.txt，装完依赖，再 COPY 源码。** 为什么？

Docker 镜像是**分层（Layer）**的，每条 `FROM/COPY/RUN` 指令生成一个只读层，层与层叠加构成最终镜像。更重要的是——**每一层都会被缓存**：

- 构建时，如果某层的输入（指令 + 涉及文件内容）没变，Docker 直接复用缓存层，跳过执行。
- 一旦某层变了，它**之后的所有层都必须重建**。

依赖安装（`pip install -r requirements.txt`）是整个构建中最慢的一步，可能几分钟。如果把 `COPY . .`（全部源码）放在最前面，那么你每改一行代码，缓存就失效，依赖全部重装——开发体验灾难。

把构建分为"慢而稳定的依赖层"和"快而多变的源码层"后：

- 第一次构建：装依赖（慢）。
- 之后改代码构建：依赖层命中缓存（瞬间），只重建源码层（秒级）。

这是 Dockerfile 编写的第一原则：**变化频率低的内容放前面，变化频率高的内容放后面。**

### 5.3 .dockerignore：构建上下文的守门员

执行 `docker build` 时，Docker 先把整个目录（构建上下文）打包发给 Docker 引擎。没有 `.dockerignore` 的话，`venv/`（几百 MB）、`.git/`、`.env`（含密钥！）全部被打包发送——又慢又危险。

我们的 `.dockerignore` 排除了虚拟环境、Git 数据、密钥文件、缓存、日志、本地数据。这和 `.gitignore` 思想相同，但服务的目标不同：

- `.gitignore`：保护仓库，防止敏感/临时文件进入版本历史。
- `.dockerignore`：保护镜像，减小构建上下文，防止密钥泄露到镜像里。

> 安全警示：即使 `.env` 只在构建阶段被 COPY 进镜像再用层覆盖，它仍存在于历史层中，可以被 `docker history` 或解压镜像提取。**密钥绝不能进入任何镜像层**，`.dockerignore` 是第一道防线。

### 5.4 为什么 P2 就要准备 Dockerfile

现在项目还没有服务化（FastAPI 是 M4 的事），为什么现在就写 Dockerfile？

1. **环境即代码（Environment as Code）**：Dockerfile 是对"这个项目需要什么样的运行环境"的精确、可执行描述。它比任何文档都权威。
2. **为后续打基础**：M2 阶段要用 Docker 部署 MCP Server，M6 阶段要用 Docker Compose 编排向量库和服务。今天的基础镜像就是那个演进的起点。
3. **可复现性**：任何人在任何机器上 `docker build` 都能得到一模一样的环境——这正是 100 天项目需要的可移植性。

## 第六章：今日总结 —— 从骨架到流水线

| 能力 | 原理核心 | 落地位置 |
|------|----------|----------|
| Git 工作流 | 对象模型、分支即指针、原子提交 | `docs/git_workflow.md` |
| 单元测试 | 测试金字塔、FIRST、依赖注入 | `tests/conftest.py`、`tests/test_*.py` |
| 覆盖率 | 行 vs 分支覆盖、80% 底线 | `pyproject.toml` `[tool.coverage]` |
| 环境脚本 | 幂等性、探测式可移植 | `scripts/setup_env.sh`、`scripts/verify_env.py` |
| 容器化 | 镜像分层缓存、构建上下文 | `Dockerfile`、`.dockerignore` |

这些能力的共同主线：**把一切"靠人肉记住"的东西，变成"由工具和代码保证"的东西**。Git 规范靠约定文档、测试靠 pytest 自动跑、环境靠脚本一键搭、运行环境靠 Dockerfile 精确描述——这是工程化的终极方向，也是后续 Agent 系统能够可靠迭代的前提。
