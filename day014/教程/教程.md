## 第二章：记忆系统复盘（D5 + D6）—— Agent 的记忆不在模型里

### 2.1 大前提：LLM 是无状态的

这是整个记忆系统的地基，值得放在最前面再强调一次：**模型本身什么都不记得。** 聊天产品里"AI 记得你叫小明"，真相是每次请求都把完整对话历史重放给模型。无状态是 LLM 服务的设计选择（可水平扩展、容错简单），代价是**状态管理的责任转移到了应用层**。

所以"Agent 的记忆"不是一个 AI 问题，而是一个工程问题：

> **应用层维护的消息历史缓冲区 + 持久化知识库，负责在每轮请求前组装出一份"恰到好处"的上下文。**

"恰到好处"的三个要求——完整性、有界性、隔离性——分别对应 D5 的三块内容：数据结构、截断策略、会话管理。

### 2.2 短期记忆（D5）：一个有界、保序、保住 system 的列表

**一句话本质**：`ShortTermMemory` 是一个消息列表，超过 `max_messages` 时保住 system 消息、按 FIFO 丢弃最老的其余消息。

```python
def _truncate(self) -> None:
    if len(self._messages) <= self.max_messages:
        return
    system_msgs = [m for m in self._messages if m.role == "system"]
    others = [m for m in self._messages if m.role != "system"]
    keep = max(self.max_messages - len(system_msgs), 0)
    self._messages = system_msgs + others[-keep:] if keep else system_msgs[: self.max_messages]
```

完整代码见 [../../day010/源码/smart-research-agent/smart_research_agent/memory/short_term.py](../../day010/源码/smart-research-agent/smart_research_agent/memory/short_term.py)。

**为什么**：

- 上下文窗口是稀缺资源：输入输出共享、按 token 计费、还有"中间遗忘"（Lost in the Middle）现象——**无脑塞满窗口不但贵，效果反而更差**。主动截断是特性，不是妥协。
- system 消息是行为契约（ReAct 格式、工具清单都在里面），丢了它模型立刻"忘记自己是谁"，所以**钉在头部永不淘汰**；对话消息随时间贬值，可以 FIFO 淘汰。
- 截断在 `add()` 写入侧立即执行，不变量"长度 ≤ 上限"永不被打破——**在写入侧维护不变量**，比在读取侧临时裁剪可靠。
- `max_messages=20` 不是拍脑袋：ReAct 一轮行动消耗 2 条消息（assistant + Observation），20 条约覆盖 `max_steps=10` 的典型任务。记忆容量和步数上限是**联动设计**的。

**常见误区**：

- **误区一：认为截断是"有损的坏设计"。** 恰恰相反，结合"中间遗忘"，精挑细选的短上下文常常胜过塞满的长上下文。
- **误区二：在 `get_all()` 里截断。** 读侧截断意味着内部状态无限膨胀，只是"看起来"短。真截断必须发生在写入侧。
- **误区三：`others[-0:]` 当空列表用。** Python 里 `-0 == 0`，`others[-0:]` 是**整个列表**——这是截断逻辑最著名的边角陷阱，`keep == 0` 时必须显式分支。

### 2.3 会话隔离（D5）：记忆必须分房间

**一句话本质**：`SessionManager` 是一个 `dict[str, ShortTermMemory]`，按 session_id 给每个会话独立记忆，杜绝串扰。

**为什么**：全局共享一份记忆 = 用户 A 的银行卡号出现在发给用户 B 的上下文里。会话串扰（Context Bleeding）是真实的隐私事故，不是理论风险。隔离粒度选"会话"而非"用户"，因为同一用户可以并行开"调研 RAG"和"调研 MCP"两个话题。

两个值得记住的设计哲学：

- **严格读取，宽容清理**：`get_memory()` 对未知 ID 抛 `KeyError`（Fail Fast，拼错的 ID 不能静默新建会话）；`close_session()` 用 `pop(id, None)` 容忍重复关闭（清理动作应当幂等）。
- **session_id 用 `uuid.uuid4().hex[:12]`**：不可猜测、零协调成本。防碰撞 12 位绰绰有余；防猜测要靠鉴权与限流，不该把安全押在 ID 长度上（纵深防御）。

### 2.4 长期记忆（D6）：从"按时间保留"到"按相关性取回"

**一句话本质**：`LongTermMemory` = Embedding 编码 + 向量库存储 + 相似度检索，三步模型——**remember 写入、recall 检索、注入上下文**。

```python
def remember(self, text: str, metadata: dict | None = None) -> str:
    record_id = uuid.uuid4().hex[:12]
    vector = self._embedding.embed(text)
    self._store.add(VectorRecord(id=record_id, text=text, vector=vector, metadata=metadata or {}))
    return record_id

def recall(self, query: str, top_k: int = 3) -> list[str]:
    query_vector = self._embedding.embed(query)
    return [r.text for r, _score in self._store.search(query_vector, top_k=top_k)]
```

完整代码见 [../../day010/源码/smart-research-agent/smart_research_agent/memory/long_term.py](../../day010/源码/smart-research-agent/smart_research_agent/memory/long_term.py)。

**为什么**：

- 短期记忆治不了三类病：被 FIFO 淘汰的旧事实（"我花生过敏"）、放不进窗口的大文档、新会话的冷启动。本质是**短期记忆按时间保留，而我们需要按相关性取回**。
- 关键词匹配做不到语义取回——"我吃什么会起疹子"和"我对花生过敏"没有共同关键词，但语义向量里它们很近。这就是 Embedding 存在的理由：**语义相近 ⇒ 向量相近**。
- 选**余弦相似度**而非欧氏距离：向量的"方向"承载语义，"长度"往往只是文本长度、词频等噪声；余弦只看方向。归一化后余弦退化为点积，计算更快，分数落在 [-1, 1] 便于设阈值。
- 教学版 `InMemoryVectorStore` 用暴力最近邻（O(N) 全表扫描），生产级方案（ChromaDB / FAISS / HNSW）用近似最近邻索引把检索压到亚线性——**接口不变，实现可换**，这正是抽象的价值。

**常见误区**：

- **误区一：把所有消息都向量化入库。** 那是日志不是记忆。噪声淹没信号、存储膨胀、隐私风险——写入策略（显式指令/规则抽取/会话摘要）是上层决策，`remember` 只提供机制。**机制要稳定，策略要可演进。**
- **误区二：以为 `MockEmbedding` 能测语义检索。** 它是 SHA-256 哈希伪向量，确定但**没有语义**——语义相近的文本不会得到相近的向量。它只够验证"存取链路通了"，验证检索质量要用真实 embedding 或手工构造的向量。
- **误区三：认为向量维度越高越好。** 维度灾难下高维距离趋同，边际收益递减；存储与计算成本线性增长。768~3072 是常见甜点区。

### 2.5 两级记忆的分工对照

| 维度 | 短期记忆（D5） | 长期记忆（D6） |
|------|---------------|----------------|
| 存什么 | 当前会话的消息历史 | 跨会话的事实与知识 |
| 保留策略 | 按时间：FIFO + system 钉住 | 按相关性：余弦相似度 top-k |
| 生命周期 | 会话级，`close_session` 即销毁 | 持久化，跨会话存活 |
| 取回方式 | 全量重放进 messages | 按需 recall，结果注入上下文 |
| 对应人类记忆 | 工作记忆 | 长期记忆 |
| 失效模式 | 旧信息被淘汰（重复查已查过的） | 噪声入库、检索不相关 |

**它们是互补不是替代**：短期记忆管"刚才聊了什么"，长期记忆管"很久以前但此刻相关的知识"。一个完整的 Agent 两者都要。

## 第三章：规划与反思复盘（D7 + D8）—— 想得全，知错能改

### 3.1 Planner（D7）：用全局计划治 ReAct 的三大困境

**一句话本质**：`Planner` 在执行开始前一次性调用 LLM，把用户目标拆解成有序子任务列表（`Plan`），再逐个交给 ReAct 循环执行——**先想后做**。

**为什么**：纯 ReAct 是贪心策略，每步只做局部最优决策，复杂任务上会犯三种病：

1. **迷失方向**——陷入细节忘了全局目标；
2. **步骤冗余**——不记得搜过什么，重复搜索；
3. **提前收场**——任务完成三分之二就交卷。

显式的 `Plan` 同时治三病：方向有计划牵引、进度有清单可查、完成标准有计划兜底。本质洞察：**局部最优的序列拼不出全局最优的路径**，所以需要一个全局视角的模块。

落地层面的两个关键设计（详见 [day010 教程](../../day010/教程/教程.md) 与 [planner.py](../../day010/源码/smart-research-agent/smart_research_agent/agent/planner.py)）：

- **提示词锁定结构**：输出必须是 JSON 字符串数组、3~6 条、动词开头。凡是程序消费的 LLM 输出，都要在提示词里显式锁定结构——和 day006 用 `Thought:/Action:` 锁定格式是同一思想。
- **防御式解析四道防线**：`find/rfind` 定位边界 → `json.loads` 语法校验 → `isinstance` 类型校验 → 非空语义校验，每层失败抛 `PlanParseError(ValueError)`。LLM 输出是不可信输入，和表单、第三方 API 响应同等待遇。

**职责边界**（判断"新功能该放哪层"的尺子）：

| 关注点 | Planner | ReactAgent |
|--------|---------|-----------|
| 输入 | 用户目标（粗粒度） | 单个子任务（细粒度） |
| LLM 调用 | 恰好 1 次 | 每子任务 1~max_steps 次 |
| 知道工具吗 | 不知道 | 知道（ToolRegistry） |
| 失败语义 | `PlanParseError` | 达到最大步数 |

**常见误区**：

- **误区一：让 ReAct 在系统提示词里"自己拆任务"。** 内嵌拆解存在于模型脑子里，程序无法读取、无法审计、失败时无法定位；且规划信息稀释 ReAct 上下文的注意力。显式 `Plan` 对象才可观察、可测试。
- **误区二：认为计划一旦做出就该执行到底。** 环境会变（子任务失败、发现新信息），僵化的计划是枷锁。成熟方案都配 RePlanner 定期重规划——这是 D7 埋的伏笔。
- **误区三：子任务拆得越细越好。** 过细 = 每个子任务起一次 ReAct 循环，成本爆炸，且把"执行细节"混进了"计划"。3~6 条是经验甜点。

### 3.2 Reflexion（D8）：把失败变成可学习的经验

**一句话本质**：Reflexion 在任务失败后，让 LLM 对自己的执行轨迹做一次"复盘"——总结失败原因、生成改进建议，把这条**文字形式的反思**存入记忆，带着它重试任务。

**为什么**：没有反思的 Agent 犯同一个错的方式是一模一样的——ReAct 循环是确定性的编排，同样的输入大概率走出同样的失败轨迹。重试一百次也没用。Reflexion 的洞察是：**LLM 不需要改权重就能从失败中学习，只要让它看到自己的失败轨迹并显式总结教训。** 这是一种"语言形式的强化学习"：奖励信号（成功/失败）不更新参数，而是变成一段自然语言反馈进入下一轮上下文。

一次完整的反思循环：

```text
执行任务（ReAct 循环）
    │
    ▼
成功？──是──▶ 返回结果
    │否（步数耗尽 / 结果校验失败）
    ▼
生成反思：把完整轨迹（Thought/Action/Observation 历史）
          喂给 LLM，问"为什么失败？下次怎么改进？"
    │
    ▼
反思文本存入记忆（短期注入下轮上下文，或长期 remember 入库）
    │
    ▼
带着"上一次失败的教训"重试任务 ──▶ 回到第一步
```

设计要点：

- **反思的对象是轨迹不是结果**：只看"最终答案错了"模型只能瞎猜原因；给它完整的 Thought/Action/Observation 序列，它才能定位"第 3 步搜错了关键词"这类具体失误。这直接复用了 day006 以来每步落盘的 history——**可观测性是反思能力的前提**。
- **反思次数必须有上限**：反思-重试也是一个循环，和 ReAct 一样需要熔断（`max_reflections`），否则失败任务会无限烧钱。
- **反思是记忆系统的第一个真实客户**：D5/D6 建好的记忆设施，在这里第一次体现"跨尝试传递经验"的价值——上一轮失败的教训通过记忆进入下一轮上下文。

**常见误区**：

- **误区一：认为 Reflexion 提升了模型能力。** 没有。模型权重一个数字都没变，变的是上下文——**改变输入分布来改变输出质量**。这也是它被归类为"推理时技术"而非"训练时技术"的原因。
- **误区二：失败立刻反思重试，不限次数。** 有些失败是环境性的（工具超时、网络抖动），反思治不了；有些任务是模型能力边界外的，反思一百次也治不了。反思要有预算，且要和"错误分类"配合。
- **误区三：反思结果只留一句话结论。** "下次注意点"没有信息量。好的反思要包含：失败发生在哪一步、当时的假设是什么、假设为什么错、下次的具体替代动作。

### 3.3 Planner 与 Reflexion 的分工

两个模块都治"复杂任务失控"，但治的阶段不同：

| 维度 | Planner（D7） | Reflexion（D8） |
|------|---------------|------------------|
| 介入时机 | 执行**前**：防患于未然 | 失败**后**：亡羊补牢 |
| 视角 | 全局目标 → 分解 | 历史轨迹 → 归因 |
| 产出 | `Plan`（子任务列表） | 反思文本（改进建议） |
| 对治的病 | 迷失方向、步骤冗余、提前收场 | 重复犯同样的错 |
| 记忆依赖 | 弱（当前架构子任务独立执行） | 强（反思靠记忆跨尝试传递） |

一个健壮的 Agent 两者都要：**规划降低失败概率，反思提高失败后的恢复力。**

## 第四章：多 Agent 协作复盘（D9）—— 当单 Agent 的能力到顶

### 4.1 为什么需要多个 Agent

**一句话本质**：把"研究员、分析师、撰稿人"三类职责拆成三个独立 Agent，各自有专属的系统提示词、工具集和上下文，通过显式的消息传递交接结果。

**为什么**：单 Agent 路线有两个天花板：

1. **上下文稀释**：一个 Agent 既搜资料又做分析又写报告，系统提示词越来越长、上下文越来越杂，每个角色都做不好——和 day010 "不让 ReAct 自己拆任务"是同一个注意力稀释问题，只是放大了一级。
2. **提示词互相打架**：研究员要"穷举、不放过细节"，撰稿人要"精炼、面向读者"，两种互相矛盾的指令塞在一个 system prompt 里，模型只能和稀泥。

多 Agent 的解法本质上是**关注点分离在 Agent 层面的重演**：每个 Agent 只对一个角色负责，提示词可以写得很纯粹、工具集可以最小化（研究员只有搜索工具，撰稿人一个工具都没有）。

### 4.2 协作模式：消息传递与结果交接

```text
用户目标
   │
   ▼
┌──────────┐   原始资料    ┌──────────┐   分析结论    ┌──────────┐
│  研究员   │ ───────────▶ │  分析师   │ ───────────▶ │  撰稿人   │ ──▶ 最终报告
│ Researcher│              │ Analyst   │              │ Writer    │
│ 工具:搜索 │              │ 工具:计算  │              │ 工具:无    │
└──────────┘              └──────────┘              └──────────┘
```

关键设计决策：

- **交接物是结构化结果，不是聊天记录**。研究员交付给分析师的是"收集到的资料文本"，不是自己的全部 ReAct 历史——否则上下文稀释问题只是换了个地方重演。**每个交接点都是一次信息压缩与提炼。**
- **串行流水线是最简单的协作拓扑**。先跑通"研究员 → 分析师 → 撰稿人"这条直线，再考虑更复杂的拓扑（并行、竞争、辩论）。和 D7 的"子任务串行下发"同理：串行保证下游能利用上游结果。
- **编排者是代码不是某个 Agent**。谁在什么时候把什么交给谁，由 Python 编排逻辑显式决定——控制权始终在代码手里，这和 ReAct 循环"驱动者是 for 循环不是 LLM"一脉相承。

**常见误区**：

- **误区一：Agent 越多越好。** 每多一个 Agent 就多一次完整 LLM 调用链的成本与失败面。角色拆分要有真实收益（提示词纯度、工具隔离），不为拆而拆。
- **误区二：让 Agent 之间自由对话。** 自由多轮对话的终止条件、成本控制都是难题。本项目用"定向交接"（A 的产出作为 B 的输入）而非"群聊"，行为可预测、可测试。
- **误区三：多 Agent 是规划的替代品。** 不是。Planner 拆的是"任务步骤"，多 Agent 拆的是"角色职责"——复杂系统里两者叠加：先规划出阶段，每个阶段由对应角色的 Agent 执行。

## 第五章：LangGraph 状态图复盘（D10）—— 把隐式编排变成显式资产

### 5.1 为什么需要状态图

**一句话本质**：LangGraph 把 Agent 流程建模为**状态（State）+ 节点（Node）+ 边（Edge）** 的有向图：每个节点是一个纯函数（读状态、返回状态更新），边定义流转规则，框架负责驱动循环与持久化。

**为什么**：回看 day006~012 的代码，编排逻辑散落在各处的 `for` / `while` 循环里——ReAct 的循环在 `react_agent.py`，反思重试的循环在反思模块里，多 Agent 交接在编排函数里。这带来三个痛点：

1. **流程不可见**：想知道"整个 Agent 有哪些状态、什么条件下走哪条路"，得把几个文件的循环读一遍在脑内拼图。
2. **不可中断恢复**：进程崩溃，跑到第 7 步的任务从头再来；想让人工审核中间结果，没有插入点。
3. **循环逻辑重复造**：每个模块都自己写"循环 + 终止条件 + 异常处理"。

状态图把这三个痛点一次解决：流程是一张**可以画出来给人看的图**；状态在每次节点执行后可被 checkpointer 持久化；循环由框架统一驱动。

### 5.2 三个核心概念

| 概念 | 本质 | 本项目对应 |
|------|------|-----------|
| **State** | 一个在节点间流动的数据字典（通常用 TypedDict 定义），每个节点返回"对状态的增量更新" | 目标、计划、当前步数、history、反思记录、最终结果 |
| **Node** | 接收状态、返回状态更新的函数——节点之间不直接调用，只通过状态通信 | plan 节点、execute（ReAct 单步）节点、reflect 节点 |
| **Edge** | 流转规则：普通边无条件流转，条件边由路由函数根据状态决定去向 | execute 后路由：出 Final Answer → END，步数耗尽 → reflect，否则 → execute |

典型骨架（langgraph 1.2 API）：

```python
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver

graph = StateGraph(AgentState)
graph.add_node("plan", plan_node)
graph.add_node("execute", execute_node)
graph.add_node("reflect", reflect_node)
graph.add_edge(START, "plan")
graph.add_edge("plan", "execute")
graph.add_conditional_edges("execute", route_after_execute,
                            {"continue": "execute", "reflect": "reflect", "done": END})
graph.add_edge("reflect", "execute")

app = graph.compile(checkpointer=MemorySaver())
result = app.invoke(initial_state, config={"configurable": {"thread_id": "demo-1"}})
```

### 5.3 持久化与断点：checkpointer 的价值

`MemorySaver` 让每次节点执行后的状态快照按 `thread_id` 存下来。这直接解锁两种能力：

- **断点续跑**：进程重启后，用同一个 `thread_id` 调 `invoke` 能从中断处继续——D8 反思重试、长任务执行都因此变得可恢复。
- **时间旅行调试**：可以取出历史上任意一个状态快照检查"当时状态长什么样"——可观测性从日志级别升级到状态级别。

`MemorySaver` 是内存版教学实现，生产环境换 Redis/Postgres 版 checkpointer，图定义一行不改——又一次"接口不变，实现可换"。

### 5.4 重构换来了什么，代价是什么

| 维度 | 手写循环（day006~012） | LangGraph 状态图（day013） |
|------|----------------------|---------------------------|
| 流程可见性 | 散在各文件的循环里 | 一张图，可加条件边自描述 |
| 中断恢复 | 无 | checkpointer + thread_id |
| 循环与终止 | 每个模块自己写 | 框架驱动，条件边表达 |
| 测试方式 | 直接调函数 | 编译图后 invoke，或单测节点函数 |
| 学习/调试成本 | 零框架依赖 | 要理解 State 合并语义、路由函数 |
| 适合场景 | 单一固定流程 | 多分支、需恢复、需人工介入的流程 |

**常见误区**：

- **误区一：把节点写成互相调用的函数。** 节点间只能通过 State 通信，这是图能持久化、能重放的根基。一旦节点 A 直接调节点 B，图的边界就被架空了。
- **误区二：State 设计成大杂烩。** State 的每个字段都应该有明确的写入方和消费方；什么都往里塞的 State 等于全局变量堆。
- **误区三：认为迁到 LangGraph 就要抛弃之前的代码。** 恰恰相反——节点函数内部调用的还是 day006 的解析器、day010 的 Planner、day011 的反思逻辑。**状态图是编排层的重构，不是业务逻辑的重写。** Agent 架构的演进是叠加而不是替换。

## 第六章：完整架构串讲 —— 六块拼图如何组成一个 Agent

这是本周最重要的一张图。一个复杂目标从进入到交付，穿过全部六天的组件：

```text
                          ┌──────────────┐
                          │   用户目标    │
                          └──────┬───────┘
                                 ▼
        ┌────────────────────────────────────────────────┐
        │            LangGraph 状态图（D10）               │
        │  ┌──────────┐   ┌──────────┐   ┌──────────┐    │
        │  │ plan 节点 │──▶│execute 节点│◀─┤reflect 节点│  │
        │  │ (D7)     │   │ (D4/D9)  │──▶│ (D8)     │    │
        │  └──────────┘   └────┬─────┘   └──────────┘    │
        │        Planner       │ 条件边：完成→END           │
        │        拆成子任务      │        步数耗尽→reflect    │
        └──────────────────────┼─────────────────────────┘
                               ▼ 每个子任务 / 每个角色
        ┌────────────────────────────────────────────────┐
        │        执行层：ReactAgent / 角色 Agent（D9）       │
        │   研究员 ──资料──▶ 分析师 ──结论──▶ 撰稿人        │
        │   每个 Agent 内部跑 ReAct 循环（D4）               │
        └──────┬───────────────────────────┬─────────────┘
               ▼                           ▼
   ┌───────────────────────┐   ┌───────────────────────┐
   │  短期记忆（D5）          │   │  长期记忆（D6）          │
   │  ShortTermMemory       │   │  LongTermMemory        │
   │  · 组装每次 LLM 调用的   │   │  · remember: 子任务结论  │
   │    messages（有界、隔离）│   │    / 反思教训 入库       │
   │  · system 钉住 + FIFO   │   │  · recall: 执行前检索     │
   │    截断                 │   │    相关知识注入上下文     │
   └───────────────────────┘   └───────────────────────┘
               │                           │
               └─────────────┬─────────────┘
                             ▼
                    ┌─────────────────┐
                    │  LLM 层（D3）     │  BaseLLM / MockLLM
                    │  工具层（D2/D3）  │  BaseTool / ToolRegistry
                    └─────────────────┘
```

一次完整任务的数据流（以"调研三个 RAG 框架并写选型报告"为例）：

1. **规划（D7）**：目标进 plan 节点，`Planner.plan()` 拆出 `["收集候选框架清单", "逐个收集资料", "对比分析", "撰写报告"]`，写入 State。
2. **执行（D4/D9）**：execute 节点按子任务调度——"收集资料"类交给研究员 Agent（带搜索工具），"对比分析"交给分析师，"撰写"交给撰稿人；每个 Agent 内部跑各自的 ReAct 循环。
3. **记忆加持（D5/D6）**：每次 LLM 调用前，短期记忆组装有界上下文；子任务产出 `remember()` 进长期记忆，后续子任务执行前 `recall()` 取回相关资料——day010 "子任务间上下文传递"的第三种方案在这里落地。
4. **失败恢复（D8）**：某子任务步数耗尽，条件边路由到 reflect 节点，LLM 对轨迹复盘生成改进建议，存入记忆，边路由回 execute 重试（有次数上限）。
5. **持久化（D10）**：每个节点执行后状态快照入 `MemorySaver`，进程崩溃后用同一 `thread_id` 断点续跑。
6. **交付**：撰稿人产出最终报告，条件边路由到 END。

读图要点：

- **每个组件都能单独回答"删掉我会怎样"**：删 Planner → 复杂任务迷失方向；删反思 → 失败任务原地重试一百次；删长期记忆 → 子任务 4 不知道子任务 2 查到了什么；删短期记忆 → 每次 LLM 调用都是金鱼；删 LangGraph → 流程不可见、崩溃从头再来。
- **层与层之间靠数据契约通信**：`Plan`、反思文本、`VectorRecord`、State 字典——没有任何一层直接伸手进另一层的内部实现。
- **控制权始终在代码**：LLM 只在节点内部被询问，走哪条边、何时终止由路由函数和框架决定。

## 第七章：核心概念对照表

| 概念 | 一句话本质 | 解决什么问题 | 关键机制 | 典型失效模式 |
|------|-----------|-------------|----------|-------------|
| 短期记忆 `ShortTermMemory` | 有界消息列表，写入侧截断 | LLM 无状态，需重放历史 | system 钉住 + FIFO | 旧信息被淘汰，重复劳动 |
| 会话管理 `SessionManager` | 按 session_id 隔离的记忆字典 | 会话串扰（隐私+污染） | uuid、严格读宽容清 | 内存泄漏（无 TTL） |
| 长期记忆 `LongTermMemory` | Embedding + 向量库 + top-k 检索 | 按相关性取回旧知识 | remember / recall / 余弦相似度 | 噪声入库稀释信号 |
| 规划 `Planner` | 执行前一次性拆解目标 | ReAct 局部最优三困境 | JSON 输出 + 四道防线解析 | 计划僵化，环境变化不适应 |
| 反思 `Reflexion` | 失败后对轨迹复盘，教训入记忆重试 | 重复犯同样的错 | 轨迹回放 + 反思文本注入 | 无预算地无限重试 |
| 多 Agent | 角色职责分离 + 定向交接 | 提示词打架、上下文稀释 | 结构化交接物、串行流水线 | 为拆而拆，成本失败面膨胀 |
| LangGraph 状态图 | State + Node + Edge 显式编排 | 流程不可见、不可恢复 | 条件边、checkpointer、thread_id | State 膨胀成全局变量堆 |

### 易混淆三对

**（1）短期记忆 vs 长期记忆**：按时间保留 vs 按相关性取回；会话级 vs 持久化；全量重放 vs top-k 注入。互补不替代。

**（2）Planner vs Reflexion**：执行前防患 vs 失败后补救；目标分解 vs 轨迹归因。前者降失败率，后者提恢复力。

**（3）多 Agent vs LangGraph**：多 Agent 是**职责拓扑**（谁干什么），LangGraph 是**编排机制**（流程怎么走）。两者正交：你可以手写循环调度多个 Agent（day012 的形态），也可以用状态图编排单个 ReAct Agent。

## 第八章：常见误区清单（速查版）

把全文散落的"常见误区"收敛成一份清单，考前自测用：

1. ❌ "截断是有损的坏设计" → 结合中间遗忘现象，主动截断是特性。
2. ❌ 在 `get_all()` 读取侧截断 → 真截断必须在写入侧维护不变量。
3. ❌ `others[-0:]` 是空列表 → 它是整个列表，`-0 == 0`。
4. ❌ 把所有消息都向量化入库 → 那是日志不是记忆，机制与策略要分层。
5. ❌ 用 `MockEmbedding` 测语义检索质量 → 哈希伪向量没有语义，只验证链路。
6. ❌ 让 ReAct 在 prompt 里"自己拆任务" → 隐式拆解不可观察、不可审计、稀释注意力。
7. ❌ 计划做出后执行到底 → 需要 RePlanner 应对环境变化。
8. ❌ Reflexion 提升了模型能力 → 权重没变，变的是输入上下文。
9. ❌ 反思重试不设上限 → 反思要有预算，还要区分"可反思的失败"与"环境性失败"。
10. ❌ Agent 越多越好 / 自由群聊 → 定向交接、串行先行、拆分要有真实收益。
11. ❌ LangGraph 节点之间直接函数调用 → 节点只能通过 State 通信。
12. ❌ 迁到状态图就要重写业务逻辑 → 节点内部复用既有的 parser/Planner/记忆组件，演进是叠加不是替换。
