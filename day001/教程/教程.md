## 第一章：从脚本到系统 —— 为什么需要工程化

### 1.1 脚本思维 vs 系统思维

很多初学者写 AI 代码的习惯是：写一个 `main.py`，把 LLM 调用、工具调用、提示词模板、日志打印全部堆进去，运行一次能出结果就结束。这在 demo 阶段没问题，但当你要构建一个**多 Agent、多工具、多环境部署**的系统时，脚本会迅速失控：

- **配置散落各处**：API Key 写在代码里，切换环境要改代码。
- **依赖混乱**：`pip install` 一堆包，但说不清楚哪些是必要的。
- **无法测试**：业务逻辑和打印混在一起，改一行代码要手动跑一遍看效果。
- **协作困难**：别人（或未来的自己）无法快速理解项目结构。

工程化的核心目标只有一个：**让系统可预测、可维护、可扩展。**

### 1.2 工程化对 AI 项目的特殊价值

AI 项目比传统软件更需要工程化，因为：

1. **不确定性高**：模型输出不可预测，必须通过日志、测试、监控来建立确定性边界。
2. **迭代速度快**：Prompt、模型、工具都在快速演进，需要快速重构而不破坏现有功能。
3. **成本敏感**：每次 LLM 调用都花钱，配置管理和成本控制必须前置。
4. **安全合规**：涉及用户数据、工具调用权限，必须有审计和防护能力。

因此，我们今天搭建的骨架，本质上是在为后续的 Agent 推理、MCP 协议、RAG 检索、模型微调建立**可承载的基础设施**。

## 第二章：项目结构设计 —— 关注点分离原则

### 2.1 目录结构反映架构

我们采用经典的 Python 包结构：

```text
smart-research-agent/
├── smart_research_agent/   # 主包：业务逻辑
│   ├── __init__.py
│   ├── config.py
│   ├── main.py
│   └── utils/
│       ├── __init__.py
│       └── logger.py
├── scripts/                # 辅助脚本：一次性操作
│   ├── setup_env.sh
│   └── verify_env.py
├── tests/                  # 单元测试：验证逻辑
│   ├── __init__.py
│   └── test_config.py
├── pyproject.toml          # 项目元数据与工具配置
├── requirements.txt        # 依赖列表
├── .env.example            # 环境变量模板
├── .gitignore
├── .pre-commit-config.yaml
└── README.md
```

这个结构体现了**关注点分离（Separation of Concerns）**：

| 目录 | 职责 | 为什么这样分 |
|------|------|-------------|
| `smart_research_agent/` | 核心 Python 包 | 业务逻辑的唯一入口，便于导入和测试 |
| `scripts/` | 运维脚本 | 环境初始化、验证等一次性操作，不进入运行时 |
| `tests/` | 测试代码 | 与业务代码分离，避免测试污染生产包 |
| 根目录配置文件 | 元数据、依赖、规范 | 集中管理项目级配置 |

### 2.2 包名与目录名的约定

注意两个命名差异：

- 项目目录：`smart-research-agent`（连字符）
- Python 包：`smart_research_agent`（下划线）

这不是随意为之，而是 Python 社区的规范：

- **PyPI 包名 / 项目目录名** 通常用连字符（kebab-case），因为 URL 和文件系统更友好。
- **Python 模块名** 必须用合法标识符，连字符不允许，所以用下划线（snake_case）。

理解这个差异，后续在使用 `pip install -e .` 或 `python -m smart_research_agent.main` 时就不会困惑。

### 2.3 `__init__.py` 的作用

`smart_research_agent/__init__.py`：

```python
"""智研 AI 助手主包."""

__version__ = "0.1.0"
```

这个文件看似简单，但决定了：

1. Python 把 `smart_research_agent/` 识别为**包（package）**，而不是普通目录。
2. `__version__` 提供版本信息，后续打包发布、日志记录、API 版本控制都会用到。
3. 它是包的命名空间入口，可以在这里做包级别的导入或初始化。

> 思考题：如果删掉 `__init__.py`，Python 3 会把它当成 namespace package，仍然可以导入，但会失去对包行为的控制。为什么要显式保留它？

## 第三章：依赖管理 —— pyproject.toml 的设计演进

### 3.1 从 requirements.txt 到 pyproject.toml

Python 依赖管理经历了几个阶段：

| 时代 | 工具 | 问题 |
|------|------|------|
| 早期 | `setup.py` + `requirements.txt` | 配置分散，元数据与依赖分离 |
| 中期 | `Pipfile` / `poetry.lock` | 工具碎片化，学习成本高 |
| 现代 | `pyproject.toml` | 统一标准，工具链集成 |

`pyproject.toml` 的核心价值是**单一事实来源（Single Source of Truth）**：项目元数据、依赖、构建配置、代码规范配置全部集中在一个文件中。

### 3.2 关键字段的设计意图

```toml
[project]
name = "smart-research-agent"
version = "0.1.0"
description = "智研 AI 助手 - 100天AI学习主线项目"
readme = "README.md"
requires-python = ">=3.10"
license = { text = "MIT" }
dependencies = [
    "pydantic>=2.0",
    "pydantic-settings>=2.0",
    "python-dotenv>=1.0.0",
]

[project.optional-dependencies]
dev = [
    "ruff>=0.6.0",
    "black>=24.0",
    "mypy>=1.11.0",
    "pre-commit>=3.8.0",
    "pytest>=8.0",
    "pytest-cov>=5.0",
]

[project.scripts]
smart-research-agent = "smart_research_agent.main:main"
```

| 字段 | 设计意图 | AI 项目意义 |
|------|----------|-------------|
| `name` | 项目唯一标识 | 打包、发布、引用时的标识 |
| `version` | 语义化版本 | 模型迭代、实验对比时追踪代码版本 |
| `requires-python` | Python 版本约束 | 确保语法特性和依赖兼容性 |
| `dependencies` | 运行时依赖 | 最小化生产环境安装体积 |
| `dev` 可选依赖 | 开发工具 | 代码检查、测试只在开发环境安装 |
| `project.scripts` | 命令行入口 | 让用户直接运行 `smart-research-agent` |

### 3.3 运行时依赖 vs 开发依赖

我们故意把依赖分为两类：

- **运行时依赖**（`pydantic`, `pydantic-settings`, `python-dotenv`）：项目运行必须安装。
- **开发依赖**（`ruff`, `black`, `mypy`, `pre-commit`, `pytest`）：只在开发环境安装，生产环境不需要。

这种分离的意义：

1. **生产环境轻量**：部署时只装 `pip install .`，不装开发工具，减小镜像体积。
2. **版本隔离**：开发工具的版本升级不会影响生产代码。
3. **CI/CD 区分**：流水线可以单独跑 `pip install -e ".[dev]"` 做代码检查。

### 3.4 为什么还需要 requirements.txt

既然有了 `pyproject.toml`，为什么还要 `requirements.txt`？

```text
pydantic>=2.0
pydantic-settings>=2.0
python-dotenv>=1.0.0
```

答案是**生态兼容性**：

- 一些老工具（如某些 CI 系统、Dockerfile、虚拟环境管理器）仍然习惯读 `requirements.txt`。
- `requirements.txt` 更适合“快速安装一组包”的场景。
- `pyproject.toml` 是标准，但 `requirements.txt` 是约定俗成的兼容层。

在实际工程中，两者可以共存：`requirements.txt` 保持精简，`pyproject.toml` 做完整定义。更严格的做法是 `requirements.txt` 通过 `pip-compile` 从 `pyproject.toml` 生成。

## 第四章：代码规范流水线 —— 自动化质量保障

### 4.1 为什么 AI 项目更需要代码规范

AI 项目的代码往往实验性强、迭代快，如果缺乏规范，会出现：

- 代码风格混乱，每次改动都伴随无意义的格式 diff。
- 类型错误在运行时才暴露（尤其是 LLM 输出处理时）。
- 变量命名随意，几天后就看不懂自己写的代码。

代码规范工具的作用是把**“人肉审查”变成“机器强制执行”**。

### 4.2 工具链分工

```toml
[tool.ruff]
target-version = "py310"
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "W", "N", "UP"]

[tool.black]
target-version = ["py310"]
line-length = 100

[tool.mypy]
python_version = "3.10"
strict = true
ignore_missing_imports = true
```

| 工具 | 职责 | 解决的问题 |
|------|------|-----------|
| `ruff` | 语法检查 + import 排序 + 格式化 | 替代 flake8 / isort / pyupgrade，速度快 |
| `black` | 代码格式化 | 消除个人风格差异，统一代码外观 |
| `mypy` | 静态类型检查 | 在运行前发现类型错误，对 AI 输出处理尤为重要 |

> 为什么选 ruff 而不是 pylint/flake8？  
> ruff 用 Rust 编写，速度比传统工具快 10~100 倍，规则覆盖广，可以替代多个工具。对于 100 天持续迭代的项目，检查速度直接影响开发体验。

### 4.3 pre-commit：把规范左移

`.pre-commit-config.yaml`：

```yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.6.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format

  - repo: https://github.com/pre-commit/mirrors-mypy
    rev: v1.11.2
    hooks:
      - id: mypy
```

pre-commit 的设计思想是**左移质量保障（Shift-left Quality）**：

- 传统方式：提交代码 → CI 发现错误 → 打回修改 → 再提交。周期长。
- pre-commit：在 `git commit` 时自动跑检查，有问题直接拦截，开发者当场修复。

对于 AI 项目，这个机制尤其重要，因为 Prompt、配置、数据处理脚本很容易引入低级错误，早拦截能避免错误进入训练/推理流水线。

## 第五章：配置管理 —— 为什么不用硬编码

### 5.1 硬编码配置的陷阱

初学者常犯的错误：

```python
# 反例：硬编码配置
API_KEY = "sk-xxxxxxxxxxxxxxxx"
MODEL = "gpt-4o-mini"
LOG_LEVEL = "INFO"
```

问题：

1. **安全风险**：密钥可能随代码提交到 GitHub。
2. **环境切换困难**：开发/测试/生产环境要改代码。
3. **缺乏校验**：API Key 格式错误、日志级别拼写错误只能在运行时发现。
4. **无法审计**：不知道当前运行用的是哪个配置。

### 5.2 Pydantic Settings 的设计哲学

`smart_research_agent/config.py`：

```python
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    """应用配置模型."""

    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )

    project_name: str = "智研 AI 助手"
    debug: bool = False
    log_level: str = "INFO"
    openai_api_key: str | None = None
    default_model: str = "gpt-4o-mini"


settings = Settings()
```

这个设计的核心思想：

#### （1）配置即代码（Configuration as Code）

把配置定义成带类型注解的类，享受 IDE 自动补全、类型检查和文档化。

#### （2）单一配置源

所有配置从环境变量和 `.env` 文件读取，代码中只保留默认值。这符合十二因素应用（12-Factor App）的“配置与代码分离”原则。

#### （3）启动时校验

`Settings()` 在程序启动时立即解析和校验。如果 `OPENAI_API_KEY` 是必填但缺失，程序会在启动阶段就报错，而不是等到调用 LLM 时才失败。**失败要趁早（Fail Fast）**。

#### （4）全局单例

`settings = Settings()` 在模块导入时创建，后续所有模块共享同一个实例，避免重复解析，也保证配置一致性。

### 5.3 `.env` 文件的意义

`.env.example`：

```text
# 模型配置
OPENAI_API_KEY=your_openai_api_key_here
DEFAULT_MODEL=gpt-4o-mini

# 运行配置
DEBUG=false
LOG_LEVEL=INFO
```

`.env` 的设计是为了：

- **本地开发方便**：不用 export 一堆环境变量。
- **模板与实例分离**：`.env.example` 进版本控制，`.env` 不进，保护敏感信息。
- **环境隔离**：不同环境用不同的 `.env` 文件。

> 安全提醒：`.gitignore` 必须包含 `.env`，否则 API Key 会泄露。

## 第六章：日志系统 —— 可观测性的第一道防线

### 6.1 为什么不能用 print

在 AI 项目中，日志不是“可有可无的调试信息”，而是：

- **推理追踪**：Agent 的 Thought → Action → Observation 链条需要日志记录。
- **成本审计**：每次 LLM 调用的 token 数、费用需要日志统计。
- **安全审计**：工具调用权限、敏感操作需要日志追溯。
- **问题排查**：生产环境出问题，日志是唯一的现场。

`print` 的问题：

1. **无级别**：无法区分调试信息、警告、错误。
2. **无格式化**：时间戳、模块名、级别都没有。
3. **无持久化**：只输出到控制台，程序结束就消失。
4. **无法过滤**：不能按级别、模块筛选。

### 6.2 标准 logging 架构

`smart_research_agent/utils/logger.py`：

```python
import logging
import logging.handlers
import sys
from pathlib import Path

from smart_research_agent.config import settings

LOG_DIR = Path("logs")
LOG_DIR.mkdir(exist_ok=True)


def get_logger(name: str) -> logging.Logger:
    logger = logging.getLogger(name)
    logger.setLevel(settings.log_level.upper())

    if logger.handlers:
        return logger

    formatter = logging.Formatter(
        "%(asctime)s | %(levelname)-8s | %(name)s | %(message)s",
        datefmt="%Y-%m-%d %H:%M:%S",
    )

    console_handler = logging.StreamHandler(sys.stdout)
    console_handler.setFormatter(formatter)
    logger.addHandler(console_handler)

    file_handler = logging.handlers.RotatingFileHandler(
        LOG_DIR / "smart_research_agent.log",
        maxBytes=5 * 1024 * 1024,
        backupCount=3,
        encoding="utf-8",
    )
    file_handler.setFormatter(formatter)
    logger.addHandler(file_handler)

    return logger
```

设计要点：

#### （1）双通道输出

- **控制台**：开发时实时查看。
- **滚动文件**：持久化，防止单个日志文件过大。

这是“开发体验”与“生产可靠性”的平衡。

#### （2）避免重复 handler

```python
if logger.handlers:
    return logger
```

这是关键细节。Python 的 `logging.getLogger(name)` 返回的是全局单例，如果重复调用 `get_logger`，handler 会不断叠加，导致一条日志输出多次。通过检查 `logger.handlers`，保证每个 logger 只配置一次。

#### （3）级别可配置

`settings.log_level` 控制日志级别。开发时用 `DEBUG`，生产用 `INFO` 或 `WARNING`，通过 `.env` 即可切换，无需改代码。

### 6.3 日志与未来 Agent 的关联

在后续 M1 阶段，我们会用 `get_logger(__name__)` 记录 ReAct 循环的每一步：

```python
logger.info("Thought: %s", thought)
logger.info("Action: %s", action)
logger.info("Observation: %s", observation)
```

有了今天的日志基础，Agent 推理过程就是可追溯、可调试的。

## 第七章：入口文件 —— 最小可运行单元

### 7.1 main.py 的职责边界

`smart_research_agent/main.py`：

```python
from smart_research_agent.config import settings
from smart_research_agent.utils.logger import get_logger

logger = get_logger(__name__)


def main() -> None:
    """项目入口."""
    logger.info("欢迎使用 %s", settings.project_name)
    logger.info("当前模型: %s", settings.default_model)
    logger.info("调试模式: %s", settings.debug)


if __name__ == "__main__":
    main()
```

设计原则：

- **只做引导，不做业务**：入口文件只负责初始化配置、日志，打印欢迎信息，不做复杂逻辑。
- **可测试**：`main()` 是无参数、无返回值（`None`）的纯函数，便于测试和复用。
- **可命令行调用**：通过 `python -m smart_research_agent.main` 或安装后的 `smart-research-agent` 命令运行。

### 7.2 `if __name__ == "__main__"` 的意义

这个惯用法的作用是：

- 当直接运行 `python main.py` 时，`__name__ == "__main__"`，执行 `main()`。
- 当被其他模块导入时，`__name__ == "main"`，不执行 `main()`。

这样 `main.py` 既能作为脚本运行，也能作为模块被测试代码导入而不触发副作用。

## 第八章：测试 —— 最小但必要的保障

### 8.1 为什么第一天就要写测试

很多人习惯“先写功能，再补测试”。但在 AI 项目中，这往往变成“永远不补”。我们坚持**从第一天写测试**，因为：

1. **测试是可执行文档**：`test_config.py` 明确说明了 `Settings` 的默认值应该是什么。
2. **测试防止回归**：后续改配置字段时，测试会立即发现破坏。
3. **测试驱动设计**：先想“我要测试什么行为”，再写实现，代码会更清晰。

### 8.2 第一个测试

`tests/test_config.py`：

```python
from smart_research_agent.config import Settings


def test_settings_default_values():
    settings = Settings()
    assert settings.project_name == "智研 AI 助手"
    assert settings.default_model == "gpt-4o-mini"
    assert settings.debug is False
```

这个测试的价值不在于“测了多少”，而在于建立了**测试基础设施**：pytest 配置、测试目录、CI 集成入口。后续所有功能都可以沿着这个模式扩展。

## 第九章：自动化脚本 —— 一键环境

### 9.1 为什么需要 setup_env.sh

每次换机器、换虚拟环境、新成员加入，都要重复：

1. 创建 venv
2. 安装依赖
3. 安装 pre-commit
4. 复制 `.env.example`
5. 验证环境

手动执行不仅慢，而且容易出错。`setup_env.sh` 的意义是**把环境准备变成可重复、可验证的流程**。

### 9.2 脚本设计

```bash
#!/usr/bin/env bash
set -euo pipefail

PROJECT_DIR="$(cd "$(dirname "$0")/.." && pwd)"
VENV_DIR="$PROJECT_DIR/venv"

echo "[1/6] 创建虚拟环境: $VENV_DIR"
python3 -m venv "$VENV_DIR"
source "$VENV_DIR/bin/activate"

pip install --upgrade pip
pip install -r "$PROJECT_DIR/requirements.txt"
pip install -e "$PROJECT_DIR"
pre-commit install

if [ ! -f "$PROJECT_DIR/.env" ]; then
    cp "$PROJECT_DIR/.env.example" "$PROJECT_DIR/.env"
fi

python "$PROJECT_DIR/scripts/verify_env.py"
```

关键设计：

- `set -euo pipefail`：任何一步失败立即退出，避免半完成状态。
- `PROJECT_DIR` 动态计算：脚本可以在任何目录下执行。
- 幂等性：如果 `.env` 已存在，跳过复制。

### 9.3 环境验证

`scripts/verify_env.py`：

```python
import importlib
import sys

from smart_research_agent import __version__
from smart_research_agent.config import settings


def check():
    print(f"Python: {sys.version}")
    print(f"项目版本: {__version__}")
    print(f"项目名称: {settings.project_name}")

    for pkg in ["pydantic", "pydantic_settings"]:
        mod = importlib.import_module(pkg)
        print(f"{pkg}: {mod.__version__}")

    print("环境验证通过")


if __name__ == "__main__":
    check()
```

验证的价值：

- **快速反馈**：环境是否搭建成功，30 秒内知道。
- **信息透明**：打印 Python 版本、项目版本、关键依赖版本，便于排查问题。
- **CI 集成**：这个脚本可以直接放入 CI 流水线作为健康检查。

## 第十章：今日总结 —— 骨架背后的工程思想

今天我们搭建的不仅是一个“能跑”的项目，而是体现了几个核心工程思想：

| 思想 | 落地体现 |
|------|----------|
| **关注点分离** | 包 / 脚本 / 测试 / 配置分目录 |
| **单一事实来源** | `pyproject.toml` 集中管理 |
| **配置与代码分离** | Pydantic Settings + `.env` |
| **失败要趁早** | 启动时校验配置，pre-commit 提前拦截 |
| **可观测性** | 标准 logging 双通道输出 |
| **自动化** | `setup_env.sh` + `verify_env.py` 一键环境 |
| **测试先行** | 第一天就写单元测试 |

这些思想在后续 99 天会反复出现：

- M1 Agent 阶段：ReAct 循环需要日志追踪、配置管理、工具测试。
- M2 MCP 阶段：Server/Client 架构需要依赖注入、接口抽象。
- M3 评估阶段：评估 Harness 需要可配置的测试框架。
- M4-M6 阶段：大模型调用、RAG、微调都依赖今天建立的配置与日志体系。
