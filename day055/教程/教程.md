## 第一章：原理之后的那一步

### 1.1 day054 留下的空缺

day054 的 `alignment/` 包提供了三样东西：`preference.py`（偏好对与对齐维度）、`reward.py`（隐式奖励）、`objectives.py` + `dpo_trainer.py`（损失与训练循环）。但它的输入是一份**手写的小数据集**。手写数据有三个无法回避的问题：

1. **不可扩展**：手写 12 条可以，手写 12000 条不现实；
2. **不可解释来源**：为什么这条 chosen 更好？没有可追溯的判据；
3. **不可复现**：换个人手写，分布就变了，实验无法对照。

本课要补的正是这三条：**可扩展的构造流程、可追溯的判据、确定性可复现的产物**。

### 1.2 一句话本质

> 偏好数据工程的本质，是**把"哪个回答更好"这个判断，拆成"候选从哪来"与"谁更好"两件事**——前者可以换（人工、模型采样、拒绝采样），后者必须是**唯一一份实现**。

判据一旦分家（比如造数据时用一套规则、训练时用另一套），就会出现"训练目标与数据标注口径不一致"的经典故障：模型在优化一个和数据不一致的目标，loss 在降、效果不涨。

### 1.3 本课的包结构

```text
   dpo/
   ├── errors.py     DPOError(ValueError)          —— 整包唯一异常基类
   ├── config.py     DPOTrainingConfig              —— TRL DPOConfig 的离线镜像 + 步数算术
   ├── losses.py     sigmoid / hinge / ipo          —— 取值、梯度、数值核对（纯函数）
   └── dataset.py    四个劣化算子 + 打分器 + 两条体检 —— 偏好数据构造与 TRL 落盘
```

边界是刻意的，与 `sft` / `peft` 两个包同一条纪律：**纯函数不碰外部世界**。`losses` 给定 margin 与 β 就有确定输出；`config` 是纯数据 + 纯算术；只有 `dataset` 读磁盘（jsonl）。于是整条链路可以在没有显卡的机器上跑完整测试。

## 第二章：偏好数据从哪来

### 2.1 两条路，各有代价

| 路线 | 做法 | 代价 | 分布 |
|------|------|------|------|
| **拒绝采样** | 让模型对同一 prompt 采 K 个回答，用规则或裁判打分，取最高分为 chosen、最低分为 rejected | 贵（K 倍推理） | 与当前策略一致，是"在线"方法 |
| **规则劣化** | 以金标准答案为 chosen，用可复现的算子把它"改坏"成 rejected | 便宜、完全离线、可审计 | 人工构造，与模型真实错误不同 |

公开偏好数据集（UltraFeedback、HH-RLHF 等）都是通用域、英文为主，与本项目的"引用规范 / 段落格式 / 拒答边界"三个维度不对齐——这就是为什么要自己造。

### 2.2 本课取两者的交集

```python
# 劣化算子负责造出候选池（离线、确定、可复现）
# 规则打分器负责排序（与拒绝采样完全同一段代码）
pool = candidates_for(example, ops=ops)
```

**候选池的来源可以换**——真实训练时把 `candidates_for` 换成"模型采样 K 条"即可；而"谁更好"的判据只有一份实现 `score_candidate`。这样既保留了离线可测的工程便利，又不把架构锁死在"只能造合成数据"上。

### 2.3 四个劣化算子：每一种改坏方式都对应一个真实故障

```python
DEGRADATION_OPS = ("drop_tail", "vague_specifics", "pad_verbose", "add_overclaim")
```

| 算子 | 对齐维度 | 改坏方式 |
|------|----------|----------|
| `drop_tail` | `honesty` | 删掉最后一句：答了一半，信息不完整 |
| `vague_specifics` | `honesty` | 把具体数字/术语换成模糊说法（"大概""通常"） |
| `pad_verbose` | `conciseness` | 追加套话与铺垫：更长、更啰嗦、信息量不变 |
| `add_overclaim` | `honesty` | 追加无依据的效果承诺：把结论说过头 |

`drop_tail` 的维度归属是一个**真实的选择题**，代码注释里写得明白：它同时像"信息不全"（更像 `citation`）与"答得太短"（`conciseness`）；记为 `conciseness` 会误导（它其实**更短**），记为 `citation` 又与"给出处"的定义冲突。最终按"缺信息"归到 `honesty` 邻域——**归类靠人判断，因此必须写进数据里**，这正是 day054 `DIMENSION_GOALS` 存在的意义。

> 这也解释了为什么 `pad_verbose` / `add_overclaim` 的追加文本里刻意**不含任何编造的事实**：它们是纯铺垫，不引入新的错误信息，否则"长度"与"事实性"就缠绕在一起，无法归因。

### 2.4 打分器：只有两项，而且这是刻意的

```python
def score_candidate(gold: str, candidate: str, *, op: str = "gold") -> CandidateScore:
    """给一个候选回答打分：**覆盖率 − 超长惩罚**."""
```

- **覆盖率**：候选覆盖了金标准的多少关键短语（`key_phrases` 按句/分句切分，过滤掉低于 `MIN_PHRASE_CHARS = 3` 的虚词片段）；
- **超长惩罚**：长于金标准的候选按 `OVERLENGTH_PENALTY = 0.5` 扣分。

为什么超长惩罚**必须**进打分器，而不只是"数据体检里报一下"：`pad_verbose` 与 `add_overclaim` 的**覆盖度与金标准完全相同**（它们只是追加，不删不改）。如果打分器只看覆盖度，这两个算子造出的候选会与金标准打成平手——"更啰嗦"这件事就白白丢掉了，两个算子等于白造。

而打分器**只有两项**同样是刻意的：

> **覆盖不了的维度就不要假装能打分。** day054 的五个维度里，`format` / `refusal` 需要结构化判定（不是字符级覆盖率能表达的），本课把它们留给手写种子数据与安全偏好集。用一个字符级覆盖率冒充"格式合规"，比对未知的诚实还要糟。

### 2.5 两条体检：不通过就丢弃，而且每一次丢弃都要有名字

```python
@dataclass
class PreferenceBuildReport:
    """偏好数据构造报告：**每一次丢弃都要有名字**."""
    total_examples: int
    cleaned_examples: int
    built: int
    drop_reasons: dict[str, int] = field(default_factory=dict)
    by_op: dict[str, int] = field(default_factory=dict)
```

构造流程的顺序不能换：

1. **清洗**：`DatasetCleaner` 的三段管道（干净化 → 规则 → 去重）先跑。占位符答案（"TODO：待补充"）不能当 chosen——它是**金标准侧**的质量问题，而偏好数据对 chosen 的要求比对 SFT 输出更高；
2. **造候选**：金标准 + 每个适用算子一份劣化产物；
3. **自洽体检**：得分最高的必须是金标准，否则记 `gold_not_best` 丢弃；
4. **区分度体检**：`score(gold) − score(rejected) >= MIN_SCORE_GAP`，否则记 `insufficient_gap` 丢弃。

第 3 条是本课最重要的一条纪律，理由与 day053 的"参考答案必须能通过它自己的用例"完全一致：

> 一条"chosen 并不更好"的偏好样本在 DPO 里贡献的梯度方向是**反的**，而它在统计里仍然算一条合格数据——这种错误不会报错，只会让模型越训越偏。

在真实数据上的实测（见 `scripts/dpo_demo.py`）：18 条种子样本 → 清洗后 16 条 → 成对 16 条，**丢弃 0 条**（说明四个算子在这份数据上都造出了"确实更差"的候选），算子分布为 `drop_tail 4 / vague_specifics 1 / pad_verbose 7 / add_overclaim 4`。

### 2.6 rejected 的挑选方式：为什么默认不是 `worst`

`pick_rejected` 提供两种模式：

- **`worst`**：取打分最低的候选。语义上最像拒绝采样，但**实测它会让四个算子退化成两个**——"删掉半数句子"永远比"多说两句废话"错得更狠，于是 `drop_tail` 与 `pad_verbose` 垄断了全部样本，另外两个算子一条都没进数据；
- **`rotate`（默认）**：按样本序号在适用算子之间轮转。它牺牲了"rejected 一定是最差"这一点，换来**四个算子各有样本**，于是"模型对哪一类改坏方式的区分度最差"这个问题才有数据可答。

轮转从 `index % len(ops)` 起步、遇不适用顺延，因此**不需要随机数**——同一份输入永远给出同一份数据。

**这是一条可以带走的工程判断：覆盖度比单条样本的极端性更重要。** 一份只含两种失败模式的数据，训出来的策略在另外两种失败模式上是没有信号的。

### 2.7 TRL 只认三列

```python
TRL_COLUMNS = ("prompt", "chosen", "rejected")
```

**多一列都会被 json 直读路径带进训练器**，所以默认只输出这三列；需要溯源时用 `include_meta=True` 追加 id / 维度 / 算子。安全偏好集（`data/eval/safety_pairs.jsonl`，由 day031 的红队 payload 派生）另行覆盖 `prompt_injection` / `jailbreak` / `pii_leak` / `tool_abuse` 四个类别——它提供的是**打分器覆盖不到**的那一类偏好信号（拒答边界）。

## 第三章：训练配置 —— 把 TRL DPOConfig 镜像成可测的算术

### 3.1 键名逐字对齐，不要翻译表

```python
def to_dpo_config(self) -> dict[str, Any]:
    """投影为 TRL ``DPOConfig`` 的构造参数（键名逐字对齐）."""
    return {
        "output_dir": self.output_dir,
        "beta": self.beta,
        "loss_type": self.loss_type,
        ...
    }
```

脚本里可以直接 `DPOConfig(**cfg.to_dpo_config())`。**翻译表就是漂移的来源**——day050 的 `to_hf_dict` 与 day051 的 `to_peft_dict` 都是同一条理由。

三项固定值单独说明：`gradient_checkpointing=True`（显存换时间，对齐训练几乎总要开）、`bf16=True`、`report_to="none"`（本课程不依赖任何外部实验追踪服务）。

### 3.2 两个学习率，差五个数量级

| 常量 | 值 | 用途 |
|------|-----|------|
| `DEFAULT_LEARNING_RATE` | `5e-6` | 真实 TRL 脚本的量级（比 SFT 小一个数量级） |
| `OFFLINE_LEARNING_RATE` | `0.5` | 离线参考模型上的标定值（沿用 day054 的量级） |

这不是笔误。真实模型上 DPO 的学习率必须很小，因为 β 的 KL 约束是"软"的——步长一大，策略在几步内就会跑离参考模型，KL 项直接爆掉；而离线参考模型是小规模的数值模型，需要大步长才动得起来。**同一个算法，两个学习率，取决于模型的规模与数值稳定性。**

### 3.3 校验必须发生在构造期

`__post_init__` 调用 `validate()`，把不合法的配置在**构造期**就拦下，不留给训练循环去炸。每条判据都对应一个真实的失败：

```python
if self.max_prompt_length + self.max_completion_length > self.max_length:
    raise DPOError(
        f"max_prompt_length({self.max_prompt_length}) + "
        f"max_completion_length({self.max_completion_length}) 超过 "
        f"max_length({self.max_length})：每一批都会被截断，"
        "模型会学到『答一半就停』"
    )
```

这条最值得记住：它**不会报错**——只会让一部分答案在训练时被悄悄切掉，而模型学到的是"答一半就停"。静默的错误比响亮的错误危险得多。

### 3.4 步数算术：开训之前就把账算准

```python
micro_per_epoch = train_pairs // self.per_device_train_batch_size
steps_per_epoch = micro_per_epoch // self.gradient_accumulation_steps
total_steps = steps_per_epoch * self.complete_epochs
warmup_steps = int(total_steps * self.warmup_ratio)
```

以默认配置（batch 2 / 累积 2 / 3 epoch）跑 7 条偏好对：micro 3 → 每 epoch 1 步 → 共 3 步，`warmup_steps = int(3 × 0.03) = 0`。

代码注释里有一段很关键的诚实说明：

> **口径必须写清楚**（否则数字对不上是必然的）：本课程按"每个 epoch 各自取整，再乘以完整 epoch 数"计算。换成"先把总 micro-batch 数算出来再除以累积步数"会得到不同的结果（同一组超参：本口径 9 步，另一口径 11 步）——**两种口径都有人用，关键是报告里写清用的是哪种**。

三种"看似能跑、其实一次更新都不会发生"的配置会被提前拦下：

1. `train_pairs` 不足一个 micro-batch；
2. 每 epoch 的 micro-batch 数凑不满累积步数；
3. `num_train_epochs < 1`（`complete_epochs` 为 0）。

第 3 条特别容易被忽略：`num_train_epochs=0.5` 在 `int()` 之后是 0 个完整 epoch，损失函数一次都不会被调用——而框架不会报错。

### 3.5 warmup 退化：一个可以回答的问题

```python
def warmup_floor(total_steps: int) -> float:
    """让 warmup 真正生效所需的**最小** ``warmup_ratio``：``1 / total_steps``."""
```

`warmup_steps` 是用 `int()` 截断的，所以步数少的训练里 warmup 很容易退化成 0 步——"配置里写了 warmup，实际一步都没走"。这不该是玄学：**9 步对应的下限是 1/9 ≈ 11.11%**，而默认的 3% 必然退化。`step_plan()` 会直接在返回值里给出 `warmup_degenerate` 布尔量，让这件事在报告里可见。

## 第四章：损失函数 —— 三种损失、起点自检、数值梯度核对

### 4.1 三种损失：只讲能被同一份数据直接驱动的

```python
LOSS_TYPES: tuple[str, ...] = ("sigmoid", "hinge", "ipo")
```

TRL 还支持 `kto_pair` / `bco_pair` / `apo_zero` / `discopop` 等取值，本课**刻意不列**：那些方法各自需要额外的数据或超参（KTO 需要"只标好/坏"的单侧数据、BCO 要成对奖励），把它们并列在同一张表里会给人"随便换一个就行"的错觉。**本课程只讲能被同一份 `(prompt, chosen, rejected)` 数据直接驱动的三种。**

| loss_type | 损失 | 梯度 | β 的角色 | 起点值（m=0） |
|-----------|------|------|----------|----------------|
| `sigmoid` | `−log σ(β·m)` | `−β·σ(−β·m)` | 温度：β 越大越激进 | `ln2 ≈ 0.693` |
| `hinge` | `max(0, 1 − β·m)` | `−β`（`β·m<1`）否则 `0` | 间隔的倒数：超过 `1/β` 不再产生梯度 | `1` |
| `ipo` | `(m − 1/(2β))²` | `2·(m − 1/(2β))` | 目标 margin 的倒数 | `1/(4β²)` |

### 4.2 换损失函数，β 的语义会跟着换

这是"随便换个 loss_type 试试"最容易被忽略的代价：

- 在 `sigmoid` 里，β 是**温度**——越大越激进，隐式奖励被放大 β 倍；
- 在 `hinge` 里，`1/β` 是**间隔阈值**——margin 超过它之后**完全不再产生梯度**；
- 在 `ipo` 里，`1/(2β)` 是**目标 margin**——把 margin 拉到这个点就停。

`loss_table()` 把三列并列，就是为了让这件事看得见。**同名超参在不同损失下的语义不同**，调参前必须先读表。

### 4.3 起点自检：期望值必须与损失函数配套

`margin = 0` 意味着"策略与参考模型逐位相同"，此时损失值是可以闭式预期的：

```python
def zero_margin_loss(loss_type: str, *, beta: float) -> float:
    """``m = 0``（策略与参考模型逐位相同）时的损失值——**起点自检的期望值**."""
```

- `sigmoid` → `ln2`（唯一能与 day054 的 `ZERO_MARGIN_LOSS` 直接对照的一档）；
- `hinge` → `1`；
- `ipo` → `1/(4β²)`，`β=0.01` 时是 **2500**。

**起点值不是 ln2 的档位，沿用 ln2 做自检就会漏掉真实的接线错误。** `expected_zero_margin_tolerance(expected)` 给判据：`max(1e-9, |expected|·1e-9)`——与期望值同量级的浮点噪声，但不放过量级错误（`2500` 与 `0.693` 的差远超容差）。

### 4.4 解析梯度 vs 中心差分


把数值核对**放进生产代码**而不只放进测试，是因为它同时是文档的一部分：`scripts/dpo_demo.py` 会把它打出来，让"梯度确实是我写下的那个式子"这件事在学员眼前发生一次，而不是只在一句注释里被断言。实测五组 (loss, margin) 组合的最大误差在 `1e-12` 量级——纯浮点噪声。

### 4.5 一个刻意保持的间断点行为

```python
def hinge_dpo_gradient(margin: float, *, beta: float) -> float:
    """``∂L/∂m = −β``（margin 不足时）或 ``0``（已越过间隔）."""
    if beta * margin < 1.0:
        return -beta
    return 0.0
```

间断点在 `β·m = 1`。真实实现（TRL 用 `torch.relu`）在不可导点取次梯度 0，本实现保持一致——**若取 `−β`，测试里的中心差分会在该点两侧给出不同结果，掩盖真正的符号错误。**

## 结语：对齐实践之后的三条工程线索

1. **判据唯一**：偏好数据的"谁更好"必须只有一份实现。真实训练时把候选池从"规则劣化"换成"模型采样"，只需替换 `candidates_for`，`score_candidate` 一行不动——**这是把在线方法与离线方法接进同一套流水线的接口**。
2. **静默错误优先防**：本课拦下的三类问题（截断、零更新、warmup 退化）都不会报错。工程上真正危险的从来不是抛异常的错误，而是"看起来在跑、其实什么也没学"的配置。
3. **数值自检要进生产代码**：起点期望值与中心差分核对都放在了 `losses.py` 而非测试里。理由是它们同时是**文档**——能在报告里被打印出来、被学员复现，比只在 CI 里静默通过更有价值。
