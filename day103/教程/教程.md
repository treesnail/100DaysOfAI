# day103：把 100 天的模块编成一张依赖图

> 阶段标签：结业之后的第三次扩张（原课程索引的 100 天之外）
> 学习时长：约 3 小时
> 前置依赖：day101（把字编成索引）、day102（把失败族编成台账）；以及 day080 的 `AssemblyError`

## 环境与依赖

本日新增的**运行时依赖为零**：解析只用标准库 `ast`，**不 import、不联网、不读密钥**。
这是刻意的：这一课要证明的是"一批 import **语句**能不能被编成一份可复算的图"，
而**任何真的去 import 的写法都会把"画图"变成"跑一遍整个仓库"**。

四处复用（今天一个子系统都没有重写）：

1. **材料**：`smart_research_agent/**/*.py`（457 份），只被**读取**，不改写；
2. **`ast`**：与 day102 同一套工具（那边读 `errors.py`，这边读全部 `.py`）；
3. **复算口径**：摘要取 `sha256` 前 16 位（与 day053 / day088 / day099 ~ day102 同一口径）；
4. **三类判据**：相等 / 上界 / 下界（与 day099 ~ day102 逐字相同的结构）。

> 说明：本日源码快照为**累积式**，包含截至 day102 的全部模块
> （全量回归 **15135 个用例全绿、1 skipped、总覆盖率 98.34%**）以及 day103 的新内容。

> `parse.py` / `graph.py` / `verify.py` / `study.py` / 包入口，合计 **802 语句 / 198 分支**；

## 今日目标

day102 的结语说："一个没人说得清归属的名字，比一个报错更难被发现。"
今天再换一个资产——把 **457 个模块之间的 import 关系**编成一张有向图：

```text
问题① 100 天之后，仓库里第三个没有被利用的资产是什么？
问题② "我依赖谁 / 动了我谁受影响"这件事，现在靠什么回答？
问题③ 一张依赖图的判据应该是什么？
```

今天的答案：

```text
问题① 是那 450 多份 .py 之间的**关系**：2002 条边、790 条跨包边
问题② 现在只能靠人肉翻和 IDE——它没有"覆盖清单"，也没有"环的清单"
问题③ 判据不是"这张图好不好看"，而是"每一个 .py 是不是都在图里、
       每一条 import 目标能不能被解析、报出来的环是不是真的、
       以及同一批文件能不能编出同一张图"——**可复算 + 可归属才是全部价值**
```

本日要建立的四件事：

1. **一份扫描**：`parse.scan_all()` → 457 个模块、2002 条 import（`unresolved 0`），
   **只用 `ast`，一行 `import` 都没有**；
2. **一张图**：`graph.build_graph()` → 457 个节点 / 56 个包 / 2002 条边 / **4 个环**；
3. **一次排序**：`topological_order()` → 凝缩之后长度 **446**（= 分量数，不是模块数）；
4. **一套判据**：七条性质、三类判据、六个失败族。

最终产出：`import_graph` 包七个文件（802 语句 / 198 分支）、
`tests/test_import_graph.py`（62 个用例，100% 覆盖）、`docs/import_graph.md`（12 节）、
`scripts/import_graph_demo.py`（6 节）。现场读数：

```text
扫描 457 个模块 | 未解析目标 0 条
图：457 个节点 | 56 个包 | 2002 条边 | 4 个环 | 摘要 a202a52f032d0e7f
跨包边 790 条 | 强连通分量 446 个 | 凝缩边 1938 条 | 线性序长度 446
折成包级：58 个节点 | 219 条边 | 1 个环
最长下游闭包 177 | utils.logger 的下游/上游闭包 2 / 150
七条性质 7/7 通过
```

## 第一章：为什么"字"与"名字"之后要编"关系"

day101 编的是**字**，day102 编的是**名字**。今天编的是**关系**：

```text
每个 .py 各写各的 import      "我需要谁才能跑起来"
没人把它摆成一张图            "谁是这个仓库的地基？哪两个包互相咬住？"
```

这件事有一个天然的好处：**它依然不依赖模型能力**——
它只依赖"把文件收齐、把 import 目标归属对、把顺序定死"。

因此今天的四个读数是扫描 / 图 / 环 / 性质，而且它们**共用同一张图**
（`study_lines(graph=...)`、`check_all(graph=...)` 读的是同一时刻的状态）。

## 第二章：收料——先说清"哪些文件必须进得来"

```text
被扫描的       smart_research_agent/**/*.py                 457 份
节点命名       foo/bar.py → smart_research_agent.foo.bar
              foo/__init__.py → smart_research_agent.foo（**包节点**）
没有进图的     仓库之外的一切（os / pathlib / 第三方库都不算节点）
```

一条纪律与 day101 / day102 逐字相同：**一份没进图的模块，与"这个模块不存在"在依赖图里读起来完全一样。**
因此 `scan.scan_module` 对"文件读不到"与"语法错"都是**抛错**（`ParseError`），不是跳过。

`__init__.py` 折成包节点这一点值得单独说：它让"包"成为图里**一等公民**——
`graph.packages` 记着 56 个包节点，而 `package_of(node)` 把任何模块折到它的顶层子包上，
于是同一张图可以给出两种粒度：模块级（457 个节点）与包级（58 个节点）。

## 第三章：两类边，以及相对导入这堵墙

图里的边只有两类：

```text
absolute   from smart_research_agent.tools.base import BaseTool   ⇒ 目标写全了
relative   from .base import BaseTool                            ⇒ 要按 level 减层算出来
```

### 3.1 相对导入的规则只有一个数字

```text
在 smart_research_agent/foo/bar.py 里，所在包 = smart_research_agent.foo
  from .base import X        level=1 ⇒ 减 0 层 ⇒ smart_research_agent.foo.base
  from ..other import Y      level=2 ⇒ 减 1 层 ⇒ smart_research_agent.other
```

**这是本课唯一"会算错而且不会报错"的地方。** 少减一层点，边就指到隔壁模块去了，
而依赖图照样画得出来、照样能排序、`sccs()` 也照样跑完——
**只有第 ⑤ 条性质（未解析目标数 <= 0）会把它抓住。**

### 3.2 目标怎么挑：长的优先，并列按名字

一条 `from M import a, b` 会给出三个候选：`M`、`M.a`、`M.b`。
规则是**越具体越准**：先挑"已知模块"，再挑"已知包 / 前缀"，都不是就算未解析。

```text
from smart_research_agent.foo import base     ⇒ 候选 [..foo, ..foo.base] ⇒ 挑 ..foo.base
from smart_research_agent.foo import Thing    ⇒ 候选 [..foo, ..foo.Thing] ⇒ 挑 ..foo
```

### 3.3 一个真实的环，和它的"延迟 import"

本仓库里有一条很有意思的边：

```python
# smart_research_agent/api/app.py（顶层）
from smart_research_agent.tools.image_analysis import ImageAnalysisTool

# smart_research_agent/tools/image_analysis.py（**函数体内部**）
def _default_llm():
    from smart_research_agent.api.app import default_llm
```

两条边合起来是一个环。它被**函数体内的延迟 import** 挡在了运行期之外，
但静态依赖图看得见它——这正是本课"读 import **语句**、不执行 import"的直接后果：

> **运行期看不见的东西，静态图看得见；静态图看得见的东西，运行期不一定发生。**

## 第四章：环——依赖图**不是** DAG

今天最值钱的一条读数：

```text
图：457 个节点 | 56 个包 | 2002 条边 | 4 个环
```

四个环分别是（模块级）：

```text
api.app        ↔ tools.image_analysis                              （2 个模块，跨包）
chunking       base ↔ fixed / recursive / semantic / structural     （5 个模块）
documents      base ↔ docx / html / markdown / pdf / text          （6 个模块）
retrieval      filters ↔ types                                     （2 个模块）
```

本课**不**写一条"图必须无环"的性质去把它们删掉。理由是：

```text
一个环是一个**读数**，不是一次失败
  - documents 的环来自"加载器 ↔ 基类"的注册表习惯（base 里留了一个后向引用）
  - chunking 的环同理
  - api ↔ tools 的环来自一个刻意写的延迟 import
把它们当成"必须有环为 0"的性质 ⇒ 这条性质会在仓库**合理地**变化时变红，
最后一定会被人关掉——而一条被关掉的性质，等于不存在。
```

折成**包级**之后，这 4 个环会塌缩成 1 个——一个 **23 个子包的巨型分量**：

```text
折成包级：58 个节点 | 219 条边 | 1 个环
  [环] agent（23 个包）：agent、alignment、api、chunking、domain_data、evaluation、
       finetune、finetune_eval、indexing、integration、llm、mcp_server、memory、mlops、
       peft、rag_debug、rag_ops、registry、retrieval、serving、sft、tools、vectorstore
```

这正是本课想说的两件事：**同一张图换个粒度，"有几个环"的答案会变**；
而"模块级 4 个 / 包级 1 个"两个数字**都对**——它们回答的不是同一个问题。

因此本课把"环"印出来（`cycles()`），只对"环**是不是真的**"做相等判据（第 ④ 条）。

## 第五章：凝缩、线性序与闭包

有环的图没有线性序，但它的**凝缩图**有：

```text
sccs()                 全部强连通分量（Kosaraju：两遍迭代 DFS，只含成员 >= 1 的分量）
cycles()               成员数 > 1 的那些（= 4 个）
condensation_edges()   分量键 → 分量键（去掉自环、排序去重）⇒ 1938 条
topological_order()    凝缩图的线性序（Kahn + 最小堆）⇒ 长度 446
```

**线性序的长度是"分量数"（446），不是"模块数"（457）。** 谁把这两个数弄混，
报告里"顺序"与"规模"就会互相矛盾。`require_acyclic()` 是"拒绝交付"的那条路：
图里真有环时抛 `CycleError`，并在消息里把环点名。

闭包有两个方向，答案极不对称：

```text
closure(node, "down")   我依赖谁        utils.logger ⇒ 2
closure(node, "up")     动了我谁受影响   utils.logger ⇒ 150（跨 32 个子包）
```

最长的一条下游闭包是 **177** 个模块（也就是"改这个模块最坏要跑多少东西"）。

## 第六章：一条真的撞到的墙——并列的排序键

本课写完后，我发第一次全量构建时得到一个 **不稳定的摘要**：同一批文件，
两次运行给出两个数字。原因在 `resolve_candidates` 的第一版：

```python
ordered = sorted({item for item in candidates if item}, key=len, reverse=True)
```

`key=len` 在**长度相同**的候选上会回到**输入顺序**，而输入来自一个 `set`——
它的迭代序随进程（`PYTHONHASHSEED`）变化。于是 `from . import a, b`
（`a` 与 `b` 同长且都是模块）会让边在两次运行之间**指向不同的目标**，
而图照样画得出来、照样能排序、`sccs()` 照样跑完。

修法只有一行：

```python
ordered = sorted({item for item in candidates if item}, key=lambda item: (-len(item), item))
```

这与 day101 的"倒排表文档名必须排序"、day102 的"族按包名升序 × 源码顺序排"
是同一条纪律的**第四次**应用。为了让它再也不能悄悄坏掉，这一课的测试里有一条
**子进程测试**：两个不同的 `PYTHONHASHSEED` 必须给出同一个摘要。

### 6.1 七条性质（三类判据齐全）

```text
1. graph_covers_all_modules        | [equality   ] | 读数 0 ✓ | 节点 457 个 / 期望 457 个
2. graph_is_reproducible           | [equality   ] | 读数 0 ✓ | 摘要 …0e7f / …0e7f
3. topological_order_is_valid      | [equality   ] | 读数 0 ✓ | 凝缩边 1938 条 / 违反 0 条
4. cycles_are_sound                | [equality   ] | 读数 0 ✓ | 环 4 个 / 不成立 0 个
5. import_targets_resolve          | [upper_bound] | 读数 0 ✓ | 未解析 0 条 ≤ 上界 0
6. closures_include_self           | [lower_bound] | 读数 1 ✓ | 最小闭包 1 ≥ 下界 1
7. dependency_depth_is_positive    | [lower_bound] | 读数 177 ✓ | 最长闭包 177 ≥ 下界 2
合计：7/7 条通过
```

**四条相等、一条上界、两条下界**：

```text
⑥ 每个模块的闭包至少含它自己    闭包是集合 ⇒ 只能从下面兜住
⑦ 至少存在一条依赖链          "有边"只能从下面兜住（写成 == 2 会漏掉更长的链）
⑤ 未解析的包内目标数          越少越好的量 ⇒ 兜的是上限
```

第 ④ 条的"环是真的吗"要**只在分量内部**判可达：一个环上的节点当然还能走到环外面去，
但那不改变"它们是环"这件事——因此 `_reach_within` 把可达性限制在成员集内。

## 第七章：六个失败族与五条边界

| 族 | 该谁去修 |
|----|----------|
| `ParseError` | 改解析：某份 `.py` 读不到或语法错时，先把它补进扫描范围或修好它 |
| `ImportTargetError` | 改解析或改源码：包内 import 目标对不上时，先回到相对导入的解析规则 |
| `GraphBuildError` | 改图实现：两次构建不一致时，去掉那个没有固定的量（集合序 / 字典序） |
| `CycleError` | 改调用或改层：要线性序就先凝缩；要真正拆环就改模块分层 |
| `NumericError` | 改数据或改实现：非有限读数与非法上下界都属于"数值不可用" |
| `ParameterError` | 改调用：边种类 / 方向 / 性质名 / 上限都是调用点的一次决定 |

两条族常量：

```text
RETURNED_FAMILY = "AssemblyError"
  day080 第一次给它命名（"把零件装成一条链"），此后被 arch_variants / encoder_decoder /
  hf_source / transformer_stack / capstone 各写一遍。day102（编台账）没有它；
  day103 要把 450 个模块"装成一张图"，于是"零件装不成一个整体"重新需要一次控制流事件。

ABSENT_FAMILY = "GradientError"
  本课是纯静态分析：不但没有反向，连一次 import 都不执行。
```

五条边界：

```text
1. 不新增任何第三方依赖：解析只用标准库 ast。
2. 不改动任何既有模块、既有测试、pyproject 与 docs 下的既有文件——只新增文件。
3. 不做 import：读的是 import **语句**（因此一个函数体里的延迟 import 也算一条边）。
4. 全部读数离线、确定性：只读文件系统与 ast，不联网、不读密钥。
5. 不判断分层好坏：只如实记录"谁 import 了谁"，不评价"这个环该不该存在"。
```

## 结语：三条可以带走的工程结论

1. **先把"哪些文件必须进得来"说清，再谈解析。**
   本课的第一条性质是覆盖（457/457），它排在所有结构性质之前。
   一份没进图的模块，与"这个模块不存在"在结果里读起来完全一样。

2. **"依赖图一定是 DAG"是一个错误的前提。**
   本仓库的模块级图有 4 个环、包级图有 1 个环。正确做法不是删掉环，
   而是**先算强连通分量、再在凝缩图上排序**——并且把"环有几个"如实印出来。

3. **并列的排序键必须带名字。**
   `sorted(key=len)` 在等长候选上会回到 `set` 的迭代序，而它随进程变化。
   这与 day101 的文档名排序、day102 的包名排序是同一条纪律；
   差别只是这次它藏在一个"看起来完全合理"的 `key=len` 里。

> **诚实的说明**：本课是**离线、确定性**的——它不调用任何模型、不做任何推理，
> 也不测量"这个架构好不好"。它给的是**一套能带走的图纪律**：
> 当你真的要为一个代码库建依赖图时，知道该先收齐什么、
> 该怎么算相对导入、该怎么处理环、该断言哪七件事。
