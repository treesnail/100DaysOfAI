## 第二章：M1 复习 —— Agent 内核的九块拼图

每个主题按同一个心智模型复盘：**本质 → 为什么 → 误区**。试着先看小标题自己复述，再展开对照。

### 2.1 Agent 四组件与 ReAct 原理（day003）

- **本质**：LLM 本身只会"说"（生成文本），Agent 给它加上"做"的回路——感知（读输入）、推理（想下一步）、行动（调工具）、记忆（记住历史），四者构成循环。
- **为什么**：纯 LLM 无法获取实时信息、无法执行计算、无法操作外部世界；ReAct 的核心洞察是**让"推理轨迹"和"行动结果"交替出现在同一个上下文里**，模型边做边想，每一步都有事实依据（Observation）校正，减少凭空编造。
- **误区**：以为 Agent 是"更聪明的提示词"。不是——提示词只是推理层的输入，Agent 是一个**有循环、有状态、有外部副作用**的系统程序。
- 代码：[../../day003/源码/smart-research-agent/](../../day003/源码/smart-research-agent/)（骨架），最终形态见 day006 的 `agent/react_agent.py`。

### 2.2 BaseTool 与 CalculatorTool（day004）

- **本质**：`BaseTool` 把"一个工具"定义为四元组——`name`、`description`、`parameters` schema、`execute()`。LLM 靠前三个字段**决定何时用**，程序靠最后一个字段**真正执行**。
- **为什么**：工具的"描述"写给 LLM 看，"执行"写给 Python 跑——这是人机双读者契约。`CalculatorTool` 用 **AST 白名单**解析表达式而不是 `eval`，因为 `eval` 会执行任意代码（`__import__("os").system(...)`），而 AST 遍历只允许数字与运算符节点——**对不可信输入永远不要 eval**。
- **误区**：以为工具越通用越好。恰恰相反，描述越精确、参数越收敛的工具，LLM 越不容易误用。
- 代码：[../../day004/源码/smart-research-agent/smart_research_agent/tools/base.py](../../day004/源码/smart-research-agent/smart_research_agent/tools/base.py)、[tools/calculator.py](../../day004/源码/smart-research-agent/smart_research_agent/tools/calculator.py)。

### 2.3 ToolRegistry 与 LLM 调用层（day005）

- **本质**：`ToolRegistry` 是工具的登记表，负责动态注册、查重、生成给 LLM 看的工具清单文本；`BaseLLM` 定义 `chat(messages) -> str` 抽象，`OpenAICompatibleLLM` 是生产实现，`MockLLM` 是测试实现。
- **为什么**：这一天确立了整个项目最重要的架构原则——**依赖倒置**。`ReactAgent` 依赖 `BaseLLM` 抽象而非具体实现，于是测试注入 `MockLLM` 就能离线、确定性地驱动全部逻辑。没有 MockLLM，后面每一天的测试都要访问网络，FIRST 原则全部失守。
- **误区**：把 Mock 当"测试技巧"。它是**架构决策的产物**：先有抽象层，Mock 才成为可能。
- 代码：[../../day005/源码/smart-research-agent/smart_research_agent/tools/registry.py](../../day005/源码/smart-research-agent/smart_research_agent/tools/registry.py)、[llm/base.py](../../day005/源码/smart-research-agent/smart_research_agent/llm/base.py)、[llm/mock.py](../../day005/源码/smart-research-agent/smart_research_agent/llm/mock.py)。

### 2.4 ReAct 循环与解析器（day006）

- **本质**：`ReactAgent.run()` 是一个带 `max_steps` 上限的循环：拼提示词（含工具清单+历史）→ 调 LLM → `parse_react_output` 解析 → 若是 Action 则执行工具并把 Observation 追加进上下文，若是 Final Answer 则返回。
- **为什么**：两个关键设计——其一，**循环必须有步数上限**，LLM 是概率模型，可能永远不收尾，上限是把"可能无限"变成"必然终止"的保险丝；其二，**解析必须防御式**，`Thought:/Action:` 标记是提示词层的软约束，`parser.py` 的正则与异常（`ReActParseError(ValueError)`）是代码层的硬约束。
- **误区**：以为"提示词写清楚了模型就会守规矩"。软约束只降低失败率，硬约束才保证系统不被坏输出击穿。
- 代码：[../../day006/源码/smart-research-agent/smart_research_agent/agent/react_agent.py](../../day006/源码/smart-research-agent/smart_research_agent/agent/react_agent.py)、[agent/parser.py](../../day006/源码/smart-research-agent/smart_research_agent/agent/parser.py)。

### 2.5 短期记忆与会话管理（day008）

- **本质**：LLM API 是无状态的——每次请求都是一张白纸。多轮对话的"记忆"其实是**每次请求都把历史消息列表重新发给模型**。`ShortTermMemory` 就是这个列表加上**最大长度与截断策略**（如保留系统消息 + 最近 N 轮）；`SessionManager` 按 session_id 隔离不同会话的记忆。
- **为什么**：上下文窗口是稀缺资源，无限追加历史会撞窗口上限、稀释注意力、推高成本。截断策略的本质是**在"记住足够多"和"装得下"之间做显式权衡**。
- **误区**：以为"模型记得我们聊过什么"。模型什么都不记得，记得的是你的代码。
- 代码：[../../day008/源码/smart-research-agent/smart_research_agent/memory/short_term.py](../../day008/源码/smart-research-agent/smart_research_agent/memory/short_term.py)、[memory/session.py](../../day008/源码/smart-research-agent/smart_research_agent/memory/session.py)。

### 2.6 长期记忆与向量检索（day009）

- **本质**：短期记忆管"这次会话"，长期记忆管"跨会话的知识"。`LongTermMemory` 把关键信息 `remember()` 进向量库（Embedding 后存 `VectorStore`），需要时 `recall(query)` 按语义相似度取回 top-k，注入上下文。
- **为什么**：截断会丢东西，而"丢掉的可能正是关键的"。向量检索提供的是**按意义而不是按时间**的召回——三天前聊过的偏好，只要语义相关就能捞回来。
- **误区**：以为向量检索是"精确查找"。它是**模糊匹配**：相似度排序返回的是"可能相关"，注入上下文时要意识到噪声的存在。
- 代码：[../../day009/源码/smart-research-agent/smart_research_agent/memory/long_term.py](../../day009/源码/smart-research-agent/smart_research_agent/memory/long_term.py)、[memory/vector_store.py](../../day009/源码/smart-research-agent/smart_research_agent/memory/vector_store.py)。

### 2.7 规划模块 Planner（day010）

- **本质**：`Planner.plan(goal)` 用一次 LLM 调用把目标拆成 3~6 个有序子任务（JSON 数组），`parse_plan` 用**四道防线**（边界定位 → JSON 语法 → 类型校验 → 语义非空）校验后交给 ReactAgent 逐个执行。
- **为什么**：ReAct 是贪心策略，局部最优 ≠ 全局最优——复杂任务上会迷失方向、步骤冗余、提前收场。显式的 Plan 同时解决三者：方向有提纲牵引、进度有清单可查、完成有兜底标准。规划-执行分离还是关注点分离：Planner 不知道工具存在，ReactAgent 不关心任务哪来的。
- **误区**：以为 Plan-and-Execute 全面优于 ReAct。计划的代价是僵化——环境变化需要 RePlanner 重规划，这是后续阶段的事。
- 代码：[../../day010/源码/smart-research-agent/smart_research_agent/agent/planner.py](../../day010/源码/smart-research-agent/smart_research_agent/agent/planner.py)。

### 2.8 反思模块 Reflexion（day011）

- **本质**：执行失败后，让 LLM 读失败轨迹，产出"失败原因 + 改进建议"的文字反思，注入下一轮重试的上下文。
- **为什么**：单纯重试是用同样的输入赌不同的采样，大概率同样的失败；反思把**隐式的失败信息显式化**为可学习的文本，让下一轮"知道自己上次错在哪"。本质是**用自然语言做梯度**——不更新权重，但更新上下文。
- **误区**：以为反思越多越好。反思消耗 LLM 调用且可能产生错误归因，生产中要限制反思次数并评估其有效性。
- 代码：[../../day011/源码/smart-research-agent/](../../day011/源码/smart-research-agent/)。

### 2.9 多 Agent 协作（day012）

- **本质**：把"调研报告"这类复合任务拆给三个角色——研究员（收集资料）、分析师（提炼观点）、撰稿人（成文），通过消息传递交接结果。
- **为什么**：和单 Agent 加多功能相比，角色分工让每个 Agent 的系统提示词聚焦（上下文不被稀释）、产物边界清晰（可单独测试）、可独立演进。这是**关注点分离从模块层面上升到 Agent 层面**。
- **误区**：以为 Agent 越多越好。每多一个 Agent 就多一层消息序列化/反序列化的损耗和交接失败的可能；协作的收益必须大过协调的成本。
- 代码：[../../day012/源码/smart-research-agent/](../../day012/源码/smart-research-agent/)。

### 2.10 LangGraph 状态图编排（day013）

- **本质**：把 ReAct 循环从"一个 while 循环"重构为**状态图**：`StateGraph` 定义状态 schema，节点是纯函数（读状态、返回状态更新），边定义流转，`add_conditional_edges` 实现"LLM 输出决定走哪条边"，`compile(checkpointer=MemorySaver())` 让状态可持久化、`thread_id` 让多会话隔离。
- **为什么**：手写循环的控制流藏在一堆 if 里，加新节点（如反思、人工审批）就要改循环体；状态图把**控制流变成数据**（图结构），加节点是声明式的，还白拿持久化、断点续跑、可视化的能力。
- **误区**：以为 LangGraph 替代了 ReAct 的思想。恰恰相反——图里的每个节点跑的还是 ReAct 的逻辑，**它重构的是编排，不是推理**。
- 代码：[../../day013/源码/smart-research-agent/smart_research_agent/graph/state.py](../../day013/源码/smart-research-agent/smart_research_agent/graph/state.py)、[graph/react_graph.py](../../day013/源码/smart-research-agent/smart_research_agent/graph/react_graph.py)。

### 2.11 安全防护与评估追踪（day015）

- **本质**：三道防线——输入侧 Prompt 注入检测（识别"忽略之前的指令"类攻击）、工具侧权限控制与审计日志（谁能调什么工具、每次调用留痕）、评估侧追踪指标（成功率、步数、延迟）。
- **为什么**：Agent 和传统程序的安全模型根本不同：传统程序的攻击面是代码漏洞，Agent 的攻击面是**自然语言本身**——用户输入、工具返回的网页内容，都可能夹带指令劫持模型的行为。输出不可信 + 工具可执行 = 必须在每个边界设防。
- **误区**：以为安全是"上线前加的功能"。权限和审计是**架构属性**，事后补救成本极高。
- 代码：[../../day015/源码/smart-research-agent/](../../day015/源码/smart-research-agent/)。

## 第三章：M2 复习 —— 把能力标准化地暴露出去

### 3.1 MCP 协议与架构（day016）

- **本质**：MCP（Model Context Protocol）是 AI 应用与外部能力之间的**标准协议**。传输层是 JSON-RPC 2.0 消息（`JsonRpcRequest(id, method, params)` / `JsonRpcResponse(id, result)` / `JsonRpcError(id, error)`），能力层用描述符声明三类原语：`ResourceDescriptor(uri, name, ...)`、`ToolDescriptor(name, description, input_schema)`、`PromptDescriptor(name, arguments)`。我们用 pydantic 给这些消息建模，获得免费的校验与序列化。
- **为什么**：没有 MCP 之前，每个 Agent 框架接每个工具都要写一对一定制代码——M 个框架 × N 个工具 = M×N 种集成。MCP 把工具侧和框架侧各自标准化一次，复杂度降为 M+N。**这和 USB-C 对充电接口、LSP 对编辑器-语言服务器做的事一模一样。**
- **误区一**：把项目内自建协议包命名为 `mcp`——会遮蔽官方 `mcp` 包，导入时拿到自己的包，排查极其痛苦。所以固定叫 `smart_research_agent.mcp_server`。
- **误区二**：以为 MCP 是"远程调用协议"。MCP 不关心对端在哪——stdio 传输出进程就在本机，SSE 传输才跨网络。**协议与部署拓扑解耦。**
- 代码：[../../day016/源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py](../../day016/源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py)。

### 3.2 MCP Resources（day017）

- **本质**：Resource 是**用 URI 寻址的只读数据**——知识库文档、配置文件、日志。FastMCP 里一个装饰器搞定：`@app.resource("scheme://path/{param}")`，URI 模板里的参数自动映射到函数参数。
- **为什么**：Agent 需要"读上下文"和"改世界"是两类性质不同的操作。Resource 承诺只读、无副作用，客户端因此可以安全地预取、缓存、索引它——**把语义承诺写进协议类型里，调用方才敢做优化。**
- **误区**：把所有数据都做成 Tool。"读取"性质的暴露用 Resource，语义更清晰，客户端处理也更简单。
- 代码：[../../day017/源码/smart-research-agent/](../../day017/源码/smart-research-agent/)。

### 3.3 MCP Tools 与 Prompts（day018）

- **本质**：`@app.tool()` 把一个 Python 函数暴露为 MCP Tool——类型注解和 docstring 自动生成 input schema 与描述；`@app.prompt()` 定义参数化的提示词模板，客户端 `get_prompt(name, arguments)` 拿到填充好的消息序列。
- **为什么**：这一天完成了 M1 → M2 的关键桥接——**M1 的 `BaseTool` 实现被包一层就成了 MCP Tool**。注意这两层各管各的：`BaseTool` 管"怎么执行"（进程内契约），MCP Tool 管"怎么被发现和远程调用"（协议契约）。Prompts 原语则让"经过验证的提示词"从散落在代码里的字符串变成**可发现、可版本化的服务端资产**。
- **误区**：以为描述和 schema 是"文档"。在 MCP（和 day004 的工具契约同理）里，**描述就是给 LLM 的使用说明书**，写得烂直接导致模型误调用。
- 代码：[../../day018/源码/smart-research-agent/](../../day018/源码/smart-research-agent/)。

### 3.4 FastMCP Server 与两种传输（day019）

- **本质**：一个 FastMCP Server 同时挂载 Resources/Tools/Prompts 三类能力，通过 `app.run(transport="stdio")`（子进程 + 标准输入输出，本地场景）或 `transport="sse")`（HTTP 长连接，网络场景）对外服务。
- **为什么**：**能力定义与传输方式解耦**是 FastMCP 最重要的设计——同一套装饰器代码，改一个参数就换部署形态。stdio 零网络配置、天然隔离（进程边界就是安全边界），适合本地 Agent 拉起工具子进程；SSE 可被多个远程客户端共享，适合团队级服务。
- **误区**：以为 stdio "低级"。stdio 是 MCP 生态里桌面 Agent（如 Claude Desktop）接入工具的主流方式，简单、安全、零端口管理。
- 代码：[../../day019/源码/smart-research-agent/](../../day019/源码/smart-research-agent/)。

### 3.5 MCP Client 集成（day020）

- **本质**：Client 侧三步——连接（`ClientSession` + `StdioServerParameters`/`stdio_client`）、初始化握手、**能力发现**（`list_tools()` / `list_resources()` / `list_prompts()`）。发现到的工具可以**动态注册进 day005 的 `ToolRegistry`**，于是 Agent 不需要改任何代码就获得了新能力。
- **为什么**：这是两阶段真正合拢的地方。回想 day005 的注册表设计——当时它注册的是进程内的 `BaseTool`；day020 注册的是"远程 MCP Tool 的本地代理"。**同一个注册表抽象，装得下两种来源的能力**，这就是当初坚持"注册表而非硬编码工具列表"的回报。
- **误区**：忽视异常回退。远程调用会网络超时、会返回协议错误，Client 包装层必须把 JSON-RPC error 翻译成 Agent 能消化的 Observation（错误文本），而不是让异常击穿 ReAct 循环。
- 代码：[../../day020/源码/smart-research-agent/](../../day020/源码/smart-research-agent/)。

### 3.6 Docker 部署 MCP Server（day022）

- **本质**：把 MCP Server 打成镜像——Dockerfile 沿用 day002 的分层缓存原则（先依赖后源码），compose 配置环境变量注入与健康检查。
- **为什么**：MCP Server 是"要被别人的 Agent 拉起/连接"的组件，**分发单元的完整性**比自己的项目更敏感：镜像把代码、依赖、协议版本一起冻结，任何客户端环境拿到都是同一个行为。健康检查则回答"这个 Server 现在能不能接客"。
- **误区**：stdio 模式下的容器化容易踩一个坑——容器内进程必须是 PID 1 语义清晰、stdout 只走协议消息（**日志必须写 stderr**，否则污染 JSON-RPC 流）。
- 代码：[../../day022/源码/smart-research-agent/](../../day022/源码/smart-research-agent/)。

### 3.7 MCP 协议测试与能力文档（day023）

- **本质**：测试用 `create_connected_server_and_client_session` 建立**内存内**的客户端-服务器对——真实走 MCP 协议的序列化、路由、响应全过程，但零网络、零子进程，毫秒级、离线、确定性。配合 `pytest-asyncio` 跑异步用例。能力文档则是把 Server 声明的 resources/tools/prompts 清单落成可查阅的文档。
- **为什么**：这是 day005 MockLLM 思想在协议层的对应物——**Mock 的是"最不确定的依赖"**。LLM 层最不确定的是模型输出，Mock 掉；协议层最不确定的是网络与进程边界，用内存传输 Mock 掉。剩下的全是确定性逻辑，测试才有意义。文档则延续了 day002 "文档即接口"的传统：能力清单就是 Server 的 API 文档。
- **误区**：以为测协议要真起服务。集成测试（真 stdio 子进程）留少量冒烟即可，主力测试一律内存传输——速度差两个数量级。
- 代码：[../../day023/源码/smart-research-agent/](../../day023/源码/smart-research-agent/)。

## 第五章：两阶段的三条接缝

M1 和 M2 不是拼接而是**对偶**——M2 的三原语，每一个都在 M1 里有对应的内核概念：

| MCP 原语（M2） | M1 内核对应物 | 对偶关系 |
|----------------|---------------|----------|
| **Tool**（day018） | `BaseTool` / `ToolRegistry`（day004/005） | 同一能力的两种契约：进程内执行契约 vs 协议发现契约 |
| **Prompt**（day018） | ReAct/Planner 的提示词模板（day006/010） | 提示词从"代码里的字符串"升级为"可发现、可版本化的服务端资产" |
| **Resource**（day017） | 长期记忆的知识条目、配置（day009、day001） | 数据从"内部状态"升级为"URI 寻址的只读接口" |

理解这三条对偶，就理解了为什么 M2 的顺序必须是"协议 → 三原语 → Server → Client"：**协议定义通信语言，三原语定义能说什么，Server 负责说，Client 负责听，最后 Docker 和测试保证"说的一致、听的放心"。**

同时也看清了边界划分的总原则，它和 day001 的工程思想一脉相承：

- **执行逻辑留在 M1 层**：工具怎么算、记忆怎么截断，这是业务内核，永远不暴露协议细节。
- **协议细节留在 M2 层**：JSON-RPC 消息长什么样、stdio 还是 SSE，内核代码一行都不该感知。
- **接缝处做翻译**：Client 包装层把 JSON-RPC error 翻译成 Observation 文本；Server 装饰器把 Python 函数签名翻译成 input schema。**好的架构，边界处都有翻译层。**

## 今日总结

复习不是"再看一遍"，而是**把离散的知识点压缩成少数几个可提取的心智模型**。今天的全部内容可以压缩成四句话：

1. **一切可靠性来自边界处的显式校验**：解析器防 LLM 乱输出（day006/010），AST 白名单防 eval 注入（day004），护栏防 Prompt 注入（day015），四道防线防坏计划（day010）。
2. **一切可测试性来自依赖倒置与 Mock**：MockLLM（day005）Mock 掉模型，内存传输（day023）Mock 掉网络。
3. **一切可扩展性来自注册表与协议**：ToolRegistry（day005）对内可插拔，MCP（day016~020）对外可发现——同一个抽象，两个方向。
4. **一切复杂任务来自分层编排**：ReAct 管单步（day006），Planner 管全局（day010），Reflexion 管失败（day011），LangGraph 管编排（day013），多 Agent 管分工（day012）。
