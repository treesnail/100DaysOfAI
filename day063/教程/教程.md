## 第二章：day061 复盘 —— 归一化就是接口设计

### 2.1 六种块是"下游消费者的清单"

```text
heading      谁要：day062 的结构策略按标题切；day069 的 RAG 提示要把它当上下文
paragraph    谁要：四种策略都要（它是最小的自然单元）
code         谁要：day062 的原子块保护（切开就是残码）
list_item    谁要：保留层级（"第 2 条的子项"与"第 3 条"不是一回事）
table        谁要：day069 的表格问答（渲染成 Markdown 再喂给模型）
quote        谁要：引用溯源
```

六种是**刻意保持得很少**的。day062 的实测给了这条纪律一个具体证据：
结构策略的 `ATOMIC_KINDS = (code, table)` 只保护两种块，而其余四种
（标题、段落、列表项、引用）都按预算正常打包——**如果没有为每一种块
想出消费者，就会出现一堆"没人用但分块器必须考虑"的分支**。

### 2.2 内容指纹：一个 id 撑起三天的功能

```python
doc_id = sha256(规范化后的全文)[:16]
```

```text
day061  批量入库按它去重：同一份内容换个文件名还是同一份
day062  chunk_id 把它当输入：文档变了 → 全部块 id 都变（索引可以整批重来）
day064  它会成为向量库里"这份文档的索引版本"的锚点
```

三条性质缺一不可：同一内容不同路径 → 同一个 id（能去重）；
改一个字节 → id 变（能失效重来）；**不含文件名/路径/时间**（"这是哪份内容"
而不是"它放在哪"）。

day062 在这一层上加了一个更有意思的推论：**同一个 id 不能同时回答"这是哪份内容"
与"这是哪一段"**。因此块级有两个字段：

```text
chunk_id     位置身份（doc_id | strategy | index | text）
fingerprint  内容身份（text 单独算）
```

### 2.3 三类状态与"只吞认识的失败"

```text
ok          解析成功且首次出现          → 会进知识库
duplicate   与前一份内容相同            → **数据治理问题，不是失败问题**
error       不在支持范围 / 解析失败      → 需要人工看一眼
```

以及那条最容易被忽略的纪律：

```python
except DocumentError:      # 只有"我们认识的失败"被记进报告
    ...                    # 其余异常**向上抛出**
```

把"我们自己的 bug"记成报告里的一行错误，会让它永远不被修——因为报告看起来
"只是一份文件失败了"。day062 在收尾层沿用了同一条：**丢内容要抛 `ChunkingError`，
而不是给一个 `coverage=0.94` 的报告**。

## 第三章：day062 复盘 —— 四种判据与那条不变量

### 3.1 四种策略的决策表（一张表就能选型）

| 策略 | 判据 | 依赖 | 重叠 | 确定性来源 | 实测块数 |
|------|------|------|------|-----------|---------|
| `fixed` | 位置（第 320 个单位） | 无 | 支持 | 纯字符串运算 | 3 |
| `recursive` | 排版（`\n\n` → `\n` → `。` → `，`） | 无 | 支持 | 纯字符串运算 | 3 |
| `structural` | 作者的标题层级 | day061 的 `blocks` | **不支持** | 纯字符串运算 | 5 |
| `semantic` | 相邻自然段相似度低谷 | embedding 提供方 | 支持 | **取决于提供方** | 5 |

（实测条件是 day062 演示脚本里那份 614 字符的 Markdown，默认参数。）

选型的三个问句：

```text
1. 我的语料有标题吗？           有 → structural 优先
2. 我的语料是问答/散文吗？       是 → semantic 值得试
3. 我的语料是日志/无结构长串吗？  是 → fixed 或 recursive（其它两种会退化）
```

### 3.2 收尾六步：四个判据共享的"切完之后"

```text
1. 修剪     去掉每段首尾空白并同步调整区间
2. 重叠     把下一块的起点往回挪（可按策略开关）
3. 去重     起点相同的块只保留包含者
4. 合并     过短的块与相邻块合并，且不越预算
5. 校验     区间合法 + 起点严格递增 + 非空白字符全覆盖
6. 成块     编号 → 度量 → chunk_id
```

这一步的设计价值可以用一个反问检验：**如果让四个策略各自收尾，会漏掉哪一条？**
答案是"不一定漏哪条，但总会漏一条"，而且漏掉的那条不会有任何报错——
只表现为某个指标悄悄变差（重复率偏高、覆盖率略低、块数偏多）。

### 3.3 那条不变量，与它的可核对差额

```python
document.text[chunk.start_char : chunk.end_char] == chunk.text
```

它由两处保证：`Span` 只带区间（构造上不可能违反）+ `_assert_spans` 逐字符核对
（违反即报错）。而"逐字符"判定的是**非空白**字符，因此覆盖率允许略低于 1：

```text
doc_chars - total_chars ≤ 2 × (块数 - 1) + 1     （仅在无重叠时有意义）
                            ↑ 块间空行      ↑ 原文结尾的换行
```

实测（第七章核对三）：`structural` 5 块、614 → 605 字符，差额 9，
**恰好等于上界**——说明"被修剪掉的只有块之间的空行"。

### 3.4 两个身份的分工（day062 最容易被考的一条）

```text
chunk_id     sha256(doc_id | strategy | index | text)[:16]   「这一块是谁」
fingerprint  sha256(text)[:16]                               「这是哪段内容」
```

只按文本算 id 会坏在"同一段话在同一份文档里出现两次"（工程文档的"注意"小节）；
只按位置算 id 会坏在跨文档去重。两个问题、两个字段，
混成一个就会出现"要么去重失效、要么块互相覆盖"，而两种失效都不报错。

实测（核对一）：同一份文档里 `chunk_id = 4a6680cde33da45e` 的块，
它的 `fingerprint = 90a20c398e18fb0b`——**两个 16 位十六进制数，
回答两个不同的问题。**

## 第四章：接缝核对 —— `knowledge_records()` 的字段级演进

day061 的 `documents/pipeline.py` 里写着：

> `IngestReport.knowledge_records()` 产出的形状就是 day009 的 `VectorStore.add`
> 需要的东西。day062 会在它上面加一层分块：**今天交出去的是整份文档，
> 明天交出去的是文档切出来的片段**，而接口形状不变。

今天把它逐字段核一遍（实测输出见第七章核对二）：

| 字段 | day061（整份文档） | day062（片段） | 变了吗 |
|------|------------------|---------------|--------|
| `doc_id` | `doc_id`（文档内容指纹） | `chunk_id`（块的位置身份） | **名字没变，身份换了** |
| `source` | 路径或 URL | 继承自 `Document.source` | 没变 |
| `text` | 规范化全文（614 字） | 片段（实测 36/153/210/102/104 字） | **内容层级降了一级** |
| `metadata` | 媒体类型、字符数、块数 | 上面这些 + 9 个块级字段 | 只增不改 |

`metadata` 多出来的九个键：

```text
parent_doc_id      指回它是从哪份文档切出来的（引用溯源的第一跳）
strategy           这一块是哪个判据切的
index / token_count / token_measurer   位置与度量口径
heading_path       breadcrumb（检索时补语境）
fingerprint        内容身份（跨文档去重）
oversized          是否"不可切且超预算"
retrieval_text     向量化时应当使用的那一份文本
```

**为什么"字段名不变、身份变一级"是安全的？** 因为下游只依赖三件事：

```text
1. 一个稳定的唯一键            ← doc_id 位置永远放唯一键
2. 一段可以被编码/引用的文本     ← text 位置永远放"要处理的那段文本"
3. 一个自由扩展的元数据口袋      ← metadata 只增不改
```

三者都不依赖"这条记录代表文档还是片段"。这也是 day062 把
`embedding_input` 单独写成一个字段的理由：**"存的文本"与"编码的文本"
从这一天起不是同一份了**（`text` 是原文片段，`retrieval_text` 带面包屑），
不写清楚就会有人把向量当成用 `text` 算的，然后"修"成一个 bug。

## 第五章：为什么这些集合都刻意很小

两天里出现了五个"刻意保持很少"的集合，它们背后是同一条理由：

| 集合 | 元素 | 刻意的理由 |
|------|------|-----------|
| 媒体类型 | 5 种 | **一个加载器对应一种类型**：一个加载器声称支持两种，内部就有一个 `if`，而那个 `if` 应该变成两个加载器 |
| 块类型 | 6 种 | 每一种都要有下游消费者（见 2.1） |
| 分块策略 | 4 种 | 每种对应一个**判据**，而不是一个实现细节 |
| 入库状态 | 3 种 | "数据治理问题"必须与"失败问题"分开 |
| 不变量 | 2 条（子串 + 非空白全覆盖） | 能被接口强制的才写进来，其余写成报告里的数字 |

反过来看这条纪律的另一面：**加一个集合元素时，要先写出它的消费者**。
day062 的结构策略只保护 `code` 与 `table` 两种块，正是因为它能说清
"其余四种块切开之后各自还能用"（段落切开仍是段落、引用切开仍是引用）。

## 第六章：M5 → M6 的交接 —— "模型上线"与"知识上线"是同构的

课程索引里 day063 的复习范围是"M5 微调 **与** M6 文档解析/分块"。
M5 与 M6 之间的接缝，比"先训模型、再建知识库"这句话深得多——
**两天在解决同一类问题，只是对象从模型换成了语料：**

| 关心的东西 | M5（模型上线，day048~day060） | M6（知识上线，day061 起） |
|-----------|---------------------------|------------------------|
| 身份 | 三元组内容寻址（day058：基座 + 适配器 + 合并模型的哈希） | 内容指纹（day061：`doc_id = sha256(规范化全文)[:16]`） |
| 版本表 | 事件流版本表 + 采纳/回滚判定（day058） | 今天还没有（day065 的索引版本、day072 的定时更新） |
| 门禁 | 合并门禁（day052：逐位比较，容差 0） | **覆盖率不变量**（day062：丢内容直接报错） |
| 灰度 | 影子流量 + 单向降级（day060） | day072 的索引灰度切换（本阶段后面才做） |
| 成本口径 | 显存/吞吐/每百万 token 成本（day051/060） | 块数与重叠放大量（day062 的三列报告） |
| 边界写下来 | 模型卡 + 部署限制（day059/060） | `LIMITATIONS` / `OUT_OF_SCOPE`（day061/062 各一份） |

两条可以直接迁移的经验：

1. **"口径"是唯一可继承的资产**：day058 的版本键要能被任何人重算，
   day062 的 `chunk_id` 同理。两者的做法都是**把输入（内容、策略、参数）
   显式列出来，然后 hash**；
2. **"做不到"要被记成结论**：day059 的 `blocked` 与 `failed` 分开、
   day060 的"未知机型"与"没用过这个机型"分开、day061 的 `duplicate`
   与 `error` 分开、day062 的 `oversized` 与"切坏了"分开——
   **四天、四个领域、同一个动作。**

## 第七章：本日的真实核对（可复现）

四组核对全部在 day062 快照上跑，**只读、离线、确定性**：

```bash
cd day062/源码/smart-research-agent
PYTHONPATH=. python <核对脚本>          # 见本章各节的输出
```

### 7.1 核对一：两个身份

```text
doc_id（内容指纹，16 位）      : 7feafd1c95ab3577
块数 / doc_chars / 覆盖率      : 5 / 614 / 98.53%
第一个块 chunk_id             : 4a6680cde33da45e
第一个块 fingerprint          : 90a20c398e18fb0b
块文本可在原文里逐字找到       : True
覆盖率差额 / 上界              : 9 / 9
```

四行结论：文档有一个身份、块有另一个身份；块文本逐字可回到原文；
覆盖率差额正好用满上界（说明没有丢内容，被剪掉的只是块之间的空行）。

### 7.2 核对二：记录形状的演进

```text
day061 记录的键       : ['doc_id', 'metadata', 'source', 'text']
day062 记录的键       : ['doc_id', 'metadata', 'source', 'text']
键集合完全相同         : True
day061 text 长度       : 614 字（整份文档）
day062 text 长度样本   : [36, 153, 210, 102, 104]
两者 doc_id 长度       : 16 / 16
day062 metadata 多出的键: ['fingerprint', 'heading_path', 'index', 'oversized',
                          'parent_doc_id', 'retrieval_text', 'strategy',
                          'token_count', 'token_measurer']
```

**键集合完全相同**这一行，就是 day061 那句承诺的验收单。而
"9 个新增的键**全部落在 metadata 里**"说明那三个字段的分工是对的：
`doc_id` 放身份、`text` 放内容、`metadata` 放一切可以增补的说明。

### 7.3 核对三：四个策略的覆盖率与差额

```text
1 份文档 × 4 个策略 → 16 块 / 2654 tokens | 超预算 0 | 重复内容组 4
策略            块数       覆盖       重复    差额    上界    超预算
fixed          3  115.15%   13.15%   -93     5      0
recursive      3  114.50%   12.66%   -89     5      0
structural     5   98.53%    0.00%     9     9      0
semantic       5  104.07%    3.91%   -25     9      0
```

读这张表有三条要点：

1. **差额为负表示"块文本总量超过原文"**，这是重叠贡献的——所以
   "覆盖率差额 ≤ 上界"这条约束只在差额为正时才是对丢内容的检查
   （重叠与丢内容是两件方向相反的事，用同一个数看会看反）；
2. `structural` 是唯一差额为正的策略，因为它**不重叠**，差额 9 恰好是上界；
3. `fixed` 的 13.15% 重复率对应理论放大量 17.65%（`48/272`）——差额来自
   末块不满与空白修剪，**预测与实测在同一个量级，这就是"参数一确定、
   成本就能算出来"的价值**。

### 7.4 核对四：探针集的两档深度

```text
top_k=3: fixed hit=100% mrr=0.444 | recursive hit=100% mrr=0.444
         structural hit=67% mrr=0.500 | semantic hit=67% mrr=0.444
top_k=8: fixed hit=100% mrr=0.444 | recursive hit=100% mrr=0.444
         structural hit=100% mrr=0.567 | semantic hit=100% mrr=0.511
```

这一档对照是 day062 最重要的方法论：**把 `top_k` 放大到覆盖全部块之后，
四个策略都回到 100%**——说明 top-3 的那两个 67% 来自"对的块排在第 4 位"，
是检索深度问题，不是分块质量问题。

再次强调（错误率最高的一条）：本次用的 `MockEmbedding` **没有真实语义**，
因此这两行只说明"片段没有被切碎会被保住"，**不能**用来比较语义召回能力。

## 第九章：常见误区清单（M6 前两课）

**1. 把 `doc_id` 当成文件名。** 它是内容指纹，改一个字节就变；文件名进不去。
反过来说，**同一份内容换个文件名入库会被判成重复**——这是特性，不是 bug。

**2. 以为"解析成功"就等于"内容抽全了"。** 中文 PDF 的 Identity-H 字体、
DOCX 的页眉脚注、编码回退后的乱码，全都存在于真实文档里，而且
**"没抽到"与"文档里本来没有"在结果里长得一样**。区分它们只能靠元数据字段。

**3. 把"块"当成"段落"。** 四种判据里只有 `structural` 认识段落结构；
`fixed` 会切在句子中间，`semantic` 会把含空行的代码块切开。
"块"是**检索单元**，不是语义单元。

**4. 以为"321"这种数字不用管单位。** `max_tokens=320` 在 `chars` 下是
320 个字符，在 `tiktoken` 下约 250 个汉字——**差 18%，而参数名一样**。

**5. 把重叠当免费的效果提升。** `overlap=48 / max=320` 的放大量是
`48/272 = 17.65%`，它按比例推高 embedding 调用量与向量库容量。
**重叠只保证"被切断的句子在至少一块里完整"，不解决"切断了"本身。**

**6. 以为语义分块的阈值可以照抄（0.7 / 0.75）。** 余弦相似度的绝对值依赖
提供方的训练目标、维度、归一化与语料语言。用分位数，不用绝对值。

**7. 忘了"切完要合并"。** 递归策略在段落处切完之后必须按预算合并，
否则一份 200 段的文档会切出 200 个碎块——**块数直接进账单**。

**8. 以为"更小的块一定更精确"。** 块太小 → 上下文不足（"阈值设为 0.85"
离开标题毫无意义）；块太大 → 噪声多、token 贵。评估时必须同时看
`hit@k` 与"命中块均长"。

**9. 用平均块长判断分块质量。** 平均块长很好而 `hit@k` 很低的情形很常见
（期望片段正好被切开）。**判定必须落在"片段是否完整"上**，那就是探针集。

**10. 把 `top_k` 的差距当成分块质量的差距。** 演示里 top-3 与 top-8 的
对照就是反例：放大深度后四个策略都到 100%。

**11. 用 `MockEmbedding` 比较语义召回。** 它没有语义，相似度接近随机。
它只适合验证"管线通不通、判定逻辑对不对"。

**12. 改一个分块参数却不重建索引。** 块边界变了 → `chunk_id` 全变 →
旧索引里的记录与新块对不上。**分块参数属于"会让历史索引全部失效"的变更**
（与 day061 改 `normalize_text` 同一量级）。
