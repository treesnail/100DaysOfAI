## 今日目标

昨天我们用 FastMCP 把一个 MCP Server 跑了起来：它能对外暴露工具（tools）、资源（resources）和提示词模板（prompts）。但 Server 只是"提供服务"的一半——**如果 Agent 连不上它，Server 做得再好也等于不存在**。

今天回答三个问题：

1. **Client 端长什么样**：连接、握手、能力发现各自解决什么问题，为什么连接要"常驻"而不是随用随建？
2. **同步与异步如何共处**：ReAct 循环是同步代码，MCP 官方客户端是异步 API，中间的鸿沟怎么桥接？
3. **远程工具如何变成"本地工具"**：适配器模式如何让 ReAct 循环完全无感地调用远程能力，远程故障又如何不打崩 Agent？

最终产出三个新文件：`mcp_server/protocol.py`（共享协议模型）、`mcp_server/client.py`（常驻连接的 McpClient）、`tools/mcp_tool.py`（McpToolAdapter 与 discover_mcp_tools），外加一组全程离线的集成测试。

## 第一章：为什么需要 MCP Client —— 工具生态的"插座标准化"

### 1.1 没有 MCP 的世界：N × M 集成地狱

回顾 day004，我们的 ToolRegistry 里注册的都是**进程内工具**：`CalculatorTool` 就是一个 Python 类，`execute()` 直接在当前进程里算完返回。这很美好，直到你想接入外部能力：

- 想查公司内部文档库 → 写一套 HTTP 客户端，处理它的鉴权、分页、错误码；
- 想接 GitHub → 再写一套客户端，处理另一套鉴权和错误码；
- 想接数据库 → 又一套。

M 个 Agent × N 个外部服务 = M×N 套定制集成。每套都有自己的连接管理、序列化格式、错误语义。**集成的复杂度随着工具数量爆炸，而且每一套都不可复用。**

MCP（Model Context Protocol）的解法是把"工具供给"标准化成一种协议：任何服务只要实现 MCP Server，就自动获得被任何 MCP Client 消费的能力。N 个 Server + M 个 Client 各自只写一次协议实现，复杂度从 N×M 降到 N+M。这和 USB 取代各种专用接口是同一个思想——**插座标准化之后，电器厂商和插线板厂商各管各的**。

### 1.2 Client 的三个职责

昨天我们看到 Server 端用装饰器声明能力。今天站在 Client 视角，一个合格的 MCP 客户端要做三件事：

```text
┌─────────────────────────────────────────────────────────┐
│  McpClient                                               │
│                                                          │
│  ① 连接管理   stdio_client 拉起 Server 子进程，建立双向流   │
│  ② initialize 握手   交换协议版本与双方能力声明              │
│  ③ 能力发现   list_tools / list_resources / list_prompts  │
│                                                          │
│  （之后才是日常使用：call_tool / read_resource / get_prompt）│
└─────────────────────────────────────────────────────────┘
```

**连接管理**回答"字节从哪来、到哪去"。stdio 传输下，Client 用 `StdioServerParameters(command=..., args=...)` 描述"怎么启动 Server"，`stdio_client` 负责拉起子进程并把它的 stdin/stdout 包装成异步读写流。

**initialize 握手**回答"我们说的是同一种方言吗"。MCP 协议在演进（有版本号），Client 和 Server 各自支持的能力子集也不同（有的 Server 不支持 prompts，有的 Client 不支持采样）。握手时双方交换 `protocolVersion` 和能力声明，谈不拢就在第一步失败，而不是等调用时才出怪错。**先对齐协议，再传输业务——这是一切 RPC 协议的通行做法**（HTTP/2 的 SETTINGS 帧、gRPC 的初始元数据同理）。

**能力发现**回答"你能干什么"。这是今天的重头戏，第三章细讲。

### 1.3 为什么连接要常驻

一个直觉的错误设计是"随用随连"：每次调工具都启动子进程、握手、调用、杀掉。问题显而易见：

| 开销项 | 随用随连 | 常驻连接 |
|--------|---------|---------|
| 子进程启动 | 每次数百毫秒 | 一次 |
| initialize 握手 | 每次一次往返 | 一次 |
| 能力发现 | 每次重新 list | 启动时一次，缓存复用 |
| Server 内部状态 | 每次清零（连接级缓存失效） | 跨调用保留 |

常驻连接把**固定成本摊销到一次**，之后每次调用只剩"发请求、收响应"的边际成本。这和数据库连接池、HTTP keep-alive 是同一个工程原理：**凡是建立成本高的连接，都值得池化或常驻。**

但"常驻"二字在 Python 异步世界里有一个隐藏的硬约束，它直接决定了我们 Client 的架构——下一章。

## 第二章：Client 端架构 —— 常驻事件循环与跨线程桥接

### 2.1 矛盾的双方：同步 ReAct × 异步 MCP

我们的 ReAct 循环（`agent/react_agent.py`）是**纯同步代码**：`agent.run()` 里 `tool.execute(**kwargs)` 是普通函数调用，返回值立刻可用。

而官方 `mcp` 包的客户端 API 是**纯异步的**：`ClientSession.call_tool()` 是协程，底层 anyio 流必须跑在事件循环上。

同步代码调用异步函数，第一反应是 `asyncio.run()`：

```python
def execute(self, **kwargs):
    return asyncio.run(self._client.call_tool(name, kwargs))  # 看起来没问题？
```

`asyncio.run` 每次调用都**新建一个事件循环、跑完、关闭**。对一次性脚本没问题，但对"常驻连接"是致命的——这就引出本章的坑。

### 2.2 实验：为什么不能跨事件循环复用会话

先记住结论：**anyio 的流对象绑定创建它的事件循环，循环关闭后流随之失效；在另一个循环里使用它，要么抛 `ClosedResourceError`，要么抛 "Attempted to exit cancel scope in a different task"。**

用真代码验证（你也可以自己跑一遍）：

```python
async def open_session():
    cm = create_connected_server_and_client_session(app)
    return await cm.__aenter__()          # 在循环 A 里建立会话

session = asyncio.run(open_session())     # asyncio.run 结束后循环 A 关闭

async def use(s):
    return await s.list_tools()

asyncio.run(use(session))                 # 在循环 B 里使用 → anyio.ClosedResourceError
```

原因不神秘：会话背后是 anyio 的内存流/套接字流，流的通知机制（事件、锁、回调）都注册在**创建它的那个循环**上。循环 A 一关，这些原语全部作废；循环 B 拿着一堆"死原语"自然无法通信。

同理，连接的"进入"和"退出"也必须在**同一个任务（Task）**里：anyio 的 cancel scope（`AsyncExitStack` 进入的每个异步上下文管理器内部都有）记录了进入时的任务 ID，退出时核对——拆到两个任务就抛 "exit cancel scope in a different task"。这就是为什么不能"connect 提交一个任务、disconnect 再提交另一个任务"。

### 2.3 解法：常驻事件循环 + 同一任务托管生命周期

既然流绑定循环、作用域绑定任务，那就把两个"绑定"都固定下来：

```text
主线程（同步世界）                守护线程（异步世界，常驻 loop 永久运行）
┌──────────────────┐            ┌────────────────────────────────────┐
│ ReactAgent.run() │            │  常驻事件循环 loop.run_forever()      │
│  tool.execute()  │            │   └─ 连接生命周期任务（同一个 Task）:  │
│       │          │            │      建连 → 握手 → 保活等待 → 断开    │
│       ▼          │            │   └─ 各次 list_tools / call_tool      │
│  asyncio.run(    │  桥接       │      （作为新 Task 提交，复用同       │
│   client.xxx()) ─┼──────────▶ │      一条已建立的流）                 │
└──────────────────┘            └────────────────────────────────────┘
```

三个设计决策，逐一对应上面的坑：

**决策一：客户端自带一个常驻事件循环。** `McpClient.__init__` 里创建一个 `asyncio.new_event_loop()`，用守护线程 `loop.run_forever()` 永久跑起来。会话在这个循环上建立、一直存活到 `shutdown()`——循环不关，流就不死。

**决策二：所有 I/O 协程都提交到常驻循环执行。** 公开方法（`list_tools`/`call_tool`/...）仍是 `async def`（遵守项目 API 约定），但内部不直接碰会话，而是：

```python
def _submit(self, coro):
    """提交协程到常驻 loop，包装成可在调用方 loop 上 await 的 Future."""
    return asyncio.wrap_future(asyncio.run_coroutine_threadsafe(coro, self._loop))
```

- `run_coroutine_threadsafe` 是 asyncio 官方的**跨线程提交**入口：从任意线程把协程排进目标循环，立刻返回一个 `concurrent.futures.Future`。
- `asyncio.wrap_future` 把这个并发 Future 包成 asyncio Future，于是**调用方在自己的循环里 `await` 它即可**——异步测试里 `await client.list_tools()` 能跑，`asyncio.run(client.call_tool(...))` 也能跑：asyncio.run 建的临时循环只负责"等待结果"，真正的 I/O 永远发生在常驻循环上。**临时循环是传声筒，常驻循环才是干活的。**

**决策三：连接的建连/保活/断开由常驻循环上的同一个任务托管。** `connect()` 提交一个 `_connection_lifecycle` 协程，它内部 `async with AsyncExitStack()` 包住建连与握手，握手成功后阻塞在一个"断开信号"上保活；`disconnect()` 只是 `set()` 这个信号，同一任务自然走到 `__aexit__` 完成清理。进入和退出从此不可能分属两个任务——**不是约定，是结构保证**。

### 2.4 连接时序全图

```text
调用方线程                     常驻 loop 线程                Server 子进程
    │                              │                            │
    │ connect()                    │                            │
    │────submit 生命周期任务──────▶│──stdio_client 拉起子进程──▶│ (进程启动)
    │                              │──initialize 请求──────────▶│
    │                              │◀───协议版本+能力声明────────│
    │  等待 ready 信号              │  set(ready)，然后保活等待    │
    │◀─握手完成────────────────────│                            │
    │                              │                            │
    │ asyncio.run(call_tool)       │                            │
    │────submit 调用协程──────────▶│──tools/call 请求──────────▶│
    │◀───文本结果──────────────────│◀──CallToolResult───────────│
    │           …（可重复任意次）…  │                            │
    │ disconnect()                 │                            │
    │────set(stop)───────────────▶│  保活解除 → 同一任务退出     │
    │                              │  AsyncExitStack → 子进程回收 │
```

### 2.5 为什么不选另外两条路

设计时还有两个候选方案，值得知道它们为什么被否掉：

- **方案 A：把 ReAct 循环改成全异步。** 方向没错，但改动面是整个 Agent 层加所有既有工具与测试，而收益（少一层桥接）对当前规模不成比例。**桥接层把异步复杂度封在 Client 内部**，上层零改动——这是更小的介入面。
- **方案 B：每个工具调用都 `asyncio.run` 且每次新建连接。** 2.2 节已证明不可行：流不能跨循环复用，每次新建连接又把常驻连接的摊销收益全部丢掉。

> 思考题：`_submit` 里 `asyncio.wrap_future` 必须在有运行中循环的线程调用才有效。如果有人在纯同步脚本里写 `client._submit(coro)` 而不经过 `asyncio.run`，会发生什么？这解释了为什么公开方法都定义成 `async def`——让"有没有循环"这件事由调用方的 `await`/`asyncio.run` 显式决定。

## 第三章：能力发现 —— 为什么工具清单是运行时才确定的

### 3.1 与本地工具的对比

day004 里，Agent 有哪些工具是**写代码时就定死的**：`registry.register(CalculatorTool())`，工具名、描述、参数 schema 都是程序员敲进去的。

MCP 把这变成了**运行时行为**：Client 连上 Server 之前，根本不知道对面有什么工具。同一个 Client 代码，连文档库 Server 得到 `search_docs`，连数据库 Server 得到 `query_sql`——**能力集合是连接对端决定的，不是 Client 决定的**。

这正是"插座标准化"的另一半含义：插座不需要预先知道你会插什么电器。带来的架构后果很深远：

| 维度 | 编译期硬编码 | 运行时能力发现 |
|------|-------------|---------------|
| 新增工具 | 改代码、发版 | Server 端注册即可，Client 下次连接自动可见 |
| Client 与 Server 版本耦合 | 紧耦合（schema 手写对齐） | 松耦合（schema 线上对齐） |
| 工具描述来源 | 程序员文档 | Server 自描述（description + inputSchema） |
| 可测试性 | 直接实例化 | 需要真实/内存 Server 配合 |

代价是最后两行：**schema 的正确性从"代码评审保证"变成"运行时契约"**，所以 Client 端需要防御性处理（比如 description 为 None 时给空串兜底），测试也必须真的起一个 Server——第六章会看到内存 Server 如何做到离线测试。

### 3.2 三类能力的发现与协议模型映射

`McpClient` 提供三个发现方法，返回的都是 `mcp_server/protocol.py` 里的**项目自有模型**，而不是官方包的类型：

```python
async def list_tools(self) -> list[ToolDescriptor]: ...
async def list_resources(self) -> list[ResourceDescriptor]: ...
async def list_prompts(self) -> list[PromptDescriptor]: ...
```

为什么多这一层映射，而不是直接把 `mcp.types.Tool` 透传出去？三个理由：

1. **隔离官方包的类型演进**。官方 `Tool` 的字段（`inputSchema` 驼峰命名、可能新增的注解字段）是外部契约；`ToolDescriptor(name, description, input_schema)` 是内部契约。外部变，内部不变——这就是防腐层（Anti-Corruption Layer）的迷你版。
2. **与 JSON-RPC 模型同源**。`protocol.py` 里同时建模了 `JsonRpcRequest/Response/Error`——MCP 的传输格式就是 JSON-RPC 2.0。能力描述符与消息格式放在同一个模块，构成一份完整的"项目内 MCP 契约"。
3. **pydantic 校验免费获得**。Server 返回的 schema 乱七八糟（缺 description、inputSchema 不是 object）时，`ToolDescriptor` 的默认值和类型校验在边界上就拦住了。

映射代码本身很简单，看一眼 `client.py` 里 `_list_tools_impl` 的列表推导即可——**重点不在代码，在"为什么要映射"**。

### 3.3 发现之后做什么：注册进 ToolRegistry

发现得到的是数据（`ToolDescriptor` 列表），Agent 需要的是对象（`BaseTool` 实例）。中间这一步转换由 `discover_mcp_tools` 完成（下一章细讲），从调用方视角，接入流程只有三行：

```python
for tool in await discover_mcp_tools(client):
    registry.register(tool)
```

之后 `registry.describe()` 输出的工具清单里，远程工具和本地工具并列出现——**对 LLM 而言它们毫无区别**，这正是下一章适配器模式要达到的效果。

> 思考题：能力发现的结果应该缓存还是每次调用前重新 list？考虑两个场景：Server 运行中动态增删工具；一次 Agent 会话期间连接不中断。我们的选择是"连接建立后发现一次、会话期间复用"，什么情况下这个选择会出错？

## 第四章：远程工具本地化 —— 适配器模式

### 4.1 BaseTool 契约回顾

day004 定义的工具契约（`tools/base.py`）：

```python
class BaseTool(ABC):
    name: str            # 唯一标识，Agent 用它路由
    description: str     # 给 LLM 看的自然语言描述
    parameters: dict     # JSON Schema 参数说明
    def execute(self, **kwargs) -> str: ...   # 同步执行，返回字符串
```

注意这个契约的四个字段与 MCP 的 `ToolDescriptor` **几乎同构**：name ↔ name，description ↔ description，parameters ↔ input_schema，execute ↔ call_tool。同构意味着适配器可以做得非常薄——但"薄"不等于"琐碎"，每一处映射都有讲究。

### 4.2 McpToolAdapter：四处映射与一个回退

完整代码见 [tools/mcp_tool.py](../源码/smart-research-agent/smart_research_agent/tools/mcp_tool.py)，核心逻辑：

```python
class McpToolAdapter(BaseTool):
    def __init__(self, client: McpClient, descriptor: ToolDescriptor):
        self._client = client
        self._descriptor = descriptor

    @property
    def name(self) -> str:
        return self._descriptor.name

    @property
    def parameters(self) -> dict[str, Any]:
        return self._descriptor.input_schema

    def execute(self, **kwargs: Any) -> str:
        try:
            return asyncio.run(self._client.call_tool(self.name, kwargs))
        except Exception as exc:
            logger.warning("远程工具 %s 调用失败: %s", self.name, exc)
            return f"远程工具 {self.name} 调用失败: {exc}"
```

逐处讲：

**元数据透传（name/description/parameters）。** 直接从 descriptor 取，不做任何改写。为什么可以这么放心？因为 LLM 看到的工具描述本来就该由工具提供方书写——Server 端作者最清楚自己的工具怎么用。Client 端改写描述反而引入信息失真。

**execute 的同步桥接。** `asyncio.run(self._client.call_tool(...))` 在同步的 ReAct 循环里安全，因为第二章的常驻循环设计保证了真正的 I/O 不在 asyncio.run 的临时循环上发生。**但注意边界**：如果未来 Agent 改成异步实现，在已运行的循环里调 `execute` 会抛 "asyncio.run() cannot be called from a running event loop"——届时适配器需要增加一个 `aexecute` 异步入口，而不是在 `execute` 里写 `get_event_loop` 猜来猜去。今天的回退策略会把这种情况也兜住（返回错误字符串），不会崩。

**kwargs 的约定。** ReAct 循环（`react_agent.py` 的 `_execute_tool`）按 `parameters["required"][0]` 把 `Action Input` 字符串塞成第一个必需参数。MCP 工具的 `inputSchema` 本身就是 JSON Schema，天然带 `required` 字段——day004 设计的契约与 MCP schema **无缝对齐**，这不是巧合，是 JSON Schema 作为"工具参数描述通用语"的胜利。

### 4.3 discover_mcp_tools：数据到对象的最后一公里

```python
async def discover_mcp_tools(client: McpClient) -> list[McpToolAdapter]:
    descriptors = await client.list_tools()
    return [McpToolAdapter(client=client, descriptor=d) for d in descriptors]
```

故意只做"发现 + 包装"两件事，**不直接碰 ToolRegistry**——注册与否、注册到哪份注册表，是调用方的决策。这保持了模块的可测试性（测试可以直接拿列表断言）与可组合性（未来可以有"过滤部分工具再注册"的策略层）。

### 4.4 适配器模式在本书的第二次登场

回想 day005：`MockLLM` 和 `OpenAICompatibleLLM` 适配到同一个 `BaseLLM` 接口。今天是同一件事的工具版：

```text
day005:  不同 LLM 后端  ──适配──▶  BaseLLM.chat() 统一入口
day020:  不同工具来源  ──适配──▶  BaseTool.execute() 统一入口
           （本地类 / 远程 MCP Server）
```

**适配器模式的本质收益是"消费者无感"**：ReactAgent 不知道、也不需要知道它调的是进程内计算还是跨进程 RPC。当消费者与生产者的数量都在增长时，这种无感是系统复杂度可控的关键。

## 第五章：异常回退设计 —— 远程故障不应打崩 Agent

### 5.1 远程调用比本地调用多出一整层故障

本地 `CalculatorTool.execute` 能出什么错？表达式不合法，抛个 ValueError，没了。远程工具的故障谱系宽得多：

```text
连接层故障   子进程崩溃、管道断开、网络超时      → 任何调用都可能失败
协议层故障   Server 返回无法解析的响应            → 单个调用失败
业务层故障   Server 正常响应，但 isError=True     → 单个调用"成功的失败"
```

MCP 协议对业务层故障有专门设计：工具内部抛异常时，Server **不会让连接崩掉**，而是返回 `CallToolResult(isError=True, content=[错误说明])`。这是个深思熟虑的协议决策——**工具是"有可能失败的外部世界"的代理，失败是常态而非异常**，所以失败被建模为合法响应而不是协议错误。

### 5.2 分层处理：Client 抛语义化异常，Adapter 回退成字符串

我们的实现把三种故障分两层消化：

**Client 层（`client.py`）——区分语义，抛出异常：**

```python
result = await self._session.call_tool(name, arguments)
text = "\n".join(c.text for c in result.content if getattr(c, "type", None) == "text")
if result.isError:
    raise McpToolCallError(f"远程工具 {name} 返回错误: {text}")
return text
```

- 未连接就调用 → `McpClientError("尚未连接")`（编程错误，该暴露）；
- 业务失败 → `McpToolCallError`（携带 Server 返回的错误文本）；
- 连接层异常 → 原样向上传播（anyio/mcp 的异常）。

为什么是抛异常而不是直接返回错误字符串？**因为 Client 是通用组件，无权替上层决定策略**。重试、降级、终止、还是告诉 LLM"工具挂了"——这些是不同的上层策略，Client 只负责把"发生了什么"用语义化异常表达清楚（对比 day010 的 `PlanParseError(ValueError)`，同一套异常哲学）。

**Adapter 层（`mcp_tool.py`）——兜底一切，回退成字符串：**

```python
except Exception as exc:  # noqa: BLE001 —— 回退策略：吞掉一切远程异常
    return f"远程工具 {self.name} 调用失败: {exc}"
```

这里用了平时该被 linter 骂的宽 `except Exception`，为什么是合理的？因为 **Adapter 是 Agent 与外部世界之间的最后一道防线**，它的契约是"execute 永远返回字符串"。ReAct 循环拿到这个错误字符串后，会把它当作普通 Observation 喂回给 LLM——LLM 读到"工具调用失败： 服务内部错误"，自然会在下一步 Thought 里换路子（用别的工具、或基于已有信息作答）。**故障从"打断循环的异常"降维成"循环可以消化的一条观察"**，这就是回退设计的全部意义。

### 5.3 与其他层的异常处理协同

项目里现在有三层"容错网"，各管一段：

| 层 | 位置 | 处理方式 | 管什么 |
|----|------|---------|--------|
| ReactAgent._execute_tool | `react_agent.py` | try/except → 错误字符串 | 所有工具（含本地）的执行异常 |
| McpToolAdapter.execute | `tools/mcp_tool.py` | try/except → 错误字符串 | 远程调用的全部故障 |
| McpClient.call_tool | `mcp_server/client.py` | isError → `McpToolCallError` | 业务失败与传输成功的区分 |

看起来 Adapter 和 ReactAgent 的容错重复了？不完全是：ReactAgent 的兜底防的是"任何工具实现里的意外"，Adapter 的兜底把"远程故障"翻译成**带工具名的、LLM 可读的中文错误说明**——信息质量更高。两层都在，属于防御纵深：即使未来有人绕过 Adapter 直接用别的包装方式，ReactAgent 的网还在。

### 5.4 回退策略的边界

回退不是银弹，两种场景需要更高级的策略（今天不做，但要知道）：

- **系统性故障**：如果每次调用都失败（Server 进程已死），让 LLM 无限重试是在烧钱。生产系统会加熔断器（连续失败 N 次后该工具暂时下线）。
- **静默错误**：Server 返回 isError=False 但内容不对（比如检索返回了无关文档）。这超出协议层能管的范围，属于 M3 评估阶段要处理的"结果质量"问题。

> 思考题：为什么 `McpToolCallError` 选择继承 `RuntimeError` 而不是 `ValueError`？对比 day010 `PlanParseError(ValueError)` 的选择依据，想一想"值不合法"和"运行时环境出问题"的区别。

### 6.2 测试的难点：既要真 Server，又要零网络

今天的测试有一个前所未有的需求：**Client 的对面必须真的有一个 Server 在跑**，否则握手、发现、调用全都无从谈起。但 FIRST 原则（day002）禁止测试访问网络。

解法来自官方包：`mcp.shared.memory.create_connected_server_and_client_session`——它在**同一进程内**用 anyio 内存流把 ClientSession 和一个真 Server 接起来，字节不离开进程，却走完整的 MCP 协议栈（握手、请求、响应、错误，一样不少）。

测试基建的骨架（fixture 部分）：

```python
@pytest.fixture
def mcp_client(demo_server: FastMCP):
    client = McpClient()
    ready, stop = threading.Event(), threading.Event()

    async def _session_lifecycle():
        # 进入与退出必须在同一个任务内（anyio cancel scope 约束）
        async with create_connected_server_and_client_session(demo_server) as session:
            holder["session"] = session
            ready.set()
            await asyncio.get_running_loop().run_in_executor(None, stop.wait)

    future = client.submit(_session_lifecycle())   # 整个生命周期跑在常驻 loop 上
    ready.wait(timeout=10)
    client.attach_session(holder["session"])
    yield client
    stop.set()
    future.result(timeout=10)
    client.shutdown()
```

注意 `_session_lifecycle` 把"进入 async with"和"退出 async with"放在**同一个协程**里——这正是第二章决策三在测试侧的对应。如果拆成"setup 提交一个任务进入、teardown 再提交一个任务退出"，就会触发 anyio 的 "exit cancel scope in a different task" 报错。**测试代码反过来印证了架构决策的必要性。**

### 6.3 四组测试各自守卫什么

完整代码见 [tests/test_mcp_client.py](../源码/smart-research-agent/tests/test_mcp_client.py)：

- **TestProtocolModels**（4 个）：JSON-RPC 模型的默认值、序列化往返、错误结构——共享规格的回归守卫。
- **TestMcpClientDiscovery**（6 个，async）：握手后发现三类能力、call_tool 正常返回、Server 报错抛 `McpToolCallError`、未连接抛 `McpClientError`。pytest 配置加了 `asyncio_mode = "auto"`，这些 `async def test_*` 无需装饰器直接被 pytest-asyncio 接管。
- **TestStdioConnect**（1 个，async）：用 `StdioServerParameters(command=sys.executable, args=["-m", "...demo_server"])` 拉起**真实子进程**，走通 stdio 全链路。这是唯一一个跨进程测试，依然是本机、离线。
- **TestMcpToolAdapter + TestReActIntegration**（6 个，sync）：适配器属性映射、execute 成功与回退、discover 后注册进 ToolRegistry，最后两个端到端用 MockLLM 驱动 ReAct 循环——**验证远程工具真正被 LLM"选中并调用"，且 Server 报错时循环照常收尾**。

MockLLM 驱动的 ReAct 集成测试是今天的"验收测试"，值得看一眼它怎么断言"工具真的被调用了"：

```python
answer = agent.run("调研 RAG 技术")

assert "检索结果" in second_call[-1].content   # 第二条消息里带着远程工具的 Observation
```

不断言返回值这种"表面结果"，而是断言**循环内部真的消化了远程工具的输出**——这才是"接入成功"的证据。

## 第七章：今日总结 —— MCP Client 集成的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 常驻连接 | 建连/握手成本高，固定成本摊销到一次 | `McpClient` 常驻 loop |
| 常驻事件循环 + 守护线程 | anyio 流绑定创建它的循环，循环关流即死 | `McpClient.__init__` |
| `run_coroutine_threadsafe` + `wrap_future` 桥接 | 同步 ReAct × 异步 MCP 的鸿沟，临时循环只做传声筒 | `McpClient._submit/run` |
| 连接生命周期同一任务托管 | anyio cancel scope 进出必须在同一任务 | `_connection_lifecycle` |
| 能力发现映射到项目自有模型 | 防腐层：隔离官方包类型演进，pydantic 边界校验 | `protocol.py` + `_list_*_impl` |
| 适配器元数据透传 | 工具描述由提供方书写，Client 不改写 | `McpToolAdapter` 属性 |
| Client 抛语义化异常 / Adapter 回退成字符串 | 通用组件不管策略，防线组件兜底一切；故障降维成 Observation | `call_tool` / `execute` |
| 内存 Server 做 fixture | 完整协议栈 + 零网络，FIRST 原则不破 | `tests/test_mcp_client.py` |

今天埋下的伏笔：

- **Server 进程从哪来**：今天 stdio 测试用 `sys.executable -m ...demo_server` 拉起本机进程；真实场景里 Server 应该打包成镜像、随处可起——这就是 day022（Docker 部署 MCP Server）的内容。
- **异步 Agent**：桥接层的存在是因为 ReAct 是同步的。当 Agent 层未来异步化，`McpClient` 的 async 方法无需任何改动即可被直接 await——今天的"async 优先"API 设计到那时兑现红利。
- **熔断与重试**：第五章提到的系统性故障处理，属于生产化阶段的议题。
