### 1.3 一条纪律：**不写新的注意力算术**


## 第二章：三张掩码

### 2.1 三张表与一次组合

```text
mask_of("full", n)        全开：每一行允许看所有位置        n² 个位置对
mask_of("causal", n)      因果：第 i 行允许 j <= i          n(n+1)/2 个位置对
padding_mask(pads)        填充：(not pads[j]) or (i == j)   对角线永远允许
combine_masks(a, b, ...)  交集：同时生效时唯一自然的含义
```

前两张**一行都没有重写**——它们转发 day073 的 `causal_mask` 与 day075 的 `full_mask`：

```python
# masks.py（原样转发，并用测试钉住“两次转发逐位一致”）
from smart_research_agent.math_foundations.attention import causal_mask as _causal_mask
from smart_research_agent.transformer_core.layers import full_mask as _full_mask
```

样本（`n = 4`）的读数：

```text
  full    | 4×4 | 允许 16/16 | 非因果 | 泄漏格子 6 个 | 熵天花板 1.386294
  causal  | 4×4 | 允许 10/16 | 因果   | 泄漏格子 0 个 | 熵天花板 0.794513
  因果/全开 的位置对比例：0.625000
```

第三列那个比例值得多看一眼：`10/16 = 0.625`，而 `n = 64` 时它是 `0.5078`——
**序列越长，因果掩码砍掉的比例越接近一半**。这是"BERT 与 GPT 的差别在长序列上更贵"
这句话的数字基础（第 12 章的伏笔里会用到）。

第 5 列是本课埋给 day083 的一根线：熵的**天花板**被掩码压低了。
全开掩码下第 0 行的天花板是 `ln 4 = 1.3863`，而因果掩码下是 `(1/4)Σln(i+1) = 0.7945`——
因此"注意力很尖"这件事在因果变体上**有一部分是掩码造成的**，不是模型学出来的。

### 2.2 填充掩码：加一条规则，而不是加一个特判

第一版的写法是"非填充的才允许看"：

```python
allowed[i][j] = not pads[j]        # 第一版
```

而它会**当场失败**：day075 的 `masked_softmax_rows` 明确拒绝"某一行的允许位置为空"，
因为那一行的注意力分布**没有定义**（softmax 的分母是 0）。
而一行全 False 在真实数据里一定会出现——`tokens = 4`、`pads = [T, T, T, T]` 时，
每一行都被拒绝。

修法是加一条规则（模块说明第二节）：

```python
allowed[i][j] = (not pads[j]) or (i == j)      # 现在
```

它给三件事，**三条都要说清**：

```text
① 每一行至少有一个允许的位置（对角线永远允许）  ⇒ 那一行的分布总有定义
② 非填充行看不到任何填充位                      ⇒ 这是填充掩码的本意
③ 填充行仍然看得到**非填充**的位置与它自己        ⇒ 它的输出没有意义
```

第 ③ 条是本课刻意**不**处理的：把填充行与其他人彻底隔离需要"按行按列同时判"，
而它换来的只是"噪声更小"——真正该做的是在池化与损失里把那一行**丢掉**。
测试把它钉成一条**行为**（而不是一个实现细节）：

```python
mask = padding_mask((True, True, False))
assert mask_allowed_counts(mask) == (2, 2, 1)   # 填充行看得见两个非填充位置与自己
assert mask[0] == (True, False, True)
```

### 2.3 组合里藏着的第四个坑

`combine_masks` 是逐位与。而**两张各自合法的掩码，交集却可以什么都没有**：

```text
((True, False),) ∧ ((False, True),) = (False, False)      ← 那一行被清空了
```

第一版把结果直接返回，于是这个错误会一路传到 `masked_softmax_rows` 才炸——
而那时报错信息与"哪两张掩码组合出的问题"已经隔了很远。修法是在组合处就挡住：

```python
return _checked_mask(first)     # 交集也可能把某一行清空 ⇒ 在这里当场拒绝
```

## 第三章：三个变体的接线

### 3.1 `mask_for_streams`：**掩码该给哪一条流**

```text
encoder_only      主流 = 全开（可选 ∧ 填充）        源流：无
decoder_only      主流 = 因果（可选 ∧ 填充）        源流：无
encoder_decoder   主流 = **因果**（由 decoder_block 强制）
                  源流 = 全开（``mask_kind`` 控制的就是这一条）
```

第 3 行那句"由 `decoder_block` 强制"不是描述，而是一条**接口事实**：

```text
day079 的 decoder_block  要求 self_attention_forward.causal 为真
day075 的 resolve_mask   拒绝 causal=True 与显式掩码同时给
两条加起来 ⇒ T5 的解码器**读不到填充信息**（编码器那一侧可以）
```

于是本课把它变成一条**显式的拒绝**，而不是悄悄忽略：

```python
>>> variant_forward(params_t5, inputs, pads=(False, True, False, False))
AssemblyError: encoder_decoder 变体的解码器**读不到填充信息**：day079 的 decoder_block
要求自注意力是因果的，而 day075 的 resolve_mask 拒绝因果与显式掩码同时给——
因此本包拒绝 `pads`，而不是悄悄把它丢掉（丢掉的后果是前向照跑、读数略有不同）。
```

"悄悄丢掉"是这一课最危险的失败模式：**它不会以任何异常的形式露面**——
填充掩码被丢掉之后，前向照样跑、形状一模一样、读数只是略有不同。
这与 day081 第 10.2 节那条"漏传 `placement`"是同一类（连读数都一模一样）。

### 3.2 反向：重放一遍前向

与 day079/080 同一条纪律——反向不依赖"记录里的中间账"，而是**用记录里的输入与三个
旋钮重放一遍前向**。代价是几毫秒，换来的是"记录可以说清"的大小。

而它要求记录里留下五个字段：

```python
VariantForward(..., inputs, source, mask, placement, use_residual, activation, ...)
```

少留任何一个，反向就会在一份**不同配置**上前进，而它的形状完全合法。
测试因此有一条专门盯它：

```python
def test_backward_replays_the_same_configuration() -> None:
    pre  = variant_forward(params, inputs, placement="pre")
    post = variant_forward(params, inputs, placement="post")
    assert variant_backward(pre, ...).grad_inputs != variant_backward(post, ...).grad_inputs
```

### 3.3 三条流的权重各留一份

```text
block_weights          编码器（或唯一那条）流的自注意力权重   (n, n) 或 (n_src, n_src)
decoder_self_weights   解码器那一侧的自注意力权重             (n_tgt, n_tgt)  只有 enc/dec
cross_weights          交叉注意力权重                        (n_tgt, n_src)  **长方形**
```

三份表不是"顺便留下的"——第 4 章的实测依赖要拿它们对照，而 day083 的可解释性
（注意力热力图）要的正是这三份原始数据。

## 第四章：因果性是用扰动量出来的

### 4.1 为什么不读 `causal=True` 这四个字

代码可以有三处对不上：

```text
① 掩码传错了流（把因果掩码给了编码器、把填充掩码给了解码器）
② 掩码算对了但没传进去（函数签名里少了一个参数——形状照样合法）
③ 反向里没把掩码穿过去（前向完全正确，只有梯度里混进了"未来"的贡献）
```

因此本课换一条路取证：

```text
扰动输入的第 j 个 token（乘 1.5）→ 重新前向 → 看输出第 i 行变了多少
```

实现是 `n` 次完整前向（`n = tokens`）：本课的规模很小，而**"重新前向一次"比
"把掩码的语义解释一遍"可信得多**——前者跑的就是真实的那条代码路径。

### 4.2 三个变体的实测表（演示脚本第四节原样输出）

```text

      0.010274 0.015739 0.142085 0.020941
      0.008129 0.010015 0.012523 0.215903
  decoder_only     | 可达 (1, 2, 3, 4) | 逐位为 0：True | 与掩码一致：True
      0.121785 0.000000 0.000000 0.000000
      0.022119 0.232419 0.000000 0.000000
      0.010426 0.022464 0.140648 0.000000
      0.009814 0.015929 0.016128 0.223479

      0.101491 0.000000 0.000000 0.000000

      0.007548 0.018328 0.154273 0.000000
```

三张方阵表把三个变体的差别画出来了：

```text
encoder_only     上三角全是正数（**双向**：第 0 行也能看到最后一个 token）
decoder_only     上三角**恰好 0.000000**（因果：未来从来没有被读过）
encoder_decoder  主流那张与 decoder_only 同形；而**交叉那一路 4×5 一格 0 都没有**
```

第 4 张表是 day079 "交叉注意力不能被赋因果掩码"那句拒绝的**正面读法**：
不加掩码 ⇒ 每个解码位置都覆盖整段源序列。它与第 2 张表**在同一个解码器里同时成立**。

### 4.3 为什么是"恰好 0.0"而不是"很小"

这不是数值上的巧合，而是实现上的一条硬事实：day073 的 `masked_softmax_rows`
**只在允许的位置上做 softmax**，被屏蔽的那些打分**从来没有被读过**：

```text
scores[i][j] 算了（它在矩阵里）   但 exp / sum / 加权三步都不碰它
⇒ 改它不会改变任何一个中间量 ⇒ 输出的每一个浮点都逐位相同
```

因此本课的容差是 `0.0`——**逐位**判据。而它有一个反证：把掩码换成全开之后，
同一张表上那些格子立刻变成非零（第 5 章）。

### 4.4 两条读数一起给，判据才有分辨力

```text
blocked_gap     被掩码挡掉的格子里最大的那个读数（**它必须是 0.0**）
allowed_floor   允许的格子里最小的那个读数（**它必须是正的**）
```

只看前者时，"掩码把一切都挡住了"与"掩码正确"无法区分——
而后者才说明这张表真的在量东西。演示脚本里三个变体的 `allowed_floor`：

```text
encoder_only     5.061108e-03
decoder_only     9.814225e-03（第四节表里最后一行的第一个数）
encoder_decoder  4.770919e-03（交叉那一路）
```

## 第五章：四张表

### 5.1 掩码的账（含两个反证）

```text
  encoder_only（全开）            | 允许 16/16 | 挡掉的格子最大读数 0.000000e+00 | 可达 (4, 4, 4, 4)       | 越界 0 · 缺失 0 | 一致
  decoder_only（因果）            | 允许 10/16 | 挡掉的格子最大读数 0.000000e+00 | 可达 (1, 2, 3, 4)       | 越界 0 · 缺失 0 | 一致
  encoder_decoder（主流=解码器）    | 允许 10/16 | 挡掉的格子最大读数 0.000000e+00 | 可达 (1, 2, 3, 4)       | 越界 0 · 缺失 0 | 一致
  encoder_decoder（编码器流）       | 允许 25/25 | 挡掉的格子最大读数 0.000000e+00 | 可达 (5, 5, 5, 5, 5)    | 越界 0 · 缺失 0 | 一致
  encoder_decoder（交叉那一路）     | 允许 20/20 | 挡掉的格子最大读数 0.000000e+00 | 可达 (5, 5, 5, 5)       | 越界 0 · 缺失 0 | 一致
  反证：decoder_only 用全开掩码      | 允许 16/16 | 挡掉的格子最大读数 0.000000e+00 | 可达 (4, 4, 4, 4)       | 越界 6 · 缺失 0 | **如期不一致**
  反证：encoder_only 用因果掩码      | 允许 10/16 | 挡掉的格子最大读数 0.000000e+00 | 可达 (1, 2, 3, 4)       | 越界 0 · 缺失 6 | **如期不一致**
  表格自评：True（正常行一致、反证行如期不一致）| 逐位为 0 的行数 7/7
```

两个反证的意思是**同一个判据在两个方向上都会亮红**：

```text
把因果掩码换成全开 ⇒ **越界 6 格**（未来被看到了：那是安全漏洞）
把全开掩码换成因果 ⇒ **缺失 6 格**（双向能力被砍掉：那是性能损失）
```

而"反证行"在记录里有一个专门的字段（`expect_mismatch=True`）而不是写在标签里——
因为"这一行该不该一致"是一个**可被断言**的性质。不加这个字段的话，
`ok` 会把反证行一起算进去，于是**反证失效时整张表看起来"正常"**。

### 5.2 家底（两条路径数出来的参数量必须相等）

```text
  encoder_only     | 块 3 + 解码器 0 | 自注意力 3 · 交叉 0 | 子层 6  | 参数 1458（解析 1458）
  decoder_only     | 块 3 + 解码器 0 | 自注意力 3 · 交叉 0 | 子层 6  | 参数 1458（解析 1458）
  encoder_decoder  | 块 3 + 解码器 3 | 自注意力 6 · 交叉 3 | 子层 15 | 参数 3384（解析 3384）
```

解析式（`d = 6`、`f = 24`）：

```text
块           2·d·f + f + d + 4·d    = 288 + 24 + 6 + 24 = 342
自注意力      4·d²                   = 144
交叉注意力    4·d²                   = 144
解码器前馈    2·d·f + f + d          = 318
解码器 LN     6·d                    = 36
```

两条路径必须相等——这条断言挡住的是"忘了数某一类参数"这种**不会报错**的错误
（参数少了一块，前向照样跑，只是那一块永远停在初始化）。

而这张表里有一条**值钱的对照**：

> `encoder_only` 与 `decoder_only` 的参数量**完全一样（1458）**。
> 因果与否不改变参数量——它只改变"能看到什么"。

### 5.3 前缀稳定性（最直观的一张表）

扰动**最后一个** token（位置 3）：

```text
  encoder_only     | 扰动位置 3 | 变了的行 (0, 1, 2, 3)（4 行）| 第 0 行的变化 2.869378e-02
  decoder_only     | 扰动位置 3 | 变了的行 (3,)（1 行）        | 第 0 行的变化 0.000000e+00
  encoder_decoder  | 扰动位置 3 | 变了的行 (3,)（1 行）        | 第 0 行的变化 0.000000e+00
```

"变了的行"这个读数（而不是一个标量）把因果性说清了：
GPT 变体上**只有最后一行**变了，前面三行的输出**逐位不变**——
因为它们在计算时从来没有读过最后一个位置。

这也是第 1.3 节那句话的实验版：**`decoder_only` 用的就是 `encoder_block`**，
两个变体的差别只在那一张掩码上。

## 第六章：六条性质

### 6.1 六条与它们的判据

```text
mask_zeroes_are_exact              权重表里掩码外的格子 `== 0.0`（逐位）
decoder_reads_only_past            实测表 == **因果掩码**（逐格，且逐位精确）
encoder_reads_every_position       实测表 == **全开掩码**（逐格）
cross_spans_all_sources            交叉那一路一格 0 都没有（长方形）
stack_preserves_shape              (n, d) → (n, d)
deterministic                      两次前向的输出与权重逐位相同
```

三个变体的报告（演示脚本第七节）：

```text
  encoder_only | 全绿 True | 不适用 ('decoder_reads_only_past', 'cross_spans_all_sources')
      [通过] mask_zeroes_are_exact | 掩码外共 0 个权重，最大读数 0.000000e+00（逐位为 0）
      [不适用] decoder_reads_only_past | encoder_only 没有解码器那一流：这条性质对它不适用
      [通过] encoder_reads_every_position | 实测可达 (4, 4, 4, 4)（应当全是 4）| 最小的允许读数 5.061108e-03
      [不适用] cross_spans_all_sources | encoder_only 没有交叉注意力：这条性质对它不适用
      [通过] stack_preserves_shape | 输入 (4, 6) → 输出 (4, 6)
      [通过] deterministic | 两次前向的输出相同：True；权重相同：True；交叉权重相同：True（3 层逐位比较）
  decoder_only | 全绿 True | 不适用 ('encoder_reads_every_position', 'cross_spans_all_sources')
      ...
      [通过] mask_zeroes_are_exact | 掩码外共 18 个权重，最大读数 0.000000e+00（逐位为 0）
      [通过] decoder_reads_only_past | 实测可达 (1, 2, 3, 4)（因果掩码应为 (1, 2, 3, 4)）| 挡掉的格子最大读数 0.000000e+00
      ...
  encoder_decoder | 全绿 True | 不适用 ()
      [通过] cross_spans_all_sources | 权重表 4×5（**长方形**）| 每一行的可达源位置 (5, 5, 5, 5) | 最小的允许读数 4.770919e-03
      ...
```

两处细节值得点出。

**第一处**：`encoder_only` 的 `mask_zeroes_are_exact` 说"掩码外共 **0** 个权重"——
全开掩码下这条性质**没有东西可查**。本课不把它写成"通过"就完事，
而是把这个 0 如实印在读数里（读者要能自己判断那个数是不是应该长这样）。

**第二处**：`encoder_only` 与 `decoder_only` 各有一条**不适用**。

### 6.2 "不适用 ≠ 通过"

```text
不适用 ≠ 通过        applicable=False 时 passed 也是 False，而报告只对**适用**的那些下结论
```

这条区分是被真实需求逼出来的：如果"不适用"直接记成"通过"，
那么把 `encoder_only` 的检查全删掉、与"它全都通过"在报告里长得一模一样。
代码层面它是一条**构造期的拒绝**：

```python
if not self.applicable and self.passed:
    raise NumericError("性质 ... 标了'不适用'却又标了'通过'：两者必须分开")
```

### 6.3 判据不许拿"它自己那张掩码"当期望

这是本课写第二版时抓到的一处**写松了的判据**。第一版的
`check_reads_every_position` 是这样比的：

```python
passed = report.matches_mask       # 实测 == 这一次前向**自己用的**那张掩码
```

它对一串因果掩码的编码器会**全绿**——因为"实测与它自己一致"永远成立，
而"这张掩码选对了没有"根本没有被检查。修法是让判据自己造期望：

```python
def _matches_expected(report, expected) -> bool:
    """期望由调用方（本函数内部）构造，**不读 ``report.mask``**"""
```

于是"把因果掩码给编码器"这种错法会在这一条上亮红，而测试里有一条专门钉它：

```python
def test_reads_every_position_fails_on_a_causal_mask() -> None:
    report = dependency_matrix(params_encoder, inputs, mask_kind="causal")
    assert not check_reads_every_position(params_encoder, report).passed
```

## 第七章：梯度校验

### 7.1 为什么放在**整条变体**上

day075 验过注意力的七步、day079 验过块的九块参数。今天新出现的只有**接线**：

```text
① 掩码有没有被穿进反向（前向因果、反向把未来的梯度也算上 ⇒ 前向完全正确）
② 两条流的梯度有没有接上（dEncoder 要累加，之后还要穿过整条编码器链）
```

第 ② 条是 `encoder_decoder` 独有的：`grad_source_inputs` 必须穿过编码器链才能
回到源序列；漏掉那一段时形状**完全合法**。

### 7.2 两条流各比一次（演示脚本第八节）

```text
  encoder_only | 全绿 True（容差 1e-06，步长 1e-06）
      main   | 解析范数 1.355482 | 数值范数 1.355482 | 最大差 1.832e-10 | 相对差 1.352e-10 | 24 个分量 | 通过
  decoder_only | 全绿 True（容差 1e-06，步长 1e-06）
      main   | 解析范数 1.242010 | 数值范数 1.242010 | 最大差 1.705e-10 | 相对差 1.373e-10 | 24 个分量 | 通过
  encoder_decoder | 全绿 True（容差 1e-06，步长 1e-06）
      main   | 解析范数 1.418204 | 数值范数 1.418204 | 最大差 2.018e-10 | 相对差 1.423e-10 | 24 个分量 | 通过
      source | 解析范数 0.298308 | 数值范数 0.298308 | 最大差 2.562e-10 | 相对差 2.562e-10 | 30 个分量 | 通过
```

容差 `1e-6` 与 day075/079 同值（三处不许走散），而**实测的差在 `1e-10` 量级**——
比容差小四个数量级。这个"多出来的余量"不是运气：它是中心差分的步长与浮点精度的
乘积（`h = 1e-6`、双精度 1e-16 ⇒ 最优误差约 `1e-10`）。

一个刻意的选择：梯度校验默认用 `gelu`（精确 erf 版本，处处光滑），
因为 ReLU 在 `x = 0` 处不可导，中心差分会踩到折点——
那是**判据自身的噪声**，而不是实现的错。

### 7.3 判据必须有一条"它会亮红"的反证

```python
def test_big_step_breaks_the_check() -> None:
    """把步长放大到 1.0，中心差分不再近似导数 ⇒ 报告立刻亮红."""
    report = check_variant_gradients(params, inputs, target, step=1.0)
    assert not report.ok
    with pytest.raises(GradientError):
        report.require_ok()
```

这一条测试的存在理由与第 5 章那两个反证完全一样：
**"它通过了"这句话，只有在"它会失败"这件事也被证明过之后才有信息量。**

## 第八章：两个只表现为"梯度对不上"的坑

### 8.1 pre-LN 下注意力必须作用在 `LN(x)` 上

第一版的 `_replay` 是这样接线的：

```python
attention = self_attention(params.blocks.attentions[index], current, mask=stream_mask)
block = encoder_block(block_params, current, attention, ...)      # 第一版（错的）
```

看起来完全正常：形状对、读数对、六条性质全绿。而**梯度校验立刻亮红**：

```text
layers=1 activation=gelu   max_gap = 2.237e-01
   analytic row0: 0.106300 0.439438 -0.598062 -0.169239 0.239071 0.043372
   numeric  row0: 0.013084 0.364694 -0.374391 -0.101552 0.261749 -0.133356
```

根因：**pre-LN 时块里的注意力作用在 `LN(x)` 上**，而反向
（`encoder_block_backward`）按"注意力在 `LN(x)` 上"那一条链把梯度分给 `γ₁/β₁`：

```text
分辨率下界    1e-16 ⇒ 无法用"看输出"发现
判别器        max|解析 − 数值| ≥ 0.2（差一个数量级，一眼可见）
```

修法只有四行（`_first_sublayer_input`）：

```python
if placement == NORM_PRE:
    normed, _cache = layer_norm(inputs, gamma=gamma, beta=beta)
    return normed
return inputs
```

修完之后：

```text
layers=1 activation=relu   max_gap = 1.479e-10
layers=1 activation=gelu   max_gap = 1.631e-10
layers=2 activation=relu   max_gap = 2.366e-10
layers=2 activation=gelu   max_gap = 1.863e-10
```

day079 的 `block_attention` 存在的理由**就是这件事**（它的文档里写了同一句话）。
本包没有直接调用它，只因为这里还需要把**显式掩码**传下去——
因此那四行是 `block_attention` 的"带掩码版本"，两处必须保持同一个口径。

测试里还有一条**不读代码的判据**：改 `γ₁` 之后注意力权重会不会变。

```text
pre    注意力吃的是 LN(x)  ⇒ 改 γ₁ 会改变权重（断言 !=）
post   注意力吃的是 x      ⇒ 改 γ₁ 不会改变权重（断言 ==）
```

### 8.2 T5 的解码器读不到填充信息

第 3.1 节写过：这是两条接口事实（`decoder_block` 要求因果、
`resolve_mask` 拒绝因果 + 显式掩码）加起来的结果。
本课把它做成一条**显式拒绝**（`AssemblyError`），而不是静默忽略。

带走的纪律与 day081 第 10.2 节同源：**"两条本该不同的配置给出同一个结果"是漏传最典型的信号**。

## 第九章：生成的 PyTorch 脚本（本机实测）

### 9.1 三个变体在三行代码里

```text
本包                                  PyTorch
encoder_block（pre-LN）               nn.TransformerEncoderLayer(norm_first=True)
decoder_block（九个阶段）              nn.TransformerDecoderLayer
一张显式掩码                           src_mask / tgt_mask / src_key_padding_mask
```

```text
encoder_only      nn.Embedding + nn.TransformerEncoderLayer + nn.TransformerEncoder
decoder_only      nn.Embedding + nn.ModuleList（每层一张上三角掩码 src_mask）
encoder_decoder   nn.Embedding ×2 + TransformerEncoder + TransformerDecoder（tgt_mask）
```

第 2 行值得单独看一眼：工业实现里的 GPT 常常就是"**一层 `TransformerEncoderLayer`
+ 一张上三角掩码**"——与本课那句"因果不是一条新代码路径，而是一张掩码"逐字对应。
而 `nn.TransformerEncoderLayer` 的 `norm_first` 就是本包的 `placement="pre"`。

### 9.2 解析侧只用 `ast`，**不执行脚本**

```python
def assembly_facts(script: str) -> dict[str, Any]:
    """把一段脚本解析回“它是什么”：类名、nn 模块、CONFIG、是否带 main."""
    config = parse_config(script)      # ast.literal_eval —— 只认字面量
```

于是"结构核对"这件事在**任何环境**下都能跑（本机没有 torch 也能跑），
而生成的脚本自己会声明运行要求：

```text
"""由 day082 的 ``arch_variants.assembly`` 生成：三个变体的 PyTorch 对照实现.

需要 PyTorch >= 1.9（nn.TransformerEncoderLayer 的 batch_first 与 norm_first）
"""
```

### 9.3 差值必须被算出来，而不是被凑平（本机实测）

演示脚本第九节（`torch 2.14.0+cpu`、`heads = 1`）：

```text
  encoder_only     | 类 EncoderOnlyStack | 与形状一致 True
      nn 模块：nn.Module, nn.Embedding, nn.TransformerEncoderLayer, nn.TransformerEncoder
      本机实测：PARAM_COUNT 1722
  decoder_only     | 类 DecoderOnlyStack | 与形状一致 True
      nn 模块：nn.Module, nn.Embedding, nn.ModuleList, nn.TransformerEncoderLayer
      本机实测：PARAM_COUNT 1722
  encoder_decoder  | 类 EncoderDecoderStack | 与形状一致 True
      nn 模块：nn.Module, nn.Embedding, nn.TransformerEncoderLayer, nn.TransformerEncoder,
                nn.TransformerDecoderLayer, nn.TransformerDecoder
      本机实测：PARAM_COUNT 3984
```

而本包的解析式是 1458 / 1458 / 3384。差值 **264 / 264 / 600** 从哪来？
把 PyTorch 那一侧逐项拆开（`d = 6`、`d_ff = 24`、`heads = 1`）：

```text
多出来的      ① 词嵌入 32 × 6 = 192                                  （本包的前向直接吃 (n, d)）
             ② 注意力的偏置：in_proj_bias(3d = 18) + out_proj.bias(d = 6) = 24 每层
                （校验：PyTorch 的 168 − 本包的 4d² = 144 ⇒ 24 ✓）

逐层核对      MultiheadAttention  108 + 18 + 36 + 6 = 168
              linear1             24×6 + 24         = 168
              linear2             6×24 + 6          = 150
              两个 LayerNorm       2 × (6 + 6)       =  24
              合计                                     510   ×3 层 = 1530
              加词嵌入 192                    ⇒ 1722 ✓（与实测一致）
```

于是两个差值都能逐项对上：

```text
encoder_only       192（词嵌入） + 3 × 24（三层注意力偏置）              = 264 ✓
decoder_only       同上                                                 = 264 ✓
encoder_decoder    2 × 192（两个词嵌入） + 3 × 24（编码器）
                   + 3 × 48（解码器的自注意力 + 交叉注意力）             = 600 ✓
```

**本课不把它们凑平**：生成的脚本会打印自己的参数量，而教程把差值写在旁边
（day080 对 `4d × N` 那处差值做的就是这件事）。真正要紧的不是"两个数相等"，
而是**"差值能被逐项解释"**。

## 第十章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 三个变体只差一张掩码 | 因果不是新代码路径 | `mask_for_streams` |
| 全开/因果掩码**转发** day073/075 | 重写一遍的代价是两处口径慢慢分开 | `masks.mask_of` |
| 填充掩码加 `or (i == j)` | 一行全 False 的分布没有定义 | `padding_mask` |
| 交集也做一次行检查 | 两张合法掩码的交集可以是空行 | `combine_masks` |
| 用扰动实测依赖 | "读代码"读不出漏传与反向没穿 | `probe.dependency_matrix` |
| 判据用 `== 0.0` | 被掩码的打分从来没有被读过 | `DependencyReport.exact` |
| 两条读数一起给 | 只看"挡掉的是 0"时，全挡也会通过 | `blocked_gap` / `allowed_floor` |
| 反证写成字段 | 否则反证失效时整张表看起来正常 | `LeakRow.expect_mismatch` |
| 不适用 ≠ 通过 | 删掉检查与它通过必须可区分 | `PropertyOutcome.applicable` |
| 判据自己造期望掩码 | 拿"它自己那张掩码"当期望会永远成立 | `_matches_expected` |
| 反向重放前向 | 记录要保持"可以说清"的大小 | `_replay` |
| pre-LN 先过一次 LN | 否则前向与反向不是同一个函数 | `_first_sublayer_input` |
| `pads` 给 T5 直接拒绝 | 静默忽略的后果是"读数略有不同" | `mask_for_streams` |
| 参数量两条路径对照 | 挡住"忘了数某一类参数" | `census_of` |
| 解析脚本只用 `ast` | 没有 torch 的机器也要能核对结构 | `assembly.assembly_facts` |
| 差值逐项解释 | "差值能被解释"比"两个数相等"更有信息 | 第 9.3 节 |
