## 第一章：为什么 MCP Server 需要容器化 —— 以及为什么 stdio 模式容器化后反而难用

### 1.1 先厘清：MCP Server 的两种存在形态

MCP 协议本身不规定 Server 必须怎么部署，它只规定通信格式（JSON-RPC 2.0）。真正的差异在**传输层**，而我们项目里的 Server 恰好两种都支持（见 [mcp_server/server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/server.py)）：

| 维度 | stdio 传输 | SSE 传输 |
|------|-----------|----------|
| 通信通道 | 子进程的标准输入/输出 | HTTP 长连接（Server-Sent Events） |
| 进程归属 | Client 拉起并管理 Server 子进程 | Server 独立运行，有自己的生命周期 |
| 网络可见性 | 无网络端口，纯进程间通信 | 监听 TCP 端口（本项目 8000） |
| 典型场景 | 本地 IDE 插件、Claude Desktop 集成 | 团队共享服务、云端部署 |
| 谁决定 Server 生死 | Client 退出 → 子进程终止 | 进程管理器/编排器（如 Docker） |

这个表格是今天所有设计决策的原点。**stdio 模式下 Server 是 Client 的"附属品"，SSE 模式下 Server 是一个独立的"服务"**——而容器化，本质上是为"独立服务"准备的交付方式。

### 1.2 为什么 stdio 模式容器化后难直接用

一个直觉的疑问：既然要容器化，把 stdio 模式的 Server 塞进容器不就行了？试过就会发现三个绕不开的麻烦：

**麻烦一：stdin/stdout 被容器边界切断。** stdio 传输的前提是 Client 和 Server 共享一套标准输入输出管道——这要求它们是**同一台机器上的父子进程**。容器的设计目标恰恰是隔离：容器内进程的标准输出默认被 Docker 接管（进日志系统），宿主机的 Client 想把自己的 stdin 接进容器，必须加 `docker run -i` 并保持附着，管道还要穿透 Docker 的进程命名空间。能做，但每加一个编排层（compose、K8s），这条管道就多一层转接，脆弱性倍增。

**麻烦二：生命周期管理错位。** stdio 模式下"Client 退出则 Server 终止"是协议语义的一部分。而容器的哲学是"容器是独立管理的单元"——编排器想重启它、扩容它、健康检查它。把"生命周期归 Client"的进程放进"生命周期归编排器"的容器里，两边抢着当家长：`docker compose up` 启动一个 stdio Server，没有 Client 连着它，它就对着空气等输入，健康检查也无从谈起。

**麻烦三：一对多关系天然不成立。** stdio 是一对一管道：一个 Client 对应一个 Server 子进程。容器化最常见的诉求却是"起一个服务，全团队都能连"。stdio 容器化后，第二个 Client 想连接就得再起一个容器——那为什么不直接在本地起子进程？容器化带来的隔离和可移植性，在 stdio 场景下几乎没有收益。

```text
stdio 容器化（拧巴）:                SSE 容器化（自然）:
┌─宿主机───────────────┐           ┌─宿主机───────────────┐
│ Client               │           │ Client A ──┐         │
│   │ stdin/stdout     │           │ Client B ──┤ HTTP    │
│   ▼ (要穿透容器边界)  │           │ Client C ──┘  :8000  │
│ ┌─容器─────────────┐ │           └───────┬─────────────┘
│ │ Server 等输入...  │ │                   ▼ 端口映射
│ │ 没有Client连它    │ │           ┌─容器─────────────┐
│ └──────────────────┘ │           │ SSE Server :8000  │
└──────────────────────┘           │  /health 可探测    │
                                   └──────────────────┘
```

### 1.3 SSE 为什么是容器部署的"天选"传输

对照上面的三个麻烦，SSE 逐一化解：

1. **通信走网络，天然穿透容器边界。** 容器就是为网络服务设计的：`EXPOSE` 声明端口，`-p 8000:8000` 做映射，宿主机的任何 Client 都能连——这是 Docker 最成熟的能力，没有任何 hack。
2. **生命周期独立，编排器全权管理。** SSE Server 是一个常驻 HTTP 服务，容器启动它就一直监听。崩溃重启、健康检查、滚动更新——编排器的全套武器都适用。
3. **一个容器服务多个 Client。** HTTP 是无状态请求-响应（SSE 是长连接，但同样支持多客户端并发），一个容器实例天然就能服务整个团队。

还有一个顺带的红利：**HTTP 意味着可观测性**。stdio 管道里的消息对外界不可见，而 HTTP 服务可以加健康检查端点、可以挂反向代理、可以接负载均衡——今天我们加的 `/health` 就是第一个例子。

> 思考题：stdio 容器化真的没有适用场景吗？提示：想一想 CI 环境里"跑一次性任务"的容器，以及 `docker run -i` 的存在意义。答案在习题第 4 题展开。

## 第二章：MCP Server 代码 —— 为容器化做的三个改造

### 2.1 包命名：为什么必须是 `mcp_server` 而不是 `mcp`

项目共享规格里有一条硬性规定：自建 MCP 相关包的包名固定为 `smart_research_agent.mcp_server`，**绝不能叫 `mcp`**。原因值得讲透：

Python 的导入系统按 `sys.path` 顺序查找模块。如果项目里存在一个 `mcp` 包（哪怕藏在子目录里，只要它出现在路径上），那么 `from mcp.server.fastmcp import FastMCP` 就可能导入到**我们自己的包**而不是官方的 MCP SDK——这就是"包遮蔽"（shadowing）。报错信息会是莫名其妙的 `ImportError: cannot import name 'FastMCP'`，因为我们的 `mcp/server.py` 里根本没有 `FastMCP`。

这类 bug 的阴险之处在于：**它在某些机器上能跑**（路径顺序恰好对了），在另一些机器上爆炸。容器化后 `sys.path` 布局可能和本地开发不同，遮蔽问题最容易在部署时爆发。命名上避让，是最便宜的防御。

### 2.2 protocol.py：把协议形状写成代码

[mcp_server/protocol.py](../源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py) 用 pydantic 对 JSON-RPC 2.0 消息与三类能力描述建模：

```python
class JsonRpcRequest(BaseModel):
    id: str | int | None = None
    method: str
    params: dict[str, Any] = Field(default_factory=dict)
    jsonrpc: Literal["2.0"] = "2.0"
```

注意 `jsonrpc: Literal["2.0"] = "2.0"` 这个设计：字段值被**字面量类型锁死**，传入 `"1.0"` 会在校验期直接拒绝。这是"让非法状态不可表示"思想的应用——协议版本是协议的一部分，不是一个随便的字符串。

为什么 FastMCP 已经帮我们处理了协议，还要自己建一套模型？三个用途：

1. **文档即代码**：`describe_capabilities()` 用 `ToolDescriptor` / `ResourceDescriptor` 导出能力清单，这份清单可以直接渲染进文档（day023 的任务），而 pydantic 模型保证了清单的字段完整。
2. **协议级测试**：测试可以断言"Server 导出的能力清单符合我们声明的 schema"，而不是去抠 FastMCP 内部的 dict 结构。
3. **学习价值**：亲手建模一遍 JSON-RPC 2.0，你对"Request 有 method 没有 result、Response 有 result 没有 method、Error 的 code 是整数"这些细节的理解，远比读一遍协议文档深刻。

### 2.3 server.py：三个容器化改造点

完整代码见 [mcp_server/server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/server.py)。相比一个"玩具"Server，为容器部署做了三件事：

**改造一：host/port 从环境变量读取。**

```python
server = FastMCP(
    name="smart-research-agent",
    host=host or os.environ.get("MCP_HOST", "0.0.0.0"),
    port=port or int(os.environ.get("MCP_PORT", str(DEFAULT_SSE_PORT))),
)
```

两个细节：

- **默认 host 是 `0.0.0.0` 而不是 `127.0.0.1`**。这是容器部署最容易踩的坑：进程绑定 `127.0.0.1` 时只接受**本机回环**连接，而宿主机通过 `-p 8000:8000` 转发进来的请求，从容器视角看是"外部连接"——会被直接拒收。现象是：容器里 `curl localhost:8000` 通，宿主机 `curl localhost:8000` 超时。排查半天，根因就这一个配置。容器里的服务，绑定地址几乎总是 `0.0.0.0`。
- **环境变量有缺省值，但可被覆盖**。本地开发不设任何变量也能跑；容器里 Dockerfile 的 `ENV` 或 compose 的 `environment` 注入新值。优先级：函数参数 > 环境变量 > 缺省值——每层都有明确的存在理由。

**改造二：`/health` 自定义路由。**

```python
@server.custom_route("/health", methods=["GET"])
async def health(request: Request) -> Response:
    """健康检查端点：仅 SSE/HTTP 传输下可达，供容器健康检查使用."""
    return JSONResponse({"status": "ok", "server": "smart-research-agent"})
```

FastMCP 的 `custom_route` 装饰器允许在 MCP 协议之外挂载普通 HTTP 端点。从 `sse_app()` 的源码可以看到实现机制：FastMCP 内部维护一个 `_custom_starlette_routes` 列表，构建 Starlette 应用时把自定义路由**追加在 MCP 路由之后**（保证协议路由优先匹配），最终整个应用就是一个标准 ASGI 应用。

这个端点的设计有意保持了极简：不查数据库、不调外部依赖，只返回"进程活着、HTTP 栈正常"。为什么？因为健康检查的职责是回答一个问题——**"这个容器还值得保留吗"**。如果健康检查里串了太多下游依赖，一次数据库抖动就会让编排器把所有容器判死、集体重启，小故障被放大成雪崩。深层依赖检查应该走单独的 readiness/详细诊断端点，而不是存活探针。

**改造三：`main()` 入口的传输分发。**

```python
parser.add_argument(
    "--transport",
    choices=["stdio", "sse"],
    default=os.environ.get("MCP_TRANSPORT", "stdio"),
)
```

缺省值是 `stdio` 而非 `sse`：本地开发场景（被 MCP Client 以子进程拉起）是历史上最高频的用法，缺省值照顾它；容器里则通过 Dockerfile 的 `CMD [... "--transport", "sse"]` 显式声明。**命令行参数与环境变量双通道**：`MCP_TRANSPORT` 环境变量也能切换，这在 compose 编排时很有用——同一份镜像，改一个环境变量就能换传输模式，不用重建镜像。

### 2.4 离线测试策略：进程内会话 + ASGI 直驱

今天的测试（[tests/test_mcp_server.py](../源码/smart-research-agent/tests/test_mcp_server.py)）全部离线，两条技术路线都值得记住：

**路线一：`create_connected_server_and_client_session`。** mcp 包提供的测试工具，在**同一进程内**用内存双向流把 Server 和一个真实 `ClientSession` 接起来：

```python
async with create_connected_server_and_client_session(server) as session:
    result = await session.call_tool("calculator", {"expression": "2 + 3 * 4"})
assert result.content[0].text == "14"
```

走的是完整的 MCP 协议栈（初始化握手、能力协商、JSON-RPC 编解码），但不经过任何网络、不起任何子进程。这继承了 day005 MockLLM 以来的同一原则：**测试要快、要确定、要在任何机器上可重复**。

**路线二：Starlette `TestClient` 直驱 ASGI 应用。** `/health` 是普通 HTTP 端点，`server.sse_app()` 返回标准 Starlette 应用，于是：

```python
client = TestClient(create_server().sse_app())
resp = client.get("/health")
assert resp.json() == {"status": "ok", "server": "smart-research-agent"}
```

TestClient 直接在进程内调用 ASGI 接口，不需要真的监听端口。**传输层被抽象掉了，业务逻辑被完整保留**——这是"协议与传输分离"架构在测试侧的回报。

异步测试依赖 `pytest-asyncio`，配置上一行搞定（`pyproject.toml`）：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
```

`auto` 模式下所有 `async def test_*` 自动被当作异步测试执行，省去逐个加 `@pytest.mark.asyncio` 的样板。

## 第三章：Dockerfile 逐行解剖 —— 镜像分层与缓存的实战应用

### 3.1 完整 Dockerfile

今天的 [Dockerfile](../源码/smart-research-agent/Dockerfile) 相对 day002 的版本做了面向服务的升级：

```dockerfile
FROM python:3.13-slim

WORKDIR /app

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt ./
RUN pip install --no-cache-dir --upgrade pip && \
    pip install --no-cache-dir -r requirements.txt

COPY smart_research_agent/ ./smart_research_agent/
COPY pyproject.toml ./
RUN pip install --no-cache-dir -e .

ENV MCP_TRANSPORT=sse \
    MCP_HOST=0.0.0.0 \
    MCP_PORT=8000

EXPOSE 8000

RUN useradd -m appuser && chown -R appuser:appuser /app
USER appuser

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

CMD ["python", "-m", "smart_research_agent.mcp_server.server", "--transport", "sse"]
```

逐层拆解设计意图。

### 3.2 基础镜像：`python:3.13-slim` 的取舍

`python` 官方镜像有三个常见变体：

| 变体 | 体积（约） | 特点 |
|------|-----------|------|
| `python:3.13` | 1 GB | 完整 Debian，带编译工具链 |
| `python:3.13-slim` | 120 MB | 精简 Debian，只留运行必需 |
| `python:3.13-alpine` | 50 MB | musl libc，最小但兼容性坑多 |

选 slim 的理由：**体积与兼容性的平衡点**。alpine 的 musl libc 会让很多带 C 扩展的 Python 包（pydantic 早期版本、numpy 等）需要现场编译，构建时间从分钟级膨胀到十分钟级，还可能踩 glibc 行为差异的坑。slim 的 Debian 基础直接吃 PyPI 上的预编译 wheel，稳。代价是多出来几十 MB——对一个服务镜像来说完全可以接受。

但 slim 砍掉了 `curl`，而我们的 HEALTHCHECK 需要它，所以第一层 RUN 把它装回来。注意三个细节：

- `apt-get update` 和 `apt-get install` 写在**同一条 RUN** 里。分开写的话，`update` 的层会被缓存，几天后 `install` 用的还是旧索引，可能装到过期的包版本——这是 Docker 官方文档点名的经典错误。
- `--no-install-recommends`：Debian 默认连"建议安装"的包一起装，加上这个参数只装硬依赖，curl 的体积从十几 MB 降到几 MB。
- `rm -rf /var/lib/apt/lists/*`：包索引在装完后就没用了，删掉它。**同一层里删除才有效**——如果在下一条 RUN 里删，上一层的索引数据依然存在于镜像历史中，体积一分不少。这是镜像分层"只增不改"特性的直接推论。

### 3.3 层顺序：缓存友好性的量化直觉

回顾 day002 讲过的原则：**变化频率低的层放前面，变化频率高的放后面**。今天的 Dockerfile 严格遵循这个排序：

```text
层 1  FROM python:3.13-slim      ← 几乎不变（换 Python 版本才变）
层 2  apt 装 curl                 ← 很少变
层 3  COPY requirements.txt       ← 依赖清单，偶尔变
层 4  pip install                 ← 跟着层 3 缓存，最慢的一层
层 5  COPY 源码 + pyproject       ← 每次改代码都变
层 6  pip install -e .            ← 快（只是装本项目）
层 7+ ENV/EXPOSE/USER/...         ← 元数据层，几乎零成本
```

算一笔账：开发期你每天改 20 次代码、改 0 次依赖。如果 `COPY . .` 在最前面，20 次构建 × 每次重装依赖（约 2 分钟）= 40 分钟浪费；现在的排序下，层 1~4 全部命中缓存，每次构建只有层 5 之后重建，**秒级完成**。层顺序不是洁癖，是每天实打实的时间。

### 3.4 ENV：十二要素之"配置存环境"

```dockerfile
ENV MCP_TRANSPORT=sse \
    MCP_HOST=0.0.0.0 \
    MCP_PORT=8000
```

这三行是**十二要素应用（The Twelve-Factor App）**第三条"配置存环境"的直接落地。十二要素是 Heroku 团队总结的 SaaS 方法论，核心主张之一是：**任何会在部署环境之间变化的东西（端口、密钥、外部服务地址），都不许写死在代码里，一律走环境变量。**

为什么这条对容器化尤其重要？因为容器的核心承诺是"**一份镜像，多处运行**"：

- 开发机跑容器：端口 8000，日志级别 DEBUG；
- 测试环境：端口 8000，日志 INFO，连测试知识库；
- 生产环境：端口 8000（由网关映射成 443），日志 WARNING。

如果端口写死在代码里，三种环境就得构建三份镜像，"一处构建、处处运行"的承诺破产，而且镜像和环境的组合爆炸无法管理。ENV 注入后，**镜像只描述"应用是什么"，环境变量描述"这次运行在哪"**。

Dockerfile 里的 `ENV` 提供的是**镜像级默认值**，运行时可被覆盖，优先级链：

```text
docker run -e MCP_PORT=9000        （运行时显式指定，最高优先级）
    ↓ 未指定则用
compose 的 environment:            （编排层配置）
    ↓ 未指定则用
Dockerfile 的 ENV                  （镜像默认值）
    ↓ 未指定则用
代码里的 os.environ.get(..., 缺省) （应用兜底）
```

四层兜底，每层都有明确职责：**代码兜底保证"裸 python 也能跑"，ENV 保证"裸镜像也能跑"，compose/run 负责具体环境**。

### 3.5 EXPOSE 的真相：它只是文档

`EXPOSE 8000` 一个常见的误解是"声明后端口就能从宿主机访问"。**不是的。** EXPOSE 不做任何网络配置，它的真实作用是：

1. **元数据**：`docker inspect` 能看到这个镜像"打算"监听 8000；
2. **文档**：读 Dockerfile 的人立刻知道服务端口；
3. **配合 `-P`（大写）**：`docker run -P` 会把所有 EXPOSE 的端口映射到宿主机随机端口——但这个用法在生产中很少见。

真正的端口映射是运行时 `-p 8000:8000` 或 compose 的 `ports:` 做的事。理解"EXPOSE 是声明，-p 是动作"能避免一类困惑：忘了加 `-p` 时宿主机访问不通，和 EXPOSE 写没写毫无关系。

### 3.6 非 root 运行与目录属主

```dockerfile
RUN useradd -m appuser && chown -R appuser:appuser /app
USER appuser
```

容器默认以 root 运行进程。容器内的 root 虽然不是宿主机 root，但在内核能力共享的前提下，容器逃逸漏洞的第一受害者就是"以 root 运行的容器"。最小权限原则：**应用用什么权限能跑，就只给什么权限。**

`chown -R appuser:appuser /app` 这一处是实战细节：我们的 logger 模块在 import 时会 `mkdir logs`（相对路径，即 `/app/logs`），而 `/app` 是之前以 root 身份创建的——不 chown 的话，appuser 连日志目录都建不了，容器启动即崩。**权限问题要在构建期解决，不要留给运行期爆炸。**

### 3.7 HEALTHCHECK：给编排器一双眼睛

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1
```

没有健康检查时，Docker 判断容器"活着"的唯一依据是**主进程是否存在**。这太粗糙了：进程还在，但事件循环卡死、端口没监听起来、依赖初始化失败——对外来说都是"死了"，Docker 却认为它很健康。HEALTHCHECK 把判断标准升级为**应用自定义的语义化检查**。

四个参数的取舍逻辑：

- `--interval=30s`：检查频率。太频繁浪费 CPU 且刷日志，太稀疏发现故障慢。30s 是常见折中。
- `--timeout=5s`：单次检查的超时。健康端点应该毫秒级响应，5s 还没响应本身就已经说明出问题了。
- `--start-period=10s`：**启动宽限期**。pip 装完的服务冷启动要加载模块、初始化事件循环，这期间 curl 必然失败——宽限期内的失败不计入重试次数，避免服务还没起来就被判死重启，陷入"启动→被杀→再启动"的死循环。
- `--retries=3`：连续失败 3 次才标记 unhealthy。网络抖动、GC 停顿都可能造成单次超时，**一次失败是噪声，连续失败才是信号**。

`curl -f` 的 `-f`（fail）是关键：curl 默认把 HTTP 500 也当"成功执行"（退出码 0），`-f` 让非 2xx 响应变成非零退出码，HEALTHCHECK 才能感知失败。`|| exit 1` 是双保险，确保任何异常路径都以退出码 1 告终。

检查状态用 `docker inspect --format='{{.State.Health.Status}}' <容器>` 查看，会经历 `starting → healthy`（或 `unhealthy`）的流转。

### 3.8 .dockerignore：构建上下文的守门员

[.dockerignore](../源码/smart-research-agent/.dockerignore) 沿用 day002 的清单，今天的语境下重新强调它的两个职责：

1. **速度**：`docker build` 第一步是把整个构建上下文打包发给 Docker 引擎。`.venv`（数百 MB）、`htmlcov/`、`.git/` 全都会被打包——排除后上下文从几百 MB 降到几 MB。
2. **安全**：`.env` 里有 API Key。一旦 `.env` 被 COPY 进镜像，即使后续层删掉它，它依然存在于历史层中，`docker history` 加镜像导出就能提取。**密钥绝不能进任何镜像层**，`.dockerignore` 是第一道（也是成本最低的）防线。

注意 `.dockerignore` 排除 `.env.*` 但不排除 `.env.example` 的话会把模板也排除——本项目选择全部排除，镜像内配置一律走 ENV 注入，模板文件对运行时没有价值。

## 第四章：docker-compose.yml —— 把运行参数也变成代码

### 4.1 为什么有了 Dockerfile 还要 compose

只用 Dockerfile，启动命令长这样：

```bash
docker build -t smart-research-mcp:dev .
docker run -d --name smart-research-mcp \
  -p 8000:8000 \
  -e MCP_TRANSPORT=sse -e MCP_HOST=0.0.0.0 -e MCP_PORT=8000 -e LOG_LEVEL=INFO \
  --restart unless-stopped \
  smart-research-mcp:dev
```

问题显而易见：**运行参数散在命令行里**，不进版本控制、没法 review、换个机器就得重新背一遍。docker-compose 把"怎么运行"也声明成代码：

```yaml
services:
  mcp-server:
    build: .
    image: smart-research-mcp:dev
    container_name: smart-research-mcp
    ports:
      - "8000:8000"
    environment:
      MCP_TRANSPORT: sse
      MCP_HOST: 0.0.0.0
      MCP_PORT: 8000
      LOG_LEVEL: INFO
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 10s
    restart: unless-stopped
```

完整文件见 [docker-compose.yml](../源码/smart-research-agent/docker-compose.yml)。逐块看。

### 4.2 build 与 image：一条命令从源码到容器

`build: .` 告诉 compose：镜像不存在时，用当前目录的 Dockerfile 现场构建。`image: smart-research-mcp:dev` 给构建产物命名。两者配合后，`docker compose up -d --build` 一条命令完成"构建 + 启动"，这是 compose 相对裸 docker 命令的第一个红利。

### 4.3 ports：宿主机与容器的桥

`"8000:8000"` 的格式是 `宿主机端口:容器端口`。请求链路：

```text
Client → 宿主机:8000 → Docker NAT 转发 → 容器内 appuser 进程 :8000（绑定 0.0.0.0）
```

再次呼应 2.3 节：链路上最后一环要求进程绑定 `0.0.0.0`，否则转发进来的包无人接收。左右两个 8000 可以不同（比如 `"9000:8000"` 避免宿主机端口冲突），容器内那个 8000 对应的是 `MCP_PORT` 和 EXPOSE，保持一致即可。

### 4.4 healthcheck：compose 层声明覆盖镜像层

Dockerfile 里已经写了 HEALTHCHECK，compose 里又写一遍，是重复吗？不是——**compose 的 healthcheck 会覆盖 Dockerfile 的定义**。这提供了分层灵活性：镜像里放一份合理的默认检查，具体部署环境可以按需调整（比如生产环境把 interval 缩短到 10s 以便更快发现故障）。两者保持一致是当前的合理选择：让 compose 文件自包含，读者不用翻 Dockerfile 就知道完整的运行姿态。

### 4.5 restart 策略：进程会死，服务不该死

`restart: unless-stopped` 的语义：容器因任何原因退出（崩溃、宿主机重启后）都自动拉起，**除非**被人为 `docker stop` / `docker compose stop` 停掉。

四种策略的对比：

| 策略 | 崩溃重启 | 机器重启后拉起 | 手动 stop 后还拉起吗 |
|------|---------|---------------|---------------------|
| `no`（默认） | 否 | 否 | — |
| `always` | 是 | 是 | **是**（下次 daemon 启动时） |
| `unless-stopped` | 是 | 是 | 否 |
| `on-failure` | 仅非零退出 | 否 | 否 |

`unless-stopped` 是服务类容器的常见最佳选择：它尊重人的显式意图（我 stop 了就是真不想让它跑），同时对意外情况（崩溃、重启）自愈。`always` 的坑在于：你手动停了容器，重启电脑后它又悄悄起来了——"unless-stopped"正是为修复这个反直觉行为而引入的。

### 4.6 compose v2 的时代印记

注意文件里**没有 `version: "3.8"` 这一行**。Compose v2（`docker compose`，子命令形式，而非旧的独立二进制 `docker-compose`）已经废弃了 version 字段——schema 由 compose 实现自动协商，写了反而会收到过时警告。本项目环境是 Compose v2.26，直接省略。

### 5.1 完整验证清单

下面的命令在有 Docker 环境的机器上按序执行（Windows 上确保 Docker Desktop 已启动）：

```bash
cd day022/源码/smart-research-agent

docker compose up -d --build

docker compose ps
```

每一步都有明确的验证点：第 2 步确认分层缓存生效（重新构建时依赖层应显示 `CACHED`）；第 4 步确认健康检查在 10s 宽限期后转绿；第 5 步确认 SSE 服务的 HTTP 面可达；第 6 步确认 ENV 注入链路通畅。

### 5.2 一个排错决策树

验证不通时按此顺序排查，能覆盖 90% 的问题：

```text
宿主机 curl 不通
  ├─ docker compose ps 显示容器 Exit？

  ├─ 容器 Up 但 health 是 unhealthy？
  │    └─ docker inspect 看 Health.Log 里 curl 的具体失败
  ├─ 容器 healthy 但宿主机访问超时？
  │    └─ 九成是服务绑了 127.0.0.1 而非 0.0.0.0（2.3 节的坑）
  └─ 容器 healthy、宿主机 connection refused？
       └─ 检查 ports 映射：docker compose ps 的 PORTS 列
```

## 第六章：今日总结 —— 容器化的本质是把"运维知识"编码

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 包名 `mcp_server` 而非 `mcp` | Python 导入遮蔽：同名包会顶掉官方 SDK | `mcp_server/__init__.py` |
| SSE 而非 stdio 用于容器 | stdio 需要父子进程共享管道，与容器隔离模型冲突 | `server.py --transport` |
| 绑定 `0.0.0.0` | 端口转发的请求对容器是"外部连接" | `server.py` / `ENV MCP_HOST` |
| `custom_route("/health")` | 编排器需要语义化存活信号；探针必须轻量 | `server.py` |
| ENV 注入 + 代码兜底 | 十二要素：配置存环境；一份镜像多处运行 | `Dockerfile ENV` / compose `environment` |
| 依赖层先于源码层 | 镜像分层缓存：变化慢的在前 | `Dockerfile` 指令顺序 |
| apt 装 curl + 清缓存同层 | 镜像层只增不改：跨层删除不减小体积 | `Dockerfile` 第一条 RUN |
| 非 root + chown /app | 最小权限；日志目录需要写权限 | `Dockerfile` USER |
| HEALTHCHECK 四参数 | 宽限期防启动死循环；重试次数滤抖动 | `Dockerfile` / compose |
| `restart: unless-stopped` | 自愈意外、尊重人为停止 | compose |
| compose 不写 version | Compose v2 废弃 version 字段 | compose |

回头看，今天写的新代码只有几十行，但 Dockerfile 和 compose 文件里的**每一行都是一条被编码的运维知识**：为什么 curl 要在这一层装、为什么是 0.0.0.0、为什么宽限期 10 秒。容器化的价值从来不只是"打包"，而是把原本存在于老员工脑子里、Wiki 角落里、事故现场复盘中的知识，变成版本控制下可审查、可复现、可演进的代码。
