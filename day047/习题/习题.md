## 第一部分：选择题

### 第 1 题（评估骨架，day025）

关于 `EvaluationHarness` 的"数据集 → 执行 → 评分 → 汇总"四步骨架，下列哪一项描述是**错误**的？

- A. 评估数据集必须固定可复现，且应当包含边界用例，而不是只放 happy path
- B. 汇总时应当按 tag 分组（`by_tag`），因为总通过率可能掩盖某个分组的塌方
- C. 为了贴近真实场景，业务逻辑（例如检索、Agent 循环）应当直接写在 Harness 的 `evaluate` 里，避免多一层间接
- D. 评分规则（阈值、公式、rubric）必须显式可审计，才能让分数回溯到具体样本与具体判断

### 第 2 题（Prompt 评估，day026）

`PromptEvaluator` 采用"规则 0.4 + LLM 裁判 0.6"的双通道评分，并设有 `TIE_THRESHOLD = 0.05`。下列哪一项**正确**？

- A. 规则权重之所以低于裁判，是因为规则实现更简单，不值得给更高权重
- B. 规则是确定性的、裁判有偏差（位置偏差、冗长偏好、自我偏好），两路权重接近但裁判略高，是为了让语义判断略占上风又不被单一路径支配
- C. `TIE_THRESHOLD` 的作用是当裁判解析失败时给出保守兜底分
- D. 双通道评分意味着"Prompt 得分高"就一定意味着"输出质量高"

### 第 3 题（输出质量与 RAG 指标，day027 / day029）

关于输出质量评估与 RAG 评估的指标口径，下列哪一项**正确**？

- A. `OutputEvaluator` 的格式校验（JSON 合法性、Markdown 结构）应调用 LLM 判定，因为只有模型能判断格式是否"好看"
- B. `retrieval_recall` 在"相关文档集合为空"时返回 0.0，表示"什么都没召回就是错"
- C. `retrieval_recall` 在"相关文档集合为空"时返回 1.0、`retrieval_precision` 在"召回集合为空"时返回 0.0，这些边界值是刻意选定的
- D. `ndcg` 与 `mrr` 度量的是生成答案的忠实度，与检索排序无关

### 第 4 题（Agent 评估与红队，day030 / day031）

关于 Agent 评估与安全红队，下列哪一项**正确**？

- A. `step_efficiency` 度量"任务是否完成"，`completion_rate` 度量"是否绕远路"
- B. 工具顺序分（LCS）应当把失败轨迹也计入，否则样本量不足
- C. 红队达到 100% 拦截率即说明系统已经安全，可以停止维护用例集
- D. 红队基线 56.3% → 修复后 100% 的过程中，"修掉一条写错的正则"的收益可能大于"新增五条规则"

### 第 5 题（服务化与流式，day038 / day039）

下列哪一项描述是**错误**的？

- A. 同步阻塞的 CPU/IO 代码应放进普通 `def` 路由，由 FastAPI 自动丢进线程池
- B. `create_app` 注入的是"造新 Agent 的工厂"而不是 Agent 实例，因为 Agent 持有单次任务状态
- C. 422 / 404 / 500 是这套服务贯穿 M4 全系的错误码契约语言（请求不合法 / 资源不存在 / 全局未捕获）
- D. SSE 流式会逐 token 校验内容，因此流式返回的答案比非流式更正确

### 第 6 题（集成流水线与归因，day043 / day046）

关于 day046 的六阶段流水线与成本归因，下列哪一项**正确**？

- A. `PipelineResult.cost_usd` 是"到目前为止的累计费用"，方便跨请求对比
- B. 流水线把"输出侧审核"放在"缓存回写"之后，这样能少做一次审核、更快返回
- C. `ModelRouter` 作为包装器本身不产生 token也不持有 `usage_log`，因此流水线归因时必须落到 `last_used_llm` 暴露出的叶子模型上
- D. 模型不在 `price_table` 中时，应当直接抛异常终止请求，避免出现"不准确"的成本数字

## 第二部分：判断题

### 第 7 题（day025 / day027）

评估体系的"死区"思想在项目里反复出现：day026 的 `TIE_THRESHOLD = 0.05`、day027 `OutputQualityLogger.aggregate()` 的 0.05 死区、day046 `PerformanceGuard` 的最小判定下限，目的都是同一个——把噪声从信号里剥离出来，避免评估结论被抖动支配。（对 / 错）

### 第 8 题（day029）

`mean_precision` 在 day029 的评测集上只有 0.39，这说明检索器质量很差，应当优先优化检索。（对 / 错）

### 第 9 题（day032 / day046）

CI 门禁的松紧应当与"指标回归的后果"成正比：质量类指标（完成率、步数效率）可以留裕度，安全类指标（红队拦截率）必须零容忍。（对 / 错）

### 第 10 题（day037 / day040 / day041）

"扩展抽象、零改动"是贯穿 M4 的设计哲学：`BaseLLM.stream` 默认整段 `yield self.chat(...)`、`BaseLLM.supports_vision` 默认 `False`、`EmbeddingProvider.embed_batch` 默认逐条 `embed`——都是给抽象加"带默认值的具体实现/属性"，而不是加抽象方法。（对 / 错）

### 第 11 题（day045）

day045 引入本地模型时，为了支持本地推理给 `BaseLLM` 新增了 `chat_local()` 抽象方法，所有既有实现都必须实现它才能实例化。（对 / 错）

### 第 12 题（day047 核对结论）

`_TimedLLMProxy` 只覆写 `chat`、其余属性通过 `__getattr__` 全量透传，所以它包住的 `MockLLM` 的 `usage_log` 可以被 `CostTracker` 直接归因；而 `CachedLLM` 是持有自身状态的包装器，若不显式透传叶子信息，"缓存 + 计费"会把真实用量静默记成 0。（对 / 错）

## 第五部分：编程题

### 第 16 题（综合编程 · 包装器用量透传的完整验证）

**背景**：day046 的结语提出"每加一层包装，就问一句：用量、错误、状态还能穿透吗？"。day047 用一次真实核对把它变成了工单，day048 的快照里用 `CachedLLM.last_used_llm` 收口。本题要求在 **day046 或 day048 快照**上完整验证这条链路。

**功能要求**（离线可跑，不调任何网络）：

1. **叶子可归因**：构造 `MockLLM(responses=["叶子回答"])`，调用一次 `chat`，用 `CostTracker().record_from_llm(llm, model="mock-model")` 断言登记条数为 1、`tracker.total_tokens > 0`。
2. **缓存包装器透传叶子**：构造 `CachedLLM(MockLLM(responses=["缓存回答"]), SemanticCache(embedding=CharNgramEmbedding()), model="gpt-4o-mini")`，断言 `cached.last_used_llm is <内层 MockLLM>`；若快照尚未包含该属性（day046），则改为断言 `hasattr(cached, "usage_log") is False` 并说明这正是断链点。
3. **包装器透传到路由的叶子**：构造 `ModelRouter([ModelSpec(name="mock-model", llm=MockLLM(...), capability=5, cost_per_1k=0.0)])`，调用一次 `chat`，断言 `router.last_used_llm` 就是那个 `MockLLM`；再用 `CostTracker().record_from_llm(router.last_used_llm, model="mock-model")` 断言登记 1 条。
4. **追踪代理天然透传**：用 `Tracer()` 起一次 trace，创建 `_TimedLLMProxy(MockLLM(...), ctx)`，断言 `hasattr(proxy, "usage_log") is True` 且 `CostTracker` 能直接归因。
5. **流水线端到端**：用 `IntegratedPipeline(llm=<CachedLLM 包住的 MockLLM>, cache=<同一个 SemanticCache>, tracker=CostTracker())` 跑两次同一个任务，断言：第一次 `cost_usd > 0`（或按快照版本断言为 0 并记录告警文案）、第二次 `cached is True`、`model == "cache"`、`cost_usd == 0.0`、底层 `MockLLM.calls` 长度仍为 1。
6. 打印每一步的关键中间值，最后打印"全部断言通过"。

**提示**：`IntegratedPipeline` 的 `_account` 取值链是 `getattr(self.llm, "last_used_llm", None) or self.llm`；`SemanticCache` 需要 `EmbeddingProvider`，离线用 `CharNgramEmbedding()`；`MockLLM.chat` 会往 `usage_log` 追加 `{"prompt_tokens": ..., "completion_tokens": ...}`；`CostTracker.record_from_llm` 依赖被传对象的 `usage_log` 与 `_cost_consumed` 两个属性。
