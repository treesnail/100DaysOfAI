## 第二章：M3 复盘 —— 评估体系的四层递进

### 2.1 第一层：骨架（day025）——评估是流水线，不是脚本

**一句话本质**：`EvaluationHarness` 用模板方法模式冻结"加载数据集 → 逐条运行 → 逐条评分 → 汇总报告"的骨架，子类只实现 `execute` 与 `score` 两个抽象方法（完整代码见 [../../day034/源码/smart-research-agent/smart_research_agent/evaluation/harness.py](../../day034/源码/smart-research-agent/smart_research_agent/evaluation/harness.py)）。

**为什么**：

- **数据集必须冻结**：评估的可比性来自"本次和下次跑同一批用例"。数据集独立于代码演进、可版本化、可审计——进代码等于把基准和实现焊死。
- **汇总层与明细层分离**：明细层回答"哪条挂了、为什么"，汇总层回答"能不能发版"。决策发生在汇总层，归因发生在明细层。
- **骨架越薄复利越大**：day029 的 RAG 评估、day030 的 Agent 评估各自只实现两个方法就拥有完整流水线——这是 day002 模板方法模式的第三次收租。

### 2.2 第二层：双通道（day026/day027）——规则查确定性，裁判查语义

**一句话本质**：输入侧（Prompt 评估）与输出侧（输出质量评估）是同一个设计范式的两个实例——**规则通道查确定性问题，LLM 裁判通道查语义问题**。

**为什么这个范式是 M3 的核心**：

| | 规则通道 | LLM 裁判通道 |
|---|---------|-------------|
| 擅长 | 格式合规、长度、占位符配对、矛盾关键词对 | 歧义、忠实度、有用性等语义判断 |
| 成本 | 零（纯代码） | 每条一次 LLM 调用 |
| 确定性 | 完全确定，可进 CI | 概率性，需 rubric + 低温 + 抽查 |
| 角色 | 廉价预筛（类似 lint） | 终审（类似 code review） |

LLM-as-a-judge 可行的原理是**评判比生成容易**（day033 之后可以说得更深：评判任务的"正确答案分布"比生成任务尖锐得多，模型在尖锐分布上犯错率低）。三个工程纪律：rubric 要显式（打分细则写进裁判 Prompt）、temperature 要低（裁判是"输出给程序看"的场景，按 day033 的结论设 0）、结果要可抽查（每条评分附理由）。

### 2.3 第三层：特化（day029/day030）——RAG 评两层，Agent 评轨迹

**RAG 评估的一句话本质**：RAG 的错误有两个独立来源——**检索错了**（没找对文档）与**生成错了**（找对了但答歪了/编了）——因此指标必须分两层，混在一起算总分永远不知道改检索器还是改 Prompt（[../../day034/源码/smart-research-agent/smart_research_agent/evaluation/rag_eval.py](../../day034/源码/smart-research-agent/smart_research_agent/evaluation/rag_eval.py)）。

- **检索层**：命中率（相关文档进没进 top-k）、MRR（第一个相关文档排多靠前）——纯集合运算，规则通道即可完成；
- **答案层**：忠实度（答案是否被检索内容支撑，即"有没有编"）——语义判断，必须裁判通道。

**Agent 评估的一句话本质**：Agent 的输出不是一段文本而是一条**轨迹**（Thought→Action→Observation 的多步序列），评估对象因此从"最终答案对不对"扩展为"答案对不对 + 路径是否合理"（[../../day034/源码/smart-research-agent/smart_research_agent/evaluation/agent_eval.py](../../day034/源码/smart-research-agent/smart_research_agent/evaluation/agent_eval.py)）。

- **结果维度**：任务成功率——最终答案达标吗；
- **过程维度**：工具选择正确性（该搜的时候搜了吗）、步数效率（3 步能搞定的事用了 8 步吗）、循环检测（有没有原地打转）。

为什么过程维度不可省：一个"蒙对答案但轨迹混乱"的 Agent 比"答错但轨迹清晰"的 Agent 更危险——前者的正确率是不可复制的运气，后者的错误是可定位、可修复的。**评估轨迹，本质是把 Agent 的"思考过程"从黑盒变成可归因的账本**——这和 day032 的 tracing 是同一个思想在离线与在线两个场景的投影。

### 2.4 第四层：对抗与运营（day031/day032）——红队找下限，CI 守底线

**红队评估（day031）**：前面所有评估用例都是"正常用户会怎么问"，红队用例是"恶意用户会怎么攻"——注入（"忽略之前的指令"）、越权、套系统提示词、诱导有害输出。安全性的特殊性在于它由**最差情况**而非平均情况定义：99% 的拦截率意味着攻击者试 100 次成功 1 次。因此红队报告的核心指标是**检出率/拦截率按攻击类别分解**（[../../day034/源码/smart-research-agent/smart_research_agent/evaluation/redteam.py](../../day034/源码/smart-research-agent/smart_research_agent/evaluation/redteam.py)，防护侧实现见 [../../day034/源码/smart-research-agent/smart_research_agent/security/injection_detector.py](../../day034/源码/smart-research-agent/smart_research_agent/security/injection_detector.py)）。

**CI/CD 与可观测性（day032）**：把九天的一切拧进工程系统：

- **质量门禁**：评估分数与成本预算变成 CI 的 pass/fail 条件——分数回退或预算超支则构建失败。评估从"偶尔跑跑的报告"升级为"每次合并的守门员"。
- **可观测性三支柱**：指标（metrics，聚合数字）回答"系统整体健康吗"；追踪（tracing，[../../day034/源码/smart-research-agent/smart_research_agent/observability/tracing.py](../../day034/源码/smart-research-agent/smart_research_agent/observability/tracing.py) 的 span 树）回答"这一次请求经历了什么"；日志回答"当时发生了什么细节"。告警不是第四支柱，而是**指标的下游消费者**。
- **成本归因**：`CostTracker`（[../../day034/源码/smart-research-agent/smart_research_agent/observability/cost_tracker.py](../../day034/源码/smart-research-agent/smart_research_agent/observability/cost_tracker.py)）按模型/接口打标签记账——账单要回答的是"哪个模型、哪类任务花了多少钱"，归因维度必须在记录时打上，事后无法猜测。

## 第三章：M4 前半复盘 —— 原理把经验法则变成推论

### 3.1 day033：自回归生成与采样参数

**一句话本质**：GPT 的原子操作是"给定文本，输出词表上下一个 token 的概率分布"；生成就是把选中的 token 追加回去反复调用的**自回归**循环。

**为什么这一个原理能解释半本经验手册**：

| 经验法则 | 原理推论 |
|----------|----------|
| 输出 token 比输入贵（day032 价格表） | 读输入可并行（预填充），生成必须逐 token 串行解码 |
| 幻觉是结构性的 | 模型每步选"概率合理的下一个 token"，不是"查事实" |
| ReAct 格式模板有效（day006） | 模板把后续 token 的分布塑造成想要的格式 |
| max_tokens 只能是硬截断 | 生成只有概率上的结束倾向，没有"说完才停"的保证 |
| Agent 场景 temperature=0 | 输出给解析器看，且早期波动被 ReAct 循环放大 |

**采样参数的数学**（[../../day034/源码/smart-research-agent/smart_research_agent/llm/sampling.py](../../day034/源码/smart-research-agent/smart_research_agent/llm/sampling.py)）：

- **temperature** 就是 softmax 里 logit 的缩放因子：`p_i = exp(z_i/T) / Σ exp(z_j/T)`。T→0 趋 one-hot（近似贪心），T→∞ 趋均匀。**T=0 不是"很低的温度"，是另一种解码算法（贪心）**——所以我们的纯函数对 T=0 抛异常，而 `SamplingParams` 允许 0.0 是因为 API 语义里 0 表示走贪心路径。
- **top_p（核采样）** 截断的是候选集而非分布形状：按概率降序累加到 p 即截断，核外置零、核内归一。它优于 top-k 的关键是**自适应**——分布尖锐时核里一两个候选，平坦时一大串（实测 `[0.9,0.05,0.05]` 核内 1 个 vs `[0.34,0.33,0.33]` 核内 3 个）。
- **多模型路由**（`llm/router.py`）：按能力/成本/可用性把请求分流到恰好的模型，降级链永远**向上**（更强）而不是向下——失败安全偏向多花钱一侧，不偏向答错一侧。`ModelRouter` 实现 `BaseLLM`，对 Agent 完全透明（day005 依赖倒置的回报）。

### 3.2 day034：Tokenization —— 输入端的地基

**一句话本质**：token 是文本进入模型的唯一单位、计费与限长的唯一单位；subword 分词在"词级（词表爆炸+OOV）"与"字符级（序列爆炸）"之间取甜点位。

**BPE 核心循环**（教具：[../../day034/源码/smart-research-agent/smart_research_agent/llm/bpe_demo.py](../../day034/源码/smart-research-agent/smart_research_agent/llm/bpe_demo.py)）：统计相邻对频率 → 选最高频对 → 全局合并并记规则，重复 N 轮。三个吃透点：

1. **频率决定粒度**：高频整词自然进入词表（演示语料里 `deepest</w>` 16 轮后成单符号），低频词保持片段形态；
2. **OOV 是副产品**：未见词按合并规则顺序套用，一路拆到已知片段乃至字节（`encode("deeply")` → `["deep","l","y","</w>"]`），无需任何专门机制；
3. **并列 tie-breaking 是正确性的一部分**：频率并列时取字典序小者，训练结果才与遍历顺序无关、测试才可断言。

**三家算法对照**：BPE（GPT 系，选频率最高对）、WordPiece（BERT，选似然提升最大对——"结合得比偶然更紧密"）、Unigram/SentencePiece（T5/LLaMA，自大词表向下裁剪，空格当普通字符故原生支持中文，且支持概率化采样多种切分做正则化）。

**工程落地**（`llm/tokenizer.py`）：

- **tiktoken 优先、字符估算兜底**：词表文件首次使用从公网下载后本地缓存（本机实测 cl100k_base 与 o200k_base 缓存命中、断网可加载）；无缓存时降级到中英感知的字符估算，`backend` 属性显式暴露当前路径。
- **中文 token 效率**：cl100k_base 下同义中文文本 token 数约为英文 3 倍（实测 27 vs 9），o200k_base 改善到 16。推论：中文场景的上下文预算与 max_tokens 要打 2~3 倍余量。
- **事前预估接回事后记账**：`estimate_cost` 与 `CostTracker` 共用 `DEFAULT_PRICE_TABLE`，"调用前预估 → 调用后记账"形成成本闭环。

### 3.3 两条主线的三个交汇点（本章最重要的复盘结论）

1. **成本维度 = token 数 × 单价**：day032 的 `CostTracker` 记账时，prompt/completion token 数还来自"4 字符 1 token"的占位估算；day034 之后，事前有 `TokenCounter.estimate_cost` 精确预估、事后有真实 usage 记账，M3 的"成本"指标才真正有了计量学基础。
2. **LLM 裁判是 LLM 调用，因此服从采样规律**：day026 说"裁判要低温"，day033 解释了为什么——裁判输出是给程序解析的分数，属"输出给解析器看"场景，且评估流水线会放大单条评分的波动，temperature=0 是推论而非规矩。rubric 显式化同理：它是在**塑造裁判模型的输出分布**。
3. **门禁阈值的单位是 token/美元**：day032 的预算门禁若按字符数估预算，中文场景会系统性低估 3 倍——day034 的精确计数让门禁阈值从"拍脑袋"变成"可计算"。

## 第五章：常见误区清单

**评估体系（M3）**：

1. **"跑几个 demo 看看就是评估"** —— demo 是展示，评估是度量：用例集必须冻结、评分规则必须显式成代码，否则"这次比上次好"无从谈起。
2. **"准确率是唯一指标"** —— 正确性/相关性/安全性/成本四维互相牵制，只看一维必然翻车；正确性 95 分但安全性 40 分的系统是危险品。
3. **"Prompt 评估能替代端到端评估"** —— Prompt 得分高 ≠ 输出质量好；前者是廉价预筛（lint），后者才是终审（单元测试）。
4. **"RAG 评一个总分就够了"** —— 检索错与生成错混在一起，报告无法回答"改检索器还是改 Prompt"；必须两层指标分开归因。
5. **"Agent 只看最终答案"** —— 蒙对答案的混乱轨迹比答错的清晰轨迹更危险；轨迹评估让"思考过程"可归因。
6. **"安全性靠 Prompt 里写'不许…'"** —— Prompt 约束是概率性的软约束；安全性必须用攻击用例集实测拦截率（day031），并按最差情况而非平均情况理解。
7. **"评估脚本跑完打印就扔"** —— 没有结构化、可序列化、受版本管理的报告，就没有历史对比与 CI 门禁。

**原理与分词（M4 前半）**：

8. **"temperature=0 是很低的温度"** —— 数学上 T=0 是除零；它是另一种解码算法（贪心）。所以纯函数抛异常、API 参数层单独放行。
9. **"top_p 和 top-k 差不多"** —— top-k 候选数固定，分布尖锐时放进烂 token、平坦时错杀好候选；核采样的候选集随分布形状自适应。
10. **"BPE 靠特殊机制处理 OOV"** —— OOV 是贪心合并的副产品：未见词沿规则表拆到已知片段/字节，`<UNK>` 是词级分词时代的遗物。
11. **"tiktoken 装上就能离线用"** —— 词表文件首次使用联网下载、本地缓存；无缓存无网络的机器首次加载会失败，这就是 `TokenCounter` 必须保留降级路径的原因。
12. **"token 数 ≈ 字符数 ÷ 4"** —— 这只对英文粗略成立；cl100k_base 下中文按字符算是 3 倍级低估，中文预算必须实测（`count_tokens`）而非估算。
13. **"预估和记账可以各用各的口径"** —— 事前 `estimate_cost` 与事后 `CostTracker` 若价格表或计数口径不一致，预算与账单系统性对不上，门禁失去意义。
14. **"降级链该往便宜方向降"** —— 失败安全应偏向"多花钱"一侧（向上降级到更强模型），而不是"答错"一侧；成本失控可追账，答错造成的后果无法追账。
