# 专属模型部署与切换手册（day060 / M5-D11）

> 本文是 `smart_research_agent/serving/` 的设计与操作说明，与代码**同源**：
> 文中每一张表都能由 `spec_table()` / `binding_table()` / `route_table()` /
> `verify_table()` / `price_book()` 现场打印出来，每一个数字都由
> `scripts/serving_demo.py` 实测。

## 1. 这五个模块各回答一个问题

```text
spec.py      线上应该跑什么     形态（base / adapter / merged）、端点、显存怎么算
binding.py   线上跑的到底是它吗 注册表 / 部署记录 / 端点自述三处比对
switch.py    流量怎么分         确定性分桶的灰度、影子流量、单向降级
verify.py    它够不够好         同一批用例上两个推理臂的合格率、错误数、延迟
cost.py      它值不值           固定成本 vs 可变成本、利用率、盈亏平衡调用量
```

它们共享一个前提：**协议层不需要任何改动**。三种形态在 OpenAI 兼容端点背后
长得一模一样，day045 的 `LocalModel` 一行都不用改。差异全部在运维层。

## 2. 三种部署形态

| 形态 | 线上是什么 | 必填字段 | 运行时依赖 | 换业务的代价 |
|------|-----------|---------|-----------|-------------|
| `base` | 未微调的基座 | （无） | 不需要额外运行时 | （无业务可换） |
| `adapter` | 基座 + 一个 LoRA 适配器 | `adapter_dir` | 需要 peft 在推理时挂载 | 换十几 MB 的适配器文件 |
| `merged` | 合并后的完整模型 | `merged_dir` | 不需要额外运行时 | 换一份与基座同量级的完整权重 |

**必填字段由形态决定，且在构造期校验。** 声明成 `adapter` 却没给
`adapter_dir` 的部署不会报错——它只会安静地服务基座，而"专属模型上线了
却没生效"正是这样发生的。

形态建议只有两条规则（`recommend_kind`）：

```text
只有一个业务、也不需要热插拔 → merged（部署链路与普通模型一致，完整权重本来只有一份）
其他情况                      → adapter（一个基座 + N 个适配器省下 N−1 份完整权重）
```

## 3. 显存算术

```text
权重      = 参数数 × 每参数字节数              与上下文无关，开机就占满
KV 缓存   = 2 × 层数 × KV头数 × head_dim × 字节数 × 上下文长度 × 并发数
适配器    = 十几 MB 到几十 MB
```

参照 Qwen3-8B 的公开结构（36 层 / 8 个 KV 头 / head_dim 128 / 约 8.2B 参数），
bf16 即每值 2 字节时的实测值：

| 场景 | 权重 | KV 缓存 | 合计 |
|------|------|---------|------|
| ctx 4096 × 并发 1 | 15.2737 GiB | 576.00 MiB | 15.8362 GiB（含 48 KiB 适配器） |
| ctx 4096 × 并发 4 | 15.2737 GiB | 2304.00 MiB | 17.5237 GiB |

每 token、每序列的 KV 缓存是 **147456 字节 = 144 KiB**。
把并发从 1 提到 4 会在权重之外多要 **1.69 GiB**，而它**不提升任何质量**——
Ollama 官方 FAQ 把这件事写在 `OLLAMA_NUM_PARALLEL` 的说明里
（并发会按并发数放大上下文与内存分配）。

4-bit 权重给的是**下界**（不含量化常数、未量化层与对齐），
报告里的 `weights_is_lower_bound` 会把它标出来。

## 4. 部署绑定：五条一致性检查

| 检查 | 挡住的故障 | 缺省是否阻塞 |
|------|-----------|-------------|
| `serving_name` | 部署脚本改错了目标服务 | 是 |
| `base_model` | 基座与适配器不匹配——**不报错，只是答错** | 是 |
| `adapter_hash` | 线上加载的是上一份适配器 | 是 |
| `kind_shape` | 形态与自述矛盾（合并形态却自述挂了适配器） | 是 |
| `registry_head` | 绑定版本不是注册表 head | **否** |

最后一条刻意不阻塞：**灰度期间"部署的不是 head"是完全正常的**
（先部署再切流量，或先给 5% 试跑）。把它设成阻塞会逼着团队为了过校验
而先提升阶段——那是"为了让门禁变绿而改数据"。

因此报告返回两个布尔量：`passed`（阻塞项全通过）与 `consistent`（全部一致）。
一个 `passed=true / consistent=false` 的部署是灰度期间最正常的状态。

## 5. 流量切换

```text
bucket = sha256(salt + "\0" + prompt)[:4] / 2**32       落在 [0, 1)
ratio        分桶值 < dedicated_ratio  → 专属模型直接服务
shadow_ratio 落在云端侧且影子分桶命中 → 额外调用专属，但只返回云端结果
fail_open    专属失败 → 回落到云端（严格模式置 False 用于测真实成功率）
```

**分桶用哈希而不是随机数的代价必须说清楚**：`dedicated_ratio=0.05` 的含义是
"哈希落在前 5% 的**那些 prompt**"，而不是"随机 5% 的请求"。同一句话被问
一万次，它要么全在专属侧、要么全在云端侧。实测（200 个不同问题的同一批）：

| 阶段 | 设定 | 专属服务 | 影子调用 | 说明 |
|------|------|---------|---------|------|
| ① 影子 | ratio 0 / shadow 0.05 | 0/200 | 16 | 用户完全不受影响 |
| ② 小流量 | ratio 0.05 / shadow 0 | 11/200 | 0 | 5% 的用户真的在用专属模型 |
| ③ 半量 | ratio 0.5 / shadow 0 | 90/200 | 0 | 一半流量，看线上指标有没有分叉 |
| ④ 全量 | ratio 1.0 / shadow 0 | 200/200 | 0 | 切换完成，`ModelSwitcher` 应当被摘掉 |

**降级只向一个方向**：专属失败可以回落云端（已验证路径），
云端失败**绝不**回落专属。反向降级等于"在云端出故障时把流量交给一个
还没通过验证的模型"，两个故障叠加且第二个的根因会被第一个掩盖。

`fail_open=True` 的代价是具体的：**"一切正常"可能是云端兜出来的**。
因此 `describe()` 必须同时暴露 `fallback_count`——只看成功率会得出
"专属模型很稳"的结论，而它其实一次都没成功过。

流式路径上有一处比 day033 更严格的取舍：**已产出片段之后不再降级**。
day033 的 `ModelRouter.stream` 在异常时直接换下一个模型重新流式，
代价是最终输出可能变成"两个模型的两段话拼在一起"——而它不会报错。

## 6. 上线验证：五条检查

| 检查 | 阈值 | 阻塞 | 没测时算什么 |
|------|------|------|-------------|
| `cases` | > 0 | 是 | 不通过（没有用例就没有证据） |
| `pass_rate` | >= 0.5 | 是 | 不通过（缺证据不能切换） |
| `regression` | >= -0.0 | 是 | 不通过（云端臂缺席时算不出差值） |
| `errors` | 0 | 是 | 不通过（调用失败是部署问题，不是模型问题） |
| `latency` | 策略给出倍数 | **否** | 跳过（降级为告警） |

`latency` 缺省不检查是刻意的：**"多慢算慢"取决于部署形态**，
本地 CPU 与 A10G 的差异是十倍量级，给一个全局缺省只会让它被无脑放宽。

比率比较带一个 `RATE_EPSILON = 1e-9`：`19/20 - 20/20` 的双精度值是
`-0.050000000000000044`，**比阈值 `-0.05` 小**——没有容差的话，
"退步恰好等于容忍度"会被判成失败，而且结论会随用例数翻转。

## 7. 成本：两个不同的模型

```text
云端 API   = 可变成本 × 请求数        不调用就不花钱
自建推理   = 固定成本 × 开机时长      开机就在花钱（吞吐上限之内）
```

实测（缺省参数：1500 入 / 500 出 token，AWS g5.xlarge $1.006/h，
吞吐按 250 token/s）：

| 月度请求量 | 云端 | 自建 | 机器数 | 利用率 | 结论 |
|-----------|------|------|--------|--------|------|
| 10,000 | $5.25 | $734.38 | 1 | 3.04% | 云端更省 |
| 100,000 | $52.50 | $734.38 | 1 | 30.44% | 云端更省 |
| 1,000,000 | $525.00 | $2,937.52 | 4 | 76.10% | 云端更省 |
| 10,000,000 | $5,250.00 | $22,765.78 | 31 | 98.20% | 云端更省 |

报表里真正该看的四个数：

```text
required_gpu_hours    处理这批请求**用掉**的算力
deployed_gpu_hours    你**为之付费**的时长（machines × 730h）
utilization_actual    两者的比值 —— 解释"为什么低请求量下自建一定更贵"
breakeven_requests    云端成本追平自建月费的请求量
```

一条可用来互相校验的恒等式：

```text
breakeven_requests / 当前请求量  ==  自建单位成本 / 云端单位成本
```

实测 100000 请求/月时两者都是 **13.99**：任何一个乘数（机器数、月时长、
时价、每请求 token）算错，两个比值都会分叉。

价格是**外部事实**，因此只有一个出处（`serving/cost.py` 的两个常量）：

| 项 | 数值 | 口径 |
|----|------|------|
| AWS g5.xlarge（A10G 24GB） | $1.006/h | us-east-1 按需 |
| AWS g4dn.xlarge（T4 16GB） | $0.526/h | us-east-1 按需 |
| GCP NVIDIA T4 | $0.35/GPU·h | us-central1，**不含 VM 机型费用** |
| RunPod Pods L4 24GB | $0.49/h | 官方定价页 |
| Lambda A10 24GB | $1.29/GPU·h | 官方定价页 |
| gpt-4o-mini | $0.15 / $0.60 每 1M token | 输入 / 输出分开计价 |
| gpt-4o | $2.50 / $10.00 每 1M token | 输入 / 输出分开计价 |

**吞吐没有缺省值**：它取决于模型、量化、批大小与序列长度。
本课缺省配置里的 250 token/s 是**待替换的占位值**——
请在目标部署上实测后填回 `settings.serving_gpu_tokens_per_second`。

## 8. API 端点

| 端点 | 方法 | 回答什么 |
|------|------|---------|
| `/serving/targets` | GET | 三种形态、显存分解、流量策略、五条检查、价格表、**不能做什么** |
| `/serving/binding/verify` | POST | 三处版本是不是同一份产物（两个布尔量） |
| `/serving/verify` | POST | 同一批用例上两个推理臂的对比（五条检查） |
| `/serving/cost/compare` | POST | 两侧成本与四个派生数字 |

四个端点全部**只读或纯计算**：不写磁盘、不联网、不加载模型、不用随机数。
真正加载模型、量延迟、切流量由 `scripts/serving_demo.py` 与部署脚本承担
——**一个需要 GPU 的流程不该挂在一个 HTTP 请求上**。

延迟在端点里由**请求送来的观测值**决定（注入确定性时钟），
因此"延迟检查"这条分支可以被逐位复现地测到，而不是只能跳过。

错误码语言与 day050~day059 一致：

```text
400  业务规则不允许（未知机型键、版本不存在、产物不完整、基座不匹配、非法策略值）
422  请求形状不对（gpu_utilization 越界、requests 为负、缺 bound_version）
```

## 9. 明确不适用

- 直接按本课的价格数字做采购决策：时价随时变化，吞吐必须实测；
- 把哈希分流的切换器当 A/B 实验平台：它不是随机分流，两侧的用户构成不可比；
- 长期把 `ModelSwitcher` 留在调用链上：它的终点是 `dedicated_ratio=1.0`
  之后被摘掉，永远留着的是一层没有收益的间接层。

## 10. 一次完整的替换流程

```text
1. 形态选型      recommend_kind(variants, needs_hot_swap) → adapter / merged
2. 起服务        ollama create / vllm serve，服务名与 ServingSpec.name 一致
3. 绑定核对      POST /serving/binding/verify → 五项必须全部一致
                 （发现 adapter_hash 不一致 → 先修 adapter_dir 再谈切换）
4. 上线验证      POST /serving/verify → 五条检查里阻塞项全过
5. 影子流量      serving_shadow_ratio = 0.05，跑一周看 shadow_failures
6. 小流量灰度    serving_dedicated_ratio = 0.05 → 0.5 → 1.0
                 每一步都同时看 dedicated_served 与 fallback_count
7. 成本复盘      POST /serving/cost/compare → 用实测吞吐替换占位值
8. 摘掉切换器    ratio = 1.0 之后把 ModelSwitcher 从调用链上移除
```
