## 今日目标

day064 结束时，`VectorIngestPipeline` 留下了一个刺眼的数字：

```text
重放同一批：输入 6 → 写入 0（未变 6）| 编码调用 6 次
```

**库没变，钱照花。** 今天要回答三个问题：

1. **"有没有变"和"该不该重算向量"是不是同一个问题**——不是。
   它们是两个身份，必须分开判，否则会漏掉整整一类变更，而且不漏报错；
2. **怎么让"换配置必须重建索引"这件事在结构上漏不掉**——把身份写进键；
3. **增量是不是永远更省**——不是。变更比例高到某个程度，逐条更新反而比整库重写更贵。

## 第一章：两个身份

### 1.1 一句话说清今天在争什么

```text
内容身份（fingerprint）  这段文本是不是另一段了   → 决定"要不要更新这条记录"
向量键（vector_key）     这个向量还能不能用        → 决定"要不要重新编码"
```

day062 已经在块这一层留下了 `fingerprint`（`content_id(text)`）。
今天加的是第二个身份 `vector_key`。**两个都要有**，理由是两张反例：

```text
只比 fingerprint：
  内容没变、但换了 embedding 模型 → 判成"未变" → **旧模型的向量被继续用**
                                    检索结果整体错乱，不报任何错

只比 vector_key：
  内容变了、长度也变了，但编码文本的键碰巧... —— 不，这条更直接：
  覆盖写场景里同一份文本被改成了另一份**等长**内容，若判据只用长度或只用向量键，
  就可能判成"未变" → **更新的内容没有进索引**，用户查不到
```

第一种漏判的症状是"检索质量下降"，第二种是"新内容查不到"——
两者的表现完全不同，但它们**都只由"少比了一个身份"造成**。

### 1.2 实测：四条判据

演示脚本第 3 节对同一个 `parent` 清单跑了四次：

```text
① 未变（原样重放同一批）
   新增 0 / 更新 0 / 删除 0 / 未变 8 | 复用率 100.00%
   to_encode=0 / changed=0 / total=8 / reuse_ratio=1.0

② 内容变了（改 1 条原文）
   新增 0 / 更新 1 / 删除 0 / 未变 7 | 复用率 87.50%
   to_encode=1 / changed=1 / total=8 / reuse_ratio=0.875

③ 删了一条（少给最后 1 条）
   新增 0 / 更新 0 / 删除 1 / 未变 7 | 复用率 87.50%
   to_encode=0 / changed=1 / total=8 / reuse_ratio=0.875

④ 换了身份（只改 model）
   新增 0 / 更新 8 / 删除 0 / 未变 0 | 复用率 0.00%
   to_encode=8 / changed=8 / total=8 / reuse_ratio=0.0
```

第 ④ 行是本模块最该被记住的地方：**报告上写着"更新 8 条"，
但一条数据都没改**——是编码器身份变了。

为什么必须把它**单独说出口**：数字相同、下一步动作完全不同
（换模型要重新标定检索阈值、甚至要重跑评估；改一条原文不用）。
而 `IndexPlan` 里只剩四组 id，已经看不出原因了。因此 `plan_reason` 在这里给出的是：

```text
编码器身份变了（旧 DemoEmbedding/default (256d) → 新 DemoEmbedding/char-ngram-2-3 (256d)）：
全部 8 条需重算，这不是数据变更——换模型或换输出维度必须整库重建，旧向量不能再复用
```

### 1.3 ② 与 ③ 的计数重合，说明为什么 `IndexPlan` 要存 id 而不只存计数

```text
② updated=1, unchanged=7
③ removed=1, unchanged=7
```

两者都是"一条变了、七条没变"。只看总数**完全一样**，
差别只在**哪些 id 落在哪一组**。这就是 `IndexPlan` 的四个字段是
`tuple[str, ...]` 而不是 `int` 的理由——与 day064 的 `WriteReport` 分工一致，
只是粒度更细一层：

```text
WriteReport     四个数    回答"这次写入发生了什么"
IndexPlan       四组 id   回答"哪些块要重算"，报告要能逐行 diff
```

## 第二章：键与身份

### 2.1 身份进键

```python
vector_key(provider, model, dimension, text) = sha256(f"{provider}|{model}|{dimension}\n{text}")[:16]
```

四个输入里**三个是编码器身份**。这条设计的价值可以用一次实测说清（演示第 1 节）：

```text
同一段编码文本
'索引手册 > 缓存\n缓存键里必须含编码器身份，否则换模型之后会命中旧向量。'

现状：      model='default'      / 256d | 身份 95df00b1373d4b1b | 向量键 b213ef25c724c42c
只换 model：model='char-ngram-2-3'/ 256d | 身份 33dc151f42b9724a | 向量键 d46048eb2a6d2285
只换维度：  model='default'      / 384d | 身份 9486942d12a1e2d3 | 向量键 a1d74e61bf7d29ee

三个向量键两两不同：True
```

**换 model 或换 dimension 之后，同一段文本的键全变了**，
于是 `planner` 会把全部条目判成 `updated`，旧向量一条都复用不了。
**这不是靠人记得重建索引，而是结构上漏不掉。**

缓存的键与向量键是**同一个函数**（`EmbeddingCache.key` → `types.vector_key`）：

```text
cache.key(同一段文本) == 上面那个向量键            → True
cache.identity_key == identity.key                → True（95df00b1373d4b1b）
```

身份进了键，所以换编码器之后**旧缓存条目永远不会命中**——
而不是"命中了旧模型的向量，检索结果只是变得不太对"。

### 2.2 时间戳为什么不能进版本号

```python
index_version_id(identity_key, metric, backend, digest)   # 四个输入，没有时间
```

`IndexManifest` 带 `created_at`，但它**不参与**版本号计算。
理由与 day062 用 `chars` 而不是 `tiktoken` 作默认度量完全一样：

```text
时间戳进版本号 → 同一份内容在两台机器上得到两个版本号
                → "这个版本在哪台机器上建的？" 变成必须回答的问题
                → 而它本来不该是一个问题
```

实测这条纪律的效果（演示第 4 节）：

```text
首次构建：version_id=7a19694afcc814e8 / parent=（首版）
重放同一批：version_id=7a19694afcc814e8 / parent=7a19694afcc814e8
版本号与首次逐位相同：True
版本表：1 版（重放没有产生新版本——版本号由内容算出）
```

**"重放不产生新版本"** 值得单独说一句：版本号由
（编码器身份 + 度量 + 后端 + 内容摘要）算出，四条输入在重放里逐位相同，
于是算出的键也相同。若哪天有人把时间戳塞进版本号，
这一节立刻会多出一个"凭空多出来的版本"——而它与上一版的差别
在报告里什么也看不出来。

### 2.3 摘要要自己排序

`entries_digest(entries)` 内部**自己按 id 排序**，不依赖调用方传进来的顺序。
这一条是被冒烟自检逼出来的：最初它按入参顺序拼字符串，
于是同一份内容按不同顺序算得两个版本号，**重建一次索引就凭空多出一个版本**。

一般化的教训：**"身份"必须是内容的函数，而不是传入方式的函数。**

## 第三章：批量编码

### 3.1 `batch_size` 是成本参数，不是正确性参数

演示第 2 节，同一个 8 条文本、三种批大小：

```text
batch_size | encoded | batches | cache_hits | 提供方调用 | 命中率
        32 |       8 |       1 |          0 |          1 |    0%
         4 |       8 |       2 |          0 |          2 |    0%
         1 |       8 |       8 |          0 |          8 |    0%
```

读三行：

1. **`encoded` 恒等于 8**：批大小只改变"分几次送"，不改变"送了几条"；
2. **`batches` 才是成本**：`1` 是"一批装下 8 条"，`8` 就是逐条调用
   ——也就是 day064 的那条基线；
3. **"提供方调用"一列与 `batches` 逐位相同**：它不是估算，
   每一次 `embed_batch` 都被脚本数过。**两个数字相等，`batches` 才是一份证据。**

### 3.2 全命中时一次调用都不发

```text
第一次：8 份文本 → 命中 0 / 编码 8 | 2 批 | 命中率 0.00%
第二次：8 份文本 → 命中 8 / 编码 0 | 0 批 | 命中率 100.00%
提供方调用次数：第一次之后 2，第二次之后 2（本次新增 0）
```

`encoded=0` 且 `batches=0` 是怎么做到的（两件事一起）：

1. 缓存键 = `vector_key(provider, model, dimension, text)`，**身份进了键**，
   所以"同一个编码器 + 同一段文本"必然命中；
2. 顺序是**先查缓存、再决定要不要发调用**。反过来（先发一批空调用）
   在真实 API 上也是一次真实账单——**空批不是免费的**。

### 3.3 同一批里的重复文本只编码一次

入参 `[A, B, A]` 的处理顺序是：

```text
A → 查缓存未命中 → 待编码
B → 查缓存未命中 → 待编码
A → 查缓存仍未命中（还没写回）→ 但**批内去重**把它识别为重复 → 不重复编码
编码 [A, B] → 写回缓存 → 按入参顺序还原成 [vA, vB, vA]
```

结果是 `encoded == 2`、`cache_hits >= 1`、`vectors[0] == vectors[2]`。
第一版实现只做了"查缓存"，`cache_hits` 恒为 0——那种写法在
**同一批内有重复文本**时会把同一段文本编码两次，而症状只是"编码次数比预期多"。

### 3.4 提供方返回值的三项校验

```text
返回条数与请求条数不符   → 无法按序对应（错位的向量比缺失的向量更危险）
某条维度与 identity 不符  → 换过模型但没重建索引
某条不是有限数或零向量    → nan 让排序变任意；零向量没有方向（余弦 0/0）
```

**零向量必须在这一层拒绝**，而不是留给 day064 的 `VectorRecord`：
因为写进缓存之后，脏数据会被**长期复用**——代价从"这一次"变成"每一次"。

顺带一个诚实的边界（`describe_embedding` 只读公开属性）：

```text
provider  = type(embedding).__name__（永远拿得到）
model     = model → model_name → 回落常量，实测取到 'default'
dimension = embedding.dimension = 256
```

`CharNgramEmbedding` 的 n-gram 阶数存在私有字段里，所以它只能落到回落值。
这不是 bug，而是"**建议值而不是判决**"的兑现：提供方可以自己给出更精确的身份，
也可以通过 `BatchEncoder(identity=...)` 覆盖。**代价要写下来**——
拿不到模型名的提供方会让"换配置"这件事无法被发现。

## 第四章：批量构建、阈值换挡与三处降级

### 4.1 增量构建的省钱证据

演示第 4 节，同一个 `IndexBuilder` 连续跑两次：

```text
首次构建：incremental 构建 | 7a19694afcc814e8 ← （首版） |
          8 条 → 写入 8 / 未变 0 / 删除 0 | 编码 8（命中 0，1 批） | 复用率 0.00%

重放同一批：incremental 构建 | 7a19694afcc814e8 ← 7a19694afcc814e8 |
          8 条 → 写入 0 / 未变 8 / 删除 0 | 编码 0（命中 0，0 批） | 复用率 100.00%
          提供方调用次数：两次构建之间增加了 0 次
```

四个数字两两成对，缺一个都会让结论说不完：

```text
encoded    8 → 0     第二次一条都没算
batches    1 → 0     第二次一批都没发
written    8 → 0     第二次一条都没写库
unchanged  0 → 8     第二次 8 条全都没碰库
```

还有一处容易被误读的地方：第二次的 `cache_hits` 仍然是 `0`。

```text
增量是"不问"（差集直接判定未变 → 连缓存都不查）
缓存是"问了才省"（查了没命中 → 编码；查了命中 → 省一次）
```

所以"缓存累计命中率 0%"与"这次省下 8 次编码"**可以同时为真**。
把这两件事混成一句话，会让人误以为"缓存没生效，所以增量没用"。

### 4.2 阈值换挡：增量不是永远更省

演示第 5 节，把 `indexing_full_rebuild_threshold` 调到 `0.1`，
让 8 条里有 4 条变化（50%）：

```text
先看计划（只读：不编码、不写库、不动版本表）：
  新增 0 / 更新 4 / 删除 0 / 未变 4 | 复用率 50.00%
  changed=4 / total=8 → 比例 50.0% > 阈值 0.10

实际构建：full 构建 | a8d699e98d8a35e1 ← 7a19694afcc814e8 |
          8 条 → 写入 8 / 未变 0 / 删除 0 | 编码 4（命中 4，1 批） | 复用率 50.00%
report.note 原文：
  变更比例 50.0% 超过阈值 0.10，已从 incremental 切到 full：增量不是永远更省——
  变更比例很高时，逐条 upsert 加逐条 delete 的开销反而高于清空重写
```

三个要点：

1. **换挡换的是"怎么写库"，不是"要不要编码"**：`encoded=4` 而不是 8，
   没改的那 4 条仍然靠缓存免掉了编码。**全量重建 ≠ 重新编码**；
2. **这句话只有装配层说得了**：`planner` 看不到"写库要花多少"，
   后端也不知道"这批数据相对上一版变了多少"——两边各缺一半，
   所以判据落在 `builder` 里；
3. **阈值是严格大于才换挡**：比例正好等于阈值时不换。
   "等于就换"会让阈值这个数字的含义变成"下限"而不是"界"。

### 4.3 三处降级：一条坏数据不许毁掉整批

批量操作会把"一条坏数据"放大成"整批失败"。三处降级专门对付这件事：

```text
文本为空的记录          → 直接进 failures，不进编码
一批编码抛 EncodingError → **对该批逐条重试**，把真正失败的那些记进 failures，其余照常
一次 upsert 抛 VectorStoreError → **逐条重试**，定位到具体记录，其余照常
```

代价只在出错时付出，收益是故障被定位到**具体 id**。
降级发生时报告里会多一句 `note` 说明这次报告的编码成本偏低——
**"降级了"与"没降级"必须在报告里能区分**，否则一次降级会被读成一次正常的快照。

还有一条纪律在这里第三次出现（day061 的 `duplicate`、day064 的 `skipped`/`failed`）：

```python
except (IndexingError, VectorStoreError):   # 只有"我们认识的失败"被记进报告
    ...
                                            # 其余异常**一律向上抛**
```

### 4.4 维度护栏要在编码之前

```text
库是 8 维、编码器是 16 维 → EncodingError（**一次编码都没发生**）
```

把它放在最前面不只是"早点报错"：放在编码之后意味着**先花了一次编码的钱**，
然后才告诉用户"这两个东西不是同一套"。这是很典型的一种浪费——
错误本身不难发现，难的是它被发现得太晚。

## 第五章：清单、版本与血缘

### 5.1 清单回答"上一版长什么样"

```text
身份    version_id / parent_version            版本与血缘
口径    identity / metric / backend            "用什么建的"
内容    entries / digest                       "建了哪些"
```

`entries` 在构造时被**强制成"按 id 升序且不重复"**。这不是美化：
清单要参与版本号计算，而"同一批条目按不同顺序排列"必须得到同一个版本号。

清单还要能被**任何人重算**——`verify_version_id()` 就是这条纪律的执行器：

```text
一份被手工改过（或截断）的清单会在下一次构建时当场炸掉，
而不是被安静地当成"上一版"。
```

### 5.2 回滚必须沿血缘，不能按时间倒序

演示第 6 节：

```text
连续构建三版（每版只改一条原文）：
  #1 7a19694afcc814e8 ← （首版）
  #2 fa3967020368edc1 ← 7a19694afcc814e8
  #3 2f60e07f3a3a0170 ← fa3967020368edc1
  current=2f60e07f3a3a0170（构建成功即采纳）

现在采纳第二版：
  versions.adopt(v2) → current=fa3967020368edc1
  血缘链（从 current 回溯）：7a19694afcc814e8 → fa3967020368edc1

再回滚一步：
  versions.rollback(steps=1) → current=7a19694afcc814e8     ← 回到 v1
```

**如果按"登记顺序倒着数"**：从最新登记的 v3 往回退一步会得到 v2。
而回滚问的是"从**当前生效**的那一版往回看"——current 是 v2，
它的 `parent_version` 是 v1，所以答案是 v1。

两个答案都只是一个合法的版本号：**没有异常、没有告警，
只有下一次检索开始给出另一批结果。**

更普遍的反例是"v3 构建失败、从未被采纳"：
那时按时间倒序会回到一个**从没生效过**的版本，而它之所以没被采纳，
通常就是因为失败了。所以 `lineage()` 一步步走 `parent_version`，
遇到断裂或成环都直接报 `VersionError`，而不是"能走多远走多远"。

最后一句要写进手册：**回滚只改版本指针，不动库与数据**
（演示里回滚后库仍然是 8 条）。要真正重建某一版，请再调用一次 `build`——
回滚是运维动作，不自动重建索引。

### 5.3 为什么历史文件是 JSONL

```text
manifest_history.jsonl   每行一个清单（追加写）
current.txt              当前生效的版本（一个指针）
```

追加一条版本是**一次写一行**：中途失败只会丢掉最后一行，
不会让整个历史文件不可读。用一个大 JSON 数组的话，
"写到一半断电"会让全部历史一起坏掉——而历史恰恰是用来恢复的东西。

## 第六章：备份与保留

演示第 7 节，`keep=2` 时创建三份备份：

```text
备份 7a19694afcc814e8-flat-0001 | 1 个文件 / 43061 B | 第 1 版快照
备份 e0a7df11887477c2-flat-0002 | 1 个文件 / 42517 B | 第 2 版快照
备份 23659a8f16b66f39-flat-0003 | 1 个文件 / 41744 B | 第 3 版快照

第三次 create 之后自动 prune，被删掉的是最旧那一份：7a19694afcc814e8-flat-0001
  backups.get(被裁的那份) → None（内存表里没有了）
  (base / backup_id).is_dir() → False
list() 现在剩 2 条（新 → 旧）：
  23659a8f16b66f39-flat-0003
  e0a7df11887477c2-flat-0002
```

### 6.1 `backup_id` 里为什么没有时间

```text
backup_id = (version_id, backend, 序号) 的产物     ← 没有 created_at
```

所以同一份内容备份两次会得到 `…-0001` 与 `…-0002`：
**id 不同、`version_id` 相同**——前者是存储位置，后者才是身份。
时间戳只作为记录字段（`created_at`）给人看。

### 6.2 账本与"现在还能恢复"是两个问题

```text
create 是追加写账本（backups.jsonl）：三份各写一行 → 账本里 3 行
prune 只删目录与内存里的记录 → 内存里的 list() 只有 2 条
backups.load() 返回 2 —— **实际可用**份数（目录还在的），不是记录条数
```

**账本记的是"曾经发生过什么"，裁剪决定的是"现在还留了什么"。**
把它们混成一个数字，就会出现"账本说有三份、恢复时却说找不到"这种争执。

### 6.3 只看不动：`read_manifest`

```text
read_manifest(e0a7df11887477c2-flat-0002)：
  版本 e0a7df11887477c2 ← 7a19694afcc814e8 | 8 条 | 摘要 0bc4344627e05394
  只看不动：库仍是 8 条（读之前 8）、账本仍是 3 条（读之前 3）
```

"我想看看那一版是什么，但不想动现在的库"是一个真实且高频的需求。
没有这个入口，人就会用 `restore` 去"看一眼"——而 `restore` 会覆盖现在的库。

`restore` 的结果（演示里恢复到另一个目录）：

```text
manifest.json      1750 B
store_v2.json     40767 B
```

清单**跟着一起回去**——没有账的库，下一次增量会当它"没有上一版"而整库重算。

### 6.4 备份不是日志

`keep` 缺省取 `settings.indexing_backups_keep`，`N <= 0` 直接报错
（一个不保留任何备份的备份机制是矛盾的）。这条不是洁癖：

```text
没有保留上限的备份目录会一直长到吃满磁盘
→ 那时**正在写库的那次构建会失败**
→ 备份把主流程搞挂了，这是备份机制最讽刺的失败方式
```

还有一条更硬的：`create` 的源文件缺失时**必须报错，不许静默跳过**。
少备份一个文件而报告说成功，是备份机制最不该有的行为——
因为它的全部价值都建立在"报告可信"上。

## 第七章：一致性体检

清单出现之后，"库里有什么"与"清单说有什么"变成了**两个可以互相矛盾的事实**。
体检（`verify_index`）把它们摆在一起：

```text
missing_in_store  = ['a3e81f5c20d97b46']     清单里有、库里没有
orphan_in_store   = []                       库里有、清单没有
count_manifest    = 8
count_store       = 7
dimension_match   = True
metric_match      = True
backend_match     = True
extra_tokens      = {'manifest': 209, 'store': 178, 'diff': -31}
```

`problems` 原文（一句能直接照做的话）：

```text
清单里有 1 条记录在库里找不到：['a3e81f5c20d97b46']——上一次构建可能半途失败，
或有人手工删过记录；请先重建清单（或用这些 id 补回向量），不要在这份清单上做增量。
```

四类不一致各自的表现与处置：

| 不一致 | 症状 | 处置 |
|--------|------|------|
| 清单有、库没有 | 上一次构建半途失败 / 有人手工删过 | 先重建清单，**别在这份清单上做增量** |
| 库有、清单没有 | 有人绕过索引流程直接写了库 | 同上：它们不会被增量更新覆盖 |
| 维度不符 | 这份清单描述的是**另一个编码器**建的库 | 所有 `vector_key` 都会变，"对不上"会被伪装成"数据全变了" |
| 度量 / 后端不符 | 清单与库不是一套配置 | 换后端可以重建，但**不能与旧版共用一份清单** |

一个重要的对照（顺着这条能理解体检的边界）：

```text
拿"没有清单"的 verify() 对照一次（builder.verify() 无参 → 从库现算一份）：
  ok=True、problems=[]
```

**它必然为真**：清单是从库现算的，两者不可能对不上。
所以 `manifest_from_store` 重建出来的清单是"从现在起"的基线，
**不是历史的那一版**——"库里被人删了一条"只有拿**原来那份清单**
来对账才看得出来。

最后一个刻意的"不检查"：

```text
tokens_match = False 却不影响 ok
```

因为 `token_count` 不进内容摘要（它只用于成本估算）。
**一个过度敏感的检查项比一个不准的更麻烦**——它会让"改一个统计字段"
变成"索引需要重建"。同样的话在 day062 里说过一次（`oversized` 是报告字段，
不进 `chunk_id`）。

## 第九章：常见误区清单

**1. 以为"内容没变"就等于"向量还能用"。** 换 embedding 模型之后内容一个字节没变，
向量却全部作废。两个身份必须分开判。

**2. 把"更新 8 条"当成"数据变了 8 条"。** 换编码器身份时报告上写的就是这一行，
而一条数据都没改。**原因必须由 `plan_reason` 说出口**——四个数字里看不出来。

**3. 把时间戳写进版本号。** 同一份内容在两台机器上会得到两个版本号，
于是"重建一次"变成"凭空多一个版本"，而两个版本的差别什么也看不出来。

**4. 认为"摘要函数"不必自己排序。** 摘要必须是**内容集合**的函数，
不是"传入顺序"的函数——否则同一份内容会有两个身份。

**5. 缓存键只取文本。** 换模型之后会命中旧模型的向量，
**而这个过程不报任何错**：命中了、写入了、查询也返回了，只是"谁更近"变了。

**6. 以为空批是免费的。** `encoded == 0` 时**一次调用都不该发**：
真实 API 的一次请求就是一次账单，而且"零条的请求"在某些提供方那里是错误。

**7. 只有"查缓存"没有"批内去重"。** 同一批里重复的文本会被编码两次，
症状只是"编码次数比预期多"，看不出是缺了去重。

**8. 零向量留给下游拦。** 写进缓存之后代价从"这一次"变成"每一次"；
而且零向量方向未定义，余弦相似度对它是 0/0。

**9. 以为增量永远更省。** 变更比例高时，逐条 upsert 加逐条 delete 的开销
反而高于清空重写。这就是 `indexing_full_rebuild_threshold` 的存在理由。

**10. 以为"全量重建"等于"重新编码"。** 换挡换的是**怎么写库**：
没改的条目仍然靠缓存免掉编码（实测 `encoded=4` 而不是 8）。

**11. 批量失败就整批放弃。** 一条坏数据会毁掉整批。**批失败要逐条重试以定位**，
而这类降级必须在报告里说明（否则一次降级会被读成一次正常的快照）。

**12. 维度护栏放在编码之后。** 那意味着先花了一次编码的钱，
再告诉用户"这两个东西不是同一套"。

**13. 回滚按时间倒序。** 会回到**一个从没生效过的版本**——
而它之所以没被采纳，通常就是因为失败了。回滚必须沿血缘。

**14. 把"备份目录里的账本行数"当成"还能恢复几份"。** 账本记的是历史，
裁剪决定的是现在。`load()` 返回的是**实际可用**份数。

**15. 备份不设保留上限。** 目录会一直长到吃满磁盘，
然后**正在写库的那次构建失败**——备份把主流程搞挂了。

**16. 备份源文件缺失时静默跳过。** 少备份一个文件而报告说成功，
等于把"报告可信"这个前提毁掉了。

**17. 用 `builder.verify()` 无参的结果证明"库没问题"。** 那份清单是从库现算的，
**必然为真**。要与历史对账，必须拿原来那份清单。

**18. 因为 `tokens_match is False` 就判定索引需要重建。** `token_count` 不进摘要，
改统计字段不需要重建——过度敏感的检查项比不准的更麻烦。
