## 第 1 题

**答案：B**

解析：注册时的类型检查和重名检查，目的是让"注册了一个不合格/冲突的工具"这类错误在**注册那一刻**就抛出，而不是等 Agent 运行到 ReAct 循环中调用工具时才以 `AttributeError` 或路由错乱的形式暴露。错误暴露的位置离错误产生的位置越近，调试成本越低——这就是 Fail Fast。

A（开闭原则）确实是注册表模式的收益之一，但它是"新增工具不用改 Agent 代码"这件事体现的原则，与题目所问的"注册时校验"无关。C、D 是干扰项，单一职责说的是类的职责划分，最小知识说的是模块间的耦合度，都不是校验行为的动机。

## 第 2 题

**答案：C**

解析：依赖倒置的要点就是"高层模块和低层模块都依赖抽象"。`ReactAgent`（高层）依赖 `BaseLLM`；`OpenAICompatibleLLM`（低层/细节）通过实现 `BaseLLM` 也依赖这个抽象——这就是"倒置"的含义：细节不再是被依赖的终点，而是反过来满足抽象契约。

A 是没有抽象时的情形，正是我们要避免的；B 完全搞反了——抽象不应知道任何具体实现的存在，否则每加一个实现就要改抽象，倒置就失效了；D 错误，`OpenAICompatibleLLM` 恰恰通过继承/实现依赖着 `BaseLLM`。

## 第 3 题

**答案：B**

解析：ReAct 的标准做法是把 Observation 以 `user` 角色回填。原因是：从模型的视角看，对话只有"我说的话"（assistant）和"外部对我说的话"（user）两类；工具执行结果和用户的提问一样，都是模型外部的输入。

A 错误：`system` 是开发者设定的行为契约，通常在对话开头固定不变，把运行期产生的 Observation 塞进去会污染系统提示。C 错误：`assistant` 专用于回放模型自己的历史输出，工具结果不是模型生成的。D 在语义上确实更精确，一些新版 API 也支持 `tool` 角色（M4 的 function calling 会用到），但在我们 day006 的文本协议 ReAct 实现中用的是 `user` 角色回填。

## 第 4 题

**答案：B**

解析：普通断言只能验证返回值（结果），而 `calls` 记录器让测试可以验证**交互过程**——"第二次调用 LLM 时，消息列表里有没有包含错误 Observation？"这类问题只有记录了入参才能回答。day006 的 `test_unknown_tool_feeds_error_back` 就依赖这个机制。

A、D 是臆造的功能，`calls` 既不防重复也不做缓存；C 是本末倒置，它是给断言用的测试设施，不是日志。

## 第 5 题

**答案：错**

解析：`get()` 内部是 `self._tools.get(name)`，找不到时返回 `None` 而不是抛异常。这是有意设计：LLM 的 `Action` 输出是不可信的（模型会幻觉出不存在的工具名），"查不到"是运行时常态而非程序错误。ReAct 循环拿到 `None` 后应该把"工具不存在"的提示喂回给 LLM 让它自我修正，而不是让整个循环崩溃。

对比：day008 的 `SessionManager.get_memory()` 对未知会话抛 `KeyError`，因为会话 ID 来自我们自己代码的管理，传错 ID 是调用方的 bug，应当立即暴露。同为"注册表式查询"，设计差异来自"查不到"的含义不同。

## 第 6 题

解析：这正是今天架构的核心收益。`OpenAICompatibleLLM` 面向 OpenAI 兼容协议编写，DeepSeek、通义、Moonshot、vLLM 本地部署全都兼容该协议。`base_url` 从 `settings` 读取，`settings` 从环境变量/`.env` 读取——切换供应商是纯配置操作，`ReactAgent`、工具层、测试全部零改动。

## 第 7 题

**答案：错（不完整，因而不是"主要目的"）**

解析：省钱只是附带收益。用 Mock 的**主要**目的是让测试满足 FIRST 原则：

1. **Fast**：真实调用每次 1~10 秒网络往返，Mock 是纳秒级内存操作；
2. **Repeatable**：模型输出是概率性的，同一个输入可能得到不同表述，断言无法稳定编写；Mock 按剧本回复，跑一万次结果一致；
3. **Independent**：真实调用依赖网络、API Key、供应商可用性，任何一个出问题测试就红，测试不再独立；
4. **可控性**：你没法命令真实模型"这次故意输出格式错误的文本"来测试解析失败的兜底路径，Mock 可以。

如果只为了省钱，大可以减少测试运行频率——但测试的确定性、速度、独立性是无论如何都绕不过去的硬要求。

## 第 8 题

**参考答案**：

两个导出形式的使用场景：

- `to_schema()`（JSON Schema 字典）：面向**结构化协议**的消费方。M4 阶段迁移到 LLM 原生 Function Calling 时，API 要求以 JSON Schema 形式声明每个工具的名称、描述、参数类型，`schemas()` 批量导出后直接塞进请求的 `tools` 字段。
- `describe()`（纯文本清单）：面向**文本协议**的消费方。我们 day006 的 ReAct 实现是让 LLM 用纯文本输出 `Action: xxx`，所以 prompt 里需要一段人能读（模型也能读）的清单文本。

"工具自我描述、注册表聚合"更可靠的原因：

1. **单一事实来源**：工具的名字、描述、参数只写在工具类里一处。prompt 清单、schema 导出、路由查找全部从这一处派生，不可能出现"prompt 里说有的工具路由里没有"这种不一致。
2. **变更自动传播**：新增/删除/修改一个工具，所有下游产物（prompt、schema、路由）同步更新，不需要人去维护第二份清单。
3. **可测试**：`test_describe_contains_tool_info` 这样的测试可以自动验证"注册了的工具确实会出现在清单里"，手写清单则只能靠人肉 review。

这就是 day001"单一事实来源"思想在 Agent 层的再现。

## 第 9 题

**参考答案**：

优先级排序的理由：

1. **显式传参优先**：调用方明确表达了意图，应被尊重。典型场景是测试（传入 `api_key="sk-test"` 脱离环境污染）和多模型并存（同进程内不同实例指向不同供应商）。
2. **全局配置居中**：不传参时回落到 `settings`，享受 day001 建立的"配置与代码分离"体系——换环境只改 `.env`。
3. **兜底值垫底**：`"sk-missing"` 让对象总能构造成功，把"缺 Key"的错误推迟到真正发起请求时才暴露（OpenAI SDK 在校验 Key 为空字符串时会直接在构造时报错）。这让离线测试（只测构造）成为可能。

`or` 链的陷阱：**`or` 按"真值"判断，不只是按 `None` 判断**。如果调用方显式传入空字符串 `api_key=""`，`"" or settings.openai_api_key` 会跳过这个显式传参、回落到全局配置——调用方"故意传空"的意图被静默吞掉了。

这是否是问题取决于语义约定：在我们的场景里，空字符串 Key 本身没有意义，静默回落到全局配置反而符合直觉。但如果某个参数"空值是合法且有意义的"（比如 `base_url=""` 想表达某种特殊端点），就必须改成显式的 `x if x is not None else default` 写法。工程经验：**只有 `None` 才是"未提供"的合法信号时，`or` 链才是安全的。**

## 第 10 题

**参考答案**：

`smart_research_agent/tools/word_count.py`：

```python
"""词数统计工具."""

from __future__ import annotations

from typing import Any

from smart_research_agent.tools.base import BaseTool


class WordCountTool(BaseTool):
    """统计文本词数（按空白字符切分）."""

    @property
    def name(self) -> str:
        return "word_count"

    @property
    def description(self) -> str:
        return "统计一段文本的词数，按空白字符（空格、换行等）切分"

    @property
    def parameters(self) -> dict[str, Any]:
        return {
            "type": "object",
            "properties": {
                "text": {
                    "type": "string",
                    "description": "要统计词数的文本",
                }
            },
            "required": ["text"],
        }

    def execute(self, text: str = "", **kwargs: Any) -> str:
        return f"词数: {len(text.split())}"
```

`tests/test_word_count.py`：

```python
"""词数统计工具测试."""

from __future__ import annotations

from smart_research_agent.tools.registry import ToolRegistry
from smart_research_agent.tools.word_count import WordCountTool


class TestWordCount:
    def test_normal_text(self):
        tool = WordCountTool()
        assert tool.execute(text="hello world foo") == "词数: 3"

    def test_empty_string(self):
        tool = WordCountTool()
        assert tool.execute(text="") == "词数: 0"

    def test_whitespace_variants(self):
        tool = WordCountTool()
        # 换行、制表符同样作为切分点
        assert tool.execute(text="a\nb\tc") == "词数: 3"

    def test_register_and_discover(self):
        registry = ToolRegistry()
        registry.register(WordCountTool())
        assert registry.get("word_count") is not None
        assert "word_count" in registry.describe()
```

要点解析：

- `"".split()` 返回空列表，所以空字符串自然得到 `词数: 0`，不需要特判——`str.split()` 无参数时按任意空白切分并忽略首尾空白，正好符合需求。
- `execute(self, text: str = "", **kwargs)` 与 `CalculatorTool` 保持同一签名风格：必填参数带默认值兜底，多余参数吞掉。这让 ReAct 循环可以用统一方式调用任何工具。
- `test_register_and_discover` 验证的不只是"能注册"，更是"注册后 Agent 的自动发现链路（get + describe）对新工具生效"——这正是注册表模式的价值闭环：新工具写完后，无需修改任何已有代码即可被 Agent 发现和路由。
