# day017 习题答案：MCP Resources

## 一、选择题

**1. 答案：B**

Resource = 可读取的**数据**（URI 寻址，application-driven）；Tool = 可执行的**行为**（名称 + 参数，model-driven）；Prompt = 可参数化的**提示词模板**（user-driven）。口诀：**问"它是什么"用 Resource，问"帮我做什么"用 Tool**。A、C、D 均把"数据"与"行为"对调或错位，是对三大原语最常见的误解。

**2. 答案：C**

错误路径的完整翻译链是：服务器端处理器抛出业务异常（本项目中是 `KnowledgeNotFoundError`）→ FastMCP 捕获并映射为 JSON-RPC 错误响应（`error.code` + `error.message`）→ 客户端会话收到错误响应后还原为 `McpError` 异常抛出。因此客户端可以用 `pytest.raises(McpError, match="不存在")` 精确断言（见 `tests/test_mcp_resources.py::test_read_missing_doc_raises_mcp_error`）。A、B 违背了 JSON-RPC "result 与 error 互斥"的规则——失败绝不会伪装成一个空成功；D 则混淆了"单次请求出错"与"连接级故障"，协议设计上单请求错误不影响会话存续。

**3. 答案：C**

`id` 由客户端生成、服务器原样带回，唯一职责是**请求-响应配对**。一条连接上可并发发出多个请求，响应顺序不保证，客户端靠 `id` 把响应还给正确的等待者。A 错：`id` 不含任何身份或加密信息；B 错：版本由 `jsonrpc: "2.0"` 字段表达；D 错：JSON-RPC 不定义校验和语义，传输完整性由下层通道（管道/TCP/TLS）保证。

**4. 答案：D**

MCP 分层架构中，协议层（方法语义）与消息层（JSON-RPC 2.0）不感知传输层差异。内存传输与 stdio 承载**完全相同的 JSON-RPC 消息流**——同样的序列化、同样的握手、同样的请求/响应配对——差别仅在字节通道（进程内队列 vs 子进程管道）。这正是"用内存传输测过的行为，stdio 部署后语义不变"的依据。A、B 错：内存传输同样走完整 JSON-RPC 编解码，不跳序列化、不用 protobuf；C 错：stdio 恰恰要求同机（宿主拉起本地子进程），内存传输要求更高——同进程。

## 二、判断题

**5. 答案：错。**

URI 模板由 `list_resource_templates`（对应协议方法 `resources/templates/list`）返回，**不是** `list_resources`。后者只列出**静态注册、无参数**的具体资源（如习题 9 新增的 `research://knowledge-index`）。我们注册的两个资源都带 `{doc_id}` / `{key}` 参数，所以只出现在模板列表中，`list_resources` 对它们返回空。这也解释了为什么"枚举所有文档的具体 URI"不能只靠模板——模板告诉你"地址的形状"，不告诉你"有哪些实例"，实例清单需要服务器额外提供（习题 9 正是在补这个能力）。

**6. 答案：错。**

`notifications/resources/updated` 只携带**变更资源的 URI**，不携带新内容。这是有意的轻量设计：通知的职责是"告诉客户端本地缓存已失效"，是否重读、何时重读由客户端决定——如果客户端接下来根本用不到这份资源，就不必浪费带宽拉取全量。这与 HTTP 缓存验证中 ETag 的思想相通：先问"变没变"，变了再拉全量。另外它是 notification（无 `id`、无响应的单向消息），服务器也不要求客户端回执。

## 三、问答题

**7. 参考答案：**

若项目内包取名为 `mcp`，当解释器在项目目录中执行 `from mcp.server.fastmcp import FastMCP` 时，import 机制按搜索路径**先匹配先赢**——项目内的 `mcp/` 会先于 site-packages 中的官方 `mcp` 库被命中。于是这行代码导入的是我们自己的包，而它没有 `server.fastmcp` 子模块、更没有 `FastMCP`，报出 `ImportError: cannot import name 'FastMCP'` 或 `ModuleNotFoundError: No module named 'mcp.server'`。

这类故障阴险在**错误位置离根因很远**：出错的 import 语句看起来完全正确，受害者（resources_server.py）与肇事者（包命名）可能隔了好几层。根因是 Python 的模块命名空间是**全局扁平**的——同名包必然互相遮蔽，没有"同名但限定项目内"的隔离机制。因此凡是要用到某第三方库的领域，自建包必须主动让名。其他缓解手段（如严格使用绝对导入、控制 sys.path 顺序）都更脆弱，改名是一次性、零运行成本的根治。

**8. 参考答案：**

判断标准：**获取这个动作有没有副作用，以及驱动方是谁**（application-driven vs model-driven）。

- （a）应做成 **Resource**（正是今天的实现）。读取本地 Markdown 文件是幂等只读：读一次与读一百次结果相同，不改变任何状态；客户端可放心缓存，配合变更通知失效重读。它回答的是"它是什么"，由宿主应用决定何时读取、是否装配进上下文。
- （b）应做成 **Tool**。实时联网搜索每次执行都产生副作用（网络请求、可能计费、结果随时变化），且本质上是模型在推理中需要主动发起的行为（"帮我查"）。它不该被缓存，也不适合声明式预取——若做成 Resource，宿主的预取/缓存机制会直接造成错误结果和意外开销。

边界在于"数据长什么样"会骗人：搜索结果也可以存成文件，天气也可以读缓存。判断时永远追问一句"**读到这份数据的那个动作，本身干了什么**"。

## 四、编程题（参考实现）

**9. 参考实现：**

在 `resources_server.py` 中新增：

```python
KNOWLEDGE_INDEX_URI = "research://knowledge-index"


@app.resource(
    KNOWLEDGE_INDEX_URI,
    name="knowledge_index",
    description="知识库文档清单（所有可用 doc_id，每行一个）",
    mime_type="text/plain",
)
def knowledge_index() -> str:
    """列出 data/knowledge/ 下全部文档的 doc_id，按字典序排序."""
    return "\n".join(sorted(p.stem for p in KNOWLEDGE_DIR.glob("*.md")))
```

并在 `RESOURCE_DESCRIPTORS` 中补充：

```python
ResourceDescriptor(
    uri=KNOWLEDGE_INDEX_URI,
    name="knowledge_index",
    description="知识库文档清单",
    mime_type="text/plain",
),
```

测试（加入 `tests/test_mcp_resources.py`）：

```python
async def test_static_index_listed_in_resources(self):
    async with create_connected_server_and_client_session(app) as session:
        result = await session.list_resources()
    uris = {str(r.uri) for r in result.resources}
    assert "research://knowledge-index" in uris

async def test_read_index_lists_all_docs(self):
    async with create_connected_server_and_client_session(app) as session:
        result = await session.read_resource("research://knowledge-index")
    text = result.contents[0].text
    for doc_id in ("mcp-protocol", "rag", "react"):
        assert doc_id in text
```

要点解析：

- 无参数 URI 注册为**静态资源**，出现在 `list_resources` 而非模板列表——这正好与第 5 题的判断题互为印证。
- `p.stem` 取文件名去扩展名（`rag.md` → `rag`），`glob("*.md")` 限定只收 Markdown。
- 排序不是洁癖：`glob` 的返回顺序依赖文件系统，**排序让资源输出确定**，测试才能稳定断言，客户端缓存也才有意义。
- 这个资源补齐了模板机制的短板：模板只描述"地址形状"，索引资源给出"实例清单"，两者配合客户端才能实现完整的资源发现。

**10. 参考实现：**

```python
async def test_reread_after_content_change(self, tmp_path, monkeypatch):
    from smart_research_agent.mcp_server import resources_server

    async with create_connected_server_and_client_session(app) as session:
        first = await session.read_resource("research://knowledge/rag")
        text_a = first.contents[0].text

        # 模拟"文件被编辑"：把 KNOWLEDGE_DIR 指向临时目录，
        # 里面放一份内容不同的 rag.md
        (tmp_path / "rag.md").write_text("# RAG（已更新版本）", encoding="utf-8")
        monkeypatch.setattr(resources_server, "KNOWLEDGE_DIR", tmp_path)

        second = await session.read_resource("research://knowledge/rag")
        text_b = second.contents[0].text

    assert text_a != text_b
    assert "已更新版本" in text_b
```

解析：

- 这个测试模拟了订阅时序中的**"变更发生 → 客户端重新拉取"**这一段：第一次读取对应"缓存建立"，`monkeypatch` 换目录对应"文件被编辑"，第二次读取对应"缓存失效后的重读"。
- 真实订阅机制补上的是中间那一环：**服务器主动检测变更并推送 `notifications/resources/updated`**。本测试里"客户端何时知道该重读"是由测试作者手动安排的；生产环境中这一决定由通知触发——客户端收到通知 → 丢弃本地缓存 → 下次用到时重读。
- `monkeypatch.setattr` 打的是**模块级常量** `KNOWLEDGE_DIR`，而不是去改真实文件——这保证了测试的 Independent 与 Repeatable：真实知识库不受测试影响，测试也不受真实文件内容影响。
- 一个容易忽略的细节：第二次 `read_resource` 发生在同一个会话内。MCP 服务器本身不缓存资源内容（每次 read 都重新走处理器），所以换目录后立即可读到新内容；若未来给服务器加了缓存层，这个测试就是检验"缓存是否可被失效"的守卫。
