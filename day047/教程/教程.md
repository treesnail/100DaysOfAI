## 第二章：成本线（day043）—— 记账要记到"路径"上

**一句话本质**：成本是唯一能直接换算成钱的指标，而**可归因的账本**（按什么维度切）决定了你能不能据此做决策。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/observability/cost_tracker.py](../../day046/源码/smart-research-agent/smart_research_agent/observability/cost_tracker.py)）：

- **`UsageRecord` + `CostTracker`**：`record(prompt_tokens, completion_tokens, model, endpoint, ...)` 逐次记流水；`record_from_llm(llm, model, endpoint)` 直接读 LLM 的 `usage_log` 自动归集；`total_cost`/`total_tokens` 出总量；`breakdown(key)` 按任意键（模型 / 接口）出分组统计；`top_cost_paths(top_n)` 找**最贵的调用路径**，并并入 `report()`。
- **为什么"路径"要组合模型与接口**：单看"哪个模型贵"不够——同一个模型，`/agent/run` 的多轮 tool calling 与 `/chat` 的单轮问答成本差一个数量级。把 `model × endpoint` 组合成路径，才能回答"钱花在哪条业务线上"。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/llm/cache.py](../../day046/源码/smart-research-agent/smart_research_agent/llm/cache.py)）：

- **`SemanticCache`**：`OrderedDict` 即 LRU（`move_to_end` 刷新热度）；`get` 走**两级匹配**——先精确匹配（规范化后查键），未命中再比语义（embedding 余弦 ≥ `similarity_threshold`，默认 **0.85**）。顺序即优先级：精确命中永远优先于语义命中，因为"字面完全一样"比"语义相近"更可信。
- **`put` 不淘汰、超容量才淘汰**：更新已有键只刷新热度，只有超过 `max_size` 才从 `OrderedDict` 头部弹出最久未用项。
- **`CachedLLM`**：`BaseLLM` 的透明包装——对外接口与普通模型完全一致，内部"先查缓存、未命中才调用真实模型"，并把**省下的调用折算成美元**（`_estimate_call_cost`）单独归因。`hit_rate` 是缓存的体检指标。
- **阈值与 embedding 质量绑定**：0.85 是给神经向量的经验值；换成 `CharNgramEmbedding` 这种字面重叠型向量，同一个阈值会命中一堆"字面像但语义无关"的请求——**缓存质量的上限是 embedding 质量**。

## 第三章：合规线（day044）—— 两道门 + 一内一外的审计

**一句话本质**：安全不是"防住攻击"一件事，而是"输入侧拦恶意、输出侧防泄露、全程可审计"三条腿。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/security/](../../day046/源码/smart-research-agent/smart_research_agent/security/)）：

- **输入侧**：`PromptInjectionDetector`（day031 埋下）拦截"忽略之前指令""泄露系统提示词"等注入——在请求**进入模型之前**把关。
- **输出侧**：`ContentModerator`（day031 建立、day044 扩展）拦截"模型不小心复述了 PII"。day044 新增两类 PII：
  - **银行卡号**：16~19 位数字，与订单号/时间戳同形，因此走**两步走**——正则取候选（`BANK_CARD_PATTERN`）→ 逐候选 `_luhn_valid` 校验 → 通过才替换（`_mask_bank_cards`）。Luhn 能筛掉约 90% 的随机长数字串，这是"校验型 PII"相对"纯正则 PII"的价值。
  - **IPv4 地址**：把"每段 0~255"编码进正则（`25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d`），让 `999.999.999.999` 整体失配——**格式精确约束**而非宽松 `\d{1,3}`。
- **审计的两层**：
  - `api/middleware.py` 的 `AccessLogStore` + `AccessLogMiddleware`：记 HTTP 接入层（method / path / status_code / duration_ms / client_ip），挂在 ASGI 最外层，**404 与 500 都留痕**（`finally` 保证失败也记录）；
  - `security/audit.py` 的 `AuditLogger`：记 Agent 内部工具调用（tool_name / arguments / result / status），追加 JSONL。
  - **一外一内**：AccessLog 回答"请求层发生了什么"，AuditLogger 回答"Agent 内部做了什么"。
- **契约**：`ChatResponse`/`AgentRunResponse` 新增 `ModerationInfo(is_safe, flagged_words, pii_types)`，且**始终返回**（即使回复干净）——契约稳定性优先于省那点体积。`/agent/run` 的 `tool_calls` 刻意**不脱敏**：它是审计证据，脱敏会破坏可追溯性。

**审核与审计的边界**：审核关心"输出是否安全"（可以改文本），审计关心"证据是否完整"（不能改文本）。两者对同一段文本的处理方式相反，不能混为一谈。

## 第四章：部署线（day045）—— 先算再跑，先量再换

**一句话本质**：本地部署的价值在于**数据不出境、成本固定、可离线**；代价是**显存、运维、质量**——所以要先算（显存预算）、先量（一致性/延迟/成本）再决定。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/llm/local_runtime.py](../../day046/源码/smart-research-agent/smart_research_agent/llm/local_runtime.py)）：

- **显存 = 权重 + KV 缓存**：`bytes_per_parameter(quant)` 给出量化档位的每参数字节（fp16/bf16 = 16、int8 = 8、int4 = 4；GGUF 的 k-quant 是混合量化，工程按平均计——Q8_0 ≈ 8.5、Q5_K_M ≈ 5.5、Q4_K_M ≈ 4.5）。
- **`estimate_vram_gb(...)`**：权重项 + KV 项。KV 缓存是"长上下文真正的显存杀手"，随上下文长度与 batch 线性增长。
- **`HardwarePlan` / `plan_deployment` / `fitting_quantizations` / `max_context_tokens`**：从"我的卡有多少显存"反推"能用哪些量化档、上下文能开多长"，`fits()` 判断是否装得下、`recommendation()` 给选型建议——**把选型从"试错"变成"计算"**。
- **`OllamaRuntime`**：`list_models`/`list_running`/`is_running`/`load_model`/`unload_model`/`pull_model`——把运维动作（加载/卸载/拉取）做成可测的方法。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/llm/local_model.py](../../day046/源码/smart-research-agent/smart_research_agent/llm/local_model.py)）：

- **协议兼容胜过 SDK 封装**：Ollama（默认端口 11434，api_key 占位 "ollama"）与 vLLM（默认端口 8000，未加 `--api-key` 时不校验）都暴露 **OpenAI 兼容接口**，所以 `LocalModel` **继承 `OpenAICompatibleLLM`** 而不是从头写——`normalize_base_url` 负责把用户填的各种地址写法规范化（这是本地部署最高频的配置错误来源）。
- **`LocalModelSpec`**：把"部署事实"（backend / model_name / base_url / context_length / keep_alive）与"协议参数"（temperature 等）分开。
- **本地才需要的两件事**：`is_available(timeout)` 探活、`list_served_models()` 查清单——云端的"模型一定在"是假设，本地的"服务起没起"是事实。
- **`keep_alive` 的四种语义**：控制模型在内存里驻留多久；冷启动（首次加载）耗时是本地部署特有的一笔账。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/evaluation/local_eval.py](../../day046/源码/smart-research-agent/smart_research_agent/evaluation/local_eval.py)）：

- **`LocalModelEvaluator` 三指标**：**一致性**（`CaseResult`/`ModelRun`/`ComparisonReport`，`DEFAULT_AGREEMENT_THRESHOLD = 0.8`，平均余弦 ≥ 0.8 视为"行为基本一致"）、**延迟**、**成本**——缺一不可：便宜但答得不一样，等于没省。

**这一课的结论**：`LocalModel` 让"本地"与"云端"在 `BaseLLM` 契约下**完全同构**；正因如此，day046 才能把两者**混着用一个路由器**。

## 第五章：集成线（day046）—— 顺序即策略，把"变慢"变成事实

**一句话本质**：所有能力都有，不等于系统正确——**装配顺序本身就是策略**；而"性能有没有退化"必须变成可判定的工程事实。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/integration/pipeline.py](../../day046/源码/smart-research-agent/smart_research_agent/integration/pipeline.py)）：

- **六阶段流水线**：`guard`（输入护栏）→ `cache`（缓存）→ `generate`（生成）→ `account`（成本归因）→ `moderate`（输出审核）→ `store`（记忆写入）。**顺序即策略**：
  - 拒答时只有 `guard` 一个阶段（注入在入口就被拦，不花钱）；
  - 缓存命中时止于 `moderate`（不再调模型，但仍要过审核——**命中缓存的旧回复同样可能含 PII**）。
- **一个真实的顺序陷阱**：如果先 `store` 再 `moderate`，被缓存的"含 PII 回复"会被反复命中并反复返回——**缓存把"一次性泄漏"变成"持续性泄漏"**。所以 `moderate` 必须在 `store`/`cache` 之前，且缓存键要包含系统提示词（`cache_key(task, system_prompt)`）——系统提示词不同，回答本就该不同。
- **`StageRecord` / `PipelineResult`**：每次运行返回"答案 + 每个阶段的账"（耗时、token、是否命中、审核结果）；`total_tokens()`、`stage(name)`、`stage_names()` 让流水线**可解释**。
- **`build_hybrid_router(local, cloud, ...)`**：本地标 `capability=3, cost_per_1k=0.0`、云端标 `capability=5, cost_per_1k>0.01`，直接复用 day033 的 `CostFirstStrategy`——**不写一行 if**，简单题自然落到免费的本地模型，复杂题（复杂度 4~5）因能力不足被路由到云端；本地宕机时自动升级到云端（降级链）。
- **`IntegratedPipeline` 集成实测暴露的真实缺陷**：`AttributeError` 把请求打成 500——根因是**包装器不透传被包装对象的可观测属性**。`ModelRouter` 包装了叶子模型，但成本追踪器要按 `llm.usage_log` 归集，于是"路由后面计费断链"。修复：`router.last_used_llm` 记录最后一次实际提供服务的叶子模型，**让计费落到真正干活的叶子上**。这是一条值得记住的通用教训：**包装器必须透传"可观测性"**，否则所有依赖观测的下游都会断链。

落点（[../../day046/源码/smart-research-agent/smart_research_agent/evaluation/perf_baseline.py](../../day046/源码/smart-research-agent/smart_research_agent/evaluation/perf_baseline.py)）：

- **`measure(...)` + `PerfBaseline`**：采集可复现的度量（`TOTAL_KEY`、各阶段耗时），`save`/`load` 存档与比对。
- **`percentile(values, q)` 用最近秩法、不做插值**：小样本下插值会造出"观测不到的耗时"，而性能门禁的结论**必须能回溯到某一次真实请求**；`q=0` 取最小、`q=100` 取最大。
- **判定下限 `DEFAULT_MIN_LATENCY_MS = 5.0` / `DEFAULT_MIN_TOKENS = 1.0`**：低于这些值的基线不参与比值判定——**防抖动**是门禁能不能长期用下去的关键（小分母会把噪声放大成"严重回归"）。
- **`PerformanceGuard.compare(current)` → `BaselineComparison.ok` + `Regression`**：把"我觉得变慢了"变成"P95 延迟相比基线上升 X%，超过阈值 → 门禁不通过"。
- **`/pipeline/run` 与 `/pipeline/baseline`**：前者要答案也要账本，后者缺基线返回 **404**——沿用 day038 的错误码契约语言（合法但资源不存在 → 404）。
- **口径声明**：`PerfBaseline` 自带采集口径（`guard_from_settings`、`compare_with_file`），**没有账本就没有数字**。

## 第六章：M3 评估框架回顾 —— 每个新能力都要有一把尺子

M4 加了一堆能力，但"加得对不对"要靠 M3 建立的评估体系来回答。day046 快照里 `evaluation/` 目录就是这套尺子的全集：

| 尺子 | 模块 | 度量的对象 | 在 M4 里的用途 |
|------|------|-----------|----------------|
| 检索指标 | `metrics.py` | recall / precision / MRR / NDCG | day041 embedding 换真实向量后，指标才有意义 |
| 红队 | `redteam.py` | 攻击用例通过率、防线拦截率 | day044 的 PII/审核规则用它做加固前后对比 |
| Agent 评估 | `agent_eval.py` / `agent_harness.py` | 任务完成率 / 步数效率 / 工具正确性 | 验证 day037 的 function calling 与 day046 的流水线 |
| RAG 评估 | `rag_eval.py` / `rag_metrics.py` | 检索质量 + 答案忠实度 | day041/day043 的语义检索与缓存命中质量 |
| Prompt 评估 | `prompt_eval.py` | 提示词版本优劣 | day036 的 `PromptLibrary` 版本化回归 |
| 输出质量 | `output_eval.py` | 格式 / 完整度 | day037 的 `tool_calls` 协议校验 |
| 质量日志 | `quality_logger.py` | 线上样本留存 | 为评估提供真实语料 |
| 性能基线 | `perf_baseline.py` | 延迟 / token 分位数 | **day046 新增**，把评估从"正确性"扩展到"性能" |

**规律**：正确性评估（质量）与性能评估（速度）是两把不同的尺子。day046 之前，`evaluation/` 只管"答得对不对"；day046 补上 `perf_baseline.py` 之后，才第一次能回答"跑得快不快、有没有变慢"。**一套完整的评估体系必须同时有一把质量尺和一把性能尺。**

## 第七章：三张横切表 —— 贯穿后半段的共性设计

### 7.1 "包装而不侵入"：一以贯之

| 日 | 包装器 | 被包装对象 | 新增能力 | 为什么不用改造 |
|----|--------|-----------|---------|----------------|
| day039 | `ModelRouter` | 多个 LLM | 自动选型 + 降级 | 叶子模型对路由完全无感知 |
| day043 | `CachedLLM` | 单个 LLM | 语义缓存 | 调用方拿到的仍是 `BaseLLM` |
| day046 | `IntegratedPipeline` | 护栏/缓存/模型/审核/记忆 | 有序装配 | 六个组件各自独立可测 |

**规律**：新能力优先做成**包装器**，而不是改造被包装对象。好处有三：不改动已验证的代码（回归风险低）、可独立测试（每层都能离线跑）、可自由组合（day046 的流水线就是六个包装/组件的排列）。代价是要**透传可观测属性**——day046 的 `last_used_llm` 缺陷正是这个代价的实证。

### 7.2 失败安全方向：宁可多花钱、宁可降级跑，不可崩溃

| 场景 | 方向 |
|------|------|
| 降级链（day033/039） | **向上**（更强模型）——答错代价 > 多付一次费 |
| 本地模型宕机（day046 混合路由） | 自动升级到云端，不中断服务 |
| `default_embedding` 未配密钥（day041） | 退回 `CharNgramEmbedding` 并告警 |
| `default_llm` 未配密钥（day005） | 退回 `MockLLM`，服务照常启动 |
| URL 解析失败/远程 URL（day040） | 显式拒绝并返回业务文案，不抛异常炸掉 Agent 循环 |

**统一口径**：能退避就不崩溃；退避要记日志/告警，让"当前在降级运行"可见。

### 7.3 契约自带元信息：可观测性设计

| 日 | 契约 | 携带的元信息 |
|----|------|-------------|
| day039 | `RouteDecision` | 为什么选了哪个模型、降级链是什么 |
| day041 | `EmbeddingResponse` | `provider` + `dimension`（这批向量能否与库里已有的比） |
| day043 | `CostTracker.report()` | 按模型/接口/路径分组的花销 |
| day044 | `ModerationInfo` | 是否安全、命中了哪些敏感词/PII 类型 |
| day046 | `PipelineResult` / `PerfBaseline` | 每个阶段的账 + 采集口径 |

**规律**：单一输出（一段文本、一串向量、一次调用、一条耗时）本身没有自描述能力；契约里带上"它从哪来、什么口径、有没有成功"，下游才能判断是否可消费、可归因。这是 day032 tracing 思想在协议层的投影。

## 第八章：常见误区清单

**成本线（day043）**：

1. **"缓存命中率越高越好"** —— 命中率要与"语义阈值是否被滥用"一起看；阈值过低会把不相关请求也命中，省了钱但答错了。
2. **"语义缓存可以替代精确缓存"** —— 两级匹配的顺序不可颠倒：字面完全相同永远比语义相近更可信，精确匹配必须先跑。
3. **"按模型统计成本就够了"** —— 同一模型在不同接口上的成本差一个数量级，必须组合 `model × endpoint` 成"路径"才可归因。
4. **"同一个相似度阈值可以套所有 embedding"** —— 0.85 是给神经向量的；字面重叠型（CharNgram）用它会大面积误命中。

**合规线（day044）**：

5. **"银行卡号用正则匹配就能脱敏"** —— 它与订单号/时间戳同形，必须加 Luhn 校验才不误伤；"格式对"不等于"内容真"。
6. **"审核放在中间件里更通用"** —— 中间件拿不到响应体、无法返回审核报告；审核要放在路由函数里，结果才能随响应返回。
7. **"审核报告命中了才返回"** —— 契约字段应始终存在，客户端才能不写分支；时有时无的字段是契约不稳定。
8. **"Agent 答案脱敏了，工具轨迹也该脱敏"** —— 工具轨迹是审计证据，脱敏会破坏可追溯性；"审核"与"审计"对文本的处理诉求相反。

**部署线（day045）**：

9. **"本地模型就是省钱的"** —— 省的是按量费用，花的是显存、运维与可能的冷启动延迟；要先算（显存预算）再决定。
10. **"模型参数能塞进显存就能跑"** —— 权重只是一半，KV 缓存随上下文与 batch 线性增长，长上下文常常是真正的瓶颈。
11. **"为本地后端写一套新 SDK 客户端"** —— Ollama/vLLM 都兼容 OpenAI 协议，继承 `OpenAICompatibleLLM` 即可，重新封装只会制造第二个契约。

**集成线（day046）**：

12. **"能力都在，系统就对"** —— 装配顺序本身就是策略；`store` 早于 `moderate` 会把一次性泄漏变成持续性泄漏。
13. **"缓存键只算用户输入"** —— 系统提示词不同，回答本就该不同；缓存键必须包含它。
14. **"性能用平均值看就行"** —— 平均值掩盖长尾；要用最近秩法分位数，且不做插值（结论必须能回溯到真实请求）。
15. **"门禁阈值随便定"** —— 必须有判定下限（`DEFAULT_MIN_LATENCY_MS`/`DEFAULT_MIN_TOKENS`）防抖动，否则小分母会把噪声放大成"严重回归"。
16. **"包装器只管转发业务调用"** —— 包装器必须透传可观测属性，否则依赖观测的下游（计费、追踪）会断链——day046 的 `AttributeError` 就是这么来的。
