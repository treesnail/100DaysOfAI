## 第 1 题

**答案：D**

解析：A、B、C 是教程第一章归纳的单体 Agent 三堵墙——上下文稀释（调研噪声污染写作判断）、角色冲突（一份提示词里两种互相拉扯的行为准则）、失败不可定位（阶段边界模糊，无法针对性改进）。D"工具调用失败"是模型输出解析或工具注册问题，在单步任务里同样会发生，与"是否承担整条流水线"无关，不属于单体做长链路任务特有的问题。

## 第 2 题

**答案：C**

解析：今天三个角色都是轻量封装，各调 1 次 LLM，共 3 次。研究员升级为 ReAct 循环后，其内部平均 3 步（2 步工具调用 + 1 步 Final Answer），分析师和撰稿人不变，合计 3 + 1 + 1 = 5 次。这个题目想强化的认知是：**角色的内部实现可以独立升级，成本变化只发生在被升级的角色内部**——这正是 `work(task, context)` 接口保持稳定的意义，编排层对此毫无感知。

## 第 3 题

**答案：B**

解析：content 和 metadata 服务两类完全不同的消费者：content 会被编排器拼进下游角色的提示词，是"给 LLM 读的"；metadata 用于程序侧的过滤、统计、审计，是"给代码读的"。混在一条通道里会互相污染——下游角色的提示词里会混入机器字段，程序想取 stage 又得从自然语言里解析。A 错（token 不是设计动机）；C 错（dataclass 没有这种限制）；D 错（因果倒置）。这条双通道原则和 day010 的"提示词约束是软约束、程序校验是硬约束"一样，都是在划清**人与机器消费边界**。

## 第 4 题

**答案：错**

解析：`MultiAgentOrchestrator` 根本没有 `llm` 属性——通读 `run()` 找不到一次 LLM 调用。这是刻意的架构决策（教程 4.2 节）：流水线拓扑固定时，调度逻辑是确定性程序，顺序写死在代码里，100% 可预测、可测试。把"下一步给谁"交给 LLM 决定属于中心调度拓扑的极端形态，那是对"拓扑需要动态变化"付的灵活性税；拓扑不变，就不该交这笔税。day013 的 LangGraph 会用程序定义的图结构表达更复杂拓扑，图的节点与边依然是代码，不是模型决策。

## 第 5 题

**答案：对**

解析：角色提示词的三段式中，负向约束（"不要下结论、不要写观点"）是多 Agent 提示词区别于单体提示词的关键。单体 Agent 什么都得做，不需要"不做某事"的约束；角色化之后，相邻角色的职责天然互相渗透——研究员一旦开始写观点，就越界做了分析师的工作，下游拿到的是夹生的资料。三个角色的第 3 条约束合起来构成单向流动的数据纪律：研究员不写观点（封住向分析师的出口）、分析师不展开成文（封住向撰稿人的出口）、撰稿人不引入新事实（封住向研究员回头的出口）。

## 第 6 题

**答案：对**

解析：`MockLLM.chat` 每次弹出 `responses` 列表的第一个元素。流水线是严格串行的：研究员的 `work()` 完整返回后分析师才开始，消费顺序必然是第 1 个响应给研究员、第 2 个给分析师、第 3 个给撰稿人。共享一个 MockLLM 还能带来额外收益：`llm.calls` 汇集了全部三次调用的消息，测试可以直接断言"分析师收到的 user 消息里包含研究员的产出"这种跨角色行为。注意这个安全性**依赖串行假设**——如果未来流水线改成并行执行，共享 MockLLM 的响应分配就变得不确定，那时应给每个角色配独立的 MockLLM。

## 第 7 题

**参考答案**：

**为什么按能力拆不好**："搜索/计算/翻译"是工具视角的拆分，拆出来的不是角色而是工具调用器——它们没有独立的判断职责，只是把某个 API 包装了一层。三个问题随之而来：一是**产出物不清**，"搜索 Agent"交付什么？一堆原始网页还是整理过的资料？说不清就无法考核质量；二是**编排逻辑膨胀**，什么时候该搜索、搜索结果够不够用，这些判断没人负责，全部推回给调用方；三是**与工具层重复**，day004 的 ToolRegistry 已经管工具了，再包一层 Agent 是冗余抽象。

**产出物链好在哪里**："调研 → 分析 → 写作"中每个角色交付一个边界清晰的标准化产物（资料清单、要点列表、文章），且**每个产出物恰好是下一个角色的输入**——这条链定义了流水线的形状。随之而来的是三个结构性好处：每个角色有独立的评价标准（全/准/顺），失败可定位到具体环节；角色可按当前职责选择实现形态（轻量封装），未来独立升级（研究员接工具）不影响他人；换人换实现时只要产出物契约不变，上下游零改动。

判断尺子很简单：**能不能用一句话说清这个角色交付什么？** 说不清，就是职责边界没划对。

## 第 8 题

**参考答案**：

**优势**：显式消息在每一次交接时**主动压缩信息**。分析师只收到资料清单（看不到话题下发的原始指令噪声），撰稿人只收到要点列表（看不到全部原始资料）。这直接延续了第一章对"上下文稀释"的治疗——分工不只是架构上拆角色，更要在数据上控制每个角色"能看到什么"。共享黑板让所有 Agent 读全部历史，调研阶段几千字的原始资料会原样进入撰稿人的上下文，架构上分了工、数据上没分，稀释问题原样复发。同时显式消息天然形成审计轨迹：消息序列就是协作历史，而黑板要靠 diff 快照才能还原过程。

**代价**：**信息在交接中可能丢失**。撰稿人只看要点列表，如果分析师漏掉了资料里的关键细节，撰稿人没有任何途径找回——它看不到原始资料。这个代价的缓解手段是把质量责任压给上游：分析师的提示词要求"归纳核心要点、指出矛盾"，撰稿人的负向约束"不引入要点之外的新事实"又禁止它自行脑补——宁浅勿错。更系统的解法是 M3 阶段的质量评估：在交接处加质量门控，要点不合格打回分析师重做。

## 第 9 题

**参考答案**：

**依赖方向角度**：`Message` 是编排层的概念——sender/receiver 描述的是"谁交给谁"的路由信息，只有站在流水线之上才能谈论。如果让角色接收 `Message` 对象，角色层就反向依赖了编排层的数据结构：撰稿人要理解"sender 是 analyst 意味着什么"，研究员要知道"receiver 是我"。依赖方向从"编排器 → 角色"变成双向耦合，层次就塌了。当前设计里角色只认识两个字符串参数（`task`、`context`），对"消息""流水线"一无所知——**角色是被编排的零件，不该知道编排的存在**。

**可替换性角度**：角色接收字符串，意味着任何能产生字符串的上游都能驱动它——今天的编排器、明天的 LangGraph 节点、后天的人工输入，甚至测试里直接 `work(task="...", context="...")` 手喂数据。如果签名改成接收 `Message`，所有这些调用方都得先构造一个编排层的消息对象，测试也要 import orchestrator 模块。同样的错误在 day010 已经回避过一次：ReactAgent 收到的子任务就是一个普通字符串，它不关心是用户给的还是 Planner 拆的——**接口参数用越通用的类型，模块的适用面越宽**。

## 第 10 题

**参考实现**：

`agent/roles.py` 新增：

```python
class ReviewerAgent(BaseRoleAgent):
    """审稿人：审校初稿，输出定稿."""

    role = "reviewer"
    system_prompt = """你是一名审稿人。你的职责是审校初稿并输出定稿。

要求：
1. 检查事实一致性：初稿内容不得超出分析要点的范围
2. 检查结构完整性（标题、引言、正文、结论）与语言通顺度
3. 只输出审校后的定稿，不要输出修改过程
"""
```

流水线延长段（如 `agent/review_pipeline.py`）：

```python
"""带审校环节的四段流水线：研究 -> 分析 -> 撰稿 -> 审稿."""

from __future__ import annotations

from smart_research_agent.agent.orchestrator import MultiAgentOrchestrator
from smart_research_agent.agent.roles import ReviewerAgent


def run_with_review(
    orchestrator: MultiAgentOrchestrator, reviewer: ReviewerAgent, topic: str
) -> dict:
    """先跑三段流水线，再把初稿交给审稿人审校，返回含定稿的完整结果."""
    result = orchestrator.run(topic)
    draft = result["article"]
    orchestrator._record("writer", reviewer.name, draft, stage="submit_review")
    final = reviewer.work(task="审校初稿并输出定稿", context=draft)
    orchestrator._record(reviewer.name, "orchestrator", final, stage="final")
    result["final"] = final
    result["message_log"] = [m.to_dict() for m in orchestrator.message_log]
    return result
```

**参考测试**：

```python
def test_run_with_review_end_to_end():
    llm = MockLLM(responses=["资料", "要点", "初稿", "定稿"])
    orchestrator = MultiAgentOrchestrator(
        researcher=ResearcherAgent(llm=llm),
        analyst=AnalystAgent(llm=llm),
        writer=WriterAgent(llm=llm),
    )
    result = run_with_review(orchestrator, ReviewerAgent(llm=llm), "RAG 技术")

    assert result["final"] == "定稿"
    log = result["message_log"]
    assert len(log) == 6
    assert (log[-2]["sender"], log[-2]["receiver"]) == ("writer", "reviewer")
    assert (log[-1]["sender"], log[-1]["receiver"]) == ("reviewer", "orchestrator")
    # 审稿人收到的 user 消息包含初稿全文
    assert "初稿" in llm.calls[3][1].content
```

**解析**：

1. **为什么延长段写在外层函数而不是改进 `run()`**：三段流水线和四段流水线是两种不同的拓扑。把审校塞进 `run()` 会让编排器背上"到底有没有审稿人"的可选分支，拓扑越加越多，`run()` 变成一堆 if/else 的泥潭。外层函数的思路是**组合而非修改**：`run_with_review` 复用 `run()` 的产出，自己只负责新增的交接段。这正是开闭原则——对扩展开放，对修改关闭。day013 的 LangGraph 会给出更系统的解法：拓扑用图声明，加节点不改已有节点。

2. **为什么复用 `_record()`**：它保证追加的消息与 `run()` 内部记录的消息格式完全一致（同样的 Message 构造、同样的 metadata 结构）。如果外层函数手写 `message_log.append(...)`，两处格式将来各自漂移，审计日志的一致性就破了。

3. **注意 `result["message_log"]` 要重建**：`orchestrator.run()` 返回的 `message_log` 是返回时刻的快照（list 推导式生成的新列表），外层追加的两条消息不在其中，所以函数末尾用最新的 `orchestrator.message_log` 重新生成——这个细节漏掉的话，`len(log) == 6` 的断言会失败，它能帮你检查自己是否真正理解了"to_dict 快照 vs 活引用"的区别。

4. **审稿人的负向约束**："只输出定稿，不要输出修改过程"让产出保持机器可交接的形态——如果输出里混着"我把第二段改了……"的元评论，下游（或最终用户）拿到的就不是干净的成品。这与三角色提示词里"只输出资料清单/要点列表"是同一条纪律的延伸。
