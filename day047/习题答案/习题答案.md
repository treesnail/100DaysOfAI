# day047 课后习题：参考答案

## 第一部分：选择题

### 第 1 题（评估骨架，day025）

**答案：C**

Harness 的职责边界是"跑"，不是"写业务"——把检索、Agent 循环等业务逻辑写进 `evaluate` 会让评估代码与业务代码互相纠缠：改一处业务要改两处，而且评估结果再也无法回答"是业务变差了还是评估实现变了"。A 正确：数据集固定可复现是评估可对比的前提，且必须含边界用例（只用 happy path 验证概率系统等于自欺）。B 正确：day025 的实测就是活证——总 `pass_rate = 0.8333`，而 knowledge 组只有 **0.5**，塌方藏在总分里。D 正确：评分规则显式可审计，分数才能回溯到"哪条样本、哪条规则、哪个阈值"。

### 第 2 题（Prompt 评估，day026）

**答案：B**

权重不是按"实现难度"分的（A 错），而是按"可信度结构"分的：规则确定但粗粒度（出现含糊词就扣分，会误伤），裁判懂语义但有已知偏差（位置偏差、冗长偏好、自我偏好）。`RULE_WEIGHT = 0.4` + `JUDGE_WEIGHT = 0.6` 让语义判断略占上风、又不被单一路径支配。C 错：`TIE_THRESHOLD` 判平局，裁判解析失败的保守兜底是 `JUDGE_FALLBACK_SCORE = 3.0`，两者是不同机制。D 错：**Prompt 高分 ≠ 输出质量好**——day026 的 V2（4.80）比 V1（4.00）高，只说明"人写得更清楚"，输出质量是 day027 的对象。

### 第 3 题（输出质量与 RAG 指标，day027 / day029）

**答案：C**

`retrieval_recall` 遇空相关集返回 **1.0**（没有要求就没漏），`retrieval_precision` 遇空召回集返回 **0.0**（什么都没给就是错），`ndcg` 在 `idcg == 0` 时返回 0.0——这些边界值都是刻意选定并被测试逐条钉住的（B 把两者说反了）。A 错：格式校验（`_is_valid_json` / `_looks_like_markdown`）是纯代码判断，**能用一行代码判定的事去调模型是评估体系里最常见的成本浪费**。D 错：`ndcg` / `mrr` 度量的是**检索排序**质量，与生成忠实度是两段不同的度量（day029 明确"分段度量才能定位病灶"）。

### 第 4 题（Agent 评估与红队，day030 / day031）

**答案：D**

A 把两者说反了：`completion_rate` 是"任务是否完成"，`step_efficiency` 才是"是否绕远路"。B 错：**顺序分只统计成功轨迹**，失败轨迹本来就走错了路，把它计入等于用错误分布污染正确指标的均值。C 错：100% 只说明"当前这 16 条用例过不去"，红队的资产是**用例集在增长**，不是某个拦截率数字。D 正确：本次修复中，`injection_detector.py` 里那条写错的正则 `(一个|一个)?`（重复分支，正确写法 `(一个|一名|一位)?`）此前几乎永远匹配不上，**修掉它的收益大于新增 5 条规则**——这是红队最常见的浪费。

### 第 5 题（服务化与流式，day038 / day039）

**答案：D**

流式**只改变感知延迟（首字 TTFT），不改变内容正确性**；它不做任何逐 token 校验。A/B/C 都正确：同步阻塞代码用普通 `def`（FastAPI 自动丢线程池，硬塞 `async def` 会冻结事件循环）；Agent 持有单次任务状态所以只能注入工厂；422 / 404 / 500 是 M4 全系接口沿用的错误码契约（day040 视觉、day041 embeddings 都沿用同一语义）。

### 第 6 题（集成流水线与归因，day043 / day046）

**答案：C**

`ModelRouter` 是**包装器**：自己不产生 token、不持有回复、当然也不持有 `usage_log`，所以流水线必须先取 `getattr(self.llm, "last_used_llm", None) or self.llm` 才能把用量归因到真正干活的叶子——这正是 day046 集成时撞出 500 的那条断链的修法。A 错：`cost_usd` 是**本次请求新增**的费用（生成前后读两次 `total_cost` 取差值），累计值回答不了"哪类问题在烧钱"。B 错：审核必须在**回写缓存之前**，否则缓存里会留下明文 PII，把一次性泄漏变成持续性泄漏。D 错：模型不在价格表时应当**显式按 0 记价并告警**（本地/自建推理的常态），服务不该因为一个可观测性协作者没接好就把用户请求打成 500。

### 第 12 题

## 第三部分：填空题

### 第 13 题

**guard** → **cache** → **generate** → **account** → **moderate** → **store**；拒答路径只有 **1** 个阶段（模型完全不被调用，`llm.calls == []`）；缓存命中路径有 **3** 个阶段（跳过 **generate** 与 **account**）。

（完整句：`STAGE_ORDER = (STAGE_GUARD, STAGE_CACHE, STAGE_GENERATE, STAGE_ACCOUNT, STAGE_MODERATE, STAGE_STORE)`。三条捷径的意涵：注入命中 → 只有 `guard`，不花一次模型调用；缓存命中 → `guard → cache → moderate`，`model="cache"`、`cost_usd=0.0`；正常路径 → 全部六个阶段。仍然复核输出审核是为了契约一致——缓存里存的已是脱敏文本，重复脱敏是幂等的。）

### 第 14 题

① **completion_rate**（完成率）；② **step_efficiency**（步数效率）；③ **tool_accuracy**（工具准确性，含 precision / recall / F1 与顺序 LCS 比）。day031 的四类攻击：prompt_injection、**jailbreak**、**pii_leak**、tool_abuse。

## 第四部分：问答题

### 第 15 题（M3 与 M4 如何互相提出需求）

**（1）新能力 ⇒ 新失败形态 ⇒ 新指标。**

- **day037 的 function calling × day030 的工具评估**：day006 之前 Agent 只能靠文本协议表达工具调用，"工具用错"的表现形式混乱；day037 引入结构化 `tool_calls` 后，"点了一个不存在的工具"（`UnknownToolError`）、"参数不合 schema"（`SchemaValidationError`）、"工具执行失败"（`ToolExecutionError`）成了三类**可枚举、可判定**的失败形态——`tool_accuracy` 的 precision / recall / F1 才有精确的统计对象，顺序 LCS 才有"期望工具序列"这个参照物。
- **day039 的路由 × day046 的 `PerformanceGuard`**：在只有单一模型时，"变慢变贵"的成因简单；引入路由与降级链之后，同一个任务可能因为"路由选了更贵的模型"或"本地服务宕机导致降级到云端"而变化。于是需要 `PerfBaseline` 采集延迟/token/成本三项指标，再用"最近秩百分位 + 判定下限"把主观的"好像慢了"变成可判定的工程事实。
- 同类推理还有：day040 的多模态 ⇒ 视觉 token 计费口径（`IMAGE_TOKEN_BUDGET = 85`）成为成本指标的一部分；day044 的输出审核 ⇒ day031 的红队用例从"Agent 内部"扩展到"请求入口"；day046 的六阶段流水线 ⇒ `StageRecord` 让"慢在哪一段"成为可观测指标。

**（2）决定流水线可验证的那条纪律：契约自带元信息（可观测）。**

day046 的 `PipelineResult` / `StageRecord` 把"每个阶段做了什么决定、花了多少毫秒"随响应返回，`IntegratedPipeline` 又把 `clock` 做成可注入的——于是测试可以传入"每次读取前进固定步长"的假时钟，把耗时断言变成**确定值**：满路径 `total_ms == 13.0`（14 次时钟读取）、拒答路径 `== 3.0`（4 次）、缓存命中路径 `== 7.0`（8 次）。这三个数字本身等价于"这条路径经过 6 / 1 / 3 个阶段"，**断言耗时即断言阶段数**。反过来看：如果流水线只返回一个字符串答案，那么"顺序错了没有、急路径上有没有多插一次昂贵调用"就完全无法被自动化验证——**不可观测的东西无法被测试，不可测的东西无法被守护**。

**（3）M5 微调是 M3 与 M4 共同的下游。**

- **评测集是微调的裁判**：微调唯一的合法性来源是"在下游任务上变好了"。这个判断只能由 day025 的 `EvaluationHarness`、day030 的 `AgentEvaluator`（完成率 / 步数效率 / 工具准确性）、day031 的 `RedTeamEvaluator` 给出**可对比的数字**；没有固定评测集，"微调后感觉更聪明了"就是全部结论。day053「微调模型评估」正是把这条线接上。
- **数据工程是微调的原料**：训练语料必须有统一 schema、必须被清洗、去重、质量过滤、按来源打标并划分训练/验证集——这正是 M4 里反复出现的"序列化 + 契约 + 可追溯"经验（day038 的 `schemas.py`、day041 的 `provider`/`dimension` 元信息、day046 的 `StageRecord`）在离线数据上的投影。
- **两处"坑"**：`data/eval/agent_tasks.jsonl` 是**评估集**，它的 `mock_responses` 只保证"期望用哪些工具"，**不保证答案正确**——例如 `task-04` 的 `answer_contains` 是 `56`，而轨迹给出的 Final Answer 是 `99`；`task-05` 期望 `225` 而答案是 `150`。直接喂给 SFT 就是把错误答案学进权重，所以必须核对 `answer_contains` 并对不一致的样本打上 `unverified` 标签后剔除。`data/eval/redteam_cases.jsonl` 的"期望输出"不是答案而是**拒答**（安全对齐样本），必须与普通问答样本分开打标（`safety`），否则模型会学到"对所有问题都拒答"。**评估集不能直接当训练集——这是 day048 数据工程的第一课。**

### 第 16 题（综合编程 · 参考答案）

```python
"""day047 #16 参考答案：包装器用量透传的完整验证（离线可跑，基于 day048 快照）."""

from smart_research_agent.integration.pipeline import IntegratedPipeline
from smart_research_agent.llm.base import Message
from smart_research_agent.llm.cache import CachedLLM, SemanticCache
from smart_research_agent.llm.embedding import CharNgramEmbedding
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.llm.router import ModelRouter, ModelSpec
from smart_research_agent.observability.cost_tracker import CostTracker
from smart_research_agent.observability.tracing import Tracer, _TimedLLMProxy

PROMPT = [Message(role="user", content="什么是语义缓存")]

# 1. 叶子可归因
leaf = MockLLM(responses=["叶子回答"])
leaf.chat(PROMPT)
tracker = CostTracker()
assert tracker.record_from_llm(leaf, model="mock-model") == 1
assert tracker.total_tokens > 0
print(f"[1] 叶子可归因        -> 登记 1 条，total_tokens={tracker.total_tokens}")

# 2. 缓存包装器透传叶子（day048 起有 last_used_llm；day046 上此处应断言 AttributeError）
inner = MockLLM(responses=["缓存回答"])
cached = CachedLLM(inner, SemanticCache(embedding=CharNgramEmbedding()), model="gpt-4o-mini")
assert cached.last_used_llm is inner
assert hasattr(cached.last_used_llm, "usage_log") is True
print("[2] CachedLLM 透传     -> cached.last_used_llm is inner -> True，叶子持有 usage_log")

# 3. 包装器透传到路由的叶子
route_leaf = MockLLM(responses=["路由叶子回答"])
router = ModelRouter([ModelSpec(name="mock-model", llm=route_leaf, capability=5, cost_per_1k=0.0)])
router.chat(PROMPT)
assert router.last_used_llm is route_leaf
router_tracker = CostTracker()
assert router_tracker.record_from_llm(router.last_used_llm, model="mock-model") == 1
print("[3] ModelRouter 归因   -> 登记 1 条（落到真正干活的叶子）")

# 4. 追踪代理天然透传（__getattr__ 全量转发，无需自己声明）
tracer = Tracer()
with tracer.start_trace("verify") as ctx:
    proxy = _TimedLLMProxy(MockLLM(responses=["代理回答"]), ctx)
    assert hasattr(proxy, "usage_log") is True
    proxy.chat(PROMPT)
    proxy_tracker = CostTracker()
    assert proxy_tracker.record_from_llm(proxy, model="mock-model") == 1
print("[4] _TimedLLMProxy     -> __getattr__ 透传，usage_log 可直接归因")

# 5. 流水线端到端：缓存包装器 + 计费，命中路径不产生用量
pipeline_leaf = MockLLM(responses=["流水线回答"])
cache = SemanticCache(embedding=CharNgramEmbedding())
pipe = IntegratedPipeline(
    llm=CachedLLM(pipeline_leaf, cache, model="gpt-4o-mini"),
    cache=cache,
    tracker=CostTracker(),
)
first = pipe.run("什么是语义缓存")
second = pipe.run("什么是语义缓存")
assert len(pipeline_leaf.calls) == 1, "缓存命中不应再次调用底层模型"
assert second.cached is True and second.model == "cache" and second.cost_usd == 0.0
print(
    f"[5] 流水线端到端       -> 首次 model={first.model} cost=${first.cost_usd:.8f} "
    f"tokens={first.total_tokens}；二次 cached={second.cached} model={second.model} "
    f"cost=${second.cost_usd}；底层调用次数={len(pipeline_leaf.calls)}"
)

print("\n全部断言通过")
```

**实测输出**（本机运行，`python day047_answer16.py`）：

```text
[1] 叶子可归因        -> 登记 1 条，total_tokens=2
[2] CachedLLM 透传     -> cached.last_used_llm is inner -> True，叶子持有 usage_log
[3] ModelRouter 归因   -> 登记 1 条（落到真正干活的叶子）
[4] _TimedLLMProxy     -> __getattr__ 透传，usage_log 可直接归因
[5] 流水线端到端       -> 首次 model=gpt-4o-mini cost=$0.00000075 tokens=2；二次 cached=True model=cache cost=$0.0；底层调用次数=1

全部断言通过
```

**几处必须理解的细节**：

1. **第 2 步在 day046 快照上会失败**（`AttributeError: 'CachedLLM' object has no attribute 'last_used_llm'`），这正是 day047 核对出的遗留缺陷；day048 的快照用三行属性把它补上。**同一个测试在两个快照上的一红一绿，就是这条工单"改没改、改对了没有"的全部证据。**
2. **第 5 步的 `tokens=2` 才是关键断言**。`_account` 归因的是 `CachedLLM.last_used_llm` 暴露的叶子，所以首次请求能拿到真实的 `usage_log` 增量（`mock-model` 价格表里是 0 单价，故 `cost` 极小但不为 0 之外的语义）。修复前，此处会退化成"打一条 `不提供 usage_log` 告警 + 记 0"。
3. **命中路径的 `cost_usd == 0.0` 不是靠特判拿到的**，而是因为命中时根本没有新的 `usage_log` 条目，差值天然为 0——**透传属性的修法没有为缓存路径引入任何额外分支**，这是"最小且语义正确"的判据。
4. 若把第 5 步的任务换成两次不同的问题（例如第二次问"语义缓存怎么工作"），`CharNgramEmbedding` 的字面重叠度不足可能不命中，`cached` 会是 `False`——**语义缓存的命中与否取决于阈值（缺省 0.85）与 embedding 的字面/语义重叠**，这也解释了为什么缓存必须先把系统提示词并入缓存键，否则"换个 system prompt 命中旧答案"比不命中危险得多。
