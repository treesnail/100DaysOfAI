## 第一部分：选择题

### 第 1 题

**答案：C**

解析：依赖分离的核心是"谁需要就装谁"。`pip install .` 只装 `dependencies`（pydantic 等运行时必需），`pip install -e ".[dev]"` 才额外装 pytest、ruff 等开发工具。A 错在两者安装时机完全不同；B 与事实相反；D 是对 dev（development）的望文生义。这个划分让生产镜像更小、攻击面更窄、CI 流水线各阶段只装所需。

### 第 2 题

**答案：B**

解析：Fail Fast 指错误暴露的时间点尽可能靠前。`Settings()` 在模块导入/程序启动时就解析环境变量并做类型校验：`DEBUG=ture` 这种拼写错误会在启动瞬间报 ValidationError，而不是三天后某个分支读到错误配置引发诡异行为。A 描述的是崩溃不是校验；C 与本概念无关；D 恰好是反例（静默兜底会掩盖配置缺失）。

### 第 3 题

**答案：C**

解析：分支只是一个指向 commit 的指针文件（约 41 字节的哈希），创建分支 = 写一个指针 + 移动 HEAD，O(1) 完成，不复制任何文件。A、B、D 都是 Git 快照模型与内容寻址的正确推论：未变化的文件在新 tree 里复用旧 blob；commit ID 由内容哈希决定，内容变则 ID 变。

### 第 4 题

**答案：B**

解析：Docker 每条指令生成一个只读层并缓存；某层输入变化后，其后所有层的缓存全部失效。`pip install` 是构建中最慢的一步，放在源码 COPY 之前，意味着改代码只让"源码层"重建，依赖层命中缓存秒级完成。A 与缓存机制无关；C 因果倒置（COPY requirements.txt 本来就在 install 前）；D 不存在这种强制要求，这是工程优化而非规定。

### 第 5 题

**答案：C**

解析：ReAct 不改变模型本身，它是一种"外部编排"：SYSTEM_PROMPT 约定输出格式，`ReactAgent.run()` 的 Python for 循环负责驱动——每步调一次 LLM、解析输出、执行工具、把 Observation 作为 user 消息回填。A 错，任何够强的 LLM 都能套 ReAct；B 错，循环控制权在代码手里，LLM 只是每步被询问一次（停止条件是代码检查到 `Final Answer` 或步数耗尽）；D 错，Observation 是工具的真实执行结果，由代码回填，不由 LLM 生成——这正是 ReAct 对抗幻觉的关键。

### 第 6 题

**答案：B**

解析：工具的输入本质上是 LLM 生成的不可信文本。`eval("__import__('os').system('...')")` 就是任意代码执行。AST 白名单的思路是"只放行明确允许的节点类型"（数字常量、六种二元运算、两种一元运算），函数调用节点（`ast.Call`）根本不在白名单内，注入代码在求值时直接报"不支持的表达式"。A、C、D 都不是安全动机；顺带记住对应原则：黑名单禁不完，白名单才可枚举、可验证。

## 第二部分：判断题

### 第 7 题

**答案：错**

解析：行覆盖 100% 只说明每一行代码被执行过，不说明所有分支路径被走过。例如：

```python
def safe_divide(a, b):
    if b == 0:
        raise ValueError("b 不能为 0")
    return a / b
```

只测 `safe_divide(4, 2)`，两行代码都执行了（行覆盖 100%），但 `b == 0` 为真的分支从未走过（分支覆盖 50%）。这就是项目里 `pyproject.toml` 配置 `branch = true` 开启分支覆盖率的原因。另外还要记住：覆盖率 ≠ 测试质量，只调用不断言的测试也能刷高覆盖率。

### 第 8 题

**答案：错**

解析：rebase 会重写提交的哈希 ID——相当于销毁旧提交、创建内容相同但 ID 不同的新提交。远程仓库里存的是旧 ID，本地是新 ID，push 被拒绝后只能 `--force` 强推；任何基于旧历史工作的人都会历史错乱。黄金法则：**只在本地未推送的分支上 rebase，已共享的历史用 merge。**

### 第 9 题

**答案：错**

解析：看 `_execute_tool` 的实现：工具不存在时返回字符串 `f"错误：不存在名为 {step.action} 的工具"`；工具执行抛异常时被 try/except 捕获，记 `logger.warning` 后返回 `f"工具执行失败: {exc}"`。两种错误都作为 Observation 文本回填给 LLM，给它自我修正的机会，循环继续。测试 `test_unknown_tool_feeds_error_back` 锁定的就是这个行为。这是"错误走 Observation 通道"的容错设计，不是崩溃式设计。

### 第 10 题

**答案：对**

解析：这正是 `MockLLM.chat()` 的全部行为：先把 messages 追加到 `self.calls`（供测试断言时序行为，比如"第二次调用时消息里有没有错误 Observation"），然后 `_responses` 非空就 `pop(0)` 按序返回脚本，脚本耗尽就返回 `_default`。这三个特性（确定性输出、可预测兜底、调用记录）共同支撑了本周所有离线 Agent 测试。

## 第三部分：填空题

### 第 11 题

**答案**：

```text
Thought: 需要计算 1024 乘以 3 的结果（任何合理的分析文字均可）
Action: calculator
Action Input: 1024 * 3
```

（4）**Final Answer**

解析：ReAct 单步输出的合法形态只有两种——继续行动（Thought + Action + Action Input）或终止循环（Thought + Final Answer）。三个字段名必须逐字准确，因为 `parser.py` 用正则 `Action:`、`Action Input:`、`Final Answer:` 做字面匹配，写成 `Actions:` 或 `ActionInput:` 都会解析失败。

### 第 12 题

**答案**：（1）**Message**　（2）**str**　（3）**依赖倒置**（Dependency Inversion Principle）

解析：`Message` 是 `llm/base.py` 中定义的 dataclass（role + content + `to_dict()`）；`chat()` 返回模型文本回复即 `str`。构造函数接收抽象基类 `BaseLLM` 而非具体实现，意味着 Agent 层不依赖"OpenAI"这个细节，细节（MockLLM / OpenAICompatibleLLM）反过来依赖抽象——这正是依赖倒置。直接收益：测试注入 MockLLM，生产注入 OpenAICompatibleLLM，同一套 ReAct 循环零修改跑两种环境。

### 第 13 题

**答案**：（1）**TypeError**　（2）**ValueError**　（3）**describe**

解析：两道防线都是 Fail Fast 的体现——非 `BaseTool` 实例抛 `TypeError("只能注册 BaseTool 的实例")`，重名抛 `ValueError(f"工具重复注册: {tool.name}")`，把配置错误拦在启动阶段。`describe()` 生成 `- name: description` 形式的清单文本，被 `SYSTEM_PROMPT.format(tools=...)` 拼进系统提示词——注册新工具后 LLM 的"武器清单"自动更新，prompt 无需手改。

## 第四部分：问答题

### 第 14 题

**参考答案**：

一次迭代经过四步：

1. **解析**：`parse_react_output(raw)` 把 LLM 的自由文本用正则解析成结构化 `ReActStep`（thought / action / action_input / final_answer），并追加到 `self.history`。若解析出 `final_answer`，循环正常终止并直接返回。
2. **工具执行**：`_execute_tool(step)` 用 `step.action` 到注册表查工具，按 `parameters.required` 的第一个键组装 kwargs 执行；工具不存在或执行异常都会变成错误字符串，不抛异常。
3. **Observation 回填**：`messages.append(Message(role="user", content=f"Observation: {observation}"))`——把工具结果伪装成一条 user 消息喂回。
4. **assistant 消息回填**：`messages.append(Message(role="assistant", content=raw))`——把 LLM 这一步的原始输出也记入对话。

两个回填缺一不可的原因：

- LLM 本身是**无状态**的，"多轮对话"的错觉完全靠每次调用时重放完整 messages 实现。
- 缺了 assistant 回填：下一轮 LLM 看不到自己上一步输出了什么 Thought/Action，推理链条断裂——它不知道刚才决定调用 calculator，可能重复同样的调用或直接跑题。
- 缺了 Observation 回填：LLM 永远拿不到工具结果，下一步只能凭空编造答案，ReAct 对抗幻觉的意义完全丧失。

一句话：**assistant 消息保住"它想过什么"，Observation 消息补上"它查到了什么"，两者合起来才构成下一步推理的完整上下文。**

### 第 15 题

**参考答案**：

1. 用 MockLLM 的理由（对照 FIRST 原则）：

   - **Fast（快）**：真实 API 调用每次数百毫秒到数秒，测试套件会慢到没人愿意跑；MockLLM 是纯内存操作，毫秒级。
   - **Repeatable（可重复）**：真实 LLM 输出不确定，同样的输入可能这次解析成功下次失败，测试时红时绿（flaky）；MockLLM 脚本化输出，任何机器、任何时间结果一致。
   - **Independent（独立）**：真实调用依赖网络、API Key、账户余额、服务商可用性——任何一个缺失测试就无法运行；MockLLM 零外部依赖。
   - （补充）还有成本：每次跑测试都烧 token 费用，CI 里跑几百次显然不可接受。

2. 验证请求组装逻辑又不发真实请求的做法：把网络边界替换掉，保留组装代码。具体可以用 `unittest.mock` 或 monkeypatch 替换 OpenAI client 的 `chat.completions.create`，捕获传进去的参数：

   ```python
   from unittest.mock import MagicMock

   from smart_research_agent.llm.base import Message
   from smart_research_agent.llm.openai_compatible import OpenAICompatibleLLM

   def test_request_assembly(monkeypatch):
       fake_create = MagicMock()
       fake_create.return_value.choices[0].message.content = "ok"
       monkeypatch.setattr(
           "openai.resources.chat.completions.Completions.create", fake_create
       )

       llm = OpenAICompatibleLLM(api_key="sk-test", model="test-model")
       result = llm.chat([Message(role="user", content="你好")], temperature=0.3)

       assert result == "ok"
       kwargs = fake_create.call_args.kwargs
       assert kwargs["model"] == "test-model"
       assert kwargs["messages"] == [{"role": "user", "content": "你好"}]
       assert kwargs["temperature"] == 0.3
   ```

   要点：mock 的是**网络边界**（SDK 方法），不是自己写的组装逻辑——这样 `to_dict()` 转换、模型名与温度传递都被真实执行并断言到了。

### 第 16 题

**参考答案**：

`smart_research_agent/tools/word_count.py`（练习用，不进主线快照）：

```python
"""单词计数工具：按空白字符统计文本中的单词数."""

from __future__ import annotations

from typing import Any

from smart_research_agent.tools.base import BaseTool


class WordCountTool(BaseTool):
    """统计文本单词数的工具."""

    @property
    def name(self) -> str:
        return "word_count"

    @property
    def description(self) -> str:
        return "统计一段文本的单词数量（按空白字符切分）"

    @property
    def parameters(self) -> dict[str, Any]:
        return {
            "type": "object",
            "properties": {
                "text": {
                    "type": "string",
                    "description": "要统计的文本",
                }
            },
            "required": ["text"],
        }

    def execute(self, text: str = "", **kwargs: Any) -> str:
        return str(len(text.split()))
```

`tests/test_word_count.py`：

```python
"""WordCountTool 测试."""

from __future__ import annotations

from smart_research_agent.tools.word_count import WordCountTool


class TestWordCount:
    def test_normal_sentence(self):
        tool = WordCountTool()
        assert tool.execute(text="the quick brown fox") == "4"

    def test_empty_and_blank_text(self):
        tool = WordCountTool()
        assert tool.execute(text="") == "0"
        assert tool.execute(text="   \n\t  ") == "0"

    def test_consecutive_whitespace(self):
        tool = WordCountTool()
        # split() 无参调用会忽略连续空白与首尾空白
        assert tool.execute(text="hello   world\n again ") == "3"

    def test_schema_export(self):
        schema = WordCountTool().to_schema()
        assert schema["name"] == "word_count"
        assert "text" in schema["parameters"]["required"]
```

要点解析：

- `str.split()` 不带参数时按任意空白字符（空格、换行、tab）切分，且自动合并连续空白、忽略首尾空白——这正好一并解决了空字符串（`"".split()` 得 `[]`）和连续空格两个边界，无需特判。
- `execute` 的返回值类型必须是 `str`（`BaseTool` 契约），所以用 `str(len(...))` 包一层。
- `description` 和 `parameters` 是写给 LLM 看的接口文档，语义越明确，LLM 越可能正确调用——不要把它们当形式主义。
- 默认参数 `text: str = ""` 与 day006 `_execute_tool` 的组装方式兼容：注册表会按 `required` 的第一个键把 `action_input` 传成 `text=...`。

### 第 17 题

**参考答案**：

```python
"""综合练习：MockLLM 驱动完整 ReAct 循环（离线）."""

from __future__ import annotations

from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.llm.base import Message
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.tools.calculator import CalculatorTool
from smart_research_agent.tools.registry import ToolRegistry


def test_comprehensive_react_loop():
    # 1. 组装注册表与 Agent
    registry = ToolRegistry()
    registry.register(CalculatorTool())
    llm = MockLLM(
        responses=[
            # 第一步：决定调用计算器
            "Thought: 需要先算 (12 + 8) * 5\n"
            "Action: calculator\n"
            "Action Input: (12 + 8) * 5",
            # 第二步：根据 Observation 给出最终答案
            "Thought: 已得到计算结果 100\n"
            "Final Answer: (12 + 8) * 5 的结果是 100",
        ]
    )
    agent = ReactAgent(llm=llm, registry=registry, max_steps=5)

    # 2. 运行
    answer = agent.run("计算 (12 + 8) * 5")

    # 3. 断言最终答案
    assert "100" in answer

    # 4. 断言历史轨迹
    assert len(agent.history) == 2
    assert agent.history[0].action == "calculator"
    assert agent.history[1].final_answer is not None

    # 5. 断言第二次调用 LLM 时消息中包含 Observation
    second_call: list[Message] = llm.calls[1]
    assert any("Observation: 100" in m.content for m in second_call)
```

要点解析：

- Action Input 写 `(12 + 8) * 5` 时，AST 求值结果是整数 `100`，`str(100)` 即 `"100"`，所以 Observation 文本精确为 `Observation: 100`。如果写成 `12.0 + 8`，结果会是 `20.0`，最终 `"100.0"`——本题想提醒你：**Observation 的字符串形式取决于表达式类型**，断言前先想清楚求值结果。
- `(12 + 8) * 5` 涉及括号与混合运算，正好验证了 CalculatorTool 的 AST 递归求值（先算括号内 BinOp，再算外层 Mult）。
- `llm.calls[1]` 是第二次调用时的完整 messages：system + user（任务）+ assistant（第一步原始输出）+ user（Observation）——共 4 条。可以自己加一条 `assert len(second_call) == 4` 验证对回填机制的理解。
- 整个测试离线、确定性、毫秒级——这就是 MockLLM + 依赖倒置架构的回报。

### 第 18 题

**参考答案**：

```python
"""parse_react_output 边界情况测试."""

from __future__ import annotations

import pytest

from smart_research_agent.agent.parser import ReActParseError, parse_react_output


class TestParserEdgeCases:
    def test_multiline_thought(self):
        text = "Thought: 先分析任务\n再决定用工具\nAction: calculator\nAction Input: 1+1"
        step = parse_react_output(text)
        assert "先分析任务" in step.thought
        assert "再决定用工具" in step.thought

    def test_final_answer_strips_trailing_whitespace(self):
        text = "Thought: 完成\nFinal Answer: 42\n\n"
        step = parse_react_output(text)
        assert step.final_answer == "42"

    def test_action_without_input_raises(self):
        with pytest.raises(ReActParseError, match="Action"):
            parse_react_output("Thought: 想做点什么\nAction: calculator")

    def test_multiline_action_input(self):
        text = "Thought: 输入较长\nAction: calculator\nAction Input: (1 +\n2)"
        step = parse_react_output(text)
        assert step.action_input == "(1 +\n2)"

    def test_final_answer_takes_precedence(self):
        text = (
            "Thought: 已有答案\n"
            "Action: calculator\n"
            "Action Input: 1+1\n"
            "Final Answer: 42"
        )
        step = parse_react_output(text)
        assert step.final_answer == "42"
        assert step.action is None
```

要点解析：

1. **多行 Thought**：`(?=\n(?:Action|Final Answer):|\Z)` 这个前瞻断言让 Thought 可以跨行，直到遇到下一个字段名或文本结尾。
2. **尾部空白**：`Final Answer:\s*(.+?)\s*\Z` 中 `\s*\Z` 会吃掉末尾所有空白，再经 `.strip()` 双重保险。
3. **缺 Action Input**：解析器要求 Action 与 Action Input 成对出现，缺任一抛 `ReActParseError("缺少 Action 或 Action Input 字段")`，match 到 "Action" 即通过。
4. **多行 Action Input**：与 Thought 同理，`re.S` 让 `.` 匹配换行，前瞻断言在文本结尾 `\Z` 处停止，两行都被捕获。
5. **Final Answer 优先**：看 `parse_react_output` 的控制流——先查 `_PATTERN_FINAL`，命中就**立即 return**，根本不再解析 Action 字段。所以同时包含两者时按"终止形态"处理，Action 被忽略。这是有意的优先级设计：Final Answer 意味着"信息已足够"，继续执行工具没有意义。（注意：这成立的前提是 Final Answer 出现在文本末尾且其后无其他字段——`\s*\Z` 锚定了结尾。）
