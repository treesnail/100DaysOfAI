## 今日目标

day066 回答了"给一句话，取回哪几条、为什么是这几条"，day067 回答了"两路一起答，每一条是哪一路顶上来的"。但那两天的排序依据**自始至终只有一个**：分数。而分数来自**双塔**——查询与文档是**分开**编码的。

今天补上最后那一段：这一批候选里，**哪一条真的最相关**。三个问题：

1. **为什么双塔排不准**：文档侧可以预计算（这是它能扫百万条的原因），代价是什么？把这个代价说清楚，才能理解为什么工业界的标准姿势是"两段式"而不是"换个更好的编码器"。
2. **重排要付多少钱**：交叉编码器对 N 篇文档是 N 次前向推理，不是 N 次点积。于是"只对前 N 条打分"不是优化技巧，而是**这条链路能不能用**的前提——而它带来一个必须写进报告的坏消息。
3. **怎么知道它真的有用**：`recall@k` / `RR` / `nDCG@k` 三条指标，与一组带金标准的探针。判据不是"感觉排得更好"，而是同一份名单在重排前后的三个数字。

最终产出 `retrieval/rerank.py`（重排器、窗口纪律、两种模式、三条指标、`measure_lift`），以及两条流水线上各一个插入点：单路的**第 6.5 步**与混合的**第 10.5 步**。

## 第一章：第一阶段为什么排不准

### 1.1 可检验的定位

先把两段式的分工写成两份"擅长/不擅长"，因为本课的第一条结论就藏在这两份清单里：

```text
双塔（bi-encoder）        查询 → 向量 ┐
                         文档 → 向量 ┘ → 点积       文档侧可预计算，但两两不相见
交叉编码器（cross-encoder） [CLS] 查询 [SEP] 文档 → transformer → 相关性 logit
                                                  两两一起过模型：更准，也贵得多
```

"文档侧可预计算"这一句是双塔的全部价值所在：一篇文档的向量在**入库时**就算好了，检索时只算查询那一侧，然后做 N 次点积。代价写在另一半里——**查询与文档从来没有见过面**。两边各自被压成一个点，相似度只是两个点的夹角。这个夹角能表达"主题像不像"，但它表达不了"这段文字是不是在回答这个问题"。

### 1.2 一个不用跑代码就能理解的例子

我们不举抽象的例子，用本课演示脚本里那份 12 条的小库（`scripts/rerank_demo.py` 第 1 节，输出在 `outputs/rerank_demo.txt`）：

```text
查询 'ERR-2043'
#0  d-01  score=+1.000000 | 把一句话映射到低维空间的向量，越近表示意思越像。
#1  d-04  score=+0.960000 | 一次全量重建索引大约 12 万条记录，按每条 320 token …
#2  d-02  score=+0.800000 | 语义缓存用分位数标定阈值，换编码器必须重新标定。
#3  d-03  score=+0.600000 | 召回深度按三倍过取，阈值在检索层落刀。
#4  d-11  score=+0.480000 | ERR-2043 这个编号既是整句包含，又只隔着一个空格，覆盖与整…
#5  d-12  score=+0.360000 | 排查 ERR-2043 的完整顺序：先确认编码器版本，再确认清单里…
#6  d-05  score=+0.000000 | ERR-2043 表示向量维度不一致，先重建索引再重试。
```

读这份名单要带着一个问题：**用户查的是一个报错编号，为什么第 1 名是一条讲"向量是什么"的？**

因为 `ERR-2043` 这个查询文本被编码器压成了一个点，而 `d-01` 恰好讲的是向量空间的话题，夹角最小。至于"这段文字里到底有没有出现 `ERR-2043` 这个编号"——点积**问不出来**，那个信息在编码时就丢掉了。

> 思考题：day067 的关键词路（BM25）明明能精确匹配 `ERR-2043`，为什么它在这里没救回来？提示：看第 7 名往后的分数与 day067 的 `min_score` 语义。

这里必须紧跟着一条**反面说明**，否则本课会被读成"重排是万能的"：

```text
重排只能改**次序**，不能改**名单**。
上面这份名单里，一条含 ERR-2043 的记录都在（第 4、5、6 名），
所以重排有东西可救；如果第一阶段压根没把它们召回，重排看到的就是
一份"全都不相关"的名单——它最诚实的输出只能是"重排后次序不变"。
```

**重排的收益上限由召回率决定**：召回漏掉的东西，再怎么重排也不会出现。这是两段式的分工纪律，也解释了为什么 day071 的 RAG 评估要把"召回"与"排序"分开量。

### 1.3 实测：同一份名单，两个次序

`scripts/rerank_demo.py` 第 1 节把两列并排打印出来（`top_n=20`，因此 12 条全在窗口内）：

```text
  重排之后（mode='replace'，窗口 top_n=20，打分 12 条）：
      #0 d-11 rerank=0.9167 | stage1 #4 → #0（移动 +4）
      #1 d-05 rerank=0.9167 | stage1 #6 → #1（移动 +5）
      #2 d-12 rerank=0.8810 | stage1 #5 → #2（移动 +3）
      #3 d-01 rerank=0.1250 | stage1 #0 → #3（移动 -3）
      #4 d-04 rerank=0.1250 | stage1 #1 → #4（移动 -3）
      #5 d-02 rerank=0.1250 | stage1 #2 → #5（移动 -3）
      #6 d-03 rerank=0.1250 | stage1 #3 → #6（移动 -3）
      #7 d-06 rerank=0.1250 | stage1 #7 → #7（移动 +0）
      ...

  两份名单逐位相同：False；名次真的变了的记录（按**新**名次）：['d-11', 'd-05', 'd-12', 'd-01', 'd-04', 'd-02', 'd-03']
  第一名：第一阶段 d-01 → 重排之后 d-11
```

三条读法：

1. **原名次与现名次各留一份证据**。`stage1 #4 → #0（移动 +4）` 里的 `stage1_rank` 是**新字段**，`moved` 是它的派生量。只报"重排后的次序"，读者无法知道"它原来在哪"——而"重排把谁动了"正是判断它有没有用的第一手材料。
2. **改动集中在少数几条**。名次真的变了的只有 7 条，`d-06` 到 `d-10` 五条原封不动（它们的分数一样、输入位置也一样，第二键 `stage1_rank` 保住了原序）。
3. **`d-11` 与 `d-05` 的重排分逐位相同（0.9166666666666666）**，次序由第二键决定。这一对精确并列是第三章与第六章的素材，不是打印误差。

## 第二章：交叉编码器 —— 把查询与文档一起读

### 2.1 真实实现长什么样

```text
[CLS] 查询 [SEP] 文档 [SEP] → transformer → 取 [CLS] 位置的相关性 logit → 分数
```

关键在"拼起来一起过模型"：查询的每一个词元都能在注意力里直接看到文档的每一个词元，因此"这段文字是不是在回答这个问题"是可表达的。主流实现是 bge-reranker、ms-marco-MiniLM 这一类模型，用法是一对文本进、一个分数出。

**它贵在哪里**：双塔对 N 篇文档是 N 次点积（可批量、可在索引里做、文档侧可预计算）；交叉编码器是 **N 次前向推理**——每一对都要把两个文本拼起来跑一遍 transformer。这个差距不是常数倍数，而是"能不能扫百万条"的量级差。所以两段式不是选择，而是唯一可行的形状：

```text
第一阶段（召回）  双塔 / BM25 / 融合 → 几十~几百条候选    追求"别漏"，允许粗糙
第二阶段（重排）  交叉编码器只对**前 N 条**打分 → 重排     追求"排准"，必须精确
```

### 2.2 诚实声明：教学版为什么用四维可手算特征

真实的交叉编码器要下载权重、要推理框架、通常还要 GPU——**这三件事本课一件都不许有**（离线、确定性、零依赖）。因此 `CrossEncoderReranker` 是一个**确定性替身**：分数由四个可手算的特征加权而成。

它没有真实语义，这句话不含糊其辞：

```text
它认不出同义改写    "重算"与"重新计算"在它眼里是两个不同的字串
它读不懂语序        "甲打败了乙"与"乙打败了甲"的特征几乎一样
```

**生产环境应当把它替换为真实重排模型**——接口就是 `BaseReranker`。这与 `llm.embedding.MockEmbedding` 的写法同源：形状留好、替身说清。

换来的东西恰恰是本课要的：**分数可以手算核对**。一个"必须先下载 2 GB 权重才能复现"的分数，在"这次评估为什么变了"这个问题前面是哑的；而四个特征里的任何一个分数，都能拿纸笔验算。第 3 节的实测表里有一列"手算和"和一列"引擎"，两列逐位相同——那就是这条取舍的兑现。

> 思考题：如果替身认不出同义改写，那么本课的 `measure_lift` 结论（"重排带来了多少提升"）还能信吗？提示：三条指标依赖的是"名单"与"金标准"，而不是"分数的绝对值"。

### 2.3 四个特征的精确定义

全部落在 `[0, 1]`，因此加权和也落在 `[0, 1]`：

```text
term_coverage    查询词元里出现在文档中的比例（**去重后**算）
                 → 替代真实模型的词汇匹配能力
exact_phrase     文档包含查询原文（strip + 折叠大小写）→ 1.0，否则 0.0
                 → 替代真实模型对整句的强匹配
proximity        1 / (1 + 最小跨度)：所有查询词元都出现时的最小窗口宽度
                 → 替代真实模型的语序/邻近敏感
length_penalty   min(1.0, IDEAL_LEN / max(len(text), 1))，IDEAL_LEN = 240
                 → 从**另一侧**对冲排序模型的冗长偏好
```

`term_coverage` 与 `proximity` 复用 `lexical.tokenize`（**同一套分词**）。这不是省事，而是一条一致性纪律：重排与关键词路如果各用一套分词，"同一个查询能不能命中同一篇"就会有两份答案，而这两份答案在报告里长得完全一样——那是评估最怕的一种不一致。同一条纪律在 day067 用在"两路共用一份过滤子句"上。

实测表（`scripts/rerank_demo.py` 第 3 节）：

```text
  情形                         | id    |     覆盖 |    整句 |     邻近 |     长度 |       手算和 |        引擎 | 一致
  整句包含，编号紧挨                  | d-05  | 1.0000 |   1.0 | 0.3333 | 1.0000 |  0.916667 |  0.916667 | True
  整句包含，另一个编号                 | d-11  | 1.0000 |   1.0 | 0.3333 | 1.0000 |  0.916667 |  0.916667 | True
  整句包含但正文很长                  | d-12  | 1.0000 |   1.0 | 0.3333 | 0.7143 |  0.880952 |  0.880952 | True
  一个编号都不含（阶段一的第 1 名）         | d-01  | 0.0000 |   0.0 | 0.0000 | 1.0000 |  0.125000 |  0.125000 | True
  覆盖率 6/6、邻近度很低              | d-06  | 1.0000 |   0.0 | 0.0370 | 1.0000 |  0.629630 |  0.629630 | True
```

拿 `d-11` 手算一遍（查询 `'ERR-2043'` → 词元 `['err', '2043']`）：

```text
term_coverage = 2/2 = 1.0           正文里 err 与 2043 都在
exact_phrase  = 1.0                 正文含 'ERR-2043' 这个整串
proximity     = 1/(1+2) = 1/3       两个词元之间的最小窗口宽度是 2（紧挨着）
length_penalty= min(1.0, 240/40) = 1.0    正文 40 字，短于标准长度
分数 = 0.5×1.0 + 0.25×1.0 + 0.125×(1/3) + 0.125×1.0
     = 12/24 + 6/24 + 1/24 + 3/24 = 22/24 = 11/12 = 0.916667
```

`proximity` 的定义里有一个容易忽略的限定：**只要求"所有词元都出现"才谈跨度**。`d-01` 一个词元都没命中，它的 `proximity` 是 `0.0` 而不是"跨度很大所以很小"——没有跨度可言。覆盖率是连续量（1/2、2/2），邻近度是"覆盖之后的奖励"，两者分工不重叠。

### 2.4 `FEATURE_WEIGHTS`：和必须逐位等于 1.0

```text
权重（顺序一一对应）：(0.5, 0.25, 0.125, 0.125) → 和 = 1.0（逐位等于 1.0）
```

四个权重的和必须**逐位**等于 `1.0`，这是构造期校验的一条硬约束。为什么强调"逐位"？因为 `1/3 + 1/3 + 1/3` 在浮点下不等于 `1.0`，而一个和略大于 1 的权重表会让"分数落在 [0, 1]"这条不变量失效——**而 `min_score` 的可标定性正建立在它上面**（第五章）：教学替身的重排分落在 `[0, 1]`，因此一个阈值在这里有绝对含义，这与 day067 里 BM25"没有绝对标度、给它一个数字是假的安全感"正好相反。

`(0.5, 0.25, 0.125, 0.125)` 是二进制精确可表示的一组数：`0.5 = 2⁻¹`、`0.25 = 2⁻²`、`0.125 = 2⁻³`，求和逐位等于 `1.0`。取这样一组权重不是为了好看，而是为了让**手算和引擎逐位一致**——第 2.3 节那张表的最后一列全是 `True`，靠的就是这个性质。

### 2.5 长度惩罚对冲着什么

交叉编码器的位置偏置里最顽固的一条是**冗长偏好**：长文档里"恰好出现某个词"的概率本来就高，注意力也更容易找到一段能与查询对上的文字，于是分数系统性地偏高。day026 在 Prompt 评估那一课已经见过它的另一种形态（更长的提示词"看起来更专业"，因此评委给分偏高）。

把长度罚项放进分数，是在**重排这一侧**对冲它。但"长文档更该被看见吗"没有普适答案——一份 800 字的文档可能真的比 200 字的有用。因此它只占 `1/8` 的权重，而不是一条硬规则：

```text
d-12 正文 336 字 → length_penalty = min(1.0, 240/336) = 0.714286
     它的覆盖、整句、邻近三项都满分，分数从 11/12 降到 0.880952
     降幅 0.035715 —— 而它的名次变化是 stage1 #5 → #2（仍然上移 3 位）
```

这是本课想留下的一种手感：**一个对冲项的作用是"压低一点"，不是"一票否决"**。把它做成硬规则（长于 N 字直接扔掉）就变成了另一种偏差，而且更难解释。

> 思考题：`IDEAL_LEN = 240` 这个常量是按本课语料的块长标定的。如果换一批平均 1200 字的语料，这个值不调会发生什么？提示：看 `min(1.0, IDEAL_LEN / len)` 在两个区间里的行为。

## 第三章：窗口纪律 —— 只对前 N 条打分

### 3.1 成本算术，以及一个必须写出来的坏消息

"只对前 N 条打分"有两个半边，两个都必须写出来：

```text
好消息   成本从 O(候选) 降到 O(N)，N 是一个可配的旋钮（retrieval_rerank_top_n）
坏消息   第 N+1 条**永远没有机会**证明自己——它的名次只由第一阶段的分数决定
```

坏消息那一半**无条件进 `notes`**。理由不是礼貌，而是准确性：只报"重排生效了"却不报"有一批条连分都没拿到"，等于把一次**有边界的**改进说成了一次全面的改进。这是本模块最容易被删掉、也最不该删掉的一行。

### 3.2 实测：窗口关小之后谁还在

`scripts/rerank_demo.py` 第 2 节，候选 12 条，把 `top_n` 从 20 收到 5：

```text
  top_n=5：候选 12 条 → 打分了 5 条、没打分 7 条
      打过分：['d-11', 'd-01', 'd-04', 'd-02', 'd-03']
      没打分：['d-12', 'd-05', 'd-06', 'd-07', 'd-08', 'd-09', 'd-10']（score=0.0、scored=False、stage1_rank 保持原值）
      结果的账：candidates=12、scored=5、window=5、top_n=5
      重排器计数器差量：calls +1、scored_pairs +5、batches +1（累计 calls=1、scored_pairs=5）；注记 2 条：只对前 N 条打分（N=top_n=5）：候选 12 条，窗口内 5 条全部打过分；窗口外的 7 条…
```

注意"打过分"那一批里**没有 `d-12` 与 `d-05`**——它们俩在第一阶段是第 5、6 名，正好卡在窗口外。而上一条实测里（`top_n=20`）它们俩是重排之后的前三名。同一份语料、同一个查询，只因为 `top_n` 从 20 变成 5，本课的第一名就从 `d-11` 换成……仍然是 `d-11`，但第二、三名被窗口外的两条占住了。

这就是窗口纪律的真实代价，也是它必须进 `notes` 的原因：**读者看到"重排之后的名单"时，必须同时知道"有多少条根本没参加"。**

> 思考题：`top_n=5` 时窗口内的 5 条里，第 5 名是 `d-03`（重排分 0.125）。如果把它换成"按第一阶段分数取前 5 条"再重排，会有什么不同？提示：窗口的定义是"输入序列的前 N 条"，而输入序列就是第一阶段给的次序。

### 3.3 尾部为什么是 `score=0.0` 而不是 `None`

窗口之外的命中在结果里长这样：`scored=False`、`score=0.0`、`features={}`、`stage1_rank` 保持原值，且**排在窗口内结果之后、保持原顺序**。

为什么不用 `None`？因为 `RerankHit.score` 是 `float`，形状上让"每条都有一个分数"；而"它其实没被打分"由 `scored` 标志与 `notes` 里那条注记负责。这样设计的两个好处：

1. **排序键不需要分支**。`(-score, stage1_rank, record_id)` 对尾部一样成立（它们的 `score` 全是 `0.0`，于是完全由 `stage1_rank` 决定，也就是保持原序）。
2. **`0.0` 不会被读成"最不相关"**。它只说明"没有分"。这两件事在报告里必须分得开——"最不相关"是一个结论，"没有分"是一个事实。

一条更直白的补充说明来自演示脚本：

```text
窗口外的那批按原顺序排在窗口结果之后，名次与分数是两套证据。
```

### 3.4 `scored` 标志与两个计数器

`CrossEncoderReranker` 上留了三个计数器：`calls`（调用次数）、`scored_pairs`（真正打分的 (查询, 文档) 对数）、`batches`（分成几批）。

它们不是为了好看，而是为了让"窗口纪律真的生效了"变成**可断言的**：

```text
top_n=5、候选 12 → calls +1、scored_pairs +5、batches +1
top_n=10、候选 12 → calls +1、scored_pairs +10、batches +1
```

如果哪天有人把窗口循环写成"全量打分再切前 N 条"，`scored_pairs` 会从 5 变成 12——**一条断言就能拦住它**（`tests/test_rerank_pipeline.py` 里就有这条）。这正是 day065 "分数变了必须能归因"那类纪律的另一种用法：**成本变了也必须能归因。**

`DEFAULT_RERANK_BATCH = 16` 是一个**纯开销旋钮**：它按 `batch_size` 分批送给重排器，而特征逐条算，因此**不改变任何分数**，只改变"分成几次算"。空列表连批次都不产生（"算过 0 批"不等于"算过 1 批空批"）。把这件事写进常量注释，是为了防止有人调 `batch_size` 之后发现"结果没变"而怀疑实现有 bug。

## 第四章：两种模式 —— `replace` 与 `blend`

### 4.1 跨阶段的分数量纲不可比（第二次出现）

```text
replace   窗口内**只**按重排分重排（第一阶段的分数降级为兜底的排序键）
blend     窗口内把两份分数**各自 min-max 归一化**到 [0, 1]，再按 weight 加权
```

`blend` 里那一步归一化**不是可选项**。第一阶段的分数量纲取决于上游：

```text
余弦          ∈ [-1, 1]
BM25          ∈ [0, ∞)
RRF           1/(k+r) 之和，量级 ~0.03
weighted 融合 一套归一化之后的加权分
重排分        ∈ [0, 1]（四个特征都在 [0,1]，权重和逐位为 1.0）
```

直接把 `0.82`（余弦）与 `0.91`（重排分）加权，看起来"两边各占一半"，实际上重排分因为标度更大而在数值上稳占上风——**量纲差冒充了相关性差**。这正是 day067 `fusion` 模块那条纪律，因此这里**复用同一个函数** `fusion._min_max_normalize`：同一条纪律只写一份实现，两份实现一定会分家。

### 4.2 `blend` 的手算，与它"随窗口变化"的代价

演示脚本第 4 节把中间值全部打出来（窗口 `top_n=6`、`weight=0.5`）：

```text
  两列分数各自在**窗口内**做 min-max（手算，只用窗口里这 6 条）：
      阶段一：min=0.360000、max=1.000000
      重排分：min=0.125000、max=0.916667
  d-01 1.000000/0.125000 → 归一 1.000000/0.000000 → blended 0.500000（手算=引擎）
  d-04 0.960000/0.125000 → 0.937500/0.000000 → 0.468750
  d-02 → 0.687500/0.000000 → 0.343750
  d-03 0.600000/0.125000 → 0.375000/0.000000 → 0.187500
  d-11 0.480000/0.916667 → 0.187500/1.000000 → 0.593750
  d-12 0.360000/0.880952 → 0.000000/0.954887 → 0.477444
```

拿 `d-12` 手算一遍，把每一步都写出来：

```text
阶段一归一化  (0.360000 − 0.360000) / (1.000000 − 0.360000) = 0/0.64 = 0.000000
重排分归一化  (0.880952 − 0.125000) / (0.916667 − 0.125000) = 0.755952/0.791667 = 0.954887
blended       = 0.5×0.954887 + 0.5×0.000000 = 0.477444
```

`replace` 与 `blend` 的名单差异很小但真实存在：

```text
  replace 名单：d-11、d-12、d-01、d-04、d-02、d-03、d-05、...
  blend   名单：d-11、d-01、d-12、d-04、d-02、d-03、d-05、...
  差别只在 d-01 与 d-12 互换
```

`replace` 只看重排分，于是 `d-12`（0.880952）排在 `d-01`（0.125）前面；`blend` 把第一阶段那 1.0 的余弦拉进来（归一化后仍是 1.0），于是 `d-01` 反超。**哪一种更对，取决于你信不信第一阶段的分数**——而这是业务判断，所以它被做成一个可配的模式，而不是写死的一种。

代价也必须写下来：归一化只在**这一次窗口内**做，因此同一篇文档的归一化分**随窗口变化**。演示脚本第 4 节直接测了这件事：

```text
  blend 的代价：d-12 的 blended 0.477444（top_n=6）→ 0.657444（top_n=8），差 +0.180000
```

`d-12` 的原始分数一个字没变，只因为窗口从 6 扩到 8（`min` 从 0.125/0.36 变成别的值），它的归一化分就变了 0.18。这是**相对量的固有性质**，不是实现缺陷——加权求和需要的只是"同一次重排内部可比"，而这条性质恰好提供它。但凡是会读这份报告的人，都应该在手册里看到这句话，而不是自己踩一遍。

### 4.3 第三个兜底键：排序确定性

排序键在代码里逐字写着：

```text
replace → (-score, stage1_rank, record_id)
blend   → (-blended, stage1_rank, record_id)
```

三个键缺一不可。只按分数排序时，"两条分数逐位相同"会让名次取决于 `sorted` 的稳定性——那是**没写下来的**排序规则，而后果是"同一次查询两次运行给出不同的 top-1"，这是最难查的一类 bug。

演示脚本第 6 节把这件事测了三层：

```text
  同一批输入跑三次：三次逐位相同：True

  语料里就躺着一对**精确并列**：d-05 与 d-11 的四个特征逐位相同
      d-11  rerank=0.9166666666666666  stage1_rank=4  rank=0
      d-05  rerank=0.9166666666666666  stage1_rank=6  rank=1
      次序 d-11 → d-05，由第二键 stage1_rank（4 < 6）决定
      注意：**不是**由 record_id 决定（d-05 < d-11 只是碰巧同向）

  把并列造得更极端：同一段正文、同一个阶段一分数（0.5），只换输入顺序
      输入 ['tie-b', 'tie-a'] → ['tie-b', 'tie-a']；输入 ['tie-a', 'tie-b'] → ['tie-a', 'tie-b']
      次序**跟着输入位置走**
```

第三层是最能说明问题的一层：`d-05 < d-11` 只是碰巧与 `stage1_rank` 同向，所以只看结果会误以为"它按 id 排"。把并列造得更极端之后，"它到底按什么排"就露出来了——**按输入位置**。而第三键 `record_id` 在这条路径上根本不会被触发（`stage1_rank` 是输入序列的位置，它本身已经把每一条区分开了），它写在那里是**防御性兜底**：让"同分"在任何调用方式下都有一个确定的答案。

> 思考题：既然 `stage1_rank` 已经把输入区分开了，第三键是不是多余的？提示：想一个"输入序列里 `stage1_rank` 会重复"的调用方式——比如把两次检索的结果拼起来再重排。

## 第五章：阈值与第四道减法

### 5.1 `min_score` 只作用于被打分过的那一批

一条小口径，但它是本课最容易出错的地方：

```text
min_score 比的是**重排分**（不是第一阶段的分数），而且只切 scored=True 的那一批。
```

比"重排分"的理由是可标定性：教学替身的重排分落在 `[0, 1]`，一个阈值在这里有绝对含义。这与 day067 里 BM25 的处境正好相反（"BM25 的分数没有绝对标度，给它一个数字是假的安全感"）。

"只切被打分过的那一批"的实测（第 5 节）：

```text
  top_n=5、min_score=2.0：窗口 5 条 → 留 0 条、切 5 条
      窗口外的 7 条：d-12、d-05、d-06、d-07、d-08、d-09、d-10 —— 它们的 score 全是 0.0，**没有一条被阈值切掉**
      结果：命中 7 条、empty_reason=（空串）

  top_n=20、min_score=2.0：窗口 12 条 → 留下 0 条、切掉 12 条
      结果：命中 0 条、empty_reason=重排阈值 2.0 把窗口内的 12 条全切掉了，而窗口外没…
```

**"切光窗口"与"空结果"是两件事**：第二行窗口被切光了，名单却不是空的——窗口外那 7 条照样在。只有第三行（窗口覆盖了全部候选）才是真的空结果，此时 `empty_reason` 必须给出唯一成因。

阈值切不到尾部，原因很直白：**它没有分数可切**。而这件事同样必须进 `notes`，因为"我设了阈值，结果还有 7 条"是一个会让人怀疑实现的观察。

### 5.2 为什么不并进 `dropped_by_top_k`

`RetrievalResult` 现在有**四个**减法计数：

| 数字 | 切掉的是什么 | 对应哪个旋钮 |
|------|-------------|-------------|
| `dropped_below_threshold` | 第一阶段阈值切掉的 | `retrieval_min_score` |
| `dropped_by_diversity` | 同文档挤掉的 | `retrieval_max_per_doc` |
| `dropped_by_top_k` | 截断到 `top_k` 丢掉的 | `retrieval_top_k` |
| `dropped_by_rerank`（新） | 重排阈值切掉的 | `retrieval_rerank_min_score` |

四个数字各自对应一个可调参数。合成一个 `dropped` 会让"该调哪个参数"这个问题永远无法回答——这是 day066 就写进包 docstring 的纪律，今天只是把它用了第四次。**同一个数字有两种来源，等于两种来源都没有。**

### 5.3 一处必须记下来的连带改动

重排阈值把窗口切完时，`empty_reason` 应该是什么？如果不管它，诊断会落到 `no_data`（"库是空的，请先建索引"）——一个**主动误导**的结论：库明明有 12 条，只是被一个阈值切光了。

因此 `_diagnose` 新增了一个可选参数 `dropped_by_rerank`，让重排阈值与第一阶段阈值共用 `below_threshold` 这个已有取值（**封闭清单不动、端点协议不变**）。代价也写进了 docstring：这一支说不出"是第几阶段的阈值切光的"。取舍的理由是"宁可少一个细节，也不要多一个自相矛盾的诊断"。

> 思考题：如果要在不新增 `empty_reason` 取值的前提下补上"是哪个阈值"，你会怎么做？提示：`RetrievalResult` 里已经有四个数字了。

## 第六章：集成 —— 单路第 6.5 步、混合第 10.5 步

### 6.1 单路的九步变成十步

`retriever.py` 的模块 docstring 里那张步骤表现在长这样：

```text
1.   规范化查询      str → RetrievalQuery；None 字段填构造参数 / settings
2.   索引体检        库空 → 直接返回 no_data（空库是合法状态，不报错）；
                    有清单 → compare_with_store 得到 drift（严格模式直接抛）
3.   算召回深度      fetch_k = max(top_k, ceil(top_k × multiplier))，封顶 MAX_FETCH_K
4.   编码查询        embed(text) + 三项校验（维度 / 有限 / 非零）
5.   库侧过滤        combine_where(where, time_range) 交给 backend.query
6.   阈值落刀        在本层按 min_score 过滤并记「切掉了几条」
6.5  重排（可选）    只对前 top_n 条调用 reranker，按重排分重编名次（day068）
7.   多样性裁剪      按 doc_id 分组，每组留前 max_per_doc 条，其余记「挤掉了几条」
8.   截断到 top_k    记「截断丢掉了几条」
9.   诊断与装配      定 empty_reason、算延迟、收集 notes
```

第 6.5 步在代码里的位置：

```python
        # 第 10.5 步：重排（可选）。**必须在多样性之前**——多样性会按 doc_id
        # 砍掉同一文档的其余记录，若先砍后重排，被砍掉的候选就再也回不到
        # 重排器眼前（理由见模块 docstring）。关着重排时这一步原样返回。
        hits, rerank_summary, dropped_rerank = self._apply_rerank(
            hits, resolved, rerank_plan, notes
        )
```

（上面这段摘自 `hybrid.py` 的第 10.5 步，两条流水线上的注释写的是同一句理由。）

### 6.2 为什么必须在多样性裁剪之前

顺序只有这一种排法，理由是一条具体的证据链：

```text
多样性的动作   按 doc_id 分组，把同一文档的第 2、3… 条**丢掉**
若先裁后重排   那些被丢掉的候选再也回不来——重排器**看不到它们**，
               于是"同一文档里的第 2 段其实更贴题"这个事实永远无法被发现
因此顺序        重排（在完整的候选集上比较）→ 多样性（在重排之后的次序上做取舍）
```

这与 day067 把多样性放在融合之后是**同一条推理**："先让所有的证据都上桌，再做取舍"，只是今天的证据来自交叉编码器而不是第二路召回。

代价也要写下来：重排**改变了"哪几条会被多样性命中"**。`tests/test_rerank_pipeline.py` 里有一条用例专门钉住它——同一份语料、`max_per_doc=1`，只翻重排开关，`doc-window` 那一组留下的成员就从 `r-t-06` 翻成 `r-t-08`。这不是 bug，而是"重排的结论被尊重"的必然结果：顺序变了，取舍的输入就变了。

### 6.3 为什么第 8 步只重编号、不重排

day066 的第 8 步是"按 `(-score, record_id)` 排序并重编号次"。重排开启之后，这一步**只重编号**：

```python
        # 第 12 步：截断（次序是融合的权威次序；重排开启时它就是重排的权威次序，
        # 因此这里同样只重编号、不重排——重排分不在 ``score`` 里，
        # 按 score 排一遍会把重排的结论原样抹掉）。
```

理由是一个容易忽略的接口事实：**重排分没有被写进 `RetrievalHit.score`**。`score` 保留第一阶段的口径（这样"它原来的分数是多少"随时查得到），重排分在新字段 `rerank_score` 里。于是如果第 8 步还按 `score` 排一遍，重排的结论会被**静默抹掉**——不报错，只是白干了。这类"看起来无害、实际上是致命"的改动，正是本课反复用注释钉住的东西。

由此产生一个必须说清的口径变化：**"越大的分越靠前"这条不变量，在重排开启后的列表里不再成立。**

```text
[A] 单路 fetch_k=15、candidates=12、命中 5：
    d-11(0.480000→rerank 0.916667, sr4)、d-05(0.0→0.916667, sr6)、
    d-12(0.36→0.880952)、d-01(1.0→0.125, 原 #0)、d-04(0.96→0.125)
    score 序列 [0.48, 0.0, 0.36, 1.0, 0.96] 不再单调
```

`score` 序列不再单调，而 `rerank_score` 序列（0.9167、0.9167、0.8810、0.125、0.125）是单调的。**读者必须知道该看哪一个**——这就是为什么两个字段都留在结果里，而不是"用一个覆盖另一个"。

### 6.4 断开重排时逐位不变

新能力的第一条纪律是"默认不生效"，第二条是"关着的时候不许改写一个字段"：

```text
第 6.5 步**只在 ``rerank_enabled``（或 ``settings.retrieval_rerank_enabled``）为真时
才存在**：关着的时候第 6 与第 7 步之间什么都没有发生、一个字段都不会被改写，
因此 day066/day067 的结果逐位不变（这是"新能力默认不生效"这条纪律的落地）。
```

演示脚本第 9 节把它测成了可执行的事实：

```text
  关闭时 rerank == {}：True；dropped_by_rerank=0；rerank_score/stage1_rank 全 None
  '逐位不变'再确认：关闭时的名单 == "根本没配过重排"的检索器给的名单：True
```

第二条对比是关键：它比的是"显式关掉"与"从来没有这个能力"两种情形。**"关掉"必须真的等于"不存在"**，否则回滚就不是回滚。

## 第七章：参数与逐次覆盖

### 7.1 六个配置项

`config.py` 在 `retrieval_bm25_b` 之后追加了一组，注释风格与 `retrieval_hybrid_*` 完全一致：

| 配置项 | 默认值 | 作用 |
|--------|--------|------|
| `retrieval_rerank_enabled` | `False` | 是否在检索链路上启用重排（**默认不生效**） |
| `retrieval_rerank_model` | `"cross-encoder-teaching-v1"` | 重排模型名（写进结果，供报告分组） |
| `retrieval_rerank_top_n` | `20` | 窗口大小（只对前 N 条打分） |
| `retrieval_rerank_weight` | `0.5` | `blend` 模式下重排分的权重 |
| `retrieval_rerank_mode` | `"replace"` | `replace` / `blend` |
| `retrieval_rerank_min_score` | `None` | 重排分下限（`None` = 不设阈值） |

两条与 `retrieval_hybrid_*` 同源的注释必须写进去：这一组**不改变任何产物的字节**（不改 chunk_id、不改向量、不改清单版本号，只改变"怎么问"），以及**新能力默认不生效**——`retrieval_rerank_enabled=False` 时 day066/day067 的端点行为逐位不变。

`None` 在这一层的含义只有一种：**"没指定，去读 settings"**。于是"项目默认"只有一处定义，端点与演示脚本不必各抄一遍。

### 7.2 `extra` 的封闭清单

逐次覆盖走 `RetrievalQuery.extra`，键名是一份**封闭清单**：

```python
RERANK_OVERRIDE_KEYS: tuple[str, ...] = ("enabled", "mode", "model", "top_n", "weight")
```

清单之外的键**必须报错**，理由与 `FUSION_OVERRIDE_KEYS` 逐字相同："静默忽略一个覆盖参数会让调用方以为它生效了"——把 `mode` 拼成 `mod`，结果看起来只是"没有变化"，而下一次排查要从头开始。

覆盖生效时**必须进 `notes`**：报告里要能看出"这一次用的是覆盖值还是构造默认值"。这条与 day067 融合参数的处理方式一致。

### 7.3 一处与 `fusion` 不同的选择

有一个不一致之处值得单独讲：**`mode="replace"` 时如果同时给了 `weight`，重排层不报错，而是记录并说明。**

```text
fusion          strategy="rrf" 且给了 weights → **直接报错**
                （RRF 的全部理由就是只看名次、不做加权，给权重说明调用方搞错了）
rerank          mode="replace" 且给了 weight → **记录进 RerankResult.weight，
                并进 notes 说明"replace 模式不看权重"**
```

为什么两种处理？因为两者的语义不同。`rrf + weights` 是**互相矛盾的意图**（"我只要名次"与"我要按分数加权"同时出现），报错能让调用方立刻发现自己想错了。而 `replace + weight` 是**无害的冗余**：窗口内只按重排分排序，那个权重从头到尾没被读过，但调用方很可能是在做"把两种模式都跑一遍"的实验——此时报错会把一次正常的对照实验打断。

`notes` 里那句话就是这条取舍的兑现：**记录并说明，而不是拒绝或静默**。这三种处置的顺序是"报错 > 记录并说明 > 静默"，本课在两种情形里各选了一种，而两种选择都写进了 docstring。

## 第八章：结果里的重排证据

### 8.1 逐条命中上的两个新字段

`RetrievalHit` 尾部追加了两个带默认值的字段：

```text
rerank_score   重排分（None = 这次没开重排）
stage1_rank    它原来在第几（None = 这次没开重排）
```

用 `None` 表达"未记录"，与 day067 里 `channels=()` 的写法同一套理由：**"未记录"与"记录了某个值"必须能被区分开**。如果把"没开重排"写成 `rerank_score=0.0`，它会与"重排分真的是 0"混成同一形状。

`RerankHit` 上的派生量 `moved = stage1_rank − rank` 是"名次动了多少"的唯一出处：正数上移、负数下移、0 表示没动。第一章那张两列表就是靠它读出来的。

### 8.2 `RetrievalResult.rerank` 摘要的每个键

对齐 `fusion` 字段的写法：**空字典 = 这次没开重排**。

```text
['candidates', 'dropped_by_min_score', 'empty_reason', 'mode', 'model', 'moved', 'params', 'scored', 'window']
```

（这一行是演示脚本第 9 节打印的真实键集合，顺序按字母序。）

一个必须点明的同名陷阱：**`rerank["candidates"]` 与 `RetrievalResult.candidates` 是两个数**。前者是"这次重排的输入条数"（单路时等于第一阶段命中的条数），后者是"库侧过滤后还剩多少条候选"。同名字段两个口径是容易出事的地方，因此 `to_summary()` 的 docstring 里专门写了这一句。

### 8.3 `explain()` 多出来的那一行，与一处已经修掉的读法坑

`RetrievalResult.explain()` 现在多一行（**非空才渲染**——空字典意味着这次没开重排，而"没开重排"不该在诊断里占一行废话）：

```text
重排：cross-encoder-teaching-v1（top_n=10、weight=0.5）—— 候选 10 条、只对前 10 条打分（真正打分 10 条）、名次动了 4 条、重排阈值切掉 0 条
```

这一行里有一个真实的坑，写下来省一次排查。最初它读的是摘要的**顶层键** `top_n`，而 `to_summary()` 把 `top_n` 放在 `params` 子字典里——顶层根本没有这个键，于是它渲染成：

```text
重排：cross-encoder-teaching-v1（top_n=10、weight=0.5）—— 候选 10 条、只对前 0 条打分（真正打分 10 条）、...
```

同一行里 `top_n=10` 与"只对前 0 条打分"**自相矛盾**。数值、排序、账本都不受影响（`params.top_n` 与 `window` 都是对的），它只污染诊断文本——而诊断文本的全部价值就是"让人相信它"。修法是"读已有的那一个键"，而不是"多补一个同义的顶层键"：

```python
window = params.get("top_n", self.rerank.get("window", 0))
```

**"多一个同义的副本"是所有分家的起点**；这一条与 day065 的"分数变了必须能归因"、day067 的"同一份过滤子句只合成一次"是同一种纪律，只是今天的对象是一个诊断字符串。

> 思考题：为什么这条缺陷值得写进教程，而不是悄悄修掉？提示：想想"自相矛盾的诊断"与"缺失的诊断"哪一种更贵。

## 第九章：评估提升 —— `recall@k` / `RR` / `nDCG@k`

### 9.1 三条指标的公式

"重排到底有没有用"不是靠感觉回答的，而是靠一组标注好的查询（`LiftProbe`：一句话 + 它的金标准 id）与三条指标。三条的公式写在 `rerank.py` 的模块 docstring 里，实现里逐字对应：

```text
recall@k   = |前 k 条 ∩ 金标准| / |金标准|                    （命中面：有没有捞回来）
RR         = 1 / (第一个相关命中的位置 + 1)（无则 0.0）        （头部质量：第一条要多久才相关）
nDCG@k     = DCG@k / IDCG@k
             DCG@k  = Σ_{i=0}^{k-1} rel_i / log2(i + 2)        二值增益 rel_i ∈ {0,1}
             IDCG@k = Σ_{i=0}^{m-1} 1 / log2(i + 2)，
                      m = min(|金标准|, k)                     （理想名单的 DCG）
```

三个细节容易被读漏，但它们决定了实现与文档是否一致：

1. **`recall@k` 的分母是去重后的金标准条数**，分子是"命中了几条"（同一条在前 k 条里出现两次只算一次）。
2. **`rel_i` 是二值增益**（相关就是 1，不相关就是 0），因此同一份金标准里出现重复 id 时，**只有首次出现才记增益**。这不是偷懒，而是为了让"理想名单"有唯一形状。
3. **`IDCG@k` 的求和上限是 `min(|金标准|, k)`**。金标准有 2 条而 `k=5` 时，理想名单只有 2 个位置能被填上——按 5 个位置算 IDCG 会把分母放大，让一个"完美的名单"算不出 1.0。

三者必须一起看，理由各自不同：

```text
只看 recall@k   "把相关的那条从第 4 名提到第 1 名"完全不可见（都在前 k 条里）
只看 RR         "前 k 条命中了 3 条还是 1 条"不可见
nDCG@k          唯一同时看"命中几条"与"排得多靠前"的那条
```

### 9.2 变量只有一个：有没有重排

`measure_lift` 的调用形状刻意设计成"只检索一次"：

```python
measure_lift(probes, retrieve, reranker, *, k=5, top_n=None, mode=None, weight=None)
```

对每条探针先 `retrieve(probe.query)` 拿 `RetrievalResult`，取 `result.ids()` 算 before 指标；再用**同一批 `result.hits`** 走 `rerank_hits` 算 after 指标。测试里用一个会计数的假检索器把这条钉住：**检索只发生一次**，before 与 after 只差"有没有重排"这一个变量。如果实现成"检索两次"（一次开重排一次不开），那么两次检索之间任何别的差异都会混进 `lift` 里，而报告上完全看不出来。

演示脚本第 7 节还有一条实测上的讲究：`retrieve` 用**不开重排**的那一份检索器，并刻意取满 12 条（比 `k=5` 深）。理由是 `measure_lift` 的 after 只能重排 `retrieve` 交上来的那份名单——**若它已被 `top_k` 截到 5 条，"召回提升"在这份报告里不可能出现**。评估时把深度放开、把截断关掉，是这个方法能测到召回的前提。

> 思考题：如果 `retrieve` 交上来的名单已经被截断到 `k` 条，`recall@k` 的 before 与 after 会是什么关系？把结论写成一句话。

### 9.3 实测：`before` / `after` / `lift`

3 条探针、`k=5`：

```text
  重排提升（3 条探针 / k=5）：ndcg 0.4124 → 1.0000（+0.5876）、recall 0.5000 → 1.0000（+0.5000）、reciprocal_rank 0.4417 → 1.0000（+0.5583）
      before = {'recall': 0.5, 'reciprocal_rank': 0.441667, 'ndcg': 0.412399}
      after  = {'recall': 1.0, 'reciprocal_rank': 1.0, 'ndcg': 1.0}
      lift   = {'recall': 0.5, 'reciprocal_rank': 0.558333, 'ndcg': 0.587601}
```

`lift` 用的是**差值而不是比值**，理由写在括号里：`before=0` 时比值是无穷。这是一个小但重要的口径选择——比值对"从 0 到 1"这种最有价值的提升恰恰给不出数字。

第一条探针的 before 可以完全用纸笔核对（演示脚本把过程打出来了）：

```text
      名单 ['d-01', 'd-04', 'd-02', 'd-03', 'd-11']、金标准 ['d-05', 'd-11']（分母 = 去重后 2 条）、命中位置 [4]
      DCG@k = Σ 1/log2(i+2) = 1/log2(6) = 0.386853
      IDCG@k = Σ(i < min(2,5)) = 1/log2(2) + 1/log2(3) = 1 + 0.630930 = 1.630930
      recall = 1/2 = 0.5；RR = 1/(4+1) = 0.2；nDCG = 0.386853/1.630930 = 0.237198
```

三个数字与引擎逐位一致（`before={'recall': 0.5, 'reciprocal_rank': 0.2, 'ndcg': 0.237198}`）。这就是"教学级替身"换来的东西：**整条评估链路都能手算复核，而结论不依赖于用哪个重排模型**。

### 9.4 `lift` 为负与 `lift` 为零，都是结论

三条探针里，第三条的 `lift` 三个数字**全是 0.0**：

```text
      查询 'retry_budget'（金标准 ['d-06']）
          before：d-06、d-01、...          after ：d-06、d-01、...
          指标 before={'recall': 1.0, 'reciprocal_rank': 1.0, 'ndcg': 1.0} lift={'recall': 0.0, 'reciprocal_rank': 0.0, 'ndcg': 0.0}
          名次变化：（无）
```

第一条探针的 `lift` 三个数字全为正（`+0.5 / +0.8 / +0.762802`），第二条更高（`+1.0 / +0.875 / +1.0`）。**"有一条探针一点没变"必须原样报出来**，而不是从报告里删掉——它恰恰说明"重排不是万能的，它在第一阶段已经排对的地方不会凭空加分"。一个只展示最好几条探针的报告，和没有报告差不多。

`tests/test_rerank_lift.py` 里还专门有一组"重排没有提升甚至变差"的对照（`lift` 的符号为负），理由是同一个：**评估工具必须能诚实地报出坏消息**，否则它在报好消息时也不可信。

`LiftReport` 的形状与端点协议对齐：

```text
LiftReport(queries=3, k=5,
           before={'recall': 0.5, 'reciprocal_rank': 0.441667, 'ndcg': 0.412399},
           after={'recall': 1.0, 'reciprocal_rank': 1.0, 'ndcg': 1.0},
           lift={'recall': 0.5, 'reciprocal_rank': 0.558333, 'ndcg': 0.587601},
           per_query=(...每条的三个 before / after / lift 与名次变化...))
```

不变量一条：**`lift` 必须逐位等于 `after − before`**。这条断言看起来是同义反复，但它拦住的是"有人顺手把某一项改成比值"这类改动。

## 第十章：端点（现在十个）

`api/routes.py` 里的 `/retrieval/*` 从七个变成**十个**，新增的三个构成一组完整的能力：跑一次看、看配置、量提升。

| 端点 | 方法 | 回答什么 |
|------|------|----------|
| `/retrieval/rerank` | POST | 一句话 → 检索 → **强制开启重排** → 重排前后的两份 id 次序并排给出 |
| `/retrieval/rerank/status` | GET | 重排的配置现状 + 重排器 `describe()` + settings 回显 |
| `/retrieval/rerank/compare` | POST | 一次查询 + 金标准 id → `recall@k` / `RR` / `nDCG@k` 的 before / after / lift |

三条本组独有的约定：

1. **`/retrieval/rerank` 把 `enabled=False` 当 400 处理**。它存在的理由就是"我要看重排做了什么"，一个显式关掉的请求是矛盾意图，静默照做会让调用方拿到两份一样的名单却以为重排坏了。
2. **`before_ids` 与 `after_ids` 是两个独立字段**（不是"结果里多一列"）。这是本端点唯一的存在理由：**让人看见次序被改动了**。若只返回重排后的名单，读者没有对照物。
3. **请求体里的 `min_score` 是重排阈值，不是第一阶段阈值**。这里有一个真实踩到的坑：`retrieval_query_of` 会把请求体的 `min_score` 折进 `RetrievalQuery.min_score`（第一阶段阈值），于是 `min_score=0.5` 会**先按余弦把召回切掉、再按重排分切一次**——实测第一版就是 `count=0 / dropped_by_rerank=1`。修法是显式清空折进查询的那一份（`replace(retrieval_query_of(req), min_score=None)`），并写进 docstring。

这个坑值得停一下：它是"两个不同阶段的参数共用一个字段名"造成的。**同一个字段名在两层有不同含义时，"传下去"永远比"算清楚"更容易写，也更难发现错了。** 用例 `test_min_score_only_cuts_once_and_on_the_rerank_side` 断言 `before_ids` 仍是八条 + `dropped_by_rerank == 7`，把"只切一次、切在重排侧"钉死。

`GET /retrieval/rerank/status` 的 `note` 字段里有一句诚实的声明：**这里端出来的是这台机器上那一个替身与它的缺省参数**，不代表生产配置。它还会如实报告 `enabled=False`（默认值），因为"缺省关闭"是一个必须能看见的事实。

`POST /retrieval/rerank/compare` 刻意**不设重排阈值**：阈值改变的是名单长度，不是排序质量，混进对照表会让"提升"同时指两件事。它也**不选路**（测的是缺省检索路径），并且声明它**不代表真实重排模型的收益**——三条指标只依赖"名单 + 金标准"，与用哪个模型无关。

## 第十一章：走读路线与自测清单

### 11.1 30 分钟走读路线（从外到内）

## 常见误区

**1. "重排就是再排一遍，把分数大的放前面。"** 为什么错：重排的分数与第一阶段的分数是**两个口径**，`score` 从头到尾没被改过，`rerank_score` 是另一个字段。正确理解：重排改的是**次序**，而"次序"这个信息不在 `score` 里（重排开启后 `score` 序列甚至不再单调）。证据：第六章 6.3 节实测 `score 序列 [0.48, 0.0, 0.36, 1.0, 0.96] 不再单调`；`retrieval/rerank.py` 模块 docstring 的"与既有包的接缝"一段。

**2. "全库都重排才准，只排前 N 条是偷工减料。"** 为什么错：交叉编码器对 N 篇文档是 N 次前向推理，全库重排的成本不是"多一点"，而是这个功能根本不可用。正确理解：两段式是**标准姿势**，不是折中——第一阶段追求"别漏"，第二阶段追求"排准"，两者的成本量级不同。证据：模块 docstring 第 14~26 行"贵多少必须写出来"；`DEFAULT_RERANK_TOP_N = 20` 的常量注释。

**3. "窗口外的条被打了很低的分。"** 为什么错：它们**一条都没有被打分**（`scored=False`、`features={}`），`score=0.0` 的含义是"没有分"，不是"最不相关"。正确理解："没有分"是事实，"最不相关"是结论，两者必须分得开。证据：演示脚本第 2 节实测 `没打分：['d-12', 'd-05', ...]（score=0.0、scored=False、stage1_rank 保持原值）`；`rerank_hits` 在 `notes` 里的无条件注记。

**4. "`min_score` 会把不相关的尾部也切掉。"** 为什么错：阈值只作用于 `scored=True` 的那一批，尾部**没有分数可切**。正确理解：`top_n=5、min_score=2.0` 时窗口被切光，但名单里仍有 7 条（窗口外那批）。证据：演示脚本第 5 节实测 `窗口外的 7 条：... 没有一条被阈值切掉`。

**5. "阈值切光窗口就等于空结果。"** 为什么错：`empty_reason` 是否非空取决于**整份名单**是否为空，而不是窗口是否为空。正确理解："切光窗口"与"空结果"是两件事，只有 `top_n` 覆盖了全部候选时后者才成立。证据：同上实测两行对照（`命中 7 条、empty_reason=（空串）` 与 `命中 0 条、empty_reason=重排阈值 2.0 把窗口内的 12 条全切掉了`）。

**6. "`blend` 就是把两份分数加起来取平均。"** 为什么错：两份分数的量纲不可比（余弦 ∈ [-1,1]、BM25 ∈ [0,∞)、RRF ~0.03、重排分 ∈ [0,1]），直接加权等于让量纲差冒充相关性差。正确理解：必须先**各自** min-max 归一化到 [0,1] 再加权，而且这一步与 day067 的 `fusion` 复用同一个函数。证据：`fusion._min_max_normalize` 的调用；演示脚本第 4 节的归一化中间值表。

**7. "归一化之后的分数是绝对量，可以直接存起来比较。"** 为什么错：归一化只在**这一次窗口内**做，同一篇文档的归一化分随窗口变化。正确理解：它只保证"同一次重排内部可比"，而这正是加权求和需要的全部。证据：演示脚本第 4 节实测 `d-12 的 blended 0.477444（top_n=6）→ 0.657444（top_n=8），差 +0.180000`。

**8. "`min == max` 时要除零，所以该特殊处理成 0 或者抛异常。"** 为什么错：窗口内所有分数相同时（例如只切到 1 条），min-max 的跨度是 0，此时**整批都归一化成 1.0**。正确理解：判据是**精确零跨度**，而且"全都一样"意味着"它们并列"，归一化成同一个值（0 或 1）都能保住并列关系，选 1.0 是因为它不与"最低分"混同。证据：`fusion._min_max_normalize` 的 `high - low <= 0.0 → 全部 1.0`。

**9. "并列时由 `record_id` 说算。"** 为什么错：第二键是 `stage1_rank`（输入序列的位置），`record_id` 只是第三键的防御性兜底。`d-05 < d-11` 只是碰巧与 `stage1_rank` 同向。正确理解：把并列造得更极端（只换输入顺序）就能看出次序**跟着输入位置走**。证据：演示脚本第 6 节实测 `输入 ['tie-b','tie-a'] → ['tie-b','tie-a']`。

**10. "`top_n=0` 就是关掉重排。"** 为什么错：`top_n` 的校验是 `>= 1`，给 0 直接报 `RerankError`——"只对前 0 条打分"不是一个请求。正确理解：要关掉重排请把 `rerank_enabled` 设为 `False`（或者不传），两条路径的语义完全不同。证据：`rerank.py` 的错误消息原文与 `tests/test_rerank_core.py` 里那条同名用例。

**11. "重排缺省就开着了，装上快照就生效。"** 为什么错：`retrieval_rerank_enabled` 的默认值是 `False`，而且这是一个刻意的决定——打开之后结果集合的次序会变（还可能改变多样性命中的成员）。正确理解：新能力默认不生效，`GET /retrieval/rerank/status` 会如实报告 `enabled=false`。证据：`config.py` 该项的注释；演示脚本第 9 节"关闭时的名单 == 根本没配过重排的检索器给的名单：True"。

**12. "`extra` 里写错键名最多是不生效。"** 为什么错：清单外的键会**报错**（由融合层与重排层两份封闭清单的并集判定），"静默忽略一个覆盖参数会让调用方以为它生效了"。正确理解：把 `mode` 拼成 `mod` 会立刻失败，而不是"看起来只是没有变化"。证据：`RERANK_OVERRIDE_KEYS` 的常量注释；`hybrid._resolve_fusion` 的错误消息。

再补三条同性质的（写下来省一次排查）：

```text
13. "换 batch_size 会改变分数"      → 不会：特征逐条算，batch 只改变"分成几次算"；空列表连批次
                                    都不产生（"算过 0 批" ≠ "算过 1 批空批"）
14. "explain() 里'只对前 N 条打分'可以随手换成别处那个数字" → 必须读 params["top_n"]（回落
                                    window）：摘要顶层没有 top_n，按顶层键读会渲染成"只对前 0 条
                                    打分"，一句与同一行里 scored 自相矛盾的诊断（本机实测踩过，
                                    已修）
15. "重排分可以当成'相关性'读"      → 教学替身没有真实语义（认不出同义改写、读不懂语序），
                                    重排分只能用于**相对排序**；生产环境请把 BaseReranker
                                    换成真实重排模型
```

## 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 两段式（召回 → 重排） | 交叉编码器比双塔贵两个数量级，全库重排不可用 | `rerank.py` 模块 docstring |
| 教学级替身 + 诚实命名 | 离线/确定/零依赖是硬约束；换来的是分数可手算 | `CrossEncoderReranker` / `DEFAULT_RERANK_MODEL` |
| 四个可手算特征 | 覆盖、整句、邻近、长度各自替代真实模型的一种能力 | `RerankFeatures` / `RERANK_FEATURE_NAMES` |
| 权重和逐位等于 1.0 | 保证分数落在 [0,1]，`min_score` 才有绝对含义 | `FEATURE_WEIGHTS` 的构造期校验 |
| 复用 `lexical.tokenize` | 重排与关键词路必须是同一套分词，否则同一问题两份答案 | `CrossEncoderReranker.features_of` |
| 窗口纪律（只对前 N 条打分） | 成本从 O(候选) 降到 O(N)，代价是第 N+1 条没机会 | `rerank_hits` 第 3 步 |
| 窗口注记无条件进 `notes` | 把"有边界的改进"说成"全面的改进"是失真 | `_build_notes` |
| 尾部 `scored=False` / `score=0.0` | "没有分"与"最不相关"必须分得开 | `RerankHit` |
| 两种模式 `replace` / `blend` | 信不信第一阶段的分数是业务判断，不是技术判断 | `RERANK_MODES` / `rerank_hits` 第 5、7 步 |
| 复用 `fusion._min_max_normalize` | 跨阶段量纲不可比；同一条纪律只写一份实现 | `blend` 分支 |
| 归一化在窗口内做、且先归一后落刀 | 先切再归一化会让"切掉几条"改变其余每条的 blended 值 | `rerank_hits` 的顺序 |
| 排序键三键 `(-score/stage1/blended, stage1_rank, record_id)` | 不确定性不来自算法，来自没写下来的排序规则 | `rerank_hits` 的排序 |
| 阈值只切 `scored=True` 那一批 | 尾部没有分数可切；"切光窗口"不等于"空结果" | `rerank_hits` 第 6 步 |
| 第四个减法 `dropped_by_rerank` | 每个数字对应一个旋钮；合并一个 `dropped` 会让问题无法回答 | `RetrievalResult` |
| `_diagnose` 新增 `dropped_by_rerank` 参数 | 否则切光窗口会被诊断成 `no_data`（主动误导） | `retriever._diagnose` |
| 重排插在多样性之前 | 先裁会让被裁掉的候选再也回不到重排器眼前 | 单路第 6.5 步 / 混合第 10.5 步 |
| 第 8 步只重编号不重排 | 重排分不在 `score` 里，按 `score` 再排一遍会静默抹掉结论 | `retriever._renumber` |
| `_rebuild_hits` 提到模块级 | 两条流水线共用一份写回，两份实现一定会分家 | `retriever._rebuild_hits` |
| `RerankError` 继承 `QueryError` | 参数写错是调用方的问题，端点"参数一律 400"的通道不必加分支 | `errors.py` |
| `extra` 封闭清单 + 覆盖进 `notes` | 静默忽略一个覆盖参数会让调用方以为它生效了 | `RERANK_OVERRIDE_KEYS` |
| `replace` 下给 `weight` 只记录不报错 | 与 `fusion` 的"矛盾意图"不同，这里是无害的冗余 | `rerank_hits` 的 `notes` |
| `measure_lift` 只检索一次 | 让 before/after 只差"有没有重排"一个变量 | `measure_lift` |
| `lift` 用差值不用比值 | `before=0` 时比值是无穷，而它恰是最有价值的提升 | `LiftReport` |
| 三条指标 + 负提升也要报 | 评估工具必须能诚实报坏消息，否则好消息也不可信 | `LiftReport.per_query` |
| 端点的 `min_score` 显式清空折进查询的那一份 | 同一个字段名在两层含义不同时，"传下去"最容易错 | `api/routes.py` 的 `POST /retrieval/rerank` |

今天埋下的伏笔：

```text
RerankResult 摘要进 RetrievalResult.rerank 与 explain()
    day069 的生成链路会把"这一批依据的排序质量"写进答案的溯源信息——
    引用编号按次序给，而次序现在是重排之后的次序，不是第一阶段给的次序。
```
