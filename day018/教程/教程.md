## 第一章：三类原语的设计哲学 —— 谁掌握控制权

### 1.1 为什么协议要区分 Resources / Tools / Prompts

day016 我们已经知道 MCP 把 Host 应用的能力分为三类原语。今天深入一层：这个分类不是随意的功能罗列，而是按**"控制权在谁手里"**划分的：

| 原语 | 控制权 | 谁决定何时使用 | 类比 |
|------|--------|----------------|------|
| **Resources** | 应用可控（Application-controlled） | Host 应用（如 IDE 自动附加当前文件） | 文件/数据 |
| **Tools** | 模型可控（Model-controlled） | LLM 自主决定是否调用、传什么参数 | 函数/API |
| **Prompts** | 用户可控（User-controlled） | 用户显式选择（如斜杠命令、快捷按钮） | 模板/宏 |

理解这个划分，才能回答工程中最常见的问题："我这个功能该注册成哪种原语？"

### 1.2 Tools：模型可控原语

Tool 的本质是**把一部分决策权让渡给 LLM**。你只负责声明"有这么一个函数、它干什么、参数长什么样"，至于什么时候调、传什么参数，由模型在推理过程中自主决定。

这带来一个关键推论：**Tool 的接口文档（name / description / schema）不是写给程序员的，是写给 LLM 的。** 模型选择工具时唯一的依据就是这些元数据。一个 description 含糊的工具，模型要么不敢用、要么乱用；一个参数 schema 缺 description 的工具，模型只能瞎猜参数格式。第二章会详细展开这一点。

对照我们的项目：day004 的 `CalculatorTool` 通过 ReAct 提示词把 `to_schema()` 拼进上下文，是"项目内部自定义格式"的工具暴露；今天注册的 MCP Tool 则是"行业标准格式"的暴露。同一份计算逻辑，两种暴露方式——**重构的是接口层，不是业务逻辑**。

### 1.3 Prompts：用户可控原语

Prompt 原语容易被误解为"又是一个模板字符串工具"。它的协议意义在于：**提示词从开发者的代码资产，变成用户可发现、可选择的产品功能**。

想象 Claude Desktop 里的斜杠命令：用户输入 `/research_report topic=RAG`，客户端向 server 请求这个 prompt，server 把模板参数填充后返回完整的消息列表，客户端再把这些消息作为对话内容发给 LLM。整条链路里：

- **Server 负责**：模板内容的质量（这是提示词工程的主战场）；
- **Client 负责**：把模板暴露成 UI 入口（斜杠命令、按钮、右键菜单）；
- **用户负责**：显式触发并填参数。

对比 Tools 就能看清设计哲学：**Tools 把选择权给模型，Prompts 把选择权还给用户**。适合做成 Prompt 的是那些"用户知道自己想要、但懒得每次重写"的标准化意图——调研报告、代码审查、会议纪要。适合做成 Tool 的是"任务过程中模型自己判断需要"的能力——计算、检索、查询。

### 1.4 一个判断框架

拿到一个新能力，问三个问题：

```text
它产出的是数据还是行为？          数据 → Resource；行为 → 继续问
触发时机该由谁决定？             用户显式触发 → Prompt
                                模型在推理中自主决定 → Tool
                                应用根据上下文自动附加 → Resource
```

我们今天注册的三个能力正好覆盖两类：calculator / knowledge_search 是"模型推理中需要时自主调用"（Tool），research_report 是"用户显式发起一次调研"（Prompt）。

> 思考题：知识库文档（kb-react、kb-planner 这些条目本身）更适合暴露成 Resource 还是 Tool？提示：区分"读取某份已知文档"与"检索未知的相关文档"——前者是确定性寻址，后者是模型发起的查询行为。

## 第二章：把 CalculatorTool 变成 MCP Tool —— 复用而非重写

### 2.1 FastMCP 的装饰器魔法

完整代码见 [mcp_server/server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/server.py)。核心只有几行：

```python
app = FastMCP("smart-research")

_calculator = CalculatorTool()

@app.tool(name=_calculator.name, description=_calculator.description)
def calculator(expression: str) -> str:
    """计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'."""
    return _calculator.execute(expression=expression)
```

`@app.tool()` 装饰器做了三件事：

1. **从函数签名推导 inputSchema**：`expression: str` 被翻译成 JSON Schema `{"properties": {"expression": {"type": "string"}}, "required": ["expression"]}`——类型标注第一次同时服务了人类读者、静态检查和协议层三方。
2. **从 docstring / description 提取工具描述**：这段文字会原样出现在 `tools/list` 的响应里，成为 LLM 选择工具的依据。
3. **注册到 FastMCP 的内部路由表**：之后 `tools/call` 请求按 name 路由到这个函数，参数校验、返回值序列化（包装成 `TextContent`）全自动完成。

### 2.2 为什么"包装"而不是"重写"

一个偷懒的诱惑是：反正 FastMCP 工具就是一个普通函数，直接在 `calculator` 函数体里重写一遍 AST 求值逻辑，不需要 `CalculatorTool` 了。这是错的，原因有三：

1. **逻辑会有两份副本**。AST 白名单（`_BIN_OPS`、`_UNARY_OPS`、`_safe_eval`）是安全敏感代码——它防御的是"模型/用户传入恶意表达式"。两份副本必然漂移：将来给白名单加 `//` 运算符时改了一处忘了另一处，安全边界就出现裂缝。
2. **测试资产会失效**。day004 为 `CalculatorTool` 写的测试覆盖的是 `execute()`；如果 MCP 层另起炉灶，那些测试对新实现毫无约束力。
3. **违反既有架构契约**。`BaseTool` 体系（name/description/parameters/execute）是项目内工具的统一抽象，ReactAgent、ToolRegistry 都建立在它之上。MCP 是**新的暴露通道**，不是**新的工具体系**。

正确的姿势是**适配器模式**：MCP tool 函数是一个薄薄的壳，持有 `CalculatorTool` 实例，把协议层的调用转发给 `execute()`。业务逻辑只有一份，暴露通道可以有 N 份——今天是 ReAct 提示词和 MCP，明天可能是 OpenAI function calling，业务逻辑都不动。

```text
                    ┌─────────────────────┐
                    │  CalculatorTool     │  ← 唯一业务逻辑（day004）
                    │  AST 白名单安全求值  │
                    └──────────┬──────────┘
              ┌────────────────┼─────────────────┐
              ▼                ▼                 ▼
      ReAct 提示词拼接    MCP @app.tool()    （未来）function calling
      （day005/006）      （今天）
```

### 2.3 参数 schema 如何影响 LLM 的工具选择

这是 Tool 原语里最值得展开的原理点。LLM 决定"调不调 calculator、expression 传什么"时，看到的**只有**这段 JSON：

```json
{
  "name": "calculator",
  "description": "计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'",
  "inputSchema": {
    "properties": {"expression": {"type": "string", "title": "Expression"}},
    "required": ["expression"],
    "type": "object"
  }
}
```

schema 的每个字段都在影响模型行为：

- **name 是路由键也是语义信号**。`calculator` 这个名字让模型在"需要算术"时自然联想到它；如果叫 `tool_a7f3`，调用率会显著下降。
- **description 决定"何时用"**。"支持 + - * / ** % 与括号"这句不只是说明能力，也在划边界——模型读到它就知道不能把这个工具当符号求解器用。description 里的**示例**（`'2 + 3 * (4 - 1)'`）是 few-shot 信号，直接教模型参数的格式。
- **类型约束决定"怎么用对"**。`"type": "string"` 告诉模型表达式是字符串不是数字；`"required"` 列表告诉它哪些参数不能省略。
- **默认值影响调用成本**。对比 `knowledge_search(query: str, top_k: int = 3)`：top_k 有默认值，模型可以只传 query，schema 里 top_k 不出现在 required 中——**必填参数越少，模型构造合法调用的成功率越高**。

一个可操作的推论：**工具调用的稳定性问题，优先从 schema 下手排查，而不是先怀疑模型能力。** 模型把日期写成 "2024年8月13日" 而你的 schema 期望 ISO 格式？在参数的 description 里写明 "YYYY-MM-DD 格式"，问题往往立即消失。这和 day010 设计 PLAN_PROMPT 是同一条原则：**凡是需要被消费的输入，都要显式锁定结构**。

```python
    return "\n".join(lines)
```

两个设计细节值得说清：

**（1）为什么用 `_toy_embed` 而不是 MockEmbedding？** day009 的 `MockEmbedding` 是 SHA-256 哈希伪向量——完全确定，但没有任何语义，"向量检索"这个查询和向量库文档的余弦相似度是随机的。做演示工具时检索必须"真的像在工作"，所以 server.py 里实现了一个**字符二元组哈希向量**：共享字符二元组的文本会在相同维度上取值，余弦相似度因此能反映表层文本重叠。它依然离线、确定、零依赖，但查询"ReAct 推理"会稳定命中 kb-react 条目。教学代码里这是一个有意的权衡：牺牲语义真实性，换取行为可演示性。

**（2）返回值为什么拼接成字符串？** MCP tool 的返回值最终要进 LLM 的上下文。LLM 消费的是文本，不是 Python 对象——把检索结果格式化成带相似度分数的编号列表（`[1] (相似度 0.812) ...`），模型既读得懂内容，也能感知相关性强弱。**Tool 的输出格式是提示词工程的延伸。**

### 2.5 research_report：参数化 Prompt 的实现

```python
@app.prompt()
def research_report(topic: str, depth: str = "详细") -> str:
    """调研报告写作提示词：topic 与 depth 由调用方动态填充."""
    return RESEARCH_REPORT_TEMPLATE.format(topic=topic, depth=depth)
```

FastMCP 对 prompt 函数的处理和 tool 类似：签名变成参数声明（`prompts/list` 里客户端能看到 `arguments: [topic, depth]`），返回值（字符串）被包装成一条 `role="user"` 的消息。

`depth: str = "详细"` 这个默认值在协议层有意义：客户端调用 `get_prompt("research_report", {"topic": "MCP"})` 时可以省略 depth，server 用默认值渲染——**模板的健壮性由默认值兜底，用户的自由度由参数开放**。

注意模板里有一句"调用 knowledge_search 工具检索已有知识，调用 calculator 工具完成必要计算"——Prompt 和 Tool 在这里发生了协同：**模板引导模型去使用同 server 暴露的工具**。这是 MCP 设计的精妙处：三类原语不是孤立的，一个设计良好的 server 让它们互相引用、互相增强。

## 第三章：JSON-RPC 2.0 —— MCP 的通信骨架

### 3.1 为什么用 pydantic 再建模一遍

官方 `mcp` SDK 内部有自己的消息类型，理论上我们不需要 `protocol.py`。但教学项目里显式建模有三个价值：

1. **让协议结构可见**。`JsonRpcRequest(id, method, params, jsonrpc="2.0")` 六个字段就是 MCP 全部通信的最小骨架——请求/响应/错误三种消息，靠 `id` 配对。看它一眼胜过读十页协议文档。
2. **边界校验**。`ToolDescriptor(name, description, input_schema)` 这类能力描述符是 Client 与 Server 之间的契约数据，pydantic 在构造时就完成类型校验，非法数据出不了边界。
3. **解耦 SDK 版本**。`McpClient.list_tools()` 返回的是我们自己的 `ToolDescriptor` 而不是 SDK 的 `mcp.types.Tool`——上层代码不依赖 SDK 类型，将来 SDK 升级改字段名，改动只收在 client.py 一处。

### 3.2 三种消息的分工

```text
Client                                    Server
  │  {"jsonrpc":"2.0","id":1,"method":"tools/call","params":{...}}  │
  │ ──────────────────────────────────────────────────────────────▶ │
  │                                                                 │
  │  成功: {"jsonrpc":"2.0","id":1,"result":{...}}                   │
  │  失败: {"jsonrpc":"2.0","id":1,"error":{"code":...,"message":...}}│
  │ ◀────────────────────────────────────────────────────────────── │
```

- **Request** 必须带 `id`——它是请求-响应配对的唯一凭据。stdio 管道上消息可能交错（server 可以主动发通知/请求），没有 id 就无法知道哪个响应对应哪个请求。
- **Response 与 Error 互斥**：JSON-RPC 2.0 规定成功响应只有 `result`、错误响应只有 `error`，绝不同时出现。我们的 `JsonRpcResponse` 和 `JsonRpcError` 是两个独立模型，正是这个互斥关系的类型化表达。
- **Error 的 code 是协议级语义**：如 `-32601` Method not found。注意区分两类失败——**协议级错误**（方法不存在、参数非法，走 error 字段）与**业务级错误**（表达式算不出来，走正常 result 里的文本 `"计算失败: ..."`）。我们的 calculator 把除零、语法错误都归为业务级：工具被"成功调用"了，只是结果是失败说明。这样 LLM 能读到失败原因并自我修正，而不是收到一个无法理解的协议异常。

### 3.3 能力描述符：三类原语的元数据

`ResourceDescriptor` / `ToolDescriptor` / `PromptDescriptor` 分别对应三类原语的 `list` 响应条目。对比它们的字段就能看出原语差异：

```python
class ToolDescriptor(BaseModel):
    name: str
    description: str = ""
    input_schema: dict[str, Any] = Field(default_factory=dict)   # ← Tool 独有：JSON Schema

class PromptDescriptor(BaseModel):
    name: str
    description: str = ""
    arguments: list[str] = Field(default_factory=list)           # ← Prompt 独有：参数名列表
```

Tool 需要完整 JSON Schema，因为**模型要在没有人类介入的情况下构造合法参数**，schema 必须精确到类型与约束；Prompt 只需要参数名列表，因为**参数由用户填写**，用户看得懂 `topic` 就知道该填什么。再次印证第一章：元数据的详略，由"谁来消费它"决定。

## 第四章：stdio 传输与 McpClient —— 进程模型详解

### 4.1 stdio 传输的进程模型

MCP 支持多种传输，stdio 是最常用的一种（Claude Desktop 的本地 server 全是 stdio）。它的进程模型：

```text
┌──────────────────── Client 进程（你的 Agent / Claude Desktop）───────────────┐
│                                                                            │
│   McpClient ──▶ stdio_client ──▶ 创建子进程，接管其 stdin/stdout 管道        │
│                                      │                                     │
└──────────────────────────────────────┼─────────────────────────────────────┘
                                       ▼ spawn
┌──────────────────── Server 子进程（python -m smart_research_agent.mcp_server.server）┐
│                                                                                      │
│   stdin  ◀── JSON-RPC 请求（client 写入）                                             │
│   stdout ──▶ JSON-RPC 响应（server 写入，协议独占！）                                  │
│   stderr ──▶ 日志、诊断（自由使用）                                                    │
└──────────────────────────────────────────────────────────────────────────────────────┘
```

要点：

- **Server 是 Client 的子进程**。生命周期由 Client 托管：`connect()` 拉起，`close()` 终止。不需要预先部署、没有端口、没有网络——这就是为什么本地 MCP server 配置只需一行命令。
- **stdin/stdout 是全双工管道**。Client 写 server 的 stdin，读 server 的 stdout。消息以换行分隔（newline-delimited JSON）。
- **stdout 被协议独占**。这是 stdio 传输最严的纪律，见 4.2。
- **每个连接一个 server 实例**。多个 client 各拉各的子进程，天然进程级隔离——一个 server 崩溃不波及其他会话，代价是无法共享内存状态（需要共享时换 HTTP/SSE 传输，day019 展开）。

### 4.2 事故复盘：一行 stdout 日志如何击垮协议

今天开发中真实发生的事故，值得作为案例固化下来。初版 stdio 端到端测试报错：

```text
pydantic_core._pydantic_core.ValidationError: 1 validation error for JSONRPCMessage
  Invalid JSON: trailing characters at line 1 column 5
  [input_value="2026-08-30 07:18:06 | IN...culator('6 * 7') = 42\r", ...]
```

原因链：server 侧 `calculator()` 里有一行 `logger.info("calculator(%r) = %s", ...)`，而项目 logger（day001 写的）控制台 handler 指向 `sys.stdout`。于是 stdout 管道里 JSON-RPC 消息和日志行交错出现，client 的解析器读到一行日志，当成 JSON 解析，直接炸掉。

修复是把 logger 的控制台输出从 `sys.stdout` 改成 `sys.stderr`（见 [utils/logger.py](../源码/smart-research-agent/smart_research_agent/utils/logger.py)）。这不只是 MCP 的补丁，而是 Unix 的经典纪律：**stdout 是程序输出的契约通道，stderr 是诊断信息的自由通道**。`curl`、`grep`、所有可管道组合的命令行工具都遵守它；stdio MCP server 把这个纪律的后果放大到了"违反即协议崩溃"的程度。

> 思考题：如果 server 里有人写了 `print("debug info")`，会发生什么？为什么 FastMCP 官方文档建议 server 侧日志一律走 stderr 或文件？

### 4.3 McpClient 的实现要点

完整代码见 [mcp_server/client.py](../源码/smart-research-agent/smart_research_agent/mcp_server/client.py)。四个关键设计：

**（1）连接是两个异步上下文管理器的嵌套。**

```python
self._stack = AsyncExitStack()
read, write = await self._stack.enter_async_context(stdio_client(self._params))
self._session = await self._stack.enter_async_context(ClientSession(read, write))
await self._session.initialize()
```

`stdio_client` 负责拉子进程、建管道；`ClientSession` 负责在其上跑 JSON-RPC 会话；`initialize()` 完成 MCP 握手（交换协议版本与双方能力声明）。用 `AsyncExitStack` 统一托管两层资源，`close()` 时一次 `aclose()` 按逆序全部清理——**嵌套资源的打开顺序与关闭顺序相反**，这和文件锁、数据库事务是同一个模式。

**（2）PYTHONPATH 注入保证子进程加载"这份代码"。**

```python
env["PYTHONPATH"] = os.pathsep.join(
    part for part in [str(_PROJECT_ROOT), env.get("PYTHONPATH", "")] if part
)
```

本机的 venv 里装着 day010 的 editable 版 `smart_research_agent`。不显式注入的话，子进程 `python -m smart_research_agent.mcp_server.server` 会导入旧代码（里面根本没有 `mcp_server` 模块）而报 ModuleNotFoundError。**子进程不继承父进程的 import 解析结果，只继承环境变量**——跨进程边界的依赖必须显式传递。

**（3）未连接时调用要快速失败。**

```python
def _require_session(self) -> ClientSession:
    if self._session is None:
        raise RuntimeError("McpClient 尚未连接，请先 connect() 或使用 async with")
    return self._session
```

异步资源最常见的误用就是"忘了先 connect"。与其让 `self._session.list_tools()` 抛一个莫名其妙的 `AttributeError: 'NoneType'`，不如主动检查并给出可操作的错误信息。这是 day010"防御式解析"思想在 API 设计上的对应物：**错误信息要告诉调用方怎么修**。

**（4）SDK 类型在边界处转换成本项目模型。**

`list_tools()` 把 SDK 的 `mcp.types.Tool` 逐条转成 `ToolDescriptor`，`call_tool()` 把 `content` 列表拼接成纯文本返回。上层调用者面对的始终是项目内类型——3.1 节说的解耦就在这里落地。

### 5.2 为什么包名必须叫 mcp_server

一个会真实咬人的坑：如果包叫 `smart_research_agent.mcp`，那么在某些导入路径下它会遮蔽官方 `mcp` 包，`from mcp.server.fastmcp import FastMCP` 可能解析到我们自己这个空壳上，报出完全误导的 ImportError。**永远不要让本地模块名与依赖的顶层包同名**——这是 Python 导入系统的经典陷阱，`mcp_server` 这个名字是刻意避让的结果。

### 5.3 两层测试策略：内存会话 + stdio 子进程

[tests/test_mcp_tools.py](../源码/smart-research-agent/tests/test_mcp_tools.py) 用两条互补的路径验证同一份 server：

**内存内会话**（大部分测试用这条）：

```python
from mcp.shared.memory import create_connected_server_and_client_session

async def test_call_calculator_returns_correct_result(self):
    async with create_connected_server_and_client_session(app) as session:
        result = await session.call_tool("calculator", {"expression": "2 + 3 * 4"})
        assert result.content[0].text == "14"
```

`create_connected_server_and_client_session` 在同一进程内用内存管道直连 server 与 client——**走的是完整的 MCP 协议栈**（JSON-RPC 编解码、能力协商、路由分发全都在），但不涉及子进程和真实管道。毫秒级、确定性、可调试，适合覆盖所有功能断言。

**stdio 子进程**（集成测试用这条）：

```python
async def test_stdio_end_to_end(self):
    async with McpClient() as client:
        tools = await client.list_tools()
        assert "calculator" in [t.name for t in tools]
        answer = await client.call_tool("calculator", {"expression": "6 * 7"})
        assert "42" in answer
```

真实拉起 `python -m smart_research_agent.mcp_server.server` 子进程，验证进程模型、PYTHONPATH 注入、stdout 纪律这些**只有跨进程才暴露的问题**——4.2 节的日志事故就是这条测试抓出来的。

两条路径的关系正是 day002 测试金字塔的应用：大量功能测试走快而稳的内存会话（金字塔底层），少量集成测试走慢但真实的子进程（金字塔上层）。**全部离线**：没有任何网络访问，也不需要 LLM。

### 5.4 pytest-asyncio 的配置

`pyproject.toml` 里加一行：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
```

`auto` 模式下所有 `async def test_*` 自动被 pytest-asyncio 接管执行，不需要逐个加 `@pytest.mark.asyncio` 装饰器。MCP 的全部客户端 API 都是异步的（网络/子进程 I/O 天然异步），测试也顺势全用 async——**异步不是装饰，是 I/O 模型的如实反映**。

## 第六章：今日总结 —— 标准化暴露的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 按控制权分三类原语 | Tools 模型可控 / Prompts 用户可控 / Resources 应用可控 | 第一章判断框架 |
| MCP tool 包装而非重写 | 业务逻辑一份、暴露通道 N 份（适配器模式） | `server.py` 的 `calculator()` |
| schema 写给 LLM 看 | 模型选工具的唯一依据是 name/description/schema | `@app.tool()` 的元数据 |
| 业务错误走文本返回 | LLM 能读到失败原因并自我修正 | `CalculatorTool.execute` 的 `"计算失败: ..."` |
| JSON-RPC 显式建模 | 协议结构可见 + 边界校验 + 解耦 SDK | `protocol.py` |
| stdout 协议独占 | stdout 是契约通道，日志归 stderr | `logger.py` 的 `StreamHandler(sys.stderr)` |
| 子进程 PYTHONPATH 注入 | 跨进程依赖必须显式传递 | `McpClient.__init__` |
| 两层测试策略 | 内存会话测功能（快稳），stdio 子进程测集成（真实） | `tests/test_mcp_tools.py` |

今天埋下的伏笔，后续几天会回收：

- **SSE/HTTP 传输**（day019）：stdio 是"一 client 一 server 进程"的本地模型，要服务化部署、要并发会话，就得换网络传输。
- **Agent 接入 MCP 工具**（day020）：今天的 McpClient 是独立演示，下一步是把 `list_tools()` 发现的工具动态注册进 `ToolRegistry`，让 ReactAgent 透明地调用 MCP 工具——M1 的 Agent 体系与 M2 的 MCP 体系在那里合流。
