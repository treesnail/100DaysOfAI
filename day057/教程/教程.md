## 第一章：为什么"洗完一次"不够

### 1.1 day048 留下的三个空缺

| 空缺 | 具体表现 | 本课怎么补 |
|------|---------|-----------|
| **只防精确重复** | `dedupe_key` 是 prompt 的 SHA-1，字符级不同就放行；"同一段内容加了一句开场白"完全抓不到 | `fingerprint.py` + `dedup.py`：shingle + MinHash 近重复 |
| **只能"通过 / 拒绝"** | 七条布尔规则给不出顺序，而配比削减与增强补样都要按"好多少"排序 | `quality.py`：五维加权连续分 |
| **没有"下一批"的概念** | `DatasetCleaner.run()` 是纯函数，每次都得把全部数据重洗一遍；没有版本、没有指纹 | `pipeline.py`：六阶段 + 清单 + 增量合并 |

第三个空缺最容易被忽略：**一次性脚本与流水线的区别不在代码量，而在有没有"账"**。day048 的 `FilterReport` 已经把清洗这一步记成账了，但它记的是"这一批"，不是"这一批相对上一批"。

### 1.2 六阶段，顺序即策略

```text
clean → quality → near_dedup → mixing → augment → freeze
清洗     五维打分   两级去重       削峰     填谷      打指纹
```

这是 day046 那条纪律（`STAGE_ORDER`：护栏 → 缓存 → 生成 → 归因 → 审核 → 回写）在数据侧的重演：**每一步的位置都有理由，换位就会出问题**。六条理由全部写在 `pipeline.py` 的模块 docstring 里，其中三条值得在教程里再钉一次：

1. **quality 在 near_dedup 之前**：先用便宜的五维打分把明显不合格的筛掉，再去跑昂贵的两两比较（`N²` 次 64 维比较）。反过来也能跑，但会为一批注定被拒的样本付近重复检测的钱。
2. **near_dedup 在 mixing 之前**：近重复会让某一组"看起来很多"。若不去重就配比，算出来的是重复项堆出来的占比，削掉的也是重复项——**用一套虚拟的数量做了一轮真实的削减**。
3. **mixing 在 augment 之前**：先削峰、后填谷。反过来，刚补进来的样本可能因为所属组超额而被立刻砍掉，白花一次增强。

### 1.3 `near_dedup` 为什么在流水线里会跑出 0

第一次跑流水线的人多半会盯着这一行发愣：

```text
[near_dedup] 进  37 → 出  37 | 丢弃   0 新增   0   （精确 0 / 近重复 0，阈值 0.7）
```

**这不是功能失效，而是数据本身干净**：那 37 条是人工撰写的种子 + 评估轨迹 + 红队样本，不存在"同一段内容被复制两遍"。近重复能力要到 `augment` 阶段才有机会被行使——而且**一个能被解释的 0，比一个含糊的 3 更有价值**：它让评审知道"这一层到底有没有在工作"（第 2.4 节会给出阈值敏感性表，那里能看出它确实在工作）。

## 第二章：近重复指纹 —— 三件套与一次真实的阈值标定

### 2.1 先划清边界：近重复 ≠ 语义重复

这是本课最容易被做错的一件事，所以放在最前面。实测七组文本对（`scripts/domain_data_demo.py` 第 8 节）：

| 场景 | 精确 Jaccard | MinHash 估计 | 精确键相同 |
|------|-------------|-------------|-----------|
| 逐字相同 | 1.0000 | 1.0000 | True |
| 加 2 字前缀 | 0.8667 | 0.8906 | False |
| 加 6 字前缀 | 0.6842 | 0.5469 | False |
| 尾部追加一句 | 0.6842 | 0.7969 | False |
| 同义改写（换疑问词） | 0.7333 | 0.6875 | False |
| 同义改写（换两个词） | **0.3000** | **0.3438** | False |
| 完全不同的问 | 0.0000 | 0.0000 | False |

最后两行是重点：**"怎么评价 RAG 的检索效果？"与"如何评估 RAG 的检索质量？"意思几乎一样，Jaccard 只有 0.3000。** 把阈值调到 0.3 去"抓语义重复"是错的——同一个领域里正常的不同提问会全部被判死，数据集直接被清空。

> **语义重复要靠 embedding 与向量检索**（day041 的 `EmbeddingProvider`、M6 的向量数据库），那是另一条链路、另一份报告。两件事分开做，才说得清"到底丢了什么"。

### 2.2 shingle：为什么是字符级，为什么 `k=3`，以及短文本怎么办

```python
def shingles(text: str, *, k: int = DEFAULT_SHINGLE_K) -> frozenset[str]:
```

用**字符** n-gram 而不是词 n-gram：中文没有空格分词，词级切分在中英混排上得不到一致的粒度（"RAG 检索"按词切与"什么是检索增强"按词切，粒度完全不同）；字符 n-gram 对中英混排都成立。

`k=3` 是本课程的经验值：取 2 会让"检索增强"与"检索质量"共享大量 shingle（假重复变多），取 5 会让不足 5 字的提问退化。

**短文本必须特殊处理**，否则会踩一个很隐蔽的坑：

```python
    if len(normalized) < k:
        return frozenset({normalized})
```

若不这样写，短文本的 shingle 集合为空，而**空集合之间的 Jaccard 是 1.0**——所有短文本会被判为"彼此完全相同"，一个"好"字与一个"差"字就成了重复项。

### 2.3 精确 Jaccard 是定义，MinHash 是估计，两者必须并存

```python
def jaccard_exact(left, right) -> float:   # |A ∩ B| / |A ∪ B|，这是**定义**
def minhash_signature(shingle_set, *, num_perm, seed) -> tuple[int, ...]
def estimate_jaccard(left, right) -> float # 相同位次的比例，这是**无偏估计**
```

MinHash 的原理一句话：对 `num_perm` 个随机置换，各自取 shingle 哈希的最小值；两集合签名在位次上相同的比例，就是真实 Jaccard 的无偏估计，标准差约 `sqrt(J(1-J)/num_perm)`。`num_perm=64`、`J=0.5` 时标准差约 0.062。

**把两个函数都留在模块里**，是为了让"估计"与"事实"各有各的名字：测试拿 `jaccard_exact` 当基准去核对 `estimate_jaccard`；报告里需要精确值时用前者，需要排序信号时用后者。**如果只有一个，就会出现"我记得它是精确的"这种无人能反驳的误用。**

置换参数刻意不用 `random.Random`，而是自己实现 SplitMix64：

```python
def _splitmix64(state: int) -> tuple[int, int]:
    state = (state + _SM_GOLDEN) & _MASK64
    value = state
    value = ((value ^ (value >> 30)) * _SM_MUL1) & _MASK64
    ...
```

理由是**置换参数是签名的组成部分**：一旦某个 Python 版本改了 `randrange` 的抽样细节，历史数据集的指纹就会变，版本链断掉。SplitMix64 只依赖整数加减乘与移位，输出可以逐位复现。

同理，shingle 哈希用 `blake2b` 而不是内建 `hash()`：后者对 `str` 默认加盐（`PYTHONHASHSEED`），**跨进程、跨运行都不稳定**。测试里用两个不同 `PYTHONHASHSEED` 的子进程把这件事钉死了。

### 2.4 阈值 0.7 是标定出来的，不是抄来的

这是本课第一个**真正的工程判断**。很多资料给的近重复经验值是 0.8~0.9，但那对应**较长文档**的 shingle 统计。本课在自建探针语料（37 条真实样本 + 16 条逐字复制 + 16 条前缀复制 = 69 条）上实测：

| threshold | 保留 | 精确重复 | 近重复 | 说明 |
|-----------|------|---------|--------|------|
| 0.6 | 40 | 16 | 13 | 抓 13/16 前缀复制 |
| **0.7** | **44** | **16** | **9** | 37 条真实样本零误判 |
| 0.8 | 53 | 16 | **0** | 近重复链路**空转** |
| 0.9 | 53 | 16 | 0 | 同上 |

阈值取 0.8 的后果是：**整条近重复链路一条都检不出来**，而它不会报错、不会告警——报告里"近重复 0"看起来和"数据很干净"完全一样。这就是这类系统里最危险的一种缺陷。

值得记住的还有取整口径的细节：文档里"加 6 字前缀"这一对的精确 Jaccard 是 0.6842，而 MinHash 估计只有 0.5469（**低估**）；"尾部追加一句"的精确值是同样的 0.6842，估计却是 0.7969（**高估**）。同一对真实相似度，估计在两个方向上偏了 ±0.15——**这就是为什么阈值必须留裕度，也是为什么报告里要同时给出相似度而不是只给布尔值**。

## 第三章：两级去重与"下一批怎么接上"

### 3.1 两级不是"更严 / 更松"，而是"确定 / 近似"

| 级别 | 判据 | 成本 | 结论的性质 |
|------|------|------|-----------|
| 精确 | 归一化后 prompt 的 SHA-1 前 16 位（与 day048 的 `dedupe_key` 同定义） | O(1) 查表 | 确定：键相同必然重复 |
| 近重复 | MinHash 签名的 Jaccard 估计 | O(已入库条数) 逐条比较 | 估计：有方差，阈值需留裕度 |

**顺序不能反**：先精确后近似，才能保证"完全相同"这一档永远由确定性判据裁决。若先跑近似，一条与已有样本逐字相同的样本也可能因为签名恰好差一位而被放行——而它本该是 100% 确定的重复项。

还有一个必须与 day048 保持一致的约定：**比较对象是 prompt，不含 output**。理由是"同一个问题配两个不同答案"在监督微调里是**冲突**而不是冗余。近似判定若换成比较整条样本，"同问不同答"就会从"冲突"变成"不同"，报告里的重复数会突然变小——**同一份数据在两套口径下得到两个结论，是数据治理最忌讳的事**。

### 3.2 增量：`add` 而不是"重新洗一遍"

```python
index = NearDuplicateIndex(threshold=0.7)
index.add_many(history)                  # 历史直接视为已接受
kept, report = index.filter(new_batch)   # 新批次跨批次去重
merged = list(history) + kept
```

实测（demo 第 9 节）：

```text
增量合并：历史 20 条 + 新批次 10 条
  去重：10 条进 / 5 条留 | 精确重复 5 / 近重复 0（阈值 0.7） → 合并后 25 条
```

**历史在前**，因此"保留首次出现"的语义在跨批次场景下自然成立——同一个问题已经在历史里，就保留历史里那一条。代价是**顺序敏感**，而顺序被显式写进了版本链（`parent_fingerprint`）。

`pipeline.merge_with_history` 刻意**不做**清洗、打分、配比与增强：它是"更新"，不是"重建"。两条路都保留，因为它们回答不同的问题——**增量回答"新来的这批里有多少是真正新的"，重建回答"按今天的标准，整份数据集应该长什么样"**。

## 第四章：五维质量打分 —— 门槛 0.6 到底在拦什么

### 4.1 五个维度、五个权重

维度表由代码生成（`render_dimension_table()`），文档与实现同源：

| 维度 | 含义 | 计算 | 挡住的故障 | 权重 |
|------|------|------|-----------|------|
| `length` | 输出长度落在舒适区 | 梯形分：`<8` / `8~40` 上升 / `40~800` 满分 / `800~4000` 下降 | 太短没信息量、太长是粘贴长文 | 0.25 |
| `repetition` | 自我重复程度 | 3-gram 重复率反向线性：`<=0.10` 满分、`>=0.35` 零分 | 车轱辘话（模型退化的典型输出） | 0.25 |
| `structure` | 结构完整性 | 三档：结构化收尾 1.0 / 有句末标点 0.75 / 都没有 0.25 | 半句话、被截断的输出 | 0.20 |
| `traceability` | 来源可追溯性 | `source` 与 `license` 各计 0.5 | 来源不明、许可证不明的语料 | 0.15 |
| `placeholder` | 无占位符 | 命中 TODO/待补充/lorem 记 0.0，否则 1.0 | 答案没写完的占位样本 | 0.15 |

这些阈值**全部由实测分布标定**：本课程 37 条样本的输出长度落在 67~165 字（中位数 78），所以 `40~800` 的满分平台让全部样本拿满分；3-gram 重复率中位数 0.0 / 均值 0.0453 / 最大 0.3767，所以反向区间取 `0.10~0.35` 能把"车轱辘话"和"正常复用术语"分开；有许可证元信息的 16/37、有结构化收尾的 5/37，这两个差额让 `traceability` 与 `structure` 成为真正有区分度的两维。

### 4.2 梯形分与反向线性分：为什么不用平滑曲线

```python
def band_score(value, *, low, ideal_low, ideal_high, high) -> float:
    if value <= low or value >= high:
        return 0.0
    if value < ideal_low:
        return (value - low) / (ideal_low - low)
    if value <= ideal_high:
        return 1.0
    return (high - value) / (high - ideal_high)
```

未使用 sigmoid 之类是刻意的：**梯形分的每一段都能手算复核**。报告里写"这条样本长度分 0.375"，评审一眼就能还原成"输出 20 字，落在 8~40 的上升段"。曲线给不出这种可核对性。

四段点必须满足 `low <= ideal_low <= ideal_high <= high`，否则直接抛 `DomainDataError`——退化的区间（例如 `ideal_low > high`）会让函数静默返回错误的分数。

### 4.3 门槛 0.6 的精确含义（必算，否则是玄学）

总分满分 1.0，门槛 0.6 精确等价于"**加权质量损失超过 0.4 才拒**"。五维里最大的权重是 0.25，于是有一条**很容易被误读**的性质：

> **任何一个维度单独归零，总分都还在 0.75 以上，不会被拒。**

第一版教程里我把它写成"任一个维度掉到 0 就会跌破门槛"——**写错了**。现在它是一条可执行的测试：

```python
@pytest.mark.parametrize("zeroed, survived", [
    ("length", 0.75), ("repetition", 0.75), ("structure", 0.80),
    ("traceability", 0.85), ("placeholder", 0.85),
])
def test_single_zero_dimension_never_falls_below_threshold(zeroed, survived):
    ...
```

这不是漏洞，而是与 day048 的硬规则**刻意分工**：单点致命问题（占位符答案、空指令、超长粘贴）由那七条布尔规则一票否决；质量分负责"都合格但有好劣"的排序，因此必须对单点不敏感。要被拒，得**多个维度同时不合格**——实测两类真实脏样本：

| 样本 | 五维明细 | 总分 | 结论 |
|------|---------|------|------|
| `"TODO：待补充。"` | length 0.0312 / repetition 1.0 / structure 0.75 / traceability 0.5 / placeholder **0.0** | **0.4828** | 拒（最低维 `placeholder`） |
| `"好的好的好的好的好的"` | length 0.0625 / repetition **0.0** / structure 0.25 / traceability 0.5 / placeholder 1.0 | **0.2906** | 拒（最低维 `repetition`） |
| 正常答案（无许可证） | length 0.6875 / repetition 1.0 / structure 0.75 / traceability 0.5 / placeholder 1.0 | 0.7969 | 通过 |

两条被拒样本都是两个以上维度同时不合格，这正是门槛设计想筛的那一类。

### 4.4 覆盖不了的维度就不打分 —— 以及由此得到的一个诚实结论

`format`（格式合规）、`refusal`（拒答边界）、`factuality`（事实性）本课**一律不给分数**——它们需要结构化或人工判定，用字符级统计量冒充"事实正确"比承认测不了更糟（day055 的同一条纪律）。

这条纪律有一个**反直觉的推论**值得单独说：把 day055 的四个劣化算子造出的产物喂进这套打分器，总分几乎不变：

```text
normal score:          total=0.9500
degrade drop_tail:     total=0.9500  （五维与正常样本完全相同）
degrade pad_verbose:   total=0.9500
degrade add_overclaim: total=0.9500
```

`drop_tail` 删掉了最后一句，剩下的文本**仍然以句末标点收尾、长度仍然合规、来源仍然完整**。这提示一条结论：

> **质量分测的是格式与治理，不是内容正确性。**

要抓 `drop_tail` 这类内容缺陷，得靠 day053 的评估套件（六个文本分量）与 day055 的偏好打分器，而不是靠 `quality`。**把边界说清楚，比让打分器去猜它测不了的东西更有用。**

### 4.5 拒绝必须归因：每一次丢弃都要有名字

```python
def rejection_by_dimension(self) -> dict[str, int]:
    counts: dict[str, int] = {}
    for index in self.rejected_indices:
        name = self.scores[index].weakest()
        counts[name] = counts.get(name, 0) + 1
    return counts
```

归因到"**最低分维度**"而不是"第一个不达标的维度"：分数是连续量，没有"不达标"这条线，只有"哪一维拖了后腿"。这与 day055 的 `drop_reasons` 是同一种记账思路，只是判据从布尔换成了排序。

`weakest()` 在并列时按 `DIMENSIONS` 顺序取第一个——**并列不能"随便取一个"**，否则同一份数据两次跑出来的 `rejection_by_dimension` 会不同。

`QualityFilterResult` 还刻意保留了与入参**等长同序**的 `scores`（包括被拒项），因此"第 i 条为什么被拒"永远可以当场回答。只留被保留样本的分数，会让"被丢掉了多少、为什么"消失在报告之外。

## 第五章：配比控制 —— 一个会连锁收紧、而且未必可达的约束

### 5.1 直觉答案是错的

day049 留下了这样一句结论（当时只是观察，没有护栏）：

> 红队安全样本 16 条占了 `16/37 = 43.2%`。直接丢进 SFT，模型会倾向"多拒答"。正确做法不是删安全样本，而是**调权或分阶段训练**。

本课补的就是那条缺失的**能报警的线**。但实现之前得先弄清一件反直觉的事：给"任一组不超过 40%"这条约束，直觉答案是"把超过的组砍到 40%"——**这是错的**。砍掉一组之后总数变小，其余组的占比反而变大，必须重算。实测跑 6 轮不动点迭代：

```text
16 : 5 : 16  （T=37，cap=14）→  14 : 5 : 14  （T=33，cap=13）
  →  13 : 5 : 13  （T=31，cap=12）→  12 : 5 : 12  （T=29，cap=11）
  →  11 : 5 : 11  （T=27，cap=10）→  10 : 5 : 10  （T=25，cap=10）收敛
```

最终 25 条，两个大组各占 `10/25 = 40.0%`，`iterations=6`，**代价是丢掉 12 条（32%）**。这就是 day049 那句"该用调权/分阶段训练而不是硬删"的**定量答案**：硬删的账太贵了。

所以本课把缺省上限设成 **0.5（安全网档）**——它在同一份数据上一条都不丢：

```text
max_ratio=0.5: quotas {seed:16, agent_tasks:5, redteam:16}，dropped 0，迭代 1 轮
```

**上限口径适合当安全网（防垄断），不适合当日常配比手段。**

### 5.2 收敛不等于可达 —— 所以必须有 `feasible` 字段

同一份数据换成 `group_by="safety"`（21 正常 : 16 安全）再收 0.4：

```text
21 : 16 → 14 : 14 → 11 : 11 → 8 : 8 → 6 : 6 → 4 : 4 → 3 : 3 → 2 : 2 → 1 : 1（保底生效）
```

**9 轮之后剩下 2 条**，两组各占 50%——约束根本达不到，因为两组各占一半时必然有一组 ≥ 50%。此时 `MixPlan.feasible` 为 `False` 并附带告警：

```json
{"quotas": {"normal": 1, "safety": 1}, "total_in": 37, "total_out": 2, "dropped": 35,
 "iterations": 9, "feasible": false, "final_ratios": {"normal": 0.5, "safety": 0.5},
 "warnings": ["实际占比无法全部落在 0.4 以内（每组至少保留 1 条与取整所致）……"]}
```

**一个悄悄违反自己约束的护栏，比没有护栏更糟**：它会让评审以为"配比已经守住 40% 了"。所以"这个目标做不到"必须是一个被输出的结论，而不是一个被吞掉的异常。

收敛性可以证明：每轮把超额组精确压到 `cap`，而 `n > cap` 意味着总数**严格下降**；总数是正整数且有下界，因此一定在有限步内收敛。**收敛不等于可达。**

还有一个必须防的浮点陷阱：`int(0.3 * 10)` 在 IEEE 754 下是 `2`（`0.3*10` 得到 `2.9999999999999996`），而正确答案是 3。差一条样本在"刚好卡在边界"的配比场景里足以让结论翻转，所以取整统一走：

```python
def _floor_ratio(max_ratio: float, total: int) -> int:
    return max(MIN_GROUP_KEEP, math.floor(max_ratio * total + _FLOOR_EPSILON))
```

**写在函数里而不是散在循环里，是为了让"取整口径"只有一个出处。**

### 5.3 缺口报告：增强的靶子

`deficit_report` 给定目标权重，用**最大余数法**算出目标条数（`sum(targets) == sum(counts)` 恒成立，否则"缺口"就变成"凭空要变出样本"）：

```text
等权目标（66 条）：targets {seed:22, agent_tasks:22, redteam:22}
                  deficits {seed:-8, agent_tasks:+13, redteam:-5}
                  → under {agent_tasks: 13}，over {seed: 8, redteam: 5}
```

**这 13 条就是增强该去补的地方。** 本课的增强是无向的（对所有样本轮转算子），因此它近似等比放大、不会破坏刚削好的配比；**定向增强（只补欠采样组）需要生成新内容，也就需要模型参与，不再属于"离线可复现"的范畴**——这是本课明确划出的边界。

`deficit_report` 还拒绝"权重表漏了一组"：漏掉一组等于宣称"这一组的目标数是 0"，而它多半只是被忘了。**安静地把一整组判成 0，是这类接口最危险的一种默认行为。**

## 第六章：数据增强 —— 三条纪律与一次真实的冲突

### 6.1 四条算子与三条纪律

| 算子 | 改善维度 | 做法 | 风险 | 默认启用 |
|------|---------|------|------|---------|
| `prefix` | 问法多样性 | 在指令前加一句口语化开场白（四个固定变体轮转） | 否 | 是 |
| `constraint` | 指令跟随 | 追加一条原答案本来就满足的输出约束（三条约束，先过守门） | 否 | 是 |
| `paraphrase` | 词汇鲁棒性 | 按受控词表替换指令里的第一处同义词 | 否 | 是 |
| `noise` | 噪声鲁棒性 | 首尾插入口语填充词（会降低质量，且质量打分察觉不到，默认关闭） | 是 | 否 |

**纪律一：只改 prompt 侧，`output` 逐字不动。** 增强样本的答案从亲本**继承**。动了 output，"换一种问法"就变成"生成新答案"，而生成意味着可能出错——一条错了的增强样本会在训练里被当成金标准反复强化。这条性质在测试里对**每一个算子**逐条断言（`test_*_never_touches_the_output`），不靠注释保证。demo 第 9 节还把它逐条打印出来给人看：

```text
op=aug:prefix      output 与亲本逐字相同=True  source 继承=True  license 继承=True
   亲本：什么是检索增强生成(RAG)?
   增强：请帮我看看：什么是检索增强生成(RAG)?
op=aug:constraint  output 与亲本逐字相同=True  source 继承=True  license 继承=True
   亲本：RAG 检索阶段最常用的相似度度量是什么?
   增强：RAG 检索阶段最常用的相似度度量是什么?
        回答请控制在 200 字以内。
```

`source` 与 `license` 同样原样继承：**增强不改变数据出处**，`source` 一变，按来源的治理统计就全部失真。

**纪律二：能改写答案正确性的增强，必须自证"答案本来就满足"。** `constraint` 往指令后追加输出约束。若原答案 300 字而约束写"200 字以内"，这条样本就是**自相矛盾**的：模型要么学会忽略指令，要么学会把答案砍短（而参考答案并没有砍短）。所以每个约束都带 `satisfied_by` 判定，只有原答案本来就满足才追加：

| 约束 | 守门条件 | 本课程数据上的效果 |
|------|---------|------------------|
| `请用中文回答。` | 答案中文占比 >= 0.3 | 4 条英文/代码密集的答案被正确跳过 |
| `回答请控制在 200 字以内。` | `len(output) <= 200` | 37 条全部满足（实测输出 67~165 字） |
| `请直接给出结论，不要复述问题。` | 答案前 8 字不在问题里 | 全部满足 |

不满足就跳过并记进 `guard_rejected`——**跳过是正确行为，不是失败**。

**纪律三：默认不启用会降低质量的算子。** `noise` 加口语填充词，模拟真实用户的口语输入。它默认关闭，理由是：

> 噪声增强造成的质量下降**恰好不在质量打分的五个维度里**——填充词不会让长度越界、不产生 n-gram 重复、也不影响收尾与来源。也就是说 `quality` 拦不住它。

这种"打分器看不见的风险"只能靠**显式标签**（`aug:noise`）与默认关闭来治理。可以带走的判断：**给流水线加一个算子之前，先问"它出错时谁会报警"**。没人报警的算子，就必须默认关闭。

### 6.2 一次真实的冲突：增强样本会被自己的亲本判重

这是本课最值得记住的一段调试。第一版把原样本也放进了增强阶段的去重索引，结果是 13 次 `prefix` 尝试里 **5 次**被丢弃：

```text
增强：37 条进 → 新增 24 条（扩容 0.65×）| 算子分布 {prefix:8, constraint:12, paraphrase:4}
     守门拦下 0 / 无变化 8 / 撞车丢弃 5
```

看起来像"去重器工作正常"，其实**去重的判据与增强的意图撞车了**：去重防的是"同一份语料被无意采集两遍"，而 `prefix` 增强**天生就是要产出与亲本高度重叠的样本**——"请帮我看看：X"与"X"的 Jaccard 实测 0.8667，稳稳超过阈值。38% 的 `prefix` 产出白花。

修法不是调阈值（那会同时放松真正的重复检测），而是**让意图显式化**——把增强阶段的去重范围收窄为**增强样本之间**：原样本已经在 `near_dedup` 阶段去过重，而"与自己的亲本像"是设计意图。改动之后：

```text
增强：37 条进 → 新增 29 条（扩容 0.78×）| 算子分布 {prefix:13, constraint:12, paraphrase:4}
     守门拦下 0 / 无变化 8 / 撞车丢弃 0
```

本课程数据上 29 条增强样本彼此零撞车，但这条护栏依然必要：**两条本来就相近的原样本被同一算子改成几乎一样的问法**时，它会救场。测试里用"四条只差一个编号的指令 × 3 次尝试"复现了"12 条产出里丢 4 条"的情形（33%）。

> **这是一条可以带走的判断：当两件事用同一个判据、但意图不同时，必须让意图显式化——调参数是最差的解法，因为它会同时放松另一侧的约束。**

### 6.3 算子轮转：覆盖度优先于单条样本的丰富度

每条原样本缺省只产出 1 个增强样本，算子按 `ops[(序号 + 第几次尝试) % 算子数]` 轮转，**不使用随机数**。这与 day055 的 `pick_rejected` 是同一条取舍：随机抽样会让一部分算子完全抽不到样本，而"哪个算子对模型更有用"这个问题必须有数据才能回答。确定性轮转保证每个算子在每个批次里都被行使。

一个容易被误读的细节：`paraphrase` 有 8 次落进 `no_change`——那不是失败，而是**指令里确实没有受控词表里的同义词**（`如何`/`为什么`/`什么是`……）。受控词表窄，是为了"语义安全"：自由改写需要模型参与，会把随机性和幻觉一起带进数据流水线。

### 7.1 实测总账

```text
raw_counts = {'seed': 18, 'eval/agent_tasks': 7, 'eval/redteam_cases': 16}，合计 41 条
  [clean     ] 进  41 → 出  37 | 丢弃   4 新增   0
      drop_reasons = {"output_too_short": 1, "placeholder_output": 1, "unverified_source": 2}

  [near_dedup] 进  37 → 出  37 | 丢弃   0 新增   0   （精确 0 / 近重复 0，阈值 0.7）
  [mixing    ] 进  37 → 出  37 | 丢弃   0 新增   0   （0.5 上限，迭代 1 轮，未触发）
  [augment   ] 进  37 → 出  66 | 丢弃   0 新增  29
      by_op = {"prefix": 13, "constraint": 12, "paraphrase": 4}，no_change = {"paraphrase": 8}
  [freeze    ] 进  66 → 出  66 | 指纹 ffa3f96a774809ee（v1）
```

前三行与 day048/day049 的已发布结论**逐项一致**（41 = 18 + 7 + 16，丢 4 条的原因也一样），这证明本课是**接在** day048 后面继续走，而不是另起一条并行链路。相邻阶段的链式关系也是一条可断言的恒等式：**上一阶段的"出"必须等于下一阶段的"进"**（测试 `test_consecutive_stages_are_chained`）。

### 7.2 一个因为"读起来像错的"而改掉的字段

阶段记录最初只有一个派生量 `dropped = total_in - kept`。于是在增强阶段（唯一的加法阶段）报告里出现了这样的表头：

```text
| augment | 37 | 66 | 丢弃 -29 |
```

**负数出现在"丢弃"这一列，评审的第一反应是"这里的账错了"**——而真正错的只是字段命名。改法是把三个派生量各给一个名字：

```python
@property
def dropped(self) -> int:      return max(0, self.total_in - self.kept)   # 恒非负
@property
def added(self) -> int:        return max(0, self.kept - self.total_in)   # 恒非负
@property
def net_change(self) -> int:   return self.kept - self.total_in           # 有符号
```

三者满足 `kept - total_in == added - dropped == net_change`（测试钉住）。这是一个很小的改动，但它体现的纪律贯穿整个项目：**报表上的每一个字段名都在被信任，命名错误等价于数据错误。**

### 7.3 清单：没有它，一份 jsonl 三个月后就说不清来路

`DomainDataManifest` 落盘为 `manifest.json`，包含：版本号、内容指纹、父版本指纹、六阶段账、来源分布、配比与实际占比、质量分分布、拒绝归因、增强算子分布、配比缺口，以及**所有影响结果的参数快照**。

- **内容指纹** = 逐条样本 prompt 精确键按顺序拼接后的 SHA-1 前 16 位。它与去重口径一致（回答"这是不是同一批问题"），并且**顺序敏感**——批次顺序会影响 day048 的可复现切分与训练时样本先后，因此"顺序变了"就是"版本变了"。
- **父版本指纹**把版本串成链，配合 `merge_with_history` 构成"可持续更新"。
- **参数快照**是"同一指纹在别人机器上能复现"的前提。缺了它，指纹只是一串好看的字符——而**不可复现的指纹，只是一串好看的字符**。

`render_markdown()` 会把清单渲染成一份可直接贴进评审文档的报告（demo 第 4 节就是它的实际输出）。

其中三组断言值得一提，因为它们钉住的是**纪律本身**而不是某个函数的输出：

1. `test_single_zero_dimension_never_falls_below_threshold`（参数化 5 组）——把"门槛 0.6 对单点不敏感"这句结论变成可执行的事实，同时暴露了第一版教程里写错的表述；
2. `test_shingle_hash_is_stable_across_processes` ——用两个不同 `PYTHONHASHSEED` 的子进程实测跨进程稳定，并顺带断言内建 `hash` 会变，**把"为什么不能用它"变成一条可运行的证据**；
3. `test_dimension_table_weights_come_from_the_weights_object` ——文档表格的权重列必须等于 `default_weights().as_dict()`，**"文档说 0.25、代码是 0.2"这类漂移会立刻变红**。

## 结语：可持续数据的三条工程线索

1. **判据要单一，口径要写进数据**：两级去重与 day048 用同一套归一化和同一个比较对象（prompt），"精确重复数"与"近重复数"才可能出现在同一张表里而不打架。**同一份数据在两套口径下得到两个结论，是数据治理最忌讳的事。**
2. **标定替代照抄**：近重复阈值 0.7、质量门槛 0.6 的长度平台、重复率的 `0.10~0.35` 区间，全部来自本课程语料的实测分布。照抄别人的 0.8 的后果不是效果差一点，而是**整条链路静默空转**——报告里"0 条重复"与"数据很干净"长得一模一样。
3. **把"做不到"和"读起来像错的"都显式化**：`feasible=False` 把"这个配比目标不可达"说出口；`dropped`/`added`/`net_change` 把"增强阶段让数据集变大了"这件事说清楚。**工程报表上的每个字段都在被信任，命名错误等价于数据错误。**
