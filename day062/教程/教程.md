## 第一章：为什么"分块"值得单独一天

### 1.1 day061 留下的那句承诺

day061 的 `documents/pipeline.py` 里有一句写死的注释：

> `knowledge_records()` 产出的形状就是 day009 的 `VectorStore.add` 需要的
> 东西。day062 会在它上面加一层分块：**今天交出去的是整份文档，
> 明天交出去的是文档切出来的片段**，而接口形状不变。

今天就是来兑现这句话的。`ChunkSet.knowledge_records()` 的产出仍然是四个键：

```python
{"doc_id": <chunk_id>, "source": …, "text": <片段>, "metadata": {...}}
```

**字段名一个没改**，只是 `doc_id` 位置换了身份：从"这份文档是谁"变成
"这个片段是谁"。一个接口形状能扛过一次语义升级，才说明它当初是照
"下游需要什么"设计的，而不是照"当天有什么"设计的。

### 1.2 分块是 RAG 里唯一"不可撤销"的一步

RAG 的链路上大部分环节都能事后补救：检索器排序不好可以加重排序（day068）、
提示词不好可以改模板（day069）、答案不好可以换模型（day033）。但**分块是
上游的结构决策**：

```text
一句话被切成两半  → 任何重排序、任何更大的模型，都拿不回这句话
```

被切开的那半句在向量库里就是一条独立的记录，它会被单独编码、单独检索、
单独拼进提示词。用户问"阈值设多少"，命中的块是"…的直接丢掉。阈值用分位数"，
而答案的另一半在另一块里——**模型会基于半句话回答，而且答得很流畅。**

这就是为什么今天要在"读文件"之后、进向量库之前，花一整天把这件事讲清楚。

### 1.3 四种策略不是四个选项，是四个**判据**

最容易犯的错是把四种策略当成"四种实现，选一个最快的"。它们其实是四个
不同的判据，回答的是同一个问题的四个版本：

| 策略 | 它认为"边界"是什么 | 它放弃了什么 |
|------|------------------|-------------|
| `fixed` | 位置（第 320 个字符） | 一切内容信息 |
| `recursive` | 排版（段落、换行、句号） | 话题与结构 |
| `structural` | 作者的意图（标题层级） | 没有标题的文档 |
| `semantic` | 内容相似度的低谷 | 结构，以及"可解释性" |

因此它们的强弱项是**互补**的，而不是可替换的。今天的第六章会用一份真实文档
把四个判据并排算一遍。

## 第二章：预算单位与那个二分原语

### 2.1 "320" 是什么的 320

四种策略里三种都有"一块最多装多少"这个参数。写下来的时候就已经埋了一个
未定义的东西：

```python
max_tokens = 320      # 320 个什么？
```

这个坑非常具体。实测同一句话：

```text
"分块预算决定索引规模。"（11 个字符）
  chars      → 11 个预算单位
  tiktoken   → 13 个 token（cl100k_base）
```

**同一个参数名，两种含义，差 18%。** 写文档的人按 token 想，读文档的人按
字符猜，最后表现为"检索出来的片段太碎"或"太糊"——而没有人会去怀疑参数单位。

因此 `chunking/tokens.py` 的第一件事是把单位**显式化成一个可注入的对象**：

```python
class TokenMeasurer(Protocol):
    name: str
    def count(self, text: str) -> int: ...
```

### 2.2 为什么默认不是真实分词器

直觉上应该默认用 `tiktoken`（day034 已经写好了 `TokenCounter`）。但分块有一条
从第 6 天就立下的纪律：**同一份输入要在任何机器上得到同一份输出**
（day057 的可复现版本链、day058 的确定性 run_id、day061 的排序遍历）。

`tiktoken` 的可用性依赖本机是否有词表缓存：

```text
有缓存 → 精确 token 数         → 分块结果 A（chunk_id 集合 A）
没缓存 → 字符级估算（day034）  → 分块结果 B（chunk_id 集合 B）
```

于是同一份文档在两台机器上切出**两套 `chunk_id`**，而知识库是按 `chunk_id`
去重的——"这条知识为什么重复了两份"会变成一个查不出来的问题。

所以分工是：

| 度量器 | 确定性 | 与计费单位一致 | 默认 |
|--------|--------|---------------|------|
| `chars` | **是**（只依赖 `len`） | 否 | **是** |
| `tiktoken` | 否（依赖本机词表缓存） | 是 | 否 |

并且 `resolve_measurer` 在本机词表不可用时**直接拒绝**：

```python
raise ChunkingError(
    "本机没有可用的 tiktoken 词表缓存，无法按真实 token 计数……"
    "改用 measurer='chars'，或在有网络的环境先预热词表。"
)
```

静默降级会让"我要的是 token 预算"变成"我拿到的是字符预算"，而两者差 18%
且结果里看不出来——**宁可报错，不要给一个看起来对的错答案**（这是 day060
"把占位吞吐到处标注"、day061 "加密 PDF 拒收"的同一条纪律）。

### 2.3 二分：`longest_prefix_within`

"从某个位置起最多能切多长"是四种策略共用的原子操作。实现用二分，
而二分的合法性依赖一条**必须被说出来的假设**：

```python
def longest_prefix_within(text: str, budget: int, measurer: TokenMeasurer) -> int:
    """返回最长的 k，使 measurer.count(text[:k]) <= budget."""
    if not text:
        return 0
    if measurer.count(text) <= budget:
        return len(text)
    low, high = 0, len(text)
    while low < high:
        mid = (low + high + 1) // 2
        if measurer.count(text[:mid]) <= budget:
            low = mid
        else:
            high = mid - 1
    return low
```

> **`count(text[:k])` 关于 `k` 单调不减。**

它在两个度量器上都成立（字符数当然单调；BPE 编码的前缀 token 数也不会因为
多了一个字符而变少），但它不是"显然"的：如果将来换一个会在分块边界上
"压缩"的度量器（比如带词干还原的计数），二分就会给出错误答案**且不报错**。
因此这条假设被写成了一条测试：`test_prefix_count_is_monotonic`。

两个出口都是明确的，而且**都必须由调用方处理**：

```text
k == len(text)   整段放得下
k == 0           连第一个字符都放不下（budget 太小）
```

`k == 0` 不能"随便切一个字符"——那会让调用方以为预算够用，于是产生一批
每一块都超预算的结果。`Chunker._hard_split` 在拿到 0 时直接报错并给出建议
（"请调大 max_tokens"）。

## 第三章：四种策略

四种策略听起来是四套东西，实际上**只有一个问题不同：在哪里切**。
切完之后的事，四者完全一样——这一点是今天最重要的结构决策（见第四章）。

### 3.1 固定长度：唯一能"先算再切"的策略

```text
从第 0 个字符开始，每 max_tokens 个单位切一刀，
刀口往回挪 overlap_tokens 个单位再切下一刀
```

它的价值不在于"切得好"，而在于它是**基线**：任何"更聪明的策略"都必须先
证明自己比它好。同时它也最容易推断——参数一确定，块数、放大量、成本全都
能算出来（`window_plan`）：

```text
step            = max_tokens - overlap_tokens           每刀前进的量
chunks          = ceil((units - max_tokens) / step) + 1  切出的块数
overlap_units   = (chunks - 1) * overlap_tokens          白算的字符数
amplification   = overlap_tokens / step                  相对原文的放大量
```

实测（614 字符的文档）：

```text
max=320 overlap=48 step=272 →  3 块，重叠 96 字符，放大量 17.65%
max=160 overlap=24 step=136 →  5 块，放大量 17.6%
max= 80 overlap=12 step= 68 →  9 块，放大量 17.6%
```

**预估与实测一致**（预估 3 块，实测 3 块）：

```text
fixed | 3 块 | 覆盖 115.15% | 重复 13.15% | 长度 p50 319 / p90 319 / max 319 chars
  #0 [  0:319] '检索手册\n\n本文给出一套可复现的检索参数，所有数'
  #1 [273:592] '= max_tokens - overlap_t'
  #2 [544:613] 'n 计，embedding 花费约 3.8 美元'
```

看第 1 块开头那 24 个字符：`= max_tokens - overlap_t`——**它从一行代码的中间
开始**。这不是缺陷，是定义：固定窗口不认识标点，一份中文文档按 320 字切，
平均每 320 字里必然包含若干个句号，而窗口不认识句号。

重叠（overlap）存在的唯一理由就是它：**重叠不解决"切断了"，
只保证"被切断的句子在至少一块里是完整的"。** 而它不免费——17.6% 的放大量
直接变成 embedding 调用量与向量库容量。

### 3.2 递归：把"优先在哪切"变成一张可读的表

递归策略的全部内容就是给固定长度加上一张**分隔符优先级表**，从强到弱
依次尝试：

```python
SEPARATOR_NOTES: tuple[tuple[str, str], ...] = (
    ("\n\n", "段落"),
    ("\n", "换行"),
    ("。", "中文句号"),
    ("！", "中文叹号"),
    ("？", "中文问号"),
    ("；", "中文分号"),
    (". ", "英文句号"),
    ("! ", "英文叹号"),
    ("? ", "英文问号"),
    ("; ", "英文分号"),
    ("，", "中文逗号"),
    (", ", "英文逗号"),
    (" ", "空格"),
    ("", "字符（无分隔符可用，硬切）"),
)
```

它之所以好用，是因为把"优先在哪里切"这件本来需要判断的事，退化成了
一个**可以写下来的字符串表**——可读、可测、可复现。

三处刻意的设计：

**第一，分隔符保留在片段的尾部。** `"第一句。第二句。"` 按 `。` 切，得到的是
`["第一句。", "第二句。"]` 而不是 `["第一句", "第二句"]`。丢掉分隔符会让
**产物再也拼不回原文**，"块文本是原文的连续子串"这条不变量直接失效。

**第二，中文标点必须在表里。** 只用英文标点（或只放 `"\n"`）的表在中文文档上会
**一路退到按字符硬切**，而退化的表现只是"块边界变差"，不会有任何报错：

```text
separator_histogram（本项目文档）
  段落       → 10
  换行       → 28
  中文句号    → 9
  中文分号    → 1
  中文叹号    → 0     ← count=0 的那一档就是从这一层掉下去的原因
  中文问号    → 0
  英文句号    → 0
```

`separator_histogram()` 就是"这份文档为什么退化了"的答案：**块长分布告诉你
"结果不好"，直方图告诉你"为什么"。**

**第三，切完必须"合回去"。** 第一刀在 `\n\n` 处切完之后，每个自然段各自成块——
一份 200 段的文档得到 200 个小块。递归切分的正确形状是
"**先切碎、再按预算合并**"：

```python
def _pack(self, text: str, spans: list[Span], reason: str = "+pack") -> list[Span]:
    """把相邻的小区间贪心地合并到预算上限（"尽量填满，但不超"）."""
```

这一步最容易被忘掉，而忘了它的后果直接出现在账单上：

```text
recursive | 3 块 | 覆盖 114.50% | 重复 12.66% | 长度 p50 250 / p90 260 / max 262 chars
  #0 sep:段落+pack            191 字 '检索手册\n\n本文给出一套可复现的检索参数…'
  #1 sep:段落+pack+overlap    262 字 '中文标点必须在分隔符表里，\n否则一份中文文档…'
  #2 sep:段落+pack+overlap    250 字 '-(-(doc_chars - max_tokens) // step) + 1'
```

`reason` 那一列是可解释性的落点：它直接写着"这一刀切在哪一档分隔符上、
有没有合并、有没有回带"。

### 3.3 结构：花掉 day061 的积蓄

前两种策略都在**纯文本**上工作。而 day061 花了一整天把结构从八种格式里
抽出来，存进 `Document.blocks`——今天就是来花它的。

**标题栈**是第一节要讲的东西：

```python
for index, block in enumerate(document.blocks):
    if block.kind == BLOCK_HEADING:
        flush()                                   # 收束上一小节
        while stack and stack[-1][0] >= block.level:
            stack.pop()                           # 弹出同级与更深层
        stack.append((block.level, block.title))
```

用栈而不是"记住上一个标题"是必需的：`h1 → h2 → h3 → h2` 的顺序下，
第二个 `h2` 必须把 `h3` 弹掉，否则它会带着上一个 `h3` 的名字。
`test_build_sections_uses_a_heading_stack` 守的就是这一条。

**breadcrumb** 是这一天最有价值的一列产物：

```text
heading_path   : '检索手册 > 分块'
text           : 'def plan(doc_chars: int, max_tokens: int, overlap_tokens: int) -> int:'
retrieval_text : '检索手册 > 分块'
```

注意 `text` 与 `retrieval_text` 的区别。代码块自己也说不清"我在讲什么"，
而它的标题路径就是"这一块所属语境的最短摘要"。因此：

```text
text            原文里的一段连续子串 —— 用来展示、引用、逐字核对
retrieval_text  heading_path 面包屑 + text —— 用来做 embedding
```

**前缀只出现在检索视图里。** 把它写进 `text` 会让"块文本是原文的连续子串"
这条不变量失效，于是引用会引到一段**原文中并不存在**的文字——这种错误在
演示里看不出来，只有在用户点开出处时才暴露。

**原子块保护**是第二节。把预算压到 40，210 字符的代码块就装不下了。此时两条路：

```text
切开会得到两块「都不对」的文本     ← 更糟：错误很隐蔽
不切会得到一个超出预算的块         ← 更好：超预算是可见、可统计的
```

因此 `ATOMIC_KINDS = ("code", "table")` 走第二条路，并留下一个显式标记：

```text
structural | 5 块 | ... | 超预算 1
  #0 [  0: 36]   36 字 | 块 0~1  | 检索手册
  #1 [ 38:191]  153 字 | 块 2~4  | 检索手册 > 分块
  #2 [193:403]  210 字 | 块 5~5  | 检索手册 > 分块     ← reason=atom:code
  #3 [405:507]  102 字 | 块 6~8  | 检索手册 > 检索
  #4 [509:613]  104 字 | 块 9~10 | 检索手册 > 成本
```

注意 `块 5~5` 那一列：结构策略在能精确定位小节时给出**精确的块区间**，
这是"小节拼起来能在全文里找到"的直接产物（`_locate`）。

### 3.4 语义：唯一会调用外部能力的策略

前三种策略切在哪里，都由写在代码里的规则决定。语义分块换了一个判据：

```text
1. 把原文按自然段切开                     （用空行来定）
2. 每个自然段编码成一个向量                （day041 的 EmbeddingProvider）
3. 算相邻两段的余弦相似度                   （day009 的 cosine_similarity）
4. 相似度最低的那些缝切一刀                 （阈值取相似度分布的分位数）
5. 按预算合并，再回带重叠
```

**阈值用分位数，不用绝对值。** 每天都会有人问"相似度低于 0.7 就切，对不对"。
答案是**这个数没有意义**：同一个 0.7 在 `text-embedding-3-small` 上可能是
"非常相似"，在 `char-ngram` 上可能是"完全不相干"，在另一种语言上又是另一个
含义。余弦相似度的绝对值依赖模型的训练目标、维度、是否归一化以及语料的语言。

分位数把它变成**相对判据**：`similarity_percentile=0.25` 表示"在相似度最低的
那 25% 的缝上切"。实测：

```text
percentile=0.10 → 5 块 | 阈值 -0.1568 | 断层 4
percentile=0.25 → 5 块 | 阈值 -0.1018 | 断层 6
percentile=0.50 → 5 块 | 阈值  0.0062 | 断层 6
percentile=0.75 → 6 块 | 阈值  0.0492 | 断层 8
```

**它是四种策略里唯一会调用外部能力的**，因此产物里必须记着"这一次是怎么
决定的"：

```python
{'units': '11', 'breaks': '6', 'threshold': '-0.1018',
 'similarity_percentile': '0.25', 'heading_breaks': '3',
 'embedding': 'MockEmbedding', 'embedding_dimension': '64'}
```

没有这一层，一个"这次块变少了"的现象无法归因——换提供方、换阈值、换文档，
三种原因长得一模一样。

**它还会在标题处额外断开。** `heading_path` 是块级属性，"一个块有两条路径"
是表达不了的。这条规则让"标题丰富的文档"在语义策略下自然接近
"结构策略 + 相似度细分"（实测两者都是 5 块）。

### 3.5 四个判据的对照表

```text
1 份文档 × 4 个策略 → 16 块 / 2654 tokens | 超预算 0 | 重复内容组 4

策略             块数     平均      覆盖率      重复率    超预算
fixed           3   235.7  115.15%   15.15%       0
recursive       3   234.3  114.50%   14.50%       0
structural      5   121.0   98.53%    0.00%       0
semantic        5   127.8  104.07%    4.07%       0
```

这张表最值得看的是**三列之间的关系**，而不是任何一列本身：

- **覆盖率 98.53%**：结构策略的差额来自块之间的空行（被修剪掉了），
  差额 9 恰好等于上界 `2×(5-1)+1`——它是可核对的，不是"差不多"；
- **重复率 15.15% vs 0%**：固定长度与递归为重叠付了 15% 的 embedding 成本，
  结构策略没有（它不需要：标题边界本身就是语义边界）；
- **平均长度 235 vs 121**：检索时命中一块带进来的上下文量差一倍，
  直接影响提示词预算与"答案里会不会混进无关内容"。

## 第四章：收尾六步与那条不变量

### 4.1 四个策略只差"在哪里切"

这是今天最重要的结构决策：把"在哪里切"与"切完之后做什么"彻底分开。

```text
子类只实现 _spans() → 一串「字符区间 + 切在这里的理由」
finalize() 统一做六件事：
  1. 修剪     去掉每段首尾空白并同步调整区间
  2. 重叠     把下一块的起点往回挪（可按策略开关）
  3. 去重     起点相同的块只保留包含者
  4. 合并     过短的块与相邻块合并，且不越预算
  5. 校验     区间合法 + 起点严格递增 + 非空白字符全覆盖
  6. 成块     编号 → 度量 → chunk_id
```

好处不是"少写几行代码"，而是**四条纪律只写一次**：一个策略如果自己收尾，
它就会自己漏掉一条；而"漏掉哪一条"没有任何报错，只表现为某个指标悄悄变差。

### 4.2 `Span` 只带区间，不带文本

```python
@dataclass(frozen=True)
class Span:
    """切分器交给收尾器的中间产物：一段**原文的字符区间** + 切在这里的理由."""
    start_char: int
    end_char: int
    reason: str = ""
    heading_path: tuple[str, ...] = ()
    start_block: int = -1
    end_block: int = -1
    oversized: bool = False
```

刻意只带区间：文本由 `document.text[start:end]` 现取。这样
**"块文本是原文的连续子串"这条不变量不可能被违反**——因为没有第二个地方
可以放文本。这与 day061 `make_document` 删掉 `text` 参数是同一种做法：
**让错误的东西无处可写。**

### 4.3 覆盖率是被接口保证的，不是测出来的

```python
covered = bytearray(len(text))
for span in spans:
    covered[span.start_char : span.end_char] = b"\x01" * (span.end_char - span.start_char)
missing = [i for i, char in enumerate(text) if not covered[i] and not char.isspace()]
if missing:
    raise ChunkingError(
        f"有 {len(missing)} 个非空白字符没有被任何块覆盖（首个位置 {missing[0]}）："
        "切分丢了内容，这与 day061「只分类不丢弃」是同一条纪律"
    )
```

day061 用"逐行核对"守住了"只分类不丢弃"；今天用"逐字符核对"守住
"只搬运不丢弃"。两者都在同一个位置：**结构化处理最容易犯的错就是让内容
悄悄消失，而它的表现只是"结果比原文短"。**

注意判定里那个 `not char.isspace()`：**只要求非空白字符被覆盖**。这不是
放松标准，而是把"块首尾的空白被修剪掉"这件事纳入契约——否则每一块都要
带着边界上的空行，而那是纯噪声。代价是覆盖率会略低于 1，但它有上界：

```text
doc_chars - total_chars ≤ 2 × (块数 - 1) + 1
                            ↑ 块间空行      ↑ 原文结尾的换行
```

实测：`fixed`（11 块）差 2，`structural`（5 块）差 9（上界恰好也是 9）。
**有了这个上界，"覆盖率 98% 是否正常"就不再是一个感觉问题。**

### 4.4 重叠：把起点往回挪，而不是给上一块加尾巴

```python
low = max(previous_start + 1, span.start_char - overlap)
if low >= span.start_char:
    continue      # 两块贴在一起，没有回带空间
start = min(span.start_char - 1, max(snap_to_boundary(text, low, span.start_char), low))
```

两种实现（"下一块往前挪"与"上一块加尾巴"）在文本上等价，但前者保持
"每一块都是一个区间"，于是覆盖率核对与去重计算都还成立。

三条护栏，每条都对应一类真实故障：

1. **不吞掉整块**：往回挪之后起点仍必须严格大于上一块的起点（否则
   `_assert_spans` 会报"窗口没有前进"）；
2. **不超过重叠预算**：最多回挪 `overlap_tokens` 个单位（否则成本失控）；
3. **落点对齐断点、且落在内容上**：

```python
def snap_to_boundary(text, low, high, boundary_chars=BOUNDARY_CHARS) -> int:
    """在 [low, high) 里找第一个"紧跟断点字符之后、且本身不是空白"的位置."""
```

第 3 条的"不是空白"是今天踩出来的（见第七章第 5 条）：两个块之间隔着一段
空行时，`low` 很可能就落在空行里，回带过来的是两个换行——它既没有语义，
又会让引用看起来像是从半空中开始的。

### 4.5 参数默认值是策略的一部分

```python
DEFAULT_POLICIES: dict[str, dict[str, Any]] = {
    STRATEGY_FIXED: {"max_tokens": 320, "overlap_tokens": 48, "min_tokens": 0},
    STRATEGY_RECURSIVE: {"max_tokens": 320, "overlap_tokens": 48, "min_tokens": 0},
    # 结构策略的重叠**必须**为 0：标题边界就是语义边界。
    STRATEGY_STRUCTURAL: {"max_tokens": 320, "overlap_tokens": 0, "min_tokens": 0},
    # 语义策略的最小块偏大：它一次切一段话题，碎块会让"话题"信息量不足。
    STRATEGY_SEMANTIC: {"max_tokens": 400, "overlap_tokens": 40, "min_tokens": 60},
}
```

同一张表里，`overlap_tokens` 对固定长度与递归是必要的，对结构策略**是错的**
（跨标题回带会把上一节的内容灌进下一节，而块的 `heading_path` 会让它看起来
本来就属于这一节）。因此默认值不能是一张全局表，必须按策略给。

连带的结论是 `ChunkPolicy` 数据类自己的字段默认值取 **0**：
"默认重叠多少"是一个策略决定，属于 `DEFAULT_POLICIES`；
直接构造 `ChunkPolicy` 得到的是**最保守的一套**。这条区分在
`test_bare_policy_is_the_conservative_one` 里被钉住。

结构策略对重叠的拒绝是**报错**而不是忽略：

```python
raise ChunkingError(
    "结构策略不支持重叠（overlap_tokens 必须为 0）："
    "标题边界就是语义边界，跨边界重叠会把上一节内容灌进下一节，"
    "而块的 heading_path 会让它看起来本来就属于这一节"
)
```

报错信息必须说清**为什么**，否则下一个人会去调小 overlap 把它"绕过去"——
而正确动作是不重叠。

## 第五章：成本、选型与打分

### 5.1 `chunk_id` 与 `fingerprint` 是两个问题

```text
chunk_id     sha256(doc_id | strategy | index | text)[:16]    ←「这一块是谁」
fingerprint  sha256(text)[:16]                                ←「这是哪段内容」
```

**只按文本算 id 会坏在"同一段话在同一份文档里出现两次"**（工程文档里的
"注意"小节经常长得一模一样，命令示例更是反复出现）：两个块的 id 相同，
向量库按 id 覆盖，"命中了 3 次"在库里只剩 1 条。

**而跨文档去重恰恰要的相反**：同一段话在 A 文档和 B 文档里各存一份是重复存储。
所以 `fingerprint` 单独留着，用于"这批块里有多少是重复内容"：

```python
def duplicate_chunks(self) -> dict[str, list[str]]:
    """跨文档/跨块重复的内容（fingerprint → 出现的 chunk_id 列表）."""
```

实测：同一份文档跑四个策略得到 16 块，其中**4 组是重复内容**——这些组
正是"同一段文字被不同策略或不同块各存了一份"。两个问题、两个字段，
混成一个就会出现"要么去重失效、要么块互相覆盖"，而两种失效都不会报错。

### 5.2 报告里必须有那三列

| 列 | 回答的问题 | 没有它会发生什么 |
|----|-----------|-----------------|
| `count` / `total_tokens` | 索引有多大、embedding 要花多少 | 上线后才发现账单翻倍 |
| `duplication_ratio` | 重叠白花了多少 | 把 `overlap` 调大"为了效果"，成本悄悄涨 |
| `oversized_count` | 有多少块注定被模型截断 | 检索命中率莫名偏低，查不出原因 |

三列都来自 `ChunkSet` 的属性，因此**报告与单份文档的统计永远同源**。

### 5.3 用探针集打分：`evaluate.py`

课程目标里写着"评估不同分块对检索效果的影响"。这句话很容易被做成
"跑一遍看一眼块长"，但那样得出的结论没有约束力——**块长好看不等于检索得准**。

```text
1. 准备探针集        (question, expect) 列表，expect 是期望命中的原文片段
2. 建索引            按某策略切块 → 每块用 retrieval_text 编码 → 入内存向量库
3. 检索              question 编码后取 top_k 块
4. 判定              某个块的**原文**里含 expect 吗？含 → 命中，记下它的排名
5. 汇总              hit@k、MRR、命中块的平均字符数、索引规模
```

判定用的是**块文本里是否含期望片段**，于是它同时测了两件事：

```text
检索到没有              → 向量召回能力
期望片段有没有被切开    → 块边界质量
```

第二件是本模块最有价值的发现通道。假设用户问"阈值该设多少"，期望片段是
"相似度低于 0.35 的直接丢掉"。如果某个策略**恰好把这句话从中间切开**，
那么它在任何块里都不完整，**该探针在该策略下必然 miss**——无论向量检索多准。
这类 miss 用"平均块长"是永远看不出来的。

实测（`MockEmbedding`，**没有真实语义**）：

| 策略 | hit@3 | MRR | 命中块均长 | hit@8 |
|------|-------|-----|-----------|-------|
| `fixed` | 100.0% | 0.444 | 236 | 100.0% |
| `recursive` | 100.0% | 0.444 | 230 | 100.0% |
| `structural` | 66.7% | 0.500 | 128 | 100.0% |
| `semantic` | 66.7% | 0.444 | 128 | 100.0% |

这里有一个**必须读出来的结论**：把 `top_k` 从 3 放大到 8（覆盖全部块），
四个策略都回到 100%。也就是说 top-3 的那两个 66.7% 来自**块变多之后
"对的块排在第 4 位"**，而不是"分块把片段切碎了"。**检索深度与分块质量
是两件事，混在一起看会得出完全错误的选型结论。**

两条纪律（比指标公式重要）：

1. 探针必须来自**你自己的查询分布**，抄别人的最优策略只对别人有效；
2. 期望片段在原文里必须**唯一**——出现多次的探针会让分数虚高且毫不显眼，
   因此 `ambiguous_probes()` 把它们单独列出来，端点也单独返回：

```text
"重复 → 期望片段在原文中出现 2 次"
```

## 第六章：接入 API 与配置

### 6.1 四个端点

| 端点 | 方法 | 回答什么 |
|------|------|---------|
| `/chunking/strategies` | GET | 四种策略、度量器、默认参数、分隔符表、覆盖不变量、"不能做什么" |
| `/chunking/split` | POST | 事前估算（块数/放大量）+ 实测统计 + 前 N 块明细（带 `start_char:end_char`） |
| `/chunking/evaluate` | POST | 多策略检索对照（hit@k / MRR / 命中块均长）+ 歧义探针 + markdown |
| `/chunking/records` | POST | 可直接入库的记录（含 `embedding_input` 说明） |

实测（demo 第 8 节）：

```text
GET  /chunking/strategies → 策略 4 个 / 度量器 2 个 / 分隔符 14 档 / 限制 5 条
POST /chunking/split      → fixed | 3 块 | 覆盖 115.15% | 重复 13.15%
     计划：3 块（精确=True） | 实测覆盖率 115.15%
POST /chunking/records    → 1 份文档 × 1 个策略 → 5 块 / 605 tokens | 5 条记录
     向量化字段 metadata.retrieval_text
POST /chunking/evaluate   → 4 个策略 × 3 条探针（top-8）| MRR 最优：structural（0.567）
```

四个端点仍然**只读或纯计算**：不写磁盘、不联网、**不遍历目录**、不留状态。
要看整个知识库切完的样子，用 `scripts/chunking_demo.py`——
**一个要读整个目录的流程不该挂在一个 HTTP 请求上**（与 day059/060/061 同源）。

`/chunking/records` 里那个 `embedding_input` 字段值得单独说：

```text
text           → 原文片段（可直接引用给用户）
metadata.retrieval_text → 向量化时应当使用的那一份（带标题面包屑）
```

**"存的"和"embed 的"不是同一段文本，这一条必须被写出来。**
不写的话，下一个人会以为向量是用 `text` 算的，然后"修"成一个 bug。

### 6.2 参数优先级的第三层：settings

```text
请求体   >   settings（项目级基线）   >   策略默认值（DEFAULT_POLICIES）
```

为什么需要"项目级基线"这一层：`settings.chunking_*` 表达的是**这个项目当前
选定的口径**（例如"我们统一按 512 字符切"），而 `DEFAULT_POLICIES` 是
**这种策略的合理起点**。两者会在真实项目里分叉。

但有两项刻意**不接受项目级覆盖**：

- `overlap_tokens`（结构策略恒为 0）：那是**结构性判断**，不该被一个全局
  默认值改掉；
- `similarity_percentile`：只有语义策略消费它，其余策略拿到它也只是原样带在
  产物里（`ChunkPolicy` 的字段注释里写着这件事，四个策略的 `describe()` 里
  也各有一行 `uses_similarity_percentile`）。

**还有一条与"比例"有关的规则**，它是今天最后踩到的一个坑：

```text
overlap    = round(max_tokens × 比例)      比例 = settings.overlap / settings.max_tokens
min_tokens = min(settings.min_tokens, max_tokens // 2)
```

`48` 这个数只在"预算 = 320"时有意义，它是 `320 × 15%`。把 48 写死会让
"预算调成 64"变成"75% 的重叠"——块一下子放大 3 倍，而**参数看起来只是变小了**。
这与 day058 的"版本键按内容算"、day060 的"成本按实际用量算"是同一种修正：
**一个绝对数只有在它的基准不变时才成立。**

### 6.3 七个配置项

```python
chunking_strategy: str = "recursive"          # 默认策略
chunking_max_tokens: int = 320                # 单块预算
chunking_overlap_tokens: int = 48             # 重叠（占预算的 15%）
chunking_min_tokens: int = 40                 # 过短块的合并下限
chunking_measurer: str = "chars"              # 预算单位
chunking_similarity_percentile: float = 0.25  # 语义策略的阈值分位数
chunking_eval_top_k: int = 3                  # 评估的检索深度
```

这一组与 `documents_*` 有一个关键差别：**它们会直接改变产物的字节**
（块的边界、数量、`chunk_id`）。因此默认值一旦定下就不能随手改——
改 `chunking_max_tokens` 等于让全量索引失效，与 day061 改 `normalize_text`
是同一量级的变更。

`chunking_eval_top_k` 的缺省 3 也是刻意的：top-3 之外的内容大概率会被提示词
长度或模型注意力稀释掉，**用"真实会被用上的块"来打分**。

## 第七章：今天踩到的六个真实缺陷

这一节比上面任何一节都值得读。六个问题全部是"参数/顺序看起来都对，
结果悄悄不对"的类型。

**缺陷一：重叠把块撑过预算，被记成了"原子块"。**

第一版的 `_make_chunk` 里写着：

```python
oversized=span.oversized or self.measurer.count(text) > self.policy.max_tokens
```

看起来合理，但递归策略的重叠是**在切完之后回带**的，于是每一块都会
"核心片段 + 重叠"，长度必然超过 `max_tokens`：

```text
recursive | 3 块 | 长度 p50 124 / p90 130 / max 131 chars（max_tokens=120）| 超预算 2
```

超预算 2 条本来是为"原子块保护"准备的，现在被重叠占用了——
**同一个字段表达两件事，报告就再也说不清是哪种。**
修法是引入 `window_budget`：切分器实际使用的预算 = `max_tokens - overlap`，
回带之后合计不超过 `max_tokens`。于是 `max_tokens` 在四种策略下含义统一为
"一个块最多多少"，而 `oversized` 只表示"不可切"。

**缺陷二：双重回带。**

递归与语义策略的重叠应该由收尾器统一施加，而第一版里 `_back_off`
（退化路径）自己也在做重叠，于是同一种重叠被叠了两次：

```text
预期放大量 ≈ 25%（overlap/(max-overlap) = 24/96）  实际 ≈ 40%
```

"多花了一点 embedding 钱"这种代价没人会去查。修法是把两个重叠拆成
两个名字：`window_overlap`（窗口内部，只有固定长度用）与
`policy.overlap_tokens`（收尾统一回带）。

**缺陷三：先重叠、后修剪，两个块的起点撞在一起。**

`_assert_spans` 报出了一个很难看的错误：

```text
块的起点必须严格递增，收到 [0, 1, 11, 22, 32, 38, 38, 38, 47, 67, 67, 67, 78, 84]
```

原因是收尾的顺序：重叠会把下一块的起点往回挪，挪过之后可能落进空白；
紧接着的"修剪"又把两块各自往前推到同一个位置。修法有两条，都保留：

1. **把顺序固定下来**：修剪 → 重叠 → 合并 → 校验（`finalize` 里的注释写着
   "重叠必须排在修剪之后"）；
2. 加一道 `_dedupe_starts`：起点相同时**只丢"被包含"的那一块**。注意它
   只自愈这一种情形——"起点倒退"或"后一块更短"是真正的切分缺陷，
   必须让 `_assert_spans` 响亮地报错，**自愈会把"窗口没有前进"变成一堆
   悄无声息的短块**。

**缺陷四：`paragraph_spans` 的尾随换行让最后一段"不一样"。**

原文结尾一定有一个换行（day061 的规范化会补一个），于是最后一个自然段的
文本比其它段多一个 `\n`，它的向量也就略有不同：

```text
三份完全相同的段落：前两段相似度 1.0，最后一段 0.98
→ 分位数阈值落在两者之间 → 语义策略**凭空在末尾切一刀**
```

表现是"块数多了一个"，而报告里看不出原因。修法是在 `paragraph_spans`
里把最后一段的尾随空白也剪掉——**自然段是内容，不含尾随空白。**

**缺陷五：`snap_to_boundary` 的落点落在空行里。**

回带落点的第一版只要求"紧跟断点字符"，于是它在两个块之间的 `"\n\n"` 里
选中了第一个位置：

```text
chunk.text = "\n第三段。"      ← 块文本以空行开头
```

它既没有语义，又会让引用看起来像是从半空中开始的。修法是给落点加两条偏好：
**优先"紧跟断点、且本身不是空白"的位置**，退一步接受"任意非空白位置"，
最后才退回 `low`；并且收尾里再兜一次（落点仍是空白就不回带）。

**缺陷六：结构策略 + 默认 `overlap=48` → 报错信息把人引向错误方向。**

第一版的 `ChunkPolicy.overlap_tokens` 字段默认值是 48（想表达"项目默认重叠"）。
于是这样一行代码：

```python
ChunkPolicy(strategy=STRATEGY_STRUCTURAL, max_tokens=40)
```

会报出 `overlap_tokens(48) 必须小于 max_tokens(40)`——**而结构策略根本不用
重叠**。收到这条报错的人会去调小 overlap，而正确动作是"这个参数对结构策略
没有意义"。修法是把字段默认值改成 0，把"默认重叠 48"这件**策略决定**
放回 `DEFAULT_POLICIES`，并在结构策略的 `__init__` 里对非零重叠给出
带理由的报错。


对比 day061 的 5731 个用例 / 98.25%：覆盖率略降 0.14 个百分点是**可解释的**，
不是回归——新包 1090 条语句的自身覆盖率是 95.85%，它在全量分母里占约 6.4%，
**新增代码的覆盖率只要低于原均值，总量就会被拉低**（这条算术对所有项目都成立，
所以"覆盖率掉了"要先问"新代码占多少、它自己是多少"）。

关于耗时，这里有一条值得单独记下来的实测：

> 同一套用例，串行 + `--cov-branch` 在本机跑不完（13 分钟只到 1%）；
> 而拆到 8 个进程之后 11 分 17 秒跑完。原因不是"测试多"，而是
> **插桩开销与"测试在算什么"有关**：5900 个快用例合计不到 2 分钟，
> 剩下十几分钟几乎全是 `alignment` / `lora` 那几十个纯 Python 数值训练用例——
> 它们每一行都在插桩下被记账。同一个 `test_alignment_dpo_trainer.py`：
> `--no-cov` 下 118 秒，带插桩后单是其中两个用例的 setup 就超过 90 秒。

这条经验对 day032 的 CI 流水线同样重要：**覆盖率插桩是"按执行行数计费"的**，
因此在 CI 上给数值密集的测试单独分组（或单独设阈值）比"把超时时间调大"更有效。

> 复现命令：`pytest -n 8 --dist loadscope`（需要 `pytest-xdist`；本日实测用
> 8 个进程，16 核机器）。不加 `-n` 也能得到同样的结果，只是慢一个数量级。

## 第九章：今日总结 —— 可以带走的判断

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|---------|
| 预算单位显式化并可注入 | "320 个什么"必须能被回答，否则差 18% | `tokens.TokenMeasurer` |
| 默认度量器是 `chars` | 可复现性优先于"与计费单位一致"（chunk_id 是去重键） | `resolve_measurer` |
| `tiktoken` 不可用时拒绝 | 静默降级会让 token 预算变成字符预算 | `resolve_measurer` 的报错 |
| 二分依赖"计数单调"假设 | 换度量器会让它给错答案且不报错 | `test_prefix_count_is_monotonic` |
| `Span` 只带区间不带文本 | 让"块不是原文子串"无处可写 | `base.Span` |
| 四个策略只差"在哪里切" | 收尾四条纪律只写一次，漏一条就会静默变差 | `Chunker.finalize` |
| 收尾顺序：修剪→重叠→合并→校验 | 先重叠再修剪会让两个起点撞在一起 | `finalize` 的注释 |
| 覆盖率是接口保证的 | 丢内容要响亮报错，不是给个 0.94 的报告 | `_assert_spans` |
| 覆盖率只算非空白字符 | 块首尾的空白是噪声，剪掉它是对的 | `_assert_spans` 的 `isspace` |
| 覆盖率差额有上界 | "98% 是否正常"从感觉问题变成算术问题 | `types.ChunkSet.coverage` |
| 重叠靠"下一块往前挪" | 每块仍是一个区间 → 覆盖率与去重都成立 | `_with_overlap` |
| 重叠落点优先落在内容上 | 带一段空行进块会让引用像从半空中开始 | `snap_to_boundary` |
| `max_tokens` 含义全局统一 | 否则重叠会被记成"原子块没切开" | `window_budget` |
| 结构策略拒绝重叠 | 跨标题回带会造出一条看起来合理的错来源 | `StructuralChunker.__init__` |
| 原子块整块保留并标记 | "两块都不对"比"一块超预算"更糟 | `ATOMIC_KINDS` |
| 定位失败退化为段落切并记 -1 | 一次"没能精确定位"必须留下痕迹 | `_locate` + `unlocated_sections` |
| 语义阈值用分位数 | 余弦相似度的绝对值依赖提供方与语言 | `similarity_percentile` |
| 语义在标题处额外断开 | `heading_path` 是块级属性，一块装不下两条路径 | `_spans` 的 `heading_breaks` |
| 自然段不含尾随空白 | 否则最后一段"不一样"，会凭空多切一刀 | `paragraph_spans` |
| `chunk_id` 含序号 | 同一段话出现两次时两块不会被互相覆盖 | `chunk_id_for` |
| `fingerprint` 单独留着 | 跨文档去重要的是"这是哪段内容" | `Chunk.fingerprint` |
| `text` 与 `retrieval_text` 分开 | 前缀写进正文会让引用引到原文里不存在的字 | `Chunk.retrieval_text` |
| 默认值按策略而不是全局 | overlap 对结构策略是错的，不是"默认 0" | `DEFAULT_POLICIES` |
| `ChunkPolicy` 字段默认值取 0 | 数据类给最保守的一套，策略默认值另有其表 | `ChunkPolicy` 的字段注释 |
| 参数按比例跟随预算 | 写死 48 会让"预算调成 64"变成"75% 重叠" | `chunking_policy_from` |
| 报告三列：规模/重复/超预算 | 三列答三个不同的问题，缺一列就会漏一类回归 | `strategy_summary` |
| 判定用"块文本含期望片段" | 它同时测召回与"片段有没有被切开" | `score_probes` |
| 指标方向分开处理 | 同一个排序函数处理两个方向一定会出错 | `ChunkingEvaluation.best` |
| 歧义探针单独返回 | 它让分数虚高且毫不显眼 | `ambiguous_probes` |

M6 的第二天到此结束。回头看它留下的东西：

```text
day062  分块：四种判据 + 预算单位 + 收尾六步 + 覆盖率不变量
        + 三列报告 + 探针集打分（192 个用例 / 95.85% 覆盖）
```

下一站是 **day063：缓冲复习日**。今天是 M6 前半段（解析 → 分块）的收口，
复习日要做的是把这两天的接缝再走一遍：`Document` 的六个块类型怎么喂给
四种判据、`knowledge_records()` 的形状怎么从"整份文档"平滑地变成"片段"、
以及那些"看起来是巧合"的一致（六种块 / 五种媒体类型 / 四种策略里那些
刻意保持得很小的数字）背后是不是同一条理由。

再往后（day064 起）会进入向量库与检索：今天交出去的 `chunk_id` 将直接成为
向量库的主键，`retrieval_text` 将成为被编码的那份文本，而
`oversized_count` 会变成"检索命中率偏低"的第一条排查线索。
