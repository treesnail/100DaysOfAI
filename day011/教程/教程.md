## 第一章：为什么需要反思 —— 失败后重试为什么总是重蹈覆辙

### 1.1 先复现问题：让 ReAct 自己面对失败

回顾 day006 的 ReAct 循环：工具执行失败后，错误会以 Observation 的形式回喂给模型，模型有机会在下一步自我纠正。day006 的测试 `test_unknown_tool_feeds_error_back` 验证的正是这条路径。看起来循环已经具备"容错能力"了，为什么还需要一个专门的反思模块？

跑一个稍微真实点的场景就会露馅。假设模型把中文数字喂给了计算器：

```text
Thought: 我需要计算 2+3
Action: calculator
Action Input: 二加三
Observation: 计算失败: 不支持的表达式
Thought: 让我再试一次
Action: calculator
Action Input: 二加三          ← 又错了，错得一模一样
Observation: 计算失败: 不支持的表达式
...
达到最大步数限制，未能得出最终答案
```

真实模型在这种局面上常出现两种失控模式：

**模式一：原样重试（Blind Retry）。** 模型看到"计算失败"，第一反应是"再试一次"——但它并不真正理解失败原因，于是把几乎相同的输入再发一遍。错误 Observation 只告诉它"失败了"，没有告诉它"为什么失败、下次该怎么改"。**没有诊断的重试，只是在消耗步数配额。**

**模式二： panic 式乱撞（Panic Wandering）。** 重试两三次仍失败后，模型开始病急乱投医：换一个不存在的工具、把输入改得面目全非、甚至直接编一个答案收场。每一步都是局部应激反应，没有一次停下来全局复盘。

### 1.2 问题的本质：执行流里没有"复盘"这个位置

ReAct 循环的结构是 Thought → Action → Observation 的**水平推进**：每一步紧接上一步，注意力永远在"下一步做什么"。但"为什么会失败"是一个需要**垂直抽身**才能回答的问题——要把整段轨迹摊在面前，跳出来看全局模式。

人类也是这样工作的。一个研究员实验失败后不会立刻原样重来，而是先写实验记录、分析失败原因、调整方案，再开始下一轮。**"做"和"复盘"是两种不同姿态的认知活动**，混在同一个循环流里，复盘永远会被"赶紧做下一步"的惯性挤掉。

```text
纯 ReAct：  尝试 ──失败──▶ 盲目重试 ──失败──▶ 乱撞 ──▶ 耗尽步数 ✗
                （错误只以 Observation 形式路过，无人诊断）

Reflexion： 尝试 ──失败──▶ 【停下来复盘】──▶ 带着改进建议重试 ──▶ 成功 ✓
                            │  输入：任务 + 完整失败轨迹
                            │  输出：失败原因 + 改进建议
                            ▼
                       建议注入下一轮 prompt
```

### 1.3 Reflexion：用语言做强化学习

Reflexion 机制来自 2023 年的同名论文（Shinn et al., *Reflexion: Language Agents with Verbal Reinforcement Learning*）。它的核心思想一句话就能说清：

> **传统强化学习用"梯度更新权重"来记住教训；Reflexion 用"自然语言写进上下文"来记住教训。**

不更新任何模型参数，只在失败后让 LLM 自己生成一段文字复盘（"我为什么失败、下次怎么改"），把这段文字存下来，在下一次尝试时注入提示词。模型权重没变，但**上下文变了**——而上下文正是 LLM 行为的全部输入。

三要素对应我们今天的实现：

| Reflexion 三要素 | 论文中的角色 | 今天的落地 |
|------------------|-------------|-----------|
| 失败信号（Reward signal） | 环境判定成功/失败 | `_attempt` 的失败检测（第二章） |
| 自我反思（Self-reflection） | LLM 总结失败原因 | `Reflector.reflect()`（第三章） |
| 情景记忆（Episodic memory） | 复盘文本入库备用 | `suggestion` 注入下一轮 prompt（第四章） |

### 1.4 与已有模块的关系：各管一段，互不越界

项目演进到现在，每个模块的职责边界都值得再对照一次：

| 模块 | 引入日 | 回答的问题 | 不管的事 |
|------|--------|-----------|---------|
| ReAct 循环（day006） | 执行原语 | "这一步做什么" | 全局方向、失败复盘 |
| Planner（day010） | 规划前置 | "整件事分几步做" | 每步具体怎么执行 |
| Reflector（今天） | 失败复盘 | "上次为什么败、下次怎么改" | 正常执行流程 |

注意 Reflector 的定位：**它只在失败时被调用，正常路径上零开销、零存在感**。这和 Planner（每次执行前必调用一次）是不同的介入时机——规划是"事前"，反思是"事后"。

> 思考题：day010 的思考题问过"子任务执行失败时当前架构会发生什么"。现在有了 Reflector，你能说出"反思"和"重规划（RePlanner）"分别处理哪一层失败吗？提示：反思改的是"同一个任务怎么做得更好"，重规划改的是"任务列表本身对不对"。

### 1.5 反思在 Agent 演进中的位置

```text
ReAct Agent（day006）
    │  会做事，但失败后只能盲目重试
    ▼
+ Planner（day010）
    │  想得全，但计划/执行出错时没有纠错机制
    ▼
+ Reflector（今天）
    │  败得起：失败被诊断、被记住、被用于改进
    ▼
多 Agent / LangGraph 编排（day012~013）
       反思成为每个节点的标准容错能力
```

可靠性不是靠"一次做对"堆出来的，而是靠"做错了能诊断、能改进"的闭环堆出来的。今天我们给 SmartResearch Agent 补上这个闭环的第一版。

## 第二章：失败检测 —— 什么时候该停下来复盘

### 2.1 反思的第一块基石：先得知道"失败了"

Reflector 自己不做失败检测——它只在**已被判定为失败**的轨迹上工作。检测职责在 ReactAgent 一侧，这符合关注点分离：执行层最清楚自己走到哪一步、工具返回了什么。

我们的失败判定有两条触发线（见 [agent/react_agent.py](../源码/smart-research-agent/smart_research_agent/agent/react_agent.py)）：

```python
# 触发线一：某步工具执行失败（仅启用 reflector 时中断本轮）
if self.reflector is not None and observation.startswith(_ERROR_PREFIXES):
    return f"尝试失败：{observation}", True, trajectory

# 触发线二：循环耗尽 max_steps 仍未给出 Final Answer
return "达到最大步数限制，未能得出最终答案", True, trajectory
```

### 2.2 触发线一：工具失败为什么立即中断

一个值得停下来想清楚的设计决策：day006 里工具失败后，错误 Observation 会回喂给模型，让它**在循环内自愈**；今天启用 reflector 后，我们却**立即中断本轮**、转入反思。为什么？

对比两种策略：

| 维度 | 循环内自愈（day006 默认） | 快速失败 + 反思（今天） |
|------|--------------------------|------------------------|
| 错误信息形态 | 一句"计算失败： ..."，无诊断 | LLM 复盘出的原因 + 改进建议 |
| 重试成本 | 每步一次 LLM 调用，可能空转多步 | 一次反思调用 + 全新一轮 |
| 上下文污染 | 失败步骤堆积在 messages 里 | 新一轮从干净的消息列表开始 |
| 适用错误 | 模型看一眼就能改的浅层错误 | 需要诊断的深层错误 |

关键洞察是：**循环内自愈和事后反思并不矛盾，它们是深浅两级容错**。浅层错误（比如 Observation 里已经写明了正确用法）模型当场就能改；但一旦模型开始原样重试——说明它没看懂错误——继续在循环里空转就是纯浪费。快速失败把这个"看不懂"的时刻显性化了：**一旦工具报错且我们启用了反思，就承认本轮已经偏离正轨，把诊断交给专门的复盘通道。**

当然，这是可争议的设计。如果工具错误大多是一次性抖动（网络超时之类），快速失败反而丢掉了循环内自愈的机会。我们把两种行为都保留了：不传 reflector 时走 day006 的自愈路径，传了才走快速失败——**策略选择权交给组装者**。

### 2.3 触发线二：耗尽步数是无声的失败

第二条触发线更隐蔽：循环走满 `max_steps`，既没有 Final Answer 也没有明显的错误 Observation——模型可能一直在"合理但无效"地打转（第一章的模式二）。这种失败没有任何异常抛出，**不主动检测就会静默溜走**。

检测方式简单到只是一行：`_attempt` 的 for 循环正常走完，就返回失败标记。但它的价值在于把"未达到终止条件"从一句兜底文案升级成了一个**可触发后续动作的事件**。

### 2.4 一个诚实的工程妥协：用字符串前缀嗅探错误

```python
_ERROR_PREFIXES = ("错误：", "工具执行失败", "计算失败")
```

必须坦白：这是启发式约定，不是健壮设计。它在赌"工具层永远用这几个前缀传递错误"。如果某个工具的**正常返回**里恰好以"计算失败"开头（比如搜索"计算失败率"这个词条），就会被误判。

为什么还这么写？因为正确的做法——让 `BaseTool.execute` 返回结构化结果（如 `ToolResult(success: bool, output: str)`）——会改动 day003~005 建立的工具层接口和所有既有测试，超出今天的范围。我们在代码注释里标注了这个妥协，并把它留作编程题（见[习题](../习题/习题.md)第 10 题）由你亲手修正。**学习项目里，把"已知的妥协"显性标注出来，比假装它不存在更有价值。**

> 思考题：除了文本前缀，还有哪些渠道可以传递"工具失败"信号？比较"异常""结构化返回值""前缀约定"三种方案的优劣。

### 2.5 轨迹：反思的原材料

光知道"失败了"还不够，Reflector 需要看到**怎么失败的**。`_attempt` 在循环中逐步积累轨迹文本：

```python
trajectory.append(
    f"第{step_no}步 Thought: {step.thought} | "
    f"Action: {step.action}({step.action_input}) | Observation: {observation}"
)
```

为什么不用现成的 `self.history`？两个原因：

- `history` 存的是结构化 `ReActStep`，**不含 Observation**——而 Observation 恰恰是失败现场最关键的证物；
- `history` 跨多轮尝试累积，反思只需要**本轮**的轨迹，混入前几轮反而稀释注意力。

所以每轮尝试维护独立的 `trajectory: list[str]`，失败时原样交给 Reflector。**给复盘者的材料应该是"这一轮的完整现场"，不多也不少。**

## 第三章：反思器的实现 —— 提示词、数据结构与软着陆解析

### 3.1 Reflection：三个字段的数据契约

```python
@dataclass
class Reflection:
    """一次反思的结构化结果."""

    failed: bool
    reason: str = ""
    suggestion: str = ""
```

三个字段各有讲究：

- **`failed` 恒为 True**。这是最反直觉的字段——既然 Reflector 只在失败时被调用，为什么还要存它？因为它是**调用方传入的事实陈述**，不是 LLM 的判断结果；留着它，`Reflection` 对象脱离调用上下文后依然自描述（呼应 day010 "Plan 携带 goal"的同一个原则：让数据自描述）。未来若扩展出"成功轨迹的事后总结"（比如提炼可复用经验），这个字段就是现成的区分标记。
- **`reason` 与 `suggestion` 分离**。原因回答"为什么败"，建议回答"下次怎么办"。混在一起的一段散文无法被程序分别消费——我们只需要把 `suggestion` 注入下一轮，而不是把整段复盘塞回去。**注入上下文的每一个 token 都要有明确目的。**

### 3.2 REFLECT_PROMPT：复盘员的人格设定

```python
REFLECT_PROMPT = """你是一名严格的事后复盘员。下面是 Agent 执行某任务的轨迹，该次执行已经失败。

请完成两件事：
1. 用一句话指出失败的根本原因（reason）
2. 给出一条可操作的改进建议，指导下一次尝试（suggestion）

严格输出 JSON 对象，不要输出其他内容，例如：
{{"reason": "失败原因", "suggestion": "改进建议"}}

任务：{task}

执行轨迹：
{trajectory}
"""
```

逐条对照 day010 的提示词设计原则：

- **角色设定"严格的事后复盘员"**：给模型一个与"执行者"不同的人格。同一个模型，被框成执行者时惯性是"赶紧做下一步"，被框成复盘员时才会冷静归因。这就是 1.2 节说的"两种认知姿态"在提示词层面的落地。
- **"该次执行已经失败"是事实陈述而非提问**：不让模型判断"是否失败"（那是执行层已做的检测），只让它归因。减少一个自由度，就少一种跑偏方式。
- **"一句话"与"一条"**：反思输出要注入下一轮的上下文，冗长的复盘会挤占宝贵的上下文窗口并稀释注意力。约束篇幅就是约束注入成本。
- **"可操作的"**：这是质量关键词。没有它，模型爱给"下次要小心一点"这类正确的废话；有了它，建议更可能是"calculator 的输入必须是阿拉伯数字表达式"这种能直接改变行为的指令。
- **JSON 输出 + few-shot 示例**：与 `PLAN_PROMPT` 完全同构的理由——输出要被程序消费，就必须锁定结构。

### 3.3 软着陆解析：与 parse_plan 的"严厉"刻意相反

day010 的 `parse_plan` 是四道防线、层层抛异常；今天的 `parse_reflection` 却**永不抛异常**：

```python
def parse_reflection(text: str) -> tuple[str, str]:
    """解析 LLM 的反思输出，返回 (reason, suggestion).

    与 parse_plan 的「四道防线 + 抛异常」不同，这里采用软着陆：
    反思结果是建议性数据，解析不出来时用原文兜底，保证重试流程不被打断。
    """
    cleaned = text.strip()
    start = cleaned.find("{")
    end = cleaned.rfind("}")
    if start != -1 and end != -1 and end > start:
        try:
            data = json.loads(cleaned[start : end + 1])
        except json.JSONDecodeError:
            data = None
        if isinstance(data, dict):
            reason = str(data.get("reason") or "").strip()
            suggestion = str(data.get("suggestion") or "").strip()
            if reason or suggestion:
                return reason, suggestion
    return cleaned or "LLM 未给出有效复盘", ""
```

为什么同一个项目里两种解析哲学并存？因为两种输出的**关键性不同**：

| 维度 | `parse_plan`（day010） | `parse_reflection`（今天） |
|------|------------------------|---------------------------|
| 输出性质 | **负载数据**：整个执行流程都建立在计划之上 | **建议数据**：有则更好，无则降级 |
| 解析失败时 | 计划不可用，必须抛异常终止 | 不该让"反思失败"成为新的故障点 |
| 兜底行为 | 无兜底，抛 `PlanParseError` | 原文作 reason，suggestion 置空 |
| 设计哲学 | 快速失败（Fail Fast） | 优雅降级（Graceful Degradation） |

设想一下如果反思解析也抛异常：任务失败了 → 调反思器 → 反思输出格式不对 → 再抛一个异常……**容错机制本身成了新的故障源**，这是容错设计的大忌。软着陆保证：哪怕 LLM 的复盘完全没法解析，重试流程也照常推进，只是没有建议可注入（suggestion 为空时，下一轮 prompt 不附加任何内容）——系统从"反思增强"优雅降级回"普通重试"。

边界截取（`find("{")` / `rfind("}")`）与 `parse_plan` 的容错手法一致，处理"JSON 外包废话"这个最常见的不听话。

### 3.4 Reflector 类：薄而有痕

```python
class Reflector:
    """反思器：对失败的执行轨迹做复盘，产出可注入下一轮的建议."""

    def __init__(self, llm: BaseLLM, max_retries: int = 2):
        self.llm = llm
        self.max_retries = max_retries
        self.reflections: list[Reflection] = []
```

三个成员各有职责：

- **依赖注入 BaseLLM**：与 Planner 完全同构的红利——生产注入真实 LLM，测试注入 MockLLM，离线且确定。
- **`max_retries=2`**：反思不是无限资源。为什么默认 2 而不是 5？经验法则是：**如果两次带诊断的重试都没成功，问题大概率不在"执行细节"而在"任务本身"**（缺工具、缺信息、目标不可达），继续重试只是烧 token。这个上限同时是成本控制阀和"该升级处理"的报警线。
- **`reflections` 列表**：每次反思都留痕。它是测试断言的抓手（`len(reflector.reflections)` 精确计数），也是运行期的审计日志——事后可以回答"这个 Agent 今天失败过几次、都败在哪"。**可观察性不是事后补的，是设计时留的。**

`reflect()` 方法本身只有五步：拼轨迹文本 → 格式化提示词 → 调 LLM → 软着陆解析 → 记录并返回。完整的见 [agent/reflexion.py](../源码/smart-research-agent/smart_research_agent/agent/reflexion.py)。

## 第四章：把建议注入下一轮 —— ReactAgent 的向后兼容改造

### 4.1 改造的整体结构：run 变薄，_attempt 出现

原来的 `run()` 直接包含整个 ReAct 循环。引入"多轮尝试"后，循环体必须能被重复执行，于是抽成 `_attempt()`，`run()` 退化为重试编排器：

```python
def run(self, task: str) -> str:
    logger.info("接收到任务: %s", task)
    max_attempts = 1 + (self.reflector.max_retries if self.reflector is not None else 0)
    suggestion = ""
    for attempt in range(1, max_attempts + 1):
        answer, failed, trajectory = self._attempt(task, suggestion)
        if not failed or attempt == max_attempts:
            return answer
        reflection = self.reflector.reflect(task, trajectory)
        suggestion = reflection.suggestion
        logger.info("第 %d 次尝试失败，注入反思建议后重试: %s", attempt, suggestion)
    return answer  # pragma: no cover - 循环内必有返回
```

三个编排细节：

1. **`max_attempts = 1 + max_retries`**：1 次原始尝试 + 至多 max_retries 次重试。语义清晰：max_retries 是"**额外**给的机会"，不是总次数。
2. **最后一次失败后不再反思**：`attempt == max_attempts` 时直接返回答案。此时反思产出的建议无人消费，调了也是白调——**不为无人消费的结果付费**。
3. **suggestion 只携带最新一条**：第 3 轮尝试只注入第 2 次反思的建议，不累积全部历史。取舍的考量是上下文成本；如果你怀疑模型会"反复犯不同错误"，可以把所有 `reflector.reflections` 的建议拼进去——这是留给你的思考题（习题第 9 题）。

### 4.2 建议注入到哪个位置：system 和 user 双管齐下

```python
if suggestion:
    system_content += REFLECTION_HINT.format(suggestion=suggestion)
    user_content += f"\n\n上一次失败的教训（来自反思模块）：{suggestion}"
```

为什么注两处？

- **system 位置**：system prompt 在多数模型的训练中被赋予更高权重，适合放"本轮必须遵守"的强指令。`REFLECTION_HINT` 用"务必遵守"的措辞强化约束。
- **user 位置**：教训与任务本身在语义上是绑定的（"这个任务上次是这么失败的"），放在任务旁边，模型做第一步推理时就能看到。

这有重复注水的嫌疑，但在提示词工程里，**关键约束冗余出现一两次，被遵守的概率显著高于只出现一次**——尤其是在长上下文里，单一位置的指令容易被注意力稀释。冗余在这里是特性不是 bug。

注意 `if suggestion:` 的守卫：反思输出解析失败时 suggestion 为空串，此时两处都不注入，下一轮 prompt 与首轮完全相同——这就是 3.3 节"优雅降级为普通重试"的具体形态。

### 4.3 向后兼容：不传 reflector 时一行行为都不变

任务要求"保持原有公开接口向后兼容"，我们是这样兑现的：

| 行为点 | 无 reflector（day006 行为） | 有 reflector |
|--------|---------------------------|--------------|
| 尝试次数 | 恰好 1 次（`max_attempts=1`） | 至多 `1 + max_retries` 次 |
| 工具失败后 | 错误 Observation 回喂，循环继续 | 立即中断本轮，转入反思 |
| prompt 内容 | 不附加任何反思内容 | 失败后续轮注入 suggestion |
| 返回值 | 与 day006 完全相同 | 成功路径相同；失败路径返回失败说明 |

关键的兼容开关在这行：

```python
if self.reflector is not None and observation.startswith(_ERROR_PREFIXES):
```

`reflector is None` 时短路求值直接跳过整个失败检测分支，循环按 day006 原样推进。day006 的三个回归测试（`tests/test_react_loop.py`）今天**一字未改、全部通过**，这就是兼容性的可执行证明。

### 4.4 完整时序：一次"失败 → 反思 → 成功"的全景

```text
ReactAgent.run("2+3 等于几？")
   │
   ├─ 第 1 次尝试 ─────────────────────────────
   │   LLM: Thought + Action: calculator(二加三)
   │   工具: 计算失败: 不支持的表达式          ← 触发线一命中
   │   中断本轮，trajectory 记录现场
   │
   ├─ Reflector.reflect(task, trajectory)
   │   LLM: {"reason": "中文数字无法解析",
   │         "suggestion": "请使用阿拉伯数字表达式"}
   │   解析 ─▶ Reflection ─▶ 记入 reflections
   │
   ├─ 第 2 次尝试（prompt 注入 suggestion）─────
   │   system: ...务必遵守：请使用阿拉伯数字表达式
   │   user:   任务: 2+3 等于几？ + 上次的教训
   │   LLM: Action: calculator(2+3) ─▶ Observation: 5
   │   LLM: Final Answer: 2+3 等于 5           ← 成功返回
   ▼
return "2+3 等于 5"
```

整个流程在 [main.py](../源码/smart-research-agent/smart_research_agent/main.py) 的 `demo_reflexion()` 里用 MockLLM 编排成可离线运行的演示，直接 `python -m smart_research_agent.main` 就能看到上面的完整日志。

### 5.2 组装一个带反思的 Agent

```python
from smart_research_agent.agent.react_agent import ReactAgent

reflector = Reflector(llm=MockLLM(responses=['{"reason": "...", "suggestion": "..."}']))
```

注意一个工程细节：**Agent 和 Reflector 各用各的 LLM 实例**。MockLLM 的 responses 队列按调用顺序消费，如果两者共享一个实例，响应脚本的顺序就要把反思调用穿插进 Agent 调用里编排，既脆弱又难读。分开注入后，两条队列各自独立，测试意图一目了然。生产环境里两个实例背后可以是同一个真实模型——**区分的是"角色"，不是"模型"**。

### 5.3 测试设计：三层覆盖

`tests/test_reflexion.py` 分三个测试类，对应本章的三块内容：

**解析层（TestParseReflection）**——验证软着陆的三种命运：

```python
def test_non_json_falls_back_to_raw_text(self):
    reason, suggestion = parse_reflection("模型直接输出了一段散文复盘")
    assert reason == "模型直接输出了一段散文复盘"

```

JSON 干净 → 正常解析；JSON 包废话 → 边界截取；完全不是 JSON → 原文兜底。每条路径一个用例。

**反思器层（TestReflector）**——验证端到端与留痕：

```python
def test_reflect_end_to_end(self):
    llm = MockLLM(responses=['{"reason": "表达式无法解析", "suggestion": "输入 2+3"}'])
    reflector = Reflector(llm=llm)
    reflection = reflector.reflect("2+3 等于几？", ["第1步 ..."])
    assert reflection == Reflection(failed=True, reason="表达式无法解析", suggestion="输入 2+3")
    assert reflector.reflections == [reflection]
```

**集成层（TestReactAgentReflexion）**——这是今天的主战场，六个用例分别钉死一个行为承诺：

| 用例 | 钉住的承诺 |
|------|-----------|
| `test_fail_reflect_retry_then_success` | 完整链路：反思被触发恰好一次，suggestion 同时出现在重试轮的 system 和 user 消息里 |
| `test_max_retries_limits_attempts` | 一直失败时 Agent LLM 恰好被调 `1 + max_retries` 次，Reflector 恰好 `max_retries` 次（最后一次失败后不反思） |
| `test_no_final_answer_triggers_reflection` | 耗尽步数（无 Final Answer）同样触发反思——触发线二不是摆设 |
| `test_success_without_reflection` | 一次成功时反思调用为零——正常路径零开销 |
| `test_backward_compatible_without_reflector` | 不传 reflector 时与 day006 行为逐字节一致 |
| `test_parse_error_in_reflection_output_still_retries` | 反思输出不是 JSON 时软着陆，重试照常推进 |

其中建议注入的断言值得看一眼写法——不猜 messages 的下标结构，而是按 role 过滤后查内容：

```python
second_attempt = agent_llm.calls[1]
assert any("请使用阿拉伯数字表达式" in m.content for m in second_attempt if m.role == "system")
assert any("请使用阿拉伯数字表达式" in m.content for m in second_attempt if m.role == "user")
```

`agent_llm.calls[1]` 是第二次 LLM 调用的完整消息列表（MockLLM 的 `calls` 属性在 day005 就为此设计好了）。**断言针对行为契约（"system 和 user 里都含有建议"），而不是实现细节（"messages[0] 的末尾追加了什么"）**，这样未来调整注入的具体位置时测试不用跟着碎。

## 第六章：今日总结 —— 反思模块的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 反思与执行分离 | "做"与"复盘"是两种认知姿态，混在循环里复盘会被惯性挤掉 | `reflexion.py` 独立成模块 |
| Reflector 不做失败检测 | 关注点分离：执行层最了解自己的失败现场 | `Reflector.reflect` 只接收已判定失败的轨迹 |
| 工具失败立即中断本轮 | 模型开始原样重试 = 没看懂错误，继续空转是浪费；快速失败把诊断交给专门通道 | `_attempt` 触发线一 |
| 耗尽步数也算失败 | 无声的失败不主动检测就会静默溜走 | `_attempt` 触发线二 |
| `max_retries=2` | 两次带诊断的重试仍失败，问题多半在任务本身而非执行细节 | `Reflector.__init__` |
| 反思解析软着陆 | 容错机制自身绝不能成为新的故障源 | `parse_reflection` 永不抛异常 |
| suggestion 双位置注入 | 关键约束冗余出现，被遵守的概率更高 | `_attempt` 的 system + user |
| 最后一次失败后不反思 | 不为无人消费的结果付费 | `run` 的 `attempt == max_attempts` 分支 |
| Agent 与 Reflector 分开注 LLM | 区分的是角色不是模型；测试队列独立、意图清晰 | 测试与 main.py 的组装方式 |
| 不传 reflector 行为不变 | 新能力以可选参数接入，旧测试一字不改全绿 | `reflector is not None` 守卫 |

今天埋下的伏笔，后续会回收：

- **结构化工具结果**：`_ERROR_PREFIXES` 的文本嗅探是已标注的妥协，`ToolResult(success, output)` 才是真正的解法（习题第 10 题）。
- **反思的长期记忆化**：现在 `reflections` 只在一次 `run` 的生命周期内有意义；接入 day009 的长期记忆后，"上次这类任务败在哪"可以跨会话复用——那才是 Reflexion 论文里"情景记忆"的完全体。
- **反思作为图节点**：day013 的 LangGraph 编排里，反思会从一个"if 分支"升级为状态图里的标准节点，与重规划节点并列。
