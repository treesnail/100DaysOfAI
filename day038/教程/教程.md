## 第一章：为什么需要服务层 —— 脚本形态的三道天花板

### 1.1 进程边界：调用方与你不在同一个进程里

脚本形态的调用方式是"同进程函数调用"：`agent.run(task)` 的调用方必须 import 你的代码、装你的依赖、跑在你的 Python 解释器里。这在三个维度上锁死了使用者：

- **语言锁死**：调用方必须会写 Python。一个 Node.js 前端、一个 Java 后端，都没法 import 你的包；
- **环境锁死**：调用方必须复刻你的依赖环境（pydantic 版本、模型 SDK、系统库），两个项目共用一个解释器时版本冲突无解；
- **部署锁死**：调用方和你的代码必须在同一台机器、同一个进程空间，没法独立扩容、独立升级。

HTTP 服务把调用方式换成"跨进程消息"：任何语言、任何环境，只要能发 HTTP 请求就能调用。**进程边界不是障碍，而是解耦的手段**——两边各自演进，只共同遵守一份 API 契约。

### 1.2 并发模型：脚本一次只服务一个任务

脚本是"跑完就退"的批处理模型。假设 Agent 跑一次任务要 5 秒（多轮 LLM 调用），十个用户同时来，脚本形态只能排队串行——第一个人等 5 秒，第十个人等 50 秒。而一个 ASGI 服务器（uvicorn）管理着一个事件循环与线程池，天然并发：请求 A 在等待 LLM 网络响应时，请求 B、C 的处理照常推进。**服务化把"一次跑一个任务"升级为"持续驻留、并发受理"**。

### 1.3 API 契约：把"怎么用"从口头约定变成机器可校验的协议

脚本形态下，"这个函数怎么调"写在哪？注释里、文档里、口头传达里。调用方传错参数，直到运行时才炸出一个 Python 堆栈。HTTP 服务则把契约前置：**请求长什么样、字段叫什么、类型是什么、哪些必填，全部在框架层声明并由框架强制执行**。今天我们会看到，FastAPI 用 Pydantic 模型声明契约后：

- 不合法的请求在**路由函数之前**就被 422 拦截，业务代码根本不会被脏数据触碰；
- 同一份声明自动生成 `/openapi.json` 与交互式文档 `/docs`——契约同时是文档，文档永远与代码同步。

这就是"为什么 Notebook/脚本形态不够"的完整答案：不是功能不够，而是**它无法提供进程边界、并发受理与机器可校验的契约**这三样工程必需品。

## 第二章：Pydantic 校验的双重角色 —— 契约即文档

### 2.1 运行时契约：请求还没进路由就被审判

看 `api/schemas.py` 中的请求模型（完整代码见 `smart_research_agent/api/schemas.py`）：

```python
class ChatRequest(BaseModel):
    message: str = Field(min_length=1, description="用户消息，不能为空")
    temperature: float = Field(default=0.7, ge=0.0, le=2.0, description="采样温度")
```

当路由声明 `def chat(req: ChatRequest, ...)`，FastAPI 在调用 `chat` **之前**完成了一整条流水线：

```text
读请求体 -> 按 Content-Type 解析 JSON -> 用 ChatRequest.model_validate 校验
  ├─ 通过 -> 构造 ChatRequest 实例，注入路由函数
  └─ 失败 -> 直接返回 422，路由函数根本不会执行
```

注意 `temperature` 的校验是**三层叠加**的：类型注解（必须是 float）、Field 约束（0~2 之间）、默认值（不传则取 0.7）。缺 `message`、传 `"message": 123`、传 `temperature: 3.0`，三种错误全部在框架层被拦截——业务代码里一行防御性校验都不用写。测试 `TestValidation` 用四组非法负载分别验证了这四条路径。

### 2.2 422 是怎么产生的

请求校验失败时，FastAPI 抛出内部的 `RequestValidationError`（Pydantic `ValidationError` 的 HTTP 化包装），框架内置的异常处理器把它转成 **HTTP 422 Unprocessable Entity**，响应体是统一结构：

```json
{
  "detail": [
    {"type": "missing", "loc": ["body", "message"], "msg": "Field required", "input": {}}
  ]
}
```

`loc` 指出出错位置（body 的哪个字段），`type` 是机器可判定的错误码（missing / string_type / less_than_equal 等），`msg` 是给人读的说明。为什么是 422 而不是 400？400 Bad Request 表示"请求格式错误，服务器无法理解"（比如 JSON 语法损坏——FastAPI 对这种情况其实也归并到 422 处理，见 `test_invalid_json_body_422`）；422 的语义更精确：**语法理解没问题，但语义不符合契约**。客户端据此可以区分"我发了个坏包"与"我的字段不合法"。

### 2.3 文档源：同一份模型，反射成 OpenAPI

Pydantic 模型的第二重角色是**文档源**。FastAPI 启动时把所有路由的签名与模型反射成 JSON Schema，拼出 `/openapi.json`——`/docs` 的 Swagger UI、客户端 SDK 代码生成器全都消费它。测试 `test_openapi_schema_contains_endpoints_and_models` 守护了这一点：三个端点与四个模型都出现在生成的 schema 里。

这就形成了与 day037 的**同源原则**（schema 从工具元数据自动生成）完全同构的结构：

```text
day037: 工具实现 <- BaseTool 元数据 -> JSON Schema -> 下发给 LLM
day038: 接口实现 <- Pydantic 模型   -> JSON Schema -> 生成 OpenAPI 文档
```

两处都是"单一事实源"：**契约不是另写的一份文档，而是从实现中派生**。文档与代码漂移的问题在结构上被消除。

### 2.4 响应侧同样受契约约束

`response_model=ChatResponse` 不只用于文档——FastAPI 还会用它**过滤与序列化**路由返回值。如果路由多返回了契约外的字段，会被剔除；少了契约要求的字段，会报错。响应契约保护的是调用方：它拿到的永远是可以按文档解析的结构。我们的 `ErrorResponse` 同理——500 错误不是一段框架默认的纯文本堆栈，而是稳定的 `{"detail", "error_type"}` 结构，客户端可以按 `error_type` 分支处理。

## 第三章：同步 Agent 代码遇上异步框架 —— 事件循环与线程池

### 3.1 事件循环为什么不能被阻塞

FastAPI 跑在 ASGI 服务器上，核心是**单线程事件循环**：所有请求的网络 I/O 都在这一个线程里以协作式多任务推进。协程在 `await` 处主动让出控制权，事件循环趁机去服务其他请求——这是它高并发的来源。

但"协作式"意味着**每一环都必须自觉让出**。如果某个路由函数里有一段阻塞代码（比如我们的 `agent.run()`——内部是同步的 `llm.chat()`，一次 LLM HTTP 调用阻塞 2 秒，十轮就是 20 秒），事件循环在这 20 秒里完全停摆：**所有**正在处理的请求一起卡住，健康检查都会超时。一个人的慢任务拖死了全部用户。

### 3.2 `def` 与 `async def` 路由的分野

FastAPI 对这个问题的处理非常务实——看路由的声明方式决定执行策略：

- 声明为 `async def`：函数在**事件循环里直接执行**。适用于内部全是 awaitable（httpx.AsyncClient、数据库异步驱动）的纯异步代码；
- 声明为普通 `def`：FastAPI 自动把函数**丢进线程池**（anyio 的 `run_in_threadpool`，底层约等于 `loop.run_in_executor`），事件循环照常运转，等线程跑完再回来序列化响应。

我们的三个端点全部声明为 `def`（见 `smart_research_agent/api/routes.py`）——因为 LLM 调用与 Agent 循环是既有 day037 的同步阻塞代码。这不是"放弃了异步性能"，而是**正确的匹配**：阻塞型工作交给线程池，事件循环专心做网络多路复用。并发能力由线程池的容量提供（默认 40 个工作线程），对 LLM 调用这种"等网络"的 I/O 密集任务完全够用。

反过来，如果我们把 `agent.run()` 包在 `async def` 路由里直接调用，就是教科书级的事故：每次 Agent 任务期间事件循环冻结。哪天把底层 LLM 客户端换成原生异步实现（`openai.AsyncOpenAI`），才轮到路由改成 `async def` 并在循环内部 `await`——**同步/异步的边界应该画在真正发生阻塞的地方**。

### 3.3 一张对照表

| 业务代码性质 | 路由声明 | FastAPI 的处理 | 事件循环状态 |
|---|---|---|---|
| 纯异步（全程 awaitable） | `async def` | 事件循环直接执行 | 不阻塞 |
| 同步阻塞（requests、time.sleep、我们的 Agent） | `def` | 丢进线程池执行 | 不阻塞 |
| 同步阻塞代码塞进 `async def` | `async def` | 事件循环直接执行 | **冻结** |

## 第四章：应用工厂与依赖注入 —— 为可测试性而设计

### 4.1 为什么是 `create_app()` 工厂而不是模块级 `app`

FastAPI 教程最常见的写法是模块级 `app = FastAPI()`。简单，但有两个硬伤：模块 import 时就完成了全部构建（测试想换个配置都来不及），且全局唯一（一个进程只能有一种装配方式）。我们采用**工厂函数**（完整代码见 `smart_research_agent/api/app.py`）：

```python
def create_app(
    llm: BaseLLM | None = None,
    agent_factory: Callable[[], FunctionCallingAgent] | None = None,
) -> FastAPI:
    ...
    app.state.llm = resolved_llm
    app.state.agent_factory = agent_factory
```

每次调用产出一个全新装配的 app：测试注入 MockLLM 得到完全离线的实例，生产不传参数走 `default_llm()`（有 API Key 用真实客户端，否则退回 Mock 占位并在日志告警——让服务在没配密钥的开发机上也能启动自检）。装配逻辑集中在一处，`uvicorn smart_research_agent.api.app:create_app --factory` 也认这个约定。

### 4.2 `app.state` 与 `Depends`：注入的两半

注入分两半完成。写的一半在工厂里：对象挂到 `app.state`（FastAPI 提供的应用级状态容器）。读的一半在路由的依赖函数里（`api/routes.py`）：

```python
def get_llm(request: Request) -> BaseLLM:
    return request.app.state.llm

def get_agent(request: Request) -> FunctionCallingAgent:
    return request.app.state.agent_factory()

@router.post("/chat", response_model=ChatResponse)
def chat(req: ChatRequest, llm: BaseLLM = Depends(get_llm)) -> ChatResponse:
    ...
```

`Depends(get_llm)` 声明："调用本路由前，先执行 `get_llm`，把返回值作为 `llm` 参数传入"。路由函数因此**不再 import 任何全局单例**——它要的每样东西都是参数喂进来的。

为什么这对测试至关重要？对比两种写法：

```text
没有 DI：路由函数内部 import 全局 llm -> 测试想换 Mock，只能 monkeypatch 模块属性
         （改的是全局状态，用例间互相污染，并行测试直接翻车）
有了 DI：测试 create_app(llm=MockLLM(...)) -> 每个用例一个独立 app 实例，
         注入对象互不可见，用完即弃
```

### 4.3 Agent 为什么是工厂而不是实例

注意 `app.state` 上挂的是 `agent_factory`（工厂）而非 agent 实例，且 `get_agent` **每个请求调用一次工厂**。原因在 day037 的 `FunctionCallingAgent` 设计里：Agent 实例持有单次任务的执行轨迹（`call_history`），跑完一个任务实例就"脏"了。如果跨请求复用同一个 Agent，请求 B 的响应里会混入请求 A 的工具调用记录——典型的状态泄漏。LLM 客户端（无单次任务状态）可以共享，Agent（有单次任务状态）必须按请求隔离。**共享与隔离的分界线，画在"对象是否携带请求级状态"上。**

### 4.4 全局异常处理器：错误也是契约

`create_app` 里注册了一个兜底异常处理器：任何路由/依赖里未捕获的异常，统一转成 `ErrorResponse` 结构的 HTTP 500，而不是框架默认的纯文本响应。客户端面对的 500 也是结构化、可编程解析的——**错误响应同样是 API 契约的一部分**。测试时用 `TestClient(app, raise_server_exceptions=False)` 让异常走处理器而不是在测试进程里直接抛出，这才贴近生产服务器的真实行为（`test_agent_exception_returns_500_error_response`）。

## 第五章：三个端点与两种运行方式

### 5.1 端点设计

| 端点 | 方法 | 用途 | 请求模型 | 响应模型 |
|---|---|---|---|---|
| `/health` | GET | 探活：负载均衡/容器健康检查 | 无 | `{"status", "version"}` |
| `/chat` | POST | 单轮对话，不走工具 | `ChatRequest` | `ChatResponse` |
| `/agent/run` | POST | 完整 Agent 任务（function calling 循环） | `AgentRunRequest` | `AgentRunResponse` |

`/agent/run` 的响应是这个服务最有价值的部分——不只返回 `answer`，还返回 `steps`（消耗了几轮 LLM 调用）与 `tool_calls`（每次调用的工具名、参数、结果、成败）：

```json
{
  "answer": "1024 乘以 4 等于 4096。",
  "steps": 2,
  "tool_calls": [
    {"name": "calculator", "arguments": {"expression": "1024 * 4"}, "result": "4096", "success": true}
  ]
}
```

**执行轨迹随答案一起返回**，调用方可以审计 Agent 的每一步决策——这是把"黑盒函数"升级为"可观测服务"的关键一步（与 day032 的可观测性一脉相承）。`steps` 的计算有个细节：LLM 实例跨请求共享时其 `calls` 日志是累积的，所以取 `run()` 前后的**差值**（见 `api/routes.py` 注释）。

### 5.2 方式一：TestClient（测试与演示用）

`fastapi.testclient.TestClient` 基于 httpx 在**进程内**直接调用 ASGI 应用：走完整的路由匹配、请求体校验、依赖注入、响应序列化链路，但不监听端口、不需要网络。我们的 `tests/test_api.py` 与 `scripts/api_demo.py` 都用它——CI 里 14 个接口测试 3 秒内跑完，全程离线。

### 5.3 方式二：uvicorn（真实服务）

```bash
# 工厂模式启动（推荐，与 create_app 约定对应）
uvicorn smart_research_agent.api.app:create_app --factory --host 0.0.0.0 --port 8000
# 或等价的模块入口
python -m smart_research_agent.api.app
```

启动后 `http://127.0.0.1:8000/docs` 就是自动生成的交互式文档：三个端点、每个字段的类型与约束、在线试调——全部来自第二章讲的 Pydantic 模型反射。

## 第六章：选型与呼应 —— FastAPI vs Flask，服务化与容器化

### 6.1 为什么是 FastAPI 而不是 Flask

| 维度 | Flask | FastAPI |
|---|---|---|
| 并发模型 | WSGI 同步，一个请求一个线程，I/O 等待时空转 | ASGI 异步 + 线程池混合，I/O 等待时服务其他请求 |
| 请求校验 | 无内建，靠 marshmallow/pydantic 手动接线 | Pydantic 模型即契约，框架内建、自动执行 |
| API 文档 | 需 flasgger 等第三方且与代码分离易漂移 | 从模型自动反射 OpenAPI，同源无漂移 |
| 类型驱动 | 可选 | 路由签名即文档，类型贯穿全链路 |

对 Agent 服务这个场景，决定性的是第一条：**我们的请求大多是"等 LLM 响应"的 I/O 密集任务**，Flask 的同步模型下每个等待中的请求都独占一个线程干等，FastAPI 的 ASGI 模型让这些等待被多路复用。第二、三条则是本章反复讲的契约与同源——Flask 要靠生态拼装，FastAPI 内建。

### 6.2 与 day022 的呼应：服务化是容器化的前提

回看 day022：当时我们把项目打进 Docker 镜像，但容器里跑的只是一个"跑完就退"的脚本——容器启动、执行、退出，更像一次批处理。今天之后，容器里终于有了一个**长驻进程**：uvicorn 监听端口、持续受理请求。这正是容器编排（K8s、docker-compose）假设的工作负载形态：

- **探活**：`/health` 端点就是容器的 liveness/readiness 探针要打的地方——没有服务层时"进程活着"只能靠 `ps` 猜，现在有了语义化的健康信号；
- **无状态**：请求级状态（Agent 轨迹）按请求隔离、随响应返回，实例本身无状态——容器可以任意复制、滚动升级，这正是 4.3 节设计决策的运维回报；
- **横向扩容**：QPS 上来时直接加容器副本，负载均衡把请求分摊到各实例——前提正是 1.1 节的进程边界与无状态设计。

至此，M4 的五天形成一条完整的链路：day034 Tokenization（理解模型的输入与成本）→ day036 Prompt 工程（行为控制）→ day037 Function Calling（结构化工具调用）→ **day038 FastAPI（服务化交付）**。Agent 从一个研究原型，变成了一个可以交付给任何调用方的工程产品。

### 6.3 今日总结

1. **服务层的价值不在"能跑"，在于三样工程必需品**：进程边界（解耦语言与环境）、并发受理（持续驻留）、机器可校验的 API 契约。
2. **Pydantic 模型一鱼两吃**：运行时按它校验请求（不合法 → 422，业务代码零防御成本），启动时由它反射出 OpenAPI 文档——契约即文档，同源不漂移。
3. **同步代码进异步框架的正确姿势是 `def` 路由**：FastAPI 把它丢进线程池，事件循环不被阻塞；把阻塞代码塞进 `async def` 会冻结整个服务。
4. **依赖注入为测试而设计**：`create_app` 工厂 + `app.state` + `Depends`，让测试注入 MockLLM 完全离线，也让"共享 LLM、按请求隔离 Agent"的状态边界清晰可见。
5. **错误也是契约**：全局异常处理器把 500 统一为 `ErrorResponse` 结构；`/health` 端点为容器探活提供语义化信号——服务化是容器化（day022）的前提。
