## 第 1 题

**答案：D**

解析：A、B、C 是教程第一章归纳的 Agent 评估三大特有难点——评估对象从"一个终态产物"变成"一条多步轨迹"（A）；"部分正确"是常态，二元对错不够用（B）；Agent 与环境有交互，环境反馈变化导致评估不可重复，必须用 MockLLM + 假工具控制环境（C）。D"参考答案不唯一、需要模糊匹配"在**单轮输出评估**里同样存在（开放式问答的参考答案从来就不唯一），它是 LLM 评估的通用难题，不是 Agent 评估特有的。

## 第 2 题

**答案：A**

解析：步数效率公式为 `min(1, 最小必要步数 / 实际步数)`。最小必要步数 = `len(expected_tools) + 1` = 2 + 1 = 3（每个期望工具一步 + 最后 Final Answer 一步）。实际走了 6 步，效率 = 3/6 = **0.5**。这 6 步里有 3 步是浪费的（冗余或犹豫），每步都是一次 LLM 调用，成本翻了一倍——这正是步数效率要暴露的问题。

## 第 3 题

**答案：C**

解析：逐项计算。

- **集合视角**：实际集合 {calculator, web_search} 与期望集合完全相同，precision = 2/2 = 1，recall = 2/2 = 1，f1 = 1.0。**集合信息看不出顺序错误。**
- **顺序视角**：`LCS(["calculator", "web_search"], ["web_search", "calculator"])` = 1（两个元素顺序颠倒后，最多只能保其中一个保持相对顺序），order = 1/2 = **0.5**。

这道题想强化的认知是教程 3.4 节的核心：**F1 满分的轨迹仍可能顺序错误**，这正是集合指标之外还要引入 LCS 顺序分的原因。B 和 D 错在把顺序错误也算进了 F1——precision/recall 是集合运算，天然忽略顺序。

## 第 4 题

**答案：对**

解析：不截断的话，考虑期望 2 个工具（最小必要 3 步）但 Agent 一步直接给答案的轨迹：效率 = 3/1 = 3.0，反而是"高效率"——这奖励了"少做事"。截断到 1.0 后，这类轨迹在效率维度不扣分（它确实快），但其工具召回率会是 0（该调的工具一个没调），由工具指标接住这个惩罚。教程 3.3 节称之为"让正确的指标管正确的事"：步数效率只管"有没有浪费步数"，可靠性交给 tool_accuracy。

## 第 5 题

**答案：错**

解析：`tool_accuracy` 的实现里顺序分有显式的守卫：

```python
if t.success:
    expected_len = len(t.expected_tools)
    order = _lcs_length(...) / expected_len if expected_len else 1.0
    orders.append(order)
```

顺序分**只在成功轨迹上统计**。原因在教程 3.4 节：失败轨迹的工具序列本身就不完整（比如循环耗尽、解析崩溃），拿一个残缺序列去算"顺序保持度"没有语义——它不是"顺序错了"，而是"根本没走到那一步"。混进失败轨迹会把顺序分稀释成一个无法解释的数字。precision/recall/f1 则对所有轨迹统计，因为"该调的没调"对失败轨迹恰恰是核心病灶。

## 第 6 题

**答案：对**

解析：确定性来自三层替换（教程 4.4 节）：真实 LLM 换成按脚本回复的 MockLLM（零随机性）、真实搜索换成返回固定文本的 FakeSearchTool（不联网），整条轨迹的每一步输出都被数据集里的 `mock_responses` 脚本钉死。因此给定数据集，三个指标的数值是数学上确定的——本项目端到端测试直接断言 `completion_rate == 0.625`、`step_efficiency ≈ 19/24`。这意味着：**任何改动（换提示词、改解析器、改工具路由）导致指标变化，测试立刻变红**。评估即回归测试，这是 M3 Harness 框架"评估进 CI"的落地方式。注意 `latency` 是唯一例外——真实时钟不可控，所以它只记录、不参与断言。

## 第 7 题

**参考答案**：

completion_rate 是二元指标：任务要么完成要么失败。轨迹 B（多调一次多余搜索、答案正确）和轨迹 C（漏调计算器、心算恰好蒙对）在它的刻度下都是 `success=True`，与完美轨迹 A 得分完全相同。但两者暴露的问题截然不同：

- **轨迹 B 是效率问题**：多调的一次 web_search 是一次多余的 LLM 决策加一次多余的工具执行，直接抬高成本和延迟。它被两个指标捕捉：`tool_accuracy.precision`（1/2，多调扣分）和 `step_efficiency`（实际步数超过最小必要步数）。在真实系统中，这类 Agent "能做成事但浪费钱"，规模化部署时成本会失控。
- **轨迹 C 是可靠性隐患**：这次蒙对纯属运气——LLM 心算多位数乘法的错误率远高于计算器工具。completion_rate 看到的是"这次对了"，看不到"下次大概率错"。它被 `tool_accuracy.recall` 捕捉（期望的 calculator 没被调用，recall < 1）。

结论：completion_rate 只能回答"做完了没有"，回答不了"做得利索吗"（B）和"下次还能做对吗"（C）。教程 3.5 节的方法论——**先枚举失败形态，再为每类形态配一个敏感指标**——就是针对这种"单一指标掩盖异质问题"的情况。

## 第 8 题

**参考答案**：

**（1）指向输出解析器（parser）组件。** parse_failure 的判定条件是 `trace.error is not None`，即 `parse_react_output` 抛了 `ReActParseError`——LLM 的原始输出无法被解析成结构化的 ReActStep，循环根本没跑起来。责任组件是"LLM 输出 ↔ 解析器"这个接口层。

**（2）为什么 error 最先归类**：异常是**最强的失败信号**——它说明系统在执行层就崩了，后面的行为分析（工具用得对不对、答案对不对）都失去了分析对象。如果顺序反过来，先看 success 再看工具序列，一条解析失败的轨迹（tool_calls 为空）会被错误地归到"规划错误"或"漏调工具"，得出"Agent 不会选工具"的错误结论——而实际上它连一步都没走成。**归因顺序就是信号强度顺序：系统崩溃 > 行为异常 > 结果偏差。**

**（3）两个优先改进动作**：

- **提示词侧**：检查系统提示词里 ReAct 格式的约束是否足够明确（参考 day010 的提示词迭代法：把历史失败案例固化成 few-shot 示例或更显眼的格式要求）。
- **解析器侧**：给 `parse_react_output` 增加容错（参考 day010 防御式解析的四道防线思路），比如容忍字段大小写差异、容忍 Thought 前的引导废话，并在容错失败时把原始输出完整记入日志供复查。

改完后重跑评估，解析失败组应该清空——形成"评估 → 归因 → 改进 → 再评估"的闭环。

## 第 9 题

**参考答案**：

**好处一：指标函数是自包含的纯函数，可独立单元测试。** `completion_rate(traces)`、`tool_accuracy(traces)` 的输入只有一个轨迹列表，不需要再传数据集。这意味着测试指标函数时可以**手工构造轨迹**（`AgentRunTrace(success=True, steps=4, tool_calls=[...], expected_tools=[...])`），完全不用启动 Agent、不用准备 mock 脚本——`tests/test_agent_eval.py` 里一半的测试就是这么写的。如果 expected_tools 放在数据集里，指标测试就必须连数据集一起构造，测试成本和耦合度都翻倍。

**好处二：轨迹脱离数据集后仍然有意义。** 轨迹可能被持久化到日志、被发给上游监控系统、被其他指标函数复用。携带 expected_tools 的轨迹无论流到哪里都自带"该做什么"的参照系，下游消费者不需要回查原始数据集。这和 day010 里 `Plan` 携带 `goal` 是同款设计——**让数据自描述，调用链下游就少一分猜测**。代价只是轨迹对象多一个字段，存储成本可以忽略。

## 第 10 题

**参考实现**：

**第一步**：扩展 `AgentRunTrace`（`evaluation/agent_eval.py`）：

```python
@dataclass
class AgentRunTrace:
    success: bool
    steps: int
    tool_calls: list[str] = field(default_factory=list)
    expected_tools: list[str] = field(default_factory=list)
    tool_inputs: list[str] = field(default_factory=list)      # 新增：实际工具参数序列
    expected_inputs: list[str] = field(default_factory=list)  # 新增：期望工具参数序列
    latency: float = 0.0
    task_id: str = ""
    answer: str = ""
    error: str | None = None
```

**第二步**：`_run_case` 中同步采集参数：

```python
tool_calls = [s.action for s in agent.history if s.action is not None]
tool_inputs = [s.action_input or "" for s in agent.history if s.action is not None]
trace = AgentRunTrace(
    ...
    tool_calls=tool_calls,
    tool_inputs=tool_inputs,
    expected_tools=expected_tools,
    expected_inputs=list(case.get("expected_inputs", [])),
    ...
)
```

**第三步**：新增指标函数：

```python
def input_accuracy(traces: list[AgentRunTrace]) -> float:
    """工具参数正确率：实际参数序列与期望参数序列逐位匹配的平均分."""
    scores: list[float] = []
    for t in traces:
        if not t.expected_inputs:
            scores.append(1.0 if not t.tool_inputs else 0.0)
            continue
        hits = sum(
            1
            for expected, actual in zip(t.expected_inputs, t.tool_inputs)
            if expected.strip() == actual.strip()
        )
        scores.append(hits / len(t.expected_inputs))
    return mean(scores)
```

**第四步**：接入 `evaluate` 的 metrics 与 `report.py` 指标总览表各加一行（`| 参数正确率 input_accuracy | ... |`）。

**参考测试**：

```python
class TestInputAccuracy:
    def test_hand_computed(self):
        traces = [
            AgentRunTrace(success=True, steps=2, expected_inputs=["2 + 3 * 4"],
                          tool_inputs=["2 + 3 * 4"]),                    # 1.0
            AgentRunTrace(success=True, steps=3, expected_inputs=["a", "b"],
                          tool_inputs=["a", "x"]),                        # 0.5
        ]
        assert input_accuracy(traces) == 0.75

    def test_end_to_end_task01(self, evaluation):
        # 数据集 task-01 增加 "expected_inputs": ["2 + 3 * 4"] 后
        assert evaluation["metrics"]["input_accuracy"] == 1.0
```

**提示问题的答案**：逐位比对与 LCS 顺序分会在"工具顺序错了但每个工具的参数都对应正确"的轨迹上分歧——例如期望 `(web_search, "A"), (calculator, "1+1")`，实际顺序颠倒：order 分得 0.5，而逐位 input_accuracy 得 0（参数按期望序列的位置比对，位置错则参数错位）。两者度量的是不同维度：**一个管"工具的顺序"，一个管"第 i 个期望工具的参数对不对"**。若想对乱序轨迹也宽容地评参数，可以改成"按工具名配对后再比参数"——那是更精细但也更复杂的设计，留给你权衡。
