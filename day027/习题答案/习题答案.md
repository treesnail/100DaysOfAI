# day027 习题答案：输出质量评估

## 第 1 题（选择）

**答案：B**

解析：格式合规是典型的**可形式化**性质——"是不是合法 JSON"有唯一客观答案，`json.loads` 一次调用就能判定，零成本、零方差。A（答非所问）、C（措辞过度自信）、D（优劣判断颠倒）都是**语义层面**的问题，规则没有判断语义的能力，必须交给模型通道。这对应教程第二章的决策表：规则吃"确定性高、形式化"的部分，模型吃"语义化、开放式"的部分。

## 第 2 题（选择）

**答案：C**

解析：`_model_score()` 解析失败返回 `None`，`evaluate()` 检测到后走降级分支：打 warning 日志，然后用规则结果合成 OutputScore 照常返回。设计原则是教程第三章强调的——**可观测性设施的可用性必须高于被观测对象**：评估器可以"看不清"（只剩规则结果），但不能"不在"（抛异常中断、或干脆不产出）。A 违反失败隔离原则；B 会让趋势统计出现数据空洞，且调用方还要处理 None；D 用陈旧数据冒充当前评估，制造了假信号，比没有信号更危险。

## 第 3 题（选择）

**答案：B**

解析：离线评估跑的是准备好的数据集，每条用例可以带 `expected` 参考答案，打分器可以直接对比 output 与 expected。在线评估面对的是真实用户任务，**没有标准答案**，能用的证据只有三样：任务文本、循环过程收集的 Observation、最终输出。今天的数字一致性检查正是"用过程证据替代标准答案"的手法。A 错：两个场景都可以混合使用规则与模型；C 错：在线评估反而多一次 LLM 调用，更贵；D 错：Harness 的 `fn` 参数是任意可调用对象，`agent.run` 完全可以接入。

## 第 4 题（判断）

**答案：错**

解析：`_check_numeric` 的第一行就是 `if not observations: return 1.0, []`——没有过程证据时**按满分放行**。这是规则检查的"不误伤"原则：宁可漏报，不可错杀。Agent 一步直接作答的场景下，输出里的数字可能来自模型自身的知识，并非编造；此时若一律判"疑似编造"，规则会大量误报，而天天误报的规则下场就是被团队关掉。注意这也意味着一个真实盲区：无工具调用的幻觉数字确实查不出来，只能靠模型通道兜底。

## 第 5 题（判断）

**答案：错**

解析：宽捕获 `except Exception` 在**主流程**里确实是坏味道（会掩盖 bug），但评估器是**旁路设施**：它的任何故障——网络超时、解析失败、磁盘写满——都不配打断用户正在等待的答案。这里的宽捕获是刻意的失败隔离设计，且做了两件事保持可观测：打 warning 日志、直接 return 不影响返回值。测试 `test_evaluator_exception_does_not_break_run` 用一个必然抛异常的 BrokenEvaluator 固化了这条保证。判断这类问题的标准是：**这段代码的失败，值不值得让用户付出代价？** 对旁路监控设施，答案永远是否。

## 第 6 题（问答）

**参考答案：**

(1) "旁路"指评估发生在答案产出之后、返回之前的**旁支路径**上：评估结果只被记录，答案本身照常返回给用户；评估器自身的失败也被捕获隔离，不影响主流程。"闸门"则相反——评估结果会决定答案能否放行。

(2) 改成"闸门"的三个具体问题：

1. **延迟与成本翻倍**：每次重试至少多一轮 ReAct 循环（若干次 LLM 调用），用户等待时间和 token 开销成倍增长，而低分答案未必值得这个代价；
2. **重试没有质量担保**：评分低的原因可能是任务本身难、或评审模型误判，重跑一遍同样的循环没有任何机制保证"这次更好"，可能陷入重试循环或越改越差；
3. **评估器成为单点故障与误伤源**：评审模型的方差（同一答案今天 0.7 明天 0.55）会直接转化为用户可见的"有时候有答案有时候没有"；评估器宕机更是等于整个 Agent 宕机——旁路设施反过来绑架了主流程。

正确的演进方向（后续阶段课题）是把低分与 issues 作为**反馈信号**输入受控的自我修正机制（限定重试次数、对比新旧分数择优返回），而不是简单的"不过线就重来"。

## 第 7 题（问答）

**参考答案：**

三个维度的对比：

| 维度 | 规则通道 | 模型通道 |
|------|---------|---------|
| 成本 | 几乎为零（正则/解析器，CPU 微秒级） | 每次评估一次 LLM 调用，真金白银 |
| 一致性 | 完全确定：同输入必同输出 | 有采样方差，需 temperature=0 压制，仍有漂移 |
| 覆盖面 | 只能查可形式化的性质（语法、长度、数字比对） | 语义层面几乎无边界，但可能被"看起来合理"的错答案骗过 |

"互补"的严格含义是：**没有任何一个维度上两者同强，也没有任何一个维度上两者同弱**。冗余意味着"去掉一个系统照常工作"，而这里去掉任何一个都有真实损失：去掉规则，格式检查这种一行 `json.loads` 的事也要花一次 LLM 调用（成本），且评分噪声进入趋势监控（一致性）；去掉模型，"答非所问"这类语义问题规则永远查不出（覆盖面）。

三个指标的分工正体现了这种互补：格式合规是纯形式问题，**纯规则**（模型在这里只有成本劣势没有覆盖优势）；有用性是纯语义问题，**纯模型**（规则根本写不出判定函数）；准确性横跨两边——数字可形式化用规则粗检，语义论断用模型复核，所以**各 50% 加权**。

## 第 8 题（问答）

**参考答案：**

选择 jsonl 的理由：

1. **追加写 O(1)**：每条记录只需打开文件、写一行、关闭，不需要读取解析重写旧内容。运行期日志写在每次 Agent 输出的热路径上，写延迟必须可忽略；单个 JSON 数组每写一条都要全量读写，日志越长越慢。
2. **单行损坏不传染**：指进程在写到一半时崩溃（断电、被 kill），只损失最后那半行，其余记录完好可用；而一个巨大的 JSON 数组少了个逗号或结尾括号，整个文件就解析失败、全部历史记录报废。聚合代码里逐行 `json.loads`、空行跳过，正是利用了这个性质。
3. **天然被流式工具消费**：`tail -f` 实时看、`jq` 逐行过滤、pandas `read_json(lines=True)` 直接读、日后接 ELK/Loki 等日志平台零改造——jsonl 是日志领域的事实标准。
4. **无并发写放大**：多进程追加写一行基本是原子的（小于 PIPE_BUF 时），而 JSON 数组的"读-改-写"在并发下必然丢数据。

## 第 9 题（编程）

**参考实现**（在 `output_eval.py` 中新增）：

```python
_TASK_KEYWORD_PATTERN = re.compile(r"[\u4e00-\u9fff]{2,}")

class OutputEvaluator:
    # ... 原有代码 ...

    @staticmethod
    def _check_task_coverage(output: str, task: str) -> tuple[float, list[str]]:
        """任务关键词覆盖检查：任务中的中文词组应至少有一个出现在答案中.

        无任务文本或任务中无可抽取词组时无法判定，按满分处理（不误伤）。
        返回 (规则侧 helpfulness 扣分基数, issues)。
        """
        keywords = _TASK_KEYWORD_PATTERN.findall(task)
        if not keywords:
            return 1.0, []
        if any(k in output for k in keywords):
            return 1.0, []
        return 0.0, ["答案未覆盖任务关键词，疑似答非所问"]

    def evaluate(self, output, task="", observations=None):
        observations = observations or []
        issues: list[str] = []
        format_score, format_issues = self._check_format(output)
        numeric_score, numeric_issues = self._check_numeric(output, observations)
        coverage_score, coverage_issues = self._check_task_coverage(output, task)
        issues.extend(format_issues)
        issues.extend(numeric_issues)
        issues.extend(coverage_issues)

        model_scores = self._model_score(output, task)
        if model_scores is not None:
            # 模型通道正常时：模型 70% + 关键词覆盖规则 30%
            helpfulness = 0.7 * (model_scores["helpfulness"] / 5) + 0.3 * coverage_score
            accuracy = 0.5 * numeric_score + 0.5 * (model_scores["accuracy"] / 5)
            issues.extend(model_scores.get("issues", []))
        else:
            helpfulness = 1.0 if len(output.strip()) >= self.min_length else 0.0
            helpfulness = max(helpfulness - 0.3 * (1 - coverage_score), 0.0)
            accuracy = numeric_score

        w_h, w_a, w_f = self.weights
        overall = w_h * helpfulness + w_a * accuracy + w_f * format_score
        return OutputScore(helpfulness, accuracy, format_score, overall, issues)
```

权重说明：模型通道正常时 helpfulness 取 `0.7 * 模型分 + 0.3 * 覆盖分`——覆盖检查只能发现"完全没提任务"的极端坏例，正常答案它恒为满分、不改变模型分的主导地位，所以给次要权重 0.3；模型通道失败时退化为"长度启发式 - 0.3 扣分"，仍保持"不误伤"。

```python
class TestTaskCoverage:
    def test_missing_coverage_penalized(self):
        llm = MockLLM(responses=['{"helpfulness": 5, "accuracy": 5, "issues": []}'])
        ev = OutputEvaluator(llm=llm)
        score = ev.evaluate("今天天气不错适合出门散步", task="对比三个 RAG 框架优劣")
        assert any("答非所问" in i for i in score.issues)
        assert score.helpfulness == pytest.approx(0.7 * 1.0 + 0.3 * 0.0)

    def test_coverage_ok_no_penalty(self):
        llm = MockLLM(responses=['{"helpfulness": 5, "accuracy": 5, "issues": []}'])
        ev = OutputEvaluator(llm=llm)
        score = ev.evaluate("三个框架优劣对比如下：推荐 LangChain", task="对比三个 RAG 框架优劣")
        assert not any("答非所问" in i for i in score.issues)
        assert score.helpfulness == pytest.approx(1.0)
```

注意测试设计的细节：正则 `[\u4e00-\u9fff]{2,}` 取的是**最大连续中文片段**，任务 `"对比三个 RAG 框架优劣"` 被切成 `["对比三个", "框架优劣"]` 两块（RAG 是英文，天然切段）。用例一的答案一个片段都不含，触发扣分；用例二的答案含 `"框架优劣"`，命中覆盖。两个用例的 MockLLM 返回相同评分，唯一变量是覆盖规则，保证断言差异可归因于被测规则本身——写第二个用例时如果只拍脑袋写"三个 RAG 框架中推荐 LangChain"，它只含 `"三个"` 和 `"框架"` 两个子串、并不含完整片段，测试会意外失败，这正是亲手跑一遍参考实现的价值。

## 第 10 题（编程）

**参考实现**：

```python
"""回归对比脚本：对比两份质量日志，检测输出质量是否显著下降."""

import json
from pathlib import Path

from smart_research_agent.evaluation.output_eval import OutputScore
from smart_research_agent.evaluation.quality_logger import OutputQualityLogger

REGRESSION_THRESHOLD = 0.1


def generate_log(path: Path, overall: float, count: int = 20) -> None:
    """模拟生成 count 条评估记录（演示用，真实环境由 Agent 运行产生）."""
    logger = OutputQualityLogger(log_path=path)
    score = OutputScore(
        helpfulness=overall, accuracy=overall,
        format_compliance=overall, overall=overall, issues=[],
    )
    for i in range(count):
        logger.log(f"任务{i}", f"输出{i}", score)


def compare(before_path: Path, after_path: Path) -> str:
    before = OutputQualityLogger(log_path=before_path).aggregate()
    after = OutputQualityLogger(log_path=after_path).aggregate()
    diff = after["avg_overall"] - before["avg_overall"]
    if diff < -REGRESSION_THRESHOLD:
        return (
            f"回归告警：输出质量显著下降 "
            f"({before['avg_overall']:.2f} -> {after['avg_overall']:.2f})"
        )
    return f"无显著回归 ({before['avg_overall']:.2f} -> {after['avg_overall']:.2f})"


# ---- pytest 测试 ----
def test_compare_detects_regression(tmp_path):
    before, after = tmp_path / "before.jsonl", tmp_path / "after.jsonl"
    generate_log(before, overall=0.85)
    generate_log(after, overall=0.60)  # 下降 0.25 > 0.1
    assert "回归告警" in compare(before, after)


def test_compare_no_regression(tmp_path):
    before, after = tmp_path / "before.jsonl", tmp_path / "after.jsonl"
    generate_log(before, overall=0.80)
    generate_log(after, overall=0.75)  # 下降 0.05 < 0.1，视为波动
    assert "无显著回归" in compare(before, after)
```

要点解析：

1. **阈值 0.1 与死区思想同源**：模型通道评分有方差，0.05 以内的均分波动是噪声；阈值取 0.1 保证只有"真实劣化"才触发告警，和 `aggregate()` 趋势判定的死区逻辑一致。
2. **对比用 avg_overall 而非 trend 字段**：trend 是同一份日志内部的"近期 vs 早期"，回归对比是**两份日志之间**的水位比较，二者回答的问题不同，不要混用。
3. **测试的两个分支缺一不可**：只测"检出回归"会漏掉误报（阈值形同虚设，任何下降都告警）；只测"无回归"会漏掉漏报。这正是教程强调的 happy path 与 sad path 同时覆盖。
4. 真实使用中（day032 的 CI/CD 流水线），`compare()` 会在发版前自动跑：before 是主干分支跑基准数据集产出的日志，after 是 PR 分支的产出，回归告警可直接阻断合并。
