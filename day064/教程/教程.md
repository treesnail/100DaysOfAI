## 今日目标

day062 交出来的 `knowledge_records()` 是四个键的字典。
今天要把它落到一个**能按相似度查**的地方。这一层看起来最简单——

3. **过滤为什么必须发生在排序之前**：这一条决定了 `_find_ids` 是不是抽象的一部分。

## 第一章：向量库不是一个库，是两个库

### 1.1 拆开看

先把这个包最重要的一句话写在最前面：

```text
一个向量库其实是两个库拼起来的
├─ 向量索引    只认 (int64 id, float32 向量)   →  负责"谁离得最近"
└─ 记录表      id → (原文, 元数据)             →  负责"命中的那条是什么"
```

为什么这句值得单独一天：**三个后端在这件事上的分工完全不同**。

| 后端 | 向量索引 | 记录表 | 谁提供 |
|------|---------|--------|--------|
| `flat` | Python 列表 + 循环 | 同一张 `dict` | 本包 |
| `faiss` | `IndexFlat*` + `IndexIDMap2` | **旁挂的一份 JSON** | 本包（FAISS 不管） |
| `chroma` | HNSW（集合内部） | 集合里的 `documents` / `metadatas` | Chroma |

FAISS 那一行是重点：**FAISS 的 `IndexFlatIP` 连 id 都不存**。
官方文档写得很直白——flat 索引"不支持 `add_with_id`"，
要存 id 必须先用 `IndexIDMap` / `IndexIDMap2` 把它包一层。
而真实项目里配 FAISS 的标准做法就是"FAISS 管向量 + SQLite 管文本"，
社区里那些 `faiss_store.py` 几乎都是这个结构。

本包把这张旁挂表写成了 `<快照>.records.json`。实测（演示脚本第 7 节）：

```text
persist → outputs/vectorstore_demo.snapshot.json
文件字节数：3773
快照头部：version=1 backend='flat' metric='cosine' dimension=8 count=6
新实例（构造时给 path，自动 load）：flat | cosine | 8d | 6 条 | 持久化 是
ids() 逐条相同：True
```

`faiss_backend.py` 落的也是同一份东西，只是多一个二进制索引文件——
**"两个库"在磁盘上就是两个文件**。

### 1.2 谁是主

拆成两个库之后，必须马上回答一个"看起来不重要"的问题：

> 删除的时候，先删索引还是先删记录表？

本包把这条定死：

```text
记录表是主，向量索引是从。
删除以记录表为准（先删表，再让索引跟随）；
查询以记录表为准（命中 id 之后回来取原文与元数据）。
```

反过来设计（以索引为主）会出现一个很难查的故障：索引里还有那条向量，
但记录表里已经没有它的原文了，于是检索命中一个"没有内容的 id"。
两种表现都不指向"删除没做干净"：要么应用层抛 `KeyError`，
要么返回一条**文本为空的命中**。

因此 `base.py` 的 `query` 里有一处看起来很可疑、但刻意保留的代码：

```python
record = self.get(record_id)
if record is None:
    # 记录表与向量索引不同步。这里**跳过并继续**而不是抛错：
    # 查询是读路径，读路径不该因为一条脏数据整体失败；
    # 而这件事必须可见——evaluate.index_health 会把它查出来。
    continue
```

两句话都要读到：**读路径不抛错**（否则一条脏数据会让整个检索功能不可用），
**但脏状态必须能被查出来**（`index_health` 会报出"哪些 id 取不回来"）。
只做前一半是"掩盖问题"，只做后一半是"一有脏数据就全站不可用"。

## 第二章：三套符号约定，两套口径

### 2.1 那张必须背下来的表

同一个"谁更近"，在三个库里有三种表达：

| | FAISS（`IndexFlatIP` / `IndexFlatL2`） | Chroma（`space`） | 本包 |
|---|---|---|---|
| `cosine` | 需自己先归一化再取内积，**越大越近** | `d = 1 − cos`，**越小越近** | `score = cos`，越大越近 |
| `ip` | 内积，**越大越近** | `d = 1 − Σ(a·b)`，**越小越近** | `score = Σ(a·b)`，越大越近 |
| `l2` | 平方 L2，**越小越近** | `d = Σ(ai − bi)²`，**越小越近** | `score = −Σ(ai − bi)²`，越大越近 |

三行合起来是一个很容易致命的结论：

> **FAISS 的"分数"越大越好，Chroma 的"距离"越小越好，
> 而两者都不叫 `similarity`。**

把 Chroma 的 `distances[0][0] = 0.12` 直接当相似度丢进阈值判断
（`if score > 0.8`）会让**最相似的那条被过滤掉**，而且不报错。

还有一个反直觉的事实藏在 `ip` 那一行：`distance = 1 − 内积`，
所以**内积大于 1 时"距离"是负数**。实测（演示第 3 节）：

```text
metric=ip：#0 a1f34c8b62e0d975 score=+10.000000 distance=-9.000000
```

**"距离一定是正数"这个直觉是错的。** 任何"把距离当长度用"的代码
（画图、算半径、做 range search）在 `ip` 度量下都会坏。

### 2.2 本包只保留两套口径，并且用名字钉死

```text
score     统一口径：**越大越近**（排序、阈值、报告只用它）
distance  原始口径：**越小越近**（与 Chroma 的 distances 同名同义）
```

`SearchHit` 两个都带。这不是冗余：报告需要前者，**与外部库对账需要后者**。
换算只写在一个地方：

```python
def similarity_from_distance(metric: str, value: float) -> float:
    if resolved == METRIC_L2:
        return -float(value)      # 平方 L2 越小越近，取负即"越大越近"
    return 1.0 - float(value)     # Chroma 就是这么定义它的距离的
```

**为什么必须集中在一处**：Chroma 的 `query` 返回 `distances`，
FAISS 的 `search` 返回 `D`，两者的符号约定相反。如果换算写在两个适配器里
各写一遍，第二次写的时候抄错一个符号，结果就是"换后端之后检索质量突然变差"
——而这种差异**没有任何异常**。

### 2.3 默认为什么是 `cosine` 而不是 `ip`

```text
cosine  值域 [-1, 1]   有绝对上界 → min_score=0.8 是一句跨数据集都能说的话
ip      值域无界       随向量模长浮动 → 同一个阈值换一批文档就换了含义
```

这与 day062 拒绝照抄 `0.7` 这个语义分块阈值是同一条纪律：
**阈值能不能跨数据集说，取决于分母是不是稳定的。**

保留 `ip` 这个选项仍有意义——它正是 FAISS 上"能跑得更快"的那个入口
（不归一化就少一遍乘法），也是**验证"你的提供方到底归没归一化"的探针**：
如果 `cosine` 与 `ip` 给出完全相同的名次，说明向量本来就已经是单位长度了。

## 第三章：记录的形状，与一条比库更严的元数据约束

### 3.1 三件东西缺一不可

| 成分 | 为什么必须有 | 少了它会怎样 |
|------|-------------|-------------|
| id | 更新/删除都按它定位 | 只能整库重建；"这份文档变了"无法表达 |
| vector | 它是被检索的东西 | 只能做关键词检索（那就不是向量库了） |
| text | 命中之后要还给人看 | 检索到了却展示不出内容 |
| metadata | 过滤与溯源 | 无法按 `strategy` 过滤、无法回指 `parent_doc_id` |

### 3.2 元数据：把最严的那个后端的限制当成公共契约

Python 的字典什么都能装。但 **Chroma 的 metadata 只能装
字符串、整数、浮点数、布尔值，以及同类型标量的数组**
（不允许嵌套、不允许空数组）。本包的选择是：

```text
VectorRecord.metadata 只允许：str / int / float / bool / list[同类型标量]
```

代价是"在纯内存后端上本来能存下的东西被拒了"，收益是
**同一个 `VectorRecord` 在三个后端上行为一致**。不这么做的典型故障是：
本地用 `flat` 跑得好好的，换 Chroma 之后在某一次 `upsert` 上抛类型错误——
那时数据已经生产出来了，问题却指向一个跟业务无关的类型细节。

报错必须发生在**构造记录的那一刻**：

```text
RecordError: metadata['a'] 的类型不合法：dict（不允许嵌套：向量库的 metadata 是**扁平**的一层）
```

两个实现细节值得单独记：

```python
METADATA_SCALAR_TYPES = (bool, int, float, str)
#  ↑ bool 必须排在 int 之前判断：isinstance(True, int) 在 Python 里是 True，
#    顺序写反会让布尔值被当成整数报错。
```

以及**元数据里的 `True == 1`**：这是 Python 的语义，不是本模块的选择。
`{"flag": {"$eq": 1}}` 会命中 `flag=True` 的记录。
因此**不要用同一个键混存布尔值与整数**——这一条没有代码层面的解法，只能靠约定。

### 3.3 契约要挂在类型上，不要挂在工厂上

这一处是本日真正"被测试逼出来"的改动，值得完整讲一遍。

最初的设计里，向量校验（非空、有限数、非零向量）只写在工厂函数
`make_record()` 里。冒烟自检时发现：

```python
types.VectorRecord(record_id="x", vector=(float("nan"), 1.0))   # 通过了！
```

**只要 `VectorRecord` 能被直接构造，就一定会有人直接构造它**
（测试、脚本、调试、以及未来的另一个模块）。校验挂在工厂上，
绕过它的人不会收到任何提示——而 `nan` 参与的任何比较都返回 `False`，
于是这条记录会在排序里落到**任意位置**，且永不报错。

所以校验被搬进了 `__post_init__`，顺带做了第二件事：

```python
object.__setattr__(self, "vector", validate_vector(self.vector))
```

把 `list` 冻结成 `tuple`。frozen dataclass 的字段如果是 `list`，
外部一句 `record.vector[0] = 0.0` 就能改掉"不可变"的记录，
而那个改动绕过所有校验。

> 一般化的教训：**不变量要挂在"任何人都会经过的那条路"上。**
> 工厂函数不是必经之路，类型构造是。

## 第四章：`where` —— 把元数据筛选写成一份可移植的声明

### 4.1 为什么用 Chroma 的语法

向量库的检索从来不是"只要最像的 K 条"，而是
"**在满足条件的那些里**最像的 K 条"。条件的表达方式每个库都不一样：
Chroma 有 `where`，**FAISS 什么都没有**（只有 `IDSelector`，按 id 筛）。

本包采用 Chroma 的语法作为规范语法。理由不是它更好，而是它
**已经是一份写下来的、被真实实现的规格**（运算符集合、嵌套规则、
类型限制都有明文）。自己发明一套 DSL，只会多出一个
"我们的语法与库的语法不一致"的翻译层。

### 4.2 12 个运算符

| 运算符 | 含义 | 值的要求 |
|--------|------|---------|
| `$eq` | 等于 | 标量（**直接写值等价于 `$eq`**） |
| `$ne` | 不等于 | 标量 |
| `$gt` / `$gte` | 大于 / 大于等于 | 标量 |
| `$lt` / `$lte` | 小于 / 小于等于 | 标量 |
| `$in` / `$nin` | 在 / 不在集合内 | **非空**列表 |
| `$contains` / `$not_contains` | 数组元数据是否包含某元素 | 标量（字段必须是数组） |
| `$and` / `$or` | 逻辑组合 | **非空**的子句列表 |

实测（演示第 5 节，库里六条记录的 `strategy` 是 recursive×2 / fixed×1 / structural×2 / semantic×1）：

```text
[$in]      {"strategy": {"$in": ["recursive", "fixed"]}}      候选 3 | 命中 3
[$and]     {"$and": [{"strategy": "structural"}, {"oversized": true}]}  候选 1 | 命中 1
[$contains]{"tags": {"$contains": "cost"}}                    候选 2 | 命中 2
[筛空]     {"strategy": {"$in": ["hybrid"]}}                   候选 0 | 命中 0  filter_applied=True
```

### 4.3 两个刻意留下的"不报错"

**一、类型不可比的比较判为不命中，而不是抛错。**
一份库里 `page` 既可能是 `int` 又可能是 `"12"`（不同批次入库的结果），
此时 `{"page": {"$gt": 10}}` 遇到字符串会触发 `TypeError`。
抛错会让**一次查询因为一条脏记录而整体失败**；判为不命中则把它降级成
"这一条没被选中"。取舍写在明面上：**查询的可用性优先于对单条脏数据的严格性**，
而脏数据的清理是入库侧的事（`assert_metadata` 已经在拦类型越界）。

**二、`$nin` 对"键不存在"也算命中。** 与它的定义一致（"不在集合内"
对一个不存在的值也成立）。想要"存在且不在内"就写成 `$and` 组合。

### 4.4 空子句的两种含义，与一次"绝不会误删"的收紧

```text
where=None   调用方没提过滤       → 不过滤
where={}     调用方提了但条件是空的 → 也不过滤（在检索路径上）
```

在**删除**路径上，`{}` 这个含义是灾难：`delete(where={})` 会清空整库。
因此 API 层的 `/vectorstore/records` 把 `where={}` 收紧成 400，
理由与实现都写在端点 docstring 里：**同一个语义在查询路径上无害，
在删除路径上不可接受——那就只收紧危险的那一侧。**

## 第五章：六个抽象原语，与"四个数"的写入报告

### 5.1 后端只需要实现六件事

```text
count()                                  有多少条
ids()                                    都是谁（**升序**）
get(record_id)                           取一条完整记录
_upsert(records) -> WriteReport          写入（已校验、已归一化）
_remove(ids) -> int                      删除
_ranked_ids(vector, limit, restrict)     向量排序（唯一需要"近似"的地方）
_find_ids(where) -> set[str] | None      元数据预筛（能用原生过滤就覆写）
```

其余行为——校验、归一化、过滤、阈值、稳定排序、写入报告、维度一致性——
全部在 `base.py` 里。**这样三个后端才会给出逐条可比的结果**，
而不是"看起来差不多"。

两个原语的返回值刻意设计成"不返回记录"：

- `_remove` 返回**真正删掉的条数**而不是请求删掉的条数。
  删一个不存在的 id 是幂等操作，不该报错；但报告里必须能看出
  "这次其实什么都没删"。
- `_ranked_ids` 返回 **id 而不是记录**。向量索引手里只有 id；
  让它在返回记录，每个后端都要自己维护一份记录表的引用，
  而 Chroma 根本不需要（它自己就是表）——那就变成了重复实现。

### 5.2 `ids()` 为什么必须升序

返回插入序的后果很具体：**插入顺序会随批量重放而变化**，
而"两次运行的 id 列表相同"是索引可复现性最基本的检查。

同一条纪律出现在排序里。`types.sort_hits` 的排序键是
**分数降序、id 升序**，第二个键不是装饰：

```text
同一段文本用确定性编码器会得到逐位相同的向量 → 分数**精确相等**
只看分数 → 顺序取决于 dict 的插入顺序
插入顺序在分批重放之后会变 → 同一次查询两次运行给出不同的 top-1
```

实测（演示第 4 节）：

```text
写入顺序：a1f34c8b62e0d975、b7e2d40a9c13f586、e08b7d25c4a91f36、
          5c9d0e13ab7f2468、2d6b9a50f31c7e84、3f5a91c0d27be684
分数精确等于 1.0 的有 2 条：
  #0 3f5a91c0d27be684 score=1.0
  #1 a1f34c8b62e0d975 score=1.0
```

插入顺序里 `a1f3…` 在前，名次却是 `3f5a…`（id 较小）在前。
**不确定性不是来自算法，而是来自没写下来的排序规则。**

### 5.3 `WriteReport` 的四个数，与 `unchanged` 为什么单独一态

```text
added      新插入的记录
updated    同一 id 被覆盖（内容确实变了）
unchanged  同一 id、内容逐位相同 → **没有改动任何东西**
skipped    被调用方或护栏拒绝的记录
```

`unchanged` 是"这次写入其实什么都没做"的**唯一证据**，
也是 day065 增量索引的地基：如果把它并进 `updated`，
"重建索引的代价"这个数就永远算不准（每个块都被报告成更新过，
而实际上一个字节都没变）。

实测（演示第 2 节）：

```text
第一次 ingest：输入 6 → 写入 6（未变 0）| 跳过 0 | 失败 0 | 编码调用 6 次
重放同一批  ：输入 6 → 写入 0（未变 6）| 跳过 0 | 失败 0 | 编码调用 6 次
库状态仍然：flat | cosine | 8d | 6 条
```

最后一行是今天最值得停一下的地方：**重放时 `unchanged=6`，
但 `embedding_calls` 仍然是 6。** 库没变，钱照花。
本课是"逐条编码、没有向量缓存"——day065 会用这个 `unchanged`
去消掉那 6 次编码。**"省了多少"只有在两个数都被记下来的时候才能回答。**

还有一个容易被忽略的取值：Chroma 把向量存成 float32，读回来必带量化误差，
因此它的"未变"判定**不能用逐位比较**（那会让 `unchanged` 永远不可达，
而它是增量索引的唯一依据），必须带一个 `1e-5` 量级的容差；
`text` / `metadata` 仍然精确比较。这段取舍写在 `chroma_backend.py` 的常量旁边。

### 5.4 维度：第一次写入时定下，之后不许变

`_prepare` 的逻辑是"库已定维则必须一致，未定维则采纳第一条记录"。
换过 embedding 提供方就要重建库——**截断或补零都会让排序静默失去意义**。
报错信息里要写清这一点，因为"维度不一致"这个现象看起来像是
"某个参数没传对"，而实际上它是"库与当前编码器不是同一套"。

FAISS 有一个额外的硬约束：**维度是构造期必填的**。
`IndexFlatIP(d)` 在创建索引时就要知道 `d`，
所以"先写入一批数据再自动学出维度"这条退路在 FAISS 上不存在。
`faiss_backend` 在库为空且未给 `dimension` 时直接报错并说明出路。

## 第六章：三个后端，三组具体的坑

### 6.1 `flat`：参照实现，不是"教学凑数"

`flat` 的价值不在于"能跑"，而在于它是**参照物**：

```text
任何"更聪明的后端"都必须先证明自己与 flat 给出同一批结果。
```

它零可选依赖、结果逐位可复现，因此测试里 `brute_force_top`
（一段只用 `math` 的朴素实现）与三个后端的对账都以它为基准。
演示第 6 节的实现刻意**不复用 `metrics.py`**：

> 如果参照实现和被测实现用的是同一段代码，那么"两者一致"
> 就只能证明"这段代码等于它自己"。

### 6.2 `faiss`：四个必须知道的细节

```text
1. Flat 索引不存 id           → 必须 IndexIDMap2 包一层，且只能用 add_with_ids
                                 （官方文档：IndexIDMap::add 会失败）
2. 输入类型有硬要求            → x 必须是 float32 的 (n, d) 数组，ids 必须是 int64
3. 结果不足时用 -1 填充        → search 返回 (D, I)，I 的 -1 是"未找到"的保留值，
                                 因此**我们生成的 int64 id 必须避开 -1**（也避开 0）
4. 没有元数据过滤              → 带 where 的检索只能"全量 search 再筛"
```

第 4 条是本日最重要的一条工程结论。**IndexFlat 是暴力索引**，
所以带过滤时直接 `search(x, ntotal)` 全量排序再筛**是正确且可接受的**；
但换成 IVF / HNSW 之后就没有这个选项了，那时只能过采样
（`k × oversample`）并**承认近似**——"过滤"在向量库里最容易被忽略的代价
就是这一条。

第 3 条还有一个真实后果：**id 是哈希映射出来的**。字符串 id 到 int64 的映射
必须稳定（同输入同输出），并且要维护一张反查表；插入时若撞号，
必须**抛错而不是覆盖**——哈希冲突概率极低，但"极低"不等于"不会"，
而覆盖的症状是"某条记录凭空消失"。

### 6.3 `chroma`：三个坑，一个比一个安静

```text
1. 集合名有硬约束   3~512 字符；首尾必须是小写字母或数字；中间只允许 . - _ ；
                    不能出现连续两个点；不能是合法 IP 地址。
                    本包 validate_collection_name 不做任何"修复"
                    （不转小写、不替换字符）——静默改名会让
                    "我指定的 collection"与实际用的不是同一个。
2. 建集合必须显式传 embedding_function=None
                    否则 Chroma 会启用**默认 embedding function**：
                    Sentence Transformers 的 all-MiniLM-L6-v2，**本地运行且会下载模型**。
                    于是"只是建了个集合"这个动作触发了一次网络下载。
3. distances 一律"越小越近"
                   l2 是**平方** L2；ip/cosine 是 1 − 相似度。
                    见第二章那张表。
```

第 2 条是那种"不写下来就一定会踩"的坑：**我们自己提供向量**
（`add(embeddings=...)`），所以必须把默认 EF 关掉。测试里有一条断言
直接钉住了这件事：假集合会检查 `embedding_function is None`。

### 6.4 依赖缺失时的三段式报错

`registry` 的中心价值不是"选一个类"，而是**把"缺依赖"这件事讲清楚**。
实测原文（演示第 8 节）：

```text
后端 faiss 不可用：缺少 faiss（numpy 已满足）。
安装：pip install faiss-cpu
或者改用：flat（零可选依赖，结果逐位可复现）
```

三句话各解决一个问题：**缺什么、怎么装、还能用什么**。
只有第一句的错误等于让使用者自己去搜文档。第三句最容易被省掉，
也最有用——`flat` 的 `requires` 是空元组，因此它在任何机器上
都给得出一个真答案：**进度不该被一个可选依赖卡死。**

顺带一个设计细节：`registry` 用 `importlib.util.find_spec` 做探测，
并且**自己不在模块顶层 import 两个可选后端**。理由在下一节。

### 6.5 包的导入成本：可选后端按需加载

`faiss_backend` 在模块顶层 `import numpy`（faiss 的 Python 绑定依赖它），
`chroma_backend` 要拿 `chromadb`。如果包的 `__init__.py` 急切导入它们，
**"只想用 flat"的人也会因为缺 numpy/faiss/chromadb 而在 import 阶段崩掉**——
而 flat 是零依赖的参照实现，它的可用性不该被另外两个后端拖累。

因此 `vectorstore/__init__.py` 用模块级 `__getattr__`（PEP 562）按需加载：

```python
import smart_research_agent.vectorstore        # 零可选依赖
    ├─ flat / types / filters / metrics / base / registry / evaluate / pipeline  立即加载
    ├─ FaissVectorStore     取用时才加载
    └─ ChromaVectorStore    取用时才加载
```

实测（`tests/test_vectorstore_package.py` 里的子进程断言）：

```text
faiss_backend loaded eagerly? False
chroma_backend loaded eagerly? False
numpy loaded on package import? False
lazy resolve FaissVectorStore: FaissVectorStore
now faiss_backend loaded? True
```

未登记的符号抛 `AttributeError` 而不是 `BackendUnavailable`：
**"这个名字不在包里"与"它需要的库没装"是两件事**，
只有前者应该让 `hasattr` 返回 False。

## 第七章：选型、摄取与产物

### 7.1 选型就是一张决策表

| 场景 | 选谁 | 理由 |
|------|------|------|
| 想先跑通、要可复现、不能装东西 | `flat` | 零依赖，与参照实现逐位一致 |
| 十万级以上、只要向量、元数据自己管 | `faiss` | 精确检索 + 成熟的索引类型体系 |
| 元数据过滤是主需求、想少写代码 | `chroma` | 向量与元数据同一个集合，原生 `where` |
| 语料只有几百条 | **先别上向量库** | 一个 `dict` + 余弦循环就够；向量库的成本大于收益 |

最后一行是刻意加进来的。**"什么时候不要用"和"什么时候用"同样重要**——
`flat` 的存在让这句话有了一个具体答案：它就是那个"先别上"的版本，
只是多了一层统一的接口。

### 7.2 摄取：day064 刻意逐条编码

`pipeline.py` 把 day062 的四个键变成 `VectorRecord` 并写库，其中三件事写死在代码里：

```text
1. retrieval_text 优先      元数据里有它就编码它（面包屑 + 正文），
                            没有才退回 text。落库的 text 仍是原文片段——
                            **"存的"与"编码的"不是同一份**（day062 埋的钩子在这里兑现）。
                            embedding_input_field() 让这件事可核对。
2. 逐条编码                  embedding_calls == 被编码的条数。这是**刻意**的，
                            为了让 day065 的"批量 + 缓存"有一个可比较的基线。
3. 三种"没做成"分家          skipped（数据问题，调用方修）
                            failed   （环境/维度问题，改环境）
                            其余异常（不在"我们认识的失败"里）**一律上抛**
```

第 3 条是 day061 那条纪律的第三次复用：

```python
except VectorStoreError:      # 只有"我们认识的失败"被记进报告
    ...
                              # 其余异常**向上抛**
```

把"我们自己的 bug"记成报告里的一行失败，会让它永远不被修——
因为报告看起来"只是有一条数据没过"。演示第 2 节的输出里
`skipped=0 failed=0` 是有意义的：**报告是绿的，等价于"没有一条需要人再看一眼"。**

### 7.3 `candidates` 与 `filter_applied`：解释一次空结果

这两个字段的存在理由可以用三行输出说清（演示第 5 节）：

```text
candidates=0 且 filter_applied=True   → 过滤器把所有记录都排除了
candidates=0 且 filter_applied=False  → 库是空的
candidates=6 而 count=0               → 阈值把命中切掉了（数据在，只是不够像）
```

没有这两个字段时，三种情形在响应体里长得**一模一样**：`hits` 很短或为空。
实测的最后一组就是第三种：

```text
min_score=1.5 → cosine | top_k=3 | 候选 6 | 命中 0 | （无）
                candidates=6 count=0 filter_applied=False
```

## 第八章：怎么知道"换个后端没换结果"

答案是**对账**（parity）。`evaluate.py` 给出一张表，每行是
"某个后端 × 某个度量"与参照实现的比较：

```text
agreed             与参照实现**逐位相同**的名次数
overlap            recall@k（集合交叠比例）
first_divergence   空串表示一致；否则写清"第几名、期望谁、实际谁"
```

实测（演示第 6 节）：

```text
flat     | cosine | 6 条 | top-3 | 一致 3/3 | 交叠 100.0% | 逐位一致 | top-1=3f5a91c0d27be684
faiss    | cosine | 不可用 | 未安装 faiss…
chroma   | cosine | 不可用 | 缺少可选依赖 chromadb…
flat     | ip     | 6 条 | top-3 | 一致 3/3 | 交叠 100.0% | 逐位一致 | top-1=a1f34c8b62e0d975
```

同一份数据只换度量（`compare_metrics`，基线是 cosine）：

```text
flat | cosine | 一致 3/3 | 交叠 100.0% | 逐位一致
flat | ip     | 一致 0/3 | 交叠 100.0% | 首个分歧在第 1 名
        first_divergence="第 1 名：期望 '3f5a91c0d27be684'，实际 'a1f34c8b62e0d975'"
flat | l2     | 一致 1/3 | 交叠 66.7%  | 首个分歧在第 2 名
        first_divergence="第 2 名：期望 'a1f34c8b62e0d975'，实际 '5c9d0e13ab7f2468'"
```

读这张表有三条要点：

1. **"一致 0/3"不一定是 bug**：cosine 与 ip 的第一名不同是**预期的**
   （样本里刻意有一条模长 10 倍的记录）。对账的价值在于
   "差异被指名道姓地写出来了"，而不是"必须全绿"；
2. **分数用容差比、名次逐位比**。浮点求和顺序不同会给出
   `0.9999999999999998` 这种值，那是容差能吸收的；
   而名次不同永远是**真问题**——本包的排序规则是确定的（分数降序、id 升序）；
3. **`first_divergence` 必须指名道姓**。一句"结果不一致"对读报告的人
   没有任何帮助；对账的产出物要能直接照着去查那一条记录。

`verify_parity` 在缺依赖的机器上给出：

```text
verify_parity：ok=False checked=6 available=2
  失败：faiss/cosine 不可用：…（安装指引原文）
```

**`ok=False` 不等于"对账失败"**：不可用的后端也会被记成一条 failure。
这正是"装了 faiss 的机器与没装的机器，报告必须长得一样"的实现方式——
差异只表现为一个 `available` 布尔与一句原因，而不是少了几行报告。

还有一个降级必须说明：生产代码不能 import 测试里的参照实现，
因此 `compare_backends` 在缺省参数下用的是 `metrics.score` 现算的"降级参照"。
此时"一致"只能说明几个后端彼此一致，**不能当 CI 判据**；
真正的对账在 `tests/test_vectorstore_parity.py` 里，
那里注入的是独立实现的期望值。

## 第十章：常见误区清单

**1. 把 Chroma 的 `distances` 当相似度用。** 它越小越近，而且
`ip` 度量下**可以是负数**。`if distance > 0.8` 会把最相似的那条丢掉。

**2. 以为"距离一定是正数"。** 只有 `l2` 是。`ip` 的"距离"是 `1 − 内积`，
内积大时它< 0；`cosine` 的"距离"是 `1 − cos`，余弦为负时它 > 1。

**3. 先排序取 top-k、再按元数据过滤。** 结果是"返回条数少于 top_k，
尽管库里还有更多符合条件的记录排在后面"，而且不报错。
**过滤必须在排序之前**——这就是 `_find_ids` 是抽象的一部分的原因。

**4. 以为 FAISS 能过滤元数据。** 它只认向量和 id。
要过滤只能预筛 id 或过采样后筛；换成 IVF/HNSW 之后还要承认近似。

**5. 在 FAISS 里用 `-1` 当自己的 id。** 官方文档明确 `-1` 是
"结果不足"的填充值、建议不要用作 id。本包的映射落在 `[1, 2**63−2]`。

**6. 建 Chroma 集合时忘了 `embedding_function=None`。** 默认 EF 是
`all-MiniLM-L6-v2`，**本地运行且会下载模型**——"只是建了个集合"
触发一次网络下载，而且在离线的 CI 里会直接失败。

**7. 用集合名做参数却不校验。** 3~512 字符、首尾小写字母或数字、
中间只允许 `. - _`、不能连续两个点。**别写"自动修复"**：
静默改名会让"我指定的集合"与实际用的不是同一个。

**8. 直接构造 `VectorRecord` 时以为校验会生效。** 校验必须挂在
`__post_init__` 上（今天刚修过这个坑）；而 `nan` 混进去之后
**排序会变得任意且永不报错**。

**9. 以为元数据什么都能存。** Chroma 只接受标量（str/int/float/bool）
与同类型标量数组。复杂结构要先序列化成字符串。

**10. 用同一个键混存布尔值与整数。** `True == 1` 是 Python 的语义，
`{"flag": {"$eq": 1}}` 会命中 `flag=True`。没有代码层面的解法。

**11. 把 `WriteReport.unchanged` 并进 `updated`。** 那样
"这次重建省下了多少次编码"就永远答不出来——而 day065 正要靠它省钱。

**12. 以为"重放没改动库"就等于"没花钱"。** 实测里
`unchanged=6` 而 `embedding_calls` 仍然是 6：**库没变，钱照花**。
向量缓存是 day065 的事。

**13. 换度量却不重新标定阈值。** `min_score=0.35` 在 `cosine` 下是
"方向大致一致"，在 `l2` 下是一个完全相反的说法（l2 的分数是 ≤ 0 的负数）。
配置项 `vector_min_score` 的默认值是 `None` 而不是 `0.0`，就是为了不做这个暗示。

**14. 忘了 float32 的量化误差。** Chroma 存 float32、读回来必然带误差，
"逐位相同"永远不成立；`unchanged` 必须用容差判断。

**15. 以为"更快"就是更好的后端。** 顺序应当是
**先正确（与 flat 逐条一致）→ 再可选（过滤、持久化）→ 最后才是快**。
演示第 6 节那张对账表就是这条顺序的检查器。
