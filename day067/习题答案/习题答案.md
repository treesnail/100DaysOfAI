## 第一部分：选择题

### 第 1 题 —— D

**考点**：`lexical.tokenize` 的四条切分规则、"单字 + 相邻 2-gram"为什么两个都要、
"不引入 `jieba` / `rank_bm25`"的两条理由，以及"空白是分隔符"这条容易忽略的细节。

**解析**：

规则与理由都写在 `smart_research_agent/retrieval/lexical.py` 的模块 docstring 里
（该文件 870 行，分词只占其中最前面的 40 行）：

```text
先按 [a-z0-9_]+ | [\u4e00-\u9fff]+ 切段（全角标点、空格、连字符都是分隔符）
拉丁/数字段    原样保留（"err"、"2043"、"retry_budget" 各是一个词元；大小写先折叠）
汉字段长度 1   保留该单字（"词" → 词）
汉字段长度 ≥2  单字 + **相邻 2-gram**（"语义缓存" → 语/义/缓/存/语义/义缓/缓存）
```

两个常量就是这两条规则的实现（`lexical.py` 第 107、110 行）：

```python
TOKEN_PATTERN = re.compile(r"[a-z0-9_]+|[\u4e00-\u9fff]+")
CJK_ONLY = re.compile(r"^[\u4e00-\u9fff]+$")
```

`tokenize` 本体只有十几行，注释里写清了每一处顺序为什么不能改：

```python
def tokenize(text: str) -> list[str]:
    if not isinstance(text, str):
        raise QueryError(
            f"tokenize 需要字符串，收到 {type(text).__name__}。"
            "要索引一条记录请用 LexicalDocument（它会先校验类型）；"
            "要给它一个向量请用 vectorstore 的那一层。"
        )
    lowered = text.lower()
    tokens: list[str] = []
    for chunk in TOKEN_PATTERN.findall(lowered):
        if not CJK_ONLY.match(chunk):
            tokens.append(chunk)
            continue
        if len(chunk) == 1:
            tokens.append(chunk)
            continue
        # 单字在前、2-gram 在后：顺序本身也是确定性的一部分（同一个输入
        # 在任何机器上给出同一个列表，逐位可比）。
        tokens.extend(chunk)
        tokens.extend(chunk[index : index + 2] for index in range(len(chunk) - 1))
    return tokens
```

实测（本题的代码在 `tests/test_zz_q11_probe.py` 里逐条钉住，下面这些是真实输出）：

```text
tokenize('语义缓存')   = ['语', '义', '缓', '存', '语义', '义缓', '缓存']
tokenize('ERR-2043')  = ['err', '2043']
tokenize('retry_budget') = ['retry_budget']
tokenize('熵')         = ['熵']
tokenize('缓存缓存')    = ['缓', '存', '缓', '存', '缓存', '存缓', '缓存']   ← 重复保留（tf 要能被读出来）
tokenize('  语义  缓存  ') = ['语', '义', '语义', '缓', '存', '缓存']        ← 没有跨空白的「义缓」
```

四件容易读漏的事：

1. **为什么单字与 2-gram 都要**（模块 docstring 的原话）："单字让'重算'与'重新计算'
   共享 重/算 两个词元（在不引入同义词表的前提下蹭到一点召回），2-gram 让'语义'与
   '义语'区分开（提高精确率）"，而且"**两个都留**而不是只留 2-gram：只留 2-gram 时
   单字查询（'熵'、'税'）会一个词元都对不上，而单字查询在中文里是真实存在的"。
2. **为什么不是"按空格切 + 去标点"**（`tokenize` 的 docstring 原文）："中文没有空格，
   那种切法会把一整句话当成一个词元，于是 BM25 退化成'整句精确匹配'——一个看起来在
   工作、实际上永远只命中原句的检索器（而它的表现是'关键词路召回率很低'，不是报错）"。
3. **为什么"空白是分隔符"值得单独说**：2-gram 只在**同一个汉字段内**生成，
   `"  语义  缓存  "` 切出来的是两个汉字段（`语义` 与 `缓存`），因此不会凭空出现
   跨空白的 `义缓`。这条差异在测试里是逐条对照的
   （`tests/test_hybrid_lexical_tokenizer.py`，145 条用例，期望值由测试侧**独立重写**的
   切分逻辑算出来）。
4. **连字符不保留**：`"ERR-2043"` 切成 `err` 与 `2043`——注释里写着这是**刻意的**：
   "编号的'前缀'与'序号'分别命中时都能给分"。而 `_` 属于 `[a-z0-9_]+`，因此
   `retry_budget` 整体是一个词元（这也是第 7 节"两路都砸中"那个查询能同时被两路召回的原因）。

不用 `jieba` / `rank_bm25` 的两条理由（模块 docstring，**缺一不可**）：

```text
1. 不新增依赖   本课的全部产物必须能在"只有 Python + 标准库"的机器上复现，
                而 BM25 与分词都是**几十行的算术**，不是一个值得为之引入依赖的能力。
                （jieba 还会带一个约 5 MB 的词典文件，它会把"离线可复现"变成
                "词典版本也会影响结果"——那正是评估最怕的东西。）
2. 评估要可复现  分词器是有版本的（jieba 换版本会切出不同的词），
                于是同一天、同一份语料、同一批查询会给出不同的 BM25 分数，
                而 day071 的 RAG 评估要求"分数变了必须能归因到某个显式参数"。
                相邻 2-gram 的分词法**没有版本**：它的定义就是"字符串的相邻两字"。
```

第 2 条就是与 day071 直接相关的那一条。代价也是真实的、且写进了边界清单
（`types.RETRIEVAL_LIMITATIONS` 第三条）："关键词一路是零依赖的 BM25：CJK 用相邻 2-gram
代替分词器，因此不做词形还原、不做同义词扩展、不认识未登录词（见 lexical）"。

**其余选项为什么错**：

- `A` 错：这正是手册第 2 节开头那两条理由要挡的做法。换上分词库确实会让 `词表 274`
  这类数字变小（分词粒度更粗），但代价是"离线可复现"变成"词典版本也影响结果"，
  而且第 2 条理由与 day071 的评估纪律直接冲突。另外，本层的第一个关键取舍
  （模块 docstring 的标题就是"为什么不引入分词库（本模块最该被记住的一处取舍）"）
  不是课程偏好，是可复现性要求。
- `B` 错：把单字当噪声会直接砍掉两类真实查询——单字查询（`熵`、`税`）与跨词边界的
  召回（"重算"与"重新计算"共享 `重`/`算`）。实测 `tokenize("熵") == ["熵"]`、
  `tokenize("语义缓存")` 里 `语/义/缓/存` 四个单字都在。
- `C` 错：中文正文里"标点与英文单词"远不足以切句，`tokenize` 的 docstring 明确算了
  这条账：整句会被当成一个词元，BM25 退化成整句精确匹配。

**结论**：四条规则 + "单字与 2-gram 都留" + "不引入依赖"的一个取舍，共同决定了
`tokenize('语义缓存') == ['语','义','缓','存','语义','义缓','缓存']` 这个可逐位核对的输出；
它没有版本、没有参数、没有词典文件，因此同一份语料在任何机器上给出同一份分数。

### 第 2 题 —— B

**考点**：`log(1 + …)` 里那个 `1` 的作用、`0 分`作为哨兵、`k1` 与 `b` 各自的单调方向。

**解析**：

公式与两个参数的出处都写在 `lexical.py` 的模块 docstring 里：

```text
idf(t) = log(1 + (N - df + 0.5) / (df + 0.5))              ← 恒正（见下）
score  = Σ_t idf(t) · tf · (k1 + 1) / (tf + k1 · (1 - b + b · dl / avgdl))
```

`_idf` 的实现只有一行，注释解释了为什么必须恒正：

```python
def _idf(total_docs: int, doc_freq: int) -> float:
    """``log(1 + (N - df + 0.5) / (df + 0.5))``：**恒正**的 IDF（理由见模块 docstring）.

    取对数而不是直接比值：比值会让"df 从 1 变 2"与"df 从 101 变 102"给出
    同样的降幅，而对数下的降幅与"稀有度"的关系更接近人对"这个词有多特别"的直觉。

    它对本模块是**公开可核对**的（测试直接对它断言单调性）：BM25 的排序
    不变量（词越稀有权重越大、``df`` 增大时权重单调下降）都落在这一个函数上。
    """
    return math.log(1.0 + (total_docs - doc_freq + 0.5) / (doc_freq + 0.5))
```

模块 docstring 里那段"为什么是 `log(1 + …)`"是全课最值钱的一段注释之一：

```text
经典 BM25 用 log((N - df + 0.5) / (df + 0.5))，它在 df > N/2 时变成**负数**——
于是一个"到处都出现的词"会给文档**减分**。两种写法的排序在多数语料上几乎一样，
但负 IDF 会带来一个很难解释的现象：score 越小越不相关**和** score 为负
意味着"减去相关性"混在一起，而 0 分又被本模块用作"完全没有共同词元"的哨兵
（见 search）。恒正的 IDF 让"0 分"这件事只有一个含义。
```

手算与实测（三个数字都可逐位核对）：

```text
_idf(10, 1)  = log(1 + (10-1+0.5)/(1+0.5)) = log(1 + 6.3333…) = log(7.3333…) = 1.992430   ← 演示第 2 节与本解都实测到 1.992430
_idf(10, 9)  = log(1 + 1.5/9.5) = 0.146603 > 0                                            ← 经典写法在这里已经是负数
_idf(10, 10) = log(1 + 0.5/10.5) = 0.046520 > 0
```

两个参数的缺省值出自 Robertson & Zaragoza（2009）的经典取值，注释把"为什么是引用
而不是发明"也写清了：

```python
#: 词频饱和参数的缺省值。出处：Robertson & Zaragoza（2009）的经典取值，
#: 与 Lucene / Elasticsearch 的 ``k1`` 默认值同源。**不是本课标定出来的**——
#: 引用一个公开取值，别人才分得清"结果不同"是语料造成的还是参数造成的。
DEFAULT_K1 = 1.5

#: 长度归一化强度的缺省值。出处同上（``b`` 的经典取值 0.75）。
#: ``b=0.75`` 的意思是"长文档打个折，但不把长度当成决定性因素"。
DEFAULT_B = 0.75
```

两个参数**各管一件事**，因此必须分开扫描——演示第 6 节的受控语料是一份
"词频与长度都可控"的三篇文档（`heavy="缓存缓存缓存缓存"` 8 字 15 个词元、
`middle="缓存缓存检索"` 6 字 11 个词元、`light="缓存"` 2 字 3 个词元），实测两张表：

```text
  k1 扫描（b 固定 0.75）：heavy / light 的分数比
          k1 |      heavy |      light |       比值 | 说明
         0.0 |   0.400594 |   0.400594 |   1.0000 | 只看出现过没有
         0.5 |   0.510648 |   0.484051 |   1.0549 | 词频收益随 k1 增大
         1.5 |   0.654492 |   0.580862 |   1.1268 | 词频收益随 k1 增大
         3.0 |   0.777723 |   0.654492 |   1.1883 | 词频收益随 k1 增大
        10.0 |   0.971784 |   0.756151 |   1.2852 | 词频收益随 k1 增大

  b 扫描（k1 固定 1.5）：heavy / light 的分数比
           b |      heavy |      light |       比值 | 说明
         0.0 |   0.728353 |   0.400594 |   1.8182 | 完全不归一化
        0.25 |   0.701948 |   0.446817 |   1.5710 | 长文档打个折
        0.75 |   0.654492 |   0.580862 |   1.1268 | 长文档打个折
         1.0 |   0.633092 |   0.683367 |   0.9264 | 完全归一化
```

注意 `b=1.0` 那一行：`heavy`（0.633092）**低于** `light`（0.683367）——"长文档里的同一个词
更不值钱"这句话在 `b=1` 时体现得最彻底。`k1=0` 那一行两条**同分**，这是 `k1=0` 的明确含义，
`BM25Params.__post_init__` 的消息里写着它："k1=0 有明确含义——'完全忽略词频，只看出现过没有'"。

构造期校验也在 `BM25Params.__post_init__` 里，两条消息各写了一个后果：

```text
k1 < 0            → "k1 是词频饱和项：它必须非负（分母 tf + k1·… 里出现它）"
b ∉ [0, 1]        → "超出这个区间的取值会让分母变成负数，于是'长文档'反而得到更高的分数
                     ——一个不会报错、只会反过来的排序"
非有限数 / 非数字  → "nan 参与的比较恒为 False，于是**任何查询都不再返回结果**" /
                     "字符串形式的参数会在打分时变成 TypeError"
```

**其余选项为什么错**：

- `A` 错：`df > N/2` 时给出负权重**不是**"合理"，而是会让两种现象混在一起
  （"分数越小越不相关"与"负分等于减去相关性"），更致命的是本模块用 `0 分`
  当"完全没有共同词元"的哨兵（`search` 只返回 `score > 0` 的文档），
  而负 IDF 会让"0 分"与"负分"同时出现、含义不再唯一。
- `C` 错：`k1` 管**词频饱和**、`b` 管**长度归一化**，两者在公式里分别出现在分子与分母的
  不同位置，方向也相反（`k1` 越大长文档越占优、`b` 越大长文档越吃亏）；把两者合成一个
  "长度惩罚"会让"结果变了"再也归因不到唯一的原因。`BM25Params` 做成一个 frozen
  dataclass 的理由正是"它们是**一对**……必须一起进报告"——但"一起报告"不等于"一起调"。
- `D` 错：方向说反了。`b=1` 时实测比值 `0.9264 < 1`，`heavy` 反而更低；
  `b=0` 才是"完全不归一化、长文档占优"（比值 1.8182，四行里最大）。

**结论**：`log(1 + …)` 让 IDF 恒正，"0 分"因此只有一个含义；
`k1=1.5` / `b=0.75` 是公开引用的经典取值（不是本课标定的），
两者的方向可以各自用一份受控语料扫出来：`k1` 越大词频收益越大（`1.0000 → 1.2852`）、
`b` 越大长文档里的词越不值钱（`1.8182 → 0.9264`）。

### 第 3 题 —— D

**考点**：跨通道分数量纲不可比、`weighted` 的两个"不是可选项"的细节、`alpha` 的真实作用。

**解析**：

`fusion.py` 的模块 docstring 用第一小节专门讲这件事（标题就是"融合要解决的第一件事：
**跨通道的分数量纲不可比**"）：

```text
向量路   余弦相似度 ∈ [-1, 1]     "0.82" 是一个有绝对上界的数
关键词路 BM25 ∈ [0, ∞)            "7.31" 是一个**没有上界**的数
```

两个数字放在一起比较是**类型错误**，而它不会报错：`0.82` 与 `7.31` 都是浮点数，
`sorted` 照单全收。演示第 5 节把这件事摆成了三个可核对的数字：

```text
  向量路分数：[1.0, 0.0, 0.0]（余弦，∈ [-1, 1]）
  关键词路分数：[4.0006]（BM25，∈ [0, ∞)，没有上界）
  直接相加时 BM25 会单方面决定名次——把量纲差当成相关性差。
  归一化（min-max 到 [0, 1]）把「谁的分数大」换成「谁在这一路里更靠前」。
```

因此本模块给两种策略，差别正是"怎么处理量纲"：

```text
rrf        Reciprocal Rank Fusion：**完全不看分数**，只看名次
           贡献 = 1 / (k + rank + 1)，两路的量纲差异在定义上就不存在
weighted   先对每一路做 min-max 归一化到 [0, 1]，再加权求和
           归一化把"量纲"换成"这一路内部相对位置"，于是权重才有意义
```

`weighted_score_fusion` 的 docstring 把两个细节写成"都不是可选项"：

```text
1. 归一化必须在**每一路**内部做（而不是对合并后的分数做）
   对合并后的分数做归一化时，"这一路的最大值"里混进了另一路的量纲，
   于是 alpha 调整的是"两路混在一起之后的重心"，仍然不是权重。
2. min == max 时定义为 1.0（**不是除零**）
   这一路只有一条命中时必然 min == max；把它归一化成 0.0 会让
   "唯一的那条证据"在加权和里消失（0 × alpha = 0），
   而它明明是该路的第一名。定义成 1.0 的意思是"这一路内部，
   它就是最相关的那条"——归一化保序，把单点映射到 1 是保序的。
```

`_min_max_normalize` 的实现与"为什么不用 epsilon"：

```python
def _min_max_normalize(scores: Mapping[str, float]) -> dict[str, float]:
    """把一路的分数 min-max 归一化到 [0, 1]（``min == max`` → 全部 1.0）.

    ``min == max`` 的两种情况都要按 1.0 处理：**只有一条命中**（这一路的第一名
    就是它），以及**多条同分**（这一路自己没区分开它们）。两种情况下
    "这一路内部最相关的"都是它们全体，归一化成 0.0 会让权重白给。

    判据是 ``high - low <= 0.0``——**精确的零跨度**，而不是"小于某个 epsilon"：
    一个凭空取出的 epsilon 会变成第三个需要标定的参数，而它的表现是
    "某些几乎相同的文档突然被归一化成 0"（比放大噪声更难解释）。
    """
    if not scores:
        return {}
    values = list(scores.values())
    low = min(values)
    high = max(values)
    if high - low <= 0.0:
        return {record_id: 1.0 for record_id in scores}
    span = high - low
    return {record_id: (value - low) / span for record_id, value in scores.items()}
```

演示第 5 节的实测两段（归一化值与 alpha 扫描表）：

```text
  min-max 的分段归一化（同一批输入的实测值）：
      h-c-01  归一化后 1.0000（权重 1.0 时可直接读出归一化值）
      h-t-01  归一化后 0.0000（权重 1.0 时可直接读出归一化值）
      h-c-02  归一化后 0.0000（权重 1.0 时可直接读出归一化值）
      h-c-03  归一化后 0.0000（权重 1.0 时可直接读出归一化值）

  alpha 扫描（alpha = 向量通道的权重，关键词通道是 1 - alpha）：
       alpha | 第 1 名    |     h-c-01 |     h-t-01 | 解释
         0.0 | h-t-01   |     0.0000 |     1.0000 | 看关键词路
         0.1 | h-t-01   |     0.1000 |     0.9000 | 看关键词路
        0.25 | h-t-01   |     0.2500 |     0.7500 | 看关键词路
         0.5 | h-c-01   |     0.5000 |     0.5000 | 并列，按 id
        0.75 | h-c-01   |     0.7500 |     0.2500 | 看向量路
         0.9 | h-c-01   |     0.9000 |     0.1000 | 看向量路
         1.0 | h-c-01   |     1.0000 |     0.0000 | 看向量路
```

读法（演示脚本原文）："两条「各自的第一名」的分数恰好是 `alpha` 与 `1 - alpha`
（向量路 top-1 归一化到 1.0，关键词路 top-1 同样归一化到 1.0）。因此 `alpha` 越过 0.5 时
第一名翻转——权重**确实**在起作用，而它在 `rrf` 下根本不存在"。`alpha=0.5` 那行
"并列，按 id"就是第三排序键的直接后果（见第 4 题的解析）。

`alpha` 的缺省 `0.5` 也有一句写在 `fusion.py` 里的理由：

```text
#: ``weighted`` 策略下**向量通道**的权重缺省值（关键词通道是 ``1 - alpha``）。
#: 0.5 是"两边都不占先"的起点：它不代表两路一样有用，只代表**还没有证据**
#: 说明该偏向哪一边——先跑一遍 ``rrf`` 看清两路各自贡献了哪些条，再决定调它。
DEFAULT_ALPHA = 0.5
```

**其余选项为什么错**：

- `A` 错：这正是手册第 9 节误区第 1 条（"融合就是把两路分数加起来"）。把 `alpha` 调小
  也只改变混合后的重心：BM25 的分数普遍偏大时，`alpha` 那个权重**根本没起作用**
  （不是"起得小一点"）。第 5 节的实测把"直接相加"的后果写得很直接：
  `[1.0, 0.0, 0.0]` 与 `[4.0006]` 放在一起，后者说了算。
- `B` 错：归 0 会让"唯一的那条证据"被 `0 × weight` 乘没（`fusion.py` 原文）。
  注意 `weighted` 里归一化出来的 0.0 与 BM25 的 0 分**不是同一个东西**：
  前者是"这一路里排最后的那条"（**保留**在名单里，只是得 0 分），
  后者是"完全没有共同词元"（在打分那一步就被排除，见第 6 题）。
- `C` 错：手册第 9 节误区第 4 条。对合并后的分数做归一化时，"这一路的最大值"里
  混进了另一路的量纲，于是 `alpha` 调整的是"两路混在一起之后的重心"。

**结论**：两路的分数**不可比**是这一层的第一性问题；`rrf` 用"名次"绕开它，
`weighted` 用"逐路 min-max"解决它，`min == max → 1.0` 与"0 分条目保留"
分别是这套解法在边界处与召回口径上的两个必要约定。

### 第 4 题 —— C

**考点**：RRF 的定义与 `k=60` 的来历、手算与引擎的一致性、第三排序键、
"不看分数"的可核对形态。

**解析**：

定义只有一段代码（`fusion.py::reciprocal_rank_fusion` 的核心四行）：

```python
_check_k(k)
table = _extract_channels(channel_hits)

contributions: dict[str, dict[str, float]] = {}
for channel, hits in table.items():
    for record_id, (rank, _score) in hits.items():
        contributions.setdefault(record_id, {})[channel] = 1.0 / (k + rank + 1)
```

`k` 的缺省值出处写在常量注释里：

```python
#: RRF 的平滑常数。缺省 60 出自 Cormack、Clarke & Buettcher（2009）的原文
#: （``k=60`` 是他们报告里效果最稳的取值），理由见模块 docstring。
DEFAULT_RRF_K = 60
```

"为什么要用名次"这件事的论证同样在 `reciprocal_rank_fusion` 的 docstring 里：
"余弦相似度 ∈ `[-1, 1]`、BM25 ∈ `[0, ∞)`——两个区间的数字直接相加，加出来的东西
没有任何解释（'0.82 + 7.31 = 8.13'是什么的相关性？）……RRF 用'名次'这个**已经跨通道
可比**的量绕开了整个问题：名次没有量纲，第 1 名在第 1 路与第 2 路是同一种东西"。
`k` 的作用是**压平头部差距**（模块 docstring）："`k=60` 时第 1 名贡献 `1/61 ≈ 0.0164`、
第 2 名 `1/62 ≈ 0.0161`（差 1.6%），而 `k=1` 时是 `1/2` 与 `1/3`（差 33%）。
k 越小越'只信排名第一的那条'，越大越接近'看谁被更多路提到'"。

演示第 4 节就是这道题的证据来源——它把"纸笔公式"与"引擎"两列逐行摆在一起：

```text
查询 'ERR-2043'，深度 fetch_k=3，k=60（RRF 原论文取值）
  向量路三名：[('h-c-01', 0, 1.0), ('h-c-02', 1, 0.0), ('h-c-03', 2, 0.0)]
  关键词路命中：[('h-t-01', 0, 4.0006)]

  手算（纸笔公式，不从引擎拿数）：
      h-c-01  1/(60+rank+1) 求和 = 0.016393443
      h-t-01  1/(60+rank+1) 求和 = 0.016393443
      h-c-02  1/(60+rank+1) 求和 = 0.016129032
      h-c-03  1/(60+rank+1) 求和 = 0.015873016

  引擎给的（同一批输入）：
      #0 h-c-01  score=0.016393443 | 通道 vector         | 手算一致：True
      #1 h-t-01  score=0.016393443 | 通道 bm25           | 手算一致：True
      #2 h-c-02  score=0.016129032 | 通道 vector         | 手算一致：True
      #3 h-c-03  score=0.015873016 | 通道 vector         | 手算一致：True

  逐位一致：True（手算与引擎用同一个定义，差一位就说明实现错了）
```

手算的依据是四行算术：`h-c-01` 与 `h-t-01` 各自只被一路的 `rank 0` 命中 →
`1/(60+0+1) = 1/61 = 0.016393443`；`h-c-02` 是 `1/62 = 0.016129032`；
`h-c-03` 是 `1/63 = 0.015873016`。第 12 题的代码会把这条对照再跑一遍
（`rel=1e-12` 比较），并把"精确并列的两条按 `record_id` 升序"也钉住。

并列时的次序由 `_assemble` 的**三个**排序键决定：

```python
ordered = sorted(
    scores,
    key=lambda record_id: (
        -scores[record_id],
        _best_rank(ranks[record_id]),
        record_id,
    ),
)
```

docstring 把"三个键缺一不可"写成了三句话：只有 `-score` 时会出现"同一份数据两次运行
给出不同 top-1"（原因不是算法，是没写下来的排序规则）；只有前两个时，两条被同一名次
命中的记录仍然无法定序。演示脚本对此有一句必须背下来的话：

```text
      这不是「向量路赢了」，而是「分数并列时必须有确定的第三键」——
      没有它，同一份数据两次运行会给出不同的 top-1。
```

"完全不看分数"的可核对形态是手册第 9 节误区第 2 条给出的那条测试：

```text
误区  "RRF 也用分数"
事实  RRF 只用名次（1/(k+rank+1)）；把某一路的分数放大 100 倍结果逐位不变
证据  test_hybrid_fusion.py::test_paper_formula_ignores_the_raw_scores_entirely
```

第 12 题的 `test_paper_formula_ignores_the_raw_scores_entirely` 用
`score=1.0/0.5` 与 `score=100.0/50.0` 两组同名列次的输入跑同一份 `reciprocal_rank_fusion`，
结果逐位相同（实测输出见第四部分）。

RRF 的三个好性质与两条代价（模块 docstring）：

```text
好性质  免标定（换编码器、换语料都不用重调）、免归一化（不存在除零与上下界问题）、
        抗异常值（某一路给出一条分数虚高 100 倍的记录，它在 RRF 里只是"第 1 名"）
代价    丢掉"差多少"（第 1 名与第 2 名差 0.001 还是差 0.5，RRF 一视同仁）
        丢掉"只有一路有"这个信号（某条被两路同时命中与分别被两路各自命中一次的
        两条不同记录，在 RRF 里得分相近）
```

第二条代价正是 `weighted` 存在的理由之一，也是 `FusedHit` 把三张证据表
（`channel_ranks` / `channel_scores` / `contributions`）逐条留下的理由。

**其余选项为什么错**：

- `A` 错：把分数重新塞回公式就丢掉了 RRF 的全部理由。手册误区第 2 条的证据就是
  "放大 100 倍结果逐位不变"——反过来看，"需要先归一化再除以 `(k+rank+1)`"这种写法
  同时引入了归一化参数与名次参数，而"结果变了"不再指向唯一原因。
- `B` 错：两处都反了。`k` 越大头部**越平**（`k=60` 时第 1 与第 2 名只差 1.6%），
  `k` 越小才越"只信排名第一的那条"；而 `k=1` 时第 1 名的贡献是 `1/2`、第 2 名是 `1/3`，
  不是 `1/61`。另外 `fuse` 的封闭纪律里有一条硬约束：`k_rrf` 必须是 `>= 1` 的整数
  （`k=0` 会让贡献退化成 `1/(rank+1)`，头部权重过大）——`_check_k` 的消息把这条写全了。
- `D` 错：抗异常值恰是 RRF 的**好性质**而不是代价；某一路给出一条分数虚高 100 倍的记录，
  它在 RRF 里只是"第 1 名"，贡献仍是 `1/61`。

**结论**：`score = Σ 1/(k + rank + 1)`，`rank` 从 0 起、`k` 缺省 60；
它只看名次因此免标定、免归一化、抗异常值，代价是丢掉"差多少"与"两路同时命中"这两类信息
（后者由 `FusedHit` 的 `channels` / `contributions` 补回来）；
并列时由 `(-score, best_rank, record_id)` 三个键定序。

### 第 5 题 —— D

**考点**：`where` 与 `min_score` 各自的落刀位置、`notes` 的"无条件"要求、
混合模式下 `below_threshold` 的新口径。

**解析**：

两处落刀位置写在 `hybrid.py` 的模块 docstring 里，各占一小节。

第一处（本课最值得讲的一个坑）：**过滤必须在两路都落刀，而且是同一份子句**。

```text
只过滤向量路    用户 where={"strategy": "structural"} → 向量路只取 structural 的
                关键词路不过滤 → 它把 fixed/semantic 的记录也捞了回来
                融合之后：结果里出现了过滤条件明确排除掉的记录
                而报告里 filter_applied=True（"过滤生效了"），没有任何异常
```

"代码结构上的保证"是这样落地的——`retrieve` 的第 5 步把子句合成放在两路取候选**之前**，
且只调一次：

```python
    # 第 5 步：过滤子句**只合成一次**（两路拿到同一个对象，见模块 docstring 的坑）。
    combined = combine_where(resolved.where, resolved.time_range)
```

随后两个调用点用的是**同一个变量**：

```python
        search = self._vector._backend.query(vector, fetch_k, where=combined)
        ...
        lexical_result = self._lexical.search(resolved.text, top_k=fetch_k, where=combined)
```

演示第 9 节用**真实的融合函数**算了一遍反面对照：

```text
      条件 where={'parent_doc_id': 'doc-concept'}（只想看 concept 那份文档）
      正确做法（两路都过滤）：向量 4 条、关键词 0 条 → 名单 h-c-01、h-c-02、h-c-03、h-c-04
      错误做法（只过滤向量路）：向量照旧 4 条，而关键词路**不过滤**时会返回 1 条（h-t-01）
      把这些合起来（用真实的融合函数算一遍）：融合后的名单里出现 1 条**不满足过滤条件**的记录 [('h-t-01', 'doc-trouble')]
      ——而报告里 filter_applied=True（「过滤生效了」），没有任何异常：
      **多而不报**，比「少而不报」更难发现（没人会逐条核对命中的 strategy）。
```

第二处：**阈值只作用于向量通道**（在融合前落一次刀），而"被忽略"这件事必须进 `notes`。

```text
向量通道   有绝对标度（余弦 ∈ [-1, 1]）→ 可以设阈值，而且这次落刀的数字要报出来
关键词通道 没有绝对标度（BM25 ∈ [0, ∞)）→ **不设阈值**
```

"假的安全感"是这段话里最要紧的词："BM25 的分数分布取决于语料（词频、文档长度、
词表大小）与查询长度，因此 `min_score=3.0` 在一份 10 篇文档的手册上可能切掉一半，
在一份 100 万篇的语料上可能一条都不切……**一个不存在的旋钮比没有旋钮更贵**"。
落刀点与 `day066` 复用同一个函数（`retriever_module._apply_threshold`），理由也在注释里：

```python
        """第 7、8 步：向量路取候选 + 阈值落刀（**只落这一路**）.

        阈值在这里落刀而不是交给 ``backend.query(min_score=...)``：与 day066
        第 6 步同一条理由——"切掉了几条"这个数字必须能被报告，而库侧切完之后
        那个数字拿不到（``candidates`` 会给过滤后的总数，而不是切掉几条）。
        """
```

而 `notes` 那句话是**无条件**追加的（只要查询里写了 `min_score`）：

```python
        # 阈值口径的注记**必须无条件出现**（不许静默地忽略一个用户设过的参数）。
        if resolved.min_score is not None:
            notes.append(
                f"min_score={resolved.min_score} **只作用于向量通道**（在融合前落刀，"
                f"本次切掉 {dropped_threshold} 条）；关键词通道不设阈值——"
                "BM25 的分数没有绝对标度，给它一个数字是假的安全感"
                "（与 settings.retrieval_min_score 缺省 None 的理由同源）。"
            )
```

演示第 8 节的实测三行（这正是 `D` 里引用的数字）：

```text
   min_score |      向量路候选 |      被阈值切掉 |   命中 | 名单
        None |         10 |          0 |    5 | h-t-01、h-c-01、h-c-02、h-c-03、h-c-04
         1.0 |          1 |          9 |    2 | h-c-01、h-t-01
         1.5 |          0 |         10 |    1 | h-t-01
```

`min_score=1.5` 把向量路的 10 条**全部**切掉（余弦最高只有 1.0），而 `h-t-01` 照样在名单里
——它只有关键词路召回它（那一路的分数是 2.27，不受影响），通道证据是 `('bm25',)`。

随之而来的第五件事：混合模式下 `empty_reason` 的口径变了一点点（手册第 5 节的原文）：

```text
单路检索里"min_score 切光即是 below_threshold"，而在混合模式下 below_threshold
**必须同时**满足"关键词路本来就没召回"（阈值不可能清空关键词路）。
本机实测（第 9 节）：query=QUERY_SEMANTIC + min_score=1.5 → below_threshold；
换成 query=ERR-2043 + min_score=1.5 则**不是空结果**（关键词路那一条还在）。
```

**其余选项为什么错**：

- `A` 错：手册第 9 节误区第 7 条。去重是按 `record_id` 合并**同一路/多路召回的同一条**，
  它不会把"过滤条件明确排除掉的记录"删掉——恰恰相反，只过滤一路时那条记录会被融合
  当成"关键词路召回的、向量路没有"的证据留在名单里（演示第 9 节实测 `[('h-t-01', 'doc-trouble')]`）。
- `B` 错：手册误区第 5 条。给 BM25 一个阈值是"假的安全感"，而且它**没有稳定效果**
  （换语料就变），出问题的人会去调它、发现调不动、再转去调别的参数。
- `C` 错：手册误区第 6 条。阈值不可能清空关键词路，因此"阈值切光向量路"只是
  `_diagnose` 的一个输入（`dropped_below_threshold > 0`），而
  `EMPTY_REASON_BELOW_THRESHOLD` 还要"`hits` 为空"这个前置条件成立；
  `ERR-2043 + min_score=1.5` 的实测就是反例（`count == 1`，`empty_reason == "hits"`）。

**结论**：`where` 只合成一次、两路共用同一份子句（代码结构保证，不是注释约定）；
`min_score` 只在向量通道、只在融合前落一次刀，并且"它只作用于向量通道"这句话
无条件进 `notes`；混合模式下 `below_threshold` 还必须满足"关键词路本来就没召回"。

## 第二部分：判断题

### 第 6 题 —— 错

**考点**：`LexicalIndex.search` 只返回 `score > 0` 的文档、这个取舍与 RRF 的关系。

**解析**：

这句话在 `lexical.py` 里有一个专门的标题（模块 docstring 的"本模块的第二个关键取舍"），
原文是完整的反向论证：

```text
BM25 会给**完全不相关的文档**一个 0 分，而它们在名次上位于所有真实命中之后。
如果把它们也算作"关键词路的命中"，那么在名次靠后的位置上会躺着一批
"和查询毫无关系"的记录——而 RRF（``fusion.py``）恰恰**只看名次不看分数**，
它会老老实实给"关键词路第 3 名"一个 1/(k+3) 的贡献。那条证据是假的。

因此 ``search`` 只返回 ``score > 0`` 的文档，并把被排除的条数写进 ``notes``：
"0 分不是'相关性很低'，而是'这次查询完全没提到它'"。这条规则让
"关键词路一条都没召回"成为一个**能说清楚的结论**，而不是"返回了 5 条 0 分记录"。
```

换句话说：把 0 分文档留在名次里**不是"多给一路证据"，而是凭空造出证据**。
RRF 的贡献公式 `1/(k+rank+1)` 里没有任何"分数"的位置，它无法分辨"关键词路第 3 名
是真的命中"与"第 3 名只是排在所有真实命中之后的一个 0 分文档"——两者都会得到
`1/63`。手册第 9 节误区第 8 条把它写成了三列表格：

```text
误区  "关键词路返回的就是它排名里的那些"
事实  它**只返回至少命中一个词元的文档**：0 分文档会被排除
      （否则 RRF 会把"毫无关系"当"第 N 名证据"）
证据  lexical.py::LexicalIndex.search；test_hybrid_bm25.py::TestZeroScoreExclusion
```

10 条样本上的实测（第 11 题会把它钉住）：查询 `ERR-2043` 时
`candidates == 10`、`count == 1`、`zero_scored == 9`，`notes` 里那一句是：

```text
有 9 篇候选文档与查询没有任何共同词元（BM25 给 0 分），已排除在名次之外：
0 分不是'相关性很低'，而是'这次查询完全没提到它'。把 0 分文档按零分排进名次，
会让只看名次的融合策略（RRF）把'毫无关系'当成'第 N 名证据'。
```

这里有一个容易被读混的地方，值得单独点出来：**本层有两种"0 分"，它们不是同一件事**。

```text
BM25 的 0 分            "完全没有共同词元" → 在**打分那一步**就被排除出候选名单
                        （lexical.search 的 `if score > 0.0:` 那一支）
weighted 归一化的 0.0    "这一路里排最后的那条" → **保留**在融合名单里，只是得 0 分
                        （fusion.py 的"保留 0 分条目而不是静默丢召回"）
```

前者的处置是"排除"，后者的处置是"保留"——两者都对，因为前者会污染名次证据、
后者是加权和里真实的 0 贡献。第 3 题选项 `B` 与第 6 题说的正是这两件事的两面。

**结论**：错。0 分文档**必须**被排除在名次之外，否则 RRF 会把"毫无关系"当成
"第 N 名证据"；而 `LexicalIndex.search` 的 `notes` 会把被排除的篇数写出来，
因此"关键词路一条都没召回"仍然是一个能说清楚的结论。

### 第 7 题 —— 对

**考点**：`channels[0] == channel` 为什么必须成立、`sum(contributions) == score` 这条不变量。

**解析**：

两处的实现与各自的 docstring 摆在一起就能看出这是一条规则的两个问法。先是
`fusion.py::_ordered_channels`（给出 `channels` 的顺序）：

```python
def _ordered_channels(per_channel: dict[str, int]) -> list[str]:
    """通道名按"名次好坏"排序；名次相同时**向量优先**，再按名字兜底.

    向量优先不是偏袒：它与 ``RetrievalHit.channel`` 的归属规则
    （"贡献最大者，并列时按 ``CHANNEL_VECTOR`` 优先"）必须是同一条，
    否则 ``channels[0]`` 与 ``channel`` 会在并列时给出两个不同的答案——
    而它们是同一个问题的两个问法。
    """
    return sorted(per_channel, key=lambda name: (per_channel[name], name != CHANNEL_VECTOR, name))
```

然后是 `hybrid.py::_dominant_channel`（给出 `channel`）：

```python
def _dominant_channel(contributions: Mapping[str, float]) -> str:
    """贡献最大的那一路（并列时向量优先；没有证据时回落向量路）.

    为什么需要"归属"：``RetrievalHit.channel`` 是 day066 就定下的形状，
    而混合模式下一条记录可能同时来自两路——必须给出**一个**名字（它是"这条
    主要是谁找回来的"），同时用 ``channels`` 保留"另一路也召回了它"这个证据。
    两处都说同一个名字会让最强证据消失；两处都不说会让报告无法排序原因。
    """
    if not contributions:
        return CHANNEL_VECTOR
    name, _value = max(
        contributions.items(),
        key=lambda pair: (pair[1], pair[0] == CHANNEL_VECTOR),
    )
    return name
```

三条不变量写在手册第 6 节里，并标注"测试逐条钉住"：

```text
channels[0] == channel            两个问题的两个问法必须给同一个答案
len(set(channels)) == len(channels)  不伪造重复的通道
sum(contributions.values()) == score  证据必须能解释分数（RRF 与 weighted 都成立）
```

第 12 题的 `test_the_three_invariants_hold_for_every_hit` 在三个查询上逐条断言前两条，
`test_rrf_first_place_contribution_is_one_over_sixty_one` 用
`math.fsum(item.contributions.values()) == pytest.approx(item.score, rel=1e-12)`
断言第三条；`test_channel_attribution_prefers_the_vector_on_a_tie` 另外把
`_dominant_channel` 的四种输入（空、单通道、两通道并列、两通道不并列）逐条钉住。

注意"为什么两处必须有**同一个**规则"的实质：`channels[0]` 是按**名次**排出来的，
`channel` 是按**贡献**算出来的。在 RRF 下贡献与名次是单调对应的（名次越好贡献越大），
因此两条规则天然一致；但在 `weighted` 下"名次最好的那路"与"贡献最大的那路"**可能不同路**
（一路的第 1 名可能因为在归一化后的值上不占优而贡献更小），这时"并列向量优先"这条
共同兜底就变成了唯一能保证两者一致的东西。

**结论**：对。两条规则都是"贡献最大/名次最好，并列时向量优先"，因此
`channels[0] == channel` 永远成立；而 `sum(contributions.values()) == score`
是这套证据形状能被称为"证据"的最低要求。

### 第 9 题（关键词一路：分词、IDF、0 分排除与词元对账）

#### 1. 切分规则、为什么"两个都要"、以及不引入分词库的两条理由

规则的四条与两条理由都已在第 1 题里逐字引过，这里按"每一条各自在挡什么"重述一遍：

```text
先按 [a-z0-9_]+ | [\u4e00-\u9fff]+ 切段（全角标点、空格、连字符都是分隔符）
拉丁/数字段    原样保留（"err"、"2043"、"retry_budget"；大小写先折叠）
汉字段长度 1   保留该单字（"词" → 词）
汉字段长度 ≥2  单字 + **相邻 2-gram**（"语义缓存" → 语/义/缓/存/语义/义缓/缓存）
```

- 第一条挡的是"按空格切"（`tokenize` 的 docstring：那会把一整句话当成一个词元，
  BM25 退化成整句精确匹配——"一个看起来在工作、实际上永远只命中原句的检索器"）；
- 第二条挡的是"把英文编号也切碎"：`retry_budget` 整体一个词元，而 `ERR-2043`
  因为连字符被切成两个——两者都是刻意的（注释："编号的'前缀'与'序号'分别命中时都能给分"）；
- 第三、四条合起来回答"单字与 2-gram 为什么都要"：单字让"重算"与"重新计算"共享 `重`/`算`
  （在不引入同义词表的前提下蹭到一点召回），2-gram 让"缓存"与"存缓"区分开（提高精确率）；
  只留 2-gram 时单字查询（"熵"、"税"）一个词元都对不上，而单字查询在中文里真实存在。

不引入 `jieba` / `rank_bm25` 的两条理由（模块 docstring，缺一不可）：

```text
1. 不新增依赖   产物必须在"只有 Python + 标准库"的机器上复现；BM25 与分词都是几十行的算术。
                jieba 还带约 5 MB 词典文件 → "离线可复现"变成"词典版本也影响结果"。
2. 评估要可复现  分词器是有版本的（jieba 换版本会切出不同的词）→ 同一天、同一份语料、
                同一批查询会给出不同的 BM25 分数，而 day071 的 RAG 评估要求
                "分数变了必须能归因到某个显式参数"。相邻 2-gram **没有版本**：
                它的定义就是"字符串的相邻两字"。
```

第 2 条与 day071 的关系是直接因果：RAG 评估要把"分数变了"归因到某个可指认的原因
（换了编码器 / 改了语料 / 调了 `k1`），而一个会随版本变化的隐式词典会让归因不可能。
代价也写在边界清单里（`types.RETRIEVAL_LIMITATIONS` 第三条），并在演示里可见：
`avgdl 34.3000`、`词表 274`——一条 20 字的句子会产生 19 个 2-gram，因此词表比真实词表大。

`tokenize("  语义  缓存  ")` 没有 `义缓`，是因为 2-gram 只在**同一个汉字段内**生成
（切段之后是两个独立的汉字段）；而 `tokenize("ERR-2043")` 切成 `["err", "2043"]`，
是因为连字符不在 `[a-z0-9_]` 里、也不在汉字区间里，它是分隔符。

#### 2. IDF 为什么恒正、手算与方向

`log(1 + (N - df + 0.5) / (df + 0.5))`：括号里那个比值恒正，`1 + 比值 > 1`，
因此 `log` 恒正——`df` 取到最大值 `N` 时它仍然给出 `_idf(10, 10) = 0.046520 > 0`。
经典写法 `log((N - df + 0.5) / (df + 0.5))` 在 `df > N/2` 时变负
（`_idf(10, 9)` 的经典版本是 `log(1.5/9.5) = -1.84…`），于是两件事混在一起：

```text
"score 越小越不相关"  与  "score 为负 = 减去相关性"
```

而本模块用 `0 分`当"完全没有共同词元"的哨兵（`search` 只返回 `score > 0`），
所以"0 分"必须只有一个含义——恒正的 IDF 保证了它。

手算 `_idf(10, 1)`：`(10 - 1 + 0.5) / (1 + 0.5) = 9.5 / 1.5 = 6.3333…`，
`1 + 6.3333… = 7.3333…`，`log(7.3333…) = 1.992430`——与演示第 2 节、第 11 题的实测一致
（`pytest.approx(1.992430, abs=1e-6)`）。对 `df` 的单调性也在第 11 题里钉住：
`[_idf(100, df) for df in range(1, 100)]` 严格递减，且与测试侧**独立重写**的公式逐位一致。

`k1` 与 `b` 各管一件事，方向由第 6 节两张表给出（这张表在第 2 题的解析里已完整引用）：

```text
k1 扫描（b=0.75）  比值 1.0000 → 1.0549 → 1.1268 → 1.1883 → 1.2852   单调递增
                   k1=0 时两条**同分**：词频完全不参与
b  扫描（k1=1.5）  比值 1.8182 → 1.5710 → 1.1268 → 0.9264            单调递减
                   b=0 完全不归一化（长文档占优）；b=1 时 heavy 反而低于 light
```

方向为什么是这样：`k1` 出现在分子 `tf·(k1+1)` 与分母 `tf + k1·(…)` 里，
它决定"同一个词多出现几次的收益有多大"（`k1=0` 时收益恒为 1，即"只看出现过没有"）；
`b` 只出现在分母的长度项 `1 - b + b·dl/avgdl` 里，它决定"长文档的同一个词被打几折"
（`b=1` 时完全按 `dl/avgdl` 归一化）。这两个方向合起来才是 BM25 与"纯词频排序"的分水岭：
"没有 `b`，长文档永远占优"（演示第 6 节原文）。

#### 3. 0 分排除、10 条样本上的实测，以及 `missing_terms` 的三种形态

`search` 的第 6 步是"打分排序"，第 7 步是"截断与注记"，中间的判断只有一行：

```python
            if score > 0.0:
                scored.append((document.record_id, score))
            else:
                zero_scored += 1
```

理由（模块 docstring 第二节，完整引文见第 6 题）：**RRF 只看名次不看分数**，
它会老老实实给"关键词路第 3 名"一个 `1/(k+3)` 的贡献，而那个"第 3 名"可能只是一个
0 分文档——"那条证据是假的"。因此"0 分不是'相关性很低'，而是'这次查询完全没提到它'"，
它必须被排除在名次之外，并且被排除的篇数要写进 `notes`。

10 条样本上的实测（查询 `ERR-2043`）：

```text
candidates == 10      （无 where，全部十篇都是候选）
count      == 1       （只有 h-t-01 同时含 err 与 2043）
zero_scored == 9      → notes 里："有 9 篇候选文档与查询没有任何共同词元（BM25 给 0 分），
                        已排除在名次之外：0 分不是'相关性很低'，而是'这次查询完全没提到它'。
                        把 0 分文档按零分排进名次，会让只看名次的融合策略（RRF）
                        把'毫无关系'当成'第 N 名证据'。"
score      == 4.000606（与 tests/hybrid_samples.py 的 EXPECTED_LEXICAL_SCORES 逐位一致）
```

`LexicalSearchResult` 的 docstring 把 `missing_terms` 的三种形态写成了三段：

```text
missing_terms 全等于 query_terms  → 一个词都不认识（纯语义改写 / 用了别的语言）
missing_terms 为空                → 词都认识，但没有任何一篇同时包含它们
matched_terms 非空且 hits 非空     → 正常命中
```

前两种都表现为"空结果"，但处置动作不同（前者要换查询说法或补语料，后者要检查
过滤条件与语料分布），因此分开列出来而不是合成一个布尔值——与 `types.EMPTY_REASONS`
的那条纪律同源。演示第 3 节的案例 B 是第一种：查询 `午饭吃点什么好` 的
`query_terms` 是 **13 个**（7 个单字 + 6 个 2-gram：`么/么好/什/什么/午/午饭/吃/吃点/好/点/点什/饭/饭吃`），
`matched_terms` 为空、`missing_terms` 全列。而"分母"就是 `LexicalIndex.vocabulary_size`：

```text
关键词路一条都没召回：查询词元与词表交集为空（纯语义改写常见）——
missing_terms=[...]（共 13 个词元，全不在词表里），词表里有 274 个词元。
这不是索引坏了，而是这一路的固有边界：它只认字面。
```

"13 个词元里 0 个在词表里"是一句**可核对**的话；只写"没找到"则无法区分
"词表太小"与"这次查询完全没提到语料"——这就是"交集为空必须有一个分母"的意思。
反过来，命中时也会给出对称的信息：`missing_terms` 非空（部分词元不在词表里）时
`notes` 会追加"查询里有 N 个词元不在词表里（…）：它们不会贡献任何分数——这是'未登录词'
这条真实边界（2-gram 分词法不认识未收录的字串）"。

#### 4. 两种"空"、`from_backend` 的升级，以及两份"不重算"

`LexicalIndex.search` 第 4 步（空索引）与中毒索引分支是两件事，处置的人也完全不同：

```python
        if not self._documents:
            notes.append(
                "关键词索引是空的（0 篇文档）：这是合法状态，直接返回空结果而不报错"
                "（与向量路 count=0 的 no_data 同一口径）"
            )
            return LexicalSearchResult(...)

        if self._total_length == 0:
            # 有文档但一个词元都没有：索引被"空的正文"毒化了（avgdl = 0 会让
            # BM25 的分母退化）。这是索引侧的事（去修入库口径或重建），不是调用方的参数问题。
            raise LexicalError(...)
```

- **0 篇文档**：合法状态（刚建好的库、刚清空重建的库都是它），返回空结果 + `notes`，
  `candidates` 给 0（"库是空的时候，过滤条件根本没有作用对象"）。修的人是"还没建索引"。
- **有文档但词元总数为 0**：`avgdl = 0` 会让 BM25 的分母退化，索引**没法打分**，
  因此抛 `LexicalError`（"改调用点走不通"那一族）。第 11 题的实测消息是
  "关键词索引里有 1 篇文档，但它们的词元总数为 0：索引无法打分（BM25 的分母里有 avgdl）……
  出路：修入库口径（正文至少要有可索引的字）或重建关键词索引"。

`from_backend` 把 `get_many` 的"跳过不存在的"升级成错误，理由写在它的 docstring 里：

```text
        ``get_many`` 的实现是"**跳过不存在的**"（``vectorstore.base`` 的原文），
        这里刻意把它升级成错误：库里报 N 条、只取回 M 条，意味着记录表与索引
        不同步（day064 那个经典故障）。如果照常建索引，后果是**关键词路静默少召回**
        ——少的那几条不会出现在任何数字里，只会表现为"关键词路好像漏了什么"。
        因此宁可在这里响（``LexicalError``，"去重建"那一族）。
```

第 11 题用一个"报 2 条、只回 1 条"的假后端把它钉住，实测消息是
"库里报 2 条记录，但只取回 1 条：记录表与向量索引不同步（get_many 会跳过不存在的 id）……"。

两处"不重算"与一处"复用"：

```text
过滤复用  LexicalIndex.search(..., where=...) 的校验与执行**完全复用**
          vectorstore.filters.compile_filter（经 retrieval.filters.validate_where 包装，
          把 FilterError 翻成 QueryError）。两路各写一份过滤实现的话，
          "同一个 where 在向量路筛掉 3 条、在关键词路筛掉 2 条"这种分家会永远存在
          而且不报错——而 hybrid 的"过滤在两路都落刀"要的正是**同一份**语义。
idf 不重算 idf 与 avgdl 都是**全库统计**（不受 where 影响）：它们是语料的性质，
          不是"这次过滤出来的那几条"的性质。用子集重算会让同一个词在两次不同过滤下
          有不同的权重，而分数是要跨查询比较的。
avgdl 不重算 同上；另外空索引返回 0.0 而不是报错（空索引是合法状态），
          而正文为空串的文档也算进平均——"把它排除在平均之外会让 avgdl 变成
          '非空文档的平均'，而那个数字在报告里解释不通"。
```

顺带一条与"复用"同源的纪律：`_check_top_k` 的上限**复用** `vectorstore.MAX_TOP_K`
（"两条路的深度上限一旦分成两个数字，混合检索取候选时就会出现'关键词路取 1000、
向量路只能取 800'这种自相矛盾的配置"），而深度的过取倍率与封顶则由向量路那
唯一一份实现算出（`hybrid.py` 第 3 步直接调 `self._vector._fetch_depth`）。

### 第 10 题（融合与混合检索：量纲、RRF、去重与两个落刀位置）

#### 1. 为什么不能直接加权求和，以及 `weighted` 的两个细节

两路的取值范围不同（`fusion.py` 模块 docstring 第一节）：

```text
向量路   余弦相似度 ∈ [-1, 1]     "0.82" 是一个有绝对上界的数
关键词路 BM25 ∈ [0, ∞)            "7.31" 是一个**没有上界**的数
```

"两个数字放在一起比较是**类型错误**，而它不会报错：`0.82` 与 `7.31` 都是浮点数，
`sorted` 照单全收"——于是"加权求和"会把量纲差当成相关性差：BM25 只要分数普遍偏大
（语料里的词频一高就会），它就会单方面决定名单顺序，而 `alpha` 那个权重根本没起作用。
演示第 5 节的实测就是这一句：向量路 `[1.0, 0.0, 0.0]`、关键词路 `[4.0006]`，
直接相加时后者说了算。

`weighted` 的两个"不是可选项"的细节（完整引文见第 3 题）：

```text
1. 逐路 min-max   对合并后的分数做归一化时，"这一路的最大值"里混进了另一路的量纲，
                  于是 alpha 调整的是"两路混在一起之后的重心"，仍然不是权重。
2. min == max → 1.0   这一路只有一条命中时必然 min == max；归 0 会让"唯一的那条证据"
                  被 0 × weight 乘没，而它明明是该路的第一名（归一化保序，把单点
                  映射到 1 是保序的）。
```

`alpha` 越过 0.5 时第一名翻转的机制：两条"各自的第一名"（向量路的 `h-c-01`、
关键词路的 `h-t-01`）在各自路内都归一化成 `1.0`，因此它们的加权分恰好是
`alpha × 1.0` 与 `(1 - alpha) × 1.0`——演示第 5 节的扫描表里 `h-c-01` 那一列
正好是 `0.0000/0.1000/0.2500/0.5000/0.7500/0.9000/1.0000`，`h-t-01` 那一列是它的镜像。
`alpha < 0.5` 时后者大、`alpha > 0.5` 时前者大，于是在 0.5 处翻转。

`alpha=0.5` 那行"并列，按 id"的依据是 `_assemble` 的第三排序键：两条分数都是 `0.5000`，
`best_rank` 也相同（各自在该路都是 `rank 0`），于是落到 `record_id` 升序——
`h-c-01 < h-t-01`，向量路那条在前。注意这**不是权重在偏袒向量路**，
而是"分数并列时必须有确定的第三键"。

#### 2. RRF 的公式、`k` 的来历、手算证据与它牺牲的东西

```text
贡献 = 1 / (k + rank + 1)        rank 从 0 起，k 缺省 60（RRF 原论文取值）
score = Σ_channels 贡献           同一条被两路召回 → 两个贡献相加
```

`1/61 = 0.016393443` 的来历是纯算术：`k=60`、`rank=0` → `1/(60 + 0 + 1)`。
`h-c-02` 是 `rank=1` → `1/62 = 0.016129032`；`h-c-03` 是 `rank=2` → `1/63 = 0.015873016`。
"手算与引擎逐位一致"值得单独留一节（演示第 4 节）的理由是：**这条公式本身就是定义**，
因此"差一位"只可能来自实现错误（浮点求和顺序、`rank` 起点、`k` 的取值），
而它是最容易被"看起来很像"掩盖的一类错误。第 12 题用 `rel=1e-12` 再钉一次。

并列时由**第三排序键**决定次序：`_assemble` 的 `(-score, best_rank, record_id)`，
其中 `best_rank = min(channel_ranks.values())`（`FusedHit.best_rank` 的定义）。
演示脚本的原话是："这不是「向量路赢了」，而是「分数并列时必须有确定的第三键」——
没有它，同一份数据两次运行会给出不同的 top-1"。

RRF 的两条代价（模块 docstring）：

```text
丢掉"差多少"   第 1 名与第 2 名差 0.001 还是差 0.5，RRF 一视同仁
丢掉了"只有一路有"这个信号   某条被两路同时命中（最强证据）与
                            分别被两路各自命中一次的**两条不同记录**，
                            在 RRF 里得分相近（都是两个 1/(k+r) 之和）
```

`fuse` 的封闭纪律里，最"会让人查不到病因"的那一条是最后一条：

```text
weighted 缺某一路的权重                      → FusionError，而**不是**默认为 0
```

"默认 0 会让那一路的证据**静默消失**（结果看起来正常，只是某一类查询突然变差了
——一个查不到病因的现象）"——其余四条（未知策略名 / `alpha` 越界 / `k_rrf < 1` /
通道名不在 `CHANNELS` 里 / `strategy="rrf"` 却给 `weights`）都会当场响，
报错消息里还会列出合法取值。

#### 3. "去重"的真实含义、`FusedHit` 的七个字段与三条口径

`fusion.py` 用一整节说明"去重"在这里的含义**恰好相反**：

```text
"去重"这个词容易让人以为目标是"把重复的去掉，让名单短一点"。在这里它的含义
恰好相反：**同一条记录被两路独立召回，是融合能给出的最有价值的一条结论**
（两条互相独立的检索路径都指向它）。因此合并时不是"丢掉一条"，而是：

一条命中          合并成一条 FusedHit，**保留全部通道的证据**
分数              两路贡献之和（rrf 是两个 1/(k+r+1)；weighted 是两个加权归一化分）
名次              两路里最好的那个（best_rank）
channels          按名次好坏排序的通道名（因此"两路都召回了它"一眼可见）
```

`FusedHit` 的七个字段（docstring 原文的表格）：

```text
record_id       哪一条
score           融合后的分数（策略定义的口径，不是一个"相关性"）
rank            融合后的名次（0 起连续）
channels        被哪几路召回（**按名次好坏排序**）——多路命中一眼可见
channel_ranks   每一路给它的名次（{"vector": 3, "bm25": 0}）
channel_scores  每一路的**原始**分数（"两路的分数量纲不同"因此可以对着看）
contributions   每一路对最终分数的贡献（两条一起解释"为什么是 0.0315"）
```

"这份形状存在的核心理由"是 `contributions`：没有它时，"`alpha=0.3` 的结果为什么与
`alpha=0.7` 一样"只能靠重跑两次来回答；有它时，读一眼 `{"vector": 0.6, "bm25": 0.0}`
就知道**关键词路这次什么都没贡献**（那时要调的不是 `alpha`，而是查询说法或语料）。
而"逐条的数值证据留在融合层、不进 `RetrievalHit`"也有理由："把它们塞进每一条命中，
会让一份报告里出现三张小表 × N 条（与'`RetrievalHit` 不带向量'是同一条理由）"。

按第 7 节的数字把并集的账对一遍（查询 `retry_budget`）：

```text
两路召回        vector 10 条、bm25 1 条          → 和 = 11
并集            candidates == 10                 ← 同一条被两路召回只算一次
被两路同时命中  fusion["deduped"] == 10 - 1 == 1  ← "合并了多少条重复证据"
融合名单        fusion["fused"] == 10
每路贡献数      fusion["contributions"] == {"vector": 10, "bm25": 1}
```

`h-t-02` 的分数 `0.032787 ≈ 2 × 0.016393` 比下一名的 `1/62 = 0.016129` 更有分量，
原因是它同时拿到了两路的 `rank 0`：**"两路都提到它"比"某一路排第一"更有分量**，
"这是融合给出的新信息，单路检索永远给不出它（它连'被几路提到'这个概念都没有）"。

`RetrievalHit.channel` 与 `channels` 在"两路都召回它"时分别给出：

```text
channel     一个名字：贡献最大的那一路（并列时 CHANNEL_VECTOR 优先）
            → h-t-02 的 channel == "vector"（两路贡献都是 1/61，并列）
channels    全部证据：这一条被哪些路同时召回（按名次好坏排序，并列时向量优先）
            → h-t-02 的 channels == ("vector", "bm25")
```

`types.RetrievalHit` 的 docstring 把两者的分工写死了："两处都说同一个名字会让最强证据消失；
两处都不说会让报告无法排序原因"。而默认值 `()` 的含义是"**未记录多路证据**"
（day066 的单路语义）——"单路向量检索刻意不填它（填 `(CHANNEL_VECTOR,)` 会把'单路'
与'混合但只被一路召回'混成同一种形状，而这两件事在诊断里的结论不同）"。

#### 4. 两个落刀位置与"两个数必须一起看"

过滤的失败模式与实测数字已在第 5 题里完整给出（反面对照出现 1 条
`[('h-t-01', 'doc-trouble')]` 而 `filter_applied=True`）。这里补一句为什么它是**结构**保证：
`hybrid.py` 第 5 步注释写着"过滤子句**只合成一次**（两路拿到同一个对象，见模块 docstring 的坑）"，
模块 docstring 的原话是"因此本模块把子句合成放在**两路取候选之前的一次调用**里，
并把'两路用的是同一份'写进代码结构（同一个变量交给两个调用点），而不是指望以后加第三路
的人记得同步"。

阈值只作用于向量路的两个理由：

```text
向量通道有绝对标度（余弦 ∈ [-1, 1]）→ 可以设阈值，而且这次落刀的数字要报出来
关键词通道没有绝对标度（BM25 ∈ [0, ∞)）→ 不设阈值：给它一个数字是"假的安全感"
```

"这句话必须出现在每一次带阈值的混合检索里"（`hybrid.py` 阈值语义一节的原文），
否则"我设了阈值为什么关键词路还在返回低分记录"会变成一个反复出现的疑问——
第 12 题的 `test_threshold_only_touches_the_vector_channel_and_says_so` 同时钉住了
正反两面：`min_score=None` 时这句话**不在** `notes` 里，而 `min_score=1.5` 时
它必须逐字出现（"min_score=1.5 **只作用于向量通道**（在融合前落刀，本次切掉 10 条）"）。

混合模式下 `below_threshold` 比单路多的那个条件（手册第 5 节原文已引）：
**还要"关键词路本来就没召回"**。一组正反实测：

```text
QUERY_SEMANTIC（关键词路 0 条）+ min_score=1.5  → count=0、empty_reason=below_threshold、
                                               dropped_below_threshold=10、
                                               channel_candidates={"vector": 0, "bm25": 0}
ERR-2043（关键词路 1 条）    + min_score=1.5  → count=1、empty_reason="hits"、
                                               channel_candidates={"vector": 0, "bm25": 1}
```

`channel_candidates` 与 `candidates` 必须一起看的原因（`hybrid.py` 模块 docstring 的最后一节）：

```text
``channel_candidates`` 与 ``candidates`` 必须一起看：并集小于两路之和的差值，
就是"被两路同时命中"的条数（融合最强的那类证据），而这个数字**只能**从
两个数一起读出来。
```

换句话说：只看 `candidates`（并集 10）看不出"关键词路是不是根本没捞到东西"；
只看 `channel_candidates`（`{"vector": 10, "bm25": 1}`）又看不出"有多少条被合并了"——
差值 `11 - 10 = 1` 才是那条最强证据。两个数一起读，还能顺带回答诊断顺序上的第一个问题：
"有一路是不是根本没捞到东西"。

最后一条与"为什么这些数字都要分开"的纪律对齐：`retrieval/__init__.py` 的第 2 条纪律
（"条数少于期望必须是可回答的"）在 day067 被用了两次——**每一路**召回了几条
（`channel_candidates`）与**每一路**贡献了几条（`fusion.contributions`）都各自成数，
因为"某路召回 3 条、贡献 0 条"（它召回的东西全被别的路挤出了名单）与
"某路召回 3 条、贡献 3 条"在只看召回数时长得一样。

三条值得单独说明的实测细节：

1. **`fusion["contributions"]` 统计的是"截断之前"的融合名单**。`QUERY_BOTH` 下

   免得读者把"贡献条数"误读成"名单里还剩几条"。

**为什么"重排 / 重算融合"绝不能发生在端点层？**

因为**融合是"这份结果为什么长这样"的唯一权威**，一旦在第二处重算，两份答案迟早会不一样，
而那时报告里给出的已经不是事实。`api/routes.py` 这段的注释把三条理由写在了一起：

```text
# 2. **端点只做"折请求体 → 调 retrieval → 序列化"**：深度、阈值、两路过滤、
#    融合、多样性、诊断全部留在 ``retrieval`` 包里（那里有它们的唯一实现）。
#    端点上重算一次融合会产出"接口与脚本给出的 top-1 不一样"这种差异。
```

三条具体的理由：

1. **唯一实现**：融合的排序键（`(-score, best_rank, record_id)`）、`contributions` 的定义、
   `deduped` 的口径都只有一份实现在 `fusion.py` / `hybrid.py` 里。端点上写第二份，
   就必须把"第三排序键""并列向量优先""截断前统计"这些约定**再实现一次**——
   而第二份实现一定会在某次修 bug 时落后于第一份（这正是"同一个库、同一句话、
   两份报告里的数字不一样"的来源）。
2. **可复述性**：`result.fusion` 里带着**这次用的是哪组参数**
   （`params == {"k_rrf": 60}` 或 `{"alpha": 0.3}`），`result.query.extra` 里带着
   调用方给的那三个键。端点上重算时要么重抄一遍参数（于是"接口与库内"可能不一致），
   要么把参数丢掉（于是"这次用的是哪组参数"再也说不清）。第 12 题的
   `test_the_hybrid_endpoint_does_not_recompute_anything` 用"端点返回的
   `channel_candidates` / `fusion` 与直接调用检索器**逐字段相同**"把这条纪律钉住。
3. **错误归属**：参数非法在检索层抛 `FusionError`（400），装配写错（例如
   `app.state.retrieval_hybrid` 不是 `HybridRetriever`）给 **500**。端点只做"折请求体 →
   调 retrieval → 序列化"，这条"参数问题 400 / 装配问题 500"的分工才守得住；
   端点上重算一次融合会把这个分工搅乱（例如它自己解析 `alpha` 时对越界值的处置
   可能与 `fusion.fuse` 不同）。

一条与之配套的界（手册第 8 节里写着）：关键词索引在**每次请求现建**
（`from_backend`，保证"两路看到的是同一批文档"），代价是 O(N) 分词；
语料大时请把索引建一次挂到 `app.state.retrieval_lexical` 上注入进来——
"现建"发生在端点这一层的**装配**上，而不是把检索决策搬到端点里。
