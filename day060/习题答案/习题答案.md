## 第一部分：选择题

### 第 1 题 → **C**

本模块存在的**全部理由**就是这一条：

> 一个 `adapter_dir` 为空的部署不会抛异常、不会返回 500，
> 它只会把基座的答案当成"专属模型的答案"交出去——
> 而那正是"专属模型上线了却没生效"最真实的一种发生方式。

实测的错误信息把这句话写进了正文：

```text
声明 adapter 却没给目录被拒：形态 adapter 缺少必填字段 adapter_dir：
声明了部署的形态却没给路径的部署不会报错，它只会安静地服务别的东西
```

B 是错的，而且错得很有代表性：**如果它抛 `FileNotFoundError`，就不需要这一层校验了**。
真正危险的情形恰恰是"路径指向一个存在但不对的目录"——文件系统不会报错，
行为差异要到"模型答得莫名其妙"时才被发现。

这与 day050"把词表随检查点落盘"、day052"校验基座是否匹配"是同一条纪律的
第三次出现：**把"静默失效"提前成"构造期失败"**。

### 第 2 题 → **B**

KV 缓存对上下文的长度与并发数**都是线性**的：

```text
每 token 每序列 = 2 × 36 层 × 8 个 KV 头 × head_dim 128 × 2 字节 = 147456 字节 = 144 KiB
4096 上下文 × 并发 1 = 147456 × 4096 × 1 = 603979776 字节 = 576.00 MiB
4096 上下文 × 并发 4 = 147456 × 4096 × 4 = 2415919104 字节 = 2304.00 MiB
差值 = 1728 MiB = 1.69 GiB
```

答案是 B，而不是 D：**并发与缓存是线性关系，不是平方**（D 把"层数 × 头数"
当成了某种平方，那是错的）。C 把 MiB 与 KiB 混了。

这 1.69 GiB 的全部代价是"多要显存"——**它不提升任何质量**。
Ollama 官方 FAQ 把这件事写在 `OLLAMA_NUM_PARALLEL`（默认 1）的说明里：
并发请求会按并发数放大上下文与内存分配。因此"把并发调到 4"是一个
必须解释清楚理由的动作。

A 是常见的误解：并发**会**影响吞吐，但它同时按同一个乘数放大 KV 缓存。

### 第 3 题 → **C**

```text
[阻塞] serving_name         部署脚本改错了目标服务（改了 A 却以为改了 B）
[阻塞] base_model           基座与适配器不匹配：能挂上，但输出与训练行为无关
[阻塞] adapter_hash         线上加载的是上一份适配器（adapter_dir 指到了旧目录）
[阻塞] kind_shape           形态与自述矛盾：合并形态却自述挂了适配器
[告警] registry_head        绑定版本不是注册表 head：有人提升了新版本却没部署（或反过来）
```

C 的理由是具体的：**灰度发布的本质就是"部署的不是 head"**——
先把新版本部署上去再逐步切流量，或者先给 5% 流量试跑、跑稳了才提升阶段。
把它设成阻塞会发生什么？团队为了过校验会**先去提升阶段**，
于是"提升"变成一个为了过门禁而做的动作，而不是一个基于证据的决定。
**一种被逼出来的假动作，比不做校验更糟。**

A 与 B 都错在事实层面：基座不匹配时服务"能跑"但**输出与训练行为无关**，
这正是它必须阻塞的原因；`adapter_hash` 是唯一能证明"线上跑的是哪一份"
的证据，缺了它或对不上，整条追溯链就断了。

### 第 4 题 → **B**

```text
专属模型（新路径）失败 → 回落到云端（已验证路径）    修复：用户拿到正确答案
云端（已验证路径）失败 → 回落到专属模型（新路径）    事故：一个未验证的模型接管了全部流量
```

选 B 的理由是"第二个故障的根因会被第一个掩盖"：云端为什么挂、
专属接管期间发生了什么，两件事会混在同一次事故复盘里。
而这次复盘要回答的问题（"用户看到的错答案是谁给的"）**恰恰需要把两者分开**。

A 是错的：反向降级当然能"让请求成功"，但成功的是**一个还没通过验证的模型**——
把"没报错"当成"没问题"正是本课反复在防的那件事。

D 也不是理由：能不能做 A/B 与降级方向无关（而且本课的哈希分桶本来就
不做统计意义上的 A/B，见第 5 题）。

### 第 5 题 → **B**

> **哈希分桶不是随机分流。** `dedicated_ratio=0.05` 的含义是
> "哈希落在前 5% 的**那些 prompt**"，而不是"随机 5% 的请求"。

实测（200 个不同问题）：

```text
① 影子     ratio=0.0   shadow=0.05  → 专属服务 0    影子 16
② 小流量   ratio=0.05  shadow=0.0   → 专属服务 11   影子 0
③ 半量     ratio=0.5   shadow=0.0   → 专属服务 90   影子 0
④ 全量     ratio=1.0   shadow=0.0   → 专属服务 200  影子 0
       先算一遍会分走 11 条（不调用任何模型）；再跑一遍结果相同：True
```

第 ② 行设定 5%、200 条里实际分走 11 条（5.5%）：**它围绕 5% 波动，
但同一个批次的答案永远不变**。这就是"稳定分桶"与"随机分流"在数字上的
可见差别。

A 是错的（那需要 `random`）；C 混淆了"请求级分流"与"token 级分流"
（本课没有做后者）；D 描述的是**轮询/取模**，它与哈希分桶看起来都能
"稳定分流"，但取模会把高度相似的请求排在相邻位置，而哈希不会。

这条限制被写进了 `route_table()` 的 `cost` 列与 `SERVING_OUT_OF_SCOPE`：
不能把它当 A/B 实验平台，因为两侧的用户构成不可比。

## 第二部分：判断题

### 第 6 题 → **错**

这正是本课最需要被记住的一条：

```text
fail_open=True ：第 1 次 [云端] 参考答案
                第 2 次 [专属] 参考答案
                影子调用 0／降级次数 1
                服务计数：专属 1 / 云端 1（合计 = 请求数 2）
                ↑ 第 1 次其实是云端兜住的：**fail_open 会让「一切正常」变成一个假象**
```

两次调用**全部成功返回**，但第 1 次是云端兜住的。只看成功率会得出
"专属模型很稳"的结论，而它其实一次都没成功过。

因此 `describe()` 必须同时暴露 `dedicated_served` 与 `fallback_count`：

| 计数 | 回答的问题 |
|------|-----------|
| `dedicated_served` | 有多少请求的答案**真的**来自专属模型 |
| `fallback_count` | 有多少请求看似成功、实际被云端兜住了 |

要测**真实成功率**，必须用严格模式：

```text
fail_open=False：专属模型调用失败且策略为 fail_open=False（严格模式）：dedicated 暂时不可用
                云端被调用 0 次（严格模式不兜底）
```

### 第 7 题 → **对**

`shadow_calls` 回答的问题是"**有多少请求付了两次推理成本**"。
一次没有真正发生的调用不能被计进去——否则那个数字只是虚高，
而它恰恰是灰度期间判断"影子阶段花了多少钱"的唯一依据。

本课第一版在视觉路径上漏了这一步：记录被 `_decide` 标成"影子"，
但专属模型一次都没有被调用。修法分两半：

```python
if shadow and dedicated_ok:
    self._run_shadow(messages, record, lambda leaf: call(leaf))
elif shadow:
    record.shadow = False   # 影子调用根本没有发生 → 不能计入
    record.reason = f"{record.reason}；专属模型不支持视觉，本次没有打影子"
```

配套的断言直接钉住数字：

```python
def test_vision_shadow_is_not_counted_when_dedicated_cannot_see():
    ...
    assert switcher.shadow_calls == 0
    assert dedicated.vision_calls == 0
    assert "本次没有打影子" in switcher.switch_log[0].reason
```

这与 day046"包装器不产生 token、计费必须落到叶子上"是同一条纪律：
**计数必须指向真实发生的事，而不是指向意图。**

### 第 8 题 → **对**

延迟是五条检查里唯一非阻塞的一条，而且它的"缺省行为"是**未检查**
而不是"通过"：

```text
[不通过/告警] latency      实际 None / 阈值 未给出倍数
跳过的检查 ['latency']（延迟中位数 云端 180ms / 专属 420ms = 2.333×）
```

报告里同时给出 `skipped_checks`（没测）与 `warnings`（没达标）两个属性，
理由与 day059 的门禁表 `when_missing` 一列完全相同：
**"没测"要补数据，"没达标"要改模型，两个动作完全不同。**

`actual` 为 `None` 表达的是"这一项没有纳入判定"，而不是"没有测量"。
这是"测量"与"判定"两件事分开的一个具体例子。

## 第三部分：简答题

### 第 9 题（"自建更便宜"缺了哪个主语）

#### 1. 为什么 0 请求时自建仍要付 $734.38

因为两个成本模型的**自变量不同**：

```text
云端 API   = 可变成本 × 请求数        自变量是"调用量"
自建推理   = 固定成本 × 开机时长      自变量是"开机时长"
```

实测的四档里，最后一行的自变量是 `1 台 × 730h`：

```text
10000 请求      | 云端 $5.25      vs 自建 $734.38 | 1 台 × 730h | 利用率 3.04%
100000 请求     | 云端 $52.50     vs 自建 $734.38 | 1 台 × 730h | 利用率 30.44%
```

**注意 10000 与 100000 两档的自建成本完全相同**——它只与"开了几台、开了多久"
有关。0 请求时云端花 $0，自建照付 $734.38。这就是本课最重要的一句话：

> **空转的 GPU 是最贵的。**

而且它的算术形式很直接：`cost = usd_per_hour × deployed_hours`，
式子里**没有利用率的分母**。于是利用率减半、单位成本正好翻倍。
把利用率从 30% 提到 60% 等于把单位成本砍半，而这不需要换模型、不需要改代码。

#### 2. `machines` 为什么要上取整

因为"用掉的算力"与"为之付费的时长"是两个量：

```text
required_gpu_hours   = 总 token / (有效吞吐 × 3600)
deployed_gpu_hours   = machines × monthly_hours
machines             = max(1, ceil(required_gpu_hours / monthly_hours))
```

不做上取整会算出什么？以 1000 万请求那一档为例：

```text
10000000 请求 | 云端 $5250.0000 vs 自建 $22765.7800 → 云端更省 | 31 台 × 730h | 利用率 98.20%
```

这一档 `required_gpu_hours = 22222.22`，除以 730 得到 **30.44 台**。
不做上取整（直接用 30.44 台乘时价）会得到约 $22,357——差额不大，
但**方案本身部署不出来**：没有"0.44 台机器"这种东西。
而如果请求量再小一点、离整台差得很远，误差就会被放大成"算得出来
但根本跑不动"的方案。

这正是 day046"性能基线要用实测值"那条纪律的另一种表现：
**一个数学上正确、物理上不存在的数字，是最难被发现的一类错误。**

#### 3. 恒等式与 13.99

```text
breakeven_requests = machines × monthly_hours × usd_per_hour / 单次云端费用
自建单位成本        = dedicated_cost_usd / (总 token / 1000)
                   = machines × monthly_hours × usd_per_hour / (总 token / 1000)
云端单位成本        = cloud_cost_usd / (总 token / 1000)
                   = 请求数 × 单次云端费用 / (总 token / 1000)

两者相除 → 自建单位成本 / 云端单位成本
        = (machines × monthly_hours × usd_per_hour) / (请求数 × 单次云端费用)
        = breakeven_requests / 请求数
```

实测（100000 请求/月）：

```text
自建 $0.0036719/1K ÷ 云端 $0.0002625/1K = 13.99
1398819 ÷ 100000                        = 13.99
```

于是"盈亏平衡点是我现在请求量的 14 倍"与"我的单位成本是云端的 14 倍"
是**同一句话的两种说法**。这条恒等式是本模块的自我校验机制：
机器数、月时长、时价、每请求 token 这四个乘数里任何一个算错，
两个比值都会分叉。它被写成了断言：

```python
assert dedicated_per_1k / cloud_per_1k == pytest.approx(
    comparison.breakeven_requests / comparison.requests, rel=1e-9
)
```

> **可以带走的判断**：一份成本报告里至少要有两个**互相可推导**的数字。
> 只有一个结论数字的报告，错了也没人知道——**一个能解释另一个的数字，
> 才值得被相信。**

#### 4. 为什么吞吐没有缺省值，却仍出现 250

因为这两件事的性质不同：

| | 是什么 | 能不能给缺省 |
|---|---|---|
| GPU 时价（$1.006/h） | **外部事实**（云厂商的公开定价） | 能给：核对后写进常量并注明出处 |
| 吞吐（token/s） | **本机测量结果**（取决于模型、量化、批大小、序列长度） | **不能**：公开资料给不出"你这套配置"的数字 |

但 API 端点需要一个可运行的缺省值，否则每次调用都要先把所有参数填满。
处理方式是把它做成**一个显式的占位值**，并且在三处点名它：

```text
配置项注释        "这个数没有权威缺省值：必须在本机的部署上量一遍再填"
请求体 docstring   "是待替换的占位值——请填入本机实测的吞吐，否则盈亏平衡点不可信"
限制清单第 1 条    "本课程没有真实 GPU：…吞吐 tokens_per_second 是**配置项而非实测值**——
                   没在本机量过吞吐的盈亏平衡点不可信"
```

这是"缺省值"与"标准值"的一次区分：**给一个能跑起来的缺省值是工程需要，
把它当成结论则是一种自欺。** 本课选择"给缺省值但到处标注它是占位值"，
而不是"不给缺省值"（那会让端点在没有实测数据时完全不可用）。

class FixedLLM(BaseLLM):
    """要么永远返回固定文本、要么永远抛错的叶子模型."""

    def __init__(self, reply: str = "ok", *, error: str = "") -> None:
        self.reply = reply
        self.error = error
        self.calls = 0

    def chat(self, messages: list[Message], temperature: float = 0.7, max_tokens: int = 1024) -> str:
        self.calls += 1
        if self.error:
            raise RuntimeError(self.error)
        return self.reply

    def stream(
        self, messages: list[Message], temperature: float = 0.7, max_tokens: int = 1024
    ) -> Iterator[str]:
        yield self.chat(messages, temperature=temperature, max_tokens=max_tokens)

    # 三处一致（绑定版本就是注册表 head）→ passed 与 consistent 同时为真
    ok = verify_binding(binding, good, head=version)
    assert ok.passed is True and ok.consistent is True
    assert ok.blocking_failures == [] and ok.warnings == []

    # 服务名不符
    wrong_name = ServedEndpoint(
        name="smart-research-other", base_model=BASE_MODEL, adapter_short_hash=ADAPTER[:12]
    )
    report = verify_binding(binding, wrong_name)
    assert [item.name for item in report.blocking_failures] == ["serving_name"]
    assert report.passed is False

    # 适配器哈希不符（adapter_dir 指到了旧目录）
    stale = ServedEndpoint(
        name="smart-research-qwen3-8b", base_model=BASE_MODEL, adapter_short_hash="deadbeef0000"
    )
    report = verify_binding(binding, stale)
    assert [item.name for item in report.blocking_failures] == ["adapter_hash"]

    # 严格模式下"必须部署 head"才阻塞
    newer = ModelVersion(
        triple=VersionTriple(
            base_model=BASE_MODEL,
            adapter_sha256="bbbb111122223333444455556666777788889999",
            dataset_fingerprint="8899aabbccddeeff",
        ),
        version="1.2.0",
        stage=STAGE_STABLE,
        artifacts={
            "adapter": "outputs/lora/adapters/adapter-final",
            "merged": "outputs/lora-merged",
        },
    )
    warn = verify_binding(binding, good, head=newer)
    assert warn.passed is True and warn.consistent is False       # 两个布尔量分开
    assert [item.name for item in warn.warnings] == ["registry_head"]
    strict = verify_binding(binding, good, head=newer, policy=BindingPolicy(require_registry_head=True))
    assert strict.passed is False

    # 降级只向一个方向
    both_dead = ModelSwitcher(
        FixedLLM(error="cloud down"),
        FixedLLM(error="gpu gone"),
        policy=TrafficPolicy(dedicated_ratio=1.0),
    )
    try:
        both_dead.chat([Message("user", "hi")])
    except RuntimeError as exc:
        assert "cloud down" in str(exc)
    else:  # pragma: no cover
        raise AssertionError("两侧都失败时竟然没有抛错")

    cloud = FixedLLM(reply="[云端] 答案")
    fallback = ModelSwitcher(
        cloud, FixedLLM(error="gpu gone"), policy=TrafficPolicy(dedicated_ratio=1.0)
    )
    assert fallback.chat([Message("user", "hi")]) == "[云端] 答案"
    assert fallback.fallback_count == 1
    assert fallback.dedicated_served == 0        # 它一次都没成功过
    assert fallback.cloud_served == 1

    # 云端失败**绝不**回落专属（反向降级两个故障叠加）
    reverse = ModelSwitcher(
        FixedLLM(error="cloud down"),
        FixedLLM(reply="[专属] 答案"),
        policy=TrafficPolicy(dedicated_ratio=0.0),
    )
    try:
        reverse.chat([Message("user", "hi")])
    except RuntimeError as exc:
        assert "cloud down" in str(exc)
    else:  # pragma: no cover
        raise AssertionError("云端失败时竟然回落到专属模型")
    print("3. 三处绑定与单向降级        ✓")

    comparison = compare_costs(

> 代码里有一处刻意的省略：**没有写任何"恒真占位断言"**。
> 像 `assert verify_binding(...) is not None` 这样的行永远为真，因此不保护
> 任何东西，只会让用例数看起来达标。本课反复用到的那句话在这里同样成立：
> **一条永远为真的断言不是保护，而是噪声**——它会让人以为存在某种未被
> 覆盖的情形，从而在别处写出多余的兜底代码。

#### 为什么"两个布尔量必须分开"值得单独断言

如果 `passed` 与 `consistent` 被合成一个布尔量（比如只保留 `passed`），
丢失的是**"我放行了，但我知道它不是 head"这一种状态**。它会具体影响
灰度发布里的**第 ① 步**：

```text
先部署、后切流量（或先给 5% 流量试跑）  →  部署的那一刻，head 仍然是旧版本
```

此时正确的结论是：

```text
这次部署可以放行（passed=True）
但它不是注册表 head（consistent=False）
→ 告警、记录、继续
```

合成一个布尔量之后只有两种可能，两种都是错的：

| 合成方式 | 灰度第①步的结果 | 后果 |
|---------|---------------|------|
| 取 AND（要求全部一致） | `passed=False` → 部署被拦下 | 灰度永远开不了头；团队被迫**先提升阶段再过校验**，门禁变成形式 |
| 取 OR（只看阻塞项） | `passed=True`，告警消失 | "线上部署了一个非 head 版本"这件事**从报告里彻底消失** |

第一种的代价在 day059 已经写过一次（"为了让门禁变绿而改数据"），
第二种的代价更隐蔽：**一个真实的观察值被一个恒真的门禁吞掉了**。

这与 day059 把门禁结果分成三类（阻塞失败 / 告警 / 跳过）是同一条思路：
**一个布尔量只能表达"能不能继续"，表达不了"我为什么继续"。**
