## 第一部分：选择题

### 第 1 题 —— B

```python
doc_id = sha256(规范化后的全文)[:16]                       # documents/types.py
def chunk_id_for(doc_id: str, strategy: str, index: int, text: str) -> str:
    payload = f"{doc_id}|{strategy}|{index}\n{text}".encode("utf-8")
    return hashlib.sha256(payload).hexdigest()[:16]        # chunking/types.py
```

`chunk_id` 的四个入参里，`doc_id` 由内容派生、`text` 由内容派生、`strategy` 与 `index` 由配置与位置派生——**文件名一个都没进去**。所以改文件名对两者都没有影响。

`C` 之所以错，是它把"内容身份"与"层级关系"搞混了：`chunk_id` 并不回答"这段内容属于哪份文档"，它回答"**这一块是谁**"（位置身份，向量库主键）；要恢复层级关系靠的是 `parent_doc_id` 这个元数据字段。`D` 错在：两者混用会同时丢掉"跨文档去重"与"同一段话出现两次时的区分"两种能力，而两种失效都不报错。

### 第 2 题 —— C

```python
MEASURER_CHARS = "chars"        # 1 个字符 = 1 个预算单位（项目默认）
MEASURER_TIKTOKEN = "tiktoken"  # 1 个 token（依赖本机词表缓存）
```

`config.chunking_measurer` 的默认值是 `"chars"`。选它不是因为"更准"，而是因为**更可复现**：`chunk_id` 是知识库的去重键，而 `tiktoken` 的可用性依赖本机是否有词表缓存——同一份文档在两台机器上切出两套 id，"这条知识为什么重复了两份"就变成一个查不出来的问题。

`A` 错（默认不是 token）；`B` 错（标点、数字、英文都算 1 个字符，"320 个汉字"只在"全是汉字且无标点"时才与 320 个字符重合）；`D` 错（`chars` 数的是字符，中文一个字是 3 个字节）。

### 第 3 题 —— B

过滤**必须早于排序**，这一点在 `vectorstore/flat.py` 里由两个私有方法的调用顺序钉死：

```text
_find_ids(where)     先用元数据把候选缩成一个 id 子集（这一步是"预筛"）
_ranked_ids(...)     再在这个子集里算分数、排序、取 Top-K
```

选 `A` 的代价是：Top-K 的名额会被无关记录挤占——库里 1000 条记录中只有 5 条属于 `handbook`，先排全库再筛之后，你很可能得到 0 条，而**库里明明有 5 条**。这个失败不报错，只是"检索效果看起来很差"。

### 第 4 题 —— B

四个 `dropped_*` 与四个旋钮的对应关系写在 `RetrievalResult.explain()` 的第三行里（实测输出，见第 14 题）：

```text
条数：3 / top_k=3（召回深度 9） —— 阈值切掉 3 条、每文档上限挤掉 2 条、
                                 top_k 截断丢掉 0 条、重排阈值切掉 0 条
        ↑ dropped_below_threshold       ↑ dropped_by_diversity
                              ↑ dropped_by_top_k        ↑ dropped_by_rerank
```

`dropped_by_diversity` 对应 `max_per_doc`（`retrieval_max_per_doc`）：它治的是"同一份文档的多段刷屏"。

### 第 5 题 —— B

`EMPTY_REASONS` 是封闭清单，且空结果**只给一个**原因（按优先级取第一个成立的）。两者处置动作完全不同：

```text
no_data        库本身是空的（合法状态）→ 先建索引（实测注记原文：库是空的（合法状态）：请先建索引）
filtered_out   过滤之后候选为零        → 放宽过滤条件（where / time_range），或确认字段名写对了
```

选 `C` 错：漂移不会产生 `no_data`，它进的是 `index_state.drift` 与 `notes`（默认只观测，不阻断）。

### 第 6 题 —— C

重排的窗口纪律：只对**前 N 条**打分，因此第 21~35 条**连重排分都没拿到**。它们不会"被排在后面"（那是 `A` 的误解——要排序就必须先有分数），也不会"被自动补默认分"（`D`）。

`B` 的前半句是对的（它们不会出现在重排后的名单里），但"必须进 `notes`"的是**这件事本身**：`rerank_hits` 会把"只对前 N 条打分"写成一条注记，因为只报"重排生效了"却不报"有一批条连分都没拿到"，等于把一次**有边界的改进**说成了一次**全面的改进**。

## 第二部分：简答题

### 第 7 题

因为**每一个数字都对应一个可执行的下一步动作**，合成之后就再也回答不了"该调哪个参数"这个问题：

```text
dropped_below_threshold 大 → 调 retrieval_min_score（或换更贴切的编码器）
dropped_by_diversity 大   → 调 retrieval_max_per_doc（同一文档刷屏）
dropped_by_top_k 大       → 调 retrieval_top_k 或调大 fetch_multiplier（深度不够）
dropped_by_rerank 大      → 调 retrieval_rerank_min_score（或关掉重排阈值）
dropped_hits（打包）      → 调 retrieval_max_context_chars / retrieval_per_hit_chars
```

合成一个 `dropped = 7` 之后，读报告的人只能猜；而"猜"在这个场景里必然表现为**盲目调参**：调了 `top_k` 没变化，再调 `min_score`，最后干脆把四个旋钮一起动——于是下一次实验的变量不止一个，收益再也归因不了。

一个反例能把这条纪律说得更清楚：如果只保留总数，`dropped_by_top_k=6`（深度不够，该调 `top_k`）与 `dropped_by_diversity=6`（同一文档刷屏，该调 `max_per_doc`）会**长得一模一样**，而两者的处置动作相反——一个是"多给名额"，一个是"少给名额"。

### 第 8 题

`index_version_id` 由"编码器身份（`provider` + `model` + `dimension`）+ 度量 + 后端 + 内容摘要"算出。加上时间戳之后会同时失效的三件事：

1. **可重算（可复现）**：版本号本应是"同一份内容任何时候算都得到同一个号"。加时间戳之后，"现在这份索引是哪一版"不再是内容的函数，而是构建时刻的函数——你无法用重算来验证"清单说的那一版就是我手上这一版"。
2. **增量判定**：`IndexPlan` 的差集（新增 / 更新 / 删除 / **未变**）依赖"同一内容对应同一身份"。若内容没变而版本号每次都变，`unchanged` 这一组就永远为空，增量构建退化成每次全量。
3. **回滚与血缘**：`IndexVersionStore` 的回滚沿**血缘**走。版本号一旦与内容解耦，"回滚到哪一版"就退化成"按时间倒序找上一个"，那样在"两次构建之间库被人工改过"的情形下会回滚到一个**从未存在过的一致状态**。

一句话：版本号是**内容的函数**，不是事件的函数。

### 第 9 题

护栏必须写在**渲染提示词之前**，因为"没调模型"与"调了但没答"是两件不同的事，而前者是**可判定的事实**（`llm_called=False`、`citations=()`、`check=None`），后者只是一段需要解释的文本。如果先渲染再判断，那次"本不该发生的提问"就已经真的发生了：提示词进了上下文、模型有机会自由发挥，而报告里只会留下"这次生成没有引用"——把一次**护栏生效**记成一次**生成失败**。

"用字符串判断兜底"会在这三种情况下静默失效：

1. **兜底文案改字**：`FALLBACK_NO_CONTEXT` 里加个动词、换个标点，判定立刻失效，而失效的样子恰好是"看起来一切正常"；
2. **模型自己说了一样的话**：`DECLINE_MARKERS` 那三条固定句式正是"模型自己拒答"的检测依据——也就是说，模型完全可能产出一段与兜底**字面相似**的答复，而它是一次**真的调用**；
3. **空回复**：`FALLBACK_REASON_EMPTY_REPLY` 那条路上 `answer` 是空串，字符串比较在空串上既可能误判为兜底，也可能让"这次为什么没答"无法统计。

代码里的对应关系是：`llm_called` 单独成为字段，判定用 `retrieval.is_empty`（结构判定），而不是"看 answer 等不等于某段文字"。

### 第 10 题

因为**文档里的一句话会过期，`notes` 里的那句话不会**。

`min_score` 在混合模式下只作用于向量路（BM25 没有绝对标度），而"看起来能调、实际不生效"的旋钮比没有旋钮更贵——它会持续制造一种虚假的确定性：有人把 `min_score` 从 0.5 调到 0.7，看到结果变化不大，于是得出"阈值对召回影响很小"的结论，而真相是这个旋钮**只动了半条链路**。

`notes` 防的是这类事故：**被忽略的参数必须跟着那一次结果一起被说出来**。三个具体差别：

```text
文档里写一句   跨版本、跨配置都成立 → 但无法回答"这一次到底生效了没有"
notes 里写一句 只在真的发生时出现   → 读报告的人看到的就是"这一次"
```

同一条纪律在 M6 里还出现在两处：重排窗口（`notes` 报"只对前 N 条打分"）与索引漂移（`notes` 报"这次可能少召回"）。三处共同的形式是：**降级与被忽略的参数，唯一的痕迹就是 `notes`**。

### 第 11 题

排查顺序（**顺序 = 链路的顺序，先出现的先怀疑**）：

```text
① 库与清单有没有数据？
   看 index_state.count_store / count_manifest / drift
   若 count_store == 0 → empty_reason 会是 no_data，处置是"先建索引"
   本例 candidates=0 而 filter_applied=true，说明问题不在库空，往下走

② 过滤条件把候选清空了吗？（本例的第一嫌疑）
   看 filter_applied（true）、query.where、query.time_range、candidates（0）
   candidates=0 且 filter_applied=true 是本例最直接的证据：
   "过滤之后一条候选都没有"——这正是 empty_reason=filtered_out 的定义

③ 候选非零而命中为零？→ 看 dropped_below_threshold（阈值 min_score）

④ 命中非零但条数不够？→ 看 dropped_by_diversity / dropped_by_top_k / dropped_by_rerank
```

**第一个该被怀疑的是过滤条件**（`where` 字段名写错、时间范围写反、或时间字段缺失被排除），第二个是**索引状态**（库为空 / 清单漂移导致候选本身不全）。

顺带一句：这一条记录里 `llm_called=false`、`fallback_reason="no_context"`、`check=null`，说明**生成侧完全不需要怀疑**——护栏按设计生效了，答案里那段话不是模型写的。这正是"每一层留下自己的数字"的收益：一次排查可以在第 5 步就结束，不必去读提示词。

### 第 12 题

**先别下结论——只看 `count=4` 与"金标准不在里面"是分不清"没抓到"与"没排上"的**。`candidates=6` 说明库里确实有 6 条候选，而 `count=4` 说明有 2 条被某一层去掉了（`count` 恒等于 `candidates` 减去各层减法的结果）。要区分，必须再看两个字段：

```text
dropped_by_top_k      > 0 → 有记录排在第 4 名之外被截断了 → 这是**排序/深度**问题
                          验证动作：把 top_k 从 4 调到 6 重跑，看 rag-006 是否出现
dropped_below_threshold > 0 → 有记录分数不够被切掉 → 这是**阈值**问题
                          验证动作：把 min_score 清掉重跑
若无重排：也要看 dropped_by_diversity（同一文档刷屏挤掉的）
若开了重排：还要看 rerank.window（窗口外的条连分都没拿到）与 dropped_by_rerank
```

如果这两个数字都是 0 而 `count` 仍比 `candidates` 小，那就该怀疑第三个旋钮（`max_per_doc`）或者"候选里有重复 id"这类更少见的情形——但**永远不要**在没看这几个数字之前断言"检索没抓到"。这也是 day066 把四道减法分开记账的直接收益。

补充一个判断技巧：把 `top_k` 临时调成 `candidates`（把整份名单都留在手里）。如果此时 `rag-006` 出现在名单里，就是**排序问题**；仍然不出现，才是**召回问题**（该回到第 ③④ 层：编码器、分块粒度、索引版本）。

### 第 13 题

三问的答案：

1. **有幻觉引用**：`invalid=[5]`。它的含义不是"多写了一个数字"，而是**指到了一份并不存在的依据**——编号 5 不在那次提示词的编号表里（提示词只给了 1..3）。这也是 `CitationCheck.record_id is None` 的那种行，它必须被单独统计进 `hallucination_rate`。
2. **`grounded=false` 是定义决定的**：`grounded = valid 非空 且 invalid 为空`。本例 `valid=[1,2]` 非空，但 `invalid=[5]` 非空，一个幻觉引用就把"接地"判为不通过。这不是苛刻——一段"两个引用正确、一个引用凭空捏造"的答案，对读的人来说**无法区分哪一句有依据**，因此不能算"可核对"。
3. **`coverage` 的口径**：`coverage = len(valid) / given = 2 / 3 = 0.6667`（题中给的值正是它）。分母是**给出去的片段数**（`given = len(valid) + len(unused) = 2 + 1 = 3`）。若改成"检索到的命中数 4"，读数会变成 `2/4 = 0.5`——这个读数错在：**第 4 条命中根本没进提示词**（它在打包时被预算从尾部丢掉，模型看不到它），把它算进分母等于让一次与模型无关的**预算决策**去惩罚生成侧的可核对率。

一句话记住：`given` 是"模型有机会用的条数"，`coverage` 是"模型真的用上了几条"，两者的分母必须是同一个口径。

逐项解释：

- **`fetch_k = 9`**：`top_k(3) × fetch_multiplier(3)`，封顶 `MAX_FETCH_K = 1000` 之后仍是 9。库里只有 8 条，所以 `candidates = 8`；
- **"阈值切掉 3 条"**：`min_score=0.5`，而样本上 `axis` 查询的 8 个分数是 `1.0 / 1.0 / 0.8 / 0.6 / 0.5 / 0 / 0 / 0`——后三条为 0 的被切掉；
- **"每文档上限挤掉 2 条"**：`max_per_doc=1`，剩下 5 条里有两条与已入选者同属一份文档，被挤掉；
- **`depth_hit_rate = 0.3333`**：`命中数 / 召回深度 = 3 / 9`。它衡量的是**深度定得准不准**，不是召回率；
- **`fill_ratio = 0.0754`**：预算 `2400` 字只用了 181 字左右——一份"预算远大于需求"的账。它同时也是"这次打包没有降级"的证据（`dropped_hits=0`、`truncated_hits=0`）。

**注释里的问题：把 `max_context_chars` 调到刚好放不下第 3 条时，检索的四条指标不会变，但哪一件事变了？**

答案是 **"进了提示词的召回率"**。实测把预算收到 `char_count - 1` 之后：

```text
上下文 3 条 → 2 条，被丢掉的是 c-c-02（dropped_hits=1）
```

检索侧的一切都没变（`fetch_k`、`candidates`、三个 `dropped_*`、最终 3 条命中逐字段相同），`recall@k` / `precision@k` / `RR` / `nDCG@k` 也一动不动——**因为那四个指标只看检索名单**。变的是"模型有机会看到几条"：如果金标准恰好是 `c-c-02`，那么这一次的召回率在报告里仍然是满分，而答案的依据里已经**没有它**了。

这就是明天 day071 要补的那个指标（**packed recall**）：金标准在名单里但不在提示词里，是一门**独立的失败**——它既不是检索的错、也不是生成的错，而是预算的错。今天先记住它的形状：

```text
retrieved_recall  检索名单里有没有它        ← day066~day068 的账
packed_recall     提示词里有没有它          ← day069 的 given / dropped_hits 的账
grounded          答案有没有可核对的引用    ← day069 的 valid / invalid 的账
```

### 第 15 题（护栏的证据）

```python
"""第 15 题参考解：空检索护栏的证据（用一个会抛异常的假模型）."""

from smart_research_agent.llm.base import BaseLLM, Message
from smart_research_agent.retrieval.pipeline import RagPipeline

class BoomLLM(BaseLLM):

    def chat(
        self,
        messages: list[Message],
        temperature: float = 0.7,
        max_tokens: int = 1024,
    ) -> str:
        raise AssertionError("护栏失效：检索为空时不允许调用 LLM")


retriever = Retriever(empty_store(), TableEmbedding(), default_top_k=3)
pipeline = RagPipeline(retriever, BoomLLM())
answer = pipeline.answer("什么是检索增强生成")

assert answer.llm_called is False
assert answer.citations == ()
assert answer.fallback_reason == "no_context"
assert answer.check is None

print("=== 断言全部通过 ===")
print(answer.summary_line())
print(f"empty_reason = {answer.retrieval.empty_reason}")
print("\n=== notes ===")
for index, note in enumerate(answer.notes, start=1):
    print(f"{index}. {note}")
```

三条注记的分工（回答第 4 问）：

```text
第 1 条  原因 —— 为什么为空（这里 empty_reason=no_data，且给了人话解释与第一处置动作）
第 2 条  护栏 —— 为什么没有调模型（把"没调"写成一句可以核对的纪律）
第 3 条  出路 —— 下一步能做什么（换说法 / 放宽过滤 / 确认索引版本）
```

这个"原因 → 护栏 → 出路"的三段式与本层另一处文案（`FALLBACK_NO_CONTEXT` 的三条建议）是同一条纪律：**"没有找到"必须跟一个下一步动作，否则它只是一次失败宣告。**

**注释里的问题：为什么必须用"抛异常的假模型"？**

因为要证明的是一个**否定命题**——"这次没有调用模型"。否定命题没有正面的观察对象：

- 看"答案像不像兜底话术"是**字符串判定**，兜底文案改一个字就失效（第 9 题已展开）；
- 看 `MockLLM.calls` 为空稍微好一些，但它证明的是"这个对象没被调用"，而不是"任何对象都不会被调用"——如果护栏写在了 20 行之后，只是恰好这次没走到，测试照样通过；
- 用一个**一旦被调用就抛异常**的假模型，等价于给"被调用"这件事装了一个报警器：只要护栏失效，测试立刻炸在 `AssertionError: 护栏失效`，而且炸点是**调用发生的那一刻**，不是断言失败的那一刻。

第四个断言 `answer.check is None` 也值得单独说一句：它的含义不是"核对没通过"，而是"**这次根本没走到生成那一步**"——`RagAnswer.__post_init__` 里专门校验了这一点，`check=None` 与 `grounded=False` 是两件不同的事。
