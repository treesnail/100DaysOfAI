## 第一章：工具调用的本质 —— LLM 的能力边界

### 1.1 LLM 到底"会"什么

在接入任何工具之前，先诚实地回答一个问题：**一个大语言模型，单独放在那里，能做什么、不能做什么？**

LLM 的本质是一个**条件概率模型**：给定前面的文本，预测下一个最可能的 token。它的全部能力都来源于训练数据中沉淀的统计规律。这带来三个天然的能力边界：

| 边界 | 具体表现 | 根源 |
|------|----------|------|
| **无实时信息** | 不知道今天的天气、此刻的股价、你内网系统里的数据 | 训练数据有截止日期，且不含你的私有数据 |
| **不会精确计算** | `137 * 284` 可能算错，长除法、对数更不可靠 | 数学结果是"背出来/猜出来"的，不是"算出来"的 |
| **无法作用于世界** | 不能真的发邮件、查数据库、读写你的文件 | 它只能输出文本，没有手和脚 |

第二点值得展开。为什么 LLM 连乘法都可能算错？因为对它来说，`137 * 284 = 38908` 和"床前明月光，疑是地上霜"没有本质区别——都是一串统计上常见的 token 序列。训练语料里出现过的算式它能"背"，没出现过的就靠"猜"。它没有执行乘法竖式的过程，只有一个"看着像正确答案"的生成过程。

> 思考题：既然 LLM 是"猜"答案的，为什么它算 `2 + 3` 几乎从不出错？  
> 因为短算式在训练语料里出现了无数次，统计信号极强。出错的概率随数字位数和运算步骤数指数上升——这恰恰说明它在做模式匹配而非计算。

### 1.2 工具是 LLM 的"外设"

突破边界的思路非常朴素：**LLM 不擅长的事，交给擅长的程序去做，LLM 只负责决策"什么时候做、用什么参数做"。**

一个绝佳的类比是计算机的外设：

```
        ┌──────────────────────────────┐
        │            LLM               │
        │   （相当于 CPU：负责决策）     │
        └──────┬───────────┬───────────┘
               │ 决定调用   │ 阅读结果
               ▼           ▲
        ┌──────────┐  ┌──────────┐  ┌──────────┐
        │ calculator│  │  search  │  │ database │  ...更多工具
        │ （外设1） │  │ （外设2）│  │ （外设3）│
        └──────────┘  └──────────┘  └──────────┘
```

CPU 不会自己去读磁盘扇区、不会自己往屏幕上画像素——它通过标准化接口指挥外设干活。同样，LLM 不需要自己会算乘法、会联网搜索，它只需要：

1. **知道有哪些工具可用**（工具的 name 和 description）；
2. **决定调用哪个工具、传什么参数**（结构化输出）；
3. **读懂工具返回的结果**（Observation），继续推理。

这就是"工具调用（Tool Use / Function Calling）"的本质：**LLM 出决策，代码出执行，二者通过契约接口协作。**

### 1.3 工具对 Agent 能力边界的扩展

没有工具的 LLM 应用，能力边界 = 模型权重里记住的东西。接入工具后：

```
纯 LLM：  用户 ──问题──▶ LLM ──猜测的答案──▶ 用户
                        （能力边界 = 训练数据）

Agent：   用户 ──问题──▶ LLM ──决定调用──▶ 工具 ──真实结果──▶ LLM ──可靠答案──▶ 用户
                        （能力边界 = 模型 + 所有工具能触达的世界）
```

每多接入一个工具，Agent 的能力边界就向外扩一圈：

- 接入 `calculator` → 精确计算不再是问题（今天）；
- 接入搜索工具 → 实时信息不再是问题（后续接入）；
- 接入数据库工具 → 私有数据不再是问题；
- 接入代码执行工具 → Agent 可以"自己写程序解决新问题"。

这也是为什么我们把工具层设计成**可插拔**的：今天一个 `CalculatorTool`，明天加十个工具，Agent 核心代码一行都不用改。要实现这种可插拔，前提是先定义好**所有工具都必须遵守的契约**——这就是第二章的主题。

## 第二章：抽象基类设计 —— 工具的四个契约

### 2.1 为什么不用鸭子类型

Python 社区有一句名言："如果它走起来像鸭子、叫起来像鸭子，那它就是鸭子。"按这个哲学，我们完全可以不定义基类——任何有 `name` 属性和 `execute()` 方法的对象都能当工具用：

```python
# 反例：鸭子类型，没有任何基类约束
class CalculatorTool:  # 不继承任何东西
    name = "calculator"

    def execute(self, expression: str) -> str:
        ...
```

代码能跑。但对一个要迭代 100 天、最终可能有几十个工具的项目，鸭子类型有三个致命伤：

1. **契约不可见**：新工具作者想知道"一个工具需要实现什么"，只能去翻已有工具的代码猜，或者去读 Agent 的调用代码反推。契约存在于"约定俗成"里，而不是代码里。
2. **错误暴露太晚**：如果新工具忘了实现 `description`，鸭子类型下要等到 Agent 运行时访问 `tool.description` 才报 `AttributeError`——可能是部署后、某个特定任务触发时。
3. **无法统一处理**：没有共同基类，就没法写 `isinstance(tool, BaseTool)` 校验，没法让 IDE 和 mypy 帮你检查，也没法在基类里给所有工具提供公共能力（比如今天写的 `to_schema()`）。

### 2.2 ABC：把契约写进代码

Python 的 `abc` 模块（Abstract Base Class，抽象基类）提供了一种机制：**把"必须实现什么"显式声明出来，并且在违反契约时尽早失败。**

```
           ┌─────────────────────┐
           │      BaseTool       │  ← 抽象基类：定义契约，不能被实例化
           │  name (抽象)        │
           │  description (抽象) │
           │  parameters (默认)  │
           │  execute (抽象)     │
           │  to_schema (公共)   │
           └─────────┬───────────┘
                     │ 继承
        ┌────────────┼────────────┐
        ▼            ▼            ▼
  CalculatorTool  SearchTool   DatabaseTool   ← 具体工具：实现契约
  （今天实现）    （后续接入）   （后续接入）
```

ABC 的关键性质：**包含抽象方法的类不能被实例化**。

```python
class BrokenTool(BaseTool):
    @property
    def name(self) -> str:
        return "broken"
    # 忘了实现 description 和 execute

BrokenTool()  # TypeError: Can't instantiate abstract class BrokenTool ...
```

错误在**实例化那一刻**就爆炸，而不是在 Agent 运行到一半时。这就是 day001 讲过的"失败要趁早（Fail Fast）"原则在接口设计上的体现。

> 思考题：ABC 在实例化时才报错，能不能在"类定义时"就报错？  
> 不能，Python 没有这种机制（Java 的编译期检查才可以）。但配合 mypy 静态检查，`mypy` 能在不运行代码的情况下发现"子类未实现抽象方法"——这就是 day001 配置 mypy 的回报之一。

### 2.3 四个契约分别服务谁

`BaseTool` 定义了四个契约，每一个都有明确的服务对象。理解"这个字段是写给谁看的"，是理解工具设计的关键：

| 契约 | 类型 | 服务谁 | 用途 |
|------|------|--------|------|
| `name` | 抽象属性 | **Agent 代码** | 唯一标识，LLM 输出 `Action: calculator` 时，Agent 用它做路由查找 |
| `description` | 抽象属性 | **LLM** | 自然语言描述，会被拼进 prompt，LLM 靠它判断"该用哪个工具" |
| `parameters` | 可覆盖属性 | **LLM + 调用方** | JSON Schema，告诉 LLM"这个工具吃什么参数" |
| `execute` | 抽象方法 | **Agent 代码** | 真正干活的入口，返回字符串结果给 LLM 阅读 |

这里最容易被忽视的是：**`description` 不是写给人类程序员的注释，是写给 LLM 的 prompt 素材。**

这带来一个反直觉的工程结论：**工具描述的写作质量直接影响 Agent 的智能程度。** 对比两种写法：

```python
# 差的描述：LLM 很难判断什么时候该用它
description = "计算"

# 好的描述：明确说出能力范围、语法、示例
description = "计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'"
```

LLM 读到后者，才能可靠地完成"用户问 15% 的小费是多少 → 这是一个数学表达式计算 → 调用 calculator，expression='158 * 0.15'"这条推理链。后续做工具多了你会发现：**调优工具 description 和调优 prompt 是同一件事。**

### 2.4 parameters 与 JSON Schema

`parameters` 用的是 **JSON Schema**——一种用 JSON 描述"数据应该长什么样"的行业标准格式：

```python
{
    "type": "object",
    "properties": {
        "expression": {
            "type": "string",
            "description": "要计算的数学表达式",
        }
    },
    "required": ["expression"],
}
```

逐字段拆解：

- `type: "object"`：这个工具的参数整体是一个对象（即一组键值对）；
- `properties`：列出每个参数的名字、类型、说明；
- `required`：列出哪些参数是必填的。

为什么用 JSON Schema 而不是随便一个字符串说明？因为它是**机器可解析的标准**：

1. OpenAI 等厂商的 function calling API 直接接受 JSON Schema 格式的工具定义；
2. 将来做参数校验时，有现成的 JSON Schema 校验库可用；
3. 它是 LLM 生态的"通用语"，MCP 协议（M2 阶段会学）也用它描述工具参数。

### 2.5 基类中的"免费午餐"：to_schema

注意 `BaseTool` 里有一个**不是抽象方法**的方法 `to_schema()`：

```python
def to_schema(self) -> dict[str, Any]:
    """导出工具 schema，用于拼入 LLM prompt 或 function calling."""
    return {
        "name": self.name,
        "description": self.description,
        "parameters": self.parameters,
    }
```

它把三个契约拼成一份完整的工具描述。因为所有子类都必须实现那三个契约，所以这个拼接逻辑**在基类写一次，所有子类免费获得**。这正是基类的另一个价值：除了"强制约束"，还能"沉淀公共逻辑"。

`to_schema()` 的输出明天（day005）会被工具注册表收集，后天（day006）会被拼进 ReAct 的系统提示词——今天的契约设计是在为整个链条铺路。

### 2.6 三种接口风格的横向对比

Python 里表达"工具契约"其实有三条路，都值得知道：

| 方案 | 约束时机 | 公共逻辑 | 适用场景 |
|------|----------|----------|----------|
| 鸭子类型（无基类） | 运行时访问属性才报错 | 无法沉淀 | 一次性脚本、demo |
| **ABC（本项目选择）** | 实例化时报错 + mypy 静态检查 | 可在基类写公共方法 | 需要"强制约束 + 公共实现"的框架层 |
| `typing.Protocol` | 仅静态检查（mypy），运行时零约束 | 无法沉淀 | 只做类型标注、不控制实现的库 |

`Protocol` 是"结构化子类型"：类不需要显式继承，只要结构上满足协议就算匹配，但纯靠 mypy 把关，运行时没有任何保护，也没法像 `to_schema()` 那样在基类里沉淀公共逻辑。对本项目"既要运行时强制、又要公共实现、还要派生 schema"的需求，ABC 是三个选项里唯一全部满足的。

## 第三章：安全求值 —— 为什么 eval() 是灾难

### 3.1 最简单的实现，最可怕的漏洞

实现一个"计算数学表达式"的工具，最容易想到的写法是一行代码：

```python
# 反例：极度危险的实现
def execute(self, expression: str) -> str:
    return str(eval(expression))
```

`eval()` 会把这个字符串**当作任意 Python 代码执行**。而工具的输入从哪里来？从 LLM 的输出来；LLM 的输出又由用户的问题驱动。也就是说：**用户通过自然语言，间接获得了在你的服务器上执行任意 Python 代码的能力。**

感受一下这条攻击链：

```
用户输入:    "帮我计算一下 __import__('os').system('rm -rf /important/data')"
                │
                ▼ LLM 忠实地把算式传给工具
LLM 输出:    Action: calculator
             Action Input: __import__('os').system('rm -rf /important/data')
                │
                ▼ eval() 原样执行
服务器:      数据被删除 💥
```

就算用户没有恶意，LLM 自己也可能"幻觉"出奇怪的表达式。`eval()` 对输入零设防，等于把服务器的 shell 交给了概率模型。

> 思考题：能不能用黑名单防御？比如拒绝包含 `import`、`os`、`system` 的输入？  
> 不能。黑名单是"列举已知的恶"，而恶的形式无穷无尽：`__builtins__`、字符串拼接绕过、getattr 动态访问……安全领域的铁律是**白名单优于黑名单**：不要"禁止坏的"，要"只允许好的"。

### 3.2 AST：先把代码变成"解剖图"

正确的思路分两步：**先解析，后甄别。**

第一步，用 Python 标准库 `ast`（Abstract Syntax Tree，抽象语法树）把表达式字符串解析成一棵树——代码的"解剖图"：

```
表达式 "2 + 3 * 4" 的语法树：

            BinOp(op=Add)
            ├── left:  Constant(value=2)
            └── right: BinOp(op=Mult)
                       ├── left:  Constant(value=3)
                       └── right: Constant(value=4)
```

每个节点是一个 Python 对象：`BinOp` 表示二元运算，`Constant` 表示常量，`Call` 表示函数调用，`Name` 表示变量名……`ast.parse()` 只做**语法解析，不做执行**——它把字符串变成结构化的树，让我们有机会逐个节点审查。

可以在交互环境里亲手看一眼这棵树（`ast.dump` 把树打印成文本）：

```python
>>> import ast
>>> print(ast.dump(ast.parse("2 + 3 * 4", mode="eval"), indent=2))
Expression(
  body=BinOp(
    left=Constant(value=2),
    op=Add(),
    right=BinOp(
      left=Constant(value=3),
      op=Mult(),
      right=Constant(value=4))))
```

注意两个细节：一是 `mode="eval"` 表示"这是一个表达式"（而不是语句序列），根节点是 `Expression`；二是整棵树里只有 `Expression / BinOp / Constant / Add / Mult` 五种节点——没有 `Call`、没有 `Name`、没有任何能"做事"的节点。**一棵纯算术树是天然无害的，危险全部来自白名单之外的节点类型。**

第二步，写一个递归函数遍历这棵树，**只放行白名单内的节点类型**：

- 放行：数字常量（`Constant`）、加减乘除乘方取余（`BinOp` 配 `_BIN_OPS` 中的运算符）、正负号（`UnaryOp`）；
- 拒绝：其他一切。函数调用？拒绝。变量名？拒绝。属性访问？拒绝。

恶意输入 `__import__('os').system('echo hacked')` 解析出来的树根节点是 `Call`（函数调用）——不在白名单里，直接抛 `ValueError`。**攻击面从"整个 Python 语言"收缩到"六种运算符加数字"**，这就是白名单的威力。

### 3.3 白名单求值的完整实现

`smart_research_agent/tools/calculator.py` 的核心是 `_safe_eval` 递归函数（[完整代码](../源码/smart-research-agent/smart_research_agent/tools/calculator.py)）：

```python
_BIN_OPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.Pow: operator.pow,
    ast.Mod: operator.mod,
}
_UNARY_OPS = {ast.UAdd: operator.pos, ast.USub: operator.neg}


def _safe_eval(node: ast.AST) -> float:
    if isinstance(node, ast.Expression):
        return _safe_eval(node.body)
    if isinstance(node, ast.Constant):
        if isinstance(node.value, (int, float)):
            return node.value
        raise ValueError("仅支持数字常量")
    if isinstance(node, ast.BinOp) and type(node.op) in _BIN_OPS:
        return _BIN_OPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _UNARY_OPS:
        return _UNARY_OPS[type(node.op)](_safe_eval(node.operand))
    raise ValueError("不支持的表达式")
```

设计要点逐条说：

#### （1）运算符查表，而非 if-elif 长链

`_BIN_OPS` 把"AST 节点类型 → 对应的运算函数"做成字典。要支持新运算符（比如 `//` 整除），只需要往字典加一行 `ast.FloorDiv: operator.floordiv`，求值逻辑一个字不用改。这是**开闭原则**（对扩展开放、对修改关闭）的一个微型示范。

#### （2）`type(node.op) in _BIN_OPS` 而不是 `isinstance`

这是一个防御性细节。`isinstance` 会被子类"骗过"——如果 AST 里出现一个继承自 `ast.Add` 的自定义节点（虽然在正常解析中不会发生，但防御性编程要考虑恶意构造的对象），`isinstance` 会放行。`type(...) in dict` 要求类型**精确匹配**，白名单边界更硬。

#### （3）递归天然处理优先级

注意 `_safe_eval` 里没有任何处理"先乘除后加减"的代码。为什么 `(2 + 3) * 4` 能算对？因为**优先级在 `ast.parse` 阶段就确定了**——解析器生成的树结构本身就编码了优先级：乘除节点永远在加减节点的下方（更深的位置），递归求值时自然是深层的先算。我们只是在"遍历并计算"一棵已经排好优先级的树。

```
"(2 + 3) * 4" 的树：        "2 + 3 * 4" 的树：
      Mult                        Add
     /    \                      /   \
   Add     4                    2    Mult
  /   \                               /   \
 2     3                             3     4
```

#### （4）错误不抛出，而是作为结果返回

`execute` 方法把异常捕获后转成字符串：

```python
def execute(self, expression: str = "", **kwargs: Any) -> str:
    try:
        result = _safe_eval(ast.parse(expression, mode="eval"))
    except (SyntaxError, ValueError, ZeroDivisionError) as exc:
        return f"计算失败: {exc}"
    return str(result)
```

为什么不把异常抛给调用方？回忆第一章的协作图：**工具的返回值是给 LLM 读的 Observation。** "计算失败： 不支持的表达式"这个字符串返回给 LLM 后，它有机会自我纠错（"上次表达式不合法，我换个写法重试"）。异常抛出去会炸掉整个 Agent 循环；错误信息返回去则变成了 LLM 的学习信号。**在 Agent 系统里，工具的错误信息是 prompt 的一部分，不是事故。**

### 4.2 BaseTool 完整实现

[完整代码](../源码/smart-research-agent/smart_research_agent/tools/base.py)：

```python
"""工具抽象基类."""

from __future__ import annotations

from abc import ABC, abstractmethod
from typing import Any


class BaseTool(ABC):
    """所有 Agent 工具的抽象基类.

    契约：
      - name: 工具唯一标识，Agent 用它路由调用
      - description: 给 LLM 阅读的自然语言描述
      - parameters: JSON Schema 形式的参数说明
      - execute: 执行入口，返回字符串结果
    """

    @property
    @abstractmethod
    def name(self) -> str:
        ...

    @property
    @abstractmethod
    def description(self) -> str:
        ...

    @property
    def parameters(self) -> dict[str, Any]:
        return {"type": "object", "properties": {}}

    @abstractmethod
    def execute(self, **kwargs: Any) -> str:
        ...

    def to_schema(self) -> dict[str, Any]:
        """导出工具 schema，用于拼入 LLM prompt 或 function calling."""
        return {
            "name": self.name,
            "description": self.description,
            "parameters": self.parameters,
        }
```

几个实现细节：

- **`@property` + `@abstractmethod` 叠用**：`name` 和 `description` 是属性不是方法。顺序必须是 `@property` 在上、`@abstractmethod` 在下，语义是"这是一个必须被子类实现的抽象属性"。
- **`parameters` 有默认实现**：返回一个空参数的 schema。因为"无参数工具"是合理的（比如一个"获取当前时间"的工具），给默认值可以让简单工具少写代码；需要参数的工具（如计算器）覆盖它即可。这是契约设计中的**合理默认**原则：强制实现的应该是最小集合。
- **`execute(**kwargs)` 用关键字参数**：因为参数列表由 `parameters` schema 动态定义，基类无法预知具体参数名，用 `**kwargs` 保持通用。具体子类可以收窄签名（如计算器的 `expression: str = ""`）。

### 4.3 CalculatorTool 的契约实现

[完整代码](../源码/smart-research-agent/smart_research_agent/tools/calculator.py)，契约部分：

```python
class CalculatorTool(BaseTool):
    """算术计算工具."""

    @property
    def name(self) -> str:
        return "calculator"

    @property
    def description(self) -> str:
        return "计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'"

    @property
    def parameters(self) -> dict[str, Any]:
        return {
            "type": "object",
            "properties": {
                "expression": {
                    "type": "string",
                    "description": "要计算的数学表达式",
                }
            },
            "required": ["expression"],
        }
```

对照第二章的表格自查一遍：name 给 Agent 路由用（简短、唯一、蛇形命名）；description 给 LLM 阅读用（说清能力范围+示例）；parameters 是标准 JSON Schema；execute 返回字符串。四个契约各司其职。

### 4.4 测试：把安全承诺变成可执行验证

第一天的教程说过"测试是可执行文档"。对计算器工具，我们要验证三类行为：

[完整代码](../源码/smart-research-agent/tests/test_calculator.py)：

```python
class TestCalculator:
    @pytest.mark.parametrize(
        ("expr", "expected"),
        [
            ("2 + 3", "5"),
            ("2 * 3 + 4", "10"),        # 优先级：先乘后加
            ("(2 + 3) * 4", "20"),      # 括号改变优先级
            ("10 / 4", "2.5"),          # 除法得浮点
            ("2 ** 10", "1024"),        # 乘方
            ("-5 + 3", "-2"),           # 一元负号
            ("7 % 3", "1"),             # 取余
        ],
    )
    def test_arithmetic(self, expr: str, expected: str):
        tool = CalculatorTool()
        assert tool.execute(expression=expr) == expected

    def test_rejects_code_injection(self):
        tool = CalculatorTool()
        result = tool.execute(expression="__import__('os').system('echo hacked')")
        assert result.startswith("计算失败")

    def test_rejects_syntax_error(self):
        tool = CalculatorTool()
        assert tool.execute(expression="2 +").startswith("计算失败")

    def test_schema_export(self):
        schema = CalculatorTool().to_schema()
        assert schema["name"] == "calculator"
        assert "expression" in schema["parameters"]["properties"]
```

三组测试对应三类承诺：

| 测试 | 验证的承诺 |
|------|-----------|
| `test_arithmetic`（7 组参数化用例） | 功能正确：四则运算、优先级、括号、一元符号 |
| `test_rejects_code_injection` | **安全承诺**：恶意代码注入被拒绝——这是今天最重要的一条测试 |
| `test_rejects_syntax_error` | 健壮性：残缺表达式不崩溃，返回可阅读的错误 |
| `test_schema_export` | 契约完整性：schema 导出符合 day005 注册表的预期格式 |

特别说明 `test_rejects_code_injection` 的断言方式：我们断言 `result.startswith("计算失败")` 而不是断言抛异常——因为设计上错误就是以字符串形式返回给 LLM 的（见 3.3 第 4 点）。**测试要锁定的是"对外行为"，不是内部实现。**

## 第五章：明日预告 —— 从"一个工具"到"工具生态"

今天我们有了第一个工具，但 Agent 还没法真正使用它。还缺两块拼图：

1. **工具注册表（day005）**：工具有了几十个之后，Agent 怎么知道有哪些可用？`ToolRegistry` 提供注册、查重、按名查找、批量导出 schema 的能力——就是工具的"插线板"。
2. **接入 ReAct 循环（day006）**：`ReactAgent.run()` 目前还是 `NotImplementedError`。day006 我们会实现完整的 `Thought → Action → Observation` 循环，让 LLM 通过今天的 `BaseTool` 契约真正调用 `calculator`。

回头看今天的抽象设计为什么重要：day006 的 Agent 循环只会面向 `BaseTool` 编程——它不知道也不关心有 `CalculatorTool` 这个类，只认 `name`、`description`、`parameters`、`execute` 四个契约。**这正是抽象的全部意义：让上层逻辑与下层实现解耦，使系统可以逐日生长。**

## 第六章：今日总结

| 主题 | 核心结论 | 落地位置 |
|------|----------|----------|
| 工具调用本质 | LLM 出决策、代码出执行；工具是 LLM 的外设，每接入一个就扩展一圈能力边界 | 第一章 |
| ABC 设计 | 契约显式化、失败要趁早、公共逻辑沉淀在基类 | `tools/base.py` |
| 四个契约 | name→Agent 路由；description→LLM 阅读（是 prompt 素材！）；parameters→JSON Schema；execute→返回字符串给 LLM | `tools/base.py` |
| eval() 危害 | 把任意代码执行能力间接交给用户与模型幻觉；黑名单防不住，白名单才行 | 第三章 |
| AST 白名单 | 先解析为语法树（不执行），再递归只放行数字与六种运算符；优先级由树结构天然保证 | `tools/calculator.py` |
| 错误设计 | 工具错误以字符串返回作为 Observation，成为 LLM 的纠错信号，而不是炸掉循环的异常 | `CalculatorTool.execute` |
| 测试 | 参数化覆盖运算正确性，独立用例锁定"拒绝代码注入"这条安全承诺 | `tests/test_calculator.py` |

一句话总结：**今天的 `BaseTool` 看起来只有四个契约，但它定义了未来 96 天里所有工具加入这个系统的"入境协议"。**
