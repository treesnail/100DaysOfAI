## 第一部分：选择题

### 第 1 题（Agent 评估的难点）

以下哪一项**不是** Agent 评估相比单轮输出评估特有的难点？

- A. 评估对象是多步轨迹，需要记录工具调用序列与步数
- B. 存在大量"部分正确"的中间态（过程对结果错、结果对过程错）
- C. Agent 与环境交互，环境反馈变化会导致评估不可重复
- D. 参考答案可能不唯一，需要模糊匹配判定

### 第 2 题（步数效率计算）

某任务的 `expected_tools = ["web_search", "calculator"]`，Agent 实际走了 6 步后给出正确答案。这条轨迹的步数效率是多少？

- A. 0.5
- B. 0.33
- C. 0.67
- D. 1.0

### 第 3 题（工具正确性子项）

某任务期望工具序列为 `["web_search", "calculator"]`，Agent 实际调用了 `["calculator", "web_search"]` 并成功完成任务。关于这条轨迹的 `tool_accuracy` 各子项，正确的是：

- A. f1 = 1.0，order = 1.0
- B. f1 = 0.5，order = 1.0
- C. f1 = 1.0，order = 0.5
- D. f1 = 0.5，order = 0.5

## 第四部分：编程题

### 第 10 题（新增"参数正确率"指标）

教程第三章的思考题指出：现有指标漏掉了一种失败形态——**Agent 调对了工具，但传错了参数**（`Action Input` 错误）。请动手补上这个维度：

**功能要求**：

1. 给 `AgentRunTrace` 增加字段 `expected_inputs: list[str]`（期望的工具参数序列，与 `expected_tools` 等长、按下标一一对应），并同步扩展 `AgentRunTrace.tool_calls` 的采集：`AgentEvaluator._run_case` 中从 `agent.history` 里同时提取 `action_input`，新增轨迹字段 `tool_inputs: list[str]`。
2. 在 `evaluation/agent_eval.py` 新增指标函数 `input_accuracy(traces) -> float`：对每条轨迹，将实际参数序列与期望参数序列按下标逐位比对（字符串相等记 1 分），单轨迹得分 = 匹配位数 / 期望参数个数（期望为空且实际也为空记 1.0），返回所有轨迹的平均分。
3. 把该指标加入 `AgentEvaluator.evaluate` 的 `metrics` 字典（键名 `input_accuracy`），并在 `report.py` 的指标总览表中加一行。

**测试要求**（写进 `tests/test_agent_eval.py`）：

- 手算用例：构造两条轨迹（一条参数全对、一条一半对），断言 `input_accuracy` 的平均值正确。
- 数据集扩展：给 `task-01` 加上 `"expected_inputs": ["2 + 3 * 4"]`，端到端断言 `input_accuracy == 1.0`（该任务的 mock 脚本参数本来就正确）。

**提示**：

- `ReActStep` 已有 `action_input` 字段，`agent.history` 里拿得到，无需改 Agent 代码。
- 逐位比对对"顺序错了但参数都对"的轨迹会给 0 分——这正是它和 order 分的区别：一个管"调没调对参数"，一个管"工具顺序对不对"。想一想这两种度量在什么轨迹上会出现分歧。
