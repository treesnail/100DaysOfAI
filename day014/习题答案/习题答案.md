## 第一部分：选择题

### 第 1 题

**答案：B**

解析：`ShortTermMemory._truncate()` 的逻辑是：把消息分拣为 system 与非 system 两堆，system 钉在头部永不淘汰，非 system 部分只保留**最新的** `keep = max_messages - len(system_msgs)` 条（`others[-keep:]`）。容量 4 = 1 条 system + 最新 3 条 user，最老的 2 条 user 按 FIFO 丢弃。A 把淘汰方向弄反了（FIFO 丢最老不是最新）；C 违反"system 永不淘汰"铁律——system 是行为契约，丢了它模型会忘记输出格式与工具清单；D 错在超容量不抛异常，而是静默截断（`max_messages < 2` 才会在构造时抛 `ValueError`）。

### 第 2 题

**答案：B**

解析：Embedding 向量的"方向"承载语义，"长度"往往只反映文本长度、词频等噪声。余弦相似度 `dot / (|a|·|b|)` 只度量方向夹角，天然把长度噪声除掉；欧氏距离会被向量模长带偏——一篇长文档和一句短查询即使语义相同，欧氏距离也可能很远。A 错，余弦并非无条件更快（归一化后它才退化为点积）；C 错，欧氏距离在高维完全可算，问题是高维下距离趋同（维度灾难）；D 错，余弦值域是 [-1, 1] 不是 [0, 1]。

### 第 3 题

**答案：B**

解析：这是 `parse_plan` 四道防线中的第一道：`find("[")` 找第一个左括号、`rfind("]")` 找**最后一个**右括号，截取中间片段——这样 JSON 前后的客套话被剥掉；随后 `json.loads` 这个权威解析器判定语法合法性（第二道防线）。A 错，提示词约束是"软约束"，LLM 是概率模型，容错解析才是"硬约束"兜底；C 错，实现里没有正则剔除中文；D 错，`json.loads` 对首尾多余的非 JSON 文本会直接抛 `JSONDecodeError`，必须先截取。

### 第 4 题

**答案：B**

解析：Reflexion 的本质是"语言形式的强化学习"：奖励信号（成功/失败）不更新参数，而是变成一段自然语言反馈进入下一轮上下文。模型权重一个数字都没变，变的是输入分布——这是它被归为"推理时技术"的原因。反思的对象必须是**完整轨迹**而不只是最终结果：只有看到 Thought/Action/Observation 序列，模型才能定位"第 3 步搜错了关键词"这类具体失误。A 错（无梯度更新）；C 错（与换模型无关）；D 错，反思重试必须有 `max_reflections` 式熔断——环境性失败（工具超时）和能力边界外的任务，反思一百次也治不了，只会无限烧钱。

### 第 5 题

**答案：C**

解析：LangGraph 的根基设计是"节点之间只通过 State 通信"：每个节点是接收 State、返回状态增量的纯函数；节点执行后框架合并状态，再由路由函数（`add_conditional_edges` 的 path_func）根据 State 决定走哪条边。只有这样，checkpointer 才能在每个节点后持久化快照、支持断点续跑与时间旅行调试。A 和 B 都架空了图的边界——一旦节点直接互调或走全局变量，状态就不再完整描述系统，持久化与重放全部失效；D 错，LLM 只在节点内部被询问，流转决策在代码（路由函数）手里。

## 第二部分：判断题

### 第 6 题

**答案：错**

解析：system 消息是**行为契约**（ReAct 格式要求、工具清单都在里面），与其他消息地位不对等：对话消息随时间贬值可淘汰，system 一旦丢失模型立刻"忘记自己是谁"，后续输出全面崩坏。所以截断策略的第一铁律是 system 钉在头部、永不淘汰——`_truncate()` 先把 system 分拣出来，FIFO 只作用于非 system 消息。

### 第 7 题

**答案：错**

解析：`MockEmbedding` 是 SHA-256 哈希伪向量：确定性、离线、可复现，但**没有语义**——哈希的雪崩效应决定了语义相近的文本得到的向量几乎正交。它只够验证"存取链路通了"（remember 之后 recall 返回了条数正确的结果），不能验证检索质量。要测"语义相近可被检索到"，要么用手工构造的向量直接喂 `InMemoryVectorStore`（绕过 embedding），要么用真实 embedding 服务。

### 第 8 题

**答案：错**

解析：两个方向的风险都要防。拆得太粗（1~2 个）等于没拆，子任务内部依然迷失方向；拆得太细（20+ 个）则每个子任务都要起一次 ReAct 循环（多次 LLM 调用），成本和延迟爆炸，且过细的拆分把"执行细节"混进了"计划"，本末倒置。3~6 个是经验甜点：**上限控制成本，下限保证拆解真实发生**。规划质量看的是粒度恰当与子任务可执行，不是数量。

### 第 9 题

**答案：错**

解析：交接物应该是**结构化、提炼过的结果**（如"收集到的资料文本"），不是完整 ReAct 历史。多 Agent 拆分的目的之一就是治"上下文稀释"——如果把研究员的全部 Thought/Action/Observation 原样塞给分析师，稀释问题只是换了个地方重演，还白白浪费 token。每个交接点都应该是一次信息压缩：下游只需要上游的**结论**，不需要上游的**心路历程**。同时这也保证了每个 Agent 的上下文干净、提示词纯粹。

## 第三部分：问答题

### 第 10 题

**参考答案**：

1. **只有短期记忆能做好**：当前会话内的多轮指代与衔接——用户第 3 轮说"那第二个方案呢"，必须靠会话内刚发生的消息历史才能理解"第二个方案"指什么；这种"正在进行的对话上下文"不需要入库检索，全量重放最直接。**只有长期记忆能做好**：跨会话、跨时间的知识取回——用户三周前说过"我对花生过敏"，早被 FIFO 淘汰，新会话的短期记忆更是一片空白；只有向量化持久存储 + 相关性检索能在此刻把它"复活"。

2. 两者管理的是**不同生命周期、不同取回逻辑**的信息：短期记忆管"刚才聊了什么"（会话级、按时间保留、全量重放），长期记忆管"很久以前但此刻相关的知识"（持久化、按相关性取回、top-k 注入）。只用短期记忆，旧知识永久丢失；只用长期记忆，每轮对话都要先检索才能理解上下文，既贵又可能漏掉"上一句话"这种显然相关但向量未必最近的依赖。互补而非替代。

3. day010 架构里子任务串行但彼此独立，"先收集资料，再基于资料写报告"这类有数据依赖的任务会断链。用长期记忆的解法：每个子任务完成后，把结果 `memory.remember(子任务结果)` 入库；下一个子任务的 ReAct 循环开始前，`memory.recall(当前子任务描述, top_k)` 取回相关历史结论，拼进 messages 注入上下文。数据流：`子任务i结果 → embed → 向量库 → 子任务i+1描述 → embed → 相似度检索 → top-k 文本 → 注入子任务i+1的上下文`。这正是教程第六章架构图中"记忆加持"那一层。

### 第 11 题

**参考答案**：

1. - **迷失方向**：`Plan` 把全局目标显式化、落地为程序可读的清单，执行中随时对照"我在为哪一步服务"，方向有计划牵引；
   - **步骤冗余**：已完成子任务在清单上可见，"哪些事做过了"有据可查，不会重复搜索；
   - **提前收场**：完成标准有计划兜底——清单上的子任务全部有结果才算完，查了两个框架就交卷会被清单挡住。

2. Reflexion 治的是 **Planner 治不了的"重复犯同样的错"**：Planner 防患于未然（执行前把方向摆正），但计划再好比避免不了执行层的具体失误（搜错关键词、用错工具参数）。没有反思时，确定性编排下同样的输入大概率走出同样的失败轨迹，重试一百次也没用；Reflexion 让 LLM 对失败轨迹归因、把教训写进记忆，下一轮带着"上次错在哪"重试。

3. 两者介入时机与视角正交：规划在执行**前**，视角是"全局目标 → 分解"，降低失败的**发生率**；反思在失败**后**，视角是"历史轨迹 → 归因"，提高失败后的**恢复率**。任何单一机制都有盲区：只规划不反思，一次环境性抖动就满盘皆输；只反思不规划，复杂任务连一份像样的初始轨迹都产生不了，反思也无的放矢。健壮系统 = 事前有预案 + 事后有复盘。

### 第 12 题

**参考答案**：

1. | 维度 | 手写循环的痛点 | 状态图的解法 |
   |------|---------------|-------------|
   | 流程可见性 | 编排逻辑散在各文件的 for/while 里，要知道"有哪些状态、何时走哪条路"得通读代码脑内拼图 | 流程是一张显式的图：节点 + 边 + 路由函数，可画可审 |
   | 中断恢复 | 进程崩溃从头再来；想人工审核中间结果没有插入点 | checkpointer 在每次节点执行后按 thread_id 存快照，断点续跑、可在节点间插入人工介入 |
   | 循环复用 | 每个模块自己写"循环 + 终止条件 + 异常处理" | 循环由框架统一驱动，终止条件由条件边表达 |

2. `MemorySaver` + `thread_id` 解锁：**断点续跑**（进程重启后用同一 thread_id 从中断处继续，长任务与反思重试因此可恢复）与**时间旅行调试**（取出历史任意状态快照检查"当时状态长什么样"，可观测性从日志级别升级到状态级别）。

3. 因为节点函数内部调用的还是既有组件：execute 节点里是 day006 的 `parse_react_output` 与 ReAct 单步逻辑、plan 节点里是 day010 的 `Planner`、reflect 节点里是 day011 的反思生成、记忆注入用的是 day008/009 的 `ShortTermMemory`/`LongTermMemory`。**被重构的只是"谁在何时调用谁"的编排层，业务逻辑一行没重写**——这正是"Agent 架构的演进是叠加而不是替换"的又一次验证。

### 第 13 题

**参考实现**（`tests/test_memory_review.py`）：

```python
"""短期记忆截断行为的三条承诺测试."""

import pytest

from smart_research_agent.llm.base import Message
from smart_research_agent.memory.short_term import ShortTermMemory


def _msg(role: str, tag: str) -> Message:
    return Message(role=role, content=f"msg-{role}-{tag}")


class TestTruncationPromises:
    def test_capacity_invariant(self):
        """承诺一：任何时刻长度不超过 max_messages."""
        mem = ShortTermMemory(max_messages=4)
        mem.add(_msg("system", "0"))
        for i in range(5):
            mem.add(_msg("user", i))
            assert len(mem.get_all()) <= 4  # 每次写入后立即检查不变量

    def test_system_pinned_and_fifo(self):
        """承诺二：system 钉在头部，最老的 user 被淘汰、最新的保留."""
        mem = ShortTermMemory(max_messages=4)
        mem.add(_msg("system", "0"))
        for i in range(5):
            mem.add(_msg("user", i))
        all_msgs = mem.get_all()
        assert all_msgs[0].role == "system"
        contents = [m.content for m in all_msgs]
        assert "msg-user-0" not in contents  # 最老的被 FIFO 丢弃
        assert "msg-user-4" in contents      # 最新的保留
        assert len(all_msgs) == 4

    def test_get_all_returns_defensive_copy(self):
        """承诺三：get_all() 返回副本，外部 append 不影响内部状态."""
        mem = ShortTermMemory(max_messages=4)
        mem.add(_msg("user", "0"))
        leaked = mem.get_all()
        leaked.append(_msg("user", "evil"))
        assert len(mem.get_all()) == 1  # 内部状态未被污染
```

**附加问答**：`others[-0:]` 中 `-0 == 0`，所以等价于 `others[0:]`——得到的是**整个列表**而不是空列表（负数切片里"0"没有负值形式）。因此 `_truncate()` 里 `keep == 0` 时必须显式走 `system_msgs[: self.max_messages]` 分支；若直接写 `others[-keep:]`，keep 为 0 时会把全部消息留下来，容量不变量瞬间被破坏。这是 Python 切片语法最著名的边角陷阱之一。

### 第 14 题

**参考实现**：

```python
"""长期记忆检索注入链路."""

from smart_research_agent.llm.base import Message
from smart_research_agent.llm.embedding import MockEmbedding
from smart_research_agent.memory.long_term import LongTermMemory
from smart_research_agent.memory.vector_store import (
    InMemoryVectorStore,
    VectorRecord,
)


def build_context_with_recall(
    memory: LongTermMemory,
    query: str,
    base_messages: list[Message],
    top_k: int = 2,
) -> list[Message]:
    """recall 取回相关记忆，拼成一条 user 消息插到 system 之后."""
    recalled = memory.recall(query, top_k=top_k)
    injection = Message(role="user", content="相关资料：" + "\n".join(recalled))
    result: list[Message] = []
    inserted = False
    for m in base_messages:
        result.append(m)
        if m.role == "system" and not inserted:
            result.append(injection)
            inserted = True
    if not inserted:  # 没有 system 消息时插到最前
        result.insert(0, injection)
    return result
```

**链路测试（MockEmbedding 验证"链路通"）**：

```python
def test_recall_injection_pipeline():
    memory = LongTermMemory(embedding=MockEmbedding())
    memory.remember("用户对花生过敏")
    memory.remember("用户偏好中文回答")
    base = [
        Message(role="system", content="sys"),
        Message(role="user", content="今晚吃什么"),
    ]
    ctx = build_context_with_recall(memory, "饮食注意事项", base, top_k=2)
    assert ctx[0].role == "system"
    assert ctx[1].content.startswith("相关资料：")  # 注入位置在 system 之后
    assert ctx[-1].content == "今晚吃什么"
```

**排序测试（手工向量验证检索质量，需 `import pytest`）**：

```python
def test_search_ranks_by_cosine():
    store = InMemoryVectorStore()
    store.add(VectorRecord(id="a", text="猫", vector=[1.0, 0.0]))
    store.add(VectorRecord(id="b", text="狗", vector=[0.9, 0.1]))
    store.add(VectorRecord(id="c", text="微积分", vector=[0.0, 1.0]))
    hits = store.search([1.0, 0.0], top_k=1)
    assert hits[0][0].text == "猫"
    assert hits[0][1] == pytest.approx(1.0)
```

**为什么不能在这一步用 MockEmbedding**：`MockEmbedding` 的向量由 SHA-256 哈希生成，哈希的雪崩效应保证语义相近的文本（"猫"/"狗"）得到的向量几乎正交——它**没有语义结构**。用它做排序断言，"猫"和"微积分"谁更近纯属碰运气，测试断言的是噪声而非行为。链路测试（recall 返回了条数正确的结果、注入位置正确）不依赖语义，可以用它；排序质量测试必须控制向量本身，所以要手工构造 `VectorRecord` 绕过 embedding。这一区分正是 day009 教程"机制 vs 语义"分层思想在测试侧的落地。

### 第 15 题

**参考实现**（`guess_graph.py` + `tests/test_guess_graph.py`）：

```python
"""最小 LangGraph 状态图：猜数字收敛."""

from typing import TypedDict

from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import END, START, StateGraph


class GuessState(TypedDict):
    target: int
    guess: int
    steps: int


def adjust_node(state: GuessState) -> dict:
    guess = state["guess"]
    if guess < state["target"]:
        guess += 1
    elif guess > state["target"]:
        guess -= 1
    return {"guess": guess, "steps": state["steps"] + 1}


def route(state: GuessState) -> str:
    return "done" if state["guess"] == state["target"] else "continue"


def build_app():
    graph = StateGraph(GuessState)
    graph.add_node("adjust", adjust_node)
    graph.add_edge(START, "adjust")
    graph.add_conditional_edges(
        "adjust", route, {"continue": "adjust", "done": END}
    )
    return graph.compile(checkpointer=MemorySaver())
```

```python
def test_guess_converges():
    app = build_app()
    result = app.invoke(
        {"target": 7, "guess": 1, "steps": 0},
        config={"configurable": {"thread_id": "t1"}},
    )
    assert result["guess"] == 7
    assert result["steps"] == 6  # 1→2→…→7 共 6 次调整
```

**运行要点**：每次 `adjust` 节点执行后，框架把返回的 dict 合并进 State，再调用 `route` 决定是回到 `adjust`（`"continue"`）还是到 `END`。注意 `steps` 的增量更新写法——节点返回的是"对状态的增量"，不是完整新状态。

**附加问答**：去掉 checkpointer 对**本次** invoke 的最终结果**没有影响**——状态在图的一次执行内本就在内存里流转。checkpointer 的价值体现在跨执行的场景：

- **断点续跑**：进程中途崩溃，用同一 `thread_id` 再 invoke 可从最近快照恢复，不必从头再来；
- **时间旅行调试**：事后取出任一历史快照检查"当时状态长什么样"；
- **人工介入（interrupt）**：在节点间暂停等待人工确认后再继续。

这正对应教程第五章：状态图把"流程可见、可恢复"从口号变成框架级能力，而代价是要理解 State 合并语义与路由函数——编排显式化从来都不是免费的。
