# day049 课后习题：参考答案

> 所有实测数字均来自 day048 快照（`day048/源码/smart-research-agent/`），本机 Python 3.10.11 + pytest 9.1.1，全量 **1124 例通过 / 覆盖率 96.44%**。

## 第一部分：选择题

### 第 1 题（PII 检测）

**答案：D**

D 的说法与 day044 的核心结论相反。审核器的命门是**误报**：一个动不动就把用户正常内容标红的审核器，一定会被关掉，而"被关掉的审核器等于不存在"。所以方向是**"宁可漏报的代价可控，也不能让误报率失控"**——这也是 Luhn 与 IPv4 值域约束存在的理由：它们不是为了"多抓"，而是为了**把假阳性压下去**。

A / B / C 都是 day044 的原话：纯正则只能描述形状；Luhn 把随机 16 位数字的误判率压到约 1/10；`999.999.999.999` 会被 `\d{1,3}` 判成合法 IPv4。

### 第 2 题（本地部署的显存口径）

**答案：C**

`overhead_ratio`（缺省 0.1）覆盖激活值、CUDA context 与显存碎片，所以估算值只作"能不能装下"的门槛判断，**不作精确承诺**。

- A 错：公式里的 `× 2` 是 **Key 与 Value 两份张量**，与训练无关。
- B 错：`q4_k_m` 属于 GGUF 的 k-quant **混合量化**（不同张量用不同位宽），工程上按平均值计，约 **4.5 bpw**；`q8_0` 约 8.5 bpw。
- D 错：KV 缓存是**推理**时随上下文增长的显存，长上下文场景下 KV 甚至可能超过权重（day045 的 `max_context_tokens` 就是反解它）。

### 第 3 题（六阶段流水线的顺序）

**答案：D**

"把成本归因移到缓存回写之后"**不是无害优化**。`_account` 阶段的语义是"读取这一次请求造成的 token 增量"。放在最后会带来两个问题：

1. **语义错位**：如果缓存回写抛异常，这一次请求的费用就永远没被记上（归因阶段根本不会被执行）；
2. **被测性质失效**：day046 的假时钟测试断言"满路径 13.0ms / 6 阶段"、"命中路径 7.0ms / 3 阶段（`guard/cache/moderate`）"——**阶段顺序是被断言观测的契约**，改顺序会让 `test_pipeline.py` 直接变红。这正是"顺序即策略"的含义。

A / B / C 都是 day047 与 day046 反复强调的三条约束。

### 第 4 题（成本归因与包装器）

**答案：A**

`ModelRouter` 与 `CachedLLM` 都**真持有自己的状态**（前者持有决策日志，后者持有缓存），它们挡在叶子前面，`getattr` 到不了叶子，所以必须显式回答"用量算谁的"——做法是暴露 `last_used_llm`。

- B 错：`_TimedLLMProxy` 只覆写 `chat`，其余属性经 `__getattr__` **全量透传**，用量、错误、状态天然穿透，**不需要为自己的存在做额外声明**。这是"看起来一样、实际不一样"的两种包装器。
- C 错：修法的正确方向是**让包装器说清楚"我替谁说话"**，而不是伪造 `usage_log`。伪造会引入"抄一份还是算一份"的语义混乱，且一旦内层是路由（`ModelRouter`）就抄错了对象。
- D 错：缓存命中路径**本来就不产生用量**（没有新的 `usage_log` 条目），所以归因结果为 0 是正确语义，不需要"补一笔"。`test_wrapper_accounting.py` 专门断言"第二次同问题命中缓存：`cost_usd == 0.0`、`len(mock.calls) == 1`"。

### 第 5 题（数据工程的三段管道）

**答案：D**

"去重两侧都做"是**错的**，而且是危险的错。

`DatasetCleaner.run` 的三阶段严格是 **清洗 → 规则 → 去重**，且去重只有一次，位置在最后。原因在 day048 教程里写得很直白：

> 先按规则把废样本丢掉，再对 survivors 取指纹，这样才能保证"保留的是首次出现的合法样本"，而不是被一个本该拒绝的样本抢先占位、把后面合法的重复项挤掉。

如果去重在清洗之前先做一次，那个本该被 `placeholder_output` / `unverified_source` 拒掉的样本会**先占住指纹位**，把后面一条合法的重复项判成 `duplicate` 丢掉——**结果是"坏样本留下了竞争名额，好样本被挤走"**，而报告里的 `drop_reasons` 看起来仍然"有归因"。

### 第 6 题（SFT 预算核算）

**答案：B**

逐项核算（本日实测）：

```text
micro-batches/epoch = 30 // 2 = 15（drop_last：不足一个 batch 的尾巴丢弃）
steps/epoch         = 15 // 4 = 3   （攒够 4 个 micro-batch 才做一次更新）
total_steps         = max(1, int(3 × 3.0)) = 9
warmup_steps        = int(9 × 0.03) = 0
effective batch     = 2 × 4 = 8 条/次更新
```

- A 错：`total_steps` **不是** `样本数 × epoch`，而是**优化器更新次数**（受 batch 与梯度累积约束）。
- C 错：`warmup_steps = 0` 是"比例取整"的**固有性质**，不是 bug。正确应对是"在小数据集上不要依赖 warmup"，而不是绕过参数——绕过它只会掩盖"这份数据的规模不足以谈 warmup"这个事实。
- D 错：梯度累积**不改变一次前向看到的样本数**，但**改变一次参数更新用到的样本数**（= `per_device × accum`），这才是 `effective_batch` 的意义：它与学习率是一对需要联调的参数。

## 第二部分：判断题

### 第 7 题

**答案：错。**

day044 的核心取舍恰好相反：**审核的落点放在路由函数里，而不是中间件里**。

理由是**语义可见性**：中间件只能看到 HTTP 报文，它无法知道"哪个字段是模型生成的文本（要审）、哪个是 `model` / `trace_id` 这类元信息（不该审）"。放在中间件里只能全量审，误报率会飙升。而且**Agent 的输出同样不能豁免**——`/agent/run` 返回的是 Agent 的最终答复，与 `/chat` 一样是模型生成的。

中间件在 day044 承担的是**另一件事**：`AccessLogMiddleware` 记录的是"网络接入层"的事实（路径、方法、状态码、耗时），它与 `AuditLogger` 记的业务语义事件互为补充。

### 第 8 题

**答案：错。**

两者语义**相反**，是 `keep_alive` 四语义里的两端：

| 取值 | 语义 | 用途 |
|------|------|------|
| `-1` | **永不卸载**（常驻） | 预热常驻模型，把首字延迟从"加载权重的十几秒"压到"纯推理的几百毫秒" |
| `0` | 请求返回后**立即卸载** | 用完即走的省显存策略，把显存让给别的服务 |

"省显存"只在 `0` 上成立；`-1` 恰恰是**占着显存不还**。二者都被保留，是因为它们服务的是两个相反的目标：**延迟优先**（`-1`）与**显存优先**（`0`）。`"5m"`（缺省）与 `"1h"` 是中间档。

### 第 9 题

**答案：错。**

判定下限是"门禁能不能长期用下去"的关键。执行时间在共享 CI 机器上**天然抖动**，没有下限的门禁会天天误报，而**天天误报的门禁一定会被关掉**——等于不存在。

这与 day031 的红队结论是同一条纪律：**安全门禁零容忍、质量门禁留裕度**。`PerformanceGuard` 用"当前值 / 基线值的倍数上限"（`perf_latency_tolerance = 1.5` 等）作为判定下限，正是为了把"变慢了"从主观感受变成**留了裕度、可持续执行的工程事实**。

### 第 10 题

**答案：错。**

这条规则**不是装饰**，而且去掉它训练集规模**会变**——变**大**（而且变大的是坏数据）。

`unverified_source` 规则的真实作用是**执行一条已经验证过的结论**：评估集 `data/eval/agent_tasks.jsonl` 里只标注了"期望调用哪个工具"，它的 `Final Answer` **并不保证正确**（`task-04` 把 7×8 答成 99）。`EvalTaskSource` 的做法是"仍然解析出来，但打上 `unverified` 标签"，**刻意保留到清洗阶段**，好让清洗报告里出现 `unverified_source` 计数——这个计数就是"这条结论在流水线里真的被执行了"的证据。

本日实测：`drop_reasons["unverified_source"] == 2`，与 `EvalTaskSource.unverified == 2` 严格对应。**去掉这条规则，那 2 条错误答案（含"7×8=99"）就会直接进训练集**；此时模型学到的不是"工具调用"，而是"算错了也一样是标准答案"。

### 第 11 题

**答案：错。**

`max_length` 应当由**数据的长度分位数**决定，而不是由基座模型的上下文窗口决定。两者的差距在真实数据上是数量级的：

```text
本日实测（day048 数据集，37 条，平均 84.24 token/条）：
  max_length=128   -> padding 占比 34.18%
  max_length=256   -> padding 占比 67.09%
  max_length=512   -> padding 占比 83.55%
  max_length=2048  -> padding 占比 95.89%
```

关键认知：**padding 的 token 一样要参与计算**。Transformer 的注意力对序列长度是平方复杂度，所以"设大一点保险"付出的不是零成本，而是接近 `(上限/实际长度)²` 的算力浪费。

正确做法是"**先画像、再定值**"：day048 的 `DatasetStats` 就是为这件事准备的。当前数据集输出上限 165 字、平均 84 token，因此 `max_length` 取 **128~256** 即可覆盖全部样本，取 512 只是为将来接入更长语料留余量。**超参要由数据说话，而不是由模型的参数量说话。**

### 第 13 题（SFT 的两个"结算点"）

1. 随后还要再做一步 **`eval_count = min(eval_count, n - 1)`**，目的是**避免出现"评估集之外没有训练数据"的退化切分**（把最后一条留给训练集）。配套地，`eval_ratio` 必须落在 `[0, 1)`：等于 1 会让训练集为空，小于 0 无意义，两者都在这里直接拒绝，而不是留到训练时报错。

## 第四部分：简答题

### 第 14 题（三套防线为什么必须都在请求路径上）

**（1）为什么"输出侧审核"必须发生在回复出去之前？**

因为**审的对象是"即将离开系统的文本"，而不是"系统内部的文本"**。一旦文本已经返回给用户，任何后续处理都无法撤回——用户已经看到了。这与 day046 的缓存顺序问题同构，但更直接：

- "先返回、再异步补审"得到的是一个**必然存在泄漏窗口**的系统，且这个窗口的宽度不受自己控制（取决于异步任务的排队延迟）。
- 更糟的是**它无法被测试观测**：day044 的测试断言的是"响应体里的 PII 已被脱敏"，而异步补审的响应体里是原文——测试会绿，用户会中招。
- 与之对照，day046 把审核放在**回写缓存之前**，正是同一条原则在"持久化"方向上的延伸：**一次性泄漏还能推给"模型说漏嘴"，写进缓存之后就变成系统在稳定泄露**。

所以正确的位置只有一处：**在生成完成之后、序列化返回之前**，也就是路由函数里。

**（2）day045 的本地部署为什么可以不改 `BaseLLM` 接口？**

因为 **Ollama 提供了 OpenAI 兼容端点**，而 `BaseLLM` 的契约本来就是围绕"OpenAI 风格的消息与响应"定义的。于是 `LocalModelLLM` 只需要：

1. 把 `base_url` 规范化（补/去 `/v1`，见 `normalize_base_url`）；
2. 把 `LocalModelSpec` 里的部署事实（模型名、上下文长度、是否支持视觉）映射到请求参数；
3. 其余（`chat` / `stream` / `chat_with_tools` / `get_model`）**继承既有实现**。

这就是"**协议兼容胜过 SDK 封装**"：接入一个后端不需要为它写一套新的胶水层，只要它说同一种协议。

"扩展抽象、零改动"要求的默认值形态是：**加"带默认值的具体方法/属性"，而不是加"抽象方法"**。day047 的横切表总结了这一点：

| 日 | 抽象改动 | 默认值 / 默认实现 |
|----|----------|------------------|
| day039 | `BaseLLM` 加流式 | `stream` 默认 `yield self.chat(...)` 整段返回 |
| day040 | `BaseLLM` 加视觉 | `supports_vision` 默认 `False`；`chat_vision` 默认抛 `NotImplementedError` |
| day041 | `EmbeddingProvider` 加批量 | `embed_batch` 默认逐条调用 `embed` |
| day045 | `BaseLLM` 加本地实现 | 新增 `LocalModelLLM`，但接口零变化 |

若加的是抽象方法，**所有既有实现会被同时逼着改造**（接口一改，`MockLLM`、`OpenAICompatibleLLM`、`ModelRouter`、`CachedLLM` 全部要动）；加带默认值的具体方法则让所有人自动获得"地板"，愿意深耕的实现再覆写拿全量收益。

**（3）归因错位 vs 归因落空**

先把两个词定义清楚：

- **归因错位**：账被记上了，但记到了**错误的对象**上（例如记在包装器头上，而真正产生 token 的是叶子）。day046 撞到的那个 500（`AttributeError: 'ModelRouter' object has no attribute 'usage_log'`）以及 day047 核对出的 `CachedLLM` 断链，都属于这一类。它的危险在于**"不报错，但账单失真"**——它伪装成正常返回。
- **归因落空**：这次请求**本来就不该产生账**（缓存命中，没有任何新的 `usage_log` 条目），结果确实是 0。这是**正确语义**，不是缺陷。

如果**把"成本归因"移到"缓存回写"之后**，对 day049 本日核对的那组数字会有两类影响：

1. **对缓存命中路径（`cost_usd == 0`）的影响**：数字本身仍然是 0，**结论不变**——因为命中的本质是"没有新的用量条目"，与阶段次序无关。
2. **对满路径（`cost_usd > 0`）的影响**：一旦"缓存回写"抛异常，归因阶段就不会被执行，**这次请求的费用会被彻底漏记**。而回写恰恰是最容易出问题的一步（磁盘满、权限错、序列化失败）。**把归因放在易失败的持久化之后，等于把账单押在了一个可能失败的步骤上**。

更根本的是：`test_pipeline.py` 用假时钟断言了"满路径 6 阶段 / 13.0ms"、"命中路径 3 阶段 / 7.0ms"，**阶段顺序本身是被断言观测的契约**。改顺序不只是"账可能错"，而是会让回归测试直接变红——这正是"顺序即策略、且策略必须写成测试"的落地。

> 一句话总结三问：**审核必须在返回前（因为泄漏不可撤回）、本地接入可以零改动（因为协议相同、抽象给了默认值）、归因必须在易失败步骤之前且必须落叶子（因为账单是审计的底线）。**

## 第五部分：编程题

### 第 15 题（参考答案）

```python
"""day049 #15 参考答案：SFT 长度预算与步数核算（只读脚本）."""

from __future__ import annotations

import tempfile
from pathlib import Path

from smart_research_agent.finetune import (
    build_dataset,
    compute_stats,
    dump_bundle,
    split_dataset,
)

bundle = build_dataset()
stats = compute_stats(bundle.examples)
train, eval_set = split_dataset(bundle.examples, eval_ratio=0.2, seed=42)


def length_budget(stats, *, candidates=(128, 256, 512, 2048)) -> dict[int, float]:
    """给定 max_length 候选，算 padding 占比（1 - 有效 token / 上限）.

    有效 token 用 avg_estimated_tokens 代表：数据集画像里的平均值就是
    "这条样本真正会用掉多少 token"的最佳估计。
    """
    budget = {}
    for cap in candidates:
        useful = min(stats.avg_estimated_tokens, cap)
        budget[cap] = 1 - useful / cap
    return budget


def step_budget(
    n_train: int,
    *,
    per_device_batch: int,
    grad_accum: int,
    epochs: float,
    warmup_ratio: float,
) -> dict[str, int]:
    """SFT 步数核算：与 transformers TrainingArguments 同名语义.

    - micro-batches = n_train // per_device_batch      （drop_last：尾巴丢弃）
    - steps/epoch   = micro-batches // grad_accum      （攒够才做一次更新）
    - total_steps   = max(1, int(steps_per_epoch * epochs))
    - warmup_steps  = int(total_steps * warmup_ratio)  （HF 的取整方式）
    """
    micro = n_train // per_device_batch
    per_epoch = micro // grad_accum
    total = max(1, int(per_epoch * epochs))
    return {
        "micro_batches_per_epoch": micro,
        "steps_per_epoch": per_epoch,
        "total_steps": total,
        "warmup_steps": int(total * warmup_ratio),
        "effective_batch": per_device_batch * grad_accum,
    }


print(f"训练集 {len(train)} 条 / 评估集 {len(eval_set)} 条")
print(f"平均 {stats.avg_estimated_tokens:.2f} token/条，输出长度上限 {stats.max_output_chars} 字")
for cap, waste in length_budget(stats).items():
    print(f"  max_length={cap:<5} -> padding 占比 {waste:.2%}（有效 token 占比 {1 - waste:.2%}）")

plan = step_budget(len(train), per_device_batch=2, grad_accum=4, epochs=3.0, warmup_ratio=0.03)
print("步数核算:", plan)
assert plan["total_steps"] == 9, plan
assert plan["warmup_steps"] == 0, plan   # 关键发现：小数据集上 warmup 退化为 0
assert plan["effective_batch"] == 8, plan
print("断言通过：total_steps=9、warmup_steps=0（退化）、effective_batch=8")

# warmup 真正生效的比例下界 = 1 / total_steps
total = plan["total_steps"]
print(f"warmup 生效的最小比例 = 1/{total} = {1 / total:.4%}"
```

**几处必须理解的细节**：

1. **`drop_last` 是隐藏的算术。** `30 // 2 = 15` 恰好整除，所以看不到丢弃；但若训练集是 31 条，`micro = 15`，**最后 1 条被丢弃**。真实训练框架（`DataLoader(drop_last=False)` 或 `Trainer` 的默认行为）**通常不丢弃尾巴**，而是让最后一个 batch 变小——这意味着 `total_steps` 的口算值可能比框架实际值少 1。**本课刻意采用 drop_last 口径，是为了让"步数"有一个纯算术的定义**；接真框架时要用 `math.ceil` 口径复核一次。
2. **`warmup_steps` 的取整方向是"向下"。** `int(9 × 0.03) = 0`、`int(33.75) = 33`——HF 的 `TrainingArguments` 在把 `warmup_ratio` 换算成 `warmup_steps` 时同样取整，所以这是**可对齐的真实语义**，不是本课自造的口径。
3. **`sleep` 式的"浪费比例"是估算，不是测量。** 它假设"每条样本都被 padding 到 `max_length`"——这只有在 `padding="max_length"` 时严格成立；`padding="longest"`（按 batch 内最长样本补齐）的实际浪费会小得多。**但方向不变**：`max_length` 设得远大于数据分布，浪费一定发生，且注意力是平方复杂度。所以结论"用分位数定值"依然成立。
4. **`tempfile.TemporaryDirectory()` 让落盘测试完全离线**：不污染仓库、不依赖已有文件，`assert 30 / 7` 直接复现了 day048 的切分结论——**这是"切分可复现"的第二重证据**（第一重是 `split_dataset` 两次调用结果相同）。

```python
"""day049 #16 参考答案：数据账闭合性核对（只读脚本）."""

from __future__ import annotations

from collections import Counter
from pathlib import Path

from smart_research_agent.finetune import EvalTaskSource, build_dataset
from smart_research_agent.finetune.collector import EVAL_TASK_SOURCE

bundle = build_dataset()
report = bundle.report

# 1. 载入量的账
loaded_seed, loaded_eval, loaded_redteam = 18, 7, 16
assert report.total == loaded_seed + loaded_eval + loaded_redteam == 41
assert report.kept == 37 and report.rejected == 4
assert report.rejected == sum(report.drop_reasons.values()), "每个丢弃都必须有归因"

# 2. 决策明细与 drop_reasons 逐项对齐
by_rule = Counter(d.rule for d in report.decisions)
assert by_rule["kept"] == report.kept == 37
assert all(by_rule[rule] == count for rule, count in report.drop_reasons.items())

# 3. 与 EvalTaskSource 的内部统计交叉核对（打标签 -> 被规则拦截 -> 计数 可闭合）
source = EvalTaskSource(Path("data/eval/agent_tasks.jsonl"))
source.load()
assert (source.kept, source.unverified, source.skipped) == (5, 2, 1)
assert report.drop_reasons["unverified_source"] == source.unverified == 2
assert bundle.source_kept[EVAL_TASK_SOURCE] == source.kept == 5

# 4. 安全样本占比（day048 结论：16/37 = 43.24%）
safety = sum(1 for e in bundle.examples if e.is_safety_example())
assert safety == 16
assert abs(safety / report.kept - 0.4324) < 0.001
print("全部断言通过")
```

**实测输出**：

```text
载入：seed 18 + eval 7 + redteam 16 = 41
清洗后：总计 41 | 保留 37 | 丢弃 4
决策明细计数: {'kept': 37, 'output_too_short': 1, 'placeholder_output': 1, 'unverified_source': 2}
EvalTaskSource: kept=5 unverified=2 skipped=1
安全对齐样本 16 条 / 共 37 条 = 43.24%

全部断言通过
```

**几处必须理解的细节**：

1. **`report.rejected == sum(drop_reasons.values())` 是最有价值的一条断言。** 它把"丢弃 4 条"从**总数**变成了**明细之和**。少了它，一个"丢弃了 4 条但只解释了 3 条"的实现仍然能通过所有其它断言——而那第 4 条就是**不明原因消失的数据**，正是数据工程里最危险的东西。
2. **`by_rule` 与 `drop_reasons` 的双向核对不是冗余。** 前者统计的是 `report.decisions`（逐条决策列表），后者是 `drop_reasons`（按原因的计数字典）。两者由 `DatasetCleaner.run` 在不同代码路径上维护（`decisions.append` vs `drop_reasons[name] += 1`），**因此可能漂移**。断言它们一致，等价于说"计数字典没有算漏，决策列表没有漏记"。
3. **`EvalTaskSource` 必须重新 `load()` 一次才能读到它的内部统计。** 因为 `bundle` 里的 `source_kept` 是**清洗后**的保留数（5 条），而 `source.kept / unverified / skipped` 是**载入阶段**的统计（5 / 2 / 1）。**两个数字的口径不同、层级不同，但它们能对上**——这才是"可闭合"的含义。`default_collector()` 内部创建的 `EvalTaskSource` 实例在 `collect()` 之后就不再暴露，所以核对时要自己 new 一个。
4. **`is_safety_example()` 是"标签可用"的证明。** 43.24% 这个数字之所以能算出来，是因为红队样本在采集那一刻就被打上了 `safety` 标签（`RedTeamSource.load` 里 `tags=(TAG_FROM_REDTEAM, TAG_SAFETY, category)`）。**治理元信息必须随样本落盘**，否则"这批数据里安全样本占多少"这个问题在事后是**补不回来的**——这也正是 `TrainingExample` 要带 `source` / `tags` / `license` 三个字段的理由。
