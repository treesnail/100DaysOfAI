## 第一章：MCP 给测试带来了什么新对象

### 1.1 从"测函数"到"测协议"

在 M1 阶段，我们的测试对象是普通 Python 对象：`parse_plan` 进一个字符串出一个列表，`CalculatorTool.execute` 进一个表达式出一个结果。调用发生在**同一个进程内**，参数是 Python 对象，返回值也是 Python 对象——类型错误靠解释器和 IDE 就能抓一大半。

MCP 改变了这一切。一旦能力走协议暴露，一次 `call_tool("calculator", {"expression": "1+2"})` 的完整路径变成了：

```text
Client 进程                              Server 进程
┌────────────────────┐                  ┌────────────────────┐
│ call_tool(name,    │                  │ FastMCP 路由到      │
│   arguments)       │                  │ calculator 函数     │
│       │            │                  │       ▲            │
│       ▼            │                  │       │            │
│ 构造 JSON-RPC      │ ──stdin 字节流──▶ │ 解析 JSON-RPC      │
│ Request 并序列化    │                  │ 校验参数 schema     │
│       │            │                  │       │            │
│       │            │ ◀─stdout 字节流── │ 序列化 Response    │
│       ▼            │                  │                    │
│ 反序列化、按 id     │                  │                    │
│ 配对、提取文本      │                  │                    │
└────────────────────┘                  └────────────────────┘
```

这条路径上出现了单元测试时代不存在的**新失效点**：

| 失效点 | 典型 bug | 同进程测试能发现吗 |
|--------|----------|--------------------|
| 序列化/反序列化 | 参数里的中文被错误编码；datetime 无法 JSON 化 | 不能（没经过序列化） |
| 协议握手 | Client 忘了 `initialize`，Server 拒绝后续请求 | 部分（取决于测试方式） |
| Schema 契约 | Server 声明的 inputSchema 与函数真实签名不一致 | 不能（同进程不校验 schema） |
| 传输通道 | 日志污染 stdout，JSON-RPC 帧被截断 | 不能 |
| 进程生命周期 | 子进程启动失败、退出时僵尸进程 | 完全不能 |

结论很清楚：**协议化把"接口"从 Python 签名升级成了"线上契约"，测试必须覆盖契约本身，而不只是契约背后的实现。**

### 1.2 一个具体的事故场景

假设我们给 `server.py` 的 resource 函数里加了一行 `print("debug:", doc_id)` 调试日志。同进程调用完全正常；但一旦走 stdio 传输，这行 print 会把非 JSON 字节写进 stdout——Client 的帧解析立刻崩掉，表现为"协议错误"而非"业务错误"，极难定位。

这个 bug 只有**真实 stdio 传输的测试**能抓到。这就是为什么本章后面要专门留一层端到端测试——它不是重复劳动，它守的是别的层守不住的边界。

### 1.3 包名红线：`mcp_server` 而不是 `mcp`

动手之前先立一条工程红线：项目内自建包的共享规格要求包名固定为 `smart_research_agent.mcp_server`，**绝不能命名为 `mcp`**。原因是 Python 的 import 机制：如果项目根目录下出现一个叫 `mcp` 的包，它会遮蔽（shadow）官方 `mcp` 包，`from mcp.server.fastmcp import FastMCP` 会导入到我们自己的空包，报出莫名其妙的 `ModuleNotFoundError`。这类"同名遮蔽" bug 的特点是报错位置远离根因，排查成本极高——**命名规范本质上是把一类 bug 消灭在发生之前**。

> 思考题：除了包名遮蔽，`python -m smart_research_agent.mcp_server.server` 这种启动方式还要求什么前提？提示：想一想子进程的 cwd 与 `sys.path`。

## 第二章：测试金字塔在 MCP 场景的落地

### 2.1 回顾金字塔，然后映射

day002 我们学过测试金字塔：底层大量快而稳的单元测试，中层适量集成测试，顶层少量慢而脆的端到端测试。MCP 场景下，这个金字塔映射为三层：

```text
            ╱  stdio 端到端   ╲      少量：真实子进程、真实管道
           ╱  （test_mcp_      ╲     测：传输、握手、进程生命周期
          ╱   integration.py）  ╲
         ╱  内存传输集成测试      ╲    适量：真实协议、内存管道
        ╱  （test_mcp_server_     ╲   测：三类能力的行为与错误路径
       ╱   unit.py）               ╲
      ╱  协议模型单元测试            ╲  大量：纯 pydantic 模型
     ╱  （test_mcp_protocol.py）     ╲ 测：契约结构、默认值、校验
    ╱──────────────────────────────────╲
```

三层的划分原则不是"按文件分"，而是**按传输成本分**：每一层引入一样真实的东西，也付出一样的代价。

### 2.2 底层：协议模型单测（test_mcp_protocol.py）

最底层测的是 [mcp_server/protocol.py](../源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py) 里的 pydantic 模型——JSON-RPC 2.0 的三种消息与三种能力描述符。

**测什么？** 三件事：

```python
class TestJsonRpcRequest:
    def test_default_jsonrpc_and_params(self):
        req = JsonRpcRequest(id=1, method="tools/call")
        assert req.jsonrpc == "2.0"      # 默认值：协议版本锁定
        assert req.params == {}          # 默认值：参数可省略

    def test_wrong_version_rejected(self):
        with pytest.raises(ValidationError):
            JsonRpcRequest(id=1, method="tools/call", jsonrpc="1.0")

    def test_round_trip(self):
        req = JsonRpcRequest(id="abc", method="resources/read", params={...})
        restored = JsonRpcRequest.model_validate(req.model_dump())
        assert restored == req           # 序列化往返无损
```

**为什么纯数据模型也值得单测？** 三个理由：

1. **模型即契约文档**。`jsonrpc: Literal["2.0"]` 这一行就是"本系统讲 JSON-RPC 2.0"的机器可执行声明。测试断言 `jsonrpc="1.0"` 被拒，等于把这条契约固化成了回归守卫——谁哪天手滑改了默认值，测试立刻红。
2. **round-trip 测试验证序列化无损**。`model_dump()` → dict → `model_validate()` 回来必须等于原对象。这是协议消息最基本的要求：发出去再收回来，信息一个比特都不能丢。
3. **这一层最便宜**。不碰网络、不起进程、毫秒级跑完。按照 FIRST 原则（day002），它应该是数量最多的一层——`test_mcp_protocol.py` 一个文件就贡献了 10 个用例。

### 2.3 中层：内存传输集成测试（test_mcp_server_unit.py）

中层引入一样真实的东西：**真实的 MCP 协议栈**——真实的握手、真实的 JSON-RPC 序列化、真实的 Server 路由。但把传输从"进程间管道"换成"内存流"。

关键工具是官方 SDK 提供的 `create_connected_server_and_client_session`：

```python
from mcp.shared.memory import create_connected_server_and_client_session
from smart_research_agent.mcp_server.server import app

class TestToolCapability:
    async def test_call_calculator_success(self):
        async with _connect() as session:
            result = await session.call_tool("calculator", {"expression": "2 + 3 * (4 - 1)"})
        assert result.isError is False
        assert result.content[0].text == "11"
```

它的原理：在内存里创建一对相连的流（类似 `os.pipe`，但纯内存实现），Server 挂在一头，ClientSession 挂在另一头。**除了没有真的起子进程，其余全是真的**——Client 发的每一个字节都经过 JSON-RPC 序列化，Server 真的解析、真的路由、真的执行 calculator。

**这一层测什么？** Server 暴露的每一个能力的 happy path 与 sad path：

| 能力 | happy path | sad path |
|------|-----------|----------|
| Tool | `2 + 3 * (4 - 1)` → `"11"` | `"1 +"` → 返回"计算失败"文本而非协议错误 |
| Resource | 读 `rag-intro` 返回知识库原文 | 读不存在的 doc_id 抛协议错误 |
| Prompt | 填 `topic`/`style` 参数得到完整提示词 | 省略可选参数时用默认值 |

注意 calculator 的 sad path 设计：表达式非法时，工具函数**内部容错**返回 `"计算失败: ..."` 文本，`isError` 仍为 False；而读不存在的资源时，Server 抛 KeyError，SDK 转成**协议级错误**，Client 侧收到异常。这两种失败语义完全不同——前者是"工具正常执行但结果为失败"，后者是"请求本身无法完成"。**测试把这两种语义的差异固定下来**，避免以后有人把错误处理改串了。

**为什么这一层不直接测函数？** 因为我们要验证的不只是"calculator 算对了"，还有"calculator 被正确注册为 MCP Tool、schema 正确生成、结果按协议格式封包"。直接调函数，这些全被绕过。

### 2.4 顶层：stdio 端到端测试（test_mcp_integration.py）

顶层引入最后一样真实的东西：**真实子进程**。Client 通过 `StdioServerParameters` 拉起一个 `python -m smart_research_agent.mcp_server.server` 子进程，通过 stdin/stdout 管道通信：

```python
class TestStdioEndToEnd:
    async def test_call_tool_over_stdio(self):
        async with McpClient.stdio() as client:
            text = await client.call_tool("calculator", {"expression": "(2 + 3) * 4"})
        assert text == "20"
```

`McpClient.stdio()` 内部构造的正是：

```python
StdioServerParameters(
    command=sys.executable,
    args=["-m", "smart_research_agent.mcp_server.server"],
    cwd=str(PROJECT_ROOT),
)
```

三个参数各有讲究：

- **`command=sys.executable`**：用当前解释器起子进程，保证子进程和测试用的是**同一个 venv**——依赖版本不一致这种坑被从根上排除。
- **`args=["-m", "..."]`**：以模块方式启动。这要求 [server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/server.py) 带有 `if __name__ == "__main__": main()` 守卫，`python -m` 执行模块时 `__name__` 恰好是 `"__main__"`，守卫内的 `app.run(transport="stdio")` 被触发。
- **`cwd=PROJECT_ROOT`**：子进程的工作目录设为项目根，`smart_research_agent` 包才能被 import 到。这就是第一章思考题的答案。

**这一层独有的价值**（前面两层都覆盖不到的）：

1. **传输通道真实性**：stdout 上每多一个字节都是协议帧，print 污染、编码错误只在这里现形。
2. **进程生命周期**：子进程能不能启动、退出时能不能干净关闭（`__aexit__` 里的清理逻辑），只有真起进程才能验证。
3. **启动方式验证**：`python -m` 能不能跑通、cwd 配置对不对，本质上是"部署形态"的测试。

**为什么这层只有 4 个用例？** 因为它慢（每个用例约 1 秒，要起进程）且脆（进程管理涉及操作系统）。金字塔的智慧在于：**行为细节在中层用便宜的方式穷举，顶层只抽查"链路是通的"**。calculator 的各种边界表达式在中层测，顶层只需确认"一次跨进程调用端到端成功"。

### 2.5 asyncio_mode = "auto"：消除样板

三层测试中后两层都是异步的。没有配置时，每个异步测试都要写 `@pytest.mark.asyncio`，纯样板。我们在 `pyproject.toml` 中开启自动模式：

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"
```

pytest-asyncio 看到 `async def test_...` 就自动按异步测试驱动。这是"让工具承担重复"的又一个实例——和 day002 用 fixture 消除环境准备样板是同一思想。

> 思考题：如果顶层端到端测试只在 CI 跑、本地开发只跑中下两层，这种"分层执行"策略的利弊是什么？提示：想想反馈速度与覆盖完整性的权衡。

## 第三章：Server 与 Client 的实现要点

### 3.1 Server：三类能力的 FastMCP 声明

[mcp_server/server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/server.py) 用三个装饰器声明三类能力，FastMCP 从函数签名自动推导 schema：

```python
app = FastMCP("smart-research-agent")

@app.tool(description="计算数学表达式，支持 + - * / ** % 与括号")
def calculator(expression: str) -> str:
    return _calculator.execute(expression=expression)

@app.resource("research://knowledge/{doc_id}", mime_type="text/plain")
def knowledge(doc_id: str) -> str:
    if doc_id not in KNOWLEDGE_BASE:
        raise KeyError(f"知识库中不存在文档: {doc_id}")
    return KNOWLEDGE_BASE[doc_id]

@app.prompt(description="生成一份调研报告的撰写提示词")
def research_report(topic: str, style: str = "正式") -> str:
    return f"请以{style}的风格撰写一份关于「{topic}」的调研报告，..."
```

两个设计细节值得注意：

**（1）Tool 复用而不是重写。** `calculator` 工具没有重新实现求值逻辑，而是委托给 day003 的 `CalculatorTool`——AST 白名单安全求值、错误容错全部继承。**MCP 层是"适配层"而非"新实现"**：它把已有的 Python 对象适配成协议能力，业务逻辑零重复。这也是 M2 重构的核心思想。

**（2）Prompt 参数从签名推导。** FastMCP 1.x 的 `@app.prompt()` 不接受显式的 arguments 列表，而是从函数签名推导：`topic: str` 无默认值 → 必填参数；`style: str = "正式"` 有默认值 → 可选参数。中层的 `test_list_prompts` 断言了 `required == ["topic"]`，把这个推导行为固定成了契约。

### 3.2 Client：连接器模式与能力发现

[mcp_server/client.py](../源码/smart-research-agent/smart_research_agent/mcp_server/client.py) 把"连接管理"和"能力调用"拆成两个类：

```text
McpClientConnector（异步上下文管理器）
  ├── __aenter__: 起子进程 → 建会话 → initialize → 能力发现 → 返回 McpClient
  └── __aexit__:  关会话 → 关管道 → 子进程随之退出

McpClient（能力调用门面）
  ├── tools / resources / prompts：能力发现的结果（描述符列表）
  ├── call_tool(name, arguments) -> str
  ├── read_resource(uri) -> str
  └── get_prompt(name, arguments) -> str
```

**为什么连接必须是异步上下文管理器？** stdio 连接持有三重资源：子进程、管道、会话。少了 `async with` 的确定性清理，测试跑完就留下僵尸子进程——在 Windows 上尤其麻烦，进程句柄泄漏会阻塞后续操作。`__aexit__` 按相反顺序逐层退出，保证资源必然归还。

**能力发现的结果为什么转成自己的描述符？** `discover_capabilities()` 把 SDK 返回的类型转成 `protocol.py` 里的 `ToolDescriptor`/`ResourceDescriptor`/`PromptDescriptor`。这叫**防腐层（Anti-Corruption Layer）**：上层代码依赖我们自己的稳定类型，官方 SDK 升级换字段名时，只有 `discover_capabilities` 一处需要适配，业务代码纹丝不动。

**结果提取的防御性。** SDK 的调用结果是 `content` 列表，元素可能是 text 也可能是 image 等类型。`call_tool` 用生成式过滤只拼接 text 块：

```python
return "".join(c.text for c in result.content if getattr(c, "type", None) == "text")
```

并且显式区分工具级失败与协议级失败：`isError=True` 时抛 `RuntimeError` 并带上工具名——**错误信息里带上上下文（哪个工具），是排障效率的倍增器**。

## 第四章：能力文档 —— MCP 生态协作的关键基础设施

### 4.1 问题：Server 提供了什么能力，谁知道？

设想另一个团队（或另一个 Agent）想接入我们的 MCP Server。它面临的第一个问题不是"怎么连"，而是"**连上之后有什么可用的**"。

答案是协议本身支持运行时能力发现——`list_tools` / `list_resource_templates` / `list_prompts`，我们的 Client 就是这么做的。但运行时发现有三个局限：

1. **要先能跑起来**：你得先装好依赖、配对参数、连上 Server，才知道它有什么。接入前的评估阶段根本做不到。
2. **结果不是给人读的**：JSON 列表没有排序、没有分组、没有"这个能力适合什么场景"的说明。
3. **无法版本化和评审**：运行时输出留不住，PR 评审时看不到"这个改动给 Server 新增了什么能力"。

能力文档（Capability Document）就是补这三块的：**一份人可读的、版本化的、静态可查阅的能力清单**。

### 4.2 为什么不能手写

直觉方案是手写一份 Markdown。问题是**文档与代码的漂移（drift）几乎是必然的**：代码改了工具参数，文档忘了同步；文档写着"支持 5 个资源"，实际只有 3 个。手写文档的保鲜期以天计。

我们的解法是 [scripts/dump_capabilities.py](../源码/smart-research-agent/scripts/dump_capabilities.py)——**让文档从运行中的 Server 里"跑出来"**：

```text
脚本启动
   │
   ▼
内存会话连接真实 Server（create_connected_server_and_client_session）
   │
   ▼
list_tools / list_resource_templates / list_prompts
   │
   ▼
把结果渲染成 Markdown 表格 ──▶ 写入 docs/mcp_capabilities.md
```

生成的文档见 [docs/mcp_capabilities.md](../源码/smart-research-agent/docs/mcp_capabilities.md)，核心内容：

```markdown
## Tools（工具）
| 名称 | 说明 | 参数（JSON Schema） |
|------|------|---------------------|
| `calculator` | 计算数学表达式，支持 + - * / ** % 与括号 | `expression`: string（必填） |

## Resources（资源）
| URI 模板 | 名称 | 说明 | MIME 类型 |
|----------|------|------|-----------|
| `research://knowledge/{doc_id}` | knowledge | 按 doc_id 读取内置知识库文档. | text/plain |
```

这个设计有三个层次的收益：

1. **零漂移**：文档内容来自真实 Server 的能力发现响应，Server 改成什么样，重新跑一遍脚本，文档就是什么样。不存在"忘了同步"。
2. **可进 CI**：流水线里加一步"运行脚本并 diff"，文档与代码不一致就构建失败——漂移从"必然发生"变成"无法合入"。
3. **天然的回归快照**：文档进版本库后，`git diff docs/mcp_capabilities.md` 就是"这个 PR 对 Server 能力面做了什么变更"的精确回答。

> 思考题：`dump_capabilities.py` 为什么要往 `sys.path` 里插入项目根目录？提示：直接 `python scripts/xxx.py` 运行时，`sys.path[0]` 是什么？

### 4.3 半自动 vs 全自动

注意我们把这一步称为"半自动"：生成是自动的，但**提交的时机由人决定**。为什么不做成 Server 启动时自动重写文档？因为那样文档会在任何一次本地调试时被意外改动，污染版本历史。"脚本随手可跑、提交人工把关"是自动化与可控性之间的恰当平衡。

### 4.4 M2 阶段收尾：代码整理清单

今天是 M2 最后一天，借能力文档的生成把 M2 的代码资产清点一遍：

| 资产 | 位置 | 守护它的测试 |
|------|------|-------------|
| 协议模型 | `mcp_server/protocol.py` | `test_mcp_protocol.py`（10 用例） |
| FastMCP Server | `mcp_server/server.py` | `test_mcp_server_unit.py`（9 用例） |
| stdio Client | `mcp_server/client.py` | `test_mcp_integration.py`（4 用例） |
| 能力文档 | `docs/mcp_capabilities.md` | 由 `scripts/dump_capabilities.py` 重新生成校验 |

至此全套 86 个测试通过、总覆盖率 92.46%（高于 `fail_under = 80` 的底线）。M2 阶段的验收标准——能力可发现、行为可验证、文档可追溯——全部达成。

## 第六章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 测试按传输成本分三层 | 每层引入一样真实的东西，付一样的代价 | 三个 test_mcp_*.py |
| 协议模型单测 | 模型即契约，round-trip 验证序列化无损 | `test_mcp_protocol.py` |
| 内存传输集成测试 | 真实协议栈 + 内存管道，行为穷举在这层 | `test_mcp_server_unit.py` |
| stdio 端到端只抽查链路 | 顶层慢且脆，行为细节交给中层 | `test_mcp_integration.py` |
| `sys.executable` 起子进程 | 保证子进程与测试同一 venv | `client.py` `McpClient.stdio` |
| 连接器 = 异步上下文管理器 | 子进程/管道/会话三重资源的确定性清理 | `client.py` `McpClientConnector` |
| 能力描述符防腐层 | 上层依赖自有类型，SDK 升级只改一处 | `discover_capabilities()` |
| 能力文档脚本生成 | 消灭文档-代码漂移；diff 即能力面变更 | `scripts/dump_capabilities.py` |
| 包名 `mcp_server` 非 `mcp` | 避免遮蔽官方包，把 bug 消灭在发生前 | 包命名规范 |

M2（MCP 应用开发）至此收官。回顾整个阶段：

```text

M2-D4~D5  FastMCP Server → MCP Client 集成       （实现两端）
M2-D6     Docker 部署                             （能上生产）
M2-D7     三层测试 + 能力文档                     （可验证、可协作）← 今天
```

下一阶段 R1 是复习缓冲日，建议把 M1（Agent 内核）与 M2（MCP 协议化）对照着复习：一个是"能力怎么产生"，一个是"能力怎么暴露与协作"。
