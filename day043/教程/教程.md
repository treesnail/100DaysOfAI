## 第一章：成本是智能体的"隐形账单"

### 1.1 为什么成本是可观测性里最硬的指标

day032 把可观测性拆成三支柱：指标（metrics）、追踪（tracing）、告警（alerting）。三者的一个共性是"度量难"：答案质量要 LLM-as-judge 打分（day026/027），任务完成率要人工标注（day030），连"这次调用花了多少钱"也常常被忽略。

但成本恰好是**唯一不需要主观判断**的指标：token 数是协议自带的客观事实，价格是厂商公开的单价，二者相乘就是钱。它不需要裁判，不需要标注集，误差只来自价格表是否及时更新。一个"会看账单"的 Agent 系统，比一个"只会跑"的系统多了一双眼睛。

### 1.2 账单的两个来源与一个盲区

单看一条账单，来源很清晰：

| 费用构成 | 含义 | 对应模块 |
|----------|------|----------|
| 输入 token | 提示词、上下文、工具结果回填 | day034 `TokenCounter` |
| 输出 token | 模型生成的回复 | day034 `TokenCounter` |
| 单价 | 模型 × 接口的每 1K token 定价 | day032 `DEFAULT_PRICE_TABLE` |

但账单要回答的**管理问题**不是"这一条多少钱"，而是"这一个月多少钱、花在哪"。这正是 day032 `CostTracker.breakdown()` 已经解决了一半的问题——按模型聚合、按接口聚合。

还有一个盲区是**重复**：同一个问题被问十遍，就付十次钱。这不是记账能解决的，是记账**暴露出来**之后，用缓存去解决的。第二章先补全"识别"，第三章再谈"优化"。

## 第二章：CostTracker 升级 —— 识别高成本调用路径

### 2.1 为什么"路径"要组合模型与接口

`breakdown("model")` 和 `breakdown("endpoint")` 是两个正交的单维度聚合。但真实场景里，"贵"往往是**组合**出来的：同一个模型走 `chat`（输入输出都计费）与走 `embedding`（只计输入）的成本结构完全不同。只看模型会漏掉"这个模型在 embedding 上烧钱"，只看接口会漏掉"这个接口用的是最贵的模型"。

于是本日新增 `top_cost_paths()`，把「模型 × 接口」当作一条调用路径归因：

```python
def top_cost_paths(self, top_n: int = 5) -> list[dict]:
    """识别高成本调用路径：按「模型 × 接口」归因，费用降序返回前 top_n 条."""
    agg: dict[tuple[str, str], dict[str, float]] = {}
    for r in self.records:
        bucket = agg.setdefault(
            (r.model, r.endpoint),
            {"calls": 0.0, "prompt_tokens": 0.0, "completion_tokens": 0.0, "cost_usd": 0.0},
        )
        bucket["calls"] += 1
        bucket["prompt_tokens"] += r.prompt_tokens
        bucket["completion_tokens"] += r.completion_tokens
        bucket["cost_usd"] += self.record_cost(r)
    rows = [
        {
            "model": model, "endpoint": endpoint,
            "calls": int(v["calls"]),
            "prompt_tokens": int(v["prompt_tokens"]),
            "completion_tokens": int(v["completion_tokens"]),
            "cost_usd": round(v["cost_usd"], 6),
        }
        for (model, endpoint), v in agg.items()
    ]
    rows.sort(key=lambda row: row["cost_usd"], reverse=True)
    return rows[:top_n]
```

归因的原则与 `record()` 完全一致：**在记录时打上标签，而非事后猜测**。每条 `UsageRecord` 天生带 `model` 与 `endpoint` 两个标签，聚合只是把它们当作分组键组合起来，没有引入任何新的猜测环节。

### 2.2 报告里直接带上路径

`report()` 在原有的 `by_model` / `by_endpoint` 之外，新增 `top_paths` 字段：

```python
"top_paths": self.top_cost_paths(),
```

这是**向后兼容**的增强：已有测试只断言 `total_calls`、`total_tokens`、`by_model` 等字段，新增字段不影响它们。`scripts/cache_demo.py` 的实测输出（本机运行）：

```text
        gpt-4o ×       chat: 1 次, $0.025000
   gpt-4o-mini ×       chat: 1 次, $0.000540
   gpt-4o-mini ×  embedding: 1 次, $0.000450
```

一眼看出：`gpt-4o × chat` 是头号烧钱路径，费用是第二名的 46 倍。成本优化从这里下手——给高频路径加缓存（第三章）、换更便宜的模型（day039 的路由策略）、压缩提示词（day036 的 Prompt 工程）。

> 价格表里的单价（gpt-4o-mini $0.00015/1K 输入、$0.0006/1K 输出；gpt-4o $0.0025/1K 输入、$0.01/1K 输出）沿用 day032 的 `DEFAULT_PRICE_TABLE`，是**演示量级**——接入真实模型时以厂商最新定价为准，只需改价格表一行，归因逻辑不动。

## 第三章：缓存 —— 最直接的成本杠杆

### 3.1 观察：重复是流量的常态

LLM 调用里藏着大量可预见的重复：

- 用户反复问同一个问题，措辞略有不同（"什么是 RAG" / "RAG 是什么"）；
- 长会话里，系统提示词与上下文前缀每次请求都原样重发——这些 token 每次都计费；
- 多个 Agent 角色（day012 的研究员、分析师、撰稿人）对同一个子问题各问一遍。

缓存的思想朴素：把「查询 → 回复」存下来，下次遇到相同或足够相似的查询直接返回，**省掉一次 API 调用**。这不是优化技巧，而是工程常识——数据库有查询缓存，CDN 有边缘缓存，LLM 调用同样值得一层缓存。

### 3.2 从精确缓存到语义缓存

最简单的缓存是**精确匹配**：把查询 `strip` 后当字典键，字面相同就命中。它零成本、零歧义，但有一个原则性短板——**措辞一变就失效**。"什么是 RAG"与"RAG 是什么"字面不同，精确缓存放走了一次本可复用的调用。

这正是 day041 埋下的伏笔。当时我们给 Agent 装上了"语义罗盘"：`CharNgramEmbedding` 让语义相近的文本得到相近的向量，`SentenceTransformerEmbedding` 更进一步，连"西红柿"与"番茄"都会被拉近。有了"语义距离"这把尺子，缓存就能从"字面相同"升级为"语义相近"——这就是**语义缓存**。

### 3.3 缓存的三条设计约束

本日的 `SemanticCache` 围绕三条约束设计：

1. **命中要快**：精确匹配 O(1)，语义匹配 O(n) 次点积——n 是缓存条目数，条目越多越慢，所以容量有上限；
2. **不能无限膨胀**：缓存占用内存，必须有淘汰策略。我们选 LRU（最近最少使用）——`OrderedDict` 队头淘汰，队尾是最近使用的；
3. **阈值可调**：语义命中"够不够像"由 `similarity_threshold` 决定。取 1.0 退化为纯精确匹配，取 0.85 允许同义改写命中——阈值越高越保守（少命中、省得少、但不误答），越低越激进（多命中、省得多、但可能张冠李戴）。

## 第四章：SemanticCache —— 精确匹配 + 语义匹配 + LRU

### 4.1 数据结构：OrderedDict 即 LRU

缓存主体是一个 `OrderedDict[str, CacheEntry]`。`OrderedDict` 记住插入顺序，我们约定：**队尾是最近使用的，队头是待淘汰的**。于是 LRU 的两个操作都成了 O(1)：

- 访问时 `_touch(key)` 把 key 移到队尾；
- 淘汰时 `popitem(last=False)` 弹出队头。

```python
class CacheEntry:
    """一条缓存记录：查询、回复与查询向量."""
    query: str
    reply: str
    embedding: list[float]
```

查询向量在 `put` 时算好并随条目保存——之后的所有 `get` 只做余弦比较，不为每次查找重新向量化查询文本。一次写入一次编码，命中判断零编码。

### 4.2 get：两级匹配，顺序即优先级

```python
def get(self, query: str) -> str | None:
    key = self._normalize(query)
    if key in self._entries:
        self._touch(key)
        self.exact_hits += 1
        return self._entries[key].reply

    if self._entries:
        qvec = self._embedding.embed(key)
        best_key, best_entry, best_score = None, None, -1.0
        for k, entry in self._entries.items():
            score = cosine_similarity(entry.embedding, qvec)
            if score > best_score:
                best_score, best_key, best_entry = score, k, entry
        if best_entry is not None and best_score >= self._threshold:
            self._touch(best_key)
            self.semantic_hits += 1
            return best_entry.reply

    self.misses += 1
    return None
```

两条匹配路径的优先级由代码顺序天然保证：

1. **精确匹配**（O(1) 字典查找）——`strip` 后字符串相等，零成本、无歧义；
2. **语义匹配**（O(n) 次点积）——与全部条目的余弦最近邻达到阈值即命中。语义命中要走一遍 embedding 编码 + n 次余弦，代价明显高于精确匹配，所以放在第二优先级。

语义匹配用的是 day009 就有的 `cosine_similarity`（`memory/vector_store.py`），**与检索链路同一口径**——缓存的"够像"与向量库检索的"相关"用的是同一把尺子，不会出现两套度量打架。

### 4.3 put：更新不淘汰，超容量才淘汰

```python
def put(self, query: str, reply: str) -> None:
    key = self._normalize(query)
    if key in self._entries:
        self._touch(key)
        self._entries[key] = CacheEntry(
            query=key, reply=reply, embedding=self._embedding.embed(key)
        )
        return
    self._entries[key] = CacheEntry(
        query=key, reply=reply, embedding=self._embedding.embed(key)
    )
    while len(self._entries) > self._max_size:
        self._entries.popitem(last=False)
        self.evictions += 1
```

两个细节：已存在的键**更新回复但不触发淘汰**（同一个问题重新生成，不应把别的条目挤出去）；新键写入后若超容量，用 `while` 循环逐个淘汰队头——防御性地处理"一次性超容多"的边界，而不是只弹一个。

### 4.4 统计：命中率是缓存的体检指标

`exact_hits`、`semantic_hits`、`misses`、`evictions` 四个计数器让缓存的行为可观测。`hit_rate` 属性在无请求时返回 0.0（不做除零）：

```python
@property
def hit_rate(self) -> float:
    total = self.hits + self.misses
    return self.hits / total if total else 0.0
```

命中率是缓存价值的直接度量：命中率 0 说明缓存白占内存（阈值太高或流量无重复），命中率趋近 1 说明缓存物超所值。

## 第五章：CachedLLM —— 透明包装与省成本归因

### 5.1 为什么是"包装"而不是"改造"

缓存不该侵入 Agent 或 LLM 的既有逻辑。`CachedLLM` 实现 `BaseLLM` 接口，包在任意 LLM（乃至 `ModelRouter`）外面——对上层 Agent 与 API 而言，缓存层是完全透明的：

```python
class CachedLLM(BaseLLM):
    """带缓存的 LLM 包装器：对上层透明，命中缓存时跳过真实调用."""
```

这一设计哲学与 day039 的 `ModelRouter` 一致：**新增能力以"包装器"落地，而不是以"改造既有类"落地**。`ModelRouter` 是"选模型"的透明层，`CachedLLM` 是"省调用"的透明层，两者还可以叠加——`CachedLLM(ModelRouter(...))` 让先选型后缓存。

### 5.2 chat：先查缓存，未命中才调用

```python
def chat(self, messages, temperature=0.7, max_tokens=1024):
    query = self._last_user_message(messages)
    cached = self._cache.get(query)
    if cached is not None:
        self.cache_hits += 1
        self.savings_usd += self._estimate_call_cost(query, cached)
        return cached
    self.cache_misses += 1
    reply = self._llm.chat(messages, temperature=temperature, max_tokens=max_tokens)
    self._cache.put(query, reply)
    return reply
```

缓存键取**最近一条 user 消息**，与 `ModelRouter._last_user_task` 的决策输入一致——路由判断"该用多强的模型"和缓存判断"这个问题见过没有"，看的是同一个东西。

一个值得注意的继承收益：`BaseLLM.stream` 的默认实现是 `yield self.chat(...)`，所以 `CachedLLM` **不覆写 stream** 也自动获得了"流式也走缓存"的能力——继承的 `stream` 会调用被覆写的 `chat`，命中缓存时直接返回缓存回复。

### 5.3 省成本归因：把省下的调用折算成美元

"缓存省了多少钱"不能是一句空话。`_estimate_call_cost` 复用 day034 的 `TokenCounter`，把「一次查询 + 一次回复」按价格表折算：

```python
def _estimate_call_cost(self, query: str, reply: str) -> float:
    expected_completion = self._counter.count_tokens(reply, self._model)
    info = self._counter.estimate_cost(
        query, self._model, self._price_table,
        expected_completion_tokens=expected_completion,
    )
    return info["total_cost_usd"]
```

这是 day034 埋下的第二个伏笔：当时 `estimate_cost` 的设计就是"在调用发生前预估费用"。缓存命中恰好是"调用没有发生"的场景——用查询文本估输入 token，用缓存回复文本估输出 token，二者相加就是这次本应发生的费用。`CachedLLM` 默认 `TokenCounter(prefer_tiktoken=False)` 走字符级估算，**离线测试全程确定**，不依赖 tiktoken 词表文件。

`scripts/cache_demo.py` 的实测：三次提问（一次首问 + 一次语义命中 + 一次精确命中）只真实调用底层 LLM 一次，累计节省成本 $0.00002010。这个数字虽小，但它证明了归因链路是通的——真实流量放大后，节省的就是真金白银。

## 第六章：阈值调优 —— 缓存质量与 embedding 质量绑定

### 6.1 同一个阈值，两种 embedding 两重天

`similarity_threshold` 的合理取值**依赖 embedding 的质量**。这是本日最需要记住的一条工程直觉。

用 `CharNgramEmbedding`（day041 的离线实现）实测三组相似度（本机运行）：

| 文本对 | 相似度 |
|--------|--------|
| "机器学习是什么" vs "什么是机器学习" | 0.5455 |
| "什么是 RAG" vs "RAG 是什么" | 0.3636 |
| "你好世界" vs "你好世界"（精确） | 1.0 |

char-ngram 的相似度来自**字面重叠**：同字重排的"机器学习是什么/什么是机器学习"共享大量字符 n-gram，相似度约 0.55；而中英混排的"什么是 RAG / RAG 是什么"因为空格切断了 n-gram，相似度掉到 0.36。这说明：**离线缺省的 char-ngram 下，阈值得设在 0.4~0.6 这个量级**才能让语义命中生效——默认配置里的 0.85 是给神经 embedding 准备的。

### 6.2 默认 0.85 是给神经向量的

`SentenceTransformerEmbedding` 产出的是神经语义向量，"西红柿炒鸡蛋"与"番茄炒蛋"这种**同义不同形**的表达也会得到高相似度（往往 0.85+）。因此在神经 embedding 下，0.85 的阈值能命中"意思一样、字面全异"的查询，又不至于误命中无关内容。而 char-ngram 只认字面，0.85 会几乎永远命中不了语义——**阈值不是孤立的旋钮，它和 embedding 质量是绑在一起的**。

这正是 `default_cache()` 把阈值读自配置、embedding 走 `default_embedding()` 工厂的原因：换了 embedding 提供方，阈值跟着调，两者通过配置对齐：

```python
def default_cache(embedding: EmbeddingProvider | None = None) -> SemanticCache:
    from smart_research_agent.llm.embedding import default_embedding
    return SemanticCache(
        embedding=embedding or default_embedding(),
        similarity_threshold=settings.cache_similarity_threshold,
        max_size=settings.cache_max_size,
    )
```

### 6.3 调阈值的两条边界

- **阈值过低**（如 0.2）：无关查询也会命中，缓存开始"张冠李戴"——用户问"晚饭吃什么"，命中了"机器学习"的缓存回复，这是**正确性事故**，比多花一次钱严重得多；
- **阈值过高**（如 0.99）：几乎只有精确匹配能命中，语义缓存退化成精确缓存，省钱的潜力浪费了。

经验法则：**宁可漏命中，不可错命中**。缓存的价值排序是"正确 > 省钱"——错命中污染的是答案质量，漏命中只是多花一次钱，代价完全不对等。这与 day041 `min_score` 过滤"宁缺毋滥"是同一套价值观。

## 第七章：配置与演示 —— 把缓存接进项目

### 7.1 两个新配置项

`config.py` 新增（`.env.example` 同步）：

```python
# 语义缓存（day043）：相似度命中阈值与最大容量
cache_similarity_threshold: float = 0.85
cache_max_size: int = 128
```

与 day041 的 embedding 配置同构：默认值提供开箱即用体验，环境变量可覆盖。`cache_max_size=128` 是刻意的保守默认——128 条缓存足够覆盖"高频问题集"，又不至于在内存里无限膨胀；LRU 保证这 128 条永远是最常被问的。

### 7.2 演示脚本：三段式验证

`scripts/cache_demo.py` 沿用 day041 `embedding_demo.py` 的"打印 + 断言"风格，演示三件事：语义缓存命中（底层只调一次）、省成本归因（$0.00002010）、高成本路径识别（gpt-4o × chat 居首）。运行方式：

```bash
python scripts/cache_demo.py
```

脚本里的 `assert` 是**可执行的教学断言**：不是"看起来对"，而是"跑起来必须对"。这与本项目的测试哲学一致——每个概念都用代码验证，不满足于"看懂了"。

## 结语：成本视角之后的三条工程线索

今天给 Agent 装上了"省钱的仪表盘"，留三条线索给后续课程：

1. **缓存与记忆是近亲**：语义缓存的本质是"用向量相似度复用历史"，与 day009 长期记忆的"向量化存储 + 相似度召回"是同一套机制的两个用途——记忆是跨会话的长期复用，缓存是会话内/近期的短期复用。day064 接入 ChromaDB/FAISS 时，两者可以共享同一套向量索引；
2. **缓存有失效问题**：本日的缓存没有 TTL——真实系统里，价格、事实、用户数据都会变，缓存需要过期策略。day044 安全合规、day072 RAG 生产化都会触及"缓存何时失效"的边界；
3. **成本是路由的反馈信号**：day039 的 `CostFirstStrategy` 用 `cost_per_1k` 做静态选型，而 `CostTracker` + `CachedLLM` 提供的是**实测成本**——把实测反馈回路由策略，就是"用真实账单校准选型"的闭环，day046 的 M4 集成会把这几个模块串起来。

下一课（day044）按课程索引是安全合规与内容审核——输出内容审核、敏感词过滤、PII 检测与脱敏，为 FastAPI 接口配置访问日志与审计。
