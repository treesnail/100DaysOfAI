# day026 习题答案：Prompt 评估

> 对应 [习题](../习题/习题.md)。每题附详细解析。

## 一、选择题

### 第 1 题：B（一致性）

**解析.** "严格按照规定格式"与"格式可以随意调整"是两条指向同一对象（输出格式）的字面矛盾指令——这正是一致性维度的定义：**指令之间是否自相矛盾**。规则侧的 `CONTRADICTION_PAIRS` 里就有 `("严格", "随意")` 这对词，该提示词会同时命中，被扣分并记录"检测到潜在矛盾指令"。

- 不选 A：清晰度问的是"读完知不知道要做什么"，这段文字反而把格式要求说得很具体，问题不在信息量；
- 不选 C：歧义是"一句话有多种解读"，这里是"两句话互相打架"，性质不同。两者的分界线：歧义源于**表述模糊**，矛盾源于**口径不一**。

### 第 2 题：B（占位符未闭合）

**解析.** 占位符闭合是**机械事实**：数一下 `{` 和 `}` 的个数是否相等、是否存在空占位符 `{}` 即可判定，规则侧用两行代码零成本完成，且判定 100% 确定。更关键的是这类问题模型评委几乎抓不到——LLM 读文本时关注语义，一个缺失的 `}` 很容易被它"脑补"过去，而这个缺陷会让 `str.format()` 在运行时直接抛 `KeyError`。

- A、C、D 都需要语义理解（词不达意、语义冲突、专业感），正是评委侧的职责。**分工原则：机械事实交给规则，语义判断交给评委。**

### 第 3 题：C（位置偏置）

**解析.** 位置偏置指评委在同一次调用中对比 A、B 两个候选时，系统性偏爱先出现（或后出现）的那个。把两份提示词塞进一次调用让评委二选一，评估结论会掺杂位置因素——交换 A、B 顺序可能得到相反结论。`compare()` 的做法是**两次独立调用分别打分，再比较 overall 分数**：每次调用里只有一份提示词，位置无从偏置。

- 自我偏好靠"评委与生成模型不同源"缓解；冗长偏好靠 rubric 锚定与规则侧长度上限对冲；训练数据污染是基准评估的问题，与本场景无关。

## 二、判断题

### 第 4 题：错误

**解析.** `parse_judge_output` 对解析出的分数一律经过 `_clamp` 钳制到 `[1.0, 5.0]` 区间：9 分被钳为 5.0，0 分被钳为 1.0。理由是**评分契约先于分数本身**：rubric 明确约定 1~5 分，超出区间的输出属于评委**没有遵守输出格式**，是格式违规而非"特别优秀"的证据。如果照单全收 9 分，加权合成的量纲就被破坏（规则侧永远封顶 5 分），不同维度的分数失去可比性。这与 day010 防御式解析的哲学一致：LLM 输出是不可信输入，必须校验后才能进入系统。

### 第 5 题：错误

**解析.** 规则侧采用扣分制：满分 5.0 的含义是"**没有发现已知的机械缺陷**"，而不是"好"。规则能验证"有角色段落"，验证不了"角色定义写得好不好"；能抓到词对表里的字面矛盾，抓不到表外的语义冲突；词表外的模糊措辞同样漏检。这正是架构上引入评委侧的原因——规则分是**保底**（机械缺陷的扣分丢不掉），语义层面的优劣由评委侧修正，最终分数是两者加权合成。教程 3.1 节明确说过：规则检查只能证伪，不能证实。

## 三、问答题

### 第 6 题：三大评委偏差与缓解

**（1）位置偏置（Position Bias）。** 表现：评委在同一次调用中对比多个候选时，系统性偏爱某个位置（多数模型偏爱先出现的，部分相反），交换候选顺序可能翻转结论。缓解：

- 本项目的做法：分别独立评估再比分数，每次调用只有一个评估对象，从根本上消除位置因素；
- 若必须同调用对比，可做**双向评估**（A-B 与 B-A 各评一次），结论一致才采信。

**（2）自我偏好（Self-preference）。** 表现：评委模型倾向给"像自己输出风格"的文本打高分——用 GPT 评 GPT 写的提示词，分数系统性偏高。缓解：

- 评委模型与生成/执行模型**不同源**（用 A 家模型评 B 家模型用的提示词）；
- rubric 里强调"以第一次阅读该提示词的模型视角评估"，把评委注意力从"我喜不喜欢"拉向"读者能不能读懂"；
- 分数只用于**版本间相对比较**，不追求绝对准确——自我偏好对两个版本大致同向施加，相减时抵消。

**（3）冗长偏好（Verbosity Bias）。** 表现：更长的文本显得"更专业"，容易拿高分，导致评估变相鼓励提示词膨胀。缓解：

- rubric 锚点中明确"清晰不等于详尽"，5 分定义为"无需任何猜测"而非"写得全"；
- 规则侧从另一侧对冲：长度超过上限（4000 字符）扣清晰度分。**一个维度同时被规则和评委看着，单一路径的偏差更难蒙混过关**——这就是双路评估的深层价值。

通用兜底手段还有**多评委（jury）**：多个模型/多次采样独立打分取中位数，平均掉单个评委的噪声。`PromptEvaluator(llm=...)` 的依赖注入设计保证了换评委、加评委都不需要改评估逻辑。

### 第 7 题：加权合成的理由

**(1) 为什么不全信规则侧？** 规则没有语义理解能力，只是三个质量维度的粗糙代理：关键词"你是"命中不等于角色定义写得好；词对表之外的矛盾、表外的模糊措辞全部漏检。全信规则，等于鼓励写出"规则全过但读着别扭"的提示词。

**(2) 为什么不全信评委侧？** 评委有三个硬伤：一，**不稳定**——换模型、换温度，分数漂移；二，**有系统性偏差**（第 6 题的三个偏差）；三，**抓不住机械事实**——未闭合的占位符、词对级矛盾，评委大概率注意不到，而这类问题会直接导致运行时异常。

**(3) 为什么评委权重略高（0.6 > 0.4）？** 三个维度里，清晰度和无歧义本质是**语义属性**，规则侧只是代理指标；只有一致性里的一部分（占位符、字面矛盾）是规则侧真正更强的领域。因此语义判断应主导总分。但规则侧保留 0.4 的意义是**保底**：评委再离谱（比如冗长偏好发作给注水长文打高分），机械缺陷的扣分也不会被完全洗掉。0.4/0.6 不是精密计算的结果，而是"语义主导、规则保底"这一原则的工程取值。

### 第 8 题：评估驱动的迭代闭环

四个环节：

1. **发现问题**：bad case（线上输出异常）、规则告警（占位符/矛盾/模糊措辞）、评委低分，任何一个渠道都可能触发改版；
2. **修改与版本化**：改动提示词，版本号 +1，在注释中写明变更原因（改了什么、针对哪个维度）——历史版本不删除，保证可回头对比；
3. **对比验证**：`compare()` 分别评估新旧版本，overall 分差超过平局阈值（0.05）才算"显著改善"，噪声不构成改版有效的证据；
4. **固化回归**：把新版本与分数线写成 `EvalCase` 加入回归套件，后续任何改版跌破分数线，测试立即变红。

`PromptEvalHarness` 扮演的是**门禁**角色：它把 harness 基座的 `expected` 字段定义为"overall 最低分数线"，让提示词质量从"一次性报告"变成"持续守卫"。相比手动跑 demo 看分，它的优势在于：

- **不可跳过**：手动看分靠自觉，测试在 CI 里自动执行，改提示词的人和看分的人可以是不同的人；
- **失败可读**：`CaseResult.detail` 里带着 issues 清单，红了能立刻看到扣分原因，不用重新评估；
- **多模板统一门禁**：一个套件同时守卫系统提示词、规划提示词、评委提示词，任何一份退化都会被捕获。

本质上，这和 day010 说的"给提示词写回归测试"是同一思想的完整形态：**人负责发现 bad case 和写改版，机器负责验证改版有效且没有回退。**

### 第 10 题：三份提示词的回归套件

在 `tests/test_prompt_eval.py` 中新增：

```python
from smart_research_agent.agent.planner import PLAN_PROMPT
from smart_research_agent.evaluation.prompt_eval import JUDGE_PROMPT

class TestPromptRegressionSuite:
    def test_all_prompts_above_threshold(self):
        judge_json = (
            '{"clarity": 5, "consistency": 5, "ambiguity_free": 4, '
            '"issues": [], "suggestions": []}'
        )
        # MockLLM 按调用顺序弹出：三个用例各消费一条评委回复
        evaluator = PromptEvaluator(llm=MockLLM(responses=[judge_json] * 3))
        harness = PromptEvalHarness(evaluator)
        cases = [
            EvalCase(name="react_system_v2", input=REACT_SYSTEM_PROMPT_V2, expected="4.0"),
            EvalCase(name="plan_prompt", input=PLAN_PROMPT, expected="3.5"),
            EvalCase(
                name="judge_prompt",
                input=JUDGE_PROMPT.replace("{{", "{").replace("}}", "}"),
                expected="3.5",
            ),
        ]
        results = harness.run(cases)
        assert harness.summary(results)["pass_rate"] == 1.0
```

**解析与注意事项：**

1. **评委提示词本身也是提示词**，同样存在清晰度/一致性/歧义问题，纳入回归套件是"评估器也要被评估"的题中之义。
2. `JUDGE_PROMPT` 里示例 JSON 的花括号写成了 `{{` `}}` 转义（因为它要过 `str.format`）。直接评估原文，`check_rules` 的占位符检查会看到配平的花括号（`{{` 与 `}}` 数量相等），不会误报，但评委读到的转义符号不是真实样貌；`replace` 还原后再评估更接近评委实际面对的内容。另一种更贴近生产的做法是评估 `JUDGE_PROMPT.format(prompt="<某份真实提示词>")` 的渲染结果。
3. **附加思考**：如果 `PLAN_PROMPT` 的 few-shot 示例里出现未转义的 `{`/`}`，`PLAN_PROMPT.format(goal=...)` 会在运行时抛 `KeyError` 或 `ValueError`——而且这种 bug 在"提示词文本 review"时极难发现。`check_rules` 的占位符检查（`{`/`}` 计数 + 空占位符检测）能发现计数不平衡，但对"多了合法配对的 `{name}` 占位符而调用方没传对应参数"这种场景，还需要结合 format 调用的参数清单才能完全检出——这正是规则检查的边界，也是可以继续迭代的方向。
