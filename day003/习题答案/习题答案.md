## 一、单选题

### 第 1 题

**答案：B**

**解析：**

- A 错：Agent 不是"更大的模型"。参数量与是否为 Agent 没有因果关系——一个小模型配上感知、行动、记忆组件就是 Agent，一个再大的模型裸奔也只是文本续写机。两者是**系统与部件**的关系，不是大小关系。
- **B 对**：这正是教程给出的定义——LLM 在 Agent 中扮演"大脑"（推理引擎）的角色，感知负责信息入口，行动负责改变世界，记忆负责跨调用保存状态。四组件组装成"感知 → 推理 → 行动 → 观察反馈"的循环，才是 Agent。
- C 错：Agent 不依赖任何特定的训练方式。ReAct 论文的重要贡献恰恰证明了**纯靠提示词约定格式、不微调**，就能让通用 LLM 表现出 Agent 行为。
- D 错：同义词说法抹掉了"会不会做"的本质区别。LLM 只负责"说"，Agent 能"做"——这是系统能力的鸿沟，不是命名差异。

### 第 2 题

**答案：B**

**解析：**

ReAct 的核心创新就是建立了推理与现实之间的**反馈回路**，而 Observation 正是这个回路的关键一环。

- A 错：如果 Observation 由 LLM 自己推测，那它和 CoT 就没有区别了——幻觉没有任何"现实锚点"，推理链依然封闭。Observation 必须来自真实世界，才有纠错价值。
- **B 对**：在 ReAct 的运行机制中，LLM 输出 `Action` + `Action Input` 后就**暂停**；由系统（我们的代码）真正执行工具调用，把真实返回结果作为 `Observation: ...` 追加回消息上下文，再让 LLM 继续。真实执行是 Observation 的全部意义。
- C 错：ReAct 是自主循环，不需要用户每轮介入。用户只在开始时给出任务。
- D 错：Observation 是运行时数据，与训练数据无关。

### 第 3 题

**答案：D**

**解析：**

- A 对：`max_steps` 存在的首要理由就是 LLM 的输出不可预测——它可能因为提示词缺陷、任务无解或模型状态不佳而永远不给 Final Answer。熔断器保证循环必有上界。
- B 对：没有熔断时，"循环何时停"完全由概率模型决定；有了 `max_steps`，无论模型怎么输出，**确定性代码**都握着最终否决权。这是对不可控组件设置确定性上限的通用工程直觉。
- C 对：10 是经验值——太小会掐断复杂任务（如查 5 个资料源再综合），太大则失控时 token 费用失控。它做成构造参数而非硬编码常量，就是为了按任务调整。
- **D 错**：`max_steps` 只保证"循环会停"，**不保证"停的时候有答案"**。循环耗尽后返回的是"达到最大步数限制，未能得出最终答案"——熔断是防失控的安全气囊，不是正确性保证。把"防失控"误读为"保正确"，是对熔断机制最常见的误解。

## 二、判断题

### 第 4 题

**答案：错**

**解析：**

这是对 CoT 的典型误读。CoT 提升的是**推理质量**（把中间步骤显式化，减少"跳步出错"），但完全不改变**信息边界**：

- LLM 推理时能用到的信息只有两类：训练时内化的参数化知识 + 当前对话上下文中的文本。CoT 两者都没有增加。
- "今天天气"属于训练截止日期之后的实时信息，不在训练数据里，也不在对话里。无论思考多少步，模型都只能在封闭信息空间里打转——推理链再长也变出不存在的事实。
- 更危险的是，CoT 的流畅文风会让幻觉**显得更有依据**：模型会煞有介事地"推理"出一个编造的答案。

正确结论是：CoT 解决"怎么想"的问题，不解决"知道什么"的问题。后者只能靠感知/行动组件从外部世界取信息——这正是 ReAct 存在的理由。

### 第 5 题

**答案：错**

**解析：**

两者在"程序员意图"层面看似等价，在**系统行为**层面截然不同：

- `return ""` 是一个**合法的返回值**。上层调用方收到空字符串，无法区分"任务执行成功但答案为空"和"功能根本没实现"——错误被静默掩盖，会沿着调用链传播到很远的地方才以诡异的方式爆发（比如把空答案写进报告）。
- `raise NotImplementedError("ReAct 循环将在 day006 实现")` 是一个**明确的失败信号**。调用方立即得到异常，异常类型说明"这是未实现而非出错"，异常消息还自带路标（哪天实现）。问题在第一时间、第一现场暴露。

这体现了"诚实的 API"原则：**未实现的功能应该大声失败，而不是假装成功。** 同时它还让"未完成"状态可以被测试锁定——`pytest.raises(NotImplementedError, match="day006")` 能精确验证这个承诺，而 `return ""` 的语义含糊，无法写出有意义的断言。骨架阶段，可测试的"未完成"远好于不可测试的"假完成"。

## 三、问答题

### 第 6 题

**参考答案：**

智能音箱是一个"Agent 程度不完整"的系统，逐个组件对照：

| 组件 | 智能音箱的对应能力 | 完整度评估 |
|------|------------------|-----------|
| 感知 | 麦克风阵列收音 + 语音识别（ASR），把环境声音转为文本输入 | 具备，且是多模态感知（声音） |
| 推理 | 意图识别与对话管理（早期是规则/小模型，新一代接入 LLM） | 部分具备：传统音箱的"推理"多为固定意图分类，缺乏开放式的逐步推理能力 |
| 行动 | 播放音乐、控制智能家居、播报天气、设置闹钟 | 具备，这是它最"Agent"的部分 |
| 记忆 | 记住唤醒偏好、绑定的音乐账号、家中设备列表 | 薄弱：多为静态配置存储，缺乏对对话历史的推理级利用，更谈不上从经验中学习 |

**结论**：智能音箱具备感知与行动两个"四肢"组件，但推理与记忆这两个"大脑"组件长期薄弱——所以老式音箱常给人"人工智障"的印象：能听清、能执行，但不会多步思考、不记得你三分钟前说过什么。这个案例恰好说明：**四组件中任何一个瘸腿，整个系统的智能感就会崩塌。** 新一代接入 LLM 的音箱，本质上就是在补"推理"这块短板。

（评分要点：不要求与表格逐字一致，但必须逐组件分析，且能指出"感知/行动强、推理/记忆弱"的不均衡结构。）

### 第 7 题

**参考答案：**

**（1）推理成就行动——让行动从"写死"变为"决策"：**

固定工具流水线的行动序列在运行前就被硬编码：第一步调 A、第二步调 B，与运行时遇到的情况无关。ReAct 中，每一步的 `Action` 与 `Action Input` 都由 LLM 基于当前完整上下文（任务 + 已有观察）**动态决策**：

- 搜索结果为空？下一步可以换关键词再搜，而不是按死流程继续；
- 发现需要先算一道算术才能确定搜索关键词？插入一步计算；
- 信息已足够？提前终止，不浪费后续调用。

推理让行动具备了**条件分支与应变能力**——行动序列不再是静态程序，而是逐状态生成的策略。

**（2）行动成就推理——给推理一个"现实锚点"：**

纯 CoT 的推理链是封闭的：每一步只能基于模型记忆和已有文本，幻觉没有校正机制，一步错、步步错。ReAct 中，行动产生的 `Observation` 是**真实世界的数据**：

- 模型不知道今天天气？查一次，真实数据进入上下文，后续推理有了事实地基；
- 模型算错了 `123456 × 789`？计算工具返回正确结果，把推理链拉回正轨；
- 模型误调了不存在的工具？真实的报错反馈让它下一步改弦更张。

行动让推理具备了**外部校验与自我纠错的机会**。一句话概括这对协同关系：**推理决定"做什么"，行动告诉推理"世界是什么样"**——缺了前者，系统僵化；缺了后者，系统做梦。

## 四、编程题

### 第 8 题

**参考实现：**

```python
"""day003 编程题参考实现：迷你 ReAct 循环."""


class SimpleLLM:
    """按预设脚本回复的最简 LLM."""

    def __init__(self, responses: list[str], default: str = "Action: 思考中"):
        self._responses = list(responses)
        self._default = default

    def chat(self, messages: list[str]) -> str:
        if self._responses:
            return self._responses.pop(0)
        return self._default


def mini_react(llm: SimpleLLM, max_steps: int) -> str:
    """迷你 ReAct 循环：熔断 + 轨迹记录的最小形态."""
    trajectory: list[str] = []
    for _ in range(max_steps):
        raw = llm.chat(trajectory)          # 轨迹即上下文（极简版）
        if raw.startswith("Final Answer:"):
            return raw.removeprefix("Final Answer:").strip()
        trajectory.append(raw)              # 记录 Action
    return "达到最大步数限制"


if __name__ == "__main__":
    # 组 A：正常终止
    llm_a = SimpleLLM(["Action: 搜索", "Action: 计算", "Final Answer: 答案是 42"])
    result_a = mini_react(llm_a, max_steps=10)
    print(f"组 A 结果: {result_a}")          # 组 A 结果: 答案是 42

    # 组 B：触发熔断（脚本用完后会一直返回兜底 Action，永远不会出现 Final Answer）
    llm_b = SimpleLLM(["Action: 搜索", "Action: 再搜索"])
    result_b = mini_react(llm_b, max_steps=3)
    print(f"组 B 结果: {result_b}")          # 组 B 结果: 达到最大步数限制
```

预期输出：

```text
组 A 结果: 答案是 42
组 B 结果: 达到最大步数限制
```

（若把轨迹列表改为 `mini_react` 的返回值或在函数内打印，可观察到组 A 轨迹长度 2、组 B 轨迹长度 3。）

**解析：**

这道不到 30 行的练习题，其实复刻了 `ReactAgent` 的全部核心设计：

1. **熔断**：`for _ in range(max_steps)` 就是 `max_steps` 字段的本质——不管 LLM（这里是 `SimpleLLM`）回复什么，循环最多转 3 圈。组 B 的脚本里**永远没有 Final Answer**，如果没有熔断，它会无限循环下去。这对应教程 4.3 节：终止的兜底控制权在确定性代码手里。
2. **轨迹记录**：`trajectory.append(raw)` 就是 `history` 字段的极简版。真实实现里轨迹记录的是结构化的 `ReActStep`（day006），这里只是字符串，但"每一步留痕、可复盘"的意图完全相同。
3. **脚本化 LLM**：`SimpleLLM` 按预设列表依次回复、用完兜底——这正是 day005 将实现的 `MockLLM` 的设计原型。你已经提前体验了"测试不依赖真实 LLM"的依赖注入思想：循环逻辑与 LLM 来源解耦，换一个会真调 API 的 `SimpleLLM`，`mini_react` 一行都不用改。
4. **终止条件的两种形态**：组 A 演示"正常终止"（模型主动给出 Final Answer），组 B 演示"熔断终止"（循环耗尽）。真实的 ReAct 循环也只有这两种出路，day006 的完整实现里你会看到与这里几乎一一对应的代码结构。

**常见错误自查：**

- 把 `max_steps` 写成 `while True` 没有上界——组 B 会死循环；
- 判断终止时忘记 `.strip()`，遇到 `"Final Answer:  答案"`（多空格）解析出错——预告了 day006 为什么需要专门的解析器；
- 把 `responses.pop(0)` 写成每次返回第一个元素而不弹出——脚本永远不会推进。
