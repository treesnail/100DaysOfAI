## 第一章：九段链——先有地图，再谈装配

把"一次真实的研究请求"拆开，只有九段：

```text
1. guard      护栏：注入检测 + 内容审核，决定这次请求能不能往下走
2. plan       规划：把问题拆成有序子任务（Planner + MockLLM 剧本）
3. retrieve   检索：混合检索器取回 top-k 命中（两路共用一份过滤与深度）
4. pack       打包：把命中折成带编号、有预算的提示词片段（[n] 从 1 起连续）
5. generate   生成：把上下文交给模型，要求它给出可核对的引用
6. ground     接地：把答案里的 [n] 与那次提示词的编号对账（幻觉引用 = 0）
7. evaluate   评估：召回 / 精确 / MRR / NDCG 四条离线指标现场算出
8. account    记账：按模型与接口归因 token 与费用（价格表折算）
9. trace      追踪：把这一整次调用记成一条 trace（root + 每个阶段一个 span）
```

这张表被写进代码（`types.ASSEMBLY_STAGES`），并在导入期做
`set(...) == set(...)` 的闭合断言。**为什么值得写进代码**：读一个报告里的数字时，
第一个问题总是"它属于哪一段"；如果这张表只存在于教程里，那你读报告时只能靠记忆。

九段与八项能力之间用 `STAGE_CAPABILITIES` 串起来：**阶段是"这条链怎么走"，
能力是"用户能看见什么"**。一次真实运行的九行读数长这样（`scripts/capstone_demo.py` 第 2 节）：

```text
  1. [guard   ] ✓ | 读数 0 | 护栏：放行 | 注入 0 / 敏感 0 / PII 0 | 检查 12 字
  2. [plan    ] ✓ | 读数 3 | 规划：3 条子任务 拆解问题、检索语料、核对引用 | 工具自检 2 + 3 * (4 - 1) = 11 ✓
  3. [retrieve] ✓ | 读数 3 | 检索：3 条（k-3=+0.0328、k-2=+0.0320、k-6=+0.0320）| empty_reason=hits
  4. [pack    ] ✓ | 读数 3 | 打包：147/600 字 | 引用 3 条 | 截断 0 / 丢尾 0
  5. [generate] ✓ | 读数 1 | 生成：模型已调用 | 回退 （无） | 32 字
  6. [ground  ] ✓ | 读数 0 | 接地：通过 | 有效 1 / 幻觉 0 / 未引用 2 | 覆盖 33.3%
  7. [evaluate] ✓ | 读数 1 | 评估：召回 1.0000 | 精确 0.3333 | MRR 1.0000 | NDCG 1.0000 | 金标准 ['k-3']
  8. [account ] ✓ | 读数 3.78e-05 | 记账：2 次调用 | token 210（196+14） | 费用 $0.00003780（gpt-4o-mini）
  9. [trace   ] ✓ | 读数 9 | 追踪：9 个 span（root=capstone.run）
汇总：阶段 9 段全通过=True | 召回 1.0000 | 费用 $0.00003780 | token 210 | span 9 | 摘要 f052e4a7dd78d232
```

四个轴（`CAPSTONE_BOUNDARIES` 与 `CAPSTONE_NOTES` 一起把话说完）：`stage`（几段）、
`capability`（几项）、`cost`（花了多少）、`trace`（走了几步）。九段、八项能力、
七条性质、五条边界，四张名单**互相引用**，任何一张改了另一张就会在导入期报错。

## 第二章：清单——能力落到子包，importlib 说了算

day098 已经用 `Get-ChildItem` 数过 50 个子包；今天要做的是把"数过"变成
"**能被程序核对**"：

```text
一项能力 → 一串子包；每个子包 → 用 importlib 真的解析一次（存在性 + 公开符号数）
```

`manifest.resolve_subpackage(name)` 只回答一个问题：**这个名字解析得到吗、它公开了几个符号**。
一个容易写错的地方：没有 `__all__` 的包，公开符号数会**取决于导入顺序**
（`dir(module)` 里有什么，跟谁先 import 过它有关）。本课的做法是：无 `__all__` 时
按目录数子模块，**保证与导入顺序无关**——否则同一个清单跑两次会给出两个数。

今天真的解析了 12 个候选子包：

```text
security      | 在场 | 公开   8 个符号 | 认领：input_guard
agent         | 在场 | 公开  11 个符号 | 认领：task_planning
retrieval     | 在场 | 公开 124 个符号 | 认领：hybrid_retrieval、context_packing、grounded_generation
evaluation    | 在场 | 公开  20 个符号 | 认领：offline_evaluation
observability | 在场 | 公开   8 个符号 | 认领：cost_and_tracing
tools         | 在场 | 公开   5 个符号 | 认领：tool_execution
llm           | 在场 | 公开  12 个符号 | 认领：input_guard、task_planning、grounded_generation、cost_and_tracing
vectorstore   | 在场 | 公开  95 个符号 | 认领：hybrid_retrieval
indexing      | 在场 | 公开  57 个符号 | 认领：（无人认领）
mcp_server    | 在场 | 公开   6 个符号 | 认领：（无人认领）
finetune      | 在场 | 公开  48 个符号 | 认领：（无人认领）
api           | 在场 | 公开   1 个符号 | 认领：（无人认领）
```

读这张表的正确方式是看**两个数字一起**：`公开符号数` 回答"这个包有没有东西"，
`认领` 回答"它被哪一项能力用着"。今天的结果是：**覆盖 8/8 项能力、被认领 8 个包、
无人认领 4 个**（`indexing`、`mcp_server`、`finetune`、`api`）。

`无人认领 ≠ 没用`——它们都已经交付，只是**不属于今天这 8 项能力的清单**：
`mcp_server` 是 day016~023 的协议交付、`finetune` 是 M5 的专属模型链路、
`api` 是 day038 起的 HTTP 端点、`indexing` 是 day065 的索引账本。
把它们列出来而不是藏起来，是因为**结项演示里"哪一项没被这次链碰到"这个问题，
答案必须写在报告里**（这正是 day098 的风险一）。

## 第三章：适配层——信封里只有带方向的小数

`adapters.py` 是本课最容易被低估的一块。它不生产信号，只做一件事：

```text
既有子系统的返回值（各不相同的形状） → 九种统一读数（只带确定性标量）
```

为什么需要它：把"检索器返回了什么"直接塞进报告，会让**每一个阶段都依赖那一个子系统的内部类型**。
换一个检索器、改一个字段名，整条链的报告就一起失效。适配层把这件事收在一处：
上游怎么变，都只改适配层里的那一行。

九种读数（`GuardReading` / `PlanReading` / `RetrievalReading` / `PackReading` /
`GenerationReading` / `GroundReading` / `EvalReading` / `CostReading` / `TraceReading`）
只有两种字段：**计数**与**带方向的小数**。"带方向"是关键——一个读数必须能回答
"这次到底怎么样"，而这只在它能与某个界比较时成立（第四、五章的两条性质就是两条不等式）。

一个真读数：`k-3` 的分数是 `+0.0328`，`k-2` 与 `k-6` 都是 `+0.0320`——
正数表示"与查询同向"，而金标准 `['k-3']` 排在第一，于是：

```text
召回 1.0000（金标准全都回来了）
精确 0.3333（3 条里只有 1 条是金标准）
MRR 1.0000（第一条就是金标准）
NDCG 1.0000（分级折损后仍是满分）
```

**四个数一起读**才有意义：只看召回会以为"检索完美"，只看精确会以为"检索很糟"。

## 第四章：护栏与规划（guard / plan）

### 4.1 护栏排在最前

护栏是唯一一处**能省下后面所有花费**的阶段：把一次攻击话术拦下来，
检索与生成就一次都不会跑。今天的读数：

```text
1. [guard] ✓ | 读数 0 | 护栏：放行 | 注入 0 / 敏感 0 / PII 0 | 检查 12 字
```

`读数 0` 是"命中的可疑项数"。它与"检查了多少字"（12 字）**必须分开报**：
只报命中数，看不出"到底扫没扫"；只报字数，看不出"扫出了什么"。

> 口径（day046 就立下的）：被判定为注入的请求**模型完全不被调用**。
> 今天这条链把它变成了阶段事实——`guard` 不放行时，第 3~9 段根本不会出现。

### 4.2 规划只花一次调用，却买来一份清单

```text
2. [plan] ✓ | 读数 3 | 规划：3 条子任务 拆解问题、检索语料、核对引用 | 工具自检 2 + 3 * (4 - 1) = 11 ✓
```

`读数 3` 是子任务条数。规划的价值不在"模型说了什么"，而在**"这次要做什么"变成了一份可读清单**
——后面任何一段对不上号时，第一步要看的往往就是它。

`工具自检 2 + 3 * (4 - 1) = 11 ✓` 是一道**纯算术**：2 个工具各一次，
如果每个工具要试 4 种调用形态，那么 3 条子任务最坏要按 `2 + 3 × (4 − 1)` 条路径核一遍。
把"要不要给模型开放某个工具"变成一道加法，比拍脑袋决定可靠。

## 第五章：检索与打包（retrieve / pack）

### 5.1 每一条命中都留着"哪几路召回了它"

```text
3. [retrieve] ✓ | 读数 3 | 检索：3 条（k-3=+0.0328、k-2=+0.0320、k-6=+0.0320）| empty_reason=hits
```

`读数 3` 是命中条数，后面三项是"最多三条命中的分数"。`empty_reason=hits`
是 day066 那条纪律的延续：**空结果只给一个原因**（封闭清单 + 优先级），
命中时就写 `hits`，让"为什么空"这个问题永远有一个字段可看。

混合检索的每一条命中都留着"哪几路召回了它、各贡献了多少"——
只看名单看不出"某一路空着"，而那正是最该被看见的失败。

### 5.2 打包是唯一能回答"上下文为什么这么短"的地方

```text
4. [pack] ✓ | 读数 3 | 打包：147/600 字 | 引用 3 条 | 截断 0 / 丢尾 0
```

四个量各有分工：

```text
读数 3        进了包的引用条数（编号只给真的进了包的那些）
147/600       实际用掉的预算 / 总预算
引用 3 条     引用编号从 1 起连续（[1] [2] [3]）
截断 0 / 丢尾 0   两个"减法"分开记：单条太长被截 vs 整条超出被丢
```

**"截断 0 / 丢尾 0"这一项为什么必须进报告**：它让"上下文为什么这么短"可核对。
预算配小了、编号写重了、整条被静默丢掉——这三种错都会让**答案照常生成**，
而且看起来更"简洁"。今天两个减法都是 0，说明这 147 字是**完整的 3 条**。

## 第六章：生成与接地（generate / ground）

### 6.1 空上下文时一次模型都不许调

```text
5. [generate] ✓ | 读数 1 | 生成：模型已调用 | 回退 （无） | 32 字
```

`读数 1` 是"模型被调用了几次"。它与"回退（无）"必须一起报：
day066 / day069 都记过同一句话——**产物看起来最像成功的那种失败，正是一个没有片段
却写得很通顺的答案**。把 `llm_called` 独立成字段，就是为了让"这次到底调没调"
不再靠读日志猜。

### 6.2 接地的判据是编号，不是字符串

```text
6. [ground] ✓ | 读数 0 | 接地：通过 | 有效 1 / 幻觉 0 / 未引用 2 | 覆盖 33.3%
```

`读数 0` 是**幻觉引用条数**（答案里出现、但那次提示词里没有的编号）。
三组编号各自成数：

```text
有效 1     答案引用了、提示词里也有（[1] → k-3）
幻觉 0     答案引用了、提示词里没有（这一项必须为 0）
未引用 2   提示词里有、答案没用（[2] [3] 未被引用）
覆盖 33.3% 有效引用 / 提示词条数 = 1/3
```

**"未引用"不是错误**——它是"给了 3 条、只用了 1 条"这个事实。
把它与"幻觉"分开记，是因为两者该做的事完全不同：
未引用要调预算或调提示词，幻觉要修生成或修编号对齐。

`grounded = 有效 非空 且 幻觉为空`——day069 的定义，今天一字未改地复用。

## 第七章：评估、记账与追踪（evaluate / account / trace）

### 7.1 四条离线指标只认识"名单 + 金标准"

```text
7. [evaluate] ✓ | 读数 1 | 评估：召回 1.0000 | 精确 0.3333 | MRR 1.0000 | NDCG 1.0000 | 金标准 ['k-3']
```

`读数 1` 是金标准的条数。四条指标的**分母各不相同**：

```text
召回  = 命中金标准 / 金标准总数 = 1/1
精确  = 命中金标准 / 返回条数   = 1/3
MRR   = 1 / 第一条金标准的位置  = 1/1
NDCG  = 折损累计收益 / 理想排序 = 1.0000
```

它们能在**没有模型**的时候跑——因为输入只有"名单 + 金标准"。这不是缺陷，
而是纪律：**它量的是检索的质量，不是答案的质量**；两件事混进一个分数，
就再也说不清是哪一段坏了。

### 7.2 记账与追踪是同一次调用的两张收据

```text
8. [account] ✓ | 读数 3.78e-05 | 记账：2 次调用 | token 210（196+14） | 费用 $0.00003780（gpt-4o-mini）
9. [trace  ] ✓ | 读数 9 | 追踪：9 个 span（root=capstone.run）
```

一张回答"花了多少"（`读数 3.78e-05` 美元 = token 210，输入 196 + 输出 14，
按 `gpt-4o-mini` 的价格表折算），一张回答"经历了几步"（`读数 9` 个 span，
root 是 `capstone.run`）。**两个问题都不该靠日志去猜。**

第 ⑥ 条性质把"记账"与"手算"钉在一起：

```text
cost_matches_hand_formula | [upper_bound] | 读数 0 ✓ | 相对差 0.000000e+00 ≤ 容差 1e-12
                                                   | 记账 $0.00003780 / 手算 $0.00003780 | token 210
```

`hand_cost_formula` 是一行纯算术：`token × 单价`。**记账走的是价格表，手算走的是公式**，
两条独立路径给出同一个数（相对差恰好 0），这才叫"记账被核对过"。

## 第八章：复算——同一输入两次运行逐位相同

```text
第一次摘要：f052e4a7dd78d232
第二次摘要：f052e4a7dd78d232
逐位相同：True | 差异项数 0（0 = 逐位相同）
```

复算的口径写死在代码里（`SystemRun.comparable()`）：

```text
参与比较：问题 / 九段记录 / 答案 / 四条指标 / 费用 / token / span 条数
不参与：  时间戳、uuid、耗时、日志文本
```

**"不参与"这一列才是本节的要点**：把它们放进读数，第二条性质会**永远失败**，
而失败的原因与链本身无关——于是这条性质就会被人关掉。
day096 把时钟做成可注入、day087 把位置由缓存长度决定，都是同一条纪律：
**可复现的前提是先把"不确定的东西"从读数里挪出去。**

摘要用 sha256 前 16 位（与 day053 的评估套件、day088 的 `principle_map` 同一口径）：

```text
摘要 f052e4a7dd78d232 = sha256(问题 + 九段记录 + 答案 + 指标 + 费用 + token + span 条数)
```

**一条元组比较就能证明"接上了"**（`SystemRun.is_identical_to`），
而一条"装上了"的链什么也证明不了——这就是今天最值钱那句话的落点。

## 第九章：从清单渲染「最终版 README + 架构文档」

```text
readme         |  2748 字符 | 覆盖 8/8 项能力 | 缺：（无）
architecture   |  3751 字符 | 覆盖 8/8 项能力 | 缺：（无）
合并正文 6499 字符；缺失 0 项
```

两份文档都是**从清单渲染**的（`document.render_readme` / `render_architecture`）：
能力表、阶段表、子包与符号数都来自 `manifest`，不是手抄的。
于是有一条可以被反驳的性质：

```text
document_covers_all_capabilities | [equality] | 读数 0 ✓ | 合并正文 6499 字符；缺失 0 项
```

**为什么"覆盖全部能力"值得做成判据**：一份 README 漏掉一项能力，
在文本上**完全合法**——它读起来毫无问题，只是读者会以为那一项不存在。
把"每一项能力都必须出现在正文里"写成一条等式（缺失项 == 0），
这类"沉默的遗漏"才会当场变红。

渲染产物落在 `outputs/capstone/`（两份 `.md`）。**不改动仓库根的 `README.md`**——
"新渲染一份"与"改掉旧的那份"是两件事：本课只新增文件（第三条纪律）。

## 第十章：七条性质、七个失败族与五条边界

### 10.1 七条性质（三类判据齐全）

```text
通过 capabilities_are_covered          | [equality   ] | 读数          8 == 8      | 覆盖 8/8 项能力；未覆盖的：无
通过 stages_match_spec                 | [equality   ] | 读数          0 == 0      | 9 段与规格逐位相同
通过 assembly_is_reproducible          | [equality   ] | 读数          0 == 0      | 差异项数 0（0 = 逐位相同）
通过 retrieval_recall_meets_floor      | [lower_bound] | 读数          1 >= 1.0    | 召回 1.0000 ≥ 下界 1.0
通过 grounding_has_no_hallucination    | [upper_bound] | 读数          0 <= 0      | 幻觉引用 0 ≤ 上界 0
通过 cost_matches_hand_formula         | [upper_bound] | 读数 0.000000e+00 <= 1e-12| 记账 vs 手算
通过 document_covers_all_capabilities  | [equality   ] | 读数          0 == 0      | 合并正文 6499 字符；缺失 0 项
合计：7/7 条通过
```

**四条相等（读数 `== 0` 或 `== 8`）、两条上界（`<=`）、一条下界（`>=`）**——
判据类型是性质的一部分，它们与 `types.CAPSTONE_PROPERTIES` 逐名对齐，
并在导入期做闭合断言。

第 ④ 条是**下界**：召回必须 `>= 1.0`。没有这条下界判据时，
把"召回 1.0 写成 0.0"这类错误在报告里是看不出来的（两个数都落在 `[0,1]` 里）。
这正是 day095 记下的那句"没有下界判据时，把两个规则写成同一个，报告会全绿"。

### 10.2 七个失败族

| 族 | 该谁去修 |
|----|----------|
| `ManifestError` | 改清单或改包：子包名写错 / 包被改没了，先把名字改对再重建清单 |
| `CapabilityError` | 改能力表：未知能力或没有承担子包时，先把能力表补完整 |
| `StageError` | 改实现或改阶段表：链的形状（次序 / 条数）对不上时，先让两者对齐 |
| `AssemblyError` | 改实现：两次运行不一致时，去掉那个没有固定的量（时间 / 哈希序 / 采样） |
| `DocumentError` | 改渲染器：文档漏掉某项能力时，先把那一项渲染进正文 |
| `NumericError` | 改数据或改实现：非有限读数与非法上下界都属于"数值不可用" |
| `ParameterError` | 改调用：子包名 / 能力名 / 性质名 / 序号都是调用点的一次决定 |

`FAMILY_OUTCOMES` 与 `_FAMILY_CLASSES` 逐键对齐，导入期断言。两条族常量：

```text
RETURNED_FAMILY = "DocumentError"
  它第一次出现是 names 一次"文档解析失败"；此后各课都把它当工具函数、
  不把它当一次控制流事件。今天"渲染最终版 README 与架构文档"成了结业链路的
  最后一个交付物，于是这个名字**回来**了——但基类从 Exception 换成
  CapstoneError(ValueError)：它要能被同一条 except ValueError 兜住，与其余六族同源。

ABSENT_FAMILY = "GradientError"
  本课装配的链里唯一的"梯度事件"仍是被调用的 finetune 那一行——
  今天连一次反向都没有触发（第 ⑨ 条边界）。所以这一族今天不在本包：
  它属于被调用的代码，而不属于装配层。
```

### 10.3 五条边界

```text
1. 不新增第三方依赖：装配用到的每一个子系统都是快照内既有的。
2. 不改动任何既有模块、既有测试、pyproject 与 docs 下的既有文件——只新增文件。
3. 复现的是装配与读数，不是新的模型能力：不重写检索器、生成器或指标。
4. 全部读数离线、确定性：MockLLM + 固定语料 + 固定编码器，不联网、不读密钥。
5. README 与架构文档是从清单渲染出来的文本，本包不承诺它的文笔——
   它承诺的是"8 项能力每一项都出现在正文里"这条可断言的事实。
```

## 结语：三条可以带进结业项目（二）的工程结论

1. **"装上了"与"接上了"是两件事。** `import` 得到只是"装上了"；
   一次端到端调用里每段都真的跑过、而且同输入两次运行逐位相同，才叫"接上了"。
   今天把这句话做成了 `SystemRun.is_identical_to` ——**一条元组比较**。
2. **清单要能被程序核对，而不是被人抄。** 8 项能力落到 12 个候选子包，
   由 `importlib` 说了算；认领不到的 4 个包被**点名**而不是藏起来。
   "哪一项没被这次链碰到"这个问题，答案必须写在报告里。
3. **读数必须现场算出，且要能跟一个界比较。** 四条指标、费用、span 条数全部来自
   这次运行；每一条性质都带判据类型（相等 / 上界 / 下界）。
   没有界，读数只是描述；有了界，读数才是证据。

> **诚实的说明**：本课的九段链是**离线、确定性**的——模型是 `MockLLM` 的剧本、
> 语料是 6 条写死的记录、编码器是确定性字符 n-gram，因此它**不测量任何真实模型的质量**。
> 第 ⑦ 节的四条指标量的是**检索**（输入只有名单与金标准），不是答案；
> 第 ⑧ 节的费用来自**价格表折算**，不是账单；第 ⑨ 节的文档是渲染出来的文本，
> 它证明的是"覆盖完整"这条事实，不证明文笔。本课**没有** `import` 任何新依赖、
> **没有** GPU、**没有**真实向量库——它给的是**一套能带走的判据**：
> 当你在真实系统上做整合时，知道该断言哪七件事。

明天（day100）是 **G2：结业项目整合（二）**：在这条链之上接部署与服务，
完成演示脚本、学习总结与能力自评。今天定下的三件事会直接复用：
**九段链**、**清单与覆盖报告**、**三类判据与"缺席要可断言"的族常量**。
