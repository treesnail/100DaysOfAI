## 今日目标

1. **算清本地部署的账**——显存怎么算、量化怎么选，为什么"先算再跑"能省下几个小时的 OOM 排查。
2. **理解协议兼容的价值**——`LocalModel` 只继承 `OpenAICompatibleLLM` 就能与云端同接口，本地与云端的真正差异在**部署与运维**，不在调用协议。
3. **掌握本地服务特有的能力**——探活、模型常驻（`keep_alive`）、模型清单，这些是 OpenAI 兼容端点给不了、只有原生 API 才有的东西。
4. **给"换模型"一个可量化的决策依据**——一致性、延迟、成本三个口径，缺一个都会做出错误的省钱决策。

到 day044 为止，我们的 Agent 已经会省钱、会看图、会流式、会脱敏。但它所有请求都要**离开本机**：数据要发给第三方、每次调用都要计费、断网就不可用。这一课把模型搬回自己的机器，并回答一个比"怎么装"更重要的问题：**搬回来之后，我的 Agent 还是原来那个 Agent 吗？**

## 第一章：本地部署的取舍 —— 三个理由与三个代价

### 1.1 为什么要自己跑

把推理搬到本机，工程上通常只有三个真实理由：

| 理由 | 具体场景 | 本地为什么能解决 |
|------|---------|-----------------|
| **数据不出域** | 医疗、金融、法务的文档不能上传第三方 | 请求只在本机回环网络内，没有外发流量 |
| **成本可预测** | 高频调用（每条消息都过一次模型）按 token 计费会失控 | 边际成本趋近电费，与调用次数解耦 |
| **可控性** | 需要固定模型版本、固定量化、固定上下文 | 权重在本地磁盘，版本由你决定，不会被上游下架 |

注意这三条里**没有"效果更好"**——同参数量级的开源模型通常弱于顶级闭源模型。本地部署是拿"能力"换"合规与成本"，这个交换必须被显式承认，否则就会掉进下一个坑。

### 1.2 三个代价

1. **显存**：模型权重要全部装进显存（或内存，但速度差一个数量级）。8B 模型 FP16 需要约 14.9GB，量化到 Q4_K_M 约 4.2GB——**选错量化直接 OOM**。
2. **运维**：多了进程存活、模型加载、上下文长度、并发排队这些云端帮你托管的事。其中最要命的是**冷启动延迟**：模型不在显存里时，第一次请求要等权重加载（数秒到数十秒）。
3. **能力降级**：小模型在复杂推理、长上下文、严格格式遵循上会退化——这正是本章第六章要量化的东西。

### 1.3 本课最重要的一个结论：协议兼容胜过 SDK 封装

很多教程会教你把 LangChain、LlamaIndex、各家 SDK 都接一遍。但 2026 年的现实是：**Ollama 与 vLLM 都提供 OpenAI 兼容端点**，调用方式与访问云端一字不差：

```python
from openai import OpenAI

# Ollama：base_url 指到本机，api_key 传占位值（官方文档原话是 required but ignored）
client = OpenAI(base_url="http://localhost:11434/v1/", api_key="ollama")
client.chat.completions.create(model="qwen3:8b", messages=[{"role": "user", "content": "hi"}])

# vLLM：默认端口 8000，未加 --api-key 时不校验密钥
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
```

这意味着**昨天写的 `OpenAICompatibleLLM` 一行不用改**。所以本课不写"Ollama 客户端"，而是让 `LocalModel` 继承它，只补本地部署特有的三件事：端点规范化、占位密钥、能力自述。这就是"协议兼容比 SDK 封装更重要"——**封装会随 SDK 版本腐化，协议不会**。

> 后端选型提示：Ollama 原生支持 Windows/macOS/Linux，开箱即用、适合个人开发机；vLLM 是吞吐优先的生产级服务（PagedAttention、连续批处理），但**仅 Linux 原生支持**，Windows 需要 WSL2 或社区构建。本机是 Windows，所以本课以 Ollama 为主、vLLM 作为协议相同的进阶对照——两者在 `LocalModelSpec.backend` 上只是一个字段的差别。

## 第二章：先算再跑 —— 显存预算与量化选型

### 2.1 显存由两块构成

```
权重显存 = 参数量 × 每参数字节数
KV 缓存  = 2 × batch × 序列长度 × 层数 × KV 头数 × head_dim × KV 精度字节数
```

两个容易踩的点：

- **"2"是 Key 与 Value 两份张量**。做长上下文推理时，KV 缓存会超过权重成为显存大头；
- **`num_kv_heads` 不是注意力头数**。Llama/Qwen 系列用 GQA（分组查询注意力），KV 头数远小于注意力头数（Qwen3-8B 是 32 个注意力头但只有 8 个 KV 头），这正是长上下文能省显存的关键。写错这个数，估算会偏高 4 倍。

以 Qwen3-8B（36 层、8 个 KV 头、head_dim 128）在 4096 上下文、单序列、FP16 KV 为例：

```
权重（Q4_K_M，4.5 bpw）= 8e9 × 4.5/8 / 1024³ ≈ 4.19 GB
KV  = 2 × 1 × 4096 × 36 × 8 × 128 × 2 / 1024³ = 0.5625 GB
```

### 2.2 量化档位：每参数几个字节

```python
#: 常见量化档位的**每参数位数**（bits per weight, bpw）.
#: fp16/bf16 = 16、int8 = 8、int4 = 4 是理论值；GGUF 的 k-quant 是混合
#: 量化（不同张量用不同位宽），工程上按平均值计：Q8_0 ≈ 8.5、Q5_K_M ≈ 5.5、
#: Q4_K_M ≈ 4.5 bpw——Q4_K_M 是"质量损失可接受 + 显存几乎减半"的常用默认档。
QUANTIZATION_BITS: dict[str, float] = {
    "fp32": 32.0, "fp16": 16.0, "bf16": 16.0, "int8": 8.0,
    "q8_0": 8.5, "q5_k_m": 5.5, "q4_k_m": 4.5, "int4": 4.0,
}
```

为什么 `q4_k_m` 是 **4.5** 而不是 4？因为 GGUF 的 k-quant 是**混合量化**：关键张量（注意力输出、FFN 下投影）用更高位宽，其余压到 4 位，加权平均约 4.5 bpw。写 4.0 会低估显存，压着显存上限部署就会 OOM。

### 2.3 估算函数：把公式变成代码

```python
def estimate_vram_gb(
    params_b: float, *, quant: str = "q4_k_m",
    num_layers: int, kv_heads: int, head_dim: int,
    context_length: int = 4096, batch_size: int = 1,
    kv_dtype_bytes: int = 2, overhead_ratio: float = 0.1,
) -> tuple[float, float, float]:
    weights_bytes = params_b * 1e9 * bytes_per_parameter(quant)
    kv_bytes = 2 * batch_size * context_length * num_layers * kv_heads * head_dim * kv_dtype_bytes
    weights_gb = weights_bytes / BYTES_PER_GIB
    kv_gb = kv_bytes / BYTES_PER_GIB
    total_gb = (weights_gb + kv_gb) * (1 + overhead_ratio)
    return weights_gb, kv_gb, total_gb
```

`overhead_ratio=0.1` 覆盖推理框架的激活值、CUDA context 与显存碎片——**估算值只作"能不能装下"的判断门槛，不作精确承诺**。这也是为什么架构参数要求显式传入而不是内置一张模型表：架构随版本变化，猜错会让估算失去意义；宁可让调用方抄一次 `config.json`。

### 2.4 结论对象与反解

`plan_deployment` 把三个数字包装成可决策的结论：

```python
@dataclass
class HardwarePlan:
    params_b: float; quant: str; context_length: int
    weights_gb: float; kv_cache_gb: float; total_gb: float; gpu_vram_gb: float

    @property
    def fits(self) -> bool:
        return self.total_gb <= self.gpu_vram_gb

    @property
    def headroom_gb(self) -> float:
        return round(self.gpu_vram_gb - self.total_gb, 3)
```

实测（`scripts/local_deploy_demo.py` 第①段）：

```
显存    8GB → 需  5.23GB | 可部署：8.0B 模型以 q4_k_m 运行，预计占用 5.23 GB（权重 4.19 + KV 0.56），剩余 2.77 GB
显存   24GB → 需  5.23GB | 可部署……
可用的量化档位（24GB 显存）： ['fp16', 'q8_0', 'q5_k_m', 'q4_k_m']
12GB 显存下 FP16 权重需要： 16.0GB（不含 KV）
24GB 显存下单序列最大上下文： 128000 token
```

注意最后两行的对比：**12GB 显卡装不下 FP16 的 8B 权重（16GB），但同一张卡装 Q4_K_M 绰绰有余**——这就是量化存在的意义。`fitting_quantizations()` 给出"按质量从高到低，哪些档位装得下"，`max_context_tokens()` 则把 KV 公式反解，回答"显存还剩多少能给上下文"：24GB 下单序列可开到 128000 token（按 1024 向下取整）。生产上这两个函数就是部署前的 checklist。

## 第三章：LocalModel —— 与云端完全同一套接口

### 3.1 端点规范化：本地部署最高频的配置错误

用户写下 `http://localhost:11434`（漏了 `/v1`）时，OpenAI SDK 会把 `/chat/completions` 直接拼在 base_url 后面，得到 `http://localhost:11434/chat/completions` → **404**。这类错误排查起来很费时间，所以把它收敛进一个函数：

```python
def normalize_base_url(base_url: str, backend: str = OLLAMA) -> str:
    text = (base_url or "").strip()
    if not text:
        raise ValueError("base_url 不能为空")
    if "://" not in text:
        text = f"http://{text}"
    parsed = urlparse(text)
    if not parsed.hostname:
        raise ValueError(f"无法解析的 base_url: {base_url}")
    path = parsed.path.rstrip("/")
    if path in ("", "/"):
        return f"{parsed.scheme}://{parsed.netloc}/v1"
    return f"{parsed.scheme}://{parsed.netloc}{path}"
```

三种写法被收敛成一种：`http://localhost:11434` → `http://localhost:11434/v1`；`localhost:11434/v1/` → 去掉尾斜杠；`https://gw.example.com/proxy/llm` → **原样保留**。最后一条是克制的表现：只在路径为空时补 `/v1`，用户显式写了反向代理前缀就不该被改写。

### 3.2 LocalModelSpec：部署事实 vs 协议参数

```python
@dataclass
class LocalModelSpec:
    name: str
    backend: str = OLLAMA
    base_url: str | None = None
    api_key: str | None = None
    supports_vision: bool = False
    context_length: int = DEFAULT_OLLAMA_CONTEXT_LENGTH  # 4096，对齐 Ollama 默认
    keep_alive: str = DEFAULT_OLLAMA_KEEP_ALIVE          # "5m"，对齐 Ollama 默认
```

这些字段都是**部署事实**而非协议参数：同一个模型换个量化版本、换个上下文窗口就是另一份 spec，但调用协议完全不变。默认值刻意对齐 Ollama 官方行为——上下文窗口默认 **4096** token（可用 `OLLAMA_CONTEXT_LENGTH` 覆盖），模型空闲常驻默认 **5m**。占位密钥也按后端区分：Ollama 用 `"ollama"`，vLLM 用 `"EMPTY"`。

### 3.3 为什么继承而不是重写

```python
class LocalModel(OpenAICompatibleLLM):
    """本地推理服务上的模型，协议层面与云端模型完全等价."""
```

`chat` / `stream` / `chat_vision` 全部复用父类实现——Ollama 的 `/v1/chat/completions` 同样接受图像部件数组（文档里就是用 `qwen3-vl:8b` 加 data URL 举例的）。继承在这里不是省代码，而是**声明一个架构事实**：本地与云端的差异被限制在"部署与运维"这一层。

### 3.4 本地才需要的两件事：探活与清单

```python
    def is_available(self, timeout: float = 2.0) -> bool:
        try:
            self._client.models.list(timeout=timeout)
        except Exception as exc:
            logger.warning("本地模型 %s 不可用（%s）: %s", self.spec.name, self.spec.base_url, exc)
            return False
        return True

    def list_served_models(self, timeout: float = 2.0) -> list[str]:
        try:
            page = self._client.models.list(timeout=timeout)
        except Exception as exc:
            raise RuntimeError(f"无法访问本地 {self.spec.backend} 服务（{self.spec.base_url}）: {exc}") from exc
        return [item.id for item in getattr(page, "data", []) or []]
```

云端模型不需要探活——服务商保证它在那儿；本地服务则可能没启动、模型没 pull。所以这两个方法是**本地路线独有的运维接口**，且语义刻意相反：

- `is_available` **吞掉异常返回 False**——探活的语义是"返回事实"，调用方据此降级到云端模型；
- `list_served_models` **抛 RuntimeError**——你要的是清单，拿不到就必须报错，且错误信息里给出端点地址。模型名拼错（`qwen3:8b` 写成 `qwen3-8b`）是本地部署最高频的错误，列出候选能把"404 model not found"变成"你要的是不是其中之一"。

### 3.5 补上 function calling

父类 `OpenAICompatibleLLM` 没有实现 `chat_with_tools`（继承自 `BaseLLM` 的默认实现会抛 `NotImplementedError`）。但 Ollama 的兼容端点已支持 `tools` 字段，本地路线不该因"部署在本地"就降级回文本协议：

```python
    def chat_with_tools(self, messages, tools, temperature=0.7, max_tokens=1024) -> dict:
        resp = self._client.chat.completions.create(
            model=self.spec.name, messages=[m.to_dict() for m in messages],
            tools=tools, temperature=temperature, max_tokens=max_tokens,
        )
        message = resp.choices[0].message
        content = getattr(message, "content", None)
        calls = []
        for call in getattr(message, "tool_calls", None) or []:
            function = getattr(call, "function", None)
            calls.append({"id": getattr(call, "id", ""), "type": "function",
                          "function": {"name": getattr(function, "name", ""),
                                       "arguments": getattr(function, "arguments", "{}")}})
        result = {"content": content}
        if calls:
            result["tool_calls"] = calls
        return result
```

返回结构与 `MockLLM.chat_with_tools`、与 OpenAI 兼容约定三者一致：`arguments` 保持 **JSON 字符串**形态（解析交给 day037 的 `parse_tool_calls`），无工具调用时**省略** `tool_calls` 键——调用方统一用 `response.get("tool_calls")` 判断，不必区分 `None` 与空列表。

## 第四章：模型生命周期 —— keep_alive 与冷启动

### 4.1 两套 API 的分工

同一台 Ollama 进程上挂着两套路径，职责清晰：

| 路径 | 用途 | 谁在用 |
|------|------|--------|
| `/v1/*` | OpenAI 兼容推理（chat / embeddings / models） | `LocalModel`、`OllamaEmbedding` |
| `/api/tags` `/api/ps` `/api/pull` `/api/generate` | 原生运维（清单、常驻、拉取、加载） | `OllamaRuntime` |

`native_base_url()` 负责在两者之间转换（去掉尾部 `/v1`），避免运维层里散落字符串拼接。

### 4.2 keep_alive 的四种语义

模型加载进显存要花时间，卸载又要重新加载——`keep_alive` 就是"请求结束后模型在显存里待多久"的旋钮：

| 取值 | 语义 | 适用场景 |
|------|------|---------|
| `"5m"` | **默认**，请求后常驻 5 分钟 | 大多数开发场景 |
| `"1h"` / `"-1"` | 长常驻 / 永不卸载 | 生产预热，把首字延迟从"加载权重的十几秒"压到"纯推理的几百毫秒" |
| `0` | 请求返回后**立即卸载** | 显存要和别的服务共享时"用完即走" |

### 4.3 把运维动作做成可测的方法

```python
    def load_model(self, name, *, keep_alive=None, context_length=None) -> dict:
        payload = {"model": name, "keep_alive": self.keep_alive if keep_alive is None else keep_alive}
        if context_length is not None:
            if context_length <= 0:
                raise ValueError("context_length 必须为正整数")
            payload["options"] = {"num_ctx": context_length}
        return self._post("/api/generate", payload, f"加载模型 {name} 失败")

    def unload_model(self, name: str) -> dict:
        return self._post("/api/generate", {"model": name, "keep_alive": 0}, f"卸载模型 {name} 失败")
```

预热的方式就是文档给出的"发一个只有 `model` 字段的 `generate` 请求"——Ollama 会加载权重并立即返回，不产生任何 token；`context_length` 通过 `options.num_ctx` 下发，这是把 Ollama 默认 4096 调大的唯一入口。`unload_model` 则是 `keep_alive: 0` 的直译。

整层 HTTP 细节通过 `transport` 参数注入（默认是标准库 `urllib_transport`）：

```python
def urllib_transport(url: str, payload: dict[str, Any] | None) -> dict[str, Any]:
    """标准库实现的极简 JSON 传输：payload 为 None 走 GET，否则 POST."""
```

这个"把怎么发 HTTP 与发什么解耦"的设计让测试可以完全离线：桩函数记录 `(url, payload)`，直接断言请求体，不需要真的装 Ollama。演示脚本第③段的输出就是最好的说明：

```
本机模型： ['qwen3:8b', 'nomic-embed-text:latest']
常驻中： True
POST http://localhost:11434/api/generate  payload={'model': 'qwen3:8b', 'keep_alive': -1, 'options': {'num_ctx': 8192}}
POST http://localhost:11434/api/generate  payload={'model': 'qwen3:8b', 'keep_alive': 0}
POST http://localhost:11434/api/pull  payload={'model': 'qwen3-vl:8b', 'stream': False}
```

## 第五章：本地 embedding —— 把向量化也搬回来

### 5.1 与 day041 的衔接

day041 的 `EmbeddingProvider` 有四种实现（mock / char-ngram / sentence-transformer / openai），本日补上第五种 `OllamaEmbedding`：走 Ollama 的 OpenAI 兼容端点 `/v1/embeddings`，所以**调用代码与 `OpenAIEmbedding` 完全同构**，差别只在 base_url 指向本机、api_key 是占位值。常用的本地 embedding 模型是 `nomic-embed-text`（137M 参数、**768 维**、约 274MB）。

本地 embedding 的收益和 LLM 一样：RAG 的建库与检索都在本机完成，语料不出域。

### 5.2 维度必须探测，不能写死

云端 `text-embedding-3-*` 的维度可以从常量表查（1536/3072），本地模型不能：输出维度取决于权重文件，各家不一。所以维度做成**首次调用后从响应推断**的惰性属性：

```python
    @property
    def dimension(self) -> int:
        """向量维度：显式传入则直接返回，否则探测一次并缓存."""
        if self._dimension is None:
            self.embed("dimension probe")
        assert self._dimension is not None  # embed 成功后必然已回填
        return self._dimension

    def embed_batch(self, texts: list[str]) -> list[list[float]]:
        if not texts:
            return []
        resp = self._client.embeddings.create(model=self._model, input=list(texts))
        vectors = [list(item.embedding) for item in resp.data]
        if vectors and self._dimension is None:
            self._dimension = len(vectors[0])
        return vectors
```

**维度为什么是要紧事**：向量库（day041 的 `VectorStore`）与语义缓存（day043）都按维度对齐存储，维度不一致的向量混进同一个库，检索结果会**静默错乱**——不报错，只变笨。这类 bug 的成本远高于一次探测请求，所以宁可多花一次调用。

### 5.3 工厂的第五个分支

```python
    if provider == "ollama":
        return OllamaEmbedding(model=settings.local_embedding_model)
```

与 day041 的"离线可启动"哲学一致：默认仍是 `char-ngram`，`EMBEDDING_PROVIDER=ollama` 才切到本机服务。

## 第六章：换模型之前先量 —— 一致性 / 延迟 / 成本

本地部署最大的诱惑是"免费"，最大的坑是"悄悄变笨"。所以最后一步不是把模型跑起来，而是**给换模型这件事一个可量化的决策依据**。

### 6.1 三个指标，缺一不可

| 指标 | 怎么算 | 为什么不能省 |
|------|--------|-------------|
| **延迟** | 每次 `chat` 前后取 `clock()` 之差 | 本地不等于更快：单卡 8B 往往慢于云端集群 |
| **成本** | `token 数 / 1000 × 混合单价` | 本地按电费摊销（默认 0），云端按公开单价，同一口径才可比 |
| **一致性** | 两个模型回复向量的余弦相似度均值 | **最容易忽略、也最容易致命**：低于阈值意味着"换的不是成本，是产品" |

token 计数统一走 `llm.mock.estimate_tokens`：本地后端与云端后端对 usage 的上报口径未必一致，用同一个估算函数才能保证**对比的是模型而不是统计口径**。

### 6.2 一致性的实现

```python
        for local_case, cloud_case in zip(local_run.results, cloud_run.results, strict=True):
            vec_local = self.embedder.embed(local_case.reply)
            vec_cloud = self.embedder.embed(cloud_case.reply)
            similarities.append(round(cosine_similarity(vec_local, vec_cloud), 4))
```

`embedder` 缺省是离线可用的 `CharNgramEmbedding`（day041），余弦相似度复用 `memory/vector_store.py` 的 `cosine_similarity`——评估不该依赖网络，也不该因为"没配 embedding 密钥"就跑不起来。

### 6.3 从数字到决策

空样本与阈值是两处容易被写错的地方：

```python
    @property
    def agreement(self) -> float:
        """平均余弦相似度；无样本时为 0.0（而不是 1.0，避免"没测过就算达标"）."""
        if not self.similarities:
            return 0.0
        return round(sum(self.similarities) / len(self.similarities), 4)
```

`verdict()` 给出可直接引用的一句话结论，`worst_case()` 则定位**相似度最低的那条任务**——这是排查"到底哪里变了"的入口。演示脚本第④段的真实输出（Mock 桩模拟"本地回答更短、云端回答完整"）：

```
  agreement: 0.3383
  agreement_threshold: 0.8
  mean_latency_s: {'local': 1.5, 'cloud': 0.4}
  latency_ratio: 3.75
  cost: {'local': 0.0, 'cloud': 0.00034, 'saved': 0.00034}
  最差样本：解释一下 RAG 的检索步骤 → 本地回复「RAG 先检索再生成。」
  结论： 需谨慎：一致性 0.3383 < 阈值 0.8，换模型会改变 Agent 行为
```

结论很清楚：这个模型**省了钱但慢了 3.75 倍、一致性只有 0.34**——直接替换会让 Agent 的回答质量显著退化。正确的做法是**混合路由**：简单任务走本地，复杂任务交给云端（day033 的 `ModelRouter` 正好提供这个能力，`ModelSpec.cost_per_1k=0` 即可表达"本地边际成本为零"）。

## 结语：本地化之后的三条工程线索

1. **混合路由才是终局**：本课证明了"本地全面替代云端"通常不成立。下一步是把本地模型作为 `ModelRouter` 的一个候选（`cost_per_1k=0`、能力档位按实测一致性标定），让路由器做"省钱但不降质"的取舍——这正好衔接 day046 的集成优化。
2. **运维要自动化**：`OllamaRuntime` 的预热/卸载目前要手动调。生产上应该由启动脚本预热常驻模型、由显存监控在长空闲后卸载，把 `keep_alive` 当作容量规划的一部分。
3. **能力声明要落进路由**：`LocalModelSpec.supports_vision` 与 `context_length` 是路由层判断"这个请求本地能不能接"的依据。把它们接进 `ModelRouter` 的视觉/长度过滤，本地模型才能真正安全地参与自动选型。

明天（day046）我们进入 **大模型应用集成与优化**——把 M4 学到的 Prompt、模型路由、成本、安全与本课的本地部署整合到 SmartResearch Agent 主线，并用集成测试与性能基线把这条主线钉死。
