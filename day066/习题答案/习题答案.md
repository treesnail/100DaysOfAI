## 第一部分：选择题

### 第 1 题 —— B

**考点**：`fetch_k` 的口径（过取倍率 + 封顶）、封顶为什么必须进 `notes`、
`MAX_FETCH_K` 为什么直接复用上游常量。

**解析**：

第 3 步 `Retriever._fetch_depth`（`retrieval/retriever.py`，本模块 845 行）就是这道题的全部依据：

```python
top_k = query.top_k if query.top_k is not None else self._default_top_k
desired = (
    query.fetch_k
    if query.fetch_k is not None
    else int(math.ceil(top_k * self._fetch_multiplier))
)
fetch_k = max(top_k, desired)
if fetch_k > MAX_FETCH_K:
    notes.append(
        f"召回深度按 {self._fetch_multiplier} 倍本应取 {fetch_k} 条，"
        f"已封顶到 MAX_FETCH_K={MAX_FETCH_K}（与 vectorstore.MAX_TOP_K 同一个上限）"
    )
    fetch_k = MAX_FETCH_K
return fetch_k
```

三个常量只有一处定义（`retrieval/types.py`）：

```python
DEFAULT_FETCH_MULTIPLIER = 3      # 第 60 行：三道减法都要吃名额，最狠的一道要 3 倍深度
MAX_FETCH_K = MAX_TOP_K           # 第 65 行：**直接复用** vectorstore.base.MAX_TOP_K
DEFAULT_MIN_HIT_CHARS = 32        # 第 70 行
```

而 `vectorstore/base.py` 第 110 行写的是 `MAX_TOP_K = 1000`，注释说明理由是
"一份 10 万块的库取 `top_k=100000` 会把整库搬进响应体里"。
`types.py` 第 62-64 行的注释把"为什么必须复用同一个常量"写死了：

> 两个数字一旦分开，就会出现"检索深度 2000、库侧上限 1000"这种自相矛盾的配置，
> 而它的表现是"设置里写 2000、实际只取了 1000"——一个必须靠读代码才能发现的差值。

演示脚本第 2 节（`outputs/retrieval_demo.txt`）的四行原文正好把"倍率算"与"封顶"分开：

```text
 构造参数缺省时读 settings：retrieval_top_k=5、retrieval_fetch_multiplier=3、MAX_FETCH_K=1000
  查询：'检索的阈值与过滤条件怎么落刀'
 top_k | fetch_k |   候选 |   命中 |     top_k 截断丢掉
     3 |       9 |    8 |    3 |              5
     5 |      15 |    8 |    5 |              3
     8 |      24 |    8 |    8 |              0
  1000 |    1000 |    8 |    8 |              0
       注记：召回深度按 3 倍本应取 3000 条，已封顶到 MAX_FETCH_K=1000（与 vectorstore.MAX_TOP_K 同一个上限）
```

`3 → 9`、`5 → 15`、`8 → 24` 是 `ceil(top_k × 3)`；最后一行是本节的封顶：
`ceil(1000 × 3) = 3000`，封到 1000，**而且这件事写进了 `notes`**。
测试里还有一对边界用例（`tests/test_retrieval_retriever.py::test_cap_boundary`）：

```python
@pytest.mark.parametrize(
    ("top_k", "expected", "capped"),
    [(333, 999, False), (334, 1000, True)],
)
def test_cap_boundary(self, top_k: int, expected: int, capped: bool) -> None:
    """恰好不超过上限时不封顶（333×3=999 → 原样；334×3=1002 → 封顶）."""
    result = sample_retriever(default_top_k=top_k).retrieve(AXIS)

    assert result.fetch_k == expected
    assert any("已封顶" in note for note in result.notes) is capped
```

`333 × 3 = 999` 原样保留，`334 × 3 = 1002 → 1000` 且必须留一句注记。
`MAX_FETCH_K` 还从另一条路被读出来：`api/routes.py::retrieval_defaults()`
把它作为 `"max_fetch_k"` 一并返回给 `/retrieval/status`，理由写在那个函数的 docstring 里
——"我设了 2000 为什么只取了 1000"这个问题只能靠它回答。

**其余选项为什么错**：

- `A` 错：这正是手册里显式纠正过的一条（`docs/retrieval.md` 第 9 节常见误区第 7 条：
  "`top_k` 就是召回深度"→ 事实是 `max(top_k, ceil(top_k × 3))`，
  `top_k=5` → 15，且封顶 1000）。`fetch_k` 与 `top_k` 是两个字段、两条语义：
  `top_k` 决定"最终返回几条"，`fetch_k` 决定"取多深"，三道减法吃的都是深度的名额。
- `C` 错：封顶**不是沉默的**。演示第 2 节最后一行就是那句话；测试
  `test_depth_is_capped_with_a_note` 的注释写得更直接——"封顶必须在 `notes` 里说明：
  否则'设置里写 400、实际取 1000'要靠读代码发现"。注记与错误信息走的是两条通道：
  前者进 `RetrievalResult.notes`，后者才抛异常，不会互相淹没。
- `D` 错：`top_k` 的**构造期**校验只拦 `> MAX_FETCH_K` 的取值
  （`_resolve_top_k` 的 `if resolved > MAX_FETCH_K: raise QueryError(...超过上限...)`），
  而"倍率算出的深度超过上限"是**运行期**的常规收敛（封顶 + 注记），不是调用方错误：
  `default_top_k=334` 是一个合法的、可以被服务的最深请求，只是服务不了 1002 条而已。

**结论**：深度 = `max(top_k, ceil(top_k × multiplier))`，倍率是"三道减法的下界"（3），
封顶是硬上限（1000，与 `vectorstore.MAX_TOP_K` 同一个常量），
封顶这种"静默改写"必须变成一句能被读出来的 `notes`。

### 第 2 题 —— C

**考点**：`TimeRange` 的三条约定（闭区间 / 按 ISO 文本比较 / 字段缺失被排除）、
`where` 与 `time_range` 撞在同一字段时为什么必须报错而不是取交集。

**解析**：

三条约定同时写在 `retrieval/types.py::TimeRange` 的类 docstring 与
`retrieval/filters.py` 的模块 docstring 里（**同一份规则只有一处定义**，两处互相引用）：

```text
1) 闭区间 [start, end]       两端可单独省略；两端都省略 = "没有时间条件"
2) 按 ISO 文本比较           库里存什么就比什么（要求入库时统一成同一种 ISO 文本）
3) 字段缺失的记录被排除      $gte 对缺失字段返回 False —— 这不是 bug
```

第 2 条是**显式约定，不是实现细节**：库里存什么就比什么，因为
"对同一种 ISO 文本（`YYYY-MM-DD` 或 `YYYY-MM-DDTHH:MM:SS`），**字典序与时间序一致**"，
而一旦库里混进 `"2026/09/20"` 这种写法，更该修的是入库口径，
而不是让检索器去猜每一条的时间格式。`_parse_iso` 只做三件事：
`Z` 结尾换成 `+00:00`（Python 3.10 的 `fromisoformat` 不认 `Z`）、
只给日期时按当日 `00:00:00` 解释、其余交给标准库（失败即 `QueryError`，
消息里列出三种可接受写法）。另外两种当场拒掉的情形写在 `TimeRange.__post_init__`：
时区混用（`start="2026-09-01"` 配 `end="2026-09-02T00:00:00+08:00"`）与区间倒置
（`start > end`，"倒置的区间必然返回空结果，因此在这里当场拒掉"）。

翻译成子句只有三种形状（`filters.time_range_clause`，实测返回值）：

```python
time_range_clause(TimeRange(start="2026-09-01", end="2026-09-30"))
# {'$and': [{'created_at': {'$gte': '2026-09-01'}}, {'created_at': {'$lte': '2026-09-30'}}]}

time_range_clause(TimeRange(start="2026-09-01"))
# {'created_at': {'$gte': '2026-09-01'}}

time_range_clause(TimeRange())
# {}   ← 两端都没给 = 这次不涉及时间条件（与"区间宽度为 0"是两件事）
```

双端**必须**用 `$and` 包一层：`vectorstore.filters._compile_field` 明确拒绝
"同一字段多个运算符"的条件，`$and` 是那层留下的唯一合法写法。

第 3 条约定在演示第 4 节有一个可核对的数字（8 条记录里 2 条没有 `created_at`）：

```text
 时间范围                                        候选 | 命中的 id
 created_at ∈ [2026-03-01, 2026-03-31]        3 | [...]
 created_at ∈ [2026-04-01, 2026-04-30]        3 | [...]
 created_at ∈ [2026-01-01, 2026-12-31]        6 | [...]（6 个 id）
 created_at ∈ [2026-04-12, +∞]                1 | [...]
 （这里的 top_k 取 8 = 库的大小，因此打印出来的 id 就是**全部候选**）

 第三条（整年区间）是本节的对照：区间覆盖了全部数据，候选却只有 6 条——
 缺 created_at 的那两条**既不在区间内、也不在区间外**，它们被排除了。
```

（那两条是 `1c8b4a95e370d26f` 与 `e9352d70b84a1c6f`，见演示第 1 节
"没有 created_at 的记录"那一行。）机制在 `vectorstore/filters.py::_operator_predicate`：
比较谓词对 `metadata.get(field) is None` 直接判为不命中。

撞车检测在 `filters.combine_where`，消息原文（演示第 4 节末尾）：

```text
过滤条件冲突：字段 'created_at' 同时出现在 where 与 time_range 里。同一个字段的两组条件请
自己合并成一个显式区间——例如把 where 里的条件删掉、改用 TimeRange(start=..., end=...)；
不合并的话，'我到底想要哪一段'会由两份条件取交集的副作用决定，而结果只会变少、不会报错。
```

合成结果**语义上是可解释的**，但它"查得出结果、也不报错"，只是比预期少——
这类"少而不报"正是本课要消灭的东西，所以选择当场报 `QueryError`，
把两个可能都成立的意图交回调用方决定（`filters.py` 模块 docstring 的原文）。
字段名的提取走 `vectorstore.filter_fields`，它会递归并跳过 `$and`/`$or`，
因此嵌套子句里的 `created_at` 也发现得了
（`tests/test_retrieval_filters.py::test_conflict_is_found_inside_nested_clauses`）。

**其余选项为什么错**：

- `A` 错：本包**不做**"解析成 `datetime` 再比"。理由是把 ISO 字符串直接交给
  `$gte`/`$lte` 时，字典序与时间序对同一种 ISO 文本是一致的——这是显式约定；
  而 `_parse_iso` 解析出来的 `datetime` 只用于两件事：判断倒置与时区混用，
  它们都不参与库侧比较。
- `B` 错：取交集"顺手合并"是**必须拒绝**的做法（`filters.py` 模块 docstring：
  "'我要 1 月之后'与'我要 6 月之后'放在一起，真实意图通常是'我复制粘贴时忘了删一个'"）。
  更关键的是：它的错误表现是"结果比预期少"而**不报错**，所以不给它静默发生的机会。
- `D` 错：把缺失当"现在"正是第 3 条约定明确拒绝的替代方案——"会让'这条什么时候建的'
  这个问题得到一个编出来的答案，而错误的时间过滤不报错，只表现为'过滤之后少了几条'"。
  本层的选择是**宁可少召回，也不猜一个时间**。

**结论**：时间范围是一个字段 + 一个闭区间，比较按 ISO 文本（字典序 = 时间序），
缺字段者被排除；`where` 与 `time_range` 撞在同一个字段**必须报错**，
冲突只在时间子句非空时判（空区间的 `{}` 不产生任何条件）。

### 第 3 题 —— C

**考点**：阈值在**检索器层**落刀且用 `>=`、三个 `dropped_*` 不能合并、
`dropped_by_top_k` 不是问题。

**解析**：

`retriever.py` 模块 docstring 的"第 6 步为什么必须在本层落刀"一节：

```text
交给库过滤   candidates=5、hits=2      → "切掉了几条"这个数字拿不到
在本层落刀   candidates=5、dropped=3   → 数字拿得到（正是 day067 融合要用的）
```

证据在 `retrieve` 的第 5 步那一行——`min_score` **没有**被传进去：

```python
# 第 5 步：库侧查询。min_score **不传给库**——理由见模块 docstring 第 6 步。
search = self._backend.query(vector, fetch_k, where=combined)
```

而真正落刀的是 `_apply_threshold`（用 `>=`，与库侧那一行逐字一致）：

```python
if min_score is None:
    return list(hits), 0
threshold = float(min_score)
kept: list[RetrievalHit] = []
dropped = 0
for hit in hits:
    if hit.score >= threshold:
        kept.append(hit)
    else:
        dropped += 1
return kept, dropped
```

并且有专门用例把"与本层语义一致"钉住
（`tests/test_retrieval_retriever.py::test_threshold_matches_the_backend_semantics`）：

```python
store = sample_store()
backend_hits = store.query(TableEmbedding().embed(AXIS), 15, min_score=0.6).ids()

result = sample_retriever(store, min_score=0.6).retrieve(AXIS)

assert result.ids() == backend_hits
```

"同一个 `>=`、同一个分数口径"这条纪律的另一半是 `>=` vs `>`：
`_apply_threshold` 的 docstring 说"一个 `>` 与 `>=` 的差别在'阈值恰好等于某条命中分数'时
体现出来，而那种情形**必然出现**——同一个确定性编码器对同文本给出逐位相同的向量"。
测试样本里 `c-a-02` 在 `axis` 查询下的分数**精确等于 0.8**，于是：

```python
def test_hit_equal_to_the_threshold_is_kept(self) -> None:
    result = sample_retriever(min_score=0.8).retrieve(AXIS)

    assert result.hits[-1].record_id == "c-a-02"
    assert result.hits[-1].score == 0.8
```

三个 `dropped_*` 的名字与"该去调哪个参数"是一一对应的（`retrieval/types.py` 模块 docstring）：

```text
dropped_below_threshold  阈值落刀切掉的       → 阈值定得太高（retrieval_min_score）
dropped_by_diversity     同文档挤掉的         → max_per_doc 定得太低（retrieval_max_per_doc）
dropped_by_top_k         截断到 top_k 丢掉的  → 这只是"取够了"，不是问题
```

"合成一个 `dropped` 是一个看起来无害、实际上致命的简化"：
"阈值切掉 3 条"要去调 `retrieval_min_score`，"多样性挤掉 3 条"要去调
`retrieval_max_per_doc`，合成之后这两个动作的判据就没了；更糟的是
day067 的融合需要用这个数字判断"这一路是不是一条都没活下来"。
演示第 5 节的实测把三个数字的账对得很平：

```text
取第 3 名的分数当阈值（min_score=0.193122，>= 才保留）：
  cosine | 深度 15 | 候选 8 | 命中 3 | hits | ...
  dropped_below_threshold=5 count=3 → 阈值切掉了 5 条
  这笔账要对上：候选 8 条 - 阈值切掉 5 条 = 剩下 3 条

阈值高到一条不剩（余弦的分数上界是 1.0，这里给 1.5）：
  candidates=8（候选还在）count=0 empty_reason=below_threshold
```

`API` 侧也是按这三个数字给出路的（`api/routes.py::retrieval_search` 的 docstring 表格）：
`dropped_below_threshold → 去调 settings.retrieval_min_score`、
`dropped_by_diversity → 去调 settings.retrieval_max_per_doc`、
`dropped_by_top_k → 这只是"取够了"`。

**其余选项为什么错**：

- `A` 错：结果集合确实逐条相同（这一点 `C` 也承认），但"在哪里切"不是性能问题——
  差别在"这个数字有没有被记下来"。交给库过滤之后，`RetrievalResult` 里的
  `dropped_below_threshold` 会永远是 0，而 day067 的按通道融合要靠它区分
  "一路被阈值清零"与"一路本来就没召回"（前者降权、后者可以补其他路的权重）。
- `B` 错：见上面的三段对应表。合成一个数字之后，"该调哪个参数"这个问题
  就永远无法回答——`retrieval/__init__.py` 的第 2 条纪律写的就是这件事。
- `D` 错：手册常见误区第 2 条正是它——"`dropped_by_top_k` 是异常"→
  事实是"它只是'取够了'，不是问题；要查的是另外两个"。原因是深度本身带过取倍率
  （默认 3 倍），深度取回的条数天然多于 `top_k`，被截断掉一部分是设计内的行为。

**结论**：阈值在本层落刀（`>=`，与库侧同口径）以便留下 `dropped_below_threshold`；
三个 `dropped_*` 各自对应一个可调参数，`dropped_by_top_k` 只是"取够了"。

### 第 4 题 —— D

**考点**：`empty_reason` 的封闭清单与优先级、`EMPTY_REASON_DIVERSITY` 的不可达性、
`RetrievalResult.__post_init__` 的两道自检。

**解析**：

清单与优先级在 `retrieval/types.py`（顺序 = 诊断优先级顺序）：

```python
EMPTY_REASON_NONE = "hits"                    # 有命中：不是"失败原因"，是"没有失败"的哨兵值
EMPTY_REASON_NO_DATA = "no_data"              # 库是空的（合法状态，不是错误）
EMPTY_REASON_FILTERED_OUT = "filtered_out"    # 过滤把候选筛成 0
EMPTY_REASON_BELOW_THRESHOLD = "below_threshold"   # 阈值把命中全切了
EMPTY_REASON_DIVERSITY = "diversity_trimmed"  # max_per_doc 把命中全挤掉了（防御性分支）

EMPTY_REASONS: tuple[str, ...] = (
    EMPTY_REASON_NONE, EMPTY_REASON_NO_DATA, EMPTY_REASON_FILTERED_OUT,
    EMPTY_REASON_BELOW_THRESHOLD, EMPTY_REASON_DIVERSITY,
)
```

`EMPTY_REASON_DESCRIPTIONS` 是这几句人话的**唯一来源**（`explain()` 与端点直接引用它）：

```text
no_data            库是空的（合法状态）：请先建索引
filtered_out       过滤条件把候选筛成了 0 条：请放宽 where 或时间范围
below_threshold    min_score 把命中的全切了：请降低阈值或不设阈值
diversity_trimmed  max_per_doc 把命中的全挤掉了：请放宽每文档条数
```

判定在 `retriever.py::_diagnose`，分支顺序就是优先级，最后两条各挡一种"报告不能是空的"：

```python
if hits:
    return EMPTY_REASON_NONE
if count_store == 0:
    return EMPTY_REASON_NO_DATA
if filter_applied and candidates == 0:
    return EMPTY_REASON_FILTERED_OUT
if dropped_below_threshold:
    return EMPTY_REASON_BELOW_THRESHOLD
if dropped_by_diversity:
    return EMPTY_REASON_DIVERSITY
if filter_applied:
    return EMPTY_REASON_FILTERED_OUT
# 库非空、无过滤、无阈值、无多样性，却一条都没排出来 → 归到"库里没有可用的数据"
return EMPTY_REASON_NO_DATA
```

文档里那句"为什么只允许一个值"写得很直白：

> 空结果的四种成因对应的动作完全不同（建索引 / 放宽过滤 / 降阈值 / 放宽多样性），
> **报告里写四条可能的猜测等于什么都没说**。优先级把**更靠上游的成因**排在前面：
> 库是空的，就谈不上"被阈值切掉"（根本没东西可切）。

`diversity_trimmed` 的可达性事实写在 `_diagnose` 的 docstring 里，是全课最值钱的一段注释：

```text
一个必须写下来的可达性事实："diversity_trimmed" 这一支在当前算法下**端到端不可达**
——第 7 步里每一组至少会留下一条（used >= limit 只对第二、第三条之后的命中成立），
因此 dropped_by_diversity > 0 时 kept 必然非空。保留这一支的理由是**诊断规则不该依赖
某一步的内部细节**：一旦第 7 步改成"每组至少两条"或"只保留主文档"，这个分支就会立刻
变成活路径，而那时它必须在正确的位置（阈值之后、兜底之前）。
```

它的"位置"与"不可达"两件事各有专门用例
（`tests/test_retrieval_retriever.py` 的两个单元级构造）：

```python
def test_diversity_trimmed_is_a_unit_level_branch(self) -> None:
    reason = _diagnose(hits=(), count_store=8, candidates=8, filter_applied=False,
                       dropped_below_threshold=0, dropped_by_diversity=2)
    assert reason == EMPTY_REASON_DIVERSITY

def test_diversity_is_checked_after_the_threshold(self) -> None:
    reason = _diagnose(hits=(), count_store=8, candidates=8, filter_applied=False,
                       dropped_below_threshold=3, dropped_by_diversity=2)
    assert reason == EMPTY_REASON_BELOW_THRESHOLD
```

端到端路径上的实测对照（手册第 4 节，5 条记录的小库探针）：

```text
where={"strategy": "nope"}   → 0 条 filtered_out      （candidates=0，filter_applied=True）
min_score=0.99               → 0 条 below_threshold    （dropped_below_threshold=5，candidates=5）
max_per_doc=1                → 3 条 hits               （dropped_by_diversity=2，但一条都没被挤完）
空库                          → 0 条 no_data           （fetch_k 仍然是算过的 9）
```

最后一行是"深度先算、体检后做"的直接证据，也是第 9 题第 1 问要用的数字。
另外 `RetrievalResult.__post_init__` 把两条纪律钉在构造期：`empty_reason`
必须是五个取值之一；**"有命中却报告非 `hits`"直接被拒**——互相矛盾的结果会让诊断失去意义。

**其余选项为什么错**：

- `A` 错：这正是本层要消灭的写法。"四条可能的猜测"对读报告的人来说信息量为 0，
  而四种成因的动作完全不同；`(_diagnose)` 因此只给一个结论。
- `B` 错：`max_per_doc=1` 时每组**至少留一条**（`used >= limit` 只对第二、第三条之后的
  命中成立），演示第 6 节实测 `max_per_doc=1` 仍然拿到 3 条命中
  （`3 份文档各留一条`，`dropped_by_diversity=5`）——它绝不会把结果挤成空。
  这是手册常见误区第 4 条。
- `C` 错：改成"阈值 → 过滤 → 库空"会让"库是空的"这类结论永远说不出口——
  库空时 `dropped_below_threshold` 本来就是 0（没东西可切），顺序看似无差别；
  但一旦库空**又恰好**开着过滤（`filter_applied=True` 且 `candidates=0`），
  按 `C` 的顺序就会报 `filtered_out`，把"请先建索引"错报成"请放宽过滤条件"。
  上游成因会掩盖下游成因，这正是优先级存在的理由。

**结论**：`empty_reason` 只给一个值、来自封闭清单，顺序 = 优先级（库空 > 过滤 > 阈值 > 多样性）；
`diversity_trimmed` 是防御性分支，保留它是因为诊断规则不该依赖第 7 步的内部细节。

### 第 5 题 —— C

**考点**：三个预算数字的出处、五步打包顺序、`truncated_hits` 的口径、"至少保一条"。

**解析**：

三个数字都在 `config.py` 与 `retrieval/types.py` 里，注释写明了取值理由：

```python
# config.py（retrieval_* 组，8 项）
retrieval_max_context_chars: int = 2400   # 按"6 个 ~400 字的片段"标定：够放下 top-5 的全部正文，又不至于把 4k 上下文撑满
retrieval_per_hit_chars: int = 800        # 预算的 1/3：一条过长时先截断它，而不是让它把整包预算吃光

# retrieval/types.py
DEFAULT_MIN_HIT_CHARS = 32                # 低于它的片段进上下文只是噪声（"阈值设为 0.85"离开标题就毫无意义）
```

打包函数 `context.py::pack_context` 的 docstring 把五步写成了固定顺序
（**每一步都会改变"还剩多少预算"**）：

```text
1. 解析预算     None → settings.retrieval_max_context_chars / retrieval_per_hit_chars
2. 单条截断     超 per_hit_chars 的块被截断并记 truncated_hits（它仍然在包里）
3. 拼包         用 BLOCK_SEPARATOR 连成一段
4. 丢尾         整包超预算 → 从**最后一条**开始整条丢，记进 dropped_hits
5. 至少保一条   只剩一条还超预算 → 把它截到 max_chars，**返回它而不是返回空**
```

第 5 步是这一层最重要的护栏（docstring 原话）：**"预算紧"不等于"没有上下文"**，
"返回空上下文会让 RAG 链路走进'检索为空'的分支，于是模型一次都不被调用
——一个因为打包而发生的静默降级，看起来与'库里没有相关内容'一模一样"。
而"至少保一条"那次截断**不计**进 `truncated_hits`，理由也写在同一处：

```text
第 2 步与第 5 步的截断**只记第 2 步**：truncated_hits 的定义是"被单条上限截断的条数"。
第 5 步那次截断的证据在 char_count == max_chars 上（包被削到刚好占满）。
```

两个常量与两种损失的性质：

```python
BLOCK_SEPARATOR = "\n\n"     # 每个块自己就带换行，单换行会让"下一条从哪开始"看不出来
TRUNCATION_MARKER = "…"      # 截断的痕迹要在提示词里看得见：不补标记时模型会顺手把话补完
```

"先截单条、再丢尾部"这个顺序不是随手定的：**截断**是"这一条少半句"（内容损失，
去调 `retrieval_per_hit_chars`）、**丢尾**是"整条不见了"（召回损失，
去调 `retrieval_max_context_chars`）；反过来或平均切每一段，报告里就只剩一个"包满了"，
"该调哪个参数"从此无从回答。

演示第 8 节的实测把三种预算下的结果都打了出来：

```text
[8.2 降级] 把预算压到 max_context_chars=220 / per_hit_chars=60：
  直接调用 pack_context → 上下文 184/220 字（占用 83.6%） | 引用 3 条 | 截断 3 条 | 丢尾 2 条
    进上下文 3 条 / 丢掉 2 条 / 截断 3 条
    进上下文的编号：[1]、[2]、[3]（与文本里的 [n] 一一对应：True）
    预算压到 60 字（放不下两条）→ 上下文 60/60 字（占用 100.0%） | 引用 1 条 | 截断 1 条 | 丢尾 4 条：
      **至少保住一条**，返回的不是空上下文
    预算 20 字（连单条下限 32 字都放不下）→ ContextError：
```

`220` 字下占用 83.6%、截断 3 条、丢尾 2 条；压到 `60` 字时占用 100%、
**引用还有 1 条**（就是"至少保一条"）。记账也有一组可手算的用例
（`tests/test_retrieval_context.py`，块头 13 字 + 换行 + 10 字正文 = 24 字）：

```text
50 ≤ 60 < 76：留下的正好是前两条 → count == 2、char_count == 50
两块之间 2 个分隔符：24×3 + 2×2 = 76（三条都不截，per_hit_chars 是单条上限）
fill_ratio == 0.8333（50/60 保留 4 位）
```

**其余选项为什么错**：

- `A` 错：这就是模块 docstring 里被否掉的"平均切每一段"——"每条都变短，
  看不出'是哪一条吃掉了预算'"，报告里只剩一个"包满了"。
- `B` 错：截断与丢弃是两件事，混起来会让 `truncated_hits` 与 `dropped_hits` 失去各自的意义。
  超过单条上限的块**仍然在包里**（只是被截短），只有整包超预算才从尾部整条丢；
  测试里 `test_truncates_an_over_long_hit_and_counts_it` 明确断言
  `result.dropped_hits == ()` 与 `assert result.count == 1`。
- `D` 错：这正是 `PackedContext` 的字段说明里被否掉的写法——"一个要去调预算，
  一个要去调单条上限，合成一个数字之后'该调哪个参数'就答不出来了"，
  与 `RetrievalResult` 的三个 `dropped_*` 是同一条理由。

**结论**：预算 = 2400/800/32（config 与 types 两处定义），五步顺序不可换，
"至少保一条"把"预算紧"与"没有上下文"分开，而它那次截断的证据是
`char_count == max_chars` 而不是计数。

## 第二部分：判断题

### 第 6 题 —— 错

**考点**：`combine_where` 与"库是空的"早退之间的顺序。

**解析**：

`retriever.py::Retriever.retrieve` 里那段注释直接回答了这道题（原文）：

```python
# 第 5 步（子句部分）：合成过滤条件。**必须排在"库是空的"这条早退之前**：
# 它只是拼字典，而"where 与 time_range 撞在同一个字段"这种调用方错误
# 在任何库状态下都该报出来——否则同一个错误会在库非空时抛 QueryError、
# 在库为空时被静默降级成 empty_reason=no_data，而后者让调用方以为
# "条件是合并生效的，只是恰好没数据"。（这一条是被 day066 的测试
# `test_filter_conflict_is_reported_even_on_an_empty_store` 逼出来的：
# 最初的实现把早退放在这里之前，行为与这段注释相反。）
combined = combine_where(resolved.where, resolved.time_range)

if state.count_store == 0:
    notes.append("库是空的（count=0）：这是合法状态，直接返回空结果而不报错")
```

对应用例（`tests/test_retrieval_retriever.py`）把两种库状态都断言了一遍：

```python
conflict_query = RetrievalQuery(
    text=AXIS,
    where={"created_at": "2026-01-01"},
    time_range=TimeRange(start="2026-06-01"),
)
with pytest.raises(QueryError):
    sample_retriever().retrieve(conflict_query)

with pytest.raises(QueryError):
    sample_retriever(empty_store()).retrieve(conflict_query)
```

"错误的库状态改变不了错误的查询"——这句话是用例 docstring 的原话。
反过来，正确顺序还有一个附带好处：错误消息由 `filters.combine_where` 统一给出，
不会出现"同一个错误在库空时变成 `no_data`、在库非空时变成 `QueryError`"两种表现。

**结论**：错。顺序是"先规范化查询 → 算深度 → 体检 → **合成过滤条件** → 才是空库早退"，
这样调用方错误在任何库状态下都报得出来。

### 第 7 题 —— 对

**考点**：`dropped_by_top_k` 的语义，以及三个 `dropped_*` 各自对应的参数。

**解析**：

`retrieval/types.py` 的模块 docstring 就是这句判断的出处：

```text
dropped_below_threshold  阈值落刀切掉的       → 阈值定得太高
dropped_by_diversity     同文档挤掉的         → max_per_doc 定得太低
dropped_by_top_k         截断到 top_k 丢掉的  → 这只是"取够了"，不是问题
```

手册常见误区第 2 条把这条写成了"误区→事实"的形式：
"`dropped_by_top_k` 是异常" → "它只是'取够了'，不是问题；要查的是另外两个"。
三条边界行为在端点层也是这么写的（`api/routes.py::retrieval_search`）：

```text
dropped_below_threshold  阈值切掉几条 → 去调 settings.retrieval_min_score
dropped_by_diversity     每文档上限挤掉几条 → 去调 settings.retrieval_max_per_doc
dropped_by_top_k         截断到 top_k 丢掉几条 → 这只是"取够了"
```

**结论**：对。深度默认按 3 倍过取，所以"取回来的多于要返回的"是**设计内**的常态；
`dropped_by_top_k > 0` 不需要任何动作，另外两个数字才是指向参数的那两个。

### 第 8 题 —— 错

**考点**：`RagAnswer.llm_called` 为什么不靠字符串比较、提示词占位符为什么必须构造期校验。

**解析**：

两个判断各有一条写在源码里的理由。第一条在 `retrieval/pipeline.py::RagAnswer` 的 docstring：

> `llm_called` 单独成为一个字段而不是"看 answer 等不等于 fallback"：
> **判定不能依赖字符串比较**——兜底答复将来改一个字，那种判定就静默失效。
> 它是护栏的**证据**：`llm_called=False` 且 `citations=()` 表示
> "模型这次没有机会自由发挥"。

`pipeline.answer` 的空结果分支返回的就是这份证据的四件套：

```python
if retrieval.is_empty:
    return RagAnswer(
        question=question_text,
        answer=self._fallback_answer,
        citations=(),
        context=None,
        retrieval=retrieval,
        llm_called=False,
        notes=tuple(_empty_notes(retrieval)),
    )
```

第二条在 `_validate_prompt` 的 docstring：

> 用 `string.Formatter().parse` 而不是"字符串里搜 `"{context}"`"：后者会把
> `{{context}}`（转义之后的字面量）也当成占位符，而那种模板渲染出来是一段谁也读不懂的文本。
> ……为什么必须在构造期报错：缺占位符的模板 `format` **不会失败**（多余的参数被忽略），
> 于是模型收到的是一段**没有资料的提示词**——它照着模板回答，看起来一切正常，
> 实际上一次检索都没用上。

两条都有用例钉住：`test_the_misspelling_is_caught_before_any_llm_call`
（覆盖参数校验在检索与调用之前，`llm.calls == 0`）与
`test_escaped_braces_are_not_placeholders`（`{{context}} 与 {{question}}` 照样被拒）。

**结论**：错。兜底文案是可以改的（改了之后字符串比较就静默失效），
因此护栏的证据必须是字段 `llm_called`；而缺占位符的模板恰恰**不会**报错，
所以它必须在构造期被拦——那正是这道护栏在链路起点上的延伸。

## 第三部分：简答题

### 第 9 题（九步流水线、撞车检测与空结果诊断）

#### 1. 九步的顺序，以及第 3 步为什么排在体检之前

顺序写在 `retriever.py` 的模块 docstring 与 `retrieve` 的逐行注释里（一一对应）：

```text
1. 规范化查询      str → RetrievalQuery；None 字段填构造参数 / settings   → _normalize_query
2. 索引体检        条数 + 清单漂移；严格模式下漂移直接抛 IndexStateError   → _inspect_index
3. 算召回深度      fetch_k = max(top_k, ceil(top_k × multiplier))，封顶 1000 → _fetch_depth
4. 编码查询        embed(text) + 三项校验（维度 / 有限 / 非零）             → _encode_query
5. 库侧过滤        combine_where(where, time_range) 交给 backend.query     → filters.combine_where
6. 阈值落刀        在本层按 min_score 过滤并记「切掉了几条」                → _apply_threshold
7. 多样性裁剪      按 doc_id 分组，每组留前 max_per_doc 条，其余记数        → _apply_diversity
8. 截断到 top_k    重排名次（分数降序 + id 升序）并记「截断丢掉几条」        → _rerank
9. 诊断与装配      定 empty_reason、算延迟、收集 notes                      → _diagnose
```

第 3 步与第 2 步的**代码顺序**是反的（先算深度、再做体检），理由写在 `retrieve` 里：

```python
# 第 3 步：算召回深度。**在体检之前算**，这样"库是空的"这条早退路径
# 也能报告"本来打算取多深"（一个空结果里的 fetch_k=0 会让人以为
# 这次没设深度，而实际上深度是算过的）。
fetch_k = self._fetch_depth(resolved, notes)

# 第 2 步：索引体检（条数 + 清单漂移）。
state = self._inspect_index()
```

空库上的实测数字有两条，它们说的是同一件事：

```text
手册第 4 节的探针（top_k=3）：空库 → 0 条 no_data（fetch_k 仍然是算过的 9）
                             notes 里还有一句"库是空的（count=0）：这是合法状态"
tests/test_retrieval_retriever.py::test_empty_store_still_reports_the_planned_depth
    默认 top_k=5 → assert result.fetch_k == 15
    （用例 docstring：空结果里的 fetch_k 不能是 0：否则会被误读成"这次没设深度"）
```

也就是说：**空结果里的 `fetch_k` 不是 0**，而是 `max(top_k, ceil(top_k × 3))`
（`top_k=3 → 9`、`top_k=5 → 15`）。如果体检排在深度之前并且提前返回，
这份报告就会写 `fetch_k=0`，读的人第一反应是"这次没设深度"——那是一个**错误的原因**。

#### 2. 撞车为什么要报错，为什么只在时间子句非空时判，为什么必须早于空库早退

`filters.combine_where` 里的判定与消息（`retrieval/filters.py`，本模块 242 行）：

```python
clause = time_range_clause(time_range)
if clause and where and time_range is not None:
    duplicated = sorted({name for name in filter_fields(where) if name == time_range.field})
    if duplicated:
        raise QueryError(
            f"过滤条件冲突：字段 {time_range.field!r} 同时出现在 where 与 time_range 里。"
            "同一个字段的两组条件请自己合并成一个显式区间——"
            "例如把 where 里的条件删掉、改用 TimeRange(start=..., end=...)；"
            "不合并的话，'我到底想要哪一段'会由两份条件取交集的副作用决定，"
            "而结果只会变少、不会报错。"
        )
```

三问三答：

1. **为什么报错而不取交集**：合成之后"语义上是可解释的"（两个条件都满足），
   但它查得出结果、也不报错，只是比预期少——这类"少而不报"正是本课要消灭的东西。
   模块 docstring 的原话是："把两个可能都成立的意图交给调用方决定，比替它挑一个更安全"。
2. **为什么只在时间子句非空时判**：`clause` 为空说明 `TimeRange` 两端都没给，
   此时它**没有任何条件**，`where` 里出现同名字段只是一次普通的元数据过滤
   （用例 `test_empty_time_range_means_no_conflict`：`combine_where({"created_at": "2026-09-01"}, TimeRange())`
   原样返回那个 `where`）。判定用的是 `time_range.field` 的**精确比较**，
   不是"看起来像时间的名字"（`test_conflict_uses_the_time_ranges_own_field`）。
3. **为什么必须排在空库早退之前**：`retrieve` 的注释把反例写完了——
   "同一个错误会在库非空时抛 `QueryError`、在库为空时被静默降级成
   `empty_reason=no_data`，而后者让调用方以为'条件是合并生效的，只是恰好没数据'"。
   用例 `test_filter_conflict_is_reported_even_on_an_empty_store` 对同一份 `conflict_query`
   分别在样本库与空库上断言 `pytest.raises(QueryError)`——**错误的库状态改变不了错误的查询**。

字段名冲突的**探测器**是 `filters.unknown_filter_fields`，但它只能发现
"整个库里都没这个键"（`{"stratgey": "structural"}`），发现不了"键对、值错"
（`{"strategy": "structual"}`）与格式写错的时间字符串，因此它只出现在
`Retriever.explain()` 的"字段拼写检查"一行，**绝不参与 `empty_reason` 的判定**。

#### 3. 三个 `dropped_*` 的账

不能合并的理由（`retrieval/__init__.py` 的第 2 条纪律）：

> `dropped_below_threshold` / `dropped_by_diversity` / `dropped_by_top_k`
> 三个数字各自对应一个可调参数，`empty_reason` 只给**一个**原因（按 `EMPTY_REASONS` 的优先级定）。
> 合成一个 `dropped` 会让"该调哪个参数"这个问题永远无法回答。

按本节给出的四行数字把账对一遍。第一张表里 `候选` 是"库侧过滤之后还剩多少条可选"，
在三道减法之前、深度取回之后：

```text
top_k=3    候选 8 = 命中 3 + dropped_by_top_k 5                （8 = 3 + 5 ✓）
top_k=5    候选 8 = 命中 5 + dropped_by_top_k 3                （8 = 5 + 3 ✓）
top_k=8    候选 8 = 命中 8 + dropped_by_top_k 0                （8 = 8 + 0 ✓）
top_k=1000 候选 8 = 命中 8 + dropped_by_top_k 0                （8 = 8 + 0 ✓）
```

阈值那两行则是"阈值切出来的那一份"：

```text
min_score=0.193122：候选 8 = 命中 3 + dropped_below_threshold 5（8 = 3 + 5 ✓）
min_score=1.5     ：候选 8 = 命中 0 + dropped_below_threshold 8（8 = 0 + 8 ✓，empty_reason=below_threshold）
```

写成一条不变量就是 `count + dropped_below_threshold + dropped_by_diversity
+ dropped_by_top_k == candidates`（深度小于候选数时右边改成 `fetch_k`），
这条不变量在测试里有四个参数化取值与两个特殊场景
（`test_three_dropped_numbers_account_for_every_candidate` 的
`accounted == result.candidates == 8`、`test_accounting_also_holds_for_a_filtered_query`
的 `== 4`、`test_accounting_holds_when_the_depth_is_shallow` 的 `== result.fetch_k == 2`）。

`dropped_by_top_k` 不是问题：深度默认按 3 倍过取（`retrieval_top_k=5 → fetch_k=15`），
"取回来的多于要返回的"是**设计内**的常态，所以 `top_k=5` 那行丢掉 3 条完全正常
——它是手册常见误区第 2 条明确点出的那件事（"它只是'取够了'，不是问题；
要查的是另外两个"）。真正要去看的是 `dropped_below_threshold`（去调
`retrieval_min_score`）与 `dropped_by_diversity`（去调 `retrieval_max_per_doc`）。

#### 4. 诊断优先级、唯一原因与那条"不可达"的防御分支

优先级就是 `EMPTY_REASONS` 的元组顺序，也是 `_diagnose` 的分支顺序：

```text
hits → no_data → filtered_out → below_threshold → diversity_trimmed
```

**为什么是这个顺序**：优先级把"更靠上游的成因"排在前面。库是空的，就谈不上
"被阈值切掉"（根本没东西可切）；过滤把候选筛成 0 时，也谈不上"阈值切掉了东西"。
本节的两句原文正好各是一个例子：

- `min_score=1.5` 时 `candidates=8`、`count=0`：数据在，只是不够像 → `below_threshold`
  （如果优先级反过来先看"是不是被过滤"，这里会错报成 `filtered_out`，因为
  `filter_applied` 为假时才轮到别的原因——但一旦查询里恰好带了一个筛不中的 `where`，
  顺序写反就会把"该降阈值"错报成"该放宽过滤"）。
- 库为 0 条时任何数字都不看：`test_no_data_wins_over_everything` 把
  `dropped_below_threshold=9`、`dropped_by_diversity=9` 一起传进去，结论仍然是 `no_data`。

**为什么只允许一个原因**：四种成因对应的动作完全不同（建索引 / 放宽过滤 / 降阈值 /
放宽多样性），"报告里写四条可能的猜测等于什么都没说"。另一半纪律在
`RetrievalResult.__post_init__`：`empty_reason` 必须是五个取值之一，
且"有命中却报告非 `hits`"直接被拒——互相矛盾的结果会让诊断失去意义。

**`diversity_trimmed` 为什么不可达**：第 7 步 `_apply_diversity` 的规则是
"入参已经按分数降序，因此'每组留前 N 条'就是'按顺序遇到就收'"，
`used >= max_per_doc` 只对**第二、第三条之后**的命中成立，因此每一组至少留下一条
（`kept` 必然非空）。演示第 6 节的实测就是证据——`max_per_doc=1` 时实际仍拿到 3 条：
"三行的 top_k 上限都是 5，实际条数却是 5 / 5 / 3：……`max_per_doc=1` → 只能凑出 3 条，
因为候选里一共只有 3 份文档，没有第四份可补。"

**既然不可达为什么还留着**：`_diagnose` 的 docstring 给了理由——
"**诊断规则不该依赖某一步的内部细节**：一旦第 7 步改成'每组至少两条'或'只保留主文档'，
这个分支就会立刻变成活路径，而那时它必须在正确的位置（阈值之后、兜底之前）"。
验证它只能直接调用 `_diagnose`（单元级构造）：

```python
_diagnose(hits=(), count_store=8, candidates=8, filter_applied=False,
          dropped_below_threshold=0, dropped_by_diversity=2)
# → 'diversity_trimmed'      ← 本机实测：直接构造才触发
```

"放在阈值之后"这件事也有专门断言：`dropped_below_threshold=3` 与
`dropped_by_diversity=2` 同时给进去，结论必须是 `below_threshold`
（`test_diversity_is_checked_after_the_threshold`）。最后一条兜底分支
（库非空、无过滤、无减法却排不出结果 → `no_data`）挡的是"后端在这一层返回了空列表"
这种更罕见的情形，它的存在保证 `empty_reason` **永远有值可比**。

**结论**：九步的顺序里只有一处"反直觉"（第 3 步先于第 2 步），它换来的是
空结果里那个"算过的深度"；撞车检测必须早于空库早退，因为调用方的错误不该被库的状态掩盖；
三个 `dropped_*` 各自指向一个参数；空结果只给一个原因、但那一份清单是封闭且有序的。

### 第 10 题（打包预算、引用编号与 RAG 护栏）

#### 1. 三个预算数字的出处、两种损失的差别、单位与 `measurer` 的约束

```text
retrieval_max_context_chars = 2400    config.py：按"6 个 ~400 字的片段"标定——够放下 top-5 的
                                      全部正文，又不至于把 4k 上下文撑满（还要留系统提示、历史与回答）
retrieval_per_hit_chars = 800         config.py：预算的 1/3——一条过长时先截断它，
                                      而不是让它把整包预算吃光（截断会记进 truncated_hits）
DEFAULT_MIN_HIT_CHARS = 32            types.py：低于它的片段进上下文只是噪声
                                      （"阈值设为 0.85"这种行离开它上面的标题就毫无意义）
```

前两个是**整包预算与单条硬上限**，第三个是**单条下限**（它只参与"预算够不够放一条"的校验，
不参与单条截断）。两种损失的性质不同，因此处置的动作也不同：

```text
截断（per_hit_chars）    "这一条少半句"   → 内容损失 → 去调 retrieval_per_hit_chars
丢尾（max_context_chars）"整条不见了"     → 召回损失 → 去调 retrieval_max_context_chars
```

模块 docstring 把"为什么顺序是先截单条、再丢尾部"写成了一句可回答性论证：
"反过来或平均切每一段，报告里就只剩一个'包满了'，而'该调哪个参数'从此无从回答"。

**单位为什么默认 chars**：与 day062 的默认度量同一条理由——确定性、离线、可复现，
"`len()` 在任何机器上给出同一个数，而 token 计数要引入分词器与版本"，
因此 `context.py::_char_measure` 就是 `len(text)`，并且**本模块不 import 任何分词器**。

**注入 `measurer` 之后必须满足的约束**：`max_chars` / `per_hit_chars` / `min_hit_chars`
**三者同单位**，否则"预算放不放得下一条"这个比较就没有意义——而它恰恰是这一层唯一会
拒绝服务的判据（`pack_context` docstring 的原话）。同单位这件事在测试里被量化过
（`tests/test_retrieval_context.py::TestMeasurerInjection`）：

```text
两块 54 字的块 + 2 个分隔符 → len(text) == 110，而 estimate_tokens(text) == 27
   → char_count == 27 != len(text)（"口径换了，数字就不该等于 len()"）
token 口径下 per_hit_chars=20 → len(result.text) == 83
   （"若按字符切，这里只会留 20 个字"——这就是 _truncate 必须按注入口径裁的原因）
```

裁法本身是"二分找最长的可行前缀"（`_truncate`）：docstring 给了两条理由——
"注入口径下能把预算**尽量填满**（逐字符回收会明显少填）"、
"调用次数从 O(n) 降到 O(log n)"；并且"返回值**一定**是量过的那一个"，
所以不会出现"截断之后反而超标"。

#### 2. 五步顺序、至少保一条、`ContextError` 的位置

五步的固定顺序见第 5 题答案（解析预算 → 单条截断 → 拼包 → 丢尾 → 至少保一条），
理由是**每一步都会改变"还剩多少预算"**。

**"至少保一条"为什么不返回空上下文**：这是这一层最重要的护栏（docstring 原话）——
"**'预算紧'不等于'没有上下文'**。返回空上下文会让 RAG 链路走进'检索为空'的分支，
于是模型一次都不被调用——一个因为打包而发生的静默降级，看起来与'库里没有相关内容'
一模一样"。也就是说，后果不是"少给了一点资料"，而是**一次配置错误被伪装成
"库里没有相关内容"**：`empty_reason` 会变成空结果那一套、`llm_called=False`、
用户看到的是"知识库中没有检索到与该问题相关的内容"。演示第 8.2 节第二个预算
（60 字）打出来的就是这条路径的正面形态：

```text
预算压到 60 字（放不下两条）→ 上下文 60/60 字（占用 100.0%） | 引用 1 条 | 截断 1 条 | 丢尾 4 条：
  **至少保住一条**，返回的不是空上下文
```

**`ContextError` 为什么排在"空 `hits`"之前**：`pack_context` 的 docstring 说
"配置检查排在'空 `hits` 返回空上下文'之前是刻意的——预算配错的时候，
'这次恰好没有命中'不该让这个错误被跳过；配错的预算会在下一次有命中的时候以同样的方式错下去"。
实测三段（演示 8.2）：`220` 字 → `184/220`（占用 83.6%，截断 3 条、丢尾 2 条）；
`60` 字 → `60/60`（占用 100.0%，引用 1 条）；`20` 字 → `ContextError`，
消息是"一条命中至少需要 32 字，本预算只给了 20 字：预算放不下任何一条命中，
而'放不下'不该被静默处理成'空上下文'……出路：调大
`settings.retrieval_max_context_chars`，或把单条下限从 32 降到能放下的值"。
对应用例 `test_config_is_checked_even_without_hits`：`pack_context([], max_chars=0)` **照样抛**。

#### 3. `truncated_hits` 与 `dropped_hits` 为什么分开

与 `RetrievalResult` 的三个 `dropped_*` 是同一条理由（`PackedContext` 的字段说明）：
"一个要去调预算，一个要去调单条上限，合成一个数字之后'该调哪个参数'就答不出来了"。

`truncated_hits` 的定义是"被单条上限截断的条数（**只算真的进了上下文的那些**）"，
因此有一个很容易被写错的场景，测试把它钉住了
（`test_truncated_hits_counts_only_the_hits_that_stayed`）：

```python
hits = flat_hits(3, text="甲" * 300)
result = pack_context(hits, max_chars=60, per_hit_chars=60)

assert result.count == 1
assert result.dropped_hits == tuple(hits[1:])
assert result.truncated_hits == 1, "只算留下的那一条（三条都被切过）"
```

三条都被单条上限切过，但只有第一条真的进了上下文，因此计数是 1 而不是 3。

**"至少保一条"那次截断的证据不在计数上**，而在 `char_count == max_chars`：

```python
result = pack_context([make_hit("h-1", "乙" * 300)], max_chars=60, per_hit_chars=800)

assert result.count == 1, "返回空上下文会让 RAG 链路走进「检索为空」的分支"
assert result.char_count == 60 == result.max_chars
assert result.truncated_hits == 0, "它的证据是 char_count == max_chars，不是计数"
assert result.fill_ratio == 1.0
```

`PackedContext` 把 `char_count` 与 `max_chars` 成对给出的理由也在这里：
"**'这次有没有被预算削过'必须是一个能被读出来的事实**。只有一个 `char_count` 时，
读的人不知道它是'包刚好这么长'还是'被削到这么长'"。

#### 4. 编号为什么由调用方给、判空为什么在上游、`llm_called` 为什么不比较字符串

**编号由调用方给**：`RetrievalHit.citation(index)` 的 docstring 原文——
"`index` 从 1 起（进提示词的就是 `[1]` `[2]`，与 day069 的引用溯源是同一个形状）。
编号**由调用方给**而不是这里自增：编号是'在这一次提示词里的位置'，
只有捧着整份上下文的人知道它"。真正的调用方是 `context.py::pack_context`，
它按 `enumerate(hits, start=1)` 把顺序变成编号，并把编号与命中的对应关系
存进 `citations`。

**被丢掉的尾部不占编号**：模块 docstring 的原文——"被丢掉的尾部如果也占着编号，
模型就可能写出一个指向不存在片段的 `[7]`——而这种错误看起来只是'引用了一个没给的片段'，
查起来却要重新跑一遍打包"。因此 `Citation.marker` 从 1 起**连续**，
并且 `PackedContext.__post_init__` 会再校验一次：

```python
expected = list(range(1, len(self.citations) + 1))
actual = [citation.marker for citation in self.citations]
if actual != expected:
    raise ContextError(f"引用编号必须是 1 起连续的 {expected}，收到 {actual}："
                       "编号是'在这一次提示词里的位置'，中间断号会让模型写出指向空位的 [n]。")
```

对应用例 `test_a_dropped_hit_has_no_marker_in_the_text`：`markers == [1, 2]` 且
`"[3]" not in result.text`；`test_marker_for_a_dropped_hit_is_none`：
被丢的 id 问编号得到 `None`（"它没进上下文"是一个正常答案，不是异常）。

**判空为什么在渲染提示词之前**：`pipeline.py` 模块 docstring 把两个分支并排写着：

```text
检索为空 + 调用 LLM   模型手里没有片段，却仍然会写出一段通顺的答案
                      → 它们全来自预训练记忆，而读的人看不出区别
检索为空 + 不调用     答案明确写着"知识库中没有检索到相关内容"，并给出三条出路
```

第一行的产物"**看起来最像成功**：语法正确、语气确定、引用格式也像模像样"，
它是 RAG 系统最贵的一种失败——"没有异常、没有告警，只有'用户问了一个知识库里没有的问题，
却拿到了一个编出来的答案'"。因此 `answer` 里判空排在**打包与渲染之前**
（"护栏写在调用的上游，而不是调用的下游"）：

```python
retrieval = self._retriever.retrieve(question)
if retrieval.is_empty:      # = not hits，且 empty_reason != "hits"
    return RagAnswer(..., llm_called=False, notes=tuple(_empty_notes(retrieval)))
```

判据是"检索层已经给出的结论"（`RetrievalResult.is_empty` 与 `empty_reason`），
不需要"看回答像不像编的"。演示 8.4 的实测把这件事变成了计数：
"调用前 LLM 次数=4，调用后=4 → 这次一次 LLM 都没调：True"。

**`llm_called` 为什么不靠字符串比较**：`RagAnswer` 的 docstring 原文——
"**判定不能依赖字符串比较**——兜底答复将来改一个字，那种判定就静默失效"。
它同时是护栏的**证据**："`llm_called=False` 且 `citations=()` 表示
'模型这次没有机会自由发挥'"。配套的三条注记由 `_empty_notes` 给出，
分别回答"为什么没调模型""护栏本身是什么""三条出路是什么"，
与 `FALLBACK_NO_CONTEXT` 的三条出路是同一条纪律——"没有找到"必须跟一个下一步动作，
否则它只是一次失败宣告。

（顺带一条同源的事实：漂移与降级也不靠布尔标志，而是三句各自可读的话——
`_degrade_notes` 分别给"被单块上限 800 字截断""预算 2400 字放不下、从尾部丢掉了 N 条
（id 预览）""索引漂移 N 项"，因为它们的处置分别是调 `per_hit_chars`、
调 `max_context_chars`、重建清单。）

**结论**：预算是"给模型多少空间"的三个数字（2400/800/32），单位与 `measurer` 绑定；
五种打包规则里第 5 条保的是"这次回答还有没有依据"；编号是位置而不是身份，
所以由捧着上下文的人给、且只给真的进包的那些；护栏的唯一判据是检索层的
`is_empty` / `empty_reason`，而它的证据是 `llm_called` 这个字段。

### 第 11 题（深度 / 同分排序 / 三道减法 / `>=` 语义）

"""day066 第 12 题：打包预算 / [n] 编号 / RAG 空结果护栏（离线、确定性）."""

from __future__ import annotations

import pytest

from smart_research_agent.llm.base import BaseLLM, Message
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.retrieval.context import TRUNCATION_MARKER, pack_context
from smart_research_agent.retrieval.errors import ContextError
from smart_research_agent.retrieval.pipeline import FALLBACK_NO_CONTEXT, RagPipeline
from smart_research_agent.retrieval.retriever import Retriever
from smart_research_agent.retrieval.types import RetrievalHit, RetrievalQuery
from tests.retrieval_samples import TableEmbedding, empty_store, sample_store

AXIS = "检索手册里怎么配置时间范围过滤"
SOURCE = "docs/a.md"
HEADER_ONE = f"[1] {SOURCE}"


class ExplodingLLM(BaseLLM):
    """一旦被调用就抛异常：它没被调用过，就是护栏生效的证据."""

    def __init__(self) -> None:
        self.calls = 0

    def chat(
        self,
        messages: list[Message],
        temperature: float = 0.7,
        max_tokens: int = 1024,
    ) -> str:
        self.calls += 1
        raise AssertionError("检索为空时不许调用 LLM：护栏被绕过了")


def make_hit(record_id: str, text: str = "", *, score: float = 1.0, rank: int = 0) -> RetrievalHit:
    return RetrievalHit(
        record_id=record_id, score=score, rank=rank, text=text, metadata={"source": SOURCE}
    )


def flat_hits(count: int = 4, *, text: str = "x" * 10) -> list[RetrievalHit]:
    """块长完全相同的若干条命中（块头 13 字 + 换行 + 10 字正文 = 24 字）."""
    return [
        make_hit(f"h-{index}", text, score=1.0 - index * 0.01, rank=index - 1)
        for index in range(1, count + 1)
    ]


def build_retriever(store=None, **overrides):
    return Retriever(
        store if store is not None else sample_store(), TableEmbedding(), **overrides
    )


def build_pipeline(store=None, llm=None, **overrides):
    return RagPipeline(
        build_retriever(store),
        llm if llm is not None else MockLLM(responses=["答案 [1]"]),
        **overrides,
    )


def test_the_truncation_is_counted_and_marked() -> None:
    result = pack_context([make_hit("h-1", "甲" * 100)], max_chars=500, per_hit_chars=60)

    assert result.truncated_hits == 1
    assert result.count == 1 and result.dropped_hits == ()
    assert result.text.endswith(TRUNCATION_MARKER)
    assert result.char_count == 60


def test_the_last_hit_survives_a_tight_budget() -> None:
    result = pack_context([make_hit("h-1", "乙" * 300)], max_chars=60, per_hit_chars=800)

    assert result.count == 1, "预算紧不等于没有上下文：返回它而不是返回空"
    assert result.char_count == 60 == result.max_chars
    assert result.truncated_hits == 0, "第 5 步那次截断不计进 truncated_hits"
    assert result.text.endswith(TRUNCATION_MARKER)


def test_the_dropped_tail_has_no_marker_in_the_text() -> None:
    hits = flat_hits(4)
    result = pack_context(hits, max_chars=60, per_hit_chars=800)

    assert result.count == 2 and result.char_count == 50
    assert result.used_hits == tuple(hits[:2])
    assert [hit.record_id for hit in result.dropped_hits] == ["h-3", "h-4"]
    assert [citation.marker for citation in result.citations] == [1, 2]
    assert "[3]" not in result.text and "[4]" not in result.text
    assert result.marker_for("h-1") == 1
    assert result.marker_for("h-3") is None

    assert [citation.marker for citation in result.citations] == [1, 2, 3]
    assert result.text.startswith("[1] ")
    assert result.text.count("[2]") == 1

        pack_context([make_hit("h-1", "正文")], max_chars=20, min_hit_chars=32)

    assert answer.context is None

    assert answer.retrieval is not None

**为什么"一旦被调用就抛异常"的假 LLM 比自己写一个字符串比较更能守住这条护栏？**

字符串比较（`assert answer.answer == FALLBACK_NO_CONTEXT`）测的是**答案文本**，
而这条护栏要守的是**调用本身**。两者的差别在"护栏失效时会怎样"：

```text
字符串比较（较弱）     检索为空 + 仍然调了 LLM，而模型这次恰好也说"资料里没有" → 断言通过（漏报）
                      兜底文案将来改一个字 → 断言在**正确实现**上变红（误报），然后被人改成
                      "只要包含'没有'就算" → 判定彻底失效
抛异常的假 LLM（较强） 检索为空 + 仍然调了 LLM → 假实现当场抛 AssertionError，
                      调用栈直接指出"护栏被绕过了"；没被调用过 == 护栏生效（`llm.calls == 0` 是计数证据）
```

更准确地说，字符串比较测的是"输出像不像兜底"，而 `llm_called` 测的是
"模型有没有机会说话"——后者才是这条护栏的**语义**，也是 `RagAnswer` 把
`llm_called` 单独做成一个字段的理由（"判定不能依赖字符串比较——兜底答复将来改一个字，
那种判定就静默失效"）。`tests/test_retrieval_pipeline.py` 里的 `ExplodingLLM`
与本题这个 8 行子类是同一种写法，它的 docstring 写得更直白：

> 用它而不是"看 answer 等不等于兜底串"：护栏失效时这里的异常会**立刻**炸出来，
> 而字符串比较那种判定只会在兜底文案改动之后静默失效。

顺带一个工程上的好处：假 LLM 让"没被调用"变成**可计数的事实**（`llm.calls == 0`），
而字符串比较只能给出一个布尔值——前者可以直接写进报告与断言，后者不能。

**结论**：`pack_context` 的账由 `char_count` / `max_chars` / `truncated_hits` /
`dropped_hits` 四个数字拼出来，其中"至少保一条"的证据是"包被削到刚好占满"而不是计数；
`[n]` 编号只给真的进了上下文的那些且从 1 起连续；而 RAG 链路的那条护栏，
最可靠的证人是"一个一旦被调用就会炸的模型"加上它的调用计数。
