## 第一部分：选择题

### 第 1 题

**答案：D**

**解析**：D 错误且因果颠倒——同进程 Python 函数调用远**快于**跨进程 HTTP（省掉序列化、网络栈、反向代理等开销），服务化恰恰是在**牺牲**单次调用性能来换取工程能力。服务层的真实收益是 A（进程边界解耦语言/环境/部署）、B（持续驻留 + 并发受理）、C（契约前置到框架层，业务代码零防御成本）。把服务化理解成"提速手段"是一个常见误解：它解决的是**协作与交付**问题，不是单机性能问题。

### 第 2 题

**答案：B**

**解析**：`temperature: 3.0` 违反 `Field(le=2.0)` 约束，Pydantic 校验失败，FastAPI 抛出内部的 `RequestValidationError`，内置异常处理器把它转成 422，响应体为 `{"detail": [{"type": "less_than_equal", "loc": ["body", "temperature"], ...}]}`。整条流水线发生在路由函数**之前**——`chat()` 根本没有执行（A 错）。C 错：请求体是合法 JSON，"语法可理解但语义不符契约"正是 422 与 400 的区别（FastAPI 把 JSON 语法损坏也归并到 422 处理，见 `test_invalid_json_body_422`，但本题负载不属于这种情况）。D 是无中生有：状态码是 HTTP 标准语义，不存在"被端点占用"一说。

### 第 3 题

**答案：C**

**解析**：这是本日第三章的核心机制。FastAPI 按路由声明方式决定执行策略：`async def` 在事件循环里直接执行（要求函数体全程 awaitable），`def` 则自动丢进 anyio 线程池（`run_in_threadpool`）。`FunctionCallingAgent.run()` 内部是同步阻塞的多轮 LLM 调用，包在 `async def` 里会让事件循环在整个任务期间停摆——**所有**请求一起卡住，连 `/health` 都会超时。声明为 `def` 后，阻塞工作在线程池里跑，事件循环照常多路复用其他请求。A 似是而非（协程开销不是决策依据）；B 错误（校验在框架层，与同步异步无关）；D 明显错误（FastAPI 主推 `async def`）。

## 第二部分：判断题

### 第 4 题

**对（在"文档由模型反射生成"的意义上）。**

OpenAPI schema 与 `/docs` 都是启动时从路由签名和 Pydantic 模型**反射**出来的，与实现共享单一事实源，天然同步——改字段、改约束、改端点，文档随之自动更新，不存在"改了代码忘改文档"的漂移路径（测试 `test_openapi_schema_contains_endpoints_and_models` 守护此行为）。需要一个限定词：自动生成的部分（结构、类型、约束）不漂移；但**语义层**（字段的业务含义、示例的合理性）仍依赖人写好 `description`——机器保证结构同步，保证不了语义质量。

### 第 5 题

**错。**

`FunctionCallingAgent` 实例携带**单次任务的执行轨迹**（`call_history`）。跨请求复用会让请求 B 的响应混入请求 A 的工具调用记录——状态泄漏；两个并发请求同时写一个 `call_history` 还会产生数据竞争。这正是"共享与隔离的分界线画在对象是否携带请求级状态"：LLM 客户端无请求级状态，可以共享；Agent 有，必须按请求新建。构建 Agent 的开销（构造一个对象 + 拼系统提示词）相对一次 LLM 网络调用可以忽略，"省开销"是伪优化——用状态泄漏换微秒级节省，是典型的错误权衡。

### 第 6 题

**错。**

`TestClient` 基于 httpx 在**进程内**直接调用 ASGI 应用对象：构造请求 → 走完整的路由匹配、请求体校验、依赖注入、响应序列化链路 → 返回响应，全程不监听端口、不经过网络。这正是它适合 CI 的原因——14 个接口测试秒级跑完、完全离线、无端口冲突。需要 uvicorn 起真服务的场景是**联调与生产部署**（真实网络、真实并发、真实进程边界）；单元/接口测试用 TestClient 即可覆盖框架层的全部行为。

## 第三部分：简答题

### 第 7 题

**参考答案**（答出两点即可，以下为三个层面）：

1. **用例级隔离，无全局污染**：每个测试用例 `create_app(llm=MockLLM(...))` 得到一个独立装配的 app 实例，注入的 Mock 只在该用例内可见。而 import 全局单例的写法下，测试换 Mock 只能 monkeypatch 模块属性——改的是进程级全局状态，用例间互相污染，并行执行直接翻车。
2. **完全离线**：MockLLM 以脚本化响应替代真实 LLM 调用，接口测试不需要 API Key、不需要网络，CI 可稳定复现（`tests/test_api.py` 14 个用例全部离线）。全局单例在 import 时即按环境构建，测试想离线必须打断模块初始化。
3. **装配逻辑集中且显式**：路由要什么，全部写在函数签名的 `Depends` 里，依赖关系一眼可读；`create_app` 的签名就是整个服务的"依赖清单"。全局单例写法则把依赖藏在函数体内部的 import 语句里，只有读完实现才知道它依赖什么。

本质上是同一个原则：路由函数**不自己抓取依赖，而是声明依赖**，控制权反转给调用方（测试与生产各自装配）。

### 第 8 题

**参考答案**：

客户端对错误的消费方式是**编程解析**，不是人眼阅读。FastAPI 默认的 500 是框架格式的纯文本/Internal Server Error，客户端只能拿到一个非结构化的字符串，无法区分"工具注册失败"与"LLM 超时"，也就无法分支处理（前者可能要告警，后者可能值得重试）。

注册全局异常处理器后，500 响应稳定为 `ErrorResponse` 结构：`{"detail": "...", "error_type": "RuntimeError"}`——`error_type` 提供了机器可判定的分支依据，`detail` 保留了人读的详情。这与正常路径的 `response_model` 形成闭环：**成功有契约，失败也有契约**，客户端的每一条代码路径都有稳定的解析依据。附带收益是日志侧的统一：`logger.exception` 在处理器里集中记录完整堆栈（含请求方法与路径），排查时不必从框架散落的默认日志里拼凑。

## 第四部分：编程题

### 第 9 题

**参考实现**（在 day038 快照基础上扩展）：

第一步，扩展 `create_app` 的注入面（`smart_research_agent/api/app.py`）——把工具注册表也挂上 `app.state`：

```python
def create_app(
    llm: BaseLLM | None = None,
    agent_factory: Callable[[], FunctionCallingAgent] | None = None,
    registry: ToolRegistry | None = None,   # 新增
) -> FastAPI:
    ...
    resolved_registry = registry or default_registry()
    app.state.registry = resolved_registry   # 新增：供 /tools 依赖注入读取
    if agent_factory is None:
        agent_factory = lambda: FunctionCallingAgent(resolved_llm, resolved_registry)
```

第二步，在 `api/schemas.py` 增加响应模型：

```python
class ToolInfo(BaseModel):
    name: str = Field(description="工具名")
    description: str = Field(description="给模型阅读的工具说明")

class ToolsResponse(BaseModel):
    tools: list[ToolInfo]
```

第三步，在 `api/routes.py` 增加依赖与端点：

```python
def get_registry(request: Request) -> ToolRegistry:
    return request.app.state.registry

@router.get("/tools", response_model=ToolsResponse)
def list_tools(registry: ToolRegistry = Depends(get_registry)) -> ToolsResponse:
    return ToolsResponse(
        tools=[ToolInfo(name=t.name, description=t.description) for t in registry.list_tools()]
    )
```

第四步，测试（`tests/test_api.py` 追加）：

```python
class TestTools:
    def test_tools_lists_calculator(self):
        resp = make_client().get("/tools")
        assert resp.status_code == 200
        names = [t["name"] for t in resp.json()["tools"]]
        assert "calculator" in names
```

**要点解析**：这个练习复刻了本日的全部套路——模型先行（schemas）、依赖注入读 `app.state`（routes）、工厂扩展注入面（app）。注意 `registry` 与 LLM 一样可以跨请求共享（注册表无请求级状态），所以挂实例而非工厂；与 `agent_factory` 的"每请求新建"形成对照，正好巩固第 5 题的判断逻辑。

### 第 10 题

**参考测试**（已实际运行通过）：

```python
def test_steps_are_per_request_not_cumulative():
    """共享 LLM 的 calls 是累积的，steps 必须按请求取差值."""
    shared_llm = MockLLM(
        tool_call_responses=[
            {"tool_calls": [{"name": "calculator", "arguments": {"expression": "1+1"}}]},
            {"content": "第一次答案"},
            {"tool_calls": [{"name": "calculator", "arguments": {"expression": "2+2"}}]},
            {"content": "第二次答案"},
        ]
    )
    registry = ToolRegistry()
    registry.register(CalculatorTool())
    factory = lambda: FunctionCallingAgent(shared_llm, registry)  # 共享 LLM，每请求新建 Agent
    client = make_client(agent_factory=factory)

    first = client.post("/agent/run", json={"task": "第一次"}).json()
    second = client.post("/agent/run", json={"task": "第二次"}).json()
    assert first["steps"] == 2
    assert second["steps"] == 2  # 不是 4：取的是 run 前后差值
    assert len(shared_llm.calls) == 4  # 底层日志确实是累积的
```

**问题说明**：`MockLLM.calls` 是实例级日志，LLM 跨请求共享时单调累积（两次请求后总数为 4）。如果 `steps` 直接返回 `len(llm.calls)`，第二个请求会得到 4——把别人的历史算进自己的账单，请求越多数字越失真。正确做法是在 `run()` 前后各取一次长度、返回**差值**：`steps = len(calls_log) - calls_before`。这是"共享对象上的累积状态"与"请求级指标"之间的通用处理模式——day032 的成本追踪里按会话切分 token 用量，用的是同一思路。
