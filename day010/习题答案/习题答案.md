## 第 2 题

**答案：D**

解析：规划阶段恰好调用 LLM **1 次**（`Planner.plan` 是一次性调用，没有循环）；执行阶段每个子任务起一次独立的 ReAct 循环，5 个子任务 × 平均 3 次 = 15 次。合计约 16 次。这个题目想强化的认知是：**规划的成本被压缩到一次调用**，而执行成本与子任务数量成正比——这正是提示词里限制"3~6 个子任务"的成本动因。

## 第 3 题

**答案：C**

解析：输入中 `[` 和 `]` 都存在，但顺序颠倒：`find("[")` 返回的位置在 `rfind("]")` 之后，即 `end < start`。代码里有专门的守卫：

```python
if start == -1 or end == -1 or end < start:
    raise PlanParseError("输出中未找到 JSON 数组")
```

没有这个检查的话，`cleaned[start : end + 1]` 会截出空串或乱码，错误会推迟到 `json.loads` 才暴露且信息混乱。先判序再截取，是边界处理的基本功。A 错（不会静默返回空列表）；B 错（根本到不了 `json.loads`）；D 错（切片不会抛 `IndexError`，且这里抛的是 `PlanParseError`）。

## 第 4 题

**答案：错**

解析：这正是教程 4.3 节职责边界表的核心一行——**Planner 不知道工具的存在**。它的输入只有目标字符串，输出只有子任务描述，整个模块不 import 任何工具层代码。拆任务依赖的是 LLM 的通用常识（"调研"通常要"收集资料→对比→撰写"），不需要知道执行层恰好配了哪些工具。这样做的好处是：工具集合变化时 Planner 零改动；Planner 也可以独立用 MockLLM 测试。如果让 Planner 感知工具，两个模块就耦合了，替换执行层时规划层也要跟着改。

## 第 5 题

**答案：对**

解析：走一遍逻辑：`find("[")` 找到的是 ```json 之后真正的数组左括号（` ```json ` 这行本身不含 `[`），`rfind("]")` 找到数组右括号，截取出 `["a", "b"]`，`json.loads` 正常解析。开头的 ` ```json ` 和结尾的 ` ``` ` 都在截取范围之外，被自然丢弃。**但注意**：这是"恰好能工作"，不是"专门支持"——如果模型在数组之外又写了别的 `[...]` 片段（比如解释文字里又举了个例子），`rfind` 会取到错误的边界。容错逻辑降低失败率，但不能替代提示词里的"不要输出其他内容"约束：软约束降概率，硬校验兜底，两者缺一不可。

## 第 6 题

**答案：对**

解析：`PlanParseError(ValueError)` 是刻意的继承选择。Python 的异常捕获按继承链匹配，`except ValueError` 能兜住所有 `ValueError` 的子类。这样设计有两层好处：

1. **向后兼容**：旧的泛化处理代码（如统一的参数校验错误处理）不需要修改就能捕获新异常。
2. **语义分层**：新代码可以写 `except PlanParseError` 精确捕获（比如未来 RePlanner 只在"计划解析失败"时触发重规划），旧代码用 `except ValueError` 宽泛捕获，两种粒度共存。

day006 的 `ReActParseError` 也是同样继承 `ValueError`，项目内保持一致。

## 第 7 题

**参考答案**：

**没有下限的风险**：拆成 1~2 个子任务（如 `["调研 RAG 技术", "写报告"]`）等于没有拆解。规划的全部价值在于把全局目标显式化、牵引执行方向；过粗的子任务丢给 ReAct 后，每个子任务内部依然是一个复杂任务，迷失方向、步骤冗余的老问题原样复发——规划层成了徒增一次 LLM 调用的摆设。

**没有上限的风险**：拆成 20+ 个子任务有两个直接代价。一是**成本与延迟爆炸**：每个子任务都要起一次 ReAct 循环（一次甚至多次 LLM 调用），20 个子任务可能意味着几十次 API 调用。二是**层级错位**：过细的拆分会把执行细节（"打开网页""复制第一段"）混进计划，而这些本应是 ReAct 循环内部现场决策的事——规划层越界做了执行层的工作，反而剥夺了执行层的灵活性。

3~6 个是平衡两端后的经验值：上限控制成本，下限保证拆解真实发生。

## 第 8 题

**参考答案**：

**代价一：计划可能本身就不合理。** 规划发生在执行之前，规划时模型对环境的了解有限，拆出来的子任务可能遗漏关键步骤、顺序错误或基于错误假设。ReAct 边想边做至少每步都能根据最新 Observation 修正方向，而固定的计划会"一条道走到黑"。

**代价二：无法响应执行中的新信息。** 执行子任务时可能发现意外情况：某个工具超时、搜到的资料推翻了原假设、用户中途改了需求。僵化计划没有吸收这些变化的机制，要么无视继续执行，要么整体失败。

**RePlanner 的作用**就是补上这两个窟窿：每完成一个子任务，把"原计划 + 已完成结果 + 当前状态"重新交给 LLM 审视，让它决定剩余计划是继续、修改还是重做。这本质上是把 ReAct"每步可纠偏"的优点嫁接到 Plan-and-Execute 的全局框架上——**规划提供方向，重规划提供弹性**。

## 第 9 题

**参考答案**：

**可测试性角度**：内嵌在 ReAct 里的拆解是模型的隐式思考，混在 Thought/Action/Observation 流里，测试时无法单独断言"拆解质量"——你只能端到端跑整个循环，用模糊的最终答案间接判断。独立 Planner 则可以用 MockLLM 精确测试：给定目标 → 断言拆出的子任务列表，失败定位零成本。

**可观察性角度**：隐式拆解存在于模型"脑子"里，程序读不到。执行失败时你无法区分是"计划错了"还是"执行错了"；想给用户展示"我打算分这几步做，请确认"也做不到。显式的 `Plan` 对象是结构化数据，可打印、可审计、可持久化。

**可演进性角度**：提示词里加一句话的"拆解"是写死的，无法独立升级。独立 Planner 模块可以平滑演进：今天一次调用出全计划，明天换带反思的规划（草稿 + 自我 critique）、分层规划（目标→阶段→任务），执行层代码一行不动。架构上这就是关注点分离——ReAct 系统提示词管"怎么做事"，Planner 管"做什么事"。

## 第 10 题

**参考实现**：

```python
"""计划执行器：把 Plan 的子任务逐个交给 ReactAgent 执行."""

from __future__ import annotations

from typing import Callable

from smart_research_agent.agent.planner import Planner
from smart_research_agent.agent.react_agent import ReactAgent


class PlanExecutor:
    """Plan-and-Execute 编排层：规划前置，逐个执行，容错汇总."""

    def __init__(self, planner: Planner, agent_factory: Callable[[], ReactAgent]):
        self.planner = planner
        self.agent_factory = agent_factory

    def execute(self, goal: str) -> dict:
        plan = self.planner.plan(goal)
        results = []
        for step in plan.steps:
            agent = self.agent_factory()  # 每个子任务独立 Agent，避免 history 累积
            try:
                results.append(agent.run(step))
            except Exception as exc:  # noqa: BLE001
                results.append(f"子任务执行失败: {exc}")
        return {"goal": plan.goal, "steps": plan.steps, "results": results}
```

**参考测试**：

```python
"""PlanExecutor 端到端测试（MockLLM 驱动，完全离线）."""

from __future__ import annotations

from smart_research_agent.agent.planner import Planner
from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.tools.registry import ToolRegistry
from plan_executor import PlanExecutor


def test_execute_end_to_end():
    llm = MockLLM(
        responses=[
            '["收集资料", "撰写报告"]',                    # 规划消耗
            "Thought: 直接回答\nFinal Answer: 资料已收集",  # 子任务1消耗
            "Thought: 直接回答\nFinal Answer: 报告已完成",  # 子任务2消耗
        ]
    )

    def agent_factory() -> ReactAgent:
        return ReactAgent(llm=llm, registry=ToolRegistry())

    executor = PlanExecutor(planner=Planner(llm=llm), agent_factory=agent_factory)
    result = executor.execute("调研 RAG 技术")

    assert result["goal"] == "调研 RAG 技术"
    assert result["steps"] == ["收集资料", "撰写报告"]
    assert result["results"] == ["资料已收集", "报告已完成"]
```

**解析**：

1. **为什么用工厂函数而不是传实例**：`ReactAgent` 是有状态的——`history` 列表会在 `run()` 中累积。如果所有子任务复用同一个实例，子任务 2 的 history 里会混进子任务 1 的推理记录，既污染调试信息，也违背"子任务相互独立"的语义（教程 4.5 节）。工厂函数让每个子任务拿到全新的 Agent，隔离性由构造保证。

2. **MockLLM 的响应顺序**：`MockLLM.chat` 按顺序弹出 responses。规划消耗第 1 个；子任务 1 的 Agent 第一次 `chat` 就拿到 Final Answer 格式，直接返回，消耗第 2 个；子任务 2 同理消耗第 3 个。两个 Agent 共享同一个 MockLLM 是安全的，因为消费顺序与执行顺序一致（串行执行）。

3. **容错策略**：`execute` 对单个子任务的异常"记档不中断"——把异常信息写进该位置的结果，继续后续子任务。这样一次工具超时不会让整份计划报废，调用方还能从 `results` 里看出哪一步失败了。这是教程 5.4 节讨论的两种策略之一；另一种"遇错即中断"实现更简单，但在生产环境中过于脆弱。

4. **边界注意**：`planner.plan()` 抛出的 `PlanParseError` **不应该**被这里的 `except Exception` 吞掉——它发生在 `for` 循环之前，计划本身不可用，理应直接向上抛出，让调用方知道"连计划都没有"。容错只针对执行阶段。
