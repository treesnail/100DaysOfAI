## 第二部分：判断题

### 第 6 题 → **对**

三个性质都在 `NearDuplicateIndex.add` 里：

- 重复样本**不入库**，因此它不会成为后续样本的比较对象——索引里只保留"已接受"的样本，这是"保留首次出现"在增量场景下的自然延伸；
- `filter()` 逐个 `add`，因此保留的样本同时进了索引，**批内重复也顺手解决**；
- 不这样做的后果：同一批次里出现两次的样本会双双通过。

### 第 7 题 → **错**

`feasible` 是 **`False`**。实测输出：

```json
{"quotas": {"normal": 1, "safety": 1}, "total_in": 37, "total_out": 2, "dropped": 35,
 "iterations": 9, "feasible": false, "final_ratios": {"normal": 0.5, "safety": 0.5},
 "warnings": ["实际占比无法全部落在 0.4 以内（每组至少保留 1 条与取整所致）……"]}
```

这道题考的是本课最容易被混淆的一对概念：**收敛 ≠ 可达**。迭代确实收敛了（总数每轮严格下降，有下界），但收敛到的点违反约束——两组各占一半时必然有一组 ≥ 50%。所以 `feasible` 必须是一个被输出的字段：一个悄悄违反自己约束的护栏，会让评审以为"配比已经守住 40% 了"。

### 第 8 题 → **对**

实测（第一版实现）：13 次 `prefix` 尝试里 5 次被自己的亲本判重丢弃，扩容比从 0.78× 掉到 0.65×。修法不是调阈值（那会同时放松真正的重复检测），而是**把增强阶段的去重范围收窄为"增强样本之间"**：原样本已经在 `near_dedup` 阶段去过重，而"与自己的亲本像"是设计意图。

**判据相同、意图不同时，必须让意图显式化。**

## 第三部分：简答题

### 第 9 题（增强的三条纪律）

**纪律一：只改 prompt 侧，`output` 逐字不动。**

- **防的故障**：增强样本的答案一旦被改动，"换一种问法"就变成"生成新答案"，而生成意味着可能出错——一条错了的增强样本会在训练里被当成金标准反复强化。
- **落点**：`augment_example` 构造新样本时把 `example.output` 原样传入（不经过任何算子）；`AugmentOp.transform` 的函数签名只返回新的 **instruction 文本**（`OpResult.text`），**在类型层面就改不到 output**。
- **违反后的现象**：数据集里出现"看起来合理但答案是错的"样本，且它们与真实样本混在一起，无法从报表上区分；训练 loss 正常下降但模型质量下降。

**纪律二：能改写答案正确性的增强，必须自证"答案本来就满足"。**

- **防的故障**：`constraint` 往指令后追加输出约束。若原答案 300 字而约束写"200 字以内"，这条样本自相矛盾——模型要么学会忽略指令，要么学会把答案砍短（而参考答案并没有砍短）。
- **落点**：`ConstraintSpec.satisfied_by`（每条约束一个判定），`CONSTRAINTS` 三条约束各自的守门条件；不满足就走 `AUG_GUARD_REJECTED` 并计入 `AugmentReport.guard_rejected`。
- **违反后的现象**：数据集中出现"指令与答案互相矛盾"的样本；训练后模型对指令的跟随度反而下降（因为一部分指令本就无法被满足）。实测本课程数据上，`请用中文回答。` 被 4 条英文/代码密集的答案正确跳过。

**纪律三：默认不启用会降低质量的算子。**

- **防的故障**：`noise` 加口语填充词，它模拟真实用户的口语输入，代价是"专业感"下降。
- **落点**：`AugmentOp.risky = True` + `DEFAULT_OPS` 不含 `noise`；样本打 `aug:noise` 标签，因此"这批里有多少是噪声增强的"永远可查。
- **违反后的现象**：训练出的模型在正式场景里说话带"嗯""那个"。

**为什么质量打分拦不住它**：噪声增强造成的质量下降**恰好不在五个维度里**——填充词不会让长度越界（`length`）、不产生 n-gram 重复（`repetition`）、不影响收尾（`structure`）、不动来源（`traceability`）、也不含占位符（`placeholder`）。实测把 `"嗯，什么是 RAG？，大概就是这个意思。"` 这类样本喂进打分器，五维与正常样本几乎一样。

**由此推出的通用判断**：

> **给流水线加一个算子之前，先问"它出错时谁会报警"。没人报警的算子，就必须默认关闭。**

## 第四部分：编程题

### 第 10 题（用不动点迭代与不变式钉住实现）

#### 参考实现

```python
"""习题第 10 题：配比不动点复算 + 增强 output 不变式."""

from __future__ import annotations

import math

from smart_research_agent.domain_data import (
    AUGMENT_OPS,
    DEFAULT_OPS,
    OPS,
    DomainDataPipeline,
    augment_example,
    group_counts,
    plan_mixing,
)
from smart_research_agent.finetune.schema import TrainingExample


def part_one() -> None:
    pipeline = DomainDataPipeline()
    raw, _ = pipeline.load_raw_batch()
    cleaned, _ = pipeline.cleaner.run(raw)
    counts = group_counts(cleaned, group_by="source")
    print(f"清洗后 {len(cleaned)} 条，来源分布 {counts}")

    for ratio in (0.5, 0.45, 0.4):
        plan = plan_mixing(cleaned, group_by="source", max_ratio=ratio)
        print(f"max_ratio={ratio}: quotas={plan.quotas} total_out={plan.total_out} "
              f"iterations={plan.iterations} feasible={plan.feasible}")

    # 手算复现 0.4 的逐轮迭代
    alive = dict(counts)
    for step in range(1, 10):
        total = sum(alive.values())
        cap = max(1, math.floor(0.4 * total + 1e-9))
        over = [name for name, value in alive.items() if value > cap]
        print(f"  第 {step} 轮：T={total}，cap=floor(0.4×{total})={cap}，超额组={over or '无'}")
        if not over:
            print(f"  收敛于第 {step} 轮，quotas={alive}")
            break
        for name in over:
            alive[name] = cap


def part_two() -> None:
    probes = {
        "prefix": TrainingExample(instruction="什么是 RAG？", output="检索增强生成。", source="s"),
        "constraint": TrainingExample(
            instruction="什么是 RAG？",
            output="检索增强生成，是一种把外部知识注入上下文的方法。",
            source="s",
            license="CC-BY-4.0",
        ),
        "paraphrase": TrainingExample(instruction="如何评估 RAG？", output="用召回率评估。", source="s"),
        "noise": TrainingExample(instruction="什么是 RAG？", output="检索增强生成。", source="s"),
    }
    for name in AUGMENT_OPS:
        example, op = probes[name], OPS[name]
        outcome = augment_example(example, op, offset=0)
        augmented = outcome.example
        assert augmented is not None, name
        # 四条不变式：output 不动、元信息继承、tags 追加一个算子标签
        assert augmented.output == example.output
        assert augmented.source == example.source
        assert augmented.license == example.license
        assert augmented.system == example.system
        assert augmented.input == example.input
        assert augmented.tags == example.tags + (f"aug:{name}",)
        print(f"{name:<11} risky={op.risky!s:<6} in_default={name in DEFAULT_OPS!s:<6} 不变式=OK")
        print(f"    原指令：{example.instruction}")
        print(f"    新指令：{augmented.instruction}")


if __name__ == "__main__":
    part_one()
    part_two()
```

```text
 max_ratio                                              quotas  total_out  iter  feasible
       0.5{'seed': 16, 'eval/agent_tasks': 5, 'eval/redteam_cases': 16}         37     1      True

       0.4{'seed': 10, 'eval/agent_tasks': 5, 'eval/redteam_cases': 10}         25     6      True

0.4 那一档的逐轮复算：
  第 1 轮：T=37，cap=floor(0.4×37)=14，超额组=['seed', 'eval/redteam_cases']
  第 2 轮：T=33，cap=floor(0.4×33)=13，超额组=['seed', 'eval/redteam_cases']
  第 3 轮：T=31，cap=floor(0.4×31)=12，超额组=['seed', 'eval/redteam_cases']
  第 4 轮：T=29，cap=floor(0.4×29)=11，超额组=['seed', 'eval/redteam_cases']
  第 5 轮：T=27，cap=floor(0.4×27)=10，超额组=['seed', 'eval/redteam_cases']
  第 6 轮：T=25，cap=floor(0.4×25)=10，超额组=无
  收敛于第 6 轮，quotas={'seed': 10, 'eval/agent_tasks': 5, 'eval/redteam_cases': 10}
```

三点值得注意：

1. **`0.45` 一档没有任何削减**：`cap = floor(0.45 × 37) = floor(16.65) = 16`，而两个大组各 16 条，`16 > 16` 为假 → 一轮就收敛。这说明"上限"是**严格大于**才触发；写循环时若用了 `>=`，同一份数据会立刻被砍掉 12 条——**边界符号在这种场景里足以让结论翻转**。
2. **两轮之间总数从 37 掉到 33 再到 31**：注意第 2 轮的下降幅度是 4（14+5+14=33 → 13+5+13=31），第 1 轮是 4（37 → 33）。收敛过程不是等比的，因为它受 `floor` 与"只有超额组才动"两条规则支配。
3. **`_floor_ratio` 里那个 `1e-9` 不是装饰**：`int(0.3 * 10)` 在 IEEE 754 下是 `2`（`0.3*10 == 2.9999999999999996`）。本课例子里 `0.4 × 25 = 10.000000000000002` 恰好偏上，但换成 `0.3` 或 `0.45` 就会踩坑。取整统一走 `math.floor(x + 1e-9)`，并**写在函数里**，让"取整口径只有一个出处"。

#### 为什么必须对**每一个**算子逐条断言

三条理由，每一条都对应一类真实缺陷：

1. **算子的实现是四段互相独立的代码。** `transform_prefix` / `transform_constraint` / `transform_paraphrase` / `transform_noise` 各自构造新的指令文本，其中任何一段都可能"顺手"改到别处。抽查一个算子只能证明那一个算子是对的——**"另外三个也应该没问题"是推测，不是证据**。
2. **聚合断言会掩盖单点缺陷。** 如果只写 `assert all(a.output == b.output for a, b in pairs)`，一条算子的越界改动会被另外三条的通过"平均"掉（更像的情况是：抽查正好抽到了好的那条）。逐条断言能让失败信息直接指向算子名。
3. **`noise` 是默认关闭的算子，恰恰最需要测试。** 它不在 `DEFAULT_OPS` 里，因此日常跑流水线永远不会碰到它——**"跑不到所以不用测"正是它出问题时最难被发现的原因**。一旦有人在某次实验里显式打开它，`output` 不变式必须仍然成立。这也是本课在测试里同时断言 `OPS["noise"].risky is True` 与 `"noise" not in DEFAULT_OPS` 的原因：**"风险被标记"与"风险被默认关掉"是两件事，都要有断言。**
