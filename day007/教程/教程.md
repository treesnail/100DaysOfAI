## 第二章：P 阶段复盘 —— 工程化底座

P 阶段的每个概念都用三节式复盘：**一句话本质 → 为什么 → 常见误区**。

### 2.1 pyproject.toml 与依赖管理

**一句话本质**：`pyproject.toml` 是项目的单一事实来源（Single Source of Truth）——元数据、依赖、工具配置全部集中在一个文件里。

**为什么**：

- 依赖分散在 `setup.py`、`requirements.txt`、各个工具自己的配置文件中时，"这个项目到底依赖什么"没有权威答案。集中管理后，任何人打开一个文件就能看清全貌。
- 运行时依赖（`dependencies`）与开发依赖（`[project.optional-dependencies].dev`）分离，让生产镜像只装必需品，CI 只装检查工具——安装体积和攻击面都最小化。
- `requires-python` 把版本兼容性问题从"运行时莫名报错"提前到"安装时明确拒绝"。

**常见误区**：

- **误区一：有了 pyproject.toml 就删掉 requirements.txt。** 实际上两者共存是常态——很多 CI 系统、Dockerfile、老旧工具链仍习惯读 `requirements.txt`。它是兼容层，不是冗余。
- **误区二：把开发工具（pytest、ruff）写进运行时依赖。** 后果是生产镜像里塞进一堆用不到的包，体积膨胀、漏洞面扩大。
- **误区三：依赖不写版本下界。** `"pydantic"` 和 `"pydantic>=2.0"` 的区别在于，后者明确宣告"我的代码用了 v2 的 API"，避免 pip 装到 v1 后出现无法理解的兼容错误。

### 2.2 配置管理：Pydantic Settings + .env

**一句话本质**：配置是带类型注解的类，程序启动时从环境变量和 `.env` 一次性解析并校验，之后全程共享一个单例。

**为什么**：

- **配置与代码分离**（12-Factor App 原则）：同一份代码，开发、测试、生产环境只换 `.env` 不换代码。
- **失败要趁早（Fail Fast）**：`Settings()` 在启动时就完成类型校验。`DEBUG=true` 写成 `DEBUG=ture` 会在启动瞬间报错，而不是三天后在某个分支里引发诡异行为。
- **密钥不进仓库**：`.env.example` 进版本控制作为模板，`.env` 被 `.gitignore` 拦截——这是防止 API Key 泄露到 GitHub 的第一道闸门。

**常见误区**：

- **误区一：把密钥硬编码进代码"先跑起来再说"。** 这个"先"字是安全事故的起点——一旦 commit，密钥就永久留在 Git 历史里，删除文件也救不回来。
- **误区二：在每个需要配置的函数里读 `os.environ`。** 配置散落各处，无法校验、无法审计、无法单测。统一走 `settings` 单例，测试时还能用 `monkeypatch.setenv` 干净地隔离。

### 2.3 日志系统：可观测性的第一道防线

**一句话本质**：日志是给未来的自己（和运维）留的现场记录，双通道输出（控制台 + 滚动文件）兼顾开发体验与生产可靠性。

**为什么**：

- Agent 系统的核心难题是**不确定性**：LLM 每一步的输出都不同。没有日志，Agent 给出错误答案时你完全无法回答"它当时在想什么"。day006 的 `ReactAgent.run()` 在每一步都记录原始输出，就是这条原则的直接落地。
- `print` 无级别、无格式、无持久化、无法过滤——四无产品，只配用于一次性脚本。

**常见误区**：

- **误区一：重复添加 handler 导致日志刷屏。** `logging.getLogger(name)` 返回全局单例，如果每次调用 `get_logger` 都 `addHandler`，一条日志会输出 N 次。我们的实现用 `if logger.handlers: return logger` 做了幂等保护——这个小细节值得记住，它是 logging 模块最常见的坑。
- **误区二：在日志里拼接敏感信息。** 日志会落盘、会被收集到日志系统，API Key、用户隐私数据绝不入日志。

### 2.4 Git：对象模型与分支的本质

**一句话本质**：Git 是内容寻址的不可变快照数据库；分支只是一个 41 字节的指针文件。

**为什么**：

- 理解"快照而非差异"后，`checkout` 切版本为什么是瞬时的、`checkout -b` 建分支为什么零成本，都不再是玄学。
- **原子提交**（一个 commit 只做一件事）让 `revert` 精确回滚、`bisect` 二分定位 bug 成为可能——这些能力在 100 天项目的排错中会反复救命。

**常见误区**：

- **误区一：rebase 已推送的分支。** rebase 重写 commit ID，等于篡改公共历史。黄金法则：只在本地未推送的分支上 rebase。
- **误区二：把暂存区当累赘。** 暂存区是 Git 的精髓设计——它让你把"顺手改的两处不相关代码"拆成两个语义清晰的 commit。
- **误区三：`reset --hard` 当常规武器。** `--hard` 会无提示地销毁工作区未提交的修改，是 Git 里少数真正不可逆的操作。

### 2.5 测试：pytest、fixture 与覆盖率

**一句话本质**：测试是可执行的文档 + 回归防护网；fixture 是测试的依赖注入；覆盖率是发现"没测什么"的工具，不是质量本身。

**为什么**：

- AI 项目迭代快，每次改 prompt、换模型、加工具都可能破坏既有行为。毫秒级反馈的单元测试是唯一跟得上这种迭代速度的验证手段。
- `parametrize` 用数据驱动消除复制粘贴，失败时测试名自带输入值（如 `[false-True]`），定位零成本。
- `branch = true` 的分支覆盖率比行覆盖率严格——行覆盖 100% 可能只走了一半的 if/else。

**常见误区**：

- **误区一：盲目追求 100% 覆盖率。** 边际收益递减，还会诱使你写"只调用不断言"的覆盖式测试。我们把底线设在 `fail_under = 80`：防缺失，但不凑数字。
- **误区二：测试依赖执行顺序。** 这违反 FIRST 原则中的 Independent。每个测试必须能单独运行——fixture 的 function 默认作用域正是为此设计。
- **误区三：测试里发真实网络请求。** 慢、脆、费钱、不可重复。day005 的 `MockLLM` 就是这个问题的答案——本周所有 Agent 测试完全离线。

### 2.6 Docker：环境即代码

**一句话本质**：容器是共享宿主机内核的进程级隔离；Dockerfile 是对运行环境的精确、可执行描述。

**为什么**：

- 消灭"在我机器上能跑"问题：任何人 `docker build` 得到一模一样的环境。
- 镜像分层缓存决定了 Dockerfile 的写法：**变化频率低的内容（依赖）放前面，变化频率高的内容（源码）放后面**。违反这条，每改一行代码都要重装几分钟依赖。

**常见误区**：

- **误区一：让 `.env` 进入构建上下文。** 即使后续层"覆盖"了密钥文件，它仍存在于历史层中可被提取。`.dockerignore` 必须排除 `.env`——密钥绝不进任何镜像层。
- **误区二：把容器当轻量虚拟机用。** 容器哲学是一个容器跑一个进程、可随时销毁重建；在里面装 sshd、跑一堆服务是 VM 思维的残留。

### 2.7 P 阶段小结：一条暗线

| 概念 | 一句话本质 | 共同的工程思想 |
|------|-----------|---------------|
| pyproject.toml | 单一事实来源 | 把一切"靠人肉记住"的东西 |
| Pydantic Settings | 启动时校验的配置单例 | 变成"由工具和代码保证"的东西 |
| logging | 可追溯的现场记录 | |
| Git | 不可变快照 + 指针分支 | |
| pytest | 可执行文档 + 回归防护 | |
| Docker | 环境即代码 | |

## 第三章：M1-D1~D4 复盘 —— Agent 是如何跑起来的

### 3.1 Agent 四组件：一个心智模型

**一句话本质**：Agent = 感知（输入）+ 推理（LLM 大脑）+ 行动（工具）+ 记忆（上下文），四者围绕一个循环协作。

```text
              ┌──────────────────────────────┐
              │           Agent              │
              │                              │
   任务 ───▶  │  感知 ──▶ 推理 ──▶ 行动       │  ───▶ 作用于环境
              │           ▲        │         │
              │           └──记忆──┘         │
              │        （上下文与历史）        │
              └──────────────────────────────┘
```

**为什么**：这个分解的价值在于**定位问题**。当 Agent 表现不佳时，你可以问：是感知不全（信息没喂够）？推理出错（prompt 或模型问题）？行动失败（工具 bug）？还是记忆丢失（上下文被截断）？没有组件划分，所有问题都糊成"Agent 又傻了"。

**常见误区**：

- **误区一：认为 Agent 就是"调 LLM 的封装"。** 普通 LLM 调用是"一问一答"，Agent 是"目标驱动的多步循环"——差别在循环、在工具、在状态。
- **误区二：四个组件必须同一天建好。** 本周的顺序恰恰相反：D1 先立骨架把组件的"位置"定义出来，再逐日填充。接口先行，实现后补——这是大型系统对抗不确定性的标准打法。

### 3.2 ReAct 范式：让推理留下痕迹

**一句话本质**：ReAct = Reasoning（思考）+ Acting（行动），强制 LLM 按 `Thought → Action → Action Input → Observation` 的节奏交替输出，把黑盒推理变成白盒轨迹。

**为什么**：

- 纯 Chain-of-Thought 只能"想"，遇到需要实时信息的问题（现在几点？这个数算出来是多少？）只能瞎编——这就是幻觉的来源之一。ReAct 让模型可以"动手查"，答案有了事实锚点。
- 每一步 Thought 都显式输出，推理过程**可审计、可调试**。Agent 答错时，你能看出它在哪一步想歪了——这直接呼应了 P 阶段建立的可观测性思想。

**常见误区**：

- **误区一：以为 ReAct 是一种模型。** ReAct 是一种 **prompt 约定 + 外部解析循环**，任何够强的 LLM 套上 SYSTEM_PROMPT 和解析器都能跑。我们 day006 用 MockLLM 离线驱动整个循环就是证明。
- **误区二：认为步骤越多越好。** 每一步都是一次付费的 LLM 调用，且有累积出错风险。`max_steps` 上限不是限制，是必要的熔断保护。

### 3.3 ReactAgent 骨架：接口先行（day003）

**一句话本质**：day003 的骨架用 `NotImplementedError` 占住 `run()` 的位置，把"Agent 由 llm、tools、max_steps、history 构成"这个**结构决策**固定下来，实现留给后续。

```python
class ReactAgent:
    """基于 ReAct（Reasoning + Acting）范式的 Agent 骨架."""

    def __init__(self, llm=None, tools=None, max_steps: int = 10):
        self.llm = llm
        self.tools = tools or []
        self.max_steps = max_steps
        self.history: list[dict] = []
```

（骨架版完整代码见 [day006 快照被替换前的说明](../源码/README.md)；day006 已用完整版替换。）

**为什么**：先定义接口再填充实现，让 D2~D3 可以并行开发工具和 LLM 层而互不阻塞——大家对着同一个构造函数签名工作。测试 `test_run_not_implemented_yet` 还有一层妙用：它断言"此处尚未实现"，day006 实现后这个测试自然被替换，进度由测试显式标记。

**常见误区**：

- **误区一：骨架里塞满半成品逻辑。** 骨架的职责是定义结构，不是提前实现。塞得越多，后续重构越痛。
- **误区二：`max_steps` 用魔法数字。** 它进构造函数参数（默认 10）而非硬编码在循环里，测试时才能用小值快速验证熔断逻辑。

### 3.4 BaseTool：给"能力"立契约（day004）

**一句话本质**：`BaseTool` 用四个抽象成员（`name`、`description`、`parameters`、`execute`）定义了"什么是工具"，让 Agent 无需知道任何具体工具的存在。

```python
class BaseTool(ABC):
    @property
    @abstractmethod
    def name(self) -> str: ...        # Agent 用它路由调用

    @property
    @abstractmethod
    def description(self) -> str: ... # 给 LLM 阅读的自然语言描述

    @abstractmethod
    def execute(self, **kwargs) -> str: ...  # 执行入口
```

完整代码见 [../../day006/源码/smart-research-agent/smart_research_agent/tools/base.py](../../day006/源码/smart-research-agent/smart_research_agent/tools/base.py)。

**为什么**：

- **依赖倒置**：Agent 依赖 `BaseTool` 抽象，不依赖 `CalculatorTool` 具体类。新增工具不需要改 Agent 一行代码——这是开闭原则的教科书落地。
- `description` 和 `parameters` 不是装饰，是**给 LLM 读的接口文档**：LLM 靠 description 决定何时调用，靠 parameters 决定传什么参数。写得含糊，工具再强也用不上。

**常见误区**：

- **误区一：把工具写成一堆自由函数。** 没有统一契约，Agent 侧就必须为每个工具写 if-else，工具数量一多立即失控。
- **误区二：`execute` 直接抛异常。** 工具执行失败应该返回错误字符串（作为 Observation 喂回 LLM），让 LLM 有机会自我纠正；抛异常会直接炸掉整个循环。day006 的 `_execute_tool` 用 try/except 兜底正是这一思想的防线。

### 3.5 CalculatorTool：AST 白名单 vs eval（day004）

**一句话本质**：计算器工具不用 `eval`，而是把表达式解析成抽象语法树（AST），只对白名单内的节点类型（数字、四则运算、乘方、取模、正负号）求值。

```python
_BIN_OPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.Pow: operator.pow,
    ast.Mod: operator.mod,
}

def _safe_eval(node: ast.AST) -> float:
    if isinstance(node, ast.Constant):
        if isinstance(node.value, (int, float)):
            return node.value
        raise ValueError("仅支持数字常量")
    if isinstance(node, ast.BinOp) and type(node.op) in _BIN_OPS:
        return _BIN_OPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    ...
    raise ValueError("不支持的表达式")
```

完整代码见 [../../day006/源码/smart-research-agent/smart_research_agent/tools/calculator.py](../../day006/源码/smart-research-agent/smart_research_agent/tools/calculator.py)。

**为什么**：工具的输入来自 LLM 的输出——本质上是**不可信输入**。`eval("__import__('os').system('rm -rf /')")` 这个经典注入在 AST 白名单下直接报"不支持的表达式"，因为 `Call`（函数调用）节点根本不在白名单里。测试 `test_rejects_code_injection` 锁死了这个安全属性。

**常见误区**：

- **误区一："eval 快一点，本地工具没风险"。** 只要输入可能来自 LLM 或网络，eval 就是任意代码执行后门。安全属性必须在第一天内建，事后补防成本极高。
- **误区二：黑名单思维。** "禁止 import、禁止 exec"永远禁不完（Python 的反射和魔术方法花样太多）；白名单"只放行明确允许的"才可枚举、可验证。

### 3.6 ToolRegistry：从"有几个工具"到"工具可发现"（day005）

**一句话本质**：注册表是工具的字典 + 校验器 + 描述生成器，把"Agent 能用哪些工具"从硬编码变成运行时数据。

```python
class ToolRegistry:
    def register(self, tool: BaseTool) -> None:
        if not isinstance(tool, BaseTool):
            raise TypeError("只能注册 BaseTool 的实例")
        if tool.name in self._tools:
            raise ValueError(f"工具重复注册: {tool.name}")
        self._tools[tool.name] = tool

    def describe(self) -> str:
        """生成给 LLM 阅读的工具清单文本."""
        return "\n".join(f"- {t.name}: {t.description}" for t in self._tools.values())
```

完整代码见 [../../day006/源码/smart-research-agent/smart_research_agent/tools/registry.py](../../day006/源码/smart-research-agent/smart_research_agent/tools/registry.py)。

**为什么**：

- `describe()` 的输出会被拼进 day006 的 `SYSTEM_PROMPT`——**注册一个新工具，LLM 的"武器清单"就自动更新**，prompt 不用手改。这是数据驱动 prompt 的雏形。
- 注册时做类型校验和重名拦截，把两类错误消灭在启动阶段而非推理中途（又一个 Fail Fast）。

**常见误区**：

- **误区一：把工具列表硬编码在 prompt 里。** 工具增删时 prompt 与代码不同步，LLM 会调用不存在的工具或不知道新工具存在。
- **误区二：允许重名覆盖。** 静默覆盖意味着同名工具行为悄悄改变，排查时是噩梦。宁可启动时报错。

### 3.7 LLM 调用层：MockLLM 是本周最被低估的设计（day005）

**一句话本质**：`BaseLLM` 抽象 + `Message` 数据类 + `MockLLM` 确定性实现 + `OpenAICompatibleLLM` 真实实现，让 Agent 层对"底层是哪家模型"完全无感。

```python
class BaseLLM(ABC):
    @abstractmethod
    def chat(self, messages: list[Message], temperature: float = 0.7,
             max_tokens: int = 1024) -> str:
        """发送对话消息，返回模型的文本回复."""
```

```python
class MockLLM(BaseLLM):
    """按预设脚本回复的 LLM，用于无网络、无 API Key 的测试环境."""

    def chat(self, messages, temperature=0.7, max_tokens=1024) -> str:
        self.calls.append(messages)
        if self._responses:
            return self._responses.pop(0)
        return self._default
```

完整代码见 [llm/base.py](../../day006/源码/smart-research-agent/smart_research_agent/llm/base.py)、[llm/mock.py](../../day006/源码/smart-research-agent/smart_research_agent/llm/mock.py)、[llm/openai_compatible.py](../../day006/源码/smart-research-agent/smart_research_agent/llm/openai_compatible.py)。

**为什么**：

- **依赖倒置第二次出现**：`ReactAgent` 的构造函数接收 `BaseLLM`，测试注入 MockLLM，生产注入 OpenAICompatibleLLM——同一套循环逻辑，零修改跑两种环境。
- `MockLLM` 让 ReAct 循环的测试**确定、离线、免费、毫秒级**。它还记录了 `calls`，使断言可以验证"第二次调用时消息里是否包含错误 Observation"这种时序行为。
- `Message` 用 dataclass 而非裸 dict，换来类型检查和 `to_dict()` 的单一转换点。

**常见误区**：

- **误区一：在 Agent 代码里直接 `import openai`。** 换模型供应商时全项目翻改；抽象层把更换成本压缩到一个新类。
- **误区二：Mock 只返回固定值。** 好的 Mock 要模拟**协议**（按顺序消费脚本、记录入参），而不只是返回字符串——否则测不到多轮交互的逻辑。

### 3.8 解析器与完整循环：把一切接通（day006）

**一句话本质**：`parse_react_output` 把 LLM 的自由文本解析成结构化 `ReActStep`；`ReactAgent.run()` 则是"LLM 输出 → 解析 → 执行工具 → Observation 回填 → 再问 LLM"的确定性循环。

```python
for step_no in range(1, self.max_steps + 1):
    raw = self.llm.chat(messages)
    step = parse_react_output(raw)
    self.history.append(step)
    if step.final_answer is not None:
        return step.final_answer
    observation = self._execute_tool(step)
    messages.append(Message(role="assistant", content=raw))
    messages.append(Message(role="user", content=f"Observation: {observation}"))
return "达到最大步数限制，未能得出最终答案"
```

完整代码见 [../../day006/源码/smart-research-agent/smart_research_agent/agent/react_agent.py](../../day006/源码/smart-research-agent/smart_research_agent/agent/react_agent.py) 与 [agent/parser.py](../../day006/源码/smart-research-agent/smart_research_agent/agent/parser.py)。

**为什么**：

- 循环的两个出口设计得很克制：**LLM 给出 Final Answer**（正常结束）或 **步数耗尽**（熔断）。没有第三个隐式出口，行为完全可预测。
- 错误也走 Observation 通道：工具不存在、工具执行异常，都作为文本 Observation 喂回 LLM，给它一次自我修正的机会。测试 `test_unknown_tool_feeds_error_back` 验证的正是这条自愈路径。
- 解析器独立成模块，使"prompt 格式变化"只影响 `parser.py` 一个文件——单一职责的回报。

**常见误区**：

- **误区一：解析失败就让整个 Agent 崩溃。** LLM 输出格式天然不稳定，解析层要假设输入是脏的；`ReActParseError` 独立定义，正是为了上层能选择性捕获和重试（后续会加）。
- **误区二：在循环里静默吞掉所有异常。** 注意 `_execute_tool` 捕获异常后返回错误字符串并 `logger.warning`——**吞掉异常但留下日志**，这和"裸 except 什么都不做"有天壤之别。
- **误区三：忘记把 assistant 的原始输出回填进 messages。** 缺了 `messages.append(Message(role="assistant", content=raw))` 这一步，LLM 看不到自己上一步说了什么，多轮推理就断裂了。

## 第四章：全链路串讲 —— 一个任务的完整旅程

这是本周最重要的一张图。任务"上海人口的两倍是多少？"从进入到出答案，每一步经过哪个组件、哪个文件：

```text
用户任务: "上海人口的两倍是多少？"
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ ReactAgent.run(task)                    agent/react_agent.py    │
│  ① 组装 messages:                                               │
│     system ← SYSTEM_PROMPT.format(tools=registry.describe())    │
│     user   ← "任务: 上海人口的两倍是多少？"                        │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ llm.chat(messages)   （生产: OpenAICompatibleLLM / 测试: MockLLM）│
│  ② LLM 输出:                                                    │
│     "Thought: 需要知道上海人口，假设约 2400 万，先算两倍           │
│      Action: calculator                                         │
│      Action Input: 24000000 * 2"                                │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ parse_react_output(raw)                          agent/parser.py│
│  ③ 正则提取 → ReActStep(thought=..., action="calculator",        │
│                          action_input="24000000 * 2")           │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ _execute_tool(step)                     agent/react_agent.py    │
│  ④ registry.get("calculator") → CalculatorTool                  │
│     按 parameters.required 的第一个键组装 kwargs                  │
│     tool.execute(expression="24000000 * 2")                     │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ CalculatorTool.execute                tools/calculator.py       │
│  ⑤ ast.parse → AST 白名单校验 → 求值 → "48000000.0"             │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼ （Observation 回填）
┌─────────────────────────────────────────────────────────────────┐
│ messages += [assistant: 原始输出, user: "Observation: 48000000.0"]│
│  ⑥ 再问 LLM → "Thought: 已得到结果                              │
│                Final Answer: 上海人口的两倍约为 4800 万"          │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────────────────┐
│ ⑦ parse 出 final_answer → run() 返回，history 记录全部 2 步     │
│   每一步都有 logger.info 落盘（控制台 + logs/*.log）              │
└─────────────────────────────────────────────────────────────────┘
    │
    ▼
最终答案: "上海人口的两倍约为 4800 万"
```

走查要点（合上书能复述才算真懂）：

1. **谁是循环的驱动者？** 不是 LLM，是 `run()` 里的 Python for 循环。LLM 只是每步被询问一次——Agent 的控制权在代码手里。
2. **Observation 是怎么回到 LLM 视野的？** 通过往 messages 追加一条 `role="user"` 的消息。LLM 本身无状态，"记忆"完全是靠重放完整消息列表实现的。
3. **错误如何被消化？** 工具不存在/执行异常 → 错误字符串作为 Observation → LLM 下一步看到错误后自我修正或放弃。
4. **什么时候停止？** 出现 `Final Answer:` 或步数达到 `max_steps`。

> 思考题：如果 LLM 连续 3 步输出不符合格式的文本（没有 Thought），当前实现会在哪一环抛什么异常？要让它"给 LLM 一次重试机会"，最小改动应该改哪个文件？（提示：异常在 parser.py 抛出，重试逻辑该加在 react_agent.py 的循环里。）

## 第五章：易混淆概念辨析

复习时最容易丢分的不是"完全不懂"，而是"两个概念记混"。把本周最易混淆的六对概念放在一起对比：

### 5.1 行覆盖率 vs 分支覆盖率

| 维度 | 行覆盖率 | 分支覆盖率 |
|------|----------|-----------|
| 度量什么 | 哪些代码行被执行过 | 每个 if/else 的真假两个方向是否都走过 |
| 宽松程度 | 宽松 | 严格 |
| 本项目配置 | 默认开启 | `branch = true` 显式开启 |
| 典型盲区 | 无（行没执行就没覆盖） | 行覆盖 100% 但分支只走了一半 |

一句话记忆：**行覆盖回答"代码跑没跑过"，分支覆盖回答"情况想没想到"。**

### 5.2 merge vs rebase

| 维度 | merge | rebase |
|------|-------|--------|
| 历史形态 | 分叉后汇合，保留真实历史 | 直线，改写历史 |
| commit ID | 原提交不变 | 生成新 ID |
| 已推送分支 | 安全 | **危险**（黄金法则禁止） |
| 本项目约定 | 学习项目用 `--no-ff` merge | 仅本地整理提交时用 |

### 5.3 eval vs AST 白名单

| 维度 | `eval()` | AST 白名单 |
|------|----------|-----------|
| 能力 | 执行任意 Python 代码 | 只放行白名单节点类型 |
| 面对 LLM 生成的输入 | 任意代码执行后门 | 非白名单节点直接拒绝 |
| 防御思路 | 无防御 / 黑名单（禁不完） | 白名单（可枚举、可验证） |
| 本项目选择 | 弃用 | `CalculatorTool` 采用 |

### 5.4 BaseLLM vs MockLLM vs OpenAICompatibleLLM

```text
        BaseLLM（抽象契约：chat(messages) -> str）
           │
     ┌─────┴──────┐
     ▼            ▼
  MockLLM    OpenAICompatibleLLM
  脚本化回复    真实 API 调用
  离线/确定/免费  联网/不确定/计费
  用于：全部测试  用于：生产运行
```

三者是"契约与两个实现"的关系，不是三个平行概念。`ReactAgent` 只认识 BaseLLM——这就是测试能离线的全部秘密。

### 5.5 Message 对象 vs 裸 dict

| 维度 | `Message` dataclass | 裸 dict |
|------|---------------------|---------|
| 类型检查 | mypy 可查 `role`/`content` | 拼错键名运行时才炸 |
| 序列化 | `to_dict()` 单一转换点 | 各处手写，格式易漂移 |
| IDE 支持 | 自动补全 | 无 |

### 5.6 Thought vs Observation

这是 ReAct 里最根本的一对：**Thought 是 LLM 写的，Observation 是工具给的。**

- Thought：模型的主观分析——"我觉得需要先算一下"。可能错，可能幻觉。
- Observation：代码执行工具后的客观结果——`"Observation: 100"`。是事实锚点。

ReAct 之所以比纯 CoT 可靠，核心就在于**用 Observation 的事实不断校正 Thought 的想象**。记反了这两个角色的来源，整个范式就白学了。

> 思考题：如果让 LLM 自己输出 Observation（有些粗糙实现确实这么干），ReAct 会退化成什么？（提示：退化成纯 CoT——模型左右互搏，幻觉再无外部校正。）

## 第六章：本周沉淀的设计原则

把具体代码抽掉，本周真正学到的是这几条可迁移的原则：

| 原则 | 本周的落地处 | 一句话解释 |
|------|-------------|-----------|
| **依赖倒置** | BaseLLM、BaseTool | 依赖抽象，不依赖实现；替换成本压到最低 |
| **失败要趁早** | Settings 启动校验、注册表重名拦截 | 错误暴露得越早，代价越小 |
| **不可信输入防御** | AST 白名单、parse 层容错 | 凡是来自外部（含 LLM）的输入都按恶意处理 |
| **可观测性内建** | logger 贯穿每个模块 | 不能追踪的系统等于不能调试的系统 |
| **测试即文档** | 每个新模块当日配测试 | 测试写的是"这个组件承诺什么行为" |
| **接口先行** | D1 骨架、BaseTool/BaseLLM 抽象 | 结构决策和实现决策分开做 |

注意这些原则之间的呼应关系：因为依赖倒置，MockLLM 才能存在；因为 MockLLM 存在，测试才能离线；因为测试离线且快速，"每日新增代码当日验证"才可持续。**好的设计决策会互相放大。**
