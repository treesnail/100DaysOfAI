
四个层次各自的"一句话本质"：

| 层 | 覆盖阶段 | 一句话本质 | 判据形态 |
|----|----------|-----------|----------|
| 应用层 | M1、M2 | 让 LLM 会"做"（Agent），并把这些能力**标准化地暴露**（MCP） | 契约测试 / 协议测试 |
| 评估与系统层 | M3、M4 | 先造尺子（评估），再造系统（应用），最后把两者焊成一条流水线 | 门禁阈值 / 分组汇总 |
| 模型与数据层 | M5、M6 | 把"通用模型"变成"专属模型"（微调），把"外部知识"接进生成（RAG） | 合取判定 / 绑定校验 |
| 原理层 | M7、M8 | 一次点积 → 一次反向 → 一条训练管线；把流程也变成可断言的算术 | 相等 / 上界 / 下界三类 |

一个值得记住的规律：**越往上，判据越像"业务阈值"；越往下，判据越像"数值对账"**。
M3 的门禁是 `min_completion_rate >= 0.6` 这类留裕度的业务线；M8 的判据是
`恢复训练最大绝对差 == 0.0` 这类不留给度的数值线。两者都叫"判据"，
但它们能反驳的错误完全不是一类。

## 第二章：应用层复盘 —— M1 Agent 与 M2 MCP

应用层只干了一件事的两个侧面：**M1 造内核**（Agent 自己会做事），**M2 标准化对外**
（别人也能标准地用这些能力）。两者用同一个 `ToolRegistry` 接缝连起来。

### 2.1 M1 Agent：智能的最小回路（day003 ~ day015）

- **本质**：给只会"说"的 LLM 加上"做"的回路。
  ```text
  ReAct 循环（day006）   Thought → Action → Observation → … → Final Answer（带 max_steps 上限）
  工具契约（day004）     BaseTool = name + description + parameters schema + execute()
  依赖倒置（day005）     ReactAgent 依赖 BaseLLM 抽象，MockLLM 是它的测试实现
  可靠性三件套           短期/长期记忆（day008/009）+ Planner（day010）+ Reflexion（day011）
  编排与设防             LangGraph 状态图（day013）+ 输入/工具/输出三道防线（day015）
  ```
- **为什么**：整个项目的可测试性都来自 day005 的**依赖倒置**——先有 `BaseLLM` 抽象，
  `MockLLM` 才成为可能；没有它，后面每一天的测试都要访问网络，FIRST 原则全部失守。
  同样地，**边界处的硬校验**（`parser.py` 的正则、`CalculatorTool` 的 AST 白名单、
  `parse_plan` 的四道防线）才是系统不被坏输出击穿的原因：提示词只是软约束。
- **误区**：
  ```text
  ① 以为 Agent 是"更聪明的提示词"（它是一个有循环、有状态、有外部副作用的系统程序）
  ② 用 eval 解析计算表达式（要 AST 白名单；eval 会执行任意代码）
  ③ 循环不设 max_steps（概率模型可能永远不收尾；上限是把"可能无限"变成"必然终止"）
  ④ 以为"提示词写清楚模型就会守规矩"（软约束只降失败率，硬约束才保系统）
  ⑤ 以为模型"记得我们聊过什么"（LLM API 无状态，记得的是你的代码）
  ⑥ 以为安全是"上线前加的功能"（权限与审计是架构属性，事后补救成本极高）
  ```

### 2.2 M2 MCP：把能力标准化地暴露出去（day016 ~ day023）

- **本质**：MCP = **JSON-RPC 2.0 之上的能力描述与调用协议**，用三类原语分类能力。
  ```text
  协议（day016）   JsonRpcRequest / JsonRpcResponse / JsonRpcError；包名固定 mcp_server（不得叫 mcp）
  三原语（day017/018） Resource（URI 寻址、只读）/ Tool（有副作用）/ Prompt（参数化模板）
  传输（day019）   stdio（本地子进程）与 SSE（HTTP 长连接）——能力定义与传输解耦
  Client（day020） 连接 → 握手 → 能力发现，发现到的工具动态注册回 ToolRegistry
  部署与测试（day022/023） Docker 冻结分发单元；内存内测试把协议正确性变成离线单测
  ```
- **为什么**：没有 MCP 之前，M 个框架 × N 个工具 = M×N 种集成；把工具侧与框架侧各标准化一次，
  复杂度降为 **M+N**——和 USB-C 对充电接口做的事一样。而 M1 → M2 的桥接点就是
  day018 那句"**把 `BaseTool` 包一层就成了 MCP Tool**"：执行逻辑留在 M1，协议细节留在 M2。
- **误区**：
  ```text
  ① 把项目内自建协议包命名为 mcp（会遮蔽官方包，导入时拿到自己的包，排查极痛苦）
  ② 以为 MCP 是"远程调用协议"（stdio 时对端就在本机；协议与部署拓扑解耦）
  ③ 把所有数据都做成 Tool（只读数据用 Resource，语义更清晰，客户端才敢预取/缓存）
  ④ 忽视异常回退（远程调用会把 JSON-RPC error 交给 ReAct 循环，必须在包装层翻译成 Observation）
  ⑤ stdio 容器里把日志写 stdout（会污染 JSON-RPC 流；日志必须走 stderr）
  ⑥ 以为测协议要真起服务（主力用内存内传输，速度差两个数量级）
  ```

## 第三章：评估与系统层复盘 —— M3 Harness 与 M4 大模型应用

这一层的两句核心命题对着看：**M3 是"不可度量 ⇒ 不可优化"，M4 是"能力不集成 ⇒ 只是零件"**。

### 3.1 M3 Harness：先把"感觉不错"变成"可判定"（day025 ~ day032）

- **本质**：M3 的全部代码只实现了一个骨架——`evaluation/harness.py` 的四步。
  ```text
  load_dataset（数据集） → evaluate（执行） → 评分（判定） → summary（汇总，必须 by_tag 分组）
  ```
- **为什么**：因为这四步各对应一条纪律，违反的后果都可复现。day025 的示例数据集 6 条
  （math / qa / safety）当天实测 `pass_rate = 5/6 = 0.8333`，而 **knowledge 组只有 0.5**——
  这一个数字就说明了"为什么汇总必须分组"：**总分掩盖塌方**。再往下，三把尺子把
  "好不好"拆成可算的量：Prompt 评估是**规则 0.4 + 裁判 0.6**（`TIE_THRESHOLD = 0.05`），
  输出质量是 **0.4/0.4/0.2** 三因子，Agent 评估是**完成率 / 步数效率 / 工具准确性**三条
  （实测 0.625 / 0.79 / F1 0.71 / 顺序 1.00，拼出"通过率偏低但工具用得对"这一诊断）。
- **为什么要有红队**：day031 用 16 条真实用例（5 注入 + 5 越狱 + 5 PII + 1 工具滥用）
  去攻自己的防线，**基线整体拦截率 56.3%，修复后 100%**；而修复动作全落在既有模块里
  （补规则 + 修掉一条写错的正则），**新增能力一个都没做**。
- **误区**：
  ```text
  ① "跑几个 demo 就算评估"（不可复现，无法回答"明天是不是变差了"）
  ② "只报总通过率"（knowledge 组的 0.5 会藏在 0.83 的总分里）
  ③ "100% 拦截率 = 安全"（它只说明当前这 16 条过不去；红队的资产是用例集在增长）
  ④ "只加新规则、不检查旧规则"（修一条写错正则的收益大于新增 5 条）
  ⑤ "门禁越严越好"（天天误报的门禁一定会被关掉；松紧应与回归后果成正比）
  ⑥ "格式校验也调 LLM"（能一行代码判定的事去调模型，是最常见的成本浪费）
  ```

### 3.2 M4 大模型应用：从"会推理的循环"到"可运营的系统"（day033 ~ day046）

- **本质**：十二天从"理解模型"一路走到"运营系统"，最后焊成一条**六阶段流水线**。
  ```text
  输入侧护栏 → 语义缓存 → 模型路由与生成 → 成本归因 → 输出侧审核 → 缓存回写
   guard       cache       generate          account     moderate     store
  ```
- **为什么**：**顺序即策略**。三条安全约束都被写成了可观测的断言：
  护栏最先（被判定为注入的请求**模型完全不被调用**，`llm.calls == []`）；
  缓存在护栏之后（否则恶意请求会先命中缓存直接返回，护栏形同虚设）；
  审核在回写缓存之前（缓存里必须存**脱敏后**文本，否则一次 PII 泄漏会被缓存变成**持续性泄漏**）。
  day046 的实测三条路径：满路径 6 阶段 `total_ms=13.0`、拒答路径 1 阶段 `3.0`、
  命中路径 3 阶段 `7.0`——**耗时断言即阶段数断言**。
- **为什么横切线值得学**：M4 反复出现"**扩展抽象、零改动**"。
  ```text
  day039  BaseLLM 加流式      stream 默认 yield self.chat(...) 整段返回
  day040  BaseLLM 加视觉      supports_vision 默认 False；chat_vision 默认抛 NotImplementedError
  day041  EmbeddingProvider 加批量   embed_batch 默认逐条调用 embed
  day045  BaseLLM 加本地实现  LocalModelLLM 新增，但接口零变化
  ```
  规律是：**加"带默认值的具体方法/属性"，而不是加"抽象方法"**——后者会逼所有既有实现
  同时改造。失败安全方向则统一为"**能退避就不崩溃，且退避必须留痕**"。
- **误区**：
  ```text
  ① "Few-shot 能教知识"（它校准格式与风格，不补知识）
  ② "CoT 永远有益"（简单任务上"想多了反而错"，要用评估对比而不是假设）
  ③ "文本解析能保证格式"（概率性的；原生 tool_calls 才是确定性）
  ④ "function calling 返回的参数可以直接执行"（必须 validate_arguments）
  ⑤ "Agent 实例可以跨请求复用"（Agent 持有单次任务状态，注入的必须是工厂）
  ⑥ "流式让回答更正确"（它只改 TTFT，不改内容正确性）
  ⑦ "缓存与审核的先后无所谓"（先写缓存后审核 = 把一次性泄漏变成持续性泄漏）
  ⑧ "装了成本追踪器就等于能归因"（包装器会挡住用量，必须显式透传叶子）
  ```

### 3.3 M3 与 M4 如何互相提出需求

复习日最值得确认的一件事是：**评估代码与业务代码耦合度极低，但两者在需求上互相牵引**。

| M4 的形态升级 | 它给 M3 提出的新指标 |
|---------------|----------------------|

## 第四章：模型与数据层复盘 —— M5 微调 与 M6 RAG

这一层把"通用模型"变成"专属模型"（M5），把"外部知识"接进生成（M6）。两者的共同点：
**都需要版本、都需要绑定、都必须回答"线上跑的到底是不是那一版"**。

### 4.1 M5 微调：从一批数据到一个线上模型版本（day048 ~ day060）

- **本质**：一条**离线**链路 + 最后一环的**上线三步**。
  ```text
  离线（day048~059）  数据（day048/057）→ 训练（day050/051/052）→ 评估（day053）
                      → 对齐（day054/055）→ 版本（day058）→ 流水线（day059）
  上线（day060）      部署（放哪一版 / 什么形态）→ 切换（灰度接管）→ 验证（切的依据）
  ```
- **为什么**：因为这一层最贵的失败全都"不报错"。day060 的五条绑定检查里，
  四条是阻塞项，每一条都把"**一个文件里的声明**"与"**另一个地方的自述**"对上：
  `serving_name`（配置 ↔ 端点自述）、`base_model`（部署单元 ↔ 端点自述）、
  `adapter_hash`（版本三元组 ↔ 端点自述短哈希）、`kind_shape`（形态 ↔ 有没有适配器）。
  而 `registry_head`（绑定版本不是注册表 head）**刻意不阻塞**——因为灰度发布的本质
  就是"部署的不是 head"，把它设成阻塞会逼团队"先提升阶段再过校验"。
  配套的三个数字同样来自现场：LoRA 与全参的显存差（7B 上 75.31 / 12.65 / 3.33 GiB）、
  合并门禁在全部上下文上逐位比较 logits（实测差 `0.00e+00`）、
  以及"一个基座 + 10 个适配器"比 10 个合并模型省 **10.00×**。
- **误区**：
  ```text
  ① 以为"可发布"等于"已上线"（注册表说 stable，端点可能加载的是上一份适配器）
  ② 声明 adapter 形态却没给 adapter_dir（构造期应拦住；否则会安静地服务基座）
  ③ 反向降级（云端失败时把流量交给未验证的专属模型；两个故障会互相掩盖）
  ④ 灰度用随机分流（哈希分桶才会让"同一句话被问一万次走同一侧"）
  ⑤ "流失率正常"就以为模型很稳（fail_open=True 会把 fallback_count=1 藏起来）
  ⑥ "自建更便宜"缺主语（云端是可变成本、自建是固定成本：0 请求时云端 $0，自建照付）
  ⑦ 比率比较不做浮点容差（19/20 − 20/20 比 −0.05 小，结论还会随分母翻转）
  ```

### 4.2 M6 RAG：把知识接进生成，并守住"检索到的确实是新版"（day061 ~ day072）

- **本质**：一条**离线建索引 + 在线检索生成**的链路，末端加一层**运维**。
  ```text
  链路   文档解析（day061）→ 分块（day062）→ 向量库（day064）→ 索引（day065）
         → 检索器（day066）→ 混合检索（day067）→ 重排序（day068）→ 生成（day069）
         → 评估（day071）→ 生产化（day072）
  护栏   检索为空时一次 LLM 都不调（day066/069）；grounded = valid 非空 且 invalid 为空
  ```
- **为什么**：day072 把"增量"拆成**两级**，因为它们比的不是同一样东西：
  ```text
  文件级（day072）  两份语料快照的差集      → "要不要跑这一趟"（语料没变就一行都不写）
  块级（day065）    planner 的四条判据      → "要重算哪些向量"（改一行只重算变了的块）
  ```
  这一层最值得带走的一句话是 **"绑定"**：`RagBaseline.load` 文件不存在会**报错**
  （"没有基线"与"基线全是零"是两回事），而 `SyncLedger.load` 文件不存在返回**空账本**
  （"没有账本"就是首次运行）。体检四项（库记录数 / 清单一致性 / 语料新鲜度 / 质量回归）
  里，"跳过"永远不是 `ok`——**缺输入的四种情况一律给 `warn`**，
  报告里不许出现一个"看起来没问题"的空洞。实测口径：3 份语料、71 字，
  改一份是"文件级 33.3% / 块级写入 1 未变 2 删除 1 编码 1"，改两份是"66.7% / 写入 3 编码 2"。
- **误区**：
  ```text
  ① 把"增量"当成一样东西（文件级与块级缺一不可：只做块级会浪费解析与分块）
  ② 变更比例用"当前来源数"做分母（"删光了"会得到 5/0；应当用并集，得到 1.0）
  ③ 失败也推进水位（失败的那批来源会被永久跳过，而库里少的记录没人提醒）
  ④ 混淆 last_run_at 与 last_success_at（"每小时都跑、每次都失败"会看起来非常新鲜）
  ⑤ 探活时跑评估（提供方一抖动会摘掉全部实例，一次外部故障变成一次全站故障）
  ⑥ 量不到就上报 0（`hallucination_rate = 0` 会被看板读成"幻觉率 0，很好"）
  ⑦ 账本进 git（一次全新部署会以为"我已经同步过了"，于是首次只做增量 = 什么都没做）
  ```
