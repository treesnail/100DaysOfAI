## 第一章：Agent 评估难在哪 —— 与单轮输出评估的三个本质差异

### 1.1 先回顾：评估一次 LLM 输出有多简单

评估单轮问答的范式非常直接：

```text
输入问题 ──▶ LLM ──▶ 输出文本
                        │
                        ▼
              与参考答案比对（accuracy / contains_rate）
```

`evaluation/metrics.py` 里的 `accuracy` 和 `contains_rate` 就是干这个的：两个字符串列表进，一个 0~1 的分数出。评估对象是**一个终态产物**，评估动作是**一次比对**。

### 1.2 差异一：评估对象是多步轨迹，不是一个产物

Agent 完成任务的方式是**一连串决策**：

```text
任务 ──▶ Step1: Thought + Action(web_search) ──▶ Observation
     ──▶ Step2: Thought + Action(calculator)  ──▶ Observation
     ──▶ Step3: Thought + Final Answer
```

如果只看最终答案，一个"答案蒙对但过程全错"的 Agent（比如该调计算器却直接心算、恰好蒙对）会被误判为优秀——而这个 Agent 在真实环境里的表现是不可靠的。反过来，一个"过程完美但答案格式不对"的 Agent 也不该得零分。

**Agent 评估必须把过程纳入度量**：它调了哪些工具？顺序对不对？走了几步？这就是为什么我们的核心数据结构叫 `AgentRunTrace`（运行轨迹）而不是 `AgentOutput`。

### 1.3 差异二：部分正确是常态，二元对错不够用

单轮输出的对错相对二元：答案要么对要么错。Agent 的轨迹存在大量"部分正确"的中间态：

| 轨迹 | 工具调用 | 答案 | 怎么算？ |
|------|----------|------|----------|
| A | 调对了所有工具，顺序正确 | 正确 | 满分，无异议 |
| B | 调对了工具，但多调了一次多余的搜索 | 正确 | 结果对，过程有浪费 |
| C | 漏调了该用的计算器，直接心算 | 恰好正确 | 结果对，过程不可靠 |
| D | 工具全对，最后一步输出格式非法 | 无 | 过程对，结果没产出 |

如果只有"完成率"一个指标，B、C 和 A 会得到完全相同的分数——但它们暴露的问题截然不同：B 是**效率问题**，C 是**可靠性隐患**，D 是**解析层缺陷**。这就是为什么我们至少需要三个指标，分别从**结果、过程、行为**三个维度度量同一条轨迹。

### 1.4 差异三：Agent 与环境有交互，评估必须控制环境

单轮 LLM 评估中，模型输出只取决于输入和模型本身。Agent 的轨迹还取决于**环境反馈**——工具返回什么，Observation 就是什么，下一步决策就随之改变。

这带来一个工程难题：**评估的可重复性**。如果评估时 `web_search` 真的去联网，那么：

- 搜索结果随时间变化，今天的满分轨迹明天可能失败（不可重复）；
- 评估需要网络和 API Key（违背 FIRST 原则中的 Repeatable，回忆 day002）；
- 一次评估几十次网络调用，又慢又贵。

解法我们在 day005 就已经造好了：**MockLLM + 假工具**。评估时把 LLM 换成按脚本回复的 MockLLM、把搜索换成返回固定文本的 FakeSearchTool，整条轨迹就变成**完全确定性**的——同样的数据集，任何机器、任何时间跑出同样的指标。这是 Agent 评估能进入 CI 的前提。

> 思考题：用 MockLLM 评估"Agent"，到底在评估什么？MockLLM 不会犯错，那我们测出的"失败"是谁的失败？提示：数据集里的 mock_responses 脚本模拟的是"某种行为模式的 LLM"，评估度量的是"当 LLM 表现出这种模式时，整个系统（解析器、工具路由、循环控制）的表现"。

### 1.5 评估金字塔中的位置

把视角拉远，AI 系统评估也呈金字塔结构：

```text
        ╱ 端到端评估 ╲      少：整条轨迹 + 环境交互（今天）
       ╱ 组件级评估   ╲     中：Planner 拆解质量、工具单项正确率
      ╱ 单轮输出评估   ╲    多：Prompt 评估、答案准确度（M3-D1~D4）
     ╱──────────────────╲
```

越往上，一次评估越贵、越慢、但越接近"用户真实感受到的质量"。端到端 Agent 评估是金字塔尖——用例贵精不贵多，我们的数据集只有 8 条，但**每一条都针对一种具体的行为模式**（详见第四章）。

## 第二章：轨迹建模 —— AgentRunTrace 的数据契约设计

### 2.1 先建模，再评估

评估系统最常见的失败是"边跑边算分"，逻辑搅在一起。我们的做法是把评估拆成泾渭分明的两层：

```text
执行层：ReactAgent 跑任务 ──▶ 产出 AgentRunTrace（纯数据，只描述"发生了什么"）
指标层：指标函数消费轨迹列表 ──▶ 产出分数（纯函数，只回答"做得怎么样"）
```

**指标函数不认识 ReactAgent，执行层也不认识指标公式**。两层之间唯一的契约就是 `AgentRunTrace` 这个数据类。这样的回报是：指标函数可以用手工构造的轨迹直接做单元测试（手算用例），完全不启动 Agent——`tests/test_agent_eval.py` 里一半的测试就是这么写的。

### 2.2 AgentRunTrace 的字段设计

```python
@dataclass
class AgentRunTrace:
    """一次 Agent 运行的结构化轨迹（评估的最小数据单元）."""

    success: bool      # 任务是否完成（产出答案且内容符合预期）
    steps: int         # 实际推理步数（一次 LLM 调用 = 一步）
    tool_calls: list[str]      # 实际调用的工具名序列
    expected_tools: list[str]  # 数据集中标注的期望工具序列
    latency: float = 0.0       # 端到端耗时（秒）
    task_id: str = ""
    answer: str = ""           # 最终答案原文（供报告与人工复查）
    error: str | None = None   # 运行期异常信息（如解析失败）
```

逐字段看设计动机：

- **`steps` 而不是 `tokens`**：步数是 Agent 的"决策次数"，直接对应 LLM 调用次数，是成本与效率的第一近似。token 级统计留给 M4 的成本追踪（day043）。
- **`tool_calls` 是序列不是集合**：顺序本身是信息。"先搜索后计算"和"先计算后搜索"语义完全不同——第三章的顺序分就是利用序列信息。
- **`expected_tools` 放在轨迹里**：指标函数是纯粹的自包含函数，输入一个轨迹列表就能算出所有分数，不需要回头查数据集。**让数据自描述**——这个原则和 day010 里 `Plan` 携带 `goal` 一模一样。
- **`answer` 保留原文**：评估分数是给人看的，人看到低分第一件事就是问"它当时到底输出了啥"。留下原文，复查零成本。
- **`error` 区分两类失败**：`answer` 为空和 `error` 非空是两种不同的失败——前者是 Agent "正常跑完但没做对"，后者是"系统层面崩了"（解析失败）。这个区分是第五章归因分析的基础。

### 2.3 成功判定也是契约的一部分

`success` 字段看似简单，实则隐藏一个关键决策：**谁来定义"完成"？** 我们的判定逻辑（`AgentEvaluator._judge`）分三层：

```python
if answer.startswith(_NO_ANSWER_PREFIX):   # "达到最大步数限制..."
    return False                            # 循环耗尽 = 没完成
if "answer_contains" in case:
    return str(case["answer_contains"]) in answer   # 数据集声明的内容检查
if case.get("expect_answer_json") is True:
    json.loads(answer)                      # 数据集声明的格式检查
return True
```

注意"内容检查的规则写在数据集里"这个设计：每条任务自带 `answer_contains` 或 `expect_answer_json` 判定标准。**判定标准即数据**，评估器不需要为每种任务写 if-else。这和 M3-D1 Harness 框架"数据集驱动"的思想一脉相承。

> 思考题：`answer_contains` 是子串匹配，很宽松。什么场景下它会把错误答案误判为成功？（提示：考虑"答案不是 42"这句话包含 "42"。）更严格的判定可以怎么设计？

## 第三章：三个指标的设计动机与公式

### 3.1 指标总览：一个维度回答一个问题

| 指标 | 回答的问题 | 维度 | 取值范围 |
|------|-----------|------|----------|
| `completion_rate` | 任务做完了吗？ | 结果 | 0~1 |
| `step_efficiency` | 做得利索吗？ | 过程 | 0~1 |
| `tool_accuracy` | 工具用对了吗？ | 行为 | 0~1（四个子项） |

三个指标**刻意不正交**：一条轨迹会被三把尺子分别量一次。量出来不一致恰恰是价值所在——完成率高但步数效率低，说明 Agent "能做成事但浪费钱"；完成率高但工具正确率低，说明答案是蒙对的，不可靠。

### 3.2 completion_rate：最朴素也最不可替代的指标

$$\text{completion\_rate} = \frac{\text{成功轨迹数}}{\text{总轨迹数}}$$

这是唯一一个"用户视角"的指标：用户不关心你调了什么工具，只关心任务完成没有。它的代码朴素到只有两行：

```python
def completion_rate(traces: list[AgentRunTrace]) -> float:
    if not traces:
        return 0.0
    return sum(1 for t in traces if t.success) / len(traces)
```

两个细节：

- **空列表返回 0.0 而不是抛异常**："没有数据"在评估语义里应该得 0 分，而不是让流水线崩溃。这个约定贯穿整个 metrics 模块（`mean([])` 也返回 0.0）。
- 它是**唯一一个带"一票否决"语义的指标**：无论过程多优雅，`success=False` 就是失败。其他指标都是连续刻度，只有它是硬门槛。

### 3.3 step_efficiency：最小必要步数 / 实际步数

动机来自一个朴素的观察：**ReAct 循环的每一步都是一次 LLM 调用，都花钱、花时间**。两个 Agent 都做对了任务，一个用 2 步一个用 6 步，它们的成本差 3 倍——完成率完全看不出这个差异。

$$\text{efficiency}_i = \min\left(1,\ \frac{\text{最小必要步数}_i}{\text{实际步数}_i}\right), \qquad \text{step\_efficiency} = \text{mean}(\text{efficiency}_i)$$

**最小必要步数怎么定义？** 我们取 `len(expected_tools) + 1`：每个期望的工具调用占一步，最后输出 Final Answer 再占一步。这是一个**下界估计**——理想 Agent 一步都不多走。

为什么要 `min(1, ...)` 截断？考虑一个"偷懒"轨迹：期望调 2 个工具（最小必要 3 步），Agent 直接心算 1 步给出答案。不截断的话效率是 3/1 = 3.0，**奖励了"少做事"**。截断到 1.0 后，偷懒轨迹在效率上不扣分（它确实快），但它的工具召回率会是 0——**让正确的指标管正确的事**：效率只管"有没有浪费步数"，可靠性交给工具指标管。

```python
def step_efficiency(traces: list[AgentRunTrace]) -> float:
    ratios: list[float] = []
    for t in traces:
        min_steps = len(t.expected_tools) + 1
        if t.steps <= 0:
            ratios.append(0.0)
        else:
            ratios.append(min(1.0, min_steps / t.steps))
    return mean(ratios)
```

### 3.4 tool_accuracy：为什么需要 precision、recall 和顺序分三个数

工具使用的错误有三种截然不同的形态，单一数字无法区分：

```text
形态一：多调  期望 [calculator]，实际 [web_search, calculator]   ← 浪费
形态二：漏调  期望 [web_search, calculator]，实际 [web_search]   ← 偷懒/不可靠
形态三：乱序  期望 [web_search, calculator]，实际 [calculator, web_search]  ← 逻辑错误
```

**集合 precision / recall** 解决前两种。把工具序列当集合看：

- precision = |实际 ∩ 期望| / |实际| —— 调用的工具里有多少是该调的。**多调扣分。**
- recall = |实际 ∩ 期望| / |期望| —— 该调的工具里有多少真被调了。**漏调扣分。**
- F1 = 2PR/(P+R)，两者的调和平均。

形态一：P=1/2, R=1 → F1=2/3；形态二：P=1, R=1/2 → F1=2/3。注意两者 F1 相同——这就是为什么报告里要同时展示 P 和 R，不能只看 F1：**F1 相同的轨迹，病灶可能完全不同。**

**但集合信息丢失了顺序**。形态三里集合完全重合，F1=1，可"先计算后搜索"明显是错的。引入**顺序分**：用最长公共子序列（LCS）度量实际序列对期望顺序的保持度：

$$\text{order} = \frac{\text{LCS}(\text{实际序列},\ \text{期望序列})}{|\text{期望序列}|}$$

形态三的 LCS 是 1（`web_search` 或 `calculator` 任选其一保持相对顺序），order = 1/2 = 0.5。LCS 的好处是比"逐位比对"宽容：实际序列里混进多余工具（形态一）时，`[web_search, calculator]` 对 `[calculator]` 的 LCS 仍是 1，顺序分不扣——多调的问题由 precision 管，顺序分只管顺序。**每个子项只惩罚一种错误，这是指标设计的正交性原则。**

另一个细节：顺序分**只在成功轨迹上统计**（`if t.success:`）。失败轨迹的工具序列本身就不完整，拿残缺序列算顺序保持度没有语义。

完整实现见 [evaluation/agent_eval.py](../源码/smart-research-agent/smart_research_agent/evaluation/agent_eval.py)，其中 LCS 用经典动态规划：

```python
def _lcs_length(a: list[str], b: list[str]) -> int:
    dp = [0] * (len(b) + 1)
    for item in a:
        prev = 0
        for j, other in enumerate(b, start=1):
            temp = dp[j]
            dp[j] = prev + 1 if item == other else max(dp[j], dp[j - 1])
            prev = temp
    return dp[-1]
```

### 3.5 指标选型背后的通用方法论

三个指标的选型过程可以提炼成一条可复用的方法论：**先枚举被评估对象可能的失败形态，再为每类形态选一个对它敏感的指标**。

```text
失败形态枚举                 敏感指标
─────────────────────────────────────────
任务没做完            ──▶   completion_rate
做完了但绕了远路      ──▶   step_efficiency
调了多余的工具        ──▶   precision
该调的工具没调        ──▶   recall
工具顺序错了          ──▶   order（LCS）
```

反过来，如果你设计的指标找不到对应的失败形态（"这个分数低了我不知道该怎么改"），那它就是虚荣指标，应该删掉。

> 思考题：我们的指标漏掉了哪种失败形态？提示：Agent 调对了工具，但传错了参数（`Action Input` 错误）。现有哪个字段能支撑这个维度的评估？

## 第四章：端到端评估流水线 —— 数据集、AgentEvaluator 与确定性执行

### 4.1 数据集设计：每条用例针对一种行为模式

评估数据集在 [data/eval/agent_tasks.jsonl](../源码/smart-research-agent/data/eval/agent_tasks.jsonl)，每行一个 JSON 对象：

```json
{"id": "task-03",
 "task": "先搜索 RAG 技术简介，再计算 1024 * 4 的 token 成本估算基数",
 "expected_tools": ["web_search", "calculator"],
 "mock_responses": ["Thought: 先搜索 ...\nAction: web_search\nAction Input: ...",
                    "Thought: 资料够了 ...\nAction: calculator\nAction Input: 1024 * 4",
                    "Thought: 两步都完成了\nFinal Answer: ... 4096"],
 "answer_contains": "4096"}
```

四个字段各司其职：`task` 是 Agent 的输入；`expected_tools` 是行为标注；`mock_responses` 是**LLM 的行为脚本**——它模拟的不是"正确答案"，而是"一种行为模式"；`answer_contains` 是成功判定标准。

8 条用例覆盖的谱系：

| 用例 | 模拟的行为模式 | 预期结果 | 预期归因 |
|------|---------------|----------|----------|
| task-01/02 | 单工具任务，正常完成 | 成功 | completed |
| task-03 | 双工具任务，顺序正确 | 成功 | completed |
| task-04 | 算数题却调搜索，答案错 | 失败 | wrong_tool |
| task-05 | 该用工具却直接心算，答案错 | 失败 | planning_error |
| task-06 | 输出不含 Thought 字段 | 失败 | parse_failure |
| task-07 | 多调一次搜索后自我纠正，最终成功 | 成功（precision 扣分） | completed |
| task-08 | 重复调用同一工具（冗余步骤） | 成功（效率扣分） | completed |

注意 task-07 和 task-08 是刻意的：**成功的轨迹也要能暴露过程问题**。如果数据集里全是"非黑即白"的用例，precision 和效率指标永远测不出差异。

### 4.2 AgentEvaluator：用工厂注入被测对象

```python
class AgentEvaluator:
    """Agent 端到端评估器：agent_factory 注入被测 Agent 的装配方式."""

    def __init__(self, agent_factory: AgentFactory):
        self.agent_factory = agent_factory
```

为什么接收**工厂函数**而不是 Agent 实例？三个原因：

1. **每条任务需要独立 Agent**：ReactAgent 的 `history` 会累积，复用实例会串味（这和 day010 习题第 10 题 PlanExecutor 用工厂的动机相同）。
2. **每条任务的 mock_responses 不同**：工厂的签名 `Callable[[list[str]], ReactAgent]` 正是"给定这条任务的脚本，装配一个 Agent"。
3. **评估器不知道 Agent 怎么装配**：注册哪些工具、max_steps 设多少，是调用方的事。评估器只面向 `ReactAgent.run()` 这个接口工作——生产环境把 `make_agent` 里的 MockLLM 换成真实 LLM，评估代码一行不动。

单条任务的执行核心是轨迹采集（`_run_case`）：

```python
start = time.perf_counter()
answer = agent.run(str(case["task"]))
latency = time.perf_counter() - start

tool_calls = [s.action for s in agent.history if s.action is not None]
```

轨迹数据从哪来？**不是让 Agent 主动汇报，而是评估器事后从 `agent.history` 里提取**。这是评估系统设计的重要原则：**被测对象不该为评估做任何改造**。ReactAgent 一行代码没改，就被完整地观测了——因为它本来就把每步决策记在 `history` 里（day006 的设计红利）。日志和观测点要在写业务代码时就埋好，评估时才能"免费"拿到数据。

### 4.3 复用 Harness：单条崩溃不拖垮整场评估

`AgentEvaluator.evaluate` 没有自己写循环，而是复用了 `evaluation/harness.py` 基座（day025 完整版的 `Harness` 兼容接口）：

```python
harness_result = harness.run(cases, self._run_case)
```

Harness 的关键价值是**错误隔离**：`runner` 抛异常时记录错误、继续跑后面的用例。为什么这很重要？考虑 task-06——它模拟"LLM 输出不符合 ReAct 格式"，`parse_react_output` 会直接抛 `ReActParseError`。如果没有 Harness 兜底，整场评估在第六条用例处崩溃，前面五条的结果全部丢失。**评估系统的鲁棒性必须高于被测系统**——被测对象的本职就是会犯错。

Harness 捕获的异常在评估器里统一归为 `parse_failure`：从评估视角看，"LLM 输出 parser 读不懂"就是解析层的失败，异常类型细节写进 `trace.error` 供报告展示。

### 4.4 确定性执行：评估结果可进 CI 的前提

整条链路的确定性来自三层替换：

```text
真实 LLM     ──替换为──▶  MockLLM（按脚本回复，零随机性）
真实搜索工具  ──替换为──▶  FakeSearchTool（返回固定文本，不联网）
真实时钟      ──保留────▶  time.perf_counter（latency 是轨迹数据，不参与断言）
```

前两层替换后，**给定数据集，三个指标的数值是完全确定的**。`tests/test_agent_eval.py` 的端到端测试直接断言到了小数：`completion_rate == 0.625`、`step_efficiency ≈ 19/24`、`f1 ≈ 17/24`。这意味着评估本身也成了回归测试——任何改动（换提示词、改解析器、改工具路由）导致指标变化，CI 立刻报警。这正是 M3 阶段"Harness 评估框架"的终极目标：**评估即测试**。

## 第五章：归因分析与报告 —— 从"分数低"到"哪里病了"

### 5.1 归因：把失败映射回组件

指标回答"做得怎么样"，但工程上更重要的问题是"**该改谁**"。我们的 Agent 有三个主要组件：Planner/循环控制（决策）、工具路由（选工具）、输出解析器（读 LLM 输出）。归因分析就是把每条失败轨迹映射到其中一个组件：

```python
@staticmethod
def _classify(trace: AgentRunTrace) -> str:
    if trace.error is not None:
        return "parse_failure"      # parser 抛异常 -> 解析层病了
    if trace.success:
        return "completed"
    if trace.answer.startswith(_NO_ANSWER_PREFIX) or not trace.answer:
        return "planning_error"     # 循环耗尽/无产出 -> 决策层病了
    if set(trace.tool_calls) - set(trace.expected_tools):
        return "wrong_tool"         # 有产出但调了多余工具 -> 工具选择病了
    return "planning_error"
```

判定顺序有讲究：**先查 error，再查 success，最后区分规划与工具**。因为异常是最强的信号（系统层崩溃优先于行为层分析），而 `wrong_tool` 要求"产出了答案"这个前提——没产出答案的轨迹谈不上"工具选错"，它的问题是更上层的决策失败。

这套映射是 M1 阶段组件化架构的直接回报：正因为 day010 坚持了规划/执行分离、day006 坚持了解析器独立成模块，今天每个失败才有明确的"责任组件"可指。**架构的边界就是归因的边界。**

### 5.2 报告的三段式结构

[evaluation/report.py](../源码/smart-research-agent/smart_research_agent/evaluation/report.py) 把评估结果渲染成 Markdown，结构按"读者提问的顺序"组织：

```text
1. 指标总览     —— 读者先问：整体怎么样？
2. 薄弱维度归类  —— 接着问：问题集中在哪类组件上？
3. 逐条明细     —— 最后问：具体哪条任务、当时调了什么？
```

实际生成的报告片段（`python scripts/run_agent_eval.py` 的产出）：

```markdown
## 指标总览
| 任务完成率 completion_rate | 0.62 |
| 步数效率 step_efficiency | 0.79 |
| 工具 F1 | 0.71 |

## 薄弱维度归类
### 规划错误（1 条）
- `task-05` 计算 7 * 8
### 工具选错（1 条）
- `task-04` 计算 (10 - 4) / 2
  - 实际工具：web_search
  - 期望工具：calculator
### 解析失败（1 条）
- `task-06` 查询 LangChain 的用途
  - 异常：缺少 Thought 字段
```

为什么选 Markdown 而不是图表库？三个理由：**零依赖**（不引入 matplotlib，CI 里跑完直接可读）；**可版本化**（纯文本 diff，指标变化在 git 历史里一目了然）；**可嵌入**（GitHub PR、Wiki、邮件都原生渲染）。"可视化"的第一要义是**让正确的人快速看到正确的信息**，不是图形炫酷。

### 5.3 从报告到行动：一个完整的改进循环

读这份报告能直接得出行动项：

- **task-04（工具选错）**：算数题调了 web_search → 改进方向是系统提示词里的工具选择指引（或 function calling 迁移，M4-D4）。
- **task-05（规划错误）**：直接心算且算错 → 改进方向是提示词中强调"数值计算必须用 calculator"。
- **task-06（解析失败）**：LLM 没输出 Thought 字段 → 改进方向是解析器容错或提示词格式约束（day010 的四道防线思路）。

改进后重跑评估，指标上升、对应归因组清空，形成闭环：**评估 → 归因 → 改进 → 再评估**。这就是"将评估结果可视化并定位薄弱环节"的完整含义——报告不是终点，是下一轮迭代的起点。

### 6.3 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 轨迹建模先于指标计算 | 执行层与指标层解耦，指标可手算单测 | `AgentRunTrace` dataclass |
| 成功判定规则写进数据集 | 判定标准即数据，评估器不写死 if-else | `answer_contains` / `expect_answer_json` |
| 三指标分别管结果/过程/行为 | 先枚举失败形态，再为每类形态配敏感指标 | 三个指标函数 |
| 步数效率截断到 1.0 | 不奖励"少做事"，可靠性交给工具指标管 | `min(1.0, min_steps / t.steps)` |
| precision/recall/order 三项并列 | F1 相同的轨迹病灶可能不同；顺序信息集合表达不了 | `tool_accuracy` 返回 dict |
| 顺序分只统计成功轨迹 | 失败轨迹序列不完整，顺序分无语义 | `if t.success` |
| agent_factory 注入 | 每任务独立 Agent；评估器不知道装配细节 | `AgentEvaluator.__init__` |
| MockLLM + 假工具 | 完全确定性，评估可进 CI、断言可到小数 | `make_agent` |
| Harness 错误隔离 | 评估系统鲁棒性必须高于被测系统 | `Harness.run` |
| 失败归因到组件 | 架构的边界就是归因的边界 | `_classify` |

今天的伏笔在 M3-D7（day032）回收：评估流水线接入 CI/CD 后，这份报告将自动生成、指标回归将自动告警——评估从"手动工具"变成"质量门禁"。
