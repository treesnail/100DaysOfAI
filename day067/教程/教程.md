## 今日目标

day066 交出来的是一条**单路**流水线：九步、三道减法、四个诊断数字。它把"为什么只有这几条"答得很清楚，却答不了另一类问题——**"这条为什么一个词都对不上"**。今天加第二路，回答三个问题：

1. **两路合起来为什么不是"更强"，而是"两种失败不再是同一种失败"**——向量路对编号、函数名、报错码「差不多就行」，关键词路对同义改写完全无力。这两件事不是同一个错误的两个程度，而是两个互补的失效面；
2. **两个来自不同系统的分数能不能直接相加**——余弦相似度 ∈ `[-1, 1]`、BM25 ∈ `[0, ∞)`。`0.82` 与 `7.31` 都是浮点数，`sorted` 照单全收，于是"加权求和"这个最自然的写法会把**量纲差当成相关性差**；
3. **融合之后，"这一条为什么排第一"还能不能读出来**——`score` 只回答排序，而 `channels` / `channel_ranks` / `channel_scores` / `contributions` 才回答"凭什么"。一个只会 `sorted(hits, key=score)` 的融合器，在"`alpha` 从 0.3 换到 0.7 为什么结果一样"前面是哑的。

## 第一章：两路的分工——两个死穴不是同一个

### 1.1 可检验的定位

```text
向量路回答      "意思像不像"   → 命中"语义缓存用分位数标定阈值"（查询"怎么让缓存不要每次都重算"）
关键词路回答    "这个词在不在"  → 命中"ERR-2043 表示向量维度不一致"（查询 "ERR-2043"）
```

两路各有一个死穴，而两个死穴**不是同一个**：向量路的死穴是**编码器没见过的东西**（编号 / 函数名 / 报错码在训练语料里太稀，只好映射到一个模糊的方向）；关键词路的死穴是**同义改写**（"重算"与"重新计算"在它眼里是两个词）。因此把两路合起来**不是为了"更强"**，而是为了**两种失败不再是同一种失败**——单路检索错的时候只有一种形状（"返回了一批不太相关的记录"，且报告里看不出错在哪），两路融合把错误劈成两种：一路空着、另一路照常给答案，而"哪一路空着、为什么"是可读的。

### 1.2 模块地图与三个新模块

```text
lexical.py  关键词一路：零依赖 BM25 + CJK 2-gram 分词 + "为什么一条都没召回"的证据
            tokenize / LexicalIndex.build / from_backend / search / LexicalSearchResult
fusion.py   融合与去重：RRF（只看名次）与归一化加权（先归一化再加权）；去重 = 合并证据
            fuse / reciprocal_rank_fusion / weighted_score_fusion / FusedHit / contribution_counts
hybrid.py   混合检索器：两路共用一份过滤子句与深度，融合后仍能逐条解释
            HybridRetriever.retrieve / _resolve_fusion / _to_hit / build_hybrid_retriever
```

`retrieval/__init__.py` 的导出范围因此从七个模块变成十个：`errors` / `types` / `filters` / `retriever` / `routing` / `context` / `pipeline` / **`lexical`** / **`fusion`** / **`hybrid`**（后三个是 day067 新增的）。

## 第二章：关键词一路——CJK 免分词的 2-gram 方案

### 2.1 为什么不用 `jieba` / `rank_bm25`（本模块最该记住的取舍）

```text
1. 不新增依赖   本课的全部产物必须能在"只有 Python + 标准库"的机器上复现，而 BM25 与分词
                都是**几十行的算术**，不值得为之引入依赖（jieba 还带约 5 MB 词典文件，
                它会把"离线可复现"变成"词典版本也会影响结果"）
2. 评估要可复现  分词器是有版本的（jieba 换版本会切出不同的词），于是同一天、同一份语料、
                同一批查询会给出不同的 BM25 分数，而 day071 的 RAG 评估要求"分数变了必须
                能归因到某个显式参数"。相邻 2-gram 的分词法**没有版本**：它的定义就是
                "字符串的相邻两字"
```

代价写在明面上：2-gram 会把"语义"与"义语"当作两个不同的词元（词表比真实词表大、精确率略低），也**不认识"未登录词"**。这两条都进了 `RETRIEVAL_LIMITATIONS`。

### 2.2 分词规则与实测

```text
先按 [a-z0-9_]+ | [\u4e00-\u9fff]+ 切段（全角标点、空格、连字符都是分隔符）
拉丁/数字段    原样保留（大小写先折叠）："ERR-2043" → err、2043
汉字段长度 1   保留该单字："熵" → 熵
汉字段长度 ≥2  单字 + **相邻 2-gram**："语义缓存" → 语/义/缓/存/语义/义缓/缓存
```

本机实测（与演示输出逐字一致，本教程另用独立脚本复算）：

```text
tokenize('语义缓存') = ['语', '义', '缓', '存', '语义', '义缓', '缓存']
tokenize('ERR-2043') = ['err', '2043']        ← 连字符是分隔符（编号的"前缀"与"序号"各成一个词元）
tokenize('午饭吃点什么好') 词元数 = 13        ← 7 个单字 + 6 个 2-gram
```

实现只有两个模块级正则加十几行循环（`lexical.py::tokenize`）：

```python
TOKEN_PATTERN = re.compile(r"[a-z0-9_]+|[\u4e00-\u9fff]+")
CJK_ONLY = re.compile(r"^[\u4e00-\u9fff]+$")

    for chunk in TOKEN_PATTERN.findall(text.lower()):
        if not CJK_ONLY.match(chunk):
            tokens.append(chunk); continue          # 拉丁/数字段原样保留
        if len(chunk) == 1:
            tokens.append(chunk); continue          # 汉字段长度 1：保留该单字
        tokens.extend(chunk)                        # 单字在前
        tokens.extend(chunk[i : i + 2] for i in range(len(chunk) - 1))   # 2-gram 在后
```

**单字与 2-gram 都要**，各补一件事：单字让"重算"与"重新计算"共享 重/算（不引入同义词表就蹭到一点召回），2-gram 让"缓存"与"存缓"区分开。只留 2-gram 时单字查询（"熵"、"税"）会一个词元都对不上，而单字查询在中文里真实存在。另有一条容易忽略的：`tokenize("  语义  缓存  ")` **没有**跨空白的 `义缓`——2-gram 只在同一个汉字段内生成（`test_hybrid_lexical_tokenizer.py` 用测试侧**独立重写**的切分逻辑做逐条对照）。

### 2.3 索引结构：四份事实与替换语义

`add` 对**已存在的 id 是替换**（不是拒绝）：这个索引是"这批文档现在长什么样"的投影，而投影的正确语义是"以最后一次写入为准"。四份事实各自独立存——文档本身、每篇的词频、每篇的长度、每个词元的 `df`；不写"存一份分词结果每次重算 `df`"的省事版本，那会让每次 `search` 变成 `O(N)`，而 `df` 正是"加一篇"时唯一需要增量维护的东西（`_forget` 把一篇文档从四份事实里一起摘掉，替换语义靠它）。

关键词索引**刻意不持久化、不做增量**，口径是"每次进程启动 / 每次注入时从向量库重建"：

```text
1. 构建成本是"分词 + 计数"，在一份百万字的语料上是秒级
2. 落盘会引入**第二种版本口径**（向量索引有清单与版本号，见 indexing）——
   两份版本号一定会分家，而分家之后"这次检索用的是哪一版"会取决于读的是哪一份文件
```

### 2.4 `from_backend`：把"静默少召回"升级成一个错误

```python
ids = [str(record_id) for record_id in backend.ids()]
records = list(backend.get_many(ids))
if len(records) != len(ids):
    raise LexicalError(
        f"库里报 {len(ids)} 条记录，但只取回 {len(records)} 条：记录表与向量索引不同步"
        "（get_many 会跳过不存在的 id）。关键词索引**不能**照常建起来——那会让关键词路"
        "静默少召回那几条，而少了多少不会出现在任何报告里。..."
    )
```

这一处是本日**错误族设计的活样本**：`get_many` 的实现是"跳过不存在的"，而这里刻意把它升级成错误——少的那几条不会出现在任何数字里，只会表现为"关键词路好像漏了什么"。`errors.py` 本日新增两族，判据仍是"**谁该去修**"：

```text
LexicalError  关键词索引与语料对不上（库里报 N 条只取回 M 条；索引里的文档全无词元）
              → 索引运维：重建关键词索引 / 修入库口径（RetrievalError 的直系子类）
FusionError   策略名不存在 / alpha 越界 / k_rrf < 1 / 某一路没有权重
              → 调用方：改这一次的调用参数（**继承 QueryError**）
```

`FusionError` 继承 `QueryError` 而不是并列：它描述的就是"这次请求的参数不对"，继承之后 `except QueryError` 的老代码**自动**把它收进去（端点层那条"参数问题一律 400"的通道不需要再加一个分支），而需要区分时又能单独 `except FusionError`——两边的代价都是零。

## 第三章：BM25——IDF 恒正、`k1` 与 `b` 各自管一件事

### 3.1 公式：只有两个量属于"这次查询"

```text
idf(t) = log(1 + (N - df + 0.5) / (df + 0.5))              ← 恒正（见下）
score  = Σ_t idf(t) · tf · (k1 + 1) / (tf + k1 · (1 - b + b · dl / avgdl))
```

`tf`（词频）与 `dl`（该文档词元数）是"这次查询"的量；`df`（含该词元的文档数）与 `avgdl`（平均文档长度）是**全库统计**，而它们**不受 `where` 影响**——这是刻意的口径（`LexicalIndex.search` 第 6 步注释）：

```text
第 6 步：打分。idf 与 avgdl 都是**全库统计**（不受 where 影响）：它们是语料的性质，
不是"这次过滤出来的那几条"的性质。用过滤后的子集重算 idf 会让同一个词在两次不同过滤下
有不同的权重，于是"换个过滤条件"会静默改变每条的分数——而分数是要跨查询比较的。
```

### 3.2 `log(1 + …)` 里的那个 1 是刻意的

经典 BM25 写 `log((N - df + 0.5) / (df + 0.5))`，它在 `df > N/2` 时变成**负数**——一个"到处都出现的词"会给文档**减分**。两种写法的排序多数时候一样，但负 IDF 会让"分数为负"与"0 分"混在一起，而本模块用 0 分表示"完全没有共同词元"（见 3.4）。恒正的 IDF 让"0 分"这件事**只有一个含义**。本机实测（手算与实现逐位一致）：`_idf(10, 1) = 1.992430`（即 `log(1 + 9.5/1.5)`）。`_idf` 是公开可核对的：`test_hybrid_bm25.py` 直接对它断言单调性，因为 BM25 的排序不变量（词越稀有权重越大、`df` 增大时权重单调下降）全都落在这一个函数上。

### 3.3 `k1` 与 `b` 的方向：在受控语料上分开扫描

缺省 `k1 = 1.5`、`b = 0.75`，出自 **Robertson & Zaragoza（2009）** 的经典取值，与 Lucene / Elasticsearch 的缺省同源。**它们不是本课标定出来的**——引用一个公开取值，别人才分得清"结果不同"是语料造成的还是参数造成的。受控语料 `[('heavy','缓存缓存缓存缓存'), ('middle','缓存缓存检索'), ('light','缓存')]` 的实测（演示第 6 节）：

```text
k1 扫描（b=0.75）      k1 |      heavy |      light |   比值       b 扫描（k1=1.5）      b |      heavy |      light |   比值
                     0.0 |   0.400594 |   0.400594 | 1.0000                          0.0 |   0.728353 |   0.400594 | 1.8182
                     0.5 |   0.510648 |   0.484051 | 1.0549                         0.25 |   0.701948 |   0.446817 | 1.5710
                     1.5 |   0.654492 |   0.580862 | 1.1268                         0.75 |   0.654492 |   0.580862 | 1.1268
                     3.0 |   0.777723 |   0.654492 | 1.1883                          1.0 |   0.633092 |   0.683367 | 0.9264
                    10.0 |   0.971784 |   0.756151 | 1.2852
```

两条读法不依赖具体数字：`k1 = 0` 时 heavy 与 light **同分**（词频完全不参与），`k1` 越大"同一个词出现更多次"的收益越大（单调）；`b` 越大长文档里的同一个词越不值钱（比值单调下降），这一条是 BM25 与"纯词频排序"的分水岭——没有它，长文档永远占优。

`BM25Params` 是 **frozen dataclass** 而不是两个散参数，理由与 `vectorstore.metrics.MetricSpec` 相同：它们是**一对**（"`k1` 调大、`b` 调小"是同一个实验的两个旋钮），必须**一起**进报告（`summary_line()` 给出 `BM25(k1=1.5, b=0.75)`）。构造期校验两类调用方错误，消息里写清后果而不是一个"参数非法"：

```python
# 两类调用方错误各自给出后果，而不是一个"参数非法"：
raise QueryError("... k1=0 有明确含义——'完全忽略词频，只看出现过没有'")
raise QueryError("... b 超出 [0, 1] 会让分母变成负数，于是'长文档'反而得到更高的分数"
                 "——一个不会报错、只会反过来的排序")
```

### 3.4 只返回"至少命中一个词元"的文档（第二个关键取舍）

BM25 会给**完全不相关的文档**一个 0 分，而它们在名次上位于所有真实命中之后。如果把它们也算作"关键词路的命中"，名次靠后的位置上就会躺着一批"和查询毫无关系"的记录——而 **RRF 恰恰只看名次不看分数**，它会老老实实给"关键词路第 3 名"一个 `1/(k+3)` 的贡献。**那条证据是假的。** 因此 `search` 只返回 `score > 0` 的文档，并把被排除的条数写进 `notes`。本机实测（10 条语料、查询 `ERR-2043`）：

```text
命中 1 条（h-t-01）| candidates 10 | query_terms 2 | missing_terms 0
note：有 9 篇候选文档与查询没有任何共同词元（BM25 给 0 分），已排除在名次之外：
      0 分不是"相关性很低"，而是"这次查询完全没提到它"。把 0 分文档按零分排进名次，
      会让只看名次的融合策略（RRF）把"毫无关系"当成"第 N 名证据"。
```

### 3.5 `matched_terms` / `missing_terms`：这一路"为什么空着"的唯一证据

关键词路的失败与向量路的失败**形状不同**：向量路总能返回"最像的 K 条"（哪怕都不像），关键词路会**干脆地一条都不返回**。那时唯一能回答"为什么"的事实就是"查询的那些词元里，有几个在词表里出现过"：

```text
missing_terms 全等于 query_terms  → 一个词都不认识（纯语义改写 / 用了别的语言）
missing_terms 为空                → 词都认识，但没有任何一篇同时包含它们
matched_terms 非空且 hits 非空     → 正常命中
```

前两种都表现为"空结果"，但处置动作不同（前者换查询说法或补语料，后者检查过滤条件与语料分布），因此**分开列出**而不是合成一个布尔值——与 `types.EMPTY_REASONS` 那条纪律同源。实测（查询"午饭吃点什么好"）：命中 0 条、`query_terms 13`、`missing_terms 13`，note 里带着"词表里有 274 个词元"这个**分母**。

### 3.6 空索引与"中毒索引"（两种极不一样的处境）

```text
0 篇文档         → 空结果 + notes（"这是合法状态"，与向量路 count=0 的 no_data 同一口径），**不抛异常**
有文档但全无词元  → LexicalError（BM25 的分母里有 avgdl，索引没法打分）
                 → 这是索引侧的事：去修入库口径或重建，**不是**"没有命中"
```

后者由 `search` 的分支显式挡住（`if self._total_length == 0: raise LexicalError(...)`）。两种处境的动作完全不同：前者去建索引，后者去修入库口径——合成一句"关键词路没有结果"会让这两件事无法区分。顺带一个口径细节：`avgdl` 在**空索引**上返回 `0.0` 而不是报错；而 `dl = 0` 的文档（正文为空串）**也**算进平均，因为"没有正文"是它自己的事实，把它排除会让 `avgdl` 变成"非空文档的平均"，而那个数字在报告里解释不通。

`search` 的七步与 `Retriever.retrieve` 刻意对齐（两条路的"问法"必须逐条对照）：

```text
1 校验（查询非空 / top_k 范围 / where 语法，复用 vectorstore.compile_filter）
2 分词（保留重复）与去重后的"打分用词元"      3 对账词表（matched / missing）
4 空索引早退（合法状态，不抛异常）             5 过滤（**与向量路同一份** compile_filter）
6 打分排序（BM25；只留 score > 0；键 (-score, record_id)）   7 截断与注记
```

第 6 步的第三键与向量路是同一条纪律：分数相同必须有**不依赖插入顺序**的第二键，否则同一份数据两次运行会给出不同的名次——而同分在关键词路上很常见（两篇同样长度、同样词频的文档分数逐位相同）。

## 第四章：融合——跨通道的分数量纲不可比

### 4.1 第一件事：两个分数不能直接相加

```text
向量路   余弦相似度 ∈ [-1, 1]     "0.82" 是一个**有绝对上界**的数
关键词路 BM25 ∈ [0, ∞)            "7.31" 是一个**没有上界**的数
```

两个数字放在一起比较是**类型错误**，而它不会报错：`0.82` 与 `7.31` 都是浮点数，`sorted` 照单全收。于是"加权求和"这个看起来最自然的融合方式会把**量纲差当成相关性差**——BM25 只要分数普遍偏大（语料词频一高就会），它就会单方面决定名单顺序，而 `alpha` 那个权重根本没起作用。实测（演示第 5 节，同一批输入）：

```text
向量路分数：[1.0, 0.0, 0.0]（余弦，∈ [-1, 1]）      关键词路分数：[4.0006]（BM25，∈ [0, ∞)）
直接相加时 BM25 会单方面决定名次。归一化（min-max 到 [0, 1]）把「谁的分数大」
换成「谁在这一路里更靠前」。
```

因此给两种策略，差别正是"怎么处理量纲"：`rrf` **完全不看分数**，只看名次（`1/(k+rank+1)`，两路的量纲差异在定义上就不存在）；`weighted` **先对每一路做 min-max 归一化到 `[0, 1]`** 再加权求和（归一化把"量纲"换成"这一路内部相对位置"，于是权重才有意义）。两个常量的出处写在代码里：`DEFAULT_RRF_K = 60`（Cormack、Clarke & Buettcher 2009）、`DEFAULT_ALPHA = 0.5`（"两边都不占先"的起点）。`FUSION_RRF` / `FUSION_WEIGHTED` 是**协议字符串**——它们会出现在报告与 `RetrievalResult.fusion` 里，改它等于改了报告的口径。

### 4.2 `rrf`：公式、`k=60` 的来历、以及它牺牲了什么

```python
contributions.setdefault(record_id, {})[channel] = 1.0 / (k + rank + 1)   # rank 从 0 起
```

三个好性质：**免标定**（不需要知道分数分布，换编码器、换语料都不用重调）、**免归一化**（不存在除零与上下界问题）、**抗异常值**（某一路给出一条分数虚高 100 倍的记录，它在 RRF 里只是"第 1 名"）。`k` 的作用是**压平头部差距**：

```text
k=60   第 1 名 1/61 ≈ 0.016393443、第 2 名 1/62 ≈ 0.016129032（差约 1.6%）
k=1    第 1 名 1/2、第 2 名 1/3（差 33%）—— 越小越只信排名第一的那条
```

代价也要写清楚，否则它会变成"永远该选 rrf"的教条：**丢掉"差多少"**（第 1 名与第 2 名差 0.001 还是 0.5，RRF 一视同仁）；**丢掉"只有一路有"这个信号**（某条被两路同时命中，与分别被两路各自命中一次的**两条不同记录**，在 RRF 里得分相近）。第二条正是 `weighted` 存在的理由之一。

### 4.3 RRF 手算核对（本课最硬的一条证据）

演示脚本第 4 节把公式手算一遍，再与引擎逐位比（查询 `ERR-2043`、`fetch_k=3`、`k=60`）：

```text
向量路三名：[('h-c-01', 0, 1.0), ('h-c-02', 1, 0.0), ('h-c-03', 2, 0.0)]
关键词路命中：[('h-t-01', 0, 4.0006)]

手算（纸笔公式，不从引擎拿数）        引擎给的（同一批输入）
  h-c-01  1/(60+rank+1) = 0.016393443    #0 h-c-01  score=0.016393443 | 通道 vector | 手算一致：True
  h-t-01  1/(60+rank+1) = 0.016393443    #1 h-t-01  score=0.016393443 | 通道 bm25   | 手算一致：True
  h-c-02  1/(60+rank+1) = 0.016129032    #2 h-c-02  score=0.016129032 | 通道 vector | 手算一致：True
  h-c-03  1/(60+rank+1) = 0.015873016    #3 h-c-03  score=0.015873016 | 通道 vector | 手算一致：True

逐位一致：True（手算与引擎用同一个定义，差一位就说明实现错了）
```

`h-c-01` 与 `h-t-01` **精确并列**（都是 `1/61`，各自只被一路的名次 0 命中），次序由**第三排序键**决定：按 `record_id` 升序得到 `h-c-01、h-t-01`。这不是"向量路赢了"，而是"分数并列时必须有确定的第三键"——没有它，同一份数据两次运行会给出不同的 top-1。三个排序键缺一不可（`fusion.py::_assemble`）：`-score`（融合分数降序）、`best_rank`（并列时在某一路上排得更靠前的优先）、`record_id`（还并列时按 id 升序，与 retriever / lexical 的第三键一致）。

### 4.4 `weighted`：先归一化，再加权

两个细节**都不是可选项**：

```text
1. 归一化必须在**每一路内部**做（而不是对合并后的分数做）
   对合并后的分数做归一化时，"这一路的最大值"里混进了另一路的量纲，
   于是 alpha 调整的是"两路混在一起之后的重心"，仍然不是权重
2. min == max 时定义为 1.0（**不是除零，也不是 0**）
   这一路只有一条命中时必然 min == max；归 0 会让"唯一的那条证据"在加权和里消失
   （0 × weight = 0），而它明明是该路第一名。定义成 1.0 的意思是"这一路内部它最相关"
   ——归一化保序，把单点映射到 1 是保序的
```

判据是 `high - low <= 0.0`——**精确的零跨度**，而不是"小于某个 epsilon"：一个凭空取出的 epsilon 会变成**第三个需要标定的参数**，而它的表现是"某些几乎相同的文档突然被归一化成 0"（比放大噪声更难解释）。代价写在明面上：跨度**非零但极小**（浮点误差级别的 `1e-15`）时归一化会把它拉满到 `[0, 1]`——这是 min-max 的固有性质（归一化保序，也保"极差为 1"），要避免它请在**打分那一侧**处理，而不是在这里塞一个阈值。另一个固有性质（**相对量**）：min-max 的上下界来自**这次的候选集合**，因此"同一路换个查询，同一份文档的归一化分不同"——这只要求**同一次融合内部**可比，而这正是加权求和需要的全部。

### 4.5 `alpha` 扫描表：权重真的在起作用

```text
   alpha | 第 1 名 |  h-c-01 |  h-t-01 | 解释          alpha | 第 1 名 |  h-c-01 |  h-t-01 | 解释
     0.0 | h-t-01 |  0.0000 |  1.0000 | 看关键词路       0.5 | h-c-01 |  0.5000 |  0.5000 | 并列，按 id
     0.1 | h-t-01 |  0.1000 |  0.9000 | 看关键词路      0.75 | h-c-01 |  0.7500 |  0.2500 | 看向量路
    0.25 | h-t-01 |  0.2500 |  0.7500 | 看关键词路       0.9 | h-c-01 |  0.9000 |  0.1000 | 看向量路
                                                       1.0 | h-c-01 |  1.0000 |  0.0000 | 看向量路
```

两条"各自的第一名"的分数**恰好是 `alpha` 与 `1 - alpha`**（两路的 top-1 都归一化到 `1.0`），因此 `alpha` 越过 `0.5` 时第一名翻转——权重**确实**在起作用，而它在 `rrf` 下根本不存在。这一节同时是"`min == max` 必须归一到 `1.0`"的现场证据：`alpha=0.0` 时关键词路只有一条命中，它的归一化值是 `1.0000`（而不是 `0.0000`），于是 `1 - alpha = 1.0` 的权重原封不动地传了下去。

### 4.6 `fuse` 的六条封闭纪律

```text
strategy 必须落在 FUSION_STRATEGIES   否则 FusionError（列出可用策略）
alpha 必须落在 [0, 1] 且有限          **任何策略下都校验**（错配置不该被"这次用另一种策略"放过）
k_rrf 必须是 >= 1 的整数               k=0 会让贡献退化成 1/(rank+1)，头部权重过大
strategy="rrf" 却给了 weights         → FusionError，而不是"忽略它"
通道名必须落在 types.CHANNELS         "bm25x" 这种拼错会凭空多出一路只有一半证据的通道
weighted 缺某一路的权重                → FusionError，而**不是**默认为 0
```

最后一条最重要：默认 0 会让那一路的证据**静默消失**（结果看起来正常，只是某一类查询突然变差了——一个查不到病因的现象）。`alpha` 越界的消息里带着"关键词通道的权重是 `1 - alpha`，因此给它 1.5 等于给关键词路 -0.5"与两条出路（`alpha=1.0` 只看向量路、`alpha=0.0` 只看关键词路）。而 `strategy="rrf"` 给 `weights` 时**直接报错**而不是"忽略它"：RRF 的定义里没有权重，而"我设了 `weights` 但结果没变"是一个会让人怀疑代码而不是怀疑参数的现象。

## 第五章：去重——同一条被两路召回是**最强的证据**

### 5.1 这里的"去重"含义恰好相反

"去重"容易让人以为目标是"把重复的去掉，让名单短一点"。在这里含义相反：**同一条记录被两路独立召回，是融合能给出的最有价值的一条结论**（两条互相独立的检索路径都指向它）。因此合并时不是"丢掉一条"，而是：合并成一条 `FusedHit`，**保留全部通道的证据**；分数是两路贡献之和；名次取两路里最好的那个（`best_rank`）；`channels` 是按名次好坏排序的通道名（并列时向量优先）。`RetrievalResult.candidates`（混合模式下的口径）就是这条语义的算术表达：它是**两路候选的并集大小**，因此"两路之和 − 并集"正好等于被合并掉的重复条数。

### 5.2 实测：`1/61 + 1/61 = 0.032787`

演示脚本第 7 节，查询 `retry_budget`（它的词元是词表里唯一的拉丁词，且向量方向恰好也指向同一条）：

```text
两路召回：vector 10 条、bm25 1 条 | 融合名单 10 条；并集 10 条；被两路同时命中的 1 条
    #0 h-t-02  score=0.032787 | channel=vector  | channels=('vector', 'bm25')
    #1 h-c-01  score=0.016129 | channel=vector  | channels=('vector',)
h-t-02 的分数是两个 1/61 之和（1/61 = 0.016393）：两路各给了它一个名次 0。
下一名的分数只剩 1/62（只有一路的名次 1）。
```

因此"两路都提到它"比"某一路排第一"更有分量——这是融合给出的**新信息**，单路检索永远给不出它（它连"被几路提到"这个概念都没有）。注意上面那一条的两个通道字段**给出了不同的答案**，而它们是同一个问题的两个问法：

```text
channel=vector               "这条主要是谁找回来的" → 贡献最大的那一路
channels=('vector','bm25')   "这条被哪几路召回"     → 全部证据
```

`HybridRetriever._to_hit` 的 `channel=_dominant_channel(contributions)` 与 `fusion._ordered_channels` 是**同一条规则**（名次相同时向量优先），因此 `channels[0] == channel` 永远成立。

### 5.3 `FusedHit`：这条凭什么在这里

七个字段里只有一个（`score`）是"能不能排序"的问题，其余六个都是"这条凭什么在这里"的问题：

```text
record_id       哪一条
score           融合后的分数（策略定义的口径，不是一个"相关性"）
rank            融合后的名次（0 起连续）
channels        被哪几路召回（**按名次好坏排序**）—— 多路命中一眼可见
channel_ranks   每一路给它的名次（{"vector": 3, "bm25": 0}）
channel_scores  每一路的**原始**分数（"两路的分数量纲不同"因此可以对着看）
contributions   每一路对最终分数的贡献（两条一起解释"为什么是 0.0315"）
```

`__post_init__` 里有一条**自洽性校验**，它是"这个形状为什么存在"被写进代码的样子：

```python
if set(self.channel_ranks) != set(self.contributions):
    raise FusionError(
        f"FusedHit 的通道证据不自洽：{sorted(self.channel_ranks)} 与 "
        f"{sorted(self.contributions)} 的通道集合不同——不一致时'这条为什么排这里'就无法回答。")
```

### 5.4 `contributions` 与召回条数是**两个**数字

没有 `contributions` 时，"向量 `alpha=0.3` 的结果为什么与 `alpha=0.7` 一样"只能靠重跑两次来回答；有它时，读一眼 `{"vector": 0.6, "bm25": 0.0}` 就知道**关键词路这次什么都没贡献**（那时要调的不是 `alpha`，而是查询说法或语料）。同一句话在 `contribution_counts` 那一层还有一个聚合版本：**某路召回 3 条、贡献 0 条**意味着"它召回的东西全被别的路挤出了名单"（这一路这次没用），而**召回 3 条、贡献 3 条**意味着"它的每一条都进了名单"——单看召回条数时这两种情况长得一样（都是 3），因此 `fusion` 摘要里 `recall` 与 `contributions` 是**两个**数字。

逐条的数值证据**留在融合层**、不进 `RetrievalHit`：最终命中只带 `channels`（"这一条是哪几路召回的"这个可读结论）。把它们塞进每一条命中，会让一份报告里出现三张小表 × N 条——与 day066 那句"`RetrievalHit` 不带向量"是同一条理由。

### 5.5 `RetrievalResult` 多出来的两块与三条不变量

```text
channel_candidates  每路各自候选多少（{"vector": 15, "bm25": 3}）——"有一路是不是根本没捞到东西"
fusion              策略 / 参数 / 每路召回条数 / 每路贡献数 / 融合与去重条数
```

两个字段**只在混合检索时非空**，空字典的含义是"这次是单路检索，没有多路证据可记"。`channel_candidates` 与 `candidates` 必须**一起**看：并集小于两路之和的差值就是"被两路同时命中"的条数。`RetrievalResult.explain()` 也相应多出两行：`两路明细：vector 10 条、bm25 1 条 —— 并集 10 条（同一条被两路召回只算一次，因此并集 <= 各路之和）`、`融合：策略 rrf（k_rrf=60）—— 每路贡献 vector 10 条、bm25 1 条`。三条不变量被测试逐条钉住：

```text
channels[0] == channel                  两个问题的两个问法必须给同一个答案
len(set(channels)) == len(channels)     不伪造重复的通道
sum(contributions.values()) == score    证据必须能解释分数（RRF 与 weighted 都成立）
```

## 第六章：十三步流水线——顺序本身就是语义

### 6.1 为什么不继承 `Retriever`

> **它刻意不继承 `Retriever`**：那条流水线（九步）与这条（十三步）在"什么时候落阈值、什么时候裁多样性"上顺序**不同**——混合模式必须把多样性放在融合之后（否则两路各自裁一遍，被某一路裁掉的记录就没有机会从另一路被救回来）。继承会强迫这两套顺序共用一套方法名，而它们的语义差别恰恰是本课要讲的东西。

```text
day066  Retriever.retrieve         九步   单路：取候选 → 阈值 → 多样性 → 截断 → 诊断
day067  HybridRetriever.retrieve  十三步  两路：过滤 → 两路各取候选 → 阈值（只向量路）→ 融合 → 装配
                                          → 多样性 → 截断 → 诊断
```

复用是**私有函数级**的：`retriever_module._fetch_depth` / `_inspect_index` / `_warn_drift` / `_apply_threshold` / `_apply_diversity` / `_diagnose` / `_elapsed_ms`（`hybrid.py` 顶部那行 `from smart_research_agent.retrieval import retriever as retriever_module`）。理由：各写一份判据，"同一个库、同一句话、两份报告里的 `dropped_below_threshold` 不一样"这种事迟早会发生。

### 6.2 十三步的完整表

| 步 | 做什么 | 落地位置 | 它留下的可见痕迹 |
|----|--------|---------|-----------------|
| 1 | 规范化查询（`None` 字段沿用向量路默认值） | `hybrid.py::HybridRetriever._normalize_query` | `result.query` |
| 2 | 融合参数解析（ctor 默认 ← `query.extra`） | `hybrid.py::HybridRetriever._resolve_fusion` | `result.fusion`、`notes` |
| 3 | 算召回深度（**复用向量路那唯一一份实现**） | `retriever.py::Retriever._fetch_depth` | `result.fetch_k` |
| 4 | 索引体检（条数与清单漂移） | `retriever.py::Retriever._inspect_index` | `result.index_state`、`notes` |
| 5 | 合成过滤子句（**只调一次**） | `filters.py::combine_where` | 两路拿到同一个对象 |
| 6 | 关键词路取候选 | `lexical.py::LexicalIndex.search` | `channel_candidates["bm25"]` |
| 7 | 向量路取候选（编码 + `backend.query`） | `retriever.py::Retriever._encode_query` | `channel_candidates["vector"]` |
| 8 | 阈值落刀（**只对向量路**） | `retriever.py::_apply_threshold` | `dropped_below_threshold` |
| 9 | 融合 | `fusion.py::fuse` | `result.fusion` |
| 10 | 装配命中（`channel` / `channels`） | `hybrid.py::HybridRetriever._to_hit` | `hits[].channel`、`hits[].channels` |
| 11 | 多样性裁剪（**在融合之后**） | `retriever.py::_apply_diversity` | `dropped_by_diversity` |
| 12 | 截断到 `top_k`（只重编号，不重排） | `hybrid.py::HybridRetriever.retrieve` | `dropped_by_top_k` |
| 13 | 诊断与装配 | `retriever.py::_diagnose` | `empty_reason`、`latency_ms`、`notes` |

表的**编号顺序与代码执行顺序不一致**：表里第 6 步在向量路（第 7 步）**之前**，而代码里向量路先跑，因为"它的编码校验会在参数有问题时先响"：

```python
# 第 7 步（先做向量路，因为它的编码校验会在参数有问题时先响）：
vector_hits, dropped_threshold = self._vector_channel(resolved, state, fetch_k, combined, notes)
# 第 6 步：关键词路（同一个 where、同一个深度）。
lexical_result = self._lexical.search(resolved.text, top_k=fetch_k, where=combined)
```

### 6.3 ASCII 结构图

```text
                query: str | RetrievalQuery
                          |
   (1) _normalize_query     向量路的默认值只有一处定义        (2) _resolve_fusion   ctor 默认 ← extra
   (3) _fetch_depth         max(top_k, ceil(top_k×3))，封顶 1000
   (4) _inspect_index       count + 清单漂移（strict 时拒绝服务）
   (5) combine_where  ──────┴──────  **一次调用、同一个对象**
              |                                |
      combined|                                |combined
              v                                v
   (7) 向量路：编码 + backend.query   (6) 关键词路：lexical.search（不设阈值）
              |                                |
   (8) _apply_threshold（**只在这里**）          |
              +---------------+    +-----------+
                              v    v
       (9) fuse → (10) _to_hit → (11) _apply_diversity（**融合之后**）
                    → (12) 截断到 top_k（只重编号）→ (13) _diagnose + 装配
```

### 6.4 两处"共用一份"的理由

**深度只有一份**（第 3 步 `fetch_k = self._vector._fetch_depth(resolved, notes)`）："两路深度不同时，融合会把'这一路取得浅'读成'这一路没有它'"——`vector` 取 15 条而 `bm25` 只取 5 条时，"`bm25` 里没有它"与"`bm25` 只取了前 5 条"就混在一起了。**多样性只有一次，且在融合之后**：

```python
# 第 11 步：多样性裁剪（在**融合之后**做，因此两路都有机会把同文档的
# 其他记录带进来；在融合之前裁会把"这一路裁掉的"直接判死）。
kept, dropped_diversity = retriever_module._apply_diversity(
    hits, resolved.max_per_doc, self._doc_id_field,
)
```

融合之前各裁一遍等于**在证据合并之前就判决**：某条在向量路被 `max_per_doc` 挤掉、在关键词路排第 1，它本该靠关键词路那条证据活下来，却在融合之前就死了。`_normalize_query` 里还有一处本层特有的收口：`max_per_doc` 要单独收一次，因为向量路的 `_normalize_query` 会把 `None` 填成**它自己的**默认值；而向量路那 `0` 表示"不限"、`RetrievalQuery` 里 `None` 才是"不限"（`0` 会被拒）——三者的换算只写在这一处。

### 6.5 `explain` 补的五行

`HybridRetriever.explain(result)` 在 `result.explain()` 的四问之上补混合模式特有的一组行：**两路明细**（召回 vs 贡献）、**融合参数**、**阈值口径**、**关键词索引现状**、**分组口径**，若带了 `where` 还会补一条**字段拼写检查**。其中"两路明细"那一行值得单独读，它把三个数字**写成了一个等式**：

```python
# "两路明细"那一行把三个数字**写成了一个等式**（下面是它的骨架）：
f"两路明细：向量路召回 {cc[CHANNEL_VECTOR]} 条、关键词路召回 {cc[CHANNEL_BM25]} 条；"
f"最终名单里各贡献 {contrib.get(CHANNEL_VECTOR, 0)} / {contrib.get(CHANNEL_BM25, 0)} 条"
f"（并集 {result.candidates} 条 = 两路之和减去被两路同时命中的 {fusion.get('deduped', 0)} 条）"
```

读的人不用自己想这几个数字之间的关系，等式本身就是解释。`retrieve_many` 与 `Retriever.retrieve_many` 一样是**刻意的逐条**：每次混合检索的两路召回数与融合证据都是独立的，而"这一批总共花了多久"与"其中一次为什么某一路没贡献"是两个不同的问题（后者才是要查的那个）。

## 第七章：过滤必须在**两路都落刀**（本课最值得讲的一个坑）

### 7.1 一个非常安静的失败模式

```text
只过滤向量路   用户 where={"strategy": "structural"} → 向量路只取 structural 的
              关键词路不过滤 → 它把 fixed/semantic 的记录也捞了回来
              融合之后：结果里出现了过滤条件明确排除掉的记录
              而报告里 filter_applied=True（"过滤生效了"），没有任何异常
```

这类"少而不报"的反面——"**多而不报**"——比少更危险：少了几条还能靠对比两次运行发现，多了几条在报告里看起来完全正常（谁也不会去核对每一条命中的 `strategy` 是不是 `structural`）。演示第 9 节用 `where = {"parent_doc_id": "doc-concept"}` 把反面对照真跑了一遍：

```text
正确做法（两路都过滤）：向量 4 条、关键词 0 条 → 名单 h-c-01、h-c-02、h-c-03、h-c-04
错误做法（只过滤向量路）：向量照旧 4 条，而关键词路**不过滤**时会返回 1 条（h-t-01）
把这些合起来（用真实的融合函数算一遍）：融合后的名单里出现 1 条**不满足过滤条件**的记录
    [('h-t-01', 'doc-trouble')]  —— 而报告里 filter_applied=True，没有任何异常
```

本教程独立复算的两行关键证据：`关键词路带 where → 候选 4、命中 []`（那 4 条里没有一条含 err/2043），`关键词路不带 where → 命中 ['h-t-01']`。**候选从 10 压到 4、命中是 0** 这两个数字分别说明"过滤落刀了"与"这 4 条里没有字面命中"——没有 `candidates` 这个数字，"命中 0 条"仍然可以被误读成"关键词路一条都没召回"。

### 7.2 保证是**结构上的**，不是注释里的约定

```python
# 第 5 步：过滤子句**只合成一次**（两路拿到同一个对象，见模块 docstring 的坑）。
combined = combine_where(resolved.where, resolved.time_range)
...
vector_hits, dropped_threshold = self._vector_channel(resolved, state, fetch_k, combined, notes)
lexical_result = self._lexical.search(resolved.text, top_k=fetch_k, where=combined)
```

`combined` 是**一个局部变量**、被两个调用点各引用一次：加第三路时，那个新调用点要么拿到同一个 `combined`，要么就得显式写出 `where=None`（那是一个会被 review 抓住的动作）。"同一份**语义**"那一半由 `LexicalIndex.search` 保证：它**完全复用** `vectorstore.filters.compile_filter`（经 `retrieval.filters.validate_where` 包装，把 `FilterError` 翻成 `QueryError`）。两路各写一份过滤实现的话，"同一个 `where` 在向量路筛掉 3 条、在关键词路筛掉 2 条"这种分家会永远存在而且不报错。

### 7.3 缺字段的记录被**两路同时**排除

day066 的约定三（`$gte` 对缺失字段返回 `False`）在混合模式下有了新的对照面：样本里 `h-t-03` 没有 `created_at`，任何时间范围都会把它从**向量通道与关键词通道**里一起排除。它不是 bug，而是"宁可少召回，也不替一条记录猜一个创建时间"的第二次生效——真正的收获是**两路的排除是同时的**，因此"两路都少了一条"在混合模式下有一个统一解释，不需要分别排查。`combine_where` 的另一条纪律（`where` 与 `time_range` 撞在同一个字段上直接报 `QueryError`）在混合模式下同样只报一次——子句在取候选之前就合成好了，两路会**一起**被拒。

## 第八章：阈值只作用于向量路，而且必须进 `notes`

### 8.1 有绝对标度与没有绝对标度

```text
向量通道   有绝对标度（余弦 ∈ [-1, 1]）→ 可以设阈值，而且这次落刀的数字要报出来
关键词通道 没有绝对标度（BM25 ∈ [0, ∞)，同一份文档在两个查询上的 7.31 不可比）
           → **不设阈值**：给它一个数字是"假的安全感"
```

"假的安全感"是这段话里最要紧的词：BM25 的分数分布取决于语料（词频、文档长度、词表大小）与查询长度，因此 `min_score=3.0` 在一份 10 篇文档的手册上可能切掉一半，在一份 100 万篇的语料上可能一条都不切。给一个**看起来能调**的参数，后果是出问题的人去调它、发现没有稳定效果、于是转去调别的参数——**一个不存在的旋钮比没有旋钮更贵**。它与 `config.retrieval_min_score = None` 的缺省理由是同一句话："标定之前给一个数字是假的安全感"。

### 8.2 实测：阈值把向量路清空时，关键词路照常给答案

查询 `ERR-2043`（向量路的分数只有 `1.0` 与 `0.0`——10 条里只有一条与查询同向）：

```text
min_score |      向量路候选 |      被阈值切掉 |   命中 | 名单
     None |         10 |          0 |    5 | h-t-01、h-c-01、h-c-02、h-c-03、h-c-04
      1.0 |          1 |          9 |    2 | h-c-01、h-t-01
      1.5 |          0 |         10 |    1 | h-t-01
```

关键一行是 `min_score=1.5`：它把向量路的 10 条**全部**切掉（余弦最高只有 `1.0`），而 `h-t-01` 照样在名单里——它只有关键词路召回它（那条路的分数是 `2.27`，不受影响），通道证据是 `[('h-t-01', ('bm25',))]`。本教程独立复算的结果与上表逐字一致。注意 `min_score=1.0` 那一行的名单次序是 `h-c-01、h-t-01`，而 `min_score=None` 时是 `h-t-01、h-c-01`：这不是"名单不稳定"，而是**两者的融合输入不同**——前者向量路只剩 1 条（`h-c-01` 排第 0），后者向量路有 10 条（`h-t-01` 在向量路的名次是 7）。`1/61 + 1/68 = 0.031099` 与 `1/61 + 1/62 = 0.032787` 的差别就来自这里。

### 8.3 被忽略这件事**必须无条件进 `notes`**

```python
# 阈值口径的注记**必须无条件出现**（不许静默地忽略一个用户设过的参数）。
if resolved.min_score is not None:
    notes.append(
        f"min_score={resolved.min_score} **只作用于向量通道**（在融合前落刀，"
        f"本次切掉 {dropped_threshold} 条）；关键词通道不设阈值——"
        "BM25 的分数没有绝对标度，给它一个数字是假的安全感"
        "（与 settings.retrieval_min_score 缺省 None 的理由同源）。"
    )
```

判据是 `if resolved.min_score is not None`——**即使这次它一条都没切、即使阈值是 `-1.0`**，这句话也要出现。"我设了阈值为什么关键词路还在返回低分记录"会变成一个反复出现的疑问，唯一能永久终结它的办法就是让它在每一次带阈值的混合检索里都被说出来。这条是本日**第四条贯穿全包的纪律**（`retrieval/__init__.py` 从三条变成四条）：**被忽略的参数必须被说出来**——一个"看起来能调、实际上不生效"的旋钮比没有旋钮更贵。

### 8.4 一个随之而来的规则变化（必须写下来）

单路检索里"`min_score` 切光即是 `below_threshold`"，而混合模式下 `below_threshold` **必须同时**满足"关键词路本来就没召回"——因为阈值**不可能**清空关键词路（那一侧不设阈值）。实测对照：`query=QUERY_SEMANTIC + min_score=1.5 → below_threshold`，而 `query=ERR-2043 + min_score=1.5 → **不是空结果**`（关键词路那一条还在）。把单路那条充分条件照搬过来，会让这条诊断**指向错误的动作**（去降阈值，而实际上关键词路一条都没召回才是真因）。`_vector_channel` 的返回值形状也值得记一下：它返回 `(kept, dropped)`，而"向量通道一条都没活下来"被拆成两句 note，因为处置不同：

```text
min_score=X 在融合前把它的命中全切了            → 前者：去调阈值
库侧这次没有返回任何候选（过滤条件或索引内容）    → 后者：补另一路的权重或换查询说法
```

这与第五章"两路之和 − 并集 = 去重条数"是同一种写法——**把不同动作的东西写成不同的句子**。

## 第九章：融合后的空结果诊断与 `dropped_*` 的归属

### 9.1 三种成因，各自一个动作

```text
处境                                 |   命中 | empty_reason     | 动作
库是空的（合法状态）                         |    0 | no_data          | 先建索引
过滤把两路候选都筛成 0 条                     |    0 | filtered_out     | 放宽 where / 时间范围
阈值切光向量路 + 关键词路本来就没召回               |    0 | below_threshold  | 降低 min_score 或不设阈值
```

本教程独立复算：空库 `empty_reason = no_data`（且 `fetch_k = 15`——**深度在空库上照样是算过的**，这是 day066"第 3 步排在体检之前"在混合模式下的直接继承）、`where={"strategy": "nope"}` → `filtered_out`、"午饭 + min_score=1.5" → `below_threshold`。第四种成因 `diversity_trimmed` 在端到端路径上**不可达**（多样性每组至少留一条，它靠直接构造诊断输入才能触发）——这条 day066 的可达性事实在混合模式下**没有变**：`_apply_diversity` 是同一个函数，"每组至少留一条"也照旧。

### 9.2 三个 `dropped_*` 在混合模式下的归属

| 数字 | 混合模式下的来源 | 谁去调 |
|------|-----------------|--------|
| `dropped_below_threshold` | 第 8 步 `_apply_threshold`，**只对向量路的命中** | 调 `min_score`（且知道它只影响一路） |
| `dropped_by_diversity` | 第 11 步 `_apply_diversity`，在**融合之后**、按 `doc_id_field` 分组 | 调 `max_per_doc`（本层构造参数优先） |
| `dropped_by_top_k` | 第 12 步截断，次序是融合的权威次序，**只重编号不重排** | 一般不用调：它只是"取够了" |

第 12 步的代码形状值得记一下——它用 `dataclasses.replace` **只改 `rank`**：`final = tuple(replace(hit, rank=position) for position, hit in enumerate(kept[:top_k]))`，`dropped_top_k = len(kept) - len(final)`。融合的次序已经是权威次序（第 9 步已按 `(-score, best_rank, record_id)` 排好），截断之后再排一次会把两个不同的排序键混在一起，而"名次"从此不再是"融合的结果"。

### 9.3 `candidates` 的口径变了，而这件事必须写下来

```python
union_candidates = len({hit.record_id for hit in vector_hits}
                       | {hit.record_id for hit in lexical_hits})
```

day066 的 `candidates` 是"库侧过滤之后还剩多少条可选"；混合模式下它是**两路候选的并集大小**。同一个字段名承载了两个口径，因此 `hybrid.py` 模块 docstring 专门写了一段"结果里多出来的两类证据"，`docs/hybrid_retrieval.md` 第 6 节又把读法做成一张七行表（`channels` / `candidates` / `channel_candidates` / `fusion` / `RetrievalHit.channel` / `RetrievalHit.channels` / `empty_reason`）。**字段名不变、口径变了**，这件事必须写在文档里，否则读者会用单路的直觉去读混合模式的报告。

### 9.4 四种"关键词路空着"的成因

```text
索引是空的（0 篇）        → 先建关键词索引（from_backend）
被 where 筛成 0 条        → 放宽过滤条件（这一路的过滤与向量路是同一份）
查询词元与词表交集为空    → 纯语义改写 / 未登录词——**这是最正常的一种**，
                          向量路正好擅长它，混合检索的价值在这里体现
词元都认识但没有一篇全中  → 语料里确实没有同时提到这几个词的内容（要去看语料）
```

第三句是这四种里最要紧的：它是**混合检索存在的正面证据**（案例 B 落的就是这一支），而报告里那句话与 notes 里"这正是 day066 留下的那个钩子"合起来，把"关键词路空着"从一次失败变成一次**预期内的分工**。`HybridRetriever.explain` 的字段拼写检查在混合模式下比单路更要紧——一个拼错的字段名会让两路同时空掉，而"两路都空"很容易被读成"语料里没有相关内容"。这是本日最有价值的一条排查提示：`filtered_out` 这一个 `empty_reason` 在混合模式下同时覆盖"字段名写错"与"语料里真的没有"两种情况，而 `explain()` 里那行字段拼写检查是**唯一**能把它们分开的证据——**那时该改的是字段名，不是语料**。

## 第十章：融合参数与配置

### 10.1 构造默认 ← `RetrievalQuery.extra`（day066 预留的那个槽）

```python
query = RetrievalQuery(text="ERR-2043", extra={"strategy": "weighted", "alpha": 0.3})
result = hybrid.retrieve(query)          # result.fusion["params"] == {"alpha": 0.3}
```

`HybridRetriever(strategy=..., alpha=..., k_rrf=..., weights=...)` 是**缺省**，`extra` 可以逐次覆盖；`None` 的明确含义是"**没指定，去读 `settings` 或去问向量路**"（`retrieval_hybrid_strategy` / `retrieval_hybrid_alpha` / `retrieval_hybrid_rrf_k`），于是"项目默认值"只有一处定义。键名是**封闭清单**（`fusion.FUSION_OVERRIDE_KEYS = ("strategy", "alpha", "k_rrf", "weights")`）：多一个键就报 `FusionError` 并列出合法取值——理由与 `RagPipeline.OVERRIDE_KEYS` 完全相同（静默忽略一个覆盖参数会让调用方以为它生效了："我把 `alpha` 拼成 `alhpa`，结果看起来只是没有变化"）。参数来自 `extra` 时**必须进 notes**：`本次覆盖了 …`（连本层默认值一起报出来），否则同一份查询在两个调用点会给出不同结果而无法解释。

### 10.2 参数校验只有一份实现，而且**构造期就响**

```python
# 融合参数的校验只有一份实现（fusion.fuse）：构造期拿一份**空输入**先过一遍它，
# 于是"参数写错"在**装配那一刻**就响（否则会把配置错误伪装成"这次请求碰巧不对"）；
# 这一次调用同时覆盖了"strategy='rrf' 却给了 weights"这个组合。
fuse({}, strategy=self._strategy, alpha=self._alpha, k_rrf=self._k_rrf, weights=self._weights)
```

`_resolve_fusion` 里那次空输入调用多了一个理由：**"库是空的"那条早退路径也照样会在参数错误上响**——否则一个写错的 `strategy` 会被"库恰好为空"掩盖掉，而在库有数据时才突然冒出来。三个配置解析函数在**构造期一次算清**，之后不再看 `settings`；`_resolve_weights` 还会**存一份副本**（"构造参数不该在运行期被外部改掉"）。`strict_index` 的取值与 `Retriever` 同一句——**只增不减**：构造参数只能把它打开，不能覆盖 `settings` 里已经打开的 `True`，也不能覆盖向量路已经打开的 `True`。

### 10.3 `config.py` 新增的六项

```python
retrieval_hybrid_enabled: bool = False        # 新能力**默认不生效**（见下）
retrieval_hybrid_strategy: str = "rrf"        # 缺省 rrf：分数量纲不可比
retrieval_hybrid_alpha: float = 0.5           # weighted 下向量通道的权重（关键词是 1 - alpha）
retrieval_hybrid_rrf_k: int = 60              # RRF 平滑常数（Cormack et al., 2009）
retrieval_bm25_k1: float = 1.5                # 词频饱和项（Robertson & Zaragoza）
retrieval_bm25_b: float = 0.75                # 长度归一化强度
```

这一组与既有的 `retrieval_*`（8 项）是**同一类**：不改变任何产物的字节（不改 `chunk_id`、不改向量、不改清单版本号），只改变"怎么问"，因此调它们随时生效、**不需要**重建索引。只多了一条别的组没有的纪律：`retrieval_hybrid_enabled = False` 的理由不是保守，而是**结果集合会变**（关键词路会捞进向量路没召回的记录——那正是它存在的意义），因此"换一层检索"必须是一次**显式决定**。`hybrid_enabled()` 是它的读口，而 `build_hybrid_retriever` 的 docstring 把最容易被误读的一件事写在了明面上：

```text
3. 注意关键词索引是**一次性快照**   它不会跟着向量库的后续写入自动更新——
   而"关键词索引落后于向量库"会让关键词路静默少召回。
   因此：库变了就重建（from_backend），或直接注入一个你自己管生命周期的 LexicalIndex。
```

"装配函数每次现建"很容易被读成"每次检索都会重建"——**不是**：`build_hybrid_retriever` 被调用一次，索引就只建一次；"每次请求现建"发生在 `api.routes.retrieval_hybrid` 那条路径上，那里也把这件事写进了注释。

|------|------|------|-------------|
| `/retrieval/status` | GET | — | `Retriever.describe()`（`defaults` 里含新增六项） |
| `/retrieval/search` | POST | `query` + 七个检索参数 | `Retriever.retrieve` → `RetrievalResult` |

| **`/retrieval/lexical/status`** | **GET** | — | `lexical.py::LexicalIndex.describe()` |

### 11.1 三条本组独有的约定

```text
1. 融合参数挂在 RetrievalQuery.extra 上（请求体里是三个具名字段）
2. 缺省关闭：retrieval_hybrid_enabled=False 时 /retrieval/hybrid 返回 **400**，
   消息里给三样东西——开关名、当前值、两条出路（环境变量 RETRIEVAL_HYBRID_ENABLED=true，
   或往 app.state.retrieval_hybrid 注入一个 HybridRetriever）——**不静默退回单路**
3. 两路的证据原样出门：channel_candidates / fusion 直接来自 RetrievalResult.to_dict()
```

"**不静默退回单路**"这条的理由是：静默退回会让你以为自己在看混合检索的结果，而实际上一次关键词检索都没发生。而"注入优先、再看开关"的顺序也是刻意的：注入一个 `HybridRetriever` 是"我明确要这条链路"的显式动作（测试就这么做），因此它不该被一个环境变量否掉；**开关管的是缺省装配**——它是"这个实例要不要长出混合检索"的运维决定。

### 11.2 两条与错误映射有关的细节

```text
注入了一个类型不对的对象（app.state.retrieval_hybrid 不是 HybridRetriever）
    → **500**：这是装配写错了，不是请求参数写错了。降级成 400 会让一个必然
      复现的配置错误看起来像"这次请求碰巧不对"
关键词索引每次请求现建（from_backend）    → 代价是 O(N) 分词；语料大时请注入
      app.state.retrieval_lexical（与多索引注入 app.state.retrieval_router 同一条出路）
```

错误码因此只有两种：**参数问题一律 400**（`QueryError` / `FusionError` / `IndexStateError` / `LexicalError` 全部继承自 `RetrievalError`，消息里已经带足出路，原样带回），**认不出来的异常一律上抛成 500**——报告只收留我们认识的失败。

### 11.3 `/retrieval/lexical/status`：一条纯粹的读端点

它存在的理由是**诊断顺序**：关键词路一条都没召回时，要按这个顺序排除——**索引是空的吗**（`count`：0 篇 = 还没建，与"语料里没有相关字面"是两件事）→ **词表有多大**（`vocabulary_size`："交集为空"要有分母）→ **文档平均多长**（`avgdl`：它进 BM25 的分母）→ **用的是哪组参数**（`k1` / `b` + `defaults` 六项，"结果不同"要能归因到显式参数）。四个问题各自对应一个动作，因此四个数字**一起**给；它**不触发任何检索**、不写任何东西。

### 11.4 一条必须写下来的边界

请求体里多余的 JSON 字段会被 pydantic 忽略（与其余端点一致），因此**拼错的字段名不会报错**——`{"weight": 0.9}` 会得到 200 和一份"参数没变"的融合摘要。这与库内那条"`extra` 里写错键名报 `FusionError`"的纪律**不是同一条通道**：`extra` 是库内 API（脚本与评估直接用），字段名错了会当场响；而 HTTP 这一层只有三个具名字段，"多给了字段"在协议层是合法的前向兼容写法。因此在这里逐次覆盖请**只用** `strategy` / `alpha` / `k_rrf` 这三个名字。`HybridRetrievalRequest` 也刻意**没有 `weights` 字段**：在请求体里传一个"通道名 → 系数"的字典，等价于把服务端的通道命名暴露成协议的一部分——要按通道调权请用 `alpha`，需要更细的权重请注入一个自己装配好的 `HybridRetriever`。`hybrid_query_of` 走 `extra` 的三个好处写在它的 docstring 里：检索器的签名不变、一份查询能被序列化回放（"这次用的是哪组参数"跟着查询走）、参数校验只有一份实现。

## 常见误区

**1. "融合就是把两路分数加起来。"** 为什么错：两路量纲**不可比**（余弦 ∈ `[-1,1]`、BM25 ∈ `[0,∞)`），直接相加会让 BM25 单方面决定名次——`0.82 + 7.31` 里"7.31 说了算"。正确理解：要么只看名次（`rrf`），要么**先按每一路归一化**再加权（`weighted`）。证据：`fusion.py` 模块 docstring；演示第 5 节实测 `[1.0, 0.0, 0.0]` 与 `[4.0006]`。

**2. "RRF 也用分数。"** 为什么错：RRF 只用名次（`1/(k+rank+1)`），`channel_scores` 只是**证据**、不参与计算。正确理解：把某一路的分数放大 100 倍，RRF 的结果逐位不变——这正是它"免标定、抗异常值"的来源。证据：`fusion.reciprocal_rank_fusion`；`test_hybrid_fusion.py::test_paper_formula_ignores_the_raw_scores_entirely`。

**3. "`min == max` 时要除零，或者归一化成 0。"** 为什么错：一路只有一条命中时必然 `min == max`，归 0 会让"唯一的那条证据"在加权和里被权重乘没（`0 × weight = 0`），而它明明是该路第一名。正确理解：定义为 **`1.0`**——归一化是保序的，把单点映射到 1 同样保序。证据：`fusion.py::_min_max_normalize`；演示第 5 节 `alpha=0.0` 那一行（关键词路归一化值是 `1.0000`）。

**4. "归一化可以对合并后的分数做。"** 为什么错：那样"这一路的最大值"里混进了另一路的量纲，`alpha` 调的是"两路混在一起之后的重心"，**仍然不是权重**。正确理解：归一化必须在**每一路内部**做。证据：`weighted_score_fusion` 的 docstring 第 1 条。

**5. "`min_score` 对两路都生效。"** 为什么错：BM25 的分数没有绝对标度（同一份文档在两个查询上的 `7.31` 与 `2.27` 不可比），给它一个数字是假的安全感。正确理解：阈值**只作用于向量通道、只在融合前落一次刀**，而且这件事**无条件进 `notes`**。证据：`hybrid.py` 阈值语义一节；演示第 8 节三行表。

**6. "阈值切光就是空结果。"** 为什么错：阈值**不可能**清空关键词路（那一侧不设阈值）。正确理解：混合模式下 `below_threshold` 还必须**同时**满足"关键词路本来就没召回"——`ERR-2043 + min_score=1.5` 得到的名单里还有 `h-t-01`。证据：演示第 9 节对照；`retriever.py::_diagnose` 的优先级。

**7. "过滤只要向量路做了就行。"** 为什么错：只过滤一路时另一路会把**已被排除的**记录抬回来，而 `filter_applied=True`、没有任何异常——"多而不报"比"少而不报"更难发现。正确理解：`where` 必须在两路都落刀，而且是**同一份子句**（一次 `combine_where`、两个调用点）。证据：`hybrid.py` 模块 docstring 的坑；演示第 9 节反面对照（名单里出现 `('h-t-01', 'doc-trouble')`）。

**8. "关键词路返回的就是它排名里的那些。"** 为什么错：BM25 会给完全不相关的文档一个 0 分，而 RRF **只看名次**，它会老老实实把"关键词路第 N 名"当成证据。正确理解：`search` **只返回 `score > 0`** 的文档，并把被排除的条数写进 `notes`。证据：`lexical.py::LexicalIndex.search` 第 6 步；实测那 9 篇被排除的文档。

**9. "同一条被两路召回是重复，要去掉。"** 为什么错：那是**最强的证据**——两条互相独立的检索路径都指向它。正确理解：合并成一条 `FusedHit` 并保留全部通道证据（`channels` 两条、贡献相加），`deduped = 两路之和 − 并集`。证据：`fusion.py` 去重语义一节；演示第 7 节 `0.032787 ≈ 2 × 0.016393`。

**10. "关键词索引是空的会报错。"** 为什么错：0 篇是**合法状态**（与向量路 `count=0` 的 `no_data` 同一口径），返回空结果 + `notes` 而不抛异常。正确理解：真正抛 `LexicalError` 的是另一种处境——**有文档却全无词元**（BM25 的分母里有 `avgdl`），那是索引侧的事（去修入库口径或重建）。证据：`lexical.py::LexicalIndex.search` 的第 4 步与中毒索引分支。

**11. "`channel` 就是唯一的通道。"** 为什么错：`channel` 只是"贡献最大的那一路"（并列时向量优先），它只能说出**一个**名字，于是"关键词路也召回了它"这个最强证据会消失。正确理解：`channel` 是归属、`channels` 是全部证据；`()` 表示"未记录多路证据"（也就是 day066 的单路语义），它**不是**"没有任何通道"。证据：`types.py::RetrievalHit` 的两个字段说明；`hybrid.py::_dominant_channel`。

**12. "混合检索缺省就开着了。"** 为什么错：`retrieval_hybrid_enabled` 缺省 **`False`**，而 `/retrieval/hybrid` 会返回 **400**。正确理解：缺省关闭不是保守，而是"结果集合会变"，因此换一层检索必须是一次**显式决定**；拒绝时消息里给开关名、当前值与两条出路（**不静默退回单路**）。证据：`config.py` 的注释；`api/routes.py::retrieval_hybrid`。

再补三条同性质的（写下来省一次排查）：

```text
13. "关键词索引会跟着向量库自动更新"  为什么错：它是一次性快照（刻意不持久化、不做增量）。
    正确理解：两路来自同一次读取，"关键词索引落后于向量库"会让关键词路静默少召回。
    证据：LexicalIndex 类 docstring、build_hybrid_retriever 的 docstring 第 3 条。
14. "`where` 与 `time_range` 可以同时写同一个字段"  为什么错：结果只会变少、不会报错。
    正确理解：combine_where 直接报 QueryError，而且两路会**一起**被拒。证据：filters.combine_where。
15. "阈值写 `>` 也行"  为什么错：阈值恰好等于分数时那种差别**必然出现**（确定性编码器给出
    逐位相同的向量，余弦恰好 1.0）。正确理解：用 `>=`，与 backend.query(min_score=…) 逐字一致。
    证据：retriever.py::_apply_threshold；演示第 8 节 min_score=1.0 那一行。
```

## 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|---------|-----------|---------|
| 关键词一路零依赖（不用 `jieba` / `rank_bm25`） | 几十行的算术不值得引入依赖；分词器有版本会让分数无法归因 | `lexical.py::tokenize` / `_idf` |
| CJK 用"单字 + 相邻 2-gram" | 单字补跨词边界与单字查询的召回，2-gram 补区分度；只留一种都会失效 | `lexical.py::TOKEN_PATTERN` / `CJK_ONLY` |
| IDF 取 `log(1 + …)`（恒正） | 负 IDF 会让"减相关"与"0 分哨兵"混在一起，而 0 分表示"没共同词元" | `lexical.py::_idf` |
| `k1 = 1.5` / `b = 0.75` 引用经典取值 | "结果不同"必须能归因到语料还是参数 | `lexical.DEFAULT_K1` / `DEFAULT_B`、`BM25Params` |
| 只返回 `score > 0` 的文档 | 否则 RRF 会把"毫无关系"当成"第 N 名证据" | `lexical.py::LexicalIndex.search` 第 6 步 |
| `idf` / `avgdl` 用全库统计、不随 `where` 重算 | 它们是语料的性质，不是"这次过滤出来的那几条"的性质 | 同上的第 6 步注释 |
| `from_backend` 把"少取回 M 条"升级成 `LexicalError` | 静默少召回不会出现在任何数字里 | `lexical.py::LexicalIndex.from_backend` |
| 融合不直接加分数（量纲不可比） | 余弦 ∈ `[-1,1]`、BM25 ∈ `[0,∞)`，直接相加会把量纲差当相关性差 | `fusion.py` 模块 docstring |
| `rrf` 缺省（`k = 60`） | 免标定、免归一化、抗异常值；用"已经跨通道可比"的名次绕开量纲 | `fusion.DEFAULT_RRF_K`、`reciprocal_rank_fusion` |
| `weighted` 在每一路**内部**做 min-max | 对合并后的分数做归一化会让 `alpha` 变成"重心"而不是权重 | `fusion.py::weighted_score_fusion` |
| `min == max` → 归一化成 `1.0`（判据是精确零跨度） | 归 0 会让唯一证据被权重乘没；epsilon 会变成第三个待标定参数 | `fusion.py::_min_max_normalize` |
| 排序键 `(-score, best_rank, record_id)` | 少一个键都会让"同一份数据两次运行给出不同 top-1" | `fusion.py::_assemble` |
| `strategy="rrf"` 给 `weights` 直接报错 | RRF 的定义里没有权重，"设了没用"会让人怀疑代码 | `fusion.py::fuse` |
| `weighted` 缺某一路权重报错（不默认 0） | 默认 0 会让那一路的证据静默消失，表现成"某类查询突然变差" | `fusion.py::_resolve_weights` |
| 去重 = 合并证据（`channels` 保留多路） | 同一条被两路独立召回是融合能给出的**新信息** | `fusion.py::FusedHit`、`hybrid.py::_to_hit` |
| `channels[0] == channel`（并列时向量优先） | 同一问题的两个问法必须给同一个答案 | `_dominant_channel` / `_ordered_channels` |
| 不继承 `Retriever`，但复用其私有函数 | 两条流水线的"落刀时机"不同，判据必须相同 | `hybrid.py::HybridRetriever` |
| 过滤子句**只合成一次**、同一个对象交给两路 | 只落一路会把已排除的记录抬回来且不报错（多而不报） | `hybrid.py::retrieve` 第 5 步 |
| 阈值只作用于向量路，且**无条件进 `notes`** | BM25 没有绝对标度；"看起来能调的旋钮"比没有旋钮更贵 | `hybrid.py::retrieve` 第 8 步后 |
| 刻意不设 BM25 阈值 | 标定之前给一个数字是假的安全感 | `hybrid.py` 阈值语义、`config.retrieval_min_score = None` |
| 多样性裁剪放在**融合之后** | 融合之前裁，等于在证据合并之前判决 | `hybrid.py::retrieve` 第 11 步 |
| 截断时只重编号、不重排 | 融合的次序是权威次序，再排一次会让"名次"不再等于融合结果 | `hybrid.py::retrieve` 第 12 步 |
| `candidates` 在混合模式下 = 两路候选的**并集** | "两路之和 − 并集"就是最强证据的条数，只能从两个数一起读出来 | `hybrid.py::retrieve`、`_fusion_summary` |
| 融合参数走 `RetrievalQuery.extra`（封闭清单） | 签名不变、查询可回放、校验只有一份实现 | `fusion.FUSION_OVERRIDE_KEYS`、`_resolve_fusion` |
| 构造期拿空输入先过一遍 `fuse` | 配置错误要在装配那一刻响，而不是伪装成"这次请求碰巧不对" | `HybridRetriever.__init__`、`_resolve_fusion` |
| `retrieval_hybrid_enabled = False` | 新能力会改变结果集合，"换一层检索"必须是显式决定 | `config.py`、`hybrid.hybrid_enabled` |
| 端点缺省关闭时返回 400（不静默退回单路） | 静默退回会让你以为在看混合结果，而实际上一次关键词检索都没发生 | `api/routes.py::retrieval_hybrid` |
| 关键词索引的现状单独成端点 | 诊断顺序：篇数 → 词表 → `avgdl` → `k1`/`b`，四问各自一个动作 | `api/routes.py::retrieval_lexical_status` |

### 今天埋下的伏笔

```text
RetrievalHit.channels / RetrievalResult.fusion
    day068 的重排消费**融合之后**那份名单：它要按分数排序，而"这一条是几路证据支持的"
    （channels 与 contributions）让它能把"重排带来的提升"归因到"融合是否已经把它摆出来了"
    ——否则重排的收益与融合的收益会混成一个数字，说不清是谁做对了。
RetrievalHit.text / score 与 fusion["channel_scores"]
    重排需要**原文与查询的交叉编码**，因此它读的是融合后的 text + score；而逐条留下的
    channel_scores 让它能对照"重排前后名次怎么变的"。
RetrievalResult.fusion["params"]
    "这次用的是哪组参数"跟着结果走。day068 评估重排时会同时换融合参数与重排模型，
    没有它就分不清收益来自哪一侧（与 day065 的"分数变了必须能归因"是同一条纪律）。
RetrievalResult.channel_candidates
    "某一路空着"是一个可读事实。day071 的 RAG 评估要按通道统计召回与贡献，
    那一层的第一手输入就是它（外加 aggregate_results 的汇总）。
RetrievalHit.citation(index) / heading_path
    day069 的引用溯源复用 1 起编号与"来源 › 标题路径"的形状；混合模式下这一条**没有变化**
    ——引用要指向原文，不指向"它是哪一路召回的"（通道是诊断信息，不是引用信息）。
过滤与阈值这两处旋钮
    `where` 要在两路都落刀、`min_score` 只作用于向量路。day071 评估时若要按过滤条件切片，
    必须记住这两条，否则切片的数字与线上的数字会用两套口径。
```
