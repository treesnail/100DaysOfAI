## 第一部分：选择题

### 第 1 题

**答案：B**

解析：MCP 是连接协议，不改变模型本身的推理能力（A 错），也不是微调方法（C 错）——它的战场在"应用与外部能力的对接面"。没有标准协议时，M 个应用 × N 个能力需要 M×N 套私有对接代码；有了 MCP，每侧只实现一次标准接口，总工作量降为 M+N。这和 USB-C 统一硬件接口的逻辑完全相同。D 错在 MCP 规范本身不解决加密问题（传输层安全由 HTTPS/SSH 等下层机制负责）。

### 第 2 题

**答案：C**

解析：MCP 的连接模型是 **1:1**——一个 Client 实例只对应一个 Server 连接。Host 要同时用三个 Server，就创建三个 Client。C 描述的"一个 Client 管多个 Server"会导致会话状态、能力清单、请求 id 空间互相串台。A、B、D 都是正确描述：Host 管业务（ReAct 循环、Planner），Client 只是协议管道；Server 面向标准协议实现，天然可被任何兼容 Host 挂载——这正是标准化的回报。

### 第 3 题

**答案：B**

解析：一次 JSON-RPC 调用要么成功要么失败，result 与 error 互斥。若建模成一个类加两个可选字段，则 `JsonRpcResponse(result=None, error=None)` 这种"既没成功也没失败"的非法状态在类型层面完全合法，只能靠运行时检查兜底。拆成两个类后，非法状态**根本无法构造**——"让非法状态不可表达"是 pydantic 建模的精髓。A 不是动机；C 明显错误（`Optional` / `| None` 就是可选字段）；D 因果倒置，JSON-RPC 规范只约束线上 JSON 格式，不关心你用几个 Python 类。

### 第 4 题

**答案：C**

解析：三原语的分流标准是**副作用 + 谁做决策**。网络搜索有外部副作用（发出 HTTP 请求），且调用时机与关键词由 LLM 在推理中决定——两个特征都指向 Tool。A 错在 Resource 是只读上下文、由应用主导读取；B 错在 Prompt 是用户主导的模板，与"模型自主决定调用"的语义相反；D 忽视了控制权归属这一本质区别——用反了不会报错，但架构语义会腐烂（参见教程 3.4 误区一）。

### 第 5 题

**答案：B**

解析：stdio 传输下，Server 的 **stdout 就是协议通道**——JSON-RPC 消息在 stdout 上流动。任何 `print` 到 stdout 的内容都会混进协议流，Client 端解析到一个非 JSON 行就会报协议错误。日志必须走 stderr 或文件（A、C 都安全）。D 完全无害，反而值得鼓励：FastMCP 会把 docstring 作为工具的 description 发给 LLM，写得越清楚，LLM 路由越准——"写 FastMCP 的 docstring 就是在写 prompt"。

### 第 6 题

**答案：B**

解析：适配器把 MCP Tool 的 name/description/schema 透传为 BaseTool 的属性，`execute()` 内部转发 `session.call_tool`，然后像本地工具一样注册进 ToolRegistry。结果是：ReAct 循环、SYSTEM_PROMPT 拼装、Planner 下发逻辑——M1 写下的所有代码**一行不改**，因为 MCP 工具长得和 CalculatorTool 一模一样。这是依赖倒置的红利：day004 定义 BaseTool 时不知道 MCP 的存在，但它接住了。A 错，适配器只转发不加速（反而多一层调用）；C 错，握手是协议强制环节，适配器不绕过也不能绕过；D 错，连接模型 1:1，多 Server 需要多 Client，适配器只是单个工具的包装。

## 第二部分：判断题

### 第 7 题

**答案：错**

解析：握手（initialize）是 MCP 生命周期的**强制第一阶段**，不是可选实践。协议规定：握手完成前收到业务请求，Server 一律报错。握手的价值有三：版本协商（新旧端优雅共存）、能力声明（Client 提前知道 Server 有没有 resources/tools/prompts，避免"调了才知道没有"）、明确的状态机（实现与调试更简单）。day020 的 Client 封装把握手做成连接后不可省略的第一步。这和 TCP 三次握手是同一个工程思想。

### 第 8 题

**答案：错**

解析：只看"返回一段文本"是表象。两者的本质区别在**控制权归属与副作用**：Resource 由应用主导读取、只读无副作用（如读知识库文档 `kb://docs/intro.md`）；Tool 由模型主导调用、可能有副作用（如搜索、写库）。混用不会让程序报错，但会让架构语义腐烂——三个月后没人说得清为什么"查文档"是 Tool 而"搜索"是 Resource；Host 侧的权限策略（Resource 可以放心预读，Tool 需要审计与确认）也会失去依据。判断标准一句话：**有没有副作用、谁做决策。**

### 第 9 题

**答案：对**

解析：`create_connected_server_and_client_session`（mcp 1.29 中位于 `mcp.shared.memory`）在同一进程内用内存管道把 Server 与 Client 接起来：不起子进程、不开端口、不碰网络，测试因此快速、确定、离线。真起 stdio 子进程做单元测试慢且脆——进程清理不干净就挂，Windows 的进程模型尤其容易出平台差异。端到端验证（真实 stdio/SSE 连接）才需要真实传输。这和 M1 阶段 MockLLM 的设计哲学相同：**把最不可控的外部依赖换成进程内替身，测试才能又快又稳。**

### 第 10 题

**答案：错**

解析：这违背 M1 就建立的"错误走 Observation 通道"原则。MCP 调用是跨进程/跨网络调用，失败是常态而非异常事件。适配器的正确做法是 try/except 捕获后返回错误字符串（如 `"工具调用失败: 连接超时"`）作为 Observation 喂回 LLM——LLM 看到错误后可以自我修正（换参数重试、换工具、或在 Final Answer 中如实说明）。让异常炸穿循环等于把一次可恢复的局部失败升级为整个任务失败。注意区分失败层级：**调用级失败**走 Observation 通道；**连接级失败**（Server 根本没起来）才该在初始化阶段 Fail Fast 直接暴露。

## 第三部分：问答题

### 第 11 题

**参考答案**：

三原语的本质划分标准是**"谁主导这次调用"（控制权归属）**，辅以副作用特征：

- **Resource**：由**应用（Host/Client）**主导——应用的逻辑决定"现在要读哪份上下文"，只读无副作用。用例：SmartResearch Agent 把知识库文档暴露为 `kb://docs/{name}`，生成报告前由应用逻辑读取相关文档注入上下文。
- **Tool**：由**模型（LLM）**主导——LLM 在推理中自行决定调用时机与参数，可能有副作用。用例：`calculator`、`web_search` 作为 ReAct 循环的 Action 执行对象，LLM 输出 `Action: calculator` 时触发。
- **Prompt**：由**用户**主导——用户显式选择模板并填入少量参数，模板展开成消息。用例：用户在界面上选"深度调研"模板、填入主题，得到一份预设结构的调研提示词。

评分要点：必须答出"控制权归属"这一划分标准（只答"都是能力"不得分）；三个用例需符合各自的控制权语义。

### 第 12 题

**参考答案**：

| 维度 | stdio | SSE |
|------|-------|-----|
| 通信介质 | 子进程的标准输入/输出管道 | HTTP（SSE 推送 + POST 发送） |
| 进程关系 | 一对一，Client 拉起 Server 子进程并管理其生死 | 多对一，独立网络服务同时服务多个 Client |
| 适用场景 | 本地工具（文件、命令行）、桌面应用 | 远程服务、团队共享能力 |

开发调试期用 stdio 的原因：

1. **零网络配置**：不占用端口、不涉及防火墙、不用处理超时/重连/鉴权；
2. **生命周期托管**：Client 退出时子进程随之结束，不留孤儿进程（前提是不忘优雅关闭）;
3. **调试直接**：Server 就是本地 Python 进程，日志、断点都顺手。

代价是只能本地一对一——将来部署成团队共享服务时切 SSE。

### 第 13 题

**参考答案**：

适配器（MCPToolAdapter）做三件事：

1. **透传元数据**：把 MCP 工具的 name / description / input_schema 映射为 BaseTool 的 `name` / `description` / `parameters` 属性，LLM 看到的说明书一字不差；
2. **转发调用**：`execute(**kwargs)` 内部调用 `session.call_tool(name, kwargs)`，把返回的内容块列表拼成字符串，作为 Observation 回填；
3. **注册**：`registry.register(adapter)`，让 MCP 工具进入 ToolRegistry，进入 LLM 的武器清单。

体现 BaseTool 红利的原因：Agent 层（ReAct 循环、SYSTEM_PROMPT 拼装、Planner）只依赖 `BaseTool` 抽象，不依赖任何具体实现。MCP 工具被包装成 BaseTool 子类后，对上层与本地工具完全同构——M1 的所有代码一行不改就接入了跨进程能力。day004 定义抽象时根本不知道 MCP 的存在，但"依赖抽象而非实现"的决策让它接住了五个月后才出现的需求。这就是依赖倒置：**好抽象的回报不在定义当天，而在每一次新需求到来时。**

## 第四部分：编程题

### 第 14 题

**参考实现**：

```python
# protocol_answer.py
from typing import Any, Literal

from pydantic import BaseModel, Field


class JsonRpcRequest(BaseModel):
    id: int | str
    method: str
    params: dict[str, Any] = Field(default_factory=dict)
    jsonrpc: Literal["2.0"] = "2.0"


class JsonRpcResponse(BaseModel):
    id: int | str
    result: Any
    jsonrpc: Literal["2.0"] = "2.0"


class JsonRpcErrorDetail(BaseModel):
    code: int
    message: str


class JsonRpcError(BaseModel):
    id: int | str
    error: JsonRpcErrorDetail
    jsonrpc: Literal["2.0"] = "2.0"
```

**参考测试**：

```python
# test_protocol_answer.py
import pytest
from pydantic import ValidationError

from protocol_answer import (
    JsonRpcError,
    JsonRpcErrorDetail,
    JsonRpcRequest,
    JsonRpcResponse,
)


def test_request_round_trip():
    req = JsonRpcRequest(id=1, method="tools/list", params={"cursor": None})
    assert JsonRpcRequest(**req.model_dump()) == req
    assert req.jsonrpc == "2.0"


def test_response_round_trip():
    resp = JsonRpcResponse(id="abc", result={"tools": []})
    assert JsonRpcResponse(**resp.model_dump()) == resp


def test_error_round_trip():
    err = JsonRpcError(id=2, error=JsonRpcErrorDetail(code=-32601, message="Method not found"))
    assert JsonRpcError(**err.model_dump()) == err
    assert err.error.code == -32601


def test_wrong_jsonrpc_version_rejected():
    with pytest.raises(ValidationError):
        JsonRpcRequest(id=1, method="tools/list", jsonrpc="1.0")


def test_error_missing_code_rejected():
    with pytest.raises(ValidationError):
        JsonRpcError(id=2, error={"message": "缺 code"})
```

**解析**：

- `jsonrpc: Literal["2.0"] = "2.0"` 一举两得：构造时免填（默认值），反序列化时钉死版本——传入 `"1.0"` 直接被 pydantic 拒掉，`ValidationError` 在业务逻辑之前就把非法输入拦下。这是"防御式解析"在协议层的应用。
- `JsonRpcErrorDetail` 单独建模（而非 `error: dict`），换来字段级校验：缺 `code` 立刻报错。结构越精确，坏数据越早暴露。
- `params` 用 `Field(default_factory=dict)` 而非 `= {}`：可变默认值必须用工厂，否则所有实例共享同一个 dict——这是 pydantic/dataclass 通用的经典坑。

### 第 15 题

**参考实现**：

```python
# review_server.py
from mcp.server.fastmcp import FastMCP

app = FastMCP("review-mcp")


@app.tool()
def add(a: int, b: int) -> int:
    """计算两个整数的和."""
    return a + b


@app.resource("review://notes/{topic}")
def notes(topic: str) -> str:
    """按主题返回复习笔记."""
    return f"{topic} 的复习笔记"


@app.prompt()
def summarize(topic: str) -> str:
    """生成主题总结提示词."""
    return f"请用三句话总结 {topic} 的核心概念。"
```

**参考测试**：

```python
# test_review_server.py
import pytest
from mcp.shared.memory import create_connected_server_and_client_session

from review_server import app


@pytest.mark.asyncio
async def test_tool_add():
    async with create_connected_server_and_client_session(app) as session:
        tools = await session.list_tools()
        assert any(t.name == "add" for t in tools.tools)

        result = await session.call_tool("add", {"a": 2, "b": 3})
        assert not result.isError
        assert result.content[0].text == "5"


@pytest.mark.asyncio
async def test_resource_notes():
    async with create_connected_server_and_client_session(app) as session:
        result = await session.read_resource("review://notes/MCP")
        assert "MCP" in result.contents[0].text


@pytest.mark.asyncio
async def test_prompt_summarize():
    async with create_connected_server_and_client_session(app) as session:
        result = await session.get_prompt("summarize", {"topic": "MCP"})
        assert "总结" in result.messages[0].content.text
```

运行方式（在临时目录中）：

```bash
/d/workspace/autocreatemd/.venv/Scripts/python.exe -m pytest test_review_server.py -q -o addopts=""
```

**解析**：

- **三个装饰器各就各位**：`@app.tool()` 把函数名、docstring、类型注解分别变成工具名、description、input_schema；`@app.resource("review://notes/{topic}")` 的 URI 模板参数 `{topic}` 与函数参数同名自动绑定；`@app.prompt()` 返回的字符串自动包成 PromptMessage。
- **内存内测试的价值**：`create_connected_server_and_client_session` 在单进程内同时拉起 Server 与 Client 并用内存管道连接——不起子进程、不开端口、不联网，完全满足"测试离线可跑"的纪律。注意它是**异步 API**，测试函数必须是 `async def` 且带 `@pytest.mark.asyncio`（依赖 venv 里的 pytest-asyncio）。
- **返回结构要读对**：`call_tool` 返回 `CallToolResult`，文本在 `result.content[0].text`；`read_resource` 返回 `ReadResourceResult`，文本在 `result.contents[0].text`；`get_prompt` 返回 `GetPromptResult`，消息在 `result.messages[i].content.text`。三者的字段名各不相同（content / contents / messages），是官方 SDK 里最容易记混的细节之一。
- 若直接在生产用 stdio 启动这个 Server（`app.run(transport="stdio")`），切记**不能往 stdout print**——stdout 是协议通道。
