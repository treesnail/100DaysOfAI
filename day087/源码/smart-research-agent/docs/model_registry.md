# 模型版本管理与持续微调（M5-D9 / day058）

> 本文是 `smart_research_agent/registry/` 的设计说明，与
> [`scripts/registry_demo.py`](../scripts/registry_demo.py) 的实际输出逐项对应。
> 文中所有数字都是**本课程快照上的实测值**，不是经验估计。
> 复现命令（需要先把包放进 `sys.path`，或 `pip install -e .`）：
>
> ```bash
> cd day058/源码/smart-research-agent
> PYTHONPATH=. python scripts/registry_demo.py
> ```

## 0. 这一课补的是哪半个问题

day048~day057 把"训得出来"做到了极致：数据可复现（`domain_data` 的
`manifest.fingerprint`）、训练可复现（`sft.checkpoint`、`peft` 的
`adapter_content_hash`）、效果可度量（`finetune_eval` 的门禁报告）、
偏好可对齐（`alignment` 的 DPO）。

但它们合起来仍然回答不了一个运维每天都要问的问题：

```text
线上这个效果，是哪一份数据 + 哪一次训练 + 哪一版基座造出来的？
现在有一份新产物，我要不要换？换了出问题怎么退？
```

`registry/` 把这句话拆成五件事：

```text
version.py   三元组与内容寻址的版本键      —— "这是不是同一份产物"
record.py    版本记录与四态流转            —— "它现在是什么状态、能不能部署"
store.py     追加写事件日志 + 折叠         —— "历史是什么，生产版本是谁"
triggers.py  触发器与否决项                —— "现在该不该训"
rollback.py  采纳判定与回滚计划            —— "换不换、退不退、怎么退"
retrain.py   六步流水线                    —— 把上面五件事串成一次可复盘的动作
```

## 1. 三元组：身份是算出来的，不是编号出来的

```text
version_key = sha256(base_model, adapter_sha256, dataset_fingerprint)[:16]
```

实测（demo 第 1 节）：

```text
规范写法：基座 Qwen3-8B | 适配器 sha256:1a2b3c4d5e6f | 数据 3f1b0c9d7e5a2468 | 键 abef9265dd96544e
脏写法  ：基座 Qwen3-8B | 适配器 sha256:1a2b3c4d5e6f | 数据 3f1b0c9d7e5a2468 | 键 abef9265dd96544e
三者相等 True | 键相同 True

  原始     → abef9265dd96544e  适配器 1a2b3c4d5e6f
  换适配器 → 55bc9fa9f8952a71  适配器 5c6d7e8f9012
  换数据集 → c0d0b7c9b0c359c2  适配器 1a2b3c4d5e6f
  换基座   → eb58037eb819dc17  适配器 1a2b3c4d5e6f
```

上表的"脏写法"是 `base_model="  Qwen3-8B  "`、`adapter_sha256="sha256:1A2B…"`、
`dataset_fingerprint` 全大写。三者归一化之后与规范写法**相等且键相同**——
这是"同一份产物只有一个身份"的前提。归一化的三个动作各自都踩过一次坑：
去空白（从终端复制哈希时尾部常带换行）、去 `sha256:` 前缀（日志里印的是带前缀的
形式）、转小写（`hexdigest()` 给小写而人常写大写）。

`abef9265dd96544e` 这类**内容寻址**的代价与收益都很具体：

| | 自增号（`v17`） | 内容寻址（`abef9265…`） |
|---|---|---|
| 可排序 | 是 | 否 |
| 跨机器指向同一份产物 | 不能保证 | 能保证 |
| 键相同 ⇒ 行为逐位相同 | 不成立 | 成立 |

因此**两个都要**：`version_key`（16 位十六进制）是身份，用于比对与去重；
`version`（`1.2.0`）是人类叙事，用于"这是第几版、相对上一版动了什么"。

## 2. 版本号递增：变化的那一项决定递增位

`bump_kind_for` 直接由三元组差异推出递增位，实测（demo 第 2 节）：

| 步骤 | 变化项 | 递增位 | 新版本号 |
|------|--------|--------|----------|
| 首版 | （首版） | minor | v1.0.0 |
| 同数据重训 | `adapter_sha256` | patch | v1.0.1 |
| 换数据集 | `dataset_fingerprint` | minor | v1.1.0 |
| 换基座 | `base_model` | major | v2.0.0 |

第三条看起来最"小"，实际上最重要：**重训是持续微调里最高频的动作**，
把它标成 `minor` 会让版本号迅速失去区分度（v1.9 → v2.0 只因为多跑了一次
同样的数据）。而 `major` 的语义被保留给基座替换——这是唯一一个让"回滚"
都必须重新评估的动作（旧适配器挂不上新基座）。

判定用的是"取最大版本号"而不是"取最后登记的那个"：

```text
next_version(["1.0.0", "1.2.0", "1.1.0"], kind="patch") == "1.2.1"
next_version(["1.9.0"], kind="minor")                   == "1.10.0"
```

第二行是那个隐蔽的陷阱：**字符串排序会把 `1.10.0` 排在 `1.9.0` 前面**，
而是"整数段排序"。`head()` 的实现建立在同一个键上。

## 3. 索引是事件流，不是"版本列表"

`versions.jsonl` 的真实内容（demo 第 3 节）：

```text
  1. type=register version=1.0.0
  2. type=stage    version=1.0.0
     stage=stable reason=首次上线，人工门禁通过
  3. type=register version=1.0.1
```

读的时候把事件折叠成当前状态。为什么不用"读全量 → 改一条 → 写回全量"：

1. **写路径会从 O(1) 变成 O(N)**，而版本数量只会单调增长；
2. **丢失了"什么时候变的、为什么变"**——`stable` 只能说明"现在是 stable"，
   说明不了"它是 3 天前因为候选胜出被提升的，还是刚刚因为回滚被设回来的"；
3. **一次崩溃就可能截断整个文件**：day027 的 `quality_logger` 选 jsonl 的
   理由正是"单行损坏不传染"。

折叠必须**确定**且**对损坏响亮**。五类损坏各自报错（测试逐类钉住），
其中"未知事件类型"最危险：跳过不认识的事件会丢状态，而**丢状态的表现
只是 `head()` 变成 `None`**，查的人根本不会想到是索引里有一行没读懂。

折叠的确定性实测：

```text
折叠后：{'candidate': 1, 'stable': 1, 'rolled_back': 0, 'archived': 0, 'total': 2} | head=1.0.0
重新加载后：{'candidate': 1, 'stable': 1, 'rolled_back': 0, 'archived': 0, 'total': 2} | head=1.0.0 | 键一致 True
版本链（v1.0.1 → 祖先）：['1.0.1', '1.0.0']
可回滚的 stable 祖先：['1.0.0']
```

幂等只覆盖"三元组键与版本号都相同"（CI 重跑同一个任务）。放宽到
"版本号相同就覆盖"是危险的：版本号是**人写的叙事**，两个人给两份不同的
产物写同一个 `1.2.0` 是常有的事，静默覆盖会让索引少掉一份真实产物。
因此"版本号相同但键不同"必须报冲突，且冲突信息里要给出**具体哪些字段不同**。

**实现时踩到的一个真实缺陷**：`_events` 最初只在读盘折叠路径上被填充，
写盘路径只写文件不更新镜像——结果是**同一份操作序列，重载后的 `events()`
有 3 条、写入方的 `events()` 有 0 条**。而"审计流"唯一被消费的地方正是
`events()`（报告与 demo 都读它）。修法是把两条路径统一到同一个
`_append`，这条结论现在被测试钉住。

## 4. 四态流转：两条被明确禁止的边

```text
             register                 promote              prune
（无）──────────────→ candidate ──────────────→ stable ──────────→ archived
                          │                        │
                          │ 回滚 / 拒绝              │ 回滚（退位）
                          └──────────┬─────────────┘
                                     ▼
                                rolled_back
```

两条边的禁止理由都是"允许它就会让某个调用方静默错"：

| 被禁止的迁移 | 允许后的后果 |
|--------------|-------------|
| `stable → candidate` | `head()` 突然返回 `None`，而线上还在跑它；部署脚本大多按"head 一定存在"写 |
| `rolled_back → stable` | 回滚可以被撤销，审计就失去意义——要复活必须**重新登记**（新的适配器哈希 → 新的键 → 新的记录） |

`stable → archived` **是允许的**，但 `prune()` 刻意不去做它：

> **`prune` 只清理候选：`stable` 是回滚目标，归档一个 stable 版本等于删掉一条退路。**

要下线一个 stable 版本，必须显式走 `rolled_back` 或 `archived`——那是一次
有理由的运维动作，而不是磁盘清理的副作用。`head()`（必然是 stable）
永不归档。

## 5. 采纳判定的七个场景（全部实测）

| 场景 | action | gain | 拦在哪一项 |
|------|--------|------|-----------|
| 首次上线（无 current，0.58） | **promote** | 不可比 | 走绝对值门槛：`0.58 >= 0.5` |
| 增益达标 +0.12 | **promote** | +0.1200 | —— |
| 落在死区 +0.01 | hold | +0.0100 | `gain < min_gain (0.02)` |
| 退步 -0.08 | hold | -0.0800 | `CHECK_GAIN` 不通过 |
| 候选缺分数 | hold | 不可比 | `CHECK_METRICS` 不通过 |
| 候选超龄 21 天（504h） | hold | +0.2000 | `CHECK_AGE` 不通过（上限 168h） |
| 候选缺合并产物 | hold | +0.2000 | `CHECK_DEPLOYABLE` 不通过 |

三处设计要点：

1. **首次上线必须是一个单独的分支**。没有任何 stable 版本时增益无从计算，
   若与"有当前版本"共用一条路径，第一版**永远上不了线**；
2. **超龄候选的 gain 照算照报**。报告里要能回答"它明明更好，为什么没换"；
3. **可部署性检查排在最前**。它是唯一一条"证据完整性"检查——
   分数再高也不能上线一个没有产物的版本。

两个数字的含义（`min_gain=0.02`、`regression_tolerance=0.0`）与 day027 的趋势
死区是同一种防抖思想：评估有方差，±0.02 的波动是噪声不是提升。
**没有死区，自动流水线会天天在不同版本之间来回切。**

### 不可比时拒绝算差值（本课的反面教材）

实测同一对版本在两种策略下的判定：

```text
缺省（require_comparable=True）: action=hold gain=未计算
  被拦下：不可比且未达绝对门槛：候选 0.4400 < 0.5
关掉可比性要求               : action=hold gain=-0.1600
  被拦下：增益 -0.1600未达到采纳门槛 0.02；本次差值不可作为提升证据
```

那个 **-0.1600** 既不是提升也不是退步，而是**两种评估分布之差**
（当前 0.6000 在数据集 A 上、候选 0.4400 在数据集 B 上）。
它被算出来之后会被下游当成提升量使用——"同一份数据在两套口径下得到两个
结论，是数据治理最忌讳的事"（day057 原话）。因此缺省策略下
`comparable=False` 的候选**改用绝对值门槛**，而不是算差值。

## 6. 触发器与否决项：两类东西，分开记

```text
trigger：有一个理由支持训练      veto：有一个理由禁止训练
should_retrain = any(trigger.fired) and not vetoed_by
```

条件表（`trigger_table()` 生成，与实现同源）：

| 类别 | 名称 | 阈值 | 含义 | 复核时机 |
|------|------|------|------|---------|
| trigger | `data_growth` | 8 | 自上次训练以来新增的可用样本数达到门槛 | 数据流水线跑完一轮之后 |
| trigger | `dataset_change` | 指纹与生产版本不同 | 数据集被重建（换了清洗口径或补了样本） | `manifest.fingerprint` 更新之后 |
| trigger | `quality_drop` | 0.5 | 线上观测到的合格率低于下限 | 线上评估窗口结束之后 |
| veto | `cooldown` | 24.0 | 距上次训练不足冷却期（**从未训练时不否决**） | 每次判定 |
| veto | `active_run` | 1 | 已有训练任务在跑（两个任务写同一份产物目录会互相覆盖） | 每次判定 |

为什么不能把 veto 写成"触发器的反向条件"（例如再加一个
`cooldown_passed` 要求它 fired）？因为报告里就分不清：

```text
fired = []                            → 没有理由训练        （去看数据与线上评估）
fired = [数据涨了] vetoed_by=[冷却]   → 有理由但时机不允许   （只需要等）
```

两者运维动作完全不同。判定实测（demo 第 6 节）：

```text
[训练]   首次训练（从未训练，全部样本都算新增）    命中 data_growth
[训练]   数据涨 30 条、冷却已过                    命中 data_growth, dataset_change
[不训练] 数据涨 30 条、冷却只过了 2h               命中 data_growth, dataset_change；否决 cooldown
[训练]   数据没涨、线上掉到 0.42                   命中 quality_drop
[不训练] 数据没涨、线上也没掉                      无命中
[不训练] 已有训练任务在跑                          命中 data_growth…；否决 active_run
```

### 缺失一律"不触发、不否决"

- `online_pass_rate=None`（还没跑线上评估）→ **不**触发质量下降；
- `hours_since_last_train=None`（从未训练）→ **不**否决冷却期。

这与 `pass_rate` 返回 `None` 是同一条纪律：**缺失与 0 是两件事**。
把缺失当 0 会让"从未训练过"的仓库被冷却期永久拦住
（`None → 0 < 24 → veto`），而它恰恰是最该训练一次的那种状态。

## 7. 回滚：第一步必须是"确认有退路"

实测计划（demo 第 7 节）：

```text
rollback | 1.0.2 → 1.0.1 | 4 步（阻塞 2） | 上线后拒答率异常升高
  1. [verify] 校验目标 v1.0.1（键 55bc9fa9f8952a71）产物齐全：适配器=True, 合并模型=True（阻塞）
  2. [freeze] 把 v1.0.2 置为 rolled_back（head() 会自动落回上一个 stable，无需反向改写目标版本）（阻塞）
  3. [record] 写入审计事件：原因「上线后拒答率异常升高」（非阻塞）
  4. [observe] 按 24.0h 观察窗口监控 v1.0.1（非阻塞）
```

**`verify` 必须在 `freeze` 之前。** 反过来写也能通过绝大多数测试，
代价只在最坏情况下暴露：

> 先冻结当前版本、再发现目标版本不可部署，结果是**生产上没有任何可服务版本**。

这与 day046/day057 的"顺序即策略"是同一种推理方式——每一步的位置都有理由，
换位只在某些输入下才出错，而那种错误最难在测试里被发现。

回滚**不需要反向改写目标版本**：`head()` 是"最新的 stable"，把出问题的版本
退出 stable 态，它就自动落回上一个 stable。这比"维护一个当前版本指针 +
再把它改回去"少一个状态。

三种情形实测：

| 情形 | 结果 |
|------|------|
| 三个 stable，退到 v1.0.1 | rollback，4 步（阻塞 2） |
| 只有首个 stable | hold，0 步，`should_execute=False` |
| 最近的祖先不可部署 | rollback 到 v1.0.0（**跳过**不可部署的 v1.0.1） |

边界处理的两处细节：`apply_rollback` 拒绝执行 `hold` 计划
（一个 hold 计划被误执行，等于"在没有目标的情况下把生产版本退掉"）；
`stable_ancestors` 跳过不可部署的祖先（一个 `stable` 记录可能只是
"当年提升过"，它的磁盘产物早被清理）。

## 8. 六步流水线：顺序即策略（第四次复用）

```text
verify_data → train → evaluate → gate → register → promote
```

申报理由，每一处都是"换位只在某些输入下出错"：

| 顺序 | 换位后的后果 |
|------|-------------|
| `verify_data` 在最前 | 先花完算力再发现数据没变——这正是触发器要防的事，但触发器看的是**调用方报上来的状态**，可能与磁盘上的数据不一致 |
| `evaluate` 在 `gate` 之前 | 门禁是对评估结果的判定，没有结果就没有判据（只能得到一个"用空指标通过的门禁"） |
| `gate` 在 `register` 之前 | 没通过门禁的候选进表会让版本表堆满"登记了但永远不该上线"的记录，而 `lineage` 会开始被污染（它不看阶段） |
| `promote` 在 `register` 之后 | 反过来会出现"生产指针指向注册表里还没有的版本"，而回滚依赖注册表找祖先 |

端到端实测（demo 第 8 节）：

```text
第一次真实运行：应该重训 | 命中触发器 data_growth, dataset_change | 计划 v1.1.0 | 已训练 True | 生产版本 1.1.0
    [OK] decide       应该重训 | 命中触发器 data_growth, dataset_change
    [OK] plan         计划 v1.1.0（minor，父 1.0.0）| 基座 Qwen3-8B | 数据 aa77c31e90f4b258 | 6 步
    [OK] verify_data  数据集指纹已核对：新增样本 30 条，指纹已变化
    [OK] train        适配器 sha256:5c6d7e8f9012 | step 42 | loss 0.3187
    [OK] evaluate     指标 {'eval_pass_rate': 0.7222, 'train_loss': 0.3187}
    [OK] register     v1.1.0 candidate   键 14dceb829e28ce44 ← 1.0.0 | 合格率 0.7222 | 可部署 True
    [OK] gate         promote | 当前 1.0.0 → 候选 1.1.0 | gain 不可比 | 目标 1.1.0
    [OK] promote      v1.1.0 提升为 stable，观察窗口 24.0h
  head 现在是 1.1.0，trainer 调用次数=1

第二次运行（同一份数据、同一个适配器）：… | 已训练 True | 生产版本 1.1.0
  登记的版本号 1.1.0 | 版本表规模 2
  trainer 调用次数=2
```

第二次运行是三件事的合成结果：

1. **三元组相同 → 复用版本号**（不新占一个），这正是 CI 重试应有的行为；
2. **训练回调仍被调用一次**——流水线无法预知"这次训练会产出什么"
   （它只知道输入，不知道权重）；
3. **复用时若该版本已处于 stable，跳过采纳判定**。此时 current 与
   candidate 是同一条记录，gain 恒为 0，任何 `min_gain` 都会判 hold——
   而那个 hold 会把"它正在服务"这个事实说成"未采纳"。这一条是实现时
   实测出来的：第一版没有这个短路，第二次运行的报告写着"生产版本（未采纳）"。

`RetrainOutcome.promoted` 因此定义为 **"运行结束时该版本是否处于 stable"**，
而不是"本次判定是否 promote"——用阶段定义，两条路径给出同一个答案。

## 9. 与 day057 的接桥

```text
DomainDataManifest.fingerprint = ffa3f96a774809ee
这条版本记录因此可以回答"是哪份数据训出来的"：
  基座 Qwen3-8B | 适配器 sha256:1a2b3c4d5e6f | 数据 ffa3f96a774809ee | 键 9b7fe75ea4d44730
```

`ffa3f96a774809ee` 与 day057 教程里那行"指纹 `ffa3f96a774809ee`（v1）"**逐位相同**，
这就是那座桥：模型版本里的 `dataset_fingerprint` 必须与
`DomainDataManifest.fingerprint` 是同一个值，否则"这个效果是哪份数据训出来的"
这句话在跨天之后就不成立了（两份指纹各自漂移，谁也说不清哪一个才是训练时用的）。

`pipeline_dataset_fingerprint()` 是这座桥的实体，`test_registry_retrain.py`
里有一条**接桥测试**同时断言两处取值一致。

两处为覆盖率做过的**设计调整**，都值得记下来：

1. `verify_data` 从流水线的私有方法提成**模块级函数**。它是唯一一段
   "在触发器已判定应该训练之后仍然会否决训练"的逻辑，端到端路径上
   根本走不到那两条 `raise`（触发器早已把这类状态挡在外面）。

2. `RetrainOutcome.summary_line` 里"有 plan 没 version"的分支**去掉了
   `# pragma: no cover`**：它不是我最初以为的防御式分支，而是 dry_run
   每次都会走的真实路径。

## 11. 三条可以带走的判断

1. **身份要算得出、不要编得出**：内容寻址让"键相同 ⇒ 行为逐位相同"成立，
   自增号给不了这个保证。代价是键不能排序，因此版本号与三元组**两个都要**；
2. **状态变更是事件，不是覆盖写**：`versions.jsonl` 存的是"发生过什么"，
   折叠出"现在是什么"。"什么时候变的、为什么变"与"现在是什么"一样重要——
   而覆盖写会把前者永久丢掉；
3. **把"做不到"显式化**：`feasible`、`should_execute`、`vetoed_by`、
   `missing_artifacts` 都是同一个模式——**一个悄悄违反自己约束的护栏，
   比没有护栏更糟**。回滚没有目标时输出 `hold` + 零步，而不是给一个
   必然失败的计划。
