# M1 - day010：规划模块 Planner —— 先想后做的任务分解艺术

> 阶段标签：M1-D7  
> 学习时长：约 2 小时  
> 前置依赖：day006（ReAct 循环）、day005（LLM 抽象层与 MockLLM）

## 今日目标

过去几天，我们的 SmartResearch Agent 已经能跑完整的 ReAct 循环： Thought → Action → Observation 交替进行，直到得出 Final Answer。但这个循环有一个隐含假设——**模型每走一步都能自己判断"下一步该做什么"**。对于"2+3 等于几"这种一步任务没问题，可一旦面对"调研 RAG 技术并写出对比报告"这样的复杂目标，纯靠边走边想就会失控。

今天我们要回答三个问题：

1. **为什么需要规划**：ReAct 逐步推理在复杂任务上到底输在哪里？
2. **怎么让 LLM 产出可用的计划**：提示词如何设计，输出如何解析与校验？
3. **规划与执行如何协作**：Planner 和 ReactAgent 的职责边界在哪里？

最终产出一个新模块 `smart_research_agent/agent/planner.py`：给定一个用户目标，先用 LLM 拆解成有序子任务列表，再把每个子任务交给已有的 ReAct 循环执行。

## 第一章：为什么需要规划 —— ReAct 的三大困境

### 1.1 先复现问题：让 ReAct 独自面对复杂任务

假设我们把"调研当前主流的 RAG 框架，对比优缺点，写一份选型建议"直接丢给 day006 的 `ReactAgent.run()`。理想情况下模型会这样推进：

```text
Thought: 我需要先搜索主流 RAG 框架有哪些
Action: web_search
Action Input: 主流 RAG 框架 2025
Observation: LangChain、LlamaIndex、Haystack ...
Thought: 接下来查 LangChain 的优缺点
Action: web_search
Action Input: LangChain RAG 优缺点
...
```

但真实运行中，常见的失控模式有三种：

**困境一：迷失方向（Losing the Thread）。** 循环走到第 6 步时，模型已经"沉浸"在 LlamaIndex 的某个 API 细节里，忘了最初的任务是"对比选型"，开始追问无关的实现细节。ReAct 的每一步只看当前上下文做局部决策，**没有一个全局目标在牵引方向**。

**困境二：步骤冗余（Wandering）。** 模型在第 3 步搜了"LangChain 优缺点"，第 7 步又搜了一遍几乎相同的内容——因为它不记得自己已经搜过（短期记忆被截断，或上下文太长注意力稀释）。每一步都是独立决策，**没有一份"已完成清单"告诉它哪些事做过了**。

**困境三：提前收场（Premature Stop）。** 模型查到两个框架的信息后，直接输出 `Final Answer: 推荐 LangChain`——第三个框架根本没查。局部看每一步都"合理"，全局看任务只完成了三分之二。

```text
用户目标: 调研 A、B、C 三个框架并对比选型

ReAct 实际轨迹:
  Step1  查 A ──▶ Step2 查 A 的细节 ──▶ Step3 查 B
     │                                   │
     ▼                                   ▼
  偏题：陷入 A 的                  提前收场：直接给结论，
  实现细节                        C 从未被调查 ✗
```

### 1.2 问题的本质：局部最优 ≠ 全局最优

ReAct 是**贪心策略**：每一步基于当前 Observation 选"看起来最好"的下一个 Action。贪心算法的问题在 Agent 领域同样成立——局部最优的序列拼起来，往往不是全局最优的路径。

人类做复杂任务时不是这样工作的。接到"写一份调研报告"的任务，一个资深研究员的第一反应是**先在纸上列提纲**：

1. 明确调研范围和评估维度
2. 收集候选框架清单
3. 逐个框架收集资料
4. 按维度对比
5. 撰写结论

然后才动手执行，执行中随时对照提纲检查进度。**提纲把"全局目标"显式化了**，它同时解决了三个困境：方向有提纲牵引（困境一）、进度有清单可查（困境二）、完成标准有提纲兜底（困境三）。

Agent 的"提纲"，就是我们今天要实现的**计划（Plan）**。

### 1.3 两种范式：边想边做 vs 先想后做

| 维度 | ReAct（边想边做） | Plan-and-Execute（先想后做） |
|------|------------------|------------------------------|
| 决策时机 | 每步现场决策 | 先全局规划，再逐步执行 |
| 目标感知 | 只有当前上下文 | 有显式的全局计划 |
| LLM 调用次数 | 每步一次 | 规划 1 次 + 每子任务内部若干次 |
| 适合任务 | 短链路、探索性强 | 长链路、结构可预知 |
| 失控风险 | 迷失方向、步骤冗余 | 计划本身可能不合理 |
| 中途纠偏 | 天然灵活（每步可转向） | 需要额外机制（重规划） |

注意最后一行：**Plan-and-Execute 不是免费的午餐**。计划一旦做出就相对固定，如果环境变化（某个子任务失败、发现新信息），僵化的计划反而成为枷锁。所以工业界的成熟方案（如 LangGraph 的 plan-and-execute 模式、BabyAGI）都会配一个 **RePlanner**：每完成一个子任务，对照当前结果重新审视剩余计划，必要时重写。

今天我们实现最基础的"规划 → 执行"骨架，重规划机制留到后续阶段。

> 思考题：既然 ReAct 每步都能转向，为什么还说它"容易迷失方向"？提示：想一想 LLM 的注意力机制和上下文窗口的关系。

### 1.4 规划-执行分离的架构价值

把"规划"从 ReAct 循环里抽出来成为独立模块，不只是为了治好三个困境，更是架构上的一次**关注点分离**（回忆 day001 的工程思想）：

```text
┌─────────────────────────────────────────────────┐
│                  用户目标 (Goal)                  │
└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│  Planner（规划层）                                │
│  职责：把目标拆成有序子任务                        │
│  输入：目标字符串        输出：Plan（子任务列表）    │
└──────────────────────┬──────────────────────────┘
                       ▼ 逐个下发
┌─────────────────────────────────────────────────┐
│  ReactAgent（执行层）                             │
│  职责：用 ReAct 循环完成单个子任务                  │
│  输入：子任务字符串      输出：子任务结果            │
└──────────────────────┬──────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────┐
│  汇总层（后续阶段实现）：合并各子任务结果为最终报告    │
└─────────────────────────────────────────────────┘
```

职责边界非常清晰：

- **Planner 不管怎么执行**：它不知道有 calculator、不知道 ReAct 格式，它只输出"做什么"的清单。
- **ReactAgent 不管怎么拆解**：它收到的就是一个普通任务字符串，至于是用户直接给的还是 Planner 拆出来的，它完全不关心。

这个边界的回报是**可测试性**与**可替换性**：Planner 可以单独用 MockLLM 测拆解质量；执行层换成别的 Agent 实现（比如未来的 function calling Agent），Planner 一行不用改。

### 1.5 规划在 Agent 演进中的位置

把视角拉远，规划能力是 Agent 从"玩具"走向"工具"的分水岭之一：

```text
单体 LLM 问答
    │  无状态、无工具，一轮对话结束
    ▼
ReAct Agent（day006）
    │  有工具、有循环，但每一步都是局部决策
    ▼
Plan-and-Execute（今天）
    │  有全局计划，长链路任务不再失控
    ▼
RePlanner / 多 Agent 协作（后续阶段）
       计划可修订、任务可分工，逼近真实工作流
```

每一层都没有抛弃前一层：Plan-and-Execute 的每个子任务内部跑的还是 ReAct 循环。**Agent 架构的演进是叠加而不是替换**——这也是为什么我们要在 day006 把 ReAct 循环做扎实：它是今天乃至后续所有高层编排的"执行原语"。

## 第二章：任务分解的提示词设计 —— 让 LLM 产出程序能消费的计划

### 2.1 设计目标：输出必须"机器友好"

Planner 的输出不是给人看的散文，而是要被 Python 代码消费的数据结构。这决定了提示词设计的核心目标：**把 LLM 的自由生成能力，约束到程序能稳定解析的窄通道里**。

先看我们的提示词全文（`smart_research_agent/agent/planner.py` 中的 `PLAN_PROMPT`）：

```python
PLAN_PROMPT = """你是一个任务规划器。请把用户目标拆解为有序、可执行的子任务列表。

要求：
1. 每个子任务用一句话描述，动词开头
2. 子任务数量 3~6 个
3. 严格输出 JSON 数组，不要输出其他内容，例如：
["子任务1", "子任务2", "子任务3"]

用户目标：{goal}
"""
```

这个提示词只有寥寥数语，但每一条要求都对应一个具体的工程目的。逐条拆解。

### 2.2 要求一：JSON 数组输出 —— 为什么结构化

假如不约束格式，让模型自由发挥，它很可能输出：

```text
好的！针对这个目标，我建议分三步走：
第一步，先收集资料……
第二步，对比各方案的优缺点……
第三步，撰写报告……
希望对你有帮助！
```

要从这段文字里提取子任务，你得写脆弱的解析逻辑：按"第一步"切分？模型下次写"首先/其次/最后"怎么办？换英文模型输出 "Step 1:" 怎么办？**自然语言的格式熵太高，解析规则永远追不上模型的发挥。**

JSON 数组把这个问题一次性解决：

| 对比项 | 自由文本输出 | JSON 数组输出 |
|--------|-------------|---------------|
| 解析方式 | 正则/启发式，规则脆弱 | `json.loads` 一次到位 |
| 顺序表达 | 依赖"第一步"等词，易乱 | 数组下标天然有序 |
| 边界判断 | 首尾客套话需剔除 | `[` 到 `]` 边界明确 |
| 类型校验 | 无法校验 | 可断言"每个元素是字符串" |
| 跨模型稳定性 | 各模型文风差异大 | JSON 是所有模型的通用语 |

这就是我们在 day006 解析 ReAct 输出时学到的同一个教训的延续：**凡是需要程序消费的 LLM 输出，都要在提示词里显式锁定结构**。ReAct 用 `Thought:/Action:` 标记锁定，Planner 用 JSON 锁定——思路完全一致。

### 2.3 要求二：限定数量 3~6 个 —— 为什么要设上下界

为什么不是"随意拆"？两个方向的风险都要防：

- **拆得太粗（1~2 个）**：`["调研 RAG 技术", "写报告"]`。这样的计划等于没拆，子任务交给 ReAct 后依然会在内部迷失方向——规划的价值归零。
- **拆得太细（20+ 个）**：每个子任务都要起一次 ReAct 循环（一次甚至多次 LLM 调用），成本和延迟爆炸；而且过细的拆分往往把"执行细节"混进了"计划"，本末倒置。

3~6 个是经验值，对应人类"工作记忆容量"式的直觉：一份能一眼看完、每条都有实质内容的提纲。**上限控制成本，下限保证拆解真实发生。**

### 2.4 要求三：动词开头 —— 为什么约束措辞

"动词开头"看起来是文风要求，实际是**可执行性校验的前置条件**：

- "收集 RAG 框架资料" → 动作明确，ReAct 拿到就知道该调用搜索工具。
- "RAG 框架资料" → 名词短语，ReAct 还要先猜"对这份资料做什么"。

子任务最终是要被 `agent.run(step)` 当作任务执行的。**一个可执行的子任务描述，本质上是一个祈使句**。动词开头是最简单的祈使句形式约束。

### 2.5 给出 few-shot 示例

提示词里嵌了一行示例 `["子任务1", "子任务2", "子任务3"]`。这不只是教模型"JSON 长什么样"，还同时传达了三个隐含信息：输出是**扁平数组**（不是嵌套对象）、元素是**字符串**（不是 `{"task": ...}`）、数量级是**个位数**。一个精心设计的示例往往比三条文字规则都管用——这就是 few-shot prompting 的价值。

> 思考题：如果把示例改成 `[{"step": 1, "task": "..."}, ...]` 这样的对象数组，会发生什么？解析代码要怎么改？为什么我们故意选择更简单的字符串数组？

### 2.6 提示词是迭代出来的，不是写出来的

初版提示词很少一次到位。一个务实的迭代流程是：

1. **写初版**：把最核心的约束写清楚（本例中是 JSON 数组）。
2. **跑 10~20 个真实目标**：用不同领域、不同复杂度的目标去试，收集失败案例。
3. **失败分类**：把失败分成"格式错"（没输出 JSON）、"数量错"（拆了 15 个）、"质量错"（子任务是名词短语）三类。
4. **对症下药**：每一类失败对应提示词里补一条针对性约束——我们的"要求 1/2/3"就是这么来的。
5. **回归验证**：新提示词重跑全部历史案例，确认旧的失败被修复且没有引入新失败。

注意第 5 步本质上是**给提示词写回归测试**。`tests/test_planner.py` 里的 `test_parse_json_with_surrounding_text` 就是一个雏形：它把"模型加废话"这个历史失败固化成了永久守卫。当项目进入 M3（评估阶段），我们会把这套做法系统化，形成真正的提示词评估流水线。

> 思考题：既然解析器已经有 `find/rfind` 容错，提示词里"不要输出其他内容"这条要求是不是多余了？提示：容错是兜底，不是鼓励；想一想失败率和 token 成本。

## 第三章：输出解析与校验 —— 防御式解析的四道防线

### 3.1 提示词约束是"软约束"，解析校验是"硬约束"

第二章的提示词写得再严，也只是**请求**模型配合。LLM 是概率模型，它可能：

- 在 JSON 前后加客套话（"好的，这是计划：……请确认"）；
- 输出 Markdown 代码块包裹的 JSON；
- 输出格式合法但内容不对的 JSON（空数组、数字数组）；
- 干脆不输出 JSON。

因此 `parse_plan` 的设计哲学是**防御式解析（Defensive Parsing）**：不信任输入，逐层校验，任何一层不通过就抛出语义明确的异常。完整代码见 [agent/planner.py](../源码/smart-research-agent/smart_research_agent/agent/planner.py)，下面逐段讲解。

### 3.2 第一道防线：定位 JSON 边界

```python
cleaned = text.strip()
start = cleaned.find("[")
end = cleaned.rfind("]")
if start == -1 or end == -1 or end < start:
    raise PlanParseError("输出中未找到 JSON 数组")
```

这段代码处理最常见的不听话：**JSON 外面包了废话**。

- `find("[")` 找第一个左括号，`rfind("]")` 找**最后一个**右括号，截取中间部分。这样 `"好的：["a","b"] 请确认"` 也能正确取出 `["a","b"]`。
- 为什么用 `rfind` 而不是 `find`？考虑模型把计划写成了嵌套或分段的输出，`rfind` 保证我们取到的是**最外层的完整数组**，而不是第一个遇到的小片段。
- `end < start` 这个检查防的是病态输入，比如 `"] 没有数组 ["`——两个字符都在，但顺序反了，直接截取会得到空串或乱码。先判序再截取，是边界处理的基本功。

### 3.3 第二道防线：JSON 语法解析

```python
try:
    data = json.loads(cleaned[start : end + 1])
except json.JSONDecodeError as exc:
    raise PlanParseError(f"JSON 解析失败: {exc}") from exc
```

截取出的片段不一定是合法 JSON：可能有尾随逗号、单引号、未闭合的字符串。用 `json.loads` 这个**权威解析器**来判，而不是自己写正则猜。

注意异常链 `from exc` 的用法：抛出的 `PlanParseError` 保留了原始 `JSONDecodeError` 作为 `__cause__`。调用方捕获到的是语义化的业务异常，调试时又能顺着异常链看到底层原因——**对使用者友好，对调试者也友好**。

### 3.4 第三道防线：类型与结构校验

```python
if not isinstance(data, list) or not all(isinstance(s, str) for s in data):
    raise PlanParseError("输出必须是字符串数组")
```

`json.loads` 成功不代表内容符合契约。`'{"a": 1}'` 是合法 JSON，`[1, 2, 3]` 也是合法 JSON，但都不是"字符串数组"。这一层校验的是**业务契约**：计划必须是若干条字符串描述。

这呼应了第二章的思考题——我们选字符串数组而非对象数组，让这一行 `all(isinstance(s, str) ...)` 就能完成校验。结构越简单，校验越可靠。

### 3.5 第四道防线：语义校验

```python
if not data:
    raise PlanParseError("计划不能为空")
```

`[]` 通过了前面所有校验，但它是一份"什么都不做"的计划，交给执行层毫无意义。这是**语义层面**的校验：语法对、类型对，但业务上无意义。

四道防线合起来，形成了一个从外到内的过滤漏斗：

```text
原始 LLM 输出
    │
    ▼ [防线1] 能找到 [...] 边界吗？        ──否──▶ PlanParseError("未找到 JSON 数组")
    ▼ [防线2] 是合法 JSON 吗？             ──否──▶ PlanParseError("JSON 解析失败: ...")
    ▼ [防线3] 是字符串数组吗？             ──否──▶ PlanParseError("必须是字符串数组")
    ▼ [防线4] 非空吗？                     ──否──▶ PlanParseError("计划不能为空")
    ▼
list[str] 子任务列表（可信，可直接消费）
```

### 3.6 为什么自定义 PlanParseError 并继承 ValueError

```python
class PlanParseError(ValueError):
    """计划输出解析失败."""
```

两个设计点：

1. **自定义异常类型**让调用方能精确捕获："是计划解析失败"与"是 LLM 网络超时"是两类完全不同的问题，未来的重试/重规划逻辑只该捕获前者。
2. **继承 ValueError** 而非直接继承 Exception：解析失败的本质是"值不合法"，继承 ValueError 让旧的 `except ValueError` 代码也能兜住它，向后兼容。

这个模式和 day006 的 `ReActParseError(ValueError)` 完全一致——项目内同类问题用同类的处理方式，这就是代码规范的"一致性"价值。

### 3.7 两个解析器的对照：同一种思想，两种形态

项目里现在有两个输出解析器，值得放在一起看：

| 维度 | `parse_react_output`（day006） | `parse_plan`（day010） |
|------|-------------------------------|------------------------|
| 目标格式 | `Thought:/Action:` 标记文本 | JSON 数组 |
| 解析工具 | 正则表达式 | 边界截取 + `json.loads` |
| 容错点 | 多行 Thought、字段顺序 | JSON 前后的废话 |
| 失败异常 | `ReActParseError` | `PlanParseError` |
| 异常基类 | `ValueError` | `ValueError` |
| 校验层次 | 字段存在性 | 边界 → 语法 → 类型 → 语义 |

底层是同一条原则：**LLM 的输出是"不可信输入"，和来自用户的表单、来自第三方 API 的响应一样，必须经过显式校验才能进入系统内部。** 只不过传统系统的不可信输入要防的是恶意攻击，LLM 输出要防的是概率性的格式漂移。

> 思考题：`parse_plan` 现在对 Markdown 代码块（`` ```json [...] ``` ``）也能正确解析吗？为什么？提示：走一遍 `find("[")` 的逻辑。

## 第四章：Planner 与 ReactAgent 的协作 —— 编排关系与职责边界

### 4.1 Planner 类的完整形态

```python
class Planner:
    """任务规划器：plan() 先行拆解，子任务交给执行层."""

    def __init__(self, llm: BaseLLM):
        self.llm = llm

    def plan(self, goal: str) -> Plan:
        logger.info("开始规划目标: %s", goal)
        raw = self.llm.chat([Message(role="user", content=PLAN_PROMPT.format(goal=goal))])
        steps = parse_plan(raw)
        logger.info("拆解出 %d 个子任务", len(steps))
        return Plan(goal=goal, steps=steps)
```

三个细节值得注意：

**（1）依赖注入 BaseLLM。** `Planner.__init__` 接收的是抽象基类 `BaseLLM`，不是具体实现。这意味着生产环境注入 `OpenAICompatibleLLM`，测试注入 `MockLLM`，Planner 本身完全不知道差异——这是 day005 建立的依赖倒置原则的直接红利。

**（2）Plan 是显式的数据契约。**

```python
@dataclass
class Plan:
    """一份拆解完成的计划."""

    goal: str
    steps: list[str] = field(default_factory=list)
```

为什么不用 `plan()` 直接返回 `list[str]`？因为 `Plan` 保留了 `goal`——下游汇总结果时需要知道"这份计划是为哪个目标做的"。数据结构里多带一点上下文，调用链下游就少一分猜测。**让数据自描述，是模块间契约设计的好习惯。**

**（3）规划是一次性调用。** `plan()` 只调一次 LLM，没有循环。规划的"思考"成本被压缩到一次请求里，复杂的多步推理留给执行层的 ReAct 循环——**各层用各自合适的方式调用 LLM**。

### 4.2 协作时序：规划前置，逐个执行

Planner 与 ReactAgent 的完整协作时序：

```text
调用方            Planner              LLM              ReactAgent           Tool
  │  goal           │                   │                  │                  │
  │───────────────▶│                   │                  │                  │
  │                │  PLAN_PROMPT       │                  │                  │
  │                │──────────────────▶│                  │                  │
  │                │  JSON 数组          │                  │                  │
  │                │◀──────────────────│                  │                  │
  │                │ parse_plan 校验     │                  │                  │
  │   Plan         │                   │                  │                  │
  │◀───────────────│                   │                  │                  │
  │                                                                     │
  │  for step in plan.steps:                                          │
  │    step[1] ───────────────────────────────────────▶│                  │
  │                                                     │  ReAct 循环     │
  │                                                     │────────────────▶│
  │                                                     │  Observation    │
  │                                                     │◀────────────────│
  │    result[1] ◀────────────────────────────────────│                  │
  │    step[2] ───────────────────────────────────────▶│   ……             │
```

关键读法：

- **规划在整个执行开始之前完成**，且只发生一次（这就是"前置"的含义）。
- 子任务是**串行下发**的：一个子任务的 ReAct 循环跑完、拿到结果，再启动下一个。串行保证后面的子任务可以利用前面的结果（未来的汇总层会用到这一点）。
- ReactAgent 收到的每个子任务就是一个**普通字符串**，与它直接从用户那里收到任务没有任何区别。

### 4.3 职责边界对照表

| 关注点 | Planner | ReactAgent |
|--------|---------|-----------|
| 输入 | 用户目标（粗粒度） | 单个子任务（细粒度） |
| 输出 | `Plan`（子任务列表） | 子任务答案（字符串） |
| LLM 调用次数 | 恰好 1 次 | 每子任务 1~max_steps 次 |
| 知道工具的存在吗 | 不知道 | 知道（通过 ToolRegistry） |
| 输出格式约束 | JSON 数组 | Thought/Action/Final Answer |
| 解析器 | `parse_plan` | `parse_react_output` |
| 失败语义 | `PlanParseError`（计划不可用） | 达到最大步数（执行未完成） |

这张表是判断"新功能该放哪层"的尺子：和"拆任务"有关的进 Planner，和"用工具完成具体一件事"有关的进 ReactAgent，谁也不越界。

### 4.4 为什么不让 ReactAgent 自己拆任务

一个自然的疑问：为什么不直接在 ReAct 的系统提示词里加一句"复杂任务请先自己拆解"？

三个理由：

1. **关注点混在一起会互相干扰**。ReAct 循环的上下文里塞着 Thought/Action/Observation，再混入规划信息，模型的注意力被稀释，两件事都做不好。分开后，规划时专注全局，执行时专注局部。
2. **计划需要被程序检查**。内嵌在 ReAct 里的"隐式拆解"存在于模型的脑子里，程序无法读取、无法展示给用户确认、无法在失败时定位是哪一步计划有问题。显式的 `Plan` 对象是可观察、可审计的。
3. **规划策略可以独立演进**。今天我们用最简单的"一次调用出全计划"，明天可以换成带反思的规划（先出草稿再自我 critique）、分层规划（大目标→阶段→任务）。因为 Planner 是独立模块，这些演进都不会波及执行层。

### 4.5 子任务之间的上下文怎么传递

当前架构里子任务是串行执行、彼此独立的：子任务 2 的 ReAct 循环看不到子任务 1 的结果。这对"查 A、查 B、查 C"这类**可并行的收集型任务**没问题，但对"先收集资料，再基于资料写总结"这类**有数据依赖的任务**就不够了。

解决思路有几种，复杂度递增：

1. **结果拼接**：把前面子任务的结果文本追加到下一个子任务的描述里，例如 `"撰写报告。已知资料：{前面所有结果}"`。简单有效，但结果文本可能很长。
2. **短期记忆共享**：让各子任务的 ReAct 循环共享一个 `ShortTermMemory`（day008），天然看到彼此的历史。代价是上下文膨胀，需要截断策略配合。
3. **长期记忆检索**：把每个子任务的结果 `remember()` 进 `LongTermMemory`（day009），下一个子任务执行前按需 `recall()`。最优雅，也最复杂。

今天我们先做到第 0 步——子任务独立执行。这正是把记忆系统安排在规划之前（day008/009 先于 day010）的原因：**基础设施先行，编排策略才有逐步升级的地基。**

> 思考题：如果某个子任务执行失败了（比如搜索工具超时），当前架构会发生什么？一个健壮的系统应该怎么处理？这就是 RePlanner 要解决的问题。

### 5.3 端到端测试：用 MockLLM 演练完整规划流程

`tests/test_planner.py` 分两组，分别测试解析函数和 Planner 类。

**解析函数组**——把第三、四章讲的四道防线逐一验证：

```python
class TestParsePlan:
    def test_parse_clean_json(self):
        assert parse_plan('["查资料", "写总结"]') == ["查资料", "写总结"]

    def test_parse_json_with_surrounding_text(self):
        text = '好的，这是计划：\n["步骤一", "步骤二", "步骤三"]\n请确认。'
        assert parse_plan(text) == ["步骤一", "步骤二", "步骤三"]

    def test_no_json_raises(self):
        with pytest.raises(PlanParseError, match="JSON"):
            parse_plan("没有任何数组")

    def test_empty_array_raises(self):
        with pytest.raises(PlanParseError, match="空"):
            parse_plan("[]")

    def test_non_string_items_raise(self):
        with pytest.raises(PlanParseError):
            parse_plan("[1, 2, 3]")
```

注意 `test_parse_json_with_surrounding_text`：它直接验证了 `find/rfind` 容错逻辑的价值——即使模型在 JSON 前后加了废话，解析依然成功。**每一条防线都对应一个测试，防线才不是摆设。**

**Planner 类组**——用 MockLLM 驱动端到端流程：

```python
class TestPlanner:
    def test_plan_end_to_end(self):
        llm = MockLLM(responses=['["收集资料", "对比方案", "撰写报告"]'])
        plan = Planner(llm=llm).plan("调研 RAG 技术")
        assert plan.goal == "调研 RAG 技术"
        assert plan.steps == ["收集资料", "对比方案", "撰写报告"]

    def test_invalid_llm_output_raises(self):
        llm = MockLLM(responses=["我不知道怎么拆解"])
        with pytest.raises(PlanParseError):
            Planner(llm=llm).plan("任意目标")
```

`test_plan_end_to_end` 走的是完整链路：`Planner.plan` → 拼提示词 → `llm.chat` → `parse_plan` → 构造 `Plan`。MockLLM 让这个测试**完全离线、完全确定**——这正是 day005 设计 MockLLM 时承诺的价值，今天兑现了。

`test_invalid_llm_output_raises` 则验证失败路径：模型不听话时，Planner 不是返回一个坏计划，而是抛出明确异常。**测试要同时覆盖" happy path "和" sad path "**，后者在 LLM 应用里尤其重要——模型的失败输出不是小概率事件，而是常态。

### 5.4 把规划和执行串起来：执行器的最简形态

有了 Planner 和 ReactAgent，串起来的编排逻辑薄得像一层纸——核心就是三行：

```python
plan = planner.plan(goal)          # 第一步：规划前置
for step in plan.steps:            # 第二步：逐个下发
    agent.run(step)                # 第三步：ReAct 执行
```

这层编排今天先不进入工程源码，而是作为课后编程题（见[习题](../习题/习题.md)第 10 题）由你亲手实现并测试——它非常适合用来检验你是否真正理解了第四章的职责边界：执行器只做"遍历与传递"，不加任何规划逻辑，也不碰任何工具细节。

写的时候留意三个工程细节：

- **每个子任务用独立的 ReactAgent 还是复用同一个？** 复用意味着 `history` 会跨子任务累积，当前实现下建议每子任务新建，保持隔离。
- **结果要收集**：`agent.run(step)` 的返回值存进列表，最终和 `plan.goal` 一起返回，调用方才能汇总。
- **异常要不要中断整个计划？** 这是最贴近生产的决策点——中断简单但脆弱，跳过灵活但需要标记失败状态。编程题里我们会对比两种策略。

## 第六章：今日总结 —— 规划模块的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 规划-执行分离 | 关注点分离；局部最优 ≠ 全局最优 | `agent/planner.py` 独立于 `react_agent.py` |
| JSON 数组输出 | 程序消费的输出必须结构化、低格式熵 | `PLAN_PROMPT` 要求 3 |
| 限定 3~6 个子任务 | 上限控成本，下限保拆解真实发生 | `PLAN_PROMPT` 要求 2 |
| 动词开头 | 子任务本质是祈使句，要可直接执行 | `PLAN_PROMPT` 要求 1 |
| find/rfind 边界截取 | 对"JSON 外包废话"的容错 | `parse_plan` 防线 1 |
| 四道防线分层校验 | 防御式解析：语法 → 类型 → 语义 | `parse_plan` |
| `PlanParseError(ValueError)` | 语义化异常 + 向后兼容 | `agent/planner.py` |
| 依赖注入 BaseLLM | 依赖倒置，测试用 MockLLM 离线驱动 | `Planner.__init__` |
| Plan 携带 goal | 数据自描述，下游不用猜上下文 | `Plan` dataclass |

今天埋下的两个伏笔，后续阶段会回收：

- **汇总层**：各子任务的结果如何合并成最终报告？这需要短期记忆（day008）把子任务结果串起来。
- **重规划（RePlanner）**：子任务失败或环境变化时如何修订计划？这是 Plan-and-Execute 架构走向生产可用的关键一步。
