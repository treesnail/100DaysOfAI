## 第一部分：选择题

### 第 1 题 —— B

两段召回各对应一个名单（`retrieval.ids()` 与 `context.citations`）：

```text
retrieved_recall = 1.0   检索交出的名单里有全部金标准      → 不是"检索漏了"
packed_recall    = 0.5   进了提示词之后只剩一半            → 有一条被预算丢在尾部
```

`A` 错（那会让 `retrieved_recall` 也小于 1）；`C` 错（生成器不参与"进不进提示词"这件事——它只收到打包好的上下文）；`D` 错（漂移会让召回**可能**变少，但它进的是 `index_state.drift` 与 `notes`，不会制造"检索全中、提示词只剩一半"这种形状）。这一条正是本课新增的那个指标（`METRIC_PACKED_RECALL`）与 `CaseOutcome.packed_away` 要捕捉的失败。

### 第 2 题 —— C

`grounded_rate`（越高越好）与 `hallucination_rate`（越低越好）在 `METRIC_DIRECTIONS` 里的方向相反：

```python
METRIC_GROUNDED_RATE: DIRECTION_HIGHER_BETTER
METRIC_HALLUCINATION_RATE: DIRECTION_LOWER_BETTER
```

`A` 与 `B` 同向（都是 higher_better）；`D` 里 `llm_call_rate` 是 `neutral`（**不判方向**），与 `fallback_rate`（lower_better）不是"相反"而是"一个不判、一个判"。

### 第 3 题 —— C

```python
METRIC_LLM_CALL_RATE: DIRECTION_NEUTRAL   # 只做描述
```

它下降有两种完全相反的读法：检索为空时按护栏不调模型（设计如此，是好），或者该调没调（是真故障）。硬安一个方向会制造一类"看起来像回归、其实是设计"的误报——而误报的代价是门禁被关掉。它**仍然进基线、进报告、进差值表**（`D` 错），只是不参与回归判定；真正的异常由 `fallback_rate` / `bad_case_rate` 报出来。

### 第 4 题 —— B

`hallucination_rate` 与 `fallback_rate` 在健康系统上的基线**就是 0**。若照抄性能基线的比值口径，`current / baseline` 在 0 基数下没有定义——day046 的处理是**跳过这条指标**，而"跳过"意味着 `0 → 0.20` 这种"从零变坏"永远不被发现。差值没有这个问题：`0.00 → 0.20` 就是 +0.20，直接与容忍度（缺省 0.05）比。

`A` 与 `C` 都是错的理由（差值不是"更快"，比例之外的类型理论上也能用比值）；`D` 错（差值同样需要容忍度——它就是"允许变差多少"）。

### 第 5 题 —— B

方向 `higher_better`、`delta = 0.76 - 0.80 = -0.04`：

```text
|delta| = 0.04 > dead_band 0.02          → 不是噪声，进入判定
变化方向是"差"（higher_better 且 delta < 0）→ 看容忍度
|delta| = 0.04 <= 容忍度 0.05            → unchanged
```

实测（第 17 题第 3 种情形）：

```text
质量未回归：6 条用例，改善指标 无明显变化；接地率 0.8000 → 0.7600
deltas: ['＝ grounded_rate: 0.8000 → 0.7600（-0.0400）[higher_better]']
```

选 `A` 的错法正是"容忍度只对变差生效"这条语义没读进去；选 `C` 是最容易犯的写错方式（第一版实现就把它记成 improved，见教程 4.4 节）。

### 第 6 题 —— B

`index_version` 是**条件**，`prompt_version` 是**自变量**：

```python
if current.k != self.baseline.k:               reasons.append("口径变了：…")
if current.index_version != self.baseline.index_version: reasons.append("条件变了：…")
if current.samples < self.min_samples …:        reasons.append("样本不足：…")
# prompt_version 不同 → 进 variables，不阻塞
```

`A` 会进 `variables`（A/B 就是要换它）；`C` 与 `D` 不阻塞（用例数只是变量，标签分布是结论的一部分）。

## 第二部分：简答题

### 第 7 题

因为**这两种读数服务两种读者**：

```text
比例（packed_recall 0.5）  进报告与基线：它要能跨批次比较、能做均值与回归判定
条数（packed_away = 1）    进排查清单：它要被当成一句待办读完——"这一批有 1 条依据被预算丢在尾部"
```

报告里"99% 召回"这类比例很难直接变成一个动作，而"丢掉 3 条依据"可以。这与 day066 把四个 `dropped_*` 分成四个**数**（而不是一个比例）是同一条纪律：**数字要落到一个可执行的下一步动作上**。

另外，条数是可以从比例反推的（`packed_away = (retrieved.recall - packed.recall) × len(relevant)`），因此它不需要额外存储——多存一份就多一处可能与比例分家的副本。

### 第 8 题

风险是**同一份账出现两个互相矛盾的读数**。归因的理由字符串里会写"检索召回 0.5000"，而这个数字来自 `CaseOutcome.retrieved.recall`（由 `measure_ids` 在运行期算好并校验过值域）。如果归因内部重算一遍：

- 算法的实现位置变了两处（一次改动只改了一处 → 两个数字在某个版本后不再一致）；
- 参数可能不同（归因用的是自己的 `k`，而 `StageMetrics` 用的是评估的 `k`）；
- 边界处理可能不同（金标准为空、名单为空、重复 id）。

于是报告里会出现"指标表说召回 0.5、归因说召回为 0"这类情形——**而两个互相矛盾的读数比一个错读数更坏**：读的人无法判断该信哪一个，往往会去信那个更符合直觉的（通常是错的），并且会开始怀疑整份报告。这与 `GroundingReport.given` 是"算出来的而不是存下来的"是同一种纪律的两个方向：能算的不要存，**但算的位置只能有一处**。

### 第 9 题

`ok = conclusive and not regressions` 防的是**"在数据不足时装作有结论"**。

`not regressions` 这个更宽松的定义下，只要没有任何指标超阈值就返回 `True`。而"不下结论"的三种情形（样本不足 / `k` 口径变了 / `index_version` 变了）**恰好都不会产生回归项**：样本不足时统计量本来就不可信；口径变了时两侧的数字根本不可比；换了索引时后一批数字的起点已经不同。于是旧的写法会给这三种情形一个**绿灯**。

真实场景：某天评测集因为数据清洗从 6 条变成 2 条，CI 里的质量门禁拿到 `ok=True` 并放行——而实际上那天系统质量可能已经劣化，只是**没有足够的样本去发现它**。今天改成 `ok=False` + `conclusive=False`，CI 会拦下这次发布并把 `reasons` 打印出来（"样本不足：当前 2 条、基线 6 条，低于下限 3"），处置动作从"发布"变成"补样本"。

### 第 10 题

`RagEvalReport.limitations` 直接搬 `retrieval.RETRIEVAL_LIMITATIONS`，理由是**两份清单一定会分家**：

评估层看到的"接地率 1.0000"这个数字，全部来自 day066~day069 那条链路——因此"这个数字在什么范围内成立"由**链路那一边**的边界决定。若评估层另写一遍：

```text
上游改了边界（例如换掉拒答检测的实现）  → 上游清单更新，评估层的副本不动
结果：报告里的"适用范围"说着一件已经不再成立的事
```

而这两条边界对 `grounded_rate` 有**直接**影响：

1. **"接地校验只做引用编号层面的核对"**：`grounded` 只说明"答案里的 `[n]` 与那次提示词的编号对得上"，**不说明这句话忠实于片段**。因此"接地率 100%"绝不能被读成"答案都对"——这句话必须跟着每一个接地率一起被打印出来。
2. **"拒答检测靠固定句式（`DECLINE_MARKERS`）"**：一个模型换一种说法拒答（或换了不要求该句式的模板），检测就失效——那一条会从"模型自己说没有"变成一次普通生成，从而**抬高**接地率的分母或改变结论。这条边界的代价是"宁可漏检，不可误判"，而读报告的人必须知道它。

### 第 11 题（干净用例）—— 归因结果是 `None`

```text
    retrieved: retrieved（3 条）：recall 1.0000、precision 0.3333、reciprocal_rank 1.0000、ndcg 1.0000
    packed:    packed（3 条）：recall 1.0000、precision 0.3333、reciprocal_rank 1.0000、ndcg 1.0000
```

12 条判据逐条落空的原因（点出六条即可）：

```text
① no_data             empty_reason 是空串（不是 "no_data"）
② retrieval_empty     empty_reason 是空串（非空检索没有"原因"）
③ retrieval_miss      retrieved.recall = 1.0 ≠ 0.0
④ rerank_cut          dropped_by_rerank = 0
⑤ packed_away         packed.recall (1.0) == retrieved.recall (1.0) → 没有丢
⑥ rank_bad            packed.recall = 1.0 但 packed.reciprocal_rank = 1.0（没低于下限 0.5）
⑦ truncated_chunk     truncated_hits = 0（且覆盖率也不低）
⑧ generation_fallback fallback_reason 是空串（没有回退）
⑨ hallucinated_citation hallucinated = 0
⑩ ungrounded          grounded = True（require_grounded 打开也不触发）
⑪ low_coverage        coverage = 1.0 ≥ 下限 0.5
⑫ weak_faithfulness   faithfulness 为 None（这次没评）
```

**注意 ⑫ 的含义**：`faithfulness=None` 不是"忠实度为 0"，而是"这次没量"。因此一条**没评忠实度**的用例会被判为干净——这是刻意的（判据只对它拿到的数字负责），但也是报告要如实展示 `notes` 的原因：那一批的忠实度均值里不能混进看不见的空洞。

### 第 12 题（预算丢掉依据）—— `packed_away`

实测：

```text
12) 预算丢掉依据 → packed_away
    原因： 金标准被预算丢在了提示词之外：检索召回 1.0000，进了提示词之后只剩 0.5000
          （丢掉 1 条依据，dropped_hits=2）——检索是对的，模型却看不到那一条
    动作： 调 retrieval_max_context_chars / retrieval_per_hit_chars：这条是预算的错，不是检索或生成的错
    packed_away = 1
```

**为什么不是 `retrieval_miss`**：`retrieved.recall = 1.0`（两条金标准 `c-1` 与 `c-3` 都在检索名单里），判据 ③ 要求 `retrieved.recall == 0.0` 才触发。也不会是 ④（`dropped_by_rerank = 0`）。

动作落在**两个配置项**上：

```text
retrieval_max_context_chars   整包的预算（放不下时从尾部丢）
retrieval_per_hit_chars       单条片段的上限（超了会截断，也是"依据变半截"的成因）
```

顺带一个算术核对：`packed_away = (1.0 - 0.5) × 2 = 1`，与"丢掉 1 条依据"一致；而 `dropped_hits = 2` 比它大——因为预算丢掉的是**尾部两条命中**，其中只有一条是金标准。**两个数字都要看**：`dropped_hits` 说预算有多紧，`packed_away` 说这次是否伤到了依据。

### 第 13 题（幻觉引用）

实测：

```text
13a) 幻觉引用 → hallucinated_citation
13b) 一个编号都没引用 → ungrounded
```

1. **标签是 `hallucinated_citation`**：`hallucinated = 1`（即 `invalid` 非空）。注意它排在 ⑩ `ungrounded` 之前——两者同时成立时（本例 `grounded = False` 也成立），**先报更有信息量的那一个**：幻觉引用点出了具体是哪个编号。
2. **`grounded` 为 false** 是由定义决定的：`grounded = valid 非空 且 invalid 为空`。本例 `valid_count = 2`（非空）但 `hallucinated = 1`（非空）→ `False`。
3. 把 `valid_count` 改成 0、`hallucinated` 改成 0（即 `cited = 0`、`unused_count = 3`、`coverage = 0.0`）之后：

```text
标签变成 ungrounded（判据 ⑩）
原因：答案没有任何有效引用（valid 为空、invalid 也为空）——这份答案无法被片段核对
```

两条的处置动作**完全不同**：⑨ 是"收紧提示词里的引用要求，或换更强/别家的模型"（因为模型编了一个编号），⑩ 是"先看提示词是否明确要求 `[n]` 引用，再考虑打开 `retrieval_require_citation`"（因为模型一个编号都没写）。这正是"只给一个标签"那条纪律的收益。

### 第 14 题（生成侧回退）—— `generation_fallback`

实测：

```text
14) 生成侧回退 → generation_fallback
    动作： 查提供方（超时/限流/密钥）；装配层可加退避重试，
          但不要在评估里静默重试——那会让这一条用例的失败被抹掉
```

- 动作来自 `FALLBACK_ACTIONS[FALLBACK_REASON_LLM_ERROR]`，属于**生成族**的处置：查提供方、必要时在装配层加重试（但**不要在评估里静默重试**，那会把一次失败从账上抹掉）。
- **为什么不该归因成 `ungrounded`**：判据 ⑧ 排在 ⑩ 之前，而它的依据是 `fallback_reason = "llm_error"` 这个**封闭值**——它说明"这次答案不是模型给的"，因此"有没有引用"根本无从谈起（`llm_called = False`，连一次调用都没成功）。把它记成 `ungrounded` 会指向一个错误的方向：读的人会去改提示词的引用要求，而真正要修的是提供方连通性。

这四道题合起来也演示了**归因的顺序纪律**：同样是 `grounded = False`，三种成因（幻觉引用 / 没引用 / 走了回退）拿到三个不同的标签与三份不同的动作。

**三个数字的解释**（第 16 题第 3 问）：

1. **`retrieval_precision` 为什么升到 1.0000**：精确率 = `|前 k 条 ∩ 金标准| / |前 k 条里实际给出的条数|`。`top_k=1` 时每条的名单只有 1 条，而这份语料里排第一的恰好总是金标准 → `1/1 = 1.0`。它衡量的是"端上来的盘子里有多少是要的"，盘子变小了，比例自然升高。
2. **`retrieval_recall` 为什么没有下降**：评测集是"5 条各 1 个金标准 + 1 条有 2 个金标准（其中 1 个本来就排在第 2 名之外）"。
   ```text
   baseline（top_k=5，名单 5 条）：recall 逐条 = 1,1,1,1,1,0.5   → 均值 5.5/6 = 0.9167
   top1   （top_k=1，名单 1 条）：recall 逐条 = 1,1,1,1,1,0.5   → 均值 5.5/6 = 0.9167
   ```
   那 5 条单金标准的用例里金标准都排第 1，缩到 1 条也不丢；有 2 个金标准的那条本来就只召回 1 个（0.5），再缩也还是 0.5。**于是召回一动不动**。
3. **在什么语料下 `retrieval_recall` 会下降**：只要存在"金标准排在第二名及之后"的用例。例如把上一条用例改成两个金标准都排在前 2 名（第 1、2 名各一个），`top_k=1` 就只剩第 1 名 → 该条 recall 从 1.0 掉到 0.5，整体均值从 1.0000 掉到 0.9167。**结论**：召回率对 `top_k` 的敏感度取决于"金标准在名次上的分布"，而不是名单长度本身——这也说明为什么调 `top_k` 之前要先看 `dropped_by_top_k` 这个数字。

### 第 17 题（验证门禁）

```python
"""day071 第 17 题参考解：只用基线与守卫，验证四种情形（不跑任何用例）."""

from smart_research_agent.rag_debug import (
    QUALITY_METRICS,
    RagBaseline,
    RagBaselineGuard,
)


def baseline(**overrides) -> RagBaseline:
    rows = {name: 0.5 for name in QUALITY_METRICS}
    rows.update(overrides.pop("metrics", {}))
    payload = {
        "label": overrides.pop("label", "demo"),
        "samples": overrides.pop("samples", 6),
        "k": overrides.pop("k", 3),
        "metrics": rows,
        "index_version": "idx-1",
    }
    payload.update(overrides)
    return RagBaseline(**payload)


base = baseline(metrics={"grounded_rate": 0.5, "hallucination_rate": 0.0})
guard = RagBaselineGuard(base, min_samples=3)

print("1) 改善：", guard.compare(baseline(metrics={"grounded_rate": 0.9, "hallucination_rate": 0.0})).summary_line())
print("2) 回归（0 基数）：", guard.compare(baseline(metrics={"grounded_rate": 0.5, "hallucination_rate": 0.2})).summary_line())
within = RagBaselineGuard(baseline(metrics={"grounded_rate": 0.8}), min_samples=3).compare(
    baseline(metrics={"grounded_rate": 0.76})
)
print("3) 变差但在容忍度内：", within.summary_line())
print("   deltas:", [item.summary_line() for item in within.deltas if item.metric == "grounded_rate"])
inconclusive = guard.compare(baseline(k=5, metrics={"grounded_rate": 0.5, "hallucination_rate": 0.0}))
print("4) 不下结论：", inconclusive.summary_line(), "| ok =", inconclusive.ok)
tiny = guard.compare(baseline(samples=2, metrics={"grounded_rate": 0.5, "hallucination_rate": 0.0}))
print("5) 样本不足：", tiny.summary_line(), "| ok =", tiny.ok)
```

实测输出（原文照录）：

```text
1) 改善： 质量未回归：6 条用例，改善指标 grounded_rate；接地率 0.5000 → 0.9000
2) 回归（0 基数）： 质量回归 1 项：hallucination_rate 0.0000 → 0.2000（+0.2000，超出容忍度 0.05）
3) 变差但在容忍度内： 质量未回归：6 条用例，改善指标 无明显变化；接地率 0.8000 → 0.7600
   deltas: ['＝ grounded_rate: 0.8000 → 0.7600（-0.0400）[higher_better]']
4) 不下结论： 不下结论（6 条用例）：口径变了：k 从 3 变成 5（前 3 条与前 5 条不是同一件事，两边的指标不可比） | ok = False
5) 样本不足： 不下结论（2 条用例）：样本不足：当前 2 条、基线 6 条，低于下限 3（两条用例不足以宣告回归） | ok = False
```

**"0 基数"那一问的答案**：

- 质量侧判定是**差值**：`delta = current - baseline = 0.20 - 0.00 = +0.20`；方向是 `lower_better`（越小越好）→ 变化方向是"差"且 `|delta| = 0.20 > 容忍度 0.05` → `degraded`。整个过程没有除法，因此 0 基数不构成任何障碍。
- 若照抄性能基线的**比值**口径：`ratio = 0.20 / 0.00` 没有定义。day046 的 `PerformanceGuard` 对此的处理是 **`if self.baseline.mean_cost_usd > 0:` 才参与判定**——也就是说，"从 0 变坏"这条指标会被**静默跳过**。对幻觉率这种"健康值就是 0"的指标而言，跳过等于"幻觉出现了但门禁看不见"。这正是本课把质量侧判定改成差值的第二条理由（第一条是方向反转）。
