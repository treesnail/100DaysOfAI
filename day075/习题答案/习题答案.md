## 一、前向与形状

### 1.（手算）单位矩阵配置下的完整前向

四个投影都是 `I`，于是 `Q = K = V = x`：

```text
inputs = ((1, 0), (0, 1))      两个正交的 one-hot token，d = 2
raw = x·xᵀ = ((1, 0), (0, 1))  一行与自己的点积是 1、与别人的是 0
缩放系数 = 1/√d_k = 1/√2 = 0.707107
scores = raw/√2 = ((0.707107, 0), (0, 0.707107))
```

因果掩码下：

```text
第 0 行  只允许看位置 0 → softmax([0.707107]) = (1.0, 0.0)        ← 恰好是 one-hot
第 1 行  允许看位置 0、1 → softmax([0, 0.707107]) = (p, 1−p)
         p = 1/(1 + e^{0.707107}) = 0.330238
         因此权重 = (0.330238, 0.669762)
```

输出（`W_v = W_o = I`）：

```text
context 第 0 行 = 1.0×(1,0) = (1, 0)
context 第 1 行 = 0.330238×(1,0) + 0.669762×(0,1) = (0.330238, 0.669762)
output = context（因为 W_o = I）
```

**验证**：演示脚本第 3 节的原样输出：

```text
  weights（因果）= ((1.0, 0.0), (0.330238, 0.669762))
  context = ((1.0, 0.0), (0.330238, 0.669762))
  output  = ((1.0, 0.0), (0.330238, 0.669762))
```

手算与实测逐位一致。注意第 0 行**恰好是 one-hot**：
它被掩码限制成"只有一个候选"，而 softmax 对单元素输入必然给出 1.0。

### 2.（概念）四个维度各自管什么

```text
d_k = 8 → scale = 1/√8 = 0.353553
d_v = 3 完全不影响缩放系数     —— scale 只由 keys 决定
```

**验证**：`AttentionShape(inputs=2, keys=8, values=3, outputs=3).scale == 1/√8`
（测试 `test_scale_uses_d_k_not_d_v`）。

`d_k` 只影响打分那一步：`raw = Q·Kᵀ` 的形状是 `(n, n)`，与 `d_k` 无关；
而输出宽度由 `d_v` 与 `d_out` 决定。**"改一个维度动全身"是合成单个 `d` 的代价**，
而它们的来源本来就不同（见手册第 2 节）。

### 3.（设计）三个形状约束

```text
① 四个矩阵的列数必须相同（= d_in）
   依据：四个投影都作用在**同一个输入**上，列数就是输入的行宽
② w_query 与 w_key 的行数必须相同（= d_k）
   依据：打分是 Q·Kᵀ，即"同一个空间里的点积"——维数不同时它没有定义
③ w_output 的列数必须等于 w_value 的行数（= d_v）
   依据：output = context·W_oᵀ，而 context 的宽度就是 d_v
```

这三条约束加起来正好是"这个式子有定义"的条件，因此它们在
`AttentionParams.__post_init__` 里**一次性**校验。

### 4.（动手）参数量

```text
四个矩阵都是 d×d 时：参数量 = 4d²      （没有偏置）
d = 6 时：4 × 36 = 144
```

**验证**：演示脚本第 10 节输出"批量梯度：144 个分量"；
小参数那一节（`d = 3`）输出"参数 36 个（四个投影，无偏置）"✓

## 二、掩码

### 5.（设计）为什么"因果 + 显式掩码"互斥

```python
if causal and mask is not None:
    raise ShapeError("causal=True 与显式掩码不能同时给：……")
```

理由与表现：

```text
理由    两个来源同时生效时，"到底用的是哪一张"要靠读代码才知道——
        而这是一个**语义**问题，不是性能问题
表现    "多看到一个位置"在输出上只表现为"数值略有不同"：
        注意力权重仍然是一个合法的概率分布（行和仍然是 1），
        没有任何异常，只有更难查的结果
```

同一取向的另一条规则：显式掩码必须保证**每一行至少有一个允许的位置**
（因果掩码天然满足：第 0 行至少能看到自己）。

### 6.（概念）"不适用"为什么也要出现在报告里

如果直接**不返回**这一项，报告里就会出现"4 项里只有 3 项"的空白——
而"没开掩码"与"掩码正确"在读报告的人眼里长得一样：

```text
报告里少一行      → 读者不知道是"没做"还是"做了没问题"
报告里写"跳过"    → 读者知道"这一次没有可检查的对象"
```

这与 day074 的 `GradientReport` 拒绝不完整报告是同一条纪律：
**一份不完整的报告比没有报告更危险。**
测试 `test_full_forward_is_reported_as_not_applicable` 把这条区分断言了下来。

### 7.（概念）为什么必须是恰好 `0.0`

两个理由：

```text
① softmax 的分母       被掩码位置不计入分母 → 剩下位置的权重才是"在一个更小的候选集上"
                       归一化出来的（否则整行和为 1 这件事会被"看不见的位置"分走一部分）
② 梯度的推论           s_j = 0 → dScores_j = s_j(g_j − 平均) = 0
                       于是"掩码位置的梯度恰好是 0"变成一条**推论**，而不是需要特例处理的补丁
```

与 day073 的关系：day073 从"非有限数不该进入概率层"的角度拒绝了 `-inf` 掩码；
今天补上的是**同一条路线的第二个好处**——显式掩码让下游（反向）也受益。
两处用的是同一个实现（`masked_softmax_rows`），这正是 day073 把它做成公共函数的回报。

### 8.（设计）全零行怎么修

```text
数据错误（真的有一个零向量 token）
  → 修上游：检查 embedding 或 one-hot 构造，把那一行修成有内容的向量
  → 这一层拒绝是对的：它拦下的是一个"下游全部可疑"的输入

padding
  → 显式处理：先把 padding 裁掉，或用掩码把那些位置排除在计算之外
  → 不要交给这一层猜："全零"在两种情况下含义完全不同
```

为什么不能猜：两者的**现象一样、修法不同**——

```text
数据错误   要让模型看见的是一行有内容的向量
padding    要让模型**看不见**这一行（掩码），或者根本不送进来
```

猜错的后果是"这一行的注意力是均匀分布"被当成正常，
而均匀分布看起来像"模型还没学到"——于是有人去调学习率。

## 三、反向传播

### 9.（手算）`dW_o`

配置同第 1 题（因果），`target = ((1,0),(0,1))`：

```text
y = output = ((1, 0), (p, 1−p))          p = 0.330238
t = ((1, 0), (0, 1))
y − t = ((0, 0), (p, p−1))
N = 行数 × 列数 = 2 × 2 = 4
dOut = 2(y−t)/N = ((0, 0), (p/2, −p/2))
```

`dW_o = dOutᵀ·context`（`W_o = I`，因此 `context = y`）：

```text
dW_o 的第 a 行 = Σ_i dOut[i][a] · context[i]
  a = 0：只有 i = 1 那一项非零 → (p/2) × context[1] = (p/2)·(p, 1−p) = (p²/2, p(1−p)/2)
         = (0.054529, 0.110591)
  a = 1：同理得到 (−0.054529, −0.110591)
```

**两行互为相反数的原因**：`dOut` 只有第 1 行非零，而那一行的两个分量是
`p/2` 与 `−p/2`（互为相反数）；乘上同一个 `context[1]` 之后仍然互为相反数。
换句话说，**损失只对"第 1 行错了多少"有意见，而它把这份意见按两半给了 W_o 的两行**。

**验证**：测试 `test_output_projection_gradient_is_hand_computed` 逐元素断言
`(p²/2, p(1−p)/2)` 与它的相反数，容差 `1e-9`。

### 10.（手算）softmax 的反向三例

```text
s = (0.5, 0.5)、g = (1, 0)
  平均 = 0.5×1 + 0.5×0 = 0.5 → dScores = (0.5×(1−0.5), 0.5×(0−0.5)) = (0.25, −0.25)

s = (0.25, 0.25, 0.25, 0.25)、g = (1, 1, 1, 1)
  平均 = 1 → 每一个 dScores = 0.25×(1−1) = 0
  直觉：**均匀分布 + 均匀梯度 = 没有方向**（整体平移不改变概率）

s = (1, 0, 0)、g = (5, 7, −3)
  dScores = (1×(5−5), 0×(7−5), 0×(−3−5)) = (0, 0, 0)
  后两个位置是 0，因为它们的 **s = 0**：一个概率恒为 0 的位置，
  无论下游梯度多大，它对输入的导数都是 0（这也是"掩码位置零梯度"的原因）
```

**验证**：演示脚本第 6 节把这三例原样打出来。

### 11.（概念）漏掉缩放系数

```text
前向   scores = raw/√d_k
反向   dRaw = dScores/√d_k        ← 漏掉这一步
后果   梯度整体差一个 √d_k 倍：d_k = 6 时是 2.449490 倍
```

**不会报错**，在训练里看起来像"学习率不太合适"——
而"梯度整体乘以一个常数"与"学习率乘以同一个常数"在 SGD 下**完全等价**，
因此它甚至可能在调 lr 之后被"治好"（换成 Adam 就治不好了，
因为 Adam 会归一化掉这个常数，于是症状变成"前几步的轨迹与预期不同"）。

**护栏**：这一处的护栏是 `gradcheck` 的五项对照中 `w_query`/`w_key` 那两项——
缩放系数正好在这两条链上。

### 12.（概念）掩码位置的梯度不置 0

```text
前向的权重会变吗？   **不会**。掩码作用在 softmax 上，
                    被掩码位置仍然是精确的 0.0——前向看起来完全正确
哪一块梯度会出错？   dScores 在被掩码位置非零 → 沿着"打分 → Q/K"两条链传下去，
                    dW_q 与 dW_k 会混进"位置 i 通过一条它看不到的路径"的贡献
为什么最难发现？     因为**损失仍然在降**（多出来的那一份梯度"方向大致对"），
                    而唯一能看出来的地方是"模型的注意力出现了不该有的模式"——
                    那需要把权重打印出来看，而不是看损失曲线
```

**护栏**：反向代码里显式再置一次零，并且
`check_causal_no_leak` 从**前向**侧守住"上三角恰好 0.0"；
两侧一起才能说清"看不到未来"这件事。

### 13.（设计）`grad_inputs` 的三条链

```text
为什么必须存在   层要能被**堆叠**（day079/080 的 Encoder 就是两层这样的层串起来）
                 没有它，这一层只能单独训练，无法参与任何多层结构
漏一条链会报错吗 **不会**。它会给出一个形状正确、数值偏小的输入梯度
                 （少了 q 或 v 那一路的贡献）
哪一项能发现它   五项校验里的 `inputs` 那一项——
                 前四项（四个参数矩阵）在前向与反向里都能自洽，
                 只有输入梯度会把"少了一条链"暴露出来
```

测试 `test_input_gradient_is_the_sum_of_three_chains` 断言它非零，
而 `check_attention_gradients` 把解析的输入梯度与数值差分的输入梯度逐点比对。

### 14.（概念）为什么用 MSE

```text
MSE 的梯度：∂MSE/∂y = 2(y−t)/N —— 一行就能手算
```

于是"外部输入的梯度"是**平凡**的，任何梯度校验失败都只可能来自注意力那七步：

```text
如果损失复杂（例如交叉熵 + 掩码 + 长度归一化），那么"梯度校验失败"
就有两个可能的来源——损失写错了，或者注意力写错了
→ 排查成本从"看七步"变成"看七步 + 看损失"
```

这与 day074 用"碗形函数"验证优化器是同一个手法：**一次只留一个不确定性。**
（代价是 MSE 在分类任务上不如交叉熵收敛快——但那不是这一课关心的事，
这一课关心的是"反向传播写对了吗"。）

## 四、梯度校验

### 15.（概念）五项各自守什么

```text
w_output   反向的第一站（它只吃损失对输出的梯度）—— 错了说明"最外层"写错了
w_value    把"输出该混哪些位置"翻译成"value 该怎么调"
w_query    梯度要穿过 softmax（这一块错了，多半是 softmax 的反向写错了）
w_key      与 query 共享同一份软打分的梯度
inputs     三条链之和 —— **唯一能发现"漏了一条链"的检查**
```

一个整体的误差数字无法回答"是哪一块错了"，而"哪一块错了"直接决定去哪一行代码：

```text
整体差 15%  → 不知道是 softmax 反向、是缩放、还是少了一条链
w_query 差  → 直接定位到"softmax 反向"或"缩放"这两处之一
```

### 16.（设计）"两边都对却对不上"

第一版：数值侧算**全行** MSE、解析侧算**监督行** MSE：

```text
最大绝对差 7.5e-3，而梯度范数只有 4.8e-2 → 差 15%
```

**为什么更难查**：排查者的第一反应是"对照不一致 → 推导错了"，
于是会去重推七步反向——而反向是对的。
"两边都对却对不上"意味着**对照的方法**错了，而不是被对照的东西错了。
（day073 也踩过同一类坑：拿两串顺序不同的数去比，得到 0.73 的假不一致。）

**修法**：给数值侧一个同名的 `supervised` 参数，让两侧算同一个式子。
修完之后：

```text
差值降到 2.1e-11（就是数值差分自身的分辨率）
```

**验证**：测试 `test_the_two_loss_conventions_are_different` 断言两种口径的
差别 > 1e-2；`test_numeric_with_supervision_matches_the_masked_analytic` 断言
修完之后 < 1e-6。

### 17.（设计）容差为什么是 `1e-6`

分辨率估算（day074 的公式 `eps·|f|/(2h)`）：

```text
损失量级 |f| ≈ 0.16（induced 任务）～1（一般情形）
步长 h = 1e-6
分辨率 ≈ 2.22e-16 × 0.16 / (2e-6) ≈ 1.8e-11        ← 与实测 2.4e-11 同量级
```

于是：

```text
容差 1e-6 = 分辨率的约 5 万倍      → 不会产生假警报（day074 的教训）
而"真的写错了"通常差 1e-2 以上    → 与 1e-6 之间还有 4 个数量级，区分度充足
```

比 day074 的 `1e-8` 松两个数量级，是因为这里的"函数值"（损失）
由一串矩阵乘法叠出来，累积的舍入比单个 `exp` 大得多。

### 18.（概念）报告 vs 控制流

```text
day073 的 bridge      梯度值对不上只是一个**结论**（status == "differs"），
                      不改变控制流：人可以读完报告再决定怎么办
day075 的 gradcheck   梯度对不上意味着**这次训练从头到尾都不可信**，
                      必须能让调用方当场停下来
```

因此 `transformer_core.errors` 多一族 `GradientError`，而它属于"控制流"：

```text
MathError       梯度对照的结论属于**报告**
GradientError   梯度校验的结论属于**控制流**（这一步就不该继续）
```

**同一种失败，"谁去修"不同，就该落在不同的族里**——这是全课的骨架。

## 五、性质检查

### 19.（概念）四条性质

| 性质 | 在说什么 | 失败意味着 |
|------|----------|-----------|
| `row_stochastic` | 每一行权重之和为 1 | 后续加权求和变成缩放错误的组合（"混合出来的向量"整体偏大或偏小） |
| `non_negative` | 每个权重 >= 0 | "加权平均"在某处变成减法（混合结果被某个位置的负权重放大） |
| `causal_no_leak` | 上三角**恰好 0.0** | 位置 i 看到了未来（训练时"作弊"，推理时不可能复现） |
| `permutation_equivariance` | 无掩码时输入换序 → 输出按同样方式换序 | 顺序信息被悄悄引入了（而这一层本该"不知道顺序"） |

### 20.（动手）置换等变

```text
无掩码：0.00e+00            —— 严格相等（不是"小于某个容差"）
因果掩码：0.4806            —— 与输出本身的量级相当
```

无掩码时为什么应当是 0：把输入行换序，`Q/K/V` 的行跟着换序，
于是 `raw = Q·Kᵀ` 的行与列同时换序、softmax 是**逐行**做的（每行内部的元素集合不变）、
`context` 的行跟着换序、`output` 的行跟着换序。**每一步都是"同一个运算、换个顺序"**。

这**不是 bug**：因果掩码把"谁在谁前面"写进了那张表，
于是"换序"不再是一个对称的操作。它引出 **day078（位置编码）**：

```text
掩码只提供一种很粗的顺序（谁在谁前面）
要表达"位置 3 与位置 5 的距离"，仍然需要位置编码
```

**验证**：演示脚本第 7 节把两个数**并排**打出来
（`无掩码 0.00e+00、因果掩码 0.4806`）——只报"置换等变通过"会掩盖这件事。

### 21.（手算）秩相关

`rank_correlation([1, 1, 2], [1, 2, 3])`：

```text
左：值 1 出现两次、并列占据了第 1、2 名 → 平均秩 (1+2)/2 = 1.5
    值 2 在第 3 名 → 秩 3
    秩 = (1.5, 1.5, 3)
右：全部不同 → 秩 = (1, 2, 3)

中心化：左 (1.5−2, 1.5−2, 3−2) = (−0.5, −0.5, 1)
        右 (1−2, 2−2, 3−2)     = (−1, 0, 1)
协方差 = (−0.5)(−1) + (−0.5)(0) + (1)(1) = 0.5 + 0 + 1 = 1.5
左平方和 = 0.25 + 0.25 + 1 = 1.5
右平方和 = 1 + 0 + 1 = 2
相关系数 = 1.5 / √(1.5 × 2) = 1.5 / √3 = √3/2 = 0.866025
```

**验证**：`rank_correlation([1.0, 1.0, 2.0], [1.0, 2.0, 3.0]) == √3/2` ✓

### 22.（设计）平均秩 vs 字典序

同一个例子里，如果并列用"字典序名次"（谁先出现谁排前面）：

```text
左：值 1 的两次出现分别记 1 与 2 → 秩 = (1, 2, 3)
右：秩 = (1, 2, 3)
相关系数 = 1.0          ← 与"平均秩"给出的 0.866025 不同
```

**为什么"依赖输入顺序"是坏事**：

```text
(1, 1, 2) 与 (1, 1, 2)（同样的值、只是两个 1 换了位置）会给出两个不同的相关系数
→ 而它们的**内容完全一样**。一个"内容相同、结果不同"的读数，
在报告里是不可复核的——它违背了 day073 起反复强调的"同一输入同一输出"。
```

## 六、与检索的类比

### 23.（概念）三个读数

| 读数 | 回答 |
|------|------|
| `peak_agreement` | 两边的 argmax 是不是同一个位置（"最看重的是不是同一个"） |
| `overlap` / `overlap_ratio` | top-k 集合的重合（"最相关的那几个是不是同一批"） |
| `rank_correlation` | 整体排序的秩相关（"整体排序像不像"） |

**为什么不能只看 top-k 重合**：它是**离散量**——
`k = 1` 时它只取值 0 或 1，很多差别会被它吞掉。
两种组合各有含义：

```text
秩相关高、重合低    整体排序一致，但边界位置在换（k 太小或分数接近）
秩相关低、重合高    只有最相关的那几个恰好相同（退化情形）
```

### 24.（设计）为什么只在允许的位置上比

一句话：**因果掩码把未来位置的权重写成 0，而余弦并不知道掩码的存在**——
不排除它们时，"不一样"里会有很大一部分只是"掩码 vs 不掩码"的差别，
而不是"两种相关性口径"的差别。

这与 day074 的"对照必须把算的是哪个式子写进参数名"是同一条纪律：
**比较必须先对齐口径。**

### 25.（写作）一句话说清差别

> 检索做的是**离散的选择**（`cos(query, doc)` 排序 → 取前 k 条，梯度传不回去），
> 注意力做的是**可微的混合**（`softmax(q·k)` 给出一个分布 → 对 value 加权平均，梯度能一路回传）。

工程上换来的是：**"哪些内容相关"这件事本身可以被训练**。
检索的"相关性口径"是人事先定的（用哪个 embedding、要不要 BM25、怎么融合），
而注意力把"想看哪里"变成了模型的一个参数（`W_q` 与 `W_k`）——
于是它可以在任务上自己学出来。这一课的训练实验就是它的证据。

## 七、训练

### 26.（概念）induction 任务的三个好处

```text
① 可逐位复核      一个"找同一个 token"的机制就能做对，答案不模糊
② 不与任务模糊性混淆  "训练有没有效果"不取决于"任务本身难不难"
③ 机制与结果可分   注意力锐化（看对了）与命中率（答对了）是两个独立读数
```

"答案必须能在上下文里找到"写成一条**校验**，是因为它一旦不成立，
任务就变成"记忆"而不是"检索"：

```text
监督位置的 token 在它之前没有出现过 → 这一位没有任何可学的机制，
模型只能靠"见过这一条样本"来做对——而那是记忆，不是这一课想验证的东西
```

**一个被自己抓到的 bug**：这条例子的第一版写成了
`if position not in _earlier_matches(tokens, position)`，
而 `_earlier_matches` 当时把 `position` 自己也算了进去——于是它**恒真**。
修法是把匹配改成"严格更早"，并把判断改成 `if not _earlier_matches(...)`。
测试 `test_supervised_position_without_an_earlier_match_is_rejected`
专门构造了"第三个 token 是全新的"样本来让它失败一次。

### 27.（动手）训练的三个读数

```text
初始：损失 0.163411、命中率 38%、峰值 0.2316
最终：损失 0.000008、命中率 100%、峰值 0.4436（200 步、Adam 0.05、4 条样本）

      步           损失       命中率        峰值权重
      0     0.163411       38%      0.2316
      8     0.071580      100%      0.2670      ← 命中率先到顶
     20     0.012415      100%      0.4137      ← 峰值明显上升
     50     0.000365      100%      0.4423      ← 损失基本到 0
    200     0.000008      100%      0.4436
```

三个读数**到达"变得明显"的步数**：命中率最快（第 8 步）、损失次之（第 50 步）、
峰值最慢（第 20 步才明显上升）。原因是它们的"难度"不同：

```text
命中率只看 argmax → 目标分量排第一就够（容易）
损失要数值逼近     → 需要混合比例与目标接近
峰值要看权重形状   → 需要注意力真正聚焦
```

**为什么"损失到 0"不等于"学到机制"**：冻结对照给出的数字是——

```text
四块全训  损失 → 0.0000、命中率 → 100%、峰值 → 0.444
只训 q/k  损失 → 0.1554、命中率 →  12%、峰值 → 0.587
```

两个方向都反直觉：

```text
只训 q/k   注意力变尖了（峰值 0.59），但损失降不下去——
           "看对了地方"只是必要条件，还要 value/output 把看到的东西映射成目标
四块全训   损失到 0，而峰值只有 0.44——
           模型在 value 路径上把不需要的分量抵消掉了（另一条路）
```

**结论：没有任何一个读数能单独说明"学到了什么"。**

### 28.（概念）冻结为什么这么便宜

因为 day074 把参数与优化器**解耦**了：

```text
AttentionParams.flatten()    → (一串数, 形状表)
optim.AdamOptimizer.step()   → 只做逐分量的 θ ← θ − lr·m̂/(√v̂+ε)
```

于是"冻结"只是"把对应块的梯度置 0"：

```python
blocks = unflatten_matrices(flat_grad, shapes)      # 按形状表切开
kept = tuple(matrix if name in trainable else zero_matrix(matrix) ...)
flatten_matrices(kept)                              # 再拼回去
```

**没有额外数据结构、没有额外的状态**——"冻结"这件事在数值上就是"梯度那一块是 0"。
一个真实场景：**LoRA** 冻结主干、只训练低秩旁路（`B·A`），
而旁路的那两块参数同样可以压平之后交给同一个优化器。

### 29.（设计）为什么用 SGD 对账

```text
SGD     步长与梯度成线性 → 梯度上 1e-11 的误差只带来 1e-11 量级的轨迹差
Adam    按 √v̂ 归一化 → 在梯度接近 0 的分量上分母也很小，
        于是**一个分量的相对误差会被放大**成"这一步方向不同"
```

实测（同样 4 条样本、同一个起点）：

```text
SGD  0.05    6 步   损失轨迹最大差 5.090e-14
Adam 0.05    6 步   损失轨迹最大差 4.621e-11
Adam 0.05   30 步   损失轨迹最大差 7.051e-11
Adam 0.10   30 步   损失轨迹最大差 1.412e-10
```

Adam 的差别比 SGD 大约 **1000 倍**，但两支都稳定收敛——
因此这不是实现问题，而是"归一化型优化器会放大梯度的相对误差"这条性质的直接观测。
**要验证梯度实现，请优先用 SGD。**

## 八、工程取舍

### 30.（概念）恒真的校验

**为什么比没有校验更坏**：

```text
没有校验     报告里空着 → 读者知道"这件事没被检查"
恒真的校验   报告里写着"通过" → 读者以为"这件事被检查过了"
```

**它怎么产生的**：把"出现过"实现成"在 `tokens[:position+1]` 里找得到相同 token"——
而"包含自己"三个字让每个位置都自动满足（一个 token 当然等于它自己）。
于是判断 `position not in matches` **永远为假**，异常分支永远不触发。

**怎么修的**：

```python
def _earlier_matches(tokens, position):
    """在**严格更早**的位置（0..position−1）里，与 tokens[position] 相同的下标."""
    return tuple(index for index in range(position) if tokens[index] == target)

if not _earlier_matches(self.tokens, position):   # ← 判断也改成了"有没有"
    raise ShapeError(...)
```

带走的一条经验：**校验的护栏是"让它失败一次"**。
测试里必须有一个专门构造的、违反该条件的样本——
否则这条校验只是"看起来像护栏"。

### 31.（设计）不加配置项

**理由**：今天新增的每一个"参数"都是**判据**——
容差、步长、初始化幅度、学习率曲线、冻结哪几块、`top_k`、置换。
它们与"配置"的性质恰好相反：

```text
配置    一次设定、多处共享、改了影响**系统行为**
判据    一次计算一份、改了只影响**这一次**训练或这一份报告
```

**一个具体场景**（为什么写进配置会变难查）：

```text
把 GRADIENT_TOLERANCE 放进 .env：
  本层的分辨率约 2e-11（第 17 题算过），因此容差必须**高于**它。
  某个人为了让一次调试"过"，把它调成 1e-12（低于分辨率）
  → 梯度校验开始"随机失败"：失败与否取决于当次的浮点噪声，
    同一份代码昨天绿今天红
  → 于是"本地通过、CI 失败"变成一个需要读多人环境变量才能解释的问题
  → 而根因只是某个人为了让某次调试通过而调低过一次
```

判据留在代码里的好处正是：**diff 会告诉你"哪一次比较换了口径"**——
而 `.env` 不会出现在任何人的 review 里。

### 32.（综合）三处"漏掉不会报错"

| 漏掉的地方 | 现象（训练曲线上看得出什么） | 护栏 |
|-----------|------------------------------|------|
| softmax 的雅可比（简写成 `dScores = dWeights`） | 训练仍然下降，只是每步幅度不对 → "收敛慢一点" | `check_attention_gradients` 的 `w_query` / `w_key` 两项（梯度会直接差 1e-2 以上） |
| 缩放系数（反向没乘回 `1/√d_k`） | 与"学习率整体小/大 √d_k 倍"等价 → SGD 下调 lr 能"治好"，Adam 下变成"前几步轨迹不同" | 同上（缩放就在 `raw` 那一步的上下） |
| 掩码位置的梯度没置 0 | **前向完全正确、损失仍然下降**，只有权重里出现"不该有的模式" | 反向里显式再置一次零；前向侧由 `check_causal_no_leak` 守住"上三角恰好 0.0" |

一张表背后的同一句话：

```text
反向传播里每一处"看起来可以简化"的地方，都要有**一条能独立失败的检查**。
因为它的错误形式不是异常，而是"训练慢一点"或"结果略有不同"。
```

## 参考答案小结

这一课 32 道题里有 12 道需要**动手跑**。它们共同的形状与 day074 相同：
先算出一个**手推的期望值**，再与实现在同一点上的输出对照。
而这一课多出一种情况——**测试自己写错了**：

```text
① "每行不等长"的期望类型搞错了族（本层 vs math_foundations）
② softmax 的两个分量写反了（第 1 行看到 [0, 1/√k]，因此第一个分量是 p 不是 1−p）
③ 零块计数的测试给了错的长度，于是"想测的那一条"没被触发
④ 一条"恒真的校验"看起来像护栏，实际上什么都没拦
```

**四种都必须先被区分开，再动手改代码**——
这一课最重要的收获不是"会写反向"，而是"知道一个绿色为什么可信"。
