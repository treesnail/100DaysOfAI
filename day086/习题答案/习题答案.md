## 一、选择题

**1. B。** `from_pretrained` 的第一步是**把文件找齐**，而不是加载权重。
找齐这件事有三段：名字 → commit（`refs/main`）→ 文件（`snapshots/<commit>/`）→
实体（`blobs/<sha256>`）。C 与 D 都发生在这之后。

**2. B。** 命中是**逐文件**的：判据是"第二次解析同一个 commit 时，每个文件的下载量都是 0"。
A 是把它写成 all-or-nothing，那是本课明确列出的错法；
C 错在换 revision 会换 commit、因而换一个快照目录；
D 说反了——快照里的路径与仓库一致（平铺），**blobs** 里才是哈希名。

**3. B。** 这是本课新增的一条纪律：`HubError` 的出路是**改环境**，
`ParameterError` 的出路是**改调用**。把前者归进后者，就会有人把
`local_files_only` 改成 `False` 再试，而网络那一步的失败**长得完全一样**。

**4. B。** 真库上跑一条即可确认：`GPT2Config().tie_word_embeddings is True` 与
`BertConfig().tie_word_embeddings is True`。真实的 `bert-base-uncased`
配置文件里根本没有这个键，于是全局默认生效——代价是一个整数：
带共享 109 482 240，不共享 132 923 136。

**5. B。** 这是本课与真库对账时冒出来的"看起来一样、其实不一样"：
`GPT2Config().n_inner is None`（缺省按 `4·hidden` 推），
而 `BertConfig().intermediate_size == 3072`（与 `hidden` 无关）。
它在 `bert-base-uncased` 上恰好等于 `4×768`，因此容易被误读成规律。

**6. B。** 掩码不知道"段"这件事：第 2 段的首行落在整条长序列的下三角之内，
于是它能看到第 1 段的**全部** token。形状完全合法、不报错、也没有 NaN，
而输出只是**偏了**（偏的方向取决于同一批里前面那条的内容）。

**7. B。** 在进程模型的窗口来自位置表长度（模型的硬上界），
Ollama 的 4096 是一个可以覆盖的部署参数。C 与 D 错：
`describe` 是那八项方法面之一；在进程模型的 `chat_with_tools` **明确抛错**。

## 二、简答题

**8.** 三段结构与它们对应的路径段：

```text
① 名字 → commit       <cache>/models--org--name/refs/main          内容 = 一串 commit hash
② commit → 文件       <cache>/models--org--name/snapshots/<commit>/<相对路径>   与仓库一致（平铺）
③ 文件 → 实体         <cache>/models--org--name/blobs/<sha256>     按内容寻址
```

"两个名字"指的是：在 ② 里它叫**相对路径**（`config.json`），
在 ③ 里它叫 **sha256**。中间的映射表（`snapshots/<commit>/` 里那一行）
就是这两个名字之间的唯一联系——把哈希名当路径，`config.json` 就找不到了。

**9.** 三条对账：

```text
① 画像 vs 配置      day085 从源码读出的默认值 ↔ 今天从 config.json 解析出的卡片
                    比法：**整数/字符串相等**（四项逐一：激活、eps、融合 QKV、token_type）
② 生成策略          pipeline.text_generation ↔ day085 的 generate
                    比法：**逐位**（同一个 logits_fn、同一份 settings 下的 token 序列）
③ 块的接线          本包的一层 ↔ day085 的 gpt2_block（L=1、heads=1、因果）
                    比法：**逐位**（两条路径只差"加性偏置 vs 显式掩码"）
```

第二条抓的是"管线在透传 settings 时偷偷改了东西"；
第三条最强，因为接线走散（LN 放错一侧、残差少加一次）时**形状完全看不出来**。

**10.** 因为"第二次解析"只有在**缓存已经存在**时才可能命中。
拿一个已经填好的缓存去跑，第一次调用本身就是一次命中，于是
`downloaded_count == 0` **永远成立**——这条判据不可能失败。

它的危害是一条更普遍的纪律（day085 也记过）：
**不可能失败的判据不算判据**。"把这条检查删掉"与"它通过了"在报告里长得一模一样，
而报告是给别人（与三个月后的自己）看的。本课因此让
`check_cache_is_per_file(fresh=True)` **从空缓存开始**，
并额外检查 `first.downloaded_count > 0`——第一次必须真的有下载，第二次才谈得上"命中"。

顺带一条同源的坑：`study.cache_rows` 也必须让两轮**共用同一个缓存**，
否则"命中"永远不会发生，而两轮看起来都正常。

**11.** 两条"不适用"：

```text
params_match_library   只对**记录在案**的两个真实模型适用（gpt2 / bert-base-uncased）；
                       玩具卡片没有库读数可对 ⇒ 不适用
block_matches_day085   只在 L=1 且 heads=1 的 GPT-2 卡片上适用；
                       day085 的 gpt2_block 是单层的、且只与单头对得上
```

必须分开印的理由（day083 第 7.2 节那条纪律的延续）：
若"不适用"直接记成"通过"，那么"把这条检查删掉"与"它通过了"在报告里一模一样。
本包在**构造期**就拒绝这种组合（`applicable=False` 而 `passed=True` 会抛 `NumericError`），
而不是靠约定。

**12.** 两个式子：

```text
正确版  μ_correct = (Σ_{i=1..k} x_i) / k          # 分母是**真实长度**
违反版  μ_buggy   = (Σ_{i=1..k} x_i + Σ_{j=1..w−k} p_j) / w    # 分母是**总宽度**
```

"只有一条样本、且它正好是最长的那条"意味着 `k = w`（没有填充），于是：

```text
Σ_{j=1..0} p_j = 0     ⇒   μ_buggy = (Σ x_i) / w = (Σ x_i) / k = μ_correct
```

两版**完全相等**。这正是这个 bug 最难被发现的原因：
拿一条样本试、或者拿一批长度全相同的样本试，都试不出来。

## 三、诊断题

**13.** 错误是**掩码给错了**：它用 `causal=card.causal` 让库内部造一张
"整条长序列的下三角"，而正确做法是给一张**段内下三角**
（`forward.block_causal_mask(tuple(width for _ in rows))`）。

它"看起来正常"的原因有三层：

```text
① 形状全对：padded 是 (3, width)、mask 也是（虽然这一段里 mask 根本没被用上）
② 不报错：掩码只是"允许集合"，给宽了不会触发任何形状检查
③ 第 1 条样本**碰巧是对的**——它前面没有别的段，于是拿单条样本试永远试不出来
```

能抓住它的判据是 `batch_matches_single`：它要求**批量与逐条逐位一致**，
而在这个实现下第 2、3 条样本会对不上（演示读数：最大差 `3.657138e+00`，
归因"跨样本串味"）。修法就在同一份文件里：把 `causal=True` 换成
`causal=False` 加一张 `block_causal_mask(...)`。

**14.** 错误是**假设了"前馈就是 4·hidden"**，而 BERT 的缺省是固定的 3072：

```text
正确的读法       ffn = card.intermediate if card.intermediate is not None \
                   else (3072 if model_type == "bert" else 4 * hidden)
```

"恰好正确"之所以掩盖它：`bert-base-uncased` 的 `hidden=768` 与
`intermediate_size=3072` **恰好**是 4 倍关系，因此在**那一个模型**上，
"按 4·hidden 推"与"读配置"给出同一个数（109 482 240 两边都对）。
一旦换一个尺寸（例如 `hidden=16`），两者立刻分家：
按 4·hidden 得到 `ffn=64`，而真实的 `BertConfig(hidden_size=16)` 给出 `3072`——
差出 48 倍，而参数量公式仍然"算得出来"（只是算的是另一个模型）。

修法与防法：读配置优先（本包的 `ModelCard.ffn`），并让
`tests/test_hf_real_bridge.py` 拿真库对一次——那一条测试就是为这类
"在某一个模型上恰好成立"的假设准备的。

**15.** 三条读数各自的诊断与动作：

```text
读数 A  批量与逐条不一致，而 naive 的差是 3.66e+00
        诊断：因果侧的批量用了整条长序列的下三角，**漏掉"段"**
        动作：换成 block_causal_mask（段内下三角）；检查第 1 条是否"碰巧是对的"
              （若第 1 条也对不上，那问题在别处——例如 padded 没填对）

读数 B  bert：两种填充宽度下池化差 1.45e+00
        诊断：均值池化的分母用了**总宽度**（违反版），或者掩码没传进池化
        动作：检查 pool_masked 的 ignore_mask 是否为 False、掩码是否按行切对；
              对照 study 的池化表——正确版这一列**必须**恒为 0

读数 C  平铺 3 个而共 4 个文件
        诊断：有一个文件名带内部前缀（落在 blobs/ 或 snapshots/ 里），
              它用 join(root, name) 找不到 ⇒ 会报成"仓库里没有这个文件"，指错方向
        动作：检查快照的写入路径——相对路径必须与仓库一致；
              用 flat_paths(snapshot) 与 snapshot.names() 对比，差的那一个就是它
```

## 四、推导题

**16.**（a）本包每一层的五项来源（`h` = hidden，`f = ffn`）：

```text
四个投影        4·h²        （**无偏置**：day075 的 AttentionParams 就是四个 h×h 方阵）
两个 LayerNorm  2·2h = 4h   （norm1 与 norm2 各一组 γ/β，γ 是 h 个数、β 也是 h 个数）
前馈 w_in       f·h         （元素个数 h·f，**带偏置**另计）
前馈 b_in       f           （f 个数）
前馈 w_out      h·f         （元素个数 f·h）
前馈 b_out      h           （h 个数）
```

把 `f = 4h` 代进去：

```text
4h² + 4h + (4h·h) + 4h + (h·4h) + h
= 4h² + 4h + 4h² + 4h + 4h² + h
= 12h² + 9h        ✔
```

（注意"四个投影不带偏置"是**本包的实现口径**，而配置口径里的四个投影**带偏置**——
这一条差别就是下面那 4h 的全部来源。）

（b）配置口径的每一层是 `12h² + 13h`，于是：

```text
(12h² + 13h) − (12h² + 9h) = 4h
差值 × 层数 L               = 4h·L        ✔
```

（c）`4h` 在两个架构里的拆法**不同，但总数相同**：

```text
GPT-2   c_attn 的偏置 3h  +  c_proj 的偏置 h
        （一次融合投影算出 3·hidden 维，它的偏置就是 3h；输出投影的偏置是 h）
BERT    query 的 h + key 的 h + value 的 h + attention.output.dense 的 h
        （四次独立投影，各带一个 h 长的偏置）
```

两边都是 `4h`，因此"差值 = 4·hidden·layers"是一条**两边通用**的断言；
而"这 4h 是从哪来的"必须分开写——否则一份 GPT-2 的推导会被当成 BERT 的。
读数：`配置 11536 / 权重 11408 / 差 128 = 4·16·2`（`python scripts/hf_integration_demo.py` 第 3 节）。

**17.**（a）设三条样本首尾相接，第 1 段是 `[0, n₁)`、第 2 段是 `[n₁, n₁+n₂)`、
第 3 段是 `[n₁+n₂, n₁+n₂+n₃)`。对任意 `i`：

```text
A_full(i)  = { j : 0 ≤ j ≤ i }                    ← 整条长序列的下三角
A_block(i) = { j : s(i) ≤ j ≤ i }，其中 s(i) 是 i 所在段的起点
```

（b）当 `i = n₁`（第 2 段的首行）时：

```text
A_full(n₁)  = {0, 1, …, n₁}
A_block(n₁) = {n₁}
A_full \ A_block = {0, 1, …, n₁−1}   ← **恰好是第 1 段的全部位置**  ✔
```

即：第 2 条样本的第一个 token 能看到第 1 条样本的每一个 token。

（c）第 1 段的行 `i < n₁` 满足 `A_full(i) = {0..i} = A_block(i)`
（因为第 1 段的起点就是 0），**位置集合完全相同**，因此 softmax 的输入相同、
输出逐位相同。

这件事让 bug 很难被发现的原因：**它只在"同一批里排在后面的那些样本"上出错**。
拿一条样本试、或者拿 `batch_size=1` 试，永远试不出来；而出错的那几条
在形状、求和、有限性上全部正常——它们只是**偏了**。
本课因此把"批量与逐条逐位一致"写成一条判据，并**同时**印出
"naive 与 safe 的差"作为必要性证据（演示读数 `3.657138e+00`）。

**18.**（a）两个式子：

```text
μ_correct = (Σ_{i=1..k} x_i) / k
μ_buggy   = (Σ_{i=1..k} x_i + Σ_{j=1..w−k} p_j) / w
```

令 `S = Σ_{i=1..k} x_i`、`P = Σ_{j=1..w−k} p_j`，则：

```text
μ_buggy − μ_correct = (S + P)/w − S/k = (kS + kP − wS) / (wk)
                    = ( kP − (w − k)S ) / (wk)
```

（b）当 `k = w` 时，填充个数 `w − k = 0`，于是 `P = 0`（空和），代入上式：

```text
μ_buggy − μ_correct = (k·0 − 0·S) / (wk) = 0        ✔
```

两版**逐位相同**（不只是数值相近：分子的两项都精确为 0）。
这正是"没有填充时两版完全一样"的证明，也是它难以被发现的原因。

（c）若填充位置上都是**零向量**（`p_j = 0`，于是 `P = 0`），则：

```text
μ_buggy = S / w = (k / w) · (S / k) = (k / w) · μ_correct
```

即违反版**恰好是正确版的 `k/w` 倍**——而 `k/w < 1`，因此它把向量**缩短**了。

对余弦相似度的影响恰恰相反（这值得单独记住）：余弦相似度对缩放**不变**，
`cos(αu, v) = cos(u, v)`（`α > 0`）。所以：

```text
当填充位置真是零向量时     违反版把向量等比缩短 ⇒ 余弦相似度**完全看不出来**
当填充位置不是零向量时     方向也被改变 ⇒ 排序开始出错（这才是被抓住的那一半）
```

这正是本课用手算锚点（`states = (1,1) (3,3) (5,5) (9,9)`、`mask = 1 1 1 0`）
取填充行为 9 而不是 0 的原因：**若取 0，`max` 恰好不受影响，而余弦相似度
也看不出来**——"它没问题"与"这次样本碰巧没暴露它"就会读起来一样。
演示里那个 `1.451731e+00` 的读数因此带着一句限定：
它的填充行是以零行代表的，量的是"池化分不分得清真实位置"，
而不是"模型对 pad id 输出什么"。
