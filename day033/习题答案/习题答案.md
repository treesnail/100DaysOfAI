## 第一部分：选择题

### 第 1 题

**答案：C**

**解析**：C 错误——自回归生成**完全不联网**：模型每步只是在词表上算一个概率分布并选一个 token，词表分布来自训练时压缩进参数的知识，与实时检索无关。（我们的 Agent 能联网，靠的是 ReAct 循环里模型输出 `Action: web_search` 后由**系统**执行工具再回喂，联网发生在模型之外。）

A 是原子操作的准确描述；B 是"自回归"一词的含义（输出回归为输入）；D 是串行解码 vs 并行预填充的算力差异，直接解释了 day032 价格表里的输出溢价。

### 第 2 题

**答案：B**

**解析**：temperature 是 softmax 里 logit 的缩放因子 `p_i = exp(z_i/T) / Σ exp(z_j/T)`。T 增大 → logit 差异被压缩 → 高分 token 的优势缩小 → 分布趋于均匀。实测 `logits=[0,1,4]` 时第三个 token 的概率：T=0.5 → 0.9972，T=1.0 → 0.9362，T=2.0 → 0.7361。A 恰好说反（那是 T 调小的效果）；C、D 都不符合公式。

### 第 3 题

**答案：C**

**解析**：对 `[0.9, 0.05, 0.05]`，第一个候选的累积概率已达 0.9 ≥ top_p，核内只有 1 个；对 `[0.34, 0.33, 0.33]`，累加两个才 0.67 < 0.9，必须留下全部 3 个。同样的 top_p，分布尖锐时核小、分布平坦时核大——**候选集大小随模型的确定性自适应**。top-k 固定保留 k 个，在尖锐分布下会放进烂 token，在平坦分布下会错杀好候选；核采样没有这个毛病。对应测试 `test_candidate_set_adapts_to_shape`。

## 第二部分：判断题

### 第 4 题

**答案：错**

**解析**：T=0 不是"很低的温度"，而是**另一种解码算法**——贪心（argmax）。数学上 `z_i / T` 在 T=0 处无定义（除零）；T→0 的极限确实是 one-hot，但极限不是函数值。API 语义里 `temperature=0` 是"走贪心路径"的开关，不是 softmax 的合法输入。因此 `SamplingParams` 允许 `temperature=0.0`（参数层面合法），而 `softmax_with_temperature` 显式拒绝 T=0 并提示改用 argmax（函数层面非法）——两个层面的语义分工是刻意的。

### 第 5 题

**答案：对**

**解析**：这是 2.4 节的核心推导。Agent 的输出消费者是**解析器**（`parse_react_output` 要求严格格式）而非人；高温度从长尾抽中的 token 会破坏格式。更隐蔽的是放大效应：ReAct 循环里每步输出都是后续步骤的输入，早期的一个随机波动沿轨迹传播放大——单轮对话的温度噪声只影响一句话，Agent 里的噪声影响整条任务链。反之，创意写作、头脑风暴、生成红队攻击话术这类"输出即目的、多样性即价值"的场景，温度恰恰是要调高的。一句话：温度是给欣赏多样性的人准备的，不是给执行精确格式的机器准备的。

### 第 6 题

**答案：错**

**解析**：降级链按**能力从强到弱**排序，方向与成本恰好相反。理由是失败安全的不对称性：降级到更弱模型可能答错（质量风险，损害用户）；降级到更强模型只是多花钱（成本风险，可计量可承受）。故障期间的成本上升应该在监控里被看见（day032 的 CostTracker + `fallback_used` 日志），而不是通过牺牲正确性来避免。对应实现 `rest.sort(key=lambda m: m.capability, reverse=True)` 与测试 `test_fallback_chain_ordered_by_capability`。

## 第三部分：问答题

### 第 7 题

**参考答案**：

（1）自回归生成里，"停止"只是词表中一个特殊的 `<end>` token 被采中——它是**概率事件**，不是机制保证。分布给 `<end>` 的概率再高也不到 1，模型没有"我已经说完了"的内部状态，只有"这个上下文后面接结束标记的概率很大"。因此调用侧必须有一条与概率无关的硬边界：max_tokens 到数就断。

（2）模型没有"遵守规则"的概念，它只会延续上下文的分布。系统提示词里的 `Thought:/Action:` 模板把"这个对话接下来该长什么样"塑造成了高概率形态——模板本质是**对概率分布的先验塑形**。这也解释了为什么提示词措辞的微小变化会改变行为（day030 的 Prompt 评估存在的理由）。

（3）模型每一步选的都是"概率上合理的下一个 token"，而不是"事实上正确的下一个 token"。当问题本身预设了不存在的事实（"拿破仑的宠物龙"），顺着问题分布走、编一个名字的概率往往高于拒答序列的概率——幻觉不是模型的 bug，是 next-token prediction 这个目标函数的必然产物。工程上的缓解（RAG 检索增强、引用溯源、输出评估）都是在系统侧补事实锚点，而不是指望模型自己"变诚实"。

### 第 8 题

**参考答案**：

成本维度：按 token 计费意味着 max_tokens 是单次调用 completion 费用的上限——`CostTracker` 记账时 `completion_tokens = min(估算, max_tokens)` 如实反映了真实 API 的截断计费。

功能维度：max_tokens 是生成的硬截断。答案在第 max_tokens+1 个 token 才完整时，这次调用产出的就是半成品：JSON 缺右括号解析失败、ReAct 的 `Final Answer:` 被截断导致 parser 报格式错误。

为什么设小可能"省小钱亏大钱"：Agent 场景一次失败的调用不是免费的——ReAct 循环会把解析失败作为错误继续消耗后续步骤（更多 LLM 调用、更多 prompt token，而 prompt 恰是 Agent 成本的大头），甚至整个任务失败需要重跑。为省几十 output token 的费用而把截断线压到平均长度附近，换来的是整轮任务的重试成本。正确做法：按最长合理答案设上限，让正常答案永远不被截断；成本控制靠路由（简单任务走便宜模型）与提示词瘦身，而不是靠砍 max_tokens。

### 第 9 题

**参考答案**：

（1）`chosen = "strong"` 只记录了**结果**，回答不了两个月后的追问："这条简单查询为什么走了旗舰模型？"可能的解释有多种——复杂度估计误判、cheap 模型当时被置为不可用、capable 集合为空走了兜底分支——每种解释对应不同的修复动作（调启发式 / 修可用性标志 / 扩容能力档位）。`reason` 把决策时刻的全部依据（复杂度值、匹配规则、价格）冻结下来，审计时不需要反推。这就是 day032"归因维度在记录时就是字段"的同一原则。

（2）`fallback_used` 非空意味着首选模型调用失败、实际服务由降级模型提供。运维含义有三：成本上，本次调用比预期贵（强模型单价高），应在成本报表里单列；可靠性上，它是首选模型故障的证据，应触发对首选模型的健康检查；质量上，降级方向向上所以质量无损，但**持续出现** fallback 说明首选模型的可用性 SLA 有问题，该考虑更换供应商或调整路由表的 `available` 标志。

（3）实验设计（本日编程题实现了它）：准备一份有代表性的混合任务清单（简单+复杂按比例），用同一份清单分别驱动 `CostFirstStrategy` 与 `QualityFirstStrategy` 两个 router；每次调用后按**实际生效模型**（`fallback_used or chosen`）的价格用 `CostTracker` 记账；两个总费用之差就是路由节省的金额，比值即节省比例。对照组（质量优先）不可或缺——没有它，"成本优先花了 $0.0013"是个无意义的绝对数；有了对照组，"节省 37.7%"才是可决策的信息。

## 第四部分：编程题

### 第 10 题

**参考实现**（`scripts/route_cost_demo.py`，已在 day033 快照中实际运行通过）：

```python
"""day033 习题 10 参考答案：路由收益实验 —— 成本优先 vs 质量优先."""

from __future__ import annotations

import sys
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(PROJECT_ROOT))

from smart_research_agent.llm.base import BaseLLM, Message
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.llm.router import (
    CostFirstStrategy,
    ModelRouter,
    ModelSpec,
    QualityFirstStrategy,
)
from smart_research_agent.observability.cost_tracker import CostTracker

TASKS = [
    "2+3 等于几",
    "法国的国鸟是什么",
    "把 1024 除以 8",
    "请分析和对比 RAG 与微调两种技术路线的取舍",
    "对比集中式与分布式记忆架构，并推理各自适用的场景",
]

PRICE_TABLE = {
    name: {"input": price, "output": price}
    for name, price in [("cheap", 0.001), ("mid", 0.01), ("strong", 0.1)]
}


class FailingLLM(BaseLLM):
    def chat(self, messages, temperature: float = 0.7, max_tokens: int = 1024) -> str:
        raise ConnectionError("模拟故障：连接被拒绝")


def make_models(fail_cheap: bool = False) -> list[ModelSpec]:
    return [
        ModelSpec(
            "cheap",
            FailingLLM() if fail_cheap else MockLLM(default="便宜模型的回答"),
            capability=2,
            cost_per_1k=0.001,
        ),
        ModelSpec("mid", MockLLM(default="中档模型的回答"), capability=3, cost_per_1k=0.01),
        ModelSpec("strong", MockLLM(default="强模型的回答"), capability=5, cost_per_1k=0.1),
    ]


def run_strategy(strategy, fail_cheap: bool = False) -> tuple[CostTracker, ModelRouter]:
    router = ModelRouter(make_models(fail_cheap), strategy=strategy)
    tracker = CostTracker(price_table={k: dict(v) for k, v in PRICE_TABLE.items()})
    by_name = {m.name: m.llm for m in router.models}
    for task in TASKS:
        router.chat([Message(role="user", content=task)])
        decision = router.decision_log[-1]
        effective = decision.fallback_used or decision.chosen
        consumed = tracker.record_from_llm(by_name[effective], model=effective)
        assert consumed == 1, "每个任务应恰好产生一次用量记录"
        print(f"  [{effective:>6}] 复杂度{decision.complexity}  "
              f"{task[:20]}…  ({decision.reason})")
    return tracker, router


def main() -> int:
    print("== 成本优先策略 ==")
    cost_tracker, cost_router = run_strategy(CostFirstStrategy())
    print("== 质量优先策略 ==")
    quality_tracker, _ = run_strategy(QualityFirstStrategy())

    c, q = cost_tracker.total_cost, quality_tracker.total_cost
    print(f"成本优先总费用: ${c:.6f}")
    print(f"质量优先总费用: ${q:.6f}")
    print(f"路由节省: {(1 - c / q):.1%}")
    assert c < q, "成本优先必须严格省钱"
    simple_decisions = cost_router.decision_log[:3]
    assert all(d.chosen == "cheap" for d in simple_decisions), "简单任务应全部路由到 cheap"

    print("== 降级验证（cheap 故障） ==")
    fb_tracker, fb_router = run_strategy(CostFirstStrategy(), fail_cheap=True)
    fb_simple = fb_router.decision_log[:3]
    assert all(d.fallback_used is not None for d in fb_simple), "降级记录必须非空"
    print(f"cheap 故障时简单任务降级到: {fb_simple[0].fallback_used}，仍全部得到回复")
    print("全部断言通过")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

**实际运行输出**：

```text

  [ cheap] 复杂度1  2+3 等于几…           (任务复杂度 1，选择满足能力要求…的最便宜模型 cheap)
  [ cheap] 复杂度1  法国的国鸟是什么…      (同上)
  [ cheap] 复杂度1  把 1024 除以 8…       (同上)
  [strong] 复杂度4  请分析和对比 RAG 与微调… (任务复杂度 4，…最便宜模型 strong)
  [strong] 复杂度4  对比集中式与分布式记忆架构… (同上)
== 质量优先策略 ==
  [strong] 复杂度1  2+3 等于几…           (质量优先策略：选择最强可用模型 strong，不考虑成本)
  …（5 条全部走 strong）
成本优先总费用: $0.001308
质量优先总费用: $0.002100
路由节省: 37.7%
== 降级验证（cheap 故障） ==
  [strong] 复杂度1  2+3 等于几…   (chosen=cheap，fallback_used=strong)
  …
cheap 故障时简单任务降级到: strong，仍全部得到回复
全部断言通过
```

**解析**：

1. **路由省的是"为过剩能力付的钱"**：3 条简单任务从 strong（$0.1/1K）切到 cheap（$0.001/1K），单价差 100 倍；2 条复杂任务两种策略都走 strong，无差异。整体节省 37.7%——节省比例完全由任务结构里简单任务的占比决定，这就是为什么路由收益要用**有代表性的任务混合**来度量。
2. **记账键是"实际生效模型"而非"首选模型"**：`effective = decision.fallback_used or decision.chosen`。降级验证段里 chosen 是 cheap 但生效的是 strong——若按 chosen 记账，故障期间的成本会被记到 cheap 头上，报表完全失真。这是 day032"归因要忠实于实际发生"的直接应用。
3. **降级链方向得到验证**：cheap 故障后简单任务落在 strong 而不是 mid——降级链按能力从强到弱（`["strong", "mid"]`），优先用质量风险最小的兜底。成本因此从 $0.001 涨到 $0.1，但这正是设计意图：失败安全偏向多花钱一侧。
4. **MockLLM 实例与模型的对应**：每个 `ModelSpec` 持有独立的 MockLLM，`usage_log` 各自累计，`record_from_llm` 的游标保证同一实例的增量只记一次——`assert consumed == 1` 验证了"每任务恰好一条用量"，多模型场景下的记账接线和单模型一样干净。
