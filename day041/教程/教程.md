## 第一章：什么是 Embedding —— 从离散符号到连续向量

### 1.1 符号表示的困境

计算机里的文本最初是"符号"：词表里的每个词一个编号。要让模型能算，最直接的编码是 **one-hot**——词表大小 N，每个词是一个 N 维向量，只有自己的位置是 1：

```text
"猫"  → [0, 0, 1, 0, ..., 0]
"老虎" → [0, 0, 0, 1, ..., 0]
```

这个表示有两个致命问题：

1. **维度灾难**：词表多大向量就多长，几万维里只有 1 个非零元素；
2. **任意两个词都正交**：one-hot 向量两两余弦相似度为 0——"猫"和"老虎"的距离，与"猫"和"发票"完全一样。符号之间的语义关系，在向量空间里一片空白。

### 1.2 分布式表示：语义即方向

**分布式表示**（distributed representation）的思想是：一个词的含义，由它经常出现的上下文决定（"看它的同伴就知道它是谁"）。把符号映射成一个**低维、稠密**的向量，让语义关系体现为向量空间的几何关系：

- "猫"与"老虎"方向接近（都是猫科动物，上下文相似）；
- 经典的 `国王 - 男人 + 女人 ≈ 女王` 说明方向差还能编码"性别"这样的抽象概念。

**Embedding** 就是把"文本 → 定长稠密向量"的映射本身。现代做法（BERT 之后的编码器）让向量不仅取决于词本身，还取决于整句上下文——"苹果发布了新产品"与"苹果富含维生素"里的"苹果"，得到的向量不同。

### 1.3 一个好的 embedding 的三条性质

我们今天的实现都围绕这三条性质设计：

1. **定长**：无论输入 3 个字还是 300 个字，输出维度固定（`EmbeddingProvider.dimension`）——向量库、检索器、神经网络下游才能消费；
2. **归一化**：向量缩放到单位长度（模长 1）。归一化后余弦相似度退化为点积（`cos(a, b) = a·b`），计算更快，且所有文本落在同一尺度上，**相似度阈值才有稳定的物理含义**——这是第六章 `min_score` 能工作的前提；
3. **余弦度量语义距离**：值域 [-1, 1]，1 是方向完全一致，0 是正交（无关），-1 是方向相反。检索就是"找余弦最近的邻居"。

### 1.4 应用场景：embedding 在项目里的四个落点

| 场景 | 用法 | 项目对应 |
|------|------|----------|
| 语义检索 / RAG | 文档与查询都编码为向量，按余弦取 Top-K | day029 RAG 评估、M6 阶段 |
| 长期记忆 | 对话/知识向量化存储，按需召回 | day009 `LongTermMemory` |
| 去重 / 近似查重 | 相似度高于阈值判为重复 | 数据清洗（day057 数据 pipeline） |
| 聚类 / 分类 | 向量空间里相近的文本归为一类 | 评估报告的场景分析 |

### 1.5 为什么 MockEmbedding 没有语义：雪崩效应

`MockEmbedding` 用 SHA-256 把文本摘要成字节再折算为向量。密码学哈希的核心性质是**雪崩效应**：输入改动一个字符，输出摘要面目全非。这对"防篡改"是美德，对"语义表示"是灾难——"我喜欢学习机器学习"与"我爱学习机器学习"只差两个字，哈希向量却几乎正交。

`scripts/embedding_demo.py` 的实测数字（本机运行）：

```text
== 语义区分度对比（锚点句：我喜欢学习机器学习） ==
     MockEmbedding: 近义句 +0.0491 | 无关句 +0.0370
  CharNgramEmbedding: 近义句 +0.6888 | 无关句 +0.0673
```

哈希伪向量的两个相似度都在 0 附近随机波动，**近义句与无关句无法区分**——用它做检索，排序等于掷骰子。下一章给它做一次真正的升级。

## 第二章：第一个真实语义：CharNgramEmbedding —— 哈希分桶的词汇表示

不装任何依赖，也能做出"有语义"的向量吗？能——只要放弃"理解"，改用**字面重叠**：两段文本共享的字面片段越多，向量越接近。这就是 `CharNgramEmbedding` 的三道工序。

### 2.1 字符 n-gram：切出字面片段

把文本按字符滑窗切成长度为 n 的片段。我们同时取 n=2 与 n=3——二元组捕捉局部搭配，三元组捕捉更长的词形：

```python
def _iter_ngrams(self, text: str):
    """产出文本的全部字符 n-gram.

    文本比某个 n 还短时，把整段文本当作一个 gram 产出——保证
    单字文本也有非零向量，而不是被静默丢弃。
    """
    for n in self._ngram_sizes:
        if len(text) < n:
            yield text
            continue
        for i in range(len(text) - n + 1):
            yield text[i : i + n]
```

选字符而非词语，是因为中文分词需要额外词典/模型，而字符 n-gram 零依赖且对未登录词天然鲁棒。

### 2.2 哈希分桶（hashing trick）：片段 → 桶 → 计数

每个 n-gram 用 MD5 哈希到 `dimension` 个桶之一并累计计数。这个技巧叫 **hashing trick**：不需要维护"片段 → 编号"的词表，哈希函数就是编号器——确定性、零存储、天然支持新片段：

```python
def embed(self, text: str) -> list[float]:
    if not text:
        return [0.0] * self._dimension
    vector = [0.0] * self._dimension
    for gram in self._iter_ngrams(text):
        bucket = int.from_bytes(hashlib.md5(gram.encode("utf-8")).digest()[:4], "big")
        vector[bucket % self._dimension] += 1.0
    return l2_normalize(vector)
```

"我爱学习机器学习"与"我喜欢学习机器学习"共享"学习""机器""机器学习"等大量片段，计数向量方向自然接近；"今天晚饭吃什么"与它们几乎没有共享片段，方向接近正交。第一章的实测数字（0.6888 vs 0.0673）正是这个机制的产出。

### 2.3 L2 归一化：把向量拉回单位球面

计数向量有长有短（长文本计数大），直接比余弦虽然不受模长影响，但归一化仍有两个工程收益：余弦退化为点积（检索更快）、所有向量同尺度（阈值可移植）。归一化函数对零向量做了防御——原样返回，避免除零：

```python
def l2_normalize(vector: list[float]) -> list[float]:
    norm = math.sqrt(sum(x * x for x in vector))
    if norm == 0:
        return list(vector)
    return [x / norm for x in vector]
```

### 2.4 词汇层面语义的天花板

CharNgramEmbedding 的相似度完全来自**字面重叠**，因此有一个原则性盲区：**同义不同形**。"西红柿炒鸡蛋"与"番茄炒蛋"几乎没有共享字符，相似度很低——但任何人类都知道它们说的是同一道菜。要跨越字面、真正"理解"语义，需要神经网络出马。

## 第三章：神经语义向量：SentenceTransformers

### 3.1 原理：编码器 + 池化

[SentenceTransformers](https://www.sbert.net/) 是把 BERT 类编码器改造成"句子级向量器"的框架：文本进入编码器得到每个 token 的上下文表示，再经**池化**（常用 mean pooling，对所有 token 表示取平均）压缩成一个定长句子向量。模型在"语义相近的句子对"上做对比学习训练，产出的向量空间里：**语义距离 ≈ 向量距离**，连"西红柿"与"番茄"都会被拉近。

### 3.2 模型选型：三个常用起点

| 模型 | 维度 | 语言 | 体积量级 | 适用 |
|------|------|------|----------|------|
| `all-MiniLM-L6-v2` | 384 | 英文 | ~90 MB | 英文场景的轻量首选 |
| `paraphrase-multilingual-MiniLM-L12-v2` | 384 | 50+ 语言（含中文） | ~470 MB | 多语言/中文起步（我们的默认） |
| `BAAI/bge-small-zh-v1.5` | 512 | 中文 | ~95 MB | 中文检索专用，MTEB 中文榜常客 |

选型的三条经验：**语言覆盖**（中文场景别用纯英文模型）、**维度与体积**（维度决定存储与检索成本，体积决定首次下载与内存）、**任务匹配**（检索场景优先选为检索训练的模型，如 bge 系列）。

### 3.3 encode：批处理与归一化开关

核心 API 是 `model.encode`：

```python
vectors = model.encode(
    ["第一段文本", "第二段文本"],
    normalize_embeddings=True,   # 输出直接是单位向量
    batch_size=32,               # 默认 32，按显存/内存调整
)
```

两个要点：`normalize_embeddings=True` 让输出直接落在单位球面上，与余弦检索对齐（等价于我们第二章手动做的归一化）；**一次传列表**而非循环传单条——批处理是神经模型的主要吞吐来源。还有一个容易踩的形状坑：`encode("单个字符串")` 返回一维数组，`encode(["单个字符串"])` 返回二维数组，因此我们的 `embed` 一律走列表入口，不写形状分支。

### 3.4 版本演进：维度查询方法的更名与兼容

sentence-transformers 在 v5.4 起把 `get_sentence_embedding_dimension()` 更名为 `get_embedding_dimension()`（旧名仍可用，但会发弃用告警）；2026 年发布的 v6.0 又引入了 ColBERT 风格的多向量编码器等新能力（[$TRAE_REF](https://sbert.net/docs/migration_guide.html)）（[$TRAE_REF](https://www.sbert.net/)）。我们的维度解析做了双向兼容——新方法存在就用新的，否则退回旧方法：

```python
def _resolve_dimension(self) -> int:
    getter = getattr(self._model, "get_embedding_dimension", None)
    if getter is None:
        getter = self._model.get_sentence_embedding_dimension
    dim = getter()
    if not dim:
        raise RuntimeError(f"无法确定模型 {self._model_name} 的输出维度")
    return int(dim)
```

### 3.5 可选依赖的惰性导入

`sentence-transformers` 依赖 torch，安装体积以 GB 计——绝不能作为硬依赖写进 `pyproject.toml`（否则每个克隆仓库的人都被迫装 torch，离线测试也没法跑）。我们的处理是**构造时惰性导入 + 清晰错误**：

```python
if model is not None:
    self._model = model          # 测试注入的假模型，走这条
else:
    try:
        from sentence_transformers import SentenceTransformer
    except ImportError as exc:
        raise RuntimeError(
            "未安装 sentence-transformers，无法构建本地神经 embedding。"
            "请先执行: pip install sentence-transformers"
        ) from exc
    self._model = SentenceTransformer(model_name)
```

效果：不装包的人照常使用其他三个提供方；想用神经向量的人装包即用；错误信息直接给出安装命令。测试则通过 `model` 参数注入假模型对象，**不下载一个权重字节**就覆盖了全部逻辑——`tests/test_embedding.py` 的 `FakeSTModel` 就是这个角色。

## 第四章：云端 Embedding API：OpenAIEmbedding

### 4.1 模型规格：一张表记住 text-embedding-3 家族

OpenAI 的 embedding 端点是 `embeddings.create`。当前主力是 text-embedding-3 系列（[$TRAE_REF](https://www.datallmlab.com/blog/text-embedding-3-small.html)）（[$TRAE_REF](https://embeddingcost.com/openai)）：

| 模型 | 默认维度 | 价格（每百万 token） | 备注 |
|------|----------|----------------------|------|
| `text-embedding-3-small` | 1536 | $0.02 | 我们的默认，性价比之选 |
| `text-embedding-3-large` | 3072 | $0.13 | 更强语义，六倍价格 |
| `text-embedding-ada-002` | 1536 | $0.10 | 旧版，不再推荐 |

两个协议要点：单次请求的输入上限 **8191 token**；`text-embedding-3-*` 支持 `dimensions` 参数把输出截断到更短（如 512 维）——这依赖 **Matryoshka 表示学习**，训练时让向量的前缀子段也携带信息，因此截断后仍可用，只是语义分辨率下降。这些规格被固化在实现的维度表里：

```python
OPENAI_EMBEDDING_DIMENSIONS: dict[str, int] = {
    "text-embedding-3-small": 1536,
    "text-embedding-3-large": 3072,
    "text-embedding-ada-002": 1536,
}
```

未知模型（如自部署的兼容端点）必须显式传 `dimension`，否则构造时抛错——**维度是向量库的硬约束**，宁可早失败，不能带着未知维度往下走。

### 4.2 批量协议：一次 HTTP 编码整批

```python
def embed_batch(self, texts: list[str]) -> list[list[float]]:
    """一次 HTTP 调用编码整批；空输入直接返回，不发请求."""
    if not texts:
        return []
    resp = self._client.embeddings.create(model=self._model, input=list(texts))
    return [list(item.embedding) for item in resp.data]
```

`input` 直接传列表，响应 `data` 数组与输入**顺序一一对应**。对云端 API 来说，批量不是优化而是必需：100 条文本循环单发是 100 次 HTTP 往返，批处理是 1 次——延迟与限流压力差两个数量级。空输入短路返回，不发无意义的请求。

### 4.3 本地还是云端：三条取舍

| 维度 | 本地（SentenceTransformers） | 云端（OpenAI） |
|------|------------------------------|----------------|
| 隐私 | 数据不出机器 | 文本发给第三方 |
| 成本 | 一次下载，永久免费 | 按 token 计费 |
| 延迟 | 取决于本机 CPU/GPU | 网络往返 + 排队 |
| 语义质量 | 受模型大小限制 | 通常更强（大模型蒸馏） |

经验法则：**离线开发与小规模私有数据用本地，大规模高质量检索评估云端**；两者在 `EmbeddingProvider` 抽象下可以随时互换——这正是下一章工厂的价值。

## 第五章：提供方抽象升级 —— embed_batch 与工厂选型

### 5.1 embed_batch：默认实现保向后兼容

抽象基类新增批量接口，但**不是抽象方法**，而是带默认实现的具体方法：

```python
def embed_batch(self, texts: list[str]) -> list[list[float]]:
    """批量编码（day041）.

    默认实现是逐条调用 ``embed``——功能正确但不一定最优。神经模型与
    云端 API 可以覆写它以获得真正的批处理收益（一次前向/一次 HTTP
    处理整批）。设计成**带默认实现的具体方法**而非抽象方法，是为了
    向后兼容：已有的提供方（如 MockEmbedding）不覆写也能继续工作，
    与 day040 ``supports_vision`` 默认值的设计哲学一致。
    """
    return [self.embed(text) for text in texts]
```

这与 day040 `supports_vision` 默认 `False` 是同一套哲学：**扩展抽象时，让旧实现零改动**。`MockEmbedding` 与 `CharNgramEmbedding` 不覆写 `embed_batch`（逐条哈希本来就无批处理收益），`SentenceTransformerEmbedding` 与 `OpenAIEmbedding` 覆写它拿到真实批处理收益。`tests/test_embedding.py` 的 `CountingEmbedding` 用调用计数验证了默认实现"逐条调用 embed"的语义。

### 5.2 default_embedding：按配置选型

```python
def default_embedding() -> EmbeddingProvider:
    provider = settings.embedding_provider
    if provider == "mock":
        return MockEmbedding()
    if provider == "char-ngram":
        return CharNgramEmbedding()
    if provider == "sentence-transformer":
        return SentenceTransformerEmbedding(model_name=settings.embedding_model)
    if provider == "openai":
        if not settings.openai_api_key:
            logger.warning("未配置 OPENAI_API_KEY，embedding 退回 CharNgramEmbedding 离线实现")
            return CharNgramEmbedding()
        return OpenAIEmbedding(model=settings.openai_embedding_model)
    raise ValueError(
        f"未知 embedding_provider: {provider}，"
        "可选值: mock / char-ngram / sentence-transformer / openai"
    )
```

`openai` 分支的退避策略与 `default_llm` 完全同构：**未配置密钥不报错，退回离线实现并记告警**——服务在任何开发机上都能启动，配置缺失是日志里的告警而不是启动时的崩溃。

### 5.3 配置项：三个新 settings

`config.py` 新增（`.env.example` 同步）：

```python

# sentence-transformer 提供方使用的本地模型名

openai_embedding_model: str = "text-embedding-3-small"
```

默认 `char-ngram` 是刻意的：它是**离线可用范围内语义最好的**选项。本地模型名与云端模型名分成两个字段，因为一个字段服务两种默认值必然互相打架——配置的清晰度值得多一行。

## 第六章：消费方升级 —— 阈值过滤、批量写入与一个真值性陷阱

### 6.1 min_score：真实语义让阈值有了意义

向量库 `search` 新增可选的 `min_score`：

```python
if min_score is not None:
    scored = [(r, score) for r, score in scored if score >= min_score]
```

为什么这个功能在 day009 没有、今天才加？因为**阈值只对真实语义 embedding 有意义**：MockEmbedding 的相似度在 0 附近随机波动，任何阈值都是噪声过滤器；CharNgramEmbedding 与神经向量的相似度才有可解释的梯度——"低于 0.2 的大概率不相关"是可以说出口的判断。注意过滤后**不递补**：凑不满 top_k 就返回更少，"宁缺毋滥"是检索场景的正确语义——把不相关的结果硬塞给下游 RAG，比少给一条危害大得多。

### 6.2 remember_many：一次编码写整批

`LongTermMemory` 新增批量写入，`recall` 透传 `min_score`：

```python
def remember_many(self, texts, metadatas=None) -> list[str]:
    if metadatas is not None and len(metadatas) != len(texts):
        raise ValueError("metadatas 长度必须与 texts 一致")
    vectors = self._embedding.embed_batch(list(texts))
    ...
```

对哈希提供方这只是代码简洁；对神经/云端提供方，这是"一次前向/一次 HTTP"与"N 次"的区别——批量接口在抽象层的一个签名，最终变成了消费方的真实性能收益。

### 6.3 一个真值性陷阱：空向量库是假值

写批量测试时踩出了一个 day009 埋下的 bug。原构造器：

```python
self._store = store or InMemoryVectorStore()   # 旧代码
```

`InMemoryVectorStore` 定义了 `__len__`——**空库的长度是 0，布尔值为假**。于是调用方传入一个空库时，`store or ...` 会把它静默替换成新库：写入进了新库，调用方拿着旧库查询，永远查不到任何东西。修复是显式判 `None`：

```python
# 必须用 is None 判断：空向量库 __len__ == 0 是假值，
# `store or ...` 会把调用方传入的空库静默换成新库（day041 修复）
self._store = store if store is not None else InMemoryVectorStore()
```

教训：**`x or default` 只适合"假值等价于缺失"的场景**；容器类一旦定义了 `__len__`/`__bool__`，空实例就是假值，默认值回退必须用 `is None`。这类 bug 在测试里很难被发现（旧测试从不注入空库），而一个"注入空库并断言记录落位"的用例立刻让它现形——这就是边界用例的价值。

## 第七章：API 端点 —— /embeddings 与 /embeddings/similarity

### 7.1 契约设计

两个端点共用 `app.state.embedding` 注入的提供方（`create_app(embedding=...)` 可替换，测试注入 `CharNgramEmbedding` 全程离线）：

| 端点 | 请求体 | 响应体 | 说明 |
|------|--------|--------|------|
| `POST /embeddings` | `{"texts": [...]}`（1~32 条） | `{"provider", "dimension", "vectors"}` | 批量编码，向量与输入顺序对应 |
| `POST /embeddings/similarity` | `{"text_a", "text_b"}` | `{"similarity", "provider"}` | 余弦相似度，值域 [-1, 1] |

两处契约细节：

- **批量入口优先**：`/embeddings` 的请求体是列表而非单字符串——对云端提供方，客户端一次请求编码整批，而不是 N 次 HTTP；`max_length=32` 限制单批条数，由 Pydantic 在路由之前校验，超限直接 422；
- **相似度端点走一次 embed_batch**：`embedding.embed_batch([req.text_a, req.text_b])` 而非两次 `embed`——对云端提供方就是一次 HTTP；相似度计算复用向量库的 `cosine_similarity`，与检索链路同一口径，**接口演示与生产检索不会出现两套度量**。

### 7.2 响应为什么带 provider 与 dimension

向量本身是一串没有自描述能力的浮点数：1536 维的向量和 384 维的向量混在一起毫无意义，不同提供方编出的向量更不可互相比较。响应里带上 `provider` 与 `dimension`，客户端才能判断"这批向量能不能和我库里已有的放在一起比"。**向量只有配合元信息才是契约**，这与 day039 `RouteDecision` 记录"为什么选了这个模型"是同一种可观测性设计。

### 7.3 测试覆盖

`test_api.py` 的 `TestEmbeddingsEndpoints` 覆盖：正常编码（维度与条数断言）、默认提供方（不注入时走 `default_embedding()` 得到 CharNgramEmbedding）、空列表 422、超批量上限 422、相同文本相似度为 1、语义序保持（近义对 > 无关对）、空文本 422、OpenAPI 文档包含两个端点与四个新模型。配合 `test_embedding.py` 的 46 个模块级用例，**提供方逻辑与 HTTP 契约各有独立防线**。
