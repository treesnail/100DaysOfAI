## 第一章：为什么需要 MCP —— N×M 集成困境

### 1.1 先看清问题：每个 Agent 都在重复造连接器

回顾我们 M1 阶段的 SmartResearch Agent：它有工具注册表（`ToolRegistry`），注册了 calculator；有短期/长期记忆；有规划器。现在假设我们要让它接入三个外部能力：读本地文件、查公司内部知识库、调一个天气 API。

传统做法是为每个能力写一个定制集成：

```text
                    ┌── 文件系统集成代码
SmartResearch Agent ┼── 知识库 API 集成代码
                    └── 天气 API 集成代码
```

看似自然，直到你把视角放大到整个行业：市面上有 M 个 Agent 应用（我们的项目、Cursor、Claude Desktop、各种 IDE 插件……），有 N 个能力提供方（文件系统、GitHub、数据库、搜索引擎……）。每个应用都要为每个提供方写一份对接代码，总集成量是 **M × N**：

```text
没有标准协议：M 个应用 × N 个能力 = M×N 份定制集成

应用A ──┬── 能力1        应用B ──┬── 能力1
        ├── 能力2                ├── 能力2
        └── 能力3                └── 能力3
        （每根线都是一份定制代码，接口各不相同）
```

这个组合爆炸带来三个具体恶果：

- **重复劳动**：第 M+1 个应用要接能力 1 时，前面 M 个应用的对接代码完全帮不上忙——它们各自用了不同的函数签名、不同的错误处理、不同的鉴权方式。
- **能力提供方痛苦**：GitHub 想让所有 Agent 都能用它的 API，难道要为每个 Agent 框架写一个插件？
- **运行时才知的工具无法接入**：我们的 `ToolRegistry` 是**编译期硬编码**的——工具集在写代码时就定死了。如果想让 Agent 连接一个"用户自己部署的服务"，程序根本无法预知那个服务有什么工具。

### 1.2 解法：把"集成"变成"协议"

MCP（Model Context Protocol，Anthropic 于 2024 年 11 月发布并开源）的思路一句话就能说完：**在 Agent 应用和能力提供方之间定义一个标准协议，双方各自实现协议的一侧**。

```text
有了标准协议：M 个应用 + N 个能力 = M+N 份协议实现

应用A ──┐                    ┌── 能力1
应用B ──┼── MCP 协议（标准） ──┼── 能力2
应用C ──┘                    └── 能力3
        每侧只需实现一次协议，即可与对侧所有实现互通
```

这个模式在软件史上反复出现，每次都带来生态爆发：

| 类比 | 标准化之前 | 标准化之后 |
|------|-----------|-----------|
| USB | 每种外设一种接口（串口/并口/PS2） | 任何外设插任何电脑 |
| HTTP | 每个客户端-服务端私有协议 | 任何浏览器访问任何网站 |
| LSP（语言服务器协议） | 每个编辑器为每种语言写插件 | 一种语言实现一次 LSP Server，所有编辑器可用 |
| **MCP** | 每个 Agent 为每个能力写集成 | 一个能力实现一次 MCP Server，所有 Agent 可用 |

LSP 是最贴切的类比：它把"编辑器 ↔ 语言智能"解耦成协议两侧；MCP 把"Agent ↔ 上下文能力"解耦成协议两侧。**协议的本质是一份双方同意遵守的消息格式契约——契约稳定，两侧就可以独立演进。**

### 1.3 MCP 不是什么

澄清两个常见误解，能帮你更准确地定位它：

- **MCP 不是工具调用协议的全部**。LLM 的 Function Calling（模型输出"我想调用某工具"的结构化请求）发生在 Agent 应用与模型之间；MCP 发生在 Agent 应用与能力提供方之间。两者是链路的不同环节，互补而非竞争。
- **MCP 不传输模型推理**。MCP Server 不与 LLM 直接对话，它只是被动地提供数据（Resources）、执行动作（Tools）、供给模板（Prompts）。模型推理完全在 Host 一侧。

> 思考题：MCP 标准化的是"应用 ↔ 能力"这一侧。如果某天各家 LLM 的 Function Calling 格式也统一了，MCP 还有存在的必要吗？为什么？

## 第二章：MCP 架构 —— Host、Client、Server 三角

### 2.1 三个角色，各管一段

MCP 官方架构定义了三个角色，初学者最容易把它们混为一谈。先看图：

```text
┌──────────────────────────────────────────────────────┐
│  Host（宿主应用）—— 用户直接面对的完整应用              │
│  例如：Claude Desktop、IDE、我们的 SmartResearch Agent │
│                                                      │
│  ┌────────────┐   ┌────────────┐   ┌────────────┐    │
│  │  Client 1  │   │  Client 2  │   │  Client 3  │    │
│  │（协议连接） │   │（协议连接） │   │（协议连接） │    │
│  └─────┬──────┘   └─────┬──────┘   └─────┬──────┘    │
└────────┼────────────────┼────────────────┼──────────┘
         │ MCP 协议        │ MCP 协议        │ MCP 协议
         ▼                ▼                ▼
   ┌──────────┐     ┌──────────┐     ┌──────────┐
   │ Server A │     │ Server B │     │ Server C │
   │ 文件系统  │     │ 知识库    │     │ 天气服务  │
   └──────────┘     └──────────┘     └──────────┘
```

- **Host（宿主）**：完整的 Agent 应用本体。它持有 LLM 连接、跑 ReAct/规划循环、决定"什么时候需要外部能力"。我们的 SmartResearch Agent 未来就是 Host。
- **Client（客户端）**：Host 内部的协议连接器，**与某一个 Server 保持一对一的有状态连接**。一个 Host 想连三个 Server，就维护三个 Client 实例。Client 负责协议细节：握手、发请求、收响应、处理通知。
- **Server（服务端）**：能力提供方。一个轻量进程，通过 MCP 暴露自己的 Resources/Tools/Prompts。Server 不需要知道 LLM 的存在，它只响应协议消息。

为什么要拆出 Client 这一层，而不是 Host 直接连 Server？**因为一个 Host 通常同时连多个 Server，而每个连接都是有状态的会话**（有握手、有能力协商、有订阅关系）。把每条连接的状态封装在一个 Client 对象里，Host 就可以用"管理 N 个 Client"的统一方式管理 N 条连接，而不是把 N 份协议状态混在自己的主逻辑里。这与我们在 day001 就强调的"关注点分离"是同一思想。

### 2.2 传输层：stdio 与 SSE/HTTP

协议消息总要通过某种物理通道传输。MCP 定义了两种主要传输方式：

**stdio（标准输入输出）**：Server 是 Host 启动的一个子进程，双方通过子进程的 stdin/stdout 交换消息——一行一条 JSON 消息。

```text
Host 进程                          Server 子进程
  │  {"jsonrpc":"2.0","id":1,...}  │
  │ ──────── stdin ──────────────▶ │
  │                                │ 处理请求
  │  {"jsonrpc":"2.0","id":1,...}  │
  │ ◀─────── stdout ────────────── │
```

stdio 的优点：**零网络配置、天然进程隔离、无需鉴权**（能启动子进程本身就代表有权限）。缺点也很明确：只能本地用。它适合"随应用分发的本地能力"——文件系统、本地数据库、命令行工具。

**SSE / Streamable HTTP**：Server 是一个独立的网络服务，Client 通过 HTTP 发请求，Server 可以通过 SSE（Server-Sent Events）长连接主动推送通知。适合远程部署的共享服务——公司知识库、团队共享的工具服务。代价是要处理网络世界的一切问题：鉴权、超时、断线重连。

| 维度 | stdio | SSE / HTTP |
|------|-------|-----------|
| 部署位置 | 本地子进程 | 本地或远程服务 |
| 连接方数量 | 一个 Host 独占 | 可被多个 Client 共享 |
| 鉴权 | 不需要（进程隔离即安全边界） | 必须（HTTP 世界没有默认信任） |
| 运维成本 | 零（随 Host 启停） | 需要独立部署、健康检查 |
| 本项目对应 | day019 的 FastMCP Server | day022 的 Docker 部署 |

关键洞察：**传输方式可以换，消息格式不变**。同一份 `initialize` 请求，走 stdin 还是走 HTTP，内容一字不差——这就是"协议与传输解耦"的设计。我们今天的建模层完全不涉及传输，正是这个解耦的体现。

### 2.3 消息格式：JSON-RPC 2.0

MCP 的消息层直接采用了 **JSON-RPC 2.0**——一个 2010 年就定稿的轻量远程调用规范。为什么 MCP 不自己发明消息格式？因为 JSON-RPC 已经把"请求-响应匹配、错误表达、通知"这三件事解决得干净彻底，没有重造轮子的理由。

JSON-RPC 2.0 只有三种消息，我们今天全部建模了（完整代码见 [mcp_server/protocol.py](../源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py)）：

**（1）请求（Request）**——调用一个方法，期待一个响应：

```json
{"jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": {"name": "calculator"}}
```

四个字段各司其职：`jsonrpc` 锁定协议版本；`id` 是请求-响应的匹配键（调用方可能同时发出多个请求，靠 id 把回来的响应对号入座）；`method` 是要调用的方法名；`params` 是方法参数。

**（2）成功响应（Response）**——id 必须与对应请求一致：

```json
{"jsonrpc": "2.0", "id": 1, "result": {"content": "ok"}}
```

**（3）错误响应（Error）**——同样带 id，但 result 换成了 error 对象：

```json
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "方法不存在"}}
```

`error.code` 是整数错误码，JSON-RPC 规范保留了 -32768 ~ -32000 这段作为标准码（我们在 `protocol.py` 里定义了常量：`-32700` 解析失败、`-32600` 非法请求、`-32601` 方法不存在、`-32602` 参数非法、`-32603` 内部错误）；业务自定义错误码要用这段区间之外的值，避免与规范冲突。

还有一个我们今天没有建模但值得知道的第四种形态：**通知（Notification）**——不带 `id` 的请求，发送方不期待任何响应。比如握手完成后 Client 发送的 `notifications/initialized`（"我准备好了"），就是一条通知。**有没有 id，是"请求"与"通知"的唯一区别**——这是 JSON-RPC 设计的精妙之处：用一个字段的存在性区分两种语义，而不是引入新的消息类型。

> 思考题：为什么错误响应里 `id` 允许为 `None`？提示：如果收到的报文根本不是合法 JSON，服务器连请求的 id 都解析不出来。

## 第三章：生命周期 —— 一切从 initialize 握手开始

### 3.1 为什么不能"上来就调"

MCP 连接是有状态的会话，不是无状态的 HTTP 接口。Client 连上 Server 后的第一条消息**必须**是 `initialize` 握手，这解决了三个无法绕过的问题：

1. **版本协商**：协议会演进，Client 和 Server 可能基于不同版本的规范实现。握手时双方互报协议版本，确认一个彼此都懂的交集——版本对不上时立刻失败，比通信到一半才发现语义误解要好得多。
2. **能力发现（Capability Negotiation）**：Server 不一定同时暴露 Resources、Tools、Prompts 三类能力，Client 也不一定都消费。握手中双方显式声明"我支持什么"，后续通信就可以跳过对方不支持的方法族，避免"调了才发现没实现"。
3. **身份识别**：`clientInfo` / `serverInfo` 让双方知道"对面是谁"，用于日志、审计与兼容性适配。

### 3.2 握手时序

完整的 MCP 生命周期是一个三段式：**握手 → 正常通信 → 关闭**。

```text
Client                                    Server
  │                                         │
  │  1. initialize 请求                      │
  │     {protocolVersion, capabilities,      │
  │      clientInfo}                         │
  │ ────────────────────────────────────────▶│
  │                                         │ 校验版本、记录 Client 能力
  │  2. initialize 响应                      │
  │     {protocolVersion, capabilities,      │
  │      serverInfo}                         │
  │ ◀────────────────────────────────────────│
  │                                         │
  │  3. notifications/initialized（通知）     │
  │ ────────────────────────────────────────▶│
  │                                         │
  │ ══════ 握手完成，进入正常通信 ═══════════ │
  │                                         │
  │  resources/list ────────────────────────▶│
  │ ◀──────────────────── {resources: [...]} │
  │  tools/call ────────────────────────────▶│
  │ ◀──────────────────── {content: ...}     │
```

三个细节值得强调：

- **响应的 id 必须等于请求的 id**。这不是礼貌，是协议正确性的根基——Client 靠它确认"这个响应确实是在回答我的握手请求"。我们测试里的 `test_handshake_id_must_match` 守的就是这一条。
- **initialized 通知是握手的收尾动作**。Server 回完响应后，Client 还要主动发一条"我确认收到了，开始干活"的通知。为什么需要这一步？因为 Server 可能在收到这个通知后才启动一些昂贵的初始化（比如建立索引），避免为"连上又立刻断开"的无效连接浪费资源。
- **握手只发生一次**。之后的 `resources/list`、`tools/call` 等方法调用都不再携带版本与能力信息——这些已经在会话建立时固化了。有状态会话的效率正体现在这里：**一次协商，全程有效**。

### 3.3 我们的握手建模

今天的 `protocol.py` 用两个函数把握手消息固化为可复用的构造函数（完整代码见 [mcp_server/protocol.py](../源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py)）：

```python
def build_initialize_request(...) -> JsonRpcRequest:
    return JsonRpcRequest(
        id=request_id,
        method="initialize",
        params={
            "protocolVersion": protocol_version,
            "capabilities": {},
            "clientInfo": {"name": client_name, "version": client_version},
        },
    )
```

```python
def build_initialize_response(...) -> JsonRpcResponse:
    if capabilities is None:
        capabilities = {"resources": {}, "tools": {}, "prompts": {}}
    return JsonRpcResponse(
        id=request_id,
        result={
            "protocolVersion": protocol_version,
            "capabilities": capabilities,
            "serverInfo": {"name": server_name, "version": server_version},
        },
    )
```

两个设计决定说一说"为什么"：

**为什么用构造函数而不是让调用方直接拼 dict？** 握手的 params/result 结构是协议规范写死的（`protocolVersion` 用驼峰命名、`clientInfo` 嵌套 name/version……）。让调用方手写 dict，等于把规范细节散布到每个调用点，写错一个 key 就握手失败。构造函数把规范封装在一处，调用方只传业务参数（名字、版本）——**这与 day005 的 BaseLLM 封装 HTTP 细节是同一手法：把易错的结构细节收敛到一个受控的函数里**。

**为什么 capabilities 默认是三个空 dict 而不是 `{}`？** 因为"显式声明支持三类能力但各自暂无内容"和"什么都没声明"在语义上不同：前者告诉 Client"你可以放心调 `tools/list`，只是现在为空"；后者让 Client 无法判断对方到底支不支持 tools。协议建模里，**默认值本身就是一份声明**。

## 第四章：三类原语 —— Resources、Tools、Prompts

### 4.1 为什么是三类，而不是统一成"工具"

很多 Agent 框架只有"工具"一个概念，MCP 却刻意把能力切成三类。这不是洁癖，而是因为这三种东西在**控制权归属**和**副作用语义**上有本质差异：

| 维度 | Resources | Tools | Prompts |
|------|-----------|-------|---------|
| 一句话定位 | 可寻址的**只读数据** | 可执行的**动作** | 可填充的**提示词模板** |
| 控制权 | 应用决定何时读取 | **模型决定**何时调用 | **用户决定**何时使用 |
| 副作用 | 无（读不改变状态） | 通常有（写、发请求、执行命令） | 无（只是文本模板） |
| 寻址方式 | URI（`memory://notes/today`） | 名称 + 参数（JSON Schema） | 名称 + 参数 |
| 典型例子 | 知识库文档、配置文件、日志 | 搜索、计算、发邮件 | "调研报告模板"、"代码评审模板" |

"控制权归属"这一行是理解三者的钥匙：

- **Resources 由应用控制**。Host 决定"把哪几份资源塞进模型上下文"。模型本身通常不主动读资源——它消费的是 Host 已经放好的内容。所以 Resources 是**被动的数据供给**。
- **Tools 由模型控制**。模型在推理过程中自主决定"我现在需要调 search 了"。这正是我们 day003~006 已经熟悉的工具调用，所以 Tools 会有副作用——模型的一个决定可能真实地改变世界（发出一封邮件），这也是为什么生产环境的 Tool 调用往往需要人类确认。
- **Prompts 由用户控制**。它们是"预制的工作流入口"：用户在 Host 的界面里选"调研报告模板"，填上主题，模板展开成一组消息发给模型。Prompts 把 Server 作者沉淀的最佳实践变成了用户可复用的入口。

用一句话记：**Resource 是名词（数据），Tool 是动词（动作），Prompt 是句型（模板）。**

### 4.2 三类原语的描述结构

我们为三类原语各建了一个 pydantic 模型（`ResourceDescriptor` / `ToolDescriptor` / `PromptDescriptor`），对照看它们的字段设计：

```python
class ResourceDescriptor(BaseModel):
    uri: str = Field(min_length=1)          # URI 是资源的唯一标识
    name: str = Field(min_length=1)
    description: str = ""
    mime_type: str = Field(default="text/plain", min_length=1)

class ToolDescriptor(BaseModel):
    name: str = Field(min_length=1)
    description: str = ""
    input_schema: dict[str, Any] = Field(default_factory=dict)  # JSON Schema

class PromptDescriptor(BaseModel):
    name: str = Field(min_length=1)
    description: str = ""
    arguments: list[PromptArgument] = Field(default_factory=list)
```

三个差异点各有讲究：

- **Resource 有 `mime_type`，Tool/Prompt 没有**。资源是"内容"，Client 需要知道内容的格式才能正确处理（`text/plain` 直接展示、`application/json` 可以解析、图片类型走多模态）。工具的返回值格式由调用结果自身描述，模板展开后是文本，都不需要静态的 MIME 声明。
- **Tool 的 `input_schema` 是 JSON Schema**。模型要自主决定调用工具，就必须知道"这个工具接受什么参数、各是什么类型、哪些必填"。JSON Schema 是描述这个契约的行业标准，LLM 的 Function Calling 也用它——MCP 直接复用，意味着我们的 `ToolDescriptor.input_schema` 将来可以几乎原样转成 Function Calling 的 functions 定义。
- **Prompt 的 `arguments` 是显式的参数列表**。每个参数有 `name` / `description` / `required`。为什么不用 JSON Schema？因为 Prompt 参数是**给用户填的表单**，不是给模型调的接口——`required` 字段直接对应表单上的"必填"标记，语义比 JSON Schema 的 `required` 数组更贴合交互场景。

### 4.3 URI：资源的寻址方案

Resource 用 URI 寻址是深思熟虑的设计。URI 的 scheme 天然表达了"这份数据存在哪类存储里"：

```text
file:///project/README.md        本地文件
memory://notes/2025-08-11        记忆系统里的笔记
kb://docs/rag-survey             知识库文档
config://agent/tools             配置项
```

对 Client 来说，**它不需要理解 scheme 的语义**——它只管把 URI 原样传给 `resources/read`，Server 负责把 URI 解析成具体内容。这与 HTTP 里浏览器不需要理解 URL 背后的文件系统是同构的：**URI 是不透明的标识符，解释权属 Server**。这个"不透明性"让 Server 可以自由组织内部存储，随意重构而不破坏 Client。

## 第五章：用 pydantic 建模协议 —— 类型即契约

### 5.1 为什么用 pydantic 而不是 dict 满天飞

协议消息天然是"跨进程序边界的数据"（来自网络、来自子进程），这类数据必须过校验才能进入系统内部——这和 day010 对待 LLM 输出的态度完全一样：**不可信输入，显式校验**。pydantic 把"校验规则"写进了类型定义本身，声明即校验。

看 `protocol.py` 里最核心的一个技巧：

```python
class JsonRpcRequest(BaseModel):
    jsonrpc: Literal["2.0"] = JSONRPC_VERSION
    id: int | str
    method: str = Field(min_length=1)
    params: dict[str, Any] = Field(default_factory=dict)
```

**`Literal["2.0"]` 是整行最精妙的地方**。它把"jsonrpc 字段必须等于字符串 2.0"这条协议规则直接编码成了类型约束：构造或反序列化时传入 `"1.0"` 或 `"3.0"`，pydantic 立刻抛 `ValidationError`。我们不需要写一行 `if` 校验代码——**类型本身就是校验器**。同时默认值 `"2.0"` 让构造方永远不用关心这个字段：协议版本由建模层锁定，调用方想错都错不了。

其余字段同理：`id: int | str` 对应规范"id 可以是数字或字符串"（但不允许 None——区分于错误响应里的 `id: int | str | None`，因为解析失败的报文可能没有 id）；`method: str = Field(min_length=1)` 挡住空方法名；`params` 默认空 dict，让无参请求不必显式传 `{}`。

### 5.2 往返测试：序列化正确性的金标准

协议模型的核心质量指标是**往返一致性（round-trip）**：模型 → JSON 字符串 → 模型，必须无损。`tests/test_mcp_protocol.py` 里每条消息类型都有一个往返测试：

```python
def test_request_round_trip(self):
    req = JsonRpcRequest(id=1, method="tools/call", params={"name": "calculator"})
    restored = JsonRpcRequest.model_validate_json(req.model_dump_json())
    assert restored == req
```

为什么往返测试是协议建模的"金标准"？因为协议的整个存在意义就是"发出去的消息能被对方正确还原"。`model_dump_json()` 模拟"我方发送"，`model_validate_json()` 模拟"对方接收解析"——两个模型实例相等，意味着消息穿越序列化边界后语义无损。pydantic 模型的 `__eq__` 按字段值比较，所以这个 `assert` 一次性校验了所有字段。

### 5.3 包名必须叫 mcp_server：一次真实的命名事故防御

今天目录结构里有个刻意为之的命名决策：我们的包叫 `smart_research_agent.mcp_server`，**绝不能叫 `smart_research_agent.mcp`**。

原因：venv 里已经安装了官方的 `mcp` 包（day017 起要用它）。Python 的导入解析按 `sys.path` 顺序查找，如果我们的包也叫 `mcp` 且恰好排在前面，那么 `import mcp`——包括官方生态里其他库写的 `import mcp`——都会解析到我们的包而不是官方的。这种**模块遮蔽（shadowing）**引发的故障极难排查：代码看起来都对，报错却在完全不相干的地方。

同理，这也是为什么不把项目里的任何东西命名为 `json`、`email`、`types` 这类标准库名字。**命名时先问一句：这个名字是不是已经被我依赖的生态占用了？** 这条经验比任何具体技术都长寿。

### 5.4 与官方 mcp.types 的关系

今天的建模是"教学简化版"。官方 `mcp` 包的 `mcp.types` 模块里有同一套消息的完整 pydantic 模型（`JSONRPCRequest`、`InitializeRequest` 等），字段更全、还包含分页游标、通知等我们今天没建模的部分。从 day017 接入 FastMCP 开始，线上代码会切到官方类型；今天的 `protocol.py` 保留下来有两个价值：

1. **学习参照**：字段少、校验显式，逐字段对照官方规范读，比直接读官方源码容易得多。
2. **测试基线**：`tests/test_mcp_protocol.py` 固化了我们对协议最小核心（三种消息 + 三类描述 + 握手）的理解，将来换官方类型时，这批测试断言的语义依然是验收标准。

## 第六章：规划 SmartResearch Agent 的 MCP Server 边界

### 6.1 边界设计的原则：只暴露"别人需要的"

今天最后一个、也是最重要的设计任务：盘点 M1 阶段的资产，决定哪些暴露成 MCP 能力、暴露成哪一类、哪些坚决不暴露。

先立三条原则：

1. **能力即接口**：暴露的每一个 Resource/Tool/Prompt 都是对外契约，改了就破坏 Client——只暴露确定要长期支持的东西。
2. **原语选对类**：用 4.1 的"控制权 + 副作用"尺子量，拿不准时优先选语义最弱的那类（能做成 Resource 就别做成 Tool）。
3. **内部机制不外露**：LLM 调用细节、提示词常量、解析器这些是 Server 的内部实现，不是能力。

### 6.2 资产盘点与归类

| M1 资产 | 位置 | 暴露为 | 理由 |
|---------|------|--------|------|
| 计算器 | `tools/calculator.py` | **Tool** `calculate` | 有"执行"语义，模型自主决定何时调用 |
| 长期记忆条目 | `memory/long_term.py` | **Resource** `memory://notes/{id}` | 只读数据，URI 寻址天然契合 |
| 会话历史快照 | `memory/session.py` | **Resource** `session://{thread_id}/history` | 只读、可寻址 |
| 调研报告模板 | （待新建） | **Prompt** `research_report` | 用户触发的工作流入口，参数：主题、深度 |
| 代码评审模板 | （待新建） | **Prompt** `code_review` | 同上 |
| Planner / ReAct 循环 | `agent/` | **不暴露** | 这是 Host 侧的内部编排逻辑，不是能力 |
| MockLLM / 解析器 | `llm/`、`agent/parser.py` | **不暴露** | 内部实现细节 |
| 配置项 | `config.py` | **暂不暴露** | 含敏感字段（API key 路径等），等 M2 后期做脱敏的只读视图再议 |

值得单独展开的两个判断：

**为什么"记忆"做成 Resource 而不是 Tool？** 都按 4.1 的尺子量：读取记忆条目是无副作用的只读操作，且每条记忆天然有 ID、可被 URI 寻址（`memory://notes/42`）——Resource 的两个特征全中。如果做成 Tool `read_memory(id)`，模型就要自己决定"何时去翻记忆"，把本该由应用控制的上下文供给交给了概率性的模型决策。**但注意**："写入记忆"（`remember()`）有副作用，如果将来要暴露，那必须做成 Tool——同一资产的不同操作可能归属不同原语，按操作而不是按资产归类。

**为什么 Planner 不暴露成 Tool？** 理论上可以做一个 `plan_task(goal)` 工具。但规划是我们 Agent 的核心编排逻辑，暴露出去意味着别的 Host 可以绕过我们的执行层直接消费规划结果——这既不是当前的学习目标，也会让"M2 阶段调试规划逻辑"的每次改动都牵动协议契约。day020 做 Client 集成时，我们会从**消费方**视角重新审视这个决定。

### 6.3 目标边界一览

M2 阶段结束时，SmartResearch Agent 的 MCP Server 将呈现这样的能力清单：

```text
SmartResearch MCP Server
├── Resources（应用控制，只读数据）
│   ├── memory://notes/{id}              长期记忆条目
│   └── session://{thread_id}/history    会话历史快照
├── Tools（模型控制，有副作用的动作）
│   └── calculate                        数学计算（day003 已有）
└── Prompts（用户控制，提示词模板）
    ├── research_report(topic, depth)    调研报告模板
    └── code_review(code, language)      代码评审模板
```

这份清单就是 day017（Resources）、day018（Tools 与 Prompts）、day019（FastMCP 完整搭建）三天的施工图纸。**今天不实现它们，但今天决定了它们长什么样**——这正是"协议先行"的价值：实现之前先固定契约，实现过程中就不会边写边改接口。

> 思考题：如果未来要把"联网搜索"接入 MCP Server，它该归哪一类？提示：它有副作用吗？谁决定何时触发它？

**实施变更说明（以 day017 起的实际代码为准）**：上面这份清单是设计图纸，day017~day019 落地时做了教学简化，实际实现与图纸有如下差异：

- **Resources 的 URI 不同**：实际落地为 `research://knowledge/{doc_id}`（本地知识库 Markdown）与 `research://config/{key}`（配置项），而非图纸中的 `memory://notes/{id}` 与 `session://{thread_id}/history`。原因： memory/session 资源需要额外接入记忆存储层，教学上先用纯文件读取把 URI 模板与只读语义讲清楚，避免引入额外存储依赖。
- **Prompts 只保留 `research_report`**：`code_review` 模板未实现——一个参数化模板已足以讲清 Prompts 原语，避免重复示例。
- **Tools 以 `calculate` 起步**：与图纸一致；day018 起另加了 `knowledge_search` 把向量检索暴露为模型可调用工具。

图纸的价值在于"协议先行"的思考过程，具体 URI 与能力清单请以下三天（day017~day019）快照中的实际代码为准。

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 引入 MCP 协议 | N×M 集成困境 → 标准化后 M+N | 本章第一、二章 |
| Host/Client/Server 三角 | 有状态连接需要独立的 Client 层封装 | 2.1 |
| stdio 与 HTTP 双传输 | 协议与传输解耦，消息格式不变 | 2.2 |
| 消息层复用 JSON-RPC 2.0 | 请求-响应匹配、错误表达已是 solved problem | 2.3、`protocol.py` |
| initialize 握手先行 | 版本协商 + 能力发现 + 身份识别 | 第三章 |
| 能力三分 Resources/Tools/Prompts | 控制权归属与副作用语义的本质差异 | 第四章 |
| `Literal["2.0"]` 锁版本 | 类型即校验，声明即约束 | `protocol.py` |
| 包名 `mcp_server` | 避免遮蔽官方 `mcp` 包 | `mcp_server/__init__.py` |
| 边界规划：按操作归类 | 记忆读取是 Resource、写入将是 Tool | 6.2 |
