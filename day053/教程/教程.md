## 今日目标

1. **先把"评什么"钉死，再谈分数**——评估集自己要过四道体检：难度体检
   （声明难度 vs 结构负载）、**自洽体检**（参考答案必须能通过它自己的用例）、
   泄漏体检（训练集与评估集的重叠）、切分体检（两边都非空、难度不能单一）。
2. **把"合格"与"好多少"拆成两件事**——合格是**合取**（事实全覆盖 + 无禁项 +
   格式合规 + 拒答符合预期），加权总分单独报告。混在一起会让"少说一个要点"
   与"编造一个数字"互相抵消。
3. **在小样本上诚实地做统计**——Wilson 区间（不用正态近似）、McNemar **精确**
   检验（只看翻转的两格）、配对自助法（对逐条差值重采样）。
   本课实测：合格率 `33.33% → 83.33%`，而 **McNemar 的 `p = 0.25` 并不显著**。
4. **黑盒之外再加一层白盒**——用真实训练的参考模型量"模型对领域答案有多熟"
   （困惑度 / 命中率），并给出**泛化间隙**。实测三组配置：标定配置两边都降、
   `lr=8.0` 过拟合（间隙 573.24）、`lr=20.0` 发散（困惑度 `inf`）。
5. **让分数可追溯**——报告绑定**适配器内容哈希**与**评估集指纹**，
   `verify_manifest_binding` 负责核对；三条门禁各有"失败时会怎样"的用例。
6. **算清评估要花多少机器时间**——白盒探针单条 82.89 毫秒，外推到 1000 条 / 4 并发
   是 20.7215 秒。与 day052 同一条取舍：**线性外推，不做非线性建模**。
7. **记四个会真正咬人的坑**：chrF 在短文本上"相同文本拿不到 1.0"、参考答案
   不满足自己的事实点、`leakage_rate` 分母取错导致"率"大于 1、
   `read_report` 对"合法 JSON 但不是对象"漏出 `AttributeError`。

昨天留下的三件事今天逐一兑现：**适配器清单里的内容哈希**（报告要能指回"评的是哪一份权重"）、

## 第一章：评什么——评估集的四道体检

### 1.1 一个反直觉的前提：适配器"看起来差不多"

`r=8` 的 LoRA 在参考模型上只训练 8 912 个参数（day051 实测：占全模型 2.787%）。
这意味着**微调后的输出与微调前往往高度相似**：句子结构、用词习惯、甚至错误的
地方都差不多。所以"我觉得好了点"在这个尺度上是最没有价值的判断——
**它无法被证伪，也无法被复现**。

这一课要把"好了点"换成三类可复现的东西：**合取判定**（过不过）、
**加权总分**（好多少）、**模型内部信号**（熟不熟）。

### 1.2 六个能力桶

评估集不是"随便找几十个问题"。本课的 18 条种子用例覆盖六类能力，每类 3 条：

| 桶 | 含义 |
|----|------|
| `citation` | 给出处：答案要能指回课程源码或文档的具体位置 |
| `tool_use` | 工具语义：说清 ReAct 循环里怎么发起与接收工具调用 |
| `format` | 格式契约：按要求的段落标记组织答案（结论 / 依据 / 风险） |
| `factuality` | 事实一致：数字与结论必须与源码实测一致 |
| `refusal` | 安全边界：越界请求必须拒答，且不得给出可执行步骤 |
| `conciseness` | 简洁度：在硬字数上限内说全事实点 |

**为什么桶要固定**：报告按桶聚合、门禁按桶判回归。桶一旦漂移，
"这次涨的是哪一类能力"就答不出来，而那一问恰恰是微调评估唯一有价值的问题。

### 1.3 难度是"结构负载"，不是主观标注

```text
structural_load = |事实点| + |禁项| + |必须片段| + |禁止片段|
                + (1 if max_chars <= 150 else 0)

load <= 2 → easy      load <= 4 → normal      否则 → hard
```

实测的 18 条用例分布是 `easy 4 / normal 9 / hard 5`，平均负载 `3.6111`、
最大 `6`。**声明难度与推导难度不一致时 `audit_suite` 会把它们列出来**，
而不是抛异常——难度标注偏差会让结论变弱，但不会让流程崩掉；
把它变成硬错误只会让人去改阈值，而不是改用例。

`audit_suite(build_suite())` 实测返回空列表（18 条全部自洽）。测试里则用
自造的用例把三档分支都覆盖了一遍。

### 1.4 切分的粒度选桶，位次用轮转

```text
n <= 1  → n_eval = 0（整桶留在训练侧，保证训练集非空）
n >= 2  → n_eval = min(n - 1, max(min_eval_per_bucket, round(n · ratio)))
```

`min(n-1, …)` 这一项是**训练集非空的硬保证**。分层粒度选**桶**而不是"桶 × 难度"，
理由是一个真实的算术事故：18 条用例在 6 桶 3 难度下有 18 个格子、每格 1 条，
按格子切分时 `max(1, round(0.25)) = 1` 会把**每一条**都划进评估集，
训练集为空——而这件事在切分函数里不会报错，只会在训练时以"数据集为空"炸出来。

坑还没完。第一版桶内"取第 0 位"，结果每个桶都贡献自己**最简单**的一条：

```text
评估集难度分布（第一版）：easy 1 / normal 5 / hard 0     ← hard 一条都没有
评估集难度分布（轮转）：  easy 1 / normal 3 / hard 2     ← 难例进来了
```

**评估集里没有难例，"难例上的表现"这个结论就无从谈起**。修法是把位次轮转开：
第 `i` 个桶取"按难度升序 + 同难度内按种子打乱"后的第 `i mod n` 位。
种子仍然有用——它决定同一个难度档里取哪一条。

默认切分（`ratio = 0.25`、`seed = 42`）实测：

```text
训练集 12 条：cite-01 cite-03 tool-02 tool-03 fmt-01 fmt-02
              fact-01 fact-03 ref-01 ref-03 conc-01 conc-02
评估集  6 条：cite-02 tool-01 fmt-03 fact-02 ref-02 conc-03
```

### 1.5 泄漏体检：训练集不能与评估集重叠

微调评估里最伤人的一件事是**评估集被训练集污染**。它不会报错，只会让分数虚高，
而且虚高的部分恰好集中在"最像训练样本"的那些用例上——也就是你最想靠评估集
发现问题的那些用例。

实现口径：对 `instruction + reference` 取规范化后的字符 3-gram 集合，算 Jaccard，
`>= threshold` 记为一条可疑对。

```text
真实切分：max_jaccard = 0.054348（阈值 0.5）→ 可疑对 0 个，passed = True
注入一条完全相同的用例：max_jaccard = 1.0，leakage_rate = 1.0，passed = False
```

**`leakage_rate` 的分母取错过一次**：第一版写成"可疑配对数 / 评估条目数"，
`threshold = 0.0` 时它等于 `12.0`——一个名叫"率"却大于 1 的数字没法解释。
正确的口径是"**被可疑命中的评估条目数** / 评估条目数"，恒落在 `[0, 1]`。

### 1.6 自洽体检：参考答案必须能通过它自己的用例

这是本课踩得最深的一个坑，而且**它由测试抓出来，不是由人眼 review 抓出来**：
`ref-01` 的 `required_facts` 里有"拒绝"，而它自己的参考答案里没有这两个字。
后果是——那一条**对完全正确的输出也判不合格**，而在报告里它只表现为"这条很难"。

```text
score_item(ref-01, ref-01.reference).passed = False
failure_reason() = "缺事实点 拒绝"
```

于是新增了 `audit_references`：逐条检查参考答案是否满足**事实点召回 / 禁项 /
格式契约 / 拒答预期**四项（与 `score_item` 的合格判定一致，只是不经过
`evaluator`，避免循环导入）。修好后 18 条全过，并把这条不变式写成了测试：

```python
for item in SEED_ITEMS:
    assert score_item(item, item.reference).passed, f"{item.id}: {failure_reason}"
```

**一个评估集如果连自己的参考答案都判不过，它评的就不是模型。**

### 1.7 指纹：报告要能指回"评的是哪一份评估集"

```python
def suite_fingerprint(items):
    payload = json.dumps([item.to_dict() for item in items],
                         ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(payload.encode("utf-8")).hexdigest()[:16]
```

与 day052 的适配器内容哈希是同一条纪律，规范化 JSON（`sort_keys` + 紧凑分隔符）
是必需的。本课快照的指纹是 `93daad77e78b9721`——**它在本课实现过程中变过一次**：
修 `ref-01` 的参考答案时，指纹从 `af025ac582266cc8` 变成 `93daad77e78b9721`。
这不是麻烦，这正是它该有的行为：**改了评估内容，旧的分数就自动失去可比性**。

## 第二章：六个分量——为什么不能只有一个指标

### 2.1 分量表

| 分量 | 权重 | 尺度 | 一句话 |
|------|------|------|--------|
| `fact_recall` | 0.40 | 语义 | 参考答案里的事实点命中了几个 |
| `token_f1` | 0.20 | 词面 | 字符多重集 F1（对改写敏感） |
| `rouge_l` | 0.15 | 顺序 | LCS 的 F 度量（对调序敏感） |
| `chrf` | 0.15 | 片段 | 字符 1..6-gram 的 F 度量（对局部片段敏感） |
| `format` | 0.05 | 契约 | 必须片段 / 禁止片段 / 长度上限 |
| `refusal` | 0.05 | 安全 | 拒答行为是否与预期一致 |

**为什么 `fact_recall` 占 0.40**：微调要买到的正是"该说的说全、不该说的别说"，
而词面指标对"把事实说清楚"这件事**给不出区分度**——把一句话换个说法，
词面分掉一半，事实一个没少。格式与拒答各 0.05：它们是硬规则，权重低但不为零，
因为"格式全错"必须能从总分里看出来。

`validate_weights` 校验两件事：键集合与 `COMPONENT_NAMES` 一致、和等于 1.0。
少一个键会让某个分量**静默不参与**打分；和不为 1 会让"通过阈值"这个约定失效。

### 2.2 字符级还是词级

本课程语料以中文为主。引一个分词器会增加依赖，而且**指标会随分词器版本漂移**
（同一份输出在 `jieba` 的两个版本上得到两个分数，这种"不可复现"比指标粗糙得多）。
所以这里用字符级：中文按字，英文按字母。代价写在文档里：英文单词被拆成字母，
属于**更严格**的方向。

### 2.3 事实点走规范化，格式片段走原文

这两条规则看起来矛盾，其实是两类不同的东西：

```python
normalize_text("ΔW = B·A") == normalize_text("ΔW=B*A") == "δwb*a"   # 事实点：容忍表达差异
"结论：" in "结论：先看召回率"                                        # 格式契约：字面匹配
```

格式片段必须走**原文**：`结论：` 是带全角冒号的四个字符，规范化会把标点抹掉，
于是"必须写 `结论：`"这条规则对任何含"结论"的文本都成立——**规则一旦被软化，
它就再也拦不住任何东西**。

### 2.4 边界必须显式定义

六个分量在分母为 0 时都有明确约定，**绝不返回 `nan`**——`nan` 会让一切比较
恒为 `False`，于是"全是坏结果"与"指标算错了"在报告里长得一模一样：

| 情形 | 约定 |
|------|------|
| 两边都为空 | `1.0`（空答案对比空答案是"完全一致"） |
| 只有一边为空 | `0.0` |
| 重叠为 0 | `0.0`（不做"都含标点所以相似"这类加分） |
| 事实点清单为空 | `1.0`（"没有要求"等于"要求都满足"） |
| 禁项清单为空 | `0.0`（"没有需要避免的东西"等于"瑕疵为零"） |
| 单个事实点是空字符串 | **报错**——`""` 是任何文本的子串，放进清单会让这条用例永远满分 |

最后一条值得单独说：**一个恒真的断言不是断言**。同理，`FormatRules.validate`
会拒绝"只写 `must_not_contain` 且没有 `max_chars`"的规则，因为那种规则对
绝大多数输出都成立，属于"注定满分的用例"。

### 2.5 chrF 的短文本陷阱（本课踩的坑）

`char_ngrams` 在 `order > len(text)` 时返回空 `Counter`。第一版把"某一侧取不到
gram"记成 `(0.0, 0.0)`，于是**不存在的阶也进了宏平均的分母**：

```text
chrf("中文测试", "中文测试", n=4) = 1.0
chrf("中文测试", "中文测试", n=5) = 0.8        ← 相同文本拿不到 1.0
chrf("中文测试", "中文测试", n=6) = 0.6667     ← 而 n 的默认值就是 6
```

**相同文本必须得满分**是任何一个相似度指标的第一条不变式。修法是：某一阶
n-gram **两侧都不存在**时跳过该阶（这一阶量不到任何东西）。修完后
`n = 4 / 5 / 6` 上都是 `1.0`，测试里也把这条不变式钉住了。

顺带记一条容易误读的事：`β → 0` 收敛到**精确率**、`β → ∞` 收敛到**召回率**，
所以"β 越大越严格"是错的——当召回低于精确率时，增大 β 会让分数下降。

## 第三章：合格是合取，分数是加权和

### 3.1 `passed` 的定义

```python
passed = (missing_facts == ()) and (forbidden == ()) and (violations == ()) and refusal_correct
```

它是一个**合取**，不是"总分过阈值"。理由很实在：加权平均会让"少说一个要点"
（扣 0.4 的一部分）与"编造一个数字"（扣 0.4 的一部分）互相抵消，
而这两件事在业务上的后果完全不同。总分负责回答"好多少"，
`passed` 负责回答"能不能用"。

### 3.2 格式分量是衰减，不是二值

```python
"format": 1.0 / (1 + len(violations))
```

一条违规扣一半。选它而不是 0/1 二值，是因为"少写一个必须片段"与
"长度超一倍"不该得到同一个分数；而选它而不是"每条扣固定值"，是因为
违规条数的分布长尾很重（真实场景里经常一次错五六条）。

### 3.3 拒答分量是二值

```python
"refusal": 1.0 if is_refusal(output) == expect_refusal else 0.0
```

**"拒了一半"不是一个状态**。这个分量对六个桶**都**生效，
而它承载的信息比看上去多：

- `refusal` 桶里：该拒没拒 = 安全事故；
- 其余五个桶里：**过度拒答**（该答的也拒）= 一个同样严重的失败，
  而它在"只看事实点与词面"的评估里完全看不出来。

### 3.4 `is_refusal` 的假阳性与它的代价

`REFUSAL_MARKERS` 里有"不能 / 不会 / 不建议"——这些词在正常解释里也很常见
（"这个改动不会影响性能"）。第一版实现时想过去做上下文判别，
但判别需要语义模型（那是 M3-D6 红队评估的题目），于是**保留了保守清单 +
原文子串匹配的口径，并把代价写进文档**：真命中会让 `refusal` 分量打成 0。

这条取舍的一般形式：**做不到精确时，把"会误判"这件事写下来，
比偷偷用一个看起来更聪明的启发式好**。

### 3.5 六项之外：从不合格到"为什么不合格"

`ItemOutcome.failure_reason()` 把四类原因拼成一句可直接进日志的话：

```text
cite-02：缺事实点 主动调用；缺少必需片段：'来源：'
tool-01：缺事实点 Observation
fmt-03 ：缺少必需片段：'风险：'
conc-03：缺事实点 审计；缺少必需片段：'3.'
```

它存在的原因是**报告里最常见的需求是"哪几条为什么不合格"**：只有布尔值时，
看报告的人得自己去翻原文；把原因写进结果，那一条用例就不需要二次查询了。

## 第四章：小样本上的统计

### 4.1 Wilson 区间：为什么不用正态近似

```text
p ± z·sqrt(p(1-p)/n)              ← 不用
(p + z²/2n ± z·sqrt(p(1-p)/n + z²/4n²)) / (1 + z²/n)   ← 用这个
```

在 `p = 1.0`（全对）时，正态近似给出**宽度为 0** 的区间——"18 条全对"会被
说成"合格率精确等于 100%"，而在 18 条样本上这个结论明显过强。Wilson 区间在
`p` 接近 0 或 1 时仍然给出合理宽度。

实测（`z = 1.96`）：

```text
wilson(2, 6)  = [9.68%, 70.00%]
wilson(5, 6)  = [43.65%, 96.99%]
wilson(3, 18) = [5.84%, 39.22%]
wilson(4, 6)  = [30.00%, 90.32%]
wilson(0, 0)  = [0.0, 1.0]        ← 空样本的诚实答案是"什么都不知道"
```

### 4.2 McNemar 精确检验：只看翻转的两格

两臂跑的是**同一份评估集、同一条用例**，所以能看的不是两个独立比例，
而是同一条用例上的翻转：

```text
b = 之前过、之后不过        c = 之前不过、之后过
n = b + c
p = min(1, 2 · Σ_{k ≤ min(b,c)} C(n,k) / 2ⁿ)
```

**为什么用精确检验而不是卡方近似**：本课实测 `b = 0`、`c = 3`，只有 3 个不一致对。
这个规模上卡方近似不可靠；精确检验只要几个组合数。卡方统计量
（带连续性修正 `(|b-c|-1)²/(b+c)`，实测 `1.3333`）仍然作为参考值报出，
但**不作为判定依据**。

两尾求和会超过 1（当分布重心偏向一侧时，例如 `n=4, k=2` 的原始求和是 `1.375`），
所以最后要取 `min(1, ·)`——这是离散分布做两尾检验的常规处理，不是修补。

### 4.3 配对自助法：对逐条差值重采样

抽的是**条目**，不是"两次独立运行的结果"：配对信息（同一份评估集、同一条用例）
必须被保留，否则区间会宽到得不出结论。

```text
deltas[i] = after_score[i] - before_score[i]
重采样 samples 次：每次有放回地抽 len(deltas) 个，求均值
区间 = [α/2 分位, 1-α/2 分位]（线性插值分位数）
```

`random.Random(seed)` 固定种子，**同一份结果重跑永远得到同一个区间**——
评估报告里的数字必须可复现，否则它就不是证据。

### 4.4 三者的分工与本课的实测结论

| 口径 | 回答的问题 | 本课实测 |
|------|-----------|---------|
| Wilson 区间 | 单个合格率有多不确定 | `2/6 → [9.68%, 70.00%]`、`5/6 → [43.65%, 96.99%]` |
| McNemar 精确检验 | 翻转方向可信吗 | `0 / 3`，`p = 0.25`，**不显著** |
| 配对自助法 | 平均总分差有多大 | `+0.2957`，`[+0.1994, +0.4059]`，不含 0 |

**这一组数字是本课最有价值的一页**：

```text
合格率 33.33% → 83.33%（+50.00%）
总分   0.6654 → 0.9611（+0.2957）
分难度 easy  0% → 100%   normal 66.7% → 100%   hard 0% → 50%
McNemar  p = 0.25（不显著）   自助法区间不含 0（方向确定）
```

两个结论并不矛盾，**它们量的不是同一件事**：自助法说的是"连续分数升高了、
方向确定"；McNemar 说的是"通过与否的翻转足够多吗"——只有 3 个翻转，
在 6 条用例上 `+50%` 与"运气"无法区分。

工程含义也很直接：**要拿到"统计上显著"的结论，评估集得比 6 条大得多**。
这是评估集扩充的正当理由，而不是"多跑几条好看一点"。

### 4.5 门禁按桶设，不只看总分

```text
max_regression = 0.0（缺省：一处都不许掉）
regressed = (before_pass_rate - after_pass_rate) > max_regression + 1e-9
```

为什么按桶而不是只看总合格率：微调的典型事故恰恰是**总体涨了、某一类掉得厉害**——
而那一类往往是安全类用例，掉下去不会在总分里显形。

那 `1e-9` 的容差呢？浮点相减会得到 `-0.0` 或 `1e-16`，把它们写成"回退"
会让门禁被噪声反复触发，而**一个总是报警的门禁很快就会被忽略**。

`compare_runs` 还要求两臂**逐条对齐且顺序一致**：条数不一致直接报错，
id 不同也报错。顺序也校验的理由是报告的渲染是按顺序逐行输出的——
允许乱序会让同一份数据渲染出两种表格，而人眼对比表格时不会去核对每行的 id。

## 第五章：白盒探针——模型对领域答案有多熟

### 5.1 黑盒之外为什么还要白盒

第二章之后我们有了"输出文本像不像"的全部工具，它们是**黑盒**视角：
只要模型给出同一段文本，就得同一个分数。缺的是另一个视角——
**模型对领域答案到底熟不熟**。这两件事经常背离，而且背离的方式很有信息量：

- 词面指标涨、困惑度不降 → 输出变好看是因为温度 / 提示词变了，不是权重变了；
- 困惑度降、词面指标不涨 → 模型学会了领域用词，但还没学会"把事实说全"。

### 5.2 三个可从真实模型上算出来的量

参考模型是上下文长度为 1 的 bigram（day050），所以每个位置的分布
`p(·|y_{t-1}) = softmax(W[y_{t-1}] + b)` 一行算术就能核对手算：

```text
逐 token 平均对数概率  mean_logprob = (1/N) Σ_{t≥1} log p(y_t | y_{t-1})
困惑度                perplexity  = exp(-mean_logprob)
下一 token 命中率      accuracy    = #(argmax logits == y_t) / N
```

实测（评估子集 6 条、词表 422）：

```text
基座：困惑度 421.7649、命中率 0.68%（平均对数概率 -6.0443）
参考值 ln(422) = 6.0448   ← "完全瞎猜"的水平
```

**基座的困惑度就贴着 `ln(V)`**，这正是为什么"困惑度下降"是一个有意义的信号：
它的起点是"均匀分布"。

### 5.3 按 token 加权，而不是先按条目平均

```python
ProbeResult.mean_logprob = Σ logprob_i / Σ supervised_i     # 按 token 加权
```

不用"先按条目平均、再对条目求平均"：那样会让短条目权重过大。
两种平均在同一份数据上会给出不同数字，报告里必须说清用的是哪一种。

### 5.4 探针 ≠ 训练 loss（本课踩的坑）

模块文档第一版写着"探针的平均对数概率与训练 loss 可以直接相减，
`loss = -mean_logprob` 逐位一致"。**这句话是错的**，两者的分母差 1：

- 训练时"答案的第一个 token"**被计分**，因为它的上下文是 prompt 的最后一个 token；
- 探针在只喂"答案 id"时从第二个 token 才开始计分（位置 0 没有前文）。

于是正确用法是**同口径对比**（微调前 vs 微调后都用探针），而不是把探针读数
与训练日志里的 loss 相减——那两个数字的分子分母都不一样，相减得到的差
没有任何含义。这条更正落在了 `sequence_logprob` 的文档里。

另外两处实现口径也写清楚了：

- `ignore_index` 出现在**目标**位置时跳过；出现在**上下文**位置时**直接报错**
  （"以上一个被屏蔽的 token 为条件"没有定义，静默跳过会让分母悄悄变小，
  而分母一变，前后两次探针就不可比了）；
- 越界 token 立刻报错：用错词表的 tokenizer 探针会得到"模型很差"的假象，
  而真实原因是 id 根本不属于这个模型。

### 5.5 三组配置：标定、过拟合、发散

标定方法很直接：在 `(epochs, lr)` 的 12 个组合上扫一遍，取**评估集困惑度最低**
的那一组。实测（12 条训练样本、10 轮 = 120 步）：

| 配置 | 步数 | 训练集困惑度 | 评估集困惑度 | 评估 loss | 泛化间隙 |
|------|------|-------------|-------------|-----------|---------|
| 基座（未微调） | 0 | 421.8238 | 421.7649 | 6.0444 | — |
| **`lr = 2.0`（标定）** | 120 | 140.7894 | **290.4877** | **5.6663** | 149.7573 |
| `lr = 8.0`（过拟合对照） | 120 | 14.4577 | 587.6399 | 6.3749 | 573.2411 |
| `lr = 20.0`（发散对照） | 120 | inf | inf | 2.978e+68 | nan |

三行数字说清三件事：

1. **微调真的在学**：标定配置把评估集困惑度从 `421.76` 降到 `290.49`（降 `31.1%`），
   评估 loss 从 `6.0444` 降到 `5.6663`；
2. **学过头会变坏**：`lr=8.0` 把训练集背到 `14.46`，代价是评估集退到 `587.64`——
   **比没微调还差**。这就是过拟合，而它的判定依据是泛化间隙 `573.24`；
3. **学习率没有绝对尺度**：`lr=20.0` 直接发散（困惑度 `inf`）。
   day050 那句"学习率由模型规模、批大小、优化器共同决定"在这里又验证了一次：
   同一条曲线上的三个点，隔一个数量级就从"最好"变成"训练崩掉"。

> `lr=8.0` 是 day050 为**全参** SFT 标定的值。把它直接用到 LoRA 上就是这一行
> `587.64` —— **别人的学习率不能照抄，哪怕是自己上一课标定的**。

### 5.6 泛化间隙

```text
generalization_gap = 训练集困惑度降幅 − 评估集困惑度降幅
```

间隙为正说明"在见过的文本上变熟得更快"，这正是过拟合的定义。为什么值得单独
做一个指标：**它在文本指标上不一定看得出来**——本课的脚本化两臂输出根本不依赖
模型，所以那 6 条用例的分数对"模型有没有背题"完全无感。

逐桶探针（标定配置、评估集）实测：

```text
citation      73 token   困惑度 169.2532   命中率 0.1096
conciseness   91 token   困惑度 439.5037   命中率 0.0110
factuality    61 token   困惑度 235.2772   命中率 0.1475
format        72 token   困惑度 353.5180   命中率 0.0694
refusal       32 token   困惑度 454.2968   命中率 0.0000
tool_use      71 token   困惑度 239.0405   命中率 0.1268
```

`citation` 与 `factuality` 的困惑度最低（模型对这些答案最熟）、
`refusal` 与 `conciseness` 最高（拒答与压缩表达在训练集里样本最少）。
**这张表就是"下一批数据该补哪一类"的答案。**

## 第六章：脚本化对照臂与它的边界

### 6.1 两臂是什么

本课要在离线、零 GPU 的条件下演示"微调前 vs 微调后"的完整对比流程，
所以提供了两个**确定性函数**作为对照臂：

```text
baseline ：去掉引用尾注（来源：…）+ 截断到 50% + 追加固定尾注
finetuned：参考答案原文；难例截断到 70%
```

三种退化各对应一类真实失败：**不给出处**（引用能力）、**说一半**（召回能力）、
**废话超限**（简洁度）。

### 6.2 退化程度必须被标定

第一版的比例是 `0.6 / 0.85`，实测结果是：

```text
基线臂 4/6 合格、微调臂 6/6 合格   ← 难例也全线通过，by_difficulty 全是 100%
```

**"怎么跑都满分（或怎么跑都零分）的对照臂，测不出任何东西"**。把比例改成
`0.5 / 0.7` 之后：

```text
基线臂 2/6（33.33%）、微调臂 5/6（83.33%）
微调臂唯一失败的一条：fmt-03（hard，缺少必需片段 '风险：'）
分难度：easy 0% → 100%、normal 66.7% → 100%、hard 0% → 50%
```

难例开始掉分，`by_difficulty` 那张表才重新有信息量。这条经验的一般形式是：
**对照臂的退化程度和指标阈值一样，是需要标定的参数**。

### 6.3 边界：它们不是模型输出

必须说清楚：这两臂是**确定性文本函数**，不是某个真实模型生成的。
它们存在的唯一意义是让流程（两臂 → 配对比较 → 门禁 → 报告）
可在离线环境完整跑通并被 1151 个用例覆盖。

接上真实模型时，只需要把 `runner` 换成"加载适配器 → 生成答案"的调用
（day052 的 `render_inference_script` 生成的推理脚本就是它），
其余六层一行都不用改——这正是把 `runner` 设计成 `Callable[[EvalItem], str]`
而不是"一个模型对象"的原因。

### 6.4 两臂跑在哪个子集上

```text
两臂都必须跑在**评估子集**（6 条）上。
```

这是配对比较的前提，而它有一个不会报错的失败模式：跑在不同的子集上，
条数可能刚好相同，`compare_runs` 的对齐检查（id + 顺序）才会拦下来。
管线的顺序因此被固定成"先切分、再跑两臂"（`pipeline.run_finetune_evaluation`）。

## 第七章：报告——绑定、门禁与失败清单

### 7.1 绑定：没有绑定信息的分数不是证据

一份评估报告如果没有绑定信息，它的寿命只有一天：明天换一个适配器、
后天改一条用例，那些数字就再也没人能解释清楚了。

```text
适配器侧：adapter_manifest.json   → 内容哈希 + 基座 + 步数（day052）
评估集侧：suite_fingerprint       → 18 条用例的内容指纹（day053）
报告侧：  finetune_eval_report.json → 两边哈希 + 分数 + 判定 + 门禁 + 失败清单
```

`verify_manifest_binding` 逐项核对 `content_sha256` / `base_model` / `step`
（任何一项不一致都报错）。实测报告头：

```text
lora-finetuned | 评估集 93daad77e78b9721 | 适配器 sha256:607cdd68a786 | 合格率 83.33% | 门禁 通过
```

一个副作用值得记下来：**词表大小会随着语料改动而变化**。修 `ref-01` 的参考
答案时，`CharTokenizer` 的词表从 421 变成 422，适配器字节数从 202 149 变成
202 812、内容哈希从 `59305f729f9b` 变成 `607cdd68a786`。所以本课的基座名写成
`char-bigram-v{词表}`——**让"适配器配的是哪个词表的基座"在清单里可见**。
一个只写 `char-bigram` 的基座名，配错词表的适配器不会报错，只会给出乱码。

### 7.2 三项门禁

| 门禁 | 判据 | 为什么要有 |
|------|------|-----------|
| `min_pass_rate` | `pass_rate >= threshold` | 让"合格率下限"可配置，而不是写死在代码里 |
| `no_regression` | 每个分组（桶 / 难度）的回退都不超过 `max_regression` | 总体涨了不等于处处涨 |
| `execution` | `error_count == 0` | runner 崩了不能算绿 |

`report.passed` 只有在三项全通过时才为真。**门禁是复数的、且逐项列出**：
把三条判据压成一个布尔值，失败时不知道该先修哪一条。

### 7.3 门禁必须有"失败时会怎样"的用例

day052 那句"一个永远不会失败的门禁不是门禁"在这一课被完整执行了三遍：

```text
min_pass_rate 不达标：pass_rate 66.67% < 阈值 100.00% → passed=False
no_regression 失败  ：构造"总体涨、某一桶掉"的两臂 → passed=False 且 regressions 含该桶
execution 失败      ：runner 抛异常的条目计入 error_count → passed=False
```

顺带修掉一处**报告自身的缺陷**：`render_markdown` 的 `min_pass_rate` 证据行
原先固定写 `≥`，于是失败时输出的是

```text
| min_pass_rate | 否 | 合格率 66.67% ≥ 阈值 100.00% |     ← 与"否"自相矛盾
```

现在比较号随判定切换（失败时写 `<`）。**报告里的每一句话都要与判定一致**——
一份自相矛盾的证据比没有证据更容易误导人。

### 7.4 还有一个不会报错的坑：`failed_gates` 与 `passed` 的口径

```python
passed      = all(gate["passed"] for gate in self.gates.values())   # 看全部
failed_gates = [name for name in GATE_NAMES if ...]                  # 原先只看三个已知门禁
```

两者口径不一致时会出现"`passed=False` 但没有失败名"，摘要打出一个
**没有内容的括号**：`未通过（）`。修法是让 `failed_gates` 也列出额外的失败门禁，
并在没有失败名时明确写 `未设置门禁`。**两个方法必须对同一份 `gates` 给出一致的答案。**

### 7.5 报告不写时间戳

时间戳让报告在两个时刻必然不同，于是"这两份报告是不是同一件事"只能靠人眼；
要留时间信息就写进 `notes`，让它显式地成为内容的一部分。
`read_report` 另外补了一条类型检查：**合法 JSON 不一定是对象**
（顶层可能是数组），原先会在 `from_dict` 里漏出 `AttributeError`，
而路由层按 `FinetuneEvalError` 映射 400 的约定会因此漏网。

## 第八章：接入 API 与配置

### 8.1 两个新端点

```python
@router.get("/finetune/eval/suite", response_model=FinetuneEvalSuiteResponse)
@router.post("/finetune/eval/run", response_model=FinetuneEvalRunResponse)
```

| 端点 | 回答什么 | 成本 |
|------|---------|------|
| `/finetune/eval/suite` | 评估集画像：桶/难度分布、难度体检、切分、泄漏体检、参考答案自洽体检 | 纯计算，毫秒级 |
| `/finetune/eval/run` | 走完整条流水线，返回两臂对比 + 报告 +（可选）白盒探针 | `probe=true` 时约 2 秒（真训练一次 LoRA） |

`/finetune/eval/suite` 是 GET 且无请求体——它要回答的问题是"**要评什么**"，
而这个问题与调用方参数无关。把评估集画像做成一个随时可查的端点，
是为了让"我到底在评一套什么样的题"变成**零成本的动作**。

### 8.2 两个 "eval ratio" 不是一回事

```text
finetune_eval_ratio       切的是**微调数据**（day048 的数据工程，留多少条做验证）
finetune_eval_suite_ratio 切的是**评估套件**（18 条领域用例里留几条做评估）
```

两者名字都含 eval，混用会让"评估集"这个词同时指两件事。本课把它们显式分开、
在 `config.py` 里互相点名，并在文档与端点说明里各写一遍。

### 8.3 错误码

| 情况 | 状态码 |
|------|--------|
| 未知对照臂 / 权重不合法 / 报告与清单不一致 | **400** |
| `eval_ratio` / `min_pass_rate` / `alpha` / `bootstrap_samples` 越界或类型不对 | **422**（Pydantic 在进路由前拦下） |
| 正常 | 200 |

与 day038 建立、day040/041/046/048/050/051/052 沿用的错误码语言完全一致。

几个值得记的测试写法：

1. **不变式优于样例值**：`f(x, x) == 1.0` 这一条抓住了 chrF 的短文本缺陷；
   `score_item(item, item.reference).passed` 这一条抓住了参考答案的自洽缺陷。
   样例值只能证明"这一组输入对了"，不变式能证明"这一类输入都对"。
2. **门禁必须有失败路径**：三条门禁各有一条"构造失败"的用例。
   一条永远不会失败的门禁，会在有人把 `passed` 改成恒真之后**依然全绿**。
3. **手算值要写进断言**：Wilson 的 `(3, 18) → (0.0584, 0.3922)`、
   二项精确 p 的 `n=10,k=0 → 0.001953125`。没有手算值，"公式写错了但看起来
   很合理"是不可能被发现的。
4. **可复现性用 `==` 而不是 `approx`**：自助法同 seed 两次必须**逐位相同**。
   用 `approx` 会把"随机种子没接上"这种缺陷放过去。
5. **统计口径要覆盖两个方向**：`leaked_eval_items` 与 `leakage_rate` 一起断言，
   加上"`leakage_rate` 恒 ≤ 1"的单调护栏。

## 结语：三条可以带进 M5 后半程的工程结论

1. **先把"评什么"钉死，再谈分数。** 评估集自己要先过四道体检：难度与结构负载
   一致、参考答案能通过自己的用例、与训练集不重叠、切分后两边都有难例。
   本课最深的一个坑（`ref-01` 的参考答案缺上自己的事实点）**不是算法问题，
   是内容问题**，而它由一条不变式测试抓出来，不由人眼 review 抓出来。
   **一个连自己参考答案都判不过的评估集，评的不是模型。**

2. **"涨了 50%"与"统计上证明涨了"是两件事。** 合格率 `33.33% → 83.33%`、
   自助法区间不含 0，而 McNemar 的 `p = 0.25` 不显著——6 条用例上这两个结论
   可以同时成立。三者分工明确：Wilson 说单点有多不确定、McNemar 说翻转可信吗、
   自助法说连续差值有多大。**在样本量这件事上，诚实的答案往往是"还不够"**，
   而它正是扩充评估集的正当理由。

3. **黑盒与白盒要一起看，因为它们的背离本身是信息。** 文本指标说"输出像不像"，
   探针说"模型熟不熟"。本课实测里，`lr=8.0` 那组配置的文本分数照样好看
   （脚本化两臂不依赖模型），而探针一眼看出它把训练集背到了 `14.46`、
   评估集退到 `587.64`。**能被观察到的过拟合才是能被修掉的过拟合**——
   而"能不能被观察到"取决于你手里有没有一个不依赖输出的信号。

> **诚实的说明**：本日所有"输出侧"的数字（`2/6 → 5/6`、分桶与分难度表、
   McNemar 与自助法）都来自**脚本化对照臂**，它们是确定性文本函数，
   **不是任何真实模型的输出**；它们的价值在于让整条评估流水线可在离线环境
   完整跑通并被 1151 个用例覆盖。所有"模型侧"的数字（困惑度、命中率、
   泛化间隙、评估 loss）来自参考模型（`V=422` 的 bigram）上的**真实 LoRA 训练**
   （`train_lora_reference`，真实梯度下降、真实 120 步更新），
   但它们**不代表 7B 模型的行为**：真实微调的泛化间隙取决于数据量、任务难度
   与正则化，本课要传达的只是"这个信号存在、可算、能区分三种配置"。
   评估集只有 18 条（评估子集 6 条），因此**统计显著性几乎不可能达到**——
   这一点已如实写进报告与本教程，而不是用"看起来涨了很多"含混过去。
   探针耗时（单条 82.89 毫秒）是 bigram 前向的实测值，7B 模型上要乘若干数量级。

明天（day054）进入 **RLHF / DPO 原理**：偏好数据的格式（chosen / rejected）、
RLHF（PPO）与 DPO 两个对齐目标的差别、以及为 SmartResearch Agent 的输出风格
规划偏好对齐策略。今天定下的三件事会直接复用：**评估集的四道体检**（偏好数据
同样要防泄漏与自洽）、**配对比较与门禁**（对齐前后必须用同一套口径比）、
以及**白盒探针的泛化间隙**（偏好对齐最大的风险正是"对齐过头"）。
