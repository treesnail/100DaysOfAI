# day022 习题答案：Docker 部署 MCP Server

## 第 1 题（选择题）

**答案：B**

**解析：** 容器的设计模型是"独立生命周期 + 网络通信"：编排器负责拉起、监控、重启容器，外界通过端口与容器交互。SSE 传输恰好是一个监听 TCP 端口的独立 HTTP 服务，与容器模型完全同构——`EXPOSE` 声明端口、`-p` 做映射、`/health` 做探测，全是 Docker 的成熟能力。

stdio 传输则相反：它要求 Client 以子进程方式拉起 Server，双方共享 stdin/stdout 管道。容器化后这条管道被容器边界切断，需要 `docker run -i` 附着等额外转接；且"Client 退出则 Server 死"的生命周期语义与编排器"我来管理容器生死"的模型直接冲突；一对一的管道也无法支撑"一个容器服务多个 Client"。

A 说反了；C 忽略了两种传输在进程模型上的本质差异；D 错误，MCP 协议只规定消息格式（JSON-RPC 2.0），不规定部署方式。

## 第 2 题（选择题）

**答案：C**

**解析：** Docker 分层缓存的规则是：某层的输入（指令 + 涉及文件内容）不变则命中缓存；一旦某层失效，**其后所有层**都必须重建。因此排序原则是"变化频率低的在前，高的在后"。

- A：`COPY . .` 把源码一起复制在最前面，每改一行代码，依赖层缓存全部失效，`pip install`（最慢的一层）每次重装。
- B：顺序错误，`requirements.txt` 还没复制进来就执行安装，直接构建失败。
- C：正确。依赖清单（偶尔变）先复制并安装，源码（每次改）后复制——改代码时依赖层命中缓存，构建秒级完成。
- D：源码在依赖清单之前复制，源码变化照样使后续所有层失效，等于白排序。

## 第 3 题（选择题）

**答案：B**

**解析：** `127.0.0.1` 是回环地址，绑定它的进程只接受**本机内部**发起的连接。`-p 8000:8000` 的映射机制是：Docker 在宿主机上监听 8000，收到包后通过 NAT 转发进容器网络命名空间——从容器内进程的视角看，这个包的源地址是容器网络的网关，**不是回环地址**，因此绑定 `127.0.0.1` 的服务不会接收它，表现为连接超时或拒绝。

修复方法：服务绑定 `0.0.0.0`（接受任意网卡上的连接），本项目 Dockerfile 中 `ENV MCP_HOST=0.0.0.0` 就是为此设置的。A 忽略了绑定地址的过滤作用；C 的 404 只有在 HTTP 层真正收到请求后才可能发生；D 错误，这是 TCP/IP 的基础语义，与 Docker 版本无关。

## 第 4 题（判断题）

**答案：错（过于绝对）。**

**解析：** stdio 容器化"难直接用"指的是**难以作为常驻服务**被编排器管理，但存在合理的例外场景：

1. **一次性任务容器**：CI 流水线里 `docker run -i image < input` 执行一次调用拿结果，容器即起即死，生命周期问题不存在。
2. **本地隔离执行**：开发者想用容器隔离某个 stdio Server 的依赖环境，`docker run -i` 保持 stdin 附着，Client 在宿主机、Server 在容器，技术上可行（Docker 的 `-i` 参数就是为这种场景保留的）。

教程第一章的论点是 stdio 与容器模型**不匹配**（生命周期错位、一对一管道、无法健康检查），而不是"任何场景都不能用"。工程判断几乎都是情境化的——这正是本题想强调的思维习惯：看到"永远"/"任何"这类绝对化表述时先打个问号。

## 第 5 题（判断题）

**答案：错。**

**解析：** `EXPOSE 8000` 不做任何网络配置，它只是**元数据与文档**：告诉读 Dockerfile 的人和 `docker inspect` 的使用者"这个镜像打算监听 8000"。真正打通宿主机访问的是运行时的端口映射：`docker run -p 8000:8000` 或 compose 的 `ports:`。

一个佐证实验：不写 EXPOSE 只加 `-p 8000:8000`，访问完全正常；只写 EXPOSE 不加 `-p`，宿主机访问不通。EXPOSE 唯一有实际效果的场景是配合 `docker run -P`（大写），把所有 EXPOSE 端口映射到宿主机随机端口——生产环境很少这么用。

记忆口诀：**EXPOSE 是声明，-p 是动作。**

## 第 6 题（问答题）

**参考答案：**

**（a）为什么镜像里不该写死端口：**

容器的核心承诺是"一份镜像，多处运行"。端口号是典型的**部署环境相关配置**：开发机用 8000，测试环境可能用 8001 避开冲突，生产环境由网关统一映射。如果写死在代码里，每个环境都得构建一份专属镜像——镜像数量随环境数爆炸，且"同一份镜像"的可追溯性被打破（你无法确定测试通过的镜像和生产跑的镜像是否一致）。把端口放进环境变量后，镜像只描述"应用是什么"，环境变量描述"这次运行在哪"，二者解耦。这正是十二要素第三条"配置存环境"的意图：一切随部署变化的东西都不进代码。

**（b）优先级链（从高到低）：**

| 层级 | 位置 | 职责 |
|------|------|------|
| 1 | `docker run -e MCP_PORT=9000` | 单次运行的显式指定，临时覆盖 |
| 2 | compose 的 `environment:` | 编排层的正式环境配置，进版本控制 |
| 3 | Dockerfile 的 `ENV` | 镜像级默认值，保证"裸镜像也能跑" |
| 4 | 代码里 `os.environ.get(..., 缺省)` | 应用兜底，保证"裸 python 也能跑" |

职责划分的原则：**越靠近运行时的层越具体，越靠近代码的层越通用**。每一层都为"上一层没有配置"的情况兜底，任何一层单独存在系统都能工作——这是防御式配置设计。

## 第 7 题（问答题）

**参考答案：**

**（a）`--start-period` 的作用：**

服务冷启动需要时间：加载 Python 模块、初始化 FastMCP、绑定端口。这期间 `/health` 必然不可达。`--start-period=10s` 声明"启动后 10 秒内的检查失败不计入 retries"。去掉它，启动期的正常失败会消耗重试次数——如果冷启动慢于 `interval × retries`（本配置不含宽限期时是 30s×3=90s 才会判死，但若 interval 调小就容易触发），容器会在**即将启动成功时**被判 unhealthy，编排器（如配合重启策略）将其杀掉重启，陷入"启动→被杀→再启动"的死循环。宽限期把"还没起来"和"起不来了"两种状态区分开。

**（b）`-f` 为什么必不可少：**

curl 的退出码语义是"**curl 这个命令本身是否执行成功**"，不是"HTTP 响应是否成功"。服务返回 500 时，curl 正常收到了响应，退出码依然是 **0**——HEALTHCHECK 会认为检查通过。`-f`（fail）让 curl 在收到非 2xx 响应时返回非零退出码，Docker 才能感知失败。末尾的 `|| exit 1` 是双保险：无论 curl 因何种原因失败（连接拒绝、超时、非 2xx），都以退出码 1 告终。健康检查命令的契约只有一条：**退出码 0 = 健康，非 0 = 不健康**，任何"悄悄成功"的路径都是 bug。

**（c）为什么 `/health` 不该查下游依赖：**

健康检查（liveness probe）回答的问题是"**这个容器还值得保留吗**"，它驱动的是"重启容器"这个动作。如果在检查里串了数据库等下游依赖，一次数据库抖动会让**所有**依赖它的容器同时被判死、集体重启——下游的小故障被放大成本服务的雪崩，而且重启容器对"数据库连不上"这个问题毫无帮助（重启后依然连不上）。正确的分层是：liveness 只检查进程自身（HTTP 栈活着）；下游依赖的可用性用单独的 readiness probe 或诊断端点表达，且就绪探针驱动的是"暂时摘除流量"而非"杀死容器"。本项目的 `/health` 只返回静态 JSON，正是 liveness 的最小正确实现。

## 第 8 题（问答题）

**参考答案：**

两种测试方式的分层对比：

| 测试方式 | 穿透（真实执行）的层 | 屏蔽（不经过）的层 |
|----------|---------------------|---------------------|
| `create_connected_server_and_client_session` | 完整 MCP 协议栈：初始化握手、能力协商、JSON-RPC 2.0 编解码、工具/资源处理器业务逻辑 | 网络传输（无 TCP、无端口）、进程边界（无子进程） |
| Starlette `TestClient` | ASGI 应用全栈：Starlette 路由匹配、请求解析、响应序列化、`/health` 处理器 | 网络监听（不绑定端口）、HTTP 报文的 TCP 传输 |

相对"真起容器再测"的优势：

1. **速度**：进程内测试毫秒级；容器测试要构建镜像、启动容器、等待健康检查转绿，分钟级。测试金字塔要求底层快反馈测试占多数。
2. **确定性**：进程内测试没有端口冲突、没有网络抖动、没有守护进程状态依赖，在任何机器（包括没有 Docker 的 CI）上结果一致——延续 day002 FIRST 原则中的 Repeatable。
3. **定位精度**：进程内测试失败时栈信息直指业务代码；容器测试失败时要在"构建错误/启动错误/网络错误/业务错误"四类原因中排查。
4. **关注点分离**：这两种测试验证的是**业务逻辑与协议正确性**；容器构建验证的是**交付物正确性**（Dockerfile 指令、依赖安装）。两者是正交的验证维度，教程第五章的验证清单负责后者。两层都有，才叫完整的验证体系；但日常开发中前者跑 100 次，后者可能只跑 1 次。

## 第 9 题（编程题）

**参考实现：**

在 `server.py` 的 `create_server()` 中（`/health` 路由之前）新增：

```python
@server.prompt()
def research_report(topic: str) -> str:
    """生成调研报告写作引导提示词."""
    return (
        f"请针对主题「{topic}」撰写一份调研报告，要求：\n"
        "1. 明确调研范围：界定主题边界与评估维度；\n"
        "2. 收集资料：列出需要查证的关键问题并逐一收集信息；\n"
        "3. 对比分析：按评估维度横向对比各候选方案；\n"
        "4. 给出结论：明确推荐方案并说明理由。"
    )
```

`describe_capabilities()` 中把 `"prompts": []` 改为：

```python
"prompts": [
    PromptDescriptor(
        name="research-report",
        description="调研报告写作引导提示词",
        arguments=[{"name": "topic", "required": True}],
    ).model_dump()
],
```

新增测试：

```python
async def test_prompt_registered(self):
    server = create_server()
    async with create_connected_server_and_client_session(server) as session:
        prompts = await session.list_prompts()
    assert "research-report" in [p.name for p in prompts.prompts]

async def test_get_prompt_contains_topic(self):
    server = create_server()
    async with create_connected_server_and_client_session(server) as session:
        result = await session.get_prompt("research-report", {"topic": "RAG 评估"})
    assert "RAG 评估" in result.messages[0].content.text
```

（如改动 `describe_capabilities`，记得同步更新 `test_describe_capabilities` 中对 `prompts` 的断言。）

**解析：** FastMCP 的 `@server.prompt()` 把 Python 函数签名自动转换为 Prompt 的 arguments schema——`topic: str` 参数即成为必填参数。这道题同时训练了两个习惯：一是**能力清单与真实注册保持一致**（`describe_capabilities` 里的 `PromptDescriptor` 是项目自建的文档层，改了真实能力要同步改清单，测试 `test_describe_capabilities` 就是防止两者漂移的守卫）；二是新增能力必配内存会话测试，保持离线可验证。

## 第 10 题（编程题）

**参考实现：**

在 `create_server()` 中新增：

```python
@server.custom_route("/info", methods=["GET"])
async def info(request: Request) -> Response:
    """服务信息端点：返回名称、传输方式与能力清单.

    注意：MCP_TRANSPORT 在请求时读取（而非 create_server 时），
    因为这个端点的语义是"报告当前环境"，运行时环境变量的变化
    应当被如实反映。
    """
    return JSONResponse(
        {
            "name": "smart-research-agent",
            "transport": os.environ.get("MCP_TRANSPORT", "stdio"),
            "capabilities": describe_capabilities(),
        }
    )
```

测试：

```python
class TestInfoRoute:
    def test_info_returns_capabilities(self):
        client = TestClient(create_server().sse_app())
        resp = client.get("/info")
        assert resp.status_code == 200
        body = resp.json()
        assert body["name"] == "smart-research-agent"
        assert body["capabilities"]["tools"][0]["name"] == "calculator"

    def test_info_reflects_env_transport(self, monkeypatch: pytest.MonkeyPatch):
        monkeypatch.setenv("MCP_TRANSPORT", "sse")
        client = TestClient(create_server().sse_app())
        assert client.get("/info").json()["transport"] == "sse"
```

宿主机验证命令序列：

```bash
cd day022/源码/smart-research-agent
docker compose up -d --build          # 构建并后台启动
docker compose ps                     # 确认 STATUS 变为 healthy
curl http://localhost:8000/health     # 探活：{"status":"ok",...}
curl http://localhost:8000/info       # 验证新端点：应含 capabilities
docker compose down                   # 停止并清理容器与网络
```

**解析：** 第 2 点是本题的陷阱所在：环境变量有"创建时读取"和"请求时读取"两种时机，语义不同。`create_server()` 的 host/port 在创建时读取是合理的——监听地址在服务器启动后无法更改；而 `/info` 这类**报告型端点**更适合请求时读取，如实反映当前环境。两种选择都不算错，错的是实现与测试不一致（比如实现请求时读取，测试却在 `create_server()` 之前 setenv 后期望创建时快照——恰好都能过，但换个调用顺序就翻车）。这呼应了 day010 的原则：测试固化的应该是**明确的语义决策**，而不是实现的偶然行为。
