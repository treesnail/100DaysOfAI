## 第一章：为什么 RAG 必须评估 —— 没有度量就没有优化

### 1.1 一个典型的事故现场

假设 SmartResearch Agent 接入了知识库，用户问"BM25 相比 TF-IDF 做了什么改进"，系统回答："BM25 是一种深度学习模型。" 答案错了。错在哪？

RAG 链路上至少有三个嫌疑人：

```text
用户问题
   │
   ▼
[检索器] ──嫌疑人①──▶ 根本没检索到 BM25 相关文档（召回失败）
   │        ──嫌疑人②──▶ 检索到了，但排在第 8 位，被 Top-3 截断（排序失败）
   ▼
[生成器] ──嫌疑人③──▶ 检索结果里有正确答案，但 LLM 没读到/读错了（生成失败）
   │
   ▼
错误答案
```

没有评估体系时，你只能盯着错误答案猜。有了评估体系，你可以把链路拆成两段分别度量：**检索段**用带标注的评测集算指标，**生成段**对比参考答案打分。检索指标满分而答案错误 → 病灶在生成；检索指标就很低 → 病灶在检索，先别动 Prompt。

这就是 RAG 评估的第一性原理：**评估的目的是定位，定位的前提是分段度量。**

### 1.2 为什么不能只看"答案对不对"

有人会问：既然最终目标是答案正确，直接端到端评估答案不就行了？三个理由不行：

1. **归因不明**。如上节，端到端结果无法区分三种失败。而三种失败的修复手段完全不同：召回失败要调 embedding 或分块，排序失败要加 rerank，生成失败要改 Prompt。
2. **成本与速度**。生成评估要调 LLM（哪怕用 MockLLM，真实环境里也是真金白银），检索评估是纯本地计算。迭代检索参数（Top-K、分块大小）时只跑检索评估，快几个数量级。
3. **标注成本不同**。检索评估只需要标注"哪些文档相关"，生成评估需要撰写参考答案——后者贵得多。检索评测集可以先建起来天天跑，生成评估抽样跑。

所以今天的架构是把两类评估做成 RagEvaluator 上两个独立的方法：`evaluate_retrieval` 与 `answer_faithfulness`，可以单独调用、单独演进。

### 1.3 评估的基础设施：标注评测集

一切检索指标的前提是有一份**带标注的评测集**：每个查询配一组"真正相关"的文档 id。我们自建了 6 条（[data/eval/rag_eval.jsonl](../源码/smart-research-agent/data/eval/rag_eval.jsonl)）：

```json
{"query": "BM25 相比 TF-IDF 做了哪些改进", "relevant_ids": ["d3"], "relevance_grades": {"d3": 2}, "reference_answer": "BM25 在 TF-IDF 基础上引入词频饱和与文档长度归一化。"}
```

一条样本四个字段，对应两类评估的输入：

| 字段 | 服务于 | 含义 |
|------|--------|------|
| `query` | 两者 | 用户查询 |
| `relevant_ids` | 检索评估 | 二值标注：哪些文档相关（recall/precision/MRR 用） |
| `relevance_grades` | 检索评估 | 分级标注：相关到什么程度，0/1/2（NDCG 用） |
| `reference_answer` | 生成评估 | 参考答案（faithfulness 用） |

注意一个细节：为什么 NDCG 要单独的 `relevance_grades` 而不能复用 `relevant_ids`？因为 NDCG 的核心价值就是区分"核心相关"与"沾边相关"——这正是第二章要展开的分级相关性。标注时 2 表示"直接回答问题的核心文档"，1 表示"有间接帮助的背景文档"。

## 第二章：检索评估四大指标 —— 公式、直觉与适用差异

这是今天的理论核心。四个指标回答的是四个不同的问题，绝不能互相替代。完整实现见 [evaluation/rag_metrics.py](../源码/smart-research-agent/smart_research_agent/evaluation/rag_metrics.py)。

### 2.1 召回率与精确率：一枚硬币的两面

**召回率（Recall）**：相关文档中，被检索出来的比例。

```text
Recall = |retrieved ∩ relevant| / |relevant|
```

**精确率（Precision）**：检索结果中，真正相关的比例。

```text
Precision = |retrieved ∩ relevant| / |retrieved|
```

手算一例：某查询标注了 2 个相关文档 `["a", "d"]`，系统 Top-3 返回 `["a", "b", "c"]`：

- 交集 = `{a}`，Recall = 1/2 = **0.5**（相关文档只找回一半）
- Precision = 1/3 ≈ **0.33**（端上来的三条里只有一条是对的）

**两者的权衡（trade-off）是信息检索的第一课。** 想象两个极端系统：

- 系统 A：返回语料库里的**全部** 1000 篇文档。Recall = 1.0（相关的一个没漏），Precision ≈ 0.002（几乎都是垃圾）。
- 系统 B：只返回它最有把握的 1 篇。如果对了，Precision = 1.0，但 Recall 可能只有 1/3（漏掉了其他相关文档）。

```text
返回数量  ──▶ 多     Recall ↑   Precision ↓
返回数量  ──▶ 少     Recall ↓   Precision ↑
```

这两个指标单独看任何一个都会被骗：**评估检索系统必须同时报召回与精确**，或者用一个调和两者的方式（比如固定 Top-K 时比较，K 固定了，分母就固定了，两个指标才有横向可比性——这正是我们评测时固定 `top_k=3` 的原因）。

**RAG 场景偏向哪一边？** 偏向召回。因为生成器（LLM）有一定的"沙里淘金"能力——Top-K 里混进一两篇无关文档，LLM 通常能忽略；但如果相关文档压根没进 Top-K，LLM 凭空编不出它没见过的知识，幻觉就此产生。所以 RAG 检索调优的常见目标是"在可接受的精确率下把召回率顶上去"。

### 2.2 MRR：只看第一个命中的"导航型"指标

**倒数排名（Reciprocal Rank）**：第一个相关文档出现在第几位，取倒数。

```text
RR = 1 / rank_of_first_relevant     （有命中）
RR = 0                               （无命中）
```

手算：返回 `["x", "a", "y"]`，标注相关 `["a"]` → 第一个命中在第 2 位，RR = 0.5。

跨查询取平均就是 MRR（Mean Reciprocal Rank）：`MRR = (1/|Q|) Σ RR_q`。

MRR 的"性格"非常极端，看它**不看**什么：

- **看**：第一个命中的位置。第 1 位得 1.0，第 2 位腰斩到 0.5，第 3 位只剩 0.33。
- **不看**：第一个命中之后的所有事。`["a", "x", "x"]` 和 `["a", "d", "d"]`（`a`、`d` 都相关）的 RR 完全相同——后面的相关文档它视而不见。

这种偏执恰恰是它适合的场景：**导航型查询**。用户问"Python 官方文档在哪"，心里只有一个正确答案，你把它放第 1 位还是第 3 位，体验天差地别；第 1 位之后还有什么，用户根本不关心。反过来，对"把 RAG 的资料都给我找全"这种**收集型查询**，MRR 就不适用——那正是召回率的主场。

### 2.3 NDCG：分级相关 + 位置折损的排序质量度量

前三个指标有一个共同的盲区：**相关是二值的**——文档要么相关要么不相关。但现实世界是分级的：对"BM25 的改进"这个查询，专门讲 BM25 的文档（等级 2）和顺带提了一句的文档（等级 1），价值完全不同。而且前三个指标里，只有 MRR 感知位置，感知方式还很粗暴（只看第一个）。

**NDCG（Normalized Discounted Cumulative Gain）** 把两件事都做了。分三步：

```text
第1步 DCG（折损累计增益）:
    DCG = Σ_i (2^rel_i - 1) / log2(i + 1)      i 为排名，从 1 开始

第2步 IDCG（理想 DCG）:
    把所有相关文档按等级从大到小重排，用同一公式算出的"满分 DCG"

第3步 归一化:
    NDCG = DCG / IDCG
```

逐项拆解设计的为什么：

**（1）增益 `2^rel - 1`：分级相关。** 等级 rel 越大增益越大，指数放大让"核心文档"（rel=2 → 增益 3）显著重于"边缘相关"（rel=1 → 增益 1）。retrieved 里没出现在标注里的文档视为 rel=0 → 增益 0。

**（2）折损 `1 / log2(i+1)`：位置惩罚。** 第 1 位折损系数 1，第 2 位 0.63，第 3 位 0.5，第 10 位只剩 0.29。模拟的是真实用户行为：很少有人翻到第 10 条。同样的相关文档，排得越靠后贡献越小。

**（3）归一化：除以 IDCG。** 裸 DCG 有个致命问题：不同查询的相关文档数量不同，DCG 绝对值没法跨查询比较（查"BM25"有 3 篇相关，查"倒排索引"只有 1 篇，前者的 DCG 天然更大）。除以"这个查询理论上能拿到的最大 DCG"之后，任何查询的 NDCG 都落在 [0, 1]，**1.0 表示当前排序已经是理想排序**——这才有了跨查询求平均的合法性。

**手算一例（务必跟着算一遍）**：标注等级 `{a: 2, b: 1}`，系统返回 `["b", "a"]`（排反了）：

```text
增益：b → 2^1-1 = 1，a → 2^2-1 = 3
折损：第1位 1/log2(2) = 1，第2位 1/log2(3) ≈ 0.6309

DCG  = 1×1    + 3×0.6309 = 2.8928
IDCG = 3×1    + 1×0.6309 = 3.6309   （理想排序是 a 在前）
NDCG = 2.8928 / 3.6309 ≈ 0.7967
```

排反一对文档，NDCG 从 1.0 掉到 0.80——损失被精确量化了。这个用例被原样固化在 `tests/test_rag_eval.py::TestNdcg::test_inverted_pair` 里。

### 2.4 四个指标的对照与选型

| 指标 | 回答的问题 | 感知位置？ | 感知相关等级？ | 典型场景 |
|------|-----------|-----------|---------------|---------|
| Recall | 相关的找全了多少 | 否 | 否 | 收集型查询、RAG 检索调优的主指标 |
| Precision | 结果里多少是对的 | 否 | 否 | 与 Recall 配对报告，衡量结果纯度 |
| MRR | 第一个答案够靠前吗 | 只看首个命中 | 否 | 导航型查询（事实问答、寻址） |
| NDCG | 整体排序质量如何 | 是（连续折损） | 是（0/1/2 分级） | 排序系统综合质量、rerank 效果对比 |

四个指标不是竞争关系而是**互补关系**。`RagEvaluator.evaluate_retrieval` 对每条查询同时算四个，原因就在这里：一次检索，四个视角。

> 思考题：fixed Top-K 下，Recall 和 Precision 之间还存在权衡吗？提示：K 固定后，两者的分母里只有一个在变。

## 第三章：纯函数实现 —— rag_metrics.py 的工程决策

### 3.1 为什么指标必须写成纯函数

打开 [evaluation/rag_metrics.py](../源码/smart-research-agent/smart_research_agent/evaluation/rag_metrics.py)，四个函数签名整齐划一：

```python
def retrieval_recall(retrieved_ids: list[str], relevant_ids: list[str]) -> float: ...
def retrieval_precision(retrieved_ids: list[str], relevant_ids: list[str]) -> float: ...
def mrr(retrieved_ids: list[str], relevant_ids: list[str]) -> float: ...
def ndcg(retrieved_ids: list[str], relevance_grades: dict[str, float]) -> float: ...
```

没有类、没有状态、不读文件、不碰网络、不调 LLM。这是刻意的设计，回报有三：

1. **可手算验证**。评估指标本身的正确性是整座评估大厦的地基——指标算错了，后面所有"优化"都是在追逐错误的信号。纯函数让"手算期望值 → 断言比对"的测试写法自然成立（day002 的 FIRST 原则中的 Repeatable、Self-validating）。
2. **可组合**。RagEvaluator、未来的 rerank 对比实验、CI 报告生成器，都可以直接调这四个函数而无需实例化任何东西。
3. **无环境依赖**。向量库换成 Qdrant、embedding 换成 OpenAI，这四个函数一行不用改。

**指标函数是整个评估模块里唯一不许出错的 15 行代码，把它们做成纯函数是给正确性上的保险。**

### 3.2 边界约定：除零时刻的语义选择

每个指标都有除零风险，约定不是随手拍的，每一条都有语义理由：

```python
# recall：没有相关文档时 → 1.0
if not relevant_ids:
    return 1.0
```
该查询没有该召回的东西，系统没有欠账。若返回 0.0，等于惩罚系统"没召回不存在的东西"，拉低均值造成误判。

```python
# precision：什么都没返回时 → 0.0
if not retrieved_ids:
    return 0.0
```
空结果谈不上"结果纯度"，记零。

```python
# ndcg：无标注或全零标注时 IDCG = 0，无定义 → 0.0
if idcg == 0.0:
    return 0.0
```
没有理想排序可对标，NDCG 在数学上无定义，按零处理并在评测集层面避免这种样本。

这些约定全部有对应测试（`test_empty_relevant_is_vacuous_full`、`test_empty_retrieved`、`test_empty_grades`）——**边界行为不写进测试，就等于没有约定**。

### 3.3 NDCG 实现里的一个细节

```python
def _dcg(gains: list[float]) -> float:
    return sum(
        (2.0**rel - 1.0) / math.log2(rank + 1)
        for rank, rel in enumerate(gains, start=1)
    )

actual = [relevance_grades.get(doc_id, 0.0) for doc_id in retrieved_ids]
ideal = sorted(relevance_grades.values(), reverse=True)
```

注意 `ideal` 的计算：IDCG 不需要知道"理想排序的文档 id 序列"，只需要**等级的降序列表**——因为 DCG 只依赖各位置上的增益值。用 `sorted(grades.values(), reverse=True)` 一行得到理想增益序列，这是对公式的忠实直译。

另一个细节：`relevance_grades.get(doc_id, 0.0)`。retrieved 里出现未标注文档时不报错、按 rel=0 处理——它零增益但仍占一个排名位，把后面的相关文档往后挤，这个"挤"的损失正是通过折损项体现的（见测试 `test_ungraded_doc_treated_as_zero`）。

## 第四章：RagEvaluator —— 把评估接入知识库

### 4.1 三层结构：指标 ← 评估器 ← 评测集

今天的模块分三层，依赖方向严格向下：

```text
data/eval/rag_eval.jsonl          评测集（数据层：查询 + 标注 + 参考答案）
        │
        ▼ 逐条驱动
RagEvaluator (rag_eval.py)        评估器（编排层：检索、算指标、聚合报告）
        │
        ▼ 调用
rag_metrics.py + vector_store     原语层（纯函数指标 + day009 向量库）
```

评估器的组装（[evaluation/rag_eval.py](../源码/smart-research-agent/smart_research_agent/evaluation/rag_eval.py)）：

```python
class RagEvaluator:
    def __init__(self, vector_store: InMemoryVectorStore, embedding: EmbeddingProvider) -> None:
        self.vector_store = vector_store
        self.embedding = embedding
```

老熟人手法：依赖注入。生产环境注入真实向量库与 embedding 服务，测试注入 `InMemoryVectorStore` + 测试专用的确定性 embedding——和 day005 的 MockLLM、day010 的 Planner 是同一条依赖倒置血脉。

### 4.2 评测流程：从 JSONL 到报告

核心方法 `evaluate_retrieval` 的循环体：

```python
for item in eval_set:
    query = item["query"]
    relevant_ids = list(item["relevant_ids"])
    grades = dict(item.get("relevance_grades") or {d: 1.0 for d in relevant_ids})
    retrieved = self.retrieve(query, top_k=top_k)
    report.per_query.append(QueryEvalResult(
        query=query,
        retrieved_ids=retrieved,
        recall=retrieval_recall(retrieved, relevant_ids),
        precision=retrieval_precision(retrieved, relevant_ids),
        mrr=mrr(retrieved, relevant_ids),
        ndcg=ndcg(retrieved, grades),
    ))
```

两个设计点：

**（1）`relevance_grades` 缺省时由 `relevant_ids` 自动生成全 1 等级。** 这让标注者可以偷懒：只标"相关/不相关"也能跑 NDCG（退化为二值版本），标了分级就用分级。渐进式标注降低了评测集的冷启动成本。

**（2）每条查询保留完整明细（`per_query`），均值只是汇总。** 为什么？因为均值会掩盖分布：mean_recall = 0.7 可能是"每条都 0.7"，也可能是"一半满分一半 0.4"——后者意味着有一类查询系统性失败，需要捞出来看 bad case。所以 `RetrievalEvalReport.to_dict()` 把逐条的 `retrieved_ids` 也带上了：**评估报告的价值一半在分数，一半在可下钻的明细。**

### 4.3 生成评估：answer_faithfulness 与 LLM-as-a-judge

生成答案的对比评估为什么用 LLM 而不是字符串匹配？因为答案的等价性在语义层：

- 参考答案："BM25 引入词频饱和与文档长度归一化"
- 生成答案 A："BM25 对词频做了饱和处理，并按文档长度归一化" ← 完全等价，字符串几乎不重合
- 生成答案 B："BM25 是一种深度神经网络" ← 字面也能有几个重合词

字符串匹配（编辑距离、词袋重合）对 A 苛刻、对 B 宽松，恰好判反。需要一个"理解语义"的裁判——这就是 **LLM-as-a-judge**：把裁判本身也变成一个 LLM 调用，用提示词锁定评分标准和输出结构：

```python
FAITHFULNESS_PROMPT = """你是一个答案评审员。请对比"生成答案"与"参考答案"，评估生成答案的忠实度。

评分标准：
- 1.0：关键事实与参考答案完全一致（措辞可不同）
- 0.5：部分一致，有遗漏或轻微偏差
- 0.0：关键事实错误或答非所问

严格输出 JSON 对象，不要输出其他内容，例如：
{{"score": 1.0, "reason": "关键事实完全一致"}}
...
"""
```

注意三档评分标准的设计：1.0 强调"措辞可不同"（明确告诉裁判比的是事实不是字面），0.5 兜住"部分正确"的灰度（避免非黑即白把信息压没）。

评审输出的解析复用 day010 的防御式解析模式，只是从找 `[]` 变成找 `{}`，并加了一道**值域校验**：

```python
if not 0.0 <= score <= 1.0:
    raise FaithfulnessParseError(f"score 越界 [0, 1]: {score}")
```

LLM 可能输出 `{"score": 8}`（心里想着十分制）——语法对、类型对，但业务上越界。这呼应 day010 的第四道防线（语义校验）：**凡是程序消费的 LLM 输出，校验必须覆盖到值域。**

### 4.4 测试策略：MockEmbedding 的局限与 ToyEmbedding 的解法

这里有一个值得展开的教学点。day009 的 `MockEmbedding` 是 SHA-256 哈希伪向量——确定、离线，但**没有语义**：语义相近的文本不会得到相近的向量。用它跑检索，排序约等于随机，手算期望值无从谈起。

测试要断言**精确的期望指标值**，就必须完全掌控检索排序。解法在 `tests/test_rag_eval.py` 里：一个 10 行的 `ToyEmbedding`——词表到标准基的映射：

```python
class ToyEmbedding(EmbeddingProvider):
    """词表 {"向量":0, "索引":1, "排序":2, "检索":3}，已知词各占一个维度."""

    def embed(self, text: str) -> list[float]:
        vec = [0.0] * 4
        for word, idx in self.VOCAB.items():
            if word in text:
                vec[idx] = 1.0
        return vec
```

于是语料和查询的向量全部透明：

```text
t1 "向量 检索"  → [1,0,0,1]      q1 "向量 检索" → [1,0,0,1]
t2 "索引"       → [0,1,0,0]      q2 "索引"      → [0,1,0,0]
t3 "排序 索引"  → [0,1,1,0]
```

q1 检索：cos(t1)=1.0，cos(t2)=cos(t3)=0（并列按插入序），Top-2 = `[t1, t2]`。q2 检索：cos(t2)=1.0，cos(t3)=1/√2≈0.707，cos(t1)=0，Top-2 = `[t2, t3]`。排序完全确定，四个指标逐一手算（就是 2.1~2.3 节算过的那些数），固化成断言。

这个模式值得记住：**当 mock 对象的抽象层级不对（MockEmbedding 模拟了"离线"但没模拟"语义"），就在测试里造一个层级正确的假实现，而不是放弃断言精度。** 项目自带的 `data/eval/` 评测集则走另一条测试路径：用 MockEmbedding 跑通流水线，只断言输出结构与值域合法（`test_eval_set_runs_end_to_end`），不断言具体数值。两条路径各管一件事。

## 第五章：检索评估与生成评估为什么要分开

回到第一章的原理，现在可以从代码层面看清"分开"的具体含义：

| 维度 | 检索评估 `evaluate_retrieval` | 生成评估 `answer_faithfulness` |
|------|------------------------------|-------------------------------|
| 评估对象 | 检索器（向量库 + embedding） | 生成器（LLM + Prompt） |
| 输入标注 | relevant_ids / relevance_grades | reference_answer |
| 是否调 LLM | 否（纯本地计算） | 是（LLM-as-a-judge） |
| 确定性 | 完全确定 | 依赖裁判模型（可用 MockLLM 锁定） |
| 运行成本 | 毫秒级，可每次提交跑 | 真实环境有 API 成本 |
| 失败含义 | 该调 embedding/分块/Top-K/rerank | 该调 Prompt/生成参数 |

最后一行是分开的终极理由：**两个指标的恶化指向完全不同的修复动作。** 合并成一个端到端分数，等于把诊断信息扔掉。

这也预告了 day071（M6-D9 RAG 评估与调试）的工作方式：端到端评估发现问题 → 分段评估定位问题 → 针对病灶优化 → 回归评估确认。今天建的分段度量就是那条流水线的地基。

## 第七章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 检索/生成分段评估 | 评估的目的是定位，合并分数丢失归因信息 | `evaluate_retrieval` / `answer_faithfulness` 两个独立方法 |
| 指标写成纯函数 | 评估地基必须可手算验证、可组合、无环境依赖 | `rag_metrics.py` |
| 除零边界显式约定 | 无定义场景不约定就会悄悄污染均值 | recall=1.0 / precision=0.0 / ndcg=0.0 |
| NDCG 分级 + 折损 + 归一化 | 二值相关与"只看首个"都不足以刻画排序质量 | `ndcg()` |
| relevance_grades 可省略 | 渐进式标注，降低评测集冷启动成本 | `evaluate_retrieval` |
| 报告保留逐条明细 | 均值掩盖分布，bad case 要可下钻 | `RetrievalEvalReport.per_query` |
| LLM-as-a-judge + 防御式解析 | 语义等价性判断需要语义裁判；输出校验覆盖到值域 | `answer_faithfulness` |
| ToyEmbedding 测试策略 | mock 抽象层级不对时，造层级正确的假实现 | `tests/test_rag_eval.py` |

后续衔接：day030（Agent 评估）会把今天的评估思想推广到整条 Agent 链路；day071（M6-D9）会在完整 RAG 链路上用今天的评估器做端到端调优。
