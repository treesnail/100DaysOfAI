# day037 课后习题

共 10 题，覆盖今天所有学习目标：function calling 的机制与文本解析路线的差异、JSON Schema 设计要点、tool_calls 解析与参数校验、失败重试的反馈回路。建议完成时间：45~55 分钟。

## 第一部分：选择题

### 第 1 题（两条路线的本质差异）

关于 ReAct 文本解析路线与 function calling 路线的对比，下列哪一项描述是**错误**的？

- A. 文本路线的格式正确性靠提示词约束与解析器容错"求"出来，function calling 由协议与解码层约束提供近似强保证
- B. function calling 的循环骨架（调模型 → 执行 → 回填 → 再调模型）与 ReAct 完全同构，是演进而非替代
- C. function calling 一次响应可以返回多个 tool_calls，天然支持并行调用；文本协议一步只能表达一个 Action
- D. function calling 强制模型把推理过程写在 content 里，因此可调试性优于文本协议

### 第 2 题（JSON Schema 设计）

关于工具参数 JSON Schema 的设计，下列哪一项实践是**错误**的？

- A. 参数的 description 是写给模型看的"选参说明书"，应包含格式约定与示例
- B. required 字段必须显式声明，否则模型可能漏传关键参数
- C. schema 应当从 BaseTool 的元数据自动生成，与工具实现保持同源
- D. 为了简洁，schema 里的 description 可以省略——参数名本身（如 `expression`）已经足够表意

### 第 3 题（错误分类与处置）

模型调用 `calculator` 时传了 `{"expression": 42}`（number 而非 string），`validate_arguments` 拦截后，`FunctionCallingAgent` 的正确处置是：

- A. 直接终止任务，因为模型的输出不可信
- B. 把"参数 expression 应为 string，实际为 int"的错误详情以 tool 消息回填给模型，计入连续失败计数，让模型修正重试
- C. 静默地把 42 转成字符串 "42" 后继续执行
- D. 忽略这次调用，直接进入下一步

### 第 4 题

在 Python 中 `isinstance(True, int)` 为 True，因此 `validate_arguments` 对 `"type": "number"` 的参数直接做 `isinstance(value, (int, float))` 校验即可，无需特判 bool。（对 / 错）

`FunctionCallingAgent` 中，工具执行异常（如网络超时、服务不可用）与 schema 校验失败一样，都会消耗重试预算（计入连续失败计数）。（对 / 错）

## 第四部分：编程题

### 第 10 题（function calling 全链路离线演示）

**功能要求**：

在项目根目录新建 `scripts/function_calling_demo.py`，全程离线（LLM 用 MockLLM 的 `tool_call_responses` 脚本扮演）：

1. **Spec 与解析**：用 `CalculatorTool` 注册 ToolRegistry，经 `specs_from_tools` 生成 `FunctionSpec`，打印 `to_openai_tool()` 的结果并断言 `type == "function"` 且 `required == ["expression"]`。构造一段 OpenAI 线上格式响应（arguments 为 JSON 字符串），用 `parse_tool_calls` 解析并断言 id、name、arguments 均正确。用 `validate_arguments` 验证：合法参数通过；`{"expression": 123}`（类型错误）抛出 `SchemaValidationError`。
2. **Agent 重试回路**：创建 `FunctionCallingAgent`（`max_retries=2`），MockLLM 脚本依次为：（a）调用 calculator 但**漏传** expression；（b）修正后调用 `{"expression": "(1 + 2) * 3"}`；（c）直接回答 `(1 + 2) * 3 = 9`。运行 `agent.run("计算 (1 + 2) * 3")`，断言：最终答案正确；`agent.call_history` 中第一次调用失败且结果含"缺少必填参数"、第二次成功且结果为 `"9"`；第二次 LLM 调用的消息列表中存在含"参数校验失败"的 tool 角色消息；第三次调用的消息列表中存在含 `[calculator] 9` 的 tool 角色消息。
3. 打印关键中间结果，最后打印"全部断言通过"。

**提示**：脚本顶部需要 `sys.path.insert(0, str(Path(__file__).resolve().parent.parent))`；MockLLM 脚本里的 `arguments` 可以直接写 dict，Mock 会代为序列化成 JSON 字符串；`llm.calls` 记录了每一轮调用的完整 messages 列表，可从中检查回填的 tool 消息。
