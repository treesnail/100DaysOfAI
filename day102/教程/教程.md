# day102：把 100 天的失败族编成一份台账

> 阶段标签：结业之后的第二次扩张（原课程索引的 100 天之外）
> 学习时长：约 3 小时
> 前置依赖：day101（把 100 天的字编成索引）、day075（`transformer_core` 第一次命名 `ShapeError`）

## 环境与依赖

本日新增的**运行时依赖为零**：扫描只用标准库 `ast`，**不做 import、不联网、不读密钥**。
这是刻意的：这一课要证明的是"一批源码能不能被编成一份可复算的台账"，
而**任何会执行被扫描代码的写法（例如 `import`）都会把"编台账"变成"跑一遍整个仓库"**。

四处复用（今天一个子系统都没有重写）：

1. **材料**：36 份 `errors.py`（35 份历史 + 本课这一份），只被**读取**，不改写；
2. **`ast`**：标准库的语法树，这个仓库里此前的静态分析（如 day032 的检查脚本）用过它；
3. **复算口径**：摘要取 `sha256` 前 16 位（与 day053 / day088 / day099 / day100 / day101 同一口径）；
4. **三类判据**：相等 / 上界 / 下界（与 day099 / day100 / day101 逐字相同的结构）。

## 今日目标

day101 的结语说："一份检索不到的文档，等于一份没写过的文档。"
今天换一个资产，做一件更具体的事：**把这 100 天写下来的 194 个错误名字，编成一张可以被核对的表**。

```text
问题① 100 天之后，仓库里第二没有被利用的资产是什么？
问题② "这个失败该谁去修"这件事，现在靠什么回答？
问题③ 这张表的判据应该是什么？
```

今天的答案：

```text
问题① 是那些**每个包都写了一遍、却从来没被横向放在一起看过**的失败族：
       36 份 errors.py 里的 194 个族、59 条跨包继承
问题② 现在只能靠人肉翻——它没有"覆盖清单"，也没有"归属口径"
问题③ 判据不是"这张表好不好看"，而是"每一个基类名能不能被归属、
       每一份文件能不能被说清、同一批文件能不能编出同一张表"——
       **可复算 + 可归属才是这份产物的全部价值**
```

本日要建立的四件事：

1. **一份扫描**：`scan.scan_all()` → 36 份模块、194 个原始族 + 每份的别名表，
   **只用 `ast`，一行 `import` 都没有**；
2. **一份归属**：`resolve.resolve_base()` → 每个基类名归到 local / builtin / imported / unresolved；
3. **一份台账**：`ledger.build_ledger()` → 36 个根 + 158 个派生 + 一个 16 位摘要（`431c8e65508c5d61`）；
4. **一套判据**：七条性质、三类判据、六个失败族。

最终产出：`failure_ledger` 包八个文件（679 语句 / 146 分支）、
`tests/test_failure_ledger.py`（67 个用例，100% 覆盖）、`docs/failure_ledger.md`（12 节）、
`scripts/failure_ledger_demo.py`（5 节）。现场读数：

```text
扫描 36 份模块 | 没有 errors.py 的子包 18 个
归属 local 158 / builtin 36 / imported 59 / unresolved 0
台账：36 份模块 | 194 个族 | 36 个根 | 158 个派生 | 摘要 431c8e65508c5d61
最小基类数 1 | 最大继承深度 2
七条性质 7/7 通过
```

## 第一章：为什么"字"之后要编"名字"

day101 编的是**字数**：46 份手册 + 53 个子包自述。今天编的是**名字**：
每个子包都写过一份 `errors.py`，但从来没有人把它们摆在一起看过。

```text
每个包各写各的       "我这一族的错误叫什么、它是谁的子类"
没人横向看过         "这 194 个名字里，哪些是同一件事的同一个名字？"
```

这件事有一个天然的好处：**它完全不依赖模型能力**——
它只依赖"把文件收齐、把基类名归属对、把顺序定死"。

因此今天的四个读数是扫描 / 归属 / 台账 / 性质，而且它们**共用同一份台账**
（`study_lines(ledger=...)`、`check_all(ledger=...)` 读的是同一时刻的状态）。

## 第二章：收料——先说清"哪些文件必须进得来"

绝大多数"做一个静态分析"的教程从选**解析器**开始。今天从**收料**开始，因为：

> 一份没被扫到的 `errors.py`，与"这个子包没有失败族"在台账里读起来完全一样。

```text
被扫描的       smart_research_agent/*/errors.py       36 份
没有被扫描的   每个子包的其它 .py（它们的失败族定义都在 errors.py 里）
点名           packages_without_errors() → 18 个子包没有 errors.py（读数，不是失败）
```

第 18 个子包这件事值得单独说：**"没有 `errors.py`"不是错误**——
`agent` / `llm` / `api` 这些包有自己的错误处理，只是没有被收成一个 `errors.py`。
本课把它当成一个**读数**印出来，而不是一条失败性质：一条会在仓库**合理地**变化时变红的性质，
最后一定会被人关掉。

一条纪律与 day101 逐字相同：**宁可当场变红，也不要让一件东西静默地缺失。**
因此 `scan.scan_module` 对"一份 `errors.py` 里一个 `ClassDef` 都没有"是**抛错**，不是跳过：

```python
raise ScanError(f"{path} 里一个 ClassDef 都没有："
                "一份没有族的 errors.py 与'这个子包没有失败族'在台账里读起来一样。")
```

## 第三章：归属——四类，且 `unresolved` 必须被点名

台账的核心工序是把**源码里写的名字**变成**台账里的一个去向**。判定只有四类，顺序写死：

```text
① local      名字就在同一个 errors.py 里     ⇒ target 是本模块的族名
② builtin    名字在内置异常白名单里          ⇒ target 是内置异常名
③ imported   名字是某个 import 的别名        ⇒ target 是"模块.名字"
④ unresolved 以上三类都不是                  ⇒ 当场点名
```

### 3.1 为什么顺序不能换

```text
先 builtin 后 local    某子包若自定义了一个 ValueError（合法），本模块的族会被误认成内置异常
先 imported 后 local   本模块里的族会被误认成"从别处导进来的同名字"
```

因此 `resolve.py` 把顺序显式写出来，并且有一条测试专门钉住它
（`test_local_wins_over_builtin_and_imported`）。

### 3.2 跨包继承是一份"契约"

真实读数里 **imported 有 59 条**。它们长这样：

```python
from smart_research_agent.transformer_core.errors import ShapeError as CoreShapeError

class ShapeError(CoreShapeError, StackError):
    """形状不符…… 同时继承 transformer_core.errors.ShapeError：
    day075 那一层写 except ShapeError 的代码不需要改动就能兜住本层的失败。"""
```

这一条 `CoreShapeError` 就是一份**契约**：它让 day075 写的 `except ShapeError` 一路兜到后面几十层。
台账把它记成 `imported`（而不是 `local`），读的人一眼就能看出"这一层挂在了哪一层下面"。

### 3.3 `unresolved` 是本课的核心纪律

```text
一个"看起来像基类名"的字符串，如果没有人能说清它属于哪一类，
它就不该被静默地当成类名。
```

归属表当前读数是 **unresolved 0**；它被写成一条**上界**性质（⑤），
并且 `require_resolved()` 是"拒绝交付"的那条路——有未解析的名字就抛 `ResolveError`。

### 3.4 一个实现细节值得单独说

`ast.unparse(base)` 对 `class A(B, C)` 给出的基类名是 `"B"`、`"C"`，
对 `class A(mod.B)` 给出的是 `"mod.B"`。本课的白名单只认**裸名字**，
因此 `mod.B` 会落进 `unresolved` ——这正是我们要的：**属性形式的基类名必须被显式解析或显式点名**，
而不是被一个"宽松匹配"悄悄放过。

## 第四章：身份与深度

一个族只有两种身份：

```text
root   没有 local 基类 ⇒ 它是这一族在**本模块内**的根
sub    有 local 基类   ⇒ 它是一个派生族
```

现场读数是 **36 个根 + 158 个派生**，而根数正好等于模块数（36）——这不是巧合，
它是第 ④ 条性质：**每一份 `errors.py` 恰好一个根**。

```text
0 个根   只可能来自源码里的继承环（谁也不是根）
1 个根   读者不必猜"我该 except 哪一个"
2 个根   读者要先猜——「这一族的基类」这句话说不清
```

继承深度的口径也只有两行：

```text
depth(root) = 0
depth(sub)  = 1 + max(depth(local 父族))      ⇒ 实测最大深度 2
```

深度只在**同一模块内部**沿 local 基类算；跨包的 `imported` 基类不参与深度
（它指向另一份 `errors.py`，那是契约，不是本模块的层数）。
一个手算例子：`class CError(BError, AError)`、`class BError(AError)`、`class AError(ValueError)`，则
`depth(AError)=0`、`depth(BError)=1`、`depth(CError)=max(1,0)+1=2` ——
**多写一个父族不会让路径变长**。

## 第五章：可复算——把"并列"的不确定性显式消掉

台账的可复算口径只有一行：

```text
comparable() = (modules, ((包.名, 身份, ((raw, kind, target), ...)), ...))
digest()     = sha256(repr(comparable()))[:16]        ⇒ 实测 431c8e65508c5d61
```

`comparable()` 里**一个集合、一个字典都没有**。为什么这条如此重要？
因为 Python 的 `dict` **保留插入顺序**，而插入顺序取决于"先遍历了谁"：
只要出现一个集合，`repr` 就会随构建顺序漂移，"两次构建逐位相同"这条性质也就失去意义。

因此本模块在任何"集合 → 序列"的地方都显式排序：

```text
族       按"包名升序 × 源码顺序"排
归属表   按 BASE_KINDS 的固定顺序排（local / builtin / imported / unresolved）
别名表   按本地名排序
```

这与 day101 的"倒排表里的文档名必须排序""并列命中按名字兜顺序"是同一条纪律的第三次应用。

## 第六章：七条性质、六个失败族与五条边界

### 6.1 七条性质（三类判据齐全）

```text
1. ledger_covers_all_error_modules | [equality   ] | 读数 0 ✓ | 模块 36 份 / 期望 36 份
2. qualified_names_are_unique      | [equality   ] | 读数 0 ✓ | 族 194 个 / 不同的 包.名 194 个
3. ledger_is_reproducible          | [equality   ] | 读数 0 ✓ | 摘要 …5d61 / …5d61
4. every_module_has_exactly_one_root| [equality  ] | 读数 0 ✓ | 根 36 个 / 异常模块 0 个
5. base_references_resolve         | [upper_bound] | 读数 0 ✓ | 未解析 0 个 ≤ 上界 0
6. every_family_has_a_parent       | [lower_bound] | 读数 1 ✓ | 最小基类数 1 ≥ 下界 1
7. inheritance_depth_is_positive   | [lower_bound] | 读数 2 ✓ | 最大深度 2 ≥ 下界 1
合计：7/7 条通过
```

**四条相等、一条上界、两条下界**。三类判据里为什么必须有两类"有方向的界"：

```text
⑥ 每个族至少一个基类    基类多是正常的（多继承）⇒ 只能从下面兜住
⑦ 最大继承深度 >= 1      "链存在"只能从下面兜住（写成 == 1 会漏掉更深的链）
⑤ 未解析数不超过 0       越少越好的量 ⇒ 兜的是上限
```

第 ⑥ 条在本课**真的贴着线**：最小基类数是 **1**（下界也是 1）。
这意味着仓库里确实有一个"只写了一个基类"的族——`min_bases()` 读的就是它。
**判据的阈值要定在"数学上必然成立"的地方**，而不是"我希望它长这样"的地方。

### 6.2 六个失败族

| 族 | 该谁去修 |
|----|----------|
| `ScanError` | 改扫描：某份 `errors.py` 读不到或语法错时，先把它补进扫描范围 |
| `ResolveError` | 改解析或改源码：基类名无法归属时，补一条别名规则或删掉那个名字 |
| `LedgerBuildError` | 改台账实现：两次构建不一致时，去掉那个没有固定的量（集合序 / 字典序） |
| `CoverageError` | 改台账范围：某个子包没有 `errors.py` 时，要么补一个族、要么显式排除它 |
| `NumericError` | 改数据或改实现：非有限读数与非法上下界都属于"数值不可用" |
| `ParameterError` | 改调用：包名 / 性质名 / 判据 / 上限都是调用点的一次决定 |

`FAMILY_OUTCOMES` 与 `_FAMILY_CLASSES` 逐键对齐，导入期断言。两条族常量：

```text
RETURNED_FAMILY = "ShapeError"
  day075 的 transformer_core 第一次给它命名，此后被十来个包各写一遍——
  它是本台账里跨包重名之最。day101（编索引）没有它；day102 要把这些同名族摆在一张表上，
  于是"一个族的名字 / 基类与它该有的对不上"重新需要一次控制流事件。

ABSENT_FAMILY = "GradientError"
  本课是一次纯静态扫描：不但没有反向，连一次前向都没有跑（它连 import 都不做）。
```

### 6.3 五条边界

```text
1. 不新增任何第三方依赖：扫描只用标准库 ast。
2. 不改动任何既有模块、既有测试、pyproject 与 docs 下的既有文件——只新增文件。
3. 不做 import：读源码文本并解析 AST，因此语法错误会被当场点名。
4. 全部读数离线、确定性：只读文件系统与 ast，不联网、不读密钥。
5. 不判断设计好坏：只如实记录"谁继承了谁"，不评价"这个继承关系该不该存在"。
```

第 3 条与 day101 的"语料是被读取的、不是被改写的"必须连起来读：
**这份台账不是一次代码审查，它是一张可复算的对照表。**

## 结语：三条可以带走的工程结论

1. **先把"哪些文件必须进得来"说清，再谈解析。**
   本课的第一条性质是覆盖（36/36），它排在所有结构性质之前。
   一份没进台账的 `errors.py`，与"这个子包没有失败族"在结果里读起来完全一样。

2. **四类归属里必须有一类是"我承认我不知道"。**
   `unresolved` 不是解析器的失败，而是**纪律**：一个没人说得清归属的名字，
   比一个报错更难被发现。把它做成一条上界性质（⑤），它就不可能被"兜住"。

3. **每一条性质的方向要和这个量的方向一致。**
   覆盖数、差异项数是**相等**；"未解析不超过 0"是**上界**；
   "每个族至少一个基类""最大深度 >= 1"是**下界**。
   方向错了，性质会在系统**变好**的时候误报失败，然后被人关掉——
   而一条被关掉的性质，等于不存在。

> **诚实的说明**：本课是**离线、确定性**的——它不调用任何模型、不做任何推理，
> 也不测量"这个设计好不好"。它给的是**一套能带走的名字纪律**：
> 当你真的要为一个代码库建一份错误台账时，知道该先收齐什么、
> 该给每个名字一个怎样的去向、该断言哪七件事。
