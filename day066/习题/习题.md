## 第一部分：选择题

### 第 1 题（召回深度与封顶）

关于 `fetch_k` 与 `MAX_FETCH_K`，下面哪一句是**对的**？

- A. `fetch_k` 就是 `top_k` 的别名：库侧只认一个条数参数，所谓"过取三倍"只是手册里的一句建议，真正取回多少仍然由 `top_k` 决定
- B. **没有显式 `fetch_k` 时按 `fetch_k = max(top_k, ceil(top_k × 3))` 算（`DEFAULT_FETCH_MULTIPLIER = 3`），两条路都要封顶 `MAX_FETCH_K = vectorstore.MAX_TOP_K = 1000` 并在 `notes` 里写明"已封顶"：`top_k=5 → 15`、`top_k=334 → 本应 1002 → 实际 1000`；而 `MAX_FETCH_K` 直接复用上游常量，是因为两个数字一旦分开就会出现"设置里写 2000、实际只取了 1000"这种只能靠读代码才发现的差值**
- C. 封顶到 1000 之后不该在 `notes` 里写话：深度是内部实现，"已封顶"这类提示会淹没真正的错误信息，报告应当只留错误
- D. `top_k=334` 时应当报 `QueryError`：倍率算出来的 1002 超过了上限，说明调用方把 `top_k` 配错了，应该让它在构造期就失败

### 第 2 题（时间范围与字段撞车）

关于 `TimeRange` 与 `where` 的关系，下面哪一句是**对的**？

- A. 时间范围应当先 `datetime.fromisoformat` 解析成 `datetime` 再比较：字符串比较在跨月、跨年、闰年这些情形上都会给出错误答案
- B. `where={"created_at": {"$gte": "2026-01-01"}}` 配上 `TimeRange(start="2026-06-01")` 时，取交集是正确做法：两个条件都满足本来就等价于"6 月之后"，替调用方合并一次还能少一层 `$and`
- C. **闭区间 `[start, end]`（两端可单独省略）、按「ISO 文本」比较（同一种 ISO 文本的字典序 = 时间序）、字段缺失的记录被 `$gte` 判为不命中而「排除」；实测 8 条记录里只有 6 条落在整月区间内，缺的两条一条在区间外（8 月）、一条根本没有 `created_at`（被排除）——而 `where` 与 `time_range` 撞在「同一个字段」时必须抛 `QueryError`，因为"我到底想要哪一段"会由两份条件取交集的副作用决定，而结果只会变少、不会报错**
- D. 字段缺失的记录应当被当成"最新的那一条"补进区间：既然它没有时间戳，说明它才刚入库，按"现在"处理才不会漏召回

### 第 3 题（阈值在哪一层落刀）

关于 `min_score` 与三个 `dropped_*` 数字，下面哪一句是**对的**？

- A. `min_score` 应当传给 `backend.query`：库侧过滤更快，而且结果集合完全相同，所以"在哪里切"只是性能问题
- B. 三个 `dropped_*` 应当合成一个 `dropped`：报告里一个数字更好读，反正它们都表示"这次少了几条"
- C. **阈值必须在检索器里落刀、并且用 `>=`：`VectorBackend.query` 也接受 `min_score`，但检索器「故意不传」——交给库过滤时"切掉了几条"这个数字拿不到，而在本层落刀能记下 `dropped_below_threshold`（day067 的融合要用它判断"这一路是不是一条都没活下来"）；用 `>=` 而不是 `>` 是因为"阈值恰好等于某条命中的分数"是「必然出现」的情形（同一个确定性编码器对同一段文本给出逐位相同的向量），实测 `min_score=0.8` 时分数精确为 `0.8` 的那条必须留下，`dropped_below_threshold=5`**
- D. `dropped_by_top_k > 0` 说明检索器有问题：上限就是 `top_k`，超出的部分本该在召回时就不取回来

### 第 4 题（空结果诊断）

关于 `empty_reason` 与它背后的诊断表，下面哪一句是**对的**？

- A. 空结果应当把四种成因一次列全：报告里写"可能是库空、可能被过滤、可能被阈值、可能被多样性"，最保险，免得漏判
- B. `max_per_doc=1` 会让结果变成空：同一文档刷屏时命中会被整组挤掉，因此 `diversity_trimmed` 是端到端最常见的空结果原因
- C. 优先级应当改成"阈值 → 过滤 → 库空"：库有没有数据是要另外查的，而被阈值切掉最常见，让它先说更实用
- D. **`empty_reason` 只允许「一个」取值，来自封闭清单 `EMPTY_REASONS`（顺序 = 优先级：`hits` → `no_data` → `filtered_out` → `below_threshold` → `diversity_trimmed`），因为四种成因对应的动作完全不同（建索引 / 放宽过滤 / 降阈值 / 放宽多样性），"报告里写四条可能的猜测等于什么都没说"；而 `diversity_trimmed` 这一支在当前算法下端到端「不可达」（第 7 步每组至少留一条），它是一条「防御性」分支，保留的理由是"诊断规则不该依赖某一步的内部细节"**

### 第 5 题（上下文打包）

关于 `pack_context` 的预算与计数，下面哪一句是**对的**？

- A. 预算不够时应当**按比例平均**切每一条：让每条都短一点，比"整条丢掉"更公平，读起来也更整齐
- B. 单条超过上限时应当整条丢掉：半截片段没有价值，留着只会让模型读到一段以逗号结尾的残缺句子
- C. **`retrieval_max_context_chars = 2400`（按 6 个 ~400 字的片段标定）、`retrieval_per_hit_chars = 800`（预算的 1/3）、`DEFAULT_MIN_HIT_CHARS = 32`（低于它的片段进上下文只是噪声）；五步顺序固定（解析预算 → 单条截断 → 拼包 → 从尾部整条丢 → 「至少保一条」），预算紧到只剩一条时把它截到 `max_chars` 后「返回它而不是返回空」（空上下文会让整条 RAG 链路走进"检索为空"的分支，一次 LLM 都不调），而"至少保一条"那次截断「不计」进 `truncated_hits`——它的证据是 `char_count == max_chars`**
- D. `truncated_hits` 与 `dropped_hits` 应当合成一个"被预算削过的条数"：两个数字都是"包放不下"的证据，分开只会让报告变啰嗦

## 第二部分：判断题

### 第 6 题

`Retriever.retrieve` 的顺序是"先算深度、再体检、然后才合成过滤条件"。
既然库为空时会走一条早退（返回 `empty_reason="no_data"`），那么这条早退应当排在
`combine_where` **之前**——库都空了，过滤条件合不合法就不重要了，
`where` 与 `time_range` 撞在同一个字段这种调用方错误，等库非空时再报也不迟。（对 / 错）

### 第 7 题

`RetrievalResult.dropped_by_top_k` 为正不代表出了问题：它只是"取够了"
（召回深度取回的条数多于要返回的条数）；真正要拿去找参数的是另外两个数字
——`dropped_below_threshold` 去调 `retrieval_min_score`、
`dropped_by_diversity` 去调 `retrieval_max_per_doc`。（对 / 错）

### 第 8 题

检索为空时 `answer.answer` 直接取 `FALLBACK_NO_CONTEXT`，因此"这次到底调没调模型"
用 `answer == FALLBACK_NO_CONTEXT` 就能判断，不必再加一个 `llm_called` 字段；
同理，提示词模板里少写一个 `{context}` 也不必在构造期拦——`format` 不会因此失败，
只是模型少看到一段资料而已。（对 / 错）
