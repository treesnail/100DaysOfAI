## 一、两级增量

### 1. 两级增量

```text
文件级（rag_ops.sync.plan_sync）    两份语料快照的差集      → "要不要跑这一趟"
块级（indexing.planner.plan_index） 上一版清单与这批记录     → "要重算哪些向量"
```

两者必须都在，理由是"谁也替代不了谁"：

```text
只做块级增量   要算差集就必须先把语料**全部解析、全部切块**——
               省下的是编码，浪费的是解析与分块（这一层最贵的一段）
只做文件级增量 一份 4000 字的文档改一个字，它的十几块全部重新编码
```

还有一个容易被忽略的收益：文件级先判一次，"一份都没变"时**连语料目录都不必细看**
（只是扫盘、算指纹），而这条路径在生产里占绝大多数次数。

### 2. 扫两次盘，快照号相同吗

```bash
cd day072/源码/smart-research-agent
python -c "
from pathlib import Path
from smart_research_agent.rag_ops.snapshot import scan_sources
root = Path('outputs/rag_ops_demo_work/corpus')   # 或自己建一个两份文档的目录
first = scan_sources(root)
second = scan_sources(root)
print(first.digest, second.digest, first.digest == second.digest)
"
```

- **相同。** 快照号由 `snapshot_id` 算出，而它只吃 `(source, fingerprint)` 两列：

  ```python
  body = "\n".join(f"{entry.source}|{entry.fingerprint}" for entry in entries)
  return hashlib.sha256(f"snapshot|{SNAPSHOT_VERSION}|{body}".encode()).hexdigest()[:16]
  ```

- **改 `created_at` 不会让 `digest` 变。** 时间戳只进 `to_dict()`，不进身份
  （`test_digest_ignores_created_at_and_skipped` 钉住了这条性质）。

理由与 day065 的"能重算的才叫版本号"逐字相同：一旦时间进了身份，
"这份快照是哪台机器、哪一刻扫的"就会变成必须回答的问题——而它其实不该被问。
更要紧的是：**含时间的身份会让每一次调度都判定"要同步"**，而那看起来只是"调度很勤快"。

### 3. 漏一份来源

```python
SyncPlan(unchanged=("docs/a.md",), previous_sources=("docs/a.md", "docs/b.md"))
```

- 抛 `SyncError`，消息是：

  ```text
  差集没有完全解释上一份快照：漏掉的来源 ['docs/b.md']、多出来的来源 []。
  漏掉的来源会静默地留在库里（没人删它），而它的表象只是"这次改得不多"。
  ```

- **不校验的后果**：`docs/b.md` 不在任何一组里。若上一版在库里、而这一次语料里
  它已经没了（本应 `removed`），那么**它会被永久留在库里**——用户提问时仍可能
  检索到一份已经不存在的文档。
- **为什么没有报错指向它**：所有下游步骤都"正常"完成了。`build_from_records`
  看到的是"这批记录里没有它"吗？不是——它看到的是**上游给出的差集**。
  整个链路上没有一步会去问"这份来源去哪了"。

  这类 bug 的特征是：**没有任何异常、只有检索质量下降**。因此它必须在
  构造期被拦下——差集是纯函数算出来的，本来就应该满足那两条恒等式。

### 4. 变更比例的分母

```python
        union = {*self.previous_sources, *self.current_sources}
        if not union:
            return 0.0
        return round(self.changed_count / len(union), 6)
```

举一个"删光了"的例子：上一份快照有 5 份来源，这一份一份都没有。

```text
用当前来源数做分母    5 / 0  → 除零（或者按"当前是 0 就返回 0"处理 → 0.0）
                     而 0.0 的含义是"没有任何变化"——与事实完全相反
用并集做分母          5 / 5  → 1.0（"这一趟全变了"）
```

`1.0` 才是要传给"要不要整库重建"的那个数字：整库清了、重写了，
而 0.0 会让它继续走增量——在一次"删光了"的变更上走增量，
意味着库里那些**已经不该存在的块**会继续留着。

## 二、水位与账本

### 5. 三段式场景

设第一次成功的快照是 `S1`，时间 `T1`；第二次失败在 `T2`；第三次成功在 `T3`，
此时语料仍是 `S1`。

```text
        snapshot      last_run_at   last_success_at   consecutive_failures   runs  failures
初始    None          ""            ""                0                      0     0
①成功   S1            T1            T1                0                      1     0
②失败   S1（不动）     T2            T1（不动）         1                      2     1
③成功   S1            T3            T3                0（清零）              3     1
```

- 第 ② 步的关键是 `snapshot` 与 `last_success_at` 都**不动**（`mark_failure` 只改
  `last_run_at` / 计数 / `last_error`）。
- **如果失败时推进了水位**：`snapshot` 会变成"第二次那份扫描结果"，
  而那份扫描**没有被成功入库**。于是第三次运行时 `plan_sync(S2, S2)` 会得出
  "一份都没变"——那批来源被**永久跳过**，库里少的记录没有任何地方会提醒你。
- **为什么"重跑幂等"是前提**：失败不推进水位的代价是"同一批来源会被再处理一次"。
  这笔代价只有在"重跑不会造成额外后果"时才可承受——而 day065 的增量对账
  正好保证了这一点（没变的块判 `unchanged`，不重新编码；重复写同一条记录是覆盖）。
  所以：**重跑幂等、漏更新不幂等**，因此宁可重复处理。

### 6. 两种"文件不存在"

```text
RagBaseline.load   文件不存在 → **报错**（FileNotFoundError）
                   理由："没有基线"与"基线全是零"是两回事，
                        后者会让回归门禁静默放行（0 → 0 判 unchanged）
SyncLedger.load    文件不存在 → 返回**空账本**
                   理由："没有账本"就是**首次运行**，它本来就该按全量处理一遍；
                        报错只会让一次全新的部署起不来
```

两者都**不接受"读不懂"**：坏 JSON、格式版本不认识一律抛
（`RagBaseline.load` 抛 `BaselineError`，`SyncLedger.load` 抛 `SyncError`）。
理由同源——**假账比没有账危险得多**。

### 7. 两个路径与"为什么不进 git"

```text
账本   settings.rag_ops_ledger_path = "data/ops/sync_ledger.json"
报告   settings.rag_ops_report_path = "outputs/rag_ops/ops_report.json"
清单   settings.indexing_dir        = "data/index"（版本表 + 备份，day065）
```

`.gitignore` 里新增的三行（含注释）：

```text
# 账本进了 git 的后果很具体：一次全新的部署会以为"我已经同步过了"，
# 于是第一次运行只做增量——而增量在空库上等于什么都没做。
data/ops/
# day065 的 indexing_dir：清单、版本表与备份（落盘时机由运维层决定）
data/index/
```

- **账本进了 git**：新部署克隆下来就"有水位"，而库里其实是空的 →
  第一次运行只做增量 → **一行都不写**（差集里全是 `unchanged`）。
- **清单/版本表进了 git**：同理，旧清单会让"首版构建"变成"增量更新"，
  而 `parent_version` 指向一个本地根本不存在的版本。
- 注意二者的差别：`data/eval/*.jsonl`（评测语料与**基线**）是**要进 git** 的
  ——那是"可比较的参照物"，而账本与清单是"这一台机器的状态"。

## 三、调度

### 8. 抖动为什么用散列

两条理由：

1. **同一次判定必须可复现**：`/rag/ops/status` 显示的"下一次"与报告里记的
   "下一次"必须是同一个时刻。用 `random` 时它们是两次独立调用，
   于是会出现两个不同的时间——而那种不一致会被读成"调度自己改了主意"。
2. **测试不能 flaky**：抖动落在 `[0, 300]` 秒里，用随机会让"还差多久"
   这条断言偶尔落在边界的两侧。

第二个分量用**运行序号**（而不是机器名/主机名）：为了**可重算**——
换一台机器、跑同一份账本，应当得到同一个抖动。这与 day065 的
"能重算的才叫版本号"是同一条纪律；用主机名的实现会得到
"抖动取决于在哪台机器上算的"，而那是不可复现的。

### 9. 手算抖动与三日推演

- **不能手算，但可以重算。** `jitter_seconds` 是
  `int(sha256(f"{anchor}|{run_index}").hexdigest()[:8], 16) % 301`，
  它要求一次 sha256——手算不可行，但**同输入永远同输出**，
  因此可以用一行代码复核。
- 锚点 `2026-10-06T03:00:00Z` 的两个抖动（实测）：

  ```text
  jitter(run_index=0) = 278 秒
  jitter(run_index=1) = 125 秒
  ```

  **首次运行取的是 `run_index = runs + 1 = 1`**（`runs` 是"已经跑过几次"，
  因此这一次是第 `runs + 1` 次），所以首次运行的计划点是
  `2026-10-07T03:02:05Z`——正是演示脚本第 2 节打出来的那个时刻
  （`03:00:00 + 1440 分钟 + 125 秒`）。

```python
from datetime import datetime, timezone
from smart_research_agent.rag_ops.schedule import decide, jitter_seconds
from smart_research_agent.rag_ops.types import SchedulePolicy, SyncLedger

policy = SchedulePolicy()
anchor = "2026-10-06T03:00:00Z"
ledger = SyncLedger(snapshot=None, last_run_at=anchor, last_success_at=anchor, runs=1)
print(jitter_seconds(policy, anchor=anchor, run_index=0))          # 278
print(jitter_seconds(policy, anchor=anchor, run_index=1))          # 125

for day in (7, 8, 9):
    now = datetime(2026, 10, day, 4, 0, 0, tzinfo=timezone.utc)
    decision = decide(policy, ledger, now=now)
    print(day, decision.mode, decision.missed_runs, round(decision.lag_minutes, 1),
          decision.next_run_at)
```

实测输出：

```text
7  due  0   57.9    2026-10-08T03:02:05Z
8  due  1   1497.9  2026-10-09T03:02:05Z
9  due  2   2937.9  2026-10-10T03:02:05Z
```

**验证 `next_run_at = 锚点 + (missed + 2) × 间隔 + 抖动`**：

```text
missed=2 → 锚点 10-06 03:00 + 4 × 1440 分钟 = 10-10 03:00，再加 125 秒抖动
        = 2026-10-10T03:02:05Z  ✓ 与实测一致
```

三行里最值得注意的是**计划点始终是 `03:02:05`**（`effective_at` 不变），
只有 `missed` 在增长——这证明了"补跑只影响这一次跑不跑，
不影响计划本身"。

### 10. 如果"下一次"从实际运行时间起算

推演（间隔 1 天、计划点 03:00、每天迟到 2 小时）：

```text
第 1 天   计划 03:00，实跑 05:00 → 下一次从 05:00 起算 → 第 2 天计划变成 05:00
第 2 天   计划 05:00，实跑 07:00 → 下一次从 07:00 起算 → 第 3 天计划变成 07:00
第 3 天   计划 07:00，实跑 09:00 → ……       → 第 4 天计划变成 09:00
```

每天往后漂 2 小时，**12 天之后计划点就漂到了次日**：
一个"每天凌晨跑一次"的调度会在两周内变成"每天下午跑"。

纪律：**"下一次"必须锚定在"计划"上，而"锚点"是上一次的尝试时间**
（不是完成时间、不是当前时间）。代码里体现为 `_next_run_at(..., anchor=anchor)`
与那个 `intervals=missed + 2`——补跑只影响"这一次跑不跑"，
不影响"下一次什么时候"。

### 11. 退避的第 5 次与第 40 次

```python
    def backoff_seconds(self, consecutive_failures: int) -> int:
        if consecutive_failures <= 0:
            return 0
        exponent = min(consecutive_failures - 1, 20)
        return min(self.backoff_base_seconds * (2**exponent), self.backoff_max_seconds)
```

- 第 5 次失败：`60 × 2^4 = 960` 秒 = 16 分钟（未超过 3600，因此不封顶）。
- 第 8 次：`60 × 2^7 = 7680` → 封顶成 3600 秒（1 小时），此后一直是 1 小时。
- 第 40 次若不限制指数：`60 × 2^39 ≈ 3.3 × 10^13` 秒 ≈ **100 万年**。
  即使封顶也会算出这个中间值（Python 的大整数不会溢出，只会算出一个巨大的数），
  而"先算出一个天文数字再封顶"与"先限制指数再算"在结果上相同、
  在**意图上**完全不同：后者明确表达"指数本身必须被限幅"。
  写 `2 ** min(n - 1, 20)` 的收益是：读的人不必去算"这个式子在 n 大时会不会炸"。

## 四、健康与监控

### 12. 探针跑评估的雪崩场景

假设 `quality_regression` 每次都真的跑一遍 6 条用例的端到端评估（检索 + 生成）：

```text
探针每 30 秒被调用一次（compose 的 interval: 30s）
    ↓
每个实例每分钟跑 2 次评估，每次 6 次模型调用 + 6 条检索
    ↓
提供方限流 / 网络抖动 → 评估超时 → 探针失败
    ↓
state=fail → /rag/ops/health 返回 503 → 编排层把**所有**实例标记为不健康
    ↓
一次外部依赖的抖动，演变成"全部实例被摘掉"的全站故障
```

更隐蔽的一层：探针失败的真正原因是**评估跑不动**，而不是**这个实例答不了问题**。
把两件事绑在一个探针上，等于让探针回答一个它不该回答的问题。
正确的分工是：探针读"别人已经算好的账"（库计数 / 清单 / 账本 / 已有评估结论），
评估由 `/rag/eval/run` 或定时任务单独跑，结论落盘后再被读到。

### 13. 四种"缺输入"

| 检查项 | 缺什么 | `warn` 消息的要点（谁该做什么） |
|--------|--------|-------------------------------|
| `vector_store` | 库空（且允许空库） | "灰度实例等第一次同步"——先跑一次 `POST /rag/ops/sync` |
| `index_integrity` | 没有清单 | "这个实例不知道库里的记录是哪一版、由谁建的"——跑一次同步会生成清单 |
| `corpus_freshness` | 从未成功同步 / 账本缺失 | "库里的内容来自上一次部署"——跑一次同步建立水位 |
| `quality_regression` | 没有评估结果 / 没有基线文件 | "本次不判质量（跳过不等于通过）"——跑一次 `/rag/eval/run` 并把基线提交进仓库 |

四条消息都遵循同一条写法：**说清"缺了什么" + "谁该去做什么"**。
一句"数据不足"是没法照着修的。

### 14. 质量指标缺席时返回空

```python
def samples_from_quality(quality: RagBaseline | None, *, at=None) -> tuple[MetricSample, ...]:
    if quality is None:
        return ()
```

- **看板上会出现的那句没有支撑的结论**：

  ```text
  "本服务的幻觉率 0.0%（近 7 天）"
  ```

  而真相是"这 7 天**没有跑过一次评估**"。0 与"没量到"在图表上是同一条线，
  但在语义上一个是"很好"、一个是"不知道"。
- 报告缺少某一项时也不许用 0 顶上：

  ```python
        if source not in quality.metrics:
            raise MetricsError(
                f"评估基线里缺少指标 {source!r}（监控要抄成 {name}）："
                "缺一项时**不能**用 0 顶上——'没量过'与'量出来是 0'是两回事。"
            )
  ```

  理由：一份"少了一项"的报告一旦被允许静默补 0，整条监控链路里
  就再也分不清"健康"与"没在量"——而这两个状态需要完全不同的处置。

### 15. 为什么 `sources_total` 不给方向

```text
higher_better 的语义是"这个数字变大代表服务变好"
sources_total 变大   可能语料更全（好），也可能是有人在灌噪声（坏）
index_records 变大   可能覆盖面更广（好），也可能是重复入库（坏）
```

给出方向等于给一条**永远会被手工忽略**的告警线：当"变大"既可能是好事
也可能是坏事时，读的人第一次收到告警就会去放宽阈值，第二次就会静音。
这一层的选择是：**只对"方向确定"的指标标方向**，其余标 `neutral`
（把"这个数不参与判定"写成一条明确声明，而不是靠"它恰好没超阈值"）。

## 五、编排

### 16. R2 为什么是"二选一"

- **不能要求"每个服务都必须有探针"**：批处理容器（`rag-ops-sync`）
  不监听端口，因此没有可探活的 HTTP 面。硬塞一个 `CMD true` 的探针
  等于把"没有探针"伪装成"探针永远绿"——而那比没有探针更危险：
  它让人**以为**有检查。
- **两种情况都要报错**：

  ```text
  既没有探针、也没有理由   编排层看不见它坏（缺失必须是有意的，并写下来）
  既有探针、又有理由       读的人不知道该信哪个（两者只能有一个）
  ```

  这是"缺失必须显式"这一条纪律的两个方向：**不许缺而不说，也不许说了又给**。

### 17. R7 为什么不写成"路径深度 ≥ 2"

- **误伤的真实路径**：官方 Chroma 镜像推荐的挂载点是 `/data`
  （`chromadb/chroma` 的 compose 示例就是 `./chroma-data:/data`）。
  深度 1 会被"路径深度 ≥ 2"直接拦掉——而那是一个正确的、被官方文档推荐的配置。
- **`/app/smart_research_agent` 为什么在清单里**：它装的是**应用代码**。
  把卷挂到它上面会遮住镜像里的代码（容器会以"模块找不到"的形式起不来），
  而这类事故的根因看着像"镜像构建失败"。

因此 R7 的判据是"**这个路径是不是镜像自带的**"，用一张前缀清单表达：

```python
RESERVED_MOUNT_PREFIXES = ("/bin", "/boot", "/dev", "/etc", "/lib", "/lib64",
                           "/proc", "/sbin", "/sys", "/usr", "/var/run",
                           "/app/smart_research_agent")
```

清单本身也是可读的：它是一份"镜像里都有什么"的明确声明。

### 18. 手改 yml 会发生什么

```bash
python -m pytest tests/test_rag_ops_deploy.py -q --no-cov
```

- 失败的用例是 `TestShippedArtifacts::test_committed_compose_matches_the_spec`，
  消息里给出**第一处不同的行号**与两行内容：

  ```text
  'docker-compose.rag.yml' 第 38 行与规格渲染结果不一致：
    仓库里：      start_period: 99s
    规格算：      start_period: 20s
  （手改 compose 不是错误，但必须同时改 specs：见 docs/rag_ops.md）
  ```

- **"渲染必须确定性"是这条检查能成立的前提**：如果渲染结果里含时间戳、
  随机容器名或"按字典插入顺序"的键序，那么每次渲染都会与文件不同，
  于是这条检查永远在报"不一致"。而一个永远报警的检查会在三天内被静音——
  之后**真正的漂移**也一起被静音了。

### 19. 为什么用 uvicorn 的 factory 模式

```python
API_COMMAND: tuple[str, ...] = (
    "python", "-m", "uvicorn",
    "smart_research_agent.api.app:create_app", "--factory",
    "--host", "0.0.0.0", "--port", str(API_CONTAINER_PORT),
)
```

`python -m smart_research_agent.api.app` 的 `main()` 是：

```python
def main() -> None:
    uvicorn.run(create_app(), host="127.0.0.1", port=8000)
```

绑 `127.0.0.1` 是**本地开发的正确默认值**（不出网、更安全），
但在容器里它是错的：`127.0.0.1` 是容器自己的回环地址，
宿主机的端口转发**一个包都进不来**。

三个症状：

```text
① 容器状态 healthy（探针在容器内访问 127.0.0.1 能通）
② 宿主机的 docker ps 显示端口已映射（0.0.0.0:8080->8080/tcp）
③ 从宿主机 curl 却超时 —— 而容器日志里什么都没有（请求根本没到应用）
```

这类故障最难查的地方正是三者同时成立：**每一个局部看起来都正常**。

## 六、端点与流程

### 20. 状态码的两种取向

**`/rag/ops/health` 的 `fail` 必须是 503**：

```text
compose 里的探针是 curl -f http://localhost:8080/rag/ops/health
curl -f 在 HTTP >= 400 时返回非零退出码 —— 它**只看状态码**
```

因此"把状态放在响应体里让人自己看"在自动化编排里不是一条可用的约定：
永远返回 200 的探针等于没有探针。响应体里同时给三态计数与四项判据，
是给**看板与人**看的；状态码是给**编排层**看的。

**`/rag/ops/sync` 的运行失败是 200、而"账本坏了"是 400**：

```text
200  report.status ∈ {not_due, no_change, synced, failed} —— 本次运行**有结论**
400  请求本身不可执行（账本损坏 → SyncLedger.load 抛 SyncError；语料目录没配对）
503  这个实例没有装配运维流水线
```

四档状态塞进 HTTP 状态码会让"没到点"与"同步失败"在监控里长得一样，
而它们的处置完全不同：前者什么都不用做，后者要有人去看。
反过来，"跑不了"（账本坏了）是调用方要改的东西，因此走 400。

### 21. 空转不覆盖证据

- 哪一档：**`not_due`**。`run_once` 里那一支调用
  `_finish(..., persist=False)`。
- **`_finish` 只留一个出口**的理由：

  ```text
  三条成功路径与一条失败路径如果各自拼一份报告，
  迟早会有一条忘了带上 schedule —— 于是"这次为什么没跑"再也答不出来
  ```

  一个出口让"每一次运行都有报告"变成结构上的必然。
- **如果空转也写报告**：`/rag/ops/status` 的 `last_report` 会被一串
  `{"status": "not_due"}` 覆盖，而值班的人打开它想看的恰恰是
  **"上一次真实运行到底成没成"**。worker 每 15 分钟醒一次，
  因此这个覆盖在一天里会发生约 96 次。

### 22. 端点实测

```bash
# 需要先起一个 app（测试里用 TestClient；本地可以 python -m uvicorn ...）
python -m pytest tests/test_rag_ops_pipeline.py -q --no-cov -k ops
```

用 `tests/test_rag_ops_pipeline.py` 的 `make_client` 实测：

```text
① POST /rag/ops/sync {"force": true}  → 200，report.status = "synced"
   GET  /rag/ops/status               → schedule.decision.mode = "forced"
② 再 POST 一次（不带 force）           → 200，report.status = "no_change"
```

## 七、综合题

### 23. 把 `/rag/ops/sync` 接进 CI/CD

一条可用的发布前判定链（在 day032 的流水线里插在"评估"之前）：

```text
① 同步语料            POST /rag/ops/sync {"force": true}
   report.status == "failed"        → **阻塞**并通知（水位没前进，本次不能发）
   report.status ∈ {synced, no_change} → 继续
   report.status == "not_due"        → 不该出现（force=true 绕过了判定）；出现说明有 bug

② 索引一致性          verify_index(pipeline.current_manifest(), store)
   有问题                            → **阻塞**（检索结果会少条或多条）

③ 质量体检            GET /rag/ops/health（或 pipeline.health_report()）
   state == "fail"                   → **阻塞**（含质量回归）
   state == "warn"                   → 记入发布说明，**继续**
                                        （warn 的典型来源是"没有评估结果"，
                                          而第 ④ 步会补上那一次评估）

④ 质量评估            POST /rag/eval/run（day071）→ 与基线对比
   有回归                            → **阻塞**
   不可比（inconclusive）             → **告警 + 放行并备注**（样本不足时不下结论，
                                        但也不该静默通过）
```

**为什么"运行失败"与"质量退化"要分开处理**：

```text
运行失败（failed）      本次没有产出任何新东西 → 门禁的输入是"旧的"，判它没有意义
                        处置：修好再跑（常见原因：语料目录、编码器、权限）
质量退化（health fail）  本次成功产出了新东西，但答案是坏的
                        处置：回滚（索引版本或提示词版本），而不是重试
```

把两者合成一档，会让"重试一次就好"与"必须回滚"在流水线里得到同样的动作——
而它们的正确动作是相反的。

### 24. 两处"两份账"

**第一处：文件级的账 vs 块级的账**

```text
语料侧（SyncPlan）    粒度 = 文件    用途：要不要跑这一趟 / 这次改了几份
索引侧（IndexPlan）   粒度 = 块      用途：要重算哪些向量 / 这次动了几块
```

两者回答的问题不同，因此**差额本身是一条读数**
（实测：改一份 4000 字文档 → 文件级 1、块级"写入 1 + 删除 1"）。

**第二处：账本 vs 报告**

```text
sync_ledger.json   状态：水位 + 尝试史            ← 必须能被**下一次运行读到**
                   寿命：与这台部署同寿（重建即丢）
                   写者：只有 pipeline 的 mark_success / mark_failure
                   读者：schedule.decide、health、metrics

ops_report.json    证据：一次运行的完整现场        ← 给人看的
                   （状态 / 调度判定 / 差集 / 构建报告 / 体检 / 采样 / notes）
                   寿命：每次运行被覆盖一次（`not_due` 除外）
                   读者：/rag/ops/status 的 last_report、排查时的人
```

分开存的三条理由：

1. **权限与寿命不同**：账本是"只被运维流水线改写"的状态；
   报告是"只被读"的产物（人可以直接打开、可以归档、可以贴进事故复盘）。
2. **体积与频率不同**：报告每次运行都会重写（含逐条 notes），
   而账本只在成功/失败那一刻前进一次。
3. **丢失的代价不同**：账本丢了 → 下一次退化成全量（幂等，昂贵）；
   报告丢了 → 只是少了上一次的证据（下一次运行就会有一份新的）。

## 八、复盘

### 25. 只留四个模块

一种合理的取舍（不同取舍只要理由成立都算对）：

```text
留下 types.py     形状与封闭表：没有它，其余模块之间没有可校验的契约
留下 sync.py      两级增量的上半段：它回答"要不要跑"，是省下成本的那一半
留下 schedule.py  纯函数判定：容器/平台换了它也不用改（"判定与载体分开"）
留下 health.py    能不能服务：没有它，"跑完了"与"服务正常"是两件事
```

被删掉的那些能力由谁承担：

```text
snapshot.py     可以不删（sync 依赖它）——真要删就是把扫盘逻辑并进 sync，
                代价是"扫盘"这件事再也无法被单独测试
metrics.py      由 day032/043 的 observability 承担**部分**（成本与追踪），
                但 sources_* / chunks_written / sync_age_minutes 这三类
                "同步侧指标"没有任何一天能承担——代价是看板上少一层
deploy.py       由 day022 的 Dockerfile/compose 承担（手写版），
                代价是那 11 条判据与"渲染一致性"全部消失
pipeline.py     由调用方自己按顺序调五个函数承担，
                代价是"每一次运行都有报告"这条性质消失（四条出口会分家）
worker.py       由平台（CronJob / 调度器）承担——这正是"判定与载体分开"的收益
```

取舍的核心判据不是"删掉多少行代码"，而是**删掉之后哪条性质会静默失效**：
`types` 的契约、`sync` 的"没变就不跑"、`schedule` 的可复现、
`health` 的"能不能服务"——这四条一旦没有，故障会以"检索质量下降"
这种没有报错的形式出现。
