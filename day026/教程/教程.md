## 第一章：为什么 Prompt 需要评估 —— 提示词即代码

### 1.1 一个常被忽视的事实

回顾 day010，我们花了很大力气打磨 `PLAN_PROMPT`：JSON 数组输出、限定 3~6 个子任务、动词开头。当时靠的是"跑 10~20 个真实目标，人工收集失败案例，对症下药"。这个流程能工作，但有两个隐患：

- **改版没有护栏**。提示词是文本，谁都能改。某天有人把"严格输出 JSON"顺手改成"尽量输出 JSON"，所有下游解析逻辑不会报错——直到某天线上失败率悄悄上升，才有人回头查这段文本。代码改动有测试守门，**提示词改动什么都没有**。
- **质量靠感觉**。"这版提示词好像好一点"——好多少？哪个维度变好了？有没有引入新问题？没有量化手段，提示词优化就停留在玄学层面。

在 Agent 系统里，系统提示词就是**行为定义的源代码**：它决定了模型扮演什么角色、遵循什么约束、输出什么格式。源代码有编译器、有测试、有 code review；提示词配得上同等待遇。这就是今天的出发点：**把提示词当作代码来评估和管理**。

### 1.2 评估一份提示词，到底在评估什么

提示词不像函数那样有确定的输入输出，不能直接断言 `prompt(x) == y`。它的"质量"体现在：模型读到它之后，**行为落在期望范围内的概率有多高**。这个概率无法直接测量，但我们可以从文本本身和语义理解两个层面逼近：

```text
提示词质量
    │
    ├── 机器可判定的层面（确定性检查）
    │     长度是否合理、角色/任务/约束段落是否齐全、
    │     占位符是否闭合、指令是否字面矛盾、有无模糊措辞
    │
    └── 需要语义理解的层面（LLM 评委）
          读完是否知道要做什么、指令间是否暗含冲突、
          是否存在多种解读空间
```

第一层用**规则检查**解决：确定、快速、离线、可精确测试。第二层用 **LLM-as-a-judge** 解决：让另一个 LLM 以评审专家的身份按 rubric 打分。两者各有盲区，加权合成才是完整的评估——这正是今天 `PromptEvaluator` 的核心架构。

### 1.3 为什么不能只用其中一种

只用规则检查，会漏掉"每条规则都满足但读起来就是别扭"的提示词——比如角色定义写得词不达意，规则看不出。只用 LLM 评委，问题更隐蔽：

- **评委不稳定**：同一个提示词，换个模型、换个温度，分数可能漂移；
- **评委有系统性偏差**（第四章详述）：偏爱长文本、偏爱自己风格的措辞；
- **评委无法检查机械事实**：`{tools` 少了个 `}`，模型评委可能根本没注意到，而这是一个会让 `str.format()` 直接抛 `KeyError` 的硬伤。

所以分工原则是：**机械事实交给规则，语义判断交给评委，谁都不越界**。

## 第二章：Prompt 质量的三个维度

评估要有维度，否则"打分"就是拍脑袋。我们把提示词质量分解为三个正交维度，每个维度 1~5 分。

### 2.1 清晰度（Clarity）：读完是否知道要做什么

清晰度回答的问题是：**一个不持有上下文的读者（模型），能否仅凭这段文字明确自己的角色、任务和输出格式？**

清晰的提示词有三个可判定的特征：

1. **角色显式**："你是 SmartResearch 智能研究助手"——模型知道"我是谁"，行为的语气、能力边界都有了锚点；
2. **任务显式**："接收用户任务后，通过思考-行动-观察循环逐步推进"——做什么，不含糊；
3. **格式显式**：给出输出模板或示例——产出长什么样，不靠猜。

规则侧对应三条检查：是否出现"你是/扮演/作为"、是否出现"输出/格式/任务"类关键词、长度是否在合理区间（过短信息不足，过长关键指令被稀释——回忆 day010 讨论的注意力稀释问题）。

### 2.2 一致性（Consistency）：指令之间是否自相矛盾

一致性回答：**指令内部是否自洽？**

最常见的两类不一致：

- **字面矛盾**："请严格按照规定格式输出……输出格式可以随意调整"。"严格"与"随意"同时指向同一件事，模型每一步都要赌你到底是哪个意思。我们的规则侧维护一张矛盾词对表（`CONTRADICTION_PAIRS`），两者同时出现即告警；
- **结构破损**：模板占位符 `{tools` 没闭合、出现空占位符 `{}`。这类问题模型评委很难发现，但程序数一下 `{` 和 `}` 的个数就能抓到——**一致性检查里，规则侧比评委侧更可靠**。

### 2.3 无歧义（Ambiguity-free）：是否存在多种解读空间

歧义是三个维度里最隐蔽的。它不违反任何字面规则，读起来也通顺，但**同一段话存在两种以上的合理解读**：

- "内容尽量写得详细一些"——"尽量"是多尽量？模型无法判定，只能靠运气；
- "回答要简洁"的同时给了五个必须覆盖的要点——简洁和全面之间的边界在哪？

规则侧用模糊措辞表（`VAGUE_WORDS`：尽量、大概、差不多、也许、等等）抓字面歧义；更微妙的语义歧义交给评委侧——评委被要求站在"第一次读这段话的模型"的立场上，报告所有可能的多种解读。

### 2.4 三个维度的关系

```text
清晰度 ── 决定模型"知不知道要做什么"
一致性 ── 决定模型的行为"稳不稳定"（同一提示词多次调用，行为方差）
无歧义 ── 决定模型的行为"可不可预测"（边界情况下走哪条路）
```

三者合成 `overall` 作为总分。注意 overall 只是**排序工具**（比较两个版本谁更好），不是**验收标准**——真正的验收要看各维度分数与 `issues` 清单。一个 overall 4.5 但 issues 里躺着"占位符未闭合"的提示词，依然是坏的。

> 思考题：为什么不把"长度"单列成一个维度？提示：长度本身不是质量，它只是清晰度的代理指标。

## 第三章：规则侧检查 —— 机器可判定的七条规则

完整代码见 [evaluation/prompt_eval.py](../源码/smart-research-agent/smart_research_agent/evaluation/prompt_eval.py) 的 `check_rules` 方法。规则侧的设计哲学与 day010 的"四道防线"一脉相承：**每条规则对应一类真实失败，每条规则产出一个可执行的建议**。

### 3.1 评分机制：扣分制

```python
return RuleReport(
    clarity=max(1.0, 5.0 - clarity_deduct),
    consistency=max(1.0, 5.0 - consistency_deduct),
    ambiguity_free=max(1.0, 5.0 - ambiguity_deduct),
    issues=issues,
    suggestions=suggestions,
)
```

每个维度满分 5 分起步，命中一条该维度的问题扣 1 分，最低 1 分。扣分制而非加分制的原因：规则检查只能证明"没发现已知问题"，不能证明"好"——满分 5 分的含义是"没有已知的机械缺陷"，语义层面的优劣留给评委侧修正。

### 3.2 逐条过一遍七条规则

| # | 规则 | 维度 | 判定方式 | 对应的真实失败 |
|---|------|------|----------|----------------|
| 1 | 长度在 [50, 4000] 字符 | 清晰度 | `len()` 区间判断 | 过短模型无所适从；过长注意力稀释 |
| 2 | 有角色定义 | 清晰度 | 正则 `你是\|扮演\|作为` | 模型语气、能力边界漂移 |
| 3 | 有任务/格式说明 | 清晰度 | 正则 `输出\|格式\|任务` | 输出结构每次都不一样 |
| 4 | 有约束性指令 | 无歧义 | 正则 `必须\|严格\|要求\|禁止\|不要` | 模型自由发挥，行为边界缺失 |
| 5 | 占位符闭合且非空 | 一致性 | `{}` 计数 + `\{\s*\}` | `str.format()` 抛 KeyError，运行时才爆 |
| 6 | 无矛盾指令词对 | 一致性 | `CONTRADICTION_PAIRS` 双向命中 | 模型在矛盾指令间反复横跳 |
| 7 | 无模糊措辞 | 无歧义 | `VAGUE_WORDS` 命中 | 同一句指令多种解读，行为不可预测 |

注意每条规则除了扣分外，还同时写入 `issues`（问题是什么）和 `suggestions`（怎么改）。**评估的终点不是分数，而是修改建议**——一份只给分不给建议的报告，和没有评估差不多。

### 3.3 矛盾指令检测的取舍

```python
CONTRADICTION_PAIRS = [
    ("必须", "可以不"),
    ("严格", "随意"),
    ("只能", "也可以"),
    ("不要输出", "额外输出"),
]
```

用词对匹配而不用 NLP 理解，是刻意的工程取舍：词对表**可枚举、可测试、可解释**，误报时人类看一眼就知道为什么命中。代价是召回有限——表外的矛盾（如"回答要简短"与"每个要点展开三段"）抓不到，那正是评委侧的职责。规则和评委不是竞争关系，是**分层过滤**：规则用零成本抓掉硬伤，评委把算力花在规则够不着的地方。

### 3.4 评委输出的防御式解析

评委侧要求 LLM 输出 JSON，但"要求"只是软约束（day010 的老教训）。`parse_judge_output` 复用了 `parse_plan` 的全部手法：

```python
start = cleaned.find("{")
end = cleaned.rfind("}")
...
try:
    scores = {key: _clamp(float(data[key])) for key in _JUDGE_KEYS}
except (KeyError, TypeError, ValueError):
    return {**{key: JUDGE_FALLBACK_SCORE for key in _JUDGE_KEYS},
            "issues": ["LLM 评审输出无法解析，该维度使用中性分兜底"], ...}
```

三个设计点：

1. **find/rfind 定位边界**：评委在 JSON 前后加客套话也能正确截取；
2. **超界分数钳制**：评委打出 9 分？钳到 5。打出 0 分？钳到 1。评分契约是 1~5，超界视为格式违规而非"特别好/特别差"；
3. **失败不抛异常，中性分兜底**：评估器是工具链的一环，评委输出坏了不该让整个评估流程崩溃——用中性分 3.0 占位，并在 `issues` 里明确记录"该维度使用中性分兜底"，让看报告的人知道这次评估的成色。**降级要可见，不能静默。**

## 第四章：LLM-as-a-judge —— 让模型当评委

### 4.1 为什么需要模型评委

规则侧能判定"有没有角色段落"，但判定不了"这个角色定义写得好不好"；能抓到字面矛盾，但抓不到语义冲突。这些判断需要**阅读理解能力**——恰恰是把提示词交给 LLM 评估的理由：评委模型和未来的执行模型是同一类读者，评委觉得歧义的地方，执行模型大概率也会犹豫。

### 4.2 Rubric 锚定：把"打分"变成"对照检查"

裸让模型"给这个提示词打分"，它会自由发挥，分数没有意义。我们的 `JUDGE_PROMPT` 给每个维度锚定了两个端点：

```text
- clarity（清晰度）：角色、任务、输出格式是否一目了然。
  1 分=读完不知要做什么，5 分=无需任何猜测
- consistency（一致性）：指令之间是否自相矛盾、结构是否统一。
  1 分=多处矛盾，5 分=完全一致
- ambiguity_free（无歧义性）：是否存在模糊措辞或多种解读空间。
  1 分=歧义遍地，5 分=每种情况都有明确指引
```

这个手法叫 **rubric 锚定（rubric anchoring）**：不告诉评委"什么是好"，而是告诉它"1 分长什么样、5 分长什么样"。锚点把连续的"感觉"离散成可对照的档位，大幅压缩评委的自由发挥空间——这与 day010 在 PLAN_PROMPT 里给 few-shot 示例是同一个思想：**凡是需要程序消费的 LLM 输出，都要在提示词里显式锁定结构**。

### 4.3 JSON 约束：评委的输出也是程序消费的数据

```text
严格输出 JSON，不要输出其他内容，格式：
{"clarity": 4, "consistency": 5, "ambiguity_free": 3, "issues": [...], "suggestions": [...]}
```

评委打分的输出要走 `json.loads` 进 `PromptScore`，所以格式必须锁死。注意 `JUDGE_PROMPT` 本身是带 `{prompt}` 占位符的模板，示例 JSON 里的花括号要写成 `{{"clarity": ...}}` 转义——**模板里的模板，是占位符检查（第三章规则 5）最容易救你一命的场景**。

### 4.4 评委的三大系统性偏差

LLM-as-a-judge 不是公正无私的裁判。文献和工业实践中反复观察到三类偏差，设计评估系统时必须心里有数：

**（1）位置偏置（Position Bias）。** 让评委同时对比 A、B 两个答案时，它系统性地偏爱先出现的那个（部分模型相反，偏爱后出现的）。我们的 `compare()` 是**分别独立评估再比分数**，而不是把两个提示词塞进一次调用让评委二选一——从根本上绕开了位置偏置。

**（2）自我偏好（Self-preference）。** 模型倾向给"像自己输出风格"的文本打高分。用 GPT 系列评委评 GPT 生成的提示词，分数会系统性偏高。缓解手段：评委模型与生成模型不同源；在 rubric 里强调"以第一次阅读的模型视角评估"；分数只用于版本间相对比较，不追求绝对准确。

**（3）冗长偏好（Verbosity Bias）。** 更长的回答/提示词容易拿高分，因为长文本"看起来更专业"。缓解手段：rubric 锚点里明确"清晰不等于详尽"，规则侧的长度上限检查（>4000 字符扣分）从另一侧对冲——**一个维度同时被规则和评委看着，偏差更难蒙混过关**。

更进一步的通用缓解还有**多评委（jury）**：让多个模型（或同一模型多个采样）独立打分取中位数，单个评委的噪声被平均掉。今天为了离线可测只接了单评委接口，但 `PromptEvaluator(llm=...)` 的依赖注入设计意味着换评委、加评委都不用动评估逻辑本身。

### 4.5 加权合成：为什么评委权重更高

```python
RULE_WEIGHT = 0.4
JUDGE_WEIGHT = 0.6

score = RULE_WEIGHT * rule_score + JUDGE_WEIGHT * judge_score
```

评委权重更高的理由：三个维度里，清晰度、无歧义本质是**语义属性**，规则侧只是它们的粗糙代理（关键词命中不等于真的清晰）；一致性里规则侧更强（占位符、字面矛盾是机械事实），但也只占一部分。0.4/0.6 的含义是：**规则分保底（评委再离谱，机械缺陷的扣分也丢不掉），语义分主导（规则全过但读着别扭，评委能把分拉下来）**。

为什么不干脆 0/1 全信评委或 1/0 全信规则？1.1 节已回答：评委不稳定、有偏差、抓不住机械事实；规则没有语义理解能力。加权是"两个都不完美的信息源"的标准融合方式。

## 第五章：评估驱动的 Prompt 迭代闭环

### 5.1 提示词模板版本化：评估的前提

要评估，先得让提示词**可被指认**。散落在 `react_agent.py` 里的字符串字面量没法指认——它改没改、改成了什么样，全藏在代码 diff 里。今天把系统提示词抽成独立模块 [agent/prompts.py](../源码/smart-research-agent/smart_research_agent/agent/prompts.py)：

```python
# v1（day006）：ReAct 循环的初始系统提示词。
REACT_SYSTEM_PROMPT_V1 = """你是一个使用 ReAct 范式解决问题的智能助手。..."""

# v2（day026）：按"角色 / 任务 / 输出格式 / 约束"四段式重写。
# 变更原因：1. 显式分隔角色定义与任务说明；2. 新增独立约束清单；3. 补充兜底指令。
REACT_SYSTEM_PROMPT_V2 = """你是 SmartResearch 智能研究助手，使用 ReAct 范式解决用户的研究与计算任务。..."""

REACT_SYSTEM_PROMPT = REACT_SYSTEM_PROMPT_V2
REACT_SYSTEM_PROMPT_VERSION = "v2"
```

三个约定：**历史版本永不删除**（要能回头对比）、**每次修改递增版本号并注释变更原因**（评估报告才有上下文）、**当前生效版本通过别名指向**（`react_agent.py` 只 import `REACT_SYSTEM_PROMPT`，切换版本不动调用方）。这就是把提示词当代码管理的具体形态——版本号就是提示词的 commit hash。

### 5.2 v1 → v2 改了什么，为什么

| 改动 | 对应维度 | 原理 |
|------|----------|------|
| 拆出独立"## 任务"段落 | 清晰度 | 角色与任务分离，降低"我是谁/要做什么"的误读 |
| 新增"## 约束"四条清单 | 无歧义 | 把 v1 隐含在示例里的规则（Action 必须是列表中的工具名等）变成显式指令 |
| "禁止凭记忆编造事实" | 无歧义 | 补上 v1 缺失的边界情况指引：信息不足时该怎么办 |
| "Action 与 Final Answer 二选一" | 一致性 | 消除"同时输出 Action 和 Final Answer"的解读空间 |

对照评估结果（见 `scripts/demo_prompt_eval.py` 输出）：v2 overall 4.8 vs v1 overall 4.0——分数差异来自评委侧指出的"角色与任务混杂""缺少独立约束清单"，而这正是改版时针对的问题。**评估分数与改版意图相互印证，评估才是可信的。**

### 5.3 版本对比：compare() 的相对评估

```python
def compare(self, prompt_a: str, prompt_b: str) -> ComparisonResult:
    score_a = self.evaluate(prompt_a)
    score_b = self.evaluate(prompt_b)
    diff = score_a.overall - score_b.overall
    winner = "tie" if abs(diff) <= TIE_THRESHOLD else ("a" if diff > 0 else "b")
    ...
```

两个细节：

- **分别评估再比较**（而非让评委二选一），规避 4.4 节的位置偏置；
- **平局阈值 `TIE_THRESHOLD = 0.05`**：评委有噪声，overall 差 0.02 不构成"更好"的证据。相对评估要回答的问题是"新版本是否**显著**更好"，显著性来自阈值，不来自小数点。

绝对分数会随评委模型漂移，但**相对结论稳健**——这是版本对比比单次打分更有工程价值的原因。

### 5.4 闭环：评估结果固化成回归用例

评估的终极形态不是跑一次看分，而是**进 CI 当门禁**。`PromptEvalHarness` 把昨天 harness 基座的 `expected` 字段定义为"overall 最低分数线"：

```python
class PromptEvalHarness(EvaluationHarness):
    def run_case(self, case: EvalCase) -> CaseResult:
        threshold = float(case.expected) if case.expected else self.default_threshold
        score = self.evaluator.evaluate(case.input)
        return CaseResult(case=case, output=f"overall={score.overall:.2f}",
                          passed=score.overall >= threshold, detail="; ".join(score.issues))
```

于是一个提示词回归套件长这样：

```python
cases = [
    EvalCase(name="react_system_v2", input=REACT_SYSTEM_PROMPT_V2, expected="4.0"),
    EvalCase(name="plan_prompt", input=PLAN_PROMPT, expected="4.0"),
]
results = harness.run(cases)
assert harness.summary(results)["pass_rate"] == 1.0
```

任何人改版提示词，只要 overall 跌破 4.0，测试立即变红，`detail` 里还带着扣分原因。这就是完整的闭环：

```text
发现问题（bad case / 规则告警 / 评委低分）
    │
    ▼
修改提示词，版本号 +1，注释变更原因
    │
    ▼
compare() 对比新旧版本，确认显著改善
    │
    ▼
把新版本与分数线固化为 EvalCase，进回归套件
    │
    ▼
下一次改版 ────────────────────────┘（循环）
```

回忆 day010 的"提示词是迭代出来的，不是写出来的"——当时靠人工收集失败案例，今天这个流程有了自动化骨架：**人负责发现 bad case 和写改版，机器负责验证改版有效且没有回退。**

> 思考题：闭环里分数线定 4.0 是拍脑袋的值。如果评委模型换了（比如从 GPT 换成开源模型），这批 EvalCase 会发生什么？该怎么处理？

## 第七章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 规则 + 评委双路评估 | 机械事实靠规则，语义判断靠评委，互不越界 | `PromptEvaluator.evaluate` |
| 三维度评分 | 清晰度=知道做什么，一致性=行为稳定，无歧义=边界可预测 | `PromptScore` |
| 扣分制规则检查 | 规则只能证明"无已知缺陷"，不能证明"好" | `check_rules` |
| rubric 锚定 + JSON 约束 | 压缩评委自由发挥空间，输出程序可消费 | `JUDGE_PROMPT` |
| 解析失败中性分兜底 | 降级要可见，不能静默崩溃 | `parse_judge_output` |
| 评委权重 0.6 > 规则 0.4 | 语义属性为主，规则分保底 | `RULE_WEIGHT/JUDGE_WEIGHT` |
| compare 分别评估 + 平局阈值 | 规避位置偏置；噪声不构成"更好"的证据 | `PromptEvaluator.compare` |
| 模板版本化 + 历史版本不删 | 评估的前提是可指认；改版原因入注释 | `agent/prompts.py` |
| 分数线固化为 EvalCase | 评估的终点是 CI 门禁，不是一次性报告 | `PromptEvalHarness` |

今天埋下的伏笔，后续会回收：

- **多评委（jury）**：单评委的噪声与偏差，用多模型投票进一步压缩；
- **输出质量评估（day027）**：今天评估的是"写给模型的指令"，明天评估"模型吐出的答案"——同一套 Harness 基座，换一个评估器；
- **评估进 CI/CD（day032）**：`PromptEvalHarness` 就是为此设计的，届时接入流水线自动门禁。
