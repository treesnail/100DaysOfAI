# day070（休息日/缓冲日）：M6 缓冲复习 —— 从字节到可核对答案的一条链路

> 阶段标签：休息日 / 缓冲复习（M6-D1 ~ M6-D8）  
> 学习时长：约 2 小时（可拆成两段）  
> 前置依赖：day061 ~ day069  
> 学习目标（引自 [../../docs/curriculum.md](../../docs/curriculum.md)）：复习 RAG 检索、重排序与生成链路；整理 RAG 实验数据。

## 今日目标

今天不写新代码。但**不写新代码不等于没有新东西**：day061 到 day069 交出了 8 个包、11 个新模块（`lexical` / `fusion` / `hybrid` / `rerank` / `generation` 等），每两天一个小闭环。到了今天，真正的问题不再是"某个模块实现了没"，而是：

1. **这条链路能不能被一口气讲完？** 从"一个字节"到"一句可核对的答案"，中间有九个决定，每一个决定都会在最终答案里留下痕迹——能不能不看代码把九个决定的**顺序与依赖**说出来？
2. **上一句话里的"痕迹"到底是什么？** 每一层都留了**数字**（`dropped_by_top_k`、`dropped_hits`、`coverage`、`invalid`）。今天要把这些数字串成一条**对账链**：答案不对时，是哪一层先出的问题？
3. **实验数据有没有被整理成可比较的形状？** 换一版提示词、加一层重排、调一次预算——每次实验都改变了结果，但"变了多少、好在哪里"必须有一张表。这张表就是明天 day071 的输入。

> 为什么复习日不安排新内容？认知科学里有个反直觉的结论：**提取练习（Retrieval Practice）的效果远好于重复阅读**。今天的主线是"主动回忆"——先合上教程自己复述，再打开原文对照。答不上来的地方，就是你真正的知识缺口，比任何测验都准（这条纪律从 day024 的 R1 复用至此）。

## 第一章：M6 全景 —— 一条链路上的九个决定

M6 的八课（day061 ~ day069，中间 day063 是前半段收口）其实只干了一件事的八个侧面：

```text
        "把一份资料变成一段能回答问题的文字，并且这段文字可被核对"

  ┌───────────── 数据侧（离线，一次） ─────────────┐   ┌──── 推理侧（在线，每次） ────┐
  │                                                │   │                              │
 bytes →  Document  →  Chunk  →  VectorRecord → 索引清单 → 命中 → 融合 → 重排 → 上下文 → 答案
  │         │            │           │            │        │      │      │        │        │
day061   day061       day062     day064       day065   day066  day067  day068  day066  day069
  │                                                                │       │        │
  └── 内容指纹即身份 ──┘└ 区间不重叠也不丢 ┘└ 记录表为主 ┘└ 版本可重算 ┘└ 名次可解释 ┘└ 引用可对账
```

读这张图有三个正确姿势：

1. **左半边是"建库"，右半边是"查库"**。"建库"错了（切得太碎、编码器换了、清单漂了），右半边无论怎么调都只是在一个错误的起点上优化；
2. **每一层都只吃上一层的产物**：`Chunk` 不知道向量是什么，`RetrievalHit` 不知道索引是怎么建的（它只认识 `IndexState`）。这条"只认识上一层的形状"的纪律，正是今天能在两小时内复盘的物理原因；
3. **每一层都留了自己的数字**：这一条是 M6 真正的收获——**一个说不出"我丢了几条"的系统，在"答案不好"这个问题前面是哑的**。

九个决定与它们的产物（一句话版本）：

| # | 决定 | 产物 | 一句话本质 |
|---|------|------|-----------|
| 1 | 各种格式怎么收敛成一种形状 | `Document` / `Block` | 解析 = 归一化，而归一化规则就是接口 |
| 2 | 长文档怎么切成"最小语境单元" | `Chunk` / `ChunkSet` | 切块只差"在哪里切"，收尾四条纪律只有一份实现 |
| 3 | 向量存在哪里、谁说了算 | `VectorRecord` / `SearchHit` | 记录表为主、索引为从；过滤必须早于排序 |
| 4 | 什么时候需要重新编码 | `IndexManifest` / `IndexPlan` | 身份进键，版本号由内容算出（没有时间） |
| 5 | 给一句话取回哪几条 | `RetrievalResult` | 三道减法各自成数，空结果只给**一个**原因 |
| 6 | 字面与语义两路怎么合 | `FusedHit` / `fusion` | 分数量纲不可比 → 要么只看名次，要么先归一再加权 |
| 7 | 合出来的名单次序对不对 | `RerankResult` | 交叉编码器更准但更贵 → 只对前 N 条打分 |
| 8 | 模型给的那段话能不能被核对 | `GroundingReport` | 判定不靠字符串比较，靠编号 |

## 第二章：八个主题的复盘（本质 → 为什么 → 误区）

每个主题按同一套心智模型复盘。**试着先看小标题自己复述，再展开对照**——先复述后阅读，是提取练习的正确顺序。

### 2.1 文档解析与加载（day061）

- **本质**：把 PDF / DOCX / HTML / Markdown / 纯文本五种格式，收敛成同一个 `Document`（`blocks` 的有序序列 + 元数据）。`doc_id = sha256(规范化后的全文)[:16]`——**内容指纹就是身份**，同一份内容换个文件名还是同一份，改一个字节就是两份。
- **为什么**：下游（分块、编码、引用）只愿意认识一种形状。而"归一化规则是接口的一部分"这句话的重量在于：**改它等于让历史索引全部失效**——所有已存的 `doc_id`、`doc_id` 派生的 `chunk_id`、以及按它们建好的索引会一起对不上。
- **误区**：
  - "解析成功 = 内容抽全了"。DOCX 只读 `word/document.xml` 一个部件，页眉页脚读不到——这件事写在 `PARTS_NOT_READ` 里，也写进了元数据；
  - "编码猜不准就随便挑一个"。`decode_bytes` 的五步顺序是固定的（`BOMS` 在前、`latin-1` 必须排最后），因为 latin-1 **永不失败**，所以它的结果必须被标记为不可信（`DecodedText.confident`）。
- 代码：[documents/](../../day061/源码/smart-research-agent/smart_research_agent/documents/) 的 `types.py`（`normalize_text` / `content_id`）、`text_loader.py`（`decode_bytes` / `encoding_chain`）、`base.py`（`detect_media_type` / `LoaderRegistry`）；手册 [docs/document_loading.md](../../day061/源码/smart-research-agent/docs/document_loading.md)。

### 2.2 分块策略（day062）

- **本质**：一个 `Chunker` 只回答**一个**问题——"在哪里切"。四种策略（`fixed` / `recursive` / `structural` / `semantic`）的差异全在这一个答案上；而修剪、重叠、合并、校验这**收尾四条纪律**写在 `Chunker.finalize` 里只实现一次。
- **为什么**：切块粒度直接决定检索能捞回什么。`Span` 只带区间不带文本，是为了让"块不是原文子串"这种 bug **无处可写**；`ChunkSet.coverage` 则是把"98% 覆盖率正常吗"从感觉问题变成算术问题（差额有上界）。
- **误区**：
  - "重叠越大越安全"。`fixed.py` 的 `window_plan` 把这件事算清楚了：`step = max_tokens - overlap_tokens`、`amplification = overlap_tokens / step`——重叠直接放大编码成本与检索噪声；
  - "语义分块的阈值可以照抄 0.7"。余弦相似度的绝对值依赖提供方与语言，所以这里用**分位数**（`similarity_percentile`）而不是绝对值；
  - "预算单位是 token"。默认度量器是 `chars`（`resolve_measurer`），因为 `chunk_id` 是去重键，**可复现性优先于"与计费单位一致"**；要 token 得显式切 `tiktoken`，它不可用时**拒绝**而不是静默降级。
- 代码：[chunking/](../../day062/源码/smart-research-agent/smart_research_agent/chunking/) 的 `base.py`（`Chunker.finalize` / `Span`）、`structural.py`（`ATOMIC_KINDS`）、`tokens.py`（`resolve_measurer`）、`types.py`（`chunk_id_for` / `Chunk.retrieval_text`）；手册 [docs/chunking_strategies.md](../../day062/源码/smart-research-agent/docs/chunking_strategies.md)。

### 2.3 向量数据库 ChromaDB / FAISS（day064）

- **本质**：`VectorBackend` 这个抽象下面有**两个库**——"向量索引"答"谁最近"，"记录表"答"那是什么"。三者（flat / faiss / chroma）口径统一到一处：`score` 越大越近；与库里原生 `distance` 的换算只有 `similarity_from_distance` 一处实现。
- **为什么**：后端可以换，但报告里的数字不能有两种含义。`sort_hits` 的排序键是"分数降序 + **id 升序**"——并列怎么断必须写死，否则同一份数据两次运行可能给出不同的 top-1。
- **误区**：
  - "先取 top-k 再按元数据过滤"。过滤**必须早于排序**，否则你是在一个被无关记录挤占的名额表里做 Top-K；
  - "重放一次没改动库就等于没花钱"。`WriteReport` 把 `added` / `updated` / `unchanged` / `skipped` 分成四个数，而 `unchanged` 才是"这次白算了多少"的账；
  - "浮点向量可以用 `==` 比"。`VECTOR_EQUAL_TOLERANCE = 1e-5`：逐位比较会让 `unchanged` 永不可达。
- 代码：[vectorstore/](../../day064/源码/smart-research-agent/smart_research_agent/vectorstore/) 的 `base.py`（`VectorBackend` / `UNKNOWN_DIMENSION`）、`flat.py`、`faiss_backend.py`（`RECORDS_SUFFIX`）、`chroma_backend.py`（`VECTOR_EQUAL_TOLERANCE`）、`filters.py`（`SUPPORTED_OPERATORS`）；可选后端按 PEP 562 的 `LAZY_EXPORTS` 延迟导入；手册 [docs/vector_store.md](../../day064/源码/smart-research-agent/docs/vector_store.md)。

### 2.4 Embedding 索引构建（day065）

- **本质**：给索引记账——`IndexPlan` 把一批记录分成四组 id（新增 / 更新 / 删除 / **未变**），`IndexManifest` 是账本，`index_version_id` 是账本的名字，而这个名字是**内容算出来的**（身份 + 度量 + 后端 + 内容摘要），**不含时间**。
- **为什么**：版本号不含时间，才让它成为"可重算"的量——同一份内容任何时候算都得到同一个号；而时间戳一旦进版本号，"同样的内容"每次构建都会变成新版本，增量与回滚都失去意义。缓存键必须含 `vector_key`（身份进键），否则**换了编码器却复用了旧向量**。
- **误区**：
  - "增量永远更省"。变更比例超过 `indexing_full_rebuild_threshold` 就从增量切全量，否则四组 id 的差集计算本身就比全量更贵；
  - "回滚按时间倒序"。回滚沿**血缘**走，不是沿时间轴走；
  - "检索器只认识库就够了"。检索器不认识语料，但必须认识 `IndexState`（版本 + 漂移），否则"我查的是哪一版"这个问题在报告里没有答案。
- 代码：[indexing/](../../day065/源码/smart-research-agent/smart_research_agent/indexing/) 的 `types.py`（`index_version_id` / `entries_digest`）、`planner.py`（`plan_index` / `plan_reason`）、`cache.py`、`encoder.py`（`describe_embedding`）、`versioning.py`（`IndexVersionStore`）、`manifest.py`（`compare_with_store`）；手册 [docs/embedding_index.md](../../day065/源码/smart-research-agent/docs/embedding_index.md)。

### 2.5 检索器实现（day066）

- **本质**：九步流水线——编码 → 过取（默认 3 倍、封顶 `MAX_FETCH_K = 1000`）→ 过滤 → 阈值 → 重排（day068 插入）→ 多样性 → top_k → 诊断 → 计时。它回答三个问题：取回哪几条、**为什么是这几条**、**为什么只有这几条**。
- **为什么**：三个 `dropped_*` 数字（阈值切掉 / 每文档上限挤掉 / top_k 截断丢掉）**不许合成一个 `dropped`**——每个数字对应一个可调参数，合成之后"该调哪个"这个问题永远无法回答。空结果只给**一个**原因（`EMPTY_REASONS` 的优先级），因为四种成因对应四个不同的处置动作，写四条猜测等于什么都没说。
- **误区**：
  - "检索为空就让模型自己答"。`RagPipeline.answer` 的第 2 步在**渲染提示词之前**判空，一次 LLM 都不调（`llm_called=False`）——检索为空 + 调用 LLM 的产物**看起来最像成功**，那是 RAG 最贵的一种失败；
  - "漂移了就应该拒绝服务"。默认只观测（进 `notes`），`strict_index=True` 才拒绝；
  - "名次可以带空洞"。`rank` 重编成从 0 连续，否则"第 3 条"这个说法得不到保证。
- 代码：[retrieval/](../../day066/源码/smart-research-agent/smart_research_agent/retrieval/) 的 `retriever.py`、`types.py`（`RetrievalResult.explain` / `aggregate_results`）、`context.py`（`pack_context` / `PackedContext.fill_ratio`）、`pipeline.py`（空检索护栏）；手册 [docs/retrieval.md](../../day066/源码/smart-research-agent/docs/retrieval.md)。

### 2.6 混合检索（day067）

- **本质**：向量路擅长同义改写、关键词路（`lexical.py` 的零依赖 BM25）擅长编号与专有名词；两路的分数量纲不可比（余弦 ∈ `[-1,1]`、BM25 ∈ `[0,∞)`），于是融合要么只看名次（`rrf`，缺省、免标定），要么先各自归一化再加权（`weighted`）。
- **为什么**：**去重 = 合并证据**。同一条被两路独立召回，是融合能给出的**新信息**（`RetrievalHit.channels` 保留双路），因此 `candidates` 在混合模式下是两路候选的**并集**，而不是两路之和。
- **误区**：
  - "阈值对两路都生效"。`min_score` 只作用于向量路，而这件事**无条件进 `notes`**——一个"看起来能调、实际不生效"的旋钮比没有旋钮更贵；
  - "过滤在两路里随便一路做就行"。`where` 只合成**一次**、同一个子句对象交给两路，只落一路会把已排除的记录抬回来且不报错；
  - "分配置权重给 RRF 也行"。`strategy="rrf"` 时给 `weights` 直接报错——RRF 的定义里没有权重。
- 代码：[retrieval/lexical.py](../../day067/源码/smart-research-agent/smart_research_agent/retrieval/lexical.py)、[fusion.py](../../day067/源码/smart-research-agent/smart_research_agent/retrieval/fusion.py)、[hybrid.py](../../day067/源码/smart-research-agent/smart_research_agent/retrieval/hybrid.py)；手册 [docs/hybrid_retrieval.md](../../day067/源码/smart-research-agent/docs/hybrid_retrieval.md)。

### 2.7 重排序 Reranker（day068）

- **本质**：召回与排序是两件事。双塔（查询与文档分开编码）的代价是两两不相见——它擅长"别漏"，不擅长"排准"；交叉编码器把两者拼起来过一遍模型，更准但每对一次前向推理。于是姿势是**两段式**：召回取几十到几百条，重排只对**前 N 条**（`retrieval_rerank_top_n`）重打分。
- **为什么**：**窗口纪律必须被说出来**。只报"重排生效了"却不报"有一批条连分都没拿到"，等于把一次有边界的改进说成了一次全面的改进——所以窗口这件事**无条件进 `notes`**。两种模式对应两种量纲处理：`replace` 只信重排分，`blend` 各自归一再加权。
- **误区**：
  - "重排排在多样性裁剪之后"。顺序反了，被多样性丢掉的那些候选**再也回不到重排器眼前**；
  - "重排阈值切掉的条数并进 `dropped_by_top_k`"。它是**第四道减法**，理由与前三道一样；
  - "提升报告可以'重排之后重新检索一遍'再对比"。那样差里就混进了两次检索的随机性，而 `measure_lift` 的价值恰恰是**把变量减到一个**（用同一批命中）。
- 代码：[retrieval/rerank.py](../../day068/源码/smart-research-agent/smart_research_agent/retrieval/rerank.py)（`CrossEncoderReranker` / `rerank_hits` / `LiftProbe` / `measure_lift`）；手册 [docs/reranking.md](../../day068/源码/smart-research-agent/docs/reranking.md)。

### 2.8 RAG 生成器与 Prompt（day069）

- **本质**：模型给的那段话，能不能被片段核对。`GroundingReport` 用**编号**对账：`cited`（答案里出现的）、`valid`（真的落在那次提示词里的）、`invalid`（**幻觉引用**）、`unused`（给了没用，是覆盖率的分母），而 `grounded = valid 非空 且 invalid 为空`。
- **为什么**：**判定不靠字符串比较**。用"答案里有没有'没有相关内容'"来判断拒答，会在兜底文案改一个字之后静默失效——而它失效的样子恰好是"看起来一切正常"。同理，`llm_called` 单独成字段，而不是"看 answer 等不等于 fallback"。
- **误区**：
  - "`coverage` 的分母是检索召回的条数"。分母是**给出去的片段数**：被预算丢掉的尾部模型根本看不到，算进分母会让覆盖率凭空变低；
  - "`[0]` 也算一次幻觉引用"。编号从 1 起，`[0]` 不是编号，它进 `notes` 而不进 `invalid`——把 0 算成幻觉，会让那句指控多出一批不成立的样本；
  - "六种回退可以合成一个布尔"。六种情形对应六种动作（改检索 / 改提示词 / 换模型 / 查提供方 / 调预算 / 收紧闸门），合成之后"这一批里有几次不可交付、分别为什么"无法统计。
- 代码：[retrieval/generation.py](../../day069/源码/smart-research-agent/smart_research_agent/retrieval/generation.py)（`GroundingReport` / `CitationCheck` / `Generation` / `RAGGenerator` / `FALLBACK_REASONS`）；手册 [docs/rag_generation.md](../../day069/源码/smart-research-agent/docs/rag_generation.md)。

## 第三章：一次全链路走读 —— 一条查询穿过八层，每层丢掉了多少

这一章是今天的核心。**把每一层的"输入形状 / 输出形状 / 这一层留下的数字"三件事各写一行**，你就拥有了排查任何一个 RAG bad case 的地图。

先给一份可以直接复述的走读稿（括号里是真实的字段名）：

```text
①  文件字节        →  Document(doc_id=内容指纹, blocks=[...])
     留下的数字      blocks 数、每种 kind 的条数、未读部件清单（PARTS_NOT_READ）
②  Document         →  ChunkSet(chunks=[Chunk(chunk_id, retrieval_text, heading_path, ...)])
     留下的数字      coverage（没有丢内容）、oversized_count、overlap 带来的放大量
③  Chunk            →  VectorRecord(record_id=chunk_id, vector, text, metadata)
     留下的数字      WriteReport.added/updated/unchanged/skipped（哪个数大就说明哪件事发生了）
④  一批 VectorRecord →  IndexManifest(version_id, entries) + IndexPlan(四组 id)
     留下的数字      entries_digest（版本号可重算）、plan_reason（为什么切了全量/增量）
⑤  一句话           →  RetrievalResult(hits, fetch_k, candidates, empty_reason, ...)
     留下的数字      dropped_below_threshold / dropped_by_diversity / dropped_by_top_k
                     channel_candidates（每路召回几条）、fusion.contributions（每路贡献几条）
                     dropped_by_rerank（第四道减法）、index_state.drift
⑥  前 N 条          →  重排后的名单（RerankResult: scored / moved / window）
     留下的数字      window（真正打分的条数）、moved（名次动了几条）
⑦  最终名单         →  PackedContext(text, citations, used_hits, dropped_hits, truncated_hits)
     留下的数字      fill_ratio（预算用了几成）、dropped_hits（尾部丢了几条）
⑧  提示词           →  Generation(answer, prompt_version, llm_called, fallback_reason, check)
     留下的数字      check.given / valid / invalid / unused / coverage、fallback_reason
```

### 3.1 一条具体的查询：从 8 条候选到 3 条命中

用手算得出来的样例走一遍，比"跑一遍看看"可靠得多。样本来自 [tests/retrieval_samples.py](../../day069/源码/smart-research-agent/tests/retrieval_samples.py)（8 条记录 + 查表编码器 `TableEmbedding` + `FlatVectorStore`），其中 `axis` 查询在这 8 条上的分数是：

```text
1.0 / 1.0 / 0.8 / 0.6 / 0.5 / 0 / 0 / 0
```

于是可以逐层对账（`top_k = 3`、`fetch_multiplier = 3` 的项目默认值）：

| 步骤 | 数字 | 谁来解释它 |
|------|------|-----------|
| 过取深度 | `fetch_k = 3 × 3 = 9`，封顶 1000 后仍是 9 | `retrieval.fetch_multiplier` / `MAX_FETCH_K` |
| 库侧候选 | 8（库里一共 8 条，`candidates=8`） | `RetrievalResult.candidates` |
| 阈值切掉 | `min_score=0.5` 时切掉 3 条（分数为 0 的三条） | `dropped_below_threshold` |
| 每文档上限挤掉 | `max_per_doc=1` 时挤掉 2 条 | `dropped_by_diversity` |
| top_k 截断 | 剩下 5 条里取前 3，丢掉 2 条 | `dropped_by_top_k` |
| 最终命中 | 3 条 | `RetrievalResult.count` |

这张表的价值在于：**"为什么只有 3 条"这个问题的答案，是四个各自可调的数字之和，而不是一句"检索就是这样"**。

### 3.2 关键一跃：从"检索到了"到"进了提示词"

`RetrievalResult` 交出名单之后，还有一个**容易被忽略的漏斗**：打包（`pack_context`）。预算 `max_context_chars` 放不下时从尾部丢（`dropped_hits`），单条超 `per_hit_chars` 时截断（`truncated_hits`）。

```text
检索到的 3 条  ──打包──▶  真正进了提示词的 n 条（citations）
      n < 3 时：检索是对的，但模型没看到那一条
```

这件事在 day069 的报告里体现为 `check.given`（给出去的片段数）与 `coverage`（有效引用 / 给出去）。它也是明天 day071 的一个核心指标——**"进了提示词的召回率"才是答案质量的下界**：金标准文档即使被检索回来了，只要被预算丢在尾部，模型就没有机会用它。

> 思考题：`coverage` 的分母是"给出去的片段数"而不是"检索到的命中数"。如果反过来（用检索到的条数做分母），哪一类 case 的读数会变差？答案：被预算丢尾的那一类——明明是无辜的生成，却会被记成"引用覆盖率低"。

### 3.3 用一句话定位"哪一层先坏了"

把上表倒过来读，就是一张诊断表（顺序 = 链路的顺序，**先出现的先怀疑**）：

```text
检索为空（empty_reason ≠ "hits"）         → 先看第 ③④ 层：库里有数据吗？过滤条件错了吗？清单漂了吗？
召回了但不在前几名                        → 第 ⑥ 层：排序问题（重排模型 / 融合策略 / 相似度口径）
金标准没进最终名单                        → 第 ⑤ 层：四个 dropped_* 哪个在吃名额？
进了名单但没进提示词                      → 第 ⑦ 层：打包预算
提示词里有、答案没用                      → 第 ⑧ 层：提示词或模型（`unused` 就是它的账）
答案引用了不存在的编号                    → 第 ⑧ 层：幻觉引用（`invalid`）
答案一个编号都没引用                      → 第 ⑧ 层：`require_citation` 是否该开、提示词是否够硬
```

**这张表的每一行都对应一个可执行的下一步动作**。这正是明天 day071 要做的事：把这套人工判断写成代码（归因），并把每一类坏例的条数变成可以进基线的数字。

| `retrieval_text` 字段名 | `EMBEDDING_TEXT_FIELD`，取不到时回落 `text` | 向量库写入侧 |

## 第五章：常见误区清单（M6 八课）

每条都给出**证据位置**——这不是"可能出错"，而是"代码里写明了它为什么错"。

1. **"改一个分块参数不用重建索引。"** 错。`chunk_id` 含策略与序号，切块变了就等于换了一批主键。证据：`chunking/types.py::chunk_id_for` 的三个入参。
2. **"`doc_id` 就是文件名。"** 错。它是内容指纹，同一内容换文件名不变。证据：`documents/types.py` 的 `doc_id = sha256(规范化后的全文)[:16]`。
3. **"解析成功就等于内容抽全了。"** 错。DOCX 只读一个部件，页眉页脚读不到——这件事被显式记成 `PARTS_NOT_READ`。
4. **"重叠是免费的效果提升。"** 错。`window_plan` 给出 `amplification`，重叠直接放大编码量。
5. **"语义分块的阈值可以照抄某个数。"** 错。绝对值依赖提供方与语言，故用分位数。
6. **"先 Top-K 再按元数据过滤。"** 错。过滤必须早于排序。证据：`vectorstore/flat.py::_find_ids` 与 `_ranked_ids` 的调用顺序。
7. **"重放一次没改动库就不用花钱。"** 错。`unchanged` 就是那次白算的账。
8. **"缓存键取文本就够了。"** 错。`vector_key` 含 provider / model / dimension——换了编码器必须重算。
9. **"版本号里加时间戳更保险。"** 错。那会让"同样的内容"每次都成为新版本。
10. **"漂移应该直接报错。"** 默认只观测；`strict_index` 才拒绝。证据：`IndexState` 的取舍说明。
11. **"空结果随便说一个原因。"** 错。`EMPTY_REASONS` 是封闭清单且带优先级，只给一个。
12. **"四个 `dropped_*` 合成一个 `dropped` 更简洁。"** 错。合成的代价是"该调哪个参数"永远无法回答。
13. **"检索为空也可以让模型先答一版。"** 错。护栏在渲染之前：`llm_called=False`、`citations=()`。
14. **"混合检索的两个分数可以直接相加。"** 错。量纲不可比（余弦 ∈ `[-1,1]`、BM25 ∈ `[0,∞)`）。
15. **"`min_score` 对两路都生效。"** 错。它只作用于向量路，且这件事无条件进 `notes`。
16. **"重排排在多样性裁剪之后。"** 错。那样被丢掉的候选再也没机会上桌。
17. **"提升报告可以两次检索各取一份名单。"** 错。变量必须减到一个：同一批命中，重排前 vs 重排后。
18. **"`grounded` 可以靠字符串判定。"** 错。判定只看编号，文案一改就静默失效。
19. **"`coverage` 用检索条数当分母。"** 错。分母是给出去的片段数。
20. **"六种回退可以合成一个布尔。"** 错。六种情形六种动作。

## 第七章：RAG 实验数据整理（为 day071 准备）

复习日的最后一件实事：**把已经跑过的实验整理成一张可比较的表**。M6 的每一课都留下了一个或多个"改变了结果"的旋钮，而它们的取值必须先能被记录，才谈得上被评估。

### 7.1 一张实验记录表应该有哪些字段

```text
run_id            这次实验的编号（同一次实验的所有变体共享它）
variant           变体名（例如 baseline / hybrid-rrf / rerank-blend / prompt-v2）
调整的旋钮          这次与 baseline 相比，**只改了哪一项**（只改一项是关键）
索引版本           IndexState.version_id（换了索引，后面所有数字都不可比）
编码器身份         EmbeddingIdentity（provider + model + dimension）
检索参数           top_k / fetch_multiplier / min_score / max_per_doc
混合参数           hybrid_enabled / strategy / alpha / rrf_k
重排参数           rerank_enabled / model / top_n / mode / weight
打包预算           max_context_chars / per_hit_chars
提示词版本         prompt_version（以及 require_citation 是否打开）
检索指标           recall@k / precision@k / RR / nDCG@k（金标准来自评测集）
打包后指标         packed_recall@k（**进了提示词的**那一段召回）
生成指标           grounded_rate / coverage 均值 / hallucination_rate
回退分布           六种 fallback_reason 各自的条数
延迟与成本         p95 延迟、平均 token
结论               一句话，必须能被上面的数字支持
```

### 7.2 三条整理纪律

1. **一次只改一个旋钮**。`measure_lift` 之所以用同一批命中，就是为了把变量减到一个；实验表同理——同时改融合策略与重排模型，收益归因不了。
2. **换了索引或编码器，历史数字立刻作废**。`IndexState.version_id` 与 `EmbeddingIdentity` 是这张表的"前任字段"——它们一变，前后两行不可比，必须新开一个基线。
3. **结论必须能追到数字**。"重排让结果更好了"不是结论；"nDCG@5 从 0.72 → 0.86，召回不变"才是。

### 7.3 从"整理数据"到"自动评估"

今天的人工表有一个明显缺陷：**它靠人填**。人填的表有三个逃不掉的问题——不一致（同一字段两次填法不同）、不可复现（没记全参数）、不可回归（改一版代码没人重跑）。

明天 day071 要做的事，就是把这套人工流程变成代码：

```text
人工表的一行        →  day071 的结构          它解决的人工缺陷
────────────────────────────────────────────────────────────────────
run_id / variant    →  一次 suite 运行 + 变体名   不可复现
调整的旋钮           →  从 settings 读出的已解析参数  没记全
检索/打包/生成指标    →  一套指标 + 一个基线对象     不一致
结论                →  回归判定（带方向与死区）      不可回归
```

| 四道减法各自成数，合成一个就失去了可调性 | `retrieval/types.py::RetrievalResult` |

| 两路分数量纲不可比 → 只看名次或先归一再加权 | `retrieval/fusion.py` |
| 重排只对前 N 条打分，而窗口纪律必须进 `notes` | `retrieval/rerank.py::rerank_hits` |
| 判定不靠字符串比较：接地看编号、调用看 `llm_called` | `retrieval/generation.py::GroundingReport` |
