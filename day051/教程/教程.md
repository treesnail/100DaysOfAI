## 第一章：LoRA 的算术

### 1.1 一个式子，三个数

LoRA 的全部内容就是一条式子：

```text
W' = W + ΔW,        ΔW = (alpha / r) · B @ A
```

其中 `W ∈ R^{out×in}` 是**冻结**的基座权重，`A ∈ R^{r×in}` 与 `B ∈ R^{out×r}` 是**新增**的两个小矩阵。由这个形状直接得到三个可以手算的数：

| 量 | 公式 | 参考模型（V=557，r=8） |
|----|------|----------------------|
| 基座参数 | `out×in (+in)` | 310 249 + 557 = **310 806** |
| 新增参数 | `r(in + out)` | 8 × 1114 = **8912** |
| 秩上界 | `min(r, in, out)` | **8** |

参数量之比是 **8912 / 319718 = 2.7875%**（分母含适配器自己——这与 peft 的 `print_trainable_parameters()` 口径一致，报告里的数字因此可以直接和训练日志对照）。

从 `out×in` 到 `r(in+out)`，是**平方级到线性级**的下降。这就是"参数高效"这四个字的全部内容。

### 1.2 秩上界是可以被断言钉死的

`ΔW = (α/r)·B·A` 的秩不可能超过 `min(out, r, in)`——因为乘积的秩受中间维度限制。这条性质在浮点下表现为"消元后非零主元的个数不超过 r"，于是它可以被一条断言固定：

```python
@pytest.mark.parametrize("r", [1, 2, 3])
def test_rank_never_exceeds_r(self, r):
    a_matrix, b_matrix = init_lora_weights(6, 6, r, seed=3, init_mode="random")
    assert matrix_rank(lora_delta(a_matrix, b_matrix, 2.0)) <= r
```

实测：`r=1` 时秩为 1（`ΔW` 的每一行都成比例）、`r=2` 时为 2、`r=6` 但矩阵只有 `5×6` 时为 **5**（被维度限制，而不是被 `r` 限制）。

最后一条是 `plan_lora` 里一条告警的来源：**`r` 超过被适配层的最小维度时，继续加大 `r` 不会增加容量，只是线性地增加显存**。

### 1.3 day049 的四个数字在运行时复算

day049 预先算出过四个"单矩阵"的 LoRA 比例。它们是方阵 `d×d` 上的 `2r/d`：

```text
d = 4096,  r = 8   -> 2r/d = 0.3906%
d = 4096,  r = 16  -> 2r/d = 0.7812%
d = 2048,  r = 8   -> 2r/d = 0.7812%
d = 11008, r = 16  -> 2r/d = 0.2907%
```

本课把它们做成函数输出（`reference_matrix_ratios()`），于是它们成了**可执行的断言**：只要有人改了公式，这四个数字立刻变红。

但这里有一个必须分清的地方。精确的比例是

```text
r(in + out) / (in·out)
```

方阵时它退化为 `2r/d`；**非方阵时 `2r/d` 只是近似，而且是偏小的近似**。以 `4096 × 11008` 的 MLP 投影、`r=16` 为例：

```text
2r/d 近似      = 2×16/11008      = 0.2907%
精确值         = 16×15104/45088768 = 0.5360%
```

相差 46%。`ModuleShape.square_shortcut_ratio` 因此在非方阵上返回 `None` 而不是给一个近似值——**近似值只在它成立的条件下才叫近似**。

### 1.4 单矩阵比例 ≠ 模型级比例

这是最容易误读的一处。真实模型有 32 层、每层 7 个投影，因此模型级比例还取决于 `target_modules`。实测（`llama-2-7b`，`r=8`，占比分母含适配器）：

| 预设 | 目标模块 | 新增参数 | 模型级占比 |
|------|---------|---------|-----------|
| `attention` | q, v | 4 194 304 | 0.0622% |
| `attention_all` | q, k, v, o | 8 388 608 | 0.1243% |
| `mlp` | gate, up, down | 11 599 872 | 0.1718% |
| `all_linear` | 七类全上 | 19 988 480 | 0.2958% |

同一份数据、同一个 `r`，**参数量相差 4.75 倍**。这四行就是"为什么 `target_modules` 必须显式写出来"的最好说明——而**没命中预期模块不会报错**，只会表现为"效果不如预期"。

`qwen3-0.6b` 上的同一张表（`r=8`）：`attention` 1 146 880（0.1920%）/ `attention_all` 2 293 760（0.3834%）/ `mlp` 2 752 512（0.4597%）/ `all_linear` 5 046 272（0.8395%）。换成 `r=16` 的 `all_linear` 就到了 **10 092 544（1.6650%）**——此时 `plan_lora` 会告警"超过 1%，LoRA 的显存优势被大幅削弱"。

### 1.5 `r` 不能乱加

`r = min(in, out)` 时，LoRA 与全参微调的可训练参数量同阶，"参数高效"完全失效。给出这条边界的具体数字：

```text
llama-2-7b 的全秩上限（七类投影都取 r = min(in,out)）：
    10 234 101 760  ——  是模型本身（6 738 415 616）的 1.52 倍
qwen3-0.6b 的全秩上限：
      645 922 816  ——  是模型本身（596 049 920）的 1.08 倍
```

也就是说，**把秩加到头，LoRA 会比全参微调还要贵**。参数量对 `r` 是严格线性的（每个秩 +1，每层多 `in+out` 个参数），而容量对 `r` 的收益是递减的——容量与开销从来不成比例。这也是 `rank_comparison()` 那张表存在的理由：**先看参数量表，再决定要不要加秩**。

### 1.6 `alpha` 单独看没有意义

LoRA 里真正生效的只有比例 `alpha/r`（`use_rslora=True` 时为 `alpha/sqrt(r)`）：

```python
@property
def scaling(self) -> float:
    denominator = math.sqrt(self.r) if self.use_rslora else float(self.r)
    return self.lora_alpha / denominator
```

`alpha = 2r` 是社区惯例，它的作用很具体：**让 `r` 翻倍时缩放保持不变**。改了 `alpha` 而没有意识到自己在改缩放，等价于**偷偷改学习率**——而日志里的 `learning_rate` 完全看不出来。所以 `describe()` 会把公式一起打印出来：

```text
LoRA r=8 alpha=16 dropout=0.05 targets=attention['q_proj', 'v_proj'] bias=none
    scaling[alpha/r = 16/8 = 2.000000]
```

`use_rslora` 的存在理由也是量级问题：秩越大，`B @ A` 中每个元素的量级随 `sqrt(r)` 增长，用 `alpha/r` 会让大秩适配器的有效步长被压小，于是"加大秩"看起来毫无收益。把分母换成 `sqrt(r)` 正是为了让不同秩之间的学习率可比。

### 1.7 适配器是可以被"带走"的

一个 `1024 × 2048` 的投影层，原本有 2 097 152 个参数；`r=8` 的适配器只有 **24 576** 个参数，bf16 落盘 **0.0469 MiB**，压缩 **85.3 倍**。而它替换的基座是 13.5 GB 级别的文件。

"一个基座 + N 个小适配器"这个部署形态就建立在这个数量级差上。day052 会把它做成落盘与验证流程。

## 第二章：初始化 —— "挂上去不改变行为"

### 2.1 `B` 全零，`A` 取尺度匹配的高斯

```python
a_std = std_scale / math.sqrt(in_features)
b_std = std_scale / math.sqrt(r) if init_mode == "random" else 0.0
```

`B` 取全零带来一条很实用的性质：**`ΔW = (α/r)·B·A = 0`，也就是第 0 步的模型输出与基座逐位一致**。接适配器不会让效果立刻变差，于是"先挂上、再评估、再训练"这条工作流是安全的。

`A` 的标准差按 `1/sqrt(fan_in)` 缩放，是让"输入维度变化时增量量级保持稳定"。这里只保证**量级**：peft 用的是 `kaiming_uniform(a=√5)`，等价于 `U(-1/√fan_in, 1/√fan_in)`，方差是 `1/(3·fan_in)`，与本实现相差 3 倍。数量级相同即可，因为真正决定增量大小的是后续的 `scaling` 与训练本身。

`init_lora_weights="random"`（让 `B` 也随机）**破坏 `ΔW = 0`**，只用于对照实验。测试里有一条断言专门守这个差别：

```python
def test_gaussian_mode_zeros_b(self):
    a_matrix, b_matrix = init_lora_weights(5, 4, 2, seed=11)
    assert all(value == 0.0 for row in b_matrix for value in row)
    assert any(value != 0.0 for row in a_matrix for value in row)
```

### 2.2 最重要的不变式：557 个上下文逐位一致

把适配器挂上之后，第一条要验的不是"能不能训"，而是"**有没有改变任何东西**"：

```python
fresh = LoRAReferenceModel(base, default_reference_lora_config(r=8, lora_alpha=16), seed=42)
mismatch = sum(1 for ctx in range(vocab) if fresh.logits(ctx) != base.logits(ctx))
```

实测：`557` 个上下文 token 里 **0 个**不同，`delta_is_zero()` 为 `True`。

用 `==` 逐元素比较而不是 `approx`，是刻意的。这条断言守的不是数值精度，而是**行/列约定没有混用**——下一章会看到，混用之后 loss 曲线照样下降、照样收敛，只有把两份 logits 摆在一起才发现对不上。

### 2.3 dropout 在 one-hot 输入下的真实语义

LoRA 的 dropout 作用在**适配器分支的输入**上（基座路径用的是原始 `x`，与 peft 的 `LoraLayer` 一致）：

```python
base_out = [sum(row[i] * x[i] for i in range(in_features)) for row in self._base]
effective = [value * mask[i] for i, value in enumerate(x)]
```

参考模型的输入是 one-hot（等价于 embedding 查表），于是逐元素 dropout 退化成一件很不一样的事：

```text
输入只有一个非零元素 → mask 的唯一效果是：以概率 p 把这个非零元素置零，
否则放大 1/(1-p)。也就是"以概率 p 整条适配器分支不被激活"。
```

这不是 bug，但它说明 **LoRA dropout 作用在查表式输入上时做的是"样本级的分支丢弃"**，与作用在稠密激活上不是一回事。测试里把这两种结果钉死了：

```python
def test_one_hot_dropout_gates_whole_branch(self):
    ...
    seen = set()
    for _ in range(40):
        out = layer.forward_context(0, training=True)
        if out == pytest.approx(kept):        # 放大 1/(1-p) = 2 倍
            seen.add("kept")
        elif out == pytest.approx(base_row):  # 整条分支被丢弃
            seen.add("dropped")
        else:
            seen.add("other")
    assert seen == {"kept", "dropped"}         # 不允许出现第三种结果
```

因为这种语义会让 loss 曲线不可复现，参考模型要求 `lora_dropout = 0`（不满足直接抛 `PEFTConfigError`）；dropout 机制由 `LoRALinear` 的专门用例覆盖。

## 第三章：行约定与列约定 —— 本课踩过的一个坑

### 3.1 同一个矩阵，两种解读

day050 的 `ReferenceSFTModel.logits(ctx)` 定义为 `W[context] + b`，即"每个上下文 token 用**一行**权重"。从线性层的角度看，这等价于把 `Wᵀ` 当作这一层的权重：

```text
logits(ctx) = W[ctx] = (Wᵀ) @ e_ctx
```

把 LoRA 挂到 `Wᵀ` 上，增量是 `scaling · B @ A`，于是

```text
(Wᵀ + scaling·B@A) @ e_ctx = W[ctx] + scaling·B@A[:, ctx]
```

**基座取 `W` 的一行、增量取 `ΔW` 的一列**。这不是笔误，而是同一个矩阵被解读了两次——方阵上两种下标空间相同，这正是它容易被混起来的原因。

而 `LoRALinear` 作为"普通线性层"的标准实现，`forward(e_index) = W @ e_index = W[:, index]` 取的是**列**。两种约定给出的是**不同的模型**：

```text
dense（forward / forward_onehot）：out = W@e_index = W[:, index]      （W 的一列）
context（forward_context）      ：out = W[index] + ΔW[:, index]       （W 一行 + ΔW 一列）
```

### 3.2 这个缺陷为什么难发现

本课实现时先写的是 `forward_onehot`（列约定），于是参考模型实际训的是"**随机噪声基座的一列 + 按列算的增量**"，而合并路径算的是"基座一行 + 增量一列"。后果是：

```text
merge 后评估 loss 3.8858638865 | 适配器模型评估 loss 3.8855603004
合并后模型 logits 与适配器模型逐位一致：False        最大差异 0.0381
```

而在此之前，**训练完全正常**：loss 从 6.32 降到 5.36，评估 loss 3.8843 甚至优于全参基线的 5.3602。也就是说，"训练在跑、loss 在降、指标还不错"三件事同时成立，而模型是错的。

修好之后（改用行约定），同一组实验给出：

```text
合并后与适配器模型的 logits 逐位一致（全部 557 个上下文）：True
合并后评估 loss 3.8842521027 | 适配器模型 3.8842521027 | 差值 0.00e+00
```

### 3.3 顺带得到的一个"部署陷阱"

两条约定的合并矩阵也不一样：

```text
merged_weight()      = W + ΔW            （密集约定，对应 forward）
merged_by_context()  = W + ΔWᵀ           （查表约定，对应 forward_context）
```

`W + ΔW` 与 `W + ΔWᵀ` 在非对称基座上完全不同——**部署时落错一个不会报错，只会让输出全错**。本课把这条关系也写成了断言：

```python
delta_transposed = [[dense[j][i] - square[j][i] for j in range(3)] for i in range(3)]
assert merged[i][j] == pytest.approx(square[i][j] + delta_transposed[i][j])
```

### 3.4 这条经验的通用形式

**任何"接上一个模块不改变行为"的设计，都必须配一条"接上之后行为逐位不变"的断言。** 检查 loss 是不够的：loss 是标量，它会掩盖几乎所有的结构性错误。这与 day050"用同一把尺子评估"是同一种纪律——**度量必须能分辨出你想分辨的那个差别**。

## 第四章：训练 —— 复用 day050 的循环，一行不改

### 4.1 接口一致，所以循环不变

`LoRAReferenceModel` 与 day050 的 `ReferenceSFTModel` **接口完全一致**：

| 方法 | 语义 |
|------|------|
| `accumulate(batch)` | 前向 + 反向，返回 `(loss 之和, 监督 token 数)` |
| `apply_update(lr)` | 按 `1/N` 缩放累加梯度并做一次 SGD |
| `zero_grad()` | 丢弃未应用的梯度 |
| `evaluate(batches)` | 只前向、不污染梯度缓冲 |
| `state_dict()` | 可序列化状态（**合并后的**权重） |
| `vocab_size` / `updates` | 与基座一致的两条属性 |

于是 `SFTTrainer(model=LoRAReferenceModel(...), tokenizer, args)` **一行不用改**就能跑起来，测试里有一条用例专门守这一点：

```python
trainer = SFTTrainer(model, tokenizer, args, template=PLAIN, system_prompt=None)
report = trainer.fit(train, eval_set, save_at_end=False)
assert report.optimizer_steps > 0
assert model.updates == report.optimizer_steps
```

这不是巧合，而是刻意的边界设计：**LoRA 改变的只有"哪些参数有梯度"**。渲染、编码、label mask、padding、梯度累积、学习率调度、评估、检查点落盘全都与它无关。把这条边界划清楚，"换微调方法"才是换一层皮，而不是重写训练脚本。

另外三处与 day050 完全同构的纪律：

1. **分母**：`apply_update` 的缩放因子是"自上次更新以来累积的**位置数**"，不是批数、也不是参数量——"loss 的分母只数监督 token"在梯度层面的同一件事；
2. **评估不污染梯度**：`evaluate` 前后对梯度缓冲做快照与恢复；
3. **可复现**：数据打乱与权重初始化都用局部 `random.Random(seed)`，同 seed 两次训练的 loss 序列逐位相同。

### 4.2 梯度是解析求出来的

LoRA 的层里没有自动微分框架，梯度是手写出来的。设 `a = A·x`、`g = ∂L/∂output`：

```text
∂L/∂B[i][j] = scaling · g[i] · a[j]
∂L/∂a[j]    = scaling · Σ_i g[i] · B[i][j]
∂L/∂A[j][k] = ∂L/∂a[j] · x[k]
```

这三行是"LoRA 为什么能训"的全部内容：**基座没有梯度，增量有梯度**。

为什么要用解析式而不是数值差分：LoRA 的增量本身很小（`B` 初始为 0），数值差分的误差量级与增量接近，两者量级相当时"梯度算得对不对"就无法判别。所以本课用**中心差分**做交叉验证（`h = 1e-6`，容差 `1e-4`）：

```python
def test_gradients_match_numerical_differences(self):
    ...
    for j in range(len(a_matrix)):
        for k in range(len(a_matrix[j])):
            plus, minus = perturb(a_matrix, j, k, +h), perturb(a_matrix, j, k, -h)
            numeric = (loss(plus, b_matrix) - loss(minus, b_matrix)) / (2 * h)
            assert grad_a[j][k] == pytest.approx(numeric, abs=1e-4)
```

扰动后的层用公开入口 `load_adapter_state` 重建（不碰私有字段），因此这条用例同时验证了序列化路径。

### 4.3 学习率必须重新标定（本课最重要的实测）

`LR_SOFT_RANGE_PEFT = (1e-4, 5e-4)` 是 **7B LoRA** 的经验区间。参考模型（557×557 bigram + 纯 SGD）的量级完全不同。实测（30 条样本、2 个 epoch = 30 步，与 day050 的全参基线同预算；评估 loss 越低越好）：

| 方法 | lr=2 | lr=8 | lr=20 | lr=32 | lr=100 | lr≥128 |
|------|------|------|-------|-------|--------|--------|
| 全参微调 | — | 5.3602 | 4.6473 | 4.2206 | **3.4344** | 发散（5.00 → 13.59） |
| LoRA r=8 | 6.2977 | 4.7815 | **3.8843** | 发散（3.4e15） | — | — |

两条结论：

1. **LoRA 的学习率区间比全参窄得多**：全参在 `[8, 100]` 都稳定（约 12 倍宽度），LoRA 在 `[8, 20]` 之后立刻爆掉（约 2.5 倍宽度）。把 day050 标定出的 `lr=8` 照抄给 LoRA，会得到"能跑但学不动"（4.7815 vs 3.8843）。
2. **不要相信"LoRA 效果更好"的说法**：把两边都调到最优，全参（3.4344）优于 LoRA r=8（3.8843）。这符合预期——**LoRA 用秩 ≤ 8 的增量去逼近 310 249 维的全秩更新，容量差距是结构性的**。LoRA 的收益是显存与落盘体积（5.96× / 22.61×），不是效果。

单 epoch（15 步）的扫法也给出同样形状：`lr=2 → 6.3156`、`lr=8 → 6.0438`、`lr=20 → 4.7799`。

这条结论的普适形式是：**任何"换了一种参数化方式"的改动，都必须重新标定学习率**。有效步长由梯度量级与参数量共同决定，而 LoRA 恰好同时改了两者。

### 4.4 秩与效果不是单调关系

同样的 30 步预算下扫秩（`lr=20`）：

| r | 可训练参数 | 占比 | 评估 loss | 耗时 |
|---|-----------|------|----------|------|
| 1 | 1 114 | 0.357% | 5.6164 | 6.0s |
| 2 | 2 228 | 0.712% | 5.1027 | 6.7s |
| 4 | 4 456 | 1.413% | 4.4437 | 8.2s |
| 8 | 8 912 | 2.787% | **3.8843** | 11.0s |
| 16 | 17 824 | 5.424% | 4.1170 | 16.8s |
| 32 | 35 648 | 10.289% | 3.7702 | 28.1s |
| 64 | 71 296 | 18.659% | 3.9113 | 53.3s |

`r=1 → 8` 是单调改善的，但 `r=16` 反而比 `r=8` 差，`r=32` 又最好，`r=64` 再次变差。**这条曲线本身就是结论**：在 30 条样本、30 步这个规模上，秩与效果的关系是**非单调**的——数据量与步数都不足以让"秩的单调收益"显现出来。day048 的"500 条以下先补数据"规则在这里第二次命中。

耗时那一列倒是严格单调的（6.0s → 53.3s，大致随 `r` 线性），这正好对应"参数量对 `r` 是线性的"那条算术。

### 4.5 ΔW 到底有多大（一个诚实的数据）

训练结束后，增量矩阵的画像：

```text
ΔW 形状 557×557 | 秩 8（上界 8）| Frobenius 322.5638 | 最大元素 14.407649
基座权重 Frobenius 6.4327  →  增量 / 基座 = 50.14 ×
```

**增量比基座大 50 倍**，这不是笔误。原因是本课的"基座"是一个随机初始化的 bigram 模型（`U(-0.02, 0.02)`，几乎没有结构），它的 6.43 几乎全是噪声；而在 `lr=20`、30 步的预算下，适配器学到的是一份真正的 bigram 统计。

这件事要说清楚，因为它划定了本课结论的适用范围：

> **本课验证的是"LoRA 的机制与算术"，不是"LoRA 在预训练模型上的效果"。** 真实场景里基座是训练好的模型，`ΔW` 的量级通常远小于基座，`alpha` 与 `r` 的作用也因此更接近教科书描述。

## 第五章：QLoRA —— 4-bit 只用于存基座

### 5.1 先纠正一句话

QLoRA 常被描述成"4-bit 训练"。这句话不准确：

```text
QLoRA 训练的是 fp16/bf16 的适配器 A / B；4-bit 只用于存储冻结的基座。
```

所以"QLoRA 掉点"从来不是"用 4-bit 训练"造成的，而是**基座权重的量化误差**造成的。误差有多大、能不能接受，是一个可以被度量的问题——本课把度量做出来，而不是留在"据说几乎无损"这个说法上。

### 5.2 NF4 码本可以按定义生成

NF4（4-bit NormalFloat）的定义很直白：**标准正态分布的 16 个等概率分位数，归一化到 `[-1, 1]`**。

```python
normal = NormalDist()
raw = [normal.inv_cdf((index + 0.5) / 16) for index in range(16)]
peak = max(abs(value) for value in raw)
levels = tuple(value / peak for value in raw)
```

实测生成的 16 个码点：

```text
code  0 (0000) -> -1.000000
code  1 (0001) -> -0.707569
code  2 (0010) -> -0.542209
code  3 (0011) -> -0.416819
code  4 (0100) -> -0.310905
code  5 (0101) -> -0.215946
code  6 (0110) -> -0.127341
code  7 (0111) -> -0.042095
code  8 (1000) -> +0.042095
code  9 (1001) -> +0.127341
code 10 (1010) -> +0.215946
code 11 (1011) -> +0.310905
code 12 (1100) -> +0.416819
code 13 (1101) -> +0.542209
code 14 (1110) -> +0.707569
code 15 (1111) -> +1.000000
```

三个值得记住的结论：

1. `levels[0] == -1.0`、`levels[-1] == 1.0`，严格递增——这是"归一化到 `[-1,1]`"的直接体现，也是码本生成正确的自检；
2. **16 个码点里没有 0**：偶数个码点时，最接近 0 的两个码点是 `±0.042095`。NF4 用"牺牲 0 附近的稠密性"换来"中间概率区间的更细分辨率"；
3. 码点在两端更稀疏：`-1.0` 与 `-0.7076` 之间的距离是 `±0.0421` 之间距离的 6 倍——这正是"按概率密度铺码点"的形状。

为什么用正态分位数：**预训练权重近似零均值正态分布**，把码点放在概率密度高的地方，量化误差自然更小。

对照码本 `fp4_levels()` 是 E2M1（1 位符号 + 2 位指数 + 1 位尾数）：8 个幅值 `{0, 0.5, 1, 1.5, 2, 3, 4, 6}` 配正负号共 **16 个编码，但只有 15 个不同取值**（`0` 有 `+0` 与 `-0` 两个编码）。对照基线 `int4_levels()` 是 `[-1, 1]` 上的 16 个等间距点。

### 5.3 分块量化与 absmax

每一块独立做一遍：

```text
absmax = max|v|                    块的量程
v_norm = v / absmax                归一化到 [-1, 1]
code   = argmin |v_norm - level|    最近的码点
v_hat  = level[code] * absmax       反量化
```

最近码点用 `bisect` 在已排序的码本上做，而不是线性扫 16 个码点。在 `557 × 557 = 310 249` 个权重上，这一点差别就是"秒级"与"十几秒级"的区别——**教学代码也应当避免无谓的规模失配**。

块大小取 **64** 是论文的选择：块越小精度越高、常数开销越大。实测每块 64 个权重共享一个 absmax 时，量化 RMSE 是 `0.001060`，而权重本身的 absmax 是 `0.020000`。

### 5.4 二级量化：4.5 bit → 4.126953 bit

一级量化的 `absmax` 常数本身也要占空间。论文的做法是**再量化一次**（8-bit 常数 + 每 256 个常数一个 fp32 缩放）：

```text
单重量化：32/64                              = 0.5       bit/参数
二级量化：8/64 + 32/(64×256)                 = 0.126953  bit/参数
```

于是每参数总位数与字节数：

| `block_size` | 二级量化 | 单重量化 | 常数开销（二级） |
|-------------|---------|---------|----------------|
| 64 | **0.515869 B/参数** | 0.562500 B/参数 | 0.126953 bit |
| 128 | 0.507935 B/参数 | 0.531250 B/参数 | 0.063477 bit |
| 256 | 0.503967 B/参数 | 0.515625 B/参数 | 0.031738 bit |
| 512 | 0.501984 B/参数 | 0.507812 B/参数 | 0.015869 bit |

**4-bit 并没有把权重压到 0.5 字节。** 而且方向容易记反：块越大、常数开销越小（每块摊到的权重更多）。代价是每块共享一个 absmax，量化精度下降。

一处必须说明的口径差异：bitsandbytes 的 4-bit 常数用的是 **FP8（E4M3）**，本课用 **8-bit 对称线性量化**模拟。位宽相同，因此**存储字节数完全一致**，只有量化误差的分布略有差异。之所以不实现 E4M3 的位级舍入：它的收益只是让"常数误差"这一项的第三位小数更漂亮，代价却是把注意力从"每参数到底占多少字节"上引开。

### 5.5 解析式 vs 实测：ceil 取整是真实存在的

在参考模型的 557×557 权重矩阵上实测：

```text
量化报告：nf4 block=64 double_quant=True | 310249 参数 160049 B
          （0.515873 B/参数，解析式 0.515869）| RMSE 0.001060
存储 160049 B（码点 155125 + 常数 4924）vs 16-bit 620498 B → 省 74.21%
解析式 0.515869 B/参数 vs 实测 0.515873（差 0.000004，来自 ceil 取整）
```

解析式给的是**下界**：实际还要 `ceil` 取整（最后一个不满的块、最后一个不满的常数分组）。两者都报出来，因为它们回答的是两个不同的问题——"理论上限"与"磁盘上占多少"。

### 5.6 为什么是 NF4（以及它什么时候不是）

三种码本的存储字节数完全相同（都是 4 bit + 同样的常数开销），差别只在误差。同一份 557×557 权重、`block_size=64`：

| 权重分布 | 最优 | NF4 RMSE | INT4 RMSE | FP4 RMSE |
|---------|------|----------|-----------|----------|
| 均匀初始化 `U(-0.02, 0.02)`（本课基座） | INT4 | 0.0010600900 | **0.0007526700** | 0.0012456900 |
| 高斯初始化 `N(0, 0.02²)`（NF4 的目标分布） | **NF4** | **0.0018276500** | 0.0019959000 | 0.0021101300 |
| 训练后的合并权重（零均值假设不成立） | FP4 | 0.0695561600 | 0.1007005500 | **0.0656704200** |

**三行的最优码本各不相同。** 第二行是"为什么是 NF4"的证据：在高斯分布上 NF4 的 RMSE 比均匀量化低 8.4%、比 FP4 低 13.4%。第一行反过来：本课的基座是**均匀**初始化的，此时等间距的 INT4 反而最优（比 NF4 低 29%）。

第三行的绝对误差大了一个数量级，因为那份矩阵里有比基座大 50 倍的 `ΔW`（见 4.5 节），分布完全不是零均值正态。

这条实测的通用形式值得记住：

> **码本要与权重的实际分布匹配。NF4 的优势不是普适的，它依赖"权重近似零均值正态"这个前提。**

### 5.7 QLoRA 训练：退化落在噪声里

用同一份数据、同一个 `lr=20`、同一个 `r=8`：

```text
bf16 基座 LoRA  ：loss 6.3225 -> 5.3615 | 评估 loss 3.8843
QLoRA（4-bit 基座）：loss 6.3225 -> 5.3649 | 评估 loss 3.8832
退化 -0.0010（-0.03%）
```

**不能把 `-0.0010` 解读成"QLoRA 更好"**：它只是一个 30 步、30 条样本、734 个评估 token 的实验里的噪声量级。能说的只有一句：**在这个规模上，4-bit 存储没有带来可测的退化**。

真正该记住的是机制：适配器自始至终是 bf16，`ΔW` 的精度不受基座量化影响；4-bit 误差只通过"前向时用略微失真的冻结权重"间接影响梯度。

## 第六章：显存 —— 拆成六项

### 6.1 六项表格

把训练显存拆开之后，三种方法的差别一眼可见（以 bf16 直接训练、AdamW 为例）：

| 项目 | 全参微调 | LoRA | QLoRA |
|------|---------|------|-------|
| 基座权重 | 2 B/参数 | 2 B/参数 | 0.515869 B/参数 |
| 基座梯度 | 2 B/参数 | **0** | **0** |
| 基座优化器状态 | 8 B/参数 | **0** | **0** |
| 适配器权重 | — | 2 B/可训练参数 | 2 B/可训练参数 |
| 适配器梯度 | — | 2 B/可训练参数 | 2 B/可训练参数 |
| 适配器优化器状态 | — | 8 B/可训练参数 | 8 B/可训练参数 |

实测（`attention_all` / `r=8`，**不含激活显存**）：

| 模型 | 全参 | LoRA | QLoRA |
|------|------|------|-------|
| `llama-2-7b` | 75.31 GiB（80.86 GB） | 12.65 GiB（13.58 GB） | 3.33 GiB（3.58 GB） |
| 相对全参 | 1.00× | 5.96× | **22.61×** |
| `qwen3-0.6b` | 6.66 GiB（7.15 GB） | 1.14 GiB（1.22 GB） | 0.31 GiB（0.34 GB） |
| 相对全参 | 1.00× | 5.86× | 21.35× |

### 6.2 8 字节/参数是最大的一项

AdamW 为**每个可训练参数**保存一阶矩与二阶矩两个 fp32 张量，`2 × 4 = 8` 字节。这常常是训练显存里最大的一块，也是"7B 全参微调需要 80 GB"这个说法的来源：

```text
6 738 415 616 × (2 + 2 + 8) = 80 860 987 392 B = 75.31 GiB
```

`adamw_bnb_8bit` 把这些状态压到 2 字节/参数（4 倍节省），代价是收敛略慢且对超参更敏感。**没有免费的显存。**

### 6.3 全参微调的两种口径

同一个模型的两个数字可以差 33%：

| 口径 | 权重 | 梯度 | 优化器 | 合计（7B） |
|------|------|------|--------|-----------|
| bf16 直接训练（`bf16=True`） | 2 B | 2 B | 8 B | 80.86 GB |
| fp32 主权重 + bf16 计算 | 4 B | 4 B | 8 B | 107.81 GB |

很多"7B 要多少显存"的争论其实是在争这个口径。`plan_memory(full_finetune_master_weights_fp32=...)` 把两者都做成了参数，并会在报告的 `notes` 里写清用的是哪一个。

### 6.4 GiB 与 GB 相差 7.4%

本课所有显存报告都同时给出两个单位。理由很实际：

```text
13.48 GiB = 14.47 GB  —— 差 7.4%
```

在"能不能放进 24 GB 卡"这种判断上，混用单位会给出错误答案。而"24 GB 的卡"其实有 24 GiB（25.77 GB）——**报错信息里"要 13.5 GiB，可用 12.0 GiB"比"要 14495514624 字节"有用得多**。

### 6.5 单卡适配表（以及它的边界）

```text
llama-2-7b / attention_all / r=8（只比较权重 + 梯度 + 优化器状态）

RTX 4090 (24 GiB)        full=×  lora=√  qlora=√
RTX 6000 Ada (48 GiB)    full=×  lora=√  qlora=√
A100 (40 GiB)            full=×  lora=√  qlora=√
A100/H100 (80 GiB)       full=√  lora=√  qlora=√
```

**这张表不含激活显存**，而激活大小取决于 `batch × sequence_length × hidden × layers`：在 `batch=2` / `seq=384` 上是几百 MB，在长上下文 + 大 batch 上可以是十几 GB。

把它塞进一个"看起来很精确"的汇总数字里，只会让这个数字变得不可信。所以本模块**拒绝估算激活显存**，并把这条写进每一行备注与响应字段里——**"放得下"不等于"跑得起来"**。知道一份预算没算什么，比多一个看起来完整的表格重要。

## 第七章：真实模型上的规格核算

### 7.1 每个数字都要能被公开配置核对

`DecoderSpec` 里的每个字段都取自公开的 `config.json`，而且**参数量会被逐项核对**：

```text
llama-2-7b : 总参数 6,738,415,616（6.738 B）
             单层 202,383,360 | 线性层 6,476,005,376（占 96.11%）
qwen3-0.6b : 总参数 596,049,920（0.596 B）
             单层 15,730,944 | 线性层 440,401,920（占 73.89%）
```

两个数字都与公开资料一致（`Llama-2-7B` 的 6.738 B、Qwen3 技术报告里 `0.6B` 的 596 049 920）。**规格写错一个字段，这两个总数立刻对不上**——这是本模块最重要的一道自检。

### 7.2 `head_dim` 不能算出来

`DecoderSpec.head_dim` 单独给出，而不是用 `hidden_size // num_heads` 算：

```text
qwen3-0.6b: hidden = 1024, num_heads = 16  →  1024/16 = 64
            但配置里的 head_dim = 128
```

用除法算会得到 64，于是 `q_proj`（1024 → 16×64=1024）与 `o_proj` 的形状全部算错，整份参数量核对随之失效。**能用公开配置核对的东西，不要用公式猜。**

顺带一句 GQA 的形状：`qwen3-0.6b` 的 `num_kv_heads = 8`，因此 `k_proj` / `v_proj` 的输出宽度是 `8 × 128 = 1024`，只有 `q_proj`（2048）的一半。这直接影响"适配 q/v 还是 k/v 更划算"——两者参数量不同。

### 7.3 `plan_lora` 的五类告警

每条告警都对应一个真实会发生的问题：

1. 目标预设**没有命中任何模块** → 直接抛错（配置看着正常，实际一个适配器都没插上）；
2. `r` 超过被适配层的最小维度 → 秩上界由维度而非 `r` 决定；
3. 可训练参数占比超过 1% → 优化器状态已接近全参规模，显存优势被削弱；
4. 只适配了 `q_proj` 或 `v_proj` 之一 → 不是 LoRA 论文消融实验里的那个配置；
5. 规格带线性偏置且 `bias != "none"` → "可训练参数 = 2·r·d"这条手算公式失效。

实测：`qwen3-0.6b` + `all_linear` + `r=16` 命中第 3 条（1.6650%），`llama-2-7b` 的同配置不命中（0.5898%）。**这条告警的适用性依赖模型规模**——与 day050"告警阈值必须与模型规模匹配"是同一条纪律。

## 第八章：生成能跑的脚本

### 8.1 相对 day050 的全参脚本只多两行

```python
peft_config = LoraConfig(task_type=TaskType.CAUSAL_LM, **LORA_CONFIG)
model = get_peft_model(model, peft_config)
```

而**数据准备一行都没变**：渲染 → 分别 tokenize → `labels` 的 prompt 段置 `-100` → padding 三件套 → 手写 collator。这正是 LoRA 的工程价值——它不要求你重写训练管线。day050 的测试守住的那些性质（"答案放不下的样本直接丢弃，绝不截断"）在这里原样成立。

### 8.2 QLoRA 版多三处，每处都有目的

```python
model = AutoModelForCausalLM.from_pretrained(
    args.model_name, quantization_config=build_quantization_config(), device_map="auto"
)
model = prepare_model_for_kbit_training(model, use_gradient_checkpointing=True)
model = get_peft_model(model, peft_config)
```

`prepare_model_for_kbit_training` 做三件事：把基座参数 `requires_grad=False`、把 LayerNorm 提升到 fp32（4-bit 反量化后的数值稳定性）、启用输入梯度（梯度检查点需要）。**漏掉它会得到一个"训练在跑但 loss 不降"的脚本**——因此生成的脚本里把这一步与它的理由一起写出来。

第四个细节在 dtype 映射上：`BitsAndBytesConfig` 实际接受 `torch.dtype` 对象，而 JSON 里只能存字符串，所以脚本里显式映射一次：

```python
COMPUTE_DTYPES = {
    "bfloat16": torch.bfloat16,
    "float16": torch.float16,
    "float32": torch.float32,
}
```

把 `torch.bfloat16` 直接序列化进模板会让模板与 torch 版本耦合；显式映射一次更清楚。

### 8.3 参数只有一个来源

生成的脚本里内嵌三份 JSON：

| 常量 | 来源 | 对应库 |
|------|------|--------|
| `TRAINING_ARGUMENTS` | `SFTTrainingArgs.to_hf_dict()` | `TrainingArguments` |
| `LORA_CONFIG` | `LoRAConfig.to_peft_dict()` | `peft.LoraConfig` |
| `QUANT_CONFIG` | `QLoRAConfig.to_bnb_dict()` | `BitsandBytesConfig` |

测试会把它们从脚本文本里抠出来 `json.loads`，再与来源逐键比对——**教程里的参数与脚本里的参数不可能漂移**。另外 `EXPECTED_TRAINABLE` 来自 `plan_lora`，脚本里用它做一次核对：

```python
if expected and abs(trainable - expected) / expected > 0.2:
    print(f"[警告] 实测可训练参数 {trainable:,} 与预期 {expected:,} 偏差超过 20%，"
          "请检查 target_modules 是否命中了预期的模块")
```

**静默少训一半参数，比直接报错难发现得多**——所以脚本自己带一个 20% 的容差检查。

实测行数：LoRA 脚本 **256 行**、QLoRA 脚本 **277 行**，两份都 `compile()` 通过。

### 8.4 诚实说明

**这两份脚本没有在本机真正运行过**（环境无 GPU、无网络下载权重）。它们的正确性由测试守住四件事：语法可编译、三份内嵌参数与来源同源、关键片段存在、依赖清单正确。这一点必须说清，而不是让读者以为它们已经跑通。

## 第九章：接入 API 与配置

### 9.1 三个只读端点

```python
@router.get("/finetune/lora/defaults", response_model=LoRADefaultsResponse)
@router.post("/finetune/lora/plan", response_model=LoRAPlanResponse)
@router.post("/finetune/lora/memory", response_model=LoRAMemoryResponse)
```

与 day050 一样，**训练本身不进 HTTP 端点**（一个需要 GPU 的长任务不该由一个同步 `def` 路由承载）。三个端点都是"算账"：

| 端点 | 回答什么 |
|------|---------|
| `GET /finetune/lora/defaults` | 默认配置（与 `LoraConfig` / `BitsAndBytesConfig` 同名）+ 每参数存储表 + 目标预设 + **参考模型上实测的参数量账** + 依赖清单 |
| `POST /finetune/lora/plan` | 参数量计划 + 风险告警 + 目标预设对照 + 秩对照 |
| `POST /finetune/lora/memory` | 全参 / LoRA / QLoRA 六项明细 + 单卡适配表（**显式标注不含激活**） |

`/finetune/lora/defaults` 返回的 `reference_model` 就是本课反复用的那一组数字：

```text
可训练 8912 / 冻结 310806 / 合计 319718 / 占比 2.7875% / 秩上界 8
```

### 9.2 一个真实的故障：单元测试全绿，端点返回 500

这是本课第二个值得记的工程教训。defaults 端点最初是这样写的：

```python
reference_plan = plan_lora(DecoderSpec(name="reference-bigram", ...), config)  # ← 错
```

`plan_lora` 面向**解码器规格**（`q_proj` / `gate_proj` … 七个投影），而参考模型只有一个叫 `weight` 的 bigram 矩阵。于是 `matched` 为空，`plan_lora` 抛 `PEFTConfigError`，端点返回 **500**。

而单元测试**全绿**——因为测试只覆盖了 helper（`plan_lora`、`LoRAConfig`、`quantization_table` 各自都对），**没有一条用例覆盖"端点的组合方式"**。

修法是把参考模型的账单独算，并顺带得到一条更好的性质——纯算术、不构造模型：

```python
def reference_lora_accounting(vocab_size: int, config: LoRAConfig) -> dict[str, Any]:
    frozen = vocab_size * vocab_size + vocab_size      # W（V×V）+ b（V）
    trainable = config.adapter_parameter_count(vocab_size, vocab_size)
    total = frozen + trainable
    ...
```

配套加了一条**交叉核对**用例：纯算术的结果必须与真的构造一个 `LoRAReferenceModel` 之后的 `describe()` 完全一致，且端点响应必须等于这个函数的输出。两边各算一遍，任何口径漂移都会立刻暴露。

这条经验的通用形式：**"每个零件都对"不等于"装起来对"。** 覆盖率的盲区往往不在函数内部，而在**函数之间的组合方式**上——所以端点层必须有自己的用例，哪怕它看起来只是在转发。

### 9.3 错误码延续既有契约

| 情况 | 状态码 | 理由 |
|------|--------|------|
| 未知模型规格 | **400** | 请求语义与能力不匹配（同 day048 未知 `format`） |
| 配置非法（`r=0`、未命中模块、`alpha<=0`） | **400** | 参数组合不可行 |
| 未知优化器 / 计算精度 | **400** | 同上 |
| `qlora_overrides` 传对照基线口径（`int4`） | **400** | 见下 |
| `model` 类型错误（如传 `123`） | **422** | Pydantic 在进路由前拦下 |
| 正常 | 200 | — |

第三行的 `int4` 值得单说：显存预算只关心**位宽**，因此它会**静默接受** `int4` 并给出与 `nf4` 完全相同的数字。而 `int4` 只是本课用来回答"为什么是 NF4"的对照码本，bitsandbytes 并不认这个取值——一旦写进 `BitsAndBytesConfig` 就会在运行时报错。所以端点在配置阶段就把它拦下，与 `to_bnb_dict()` 的口径一致。**"对照基线能进生产配置"本身就是一个陷阱。**

### 9.4 十一个配置项

```text
lora_output_dir           = "outputs/lora"
lora_r                    = 8        # 方阵单层比例 = 2r/d
lora_alpha                = 16       # 实际生效的是 alpha/r
lora_dropout              = 0.05     # 只作用在适配器分支的输入上
lora_target_preset        = "attention"
lora_bias                 = "none"
lora_use_rslora           = False
qlora_quant_type          = "nf4"
qlora_compute_dtype       = "bfloat16"
qlora_use_double_quant    = True
qlora_block_size          = 64
```

它们的注释里写清了一件容易混淆的事：**`LoRAConfig` 的字段缺省值按"7B 模型 + peft 官方文档的常见组合"标定，而参考模型需要的是 `lr ∈ [8, 20]` 这个量级**——两者相差四个数量级，混用会得到一条水平的 loss 曲线（4.3 节实测）。

几个值得记的测试写法：

1. **结构性质用 `==` 而不是 `approx`**：初始化不变式与合并等价性都逐位比较。它们守的是"约定有没有混用"，而约定混用不会带来数值误差、只会带来结构性错误。
2. **解析梯度必须与数值差分交叉验证，而且输入不能退化**：`B` 初始全零时 `∂L/∂A ≡ 0`，此时"A 的梯度算得对不对"这条断言会**自动通过**——所以用例先做一次更新让 `B` 离开零，再开始核对差分。**用退化输入验证出来的正确性是假的。**
3. **两种约定的差异要有一条"对不上"的断言**：`assert row != pytest.approx(column)`——把"它们确实不同"这件事也钉住，否则将来有人"顺手统一"成一种约定时不会有人发现。
4. **把不可达的防御分支变成可测的输入**：`bisect` 的"超出码本上界"那个出口在满量程码本下永远走不到，于是用自定义码本 `(0.0, 0.5)` 去覆盖它。反过来，`_backward_into_column` 里那个"检查前向缓存"的分支在两个调用方都经过 `_cached_index()` 之后**确实不可达**，于是直接删掉它而不是加 `pragma: no cover`。**两种做法都指向同一件事：覆盖率这个指标只有在"没有不可达代码"时才有意义。**
5. **端点的组合方式要有自己的用例**：`/finetune/lora/defaults` 那次 500 就是这么暴露出来的（9.2 节）。

## 结语：三条可以带进 M5 的工程结论

1. **参数高效的收益是算术，不是承诺。** `r(in+out)` 与 `2r/d` 是可以在提交任务之前算完的，`target_modules` 的选择能让参数量相差 4.75 倍，而 `r` 加到头会**比全参更贵**。这个模块的全部价值，是把"LoRA 应该挺省的吧"变成一句能被复核的话。

2. **"接上模块不改变行为"必须被断言，而不是被相信。** 本课踩过的行/列约定缺陷，让模型在 loss 正常下降、指标还不错的情况下算错了东西；而它唯一的表征是"合并后的 logits 与适配器模型对不上"。**标量指标会掩盖几乎所有结构性错误**——这与 day050"用同一把尺子评估"是同一条纪律的两个面。

3. **换一种参数化方式，就要重新标定学习率——而且要重新看它的可用区间。** LoRA 在 `[8, 20]` 之外就发散，全参在 `[8, 100]` 都稳定；把两边都调到最优时全参更好。**"更省"不等于"更好"，也不等于"更省心"。** 任何"某个方法更好"的结论，如果不配一张双方都调过的对照表，它就不成立。

> **诚实的说明**：本课的所有训练结果都来自一个 557×557 的 bigram 参考模型，在一份 30 条样本的教学数据集上。它**不是一个可用的模型，也无意成为**；更要注意的是，它的基座是**随机初始化**的，因此训练后的 `ΔW` 比基座大 50 倍（4.5 节）——**真实场景里基座是训练好的模型，`ΔW` 的量级通常远小于基座**，`alpha` 与 `r` 的作用也因此更接近教科书描述。另外，本课生成的 `peft` / `bitsandbytes` 训练脚本**没有在本机真正运行过**（无 GPU、无权重下载），它们由 32 个测试用例守住语法、参数同源与关键片段——这一点必须说清。最后，NF4 码本按定义生成，与 bitsandbytes 实际落盘的查找表**数值不完全相同**（该表由同一分布的量化点经优化得到），因此"逐位对比 code"没有意义，本课对比的是误差量级。

明天（day052）进入 **训练脚本与 PEFT 实践**：把今天"能训"的结论做成一条能交付的流水线——完整的 LoRA SFT 训练脚本（数据加载 → 训练 → 落盘）、用 Accelerate 支持多卡/混合精度、以及**把适配器合并成可部署模型并验证**。今天定下的三件事会直接复用：**`LoRAReferenceModel` 的接口**（训练器直接接上）、**`merged_by_context` 的合并语义**（落盘必须选对那一个矩阵）、**`plan_memory` 的六项预算**（多卡与混合精度改的正是这几项）。
