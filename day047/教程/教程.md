## 第二章：M3 复盘 —— 把"感觉不错"变成"可判定"

### 2.1 一个骨架，六次实例化

M3 的全部代码只实现了一个模式，`evaluation/harness.py` 把它的四步写成契约：

```text
load_dataset（数据集）→ evaluate（执行）→ 评分（scorer/判定）→ summary（汇总）
```

四步的每一步都对应一条纪律：

| 步骤 | 纪律 | 违反后果 |
|------|------|---------|
| 数据集 | 固定、可复现、**必须含边界用例** | 用 3 个手工样本验证概率系统 = 自欺 |
| 执行 | Harness 内**不写业务逻辑**，只负责"跑" | 评估代码与业务代码纠缠，改一处要改两处 |
| 评分 | 评分规则显式可审计（阈值、公式、rubric） | 分数无法回溯到某条样本的某个判断 |
| 汇总 | 必须**分组**（`by_tag`）而不是只给总通过率 | 总分掩盖塌方：safety 组 0 分也能有 0.83 的总分 |

day025 的示例数据集 6 条（math / qa / safety），当天实测 `pass_rate = 5/6 = 0.8333`，而 knowledge 组只有 **0.5**——这一个数字就说明了"为什么汇总必须分组"。

### 2.2 day026：Prompt 评估 —— 双通道 0.4 / 0.6

`PromptEvaluator` 的评分由两路合成：

```python
RULE_WEIGHT = 0.4     # 7 条确定性规则：长度区间、含糊词（尽量/大概/差不多/也许/等等）、
                      # 自相矛盾的指令对（CONTRADICTION_PAIRS 4 对）、占位符等
JUDGE_WEIGHT = 0.6    # LLM 裁判：clarity / consistency / ambiguity_free 三项，各 1~5 分
TIE_THRESHOLD = 0.05  # 两个版本的分数差小于它就算"平局"，不宣布胜者
JUDGE_FALLBACK_SCORE = 3.0  # 裁判输出解析失败时的保守兜底，不让评估整体崩掉
```

三个设计决定值得单独记：

1. **为什么规则只占 0.4**：规则是确定性但粗粒度的（"出现'尽量'就扣分"会误伤），裁判懂语义但会漂移（位置偏差、冗长偏好、自我偏好）。**两路互相制衡**比任何单路都稳。
2. **为什么需要 `TIE_THRESHOLD`**：评估的目的是做决策，而"0.02 分的差距"不足以支撑一个决策。设平局阈值等于把"噪声"显式地从"信号"里剥离出来。
3. **为什么裁判要有 fallback 而不是抛异常**：评估器本身是被评估流程的一个协作者，它的失败不该让整场评估作废——但要给一个**保守**的值（3.0 分，即"中等偏下"），让异常情况不至于伪装成"优秀"。

当天实测 `REACT_SYSTEM_PROMPT_V2` 得 **4.80**，V1 得 **4.00**——而这个差距是"人写得更清楚"，不是"模型更聪明"。**Prompt 高分 ≠ 输出质量好**，这是 day026 最重要的边界，也是 day027 存在的理由。

### 2.3 day027：输出质量评估 —— 把"好不好"拆成可算的三项

`OutputEvaluator` 的加权公式：

```text
overall    = 0.4 * helpfulness + 0.4 * accuracy + 0.2 * format
accuracy   = 0.5 * numeric_consistency + 0.5 * (model_score / 5)
format     = 1.0 起，每处违规扣 0.5（JSON 合法性 / Markdown 结构）
```

三点设计意图：

- **`accuracy` 拆成"数字一致 + 模型打分"两半**：数字类断言（`_extract_numbers` + `_check_numeric`）是确定性的，模型打分是概率性的；前者是锚，后者补语义。**只有确定性的那一半能当门禁用**。
- **格式校验绝不调 LLM**：`_is_valid_json` / `_looks_like_markdown` 都是纯代码判断。能用一行代码判定的事去调一次模型，是评估体系里最常见的成本浪费。
- **权重是公开常量而非埋在代码里**：`0.4/0.4/0.2` 写在模块顶层，改权重是一次**有意识的决策**，而不是一次无痕调参。

`OutputQualityLogger.aggregate()` 用"最近 10 条 + 0.05 死区"判定 improving / degrading / stable——**死区**再次出现（与 day026 的 `TIE_THRESHOLD` 同源）：评估结论要么有阈值，要么就是噪声。

### 2.4 day029：RAG 评估 —— 两段式度量

RAG 有三段（检索、拼上下文、生成），但 day029 只度量两段，因为中间那段无可度量的独立量：

```text
retrieval_recall    = |召回 ∩ 相关| / |相关|      （空相关集 → 1.0，即"没有要求就没漏"）
retrieval_precision = |召回 ∩ 相关| / |召回|      （空召回集 → 0.0，即"什么都没给就是错"）
mrr                 = mean(1 / rank_of_first_relevant)
ndcg                = DCG / IDCG,  DCG = Σ (2^rel − 1) / log2(i + 1)
```

每个指标的边界值都是**刻意选的**，测试逐条钉住（`recall` 遇空相关集给 1.0、`precision` 遇空召回集给 0.0、`idcg = 0` 时给 0.0）。这些"看起来奇怪的默认值"才是评估代码的价值所在——**没想清楚边界，指标就会在真实流量上悄悄撒谎**。

`mean_precision` 在评测集上只有 0.39，看起来很低，但这是**评测集标注密度造成的结构性结果**（标注只标"应该被检索到的文档"，不标"其余都是不相关"）。day029 明确写了这条读法：**读指标之前先读评测集**。

### 2.5 day030：Agent 评估 —— 三把尺子量一条轨迹

评估对象从"一段文本"变成"一条多步轨迹"后，单一指标立刻失效：

| 尺子 | 公式 | 抓什么失败形态 |
|------|------|---------------|
| `completion_rate` | 达成任务的轨迹数 / 总轨迹数 | 任务根本完不成 |
| `step_efficiency` | `mean(min(1, (len(expected_tools) + 1) / steps))` | 能完成但绕远路（烧钱） |
| `tool_accuracy` | 工具集合的 precision / recall / F1 + 顺序 LCS 比 | 用错工具、顺序错乱 |

实测 0.625 / 0.79 / F1 0.71 / 顺序 1.00，四个数字拼出的是"**通过率偏低但工具用得对**"这一诊断——这正是指标分组的意义：一个 0.625 没法指导优化，四个数字可以。

两个细节是踩过坑才写得出来的：

- `_NO_ANSWER_PREFIX = "达到最大步数限制"`：把"步数用尽"识别为一次**失败**而不是一次"答案略差"，否则完成率会被虚高。
- **顺序分只统计成功轨迹**：失败轨迹的顺序没有意义（它本来就走错了路），把它算进去等于用错误的分布污染一个正确指标的均值。

### 2.6 day031：红队 —— 56.3% 到 100%

红队是唯一一种"以攻促防"的评估：用 16 条真实攻击用例（5 注入 + 5 越狱 + 5 PII 套取 + 1 工具滥用）去打自己的防线，**漏网清单就是加固工单**。

基线实测：

| 类别 | 基线拦截率 | 修复后 |
|------|-----------|--------|
| prompt_injection | 60% | 100% |
| jailbreak | 40% | 100% |
| pii_leak | 80% | 100% |
| tool_abuse | 100% | 100% |
| **整体** | **56.3%** | **100%** |

修复的动作全部落在既有的两个模块里，**新增能力一个都没做**：

- `injection_detector.py` 补 5 条规则，并修掉一条正则的**真实缺陷**：`(一个|一个)?` 写错了（重复分支），正确写法是 `(一个|一名|一位)?`——这条规则此前几乎永远匹配不上。
- `content_moderator.py` 的手机号正则收紧为 `(?<!\d)1[3-9]\d[-\s]?\d{4}[-\s]?\d{4}(?!\d)`，用前后否定环视防止把长数字串截出一段"像手机号"的片段。

两个反直觉结论必须记住：

1. **100% 拦截率不等于安全**。它只说明"当前这 16 条用例过不去"。红队的价值在于**用例集本身在增长**，而不在于某一个拦截率数字。
2. **只加规则不修旧规则是红队最常见的浪费**。本次新增 5 条规则的收益，远小于修掉那条写错的正则——**旧规则里的一处笔误，可能比新规则重要得多**。

### 2.7 day032：门禁与可观测性 —— 把评估变成 CI 的一部分

day032 把"评估脚本"升级成"确定性门禁"，关键是把**非确定性**从门禁里剔出去：

```text
run_agent_eval.py --min-completion-rate 0.6 --min-step-efficiency 0.7   # 允许的波动底线
run_redteam.py    --min-block-rate 1.0                                  # 安全零容忍
pytest --cov-fail-under 80                                              # 覆盖率底线
```

- **质量指标留裕度（0.6 / 0.7），安全指标不留（1.0）**：质量指标受模型与数据漂移影响，卡死在实测值上会天天误报；安全指标一旦回归就是事故，必须零容忍。**门禁的松紧应当与"这个指标回归的后果"成正比。**
- `cost_tracker.py` 在这里定型：`UsageRecord`（模型 + 接口 + 输入/输出 token）+ 可配置 `DEFAULT_PRICE_TABLE` + **模型不在价格表就抛 `KeyError`**——宁可报错不可漏算，这是会计纪律。
- `tracing.py` 把"日志"升级为"trace"：log 回答"系统发生了什么"，trace 回答"这一次请求经历了什么"。`_TimedLLMProxy` 用 `__getattr__` 全量透传属性、只覆写 `chat` 做计时——**"用代理插桩、不改业务代码"的范式**，第四章会看到这个设计的另一面价值。

### 2.8 M3 的三条原则（可以直接搬走）

1. **能用代码判定的，绝不交给模型**（格式、数字、正则、空集边界）。
2. **每个分数都必须是路径相关的**：能回溯到"哪条数据、哪条规则、哪个阈值"。
3. **门禁的松紧与后果成正比**，并且**必须设死区**（TIE_THRESHOLD / 0.05 / 判定下限），否则误报会让人关掉门禁——**一个被关掉的门禁等于没有门禁**。

## 第三章：M4 复盘 —— 从"会推理的循环"到"可运营的系统"

M4 十二天的递进关系比 M3 更线性：**先懂模型（内部机制）→ 再管输出（协议）→ 再服务化（进程边界）→ 再扩模态（输入输出）→ 再算账（成本）→ 再设防（安全）→ 最后集成**。

### 3.1 六条主线一览

| 主线 | 课程 | 一句话本质 | 关键落点 |
|------|------|-----------|---------|
| ① 机制与成本地基 | day033、day034 | 自回归生成受采样参数支配；token 是计费与长度的统一单位 | `sampling.py`、`tokenizer.py`（BPE / tiktoken + 字符级降级） |
| ② 输出端控制 | day036、day037 | 从"提示词求格式"升级为"协议保证格式" | `prompt_library.py`、`function_calling.py`、`fc_agent.py` |
| ③ 服务化 | day038、day039 | 把 Agent 变成可被跨进程调用的 HTTP 服务，再叠加流式与选型 | `api/create_app`、`/chat/stream`、`ModelRouter` |
| ④ 输入模态语义化 | day040、day041 | 图像以 data URL 进 content 部件；文本映射为连续向量 | `multimodal/image.py`、`llm/embedding.py` |

### 3.2 三条贯穿 M4 的横切设计

**（一）"扩展抽象、零改动"哲学**——给抽象加新能力时，旧实现一行都不用改：

| 日 | 抽象改动 | 默认值 / 默认实现 |
|----|----------|------------------|
| day039 | `BaseLLM` 加流式 | `stream` 默认 `yield self.chat(...)` 整段返回 |
| day040 | `BaseLLM` 加视觉 | `supports_vision` 默认 `False`；`chat_vision` 默认抛 `NotImplementedError` |
| day041 | `EmbeddingProvider` 加批量 | `embed_batch` 默认逐条调用 `embed` |
| day045 | `BaseLLM` 加本地实现 | 新增 `LocalModelLLM`，但接口零变化 |

规律是：**加"带默认值的具体方法/属性"，而不是加"抽象方法"**。后者会逼所有既有实现同时改造，前者让所有人自动获得地板、愿意深耕的人覆写拿全量收益。

**（二）失败安全方向：能退避就不崩溃。**

| 场景 | 方向 |
|------|------|
| 路由降级链（day033/039/046） | **向上**（更强、更贵的模型）——答错代价 > 多付一次费 |
| `default_llm` 未配密钥（day005） | 退回 `MockLLM`，服务照常启动 |
| `default_embedding` 未配密钥（day041） | 退回 `CharNgramEmbedding` 并告警 |
| 模型不在价格表（day046） | 显式按 0 记价**并告警**，而不是抛异常打断用户请求 |

统一口径：**退避必须留痕**。"静默降级"比"直接报错"更危险，因为它把问题藏进了正常返回里。

**（三）契约自带元信息。**

| 日 | 契约 | 携带的元信息 |
|----|------|-------------|
| day039 | `RouteDecision` | 为什么选了它、是否降级、降级到谁 |
| day041 | `EmbeddingResponse` | `provider` + `dimension`（说明这批向量能否与库里已有的比） |
| day038 | `ToolCallRecord` | `name` / `arguments` / `result` / `success` |
| day046 | `StageRecord` + `PipelineResult` | 每阶段耗时与决定、单次归因费用、是否命中缓存/被拦截 |

单一输出（一段文本、一串向量、一次调用）没有自描述能力；契约里带上"它从哪来、什么口径、成没成功"，下游才可能判断"能不能用、该记谁账上"。

### 3.3 day046 的六阶段与"顺序即策略"

M4 的收口是 `integration/pipeline.py`：

```text
输入侧护栏 → 语义缓存 → 模型路由与生成 → 成本归因 → 输出侧审核 → 缓存回写
 guard       cache       generate          account     moderate     store
```

顺序里藏着的三条安全约束（每条都可被断言观测）：

1. **护栏最先**：被判定为注入的请求**模型完全不被调用**（`llm.calls == []`）。
2. **缓存在护栏之后**：否则一条恶意请求会先命中缓存并直接返回，护栏形同虚设。
3. **审核在回写缓存之前**：缓存里必须存**脱敏后**文本。否则第一次泄漏还能推给"模型说漏嘴"，第二次起就是系统在稳定泄露——**缓存把一次性缺陷变成了持续性缺陷**。测试用 `pii_types` 从 `["邮箱"]` 变成 `[]` 把这个性质钉死了。

## 第四章：一次真实的核对 —— 把"提醒"变成工单

day046 的结语留了三条工程线索，第二条是：

> **包装器要交代清楚"我替谁说话"**。`ModelRouter.last_used_llm` 是一次修补；系统里还有别的包装器（`CachedLLM`、未来的限流器、重试器）需要同样对待。**每加一层包装，就问一句：用量、错误、状态还能穿透吗？**

今天（R2 复盘日）把这句话从"提醒"执行成了一次**核对**。做法：写一个只读脚本，把项目里现存的四个"LLM 形态"各probe一次——看它有没有 `usage_log`、`CostTracker` 能不能直接归因。

### 4.1 核对结果（本轮实际运行）

| LLM 形态 | 持有 `usage_log` | `CostTracker.record_from_llm` 直接归因 | 结论 |
|----------|-----------------|--------------------------------------|------|
| `MockLLM`（叶子） | 有 | 成功，登记 1 条 | 正常 |
| `CachedLLM`（缓存包装器） | **无** | `AttributeError: 'CachedLLM' object has no attribute 'usage_log'` | **断链（遗留项）** |
| `ModelRouter`（路由包装器） | 无 | 直接传它 → 失败；但传 `router.last_used_llm` → 成功，登记 1 条 | day046 的修补**有效** |
| `_TimedLLMProxy`（追踪代理） | 有（`__getattr__` 全量透传） | 成功，登记 1 条 | 正常 |

这张表最有价值的地方在于**它区分了"看起来一样、实际不一样"的两种包装器**：

- `_TimedLLMProxy` 只覆写 `chat`，其余属性**全量透传**（`__getattr__`），所以用量、错误、状态天然穿透——它不需要为自己的存在做任何额外声明。
- `ModelRouter` 和 `CachedLLM` 都是**真实持有状态**的包装器（前者持有决策日志、后者持有缓存），它们挡在了叶子前面，`getattr` 到不了叶子。**只要包装器持有自己的状态，就必须显式回答"用量算谁的"。**

`ModelRouter` 已经回答了（`last_used_llm`），而 `CachedLLM` 没有——于是"缓存 + 计费"这个组合会**静默把真实用量记成 0**，与 day046 撞到的那个 500 是同一根因的另一种表现形式：**一个报错、一个不报错，后者更危险**。

### 4.2 修复方向（交给下一份快照）

最小且语义正确的修法与 day046 完全同构——**不要让包装器去伪造 `usage_log`，而是让它说清楚"我替谁说话"**：

```python
class CachedLLM(BaseLLM):
    @property
    def last_used_llm(self):
        """最后一次实际产生用量的叶子模型.

        内层若自己也是包装器（例如 ModelRouter），就继续向内取它的
        last_used_llm；内层是普通客户端时直接返回它。
        """
        return getattr(self._llm, "last_used_llm", None) or self._llm
```

为什么这样就够：`IntegratedPipeline._account` 的取值链是

```python
target = getattr(self.llm, "last_used_llm", None) or self.llm
if not hasattr(target, "usage_log"):
    logger.warning("模型 %s（%s）不提供 usage_log，本次用量记 0；…")
    return 0.0, 0, 0
```

有了这个属性，`target` 会一路穿到真正产生 token 的那一层；而**缓存命中路径本来就不产生用量**（没有新的 `usage_log` 条目），所以归因结果自动为 0——语义与行为都不需要打折。

一个必须坚持的约束：**这个改动不许改变任何既有行为**。缓存命中仍然直接返回、仍然不调底层模型，只是"当它真的调了底层"时，账单能落到正确的对象上。

> 这条工单在下一份快照（day048）中收口，并配了专门的回旧测试（`CachedLLM` 包住叶子 / 包住 `ModelRouter` / 经流水线归因 / 命中路径成本为 0 / 日志里不再出现"不提供 usage_log"告警）。

### 4.3 顺手复核的两个"已发布结论"

复习日的另一个价值是**抽查已发布内容是否还成立**。今天复核了 day046 教程里的两组数字，全部复现：

```text
满路径  阶段数=6  ['guard','cache','generate','account','moderate','store']  total_ms=13.0
拒答路径 阶段数=1  ['guard']                                                  total_ms=3.0   blocked=True 模型=blocked llm.calls=0
命中路径 阶段数=3  ['guard','cache','moderate']                               total_ms=7.0   cached=True  模型=cache cost=0.0
```

13.0 / 3.0 / 7.0 毫秒这三个数字（在假时钟下是确定值）分别等于"14 次 / 4 次 / 8 次时钟读取"的步进差，也就是**六个 / 一个 / 三个阶段**的另一种表达。**耗时断言即阶段数断言**——将来谁在急路径上多插一次计时，测试会立刻变红。混合路由的分流也复核无误：

```text
1+1 等于几                        -> qwen3:8b      （复杂度 1，本地免费且能力足够）
请分析并对比 RAG 与微调的优劣，…    -> gpt-4o-mini  （复杂度 4，本地 capability=3 被能力阈值排除）
```

**这段实测最值得记的不是结论，而是方法**：结语里写下的"提醒"如果不转成一次核对，它就只是文字；转成核对之后，它变成了一张有证据的表、一条可分配的工单、以及一组"改了没改、改对了没有"的回归断言。**工程里的"我记住了"必须落到"我验证过"。**

## 第六章：常见误区清单（22 天总集）

**M3 评估（day025~032）**

1. **"跑几个 demo 就算评估"** —— 没有固定数据集与显式评分规则的"评估"只是手动试跑；它不可复现，也无法在明天告诉你"是不是变差了"。
2. **"只报总通过率"** —— 分组合计才能暴露塌方（day025 的知识组 0.5 藏在 0.83 的总分里）。
3. **"唯准确率"** —— 相关性、安全性、成本、延迟同样是"好不好"的一部分，且它们的回归后果更重。
4. **"评估集写完就不动"** —— 黄金集的三来源是"线上 bad case > 人工边界 > happy path"，其中 bad case 是持续流入的。
5. **"100% 拦截率 = 安全"** —— 它只说明当前这批用例过不去；红队的资产是用例集在增长，不是某个数字。
6. **"只加新规则、不检查旧规则"** —— 本次那条写错的正则（`(一个|一个)?`）的修复收益大于新增 5 条。
7. **"门禁越严越好"** —— 天天误报的门禁一定会被关掉；松紧应与回归后果成正比，并且要设死区。
8. **"评估器自己不需要兜底"** —— 裁判解析失败要给保守 fallback（3.0），而不是让整场评估 crash。
9. **"格式校验也调 LLM"** —— 能一行代码判定的事去调模型，是评估体系里最常见的成本浪费。
10. **"指标越低越差"要分清** —— `mean_precision = 0.39` 是评测集标注密度的结构结果，读指标前先读评测集。

**M4 应用（day033~046）**

11. **"Few-shot 能教知识"** —— 它校准格式与风格，不补知识。
12. **"CoT 永远有益"** —— 简单任务上"想多了反而错"，要用评估对比而不是假设。
13. **"文本解析能保证格式"** —— 概率性的；原生 `tool_calls` 才是确定性。
14. **"function calling 返回的参数可以直接执行"** —— 必须 `validate_arguments`，且 `bool` 与 integer/number 在 JSON Schema 里互不相容，必须特判。
15. **"同步阻塞代码塞进 async def 更快"** —— 会冻结事件循环；同步代码用 `def` 交给线程池。
16. **"Agent 实例可以跨请求复用"** —— Agent 持有单次任务状态，注入的必须是工厂。
17. **"流式让回答更正确"** —— 它只改 TTFT；function calling 与超长轨迹不适合流式。
18. **"文件扩展名就是 MIME"** —— 用 magic bytes 识别真实类型。
19. **"图片可以用远程 URL"** —— 工具层显式拒绝，防 SSRF。
20. **"MockEmbedding 够用"** —— 哈希雪崩让相似度全在 0 附近，阈值与排序都失去意义。
21. **"容器非空判断用 `or`"** —— 定义了 `__len__` 后空实例是假值，必须 `is not None`。
22. **"缓存与审核的先后无所谓"** —— 先写缓存后审核 = 把一次性 PII 泄漏变成持续性泄漏。
23. **"模型不在价格表就跳过计费"** —— 必须显式按 0 记价**并告警**；静默跳过等于静默撒谎。
24. **"装了成本追踪器就等于能归因"** —— 包装器（`ModelRouter`、`CachedLLM`）会挡住用量，必须显式透传叶子（本日核对的核心结论）。
25. **"本地模型和云模型二选一"** —— 用 `capability` + `cost` 交给路由自动分流，就不需要为省钱写任何 `if`。

完成后用 [../习题/习题.md](../习题/习题.md) 的 16 题自测：选择题覆盖 M3/M4 的辨析，判断题专打上面 25 条误区，简答题要求把"M3 与 M4 如何互相提出需求"串着讲，编程题则在 day046 快照上把"包装器用量透传"这条本日核对出的工单**完整验证一遍**。

## 下一阶段衔接：day048 起进入 M5 微调

明天开始是 M5（day048 ~ day060），第一课就是**微调概览与数据工程**。它对本阶段的两处直接依赖，正好是今天复盘的两个产出：

1. **M3 的评测集是微调的裁判**：微调前后到底变好了没有，只能靠 `EvaluationHarness` + `AgentEvaluator` + `RedTeam` 给出可对比的数字；没有评测集，微调就只是"感觉更好了"。
2. **M4 的数据产线是微调的原料**：`data/eval/agent_tasks.jsonl` 里的 ReAct 轨迹、`data/eval/redteam_cases.jsonl` 里的攻击用例，本身就是现成的 SFT 语料来源——但它们**带着各自的坑**（评估集的轨迹只标注了"期望工具"，并不保证答案正确；红队用例的"期望输出"是拒答而非回答），必须先清洗、打标、过滤，才能进训练集。这正是 day048 数据工程要解决的问题。
