## 第 1 题

**答案：D**

解析：A、B、C 是教程第一章的控制权对照表——Tools 模型可控、Prompts 用户可控、Resources 应用可控。D 把 Tools 说成"用户可控"恰好颠倒了：Tool 的全部意义就是**把调用决策权让渡给 LLM**，Server 只声明能力，模型在推理中自主选择。注意区分一个常见误解：有些 Host 产品（如 Claude Desktop）会提供"工具调用前用户确认"的开关，那是 Host 在**应用层**加的安全闸门，不改变 Tool 在**协议层**"模型可控"的本质——协议设计上，调用意图由模型发起。

## 第 2 题

**答案：B**

解析：stdio 传输的进程模型是"Client 拉子进程、管道通信"：`McpClient.connect()` 通过 `stdio_client(StdioServerParameters(...))` 把 server 拉成子进程，接管其 stdin/stdout，双方用换行分隔的 JSON-RPC 消息通信。

- A 错：那是 HTTP/SSE 传输的模型，stdio 不需要端口、不需要预先部署——这正是本地 MCP server 配置只需一行命令的原因。
- C 错：stdio 是"一 client 一 server 进程"，并发会话要各拉各的子进程（进程级隔离），需要共享内存状态时得换网络传输。
- D 错：stdout 被协议独占，`print()` 的任何输出都会混进 JSON-RPC 字节流，让 client 解析崩溃——教程 4.2 节的事故复盘就是这个。

## 第 3 题

**答案：B**

解析：MCP 里要区分两层失败。**协议级错误**（方法不存在、参数类型不符）走 JSON-RPC 的 `error` 字段，语义是"这次调用本身不成立"。而"表达式算不出来"属于**业务级错误**：工具被正确调用了，只是业务结果是失败。把它放进正常 result 的文本里（`"计算失败: ..."`）是刻意设计——LLM 会把这段文本当作 Observation 读进上下文，理解失败原因后换个表达式重试；如果换成协议级错误，模型面对的只是一个冰冷的错误码，自我修正的闭环就断了。day010 防御式解析里的教训在这里同样适用：错误信息要写给它的消费者看，Tool 结果的消费者是 LLM。

- A 错：`-32602` 是 Invalid params，指参数不符合 schema，不是"参数合法但算不出结果"。
- C 错：异常适合表达"协议/系统故障"，业务失败是正常结果的一种取值。
- D 错：业务错误根本不影响传输层。

## 第 4 题

**答案：错**

解析：这是教程 2.2 节的核心论点。重写一份 AST 求值逻辑有三个硬伤：

1. **逻辑双份必漂移**：AST 白名单是安全敏感代码（防御恶意表达式），将来修改时改一处漏一处，安全边界就出现裂缝。
2. **测试资产失效**：day004 为 `execute()` 写的测试对重写版毫无约束力。
3. **破坏架构契约**：`BaseTool` 是项目内工具的统一抽象，MCP 只是新的**暴露通道**，不是新的工具体系。

正确姿势是适配器模式：MCP tool 函数是薄壳，转发给 `CalculatorTool.execute()`。业务逻辑一份，暴露通道可以有 N 份（ReAct 提示词、MCP、未来的 function calling）。

## 第 5 题

解析：这是 Tool 原语最反直觉也最重要的原理。模型调用工具时没有 IDE、没有源码、没有文档，它在上下文里看到的**只有** `tools/list` 响应里的 name、description、inputSchema 三元组。由此直接推出两个工程结论：

## 第 6 题

**答案：错**

解析：题干把因果关系说反了。子进程**不会**继承父进程已解析的 import 结果——Python 的模块解析发生在每个进程自己的解释器里，跨进程边界能传递的只有环境变量和命令行参数。注入 `PYTHONPATH` 恰恰是因为**不注入会出问题**：本机 venv 里装着旧版 editable 安装，子进程 `python -m smart_research_agent.mcp_server.server` 会优先解析到 site-packages 里的旧代码（没有 mcp_server 模块）而报 ModuleNotFoundError。显式注入项目根到 `PYTHONPATH` 最前面，保证子进程加载的是"这份代码"。原则：**跨进程边界的依赖必须显式传递，不能靠侥幸。**

## 第 7 题

**参考答案**：

**从 schema 层入手**，具体改法：给参数补上格式说明与示例——

```json
"date": {
  "type": "string",
  "description": "查询日期，ISO 8601 格式，例如 '2024-08-13'"
}
```

必要时再加 `"pattern": "^\\d{4}-\\d{2}-\\d{2}$"` 让校验前移到协议层。

**为什么优先于换模型**：

1. **模型选工具、造参数的唯一依据就是 schema**（第 5 题）。schema 里没写格式，模型只能按训练语料里最常见的中文习惯自由发挥——这不是模型笨，是你没告诉它契约。
2. **成本与确定性**：改 schema 是一行配置的改动，效果立竿见影且可回归验证；换模型是昂贵且不确定的赌注，而且只要 schema 依然含糊，更强的模型也只是"错得少一些"。
3. 这与 day010 设计 PLAN_PROMPT 是同一条原则的延续：**凡是需要被程序消费的输入，都要在源头显式锁定结构**。提示词锁定 LLM 的输出结构，schema 锁定 LLM 的输入构造。

## 第 8 题

**参考答案**：

如果 prompt 只能返回一个字符串，模板就只能表达"一段 user 消息"。但很多高质量提示词本质上是**多轮结构**——最典型的就是 few-shot 模板：

```text
user:      请把"开心"翻译成英文
assistant: happy
user:      请把"难过"翻译成英文
assistant: sad
user:      请把"{word}"翻译成英文
```

这里 assistant 的示例回答是**对话历史的一部分**，只有"消息列表 + role 字段"的数据结构才能表达：模板函数返回若干条 `PromptMessage(role=..., content=...)`，client 把它们原样铺进对话再交给 LLM。

所以这个设计的本质是：**Prompt 原语返回的不是"文本"，而是"一段构造好的对话上下文"**。字符串只是其中最简单的一个特例（单条 user 消息，我们今天的 `research_report` 就是）。协议按最一般的情况设计返回值，简单场景自然被覆盖。

## 第 9 题

**参考答案**：

**（1）崩溃机理**：stdio 管道上，client 的消费方式是"按行读取，每行都必须是一个完整的 JSON-RPC 消息"。server 往 stdout 写一行日志，这行字节和协议消息混在同一个字节流里，client 无从区分——它把日志行当 JSON 解析，抛 ValidationError，会话就此损坏。管道是**无类型的字节流**，没有"这条是日志、那条是协议"的标记位，所以纪律只能靠写入方遵守。

**（2）Unix 惯例与放大效应**：惯例是 **stdout 承载程序的标准输出（契约通道，可被下游程序管道消费），stderr 承载诊断信息（自由通道，给人看）**。`grep error log.txt | wc -l` 能工作，就是因为 grep 的结果走 stdout、错误信息走 stderr。stdio MCP server 把这个惯例的后果放大到了极限：传统场景下 stdout 混入一行杂质，下游可能只是一个计数偏差；而在 MCP 里，stdout 的每一行都是协议帧，**一行杂质即协议崩溃**。这也是为什么修复落在 `logger.py`——把控制台 handler 从 `sys.stdout` 改到 `sys.stderr`，一行改动恢复整个纪律。

## 第 10 题

**参考实现**（追加到 `mcp_server/server.py`）：

```python
import re
from collections import Counter

_SPLIT_RE = re.compile(r"[\s，。、；：？！,.;:?!\"'（）()\[\]【】]+")


@app.tool(
    name="word_count",
    description="统计文本中各词的出现频次，返回最高频的 top_k 个词，例如 text='a b a' 返回 'a: 2\\nb: 1'",
)
def word_count(text: str, top_k: int = 5) -> str:
    """按空白与常见标点切分统计词频，频次并列时按字典序排列."""
    words = [w for w in _SPLIT_RE.split(text) if w]
    if not words:
        return "（空文本）"
    counter = Counter(words)
    # 先按频次降序、再按字典序升序，保证输出确定性
    ranked = sorted(counter.items(), key=lambda kv: (-kv[1], kv[0]))[:top_k]
    return "\n".join(f"{word}: {count}" for word, count in ranked)
```

**参考测试**（追加到 `tests/test_mcp_tools.py`）：

```python
class TestWordCountTool:
    async def test_list_tools_contains_word_count(self):
        async with create_connected_server_and_client_session(app) as session:
            tools = await session.list_tools()
            wc = next(t for t in tools.tools if t.name == "word_count")
            assert "text" in wc.inputSchema["required"]
            assert "top_k" not in wc.inputSchema["required"]

    async def test_word_count_orders_by_frequency(self):
        async with create_connected_server_and_client_session(app) as session:
            result = await session.call_tool("word_count", {"text": "a b a c a b"})
            lines = result.content[0].text.splitlines()
            assert lines[0] == "a: 3"
            assert lines[1] == "b: 2"

    async def test_word_count_default_top_k_is_five(self):
        async with create_connected_server_and_client_session(app) as session:
            result = await session.call_tool(
                "word_count", {"text": "w1 w2 w3 w4 w5 w6 w7"}
            )
            assert len(result.content[0].text.splitlines()) == 5
```

**解析**：

1. **默认值为什么必须写在签名里**：FastMCP 从函数签名推导 inputSchema——`top_k: int = 5` 让 schema 里 top_k 带默认值且不进 required 列表，模型/客户端才能合法地省略它。如果把 `top_k = 5` 挪进函数体（如 `top_k = top_k or 5`），签名上 top_k 就成了必填，协议层会拒绝缺参调用。**签名即契约，这是 FastMCP 的核心心智模型。**
2. **确定性排序**：`Counter.most_common()` 对频次并列的元素顺序依赖插入顺序，而插入顺序依赖文本中词的出现先后——同名测试换个文本就可能翻案。显式 `sorted(..., key=lambda kv: (-kv[1], kv[0]))` 把并列时的次序固定为字典序，输出才真正可断言。测试工具类代码时，**任何依赖"恰好稳定"的行为都应改成"显式稳定"**。
3. **description 里的示例**：`'a b a' 返回 'a: 2\nb: 1'` 这一段是写给 LLM 的 few-shot 信号（教程 2.3 节）——模型读到它就知道该传纯文本、以及返回格式的样子，比抽象的文字说明有效得多。
4. **required 断言的意义**：`"text" in required`、`"top_k" not in required` 这两条断言锁定的不是实现细节，而是**工具的对外契约**——将来谁重构时把 top_k 改成必填，测试立即报警，下游所有省略 top_k 的调用方免于被动 break。
