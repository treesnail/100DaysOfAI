## 第一部分：选择题

### 第 1 题（LoRA 的算术）

**答案：A**

`r=8` / `alpha=16` 时：

- 新增参数 `r(in+out) = 8 × (557 + 557) = 8912`；
- 分母是**模型总参数**（基座 310 806 + 适配器 8 912 = 319 718），因此占比 `8912 / 319718 = 2.7875%`——这与 peft 的 `print_trainable_parameters()` 口径一致，报告里的数字因此能直接和训练日志对照。B 选项用的 2.867% 是 `8912 / 310806`，分母少了适配器自己；C 错在"旁路不增加参数"（旁路本身就是那两个小矩阵）；D 错在秩上界由 `min(r, in, out)` 决定，`r=8` 时是 8 而不是 557。

### 第 2 题（单矩阵比例 vs 模型级比例）

**答案：C**

`2r/d` 只在方阵上精确。非方阵的精确值是 `r(in+out)/(in·out)`：以 `4096×11008`、`r=16` 为例，`2r/d` 给 0.2907%，而精确值是 **0.5360%**——偏小 46%。本课因此让 `ModuleShape.square_shortcut_ratio()` 在非方阵上返回 `None` 而不是给近似值：**近似值只在它成立的条件下才叫近似**。

A、B、D 都正确。B 那一组数字来自 `target_preset_table`：`attention` 4 194 304 与 `all_linear` 19 988 480 相差 4.75 倍。

### 第 3 题（初始化）

**答案：B**

`B` 全零使 `ΔW = (α/r)·B·A = 0`，于是"刚挂上适配器"时模型输出与基座逐位一致——这正是"先挂上、再评估、再训练"这条工作流安全的原因。本课实测：557 个上下文 token 全部逐位相同（`scripts/lora_demo.py` 第 3 节）。

A 错在"没有梯度"：`∂L/∂B[i][j] = scaling·g[i]·a[j] ≠ 0`，梯度是有的，只是 `A` 那一侧暂时为 0（见下题）。D 恰好相反：第一步**只动 `B`**，因为 `∂L/∂A[j][k] ∝ Σ_i g[i]·B[i][j] = 0`。

顺带一个推论（测试里也钉住了）：**第一次更新只改变 `B`**——适配器先学"输出方向"，再学"输入投影"。

### 第 4 题（行约定与列约定）

**答案：B**

```text
dense（forward / forward_onehot）：out = W @ e_index = W[:, index]     （W 的一列）
context（forward_context）      ：out = W[index] + ΔW[:, index]        （W 一行 + ΔW 一列）
```

本课的基座 `ReferenceSFTModel.logits(ctx) = W[ctx]` 等价于把 `Wᵀ` 当作这一层的权重，因此增量走 `ΔW[:, ctx]`——**"基座取行、增量取列"不是笔误，而是同一个矩阵被解读了两次**。

A 错（两者结果不同）；C 错（两条约定的合并矩阵不同：`W + ΔWᵀ` 与 `W + ΔW`）；D 错——混用之后 loss 照常下降、指标看起来还不错，本课实现时实测到的是"合并后与该适配器模型的 logits 最大差 0.0381"，而训练曲线的表现是 `loss 6.32 → 5.36`、评估 loss 3.8843。

### 第 5 题（QLoRA 的存储）

**答案：C**

QLoRA 训练的是 bf16 的适配器，4-bit 只用于存储冻结的基座。每参数存储 = 码点 4 bit + 常数开销：`block=64` + 二级量化时是 `4 + 8/64 + 32/(64×256) = 4.126953 bit = 0.515869 字节`。

A 错（适配器全程 bf16）；B 错（常数开销真实存在，4-bit 并不等于 0.5 字节）；D 把方向记反了——**块越大、常数开销越小**（块 512 时降到 0.501984 B/参数），代价是每块共享一个 absmax、精度下降。

### 第 6 题（显存六项）

**答案：D**

本课所有显存报告都**同时给出 GiB 与 GB**，因为两者相差 7.4%（`13.48 GiB = 14.47 GB`），在"能不能放进 24 GB 卡"这种判断上混用单位会给出错误答案。A、B、C 都正确。

## 第二部分：判断题

### 第 7 题

**错。**

单独看 `lora_alpha` 没有意义，真正生效的只有比例 `alpha/r`（rsLoRA 时是 `alpha/sqrt(r)`）：

```text
LoRA r=8 alpha=16 → scaling = 16/8 = 2.000000
LoRA r=16 alpha=16 → scaling = 16/16 = 1.000000   ← 秩翻倍，缩放减半
```

改 `alpha` 而没意识到自己在改缩放，等价于**偷偷改学习率**——而日志里的 `learning_rate` 完全看不出来。所以 `LoRAConfig.describe()` 会把公式一起打印出来。

### 第 8 题

**错。**

在 30 条样本、30 步的同一预算下把两边都调到最优（评估 loss）：

| 方法 | 最优 lr | 评估 loss |
|------|--------|----------|
| 全参微调 | 100 | **3.4344** |
| LoRA r=8 | 20 | 3.8843 |

全参更好，而且这是**结构性**的：LoRA 用秩 ≤ 8 的增量去逼近 310 249 维的全秩更新，容量上限就在那里。LoRA 的收益是显存与落盘体积（5.96× / 22.61×），不是效果。

反过来那句"LoRA 一定更差"也不成立——它取决于 `r`、数据量与步数预算（本课秩扫里 `r=32` 就降到 3.7702，比 `r=8` 更好）。**任何"某个方法更好"的结论，都必须配一张双方都调过的对照表。**

### 第 9 题

**错。**

NF4 有 16 个码点，是**偶数个**，因此最接近 0 的两个码点是 `±0.042095`（相对满量程），**没有 0**。实测的 16 个码点里 `code 7 = -0.042095`、`code 8 = +0.042095`。

这是刻意的取舍：NF4 用"牺牲 0 附近的稠密性"换来"中间概率区间的更细分辨率"。相比之下 `fp4`（E2M1）的 8 个幅值里有 0，`int4`（等间距）也没有 0。

### 第 10 题

**错。**

实测（同一份 557×557 矩阵、`block=64`）：

| 权重分布 | 最优码本 | NF4 RMSE | INT4 RMSE | FP4 RMSE |
|---------|---------|----------|-----------|----------|
| 均匀 `U(-0.02, 0.02)` | INT4 | 0.0010600900 | **0.0007526700** | 0.0012456900 |
| 高斯 `N(0, 0.02²)` | **NF4** | **0.0018276500** | 0.0019959000 | 0.0021101300 |
| 训练后的合并权重 | FP4 | 0.0695561600 | 0.1007005500 | **0.0656704200** |

第二行才是"为什么是 NF4"的证据（在正态分布上它最好）。第一行反过来：本课基座是均匀初始化的，等间距的 INT4 反而最优。**NF4 的优势依赖"权重近似零均值正态"这个前提。**

### 第 11 题

**错。**

合并的做法取决于"哪个约定"。本课里两条都实现了，而且它们的合并矩阵不同：

```text
merged_weight()      = W + ΔW      ← 对应 forward（dense 约定）
merged_by_context()  = W + ΔWᵀ     ← 对应 forward_context（查表约定）
```

参考模型走后者（它的 `logits(ctx) = W[ctx]`）。**部署时落错一个不会报错，只会让输出全错**——所以本课把这条关系写成了逐元素断言。

## 第四部分：简答题

### 第 14 题（两个真实教训）

**（1）行 / 列约定混用**

- **表征**：`LoRAReferenceModel.merge()` 得到的普通模型与带适配器的模型在同一个上下文 token 上给出不同的 logits（实测最大差 **0.0381**），评估 loss 也差 `3.8858638865` vs `3.8855603004`。
- **为什么难发现**：训练完全正常——`loss 6.3225 → 5.3615`、评估 loss 3.8843。**所有标量指标都没问题**：loss 在降、loss 曲线平滑、评估指标甚至比全参基线好。错的是"模型的语义"，而标量指标看不见语义。
- **守住它的手段**：一条**结构性**断言——**`ΔW = 0` 时（刚挂上适配器、还没训练），适配器模型在全部 557 个上下文 token 上必须与基座逐位相同**。用 `==` 逐元素比较而不是 `approx`。这条断言在混用约定的实现里立刻失败，而在只看 loss 的检查里永远通过。

  换句话说：**"接上模块不改变行为"这类设计必须被断言，而不是被相信。** 检查 loss 是不够的，因为 loss 会掩盖几乎所有的结构性错误。

**（2）端点返回 500 而单元测试全绿**

- **表征**：`GET /finetune/lora/defaults` 返回 500，`error_type = "PEFTConfigError"`，`detail` 是"没有匹配 target_modules=['weight'] 的模块"。
- **为什么难发现**：`plan_lora`（面向解码器规格）与"参考模型只有一个 bigram 矩阵"这两件事**各自都是对的**，单元测试也各自都覆盖了；错的是**端点的组合方式**——把参考模型的规格硬塞进 `plan_lora`，于是 `matched` 为空、抛错。**"每个零件都对"不等于"装起来对"。**
- **守住它的手段**：两层。
  1. 给端点层写自己的用例（哪怕它看起来只是在转发）——本课的 `test_lora_api.py` 就是这么发现它的；
  2. 把参考模型的账单独做成一个纯算术函数 `reference_lora_accounting()`，并加一条**交叉核对**用例：纯算术的结果必须与真的构造一个 `LoRAReferenceModel` 之后的 `describe()` 完全一致，端点响应也必须等于这个函数的输出。**两边各算一遍，任何口径漂移都会立刻暴露。**

  这条经验的通用形式：**覆盖率的盲区往往不在函数内部，而在函数之间的组合方式上。**

实测输出要点：

```text
总参数（API）: 1,721,862,144
逐项重算    : 1,721,862,144 一致
单层: 60,821,504 | 词嵌入: 262,144,000
attention_width: 2048 kv_width: 512

  r=128  可训练  134,217,728 占比 1.9529%  ← 首次 > 1%
```

**关于"线性但不划算"**：可训练参数对 `r` 是**严格线性**的（每加一秩，每层多 `in+out` 个参数，`llama-2-7b` 的 `all_linear` 每层多 1048 576 个）。但**容量对 `r` 的收益是递减的**——秩从 1 加到 8 时，`ΔW` 能表达的子空间从 1 维扩到 8 维，这一步的变化是数量级的；而从 64 加到 128 时，多出来的那 64 维对"拟合 30 条教学样本"几乎没有贡献，只是把优化器状态、显存和步数成本再翻一倍。

本课 rank 扫的实测也印证了这一点：`r=8` 的评估 loss 是 3.8843，`r=16` 反而升到 4.1170，`r=32` 才降到 3.7702——**30 条样本、30 步这个预算下，秩与效果根本不成单调关系**（day048"500 条以下先补数据"的规则在这里第二次命中）。所以正确的做法是：参数量用算术算清（这一题），容量用评估集去量（不能靠公式）。

### 第 16 题（参考答案）

```python
from smart_research_agent.peft import LoRAConfig, LoRALinear

square = [[0.10, 0.20, 0.30], [0.40, 0.50, 0.60], [0.70, 0.80, 0.90]]
config = LoRAConfig(r=2, lora_alpha=4, lora_dropout=0.0, target_modules=("weight",))
layer = LoRALinear(square, config, seed=5)

# 1. ΔW = 0 时两种约定都等于基座（此时差异不可见）
for i in range(3):
    assert layer.forward_context(i) == square[i]                       # 第 i 行
    assert layer.forward_onehot(i) == [square[k][i] for k in range(3)] # 第 i 列

# 2. 训练 3 步（让 ΔW 离开零）
for _ in range(3):
    layer.accumulate([1.0, 0.0, 0.0], [0.5, -0.5, 1.0])
    layer.apply_update(0.3)
row0 = layer.forward_context(0)
col0 = layer.forward_onehot(0)
assert row0 != col0
print("行约定:", row0)
print("列约定:", col0)

# 3. 合并矩阵：走 context 约定的那一份才与 forward_context 一致
merged_context = layer.merged_by_context()
merged_dense = layer.merged_weight()
for i in range(3):
    assert layer.forward_context(i) == merged_context[i]
assert merged_context[0] != merged_dense[0]

# 精确关系：M[i][j] = W[i][j] + ΔW[j][i]
for i in range(3):
    for j in range(3):
        delta_transposed = merged_dense[j][i] - square[j][i]
        assert abs(merged_context[i][j] - (square[i][j] + delta_transposed)) < 1e-12
print("merged_by_context = W + ΔWᵀ；merged_weight = W + ΔW")
```

实测输出：

```text
1) 初始化（ΔW=0）时两种前向是否都等于基座：
   i=0 row=[0.1, 0.2, 0.3] column=[0.1, 0.4, 0.7] | row == 基座第 i 行: True | column == 基座第 i 列: True
   i=1 row=[0.4, 0.5, 0.6] column=[0.2, 0.5, 0.8] | row == 基座第 i 行: True | column == 基座第 i 列: True
   i=2 row=[0.7, 0.8, 0.9] column=[0.3, 0.6, 0.9] | row == 基座第 i 行: True | column == 基座第 i 列: True

2) 训练 3 步（accumulate + apply_update，lr=0.3）：
   i=0 行约定: [-12.238621, 12.538621, -24.377243]
   i=0 列约定: [-12.238621, 12.738621, -23.977243]
   两者是否相同: False | 最大差异: 0.400000

3) merged_by_context[0] = [-12.238621, 12.538621, -24.377243]   （与 forward_context 一致）
   merged_weight[0]     = [-12.238621, -0.991146, -2.805317]    （不是同一个矩阵）
   精确关系 M[i][j] = W[i][j] + ΔW[j][i] → 全部 9 个元素都满足（已断言通过）
```

**这个实验说明了三件事**：

1. **`ΔW = 0` 时两种约定给出相同的结果**——因为差异只来自 `ΔW` 而不是基座。这解释了为什么"挂上适配器后第一次前向对比基座"这个检查**通不过这一关**：它只能发现"基座取错了行/列"，发现不了"增量取错了行/列"。真正能守住的是那条更强的断言（全部 557 个上下文逐位一致 + 合并后逐位一致）。
2. **训练之后差异立刻显现**（本例最大差 0.4）。注意这里差异之所以明显，是因为学习率 0.3 对一个 3×3 的小矩阵来说很大；在真实规模上差异会更小，但**方向性错误不会因为小而变成正确**。
3. **合并时必须选对那一个矩阵**：`merged_by_context = W + ΔWᵀ` 才与 `forward_context` 一致。两者的关系是精确的 `M[i][j] = W[i][j] + ΔW[j][i]`——把它写进断言，比写进注释有用。
