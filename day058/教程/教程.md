## 第一章：为什么"训得出来"不等于"敢上线"

### 1.1 day057 留下的那句伏笔

day057 的结语里写着：

> 今天的 `manifest.json` 与内容指纹会直接成为模型版本链的上游：数据集指纹 +
> 适配器内容哈希 + 基座名，三者合起来才回答得了"这个效果是哪一份数据、
> 哪一次训练、哪一版代码造出来的"。

今天就是把这句伏笔兑现。而兑现的第一步是承认一件事：**那三个值分布在三个
互不相识的地方**。

| 证据 | 谁产生的 | 存放在哪 | 回答什么问题 |
|------|---------|---------|-------------|
| `dataset_fingerprint` | day057 的 `domain_data.pipeline` | `outputs/domain_data/manifest.json` | 是哪批问题 |
| `adapter_sha256` | day052 的 `peft.trainer` | `outputs/lora/adapters/adapter-final/` | 是哪份权重 |
| `base_model` | day050 的配置 / HF 模型名 | `.env` 与生成的训练脚本里 | 挂在哪个基座上 |

三份证据各自都可复现，但它们之间**没有一根绳子**。而没有绳子的后果很具体：

- 磁盘上躺着 `outputs/lora/adapters/` 下的七个适配器目录，没人说得清
  哪一个对应哪一版数据；
- 想把线上回退到"上周那版"，你得先重建"上周那一版"这个概念——
  而它在系统里根本不存在；
- 两次训练得到同一个 loss，你会怀疑数据没变，但无法证明。

### 1.2 四个问题与五个模块

`registry/` 包把上面那两句问话拆成四件事，每件事一个模块：

```text
version.py   三元组与内容寻址的版本键      —— "这是不是同一份产物"
record.py    版本记录与四态流转            —— "它是什么状态、能不能部署"
store.py     追加写事件日志 + 折叠         —— "历史是什么，生产版本是谁"
triggers.py  触发器与否决项                —— "现在该不该训"
rollback.py  采纳判定与回滚计划            —— "换不换、退不退、怎么退"
retrain.py   六步流水线                    —— 把上面五件事串成一次可复盘的动作
```

### 1.3 三种"版本管理"与它们的代价

这不是一道只有唯一答案的设计题。三种做法都真实存在于工程里：

| 做法 | 实现成本 | 代价 |
|------|---------|------|
| **目录约定**（`outputs/lora/adapter-20260916/`） | 零 | 三个字段散在目录名、README 与口头记忆里；改名就等于改元数据 |
| **自增号 + 一张表**（`v17` 存在数据库） | 低 | 跨机器不指向同一份产物；"v17 能不能替代 v16"答不出来 |
| **内容寻址 + 语义化版本**（本课） | 中 | 键不能排序（因此不能只留键）；需要一次规范化序列化的设计 |

选第三种的理由只有一条，但它足够硬：**键相同必须意味着行为逐位相同**。
自增号给不了这个保证——两个仓库里都叫 `v17` 的两份产物，完全可能是两件事。

## 第二章：版本三元组 —— 身份是算出来的

### 2.1 内容寻址：三项缺一不可

```python
version_key = sha256(canonical(base_model, adapter_sha256, dataset_fingerprint))[:16]
```

每一项缺了会怎样，逐条都是具体的故障：

| 字段 | 缺了它会怎样 |
|------|-------------|
| `base_model` | 同名同格式的适配器挂在不同的基座上会给出**完全不同**的输出，而且**不会报错**（day052 的推理脚本专门为此打了警告） |
| `adapter_sha256` | 分不清"调了学习率重训"与"同一个权重" |
| `dataset_fingerprint` | 分不清"同一份数据多训了两轮"与"换了一批数据"——而这两件事的效果差异通常比调参大得多 |

实测（demo 第 1 节）：

```text
原始     → abef9265dd96544e  适配器 1a2b3c4d5e6f
换适配器 → 55bc9fa9f8952a71  适配器 5c6d7e8f9012
换数据集 → c0d0b7c9b0c359c2  适配器 1a2b3c4d5e6f
换基座   → eb58037eb819dc17  适配器 1a2b3c4d5e6f
```

### 2.2 归一化：抄哈希时的三个坑

下面这一对**必须相等**，否则注册表里会出现两份指向同一产物的记录，
而它们的"重复"不会以任何形式暴露：

```python
canonical = VersionTriple(base_model="Qwen3-8B", adapter_sha256=ADAPTER_A, ...)
sloppy    = VersionTriple(base_model="  Qwen3-8B  ",
                          adapter_sha256=f"sha256:{ADAPTER_A.upper()}",
                          dataset_fingerprint=DATA_A.upper())
```

实测 `三者相等 True | 键相同 True`。三个归一化动作各自对应一个人工事故：

- **去空白**：从终端复制哈希时尾部常带换行，而 `"abc\n" != "abc"`；
- **去 `sha256:` 前缀**：`AdapterManifest.summary_line()` 印的就是带前缀的形式
  （`sha256:5c6d7e8f9012`），人肉抄进配置时会把前缀一起抄进来；
- **转小写**：`hexdigest()` 给小写，但很多人手写大写——哈希比较必须是
  **值比较**，不是字符串比较。

归一化之后**立刻做十六进制校验**：一个含 `g` 的"哈希"是抄错了，
而它如果混进键里，只会表现为"版本总是不匹配"，不会有任何报错。

### 2.3 递增位：让"变化的那一项"决定

版本号规则不是另定一套，而是**直接由三元组的差异推出**（`bump_kind_for`）。
实测一条四步演进（demo 第 2 节）：

| 步骤 | 变化项 | 递增位 | 新版本号 |
|------|--------|--------|----------|
| 首版 | （首版） | minor | v1.0.0 |
| 同数据重训 | `adapter_sha256` | patch | v1.0.1 |
| 换数据集 | `dataset_fingerprint` | minor | v1.1.0 |
| 换基座 | `base_model` | major | v2.0.0 |

第三条看起来最"小"，实际上最重要：**重训是持续微调里最高频的动作**。
把它标成 `minor` 会让版本号迅速失去区分度（v1.9 → v2.0 只因为多跑了一次
同样的数据）；而 `major` 的语义被保留给基座替换——这是唯一一个让"回滚"
都必须重新评估的动作，因为**旧适配器挂不上新基座**。

递增时右边的位必须归零，否则会得到 `1.9.3 → 2.9.3` 这种"跨了大版本
却还带着小版本号"的怪号。

### 2.4 一个容易踩的排序陷阱

```python
next_version([], kind=BUMP_MAJOR)                       == "1.0.0"
next_version(["1.0.0", "1.2.0", "1.1.0"], kind=...)     == "1.2.1"
next_version(["1.9.0"], kind=BUMP_MINOR)                == "1.10.0"
```

三行各有一个判断：

1. 空历史无论如何都给 `1.0.0`（递增位只在**有历史**时才起作用）；
2. 取的是**最大的**版本号而不是"最后登记的那个"——手工登记与自动登记
   混用时，"最后一个"取决于登记顺序，而"最大的"才是版本号本身的语义；
3. `1.9.0 → 1.10.0` 而不是 `2.0.0`。这个看起来显而易见，但**如果排序用
   字符串比较就会答错**：字符串序里 `"1.10.0" < "1.9.0"`，
   于是"最新版本"会答错——而 `head()` 的实现正建立在这个排序上。

## 第三章：事件流索引 —— 版本表是日志，不是列表

### 3.1 只有两种事件，没有"删除"

`versions.jsonl` 的真实内容（demo 第 3 节）：

```text
  1. type=register version=1.0.0
  2. type=stage    version=1.0.0
     stage=stable reason=首次上线，人工门禁通过
  3. type=register version=1.0.1
```

读的时候把事件折叠成当前状态。**看起来比"直接存一个版本列表"更复杂，
那为什么还要这么做？** 因为覆盖写会同时引进三个问题：

1. **写路径从 O(1) 变成 O(N)**，而版本数量只会单调增长；
2. **丢失了"什么时候变的、为什么变"**——记录里的 `stage` 字段只能说明
   "现在是 stable"，说明不了"它是 3 天前因为候选胜出被提升的，还是刚刚
   因为回滚被设回来的"。而这两种情况在运维上完全不同；
3. **一次崩溃就可能截断整个文件**。day027 的 `OutputQualityLogger` 选 jsonl
   的理由正是"单行损坏不传染"；重写全量的写入方式把这条保护还回去了。

代价是**读的时候要多做一次折叠**。这条代价很小，而且能被测试钉住。

### 3.2 折叠必须确定，损坏必须响亮

实测（demo 第 3 节）：

```text
折叠后：{'candidate': 1, 'stable': 1, 'rolled_back': 0, 'archived': 0, 'total': 2} | head=1.0.0
重新加载后：{'candidate': 1, 'stable': 1, 'rolled_back': 0, 'archived': 0, 'total': 2} | head=1.0.0 | 键一致 True
版本链（v1.0.1 → 祖先）：['1.0.1', '1.0.0']
可回滚的 stable 祖先：['1.0.0']
```

五类索引损坏各自报错，每一类都是"静默丢状态"的入口：

| 损坏 | 抛错理由 |
|------|---------|
| 不是合法 JSON | 行号 + 解析器原文 |
| 不是 JSON 对象（例如一个数组） | 折叠只认对象 |
| 未知事件类型 | **跳过不认识的事件会丢状态，而丢状态的表现只是 `head()` 变 `None`** |
| `register` 缺必需字段 | 缺 `version` / `base_model` / `adapter_sha256` 都构不成一条记录 |
| `stage` 指向不存在的版本 | 说明索引被手工改坏过，此时继续折叠只会产生更深的错 |

### 3.3 幂等 ≠ 宽松

`register` 只在**三元组键与版本号都相同**时幂等（CI 重跑同一个任务正是
这种情形），且幂等命中时**不写重复事件**——重复写会让索引膨胀，而语义上
什么都没发生。实测两种冲突：

```text
非法迁移被拒：非法状态迁移 stable → candidate（1.0.0）；允许的目标：archived, rolled_back
版本号冲突被拒：版本号 1.0.0 已属于键 abef9265dd96544e（…），不能再给键 9a8b309ccd09837f 使用；
              版本号是人写的叙事，两份不同产物写同一个号是常有的事，静默覆盖会让索引少掉一份真实产物
  幂等重登记：1.0.0
```

把幂等放宽到"版本号相同就覆盖"是危险的：**版本号是人写的叙事**，
两个人给两份不同的产物写同一个 `1.2.0` 是常有的事。因此"版本号相同但
键不同"必须报冲突，而且冲突信息里要给出**具体哪些字段不同**
（`VersionConflict.fields`）——只报 "conflict" 的话，运维唯一的动作就是去翻文件。

### 3.4 一个在测试里第一次跑就暴露的缺陷

第一版的 `ModelRegistry` 有两个填充 `_events` 的入口不一致：

- **读盘折叠**（`_fold`）会 append 到 `_events`；
- **写入追加**（`_append`）只写文件，**不更新内存镜像**。

于是同一份操作序列出现两个答案：

```text
重载后的 events()      有 3 条
写入方的 events()      有 0 条
```

这不是"小瑕疵"：`events()` 是**审计流唯一被消费的地方**（报告与 demo 都读它），
而"写入方看不到自己刚做的事"会让任何基于审计的断言形同虚设。
修法是把两条路径统一到同一个 `_append`（写文件 + 追加镜像），
并把这条结论写成 `test_reload_rebuilds_identical_state` 里的
`断言 reloaded.events() == registry.events() == 3 条`。

> 可以带走的判断：**当同一个概念有两条写入路径时，先问"它们会不会不一致"，
> 再问"不一致时谁会报错"。** 这个缺陷不报错、不告警，只让一份审计流安静地空掉。

### 3.5 四态流转与两条被禁止的边

```text
             register                 promote              prune
（无）──────────────→ candidate ──────────────→ stable ──────────→ archived
                          │                        │
                          │ 回滚 / 拒绝              │ 回滚（退位）
                          └──────────┬─────────────┘
                                     ▼
                                rolled_back
```

| 被禁止的迁移 | 允许后的后果 |
|--------------|-------------|
| `stable → candidate` | `head()` 突然返回 `None`，而线上还在跑它；部署脚本大多按"head 一定存在"写 |
| `rolled_back → stable` | 回滚可以被撤销，审计就失去意义——要复活必须**重新登记**（新的适配器哈希 → 新的键 → 新的记录） |
| `archived → 任何` | 终止态。归档是"退出保留窗口"，不是"暂停" |

`stable → archived` **是允许的**，但 `prune()` 刻意不去做它：

> **`prune` 只清理候选：`stable` 是回滚目标，归档一个 stable 版本等于删掉一条退路。**

要下线一个 stable 版本，必须显式走 `rolled_back` 或 `archived`——那是一次
有理由的运维动作，而不是磁盘清理的副作用。

## 第四章：采纳判定 —— 阈值、死区与"不可比"

### 4.1 三个动作必须分开

```text
拒绝候选（hold）    候选不如当前 → 什么都不发生，当前版本继续服务
采纳候选（promote） 候选明显更好 → 候选升为 stable，成为新的 head
回滚（rollback）    当前版本出问题 → 退回到最近一个 stable 祖先
```

**"拒绝候选"与"回滚"必须分开**，理由是它们从触发者到后果全都不一样：

| | 拒绝候选 | 回滚 |
|---|---|---|
| 触发者 | 离线评估（还没上线） | 线上事故（已经上线） |
| 对象 | 新候选 | 当前生产版本 |
| 后果 | 什么都不发生 | 生产版本换人，有服务窗口 |
| 能否"改回去" | 不需要，本来就没换 | 不能——回滚本身要被审计 |

把两者混成一个 `if score < threshold: revert()`，会把"候选没通过评估"
变成"把线上版本也退掉"，而后者的代价远大于前者。

### 4.2 七个场景（全部实测）

| 场景 | action | gain | 拦在哪一项 |
|------|--------|------|-----------|
| 首次上线（无 current，0.58） | **promote** | 不可比 | 绝对值门槛：`0.58 >= 0.5` |
| 增益达标 +0.12 | **promote** | +0.1200 | —— |
| 落在死区 +0.01 | hold | +0.0100 | `gain < min_gain (0.02)` |
| 退步 -0.08 | hold | -0.0800 | `CHECK_GAIN` 不通过 |
| 候选缺分数 | hold | 不可比 | `CHECK_METRICS` 不通过 |
| 候选超龄 21 天（504h） | hold | +0.2000 | `CHECK_AGE` 不通过（上限 168h） |
| 候选缺合并产物 | hold | +0.2000 | `CHECK_DEPLOYABLE` 不通过 |

三处设计要点：

1. **首次上线必须是一个单独的分支**。没有任何 stable 版本时增益无从计算，
   若与"有当前版本"共用一条路径，第一版**永远上不了线**（`gain` 是 undefined，
   任何与 `min_gain` 的比较都没有意义）；
2. **超龄候选的 gain 照算照报**。"它明明更好，为什么没换"必须能从报告里
   一句话回答——那是时效检查，不是增益检查；
3. **可部署性检查排在最前**。它是唯一一条"证据完整性"检查：分数再高也
   不能上线一个没有产物的版本。

### 4.3 两个数字：死区与退步容忍

- `min_gain=0.02` 是**采纳门槛**，也是死区：模型评估有方差，±0.02 的波动
  是噪声不是提升（day027 的趋势判定用的是同一个思想，那时取 0.05）。
  **没有死区，自动流水线会天天在不同版本之间来回切**；
- `regression_tolerance=0.0` 是**退步容忍度**：缺省意味着"任何退步都拒绝"。

两个数字都必须在报告里被打印出来——**一个没有写出阈值的判定，无法被复核**。
「落在死区」的检查通过（`+0.01 >= 0`）但决定是 hold，理由写在 `reason` 里：

```text
■ 落在死区 +0.01 → hold（gain +0.0100，可比 True）
    [通过] gain: 实际 0.01 / 阈值 >= -0.0 —— 增益 +0.0100未达到采纳门槛 0.02
  结论：增益 +0.0100 落在死区（< 0.02）：评估方差量级内不值得切换生产版本
```

### 4.4 不可比时拒绝算差值（本课的反面教材）

`version.comparable` 定义了"两个版本的效果可否直接比较"：**基座相同 +
数据集指纹相同**。实测同一对版本在两种策略下的判定：

```text
缺省（require_comparable=True）: action=hold gain=未计算
  被拦下：不可比且未达绝对门槛：候选 0.4400 < 0.5
关掉可比性要求               : action=hold gain=-0.1600
  被拦下：增益 -0.1600未达到采纳门槛 0.02；本次差值不可作为提升证据
```

那个 **-0.1600** 既不是提升也不是退步，而是**两种评估分布之差**
（当前 0.6000 在数据集 A 上、候选 0.4400 在数据集 B 上）。它被算出来之后
会被下游当成提升量使用——这正是 day057 那句"同一份数据在两套口径下得到
两个结论，是数据治理最忌讳的事"的另一种形态：

> 把跨分布的差值当成提升量，等于**用一个口径的数字去解释另一个口径的现象**。

因此缺省策略下 `comparable=False` 的候选**改用绝对值门槛**
（`absolute_min_pass_rate=0.5`），`gain` 字段如实返回 `None`。
`require_comparable` 这个开关保留下来，只为让上面那段反面教材可以被实测。

### 4.5 `CHECK_COMPARABLE` 是信息项，不是阻塞项

可比性检查的 `passed` **恒为 True**，它只决定走哪条判定分支。为什么不把它
做成"不可比就拒绝"？因为**不可比不是候选的错**——换数据集本来就是持续微调的
常态，而那样写会让每一次数据更新都变成一次上不了线。

对应地，`CandidateDecision.comparable` 记录的是**事实上的可比性**
（而不是"走了哪条分支"），这样报告里"不可比但按绝对门槛采纳"这件事
是显式可见的。

## 第五章：触发器与否决项 —— 两类东西

### 5.1 为什么不是"每天夜里训一次"

定时任务式的持续微调有三个具体代价：

1. **算力浪费**：数据一天没变，训出来的适配器哈希与上一版几乎相同，
   而评估、门禁、部署检查一样都不能省；
2. **版本表被噪声灌满**：每天多一个版本，回滚目标的选择空间被稀释，
   "哪一版是好的"越来越难回答；
3. **评估方差被当成信号**：评估有 ±0.02 的噪声（day027 的死区），
   天天换版本等于天天在噪声上做决策。

于是今天的任务是：把"该不该训"做成一份**可核对的判断**，而不是
`if now - last > 1h`。

### 5.2 触发器（trigger）与否决项（veto）

```text
trigger：有一个理由支持训练      veto：有一个理由禁止训练
should_retrain = any(trigger.fired) and not vetoed_by
```

条件表由 `trigger_table()` 生成，与实现同源：

| 类别 | 名称 | 阈值 | 含义 | 复核时机 |
|------|------|------|------|---------|
| trigger | `data_growth` | 8 | 自上次训练以来新增的可用样本数达到门槛 | 数据流水线跑完一轮之后 |
| trigger | `dataset_change` | 指纹与生产版本不同 | 数据集被重建（换了清洗口径或补了样本） | `manifest.fingerprint` 更新之后 |
| trigger | `quality_drop` | 0.5 | 线上观测到的合格率低于下限 | 线上评估窗口结束之后 |
| veto | `cooldown` | 24.0 | 距上次训练不足冷却期（**从未训练时不否决**） | 每次判定 |
| veto | `active_run` | 1 | 已有训练任务在跑（两个任务写同一份产物目录会互相覆盖） | 每次判定 |

**为什么不能把 veto 写成"触发器的反向条件"**（例如再加一个
`cooldown_passed` 要求它 fired 才算数）？因为报告里就分不清这两行：

```text
fired = []                            → 没有理由训练        （去看数据与线上评估）
fired = [数据涨了] vetoed_by=[冷却]   → 有理由但时机不允许   （只需要等）
```

判定实测（demo 第 6 节）：

```text
[训练]   首次训练（从未训练，全部样本都算新增）    命中 data_growth
[训练]   数据涨 30 条、冷却已过                    命中 data_growth, dataset_change
[不训练] 数据涨 30 条、冷却只过了 2h               命中 data_growth, dataset_change；否决 cooldown
[训练]   数据没涨、线上掉到 0.42                   命中 quality_drop
[不训练] 数据没涨、线上也没掉                      无命中
[不训练] 已有训练任务在跑                          命中 data_growth…；否决 active_run
```

第三行是这套设计存在的全部理由：`fired` 与 `vetoed_by` **同时非空**。

### 5.3 缺失一律"不触发、不否决"

- `online_pass_rate=None`（还没跑线上评估）→ **不**触发质量下降；
- `hours_since_last_train=None`（从未训练）→ **不**否决冷却期。

这与 `ModelVersion.pass_rate` 返回 `None` 是同一条纪律：**缺失与 0 是两件事**。
把缺失当 0 的后果可以精确地算出来：

```text
hours_since_last_train = None → 当成 0 → 0 < 24 → veto
```

于是"从未训练过"的新仓库会被冷却期**永久**拦住，而它恰恰是最该训练一次
的那种状态。这也是为什么 `TriggerEvaluation.actual` 允许为 `None`——
"没有观测值"与"观测值是 0"在报告里不能打印成同一个样子。

### 5.4 判定顺序 = 展示顺序

评估顺序固定为三个触发器 → 两个否决项，与 `render_markdown()` 的展示顺序
逐项一致。**报告的顺序与代码的顺序不同，是最容易让"读报告的人"与
"改代码的人"对不上的一种漂移**，所以它被一条用例钉住
（`test_evaluation_order_is_triggers_then_vetoes`）。

## 第六章：回滚计划 —— 第一步是"确认有退路"

### 6.1 计划与执行分开

`plan_rollback` 只**产出计划**，不做任何副作用。这不是偷懒：

> **回滚必须先被看见再被执行。** 把计划打印出来给人确认，
> 是唯一能在"自动回滚把好版本也退掉"这类事故前踩到刹车的做法。

实测（demo 第 7 节）：

```text
rollback | 1.0.2 → 1.0.1 | 4 步（阻塞 2） | 上线后拒答率异常升高
  1. [verify] 校验目标 v1.0.1（键 55bc9fa9f8952a71）产物齐全：适配器=True, 合并模型=True（阻塞）
  2. [freeze] 把 v1.0.2 置为 rolled_back（head() 会自动落回上一个 stable，无需反向改写目标版本）（阻塞）
  3. [record] 写入审计事件：原因「上线后拒答率异常升高」（非阻塞）
  4. [observe] 按 24.0h 观察窗口监控 v1.0.1（非阻塞）
```

### 6.2 顺序即策略（第四次复用）

**`verify` 必须在 `freeze` 之前。** 反过来写也能通过绝大多数测试，
代价只在最坏情况下暴露：

> 先冻结当前版本、再发现目标版本不可部署，结果是**生产上没有任何可服务版本**。

这与 day046 的六阶段、day057 的六阶段是同一种推理方式：每一步的位置都有
理由，换位只在某些输入下才出错——**而那种错误最难在测试里被发现**。
所以它被写成代码里的固定顺序，并有一条断言直接钉住
`[step.action for step in plan.steps] == [verify, freeze, record, observe]`。

### 6.3 回滚不需要"改回去"

一个值得单独说的设计：回滚**不需要反向改写目标版本**。因为
`head()` 的定义是"最新的 stable"，把出问题的版本退出 stable 态，
它就自动落回上一个 stable。

这比"维护一个当前版本指针 + 再把它改回去"少一个状态，而少的那一个状态
恰好是最容易出错的（两个指针不同步时，谁也说不清线上跑的是哪一版）。

### 6.4 三种情形与两处边界

| 情形 | 结果 |
|------|------|
| 三个 stable，退到 v1.0.1 | rollback，4 步（阻塞 2） |
| 只有首个 stable | hold，0 步，`should_execute=False` |
| 最近的祖先不可部署 | rollback 到 v1.0.0（**跳过**不可部署的 v1.0.1） |

两处边界的理由：

- `stable_ancestors` **跳过不可部署的祖先**：一个 `stable` 记录可能只是
  "当年提升过"，它的磁盘产物早被清理；把回滚目标选成它，
  等于计划了一个**必然失败**的动作；
- `apply_rollback` **拒绝执行 `hold` 计划**：一个 hold 计划被误执行，
  等于"在没有目标的情况下把生产版本退掉"——这是本模块能造成的最大伤害，
  所以在唯一有副作用的入口拦一次。

```text
hold | 1.0.0 → （无目标） | 0 步（阻塞 0） | v1.0.0 没有可部署的 stable 祖先（祖先 0 个，可部署 0 个）：
     回滚目标必须是一个真的能兜住流量的版本
should_execute=False steps=0
```

**"没有退路"必须是一个被输出的结论，而不是一个被吞掉的异常。**

## 第七章：六步流水线 —— 把五件事串起来

### 7.1 申报理由（顺序即策略）

```text
verify_data → train → evaluate → gate → register → promote
```

| 顺序 | 换位后的后果 |
|------|-------------|
| `verify_data` 在最前 | 先花完算力再发现数据没变——这正是触发器要防的事，但触发器看的是**调用方报上来的状态**，可能与磁盘上的数据不一致 |
| `evaluate` 在 `gate` 之前 | 门禁是对评估结果的判定，没有结果就没有判据（只能得到一个"用空指标通过的门禁"） |
| `gate` 在 `register` 之前 | 没通过门禁的候选进表会让版本表堆满"登记了但永远不该上线"的记录，而 `lineage` 会开始被污染（它不看阶段） |
| `promote` 在 `register` 之后 | 反过来会出现"生产指针指向注册表里还没有的版本"，而回滚依赖注册表找祖先 |

### 7.2 先登记为候选、再按判定提升

这与"训练脚本自己把结果标成 stable"只差一行，但差别很大：

- 候选阶段让 `head()` 保持不变，**上线是一个显式的、有记录的动作**；
- 采纳判定拿到的 `current` 与 `candidate` 都是注册表里的正式记录，
  没有"半登记状态"；
- 门禁不通过时注册表里留下的是 `candidate`，**回滚链上一个都没多**。

一个自然会被问到的反问题：**门禁没通过为什么还要登记？** 三个理由：
① "这次训练产出了什么"本身是需要留档的事实；② 下一次可以用同一份产物
重跑门禁（换策略、等人工复核），不必重新训练；③ 候选阶段不影响任何
已有行为，`head()` 与回滚链都不看它。

### 7.3 端到端实测

```text
第一次真实运行：应该重训 | 命中触发器 data_growth, dataset_change | 计划 v1.1.0 | 已训练 True | 生产版本 1.1.0
    [OK] decide       应该重训 | 命中触发器 data_growth, dataset_change
    [OK] plan         计划 v1.1.0（minor，父 1.0.0）| 基座 Qwen3-8B | 数据 aa77c31e90f4b258 | 6 步
    [OK] verify_data  数据集指纹已核对：新增样本 30 条，指纹已变化
    [OK] train        适配器 sha256:5c6d7e8f9012 | step 42 | loss 0.3187
    [OK] evaluate     指标 {'eval_pass_rate': 0.7222, 'train_loss': 0.3187}
    [OK] register     v1.1.0 candidate   键 14dceb829e28ce44 ← 1.0.0 | 合格率 0.7222 | 产物 2/3 | 可部署 True
    [OK] gate         promote | 当前 1.0.0 → 候选 1.1.0 | gain 不可比 | 目标 1.1.0
    [OK] promote      v1.1.0 提升为 stable，观察窗口 24.0h
  head 现在是 1.1.0，trainer 调用次数=1

第二次运行（同一份数据、同一个适配器）：… | 已训练 True | 生产版本 1.1.0
  登记的版本号 1.1.0 | 版本表规模 2
  trainer 调用次数=2
```

第一次运行里 `gate` 那一行写着 **gain 不可比**：当前版本用的是数据集 A、
候选用的是数据集 B，因此走的是"不可比 → 绝对门槛"分支
（`0.7222 >= 0.5`）。这不是跑错了——它恰好演示了 4.4 节那条设计。

### 7.4 第二次运行：三件事的合成

第二次运行同一份状态，结果里有三个值得分别讲清的点：

1. **三元组相同 → 复用版本号**（`1.1.0`，不新占一个）。这正是 CI 重试
   应有的行为；
2. **训练回调仍被调用一次**（`trainer 调用次数=2`）。流水线无法预知
   "这次训练会产出什么"——它只知道输入，不知道权重；
3. **复用时若该版本已处于 stable，跳过采纳判定。**

第 3 点是我实现时**实测出来的一个缺陷**。第一版没有这个短路，
第二次运行的报告写着 `生产版本（未采纳）`——因为此时 `current` 与
`candidate` 是同一条记录，`gain = 0.7222 - 0.7222 = 0.0000`，
任何正的 `min_gain` 都会判 hold，而那个 hold 把"它正在服务"这个事实
说成了"未采纳"。

修法是两层：

```python
if existing is not None:
    outcome.version = existing
    if existing.stage == STAGE_STABLE:
        # 复用 + 已上线：不再做采纳判定（同一条记录，gain 恒为 0）
        return outcome

@property
def promoted(self) -> bool:
    """运行结束时，本次产出的版本是否处于 stable."""
    return self.version is not None and self.version.stage == STAGE_STABLE
```

`promoted` 因此定义为**"运行结束时该版本是否处于 stable"**，
而不是"本次判定是否 promote"——用阶段定义，两条路径给出同一个答案；
用判定定义，重跑会得出一个误导性的结论。

> 可以带走的判断：**当一个布尔量的两种定义在正常路径下等价、在重跑路径下
> 分岔时，选那个不需要额外解释的定义。**

### 7.5 回调契约与两条闸门

训练与评估是**注入的回调**（`Trainer` / `Evaluator` 两个 `Callable` 类型别名），
流水线不持有任何模型：

```python
def trainer(plan: RetrainPlan) -> dict:      # 至少返回 adapter_sha256
def evaluator(artifacts: dict[str, str]) -> dict:  # 至少返回 eval_pass_rate
```

- 训练回调缺 `adapter_sha256` 会**立刻报错**：没有它就算不出版本键，
  而版本键是这条记录的身份证。返回的 `artifacts` 里未知槽位被静默丢弃
  （不写进记录的 `artifacts`）；
- `verify_data` 是**第二道闸门**：它在触发器已经判定"应该训练"之后
  仍然可以否决训练。两条判据是"数据指纹不能为空"（硬约束）与
  "数据没变却要训练必须有理由"（质量下降触发的同数据重训是合法的，
  理由会写进时间线）。

这里有一个实现细节值得单独记：`verify_data` 第一版是流水线的私有方法，
但**它的 `raise` 分支在端到端路径上根本走不到**——触发器已经把这类状态
挡在外面了。一个永远走不到的 `raise` 既拿不到覆盖率，也没人会发现它的
条件写反了。因此它被提成模块级函数 `verify_data(state, decision)`，
可以被单独驱动。

## 第八章：接入 API 与落盘

### 8.1 五个端点，一个共同的取舍

| 端点 | 方法 | 回答什么 |
|------|------|---------|
| `/registry/layout` | GET | 身份怎么算、号怎么涨、状态怎么流转、六步顺序（自我描述） |
| `/registry/versions` | POST | 折叠一批版本记录 → 阶段分布 + 当前生产版本 + markdown |
| `/registry/candidate/evaluate` | POST | 要不要把候选提升为生产版本（逐项检查） |
| `/registry/triggers/evaluate` | POST | 现在该不该训（含条件表） |
| `/registry/rollback/plan` | POST | 回滚计划（有序动作序列 + 版本链） |

五个端点**全部只读或纯计算**：不写磁盘、不联网、不调模型、不用随机数，
因此同一个请求体永远得到同一个响应。

**版本表的写入不进 HTTP**。请求体带**全量版本记录**，服务端只做折叠与判定。
理由是具体的：版本表的写入在"多副本部署"下无法保证"谁先写"，
而一个写入竞争下的注册表会产生两份互相矛盾的"当前生产版本"。
把写入留给流水线与脚本（单点），把读取与判定留给 HTTP（可水平扩展）。

### 8.2 `layout`：文档与实现同源

`/registry/layout` 的每一个字段都从代码常量现场读出：

```text
transitions       ← ALLOWED_TRANSITIONS
plan_steps        ← PLAN_STEPS + STEP_MEANINGS
trigger_conditions← trigger_table()
promotion_policy  ← settings.retrain_*
```

因此"文档说 `stable` 可以退回 `candidate`、代码里不行"这类漂移会在接口上
一眼看出来。这与 day057 的 `/data/domain/dimensions` 是同一个取舍。

### 8.3 错误码语言：400 与 422 的分工

| 情况 | 错误码 | 例子 |
|------|--------|------|
| **请求形状**不对 | 422 | `new_examples: -1`（Pydantic `ge=0`）、`versions: []`（`min_length=1`）、`observe_window_hours: 0`（`gt=0`） |
| **业务规则**不允许 | 400 | 非法版本号 / 非十六进制哈希 / 未知阶段 / 悬空父版本 / 非法策略阈值 |

这条分工与 day050~day057 一致。**刻意不在 Pydantic 上复制业务规则的区间**：
复制出来的第二份规则会漂移，而且会把"参数不合法"从 400 变成 422。

## 第十章：今日总结 —— 三条工程线索

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|---------|
| 三元组内容寻址 | 键相同 ⇒ 行为逐位相同；自增号给不了这个保证 | `version.version_key` |
| 归一化 + 十六进制校验 | 抄哈希的三个坑（空白/前缀/大小写）会让同一产物有两个键 | `version.normalize_digest` |
| 变化的那一项决定递增位 | 重训是最高频动作，不能让它涨大版本 | `version.bump_kind_for` |
| 事件流 + 折叠 | 覆盖写会丢掉"什么时候变的、为什么变" | `store.ModelRegistry` |
| 幂等只覆盖"键与号都同" | 版本号是人写的叙事，静默覆盖会少掉一份真实产物 | `store._insert` |
| 五类损坏各自报错 | 跳过不认识的事件会丢状态，而丢状态只表现为 `head()` 变 None | `store._fold` |
| `prune` 只清候选 | stable 是回滚目标，归档它等于自断退路 | `store.prune` |
| 拒绝候选 ≠ 回滚 | 触发者、对象、后果都不同；混写会把"候选没过评估"变成"线上也退掉" | `rollback` 模块 |
| 不可比不算差值 | 跨分布的差值会被下游当成提升量 | `evaluate_candidate` 分支 B |
| 死区 0.02 | 评估方差是噪声，自动流水线不能对噪声过敏 | `PromotionPolicy.min_gain` |
| 触发器与否决项分开 | "没有理由"与"时机不允许"的运维动作完全不同 | `triggers.evaluate_triggers` |
| 缺失 ≠ 0 | 把 None 当 0 会让新仓库被冷却期永久拦住 | `TriggerState` 可空字段 |
| `verify` 在 `freeze` 之前 | 回滚不可逆，第一步必须确认有退路 | `plan_rollback` |
| `hold` 计划不可执行 | 误执行等于在没有目标时把生产版本退掉 | `apply_rollback` |
| 六步顺序 | gate 前置于 register、promote 后置于 register | `retrain.PLAN_STEPS` |
| `promoted` 用阶段定义 | 复用已上线版本时判定路径根本不执行 | `RetrainOutcome.promoted` |
| 写入不进 HTTP | 多副本下"谁先写"无法保证，版本表写入必须单点 | `api/routes.py` |

今天埋下的伏笔：

- **实验追踪**：现在的指标散在 `ModelVersion.metrics` 与各阶段的报告里，
  day059 会把它们收进一个追踪器（实验参数、指标、产物的统一记录）；
- **流水线集成**：今天的手动/脚本触发会在 day059 变成一条端到端 MLOps
  流水线，并接入 GitHub Actions；
- **模型卡**：`ModelVersion` 已经有产出模型卡所需的全部字段
  （三元组、指标、父版本、产物路径），day059 会把它渲染成一份交付文档。
