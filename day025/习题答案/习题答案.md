## 一、选择题

### 第 1 题：B

**解析**：

- **A 错**。LLM 是概率模型，temperature > 0 时同一输入每次输出都可能不同；"一次通过"不构成统计意义上的证据。
- **B 对**。这正是教程第一章的核心结论：输入空间开放（任意自然语言，无法穷举）+ 正确性判定可能模糊（"答案对但说法不同"），所以只能用有代表性的样本集 + 明确的打分规则 + 统计汇总去逼近真实表现。
- **C 错**。单元测试验证的是"代码逻辑对不对"（解析器、工具调用、数据结构），验证不了"模型表现好不好"。两者是 pytest 与 Harness 的分工，缺一不可。
- **D 错**。数据集不是越大越好——人工标注全量流量成本不可行，且无代表性的大数据集不如小而精的分层样本。评估数据集的关键是**代表性**与**可维护性**，不是体积。

### 第 2 题：B

**解析**：回答里每个事实都正确（法国确实位于西欧、是欧盟创始国），但**没有回答问题**。这是教程 2.3 节举的原例：正确性维度通过，相关性维度失败。这个区分的工程意义在于优化手段不同——正确性问题改模型/知识，相关性问题改提示词/检索；如果两个维度混在一起统计，看到"失败"也不知道该修哪里。

- A 错：陈述内容本身没有事实错误。
- C 错：没有泄露提示词、有害内容或危险操作。
- D 错：与成本无关。

### 第 3 题：B

**解析**：score（0.0~1.0 连续值）与 passed（布尔判定）承载不同信息。纯布尔结果会丢失"0.9 分没过"和"0.1 分没过"之间的差别——前者提示系统差一点就达标，调一版提示词可能就过；后者说明方向性错误。连续分数保留了**改进趋势信号**，布尔判定服务于**"这条算不算过"的决策**（比如红队用例的一票否决）。

- A 错：两个字段都存储、都展示，格式差异不是设计动机。
- C 错：Harness 与 pytest 是互补关系而非兼容关系，passed 不是为 pytest 准备的。
- D 错：多一个布尔字段的内存开销可以忽略，不是设计考量。

## 二、判断题

### 第 4 题：错

**解析**：这是教程 3.3 节"分层评估"思想要正面回应的质疑。MockLLM 离线评估是第一层，它验证的是**系统的确定性部分**：Harness 流程本身、ReAct 解析器能否接住该格式的输出、工具调用链是否通畅、scorer 判分是否正确、summary 统计是否准确。这些逻辑如果有 bug，第二层（真实模型离线评估）和第三层（在线评估）的所有结论都建立在坏骨架上，全是垃圾数据。

"先验骨架、再接活模型"：第一层快、免费、绝对确定、可进 CI；它评的不是模型能力，而是**评估机器本身与系统的工程链路**——这恰恰是真实模型评估前必须先保证的东西。

### 第 5 题：错

**解析**：安全性指标与正确性指标存在**不对称性**（教程 2.4 节）。正确性 90% 意味着 10% 的回答不够好——体验下降，可以接受再迭代；安全性 90% 意味着 10% 的攻击成功了——每一次成功都是一次事故（提示词泄露、有害内容外发），没有"大多数时候安全"这种及格线。因此安全用例的评估标准必须逼近 100%，且通常配合更严格的 pass 语义（一票否决），数据集也采用对抗性构造（M3-D6 红队评估专门处理）。

## 三、问答题

### 第 6 题

**参考答案**：

评估报告的价值建立在"同一版本系统 + 同一数据集，跑两次得到同样结论"这条公理上。如果结果不可复现，工程后果是：

1. **信号与噪声无法区分**：今天通过率 80%、明天 75%——你无法判断是代码真的退化了（信号），还是模型采样手气不好（噪声）。没有区分能力，评估数字就不能指导任何决策。
2. **CI 评估 flaky 化**：流水线上的评估一会儿绿一会儿红，团队很快学会忽略红色告警，评估体系名存实亡——比没有评估更糟，因为它提供了虚假的安全感。
3. **版本对比失效**：A/B 两个提示词版本的对比，前提是其他变量全部受控；随机性不冻结，对比结论无效。

MockLLM 冻结的随机性来源（教程 3.2 节的表格）：

- **模型采样随机性**：预设脚本回复，彻底消除 temperature 带来的输出抖动（这是最彻底的一档，连 temperature=0 下 GPU 浮点与批处理导致的微小不确定性也不存在）；
- **网络与外部服务随机性**：无网络、无 API Key，工具返回由脚本/本地代码决定；
- **计时与并发随机性**：评估串行执行，延迟只统计均值、不断言绝对阈值。

### 第 7 题

**参考答案**：

**理由一：状态隔离。** ReactAgent 是有状态对象——`history` 会随着每次 `run()` 累积 ReActStep。如果多条评估用例共用一个 Agent 实例，后面的用例会"看到"前面用例的对话历史，评估结果互相污染，违反了用例独立性（等价于 pytest 的 Independent 原则）。工厂函数让每条用例获得一个全新的 Agent，隔离性由构造过程保证，而不是靠使用者记得"每次用完要清空"。

**理由二：按用例注入依赖。** 工厂签名是 `agent_factory(case)`——它接收用例本身。测试中可以按 `case.id` 给 MockLLM 注入对应的回复剧本（`scripts[case.id]`）；生产中可以按用例的 tag 选择不同配置（比如 safety 用例挂上加固版安全模块）。如果注入的是一个成品 agent，这两种按用例定制的能力都不存在。

这本质上是 day005 依赖注入与 day002 fixture 思想的延续：**注入"构造能力"比注入"构造结果"更灵活**。

### 第 8 题

**参考答案**（任意三条即可）：

1. **可流式处理**：逐行读取解析，不用把整个文件载入内存，数据集涨到十万条也不用担心内存。
2. **单点故障隔离**：某一行 JSON 损坏时，可以精确定位到行号报错（我们的加载器抛 `ValueError(f"第 {line_no} 行 ...")`），而大 JSON 数组中一处损坏会导致整个文件解析失败。
3. **版本控制友好**：每行独立成一条记录，追加用例就是追加一行，git diff 干净、合并冲突少；大 JSON 数组追加一条要动文件结尾的 `]`，diff 噪音大。
4. **追加写入友好**：新用例直接 append 到文件末尾即可，不需要解析-修改-重写整个文件。
5. **生态事实标准**：OpenAI 微调数据、主流评估基准（如 lm-evaluation-harness 的数据集）都用 JSONL，工具链兼容性好。

## 四、编程题

### 第 9 题

**参考实现**（可放在 `smart_research_agent/evaluation/agent_harness.py` 中，与其他 scorer 并列）：

```python
def keyword_scorer(output: str, expected: str) -> float:
    """关键词命中比例打分：expected 用 | 分隔多个关键词，返回命中比例."""
    keywords = [k.strip() for k in expected.split("|") if k.strip()]
    if not keywords:
        return 0.0
    hits = sum(1 for k in keywords if k in output)
    return hits / len(keywords)
```

**解析**：

- `keyword_scorer` 遵守 `Scorer = Callable[[str, str], float]` 签名，因此可以直接作为 `AgentEvalHarness(scorer=...)` 的参数插入——这就是"变化点收敛为一个函数签名"的回报。
- 返回**命中比例**而非全有/全无，保留了"命中一半关键词"的中间信息（score 与 passed 分离设计的应用场景）。
- 空 `expected` 返回 0.0 而不是抛异常：空期望意味着这条用例的 scorer 配置有误，判为失败可以在报告里暴露出来，而不是中断整个评估批次。

**参考测试**：

```python
from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.evaluation import AgentEvalHarness, EvalCase
from smart_research_agent.evaluation.agent_harness import keyword_scorer
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.tools.registry import ToolRegistry


def _harness(script: str) -> AgentEvalHarness:
    def factory(case: EvalCase) -> ReactAgent:
        return ReactAgent(llm=MockLLM(responses=[script]), registry=ToolRegistry())

    return AgentEvalHarness(agent_factory=factory, scorer=keyword_scorer)


class TestKeywordScorer:
    def test_all_keywords_hit(self):
        assert keyword_scorer("法国的首都是巴黎", "巴黎|法国") == 1.0

    def test_partial_hit_returns_ratio(self):
        assert keyword_scorer("首都是巴黎", "巴黎|法国") == 0.5

    def test_empty_expected_returns_zero(self):
        assert keyword_scorer("任意输出", "") == 0.0

    def test_harness_with_keyword_scorer(self):
        harness = _harness("Thought: 直接回答\nFinal Answer: 法国的首都是巴黎")
        result = harness.evaluate(EvalCase(id="c1", input="q", expected="巴黎|法国"))
        assert result.score == 1.0
        assert result.passed is True

        harness = _harness("Thought: 直接回答\nFinal Answer: 首都是巴黎")
        result = harness.evaluate(EvalCase(id="c2", input="q", expected="巴黎|法国"))
        assert result.score == 0.5
        assert result.passed is False  # 默认 pass_threshold=1.0
```

### 第 10 题

**参考实现**（用子类扩展，不改动 `harness.py` 的既有行为）：

```python
"""按 tag 筛选的评估 Harness（习题参考答案）."""

from __future__ import annotations

from smart_research_agent.evaluation.harness import EvaluationHarness


class TagFilteredHarness(EvaluationHarness):
    """在 run() 中按 tag 筛选用例后再评估；不传 tag 时行为与基类一致."""

    def run(self, dataset_path, tag: str | None = None):
        cases = self.load_dataset(dataset_path)
        if tag is not None:
            cases = [c for c in cases if tag in c.tags]
        self.cases = cases
        self.results = [self.evaluate(c) for c in self.cases]
        return self.results
```

**解析**：

- **子类扩展而非修改基类**：`AgentEvalHarness` 继承 `TagFilteredHarness` 即可获得筛选能力，`EvaluationHarness.run()` 的原有签名与行为完全不动——这满足开闭原则，也不会破坏已有的 77 个测试。
- **`summary()` 不用改**：它只统计 `self.cases` / `self.results`，筛选发生在 `run()` 入口，下游统计天然只覆盖被评用例。这是"数据先过滤、流程不变"的管道式思路。
- 也可以实现为独立函数 `run_with_tag(harness, path, tag)`，效果等价；子类版本的好处是能力跟随类型走，调用方不需要记额外函数。

**参考验证代码**（基于 `AgentEvalHarness` 继承 `TagFilteredHarness` 后）：

```python
import json
from pathlib import Path

DATASET = Path("data/eval/sample_eval.jsonl")

harness = AgentEvalHarness(agent_factory=my_factory)  # AgentEvalHarness 改为继承 TagFilteredHarness
harness.run(DATASET, tag="math")
summary = harness.summary()
assert summary["total"] == 3
assert "safety" not in summary["by_tag"]
assert "math" in summary["by_tag"]
```

注意 `math` tag 的 3 条用例都同时带 `calculator` tag，所以 `by_tag` 中会出现 `calculator`，但不会出现只属于 `safety-001` 的 `safety`——这正是断言 `"safety" not in by_tag` 能验证筛选生效的原因。
