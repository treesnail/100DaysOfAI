## 第二章：主线一 —— 输出端控制：从"提示词求格式"到"协议保证格式"

### 2.1 day036：Prompt 工程 —— 提示词是一等工程制品

**一句话本质**：提示词不是"发给模型的文案"，而是可版本化、可回归、可审计的**工程制品**。

day036 的落点（源码见 [../../day041/源码/smart-research-agent/smart_research_agent/agent/](../../day041/源码/smart-research-agent/smart_research_agent/agent/)）：

- **`agent/techniques.py`**：`zero_shot()` / `few_shot()` / `chain_of_thought()` / `tree_of_thoughts()` 四个 message 构造器——它们是"纯函数"，只组装 messages 不碰 LLM，因此离线测试只需断言"构造出来的 prompt 长什么样"。CoT 是"把计算摊到生成过程里"，所以 `chain_of_thought` 的输出以 `zero_shot` 开头再接引导语；ToT 的分支必须用不同探索视角，否则搜索退化为瞎试。
- **`agent/prompt_library.py`**：`PromptTemplate(name, template, version, changelog, created_at)` + `PromptLibrary`。这是 day026 `PromptEvaluator` 的自然延伸——既然要评估提示词谁更好，就得先让提示词有版本、有变更记录可对比。`render()` 用正则 `\{([a-zA-Z_][a-zA-Z0-9_]*)\}` 解析变量、缺失变量抛 `PromptRenderError`：**宁可在渲染时失败，也不要把缺变量的有损提示词发给模型浪费 token。**
- **`agent/prompts.py`**：`REACT_SYSTEM_PROMPT_V1/V2` 迁移进 `PromptLibrary`（day026 的 era 遗留文本协议），`build_default_prompt_library()` 生成默认库。

**Few-shot 的边界要拎清**：它校准的是**格式与风格**，不是**知识**——给 2 个正确例子不等于教会模型"算对"。这是 day036 最常见的误区源头。

### 2.2 day037：Function Calling —— 从"求"到"保证"

**一句话本质**：让模型用结构化 `tool_calls` 协议表达工具调用，把格式正确性从**提示词求来的概率性**变成**协议保证的确定性**。

day036 之前，ReAct 依靠提示词把输出约束成 `Thought/Action/Observation` 文本块，再由解析器容错识别——工具名写错、参数带噪声、格式违例都要层层兜底。day037 换成原生函数调用接口，落点（[../../day041/源码/smart-research-agent/smart_research_agent/llm/function_calling.py](../../day041/源码/smart-research-agent/smart_research_agent/llm/function_calling.py)）：

- **`FunctionSpec.from_tool(tool)`**：直接从 `BaseTool` 的 `name/description/parameters` 生成 OpenAI 函数的 schema——**schema 与工具实现同源，永不漂移**（改工具不用改两处，这是依赖倒置的又一次回报，day004/day005 埋的线）。
- **`specs_from_tools(tools)`**：一批工具批量转规格，交给 `chat_with_tools`。
- **`parse_tool_calls(response) -> list[ToolCall]`**：解析 OpenAI 兼容的 `tool_calls` 数组；`ToolCall(id, name, arguments)`，`arguments` 兼容 JSON 字符串或已解析 dict。
- **`validate_arguments(spec, arguments)`**：实现 JSON Schema 子集——`required` + `type`（`_TYPE_MAP`: string→str、number→int/float、integer→int、boolean→bool、array→list、object→dict）。`bool` 有一个隐藏坑：`isinstance(True, int)` 为真，但 JSON Schema 里 boolean 与 integer/number **互不相容**，必须特判。校验失败抛 `SchemaValidationError`。
- **三类错误**：`SchemaValidationError`（参数不合规）、`UnknownToolError`（模型点了个不存在的工具）、`ToolExecutionError`（工具执行失败）——统一继承 `ToolCallError`，`kind` 字段用于分类处置。
- **`FunctionCallingAgent`（`agent/fc_agent.py`）**：与 ReAct 等价但用 `tool` 角色消息回填执行的观察，`_execute` 返回 `(结果, 是否失败, 是否占重试预算)` 三元组；连续失败超过 `max_retries`（默认 2）终止，一次成功清零。坏 JSON 降级为 **user 消息反馈**而非 tool 消息——tool 消息必须与调用配对，降级 user 避免协议错位。
- **`MockLLM.chat_with_tools(tool_call_responses=[...])`**：离线脚本化模拟，`{"tool_calls": [...]}` 表示调工具、`{"content": "..."}` 表示直接答，返回前统一规整为 OpenAI 兼容格式（arguments 序列化、补 id/type）。

**为什么两件套要连着看**：day036 的 `PromptLibrary` 管"怎么问"，day037 的 `FunctionCallingAgent` 管"模型怎么表达工具调用"。前者是内容与知识层的管理，后者是协议层的保证——**两者正交，缺一不可**。而"输出给解析器看的调用"天然要求低温：day033 的采样推论在 day037 落地为"function calling 用 temperature=0"，让 `tool_calls` 格式稳定可解析。

## 第三章：主线二 —— 服务化：从脚本到可被调用的系统

### 3.1 day038：FastAPI 服务搭建 —— 进程边界与 API 契约

**一句话本质**：把 Agent 从脚本形态升级为 HTTP 服务——进程边界、并发受理、**可机器校验的契约**。

新增硬依赖 `fastapi==0.141.1`、`uvicorn==0.52.4`（见 [requirements.txt](../../day041/源码/smart-research-agent/requirements.txt)），落点（[../../day041/源码/smart-research-agent/smart_research_agent/api/](../../day041/源码/smart-research-agent/smart_research_agent/api/)）：

- **`create_app(llm, agent_factory, models, embedding)`**：工厂模式 + 依赖注入。Agent 是**工厂**而非实例——**Agent 持有单次任务状态，不能跨请求复用**，所以注入的是"造新 Agent 的工厂"。
- **`routes.py` 依赖**：`get_llm/get_models/get_agent/get_embedding/resolve_model`。`resolve_model` 负责"不点名走默认、点名且存在就走对应客户端、未命中抛 404"。
- **`schemas.py` 契约**：`ChatRequest(message 最小 1 字符, temperature 默认 0.7 范围 [0,2])`、`AgentRunRequest(task, max_steps 默认 10 范围 [1,50])`、`AgentRunResponse(answer, steps, tool_calls)`、`ToolCallRecord(name, arguments, result, success)`、`ErrorResponse(detail, error_type)`。
- **错误码语义**（整个 M4 后续接口沿用的契约语言）：请求不合法 → **422**；合法但资源不存在（如点了不存在的模型）→ **404**；全局未捕获 → **500** 统一 `ErrorResponse`。
- **同步/异步的坑**：同步阻塞代码进 FastAPI 必须用 `def`（FastAPI 自动丢线程池）；硬塞进 `async def` 会**冻结事件循环**、拖垮整个进程。`response_model` 不只是文档，它还会过滤与序列化返回值。

`TestClient` 基于 httpx、不监听端口，所以全部接口测试**3 秒内跑完**——离线可测是服务化的前提。

### 3.2 day039：流式输出与多模型路由 —— 感知性能 × 自动选型

**一句话本质**：流式解决的是**感知性能（TTFT）**，路由解决的是**自动选型**；两者正交，可叠加，分别提升体验与成本。

- **流式**：`BaseLLM.stream()` 默认退化为整段 `yield self.chat(...)`（向后兼容），`MockLLM.stream()` 按 `_CHUNK_SIZE=4` 切分模拟增量，`OpenAICompatibleLLM.stream()` 走 OpenAI `stream=True`。API 层 `POST /chat/stream` 用 FastAPI 内建 `StreamingResponse(media_type="text/event-stream")`，头部 `Cache-Control: no-cache`、`X-Accel-Buffering: no`；SSE 约定 `data: {"delta": "..."}` 逐片下发、`[DONE]` 结束。
  - **流式不改变内容正确性**，只改变用户感知到的首字延迟；它适配纯文本对话，而 function calling 与 Agent 轨迹不适合流式（中途降级会"重头再来"——day039 明确简化为降级时换模型重新生成）。
- **路由**：day033 的 `ModelRouter` 从"只能 chat"升级为 `BaseLLM` 的完整替身（`stream`/`chat_with_tools`/`get_model`/`supports_vision` 全部补齐）；`ChatRequest` 新增 `model` 字段允许显式点名，`GET /models` 暴露可用清单。降级链依然**向上**（偏强模型、偏多花钱一侧），因为"答错"的代价永远大过"多付一次费"。

**为什么这两件更总要连着看**：day038 解决了"能不能被跨进程调用"，day039 在已有的工厂与依赖注入之上叠加"流式 + 选型"，没有推翻一行服务层代码——**服务化的价值正是让上层能力可以逐个叠加。**

## 第四章：主线三 —— 输入模态的语义化：从文字到图像与向量

### 4.1 day040：多模态输入 —— 图像进入 content 部件

**一句话本质**：图像以 **data URL 内嵌在 content 部件数组**里进入模型，通过"校验 → 编码 → 组装"三道工序接入。

落点（[../../day041/源码/smart-research-agent/smart_research_agent/multimodal/image.py](../../day041/源码/smart-research-agent/smart_research_agent/multimodal/image.py)）：

- **`validate_image(data)`**：用 **magic bytes** 识别真实 MIME（PNG/JPEG/GIF87a/GIF89a/WebP），**不信任文件扩展名**；顺序为"空 → 超限 → 类型"。上限 `MAX_IMAGE_BYTES = 10 * 1024 * 1024`；`EmptyImageError`/`ImageTooLargeError`/`UnsupportedImageTypeError` 三类异常。
- **`build_data_url(data, mime)` + `build_vision_payload(prompt, image_data_url)`**：组装 `[{"type":"text","text":prompt}, {"type":"image_url","image_url":{"url": data_url}}]` 的 content 部件数组。
- **能力声明**：`BaseLLM.supports_vision` 默认 `False`（扩展抽象让旧实现零改动的哲学），`chat_vision()` 默认抛 `NotImplementedError`；`ModelRouter.supports_vision` 只要池中有视觉模型就返回 True，`chat_vision` **只选 `supports_vision` 的候选（纯文本模型跳过）**——视觉请求不能发给"看不见"的模型。
- **Agent 工具**：`tools/image_analysis.py` 的 `ImageAnalysisTool`（`name="image_analysis"`），`_resolve_image_bytes` 支持 data URL / 本地路径 / 裸 base64，**远程 URL 显式拒绝（防 SSRF）**。
- **API**：`POST /vision/describe` 用 multipart 收图（FastAPI/Starlette 内建，依赖 `python-multipart`），响应 `VisionDescribeResponse(description)`。错误码契约沿用 day038：空/超限/不支持 → 422，点名模型不支持视觉 → 400，模型不存在 → 404。
- **计费口径**：`IMAGE_TOKEN_BUDGET = 85` 对应 OpenAI 视觉低细节计费——视觉 token 与文本 token 有了统一的计量单位，这为 day043 成本追踪埋了线。

**为什么联网要以 data URL 而非 URL**：图片不进 JSON、走 multipart 上传，服务端先落本地再内嵌编码——既避免了远程 URL 的 SSRF 风险，也让格式自包含、不依赖外部可访问性。

### 4.2 day041：Embedding 与向量表示 —— 语义罗盘

**一句话本质**：把"离散符号"映射成"低维稠密连续向量"，让**语义距离 ≈ 向量距离**；检索、记忆、去重、聚类都由此获得语义能力。

落点（[../../day041/源码/smart-research-agent/smart_research_agent/llm/embedding.py](../../day041/源码/smart-research-agent/smart_research_agent/llm/embedding.py)）：

- **三条性质**：**定长**（`dimension` 固定，向量库才能消费）、**归一化**（L2 归一化后余弦退化为点积、阈值有稳定含义）、**余弦度量语义**（1 相同 / 0 正交 / -1 相反）。
- **四提供方**：`MockEmbedding`（SHA-256 伪向量，雪崩效应让它"没有语义"）、`CharNgramEmbedding`（字符 n-gram + MD5 哈希分桶，字面重叠即相似度，离线零依赖）、`SentenceTransformerEmbedding`（编码器 + mean pooling，可选依赖构造时惰性导入）、`OpenAIEmbedding`（`text-embedding-3-small` 默认 1536 维、$0.02/1M、支持 `dimensions` 截断——Matryoshka 表示）。
- **`embed_batch`**：设计成**带默认实现的具体方法**（默认逐条 `embed`），只有神经/云端提供方覆写拿真实批处理收益——这与 day040 `supports_vision` 默认 False 是同一套"扩展抽象零改动"哲学。
- **`default_embedding()` 工厂**：按 `settings.embedding_provider` 选型，`openai` 分支未配置密钥时**退回 `CharNgramEmbedding` 并记告警**——失败安全偏"能离线运行"而非崩溃（与 `default_llm` 同构）。
- **消费方升级**：向量库 `search` 支持 `min_score` 过滤且**不递补**（宁缺毋滥）；`LongTermMemory.remember_many` 批量写入并修复 `store or ...` 把空库静默替换的真值性陷阱（空库 `__len__==0` 是假值，必须 `is not None` 判断）。
- **API**：`POST /embeddings`（批量）与 `POST /embeddings/similarity`（余弦），响应带 `provider`/`dimension` 元信息——**向量只有配合元信息才是契约**。

**为什么 day041 是 M4 前半段的收尾**：day009 的长期记忆一直用 `MockEmbedding`（诚实的占位符，无语义），今天换成真实语义向量后，`min_score` 阈值、`remember_many` 批量、检索排序才真正有意义——前面积累的 RAG 评估指标（day029 的召回率/MRR）从此有了可调的语义标尺。**Vector 时代的地基已经就位，M6 只需把 `InMemoryVectorStore` 换成专业索引即可。**

## 第五章：三张横切表 —— 贯穿六天的共性设计

### 5.1 "扩展抽象、零改动"哲学：一以贯之

| 日 | 抽象改动 | 默认值/默认实现 | 为什么向后兼容 |
|----|----------|----------------|----------------|
| day040 | `BaseLLM` 加视觉能力 | `supports_vision: property -> False` | 纯文本模型不覆写也能当 `BaseLLM` 用 |
| day041 | `EmbeddingProvider` 加批量 | `embed_batch` 默认逐条 `embed` | `MockEmbedding`/`CharNgram` 不覆写也能工作 |
| day039 | `BaseLLM` 加流式 | `stream` 默认整段 `yield chat(...)` | 旧模型实现不写流式也能被 SSE 调用 |

**规律**：给抽象加新能力时，**旧实现零改动**——用"带默认值的具体方法/属性"而非"新增抽象方法"。这样所有既有提供方自动获得新能力的地板，愿意深耕的覆写拿到全量收益。这比"加抽象方法逼所有人实现"更可持续。

### 5.2 失败安全方向：宁可多花钱、宁可离线跑，不可崩溃

| 场景 | 方向 |
|------|------|
| 降级链（day033/day039） | **向上**（更强模型）——答错代价 > 多付一次费 |
| `default_embedding` openai 未配密钥（day041） | 退回 `CharNgramEmbedding` 并告警，不抛错 |
| `default_llm` 未配密钥（day005） | 退回 `MockLLM`，服务照常启动 |

**统一口径**：能退避就不崩溃；退避记日志/告警，让"当前在降级运行"可见。成本失控可追账、可恢复；答错或服务起不来造成的后果不可追。

### 5.3 契约自带元信息：可观测性设计

| 日 | 契约 | 携带的元信息 |
|----|------|-------------|
| day039 | `RouteDecision` | 记录"为什么选了哪个模型" |
| day041 | `EmbeddingResponse` | `provider` + `dimension`（说明这批向量能否与库里已有的比） |
| day038 | `ToolCallRecord` | `name/arguments/result/success`（每次工具调用的审计） |

**规律**：单一输出（一段文本、一串向量、一次调用）本身没有自描述能力；契约里带上"它从哪来、什么口径、有没有成功"，下游才能判断是否可消费、可归因。这是 day032 tracing 思想在协议层的投影。

## 第七章：常见误区清单

**输出端控制（day036~037）**：

1. **"Few-shot 能教会模型知识"** —— Few-shot 校准的是格式与风格，不是知识；给例子不等于教会它"算对"。
2. **"CoT 永远有益"** —— CoT 是"把计算摊到生成过程"，对简单任务可能"想多反而错"；要用 `PromptEvaluator` 对比而不是假设。
3. **"ToT 分支随便开几个都行"** —— 分支必须用不同探索视角，否则搜索退化为瞎试。
4. **"文本解析就能保证格式正确"** —— 文本路径下工具名写错、参数带噪声、格式违例都靠提示词兜底，是概率性的；原生 `tool_calls` 协议才把格式变成确定性的。
5. **"function calling 返回参数可以直接执行"** —— 必须 `validate_arguments`（required + type）后再执行；且 `bool` 特判不可省（`isinstance(True, int)` 为真但 schema 里不相容）。
6. **"坏 JSON 用 tool 消息反馈"** —— tool 消息必须与调用配对，坏 JSON 该降级为 user 消息反馈以免协议错位。

**服务化（day038~039）**：

7. **"同步阻塞代码用 async def 更快"** —— 会冻结事件循环、拖垮全进程；同步代码用 `def`，FastAPI 自动丢线程池。
8. **"Agent 实例可以跨请求复用"** —— Agent 持有单次任务状态，必须注入"造新 Agent 的工厂"。
9. **"流式让回答更正确"** —— 流式只改感知性能（TTFT），不改变内容；function calling 与超长轨迹不适合流式。
10. **"404 只用于页面，422 只是 FastAPI 的细节"** —— 422/404/500 是 M4 全系接口的错误码契约语言，前端按此分支处理，语义不清会让所有下游困惑。

**输入模态（day040~041）**：

11. **"文件扩展名就是 MIME"** —— 不信任扩展名，用 magic bytes 识别真实类型（PNG/JPEG/GIF/WebP）。
12. **"图片可以直接用远程 URL"** —— 工具层显式拒绝远程 URL，避免 SSRF。
13. **"视觉请求可以发给任意模型"** —— 必须经 `supports_vision` 过滤，纯文本模型拿到图像会静默出错/报错。
14. **"MockEmbedding 够用就行"** —— 哈希雪崩让近义/无关句相似度都在 0 附近、无法区分，检索排序等于掷骰子；阈值、排序、去重都必须建立在有语义的 embedding 上。
15. **"embed_batch 每个提供方都得重写"** —— 它被设计成带默认实现的具体方法，逐条 `embed` 也"能跑"，只是神经/云端该覆写拿真实批处理收益。
16. **"空向量库可以放心用 `store or default`"** —— 容器定义了 `__len__` 后空实例是假值，`or` 会把调用方传入的空库静默换掉；必须 `is not None` 判断。
