## 第一章：都会了，为什么还需要"集成"

### 1.1 六块拼图各就各位，却没有一条路走通

先把 day037 ~ day045 的成果摆出来：

| 能力 | 模块 | 谁在用它 |
|------|------|---------|
| 多模型路由 | `llm/router.py` | `/chat` 的默认 LLM（可选） |
| 语义缓存 | `llm/cache.py` | `CachedLLM` 包装器 |
| 成本追踪 | `observability/cost_tracker.py` | 各类演示脚本 |
| 输入侧护栏 | `security/injection_detector.py` | 只在 ReactAgent 内部 |
| 输出侧审核 | `security/content_moderator.py` | `/chat`、`/agent/run` |
| 本地部署 | `llm/local_model.py` | `settings.llm_backend == "local"` 时 |

每一条都有测试、都能单独工作。但把它们**连起来**会遇到三类问题，而这些问题的共同点是：**任何单个模块的测试都不可能发现它们**。

1. **顺序问题**：缓存和审核谁先谁后？倒过来会怎样？
2. **契约问题**：A 模块要求的输入，B 模块到底提供不提供？
3. **口径问题**：两个模块各自算出的"成本"，是同一个东西吗？

第 2 类问题在 day046 的实操中真的发生了，而且一撞就是 500——第三章会完整复盘。

### 1.2 流水线的六阶段：顺序即策略

`integration/pipeline.py` 把六层能力串成一条链：

```text
输入侧护栏 → 语义缓存 → 模型路由与生成 → 成本归因 → 输出侧审核 → 缓存回写
```

阶段名在代码里是常量，顺序有唯一权威来源：

```python
STAGE_GUARD = "guard"
STAGE_CACHE = "cache"
STAGE_GENERATE = "generate"
STAGE_ACCOUNT = "account"
STAGE_MODERATE = "moderate"
STAGE_STORE = "store"

#: 正常路径的阶段顺序（拒答时只有 guard 一个阶段，缓存命中时止于 moderate）
STAGE_ORDER: tuple[str, ...] = (
    STAGE_GUARD,
    STAGE_CACHE,
    STAGE_GENERATE,
    STAGE_ACCOUNT,
    STAGE_MODERATE,
    STAGE_STORE,
)
```

这六个位置每一个都有非它不可的理由，逐条说清楚：

- **护栏必须最先**。恶意输入不该花掉一次昂贵的 LLM 调用，更不该被送进模型上下文。拒答时模型**完全不被调用**（`llm.calls` 为空，测试里断言了这一点）。
- **缓存在护栏之后**。缓存命中的是"安全前提下的重复问题"。若把缓存提到护栏之前，一条被判定为注入的请求会先命中缓存并直接返回——护栏形同虚设。
- **缓存在生成之前**。命中就能跳过最贵的一步，这正是缓存的全部意义。
- **审核在回写缓存之前**。这是**最容易写错、后果最严重**的一条，下一节单独讲。
- **成本归因紧跟生成**。只有真正发生了调用才有账单；归因与调用相邻，才不会把别的开销算进来。

### 1.3 一个真实的顺序陷阱：缓存会把"一次性泄漏"变成"持续性泄漏"

假设顺序写错，先回写缓存、再做输出审核：

```text
第一次请求：模型回复含用户手机号 → 原文写入缓存 → 审核脱敏后才返回给客户端
第二次请求：同样的（或语义相近的）问题 → 直接命中缓存 → 返回的是**未脱敏原文**
```

第一次泄漏还能解释成"模型不小心说漏了嘴"；第二次开始，就是系统自己在稳定地泄露。**缓存把一个偶发问题变成了一个持续性缺陷。**

正确顺序下这件事不可能发生——缓存里存的永远是脱敏后的文本。而且这个性质**可以被测试直接观测**：

```python
def test_cached_reply_is_already_clean(self):
    """缓存里存的是脱敏后文本：命中时二次审核"无事可做"（pii_types 为空）."""
    pipe = make_pipeline(
        llm=StubLLM(reply="邮箱是 a@b.com"),
        cache=make_cache(),
        moderator=ContentModerator(),
    )
    first = pipe.run("给我邮箱")
    second = pipe.run("给我邮箱")
    assert first.moderation.pii_types == ["邮箱"]   # 首次真的检出了 PII
    assert second.cached is True
    assert second.moderation.pii_types == []        # 命中时已无可脱之物
    assert "a@b.com" not in second.reply
```

`pii_types` 从 `["邮箱"]` 变成 `[]`，就是"缓存里没有明文 PII"的可观测证据。若把顺序改错，这个断言会立刻变红——**把安全约束写成断言，是让它在未来一百次重构里活下来的唯一办法**。

## 第二章：六个阶段的具体实现

### 2.1 结果对象：答复 + 每个阶段的账

流水线的返回值是一份"带账本的答复"：

```python
@dataclass
class StageRecord:
    name: str
    duration_ms: float
    detail: str = ""

@dataclass
class PipelineResult:
    reply: str
    model: str          # 实际生效的模型；"cache"=缓存命中，"blocked"=被拦截
    cached: bool
    blocked: bool
    moderation: ModerationResult
    cost_usd: float     # 本次请求的**新增**费用，不是累计值
    prompt_tokens: int
    completion_tokens: int
    injection: InjectionReport | None = None
    stages: list[StageRecord] = field(default_factory=list)
    total_ms: float = 0.0
```

`detail` 字段是给人看的：每一阶段都写清"做了什么决定"。比如真实运行一段后，阶段账长这样（取自 `scripts/integration_demo.py` 的输出，各阶段的**毫秒数随机器抖动**，结构与文字是稳定的）：

```text
=== 完整路径：六个阶段依次执行 ===
模型: gpt-4o-mini | 命中缓存: False | 被拦截: False
费用: $0.000005 | tokens: 11 | 总耗时: 0.23ms
  - guard        0.024ms  通过
  - cache        0.004ms  未命中
  - generate     0.045ms  model=gpt-4o-mini
  - account      0.017ms  tokens=11 cost=$0.000005
  - moderate     0.019ms  通过
  - store        0.094ms  已写入缓存（脱敏后文本）
```

当一次请求变慢或变贵，看一眼阶段账就能回答"是缓存没命中、还是路由选了贵的、还是审核在长文本上回溯"——而不是对着一个孤零零的总耗时猜。

### 2.2 输入侧护栏：补上 day044 留下的缺口

day044 的结语写了三条待办，第一条就是："本课只把**输出侧**审核接进了 API。`PromptInjectionDetector`（输入侧）目前还只在 Agent 内部，把它接到请求入口是下一处要补的闸。"今天补上：

```python
injection: InjectionReport | None = None
guard_start = self._clock()
if self.detector is not None:
    injection = self.detector.scan(task)
stages.append(StageRecord(
    name=STAGE_GUARD,
    duration_ms=self._elapsed_ms(guard_start),
    detail=("未装配输入侧护栏" if injection is None
            else (f"命中注入规则: {', '.join(injection.matched_patterns)}"
                  if injection.is_injection else "通过")),
))
if injection is not None and injection.is_injection and self.block_on_injection:
    self.blocked_requests += 1
    moderation = self._moderate(REFUSAL_REPLY)
    return PipelineResult(reply=moderation.sanitized_text, model="blocked", ...)
```

两个设计细节值得记下来：

1. **拒答文本是常量，不由模型生成**。如果让模型"解释为什么拒绝"，就等于把攻击串送进了模型上下文，护栏白设了。所以 `REFUSAL_REPLY` 是一条固定的中文拒答。
2. **拒答模式可灰度**。`block_on_injection=False` 时只记录不拦截，便于上线初期观察误报率——这比"要么全开要么全关"更符合真实工程。

### 2.3 缓存键必须包含系统提示词

缓存键不是简单的用户文本：

```python
def cache_key(self, task: str, system_prompt: str | None = None) -> str:
    prefix = (system_prompt if system_prompt is not None else self.system_prompt) or ""
    return f"{prefix}\n{task}" if prefix else task
```

原因：同一句"总结一下"，在不同人格/指令下应当得到不同回答。若只按用户文本做键，换个 `system_prompt` 就会命中旧答案——**这种"张冠李戴"比缓存不命中危险得多**，因为它看起来完全正常。

### 2.4 成本归因：为什么必须是"差值"

`CostTracker` 是累计的，而我们要回答的是"这一次请求花了多少钱"：

```python
before_cost = self.tracker.total_cost
before_records = len(self.tracker.records)
self.tracker.record_from_llm(target, model=model)
new_records = self.tracker.records[before_records:]
prompt_tokens = sum(r.prompt_tokens for r in new_records)
completion_tokens = sum(r.completion_tokens for r in new_records)
return round(self.tracker.total_cost - before_cost, 8), prompt_tokens, completion_tokens
```

差值的意义在于**归因**：只有能回答"这次请求花了多少"，才可能回答"哪类问题在烧钱"。累计值只能告诉你"到今天为止花了多少"。

还有一个刻意的宽松处：如果模型不在价格表里（本地/自建模型的常态），流水线**显式按 0 记价并打告警**——

```python
if model not in self.tracker.price_table:
    self.tracker.price_table[model] = dict(ZERO_PRICE)
    logger.warning("模型 %s 不在价格表中，本次按 0 成本计入（本地/自建推理的常见情形）", model)
```

"成本为零"必须是一个**被记录的决定**，而不是一个被忽略的异常。告警的价值就在于：哪天你以为在省钱、实际在用付费模型，日志里会有痕迹。

## 第三章：集成实测暴露的一个真实缺陷

这是本课最有价值的一章。它不是设计好的教学案例，是**跑演示脚本时撞出来的**。

### 3.1 现象：一条 AttributeError 把请求打成 500

`scripts/integration_demo.py` 第一次运行时——用 `build_hybrid_router()` 装配了本地 + 云端路由，再交给流水线——直接崩了：

```text
File "smart_research_agent/integration/pipeline.py", line 258, in _account
    self.tracker.record_from_llm(self.llm, model=model)
File "smart_research_agent/observability/cost_tracker.py", line 76, in record_from_llm
    new_entries = llm.usage_log[consumed:]
AttributeError: 'ModelRouter' object has no attribute 'usage_log'
```

关键在于：**在集成之前，两边各自全绿**。

- `test_router.py` 里 31 个用例全过——它们只验证"路由选谁、失败怎么降级"；
- `test_observability.py` 里成本追踪的用例也全过——它们把 `MockLLM` 直接交给 `CostTracker`，而 `MockLLM` 按 day032 的约定**有** `usage_log`。

两个模块各自都对，拼在一起就炸。这就是第一章说的"契约问题"：**A 集成方以为对方提供某个能力，而对方其实没有**。

### 3.2 根因：包装器不透传"被包装对象的可观测属性"

先把计费器的工作方式看清楚（day043 的实现）：

```python
def record_from_llm(self, llm, model: str, endpoint: str = "chat") -> int:
    """把 LLM 实例自上次调用本方法以来新增的 usage_log 条目登记进来."""
    consumed = getattr(llm, "_cost_consumed", 0)
    new_entries = llm.usage_log[consumed:]
    ...
```

它**要求被传入的对象自己持有 `usage_log`**。`MockLLM` 有，`OpenAICompatibleLLM` 也按同样约定接线。但 `ModelRouter` 是什么？

看它的定义就明白了：

```python
class ModelRouter(BaseLLM):
    """多模型路由器：每次调用先路由再调用，失败沿降级链自动切换."""
```

它是一个**包装器**：自己不产生 token、不持有回复、当然也不持有用量。它唯一知道的是"我把请求转给了谁"。于是"路由 + 计费"这个组合天然断裂——不是谁写错了，而是**没人负责把两个模块的契约对齐**。

顺带说，`BaseLLM` 的抽象边界也在这里露出了一角：`usage_log` 从来不是 `BaseLLM` 的接口成员，它只是 `MockLLM` 与 OpenAI 兼容客户端之间的**事实约定**（duck typing）。模块一多，这类"事实约定"就是最脆弱的地方。

### 3.3 修复：让路由器回答"谁真的花了钱"

修复思路很直接：既然路由器知道自己把请求转给了谁，那就把这个事实暴露出来。`llm/router.py` 新增：

```python
#: 最后一次实际成功提供服务的叶子模型（day046）。
#: 路由是**包装器**：计费与用量必须落到真正干活的叶子上，
#: 否则成本追踪器按 ``llm.usage_log`` 归集时会在这里断链。
self._last_used: BaseLLM | None = None
```

并在四条调用路径（`chat` / `stream` / `chat_with_tools` / `chat_vision`）的**成功分支**上记录它：

```python
for spec in chain:
    try:
        reply = spec.llm.chat(messages, temperature=temperature, max_tokens=max_tokens)
    except Exception as exc:
        errors.append(f"{spec.name}: {exc}")
        continue
    self._last_used = spec.llm          # 只有成功才记账
    if spec.name != decision.chosen:
        decision.fallback_used = spec.name
    return reply
```

对外暴露为只读属性：

```python
@property
def last_used_llm(self) -> BaseLLM | None:
    """最后一次实际生效的叶子模型（day046）；从未调用过时为 None."""
    return self._last_used
```

注意"**成功才记录**"这个细节：失败尝试不应该被记成"用过的模型"，否则成本会算到一个根本没干活的客户端头上。测试里专门验证了这一点：

```python
def test_all_candidates_failing_keeps_no_leaf(self):
    """全部候选失败时不产生"用过的模型"（失败者不应被计入成本归因）."""
    router = ModelRouter([ModelSpec("cheap", FailingLLM(), ...), ...])
    with pytest.raises(RuntimeError, match="所有候选模型均调用失败"):
        router.chat([Message(role="user", content="2+3 等于几")])
    assert router.last_used_llm is None
```

还有一个容易忽略的语义：**降级时记的是"真正回答"的模型**。而由于 `CostFirstStrategy` 把首选之后的候选按能力**从强到弱**排列（"降级往上"——多花钱比答错安全），便宜模型失败后落到的是最强的那个，不是中间的：

```python
def test_fallback_records_the_model_that_actually_answered(self):
    models[0] = ModelSpec("cheap", FailingLLM(), capability=2, cost_per_1k=0.001)
    router = ModelRouter(models)
    router.chat([Message(role="user", content="2+3 等于几")])
    assert router.decision_log[-1].fallback_used == "strong"
    assert router.last_used_llm is models[2].llm
```

### 3.4 计费落叶子：流水线侧的配合与降级

路由器提供了叶子，流水线负责用它：

```python
target = getattr(self.llm, "last_used_llm", None) or self.llm
if not hasattr(target, "usage_log"):
    logger.warning(
        "模型 %s（%s）不提供 usage_log，本次用量记 0；"
        "如需计费请让该客户端按约定上报用量",
        model, type(target).__name__,
    )
    return 0.0, 0, 0
```

两个决定：

1. **有叶子就用叶子**。`getattr(..., None) or self.llm` 让"不是路由器的普通 LLM"走原路径，不引入任何分支负担——因为普通 LLM 没有 `last_used_llm` 属性，`getattr` 返回 `None`，`or` 自然回落到自身。
2. **叶子不会上报用量时，记 0 并告警，而不是抛异常**。这是一个明确的取舍：**服务不该因为一个可观测性协作者没接好，就把用户的请求打成 500**。观测能力缺失可以降级，主流程不该陪葬。但降级必须留下日志，否则就是"静默不算账"，比报错更糟。

对应测试（同时验证不崩与有告警）：

```python
def test_leaf_without_usage_log_is_reported_not_crashed(self, caplog):
    tracker = CostTracker()
    pipe = make_pipeline(llm=StubLLM(reply="无用量"), tracker=tracker)
    with caplog.at_level(logging.WARNING, logger="smart_research_agent.integration.pipeline"):
        result = pipe.run("用量缺位")
    assert result.cost_usd == 0.0
    assert result.total_tokens == 0
    assert tracker.records == []
    assert any("不提供 usage_log" in r.message for r in caplog.records)
```

### 3.5 这一章的结论

三条可以直接搬走的经验：

1. **单元测试验证"模块对不对"，集成测试验证"契约齐不齐"**。前者的全绿不能推出后者——本次缺陷就是活证。
2. **包装器要显式透传被包装者的可观测能力**（用量、日志、状态）。包装器越多，"事实约定"越容易断链，最好把这类透传写成明确的属性并配测试。
3. **集成缺陷的回归测试，要写在"发现缺陷的那一层"**。本次的回归测试放在 `test_pipeline.py::TestRouterAccountability`，因为"路由 + 计费"的组合才是缺陷的现场。

## 第四章：混合路由 —— 本地扛简单题，云端扛复杂题

### 4.1 不写一行 if 的分流

day045 结语留了一个问题："本地模型值不值得用？" 架构层面的答案是：**不搞二选一，让路由器按题目难度自动分流**。

```python
def build_hybrid_router(
    local: BaseLLM,
    cloud: BaseLLM,
    *,
    local_name: str | None = None,
    cloud_name: str | None = None,
    local_capability: int = 3,
    cloud_capability: int = 5,
    local_cost_per_1k: float = 0.0,
    cloud_cost_per_1k: float = 0.01,
) -> ModelRouter:
```

它做的事只有一件：把本地模型标成 **capability=3、cost=0**、云端标成 **capability=5、cost>0**，然后直接复用 day033 的 `CostFirstStrategy`——"在满足能力阈值的候选里挑最便宜的"。于是：

- 复杂度 1~3 的任务：两者都满足阈值，**本地免费 → 选本地**；
- 复杂度 4~5 的任务：只有云端满足阈值，**能力不足的本地被排除 → 选云端**。

实测的决策日志（`scripts/integration_demo.py` 输出）：

```text
任务复杂度 1 -> qwen3:8b
  理由: 任务复杂度 1，选择满足能力要求（capability>=1）的最便宜模型 qwen3:8b（capability=3，$0.0/1K）
任务复杂度 4 -> gpt-4o-mini
  理由: 任务复杂度 4，选择满足能力要求（capability>=4）的最便宜模型 gpt-4o-mini（capability=5，$0.01/1K）
```

复杂度由 day033 的确定性启发式给出（`estimate_complexity`）：文本长度 + 复杂动词（"分析/对比/推理/评估/综述"…）命中数，取值 1~5。"1+1 等于几"得 1 分；"请分析并对比 RAG 与微调的优劣，并给出评估建议"命中"分析""对比"两个动词，得 4 分。**零成本、可解释、在测试里完全确定**——这正是一个路由策略该有的样子。

### 4.2 本地宕机就自动升级

本地服务的可用性远不如云 API 稳定（进程没起、显存不足、机器重启）。而这个组合天然处理它——本地调用抛异常就沿降级链往上走：

```python
def test_local_failure_falls_back_to_cloud(self):
    """本地服务宕机（连接失败）时自动升级到云端，用户无感."""
    router = build_hybrid_router(
        StubLLM(fail=True), StubLLM(reply="云端兜底"),
        local_name="qwen3:8b", cloud_name="gpt-4o-mini",
    )
    assert router.chat([Message(role="user", content="简单问题")]) == "云端兜底"
    assert router.decision_log[-1].fallback_used == "gpt-4o-mini"
```

两个边界校验防止"静默错误配置"：

- `local_capability` 不低于 `cloud_capability` 时**打告警**——这种配置下云端永远不会被选中，等于花两份钱只用一份（可能有意，但更可能是配错）；
- 两个模型名相同时直接报错——路由器无法区分候选，配置一定错了。

## 第五章：性能基线 —— 把"变慢了"变成可判定的工程事实

集成之后必然要问的问题不是"跑得通吗"（测试已回答），而是"**比昨天慢了吗、贵了吗**"。要回答它需要三样东西。

### 5.1 可复现的度量

```python
def measure(
    pipeline: IntegratedPipeline,
    tasks: list[str],
    *,
    label: str = "pipeline",
    system_prompt: str | None = None,
) -> PerfBaseline:
```

它在一组固定任务上跑流水线，采集每个阶段的耗时、token 与费用。关键实现选择：耗时取流水线**自报**的 `total_ms` 与 `StageRecord.duration_ms`，而不是在外面再包一层计时——否则"测到的耗时"与"响应里报告的耗时"会对不上，两个数字都不再可信。

### 5.2 百分位数用最近秩法，不做插值

```python
def percentile(values: list[float], q: float) -> float:
    """最近秩法百分位数：返回样本中真实存在的那个值（空列表返回 0.0）."""
    if not 0.0 <= q <= 100.0:
        raise ValueError("q 必须在 0~100 之间")
    if not values:
        return 0.0
    ordered = sorted(values)
    rank = math.ceil(q / 100.0 * len(ordered)) - 1
    index = max(0, min(rank, len(ordered) - 1))
    return ordered[index]
```

为什么不用线性插值？**样本量小的时候，插值会凭空捏造出样本里并不存在的耗时值**。一次评测往往只有十几条任务，性能门禁的每一个结论都必须能回溯到某一次真实请求——所以这里永远返回真实观测值。测试里用 20 个样本验证了这一点：

```python
def test_nearest_rank_is_an_observed_value(self):
    """20 个样本取 P95 -> 第 19 个（下标 18），是真实样本而非插值."""
    values = [float(i) for i in range(1, 21)]
    assert percentile(values, 95) == 19.0
```

### 5.3 判定下限：门禁能不能长期用下去的关键

判定规则统一为比值：`当前值 / 基线值 > 容忍倍数` 即判为回归。但**比值不能无条件算**：

```python
#: 默认判定下限：低于这些值的基线不参与比值判定（防抖动）
DEFAULT_MIN_LATENCY_MS = 5.0
DEFAULT_MIN_TOKENS = 1.0
```

```python
for metric, base_value in self.baseline.latency_ms.items():
    current_value = current.latency_ms.get(metric)
    if current_value is None or base_value < self.min_latency_ms:
        continue                       # 基线太小，比值没有意义
    ratio = current_value / base_value
    if ratio > self.latency_tolerance:
        regressions.append(Regression(...))
```

道理很朴素：1ms 变成 2ms 是"2 倍回归"，但对用户完全无感，而且会被调度抖动随机触发。**一个天天误报的门禁，最后一定会被人关掉**——所以宁可放过微秒级的"回归"，也要保住门禁的可信度。另外两个细节：

- 当前采集里**缺失的阶段**不参与判定（缓存命中时本来就没有 `generate` 阶段），用 `current.latency_ms.get(metric)` 返回 `None` 直接跳过；
- 成本基数为 0 时（全本地模型的常见情形）也跳过——0 的任意倍数还是 0，比值判定没有意义。

### 5.4 口径声明：没有账本就没有数字

token 与费用的**唯一来源是成本归集阶段**，流水线未装配 `CostTracker` 时这两个指标恒为 0。这是一个刻意的口径声明：

> 没有账本就没有可核对的用量，绝不用"字符数除以 4"之类的估算顶替——否则基线与真实账单会在同一张表里混成两种口径，数字就再也不能对比了。

测试把这条口径也钉住了：

```python
def test_measure_without_tracker_has_no_numbers(self):
    pipe = IntegratedPipeline(StubLLM(), clock=FixedClock())
    baseline = measure(pipe, ["a", "b", "c"])
    assert baseline.mean_tokens == 0.0
    assert baseline.mean_cost_usd == 0.0
```

### 5.5 存档与比对

基线写进 JSON 随仓库提交，它就是这次迭代的"体检报告底片"：

```python
def save(self, path: str | Path) -> Path: ...
@classmethod
def load(cls, path: str | Path) -> PerfBaseline:
    """读取基线文件；文件不存在时抛 ``FileNotFoundError``.

    刻意不返回"空基线"兜底：**没有基线**与"基线全为零"是两回事，
    前者应当明确报错（提示先跑一次采集），后者会静默地把所有回归
    判定都跳过——那是最危险的失败方式。
    """
```

`scripts/integration_demo.py` 会把采集结果写入 `data/eval/perf_baseline.json`，再与它比对一次，输出一行结论：

```text
回归比对: 性能未回归：当前 3 个样本，平均总耗时 <1ms、平均 3.0 token、平均 $0.000001
```

> **诚实的说明**：这条演示基线的耗时是**亚毫秒级**（MockLLM 的推理近乎瞬时，具体数值还会随机器抖动，因此上例不写死毫秒数），远低于判定下限 5ms，所以它**只用于打通流程，不构成任何真实性能结论**。要得到有意义的基线，把流水线里的 LLM 换成真实模型（或本地 Ollama）再跑一遍即可——机制在离线环境已经完整验证过了。

## 第六章：接入 FastAPI —— 两个端点的分工

### 6.1 `/pipeline/run`：要答案，也要账本

```python
@router.post("/pipeline/run", response_model=PipelineRunResponse)
def pipeline_run(
    req: PipelineRunRequest,
    pipeline: IntegratedPipeline = Depends(get_pipeline),
) -> PipelineRunResponse:
    return to_pipeline_response(
        pipeline.run(req.task, temperature=req.temperature, system_prompt=req.system_prompt)
    )
```

它与 `/chat` 的分工很清晰：`/chat` 是"只要答案"的轻接口（审核后返回文本），本接口是"要答案 + 要账本"的重接口——`stages`（逐阶段耗时）、`cost_usd`（单次归因）、`cached`/`blocked`、`injection` 全部随响应返回。两者**共用同一套底层能力**，差别只在是否把过程暴露给调用方。

共享是刻意保证的：`create_app` 把已经注入的审核器交给流水线，避免"两个入口两套审核规则"的裂缝。

```python
app.state.pipeline = pipeline or default_pipeline(
    resolved_llm, moderator=app.state.moderator
)
app.state.perf_baseline_path = perf_baseline_path or settings.perf_baseline_path
```

### 6.2 `/pipeline/baseline`：缺基线就返回 404

```python
try:
    baseline = PerfBaseline.load(request.app.state.perf_baseline_path)
except FileNotFoundError as exc:
    raise HTTPException(status_code=404, detail=str(exc)) from exc
return PerfBaselineResponse(**baseline.to_dict())
```

为什么是 404 而不是"返回一份零值基线"？因为**"还没有基线"是一个必须被看见的状态**。假基线会让所有回归判定静默通过——最坏的情况不是报错，而是你以为门禁在工作，它其实什么都没拦。

### 6.3 装配自述：确认"这层到底开没开"

```python
def describe(self) -> dict[str, Any]:
    return {
        "llm": type(self.llm).__name__,
        "stages": list(STAGE_ORDER),
        "cache": self.cache is not None,
        "tracker": self.tracker is not None,

```

六层能力全部可注入（`None` 表示"这一层不启用"），因此同一条流水线既能装配成生产形态，也能退化成裸调用。后者对排障极有价值：**怀疑某层有副作用时，逐层关掉即可二分定位**。

### 假时钟：让耗时断言完全确定

耗时测试最容易写坏（`time.sleep` 又慢又不稳）。这里的做法是注入一个"每次读取前进固定步长"的时钟：

```python
class FakeClock:
    def __init__(self, step: float = 0.001):
        self._now = 0.0
        self._step = step
    def __call__(self) -> float:
        value = self._now
        self._now += self._step
        return value
```

于是"第几次读取时钟"与"过了多少毫秒"一一对应，三条路径的总耗时可以被**精确断言**：

```python
def test_fake_clock_makes_timings_deterministic(self):
    """14 次时钟读取 -> 总耗时恰好是第 14 次与第 1 次之差（13ms）."""
    result = make_pipeline().run("计时")
    assert result.total_ms == 13.0

def test_blocked_path_timing(self):
    assert make_pipeline(detector=PromptInjectionDetector()).run(ATTACK).total_ms == 3.0

def test_cache_hit_path_timing(self):
    """命中路径 8 次时钟读取：guard/cache/moderate 三段 + 总计时."""
    pipe = make_pipeline(cache=make_cache())
    pipe.run("计时")
    assert pipe.run("计时").total_ms == 7.0
```

13ms / 3ms / 7ms 这三个数字本身就是"这条路径经过几个阶段"的另一种表达：**满路径 6 个阶段（13 次读数）、拒答 1 个阶段（3 次）、命中 3 个阶段（7 次）**。断言耗时等于间接断言了阶段数——将来谁不小心在急路径上多加了一次时钟读取，测试会立刻发现。

## 结语：集成之后的三条工程线索

1. **顺序要写进测试，而不是只写在注释里**。"审核先于回写缓存"是一条安全约束，注释会被忘记，断言不会。本课把这类顺序约束全部转成了可观测断言（`pii_types == []`、阶段序列、`llm.calls == []`）。
2. **包装器要交代清楚"我替谁说话"**。`ModelRouter.last_used_llm` 是一次修补；系统里还有别的包装器（`CachedLLM`、未来的限流器、重试器）需要同样对待。**每加一层包装，就问一句：用量、错误、状态还能穿透吗？**
3. **性能门禁贵在"长期可信"，不在"灵敏"**。判定下限、最近秩法、缺失指标跳过——这三条都是在为"门禁不被关掉"服务的。一个误报率高的门禁活不过两周。
