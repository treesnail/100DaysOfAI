## 第 1 题

解析：工具调用的本质是"LLM 出决策、代码出执行"的分工协作。LLM 只负责判断何时调用工具、传什么参数，以及阅读工具返回的结果；精确计算、联网、数据库访问等执行工作由外部程序完成。

- D 错误：节省 token 不是主要价值，工具解决的是"LLM 根本做不到"的问题（实时信息、精确计算、作用于世界），不是成本问题。

## 第 3 题

**答案：B**

解析：`ast.parse` 的关键性质是**只解析、不执行**——它把字符串变成结构化的语法树，让我们有机会在执行前逐个节点审查。白名单求值只放行 `Constant`（数字）、`BinOp`（六种运算符）、`UnaryOp`（正负号），函数调用（`Call`）、变量名（`Name`）等危险节点类型直接被拒绝。

- A 错误：`ast.parse` 不做任何"删除"，恶意代码原样存在于树中，是我们的 `_safe_eval` 遍历时拒绝执行它。
- C 错误：安全性不来自"标准库"身份，而来自白名单设计本身。
- D 错误：白名单不是"转换"，是"甄别后拒绝"。

## 第 4 题

**答案：错**

解析：`description` 的主要读者是 **LLM**——它会被拼进系统提示词，是 LLM 判断"这个任务该用哪个工具"的依据。描述写得模糊（如"计算"），LLM 就难以在恰当时机选择该工具；写得清晰（能力范围 + 语法 + 示例），工具选择准确率明显提升。调优工具 description 本质上就是 prompt 工程的一部分，写作风格直接影响 Agent 行为。

## 第 5 题

**答案：对**

解析：`isinstance` 会被继承关系"骗过"——如果存在某个继承自 `ast.Add` 的自定义节点类型，`isinstance(node, ast.Add)` 会返回 True，白名单边界就被绕过了。`type(node.op) in _BIN_OPS` 要求类型**精确匹配**字典中的键，任何子类都无法混入。这是防御性编程的细节：白名单机制本身要足够硬，否则白名单形同虚设。

## 第 6 题

**答案：对**

解析：在 Agent 架构中，工具的返回值是给 LLM 阅读的 Observation。如果把异常抛给调用方，整个 ReAct 循环会崩溃；把错误转成字符串返回，LLM 读到"计算失败： 不支持的表达式"后有机会调整参数重试——**错误信息变成了模型的纠错信号**。这正是"工具错误是 prompt 的一部分，不是事故"的设计思想。当然，前提是错误信息本身不泄露敏感信息（如服务器路径、密钥）。

## 第 7 题

**参考答案**：

| 契约 | 服务谁 | 说明 |
|------|--------|------|
| `name` | Agent 代码 | 工具唯一标识。LLM 输出 `Action: calculator` 时，Agent 用 name 在工具集中路由查找对应实例 |
| `description` | LLM | 自然语言描述，作为 prompt 素材告诉 LLM 这个工具能干什么、什么时候该用 |
| `parameters` | LLM + 调用方 | JSON Schema，描述参数结构；LLM 据此生成合法参数，调用方/注册表可据此校验 |
| `execute` | Agent 代码 | 真正的执行入口，返回值（字符串）作为 Observation 喂回给 LLM |

新增无参数工具时可以少写代码：`BaseTool` 给 `parameters` 提供了默认实现 `{"type": "object", "properties": {}}`——这是"合理默认"的契约设计：强制实现的只有最小集合（name、description、execute），无参数工具不需要覆盖 `parameters`。同时基类的 `to_schema()` 自动可用，新工具类只需实现三个契约就能获得完整的 schema 导出能力。

## 第 8 题

**参考答案**：

1. 三个字段含义：
   - `type: "object"`：参数整体是一个对象（一组键值对），对应调用时 `execute(**kwargs)` 的关键字参数集合；
   - `properties`：逐一声明每个参数的名字、类型和自然语言说明（`expression` 是 string，含义是"要计算的数学表达式"）；
   - `required: ["expression"]`：声明哪些参数必填，缺少必填参数的调用视为不合法。

2. 用 JSON Schema 而非自然语言的理由：
   - **机器可解析**：OpenAI 等厂商的 function calling API 直接接受 JSON Schema 格式的工具定义，自然语言描述无法被 API 消费；
   - **可校验**：将来有现成的 JSON Schema 校验库可以自动检查 LLM 生成的参数是否合法；
   - **生态通用**：JSON Schema 是行业标准，MCP 协议（M2 阶段）也用它描述工具参数，一次学习多处复用；
   - **无歧义**：自然语言"一个数学表达式字符串"没说参数名叫什么、是否必填，结构化 schema 全部明确。

## 第 9 题

**参考答案**（`smart_research_agent/tools/string_length.py`）：

```python
"""字符串长度工具."""

from __future__ import annotations

from typing import Any

from smart_research_agent.tools.base import BaseTool


class StringLengthTool(BaseTool):
    """计算字符串长度."""

    @property
    def name(self) -> str:
        return "string_length"

    @property
    def description(self) -> str:
        return "计算字符串的字符个数，参数为任意文本，例如 'hello' 返回 5"

    @property
    def parameters(self) -> dict[str, Any]:
        return {
            "type": "object",
            "properties": {
                "text": {
                    "type": "string",
                    "description": "要计算长度的字符串",
                }
            },
            "required": ["text"],
        }

    def execute(self, text: str = "", **kwargs: Any) -> str:
        if not text:
            return "错误: 缺少 text 参数"
        return f"字符串长度为 {len(text)}"
```

测试（`tests/test_string_length.py`）：

```python
"""字符串长度工具测试."""

from __future__ import annotations

from smart_research_agent.tools.string_length import StringLengthTool


class TestStringLength:
    def test_normal(self):
        assert StringLengthTool().execute(text="hello") == "字符串长度为 5"

    def test_missing_text(self):
        assert StringLengthTool().execute() == "错误: 缺少 text 参数"

    def test_schema_export(self):
        schema = StringLengthTool().to_schema()
        assert schema["name"] == "string_length"
        assert "text" in schema["parameters"]["properties"]
        assert schema["parameters"]["required"] == ["text"]
```

要点解析：

- 结构完全复刻 `CalculatorTool`：四个契约逐一实现，这就是抽象基类的价值——**新工具的开发变成"填空"，而不是"发明"**。
- `description` 的写法遵循"面向 LLM 写作"：说清用途（计算字符个数）、参数（任意文本）、示例（'hello' 返回 5）。
- 运行 `pytest tests/ -q --no-cov` 验证：新测试应全部通过，且原有测试不受影响（工具之间相互独立）。

## 第 10 题

**参考答案**：

只需修改两处：

1. `_BIN_OPS` 字典新增一行：

```python
_BIN_OPS = {
    ast.Add: operator.add,
    ast.Sub: operator.sub,
    ast.Mult: operator.mul,
    ast.Div: operator.truediv,
    ast.Pow: operator.pow,
    ast.Mod: operator.mod,
    ast.FloorDiv: operator.floordiv,  # 新增：整除
}
```

2. `description` 更新为：

```python
return "计算数学表达式，支持 + - * / // ** % 与括号，例如 '2 + 3 * (4 - 1)'"
```

测试补充（加入 `test_arithmetic` 的参数化列表）：

```python
("7 // 2", "3"),
("10 // 4", "2"),
```

思考题的答案：**不需要改 `_safe_eval` 的代码**。求值函数写的是"如果运算符在白名单字典里，就查表执行"——字典是数据，函数是逻辑。新增运算符只是往数据里加一行，逻辑零改动。这体现了**开闭原则**（对扩展开放、对修改关闭）：把"会变化的部分"（支持哪些运算符）抽成数据表，把"不变的部分"（如何遍历求值）留在代码里。

同时注意第 3 步不是可选项：工具的 description 是 LLM 选择和使用工具的依据，**能力扩展了但不更新描述，LLM 就不会主动使用新能力**——代码与 prompt 素材必须同步演进。
