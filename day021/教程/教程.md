## 第二章：MCP 协议与架构（day016 复盘）

### 2.1 为什么需要 MCP —— M×N 问题的解法

**一句话本质**：MCP 是"AI 应用的 USB-C 接口"——一套标准化协议，让任何 LLM 应用（Host）可以即插即用地接入任何外部数据源与工具（Server）。

**为什么**：回到 M1，我们的 `CalculatorTool` 是直接 `import` 进进程的。这在单项目里没问题，但放大到生态层面会撞上一堵墙：

- 有 M 个 LLM 应用（我们的 Agent、Claude Desktop、Cursor……），N 个外部能力（文件系统、数据库、搜索引擎、日历……）。
- 没有标准协议时，每个应用要给每个能力写一套私有对接代码，总工作量 **M×N**。
- 有了 MCP，每个应用实现一次 Client，每个能力实现一次 Server，总工作量降为 **M+N**。

这和 USB-C 的逻辑一模一样：接口标准化之后，设备厂和应用厂各自只对接标准，不再两两私聊。**MCP 的价值不在技术多新，而在"把对接成本从乘法降为加法"。**

### 2.2 三种角色：Host / Client / Server

**一句话本质**：Host 是用户面对的 AI 应用本体，Client 是 Host 内部的协议连接器（一个 Server 配一个 Client），Server 是能力提供方。

```text
┌─────────────────────────────────────────────────────┐
│                      Host                            │
│         （SmartResearch Agent / Claude Desktop）     │
│                                                      │
│   ┌──────────────┐   ┌──────────────┐                │
│   │ MCP Client A │   │ MCP Client B │   ……           │
│   └──────┬───────┘   └──────┬───────┘                │
└──────────┼──────────────────┼────────────────────────┘
           │ JSON-RPC         │ JSON-RPC
           │ (stdio)          │ (SSE/HTTP)
           ▼                  ▼
   ┌───────────────┐  ┌───────────────┐
   │  MCP Server A │  │  MCP Server B │
   │ 知识库/文件系统 │  │ 搜索/数据库    │
   └───────────────┘  └───────────────┘
```

关键读法：

- **Host 和 Client 不是一回事**。Host 关心的是"任务怎么完成"（我们的 ReAct 循环、Planner），Client 关心的只是"协议怎么说话"（发请求、收响应）。一个 Host 同时连多个 Server 时，每个连接是一个独立的 Client。
- **Server 不挑 Host**。我们写的 MCP Server 既能被自己的 Agent 用，也能被 Claude Desktop 直接挂载——这正是标准化的回报。

**常见误区**：

- **误区一：把 Client 当成 Host。** Client 没有业务智能，它只是协议管道；让 Client 做任务决策等于把网关当应用服务器用。
- **误区二：一个 Client 连多个 Server。** MCP 的连接模型是 1:1，连三个 Server 就需要三个 Client 实例。混淆这一点会导致会话状态、能力清单互相串台。

### 2.3 JSON-RPC 2.0 —— 一切通信的"信封"

**一句话本质**：MCP 的所有消息都是 JSON-RPC 2.0 包——请求、响应、错误、通知四种信封，字段固定，语义明确。

day016 用 pydantic 把这四种信封建模成类型（完整代码见 [day016 快照 protocol.py](../../day016/源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py)）：

```python
class JsonRpcRequest(BaseModel):
    id: int | str
    method: str
    params: dict[str, Any] = Field(default_factory=dict)
    jsonrpc: Literal["2.0"] = "2.0"

class JsonRpcResponse(BaseModel):
    id: int | str
    result: Any
    jsonrpc: Literal["2.0"] = "2.0"

class JsonRpcError(BaseModel):
    id: int | str
    error: JsonRpcErrorDetail   # 内含 code 与 message
    jsonrpc: Literal["2.0"] = "2.0"
```

设计要点复盘：

- **`id` 是请求-响应配对的钥匙**。Client 发出 `id=3` 的请求，必须收回 `id=3` 的响应。这是异步并发调用的基础——没有 id，同时发三个请求就无法分辨哪个响应对应哪个请求。
- **响应和错误是两个类型，不是一个类型加个可选字段**。一次调用要么成功（result）要么失败（error），互斥关系用两个类表达，比 `JsonRpcResponse(result=None, error=None)` 的可选字段组合更不容易写出"两个都是 None"的非法状态。**让非法状态在类型层面不可表达，是 pydantic 建模的精髓。**
- **`jsonrpc: Literal["2.0"] = "2.0"`**：协议版本钉死，反序列化时自动校验——收到 `"jsonrpc": "1.0"` 的消息在 pydantic 层就被拒了，根本进不了业务逻辑。这是 day010 学的"防御式解析"在协议层的重演。
- **通知（Notification）是没有 id 的请求**——"我告诉你一件事，不用回"。`notifications/initialized` 就是典型。

**常见误区**：

- **误区一：自创消息格式"更简单"。** JSON-RPC 的价值恰恰在于无聊：字段固定、语义通用、所有语言都有现成实现。自创格式省下的半小时，会在联调时以十倍讨还。
- **误区二：包名用 `mcp`。** 我们项目内的包固定叫 `smart_research_agent.mcp_server`——如果叫 `mcp`，会**遮蔽官方 mcp 包**，`import mcp` 时 Python 会优先找到我们自己的包，报出一堆莫名其妙的 ImportError。命名冲突是 Python 工程里最常见的"灵异 bug"来源之一。

### 2.4 生命周期三阶段

**一句话本质**：一次 MCP 会话 = 初始化握手 → 正常通信 → 优雅关闭，顺序固定，不可跳跃。

```text
Client                                    Server
  │                                         │
  │──── initialize ────────────────────────▶│   ① 初始化：报协议版本 + 客户端能力
  │◀─── 协议版本 + Server 能力 + 元信息 ─────│
  │──── notifications/initialized ─────────▶│   （通知：握手完成，无 id 不用回）
  │                                         │
  │════ resources/list, tools/call … ══════▶│   ② 正常通信：一切业务能力
  │◀═══ result / error ════════════════════│
  │                                         │
  │──── 关闭（stdio 管道 EOF / 进程退出）──▶│   ③ 关闭
```

**为什么要有握手而不是直接干活**？三个理由：

1. **版本协商**：Client 说自己会说哪些协议版本，Server 挑一个共同支持的回。今天大家都是 2024/2025 版本，但协议会演进，握手机制让新旧两端能优雅共存而不是直接崩。
2. **能力声明**：Server 在握手时声明"我有 resources、有 tools、没有 prompts"，Client 后续就不会傻乎乎地发 `prompts/list` 过去。**把能力发现前置到握手，避免了"调了才知道没有"的运行时尴尬。**
3. **明确的状态机**：握手没完成前收到业务请求怎么办？协议规定一律报错。状态机越明确，实现和调试越简单——这和 TCP 三次握手是同一个工程思想。

**常见误区**：

- **误区一：跳过 initialize 直接调 tools/call。** 协议明确规定这是错误行为，Server 有权拒绝。day020 的 Client 封装里，连接后第一件事就是握手——把它做成不可省略的步骤，而不是"可选的最佳实践"。
- **误区二：认为关闭不重要。** stdio 传输下，Client 是通过子进程的 stdin/stdout 与 Server 通信的。不优雅关闭会导致子进程变僵尸、管道句柄泄漏——单次看不出来，长跑服务迟早翻车。

### 2.5 两种传输：stdio 与 SSE

| 维度 | stdio | SSE（Server-Sent Events） |
|------|-------|---------------------------|
| 通信介质 | 子进程的标准输入/输出 | HTTP（SSE 推 + POST 发） |
| 部署形态 | Server 是 Client 拉起的本地子进程 | Server 是独立网络服务 |
| 进程关系 | 一对一，Client 管 Server 生死 | 多对一，Server 服务多个 Client |
| 适用场景 | 本地工具（文件、命令行）、桌面应用 | 远程服务、团队共享能力 |
| 网络依赖 | 无 | 有（要考虑超时、重连、鉴权） |

一句话记忆：**stdio 是"打电话给自己家保姆"，SSE 是"打电话给客服中心"**。我们项目两种都实现了（day019），开发调试期用 stdio（零网络配置），将来部署成共享服务时切 SSE。

## 第三章：三大原语对比 —— Resources / Tools / Prompts（day017~018 复盘）

### 3.1 为什么要分三种，而不是统一成"能力"

**一句话本质**：三原语按**"谁主导这次调用"**划分——Resource 由应用（Host）主导读取，Tool 由模型（LLM）主导调用，Prompt 由用户主导触发。

这是理解 MCP 设计最关键的一刀。三种东西如果只看"都是 Server 提供的能力"，确实像一回事；但从控制权角度看，它们服务三种完全不同的交互模式：

- **Resource**：应用决定要读什么上下文。像**打开一个文件**——应用（或最终是应用背后的逻辑）说"给我 `kb://docs/intro.md`"，Server 返回内容。
- **Tool**：模型决定要用什么功能。像**让助手去办一件事**——LLM 在 ReAct 循环里说"我要调 calculator，参数是 2+3"，模型是决策者。
- **Prompt**：用户决定要套用什么模板。像**点菜单上的固定套餐**——用户在界面上选"深度调研"模板，填入主题，模板展开成完整提示词。

### 3.2 对比总表

| 维度 | Resource | Tool | Prompt |
|------|----------|------|--------|
| 本质 | 可读的数据/上下文 | 可执行的函数 | 可复用的提示词模板 |
| 谁主导 | 应用（Host/Client） | 模型（LLM） | 用户 |
| 类比 | 打开文件 | 调用 API | 点菜单选模板 |
| 寻址方式 | URI（如 `kb://docs/{name}`） | 名称 + JSON Schema 参数 | 名称 + 参数列表 |
| 返回 | 内容 + mime_type | 执行结果（文本/结构化） | 展开后的消息列表 |
| 副作用 | 无（只读） | 可能有（写库、发请求） | 无 |
| 描述符 | ResourceDescriptor(uri, name, description, mime_type) | ToolDescriptor(name, description, input_schema) | PromptDescriptor(name, description, arguments) |
| 在 ReAct 里的角色 | 注入上下文 | Action 的执行对象 | 组装 system/user 消息 |
| day 快照 | day017 | day018 | day018 |

### 3.3 各自的"为什么"

**Resource 为什么是 URI 寻址？** URI 是互联网通用的资源定位方式，`kb://docs/{name}` 这样的模板让 Server 可以用一个模式暴露一整类资源，而不是逐条注册。参数化的 URI 模板（`{name}`）把"无数个资源"压缩成"一个模板 + 一个处理函数"。

**Tool 为什么带 input_schema（JSON Schema）？** 因为调用方是 LLM——它不知道 Python 类型注解，只认 JSON Schema。Schema 同时服务两端：给 LLM 看是"这个工具怎么吃参数"的说明书，给 Server 看是入参的自动校验器（FastMCP 会从函数签名自动生成）。

**Prompt 为什么要放在 Server 侧？** 提示词是一种领域知识。"如何调研一个技术主题"的最佳提示词，由最懂调研的 Server 作者写一次，所有 Host 共享——比每个应用各自重复发明要好。这也呼应了 M4 阶段要学的 Prompt 工程：**好的提示词是资产，资产应该集中管理、版本化、可复用。**

### 3.4 常见误区

- **误区一："Resource 和 Tool 都能返回数据，随便用。"** 判断标准是**有没有副作用、谁做决策**。读知识库文档用 Resource（只读、应用决定读哪份）；搜索网络用 Tool（有外部调用、模型决定何时搜）。用反了不会报错，但会让架构语义腐烂——三个月后没人说得清为什么"查文档"是个 Tool 而"搜索"是个 Resource。
- **误区二：把动态数据塞进 Prompt 模板。** Prompt 的参数应该只是"主题""风格"这类少量变量；大段上下文数据该走 Resource。把 5000 字文档当 Prompt 参数塞进去，等于把数据层和模板层焊死了。
- **误区三：Tool 的 description 随便写写。** 和 M1 的 `BaseTool.description` 一样，这是 LLM 选择工具的唯一依据。"计算"两个字和"对数学表达式求值，支持加减乘除、乘方、取模与括号"之间，隔着 LLM 能不能正确路由的天堑。

## 第四章：FastMCP Server 开发要点（day019 复盘）

### 4.1 FastMCP 是什么、不是什么

**一句话本质**：FastMCP 是官方 mcp 包里的高层 Server 框架——用装饰器把普通 Python 函数暴露成 MCP 能力，协议细节（JSON-RPC 编解码、握手、能力协商）全部托管。

**它不是什么**：不是协议本身，不是唯一实现。它之于 MCP，就像 Flask 之于 HTTP——框架帮你省掉样板代码，但理解底下的协议仍然是你的功课（这就是 day016 先手工建模 JSON-RPC 的原因）。

### 4.2 三个装饰器，一天的精华

```python
from mcp.server.fastmcp import FastMCP

app = FastMCP("smart-research")

@app.resource("kb://docs/{name}")
def read_doc(name: str) -> str:
    """按名称读取知识库文档."""
    ...

@app.tool()
def calculator(expression: str) -> str:
    """对数学表达式求值，支持加减乘除、乘方、取模与括号."""
    ...

@app.prompt()
def research_briefing(topic: str) -> str:
    """生成深度调研任务的提示词模板."""
    ...
```

复盘三个装饰器背后的设计：

**（1）约定优于配置。** 函数名即能力名（可覆盖），docstring 即 description，类型注解即 input_schema。你写的每一行"本来就该写"的东西都被框架消费了——**零冗余**。这也是 Python 装饰器框架（Flask、FastAPI、Click）共同的审美。

**（2）docstring 不再是给人看的，是给 LLM 看的。** `@app.tool()` 会把 docstring 原样放进 ToolDescriptor 发给模型。写 `@app.tool()` 时偷懒写个"工具"二字，等于给 LLM 一本没有内容的说明书。**写 FastMCP 的 docstring 就是在写 prompt。**

**（3）返回值自动包装。** 函数返回 `str`，框架自动包成 MCP 规定的 `TextContent` 列表。你专注业务返回，协议封装归框架——这正是"框架的价值 = 替你维护协议正确性"。

### 4.3 传输启动与元数据

```python
if __name__ == "__main__":
    app.run(transport="stdio")   # 或 transport="sse"
```

- `FastMCP("smart-research")` 传入的名字会出现在握手响应的 serverInfo 里——Client 侧日志和调试界面靠它分辨"我连着谁"。
- stdio 模式下**任何 print 到 stdout 的输出都会污染协议流**，日志必须走 stderr 或文件（第二章的思考题答案）。这是 FastMCP 新手最常踩的坑，没有之一。

### 4.4 内存内测试：`create_connected_server_and_client_session`

day019 测试的关键手法：

```python
from mcp.shared.memory import create_connected_server_and_client_session

async with create_connected_server_and_client_session(app) as session:
    tools = await session.list_tools()
    result = await session.call_tool("calculator", {"expression": "2 + 3"})
```

这个 helper 在**同一进程内**用内存管道把 Server 和 Client 接起来，不用起子进程、不用开端口、不用网络——测试因此快速、确定、离线。这和 M1 阶段 MockLLM 的设计哲学是同一个：**把最不可控的外部依赖（LLM / 网络 / 子进程）换成可控的进程内替身，测试才能又快又稳。**

**常见误区**：

- **误区一：在测试里真起 stdio 子进程。** 慢、脆（进程清理不干净就挂）、平台差异大（Windows 的进程模型尤其爱出问题）。单元测试用内存管道；端到端验证才用真实传输。
- **误区二：以为 `app.run()` 能在 pytest 里直接调。** `run()` 会阻塞在事件循环里等服务，测试必须走 client session 这条路。

## 第五章：Client 集成与工具动态接入（day020 复盘）

### 5.1 初始化的固定四步

**一句话本质**：MCP Client 的启动流程是固定仪式——建连接 → 握手 → 收能力清单 → 把能力翻译成 Host 内部对象。

```python
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

params = StdioServerParameters(command="python", args=["-m", "smart_research_agent.mcp_server.server"])
async with stdio_client(params) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()            # ② 握手（生命周期不可省略）
        tools = await session.list_tools()    # ③ 能力发现
```

四步缺一不可，尤其第②步——跳过握手的 Client 是不守协议的 Client，正规 Server 会直接报错。

### 5.2 动态接入：MCP Tool → BaseTool 的适配器

这是 day020 最重要的一笔，也是 M2 和 M1 的缝合点：

```text
MCP Server 侧                     MCP Client 侧                 Agent 侧
┌──────────────┐   tools/list   ┌──────────────┐  适配器包装  ┌──────────────┐
│ @app.tool()   │──────────────▶│ ToolDescriptor│────────────▶│  BaseTool 子类 │
│ calculator    │               │ name/schema   │             │ name 同原工具  │
└──────────────┘               └──────────────┘             │ execute() 内 │
                                                             │ 调 session.  │
                                                             │ call_tool()  │
                                                             └──────┬───────┘
                                                                    ▼
                                                        注册进 ToolRegistry
                                                        ReAct 循环无感使用
```

适配器做三件事：

1. **透传元数据**：MCP 工具的 name/description/schema 直接映射为 BaseTool 的 `name`/`description`/`parameters`——LLM 看到的说明书一字不差。
2. **转发调用**：`execute(**kwargs)` 内部调 `session.call_tool(name, kwargs)`，把 MCP 返回的内容列表拼成字符串，作为 Observation 回填。
3. **注册**：像注册本地工具一样 `registry.register(adapter)`。

**为什么这套设计漂亮**：Agent 的 ReAct 循环、SYSTEM_PROMPT 的拼装、Planner 的下发逻辑——**M1 写下的所有代码一行没改**。MCP 工具进来后长得和 CalculatorTool 一模一样。这是依赖倒置的第三次胜利，也是对"好的抽象经得起新需求"的最好证明：day004 定义 BaseTool 时根本不知道 MCP 的存在，但它接住了。

### 5.3 异常与回退

MCP 调用比本地调用多了一整层失败面：连接断开、Server 崩溃、超时、协议错误。处理原则沿用 M1 的"错误走 Observation 通道"：

- 调用失败时，适配器捕获异常，返回 `"工具调用失败: {原因}"` 这样的错误字符串喂回 LLM，给它自我修正或换路的机会，**而不是让异常炸穿 ReAct 循环**。
- 连接级别的失败（Server 根本没起来）要在初始化阶段暴露——Fail Fast，别等到任务跑到一半才发现工具全是摆设。

**常见误区**：

- **误区一：把 MCP 工具当"永远在线"。** 本地函数调用几乎不会失败，跨进程/跨网络调用失败是常态。适配器层的 try/except 不是防御过度，是必需品。
- **误区二：在 ReAct 循环里直接写 `session.call_tool`。** 这等于把 MCP 细节泄漏进 Agent 层，换协议或换 Server 时要翻改循环代码。一切外部差异都应该被消化在适配器层——和 day005"Agent 代码里不许直接 import openai"是同一条纪律。

## 第六章：常见误区总清单

把 day016~day020 的误区集中成一张清单，复习时逐条自问"我有没有这么想"：

**协议与架构（day016）**

1. 把 Client 当 Host——Client 是协议管道，不是业务决策者。
2. 一个 Client 连多个 Server——连接模型是 1:1。
3. 自创消息格式替代 JSON-RPC——标准的无聊正是它的价值。
4. 包名用 `mcp` 遮蔽官方包——项目内固定用 `smart_research_agent.mcp_server`。
5. 跳过 initialize 直接调业务方法——生命周期不可跳跃。
6. 不优雅关闭连接——stdio 子进程会变僵尸。

**三原语（day017~018）**

7. Resource 与 Tool 混用——按"有无副作用、谁做决策"分流。
8. 把大段动态数据塞进 Prompt 参数——数据走 Resource，模板走 Prompt。
9. Tool 的 description 敷衍——那是 LLM 选择工具的唯一依据。
10. 以为三原语只是"三种能力"——它们的本质区别是**控制权归属**。

**Server 开发（day019）**

11. stdio 模式下 print 到 stdout——污染协议流，日志走 stderr/文件。
12. 测试里真起子进程/开端口——用 `create_connected_server_and_client_session` 内存内测。
13. docstring 随便写——FastMCP 里 docstring 就是 prompt。
14. 以为 FastMCP 就是 MCP——框架可换，协议概念不变。

**Client 集成（day020）**

15. 跳过握手、不做能力发现——初始化的固定四步一步不能省。
16. 调用失败让异常炸穿循环——错误走 Observation 通道喂回 LLM。
17. 在 Agent 层直接写 MCP 调用——差异消化在适配器层，Agent 只认 BaseTool。
18. 把 MCP 工具当永远在线——跨进程调用失败是常态，适配器必须有兜底。
