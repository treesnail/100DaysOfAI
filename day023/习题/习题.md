# day023 课后习题：MCP 协议测试与文档

> 共 10 题：选择题 3、判断题 2、问答题 3、编程题 2。建议先独立完成，再对照[习题答案](../习题答案/习题答案.md)。

## 一、选择题

**1.** 在 MCP 三层测试结构中，"内存传输集成测试"（`create_connected_server_and_client_session`）与 stdio 端到端测试的关键区别是：

A. 前者不测协议握手，后者测  
B. 前者不起真实子进程、不走操作系统管道，其余协议栈都是真实的  
C. 前者只能测 Tool，后者能测全部三类能力  
D. 前者用 MockLLM，后者用真实 LLM

**2.** 以下哪种 bug **只能**被 stdio 端到端测试发现，内存传输测试无能为力？

A. calculator 对 `"1 +"` 这类非法表达式的容错行为  
B. Server 的 resource 函数里遗留了一行 `print()`，污染了 stdout 上的 JSON-RPC 字节流  
C. Prompt 模板的必填参数推导错误  
D. JSON-RPC 请求缺少 `method` 字段

**3.** `McpClient.stdio()` 内部用 `StdioServerParameters(command=sys.executable, args=["-m", "smart_research_agent.mcp_server.server"], cwd=PROJECT_ROOT)` 起子进程。其中 `command=sys.executable` 的主要目的是：

A. sys.executable 比 "python" 拼写更短  
B. 保证子进程使用与测试进程完全相同的解释器与虚拟环境  
C. sys.executable 启动速度更快  
D. 避免 Windows 下的权限问题

## 二、判断题

## 三、问答题

**6.** `test_mcp_server_unit.py` 中，calculator 收到非法表达式 `"1 +"` 时返回 `"计算失败"` 文本且 `isError=False`；而读取不存在的资源 `research://knowledge/not-exist` 时 Client 侧抛出协议级异常。这两种失败语义有何本质区别？为什么 calculator 选择前者而 knowledge 选择后者？

**7.** `client.py` 中 `discover_capabilities()` 把 SDK 返回的能力对象转换成项目自定义的 `ToolDescriptor`/`ResourceDescriptor`/`PromptDescriptor`，而不是直接把 SDK 类型暴露给上层。这种"防腐层"设计解决了什么问题？代价是什么？

**8.** 测试金字塔要求"顶层端到端测试数量少"。请结合本日的三层耗时（底层约 0.1s、中层约 0.5s、顶层约 3s）解释：为什么把行为细节的穷举放在中层而不是顶层，是工程上的理性选择？如果反过来做会有什么后果？

## 四、编程题

**9.** 为 Server 新增一个 Tool：`word_count(text: str) -> str`，返回文本的字符数与词数（以空白分隔），格式为 `"字符数: N, 词数: M"`。要求：
- 在 `smart_research_agent/mcp_server/server.py` 中用 `@app.tool()` 注册；
- 在 `tests/test_mcp_server_unit.py` 中用内存会话补充两个测试：正常文本计数、空字符串计数；
- 重新运行 `python scripts/dump_capabilities.py`，确认能力文档自动包含新工具。

**10.** 编程实现一个"能力契约守卫"测试，放在 `tests/test_mcp_integration.py` 中：通过 stdio 连接真实 Server，断言以下不变式——
- 每个 Tool 的 `input_schema` 都是合法 JSON Schema（含 `"type": "object"` 与 `"properties"` 键）；
- 每个 Resource 模板的 URI 都以 `research://` 开头；
- 每个 Prompt 至少有一个参数或显式无参数（不允许 None）。

并说明：这类"对能力面整体做不变式断言"的测试，与针对单个能力的测试相比，互补价值在哪里？
