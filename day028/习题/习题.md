## 第一部分：选择题

### 第 1 题（评估指标体系）

关于 AI 系统评估的四大指标维度，下列说法**错误**的是：

- A. 正确性回答"答案对不对"，相关性回答"有没有答非所问"
- B. 安全性可以用"系统提示词里写了禁止泄露"来证明，无需专门测试
- C. 成本维度既包含 token 费用，也包含延迟（P50/P95）
- D. 四个维度必须并立，但权重应由具体场景决定

### 第 2 题（EvaluationHarness 设计）

`EvaluationHarness` 基类把评估流程固化为"加载数据集 → 逐条执行 → 逐条评分 → 汇总报告"四步，并要求子类实现 `execute()` 和 `score()`。这种设计的主要收益是：

- A. 让评估跑得更快
- B. 模板方法模式：骨架冻结保证所有评估行为一致，血肉（怎么调被测系统、怎么打分）留给子类，RAG 评估、Agent 评估可复用同一副骨架
- C. 减少 LLM 调用次数
- D. 让数据集可以不用版本管理

### 第 3 题（LLM-as-a-judge 原理）

"用 LLM 当裁判评估 LLM 的输出"之所以在实践中可靠，最根本的原因是：

- A. 裁判模型一定比被测模型聪明
- B. 判断比创造容易——评估一个答案的质量比从零生成一个高质量答案容易，因此够强的模型按 rubric 打分在统计上可靠
- C. LLM 不会有任何偏差
- D. 裁判打分不需要消耗 token，成本低

### 第 4 题（裁判偏差）

用 LLM 裁判对两个答案 A、B 做成对比较，发现裁判总是倾向于选先出现的那个答案。这种偏差叫什么，正确缓解手段是：

- A. 冗长偏差；在 rubric 里声明长度不加分
- B. 自偏好偏差；换一个模型当裁判
- C. 位置偏差；交换 A/B 的顺序各评一次，取平均或要求两次结论一致
- D. 格式偏差；要求裁判输出 JSON

### 第 5 题（双重评估分工）

day027 的输出质量评估中，"输出是否为合法 JSON、必填字段是否齐全、长度是否在区间内"这类检查应该由规则评分器而非 LLM 裁判完成，最根本的理由是：

- A. 规则评分器代码更简单
- B. 这些是确定性契约问题：规则判定 100% 可复现、零成本、毫秒级；用模型判确定性问题既花钱又引入不必要的概率波动——"能用代码判的，绝不用模型判"
- C. LLM 看不懂 JSON
- D. 规则评分器更容易通过单元测试

## 第五部分：编程题

### 第 14 题（编程题 · 实现一个迷你 Harness）

参照 day025 快照中 `evaluation/harness.py` 的模板方法设计，编写一个**离线可运行**的迷你评估 Harness，评估一个"问答函数"（普通 Python 函数，不涉 LLM）：

```python
def qa_system(question: str) -> str:
    # 被测对象：一个极简规则问答
    return {"1+1 等于几": "2", "中国的首都是哪": "北京"}.get(question, "不知道")
```

要求：

1. 用 dataclass 定义 `EvalCase`（字段：`id`、`input`、`expected`）和 `CaseResult`（字段：`case`、`output`、`passed`）；
2. 实现 `load_dataset()`：从一个 JSONL 字符串（每行一个 JSON：`{"id":..., "input":..., "expected":...}`）解析出 `list[EvalCase]`，解析失败行抛出带行号的 `ValueError`；
3. 实现 `run()`：逐条调用被测函数，正确性判定为"输出**包含** expected 中的关键字符串"，汇总返回 `(通过率, 失败用例id列表)`；
4. 编写至少 4 个 pytest 测试：正常 JSONL 解析、含坏行的 JSONL 抛错且错误信息带行号、全通过时通过率为 1.0 且失败清单为空、部分失败时通过率与失败清单正确；
5. 全部测试离线可跑，不引入新依赖。

提示：通过率的浮点比较用 `pytest.approx`。

### 第 15 题（综合编程题 · 用 MockLLM 驱动双重评估）

基于 day027 快照中的 `MockLLM`（`../../day027/源码/smart-research-agent/smart_research_agent/llm/mock.py`），编写一个离线可运行的双重评估练习，模拟 day027 输出质量评估（`evaluation/output_eval.py`）的核心结构：

1. 实现 `rule_score(output: str) -> float`：规则通道——输出以 `"Final Answer:"` 开头且总长度 ≤ 200 字符得 1.0，否则 0.0；
2. 实现 `judge_score(llm, question: str, output: str) -> float`：裁判通道——组装一段含 rubric 的裁判 Prompt（要求裁判"先给理由，最后一行输出 `分数: X`，X 为 1~5 的整数"），调用 `llm.chat()`，从回复中用正则解析最后一行的 `分数: (\d)` 并归一化到 0~1（除以 5）；解析失败抛 `ValueError`；
3. 实现 `evaluate(llm, question, output)`：总分 = `0.4 * rule_score + 0.6 * judge_score`；
4. 用 MockLLM 编写测试：
   - 裁判回复 `"理由：回答完整准确。\n分数: 5"` 且输出合规时，总分为 1.0；
   - 裁判回复 `"分数: 3"` 且输出不合规（不以 "Final Answer:" 开头）时，总分为 `0.6 * 0.6 = 0.36`（用 `pytest.approx`）；
   - 裁判回复不含 `分数:` 行时抛 `ValueError`；
   - 断言裁判收到的 Prompt 中同时包含原始问题和被评输出（用 `mock_llm.calls` 验证）。
