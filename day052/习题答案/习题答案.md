## 第一部分：选择题

### 第 1 题（全局批与学习率缩放）

**答案：A**

`plan_distributed()` 里两行算术：

```python
global_batch = args.per_device_train_batch_size * args.gradient_accumulation_steps * devices
scaled_lr = scale_learning_rate(base_lr,
                                base_global_batch_size=args.effective_batch_size,
                                new_global_batch_size=global_batch,
                                mode=lr_scaling_mode)
```

代入 `per_device=2` / `accum=4` / `devices=4`：`global_batch = 2 × 4 × 4 = 32`。实测三种法则（基座 `lr = 2e-4`，`effective_batch_size = 8`）：

```text
mode=linear 2e-4 * f(32/8) = 0.0008      ← ×4
mode=sqrt   2e-4 * f(32/8) = 0.0004      ← ×2 = sqrt(4)
mode=none   2e-4 * f(32/8) = 0.0002      ← ×1
```

同一函数在别的批比上：

```text
8->16 linear: 0.0004 | 8->16 sqrt: 0.000282843
8->64 linear: 0.0016 | 8->64 sqrt: 0.000565685
```

- B 错在**设备数必须乘进去**：数据并行不是把同一个批拆开，而是每个设备吃**不同的** micro-batch，梯度是 `D` 份的**求和 / 平均**，所以有效批确实变成 `D` 倍；
- C 把两条法则记反了（`linear` 才给 ×4）；
- D 错——`none` 是合法取值（比例因子恒为 `1.0`），它只在 `devices > 1` 时命中 `plan_distributed()` 的一条**告警**（"梯度被多卡平均后变小而步长不变，训练会明显变慢"），不是异常。本课的设计原则是**把"不缩放"显式化，比让它悄悄发生好**。实测（`lr_scaling_mode="none"`，其余同上）：

  ```text
  devices=1 strategy=zero2 mode=none -> lr 0.0002 | warnings=0
  devices=2 strategy=zero2 mode=none -> lr 0.0002 | warnings=1
  devices=4 strategy=zero2 mode=none -> lr 0.0002 | warnings=1
      - 全局批从 8 放大到 32（4 个设备），但 lr_scaling_mode=none：梯度噪声变小而步长不变，训练会明显变慢。批大小翻倍时通常把学习率同倍放大（线性法则），并重新标定。
  ```

### 第 2 题（ZeRO 的分片规则）

**答案：B**

源码注释就是这条规则的定义：

```text
zero2：切优化器状态 + 梯度，**参数不切**（每个设备仍持有完整权重）
zero3：参数也切（每层前向/反向各 all-gather 一次）
```

实测的**逐项字节分解**（`llama-2-7b` / LoRA `attention_all` `r=8` / 4 个设备）：

| 项 | ddp | zero2 | zero3 |
|----|-----|-------|-------|
| `base_weight_bytes` | 13 476 831 232 | 13 476 831 232（**不变**） | 3 369 207 808（÷4） |
| `base_gradient_bytes` | 0 | 0 | 0 |
| `base_optimizer_bytes` | 0 | 0 | 0 |
| `adapter_weight_bytes` | 16 777 216 | 16 777 216（**不变**） | 4 194 304（÷4） |
| `adapter_gradient_bytes` | 16 777 216 | 4 194 304（÷4） | 4 194 304（÷4） |
| `adapter_optimizer_bytes` | 67 108 864 | 16 777 216（÷4） | 16 777 216（÷4） |
| `as_gib` | 12.645027 | 12.586433 | 3.161257 |

- A 错：zero2 **不切参数**；本模块也**不包含激活显存**（`device_fit_summary()` 的 note 原文是"只比较权重 + 梯度 + 优化器状态，不含激活显存"），所以"多切了激活"这个说法没有对应物；
- C 两条策略反了；
- D 错：`devices == 1` 时 `per_device_memory()` 走 `if strategy == "ddp" or devices == 1` 这条分支，**直接返回基线**并追加一条 note（`"{strategy}：每个设备一份完整副本"`），不抛异常。

### 第 3 题（LoRA 场景下的 zero2 与 zero3）

**答案：B**

- zero2 在 LoRA 上只切"适配器的优化器状态 + 适配器梯度"这两项（基座的梯度与优化器状态本来就是 0）：
  `(8 388 608 × 8 + 8 388 608 × 2) × 3/4 = 62 914 560 B = 60.0 MiB = 0.058594 GiB`。
  实测 `ddp.total_bytes − zero2.total_bytes = 62 914 560 B`，于是 `12.645027 − 0.058594 = 12.586433 → 12.59 GiB`，`memory_saving_factor = 1.00`。
- zero3 才把参数也切开：`13 476 831 232 / 4 = 3 369 207 808 B`，每设备 `3.161257 GiB ≈ 3.16`，`memory_saving_factor = 4.00`。
- 代价是通信：zero2 `25 165 824 B = 0.025 GB`；zero3 `26 978 828 288 B = 26.979 GB`。`plan_distributed()` 的告警原文（4 个设备）：

```text
zero3 的每步通信量是 zero2 的 1072 倍（26.98 GB vs 0.025 GB），而每设备显存只从 12.65 降到 3.16 GiB。**zero3 的显存收益来自切分参数，而它的通信代价正是每层前向都要all-gather 一遍参数**——这笔交换是否值得要用实测吞吐来判断，不能只看显存表。
```

- A 错（zero2 的数字是 12.59 而不是 3.16；3.16 是 zero3）；
- C 错（zero3 的通信量是三个数量级里最大的那个："能跑"不等于"跑得快"）；
- D 错（LoRA 单卡 12.65 GiB，4 个设备上 ddp 仍是 12.65 GiB——它本来就装得进 24 GiB 卡；LoRA 省显存的收益发生在 day051 那张表里，不发生在"多卡"这一步）。

### 第 4 题（混合精度）

**答案：A**

`MIXED_PRECISION_PROFILES` 实测打印：

```text
bf16  dtype=torch.bfloat16  bytes=2  loss_scaling=False  notes=['8 位指数与 fp32 相同：动态范围大，几乎不会溢出', 'Ampere 及之后的缺省选择']
fp16  dtype=torch.float16   bytes=2  loss_scaling=True   notes=['5 位指数：动态范围窄，梯度下溢需要 loss scaling', '10 位尾数：精度略高于 bf16']
fp32  dtype=torch.float32   bytes=4  loss_scaling=False  notes=['没有混合精度收益，只作为对照口径']
```

- B 错：fp16 的**尾数**更多（10 位）、**指数更少**（5 位），因此动态范围**更窄**，容易溢出为 `inf`，所以才需要 loss scaling；
- C 错：字节数一样（都 2 字节），但能表示的数值范围不同——这正是"不需要 loss scaling"的全部理由；
- D 错：fp32 的 `needs_loss_scaling` 是 `False`（它不需要缩放，也没有混合精度收益）。

另外 `plan_distributed()` 在 `mixed_precision="fp16"` 时会追加一条告警，提醒 fp16 在批很大或学习率偏高时容易溢出、且需要 loss scaling。

### 第 5 题（适配器检查点）

**答案：B**

`ADAPTER_FILES = ("adapter_config.json", "adapter_model.json", "training_state.json")`，顺序即写盘顺序。实测（训练 4 步后的适配器）：

```text
adapter_config.json         435 B
adapter_model.json       272918 B
training_state.json        1325 B
合计 274678 B | sha256:4aa1b146abb3
```

`adapter_content_hash()` 的 docstring 写得很直接——**"只覆盖配置与权重，不含训练状态"**：

```python
digest.update(_canonical_bytes({"config": config}))
digest.update(_canonical_bytes({"model": model}))     # training_state 不参与
```

实测证据：把 `training_state.json` 里的 `step` 从 4 改成 999，`load_adapter()` 重算出的哈希**不变**：

```text
哈希（原样）: 57ca0fff35a8
改 training_state 的 step=999 后: 57ca0fff35a8
直接重算: 57ca0fff35a8
```

- A 错（三个文件，缺任何一个都不该被加载）；
- C 错（刻意排除训练状态：把时间戳 / 步数混进去，"权重是不是同一份"这个问题的答案就会随无关量漂移）；
- D 错（`load_adapter()` 先做 `missing` 检查，缺任何一个都抛 `AdapterCheckpointError`，**不返回"部分可用的对象"**——一个缺了 `adapter_config.json` 的目录看着能用，实际会用上默认的 `alpha`，缩放悄悄变一个倍数）。

### 第 6 题（合并验证这道门禁）

**答案：D**

实测 `verify_merge()` 的输出：

```text
检查 557 个上下文 | 逐位一致 True | 最大 logits 差 0.000e+00 | loss 6.3136913150 vs 6.3136913150（差 +0.000e+00）| 通过 True
```

对应的 `MergeVerification` 字段：`contexts_checked=557`、`bitwise_identical=True`、`max_logit_difference=0.0`、`adapter_loss=6.3136913150`、`merged_loss=6.3136913150`、`tolerance=0.0`、`passed=True`。

D 错在**用 loss 判定合并正确性**。`tolerance=0.0`（缺省）要求逐位一致，这不是苛刻：两条路径做的是同一批浮点运算（`W[i][j] + ΔW[j][i]` 一次算完 vs 每次前向现算一次），结果本就应当相同。而 loss 是**标量**——day051 的教训（本题也是同一个坑的第二次出现）就是标量指标会掩盖结构性错误：行 / 列约定混用时训练照常、loss 照常下降、评估指标看起来还不错，但两条路径的 logits 最大差是 `0.0381`。所以门禁比的是**逐位 logits**，不是 loss；`loss` 字段只是给人看的旁证。

A、B、C 都正确（`tolerance < 0` 抛 `PEFTConfigError`；`passed` 的判据是 `bitwise_identical or max_logit_difference <= tolerance`）。

## 第二部分：判断题

### 第 7 题

**错。**

只有 zero3 恰好把三项（权重 / 梯度 / 优化器状态）都除以设备数，`75.31 / 4 = 18.83` 是它的**结果**，不是通则。同一份配置（`llama-2-7b` / 全参微调 / 4 个设备 / 1000 条样本）实测：

| 策略 | 每设备 GiB | 相对单卡 |
|------|-----------|---------|
| ddp | **75.31** | 1.00×（每个设备一份完整副本） |
| zero2 | **28.24** | 2.67×（只切优化器状态与梯度） |
| zero3 | **18.83** | 4.00×（三项都切） |

三者的每步通信量是 `20.215 GB` / `20.215 GB` / `47.169 GB`：**"能不能多卡跑"的答案取决于策略，而不是设备数**。把"除以 D"当通则，会得出"4 卡就能把 7B 全参塞进 24 GB 卡"这种会直接 OOM 的结论。

### 第 8 题

**错。**

"切得更细"恰好反了：zero2 只切**优化器状态与梯度**，zero3 连**参数**一起切。LoRA 场景下 zero2 几乎不省，因为它的优化器状态只覆盖 8 388 608 个适配器参数：

```text
ddp   → 12.645027 GiB
zero2 → 12.586433 GiB   （只省了 62 914 560 B = 60.0 MiB，1.00×）
zero3 →  3.161257 GiB   （4.00×，代价是通信量 0.025 GB → 26.979 GB）
```

一天里的正确说法是：**全参微调里 zero2 是"最划算的一步"（它砍掉最大的一项——优化器状态）；LoRA 里最大的一项是冻结的基座权重，所以只有 zero3 有用。**

### 第 9 题

**错。**

哈希**刻意**只覆盖 `adapter_config.json` 与 `adapter_model.json`（`adapter_content_hash(config=..., model=...)`）。理由：同一个适配器续训一步之后**权重可能没变、但"训到哪了"变了**。哈希要回答的是"**权重是不是同一份**"，把时间戳 / 步数混进去会让这个问题的答案随无关量漂移。实测：把 `training_state.json` 的 `step` 改成 999，哈希仍然是 `57ca0fff35a8`。

"线上跑的是哪一份"由**清单**一起回答：`AdapterManifest` 里同时有 `content_sha256`（权重身份）、`step`、`train_loss`、`learning_rate`、`base_model`、`tags`——身份与元信息**分开存**，而不是把元信息塞进身份。

### 第 10 题

**错。**

生成的脚本 `compile` 是**通过**的（`scripts/lora_pipeline_demo.py` 第 4 节会对三个脚本逐个 `compile(script, f"{name}.py", "exec")`）：

```text
多卡训练（Accelerate）：280 行，compile 通过
合并（merge_and_unload）：76 行，compile 通过
推理（适配器形态）：56 行，compile 通过
```

`TypeError: got multiple values for keyword argument 'gradient_accumulation_steps'` 只在**真正运行到那一行**时才抛（`TrainingArguments(output_dir=..., gradient_accumulation_steps=1, **TRAINING_ARGUMENTS)`），因为 `gradient_accumulation_steps` 同时以关键字和 `**` 展开两种方式出现。这正是它难发现的原因：**语法合法、`compile` 通过、只有跑起来才崩**。

本课的守法是**在渲染阶段就消掉这个键**（`render_accelerate_lora_script` 里）：

```python
training_arguments = args.to_hf_dict()
training_arguments.pop("gradient_accumulation_steps", None)
```

实测核对：

- `args.to_hf_dict()` 有 24 个键，**内嵌进多卡脚本的 JSON 只有 23 个**（`gradient_accumulation_steps` 被 pop 掉）；
- 多卡脚本里 `accelerator = Accelerator(gradient_accumulation_steps=4)`、`TrainingArguments(...)` 处写死 `gradient_accumulation_steps=1`（累积只由 Accelerator 做一次，否则有效批会变成 `accum²` 倍）；
- 对照：单卡脚本 `render_lora_script()`（256 行）的内嵌 JSON **带**这个键，值 `4`。

## 第四部分：简答题

### 第 14 题（两个真实的坑）

**（1）多卡脚本里的重复关键字参数**

- **表征**：生成的脚本能 `compile` 通过、能存盘、看起来一切正常；真跑起来在那行抛

  ```text
  TypeError: ... got multiple values for keyword argument 'gradient_accumulation_steps'
  ```

  （脚本里的写法是 `TrainingArguments(output_dir=args.output_dir, gradient_accumulation_steps=1, **TRAINING_ARGUMENTS)`；当 `TRAINING_ARGUMENTS` 里也有这个键时，Python 直接拒绝调用。用同样签名的最小函数即可复现，实测得到的消息是 `__main__.training_arguments_stub() got multiple values for keyword argument 'gradient_accumulation_steps'`——前缀是函数限定名，关键字名与源码注释里记的那个一字不差。）

- **为什么难发现**：错误不在语法里，也不在类型里，而在**两个合法的参数来源之间**。`compile()` 只看语法，通过；静态类型检查也看不出（两处都是 `int`）；只有真正构造 `TrainingArguments` 时才炸。更麻烦的是这个坑**只在"把 `to_hf_dict()` 的输出原样内嵌进脚本"这条路径上出现**——单卡脚本 `render_lora_script()` 的内嵌 JSON 带这个键是对的，多卡脚本里就成了错的。
- **守住它的手段**：把两个累积开关的**归属**定死。多卡脚本里梯度累积由 `Accelerator(gradient_accumulation_steps=args.gradient_accumulation_steps)` 负责，`TrainingArguments` 一侧写死 `1`；同时**在渲染阶段就把键从内嵌 JSON 里删掉**：

  ```python
  training_arguments = args.to_hf_dict()
  training_arguments.pop("gradient_accumulation_steps", None)
  ```

  并且用测试把"内嵌 JSON 不含这个键""`Accelerator` 行里含这个键"两件事都钉住。实测核对结果：`to_hf_dict()` 24 个键 → 内嵌 JSON 23 个键；另外两处真实原因是：如果两处各累积一次，有效批会变成 `accum²` 倍（4 → 16 倍），而日志里的数字看起来仍然"像个正常值"。

**（2）YAML 1.1 把 `mixed_precision: no` 读成布尔 `False`**

- **表征**：`accelerate_config(mixed_precision="fp32")` 会把 `mixed_precision` 归一化成字符串 `"no"`；渲染成 YAML 时如果按普通字符串写出去，得到 `mixed_precision: no`。这份文本**看起来对**、`accelerate` 也吃得下，但 `yaml.safe_load()` 读回来的是**布尔 `False`**——**渲染出去的配置与读回来的配置不一致，而两边都"没报错"**。实测（PyYAML 6.0.3）：

  ```text
  mixed_precision: no     -> False (bool)
  mixed_precision: yes    -> True (bool)
  mixed_precision: on     -> True (bool)
  mixed_precision: off    -> False (bool)
  mixed_precision: null   -> None (NoneType)
  mixed_precision: bf16   -> 'bf16' (str)
  mixed_precision: fp16   -> 'fp16' (str)
  mixed_precision: "no"   -> 'no' (str)     ← 加了引号才对
  ```

- **为什么难发现**：`no` / `yes` / `on` / `off` / `null` / `~` 是 YAML 1.1 的**布尔与空值别名**，而 YAML 1.1 又被大量实现（含 PyYAML）沿用。于是"一个字符串"与"一个布尔"在**序列化方向**上看起来一模一样（`str(False)` 之外的路径都不显眼），差异只出现在**反序列化方向**；而生成配置的人往往不会把配置读回来逐键核对。等到 `False` 传进 `accelerate`，它既不是 `"no"` 也不是 `"bf16"`，`mixed_precision` 就变成了"未指定"——训练仍会跑，只是精度悄悄回到了 fp32。
- **守住它的手段**：两层。
  1. **渲染时就加引号**：`_yaml_scalar()` 显式枚举 YAML 1.1 的保留字（`{"no", "yes", "on", "off", "true", "false", "null", "~", "none", ""}`），命中就 `json.dumps(text, ensure_ascii=False)`。实测渲染出的那一行是 `mixed_precision: "no"`（`bf16` / `fp16` 不加引号，因为它们不是保留字）。
  2. **把它做成一条往返回归**：渲染出的 YAML 必须被 `yaml.safe_load()` 解析回来**逐键比对**——"写出去"与"读回来"必须相等。**只测一个方向的序列化等于没测。**

| 设备 | 策略 | 每设备 GiB | 省× | 通信 / 步 | 全局批 | 缩放后 lr | 告警 |

（通信量的原始字节：2 设备 zero2 = `16 777 216 B`、4 设备 zero2 = `25 165 824 B`、2 设备 zero3 = `26 970 439 680 B`、4 设备 zero3 = `26 978 828 288 B`。zero3 的那一项几乎与设备数无关，因为它是"把 6 738 415 616 个基座参数 all-gather 两次"：`2 × 6 738 415 616 × 2 = 26 953 662 464 B`，梯度项只占剩下的 `16.8 / 25.2 MB`。）

**哪一种组合最"划算"？**

先看预算：6 种组合里**没有一个超过 24 GiB**（最大是 ddp 的 12.65 GiB），所以"放得下"这一关拦不住任何组合；决定胜负的是**通信量**。

| 候选 | 每设备显存 | 通信 / 步 | 判断 |
|------|-----------|----------|------|
| 4 设备 ddp | 12.65 GiB | 0.025 GB | 可用，但比 zero2 多占 60 MiB |
| **4 设备 zero2** | **12.59 GiB** | **0.025 GB** | **最划算**：显存最小且在 24 GiB 内，通信与 ddp 完全相同，0 条告警 |
| 4 设备 zero3 | 3.16 GiB | 26.979 GB | 用 **1072 倍**通信换 9.43 GiB 显存；已经放得下时是纯亏损 |
| 2 设备 zero2 | 12.61 GiB | 0.017 GB | 通信更省，但全局批只有 16（lr 只能 0.0004），吞吐减半 |
| 2 设备 zero3 | 6.32 GiB | 26.970 GB | 同样不划算（1608 倍通信） |

**结论：4 个设备 + `zero2` 最划算。** 这里的关键不是"哪个策略切得最狠"，而是**"要不要为已经放得下的模型付通信费"**：

1. LoRA 场景下每设备显存与设备数几乎无关（12.65 → 12.59）——因为最大的一项是**冻结的基座权重**，`zero2` 不切它。所以"多卡"在 LoRA 上的收益是**吞吐**（全局批 8 → 32、`lr` 可线性放大到 0.0008），不是单卡显存；
2. `zero3` 是唯一让显存随设备数下降的策略（2.00× / 4.00×），但它的通信代价来自"每层前向 / 反向各 all-gather 一遍参数"，**这笔成本是每个 step 都付、每一次前向都付**；
3. 只有当"每个设备装不下 12.59 GiB"（比如序列长度带来的激活显存把预算挤爆、或单卡预算只有 8 GiB）时，`zero3` 才从"纯亏损"变成"唯一的出路"——**"能跑"不等于"跑得快"，这两个结论要分开下**。

   差值 `10 × (base − adapter) ≈ 10 × base`——因为 `adapter_ratio = round(274 678 / 13 476 831 232, 8) = 2.038e-05`（精确值是 `2.0381497e-05`，即**适配器只有基座的约 1/49 064**；demo 里打印的"小 49068 倍"是用四舍五入到 8 位小数的 `adapter_ratio` 反算出来的，两者差在末位，不影响"差 10 倍"这个结论）。换句话说：**"一个基座 + N 个适配器"省下的是 `(N−1)` 份基座，不是"N 份模型变成了小模型"。** 适配器本身没变小，是**被复制的那个东西变便宜了**。
8. **注册表**：`adapter_registry()` 刻意保留 `base_model` 与 `short_hash`——前者回答"这个适配器能不能挂到我的基座上"（**基座不匹配不会报错，只会给出莫名其妙的结果**，`render_inference_script()` 生成的推理脚本会在清单与 `--base_model` 不一致时打印警告），后者回答"线上到底跑的哪一份"。

> 一个值得注意但**不影响正确性**的细节：`training_state.json` 里内嵌了 `training_arguments`，所以它的体积随训练超参变化。实测同一份（未训练的）权重、两组不同的 `SFTTrainingArgs`：
>
> ```text
> A(lr=8):   {'adapter_config.json': 435, 'adapter_model.json': 190847, 'training_state.json': 1325} 合计 192607 B | sha256:57ca0fff35a8
> B(lr=2e-4): {'adapter_config.json': 435, 'adapter_model.json': 190847, 'training_state.json': 1331} 合计 192613 B | sha256:57ca0fff35a8
> ```
>
> 状态文件 1325 → 1331 B，**哈希不变**（`57ca0fff35a8`）——这正是第 5 题那条"哈希只回答权重身份"的实测证据。
