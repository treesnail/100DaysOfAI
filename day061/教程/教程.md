## 第一章：为什么 M6 要从"读文件"开始

### 1.1 day060 留下的伏笔

day060 的结语里写着：

> 下一阶段进入 **M6：RAG 应用开发**（day061 起）——文档解析、分块策略、
> 向量数据库、混合检索、重排序与生产化部署。届时今天这套"部署 + 切换 + 验证"
> 的基础设施会迎来它的第一个真实负载：**知识库的更新同样需要版本、
> 同样需要灰度、同样需要一个能证明"检索到的确实是新索引"的绑定校验。**

M5 解决的是"模型怎么上线"，M6 解决的是"知识怎么上线"。而知识上线的第一步，
是把磁盘上那些**格式各异**的文件变成一串**可以被切成片段、可以被向量化**的东西。

### 1.2 下游只应该认识一种东西

如果分块器要分别处理 Markdown 的标题、PDF 的文本流、docx 的表格，
那么每加一种格式就要动一次分块逻辑——而分块策略本身已经够复杂了
（day062 要讲固定长度、递归、语义、结构四种）。因此今天先做一次**结构归一**：

```text
各种格式  →  Document（全文 + 块序列 + 元数据 + 内容指纹）  →  下游只认识 Document
```

### 1.3 三条贯穿全包的纪律

| 纪律 | 具体表现 | 反例（如果没有它） |
|------|---------|------------------|
| **只分类，不丢弃** | 三个结构解析器都不允许"未识别的行被静默吞掉" | 一份文档比原文短，而谁也不知道少了什么 |
| **能力边界进元数据** | PDF 的 CID 字体、DOCX 读不到的部件、编码的"没把握"都以字段形式跟着文档走 | "没抽到的内容"被当成"文档里本来就没有" |
| **同一份内容只有一个指纹** | `doc_id = sha256(规范化文本)[:16]` | 同一份规范存了两个渠道就变成两份，去重失效 |

第二条是本日最容易被跳过、代价最大的一条。举一个具体的例子：
一份中文 PDF 用 Identity-H 编码（中文 PDF 里非常常见），
本模块抽出来会是空文本或乱码——**这不是 bug，是规范层面的不可判定**
（PDF 32000-1 §9.10.2 的原话：如果这些方法都得不到 Unicode 值，
就无法确定字符码代表什么）。但如果这件事不被写下来，
三个月后有人问"为什么知识库里搜不到那份 PDF"时，
只能从"解析结果为空"倒推，而"解析结果为空"与"文档里本来就没内容"
在结果里长得一模一样。

因此 `Document.metadata` 里有 `pdf_cid_font_detected`、`encoding_confident`、
`docx_parts_not_read` 这样的字段——**它们是给未来的排查留的线索。**

## 第二章：归一化的形状

### 2.1 六种块

```text
heading      标题（Markdown 的 # / HTML 的 h1~h6 / DOCX 的 pStyle=Heading1）
paragraph    段落（空行分段 / <p> / w:p / PDF 的行距分段）
code         代码块（围栏 / <pre>）——day062 不该把它从中间切开
list_item    列表项（- / <li> / w:numPr）——保留层级信息
table        表格（GFM 表格 / <table> / w:tbl）——保留行列结构
quote        引用（> / <blockquote>）——引用溯源
```

**六种是刻意保持得很少的**：每一种都要有下游消费者。加进来一个"没人用"的
类型只会让 day062 的分块器多一个要考虑的分支。

实测（demo 第 2 节，一份 264 字符的 Markdown）：

```text
2de1fccfba62a249 text/markdown 264 字符 | 9 块
  （heading=2 paragraph=2 code=1 list_item=2 table=1 quote=1）| docs/design.md
```

### 2.2 `doc_id` 是内容指纹，不是文件名

```python
doc_id = sha256(规范化全文)[:16]
```

三条性质，每条都有具体用途：

1. **同一份内容从两个路径读进来得到同一个 id**：复制了一份文件、从两个渠道
   各下了一份同一份规范，在入库时会被认成同一份文档；
2. **改一个字节 id 就变**：id 变了说明内容变了——这与 day058 的三元组
   "内容寻址"、day060 的部署绑定完全是同一种设计；
3. **它不包含文件名、路径与时间**：那些是"这份内容放在哪"，而不是"这是哪份内容"。

因此**规范化规则必须被写死并被测试覆盖**：

| 规则 | 消除的差异 |
|------|-----------|
| `\r\n` / `\r` → `\n` | Windows 与 Unix 换行 |
| 去掉每行行尾空白 | 编辑器留下的尾随空格 |
| 连续空行折叠到 1 个 | 导出的多余空行 |
| 去掉首尾空白并在结尾补一个 `\n` | 有无结尾换行 |

最后一条的"补一个换行"值得单独说：**一个"没有结尾换行"的文件与
"有一个结尾换行"的文件是同一份内容**，而它们在字节上不同。统一补一个，
让两者得到同一个指纹。

不做的事也要说清楚：**不做 Unicode 规范化**（不把全角逗号换成半角、
不折叠空格）。理由是中英文混排的技术文档里，全角逗号与半角逗号经常是
内容差异而不是格式差异，把它们合并会改变检索结果——
而这类"看起来更干净"的规范化最难被发现。

### 2.3 全文只能由块拼出

第一版的 `make_document` 允许调用方传一个 `text` 参数覆盖拼接结果，
理由是"加载器可能有更准确的全文"。它被删掉了：

> **那个参数的存在本身就是在允许两份内容不一致**，而一旦不一致，
> 两份都会有人依赖——这类缺陷不会报错，只会让"检索命中的段落"
> 与"引用到的原文"长期对不上。

留下一条把接口形状钉住的测试：

```python
def test_full_text_is_always_derived_from_the_blocks():
    parameters = inspect.signature(make_document).parameters
    assert "text" not in parameters
    assert set(parameters) == {"source", "media_type", "blocks", "metadata"}
```

**删掉一个参数，同时留下"为什么可以删"的证据**——这样将来谁加回它，测试会立刻变红。

## 第三章：类型识别与编码 —— 两个"猜"的地方

### 3.1 类型识别：内容优先，冲突必报

| 后缀 | 内容 | 结果 |
|------|------|------|
| 有 | 有且一致 | 按它 |
| 有 | 有但不同 | **按内容**，`conflict=True` |
| 有 | 无 | 按后缀 |
| 无 | 有 | 按内容 |
| 无 | 无 | `text/plain`（`decided_by="fallback"`） |

实测（demo 第 1 节）：

```text
guide.md       → text/markdown（按 suffix 判断）
fake.txt       → application/pdf（**冲突**：后缀说 text/plain、内容说 application/pdf；按内容处理）
report.docx    → ...wordprocessingml.document（按 suffix 判断）
noextension    → text/plain（按 fallback 判断）
```

只信后缀的代价在真实数据里非常具体：**导出工具改名不改内容**、
**下载器按 URL 猜后缀**、**磁盘上有人手工改过扩展名**。
把它报成一个"有冲突但按内容处理"的记录，比静默按后缀处理要安全得多——
后者会得到一个"解析成功但内容全空"的文档。

`docx` 是唯一一处**刻意的特例**：它的魔数 `PK\x03\x04` 只能证明"这是一个 ZIP"
（xlsx / pptx 也是），因此"后缀 docx + 内容 ZIP"不算冲突——
那是同一件事的两种描述，最终结论由 docx 加载器在解包时给出。

### 3.2 编码探测：五步固定顺序

| 步骤 | 规则 | 为什么排在这里 |
|------|------|---------------|
| 1 | BOM（utf-32-be / utf-32-le / utf-8-sig / utf-16-be / utf-16-le） | 有 BOM 就是明示，不需要猜 |
| 2 | 二进制探测（头 8 KiB 出现 NUL 即拒收） | 不是文本就不该进这条链路 |
| 3 | utf-8 **严格**解码 | 严格让"成功"本身成为可靠证据 |
| 4 | `gb18030` | GB18030 是 GBK 与 GB2312 的超集，一个编码覆盖三代 |
| 5 | `latin-1` | 永不失败，因此只能排最后 |

实测：

```text
utf-8 中文          → utf-8（按 strict 判断，可信）
GB18030 中文        → gb18030（按 fallback 判断，可信）
带 BOM 的 utf-16-le → utf-16-le（按 bom 判断，可信）
两者都不成立        → latin-1（按 latin-1 判断，**不可信**）
```

第 3 步的"严格"是关键：UTF-8 有一个很强的性质——**不合法的字节序列很少**，
因此"严格解码成功"本身就是一条相当可靠的证据。反过来，如果用
`errors="replace"` 去试，那么任何字节序列都会"成功"，这个判据就完全失效了。

### 3.3 BOM 的顺序敏感

```text
UTF-32-LE 的 BOM：FF FE 00 00
UTF-16-LE 的 BOM：FF FE
```

**UTF-32-LE 的 BOM 以 UTF-16-LE 的 BOM 开头**。如果先判 UTF-16-LE，
一份 UTF-32 的文件会被解成"每个字符后面跟一个 NUL"，而那种乱码看起来
很像文件损坏——于是排查会从"文件是不是坏了"开始，而真正的原因是
**我们查表的顺序**。

### 3.4 latin-1 是最后一张网

```python
DecodedText(text=..., encoding="latin-1", decided_by="latin-1", confident=False)
```

- 它**保证总能返回一个字符串**：调用方需要处理的是 `confident=False`
  这种情形，而不是异常；
- 因此它必须被**显式标记**：`encoding_confident=false` 说明中文多半已是乱码，
  而乱码会一路通过分块、向量化与检索，最后以一个"模型答非所问"的形式
  出现在用户面前。**把它做成一个字段，而不是一个沉默。**

这与 day059 门禁的 `when_missing` 一列是同一种表达。

顺带说一句测试里踩到的坑：`b"\xff\xfe\xfd"` 看起来像"一个随机字节序列"，
但它其实**以 UTF-16-LE 的 BOM 开头**，会被第 1 步接走，
而因为字节数是奇数会解码失败。真正的"走投无路"的样本是
`b"\x80\x80"`——`0x80` 在 utf-8 与 gb18030 里都是非法起始字节。

### 3.5 二进制探测：判据只有 NUL 一个

```python
def looks_binary(data): return b"\x00" in data[:BINARY_SCAN_BYTES]
```

只用 NUL 一个判据，是因为它在文本里几乎不可能出现（UTF-16 的文本
已经由 BOM 那一步先拦下了）。更复杂的启发式（控制字符比例、
可打印字符比例）会带来误判，而**误判的代价是不对称的**：

```text
把文本判成二进制 → 一份正常文档入库失败（可见、可修）
把二进制判成文本 → 得到一段明显是乱的文本（而且 confident 标记会提示它）
```

## 第四章：五个加载器

### 4.1 Markdown：结构写在文本里的格式

| 结构 | 规范条款 |
|------|---------|
| ATX 标题 | CommonMark v0.31.2 §4.2（**`#` 后必须有空格**） |
| 围栏代码块 | CommonMark v0.31.2 §4.5 |
| 表格 | GFM v0.29-gfm §4.10 |
| 列表项 | CommonMark v0.31.2 §5.2 / §5.3 |
| 引用 | CommonMark v0.31.2 §5.1 |
| front matter | Jekyll / Hugo 约定（文件**最开头**由 `---` 包围） |

那个"必须有一个空格"不是形式主义：**`#标签` 是话题标签而不是标题**，
而中文技术文档里 `#话题` 很常见。把它当标题会让文档结构凭空多出一节。

三处刻意的取舍：

1. **只做"结构抽取"，不做 Markdown 渲染**。M6 的下游要的是"这句话在哪一段、
   哪一节"，而不是"它渲染出来长什么样"。行内标记（`**粗体**`、`[链接](url)`）
   原样保留还有一个副作用：**引用时能给出原文**；
2. **未识别的行不会被丢掉**。任何不匹配已知结构的行都归入当前段落。
   这一点由一条"逐行核对"的测试守着：

   ```python
   def test_every_non_blank_line_survives_parsing():
       # 去掉 Markdown 标记之后，原文里每一个非空行都必须能在某一块里找到
   ```

3. **front matter 进元数据，不进正文**。把它当正文会让每一份文档的前几行
   都是同一堆字段名，而检索 `tags` 这种词会命中所有文档。解析只认
   `key: value` 与 `key: [a, b]` 两种形式——**不引入一个只为了读六行头的依赖**。

### 4.2 HTML：标记比内容多的格式

一份从网页另存的文档，正文字符可能只有 3 KB，而标签有 30 KB。
如果不做剥离就入库，检索"配置"这个词会命中页面的埋点脚本——
**而那种命中看起来完全正常**。

为什么用标准库 `html.parser` 而不是正则或第三方解析器：

| 方案 | 问题 |
|------|------|
| 正则 | HTML 不是正则语言。属性里的 `>`、注释里的标签都会让它出错，而**出错的样子是"少了一段内容"** |
| BeautifulSoup / lxml | 引入依赖，且它们会顺手做编码嗅探与容错修复——而"容错修复"会让"解析结果与原文哪里不同"不可核对 |
| `html.parser` | 事件式，**没有隐式修复**，行为完全可预测 |

实测（demo 第 3 节）：

```text
解析规则：
  整体跳过     script, style, noscript, template
  标题         h1 ~ h6
  段落与列表    p / li（ul、ol 记层级）
  引用与代码    blockquote / pre
  表格         table / tr / td / th
  容器         div, section, article, header, footer, main …

c9c2944086436e7d text/html 100 字符 | 6 块（heading=1 paragraph=1 list_item=2 table=1 quote=1）
  元数据：title='RAG 入门' lang='zh-CN' table_count=1
  埋点脚本是否被剥掉：True
```

两个细节：

- **容器标签只作为块边界**（先落块），不产生独立的块——`<div>` 没有语义内容；
- **实体解码是必须的**：中文网页里 `&nbsp;` 与全角空格混用是常态，
  不解码的话检索会拿一段实体去匹配。

### 4.3 DOCX：ZIP 包里的 OOXML

`.docx` 的本质是一个 ZIP 包，正文在 `word/document.xml` 里。
Microsoft 官方文档给出的最小结构（引 ISO/IEC 29500）是：

```xml
<w:document xmlns:w="http://schemas.openxmlformats.org/wordprocessingml/2006/main">
  <w:body>
    <w:p><w:r><w:t>文本在这里</w:t></w:r></w:p>
  </w:body>
</w:document>
```

命名空间 URI **必须按完整形式匹配**：`ElementTree` 里标签名是 `{uri}local`，
用 `"w:t"` 去查会一个都找不到——而"找不到"的表现是**解析成功但内容为空**。

三处刻意的处理：

1. **只读 `word/document.xml`**：页眉页脚、脚注、批注、文本框里的内容读不到。
   这是已知边界，写进元数据（`docx_parts_not_read`）而不是假装没有；
2. **`w:t` 之间不加分隔符**：同一个段落里的多个 run 是"同一句话的不同格式片段"
   （例如"**注意**：……"），它们之间本来就没有空格，加分隔符会把一个词从中间切开；
3. **`w:tab` / `w:br` 会变成空格与换行**：它们在 XML 里是独立标签、没有文本内容，
   不显式处理就会静默丢掉——而丢掉之后"第 1 行"与"第 2 行"会粘成"第 1 行第 2 行"。

另外加了一道护栏：**只解压一个部件**，不做整包解压，
因此一个恶意的 zip 炸弹（高压缩比的超大文件）无从展开。

### 4.4 PDF：为打印而设计的格式

PDF 描述的是"每个字符画在纸上的哪个位置"，而不是"这是一段话"。
因此"从 PDF 提取文本"本质上是一次**逆向工程**：

```text
1. 扫描文件里全部 stream ... endstream 段
2. 用 zlib 解 FlateDecode（§7.4）；解不开就按原文用
3. 在内容流里跑一个小型词法分析器，识别文本操作符
4. 把"一串字符 + 它在页面上的纵坐标"收集成行，再按行距把行聚成段落
```

认识的操作符（demo 第 5 节）：

| 操作符 | 含义 | 规范条款 |
|--------|------|---------|
| `BT` / `ET` | 文本对象的开始与结束 | §9.4.1 |
| `Td` / `TD` / `T*` / `Tm` | 文本定位 | §9.4.2 |
| `Tj` / `'` / `"` / `TJ` | 显示文本（`TJ` 数组里的负位移判为空格） | §9.4.3 |
| `Tf` | 选字体（只记录，不做字形映射） | §9.3 |

**行距分段是本模块唯一的版面推断**：相邻两行的纵坐标差超过
**中位行距的 1.5 倍**时判为段落边界。用中位数而不是平均值，
因为标题与图注会把平均值抬到"正常行距的两倍"，于是所有正常的段落边界
都判不出来——而那种失效看起来只是"段落变少了"。

四条边界（**这一段比上面重要**）：

1. **Identity-H 编码的 CID 字体**：字符码是字形索引而不是 Unicode。
   规范 §9.10.2 判定为**不可确定**——这不是本模块的缺陷，而是规范层面的
   不可判定。元数据里有 `pdf_cid_font_detected=true` 与一条明确的告警；
2. **不以文本形式存储的内容**：扫描件（整页是图片）、矢量轮廓化的文字；
3. **阅读顺序的完全还原**：双栏排版、表格、脚注会被读成"按纵坐标排序的行流"；
4. **加密的 PDF**：`/Encrypt` 出现即拒收，而不是返回一堆乱码。

第 4 条值得单独说：**返回一堆乱码比拒收更糟**——乱码会一路走进索引，
而且看不出来。这与 day060 把"占位吞吐"到处标注是待替换值、day059 把
"缺证据"判成不通过是同一条纪律：**宁可说"不知道"，不要给一个看起来对的错答案。**

与 pypdf（6.18.0，2026-09-08）/ pdfplumber（0.11.10）的关系写在模块 docstring 里：
它们质量远高于本模块，本课程不复用它们**只为保证离线零依赖**，
不是因为在质量上等价。

### 4.5 三个真实的解析缺陷（本课踩到的）

**缺陷一：HTML 漏传层级 → 整份 HTML 解析失败。**

`Block` 会校验标题层级落在 1~6，而 `_flush` 里只给列表项传了 `level`：

```python
if kind == BLOCK_LIST_ITEM:
    self.blocks.append(Block(kind=kind, text=text, level=level))
else:
    self.blocks.append(Block(kind=kind or BLOCK_PARAGRAPH, text=text))   # 标题丢了 level
```

表现是整份 HTML 变成 `[error]`：

```text
docs/page.html 解析失败：标题层级必须是 1~6，收到 0
```

值得记住的是**它为什么会被立刻发现**：`Block` 的构造期校验把
"漏传一个字段"变成了一个响亮的错误，而不是一个 level=0 的标题
悄悄进入下游。这与 day060 把形态与必填字段绑定是同一种做法。

**缺陷二：嵌套列表粘成一个块。**

`_open` 只在"类型不同"时落块，而 `<li>外层<ul><li>内层` 之间**没有结束标签**，
于是两个 `li` 都被当成同一个块：

```text
期望 [0, 1]（外层 0、内层 1）  实际 [1]（粘成一个，层级取最后一次的）
```

修法是给"同一类型的相邻块"一个 `force=True`：

```python
def _open(self, kind, *, level=0, force=False):
    if force or (self._kind and self._kind != kind):
        self._flush()
```

相邻的 `<p>` 不会遇到这个问题（它们之间一定有一个 `</p>`），
所以只有 `li` 与标题需要 `force`。

**缺陷三：PDF 收尾多出一个空行，以及一条假告警。**

```python
state.commit_line()          # 无条件落行 → 末尾必然多一个空行
if state.current:            # 改为：还有内容才落
    state.commit_line()
```

两个后果都很难看：单测里 `lines[-1][1]` 永远是空串；
而"未压缩的内容流"（完全合法的写法）会带着一条"没有任何一条流解压成功"
的诊断，让"这份 PDF 有问题"这个信号被噪声稀释。修法是两个：收尾按内容落行、
告警改成"既没解压成功、也没抽到文本"才发。

### 4.6 两处被删掉的恒真分支

**第一处：`_group_paragraphs` 结尾的 `if buffer`。**

`kept` 非空时循环至少执行一次，因此那个条件恒为真——覆盖率报告指出它不可达。
与 day059 被删掉的"至少要有一个无依赖阶段"是同一种清理：

> **一条恒为真的断言不是保护，而是噪声。**

**第二处：`_string_token` 的兜底返回。**

```python
    ...
    return ""      # 永远执行不到：调用方只会传 "str" 与 "arr"
```

它会让"传错了类型"变成一个**静默的空字符串**。删掉之后函数只有两个出口，
两个都可到达。

## 第五章：批量入库

### 5.1 内容指纹去重：先看到的留下

```text
文档 → sha256(规范化文本)[:16] → 先看到的留下，后来者标记 duplicate_of
```

"先看到"的定义必须是**确定的**：`ingest_dir` 会把文件列表**排序之后**再处理。
这不是洁癖——day057 的"可复现版本链"、day058 的"确定性 run_id"、
day060 的"确定性分桶"都在同一个位置上：

> **同一份输入要在任何机器上得到同一份输出**，否则"这次入库比上次少了三个文档"
> 永远说不清为什么。

实测（demo 第 6 节，9 个文件）：

```text
9 个文件 → 6 份文档 | ok 6 / 重复 1 / 失败 2 | 478 字符
   [ok] docs/guide.md | text/markdown | 264 字符 / 9 块 | 2de1fccfba62a249
   [重复] docs/guide-copy.md（与 docs/guide.md 内容相同）
   [error] docs/broken.txt —— 看起来是二进制文件（头 8192 字节里出现 NUL）
   [error] docs/fake.pdf —— 不是 PDF（头四个字节不是 %PDF-）
```

### 5.2 三类状态

| 状态 | 判据 | 含义 |
|------|------|------|
| `ok` | 解析成功且首次出现 | 会进知识库 |
| `duplicate` | 与前一份内容相同 | **数据治理问题，不是失败问题** |
| `error` | 不在支持范围 / 解析失败 | 需要人工看一眼 |

三个键**恒存在**（取值为 0 也在）：报告的表头不该随内容变化，
否则两张报告没法逐列对比。这与 day060 的 `block_counts` 固定六类块是同一条理由。

### 5.3 报错分两类，而且只有一类被吞掉

```text
DocumentError（含 UnsupportedDocument）  记进报告的 error 字段，这一批继续
其余异常                                  **向上抛出**
```

第二行是刻意的：把"我们自己的 bug"记成报告里的一行错误，会让它永远不被修——
因为报告看起来"只是一份文件失败了"。这与 day059 把 `blocked` 与 `failed` 分开、
day060 把"未知机型"与"没用过这个机型"分开是同一条纪律：

> **"做不到"要被记成结论，"出错了"要响亮。**

### 5.4 与知识库的接缝

`IngestReport.knowledge_records()` 的字段只有四个，而且**刻意不做分块**：

```python
{"doc_id": "2de1fccfba62a249", "source": "docs/design.md", "text": "…", "metadata": {...}}
```

这个形状就是 day009 的 `VectorStore.add` 需要的。
**今天交出去的是整份文档，明天交出去的是文档切出来的片段，而接口形状不变**——
这正是先做归一化的价值。

## 第六章：接入 API 与配置

### 6.1 四个端点

| 端点 | 方法 | 回答什么 |
|------|------|---------|
| `/documents/loaders` | GET | 五个加载器、编码链、六张格式对照表、**不能做什么** |
| `/documents/detect` | POST | 这份文件是什么、这个判断是怎么来的、编码可不可信 |
| `/documents/parse` | POST | 归一化后的文档（含块明细与内容指纹） |
| `/documents/ingest` | POST | 一批文件的三类状态、块统计、去重结果 |

实测（demo 第 7 节）：

```text
GET  /documents/loaders  → 媒体类型 5 种 / 加载器 5 个 / 编码链 5 步 / 限制 5 条
POST /documents/detect   → fake.txt → application/pdf（**冲突**：后缀说 text/plain、内容说 application/pdf；按内容处理）
POST /documents/parse    → 2de1fccfba62a249 text/markdown 264 字符 | 9 块 | design.md
POST /documents/ingest   → 3 个文件 → 1 份文档 | ok 1 / 重复 1 / 失败 1 | 264 字符
```

四个端点全部**只读或纯计算**：不写磁盘、不联网、**不遍历目录**、不留状态。
与 day059/060 的取舍同源——**一个要读整个目录的流程不该挂在一个 HTTP 请求上**；
目录遍历与批量入库由 `scripts/documents_demo.py` 承担。

两处与前两天共享的形状：

- **输入是"调用方带来的事实"**（这里是文件字节，day060 是端点自述与实测延迟），
  因此同一个请求体永远得到同一个响应；
- **来源标签留空时用显式占位名** `<inline>`，而不是空串——它明确说出了
  "这份内容没有文件名"这件事。

### 6.2 错误码语言

| 情况 | 错误码 | 例子 |
|------|--------|------|
| **请求形状**不对 | 422 | 字段类型错误 |
| **业务规则**不允许 | 400 | base64 非法、内容为空、未知媒体类型、加密 PDF、缺 `document.xml`、二进制 |

还有一种情况**既不是 400 也不是 422**：一批里某个文件"不在支持范围"——
它走**报告路径**（记成 `error` 条目，整批继续）。缺数据/坏文件是结论，不是错误。

### 6.3 配置项（4 个）

```python
documents_max_file_mib: float = 32.0        # 单份文件的解析上限（在入口拦一次）
documents_dir: str = "data/documents"       # 演示与批量入库默认扫描的目录
documents_text_encoding_hint: str = "utf-8" # 本项目文档以什么编码为主（说明用）
documents_ingest_limit: int = 0             # 每个目录最多处理多少个文件（0 = 不限制）
```

这一组分成三小类，**它们出问题时表现完全不同**：

```text
大小上限   超出即报错，看得见
编码兜底   只影响"怎么猜"，猜错时表现为乱码
目录约定   只影响演示脚本往哪读，不影响任何判定
```

`documents_ingest_limit` 的缺省 0（不限制）是刻意的：截断会让"入库结果"
取决于目录规模，而那种依赖一旦存在，报告里的"文档数"就不再是一份
可以被比较的数字。

## 第八章：今日总结 —— 三条可以带走的判断

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|---------|
| 六种块、五种媒体类型 | 每一种块都要有下游消费者，一个加载器只能对应一种格式 | `types.BLOCK_KINDS` / `base.MEDIA_TYPES` |
| `doc_id` 是内容指纹 | 同一份内容换个文件名还是同一份；改一个字节就是两份 | `types.content_id` |
| 规范化规则是接口的一部分 | 改它等于让历史索引全部失效 | `types.normalize_text` |
| 不做 Unicode 规范化 | 全角逗号常是内容差异而不是格式差异 | `normalize_text` 的 docstring |
| 全文只能由块拼出 | 两份内容不一致时，两份都会有人依赖 | `make_document` 的签名测试 |
| 类型识别内容优先 | 导出工具改名不改内容、下载器按 URL 猜后缀 | `detect_media_type` |
| 冲突必报 | "文件被人改过"的第一手证据 | `MediaTypeDetection.conflict` |
| docx 的 ZIP 签名不算冲突 | 那是同一件事的两种描述 | `detect_media_type` 的特例 |
| 编码五步固定顺序 | "成功"本身要成为可靠证据（严格解码） | `decode_bytes` |
| UTF-32 的前缀与 UTF-16 相同 | 顺序写反会得到"每个字符后跟一个 NUL" | `BOMS` 的表序 |
| latin-1 只能排最后 | 它永不失败，因此结果必须标记为不可信 | `DecodedText.confident` |
| 二进制探测只看 NUL | 误判的代价不对称 | `looks_binary` |
| Markdown 不做渲染 | 下游要的是"在哪一段"，不是"长什么样" | `MarkdownLoader` 的取舍 |
| 未识别的行归入段落 | 结构化解析最容易犯的错是让内容消失 | 逐行核对的测试 |
| front matter 进元数据 | 当正文会让检索命中所有文档 | `split_front_matter` |
| HTML 用标准库 | 第三方解析器的"容错修复"让差异不可核对 | `HtmlStructureParser` |
| 脚本与样式整体跳过 | 不剥干净会让"配置"这个词命中埋点脚本 | `SKIP_TAGS` |
| 容器标签只作块边界 | `<div>` 没有语义内容 | `CONTAINER_TAGS` |
| DOCX 只读一个部件 | 页眉页脚读不到——**这一条要写进元数据** | `PARTS_NOT_READ` |
| `w:t` 之间不加分隔符 | 多个 run 是同一句话的不同格式片段 | `_text_of` |
| PDF 用中位数判段落 | 标题与图注会把平均值拉飞 | `PARAGRAPH_GAP_FACTOR` |
| CID 字体是规范级不可判定 | §9.10.2 的原话：无法确定字符码代表什么 | `CID_MARKERS` |
| 加密 PDF 拒收而不是给乱码 | 乱码会一路走进索引，而且看不出来 | `ENCRYPT_MARKER` |
| 去重按内容指纹、先看到的留下 | 顺序就是优先级，因此结果与遍历顺序无关 | `DocumentIngestor.ingest_bytes` |
| 重复单独一态 | 数据治理问题 ≠ 失败问题 | `IngestEntry.status` |
| 只吞"我们认识的失败" | 把自己的 bug 记成一行错误，会让它永远不被修 | `ingest_bytes` 的 except |
| 删掉恒真的分支 | 一条永远为真的检查不是保护，而是噪声 | `_group_paragraphs` |
| 不留永不到达的兜底返回 | 它会让"传错了类型"变成静默的空字符串 | `_string_token` |
| 端点是"调用方带来的事实" | 不读磁盘、不遍历目录 → 同一个请求体同一个响应 | `/documents/*` |
| 边界写在三个地方 | 让同一条限制在三个消费面上都可见 | `pdf_boundaries` / 元数据 / 测试 |

M6 的第一天到此结束。回头看它留下的东西：

```text

```

下一站是 **day062：分块策略**。今天交出去的 `Document` 里，
`blocks` 那个字段就是为它准备的：固定长度怎么切、递归怎么按结构切、
语义怎么按相似度切、结构怎么按标题切——**四种策略都要在同一个形状上工作**，
而"哪些块不该被切开"（代码块、表格）的信息今天已经保留在 `kind` 里了。
