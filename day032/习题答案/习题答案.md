## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：这是 LLM 项目 CI 的根本特殊性。单元测试断言的是**机制**——ReAct 循环是否转动、解析器是否认得出格式、权限策略是否拒绝越权调用——这些判定都是确定性的。但把系统提示词从"请简明回答"改成"请详细回答"，全部单测依然全绿，而 Agent 的行为品质（答案啰嗦、工具选择变糟）已经退化了。品质退化是确定性测试的盲区，只能靠"评估即测试"——把 completion_rate、block_rate 这类行为指标设为门禁来捕捉。

A 因果颠倒（评估通常比单测更慢）；C 与事实相反（评估需要数据集与指标设计，更难写）；D 不存在这种要求。

### 第 2 题

**答案：C**

**解析**：归因的本质是"在信息最完整的时刻保留信息"。调用发生的时刻，代码确切知道自己在调哪个模型、哪个接口；到了月底，账单上只有模型维度的总额，自由文本日志里的模型名要靠正则去猜——格式一变就解析失败，没打日志的调用直接丢失。day015 的审计日志是同一个原则：结构化的观测数据要在产出的时刻就结构化，事后补救既不可靠也不可行。

A、B 都不是这种设计的目标（字段多一点存储、record 慢一点都无关紧要）；D 低估了工程差异——"事后能还原"在日志实践中几乎总是落空。

### 第 3 题

**答案：D**

**解析**：D 错误。trace 不是 log 的超集，两者回答的问题不同：log 是离散事件流，适合告警、审计、异常细节（堆栈、参数值）；trace 是单请求的结构化账本，适合性能归因与单请求复盘。trace 的 span attributes 是少量键值对，装不下日志承载的详细上下文；而日志没有时间跨度与层级结构，做不了耗时聚合。工程实践是两者并存互补（本项目：`utils/logger.py` 管日志，`observability/tracing.py` 管 trace）。

A、B、C 都是教程第三章的正文原义。

## 第二部分：判断题

### 第 4 题

**答案：对**

**解析**：这是"宁可报错，不可漏算"的失败安全设计。成本数据的两种错误模式不对称：报错（KeyError）会立刻被发现、被迫修复；漏算（按 0 元记）则让一切报表绿油油，问题潜伏到月底真实账单到来才暴露——而那时归因信息已经丢失，连排查都困难。同理，价格表是构造参数而非全局常量，保证调价、换模型时价格是显式决策。一个相关推论：监控/计费类代码里，"静默降级为零"永远应该警惕。

### 第 5 题

**答案：错**

**解析**：因果恰好相反——**失败时的报告才最有保存价值**。CI 门禁失败时，开发者拿到的唯一线索是"某某步骤退出码 1"，而评估报告里才有复盘需要的第一手材料：哪个指标跌破阈值、哪些用例失败、漏网攻击是哪些。GitHub Actions 默认在前序步骤失败后跳过后续步骤，`if: always()` 就是覆盖这个默认，保证失败现场被留存。这与教程 3.4 节"观测系统的价值在故障时最大"是同一原则在 CI 配置上的体现。

### 第 6 题

**答案：对**

**解析**：`run_with_trace` 在运行前把 `agent.llm` 换成 `_TimedLLMProxy`，`finally` 里换回——ReactAgent 源码零改造，延续了 day030"被测对象不为观测做改造"的规矩。代理只实现 `chat`（包一个计时 span），其余属性经 `__getattr__` 透传给内层 MockLLM，所以 `agent.llm.calls`、`usage_log` 照常累积；测试里 `len(tracer.query(name="llm.chat")) == len(llm.calls)` 验证了两侧观测的一致性。这种模式（代理插桩）也是装饰器、缓存、限流的通用思想。

## 第三部分：问答题

### 第 7 题

**参考答案**：

（1）当前基线 completion_rate = 0.62（8 条任务过 5 条），直接定 1.0 意味着门禁从今天起永远红着。长期红灯的后果不是"团队发愤图强"，而是团队学会无视红灯、绕过门禁（`--no-verify`、admin 强合）——**门禁一旦失去权威就再也立不起来**。而且 0.62 里有用例集本身的校准问题（如 task-06 的解析失败是预期行为演示），把"还没优化到的目标"写成门禁，混淆了"现状描述"与"质量承诺"。

（2）红队拦截率的用例集是**已知攻击集**——每一条用例都是我们已经掌握手法、防线理应拦住的攻击。拦不住已知攻击没有任何借口：要么防线有 bug，要么规则回退了。对"已知集合必须 100%"的指标，1.0 不是严苛而是定义。这正是"防退化"语义最纯粹的体现。

（3）改阈值而不是改数据：先完成防线/提示词优化，让实际指标稳定超过 0.8；然后提交一个独立的 PR，把 `--min-completion-rate 0.6` 改成 `0.8`，PR 描述里附上支撑数据。阈值变更经过评审，等于把"我们达到了新水平"变成一次显式的、可回溯的质量决策；反过来如果趁别的 PR 偷偷改数据过门禁，质量承诺就失效了。

### 第 8 题

**参考答案**：

（1）GitHub Actions 只扫描**仓库根目录**下的 `.github/workflows/*.yml`。本课程每天的快照是仓库根 `autocreatemd/` 下的子目录，配置位于 `day032/源码/smart-research-agent/.github/` 内，深度不对，不会触发。

（2）方式一：把 `smart-research-agent/` 作为独立仓库推送（本目录即仓库根），配置原样生效；方式二：在已有仓库根目录放 `.github/workflows/ci.yml`，项目在子目录则给每个 `run` 步骤加 `working-directory: smart-research-agent`。

（3）因为流水线的判定逻辑——pytest 覆盖率门禁、两个评估脚本的阈值参数、退出码语义——全部由仓库内的代码实现，与 GitHub 无关。`scripts/run_all_checks.sh` 用与 ci.yml 完全相同的命令和阈值在本地跑通了整条流水线（445 passed → 评估门禁 → 红队门禁 → 全绿），ci.yml 只是把同样的命令包进 GitHub 的语法。本地脚本就是流水线逻辑的"单测"，CI 配置的正确性因此可以被离线验证。

### 第 9 题

**参考答案**：

（1）吞掉异常会让调用方以为操作成功了——Agent 拿不到 LLM 的异常就无法走重试/降级，错误被静默掩盖，观测系统从"帮忙定位问题"变成"制造问题"。观测代码的铁律是绝不改变业务语义：记录完之后 `raise` 原样抛出。

（2）异常恰恰是最需要被观测的场景。如果异常路径不落盘，那么每次故障请求留下的 trace 都是残缺的——平时一切正常时数据齐全，真出问题时反而没有数据，观测系统在最需要它的时刻失明。先 `finish(status="error")` 落盘再抛出，保证 error span 成为事后分析的索引（`tracer.query(status="error")`）。

（3）有，多处。day015 审计日志：工具执行抛异常时 `_execute_tool` 先把 `status="error"` 记入审计再把错误文本作为 Observation 回喂，失败调用不会逃出审计视野；day030 的评估 Harness：任务执行抛异常时被捕获、记为失败用例（含错误信息）继续跑下一条——评估不因为单条任务崩溃而丢掉整批结果；day030 的 OutputEvaluator 接线（`_evaluate_output`）则是另一个方向：评估异常被 catch 住绝不影响主流程。三个案例共同的原则：**观测/评估代码自己永远不该成为新的故障源，同时故障路径的数据一条不能丢**。

## 第四部分：编程题

### 第 10 题

**参考实现**（`scripts/trace_and_cost_demo.py`，已在 day032 快照中实际运行通过）：

```python
"""day032 习题 10 参考答案：带 trace 跑一次 Agent 并算一笔账."""

from __future__ import annotations

import sys
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parent.parent
sys.path.insert(0, str(PROJECT_ROOT))

from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.observability.cost_tracker import CostTracker
from smart_research_agent.observability.tracing import Tracer, run_with_trace
from smart_research_agent.tools.calculator import CalculatorTool
from smart_research_agent.tools.registry import ToolRegistry

TRACE_PATH = PROJECT_ROOT / "data" / "eval" / "traces.jsonl"


class FakeSearchTool(CalculatorTool):
    @property
    def name(self) -> str:
        return "web_search"

    @property
    def description(self) -> str:
        return "联网搜索，返回与查询相关的资料摘要"

    def execute(self, expression: str = "", **kwargs) -> str:
        return "模拟搜索结果：这是离线评估使用的固定回复"


def make_agent(responses: list[str]) -> ReactAgent:
    registry = ToolRegistry()
    registry.register(CalculatorTool())
    registry.register(FakeSearchTool())
    return ReactAgent(llm=MockLLM(responses=responses), registry=registry, max_steps=6)


def main() -> int:
    agent = make_agent(
        [
            "Thought: 需要先搜索一下\nAction: web_search\nAction Input: RAG 检索增强",
            "Thought: 资料够了\nFinal Answer: RAG 是检索增强生成技术。",
        ]
    )
    llm = agent.llm

    tracer = Tracer(sink_path=TRACE_PATH)
    answer = run_with_trace(agent, "什么是 RAG？", tracer)

    tracker = CostTracker()
    tracker.record_from_llm(llm, model="gpt-4o-mini")

    trace_id = tracer.spans[-1].trace_id
    print(f"trace_id: {trace_id}")
    for span in tracer.get_trace(trace_id):
        print(f"  {span.name:<12} {span.duration_ms:>8.3f}ms  {span.status}")
    print(f"prompt tokens:     {llm.total_prompt_tokens}")
    print(f"completion tokens: {llm.total_completion_tokens}")
    print(f"费用: ${tracker.total_cost:.6f}")

    reloaded = Tracer.load(TRACE_PATH)
    assert len(reloaded) == len(tracer.spans), "回放记录数与内存不一致"
    print(f"回放: 从 {TRACE_PATH.name} 读回 {len(reloaded)} 条 span，与内存一致")

    root = tracer.query(name="agent.run")[0]
    assert root.status == "ok"
    assert root.attributes["answer"] == answer
    assert len(tracer.query(name="llm.chat")) == len(llm.calls)
    print("全部断言通过")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

**实际运行输出**（span 耗时与 trace_id 每次运行略有不同）：

```text
trace_id: 0ad58270bfa5431a
  agent.run       1.976ms  ok
  llm.chat        0.008ms  ok
  llm.chat        0.008ms  ok
prompt tokens:     276
completion tokens: 24
费用: $0.000056
回放: 从 traces.jsonl 读回 3 条 span，与内存一致
全部断言通过
```

**解析**：

1. **两个观测系统在同一次运行上汇合**：`run_with_trace` 产出 3 个 span（root + 2 次 `llm.chat`），`CostTracker` 从同一个 MockLLM 实例的 `usage_log` 记账——trace 管"这次请求经历了什么"，成本追踪管"这次请求花了多少钱"，两者经 `llm` 实例的观测点自然对齐。
2. **费用的来路可以验算**：276 prompt + 24 completion，按 gpt-4o-mini 价格表 `(276×0.00015 + 24×0.0006)/1000 = 0.0000558 ≈ $0.000056`。prompt 远大于 completion 是 Agent 应用的典型成本结构——系统提示词和历史消息每步都重发，day033 讲自回归原理时会看到这也是输出 token 更贵的原因之一。
3. **记账时机的细节**：`record_from_llm` 必须在 `run_with_trace` 返回之后调用——运行期间 `agent.llm` 是计时代理，真正的 MockLLM（持有 `usage_log`）被包在里面；`llm = agent.llm` 在运行前取的引用指向真身，所以记账用的是保存下来的引用，而非运行后去碰代理。
4. **回放验证的是观测数据的持久性**：`Tracer.load()` 读回的 3 条记录与内存一致，意味着进程死掉之后 trace 仍可分析——这是观测数据"落盘 jsonl"而非"只留内存"的意义（审计日志同理）。
