## 第 1 题

**答案：B**

解析：教程 1.1 节的核心论证：没有标准协议时，M 个 Agent 应用接入 N 个能力提供方需要 M×N 份两两定制集成；MCP 把集成变成协议后，每侧只需实现一次，总量降为 M+N。A 错——MCP 与模型推理无关，Server 根本不与 LLM 对话（教程 1.3 节特别强调）。C 错——Function Calling 发生在"应用 ↔ 模型"之间，MCP 发生在"应用 ↔ 能力提供方"之间，是链路的不同环节。D 错——MCP 的消息层反而跑在 stdio/HTTP 之上，它是应用层协议，不替代传输层。

## 第 2 题

**答案：C**

解析：Client 与 Server 是**一对一**的有状态协议连接（握手、能力协商、订阅关系都绑定在单条连接上），所以 Host 连 N 个 Server 就维护 N 个 Client 实例——这正是把 Client 从 Host 里拆出来的原因：用"管理 N 个 Client"的统一方式管理 N 份连接状态，而不是让协议状态混入 Host 主逻辑。A 错（Host 通常同时连多个 Server）；B 错（方向反了，是一个 Host 对多 Client，不是一个 Client 对多 Server）；D 错（Server 不持有 LLM 连接，它只被动响应协议消息，模型推理完全在 Host 一侧）。

## 第 3 题

**答案：B**

解析：教程 4.1 节"控制权归属"一行是区分三者的钥匙：

- **Resources 由应用控制**：Host 决定把哪些数据放进模型上下文，模型被动消费；
- **Tools 由模型控制**：模型在推理中自主决定"现在该调 search 了"，因此 Tools 通常有副作用，生产环境才需要人类确认环节；
- **Prompts 由用户控制**：用户在界面里选模板、填参数，是"预制工作流入口"。

记忆口诀：**Resource 是名词（数据），Tool 是动词（动作），Prompt 是句型（模板）。**

## 第 4 题

**答案：C**

解析：JSON-RPC 2.0 里**有没有 `id` 字段是请求与通知的唯一区别**。通知不带 `id`，发送方不期待任何响应，`notifications/initialized`（握手收尾通知）就是最典型的例子。A 是请求（有 id 有 method）；B 是成功响应（有 id 有 result）；D 是错误响应——注意它虽然 `id` 为 `null`，但 `id` 字段**存在**，且含 `error` 对象，这是对一条无法解析出 id 的畸形请求的应答，不是通知。

## 第 5 题

**答案：错**

解析：这不是命名习惯，是**语义契约**。Resource 的承诺是"只读、无副作用"，Client 可以基于这个承诺放心地预取、缓存、展示资源内容，不用担心触发任何状态变更。如果把写操作混进 Resource，所有建立在"读取安全"假设上的 Client 行为都变成隐患——比如一个 Client 为了预览而读取某个 URI，结果悄悄修改了数据。反之，Tool 的语义就是"可能有副作用的动作"，Client 会对其施加确认、审计、限流等额外控制。**原语分类的本质是给 Client 一份关于风险的事前声明**，归错类等于撒谎。

## 第 6 题

**答案：错**

解析：教程 5.3 节专门讲了这次命名决策。venv 里已安装官方 `mcp` 包（day017 起要使用），Python 按 `sys.path` 顺序解析导入。如果我们的包也叫 `mcp` 且路径排在前面，那么**任何人写的 `import mcp`**——包括官方生态中其他库内部的 `import mcp`——都会解析到我们的包，引发极难排查的模块遮蔽故障。"项目内部包"挡不住这件事：遮蔽发生在导入解析层，不区分你是不是故意。所以包名固定为 `mcp_server`。同理，项目内任何模块都不该叫 `json`、`email`、`types` 这类已被占用的名字。

## 第 7 题

**答案：对**

解析：`id` 是 JSON-RPC 请求-响应的**匹配键**。Client 可能同时发出多条未决请求，回来的响应全靠 id 对号入座；握手是整条连接的第一条请求，若响应 id 对不上，Client 无法确认对方回答的是自己的 initialize——可能连错了会话，也可能中间有代理串话。教程 3.2 节强调这不是礼貌而是协议正确性的根基，测试 `test_handshake_id_must_match` 守的就是这条。所以 `build_initialize_response(request_id=req.id)` 要求显式传入请求的 id，而不是自己生成一个。

## 第 8 题

**参考答案**：

**为什么 `jsonrpc` 用 `Literal["2.0"]` 而不是 `str`：** `Literal["2.0"]` 把"该字段必须等于字符串 2.0"这条协议规则直接编码成了类型约束——构造或反序列化时传入 `"1.0"`、`"3.0"`，pydantic 立即抛 `ValidationError`，不需要写一行 `if` 校验。若标注为 `str`，任何字符串都能通过，版本校验就得靠各处手写检查，总有一处会漏。同时默认值 `"2.0"` 让构造方无需关心此字段：**协议版本由建模层锁定，调用方想错都错不了**。这就是"类型即契约"——声明即校验（对应测试 `test_invalid_jsonrpc_version_raises` 与 `test_invalid_jsonrpc_version_on_deserialize`）。

**为什么错误响应的 `id` 允许 `None`：** 考虑服务器收到一段根本不是合法 JSON 的字节流（触发 `-32700` Parse error）——它连请求都解析不出来，自然拿不到请求的 id。规范为此规定：此时错误响应的 `id` 为 `null`，表示"我无法确定这条错误在回答谁"。所以 `JsonRpcError.id` 的类型是 `int | str | None`，而正常请求/成功响应的 `id` 不允许 `None`——类型差异精确对应了协议中两种场景的区别。

## 第 9 题

**参考答案**：

**记忆读取归为 Resource 的理由：**

- **副作用语义**：按 ID 读取一条记忆是无副作用的只读操作——读一百次不改变任何状态。Resource 的契约正是"只读数据"，完全吻合；Tool 的契约是"可能有副作用的动作"，用它表达纯读取是语义升级（变强了），会引来不必要的确认与审计开销。
- **控制权归属**：记忆是**上下文供给**——该由 Host（应用）决定"这次对话要不要带上这条笔记"，而不是让模型在推理中概率性地决定"现在去翻翻记忆"。做成 Tool 等于把上下文组装的主动权交给了模型的即兴判断；做成 Resource，应用可以确定性地下发 `resources/read` 并把内容放入上下文。
- **可寻址性**：记忆条目天然有 ID，`memory://notes/{id}` 的 URI 寻址与 Resource 模型严丝合缝，Client 甚至不需要理解 scheme 语义（URI 对 Client 不透明，解释权属 Server）。

补充一点教程强调的精细之处：**按操作归类，不按资产归类**——同一套记忆系统，"读取"是 Resource，将来若暴露"写入记忆"（`remember()`），因为有副作用，必须做成 Tool。

**联网搜索应归为 Tool。** 两个理由：（1）触发时机应由模型决定——只有模型在推理中才知道"我现在缺这个信息，该搜了"，这正是 Tool 的 model-controlled 语义；（2）它有实质副作用与成本：对外发起网络请求、消耗 API 配额、结果随时间变化（非幂等只读）。它不满足 Resource"被动数据供给 + 可缓存"的任何特征，也不是用户触发的模板，因此 Tool 是唯一正确的归类。

## 第 10 题

**参考实现**（`smart_research_agent/mcp_server/capabilities.py`）：

```python
"""MCP 能力注册表：聚合三类能力描述，生成 initialize 能力声明."""

from __future__ import annotations

from smart_research_agent.mcp_server.protocol import (
    PromptDescriptor,
    ResourceDescriptor,
    ToolDescriptor,
)


class CapabilityRegistry:
    """按类聚合 Resource/Tool/Prompt 描述符，判重并生成能力声明."""

    def __init__(self) -> None:
        self._resources: dict[str, ResourceDescriptor] = {}
        self._tools: dict[str, ToolDescriptor] = {}
        self._prompts: dict[str, PromptDescriptor] = {}

    def register_resource(self, desc: ResourceDescriptor) -> None:
        if desc.uri in self._resources:
            raise ValueError(f"Resource URI 重复注册: {desc.uri}")
        self._resources[desc.uri] = desc

    def register_tool(self, desc: ToolDescriptor) -> None:
        if desc.name in self._tools:
            raise ValueError(f"Tool 名称重复注册: {desc.name}")
        self._tools[desc.name] = desc

    def register_prompt(self, desc: PromptDescriptor) -> None:
        if desc.name in self._prompts:
            raise ValueError(f"Prompt 名称重复注册: {desc.name}")
        self._prompts[desc.name] = desc

    def to_initialize_capabilities(self) -> dict:
        """生成 initialize 响应 result["capabilities"] 所需的能力声明."""
        return {
            "resources": {"listChanged": False, "count": len(self._resources)},
            "tools": {"listChanged": False, "count": len(self._tools)},
            "prompts": {"listChanged": False, "count": len(self._prompts)},
        }

    def list_all(self) -> dict[str, list]:
        """返回三类能力的完整描述符列表."""
        return {
            "resources": list(self._resources.values()),
            "tools": list(self._tools.values()),
            "prompts": list(self._prompts.values()),
        }
```

**参考测试**（`tests/test_mcp_capabilities.py`）：

```python
"""CapabilityRegistry 测试."""

from __future__ import annotations

import pytest

from smart_research_agent.mcp_server.capabilities import CapabilityRegistry
from smart_research_agent.mcp_server.protocol import (
    PromptDescriptor,
    ResourceDescriptor,
    ToolDescriptor,
)


def _make_registry() -> CapabilityRegistry:
    registry = CapabilityRegistry()
    registry.register_resource(ResourceDescriptor(uri="memory://notes/1", name="笔记1"))
    registry.register_tool(ToolDescriptor(name="calculate", input_schema={"type": "object"}))
    registry.register_prompt(PromptDescriptor(name="research_report"))
    return registry


class TestCapabilityRegistry:
    def test_counts_after_registering_each_kind(self):
        caps = _make_registry().to_initialize_capabilities()
        assert caps["resources"]["count"] == 1
        assert caps["tools"]["count"] == 1
        assert caps["prompts"]["count"] == 1

    def test_duplicate_tool_name_raises(self):
        registry = _make_registry()
        with pytest.raises(ValueError, match="calculate"):
            registry.register_tool(ToolDescriptor(name="calculate"))

    def test_duplicate_resource_uri_raises(self):
        registry = _make_registry()
        with pytest.raises(ValueError, match="memory://notes/1"):
            registry.register_resource(
                ResourceDescriptor(uri="memory://notes/1", name="同名URI")
            )

    def test_empty_registry_counts_zero(self):
        caps = CapabilityRegistry().to_initialize_capabilities()
        assert caps["resources"]["count"] == 0
        assert caps["tools"]["count"] == 0
        assert caps["prompts"]["count"] == 0

    def test_list_all_returns_descriptors(self):
        all_caps = _make_registry().list_all()
        assert all_caps["tools"][0].name == "calculate"
        assert all_caps["resources"][0].uri == "memory://notes/1"
```

**解析**：

1. **为什么用三个 dict 而不是三个 list**：dict 的 key（uri / name / name）就是判重键，`in` 判断 O(1)，计数 `len()` 也是 O(1)，注册即索引。用 list 的话判重要每次线性扫描，且"按名取描述符"（将来 `tools/list` 会需要）也不方便。
2. **为什么 `to_initialize_capabilities` 只报 count 而不内嵌描述符**：这是握手阶段的**能力声明**，它只回答"我支持哪些方法族"——Client 据此决定要不要调 `tools/list` 去拿完整清单。分层的好处：握手消息保持轻量（Server 可能有几百个工具，全塞进握手响应会让每个新连接都付出巨大首包代价），详细清单按需拉取。这与 HTTP 世界里"先 OPTIONS 探能力，再 GET 取内容"是同一思想。
3. **`listChanged: False` 的含义**：这是 MCP 规范中的能力标志位，声明"我的能力清单是否会动态变化（变化时会发 `notifications/*/list_changed` 通知）"。今天的注册表是静态的，所以固定为 `False`；day018~020 实现动态工具接入时可以把它变成真实的状态。
4. **`match="calculate"` 的断言技巧**：`pytest.raises(..., match=...)` 按正则匹配异常消息，既验证了异常类型，也验证了错误信息里确实带着冲突的名字——这正是题目要求"错误信息包含冲突的名字"的测试化表达。
