## 第一章：Prompt 工程到底在工程什么

### 1.1 提示词的三重身份

提示词在 Agent 系统里同时扮演三个角色：

```text
对模型:  它是"程序"——LLM 是解释器，提示词是它执行的条件逻辑
对产品:  它是"配置"——语气、格式、边界都由它定义，运营也想改它
对团队:  它是"代码"——多人协作修改，改动直接影响线上行为
```

三重身份推出今天的核心主张：**提示词必须享受与代码同级的工程纪律**——版本化（改了什么、为什么改）、可复现（任何时候能取回历史版本）、可回归（新版本先过评估再上线）。day026 我们用"模块常量 + 版本注释"做了朴素版（`REACT_SYSTEM_PROMPT_V1/V2`），今天用 `PromptLibrary` 把它正式化。

### 1.2 好提示词的解剖：五要素

先看一条"什么都不缺"的提示词应该长什么样。五个要素，缺一个就有一类典型的翻车方式：

| 要素 | 回答的问题 | 缺失时的典型症状 |
|------|-----------|-----------------|
| 角色 Role | 你是谁、能力边界在哪 | 回答风格飘忽，时而专业时而闲聊 |
| 任务 Task | 要做什么 | 模型自由发挥，答非所问 |
| 上下文 Context | 基于什么信息做 | 模型凭记忆编造事实（幻觉） |
| 格式 Format | 输出长什么样 | 下游解析器拿不到结构化字段 |
| 约束 Constraint | 禁止什么、必须什么 | 编造工具、泄露提示词、超范围回答 |

day026 的 `REACT_SYSTEM_PROMPT_V2` 就是按这个解剖重写的（`../源码/smart-research-agent/smart_research_agent/agent/prompts.py`）：开头"你是 SmartResearch 智能研究助手"是**角色**，"## 任务"段是**任务**，"## 输出格式"段是**格式**，"## 约束"四条是**约束**，而 `{tools}` 占位符渲染出的工具清单就是**上下文**。v1 → v2 的变更日志逐条对应症状修复：角色与任务混写导致"我是谁、要做什么"被误读 → 拆开；规则藏在示例里导致模型不遵守 → 变成显式约束清单；没有兜底指令导致凭记忆编造 → 补"信息不足时继续调用工具"。

**五要素不是模板教条，而是检查清单**：写完提示词后逐项问"模型能不能从文本里读到这个信息"，读不到就是隐患。

## 第二章：四种技巧的原理与适用场景

四种技巧都在回答同一个问题：**如何让模型在"生成下一个 token"这个机制下，把活干得更好**。它们的差异在于给模型提供的"支架"不同。

### 2.1 Zero-shot：直接问，靠的是预训练泛化

```text
请完成以下任务：

把『人工智能正在改变科研工作流』翻译成英文
```

没有任何示例，直接下指令。它能工作是因为指令微调（instruction tuning）让模型在预训练知识之上学会了"听懂任务描述"。**适用场景**：任务简单、常见、输出形式无需特殊约定——翻译、摘要、分类、改写。成本最低（prompt 最短），是任何任务的**基线**：新技巧的收益都应当相对 zero-shot 基线来衡量。

### 2.2 Few-shot：示例校准的不是知识，是格式与风格

```text
请参照以下示例完成最后的任务。

示例 1：
输入：把『你好』翻译成英文
输出：Hello

示例 2：
输入：把『谢谢』翻译成英文
输出：Thank you

任务：把『人工智能正在改变科研工作流』翻译成英文
输出：
```

Few-shot 的经典误解是"示例在教模型知识"。翻译"你好"这种示例显然没教任何新知识——它校准的是**输出的呈现方式**：要不要解释、要不要引号、粒度多细、风格多正式。模型是强大的模式匹配器，示例就是最精确的模式规范。这也是为什么 few-shot 对**格式敏感型任务**（输出 JSON、特定分类标签、特定文风）提升最大。**适用场景**：输出格式/风格有精确要求、用自然语言描述格式反而词不达意时。代价是 prompt 变长（token 成本上升，回忆 day034 的计费口径），且示例选得偏了会把模型带偏（示例分布 = 隐性先验）。

### 2.3 Chain-of-Thought：把计算摊到生成过程里

CoT 只需在任务后追加一句引导语（我们实现里的 `COT_INSTRUCTION`）：

```text
请完成以下任务：

一个水池有进水管和出水管，单开进水管 4 小时注满，单开出水管 6 小时放空。两管同开，几小时注满？

让我们一步一步思考，先写出推理过程，再给出最终答案。
```

**为什么这一句能显著提高数学/推理题的正确率？** 回到 day033 的自回归机制：模型生成每个 token 时都以前面所有 token 为条件。不让它写过程，它就必须在生成答案的那一个 token 时，在**单次前向传播**里完成全部计算——相当于心算。让它先写过程，等于把中间结果"落到纸面"：

```text
不进 CoT: 问题 -> [一次前向传播] -> "几小时"          （心算，易错）
进 CoT:   问题 -> "进水速度 1/4，出水速度 1/6，净速度 1/12" -> "12 小时"
                  └── 这些 token 成为后续生成的条件 ──┘   （笔算，每步都简单）
```

每个中间 token 生成都只是一步简单推理，而写下的中间结果成为后续 token 的条件——**计算被分摊到了整个生成序列上，有效计算深度随输出长度增长**。这就是"test-time compute"的原始形态：用更多生成 token 换更强推理能力。**适用场景**：数学、逻辑、多步推理、需要追溯推理过程的调试场景。**不适用**：简单检索型任务（白白浪费输出 token，还可能"想多了"把对的想错）。

### 2.4 Tree-of-Thoughts：从单链推理到搜索

CoT 有一个结构性弱点：**链条是单线的**。第一步想错，后面每一步都以错误为条件，错误沿链放大，模型没有"回头看"的机会。ToT（Tree of Thoughts，Yao et al. 2023）把推理从"一条链"升级为"一棵树"：

```text
                任务
          ┌──────┼──────┐
       分支 1   分支 2   分支 3      ← 并行展开：不同视角独立推理
       (稳妥)   (非常规) (排错优先)
          └──────┼──────┘
               汇总步               ← 评估、比较、择优、融合
              最终答案
```

这是把**搜索思想**引入推理：分支 = 展开候选路径，汇总 = 评估函数 + 选择。它换来的是对单点失败的鲁棒性——三条独立推理同时想错同一个地方的概率，远低于一条链上某步想错的概率。代价同样直接：**LLM 调用数 = 分支数 + 1 次汇总**（我们的测试 `test_tot_consumes_2n_plus_calls` 精确断言了这一点），成本是单链技巧的 n+1 倍。**适用场景**：答案空间大有多种合理路径、错误代价高、值得用计算换正确率的任务（方案设计、复杂证明、多约束规划）。我们的实现里各分支用不同"探索视角"提示词（`_BRANCH_ANGLES`）保证多样性——分支若只是同一提示跑 n 次，低温下会产出雷同结果，搜索就退化了。

### 2.5 四种技巧一页对照

| 技巧 | 给模型的支架 | 额外成本 | 最适场景 | 主要风险 |
|------|-------------|---------|---------|---------|
| Zero-shot | 无（任务本身） | 无 | 简单常见任务、建立基线 | 格式/边界不受控 |
| Few-shot | 示例（格式先验） | prompt 变长 | 格式/风格敏感任务 | 示例偏差传染 |
| CoT | 推理引导语 | 输出变长 | 数学/逻辑/多步推理 | 简单任务上想多反而错 |
| ToT | 分支 + 汇总裁决 | 调用 ×(n+1) | 高错误代价的多路径任务 | 分支同质化导致退化 |

## 第三章：techniques.py —— 把技巧做成可复用构造器

实现位于 `../源码/smart-research-agent/smart_research_agent/agent/techniques.py`。设计取舍：**每个构造器只负责产出 messages 列表，不碰 LLM**——技巧是"怎么问"，调用是"去问"，两者解耦后同一套构造器可服务任何 `BaseLLM` 实现。

```python
def zero_shot(task: str) -> list[Message]:
    return [Message(role="user", content=f"请完成以下任务：\n\n{task}")]

def chain_of_thought(task: str) -> list[Message]:
    # = zero-shot + 思维链引导语；测试断言 cot.startswith(zero_shot 内容)
    return [Message(role="user", content=f"请完成以下任务：\n\n{task}\n\n{COT_INSTRUCTION}")]
```

`few_shot` 把 `(输入, 输出)` 示例对排成"示例 i / 输入 / 输出"的固定版式，最后以"输出："收尾——结尾的冒号是有意的：它把模型"卡"在续写答案的位置上，这是 few-shot 的经典排版技巧。

`tree_of_thoughts` 返回的不是 messages 而是一个 `ToTPlan`：

```python
@dataclass
class ToTPlan:
    task: str
    branch_messages: list[list[Message]]        # n 条相互独立的分支提示

    def synthesis_messages(self, branch_outputs: list[str]) -> list[Message]:
        # 把 n 条分支输出拼成"评估 + 择优 + 融合"的汇总提示
```

为什么拆成两步？因为汇总提示的内容**依赖分支的实际输出**——必须先生成 n 条分支提示、各自调用 LLM 拿到结果，才能构造汇总提示。`ToTPlan` 把这个两阶段协议固化成了类型。用 MockLLM 演示同一任务上四种技巧的差异（测试 `test_all_techniques_produce_valid_messages`）：四种技巧发出的 prompt 互不相同，MockLLM 按预设脚本分别给出"直译答案 / 模仿示例格式的答案 / 带推理过程的答案 / 分支+汇总答案"，离线就能观察技巧的结构性差异。

## 第四章：PromptLibrary —— 提示词的版本管理

### 4.1 数据模型：PromptTemplate

实现位于 `../源码/smart-research-agent/smart_research_agent/agent/prompt_library.py`。核心数据类只有五个字段：

```python
@dataclass
class PromptTemplate:
    name: str          # 模板名（同一 name 下按 version 演进）
    template: str      # 模板文本，变量以 {var} 占位
    version: str = "v1"
    changelog: str = ""        # 本版变更原因——prompt 即代码，必须留痕
    created_at: str = ...      # 注册时刻 ISO 时间戳，默认自动填充
```

`changelog` 不是可选的装饰品。模型行为对措辞极其敏感，三个月后面对"v3 比 v2 转化率低 8%"时，唯一能告诉你"当初为什么改"的就是 changelog——它等价于代码的 commit message。

### 4.2 渲染：显式替换而非 str.format

`render()` 做两件事：**缺失校验**（模板声明的变量必须全部提供，缺一即抛 `PromptRenderError` 并列出缺失名单），然后做变量替换：

```python
_VAR_PATTERN = re.compile(r"\{([a-zA-Z_][a-zA-Z0-9_]*)\}")

def render(self, **variables):
    missing = [v for v in self.variables if v not in variables]
    if missing:
        raise PromptRenderError(f"... 缺少变量: {', '.join(missing)}")
    return _VAR_PATTERN.sub(_sub, self.template)
```

为什么不用 `str.format`？因为 format 对**所有**花括号敏感——提示词里经常出现给模型看的 JSON 示例（`{"k": 1}`），用 format 就得全文转义成 `{{ }}`，模板可读性报废。我们的正则只认 `{合法标识符}`，JSON 片段自然穿过不参与替换（测试 `test_render_ignores_non_identifier_braces` 专门守这个行为）。缺失校验则是把"运行时 KeyError 在 LLM 调用前"变成"带着变量名单的明确错误"——渲染失败是**免费**的，发出去一条缺变量的提示词浪费的是真金白银的 token。

### 4.3 版本演进与持久化

`PromptLibrary` 内部是 `dict[name, list[PromptTemplate]]`：同名模板按注册顺序排队，`get(name)` 默认取最后一版（最新），`get(name, "v1")` 取历史版本，`history(name)` 返回完整演进序列。持久化提供两种格式，字段完全一致：

- **JSONL**（一行一个版本）：适合程序追加写入，天然是"版本演进日志"；
- **YAML**（模板列表）：适合人工阅读与手工编辑——prompt 的评审者常常不是工程师。

### 4.4 day026 模板的迁移：首批注册条目

迁移发生在 `prompts.py` 末尾（`../源码/smart-research-agent/smart_research_agent/agent/prompts.py`）：

```python
def build_default_prompt_library() -> PromptLibrary:
    library = PromptLibrary()
    library.register(PromptTemplate(
        name="react_system", template=REACT_SYSTEM_PROMPT_V1, version="v1",
        changelog="day006 初始版本：ReAct 循环的首个系统提示词"))
    library.register(PromptTemplate(
        name="react_system", template=REACT_SYSTEM_PROMPT_V2, version="v2",
        changelog="day026 重写：按角色/任务/输出格式/约束四段式拆分；..."))
    return library

DEFAULT_PROMPT_LIBRARY = build_default_prompt_library()
```

关键设计是**常量原样保留做兼容转发**：`REACT_SYSTEM_PROMPT` 等常量一个字没改，`react_agent.py` 和所有 day026 测试零改动；库里的模板与常量共享同一份文本，只是多了版本号、changelog 和时间戳。测试 `test_library_templates_match_compat_constants` 断言两者永不漂移。这是存量代码迁移的标准姿势：**新机制接管元数据，旧接口保持逐字节兼容**。

## 第五章：版本管理与回归评估的联动

版本管理的全部意义在于支撑一个工作流，而不是存一堆字符串：

```text
改 prompt（新版本注册进库，写 changelog）
   ↓
PromptEvaluator.compare(旧版, 新版)      ← day026，规则检查 + LLM 评委加权
   ↓ 新版本 overall 不掉分？
PromptEvalHarness 回归用例              ← overall >= 阈值固化成 EvalCase
   ↓ 通过
切换生效版本（库的"最新版"指针天然就是发布机制）
```

`PromptEvaluator.compare` 对两个版本各评一次分，分差超过 `TIE_THRESHOLD=0.05` 才分胜负——这避免了评委噪声造成的"伪提升"。`PromptEvalHarness` 把"提示词改版不掉分"固化为回归用例：`EvalCase.input` 是待评提示词、`expected` 是 overall 最低分数线，改版后跑一遍 harness，掉分立即暴露。这套联动就是"prompt 即代码"的完整含义：**有版本历史（git）、有质量门禁（CI）、有回滚能力（取历史版本）**。

### 5.1 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 五要素解剖法 | 缺哪个要素就有哪类典型翻车 | 第一章对照表 |
| Few-shot 示例校准格式而非知识 | 模型是模式匹配器，示例 = 精确的模式规范 | `few_shot` |
| CoT 追加引导语即生效 | 中间结果落成 token 后成为后续生成的条件，计算摊到生成过程 | `chain_of_thought` / `COT_INSTRUCTION` |
| ToT 分支用不同探索视角 | 分支同质化会让搜索退化；多样性是搜索的前提 | `_BRANCH_ANGLES` |
| ToT 拆成 Plan + synthesis 两步 | 汇总提示依赖分支实际输出，两阶段协议固化为类型 | `ToTPlan` |
| 构造器只产 messages 不碰 LLM | "怎么问"与"去问"解耦，适配任何 BaseLLM | `techniques.py` 整体 |
| render 缺失变量即抛错 | 渲染失败免费，缺变量的调用浪费 token | `PromptTemplate.render` |
| 显式替换而非 str.format | 提示词里的 JSON 示例不应被迫全文转义 | `_VAR_PATTERN` |
| changelog 强制留痕 | 行为回归时唯一能回答"当初为什么改"的信息 | `PromptTemplate.changelog` |
| 常量保留 + 库接管元数据 | 存量迁移：旧接口逐字节兼容，新机制接管版本管理 | `build_default_prompt_library` |
| 版本间 compare 设 TIE_THRESHOLD | 评委噪声不应造成伪提升/伪回归 | day026 `PromptEvaluator.compare` |
