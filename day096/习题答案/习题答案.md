## 第一部分：选择题

### 第 1 题：**A**

```python
STAGES: tuple[str, ...] = ("dataset", "sampler", "dataloader", "device",
                           "train", "checkpoint", "inference")
PIPELINE_AXES: tuple[str, ...] = ("batch", "worker", "device", "time")
```

两张名单都写在 `types.py` 里，并在导入期与 `STAGE_DESCRIPTIONS` / `STAGE_OWNERS` /
`AXIS_DESCRIPTIONS` / `AXIS_FORMULAS` 做 `set(...) == set(...)` 的闭合断言。

**为什么值得写进代码**：读报告里一个数字时，第一个问题永远是"它属于哪一段"。
如果这张表只存在于教程里，那你读报告时只能靠记忆——而记忆在有七个阶段时不可靠。

B 错误：阶段是**逻辑分层**而不是文件清单（`train.py` 一个文件就横跨"训练 + 检查点"两段）。
C 错误：四个轴是 `batch / worker / device / time`（设备的取值才是 `cpu / cuda / mps`）。
D 错误：导入期断言是这一课的核心手段之一（"缺席要可断言"），它换来的是"两张表不会悄悄错位"。

### 第 2 题：**B**

```python
@dataclass(frozen=True)
class TabularDataset:
    name: str
    samples: tuple[Sample, ...]
```

- `frozen=True`：切分只能返回**新对象**。一次训练里最贵的错误是"数据被就地改过"——
  它不报错，只会让同一个种子跑出两个不同结果；
- 指纹：规范化 JSON（`sort_keys=True` + 紧凑分隔符）的 `sha256` 前 16 位。
  实测三条：`22bc0a3f878c7012` / `f8f70f5ccf76bc9c` / `0f2166367b3b3e58`；
- 它回答的问题是 **"这两个分数能不能比"**——与 day053 的评估套件指纹、
  day088 的 `principle_map` 同一条纪律。

A 错误（不可变；指纹覆盖全部样本内容）。C 错误：`sort_keys` 排的是**字典的键**，
列表顺序照样参与——上一课的 `preference_fingerprint` 正是在这里踩过一次。
D 错误：指纹不同也可能只是顺序不同，条数相同。

### 第 3 题：**B**

```text
批数公式：drop_last=True：批数 = n // b；drop_last=False：批数 = ceil(n / b) = (n + b − 1) // b
丢弃公式：dropped = n − b × 批数（drop_last=True 时它是被整批丢掉的尾批）
```

24 条、b=7 的实测：

```text
不丢尾批：批数 4 | 丢弃 0
丢尾批：  批数 3 | 丢弃 3
```

A 错误（丢尾批时是 3 批）。C 错误（`drop_last=False` 会保留不满的尾批）。
D 错误（那是没有 `max(0, ...)` 的第一版实现，见下一题的解析）。

### 第 4 题：**B**

```text
worker k 的分片 = { i : i % workers == k }（互不相交、并集为全集）
```

24 条、4 个 worker 的实测：四个分片各 6 条，**并集覆盖率 `1.000000`、重叠项数 `0`**。

判据类型的选择是有讲究的：

- **互不相交**用相等判据（重叠项数 `== 0`）——"零重叠"是精确的事实；
- **并集为全集**用**下界**判据（覆盖率 `>= 1.0`）——它的语义是"**一条样本都不能漏**"，
  而上界判据说的是"不能超过"。覆盖率天然落在 `[0, 1]`，两种写法数值上都成立，
  但下界判据才表达了正确的要求。

A 错误：覆盖不足会让**一部分数据根本没参与训练**，而损失照常下降（第九节："丢弃 0"
这一项进报告就是为了让这种错可核对）。C 错误：连续切分是最常见做法但不是定义，
`i % workers == k` 只是其中一种可实现该性质的分法。D 错误：见上。

### 第 5 题：**B**

```text
total = params + activations + optimizer_multiplier × params
params      = 参数量 × DTYPE_BYTES[dtype]
activations = batch_size × width × DTYPE_BYTES[dtype]
```

实测（114 个参数、batch=8、width=4、float32）：`456 + 128 + 1368 = 1952` 字节。
预算不足**不抛异常**，只把 `fits` 置 `False` 并给一条警告：

```text
警告：超出预算 928 字节——先降 batch_size、再降 width，最后才考虑换精度
```

检查点清单的哈希**只覆盖** `params_sha256` 与 `optimizer_sha256`，它们回答的是
"权重是不是同一份"，不是"文件有没有被动过"。理由与 day052 的适配器清单一致：
把指标也纳进来会让"我补写了一行日志"变成"权重变了"——一个永远不该被相信的假警报。

A 错误（`fits` 才是答案，异常只留给"未知设备名 / 非正批大小"这类真非法状态）。
C 错误（见上）。D 错误（缺省是 3 倍，对应 Adam 的一阶动量 + 二阶动量 + 主权重）。

### 第 6 题：**B**

```text
恢复 = 载入 params + 装回优化器跨步状态 + 从 epoch k+1 继续（order(k+1) 逐位相同）
```

实测：一口气训到第 6 轮 vs 第 3 轮落盘后恢复，114 个参数的**最大绝对差 `0.0`**。

A 错误：只读权重会让 Adam 的动量从 0 重新开始，前几步方向就与原来不同——
而**训练照常下降**，只是曲线悄悄分叉。C 错误：从 `k` 重新训等于多训一轮，
损失更低、看起来"恢复得很好"。D 错误：推理必须只走推理相（BN 用 `running`、
dropout 恒等），走训练相会让同一条样本的两次预测不同。

## 第二部分：判断题

### 第 7 题：**错**

`dropped_samples` 恰恰是"这次训练到底用了几条样本"的唯一可核对读数。三种错都会
改变它，而且**三者都不会报错**：

1. 批切分公式写错（批数与实际消费的样本数不一致）；
2. `drop_last` 配反了；
3. 分片漏掉一部分（某个 worker 的索引区间算错）。

它们的共同现象是"损失照常下降"。所以第九节把"丢弃 0"直接放进报告——
**一个能被核对的数量，胜过十句"配置检查过了"。**

### 第 8 题：**错**

打乱的确定性是恢复训练逐位相等的**前提之一**。恢复之后如果第 `k+1` 轮的顺序和
原来不同，那么"恢复训到第 6 轮"与"一口气训到第 6 轮"必然分叉——而程序无法察觉，
因为数据确实变了、损失也确实下降了。

第 ① 条性质量的就是它：`Sampler(seed=100).order(3)` 两次调用的差异项数
必须是 `0.000e+00`。这也是"随机源必须可注入/可复现"这条纪律在数据侧的具体落点。

### 第 9 题：**错**

方向反了。"放不下"是一个**可被上层处理的决策输入**（降 batch、换设备、分片、
换精度），不是非法状态。把它做成 `fits=False` + 一条警告，调用方才有得选；
做成 `raise`，调用方只能捕获它然后再做同样的事——**多了一层没有信息量的异常**。

真正非法的只有"未知设备名"（`DeviceError`）与"非正批大小 / 非法 worker"这类
（`ParameterError`）。这与 day051 的显存预算表"**显式标注不含激活**"是同一条纪律：
**把结论交出来，不要替调用方做决定。**

### 第 10 题：**错**

这是本课第 ⑧ 节的核心取舍。用 `time.perf_counter()` 直接量，报告里的延迟数字
**无法复现**，于是"吞吐从 1e6 涨到 8e6"这句话永远无法被验证——它甚至可能在下一次
运行时给出相反的顺序。

修法是把时钟做成可注入参数（默认 `time.perf_counter`，测试与演示注入确定性的假时钟），
于是读数逐位可复现：

```text
b=1  | 调用 32 次 | 样本 32 | 0.000032s | 每条 0.000001000s | 吞吐 1000000.0/s
b=8  | 调用  4 次 | 样本 32 | 0.000004s | 每条 0.000000125s | 吞吐 8000000.0/s
```

**注意这张表不是"批越大越快"的性能证据**——假时钟按"每次调用固定开销"计费，
所以数字必然按调用次数比例变化。它证明的是**口径可复现**。
真实加速比要留给真实硬件去量。**"可复现"和"正确"是两件事，别把它们混起来。**

### 第 11 题：**错**

"读数全是 0"不等于"性质太容易通过"，因为**判据类型不同，0 的含义就不同**。
七条性质里有**六条读数恰好是 `0.000e+00`，而它们分属两类判据**——这正是关键：

- **五条相等判据**读数都是 `0.000e+00`：两次打乱、批数与公式、`save → load` 的参数、
  恢复与一口气、批推理与逐条。它们断言的是"**两个独立算出来的东西必须一致**"；
  这类判据一旦失败，读数就是任意大的正数，所以"通过时读数为 0"是它的**唯一正常形态**；
- **一条上界判据**读数 `0.000e+00 <= 1.0e-09`：字节数是整数算术，理论上应当精确为 0，
  留 1e-9 只是为了容忍浮点表示；
- **一条下界判据**读数 `1.000e+00 >= 1.0`：覆盖率必须**正好达到 1**
  （漏一条就小于 1），所以"刚好等于下界"才是通过。

真正让这一课不"太容易"的是：**把三个独立实现出来的东西放在一起比**。
如果哪天有人把 `Sampler` 写成随机、把分片写成连续切、把恢复写成从 `k` 开始，
这七条里会立刻有三条变红。day095 记过一句"没有下界判据时，把两个规则写成同一个，
报告会全绿"——今天这条覆盖率下界就是那句话的延续。

## 第四部分：简答题

### 第 14 题

**共同点**：四个决定都让"接口变难用了一点"，换来的是"**读数可复现、失败可定位**"。
它们对应同一句纪律：**把结论交出来，而不是替调用方做决定；把不确定性注入进去，
而不是让它在背后乱跑。**

#### （1）预算放不下时只置 `fits=False`

- **这个决定是什么**：`plan_device` 把 `fits` 与 `headroom_bytes` 交出来，
  自己不做"降 batch 还是换精度"的决定；
- **改成 `raise` 会怎样**：调用方只能 `try/except` 再自己算一遍，
  或者干脆把预算写大一点"让它过去"——于是预算检查退化成一句装饰；
- **守住的手段**：`fits` 是 `DevicePlan` 的属性（`device.py`），
  测试里有专门的用例构造"压到 0 预算 → `fits is False` 且警告非空"；
  真非法状态（未知设备名）才抛 `DeviceError`。

#### （2）哈希只覆盖权重与优化器状态

- **这个决定是什么**：`params_sha256` / `optimizer_sha256` 回答的是
  "**权重是不是同一份**"；
- **改成覆盖五个文件会怎样**："我补写了一行训练日志"会变成"权重哈希不符"。
  一个总是误报的校验，最终会被所有人跳过——它保护不了任何东西；
- **守住的手段**：`CheckpointManifest` 的字段设计（`checkpoint.py`），
  以及测试里"改 `metrics.json` 不报错、改 `params.json` 报错"两两对照的用例。
  这与 day052 的 `adapter_content_hash`（只覆盖配置与权重）是同一条设计。

#### （3）延迟必须用可注入的时钟

- **这个决定是什么**：`InferenceEngine` 的 `clock` 是一个可注入参数，
  默认 `time.perf_counter`，测试/演示注入确定性假时钟；
- **改成直接调 `perf_counter` 会怎样**：报告里的延迟数字不可复现，
  "吞吐提升 8 倍"这句话无法验证；更糟的是，不同机器上的报告**看起来一样可信**，
  但它们不可比；
- **守住的手段**：`inference.py` 的 `clock` 参数 + 第 ⑧ 节的三个批大小读数
  （b=1/4/8 严格成比例），以及一条"注入假 clock 后 `seconds_per_sample`
  与手算一致"的用例。

#### （4）恢复的判据是相等而不是"差不多"

- **这个决定是什么**：第 ⑥ 条性质用 `Check(reading=<最大绝对差>, upper_bound=0.0)`；
- **改成"损失差不多"会怎样**：三种典型错法（不存优化器状态、从 `k` 而不是 `k+1`
  继续、恢复后重新构造 sampler）**全都会让损失更低或差不多**，
  于是"看起来恢复得很好"——这是最危险的失败模式；
- **守住的手段**：`verify.check_resume_matches_uninterrupted()`（`verify.py`）
  直接比较两次训练最终的 114 个参数；而它同时钉住了 `Sampler` 的确定性、
  优化器状态契约（`OPTIMIZER_STATE_KEYS`）与训练回路的顺序。

**四条经验的一般形式**：**当"更直观"的做法会让某个数字变得更不可信时，
就应该把那个数字做成可注入、可断言、可核对的东西。**

## 第五部分：编程题

### 第 15 题

```python
"""用公开 API 复算 DataLoader 的三个读数与分片性质."""

from __future__ import annotations

from smart_research_agent.sequence_models.train import make_sign_dataset
from smart_research_agent.torch_pipeline import (
    DataLoader,
    Sampler,
    make_dataset,
    shard_indices,
    split_dataset,
)


def main() -> None:
    samples = make_sign_dataset()
    full = make_dataset(samples, name="sign")
    train, evaluation = split_dataset(full, eval_ratio=0.25, seed=100)
    print(f"full  {len(full)} 条 | 指纹 {full.fingerprint()}")
    print(f"train {len(train)} 条 | 指纹 {train.fingerprint()}")
    print(f"eval  {len(evaluation)} 条 | 指纹 {evaluation.fingerprint()}")

    batch_size = 7
    keep_tail = DataLoader(
        train, batch_size=batch_size, shuffle=True, drop_last=False, seed=100
    )
    drop_tail = DataLoader(
        train, batch_size=batch_size, shuffle=True, drop_last=True, seed=100
    )
    n = len(train)
    print(f"不丢尾批：批数 {len(keep_tail.batches(1))} | 丢弃 {keep_tail.dropped_samples()}")
    print(f"丢尾批：  批数 {len(drop_tail.batches(1))} | 丢弃 {drop_tail.dropped_samples()}")
    assert len(keep_tail.batches(1)) == (n + batch_size - 1) // batch_size  # ceil
    assert len(drop_tail.batches(1)) == n // batch_size
    assert keep_tail.dropped_samples() == 0
    assert drop_tail.dropped_samples() == n - batch_size * (n // batch_size)

    shards = [shard_indices(n, workers=4, worker_id=worker) for worker in range(4)]
    union = set().union(*(set(shard) for shard in shards))
    coverage = len(union) / n
    overlap = sum(
        len(set(left) & set(right))
        for index, left in enumerate(shards)
        for right in shards[index + 1 :]
    )
    print(f"4 个分片：并集覆盖 {coverage:.6f} | 重叠项数 {overlap}")
    assert coverage >= 1.0                       # 下界判据：一条都不能漏
    assert overlap == 0                          # 相等判据：互不相交

    first = Sampler(n, shuffle=True, seed=100).order(3)
    second = Sampler(n, shuffle=True, seed=100).order(3)
    differing = sum(1 for left, right in zip(first, second) if left != right)
    print(f"打乱确定性：order(3) 差异项数 {differing}")
    assert differing == 0


if __name__ == "__main__":
    main()
```

```text
full  32 条 | 指纹 22bc0a3f878c7012
train 24 条 | 指纹 f8f70f5ccf76bc9c
eval  8 条 | 指纹 0f2166367b3b3e58
不丢尾批：批数 4 | 丢弃 0
丢尾批：  批数 3 | 丢弃 3
4 个分片：并集覆盖 1.000000 | 重叠项数 0
打乱确定性：order(3) 差异项数 0
```

**逐条解释**

1. 三条集的指纹互不相同——**这三个报告里的分数不可直接比较**。这就是把指纹
   写进 `TabularDataset` 的全部意义；
2. `24 = 3 × 7 + 3`：不丢尾批时余下 3 条自成一批（批数 4、丢弃 0）；
   丢尾批时那 3 条被整批丢掉（批数 3、丢弃 3）。**两种配置消费的样本数不同**，
   所以它们的损失不可直接比较；
3. 分片的覆盖率用**下界**判据断言（`>= 1.0`），重叠用**相等**判据（`== 0`）——
   两类判据的语义差别见第 4 题；
4. `make_sign_dataset` 属于 day094 的 `sequence_models.train`，
   不在 `torch_pipeline` 的导出名单里：**复用别人的数据生成器要写清来源**，
   而不要在本包里再拷贝一份。

### 第 16 题

```python
"""端到端报告与七条性质的自查."""

from __future__ import annotations

from smart_research_agent.sequence_models.train import make_sign_dataset
from smart_research_agent.torch_pipeline import (
    PipelineConfig,
    make_dataset,
    move_report,
    plan_device,
    train_pipeline,
)
from smart_research_agent.torch_pipeline import verify as verification

#: 本课的模型规模：lstm(H=4, D=1) → bn(4) → dropout → dense(4→2)，共 114 个参数.
MODEL_PARAMS = 114


def main() -> None:
    dataset = make_dataset(make_sign_dataset(), name="sign")
    report = train_pipeline(dataset, config=PipelineConfig(epochs=10, batch_size=8))
    print("report:", report.summary_line())
    print(
        f"steps {report.steps} | 每轮批数 {report.batch_count} | "
        f"丢弃 {report.dropped_samples} | 指纹 {report.dataset_fingerprint}"
    )
    assert report.final_train_loss < report.initial_loss
    assert report.improvement > 0.0
    assert report.steps == report.epochs_run * report.batch_count
    assert report.dropped_samples == 0
    assert report.dataset_fingerprint == dataset.fingerprint()

    plan = plan_device(MODEL_PARAMS, batch_size=8, width=4, device="cpu", dtype="float32")
    print("device:", plan.line())
    print("move:", move_report(plan)[0])
    assert plan.total_bytes == 456 + 128 + 3 * 456 == 1952
    assert plan.fits is True

    properties = verification.check_all()
    print("properties:", properties.lines()[0])
    print(f"七条性质：{properties.passed}/{properties.total} 通过")
    assert properties.total == 7
    assert properties.all_passed() is True


if __name__ == "__main__":
    main()
```

**实测输出**

```text
report: 10 轮 × 3 批 | 训练 2.026e+00 → 3.892e-02（↓98.1%）| 推理 2.447e-02（最好 2.447e-02）| 30 步 | 丢弃 0
steps 30 | 每轮批数 3 | 丢弃 0 | 指纹 22bc0a3f878c7012
device: cpu/float32 | 参数 456 B + 激活 128 B + 优化器 1368 B = 1952 B / 8.0 GiB | fits=True
move: 留在 CPU：搬运 0 字节（本课所有读数都在这里复算）
properties: 通过 shuffle_order_is_deterministic  | 读数 0.000e+00 == 0 | Sampler(seed=100).order(3) 第一次 vs Sampler(seed=100).order(3) 第二次
七条性质：7/7 通过
```

**逐条解释**

1. `steps == epochs_run × batch_count` 是训练回路的一条不变式：
   `30 = 10 × 3`。它把"轮数 / 批数 / 步数"三个读数绑在一起，
   任何一个写错都会立刻违反它；
2. `report.dataset_fingerprint == dataset.fingerprint()` —— **报告绑定数据**。
   这直接对应 day053 那句"没有绑定信息的分数不是证据"：如果报告不写数据指纹，
   过两周再看这条曲线，你已经不知道它是在哪份数据上跑的了；
3. `456 + 128 + 3 × 456 = 1952` 与 `plan.line()` 逐项一致：设备账是**算术**，
   所以它能被手算核对（第 ⑤ 章）。`fits=True` 是因为 8 GiB 远大于 1952 字节；
4. `move_report` 在 CPU 上给出"留在 CPU：搬运 0 字节"——**没有搬运也要有一行**，
   否则"搬运了 0 字节"与"忘了打印搬运"无法区分；
5. `check_all()` 一次跑完七条性质。**注意这里没有 `assert properties.passed == 7`
   就收工**：还要断言 `total == 7`，否则"性质名单被删掉几条"会让
   `passed == total` 依然成立——day095 记过"一个永远为真的告警等于没有告警"，
   这里是它的姊妹版：**一个能被删空的名单，会让"全绿"变得廉价。**

## 附：本课最值得带回工作现场的五句话

1. **把"流程"也变成可断言的算术。**
   （七条性质里六条断言的是流程而不是数学：打乱、分片、批数、字节、往返、恢复）
2. **"结果更好看"是最危险的失败模式。**
   （恢复时忘了装回优化器状态、忘了从 `k+1` 开始，两者都会让损失更低 → 用相等判据）
3. **把不确定的东西注入进去。**
   （时钟、随机源、设备预算、数据顺序全部可注入；可注入才能可复现，可复现才能被断言）
4. **把结论交出来，不要替调用方做决定。**
   （`fits=False` 而不是 `raise`；哈希只覆盖"权重是不是同一份"）
5. **报告必须绑定数据。**
   （`PipelineReport.dataset_fingerprint`；"没有绑定信息的分数不是证据"）
