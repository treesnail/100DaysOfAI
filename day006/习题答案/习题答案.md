## 第 1 题答案：B

**解析**：ReAct 单步是"感知输入 → LLM 推理 → 解析 → 执行工具 → 回填观察"五态转换。感知输入在前——必须先把任务与历史拼成 messages，LLM 才有上下文可推理；解析必须在执行工具之前——程序只能执行结构化后的 `action`/`action_input`，不能直接执行自由文本。A 把感知放到了推理之后，C 把解析放到了推理之前（无文本可解析），D 先执行后解析（顺序颠倒），均不成立。

## 第 2 题答案：B

**解析**：`run()` 有两道刹车：(1) 协议终止——解析出 `final_answer` 时 `return step.final_answer`；(2) 熔断终止——`for step_no in range(1, self.max_steps + 1)` 耗尽后返回 `"达到最大步数限制，未能得出最终答案"`。A 错在缺少熔断，循环可能无限烧 token；C 错在工具失败被 `_execute_tool` 捕获后转为 Observation 反馈，不中断循环（自愈设计）；D 错在今天没有对消息列表设阈值（那是 day008 短期记忆要解决的截断问题）。

## 第 3 题答案：错

**解析**：`_execute_tool` 用 `try/except Exception` 捕获一切工具异常，返回 `f"工具执行失败: {exc}"` 字符串作为 Observation 回填给 LLM。这是刻意的**自愈循环**设计：LLM 是概率模型，调错工具、传错参数属于模型行为的正常分布，不是系统故障。把错误转成信息反馈回去，LLM 下一轮读到错误描述通常会自我纠正。端到端测试 `test_unknown_tool_feeds_error_back` 验证的正是这条路径。若让异常传播，一次模型幻觉就摧毁整个任务，系统鲁棒性荡然无存。

## 第 4 题答案：错

**解析**：熔断时 `run()` 返回的是普通字符串 `"达到最大步数限制，未能得出最终答案"`，不抛异常。设计哲学与自愈循环一致：**失败是信息，不是事故**。字符串返回值对终端用户可读，对上游调用方（如未来的 Planner）可直接拼进上下文继续推理，对评估代码可通过 `len(history) == max_steps` 且无 `final_answer` 精确统计熔断事件。`test_max_steps_guard` 断言了返回值包含"最大步数"且 `history` 恰好 3 条。

## 第 5 题答案（要点）

**LLM 的概率本质角度**：LLM 是按概率分布生成文本的采样器，不是遵守规则的程序。只给意图（"请用工具解决问题"）时，输出落在"符合格式"这个子空间的概率没有保障——模型可能用 Markdown 加粗、全角冒号、先寒暄再输出、把字段名翻译成中文。每一种变体都是分布中的合法样本，却都是解析器的灾难。把格式契约写进 System Prompt（强措辞 + 逐字段定义），本质上是**提高目标格式在输出分布中的概率质量**，把"可能符合"变成"几乎必然符合"。

**解析器的工作方式角度**：`parse_react_output` 用正则匹配固定字段标签（`Thought:`、`Action:`、`Action Input:`、`Final Answer:`），它是**确定性的字符串匹配器**，没有任何语义理解能力。人机之间因此构成一个协议：prompt 负责约束输出侧，正则负责消费侧，两侧必须对齐到字节级的标签约定。这个协议与 HTTP、JSON Schema 同构，只是约束对象从程序换成了模型——协议的严肃性不因约束对象是 AI 而降低。

## 第 6 题答案（要点）

这是一个 A/B 实验设计问题，要点：

- **实验变量**：唯一自变量是 System Prompt——对照组为当前版本，实验组在其后追加 1~2 个 few-shot 示例（完整的 Thought/Action/Action Input 输出样例）。温度、模型、任务集等其他条件必须保持一致。
- **样本**：准备一批有代表性的任务（如 30~50 个需要计算的题目），每个任务在两组 prompt 下各跑 N 次（如 3 次），因为单次采样有随机性。
- **判定指标**：首选**解析成功率**——`parse_react_output` 不抛 `ReActParseError` 的比例；可辅以**任务完成率**（得到 Final Answer 的比例）与**平均步数**作为次级指标。
- **离线替代**：没有 API 额度时，可用 MockLLM 模拟"格式漂移"的输出分布做解析器的单元级回归，但这只能验证解析器鲁棒性，不能替代真实模型的 prompt 实验——两者的结论层次不同，要在报告中区分。

判定标准示例：实验组解析成功率显著高于对照组（如从 80% 提升到 98%），且任务完成率不下降，则采纳 few-shot 版本。

## 第 7 题答案（要点）

**抛异常的好处**：

1. **显式暴露协议违例**：返回 `None` 会把"解析失败"和"本步没有 action"两种语义混淆（`ReActStep` 的字段本来就用 `None` 表示"无值"），异常把失败从正常控制流中分离出来；
2. **强制上层决策**：调用方必须显式 `try/except` 并选择策略（重试/降级/熔断），失败不会被静默吞掉；
3. **便于测试**：`pytest.raises(ReActParseError)` 直接断言失败路径，如 `test_missing_thought_raises`。

**重试策略实现思路**：在 `run()` 的循环体中，用 `try/except ReActParseError` 包住 `parse_react_output(raw)`；捕获后不中断循环，而是把 `raw` 原文作为 assistant 消息回填，再追加一条 user 消息如 `"格式错误：缺少 Action 字段。请严格按照 Thought/Action/Action Input 格式重新输出"`，然后 `continue` 进入下一步（消耗一次步数额度——这很重要，否则解析失败可以无限重试，熔断就失效了）。LLM 读到格式错误反馈后通常会自我纠正，这与工具错误的自愈机制是同构的：**一切失败皆 Observation**。

## 第 8 题答案（要点）

**各自服务谁**：`messages` 服务 LLM——它是下一轮推理的上下文，保持模型"自己说过"的原始口吻以维持推理连贯性；`self.history` 服务人类与程序——结构化的 `ReActStep` 列表，用于调试、审计、评估（如统计平均步数、工具失败率）。

**不合并的理由**：两者的内容粒度、增长速率（每步 +2 条 vs +1 条）、生命周期（局部 vs 实例级）都不同。合并意味着要么 LLM 读到结构化数据的序列化噪音，要么程序从自由文本里反复重新解析。

**删掉 history、从 messages 重新解析的问题**：

1. **重复劳动且脆弱**：每次需要推理痕迹都要对所有 assistant 消息重新跑解析器，而 messages 里还混着 system prompt 和 Observation，需要先过滤角色；
2. **解析可能二次失败**：历史输出在当时能解析成功，不代表重放解析永远稳定（比如解析器升级后正则变了），历史数据与历史解析结果应该"落账即定"；
3. **职责错位**：评估代码不该关心消息协议的细节，`history` 提供的是与协议无关的干净领域模型。

## 第 9 题答案（编程）

`smart_research_agent/tools/time_tool.py`：

```python
"""时间查询工具：返回当前时间."""

from __future__ import annotations

from datetime import datetime
from typing import Any

from smart_research_agent.tools.base import BaseTool


class TimeTool(BaseTool):
    """查询当前时间的工具."""

    @property
    def name(self) -> str:
        return "current_time"

    @property
    def description(self) -> str:
        return "查询当前日期和时间，无需参数"

    def execute(self, **kwargs: Any) -> str:
        return datetime.now().strftime("%Y-%m-%d %H:%M:%S")
```

端到端测试：

```python
"""时间工具接入 ReAct 循环的端到端测试."""

from __future__ import annotations

from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.tools.registry import ToolRegistry
from smart_research_agent.tools.time_tool import TimeTool


def test_time_tool_end_to_end():
    registry = ToolRegistry()
    registry.register(TimeTool())
    llm = MockLLM(
        responses=[
            "Thought: 需要查询当前时间\nAction: current_time\nAction Input: ",
            "Thought: 已得到时间\nFinal Answer: 现在的时间已查到",
        ]
    )
    agent = ReactAgent(llm=llm, registry=registry)
    answer = agent.run("现在几点？")

    assert answer == "现在的时间已查到"
    assert len(agent.history) == 2
    # 第二次 LLM 调用的消息里应包含 Observation（时间字符串）
    second_call = llm.calls[1]
    assert any(m.content.startswith("Observation:") for m in second_call)
```

**解析**：

- 无必填参数的工具走 `_execute_tool` 的 `required = tool.parameters.get("required") or []` → 空列表 → `kwargs = {}` 分支，所以 `execute()` 被无参调用。这就是为什么这个分支在单参数实现里就已经存在——schema 驱动设计天然兼容零参数工具。
- `parameters` 直接用基类默认值 `{"type": "object", "properties": {}}`，`required` 缺省即无必填。
- MockLLM 第一步的 `Action Input:` 留空也能解析（正则 `.+?` 配合 `\Z` 前瞻，空内容时 `action_input` 可能为空白字符串，而本工具根本不看它）。
- 断言 Observation 出现在第二次调用的消息中，验证的是闭环而非仅仅返回值。

## 第 10 题答案（编程）

修改 `_execute_tool`（`smart_research_agent/agent/react_agent.py`）：

```python
import json  # 文件顶部新增

def _execute_tool(self, step: ReActStep) -> str:
    tool = self.registry.get(step.action or "")
    if tool is None:
        return f"错误：不存在名为 {step.action} 的工具"
    required = tool.parameters.get("required") or []
    if not required:
        kwargs: dict = {}
    elif len(required) == 1:
        kwargs = {required[0]: step.action_input or ""}
    else:
        # 多参数工具：Action Input 约定为 JSON 对象字符串
        try:
            kwargs = json.loads(step.action_input or "{}")
        except json.JSONDecodeError as exc:
            return f"参数解析失败: Action Input 不是合法 JSON ({exc})"
        if not isinstance(kwargs, dict):
            return "参数解析失败: 多参数工具的 Action Input 必须是 JSON 对象"
    try:
        return tool.execute(**kwargs)
    except Exception as exc:  # noqa: BLE001
        logger.warning("工具执行异常: %s", exc)
        return f"工具执行失败: {exc}"
```

演示工具 `AddTool`（可放在测试文件内）：

```python
class AddTool(BaseTool):
    @property
    def name(self) -> str:
        return "add"

    @property
    def description(self) -> str:
        return "计算两个数 a 与 b 的和"

    @property
    def parameters(self) -> dict[str, Any]:
        return {
            "type": "object",
            "properties": {
                "a": {"type": "number", "description": "第一个加数"},
                "b": {"type": "number", "description": "第二个加数"},
            },
            "required": ["a", "b"],
        }

    def execute(self, a: float = 0, b: float = 0, **kwargs: Any) -> str:
        return str(a + b)
```

端到端测试：

```python
def test_multi_param_tool_end_to_end():
    registry = ToolRegistry()
    registry.register(AddTool())
    llm = MockLLM(
        responses=[
            'Thought: 需要相加\nAction: add\nAction Input: {"a": 3, "b": 4}',
            "Thought: 已得到结果\nFinal Answer: 3 加 4 等于 7",
        ]
    )
    agent = ReactAgent(llm=llm, registry=registry)
    answer = agent.run("3 加 4 等于几？")

    assert "7" in answer
    # 验证 Observation 确实是计算结果 "7"
    second_call = llm.calls[1]
    assert any("Observation: 7" in m.content for m in second_call)
```

**解析**：

- 分支顺序：零参数 → 单参数（保持原行为，向后兼容）→ 多参数走 JSON。新增分支没有改动既有路径，符合开闭原则。
- JSON 解析失败返回错误字符串而非抛异常，延续自愈循环哲学——LLM 读到"参数解析失败"后下一步通常会输出合法 JSON 重试。
- `isinstance(kwargs, dict)` 校验防止 LLM 输出 `[1, 2]` 这类 JSON 数组导致 `**kwargs` 炸出 `TypeError`（虽然外层 `except Exception` 也能兜住，但提前返回的错误信息更精确，模型更容易据此自我纠正）。
- 这正是 OpenAI function calling 的工作方式雏形：模型输出 JSON 参数、客户端解析后派发。区别只是 function calling 由 API 层保证 JSON 合法性，而我们要自己容错。
