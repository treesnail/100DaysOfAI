## 第一部分：选择题

### 第 1 题 —— B

**考点**：一个向量库其实是两个库（向量索引 + 记录表），以及"谁是主"这个约定落到删除与查询上的后果。

**解析**：

`base.py` 的模块 docstring 把拆法写在最前面：

```text
一个向量库其实是两个库拼起来的
├─ 向量索引    只认 (int64 id, float32 向量)   →  负责"谁离得最近"
└─ 记录表      id → (原文, 元数据)             →  负责"命中的那条是什么"
```

三个后端在这件事上的分工完全不同：

| 后端 | 向量索引 | 记录表 | 谁提供 |
|------|---------|--------|--------|
| `flat` | Python 列表 + 循环 | 同一张 `dict`（`_records: dict[str, VectorRecord]`） | 本包 |
| `faiss` | `IndexFlat*` + `IndexIDMap2` | **旁挂的一份 JSON**（`<快照>.records.json`，后缀常量 `RECORDS_SUFFIX`） | 本包（FAISS 不管） |
| `chroma` | HNSW（集合内部） | 集合里的 `documents` / `metadatas`（`native_metadata = True`） | Chroma |

于是"谁是主"必须定死，`base.py` 写的是：

```text
记录表是主，向量索引是从。
删除以记录表为准（先删表，再让索引跟随）；查询以记录表为准（命中 id 之后回来取原文与元数据）。
```

**B 正确**，因为它同时说出了这个约定的两半。一半写在 `base.query` 里那段"看起来很可疑、但刻意保留"的代码：

```python
record = self.get(record_id)
if record is None:
    # 记录表与向量索引不同步。这里**跳过并继续**而不是抛错：
    # 查询是读路径，读路径不该因为一条脏数据整体失败；
    # 而这件事必须可见——evaluate.index_health 会把它查出来。
    continue
```

另一半在 `evaluate.index_health` 的 `retrievable` 一项里，它的 detail 文案就是这条故障的描述：
"记录表里取不回：…（向量索引里有、记录表里没有 → 检索会静默少一条）"。
**只做前一半是"掩盖问题"，只做后一半是"一有脏数据就全站不可用"。**

`faiss_backend` 把"主从"写成了可核对的形态，三处都值得记住：

```text
删除   先按记录表确定"确实存在的那些 id"，再让索引跟随，最后拿索引的返回值与请求数对账
       （removed != len(targets) → VectorStoreError("删除对账失败")）
写入   先算出整批的计划 → 再动索引 → 最后提交记录表（不让半批数据落库）
统计   describe_extra() 里 index_ntotal 与 records 是两个数字，正常永远相等——差就是"两个库不同步"
```

**其余选项为什么错**：

- `A` 错：三个后端的 `count()` **都以记录表为准**。`flat.count()` 是 `len(self._records)`；
  `faiss_backend.count()` 的注释直接写着"以**记录表**为准"；`chroma.count()` 之所以能问库，
  是因为在 Chroma 上记录表就是集合本身。
- `C` 错：`delete` 是**幂等**的——删一个不存在的 id 不报错，返回值只说"真正删掉几条"
  （`flat._remove` 的注释："请求删 5 条、实际删掉 0 条是一个调用方需要看见的事实"）。
  真正会响的是 FAISS 的删除对账，而它的前提是"有人绕过了本类直接改索引/快照的两个文件不是一次写出的"。
- `D` 错：两处都站不住。哈希不可逆——`to_int64_id` 是 sha256 单向映射，反查必须靠 `_reverse` 表
  （源码注释："它是状态而不是缓存"）；原文与元数据**根本不在索引里**——`faiss.write_index`
  只能写它自己的二进制格式，所以它们被写进旁挂文件。
  `flat` 的快照同理：向量与原文在**同一份 JSON** 的一个数组里。

**结论**：记录表为主 = "读路径不抛错" + "脏状态必须可查"（`index_health`）；
对着这个约定去读三个后端的 `count/ids/get/_remove/_upsert`，它们的行为就都能解释了。

### 第 2 题 —— C

**考点**：三套符号约定、`ip` 的"距离"可以是负数、以及换算为什么只能有一处。

**解析**：

那张必须背下来的表（教程 2.1 / `metrics.py` 模块 docstring）：

| | FAISS（`IndexFlatIP` / `IndexFlatL2`） | Chroma（`space`） | 本包 |
|---|---|---|---|
| `cosine` | 需自己先归一化再取内积，**越大越近** | `d = 1 − cos`，**越小越近** | `score = cos`，越大越近 |
| `ip` | 内积，**越大越近** | `d = 1 − Σ(a·b)`，**越小越近** | `score = Σ(a·b)`，越大越近 |
| `l2` | 平方 L2，**越小越近** | `d = Σ(ai − bi)²`，**越小越近** | `score = −Σ(ai − bi)²`，越大越近 |

**C 正确**，两句话都对：Chroma 的三种 `space` 都是"越小越近"，而 `ip` 的距离是 `1 − 内积`
——**内积大于 1 时它是负数**。实测（演示第 3 节）：

```text
metric=ip：#0 a1f34c8b62e0d975 score=+10.000000 distance=-9.000000
```

`1 − 10 = −9`，所以"距离一定是正数"这个直觉是错的；同理 `cosine` 的"距离"是 `1 − cos`，
余弦为 −1 时它是 2 > 1，"距离落在 [0, 1]"也是错的。**任何"把距离当长度用"的代码**
（画图、算半径、做 range search）在 `ip` 度量下都会坏。

本包因此只保留两套口径，并且用名字钉死：

```text
score     统一口径：**越大越近**（排序、阈值、报告只用它）
distance  原始口径：**越小越近**（与 Chroma 的 distances 同名同义）
```

换算只写在 `metrics.similarity_from_distance` 一处：

```python
def similarity_from_distance(metric: str, value: float) -> float:
    if resolved == METRIC_L2:
        return -float(value)      # 平方 L2 越小越近，取负即"越大越近"
    return 1.0 - float(value)     # Chroma 就是这么定义它的距离的
```

`SearchHit` 两个字段都带，也不是冗余：报告（`summary_line` 里打印 `score` 与 `distance`）
用前者，**与外部库对账需要后者**。一个容易被忽略的差别是两者怎么来的：
`base.query` 里 `distance` 是本包**现算**的（`distance(self.metric, query_vector, record.vector)`），
而 `chroma_backend.query` 是**透传**库返回的那个数——源码里写了理由：
"再算一遍会让'库返回的距离'与'报告里的距离'变成两个数，而二者不一致时你无法判断是谁错了"。

**其余选项为什么错**：

- `A` 错：方向相反。FAISS 的 `IndexFlatIP` 的 `D` 是内积（越大越近），
  Chroma 的 `distances` 是 `1 − 相似度`（越小越近）。
- `B` 错：只有 `l2` 非负，见上面的实测。
- `D` 错（也是本日最容易吃亏的一条）：换算写两遍，**第二次就会抄错一个符号**，
  而结果是"换后端之后检索质量突然变差"——**没有任何异常**。`faiss_backend._to_score`
  把这个过程写成"先统一口径，再统一换算"：`IndexFlatIP` 的 `D` 先折成 `distance = 1 − D`
  再交给 `similarity_from_distance`；`IndexFlatL2` 的 `D` 已经是距离，直接交进去。
  于是"两个库的距离方向相反"这件事**只出现在一个 if 里**。

**结论**：看到"距离"先问是谁定义的；本包内部只信 `score`，`distance` 只用于对账与透传。

### 第 3 题 —— B

**考点**：过滤必须发生在排序之前；为什么 `_find_ids` 是抽象的一部分。

**解析**：

`base.py` 的模块 docstring 是这道题的原文依据：

> FAISS **没有任何元数据过滤能力**。于是"带过滤的检索"只有一个正确做法：
> 先按条件筛出候选 id，再在候选里排序。而"先排序取 top-k、再过滤掉不符合的"会让
> **返回条数少于 top_k，尽管库里还有更多符合条件的记录排在更后面**
> ——这个 bug 不报错、只表现为"过滤之后结果变少了"。

`faiss_backend._ranked_ids` 里最关键的一行：

```python
depth = total if restrict is not None else min(limit, total)
```

有 `restrict` 时检索深度是**全库**（`ntotal`），拿到全量排序之后逐条筛、取前 `limit`。
它在源码里的理由是："`IndexFlat` 是**精确**索引，因此这里可以走'全量 `search` + 过滤'这条笨办法"。

用测试样本可以把这个 bug 的具体形状算出来（数值见第 12 题答案）：

```text
无过滤 top-3        [4a6680cde33da45e, 7b3e0d5c9a14f286, 1c9f4b7a2e6d8035]
其中满足 strategy=structural 的只有 7b3e0d5c9a14f286（另一条 35d8c1b0a6e47f92 排在第 4 位之后）
正确实现（先筛候选再排序） → 2 条：7b3e0d5c9a14f286、35d8c1b0a6e47f92
"先取 top-3 再筛"（错）    → 1 条：7b3e0d5c9a14f286      ← 少了一条，且不报错
```

`_find_ids` 因此是抽象的一部分：**能用原生过滤的后端必须覆写它**
（Chroma 把它翻译成一次 `collection.get(where=..., include=[])`），不能的就老老实实扫记录表
（`faiss_backend` 的 `native_metadata = False`，所以它用 `base._find_ids` 的默认实现）。
Chroma 更进一步：它**覆写 `query()`** 把 `where` 一次下推给原生查询，
因为"`n_results` 只有在 `where` 一起交给原生查询时，才是**过滤之后要的条数**"。

**其余选项为什么错**：

- `A` 错：`search` 的 `k` 可以大于 `ntotal`；结果不足时 `I` 的尾部用 `-1` 填充
  （`FAISS_ID_NOT_FOUND`），`D` 用 `∓Inf` 哨兵，适配器必须"按 `-1` 丢弃，而不是翻译它"。
  测试里 `test_padding_entries_are_discarded_when_ntotal_is_stale` 专门钉住这条。
- `C` 错：先排序不会把分数算错，少的是**条数**。`similarity_from_distance` 的换算与
  过滤的先后没有任何关系。
- `D` 错：`sort_hits` 自己就排序（`key=lambda hit: (-hit.score, hit.record.record_id)`），
  它不要求输入有序——Chroma 那边还刻意"库给的顺序只用于取哪些 id，最终顺序一律由 `sort_hits` 决定"。

**代价也要记住**（这是本日最重要的一条工程结论）：`IndexFlat` 是暴力索引，
所以"全量 search + 过滤"是正确且可接受的；换成 IVF / HNSW 之后 `search(x, ntotal)`
等于放弃索引的意义，那时只剩"过采样（`k × oversample`）+ 承认近似"一条路——
**"过滤"与"近似"天生互相消耗**。

**结论**："过滤在排序之前"是**正确性**要求（少返回且不报错），不是性能优化。

### 第 4 题 —— B

**考点**：`WriteReport` 四态各自的意义、`unchanged` 为什么是独立的一态、逐条编码是刻意留下的基线。

**解析**：

`WriteReport` 的五个数与三个派生量：

```text
added      新插入的记录
updated    同一 id 被覆盖（内容确实变了）
unchanged  同一 id、内容逐位相同 → 没有改动任何东西
skipped    被调用方或护栏拒绝的记录
removed    delete 删掉的条数
written = added + updated      total = added + updated + unchanged + skipped
changed = added + updated + removed
```

**B 正确**，两句话都能在源码里找到。第一句"完全不碰库"在三个后端各写了一次：

```python
# flat._upsert
elif self._same_record(existing, record):
    unchanged += 1
    # 刻意不写回：见 docstring（对象身份是 day065 的地基）。
    continue
```

```text
faiss._upsert   ``unchanged`` 的记录**完全不碰索引**（continue）：重放同一批数据时，
                索引不该有任何写操作
chroma._upsert  **``unchanged`` 的记录完全不碰库**：这是它与直接把整批交给
                collection.upsert 的区别所在
```

这一条不是"省一次赋值"：day065 的增量索引要靠"库里那个对象没被换过"来判断
"这一块的向量不需要重算"。

第二句"并进 `updated` 就永远算不准"是 `WriteReport` 的 docstring 原文：
"如果把它并进 `updated`，'重建索引的代价'这个数就永远算不准（每个块都被报告成更新过，
而实际上一个字节都没变）"。

判 `unchanged` 的口径本身也值得写下来——三个字段**分开**比较，而不是整体比较 dataclass：

```python
existing.vector == incoming.vector and existing.text == incoming.text
    and existing.metadata == incoming.metadata
```

理由是"一旦将来给记录加一个'仅用于展示'的字段（比如入库时间），整条比较会**静默地永远不相等**，
于是每次重放都报 `updated`——而 day065 正是要看这个数字"。

顺带一个 Chroma 特有的细节：它把向量存成 **float32**，读回来必带量化误差，
所以它的"未变"判定必须带容差 `VECTOR_EQUAL_TOLERANCE = 1e-5`（`text` / `metadata` 仍精确比较）。
按逐位比的话，`unchanged` 这一态在 Chroma 上**永远不可达**。

**其余选项为什么错**：

- `A` 错：`unchanged` 的回执是"没有改动任何东西"，连对象都没有换过（见上面三处 `continue`）。
- `C` 错：`embedding_calls=6` 是**故意的**。`pipeline.py` 的模块 docstring 写着
  "day064（本模块）逐条 embedding → 直接 upsert。`embedding_calls == 被编码的条数`"，
  并说明了为什么："它让 `IngestReport.embedding_calls` 有一个**精确**的含义——
  '这次实际编码了几段文本'。有了它，day065 的任何优化才产生一个**可比较的数字**"。
  取舍表里也明写了代价："向量缓存 → 重放同一批会**重新编码**（但库不变，报告是 `unchanged`）"。
  演示脚本第 2 节最后一句就是这句题的答案：**库没变，钱照花。**
- `D` 错：`add` 与 `upsert` 的差别是**批量语义**。"`upsert` 是'把这份数据对齐到库里'，
  `add` 是'这批数据必须是新的'"；`add` 撞上已存在的 id 会**整体拒绝**（`RecordError("add() 撞上 … 个已存在的 id")`），
  而不是部分写入、更不是覆盖——"让一次批量操作是原子的，比让它'尽量成功'更重要"。
  它的用途是**第一次建库时防错**：建库脚本被误跑第二次时，`upsert` 会把它变成一个静默的正常结果。

**结论**：`unchanged` 是"这次重建省掉了多少"的分母，也是 day065 增量索引的地基；
它的判定口径（三字段分开比 + Chroma 用容差）与它的存在理由一样重要。

### 第 5 题 —— C

**考点**：Chroma 的三个坑（集合名、默认 embedding function、distances 口径），以及它们的共同点。

**解析**：

三个坑，一个比一个安静：

```text
1. 集合名有硬约束   3~512 字符；首尾必须是小写字母或数字；中间只允许 . - _ ；
                    不能出现连续两个点；不能是合法 IP 地址。
                    本包 validate_collection_name 不做任何"修复"
                    （不转小写、不替换字符）——静默改名会让
                    "我指定的 collection"与实际用的不是同一个。
2. 建集合必须显式传 embedding_function=None
                    否则 Chroma 会启用**默认 embedding function**：
                    Sentence Transformers 的 all-MiniLM-L6-v2，**本地运行且会下载模型**。
                    于是"只是建了个集合"这个动作触发了一次网络下载。
3. distances 一律"越小越近"
                    l2 是**平方** L2；ip/cosine 是 1 − 相似度。
```

**C 正确**，把三条都说了。逐条对应的源码位置：

- `validate_collection_name`（`chroma_backend.py`）逐条校验五件事，并在 docstring 里写清了
  为什么不做修复："注意它**不做任何'修复'**（不转小写、不替换非法字符）：静默改名会让
  '我明明指定了 collection=X'与'实际用到的集合'不一致，而那种不一致只会在下一次
  '数据集怎么空了'时才暴露。"它把校验放在适配器而不是"交给库去报错"，理由是
  库的报错发生在 `create_collection` 那一刻、且"错误信息里通常只有一句正则"。
- `_acquire_collection` 里 `embedding_function=None` 与"只传 `configuration`"两条：
  后者是因为"两者都能设 `hnsw.space`，同时给会被真库判为冲突；而集合已存在时 `metadata`
  会被忽略，写进去只会让 `describe_extra()` 读出一个与磁盘不一致的说法"。
  测试里有一条断言直接钉住这件事：假集合会检查 `embedding_function is None`。
- `SPACE_BY_METRIC` 是**恒等映射，仍然显式写出来**：三个名字恰好一样是巧合
  （`ip` 在 FAISS 里"越大越近"、在 Chroma 里"越小越近"），写出来的作用
  "是让'这里做过一次翻译'这件事在代码里可见"。

**其余选项为什么错**：

- `A` 错：不修复（见上）。它是**报错**，而且消息里指出"是哪一条"违反。
- `B` 错：不给 `embedding_function` 时，真库会**启用默认 EF**；本包确实永远自己提供向量
  （`add(embeddings=...)` / `upsert(embeddings=...)`），但默认 EF 仍然会在
  `get_or_create_collection` 那一刻被启用，于是"只是建了个集合"这个动作会触发一次下载——
  在离线环境里表现为**卡住**，在受限网络里表现为一个与业务无关的**超时**。
- `D` 错：Chroma 存 **float32**（约 7 位十进制有效数字），逐位比较会让 `unchanged` 永不可达
  （见第 4 题解析）。

另外两个与 Chroma 有关、同样"不报错"的事实也值得记：
它的 `persist()` **不写快照**，只是"确认并回显那个目录"（数据从头就在盘上），
内存客户端调 `persist()` 直接抛 `BackendUnavailable`；`_records_equal` 里向量用容差、
`text`/`metadata` 精确比较——"它们是被原样存取的，出现差异就是真的有差异"。

**结论**：三个坑的共同点是**都不报错**。Chroma 的适配器之所以比另外两个厚，
就是因为这些约束只能靠"在适配器里显式做一次"来暴露。

## 第二部分：判断题

### 第 6 题 —— 错

**考点**：元数据的硬约束（把最严后端的限制当公共契约），以及"不变量要挂在类型上"。

**解析**：

**第一句错**：`VectorRecord.metadata` 只允许 `str / int / float / bool / list[同类型标量]`。
`METADATA_SCALAR_TYPES = (bool, int, float, str)`，数组还必须**同类型且非空**：

```python
def is_valid_metadata_value(value: Any) -> bool:
    if isinstance(value, METADATA_SCALAR_TYPES):
        return True
    if isinstance(value, (list, tuple)):
        if not value:
            return False
        kinds = {metadata_type_name(item) for item in value}
        return len(kinds) == 1 and all(isinstance(item, METADATA_SCALAR_TYPES) for item in value)
    return False
```

两个实现细节值得单独记：

```python
METADATA_SCALAR_TYPES = (bool, int, float, str)
#  ↑ bool 必须排在 int 之前判断：isinstance(True, int) 在 Python 里是 True，
#    顺序写反会让布尔值被当成整数报错。
```

以及**元数据里的 `True == 1`**：这是 Python 的语义，不是模块的选择，
`{"flag": {"$eq": 1}}` 会命中 `flag=True` 的记录，**没有代码层面的解法，只能靠约定**。

为什么要把 Python 允许的宽松度收紧：`types.py` 的 docstring 写的是取舍——
"代价是'在纯内存后端上本来能存下的东西被拒了'，收益是**同一个 `VectorRecord`
在三个后端上行为一致**"。不这么做的典型故障是"本地用 `flat` 跑得好好的，
换 Chroma 之后在某一次 `upsert` 上抛类型错误——那时数据已经生产出来了，
问题却指向一个跟业务无关的类型细节"。

报错必须发生在**构造记录的那一刻**（`assert_metadata`），消息里点名是哪个键、什么类型：

```text
metadata['a'] 的类型不合法：dict（不允许嵌套：向量库的 metadata 是**扁平**的一层）
```

`metadata_type_name(None)` 还专门把"不存 null"写进类型名里："NoneType（向量库不存 null，请改用空串或 0）"。

**第二句也错**：校验必须挂在**类型**上（`__post_init__`），不能只挂在工厂上。
这一处是本日"被测试逼出来"的改动，值得完整复述：

```python
types.VectorRecord(record_id="x", vector=(float("nan"), 1.0))   # 通过了！
```

"**只要 `VectorRecord` 能被直接构造，就一定会有人直接构造它**（测试、脚本、调试、
以及未来的另一个模块）。校验挂在工厂上，绕过它的人不会收到任何提示——
而 `nan` 参与的任何比较都返回 `False`，于是这条记录会在排序里落到**任意位置**，且永不报错。"

搬进 `__post_init__` 后顺带做了第二件事：

```python
object.__setattr__(self, "vector", validate_vector(self.vector))
```

把 `list` 冻结成 `tuple`——frozen dataclass 的字段如果是 `list`，
外部一句 `record.vector[0] = 0.0` 就能改掉"不可变"的记录，而那个改动绕过所有校验。

一般化的教训写在源码注释里：**不变量要挂在"任何人都会经过的那条路"上。工厂函数不是必经之路，
类型构造是。**

**结论**：错。两条都不成立：元数据比 Python 允许的更严（且 `bool` 的判断顺序有讲究），
而校验的落点必须是类型构造，不是工厂。

### 第 7 题 —— 错

**考点**：`sort_hits` 的第二个排序键（分数降序、**id 升序**），以及"确定性要能被回答"。

**解析**：

```python
def sort_hits(hits: list[SearchHit]) -> list[SearchHit]:
    ordered = sorted(hits, key=lambda hit: (-hit.score, hit.record.record_id))
```

题干的推理有两处错。

**第一处："同分不容易出现"是错的——同分一定会出现。** 同一段文本用同一个确定性编码器
会得到逐位相同的向量，于是分数**精确相等**。实测（演示第 4 节，脚本自带的 6 条样本）：

```text
写入顺序：a1f34c8b62e0d975、b7e2d40a9c13f586、e08b7d25c4a91f36、
          5c9d0e13ab7f2468、2d6b9a50f31c7e84、3f5a91c0d27be684
分数精确等于 1.0 的有 2 条：
  #0 3f5a91c0d27be684 score=1.0
  #1 a1f34c8b62e0d975 score=1.0
```

注意这两条：`a1f3…` 在**写入顺序里排第一**，名次却是 `3f5a…`（id 较小）在前。
如果名次真的由插入顺序决定，它应当正好反过来——**所以名次不是由插入顺序决定的。**

**第二处："稳定排序就够了"是错的。** `sorted` 的稳定性保证的是"相等元素的相对顺序不变"，
而那个相对顺序来自**输入序列的顺序**，在 `flat` 里就是 `dict` 的迭代顺序（插入序）：

```text
同一段文本用确定性编码器会得到逐位相同的向量 → 分数**精确相等**
只看分数 → 顺序取决于 dict 的插入顺序
插入顺序在分批重放之后会变 → 同一次查询两次运行给出不同的 top-1
```

稳定性只保证"这一次的顺序与这一次的输入顺序一致"，它不能把"输入顺序"本身变成一个稳定量。

同一条纪律在本包出现了两次，两次是同一个理由：

```text
ids()     必须升序（插入序会随"批量怎么分批"变化，而"两次运行的 id 列表相同"
          是索引可复现性最基本的检查）—— flat.ids() 用 sorted(self._records)
sort_hits 分数降序 + id 升序（第二关键字不是装饰）
```

**结论**：错。不确定性不是来自算法，而是来自**没写下来的排序规则**；
第二个排序键就是那条被写下来的规则。

### 第 8 题 —— 错

**考点**：三种"没做成"分家（skipped / failed / 上抛）、`ok` 的定义、以及"报告只能收留我们认识的失败"。

**解析**：

`pipeline.py` 的模块 docstring 把三种"没做成"写成明文：

```text
skipped   数据问题：缺 doc_id / text 与 retrieval_text 都是空白   → 调用方修数据
failed    环境与匹配问题：VectorStoreError（维度不一致、后端整批拒绝）→ 修环境或重建索引
异常上抛   不在"我们认识的失败"里的异常一律向上抛，**不许记进报告**
```

这是 day061 那条纪律的**第三次复用**（day061 的 `except VectorLoaderError`、day062 的
`except ChunkingError`、今天的 `except VectorStoreError`）：

```python
except VectorStoreError:      # 只有"我们认识的失败"被记进报告
    ...
                              # 其余异常**向上抛**
```

代码里三处都只吞这一族：第 4 步的维度逐条判定（`if expected_dimension and len(vector) != expected_dimension`）、
第 5 步 `record_from_knowledge` 的 `except VectorStoreError`（"RecordError 也属于这一族"）、
第 6 步 `backend.upsert` 的 `except VectorStoreError`。**编码器自身抛出的任何异常直接冒泡。**

题干的第一个错在"更稳妥"：把"后端实现里有个 `TypeError`"这种真 bug 记成一行 `failed=1`，
它**永远不会被修**——因为报告看起来"只是有一条数据没过"。源码里的原话：
"报告只能收留我们认识的失败，不认识的失败必须让调用栈把它喊出来。"

题干的第二个错在 `ok` 的定义：

```python
@property
def ok(self) -> bool:
    """这批数据是否**干净地**进了库（有跳过或有失败都算不干净）."""
    return self.skipped == 0 and self.failed == 0
```

`skipped` 也让它为 `False`：跳过意味着调用方给的数据有洞，
而"报告是绿的"应该等价于"这批数据没有任何一条需要人再看一眼"。
所以演示第 2 节里 `skipped=0 failed=0` 是有意义的。

另外两点值得一起记住：

- 失败是**逐条记账**而不是记一条汇总（`failed += len(prepared)` 并用
  `failures.extend((record.record_id, "失败：整批写入被后端拒绝：…") …)`），
  目的是"让 failures 与 failed 计数保持一一对应"；
- 报告的自检点是一个恒等式：`seen == written + unchanged + skipped + failed`，
  对不上就说明有一条记录的归宿没有说法。

**结论**：错。窄捕获（只吞 `VectorStoreError`）+ 其余上抛 + `skipped` 也影响 `ok`，
三者缺一不可。

## 第三部分：简答题

### 第 9 题

**考点**：`agreed` / `overlap` 的分工、`first_divergence` 的措辞纪律、`verify_parity` 的
`ok` / `checked` / `available`、以及"降级参照"为什么弱。

**解析**：

**1）两个指标各回答一半。**

```python
agreed = rank_agreement(expected_ids, candidate_ids)   # 逐位相同的前缀长度
overlap = recall_at_k(expected_ids, candidate_ids, top_k)  # 前 k 条的集合交叠
```

```text
rank_agreement   逐位相同的前缀长度   → "顺序对不对"
recall_at_k      前 k 条的集合交叠    → "选出来的这批是不是同一批"
```

只留一个一定会漏，源码把两种漏法都写下来了：只看 `agreed` 会把"集合相同、顺序不同"
当成严重不一致（它可能只是一个同分平局的断法差异）；只看 `overlap` 则完全看不见顺序错乱
——**`overlap == 1.0` 而 `agreed == 0` 是一种真实且危险的状态**。
`tests/test_vectorstore_parity.py` 里 `test_compare_backends_reports_first_divergence_with_expected_and_actual`
就是这个形状：把参照换成"把 `r_d` 顶到第一"的假排名之后，`agreed == 0` 而 `overlap == 1.0`。

`agreed` 之所以取**前缀**而不是"相同位置的个数"：一旦第 3 名不同，第 6 名的"相同"已经不再
意味着同一件事——两个排名的尾部是从不同分支长出来的，逐位比下去只会得到一个既不是 0
也不是全长的数，而那个数没法指导任何人去看哪一行。候选比参照短时按短的那个截断，
缺的由 `overlap` 去说（`recall_at_k` 的分母取 `len(reference[:k])` 而不是 `k`，
否则参照自己短了会把"只看得到 2 条、2 条都在"报成 0.4）。

**2）`first_divergence` 必须指名道姓。**

对账的产出物要能**直接照着去查那一条记录**；一句"结果不一致"对读报告的人没有任何帮助。
所以 `_first_divergence` 生成的措辞里同时有"期望"与"实际"两个词（测试直接断言这两个片段），
形如：

```text
第 1 名：期望 '3f5a91c0d27be684'，实际 'a1f34c8b62e0d975'
```

两边长度不等时用 `（缺失）` 占位——候选比参照短本身就是一个必须被看见的事实
（通常是库里记录不足或被阈值切掉了）。

容差 `SCORE_TOLERANCE = 1e-6` 只在一种情形下被追加进这句说明：

```python
if left is not None and right is not None and scores_within_tolerance(left[1], right[1]):
    message += ("（两者分数差在 1e-06 的容差内：名次差异来自平局断法，不是数值精度）")
```

也就是"两个 id 不同、而两者的分数在容差内"——它在告诉读报告的人"下一步该去看排序规则，
而不是去查浮点精度"。**它不能解释任何名次差异**：本包的排序规则是确定的
（分数降序、id 升序），名次不同永远是**真问题**。分数之所以要用容差比，是因为
`flat` 用 `math.fsum` 累加、FAISS 的 C++ 内核按 float32 累加、Chroma 存 float32 再读回来，
同一个查询可能给出 `0.9999999999999998` 与 `1.0`——这两个数的名次完全一致，
用 `==` 比较只会换来一堆假失败。

**3）`ok=False` 的含义是"这份报告里有需要看的东西"，不一定是"对账失败"。**

`verify_parity` 逐行折 `failures`，**不可用的行也会被记成一条 failure**：

```text
verify_parity：ok=False checked=6 available=2
  失败：faiss/cosine 不可用：…（三段式安装指引原文）
```

上面这 6 行里有 4 行（faiss / chroma × cosine / ip）不可用，所以 `ok=False`，
而真正比过的 2 行（flat × cosine / ip）是"一致 3/3 / 交叠 100.0%"。
这正是"**装了 faiss 的机器与没装的机器，报告必须长得一样**"的实现方式：
差异只表现为一个 `available` 布尔与一句原因，而不是少了几行报告。

`checked` 与 `available` 两个计数的用途是让"因为全都不可用所以没有失败项"这种报告**可见**：
没有它们，`ok` 会在什么都没比的情况下为真（源码原话："一个'因为全都不可用所以没有失败项'
的报告必须是可见的，否则 `ok` 会在什么都没比的情况下为真"）。

**4）降级参照弱在哪；以及为什么样本要用 `metric="ip"` 构造。**

`compare_backends` 在 `reference=None` 时走 `_naive_reference`：

```python
scored = [(record.record_id, metric_score(metric, query, record.vector)) for record in records]
scored.sort(key=lambda item: (-item[1], item[0]))
```

它用的是 `metrics.score`（与 `flat._ranked_ids` 调用的**是同一个函数**）与**同一个排序键**。
于是"一致"只证明**它等于它自己**：

```text
flat 的 _ranked_ids 调用的正是 metrics.score   → agreed 恒等于 top_k
"实现里少排了一条"       → 降级参照会与后端一起少排（它读的也是同一批记录）
"平局的断法反了"         → 降级参照与后端共享同一个排序键，会一起反
```

所以它产出的"全绿"没有任何信息量，只适合"给人临时看一眼"，**不能作为 CI 的判据**。
真正的对账必须显式传入独立实现算出的期望值（`tests/test_vectorstore_parity.py` 里每一条都这么写），
而 `evaluate.py` 是生产代码、**不能 `import tests`**（测试件不该进生产依赖），
所以它接受一个 `reference` 参数由调用方注入——这正是"注入独立参照"这条纪律的落点。
同一条限制也适用于端点的 `/vectorstore/compare`：它注的是降级参照，因此那一行
`agreed/overlap` 只能说明"同一台机器上几个后端彼此一致"。

第二条：`types.make_record` **只在 `cosine` 下做 L2 归一化**。用
`sample_records(metric="cosine")` 构造时所有向量都已经是单位长度，此时 `ip` 与 `cosine`
的排名**完全相同**（第 11 题答案里有实测：两者 top-3 都是
`[4a6680cde33da45e, 7b3e0d5c9a14f286, 1c9f4b7a2e6d8035]`），看不出两个度量的差别。
要看见差别必须用 `metric="ip"` 构造（不归一化），那时模长 10 倍的那条会把 `ip` 的 top-1
顶到 `7b3e0d5c9a14f286`（`ip` 分数 10.0，而 `cosine` 里它与 `4a6680cde33da45e` 并列 1.0）。
演示脚本自带的样本里，这条记录是 `a1f34c8b62e0d975`——同一手法，两套 id。

**结论**：`agreed` 管顺序、`overlap` 管集合，两个一起看才分得清"选错了"与"排错了"；
`first_divergence` 必须指名道姓，容差只能用来解释平局；`ok=False` 是"有东西要看"；
降级参照的全绿不能当判据，要看见度量差异必须用 `metric="ip"` 构造数据。

### 第 10 题

**考点**：三段式报错的三句话、400 与 409 的分工、"缺依赖"在两个端点表现不同的原因。

**解析**：

**1）三句各解决一个问题。**

```text
后端 faiss 不可用：缺少 faiss（numpy 已满足）。
安装：pip install faiss-cpu
或者改用：flat（零可选依赖，结果逐位可复现）
```

```text
缺什么          让使用者知道是自己的环境还是别人的代码
怎么装          一条**可复制粘贴**的命令（不是"请安装 faiss"）
还能用什么      现场可用的替代品，并且带上它适合什么
```

第一句里的"（numpy 已满足）"来自 `_missing_phrase`，它把 `requires` 里**已满足**的依赖一并说出来：
"faiss 缺的常常只是 faiss 本身而 numpy 在，这时'缺少 faiss、numpy'会让使用者去装一个
已经有了的包；而只说'缺少 faiss'又丢掉'numpy 这个前提已经成立'这个事实。"

第三句最容易被省掉（写报错的人容易觉得"我只负责说清我缺什么"），也最有用：
**进度不该被一个可选依赖卡死**。`_available_alternatives` 还会**过滤掉同样不可用的后端**
——"否则会给出'改用 chroma'而 chroma 同样没装——这种建议比没有建议更浪费时间"。

`flat` 在 `BACKEND_PROFILES` 里排第一（`requires=()`）正是为了让这一句在任何机器上都成立；
源码里那个"连 flat 都不可用"的分支是**防御性**的（`# pragma: no cover`），
但它仍然留了一句话而不是返回空串："三段式的第三句宁可说'没有别的可用后端'，
也不能变成'或者改用：'这种把使用者晾在半路的样子。"

顺带两个实现细节：探测走 `importlib.util.find_spec`（只读 `sys.path`，不真的 `import faiss`
——那会把几百 MB 与一次磁盘 IO 拉进来，"探测的代价与使用的代价是两件事"）；
而且用的是**属性访问**（`importlib.util.find_spec(...)`）而不是 `from importlib.util import find_spec`，
"区别在于前者可以被 monkeypatch 替换——'缺依赖'与'依赖齐全'两条分支因此都能在测试里被真实走到"。

**2）400 与 409 的分工，判据是"重发一次请求能不能修好"。**

```text
where 写法非法 / top_k 越界   → 400  FilterError（查询本身写错了，改请求就能修好）
查询向量与库维度不一致          → 409  VectorError（库与编码器不是同一套，改请求修不好）
```

`400` 的触发者是 `FilterError`，覆盖的写法错误有：未知运算符、`$in`/`$nin` 给空列表
（"空列表会让条件的命中集恒为空，因此直接拒绝而不是静默返回空结果"）、同一字段写多个运算符、
字段条件是空字典 `{"field": {}}`、`$and`/`$or` 的值不是非空列表、`$and`/`$or` 与其他字段条件混写。
`FilterError` 的消息里**带着 12 个运算符**（`SUPPORTED_OPERATORS`），写错的人当场就能改对。
`top_k` 的两条边界（`< 1`、`> MAX_TOP_K = 1000`）也走这一族；`top_k=0` 表示"没给"，
用项目级基线 `settings.vector_default_top_k`。

`409` 的触发者是 `VectorError`，报错文案与 `base.query` 的那一条逐字一致：

```text
查询向量是 8 维，本库是 4 维：查询用的编码器与建库用的不是同一个。
```

它在端点的 docstring 里被解释为"**Conflict**：库与查询用的编码器不是同一套，重新编码能修，
换个请求参数修不了"。同一个请求重发多少次都还是 409——**这类错误的正确动作是换编码器或重建库**。
把两者合成一个 400 会让客户端按"改参数"的思路去试，而那条路走不通。

实现上有一处顺序值得注意：`routes.vectorstore_search` 里 `except FilterError` 必须写在
`except VectorError` 之前（注释："FilterError 是 VectorStoreError 的子类，必须写在它前面"），
否则 `where` 的 400 会被 409 那条分支先接住。

**3）同一个"缺依赖"，两个端点的差别来自"走哪条代码路径"。**

- `/vectorstore/compare` → `compare_backends` → `_compare_one`，那里只把
  `BackendUnavailable` / `ImportError` **折成一行**（`_unavailable_row`：
  `available=False`、`agreed=0`、`overlap=0.0`、`first_divergence="后端不可用"`、
  `note` 里是三段式原文），**其余异常一律上抛**。所以缺 faiss 只是一行报告，端点 200。
  端点 docstring 的理由："同一个请求在装了 faiss 的机器与没装的机器上返回**行数相同**的报告，
  只差一个布尔……若把缺依赖变成 500，第二台机器上就只能得到一句错误。"
- `/vectorstore/records` → `store.delete(...)`：`BackendUnavailable` 被端点的
  `except BackendUnavailable → 409` 直接接住（来源是 `base.delete` 里的
  `if not self.supports_delete: raise BackendUnavailable(...)`，或后端在构造期就不可用）。
  这里没有"折成一行报告"这件事可做——删除是**一次要改库的动作**，
  不存在"返回一份报告说这条没删成"的中间态。
- 同端点上 `where={}` 的 400 是**端点自己加的**（比底层更严）：底层把空子句当"无过滤"
  是正确的查询语义，但同一个值落到删除上就变成"清空整库"，
  所以"**同一个语义在读写两条路径上的后果不对等时，收紧那条危险的一侧**"。

把这一套状态码收全，它们各自指向"该改什么"：

```text
/vectorstore/upsert    records 为空 → 400；VectorStoreError（维度不一致、整批被拒）→ 400；
                       编码器自身抛出的其它异常 → 500（报告只能收留我们认识的失败）；形状不对 → 422
/vectorstore/search    where 非法 / top_k 越界 → 400；维度不一致 → 409；形状不对 → 422
/vectorstore/records   ids 与 where 同时给 / 两者都不给 / where={} → 400；
                       后端不支持删除 → 409；删不存在的 id → 200 且 removed=0（幂等，但返回值必须诚实）
/vectorstore/compare   缺依赖 → 200（行里 available=False）；records/query 为空、记录不合格、
                       未知度量、top_k 越界 → 400；形状不对 → 422
```

**结论**：三段式的价值在"下一步做什么"；状态码的价值在"该改请求还是该改库还是该改环境"——
`400` 改请求、`409` 改库/编码器、`200 + available=False` 只是"这台机器没装"。

  但从**第 2 名起**就与 `cosine` 分家了（`1c9f…` vs `7b3e…`）——`agreed` 恰好是 1。

**为什么参照实现必须是 `brute_force_top`，不能用 `compare_backends` 的缺省参照？**

因为缺省参照（`evaluate._naive_reference`）就是 `metrics.score` 现算 + 同一个排序键，
而 `flat._ranked_ids` 调用的**正是** `metrics.score`：

```text
flat 的 _ranked_ids 调用的正是 metrics.score   → agreed 恒等于 top_k
"实现里少排了一条"  → 降级参照会与后端一起少排（它读的也是同一批记录）
"平局的断法反了"    → 降级参照与后端共享同一个排序键，会一起反
```

也就是说，用缺省参照时这条断言"一定通过"——它只证明这段代码等于它自己，
不会因为"索引类型选错（`IP` vs `L2`）""换算方向抄反""平局断法反了"中的任何一条而变红，
**这就是"不会变红的断言等于没有断言"**。

`tests/vectorstore_samples.brute_force_top` 是**不复用 `metrics.py`** 的一段朴素实现，
只用 `math` 与最朴素的循环重写三种公式，排序键也自己写一遍：

```text
cosine   cos = Σ(a·b) / (|a| · |b|)
ip       dot = Σ(a·b)
l2       score = −Σ(a − b)²        （取负号让"越大越近"统一）
```

两条独立实现互相对账，上面那三类错误才会露馅。`evaluate.py` 的模块 docstring 把这条
方法论写成了明文："判定的依据必须与被判定的实现相互独立，否则它只是在复述实现。"

工程上还有一个理由：`evaluate.py` 是生产代码、**不能 `import tests`**，
所以生产侧的缺省参照只能是降级参照；真正的对账在
`tests/test_vectorstore_parity.py` 里——那里每一条都显式注入独立算出的期望排名。
本题就是照着那条纪律写的。

四个数各有分工，值得逐个读一遍：

```text
candidates     过滤之后的候选条数（= _find_ids 的基数）；没有 where 时等于库内条数
count          这次实际返回的命中条数（受 top_k 与 min_score 影响）
filter_applied where 非空时为 True（{} 与 None 都是 False，两处都"不过滤"但含义不同）
ids()          名次顺序（分数降序、id 升序）
```

`where={"strategy": "structural"}` 那一行是本日的核心证据：
样本库里有 **2** 条 `structural` 记录，而"最像的 3 条"里只有 1 条是 `structural`
（另一条 `35d8c1b0a6e47f92` 排在更后面）。**正确实现返回 2 条，朴素的"先 top-k 再筛"只返回 1 条，
且不报错。** 这就是 `base.py` 与 `faiss_backend.py` 两处 docstring 反复强调的那句话。

`faiss` 侧额外要记的一点：它的 `native_metadata = False`，所以 `_find_ids` 走的是
`base._find_ids` 的默认实现（扫记录表），而 `_ranked_ids` 在 `restrict` 非空时把检索深度
提到 `ntotal`（全量）——`IndexFlat` 是精确索引，所以"全量 search + 筛"与 `flat` 逐条一致。
（`_find_ids` 的语义必须与查询路径一致，否则 `delete(where=...)` 与 `query(where=...)`
会给出不同的候选集，"而那种不一致非常难查"。）

**为什么"反事实"比"断言返回条数等于 2"更能守住这条契约？**

因为"条数等于 2"只是一个**数字**，它可能被错误实现"恰好也对"地满足：

```text
正确的做法   先在 {7b3e…, 35d8…} 里排序 → 2 条
先取 top-3 再筛  只剩 {7b3e…}           → 1 条
```

如果哪一天有人把 `where` 的实现换成"在 top-k 结果上做交集"，只要样本恰好让 top-k 覆盖了
全部符合条件的记录，这个数字仍然是 2、断言仍然全绿——**测试通过而契约已经破了**。
把反事实也算出来，就把"两种做法的差别"本身写进了断言：

```text
naive 的条数（1）必须 **小于** 正确实现的条数（2）
被漏掉的那条 id 必须是 35d8c1b0a6e47f92（而不是"某条不确定的记录"）
```

这样"过滤跑到了排序后面"这件事一发生，断言立刻变红，而且报错信息直接指出被漏掉的是谁。
这与 day062 第 12 题"必须**同时**断言上限与例外"是同一条纪律：
**把契约的反面也写进断言**——只断言"正确时应该是什么"，
就永远抓不到"错误时会变成什么"。

顺带两条同样是"反面"的断言值得保留：

- `candidates` 必须在**正确实现**下才等于 2：它是 `_find_ids` 的基数，与 `top_k` 无关。
  连 `min_score` 那一组一起看（`candidates=5` 而 `count=2`），"候选"与"命中"两个概念
  才真正分开——这正是 `SearchResult` 里那两个字段存在的理由：
  ```text
  candidates=0 且 filter_applied=True   → 过滤器把所有记录都排除了
  candidates=0 且 filter_applied=False  → 库是空的
  candidates>0 而 count=0               → 阈值把命中切掉了（数据在，只是不够像）
  ```
- `store._find_ids({"strategy": "structural"})` 单独断言一次：
  它把"候选集是谁"从"返回了几个"里解放出来，将来若有人把 `_find_ids` 改成
  "先取 top-k 再交集"，这一条会先红。
