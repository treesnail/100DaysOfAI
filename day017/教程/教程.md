## 第一章：为什么需要 MCP —— 从 N×M 集成灾难到标准协议

### 1.1 先看清问题：能力接入的"组合爆炸"

回顾 M1 阶段我们的工作：给 Agent 接计算器，写了 `tools/calculator.py`；接 LLM，写了 `llm/openai_compatible.py`。这些接入全是**私有方式**——每接一个新能力，就要在 Agent 代码里写一份专用的适配代码。

把这个模式放大到整个行业，问题就出现了。假设：

- 有 N 个 LLM 应用（Claude Desktop、IDE 插件、你的 SmartResearch Agent……）；
- 有 M 个能力提供方（文件系统、数据库、搜索引擎、企业内部知识库……）。

没有标准协议时，每个应用想接每个能力，都要写一份专用集成代码，总工作量是 **N × M**。每边的开发者都要了解对边的 API 细节，接口一旦变动，N×M 份代码跟着改。

MCP（Model Context Protocol）的思路是经典的**协议解耦**：在两者之间插入一个标准层。

```text
没有 MCP：                         有了 MCP：
 应用A ──┐                           应用A ──┐
 应用B ──┼── 各自私有集成 ── 能力X     应用B ──┼─ MCP Client ─┐
 应用C ──┘                    能力Y     应用C ──┘              │
                                  能力Z                        ├─ 标准协议（JSON-RPC 2.0）
                                N×M 份适配代码                 ┘
                                                     能力X ──┐
                                                     能力Y ──┼─ MCP Server ─┘
                                                     能力Z ──┘
                                                  N+M 份适配代码
```

工作量从 N×M 降为 N+M：**每个应用只实现一次 MCP Client，每个能力方只实现一次 MCP Server**，两边从此互不相识也能协作。这和 HTTP 统一了"浏览器与服务器"的对接是同一个思想——协议的价值不在于技术上多新奇，而在于**把双边谈判变成多边共识**。

### 1.2 MCP 的三大原语

MCP 把"能力"归纳为三种原语（primitive），今天的主角是第一个：

| 原语 | 本质 | 谁决定何时用 | 类比 |
|------|------|-------------|------|
| **Resources** | 可读取的**数据**，URI 寻址 | 应用（application-driven） | 文件、数据库记录、配置项 |
| **Tools** | 可执行的**行为**，带参数 | 模型（model-driven） | 函数调用 |
| **Prompts** | 可参数化的**提示词模板** | 用户（user-driven） | 邮件模板 |

注意"谁决定何时用"这一列，它是理解三者分工的钥匙：

- Resource 是**被动数据**，由宿主应用决定何时读取、塞不塞进上下文——模型甚至可以不知道资源的存在。
- Tool 是**主动行为**，由模型在推理过程中决定何时调用（回想 day006 的 ReAct 循环：`Action:` 就是模型在做这个决定）。
- Prompt 是**给人用的模板**，通常由用户在界面上点选，填充参数后作为对话起点。

### 1.3 消息格式：JSON-RPC 2.0

MCP 的所有通信都承载在 **JSON-RPC 2.0** 之上。这是一个极简的远程调用协议，只定义三种消息：

```json
// 请求：id 是配对凭证，method 是要调的方法，params 是参数
{"jsonrpc": "2.0", "id": 1, "method": "resources/read", "params": {"uri": "research://knowledge/rag"}}

// 成功响应：id 原样带回，result 装结果
{"jsonrpc": "2.0", "id": 1, "result": {"contents": [{"uri": "...", "text": "# RAG 速览"}]}}

// 错误响应：id 原样带回，error 装错误码与消息（与 result 互斥）
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32602, "message": "Unknown resource"}}
```

三个设计细节值得记住：

1. **`id` 是请求-响应的配对凭证**。一条连接上可以并发发出多个请求，响应顺序不保证，客户端靠 `id` 把响应还给正确的等待者。这解释了为什么 `id` 必须原样带回。
2. **result 与 error 互斥**。一条响应要么成功要么失败，不存在"半成功"。这种二元性让客户端的错误处理逻辑非常干净。
3. **`jsonrpc: "2.0"` 是版本哨兵**。解析器看到它就知道该按哪个版本的规则解释消息——协议可演进的锚点。

我们在 [mcp_server/protocol.py](../源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py) 中用 pydantic 对这三类消息和三种能力描述（ResourceDescriptor / ToolDescriptor / PromptDescriptor）建了模。这份"词汇表"在后续 day018~day023 会被反复引用，是 M2 阶段所有 MCP 代码的共同地基。

### 1.4 一个工程细节：为什么包名绝不能叫 `mcp`

今天新建的包叫 `smart_research_agent.mcp_server`，而不是看起来更自然的 `smart_research_agent.mcp`。这不是口味问题，是一条硬约束：

Python 的 import 是**先匹配先赢**。如果项目里存在 `smart_research_agent/mcp/`（或以其他方式进入搜索路径的 `mcp` 包），那么 `from mcp.server.fastmcp import FastMCP` 命中的将是**我们自己那个没有 FastMCP 的包**，而不是官方 `mcp` 库——报错信息会是莫名其妙的 `ImportError: cannot import name 'FastMCP'`。

这类 bug 的阴险之处在于：代码看起来完全正确，错误位置却离根因很远。**凡是项目要用到同名第三方库的领域，自建包就必须主动让名。** 这是用一次命名成本，换掉一类隐蔽故障。

> 思考题：除了改名，还有什么机制能避免这种遮蔽？提示：想想 Python 的绝对/相对导入和包搜索路径的顺序。

## 第二章：Resources 原语 —— 数据而非行为

### 2.1 用 URI 给数据一个地址

Resource 的核心思想朴素得像 Web：**每一份数据都有一个地址（URI），客户端凭地址读取内容。** 我们今天暴露的两类资源：

```text
research://knowledge/rag        ──▶ data/knowledge/rag.md 的全文
research://config/project_name  ──▶ "智研 AI 助手"
```

URI 的三个部分各有职责：

```text
research://knowledge/rag
└──┬──┘  └────┬───┘ └┬┘
 scheme    资源类别   参数（哪一份）
```

- **scheme（`research`）**：命名空间，声明"这是 SmartResearch 体系的资源"，避免与其他 Server 的 URI 冲突。选什么 scheme 是协议留给我们的自由，但**一个 Server 一个语义清晰的 scheme** 是好习惯。
- **路径中的类别段（`knowledge` / `config`）**：把资源按域分组，客户端看一眼 URI 就知道自己读的是什么性质的数据。
- **参数段（`rag`）**：定位具体那份数据。

### 2.2 URI 模板：一个处理器服务无穷多地址

如果每篇知识文档都要单独注册一个资源，服务器代码会爆炸。MCP 的答案是 **URI 模板（URI Template）**：

```python
@app.resource(
    "research://knowledge/{doc_id}",   # 模板：{doc_id} 是占位参数
    name="knowledge_doc",
    description="知识库 Markdown 文档，按 doc_id 读取 data/knowledge/{doc_id}.md",
    mime_type="text/markdown",
)
def knowledge_doc(doc_id: str) -> str:
    return load_knowledge_doc(doc_id)
```

机制与 Web 框架的路由完全同构（FastAPI 的 `@app.get("/docs/{doc_id}")` 你一定眼熟）：

1. 服务器收到 `resources/read`，URI 为 `research://knowledge/rag`；
2. FastMCP 把它与已注册的模板逐个匹配，`research://knowledge/{doc_id}` 命中；
3. 占位参数被提取出来，作为函数实参：`knowledge_doc(doc_id="rag")`；
4. 返回值被包装成 `TextResourceContents`（带上 `mime_type`），作为 `result` 返回。

**模板把一个"资源族"压缩成一次注册**：今天 data/knowledge/ 下有 3 篇文档，明天加到 300 篇，服务器代码一行不用改——新增文件自动获得新 URI。这是"数据驱动"对"代码驱动"的胜利。

客户端通过 `resources/templates/list` 拿到模板清单（注意：不是 `resources/list`——后者只列出**静态注册、无参数**的具体资源；我们的两个资源都带参数，所以只出现在模板列表里）。

### 2.3 读取语义：为什么 Resource 必须是"安全只读"

MCP 对 Resource 的隐含契约是**幂等只读**：读一次和读一百次，返回同样的内容，且不改变服务器状态。这个约束不是装饰，它有直接的工程后果：

- **客户端可以放心缓存**。读 `research://knowledge/rag` 的结果可以缓存到本地，直到收到变更通知（见第三章）——如果读取有副作用，缓存就是定时炸弹。
- **应用可以自动预取**。宿主（如 IDE 插件）可能为了提速而预读一批资源；若读取会触发扣费、写库、发消息，"预取"就成了灾难。
- **LLM 上下文装配可以声明式**。宿主可以把一组 URI 声明为"本对话的相关上下文"，由框架统一读取装配——这只有在读取无代价差异时才可行。

HTTP 里 GET 的"安全方法"语义，在 MCP Resource 上以同样的理由复现了。

### 2.4 Resources vs Tools：本质区别是"数据 vs 行为"

这是今天最需要内化的一个区分，值得从五个维度对照：

| 维度 | Resource | Tool |
|------|----------|------|
| 本质 | **数据**：一份可被读取的内容 | **行为**：一个可被执行的操作 |
| 寻址方式 | URI（名词） | 名称 + 输入参数（动词） |
| 副作用 | 不允许（安全只读） | 允许且常见（搜索、写库、调 API） |
| 驱动方 | 应用决定何时读（application-driven） | 模型决定何时调（model-driven） |
| 返回值特征 | 内容 + mime_type，可直接入上下文 | 结构化结果，常需模型再加工 |

判断"新能力该做成 Resource 还是 Tool"的口诀：**问"它是什么"用 Resource，问"帮我做什么"用 Tool。**

- 知识库文档是"它是什么" → Resource（今天做的）。
- "按关键词搜索知识库"是"帮我做什么" → Tool（day018 的任务）。

一个容易混淆的边界案例：读取"今天的天气"。如果它是服务器上静态缓存的一份数据文件，做成 Resource 合理；如果每次读取都要实时调用气象 API，那它本质是一次行为，应该做成 Tool。**判断标准不在数据长什么样，而在获取它的动作有没有副作用。**

### 2.5 我们的实现：两个资源与一个安全决策

完整代码见 [mcp_server/resources_server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/resources_server.py)，核心结构：

```python
app = FastMCP("smart-research")

@app.resource("research://knowledge/{doc_id}", ..., mime_type="text/markdown")
def knowledge_doc(doc_id: str) -> str:
    return load_knowledge_doc(doc_id)

@app.resource("research://config/{key}", ..., mime_type="text/plain")
def config_item(key: str) -> str:
    return load_config_item(key)
```

两个处理器都很薄，厚度在 `load_*` 函数里——那里有两个刻意的防御设计：

**（1）配置资源的白名单。** `Settings` 里有 `openai_api_key` 这种敏感字段，如果 `research://config/{key}` 直接 `getattr(settings, key)`，任何一个能连上 Server 的客户端都能把密钥读走。所以：

```python
CONFIG_WHITELIST = ("project_name", "default_model", "log_level", "debug")

def load_config_item(key: str) -> str:
    if key not in CONFIG_WHITELIST:
        raise KnowledgeNotFoundError(f"配置项不可暴露或不存在: {key!r}")
    return str(getattr(settings, key))
```

注意白名单拒绝时，我们**不区分"键不存在"和"键被屏蔽"**——统一报"不可暴露或不存在"。这是安全设计的一个细节：如果两种情况的报错不同，攻击者就能用报错差异探测出系统里存在哪些敏感键（一种侧信道）。**对未授权访问，信息泄露越少越好。**

**（2）知识库的目录穿越防护。** `doc_id` 来自 URI，是不可信输入。若不设防，`doc_id = "../config"` 就可能拼出 `data/knowledge/../config.md` 这样的路径，读到知识库目录之外的文件：

```python
if "/" in doc_id or "\\" in doc_id or doc_id.startswith("."):
    raise KnowledgeNotFoundError(f"非法的 doc_id: {doc_id!r}")
```

URI 模板参数按规范不含 `/`，但**防御代码不该依赖"上游一定守规矩"**——这就是纵深防御（defense in depth）：协议层挡一次，代码层再挡一次。

## 第三章：订阅与通知 —— 数据变了，客户端怎么知道

### 3.1 问题：缓存与新鲜度的矛盾

第二章说 Resource 幂等只读、客户端可以缓存。但知识库文档是会更新的——研究员改了 `rag.md`，缓存了旧版本的客户端怎么办？

两种解法：

- **轮询**：客户端每隔一段时间重读所有资源。简单，但大部分重读都是浪费（数据没变），且变更到感知之间有延迟窗口。
- **订阅推送**：客户端声明"我关心这个 URI"，服务器在内容变化时主动推送通知。精准、及时，但要求服务器维护订阅状态。

MCP 选了后者，协议词汇是三个方法：

```text
resources/subscribe        客户端 → 服务器：订阅某个 URI
resources/unsubscribe      客户端 → 服务器：取消订阅
notifications/resources/updated   服务器 → 客户端：这个 URI 的内容变了
```

注意第三个方法的 `notifications/` 前缀——它是 **JSON-RPC notification**：一种没有 `id`、不要求响应的单向消息。订阅通知不需要客户端回执，服务器"喊一嗓子"就完事，这是 notification 语义的典型用武之地。

### 3.2 能力声明：订阅是"可选技能"

MCP 的连接初始化握手时，服务器会声明自己的能力（capabilities）：

```json
{"capabilities": {"resources": {"subscribe": true, "listChanged": true}}}
```

- `subscribe: true`：本服务器支持订阅通知；
- `listChanged: true`：资源清单本身可能变化（比如知识库加了新文档），变化时会发 `notifications/resources/list_changed`。

为什么做成显式声明而不是默认支持？**因为协议要适配能力参差的服务器**。一个只读静态文件服务器实现订阅很容易；一个代理上游 API 的服务器可能根本不知道上游数据何时变化。能力声明让客户端在握手时就知道"这段连接里哪些特性可用"，避免了运行时的"调了才知道不支持"。

> 思考题：这种"握手时声明能力"的模式，在 HTTP/2、WebSocket 扩展协商里也能看到。它的本质好处是什么？

### 3.3 订阅机制的完整时序

```text
客户端                     服务器                知识库文件
  │  initialize（握手，声明能力） │                    │
  │◀──────────────────────────▶│                    │
  │  resources/subscribe        │                    │
  │  {uri: research://knowledge/rag}                  │
  │──────────────────────────▶│  记录订阅表           │
  │  resources/read             │                    │
  │──────────────────────────▶│──── 读 rag.md ──────▶│
  │  result（缓存到本地）         │                    │
  │◀──────────────────────────│                    │
  │                            │              （文件被编辑）
  │  notifications/resources/updated                 │
  │◀──────────────────────────│  检测到变更           │
  │  丢弃本地缓存                                     │
  │  resources/read（重新拉取）  │                    │
  │──────────────────────────▶│──── 读 rag.md ──────▶│
```

关键洞察：**通知本身不携带新内容，只携带"哪个 URI 变了"**。这是有意的设计——通知保持轻量，是否重新读取、何时重新读取的决定权留给客户端（也许客户端接下来根本用不到这份资源，那就别浪费带宽）。这和 HTTP 缓存验证里的 ETag 思想相通：先问"变没变"，变了再拉全量。

### 3.4 今天的实现范围

订阅通知需要文件监控（watchdog 之类的机制）支撑，属于后续增强。今天我们的服务器聚焦**读取链路**（模板注册 → URI 匹配 → 读取 → 错误处理），这是 Resources 原语的主干；订阅机制本章讲清原理即可，习题里会要求你动手模拟一遍通知流程，把原理落成代码手感。

## 第四章：传输层 —— 内存传输与 stdio 传输的关系

### 4.1 同一条消息流，不同的字节通道

MCP 的架构是严格分层的：

```text
┌────────────────────────────────────────────┐
│  协议层：方法语义（resources/read、tools/call …）│  ← 本章与今天测试关心的是这里
├────────────────────────────────────────────┤
│  消息层：JSON-RPC 2.0（request/response/notification）│
├────────────────────────────────────────────┤
│  传输层：stdio / Streamable HTTP / 内存        │  ← 可替换的字节通道
└────────────────────────────────────────────┘
```

上面两层完全不知道自己在用什么传输。`resources/read` 的语义不会因为跑在 stdio 上还是 HTTP 上而改变——**传输层只是消息的搬运工**。这个分层带来的直接好处：

- **stdio**：宿主进程（如 Claude Desktop）把 MCP Server 当子进程拉起，双方通过子进程的标准输入/输出互发 JSON-RPC 消息。零网络配置、天然进程隔离，是本地集成的首选。我们的 `main()` 就是为它准备的：`app.run(transport="stdio")`。
- **Streamable HTTP**：Server 独立部署成网络服务，远程客户端走 HTTP。留给生产部署（M2 后期与 Docker 结合）。
- **内存传输**：客户端与服务器在**同一进程内**通过一对内存队列直连。不走子进程、不走网络，是官方为**测试**准备的通道。

### 4.2 内存传输的工作原理

`create_connected_server_and_client_session` 做的事，拆开看并不神秘：

```text
   客户端 (ClientSession)                服务器 (FastMCP)
   ┌──────────────────┐                ┌──────────────────┐
   │ write ──────────▶│  内存队列 req   │──────────▶ read   │
   │ read  ◀──────────│  内存队列 resp  │◀────────── write  │
   └──────────────────┘                └──────────────────┘
```

它在进程内建两条双向消息流，把客户端的写端接服务器的读端、服务器的写端接客户端的读端，然后完成 MCP 初始化握手，最后把一个**就绪的 `ClientSession`** 交给你的测试代码。

关键点是：**经过内存传输的消息与经过 stdio 的消息一模一样**——同样的 JSON-RPC 序列化、同样的握手、同样的请求/响应配对。唯一的差别是字节走的通道。所以我们用内存传输测过的行为，换成 stdio 部署后语义完全不变，变的只是集成方式。这就是"分层架构让测试替身（test double）成为可能"的绝佳示范。

### 4.3 为什么测试必须用内存传输

对照 FIRST 原则（day002）逐条看：

- **Fast**：不起子进程、不开端口，一次会话建立是微秒级。
- **Independent**：每个测试可以自建会话，互不干扰。
- **Repeatable**：无网络、无外部进程，任何机器任何时间结果一致。
- **Self-validating**：断言语义结果（内容、错误类型），不看日志。

如果用 stdio 测，就得拉起真实子进程、通过管道收发消息——慢、脆（进程清理问题）、跨平台细节多（Windows 的 stdio 管道尤其多坑）。**测试应该验证"我的资源逻辑对不对"，而不是顺带验证"操作系统的进程管道好不好用"。** 内存传输把后者干净地切掉了。

### 4.4 异步测试与 pytest-asyncio

MCP 的客户端 API 全是 async 的（`await session.read_resource(...)`），因此测试函数也是 async 的。pytest 默认不认识 `async def test_`，会直接跳过——这是 pytest-asyncio 存在的意义。

我们在 `pyproject.toml` 里加了一行：

```toml
[tool.pytest.ini_options]
asyncio_mode = "auto"
```

`auto` 模式的含义：**所有 `async def test_` 函数自动被当作 asyncio 测试执行**，不用逐个加 `@pytest.mark.asyncio` 装饰器。这是 pytest-asyncio 1.x 推荐的项目级配置方式——模式写在配置里一次，测试代码保持干净。

### 5.2 服务器的组装：声明式注册

得益于 FastMCP，服务器的"组装"几乎全是装饰器声明：

```python
from mcp.server.fastmcp import FastMCP

app = FastMCP("smart-research")

@app.resource("research://knowledge/{doc_id}", name="knowledge_doc", ...)
def knowledge_doc(doc_id: str) -> str: ...

@app.resource("research://config/{key}", name="config_item", ...)
def config_item(key: str) -> str: ...
```

对比 M1 阶段手写的 `ToolRegistry`（day003）：FastMCP 做的事本质相同——**收集能力描述 + 分发调用**——但它额外实现了完整的 MCP 协议机（握手、能力声明、错误码映射、通知），这些是我们自己造轮子时最容易写错的部分。这也是为什么 M2 转向官方框架：协议正确性的价值远高于框架学习成本。

注意处理器函数刻意保持"薄"：真正的文件读取和校验逻辑在 `load_knowledge_doc` / `load_config_item` 这两个**不依赖 MCP 的普通函数**里。这个分层让业务逻辑可以被同步单元测试直接覆盖（`TestLoaders` 组），不必事事都走一遍协议会话。

### 5.3 测试的三层结构

[tests/test_mcp_resources.py](../源码/smart-research-agent/tests/test_mcp_resources.py) 按"离协议远近"分三组：

**第一层：协议模型测试（TestProtocolModels）**——验证 pydantic 模型的契约，如同 `jsonrpc` 默认值、错误体结构：

```python
def test_request_defaults_jsonrpc_2_0(self):
    req = JsonRpcRequest(id=1, method="resources/read", params={"uri": "research://a/b"})
    assert req.jsonrpc == "2.0"
```

**第二层：加载器单元测试（TestLoaders）**——不走协议，直接测业务逻辑与防御代码：

```python
def test_path_traversal_rejected(self):
    with pytest.raises(KnowledgeNotFoundError, match="非法"):
        load_knowledge_doc("../config")

def test_sensitive_config_blocked(self):
    with pytest.raises(KnowledgeNotFoundError, match="不可暴露"):
        load_config_item("openai_api_key")
```

**第三层：内存会话端到端测试（TestMcpResourcesInMemory）**——走完整 MCP 协议栈：

```python
async def test_read_knowledge_doc(self):
    async with create_connected_server_and_client_session(app) as session:
        result = await session.read_resource("research://knowledge/rag")
    content = result.contents[0]
    assert content.mimeType == "text/markdown"
    assert "检索增强生成" in content.text
```

三层各管一段：第一层管"消息格式对不对"，第二层管"业务逻辑对不对"，第三层管"协议集成对不对"。出问题时报错位置直接指向故障层——**测试的分层结构就是调试的路标**。

特别注意第三层的错误路径测试：

```python
async def test_read_missing_doc_raises_mcp_error(self):
    async with create_connected_server_and_client_session(app) as session:
        with pytest.raises(McpError, match="不存在"):
            await session.read_resource("research://knowledge/nope")
```

处理器抛出的 `KnowledgeNotFoundError` 被 FastMCP 捕获、映射成 JSON-RPC 错误响应，客户端会话再把它还原为 `McpError` 抛出。这个测试验证了完整的错误翻译链：**业务异常 → 协议错误 → 客户端异常**，三个世界无缝衔接。

## 第六章：今日总结 —— Resources 原语的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 用 MCP 而非私有集成 | N×M → N+M，协议解耦 | 整个 `mcp_server/` 包 |
| 包名 `mcp_server` 不叫 `mcp` | 避免遮蔽官方 `mcp` 包 | `mcp_server/__init__.py` |
| pydantic 建模 JSON-RPC | 协议词汇显式化、可校验 | `protocol.py` |
| URI 模板 `{doc_id}` | 一个处理器服务一个资源族 | `resources_server.py` 装饰器 |
| 配置键白名单 | 敏感字段绝不整体暴露；拒绝时不区分"不存在"与"被屏蔽" | `load_config_item` |
| doc_id 路径穿越检查 | URI 参数是不可信输入，纵深防御 | `load_knowledge_doc` |
| 订阅通知只带 URI 不带内容 | 通知轻量，重读决定权留给客户端 | 协议机制（第三章） |
| 测试用内存传输 | 与 stdio 同消息流，但 Fast/Repeatable | `test_mcp_resources.py` |
| `asyncio_mode = "auto"` | 配置一次，测试免装饰器 | `pyproject.toml` |

今天埋下的伏笔：

- **Tools 与 Prompts**（day018）：项目现有的 calculator 等工具将重构为 MCP Tool，提示词将参数化为 MCP Prompt。
- **订阅通知的实现**：文件监控 + `resources/updated` 通知，待服务器走向生产时补齐。
- **Client 侧集成**（day020）：SmartResearch Agent 将反过来作为 MCP Client，消费别的 Server 的资源与工具。
