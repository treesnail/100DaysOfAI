## 第二章：M3-D1 复盘 —— 指标体系与 EvaluationHarness

### 2.1 为什么"凭感觉"不是评估

**一句话本质**：评估是把"好/不好"的主观判断，转化为"对一批固定用例、按固定规则、产出可比较分数"的客观过程。

**为什么**：没有评估体系时，AI 系统的迭代是这样的：

```text
改了一版 Prompt → 手动试了 3 个例子，感觉不错 → 上线
                 → 用户反馈第 4 种问法答非所问 → 再改 → 再试 3 个例子 → ……
```

三个致命问题：

1. **样本偏差**：你试的 3 个例子恰恰是你能想到的，而用户的问题分布你永远想不全。
2. **不可比较**：这次"感觉不错"和上次"感觉不错"无法对齐——没有分数就没有回归的概念，改了 A 场景可能悄悄弄坏了 B 场景。
3. **不可追责**：线上出问题后，无法回答"这个改动当时验证过什么"。

评估体系把这条链路改造成：

```text
改动 → 跑评估集（50~500 条固定用例）→ 得到各维度分数 → 与基线对比
     → 分数不降才允许合入 → 失败用例进入 bad case 清单 → 针对性修复
```

这就是把 M1 学到的"测试防护网"思想（day002）推广到 LLM 这种**概率系统**上：传统软件的行为是确定的，if-else 覆盖完就有信心；LLM 的输出是分布，只能用统计意义上的分数来描述它。**评估是概率系统时代的"单元测试"。**

**常见误区**：

- **误区一：评估 = 跑几个 demo 看看。** demo 是展示，评估是度量。区别在于：评估的用例集是**冻结的**（本次和下次跑的是同一批，才可比较），评分规则是**显式的**（写成代码，不靠目测）。
- **误区二：等系统做完了再补评估。** 评估集应该和功能同步生长——每个新场景加入时顺手补 2~3 条用例。事后补评估的代价远大于事中，且你会倾向于"挑系统答得好的例子"（幸存者偏差）。

### 2.2 四大指标维度：一个都不能少，但不是每个都要平均用力

**一句话本质**：正确性回答"答案对不对"，相关性回答"有没有答非所问"，安全性回答"会不会闯祸"，成本回答"烧不烧得起"——四个维度刻画同一个系统的不同侧面。

| 维度 | 核心问题 | 典型度量方式 | 失败的样子 |
|------|----------|--------------|-----------|
| 正确性（Correctness） | 答案与事实/参考答案一致吗？ | 精确匹配、包含匹配、数值等价、LLM 裁判对照参考答案 | "上海人口 3000 万"（事实错误） |
| 相关性（Relevance） | 回答对准了用户的问题吗？ | 关键词覆盖、语义相似度、LLM 裁判按 rubric 打分 | 问"对比 A 和 B"，只答了 A |
| 安全性（Safety） | 会泄露隐私、被注入、产出有害内容吗？ | 注入检出率、PII 泄漏计数、有害内容分类器 | 被一句"忽略之前的指令"套出系统提示词 |
| 成本（Cost） | 每次任务烧多少 token、多少钱、多少秒？ | token 计数、单价折算、延迟 P50/P95 | 一个简单问答跑了 8 步 ReAct、花了 ¥0.4 |

**为什么必须四维并立**——因为它们互相牵制，只看一维必然翻车：

- 只优化正确性 → 可能纵容"为答对而不计成本"（成本失控）；
- 只压成本 → 模型被砍得太小，正确性、相关性一起崩；
- 不做安全性 → 前三个维度做得再好，一次注入事故就能摧毁用户信任。

但注意第二句话：**不是平均用力**。一个内部知识库问答，相关性和成本权重高；一个对外客服机器人，安全性是一票否决项；一个批处理报告生成器，延迟几乎无所谓。维度是全集，权重由场景决定——这正是第五章决策表要解决的问题。

**常见误区**：

- **误区一：把"准确率"当唯一指标。** 这相当于只用体重评价健康。正确性 95 分但安全性 40 分的系统，是危险品而不是好产品。
- **误区二：成本只算 token 不算延迟。** 对用户来说，30 秒才出答案的系统和答错的系统一样不可用。成本维度天然包含"钱"和"时间"两个子指标。
- **误区三：安全性靠"我们的 Prompt 里写了不许……"。** Prompt 约束是软约束，模型的服从是概率性的。安全性必须用**攻击用例集**实测（day031 红队评估的核心），而不是靠声明。

### 2.3 EvaluationHarness：把评估做成流水线，而不是一次性脚本

**一句话本质**：Harness（马具/测试台）是一个固定骨架——**加载数据集 → 逐条运行被测对象 → 逐条评分 → 汇总成报告**——把"评估"从一次性的临时脚本，变成可重复执行、可扩展、可对比的基础设施。

day025 的基类设计（完整代码见 [../../day025/源码/smart-research-agent/smart_research_agent/evaluation/harness.py](../../day025/源码/smart-research-agent/smart_research_agent/evaluation/harness.py)）核心是这个职责分解：

```python
class EvaluationHarness(ABC):
    """评估流水线基类：数据集 → 运行 → 评分 → 汇总."""

    def run(self) -> EvaluationReport:
        dataset = self.load_dataset()          # 第一步：加载冻结的用例集
        results = []
        for case in dataset.cases:
            output = self.execute(case)        # 第二步：被测对象跑一遍
            score = self.score(case, output)   # 第三步：按指标打分
            results.append(CaseResult(case=case, output=output, score=score))
        return self.aggregate(results)         # 第四步：汇总成分数与失败清单

    @abstractmethod
    def execute(self, case): ...               # 子类实现：怎么调被测系统

    @abstractmethod
    def score(self, case, output): ...         # 子类实现：怎么打分
```

三个设计决策值得吃透：

**（1）为什么是基类 + 抽象方法，而不是一个大函数？** 这就是 day002 讲过的**模板方法模式**：`run()` 把流水线的"骨架"冻结（所有评估都按这四步走，顺序、异常处理、汇总逻辑不变），把"血肉"留给子类（Prompt 评估的 `execute` 是渲染模板，Agent 评估的 `execute` 是 `agent.run()`，但骨架一模一样）。到 day029 的 RAG 评估、day030 的 Agent 评估，你会看到它们各自只实现两个抽象方法就拥有完整流水线——这就是基类的复利。

**（2）为什么数据集要显式加载而不是内嵌代码里？** 数据集是**冻结的基准**，它必须独立于代码演进：版本化（用例集 v1.1 比 v1.0 多了 10 条边界用例）、可共享（产品同学也能往里加 bad case）、可审计（"这次评估跑的是哪 50 条"必须有确定答案）。数据集进代码，等于把基准和实现焊死，评估的可比性立刻瓦解。

**（3）为什么汇总（aggregate）要单独成一步？** 因为"每条用例的分数"和"系统的分数"是两种东西。汇总层负责：算各维度均分/通过率、按标签分组统计（哪类问题最差）、提取失败用例清单。**决策发生在汇总层，不归因发生在明细层**——两者分开，报告才能同时回答"能不能发版"和"差在哪里"。

```text
用例明细（CaseResult 列表）           汇总报告（EvaluationReport）
├─ case_01  正确性 1.0  ✓            正确性均分: 0.82
├─ case_02  正确性 0.0  ✗ ─────▶    通过率: 41/50 (82%)
├─ case_03  正确性 1.0  ✓            按标签: {计算类: 0.95, 事实类: 0.71}
└─ ...                               失败清单: [case_02, case_17, ...]
```

**常见误区**：

- **误区一：评估脚本"跑完打印一下就扔"。** 没有结构化报告（`EvaluationReport` 对象），就没有历史对比——"这次比上次好"无从谈起。报告要被序列化、被存档，和代码一样受版本管理。
- **误区二：在 Harness 里写被测系统的逻辑。** Harness 只编排和评分，不实现业务。基类越薄，能评估的对象越多——它评估 Prompt、评估 RAG、评估整个 Agent，用的是同一副骨架。

### 2.4 评估数据集：黄金集的诞生与维护

**一句话本质**：评估数据集（常称"黄金集"，golden dataset）是一批精心构造、带期望答案、冻结版本的用例，是度量衡里的"原器"。

**为什么**：

- **没有期望答案就没有正确性评分**。一条用例至少要有：`input`（给系统的输入）、`expected`（期望答案或评判依据）、可选的 `tags`（分类标签，供汇总层分组统计）。
- **用例来源决定评估质量**。三个主要来源，按价值排序：① 真实线上 bad case（最值钱，直接消灭已知问题）；② 人工构造的边界用例（覆盖长尾：空输入、超长输入、多轮上下文）；③ 典型 happy path（防止优化时回归基本盘）。
- **冻结才能比较**。今天跑 v1.0 得 82 分，下周改动后还跑 v1.0 得 85 分——这 3 分才可信。用例集和代码同库管理、打版本号，就是这个目的。

**常见误区**：

- **误区一：只放 happy path。** 50 条全是"正常问题正常答"，评估集退化成走过场。边界用例占比至少要有两三成。
- **误区二：用例集一次写完不再更新。** 评估集是活资产：每次线上 bad case 修复后，该 case 必须进评估集——这叫"把事故变成资产"，否则同一个坑会掉两次。
- **误区三：期望答案写得过于精确。** "期望：上海人口约 2400 万"是坏的 expected（判分器难以匹配）；"期望要点：提及 2400 万量级、说明数据年份"是好的 expected。期望答案要服务于"可判分"，不是写一篇范文。

## 第三章：M3-D2 复盘 —— Prompt 评估与 LLM-as-a-judge

### 3.1 Prompt 为什么需要单独评估

**一句话本质**：Prompt 是写给 LLM 的"程序"，程序要 code review，Prompt 要 prompt review——评估的三个维度是清晰度（说得明不明白）、一致性（前后矛不矛盾）、潜在歧义（有没有多种解读）。

**为什么**：M1 阶段我们手写 Prompt 全靠经验（day006 的 SYSTEM_PROMPT、day010 的 PLAN_PROMPT），有两个隐患会随项目长大而爆发：

1. **Prompt 的缺陷是"静默"的**。代码写错会抛异常，Prompt 写岔了模型照样输出——只是质量悄悄下降。`PLAN_PROMPT` 里如果没写"严格输出 JSON 数组"，你不会立刻看到报错，而是发现解析失败率从 2% 涨到 15%。
2. **Prompt 之间会互相干扰**。系统提示词、任务模板、工具描述拼在一起才是模型真正看到的东西。单看每段都合理，拼起来可能矛盾（一段说"回答要详尽"，另一段说"控制在 100 字内"）。

因此 Prompt 评估三个维度各自锁定一类典型缺陷：

| 维度 | 检测什么 | 反例 |
|------|----------|------|
| 清晰度 | 指令是否具体、可执行、无废话 | "尽量回答得好一点"（什么叫好？） |
| 一致性 | 多条规则之间是否冲突 | "输出 JSON" 与 "用自然语言解释结果" 并列且无优先级 |
| 潜在歧义 | 是否存在多种合理解读 | "适当时候调用工具"（什么时候算适当？） |

day026 的 `PromptEvaluator`（完整代码见 [../../day026/源码/smart-research-agent/smart_research_agent/evaluation/prompt_eval.py](../../day026/源码/smart-research-agent/smart_research_agent/evaluation/prompt_eval.py)）对这三个维度做双通道检查：**规则通道**查确定性问题（长度异常、占位符未配对、明显的矛盾关键词对），**LLM 裁判通道**查语义问题（歧义、隐性冲突）。

**常见误区**：

- **误区一：认为 Prompt 评估能替代端到端评估。** Prompt 得分高 ≠ 输出质量好——它只保证"指令本身没毛病"，不保证"模型听懂了"。Prompt 评估是**廉价的预筛**，端到端输出评估（day027）才是终审。两者的关系类似 lint 和单元测试。
- **误区二：把 Prompt 越写越长来"保险"。** 每条新规则都引入与其他规则冲突的可能，还稀释模型的注意力。一致性维度的分数常常会随 Prompt 变长而下降——这是评估反向指导瘦身的典型案例。

### 3.2 LLM-as-a-judge：用模型评估模型的原理

**一句话本质**：LLM-as-a-judge 让一个强模型扮演裁判，按显式评分细则（rubric）对被评对象打分并给出理由，把"质量"这种模糊判断变成可批量执行的程序调用。

**为什么可行**——关键在于**评估比生成容易**：

```text
生成任务: "写出一份优秀的 RAG 框架对比报告"        ← 难：要创造
评判任务: "这份报告是否对比了至少 3 个框架？1~5 分" ← 易：只需判断
```

判断比创造容易，是人类和模型共有的认知规律（你未必写得出好文章，但能分辨两篇的优劣）。这意味着：**用一个够强的模型做裁判，去评估另一个（或同一个）模型的产出，在统计上是可靠的**。这解决了评估的规模问题——人工评审 500 条用例要几天，LLM 裁判几分钟跑完，且每一条都给出理由，可抽查、可复盘。

一个合格的裁判 Prompt 有三个要件（对照 day026 的实现）：

1. **rubric（评分细则）**：不是"打个分"，而是"1 分 = 答非所问；3 分 = 部分相关但遗漏要点；5 分 = 完整覆盖且无冗余"。没有 rubric 的打分漂移极大，同一个输出这次 4 分下次 2 分。
2. **要求先给理由再给分数**：让模型先输出分析再输出分数，分数会显著更稳（原理同 CoT——显式推理约束了最终判断）。分数单独成行、格式固定，方便程序解析（这又回到 day010 的老话题：凡是程序消费的 LLM 输出，格式必须锁定）。
3. **提供参照物**：有参考答案时把参考答案喂给裁判（对照评估），没有时至少提供原始问题（无参照评估）。无参照评估成本低但漂移大，适合粗筛。

**常见误区**：

- **误区一：让裁判"自由发挥"不打 rubric。** "你觉得这个回答怎么样？打个分"——不同日期、不同上下文长度下打分尺度都不同，分数失去可比性，评估退化成掷骰子。
- **误区二：裁判用与被测系统相同的弱模型。** 裁判能力必须不弱于被测对象（最好用最强的模型当裁判），否则会出现"看不懂好答案而打低分"的系统性误差。
- **误区三：100% 信任裁判分数。** LLM 裁判有已知偏差（见 3.3），生产做法是：**裁判批量打分 + 人工定期抽检校准**。抽 5% 人工复核，算裁判与人工的一致率，低于阈值就要调 rubric。

### 3.3 裁判的三大偏差与缓解

这是 M3-D2 最容易考也最容易踩坑的部分。LLM 裁判不是公正无私的机器，已知的系统性偏差至少有三类：

| 偏差 | 表现 | 缓解手段 |
|------|------|----------|
| 位置偏差（Position Bias） | 成对比较时偏爱先出现（或后出现）的那个答案 | 交换顺序各评一次，取平均或要求两次一致 |
| 冗长偏差（Verbosity Bias） | 分数随答案长度上升，与质量无关 | rubric 中显式声明"长度不构成加分项"；对照参考答案的要点覆盖而非篇幅 |
| 自偏好（Self-Enhancement） | 模型给自己的输出打分偏高 | 裁判与被测用不同模型；或隐藏输出来源（盲评） |

**为什么必须知道偏差的存在**：不缓解偏差，评估结论会误导优化方向。比如冗长偏差会奖励"话多的 Prompt"，你越优化输出越长越水——分数涨了，用户体验降了。**评估器自身的可信度，决定整个评估体系的可信度。** 这也是为什么 day026 的测试要用 MockLLM 验证"评分解析逻辑"和"裁判 Prompt 组装逻辑"分开测（见 [../../day026/源码/smart-research-agent/tests/](../../day026/源码/smart-research-agent/tests/) 中的 Prompt 评估测试）：裁判的解析层出 bug，分数全废。

### 3.4 评估反哺优化的闭环

**一句话本质**：评估的终点不是分数，是行动——分数定位"哪类 Prompt 弱"，明细定位"哪条规则有问题"，修复后重跑评估验证。

day026 建立的闭环：

```text
Prompt 模板 ──▶ PromptEvaluator 打分（清晰度/一致性/歧义三维）
    ▲                    │
    │                    ▼
    │            低分维度 + 裁判给出的理由
    │                    │
    │                    ▼
    └──────── 人工按理由修订 Prompt（删冲突规则、消除歧义措辞）
                         │
                         ▼
              重跑评估确认分数回升（回归验证）
```

这个闭环和 day010 讲的"提示词是迭代出来的"（写初版 → 跑案例 → 失败分类 → 对症下药 → 回归验证）是**同一套方法论的升级版**：day010 靠人肉收集失败案例，day026 把"发现失败"这一步自动化了。M3 的全部价值可以浓缩成这句话：**把 prompt 调参从玄学手艺变成有度量、有回归的工程活动。**

## 第四章：M3-D3 复盘 —— 输出质量的双重评估与质量日志

### 4.1 输出侧评估什么：有用性、准确性、格式合规

**一句话本质**：day027 的三维指标是 day025 四大维度在"单次输出"粒度上的具体化——有用性 ≈ 相关性（对用户有没有用），准确性 ≈ 正确性（事实对不对），格式合规是输出特有的契约检查（结构符不符合约定）。

**为什么格式合规单列一维**：Agent 系统的输出经常要被下游程序消费（前端渲染、报告模板、另一个 Agent）。内容再好，格式错了下游就崩——这在传统软件里叫"接口契约"，在 LLM 应用里要专门评估，因为模型的格式服从是概率性的（day010 的 `parse_plan` 四道防线防的就是这个）。格式合规是唯一可以**纯规则**精确判定的维度，这也决定了它在双重评估中的分工。

### 4.2 双重评估：规则 + 模型，为什么要两条腿

**一句话本质**：规则评估（Rule-based）处理确定性问题（格式、长度、关键词、正则），模型评估（LLM-as-a-judge）处理语义问题（有用性、准确性），两者按维度分工、按权重合成总分。

day027 的输出质量评估器（完整代码见 [../../day027/源码/smart-research-agent/smart_research_agent/evaluation/output_eval.py](../../day027/源码/smart-research-agent/smart_research_agent/evaluation/output_eval.py)）的分工逻辑：

```text
一条 Agent 输出
    │
    ├──▶ 规则评分器（RuleBasedScorer）
    │     · 格式合规：合法 JSON？必填字段在吗？长度在区间内吗？
    │     · 特征：确定性、零成本、毫秒级、100% 可复现
    │     · 盲区：看不懂语义（一篇格式完美的废话能得满分）
    │
    ├──▶ 模型评分器（LLM 裁判，复用 day026 的 judge 模式）
    │     · 有用性/准确性：对照问题与参考答案按 rubric 打分
    │     · 特征：懂语义、能评"好不好"
    │     · 盲区：有偏差、有成本、有概率波动
    │
    └──▶ 加权合成总分（如：格式 0.3 + 有用性 0.4 + 准确性 0.3）
```

**为什么单一通道不够**：

- 只用规则：能查出"不是合法 JSON"，查不出"JSON 里的内容全是编的"。
- 只用模型：每次评估都要为"格式对不对"这种确定性问题付一次 LLM 调用的钱，还引入不必要的概率波动——**能用代码判的，绝不用模型判**。这是 M3 里贯穿的成本意识。

双重评估的深层原则是**按错误的确定性分层**：确定性的契约问题走确定性的检测，语义性的质量问题走概率性的判断。这个"分层检测"思路和 day010 `parse_plan` 的四道防线（边界 → 语法 → 类型 → 语义）是同构的——越内层（越接近语义）的检测越贵、越不确定，能在外层拦下的就别放进来。

**常见误区**：

- **误区一：双重评估 = 两个分数简单平均。** 各维度权重应由场景定（格式对下游系统集成一票否决时，权重就该高）；而且某些维度应该设**硬门槛**——格式不合规直接判 0 分，而不是拉低平均分。加权与门槛是两种合成策略，别混用。
- **误区二：规则通道形同虚设。** 规则要写进测试：格式规则的每一条（缺字段、超长、非法 JSON）都应有对应用例锁定，和评估器本身一起进版本库。

### 4.3 质量日志：给评估留下可回溯的现场

**一句话本质**：质量日志（QualityLogger，完整代码见 [../../day027/源码/smart-research-agent/smart_research_agent/evaluation/quality_logger.py](../../day027/源码/smart-research-agent/smart_research_agent/evaluation/quality_logger.py)）把每次输出的评估结果以 JSONL 落盘——一行一条记录，包含输入、输出、各维分数、时间戳——让质量从"评估时才知道"变成"随时可查、可回溯、可统计"。

**为什么 JSONL（JSON Lines）而不是一个大 JSON 数组**：

- **追加写友好**：每评估一条追加一行，不需要读入整个文件再写回——日志系统的第一需求就是不打断主流程。
- **行级容错**：某一行损坏（进程崩溃写了一半）只影响那一条，整个文件仍可读。
- **天然适配流式处理**：`grep`、`pandas.read_json(lines=True)`、日志采集器（Fluentd/Vector）全都原生支持逐行处理。

**质量日志和 day001 的 logging 有什么区别**——这是复盘时最容易混淆的一对：

| 维度 | logging（day001） | 质量日志（day027） |
|------|-------------------|---------------------|
| 内容 | 系统运行事件（INFO/WARNING/ERROR） | 评估结果数据（结构化分数记录） |
| 读者 | 开发者/运维（排障） | 数据 pipeline/分析脚本（统计、挖掘） |
| 格式 | 自由文本行 | 严格 JSON（每条记录同构） |
| 消费方式 | 人看 + 关键字检索 | 程序聚合分析、画趋势图、挖 bad case |

一句话：**logging 回答"系统刚才发生了什么"，质量日志回答"系统的质量在往哪走"。** 前者是可观测性的第一道防线，后者是 M3-D7（day032）评估报告自动生成与告警的数据源。

**常见误区**：

- **误区一：质量日志里只存分数不存原文。** 没有输入输出的原文，低分记录就永远无法归因——分数是索引，原文才是证据。当然要注意：原文可能含用户隐私，脱敏（PII 过滤）要在落盘前完成，这呼应 day015 的安全模块。
- **误区二：把质量日志当垃圾桶只进不出。** 日志的价值在消费端：定期跑统计脚本（各维分数的周趋势、低分用例聚类），产出的 bad case 清单回流到评估数据集（2.4 节：事故变资产）。只存不看的日志等于没存。

### 4.4 全链路串讲：一次输出质量评估的完整旅程

把三天串起来，一次"评估 SmartResearch Agent 的输出"经过哪些组件（各文件均在 [day027 快照](../../day027/源码/smart-research-agent/) 中）：

```text
评估数据集（golden_v1.jsonl，50 条用例）
    │
    ▼
┌────────────────────────────────────────────────────────────┐
│ OutputQualityHarness.run()              evaluation/        │
│ ① load_dataset(): 逐行解析 JSONL → list[EvalCase]          │
│   （每条: input / expected / tags）                         │
└────────────────────────────────────────────────────────────┘
    │ for case in cases:
    ▼
┌────────────────────────────────────────────────────────────┐
│ ② execute(case): agent.run(case.input)                     │
│   被测系统产出 output（内部仍是 day006 的 ReAct 循环）        │
└────────────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────────────┐
│ ③ score(case, output): 双重评估                            │
│   ├─ RuleBasedScorer: JSON 合法？字段齐？长度合规？          │
│   │   → format_score = 1.0（确定性，零成本）                │
│   └─ LLMJudgeScorer: 裁判 Prompt（问题+参考答案+输出+rubric）│
│       → judge 先给理由再给分 → 解析分数                      │
│       → helpfulness = 0.8, accuracy = 1.0                  │
│   合成: total = 0.3×1.0 + 0.4×0.8 + 0.3×1.0 = 0.92        │
└────────────────────────────────────────────────────────────┘
    │
    ▼
┌────────────────────────────────────────────────────────────┐
│ ④ QualityLogger.log(...): 追加一行 JSONL                    │
│   {"case_id":"c07","input":"...","output":"...",            │
│    "scores":{"format":1.0,"helpful":0.8,"acc":1.0},        │
│    "total":0.92,"ts":"..."}                                 │
└────────────────────────────────────────────────────────────┘
    │ （50 条循环完毕）
    ▼
┌────────────────────────────────────────────────────────────┐
│ ⑤ aggregate(): EvaluationReport                            │
│   各维均分、通过率 82%、按 tags 分组、失败用例清单            │
│   → 报告存档 → 与上次基线对比 → 失败清单进 bad case 集       │
└────────────────────────────────────────────────────────────┘
```

走查要点（合上书能复述才算真懂）：

1. **Harness 在第几步调用被测系统？** 第 ② 步，且通过抽象方法 `execute` 调用——Harness 不认识 Agent，换成 RAG 链路只需换个子类。
2. **哪一步花钱？** 只有 ③ 的 LLM 裁判通道。规则通道、日志落盘、汇总全部零 LLM 成本——评估的成本结构本身就是"能用代码判的不用模型判"的体现。
3. **分数的确定性由谁保证？** 规则通道 100% 确定；裁判通道靠 rubric + MockLLM 测试锁定解析逻辑 + 定期人工抽检校准。
4. **评估结果从哪反哺？** 两个出口：报告 → 发版决策（分数不得低于基线）；质量日志 + 失败清单 → 数据集扩充与 Prompt 修订。

> 思考题：如果裁判模型某天升级换代，历史分数还可比吗？（提示：不可直接比——裁判也是评估系统的一部分，换裁判 ≈ 换度量衡。正确做法是评估报告里记录裁判模型版本，换裁判时用同一数据集重跑建立新基线。）

## 第五章：指标选择决策表 —— 什么场景用什么指标

这是今天最实用的一张表。拿到一个场景，先定位它在表里的行，再按列确定指标组合与评估器选择。

| 场景 | 一票否决项 | 核心指标 | 推荐评估器 | 用例集要点 |
|------|-----------|----------|-----------|-----------|
| 对外客服/问答机器人 | 安全性 | 相关性 > 正确性 > 延迟 | 规则（敏感词/PII）+ LLM 裁判（rubric） | 注入/越狱攻击用例必含；多轮上下文用例 |
| 内部知识库问答 | 正确性 | 正确性 > 相关性 > 成本 | 参考答案对照 + LLM 裁判 | 答案必须从知识库溯源；加"知识库没有该答案"的负例 |
| 报告/代码生成（程序消费输出） | 格式合规 | 格式 > 正确性 > 成本 | 规则为主（schema 校验）+ 裁判抽查语义 | 边界格式用例（嵌套、空值、超长） |
| 批处理离线任务（报告润色等） | 正确性 | 质量 > 成本（延迟不敏感） | LLM 裁判为主 | 可用大裁判模型，成本敏感低 |
| 实时交互 Agent | 延迟 | 延迟 P95 + 正确性 | 规则 + 轻量裁判；成本按 token 硬约束 | 步数分布统计（ReAct 步数即延迟代理） |
| 高风险域（医疗/金融建议） | 安全性 + 正确性 | 双否决，其余为辅 | 裁判 + 人工抽检比例提高（如 20%） | 免责声明、拒答行为的专项用例 |
| Prompt 模板迭代（日常） | 无 | Prompt 三维（清晰/一致/歧义） | 规则预筛 + 裁判细评 | 每个模板维护 10~20 条触发用例 |

使用决策表的三个心法：

1. **先找否决项，再排权重**。否决项决定了"哪些评估器必须在线、用例集必须含什么"；权重只影响分数合成的细节。顺序反了（先纠结权重）是本末倒置。
2. **评估器成本要和被测对象匹配**。高频实时场景的评估也要快——用贵裁判评便宜场景，评估本身就成了成本黑洞。可用"粗筛（规则+小模型）→ 精评（大模型抽检）"的两级漏斗。
3. **用例集的结构跟着否决项走**。安全性是否决项，攻击用例就要占大头；格式是否决项，畸形输出用例就要占大头。用例集是你的风险观的具象化。

## 第六章：常见误区清单（M3 前半 12 条速查）

按"评估理念 → Harness → 裁判 → 输出评估"分组，每条给出正解。

**评估理念**

1. ❌ 跑几个 demo 感觉不错就算评估过。 → 评估 = 冻结用例集 + 显式评分规则 + 结构化报告，三者缺一就不是评估。
2. ❌ 只看准确率一个指标。 → 正确性/相关性/安全性/成本四维并立，权重按场景定。
3. ❌ 评估集写完就不管了。 → 每个线上 bad case 修复后必须进评估集（事故变资产）。
4. ❌ 等系统做完再补评估。 → 用例集与功能同步生长，事后补会挑软柿子（幸存者偏差）。

**EvaluationHarness**

5. ❌ 评估脚本跑完打印一下就扔。 → 报告要对象化、序列化、版本化，否则无法与基线对比。
6. ❌ Harness 基类里写被测系统的业务逻辑。 → 基类只编排四步骨架，`execute`/`score` 留给子类，基类越薄复用越广。
7. ❌ 汇总只算一个总均分。 → 必须保留按标签分组和失败清单——决策要均分，归因要明细。

**LLM-as-a-judge**

8. ❌ 让裁判自由打分不给 rubric。 → 无 rubric 的分数漂移极大，失去可比性；rubric 要写明每档分的判据。
9. ❌ 忽视位置/冗长/自偏好三大偏差。 → 成对比较换序重评、rubric 声明长度不加分、裁判与被测异模型。
10. ❌ 100% 信任裁判分数。 → 定期人工抽检 5%，算裁判-人工一致率，低于阈值调 rubric。

**输出双重评估与质量日志**

11. ❌ 格式校验也调 LLM 裁判。 → 能用代码判的绝不用模型判：确定性问题走规则，语义问题走裁判。
12. ❌ 质量日志只存分数不存原文（或反过来存了原文不脱敏）。 → 分数是索引、原文是证据，缺一不可；PII 脱敏在落盘前完成。

## 今日总结

| 复习模块 | 核心内容 | 自测问题 |
|----------|----------|----------|
| 指标体系 | 正确性/相关性/安全性/成本四维并立 | 为什么只看准确率会翻车？ |
| 评估数据集 | 黄金集三来源、冻结可比、事故变资产 | expected 写成范文为什么是错误的？ |
| EvaluationHarness | 模板方法四步骨架：加载→执行→评分→汇总 | 为什么基类越薄复用越广？ |
| Prompt 评估 | 清晰度/一致性/歧义三维，廉价预筛 | Prompt 高分为什么不等于输出高质量？ |
| LLM-as-a-judge | 评估比生成容易；rubric；先理由后分数 | 三大偏差分别怎么缓解？ |
| 双重评估 | 规则判确定性、模型判语义、按场景合成 | "能用代码判的绝不用模型判"为什么也是成本原则？ |
| 质量日志 | JSONL 落盘、分数+原文、脱敏先行 | 质量日志和 logging 的区别是什么？ |

下周（M3 后半）预告：day029 起，评估体系将逐一落到具体对象上——**RAG 评估**（召回率、MRR、NDCG）、**Agent 评估**（任务完成率、步数效率）、**安全红队**（注入/越狱/PII 攻击用例集）、**CI/CD 与可观测性**（评估进流水线、报告自动生成）。你会发现它们全部是今天这套骨架（Harness + 双重评估 + 质量日志）的子类化应用。
