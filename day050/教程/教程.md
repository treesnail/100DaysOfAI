## 第一章：SFT 与预训练的唯一区别

### 1.1 同一个损失函数，不同的分母

SFT（Supervised Fine-Tuning，监督微调）的损失函数与预训练**完全一样**，都是 next-token 的交叉熵：

```text
预训练：  L = -(1/T)   Σ_{t=1..T}  log p(y_t | y_<t)
SFT：     L = -(1/T')  Σ_{t∈S}     log p(y_t | y_<t)      S = 监督位置集合
```

唯一的变化是**求和的集合与分母**：预训练对全序列求平均，SFT **只对答案段求平均**。

工程上这个"只对答案段"落在哪里？落在 `labels` 数组的一个约定值上：

```python
IGNORE_INDEX = -100
```

PyTorch 的 `nn.CrossEntropyLoss` 有 `ignore_index` 参数（默认值就是 `-100`），它规定"值为 `-100` 的位置不计入损失、不产生梯度"。HuggingFace 生态沿用了这个约定，TRL 的 `SFTTrainer` 处理 `assistant_only_loss` 时最终也落到这里。

**用同一个约定值带来一个实际好处**：本课的数据准备工作可以直接喂给 `transformers.Trainer`，不需要任何额外的转换层。

### 1.2 为什么必须屏蔽 prompt

如果 prompt 也参与 loss，模型会被同时训练去"预测用户的问题"。而用户的提问在推理时是**给定的输入**，模型不需要（也不应该）学会生成它。两个直接后果：

| 后果 | 说明 |
|------|------|
| **浪费容量** | 一部分参数被用于"学会像用户那样提问"，而这部分能力推理时完全用不上 |
| **稀释信号** | 本课程数据集里 prompt 平均 151.8 token、答案平均 99.1 token；prompt 计入 loss 意味着约 **60.5%** 的监督信号被用在一个错误的目标上 |

第二点今天是**可测量的**：实测屏蔽 prompt 时训练集的监督 token 占比是 **39.31%**（2933 / 7462），不屏蔽时是 **100%**。第六章的对照实验会证明前者得到的模型在答案 token 上更好。

### 1.3 "训练脚本能不能跑"和"训练有没有用"是两件事

这是本课最重要的一条认知。一个 SFT 脚本可以完美运行、loss 曲线平滑下降、日志一切正常，而实际上什么都没学到：

- **`-100` 写错位置**（比如整条序列都没屏蔽）→ loss 照样下降，只是学的目标错了；
- **学习率比模型规模小了数量级** → loss 几乎是一条水平线，但脚本"成功结束"；
- **数据太少** → 9 次参数更新不可能产生有效变化（day049 已经算过）；
- **`max_length` 定得太小** → 答案被静默截断，模型学到"说一半就停"。

所以本课的实现贯穿一条纪律：**每一个"可能什么都没发生"的环节，都要么给出可观测的数字，要么直接报错**。后面逐章展开。

## 第二章：模板渲染 —— 把边界标出来

### 2.1 三种模板，同一件事

`template.render_supervised` 支持三种模板（`chatml` / `llama3` / `plain`），它们做的事完全一样：把 `TrainingExample` 拼成一段文本，并**标出"从哪里开始是答案"**。

| 模板 | 前缀（不参与 loss） | 监督区间（参与 loss） |
|------|--------------------|---------------------|
| `chatml`（缺省） | `<\|im_start\|>system\n…<\|im_end\|>\n<\|im_start\|>user\n…<\|im_end\|>\n<\|im_start\|>assistant\n` | `答案<\|im_end\|>\n` |
| `llama3` | `<\|begin_of_text\|><\|start_header_id\|>…<\|end_header_id\|>\n\n…` | `答案<\|eot_id\|>` |
| `plain` | `系统提示\n\n### 指令\n…\n\n### 回答\n` | `答案\n` |

ChatML 的那一行是当前开源指令模型最通用的一种写法（Qwen 系、InternLM 系都用它），训练与推理必须使用**同一个**模板——**"训练时看到的 prompt"和"推理时给的 prompt"不一致，是最隐蔽的一类缺陷**，它不会报错，只会让效果莫名变差。

`llama3` 模板里有个容易写错的细节：header 之后是**两个换行**（`<|end_header_id|>\n\n`）。少一个换行就等价于换了模板。

### 2.2 字符偏移：为什么用两个整数而不是两个字符串

`RenderedSample` 的产出是：

```python
@dataclass(frozen=True)
class RenderedSample:
    text: str
    prompt_chars: int        # 前缀字符数，等于监督区间的起始下标
    supervised_chars: int    # 监督区间字符数
    template: str
```

不变式（构造时校验）：

```text
text[prompt_chars : prompt_chars + supervised_chars] == 监督区间
prompt_chars + supervised_chars == len(text)
```

为什么必须是**字符偏移**而不是"前缀字符串 + 答案字符串"两个字段？因为下游要拿它做一件精确的事：**分别 tokenize**。

```python
prompt_ids = tokenizer.encode(rendered.prompt_text)      # 前缀单独编码
answer_ids = tokenizer.encode(rendered.supervised_text)  # 监督区间单独编码
input_ids = prompt_ids + answer_ids                      # 再拼接
```

如果反过来——先 `encode(rendered.text)` 再按字符偏移切片——在 BPE 类分词器上会出错：**跨边界的字符合并会产出一个"同时属于 prompt 与 answer"的 token**，切片时切给谁都错。切给 prompt 就丢了答案的第一个词；切给 answer 就让模型学着预测一个它本不该预测的 token。字符偏移是唯一能表达"从哪里切开"且不依赖具体分词器的表示。

本课自带一个**字符级 `CharTokenizer`**（离线、确定、可逆），它让每一个 token 都能手数出来，因此"第几个 token 的 label 是 -100"这类断言才成立。它的代价也必须说清楚：中文约 1 字 1 token，而 BPE 会低得多，所以它只用于**验证机制**，不用于真实训练的长度预算——真实预算由 day034 的 `TokenCounter` 与 day048 的 `DatasetStats` 给出。

### 2.3 轮次终止符要不要监督？要

```python
supervised = answer + terminator if include_turn_terminator else answer
```

缺省 `include_turn_terminator=True`，即监督区间是 **`答案 + 轮次终止符`**。理由是模型必须学会"在哪里停下"，而 EOS/终止符正是这个信号。如果只监督答案本身，模型学到的是"永远继续写下去"——它会生成语义正确但**不会结束**的输出，而这在评测里往往表现为"回答太长"而不是"回答错误"，更难定位。

对应地，TRL 的文档里也有一条同类提醒：对于 Qwen 这类自带 chat 模板的模型，"有必要把 `eos_token` 与 chat 模板对齐，以保证模型的回复正确终止"。本课把这条要求直接做进了监督区间。

### 2.4 system 提示词的三态语义

```python
render_supervised(example, system_prompt=DEFAULT_SYSTEM_PROMPT)
```

三种传法对应三种语义（与 day041 `default_embedding()` 同一种"显式 `None` vs 缺省值"纪律）：

| 传法 | 语义 |
|------|------|
| 不传 | 用 `DEFAULT_SYSTEM_PROMPT`（"你是智研 AI 助手…"） |
| 传 `None` | **不要 system 轮**（用于把"无 system"也作为一种训练条件） |
| 传字符串 | 用该字符串 |

而**样本自带的 `example.system` 优先级最高**——样本级设定不该被全局缺省值盖掉，否则"这条样本要带角色设定"的意图就丢了。

## 第三章：label mask —— 本课的核心机制

### 3.1 一个函数，四行关键代码

`encoding.encode_supervised` 是全课最核心的函数。它的关键部分只有四行：

```python
ids = kept_prompt + answer_ids
prompt_labels = [ignore_index] * len(kept_prompt) if mask_prompt else list(kept_prompt)
labels = prompt_labels + list(answer_ids)
```

产出：

```python
@dataclass(frozen=True)
class EncodedSample:
    input_ids: tuple[int, ...]
    labels: tuple[int, ...]
    attention_mask: tuple[int, ...]
    prompt_tokens: int       # 序列里属于前缀的 token 数（与是否屏蔽无关）
    supervised_tokens: int   # labels 里非 -100 的个数（= 真正参与 loss）
    masked_prompt: bool
    truncated: bool
```

实测（ChatML 模板、本课程数据集第一条样本）：

```text
渲染：总字符 266 = prompt 146 + 监督 120
编码：tokens=266  prompt=146  监督=120  占比=45.11%
  labels[:146] 全为 -100 -> True
  labels[146:] 全非 -100 -> True
```

`EncodedSample` 的构造期校验（`__post_init__`）拦下四种送错数据的方式：

| 校验 | 拦下什么 |
|------|---------|
| 三个序列必须等长 | `input_ids` / `labels` / `attention_mask` 长度不一致——**这是 SFT 里最典型的送错数据的方式**，而它在 loss 计算时往往不会立刻报错（很多实现按 `input_ids` 长度循环，多出来的 label 被静默忽略） |
| 监督 token 数必须 > 0 | 零监督样本：**消费算力但不产生梯度**的死数据 |
| prompt token 数必须 ≥ 1 | 第一个监督 token 没有上下文，构不成 next-token 预测任务 |
| 屏蔽时监督数必须等于监督区间长度 | **记账错误**——`supervised_tokens` 与实际屏蔽范围不符，会让分母算错 |

第三、四条尤其值得注意：它们不是"防御式编程"，而是**把两类真实故障提前到构造处**。零监督样本会让 loss 曲线看起来正常（其余批次在降），却让样本的实际利用率悄悄下降；而记账错误会直接导致 loss 的分母被算错（见 3.4）。

### 3.2 截断：答案放不下就丢弃，绝不截断答案

`truncation` 有两种策略：

- **`keep-answer`（缺省）**：预算先给答案，剩下的给 prompt，并从**左侧**裁掉 prompt——靠近答案的那部分指令信息密度最高，丢掉开头的客套话代价最小。**答案放不下则直接抛 `SFTDataError`**。
- **`head`**：朴素地取前 `max_length` 个 token。它可能把答案整个切掉，此时同样抛错。

两种策略在"会产出零监督样本"时都选择**失败而不是继续**。这是刻意的：

> 截断答案等于把"说了一半就停"教给模型。

实测（`max_length=10`，前缀 17 token、答案 2 token）：

```text
total_tokens = 10
prompt_tokens = 8          ← 从 17 裁到 8，裁掉的是**前** 9 个字符
supervised_tokens = 2
truncated = True
保留的 prompt == 原文 prompt[-8:]  -> True
```

### 3.3 padding 的三件套

`collate` 把若干样本补齐成批次。三件事必须**一起做**：

```python
input_ids.append(sample.input_ids + (pad_token_id,) * padding)
labels.append(sample.labels + (IGNORE_INDEX,) * padding)      # ← 补 -100
masks.append(sample.attention_mask + (0,) * padding)
```

缺任何一个都会出错：labels 没补 `-100` 会让 loss 去预测 pad；attention_mask 没补 0 会让 pad 参与注意力；input_ids 没补 pad id 则形状对不上。

padding 长度缺省按 **batch 内最长样本**（等价于 `padding="longest"`），这样 padding 量由数据自己决定，不会因为全局 `max_length` 设得过大而白算。`Batch.padding_tokens` 就是这个量的直接度量——**它不产生梯度，但参与注意力计算**。

### 3.4 loss 的分母：一个错了不报错的地方

`loss.masked_cross_entropy` 返回 `(loss, 监督 token 数)`——**把分母交出来**：

```python
def masked_cross_entropy(logits_seq, labels, *, ignore_index=IGNORE_INDEX) -> tuple[float, int]:
    ...
    for logits, target in zip(logits_seq, labels):
        if target == ignore_index:
            continue
        total += cross_entropy(logits, target)
        count += 1
    ...
    return total / count, count
```

把分母交出来是一个刻意的设计：它让调用方能核对 `count` 是否等于自己预期的监督 token 数。测试里专门有一条断言把"分母不能用序列长度"钉死：

```python
def test_denominator_is_not_sequence_length(self):
    logits = [[0.0, 0.0]] * 4
    labels = [0, 0, IGNORE_INDEX, IGNORE_INDEX]
    loss, count = masked_cross_entropy(logits, labels)
    assert count == 2
    assert loss == pytest.approx(LN2)   # 而不是 LN2 * 2 / 4
```

若分母误用序列长度，loss 会被系统性**压低**——分子不变而分母变大。于是"loss 从 2.7 降到 0.9"看起来非常漂亮，但它同时意味着**梯度被缩小了 `T'/T` 倍，学习率实际上被偷偷改小了一个数量级**。

### 3.5 数值稳定性：先减最大值

```python
def log_softmax(logits):
    largest = max(logits)
    shifted = [value - largest for value in logits]
    log_total = math.log(sum(math.exp(value) for value in shifted))
    return [value - log_total for value in shifted]
```

不减最大值时，logit 稍大（如 1000）就会让 `exp` 溢出为 `inf`，而 `inf / inf` 得到 `nan`——训练会从"梯度爆炸"变成"梯度是 nan"，后者更难定位。减最大值不改变数学结果（softmax 对整体平移不变），只是把指数控制在 `exp(0) = 1` 以内。测试里有两条专门的断言：一条用 `[1000.0, 1000.0]` 验证结果仍是 `[0.5, 0.5]`，一条验证概率下溢时 `log_softmax` 仍给出有限值。

## 第四章：长度与超参 —— 先把账算清

### 4.1 `max_length`：本课最重要的实操教训

day048 的数据集画像给出 `avg_estimated_tokens = 84.24`。如果照它取 `max_length = 128`，会发生什么？实测（train 30 条）：

```text
max_length=84   成功  9 / 失败 21 / 截断  9   （失败率 70%）
max_length=128  成功 27 / 失败  3 / 截断 27   （失败率 10%）
max_length=256  成功 30 / 失败  0 / 截断 15   （失败率  0%）
max_length=320  成功 30 / 失败  0 / 截断  0   （失败率  0%）
max_length=512  成功 30 / 失败  0 / 截断  0   （失败率  0%）
```

两种失败方式都出现了，而且**第二种更危险**：

- **硬失败**：答案放不下，`keep-answer` 直接抛 `SFTDataError`（84 时 21 条、128 时 3 条）。这是"好的失败"——它会立刻拦住你。
- **静默的坏数据**：剩下那些"成功"的样本**全部被截断**（84 时 9 条、128 时 27 条），prompt 被从左侧砍到只剩极短的一截。实测第一条样本在 `max_length=128` 下保留的 prompt 是：

  ```text
  ')?<|im_end|>\n<|im_start|>assistant\n'
  ```

  **系统提示词与 `<|im_start|>system` 标记已经全部丢失。** 也就是说，这些样本的训练模板和推理模板**不是同一个**——模型看到的是一个残缺的格式，而脚本不会报任何错。这类缺陷就是 1.2 节说的"脚本完美运行、实际什么都没学到"的典型来源。

`max_length=256` 已经不报错，但仍有 15/30 条被截断（prompt 被砍到 50~150 token）；只有取到 p100（320）才做到 **0 截断**。这就是"`max_length` 必须按渲染后的长度分位定"的全部理由。

因为真正送进模型的序列，比"指令 + 答案"的原始文本长得多。实测（ChatML 模板、字符级分词）：

```text
min=219  p50=248  p90=276  p95=302  max=320  mean=250.9
  其中 prompt 均值 151.8 / 监督区间均值 99.1
```

差距 **2.98 倍**，来自三处：

1. **系统提示词与角色标记**：ChatML 的前缀约 100 字符（`<|im_start|>system\n…<|im_end|>\n<|im_start|>user\n…<|im_end|>\n<|im_start|>assistant\n`）；
2. **轮次终止符**；
3. **字符级分词**把中文按约 1 字 1 token 计（BPE 会低得多）。

所以正确的做法是：

```python
from smart_research_agent.sft import render_supervised_list, suggest_max_length

rendered = render_supervised_list(examples)
suggest_max_length(rendered, tokenizer, quantile=0.95)   # -> 320
```

`quantile=0.95` 而不是最大值，是为了**容忍个别超长样本**。长尾样本往往正是"答案啰嗦"或"指令异常"的脏数据；为它们把整批数据的 `max_length` 抬高，代价是全部样本的算力。而被切掉的那部分会在编码阶段被如实记录（`EncodingReport.truncated`）——**它是可观测的，不是静默的**。要"一条都不截断"就传 `quantile=1.0`。

本数据集 p95 与 p100 恰好都是 320，所以取 320 时 **0/30 条被截断**。若取 2048，则有 **87.75%** 的位置是 padding（`1 - 250.9/2048`）——**而 padding 同样参与注意力计算，注意力对序列长度是平方复杂度**。

分位数用**最近秩法**（不插值），与 day046 `perf_baseline.percentile` 是同一条纪律：分位数必须对应一个**真实存在的样本长度**，插值出来的数字不是任何一条样本的长度，作为"取多长能不截断"的依据会误导。

### 4.2 步数：day049 的六个数字在运行时被验证

```python
from smart_research_agent.sft import SFTTrainingArgs, plan_training

plan = plan_training(SFTTrainingArgs(num_train_epochs=3.0), train_size=30, eval_size=7)
```

实测输出：

```text
micro_batches_per_epoch = 15
steps_per_epoch         = 3      （drop_last 口径）
total_steps             = 9
steps_per_epoch_flushing= 4      （HF Trainer 会 flush 尾部梯度）
total_steps_flushing    = 12
warmup_steps            = 0      ← 3% 的 warmup 在 9 步下取整为 0
effective_batch_size    = 8
```

与 day049 教程第六章预先算出的六个数字**逐项一致**。`TrainingPlan` 同时给出两种口径，是因为它们必然不同：

| 口径 | 计算 | 实测 |
|------|------|------|
| `drop_last`（本课训练循环） | `(micro // accum) × epochs` | 9 |
| `flush` 尾部（HF `Trainer` 的默认行为） | `ceil(micro / accum) × epochs` | 12 |

**做对照实验时不说口径，步数就不可比**——所以这条差异被写成了一条告警。

### 4.3 学习率：没有绝对尺度

这是本课最容易犯的错。实测（30 条样本、9 次更新，起点 loss = `ln(557) = 6.3226`）：

```text
lr = 2e-4  ->  6.3212 -> 6.3212   降幅  0.00%   ← 完全学不动
lr = 2.0   ->  6.3212 -> 6.2128   降幅  1.72%
lr = 4.0   ->  6.3212 -> 6.1070   降幅  3.39%
lr = 8.0   ->  6.3212 -> 5.9048   降幅  6.59%
lr = 20.0  ->  6.3212 -> 5.3933   降幅 14.68%
```

`2e-4` 是 **7B 全参 + AdamW** 的合理量级；对 557×557、纯 SGD、每次更新在上千个监督 token 上求均值的模型，它小了**四个数量级**。原因不神秘：**梯度幅度与参数量、批大小一起决定了步长**。

所以本课把这些阈值显式写成两个区间：

```python
LR_SOFT_RANGE            = (1e-5, 5e-4)    # 7B 全参 + AdamW
LR_SOFT_RANGE_PEFT       = (1e-4, 5e-4)    # LoRA / PEFT
LR_SOFT_RANGE_REFERENCE  = (1.0, 50.0)     # 本课参考模型
```

`plan_training(lr_range=...)` 让调用方选择用哪一个。这不只是"多一个参数"——它体现的是一条与 day046 性能基线判定下限相同的纪律：**告警阈值必须与模型规模匹配，否则它只会变成噪声，而天天误报的告警一定会被忽略**。

测试里有一条专门守这点的用例：同一组超参（`lr=8.0`）在参考区间里"不告警"、在 7B 区间（缺省）里"告警"。

### 4.4 学习率调度：一个反直觉的细节

`lr_at(step, total_steps)` 按 HF `get_*_schedule_with_warmup` 的分段定义实现：

```text
step <  warmup :  lr * step / warmup
warmup <= step :  lr * decay(progress)      progress = (step - warmup) / max(1, total - warmup)
```

`cosine` 用半周期余弦 `0.5 * (1 + cos(pi * progress))`，`linear` 用 `1 - progress`。实测（缺省 `lr=2e-4`、`warmup=0`、`total_steps=9`）：

```text
step 0 -> 0.00020000      step 4 -> 0.00011736      step 7 -> 0.00002340
step 2 -> 0.00017660      step 5 -> 0.00008264      step 9 -> 0.00000000
```

一个必须知道的反直觉细节：**`step = 0` 且 `warmup > 0` 时学习率为 0**。这不是 bug——`torch.optim.lr_scheduler.LambdaLR` 在**构造时就会求值一次** `lr_lambda(0)`（`last_epoch=-1` 的初始化行为），所以 warmup 段的第 0 步是一次**空更新**。

它对训练循环提出一个硬要求：**这一步必须照常执行，并把梯度清零**，否则这段梯度会漏进下一个窗口，把两次更新混成一次。本课的实现：

```python
if learning_rate > 0:
    self.model.apply_update(learning_rate)
else:
    self.model.zero_grad()   # 零 lr：更新无效果，但梯度必须丢弃
```

测试里用 `warmup_ratio=0.5` 专门验证这条路径：`records[0].learning_rate == 0.0`，且 `model.updates == 总步数 - 1`（第 0 步没有真的更新）。

### 4.5 八条告警，每条对应一个真实失败模式

`plan_training` 生成 `warnings`。本课程数据集上实测命中四条：

```text
- 总优化器步数仅 9 步（< 20）：训练几乎不会产生有效变化…先补数据，而不是调学习率。
- warmup_ratio=0.03 在 total_steps=9 下取整为 0：warmup 不会生效…要让 warmup 至少 1 步，
  比例需 ≥ 1/9 ≈ 11.11%，或改用更小的学习率。
- 训练样本仅 30 条：与 day048 的选型规则一致，500 条以下先补数据比换方法有效。
- 两种口径的步数不同：drop_last（本课训练循环）= 9 步，flush 尾部 = 12 步…
```

另外四条在别的输入下会命中：累积窗口比数据还大（0 次更新）、`eval_steps`/`save_steps` 大于总步数、未提供评估集、学习率超出区间、`max_length` 与长度分布不匹配。

`warnings` 与 `plan` 分开放，理由与 day048 `recommend_method` 的 `reasons` / `warnings` 相同：一个描述"会怎样"，一个描述"还要注意什么"。

## 第五章：训练循环 —— 让 loss 真的下降

### 5.1 参考模型：为什么要在课程里写一个模型

`reference_model.ReferenceSFTModel` 是一个上下文长度为 1 的 next-token 模型（bigram + softmax）：

```text
参数：  W ∈ R^{V×V}（每个上下文 token 一行 logits）、b ∈ R^V
前向：  logits = W[ctx] + b ；  probs = softmax(logits)
损失：  L = -(1/N) Σ_{t∈S} log probs[y_t]        S = 监督位置，N = |S|
梯度：  ∂L/∂logits_t = (probs_t - onehot(y_t)) / N
```

这个梯度是**解析求出来的**，不是数值近似：`logits = W[ctx] + b` 对 `W[ctx]` 与 `b` 的偏导都是 1，所以 `∂L/∂logits` 就是梯度本身。

它存在的理由只有一个：**让训练循环在离线、确定、零依赖的条件下真的发生一次**。

如果这一课只讲"怎么调 `SFTTrainer`"，学员看到的永远是"提交任务 → 等 40 分钟 → 看到一个 loss 数字"。而 loss 该从多少降到多少、梯度长什么样、为什么分母要只数监督 token——这些**必须能被手算验证**的东西，全都被框架盖住了。

### 5.2 它是真的在学（实测）

```text
参考模型：词表 557，参数 310249（W）+ 557（b），纯 SGD，lr=8.0
均匀分布参考 loss = ln(557) = 6.3226

训练集编码：30/30 条（截断 0）| 共 7462 token，其中监督 2933 (39.3%)、屏蔽 4529 | 平均 248.7 token/条
评估集编码：7/7 条（截断 0）| 共 1822 token，其中监督 734 (40.3%)、屏蔽 1088 | 平均 260.3 token/条

优化器步数 30（epochs_run=10）| 监督 token 使用量 23605
  step  1 | epoch 1  | loss 6.3212 | lr 8.0000
  step  5 | epoch 2  | loss 5.9573 | lr 7.6542
  step 10 | epoch 4  | loss 5.7247 | lr 6.3511
  step 15 | epoch 5  | loss 5.4154 | lr 4.4181
  step 20 | epoch 7  | loss 5.3857 | lr 2.3731
  step 25 | epoch 9  | loss 5.4039 | lr 0.7639
  step 30 | epoch 10 | loss 5.4760 | lr 0.0219

loss 6.3212 -> 5.4760 （降幅 +13.37%）
评估 loss 5.3596 | 困惑度 212.64（均匀分布 = 557）
耗时 9.76s
```

`loss` 的起点 `6.3212` 几乎正好是 `ln(557) = 6.3226`——这本身是一条自检：它说明模型初始化接近均匀分布、标签没有串位。如果起点明显偏离 `ln(V)`，问题多半出在 mask 或数据映射上。

最后一段的 loss 轻微回升（step 27 的 5.1607 → step 30 的 5.4760）也是可解释的：学习率在余弦末端已经降到 0.0219（接近 0），模型基本停止更新，而每个 batch 的样本组合不同，因此 loss 在小范围内波动。**这是"学习率已经走完"的正常表现，不是发散。**

再给一个直观的证据：某上下文 token 的下一 token 概率分布已经从"几乎均匀"变成了明显偏斜：

```text
上下文 38 的 top-3：(id, prob) = [(19, 0.0242), (81, 0.0191), (54, 0.0146)]
均匀分布下每个 token 的概率 = 0.001795
最高概率 / 均匀概率 = 13.46×
```

### 5.3 梯度累积：一个"先累加、后除 N"的会计问题

`accumulate` 与 `apply_update` 是**分成两步**的，接口与 PyTorch 的语义对齐：

```python
def accumulate(self, batch) -> tuple[float, int]:
    """前向 + 反向，把梯度**累加**进缓冲，返回 (loss 之和, 监督 token 数)"""

def apply_update(self, learning_rate):
    """把累加的梯度按 1/N 缩放到均值、应用一次 SGD，然后清零缓冲"""
```

为什么要"梯度项先累加、最后统一除以 N"，而不是"每个 micro-batch 各算均值再相加"？**前者是精确的**——它等于把整个累积窗口当成一个大 batch；后者在窗口内各 micro-batch 的监督 token 数不等时会引入偏差（实测各 micro-batch 的监督 token 数在 708~852 之间波动，偏差不可忽略）。

`N` 是**自上次更新以来累积的监督 token 数**，不是样本数、也不是 token 总数。这是"SFT 的 loss 分母只数监督 token"在梯度层面的落点——同一个纪律，两处体现。

### 5.4 评估不能污染梯度

```python
def evaluate(self, batches) -> tuple[float, int]:
    saved_weights = [row[:] for row in self._grad_weights]
    saved_bias = self._grad_bias[:]
    saved_tokens = self._pending_tokens
    ...
    self._grad_weights = saved_weights
    self._grad_bias = saved_bias
    self._pending_tokens = saved_tokens
```

评估只做前向，**且必须不污染梯度缓冲**。否则"训练 — 评估 — 继续训练"会把评估的梯度混进下一次更新——这是真实框架里也偶尔出现的 bug，因为评估通常忘记 `zero_grad`。

本实现的做法是"评估前记下缓冲状态、评估后恢复"，比"相信没人会忘记"更可靠。测试里直接验证：先 `accumulate` 一个批次，记下权重快照，调 `evaluate`，再断言权重未变，且**缓冲仍然可用**（`apply_update` 还能正常执行）。

### 5.5 `drop_last` 的代价与收益

训练循环采用 `drop_last`（每个 epoch 丢弃尾部不满一个累积窗口的 micro-batch），这样"总步数"有纯算术定义，与 day049 的预算一致。代价是**每个 epoch 丢掉一部分样本**：30 条样本 / batch 2 = 15 个 micro-batch，其中 12 个进入 3 个累积窗口，剩下 3 个被丢弃。

这个代价在报告里被如实记录。`supervised_tokens_seen` 取的是 **`records` 的求和**（= 真正参与更新的 token），而不是"曾经累加进缓冲的总量"——后者会明显偏大（每个 epoch 的 15 个 micro-batch 里只有 12 个进入更新窗口，**至少高估 20%**），属于典型的"账对不上"。

对应地，`SFTReport.to_dict()` 里同时给出 `plan.total_steps`（9，drop_last）与 `plan.total_steps_flushing`（12，flush 口径），让读者一眼看到差异来源。

### 5.6 可复现性

- 数据打乱用局部 `random.Random(data_seed)`，不污染全局随机状态（与 day048 `split_dataset` 同一条纪律）；
- 权重初始化用 `random.Random(seed)`；
- 测试里有一条断言：**同 seed 两次训练的 loss 序列逐位相同**。

## 第六章：对照实验 —— 屏蔽 prompt 到底有没有用

### 6.1 公平比较的关键是"同一把尺子"

第一章说"屏蔽 prompt 更好"，但直接比较两次训练的 `final_loss` 是**不成立的**：不屏蔽时 loss 的求和集合包含 prompt，两者的分母口径不同。

正确做法是：**两种训练法都用同一把尺子评估**——评估集一律按**屏蔽**口径编码，衡量的都是"模型在答案 token 上的预测能力"。

### 6.2 实测结果

```text
屏蔽 prompt（标准 SFT）
  训练集监督 token 占比：39.31%（监督 2933 / 共 7462）
  训练报告 loss（各自口径）：6.3212 -> 5.4760
  **统一尺子**下的答案 loss：5.3596（734 个监督 token 上求均值）

不屏蔽 prompt
  训练集监督 token 占比：100.00%（监督 7462 / 共 7462）
  训练报告 loss（各自口径）：6.3219 -> 4.6345
  **统一尺子**下的答案 loss：5.5475（734 个监督 token 上求均值）

结论：统一尺子下 屏蔽=5.3596 / 不屏蔽=5.5475，屏蔽更好（差值 0.1879）
```

注意一个反直觉的细节：**不屏蔽时"训练报告 loss"反而更低（4.6345 < 5.4760）**。这正是第一步要避免的误读——它的 loss 低，一部分来自"prompt 部分更好预测"，而不是"答案学得更好"。**换到统一尺子下，结论反转。**

这条实测是本课核心机制的唯一实证，因此它被写成了测试：`test_masked_prompt_beats_unmasked` 在合成数据集上做同样的事，并用 `assert results[True][0] < results[False][0]` 钉死方向。

### 6.3 这个实验的通用形式

把"要不要屏蔽"做成开关（`encode_supervised(mask_prompt=...)`、`SFTTrainer(mask_prompt=...)`）不是为了"多一个选项"，而是为了**让一个结论可以被证伪**。任何"某个设计更好"的说法，如果不配一个可运行的对照实验，它就只是一句话。

## 第七章：切到真实框架 —— 生成能跑的脚本

### 7.1 为什么是"生成"而不是"手写"

`hf_script.render_hf_sft_script(args)` 返回一份完整的 `transformers` + `Trainer` 训练脚本（实测 240 行），`render_trl_sft_script(args)` 返回 TRL `SFTTrainer` 版本（105 行）。

生成而不是手写的好处与 day048 `render_methods_table` 相同：**参数值只有一个来源**。脚本里内嵌的 `TRAINING_ARGUMENTS` 直接来自 `SFTTrainingArgs.to_hf_dict()`，测试会把它从文本里抠出来、`json.loads`，再与 `to_hf_dict()` 逐键比对——**教程里的参数与脚本里的参数不可能漂移**。两份生成物都会被 `compile()` 验证语法。

### 7.2 字段名必须逐字对齐

```python
def to_hf_dict(self) -> dict:
    return {
        "output_dir": self.output_dir,
        "num_train_epochs": self.num_train_epochs,
        "per_device_train_batch_size": self.per_device_train_batch_size,
        "gradient_accumulation_steps": self.gradient_accumulation_steps,
        "learning_rate": self.learning_rate,
        "warmup_ratio": self.warmup_ratio,
        "lr_scheduler_type": self.lr_scheduler_type,
        "eval_strategy": self.eval_strategy,      # 注意：不是 evaluation_strategy
        ...
    }
```

对齐的收益很实际：`TrainingArguments(**args.to_hf_dict())` 可以直接展开，**不需要一张"我们的字段 → HF 字段"的翻译表**——而翻译表就是漂移的来源。

两个容易踩的坑：

1. **`evaluation_strategy` 已废弃**（transformers 4.41 起改名 `eval_strategy`，v4.46 移除旧名）。本课用新名，测试里有一条断言专门检查旧名**不出现**。
2. **`max_length` 不属于 `TrainingArguments`**。它属于 TRL 的 `SFTConfig`（且从 `max_seq_length` 改名而来）。传进 `TrainingArguments` 会抛 `TypeError`——所以 `to_hf_dict()` 刻意**不含**它，而 `to_trl_dict()` 才有：

```python
payload.update({
    "max_length": self.max_length,
    "packing": False,                 # 本课刻意关闭（见 7.4）
    "completion_only_loss": True,
    "assistant_only_loss": True,
})
```

### 7.3 生成脚本里的三处关键实现

```python
# 1. 从左侧裁 prompt，保留靠近答案的指令
kept_prompt = prompt_ids[-budget:]

# 2. 答案放不下的样本丢弃，**不截断答案**
if budget < 1:
    return None

# 3. label mask
"labels": [IGNORE_INDEX] * len(kept_prompt) + answer_ids,
```

外加 padding 三件套（手写 collator，等价于库里的 `DataCollatorForSeq2Seq(tokenizer, label_pad_token_id=-100)`）与一个 `mean_token_accuracy` 的 `compute_metrics`。手写 collator 而不直接调库，是为了让"padding 到底补了什么"在脚本里可见。

脚本还打印监督 token 占比——**在真实训练开始前，这是"这笔算力花得值不值"的第一手数字**，与本课 `EncodingReport.summary_line()` 完全相同的目的。

### 7.4 `packing=False` 是刻意的

TRL 支持把多条短样本拼进同一条序列（`packing=True`）以提高吞吐。本课**关闭**它，因为它会：

- 改变样本边界（一条序列里混了多条样本）；
- 改变 loss 的分母口径（一次前向里的监督 token 数不再对应一条样本）；
- 让"第 N 步看到哪些样本"不可复现。

在 37 条样本这个规模上，吞吐收益远小于可解释性损失。`generated_script_summary()` 里把 `packing: False` 作为自述信息的一部分返回，就是为了让这个选择**是显式的**。

### 7.5 依赖与运行

```bash
pip install "transformers>=5.16" "datasets>=3.0" "accelerate>=1.0" "torch>=2.5"

python sft_train_transformers.py \
    --model_name Qwen/Qwen3-0.6B \
    --train_file data/finetune/out/train.jsonl \
    --eval_file data/finetune/out/eval.jsonl
```

基座缺省是 `Qwen/Qwen3-0.6B`——0.6B 级别单卡即可 SFT，适合作为"第一次跑通"的目标。**注意：本课并没有真的跑这个脚本**（环境无 GPU / 无网络下载权重），它的正确性由 26 个测试用例守（语法、参数同源、关键片段、依赖清单）。这一点在结语里会如实说明。

## 第八章：检查点与可复现性

### 8.1 五个文件

一次训练结束后，最有价值的产物不是权重文件，而是**一次可被审计的记录**：

| 文件 | 内容 | 为什么必须有 |
|------|------|-------------|
| `training_args.json` | 完整超参（含不属于 HF 的字段） | 复现这次训练的唯一依据 |
| `tokenizer.json` | 词表 | **没有词表，`input_ids` 无法还原为文本** |
| `model_state.json` | 权重 + 偏置 + 已更新次数 | 可继续训练或做推理 |
| `metrics.json` | 汇总指标 + 派生量 plan（附 `_meta`） | 一眼判断"这次训练有没有意义" |
| `train_log.jsonl` | 逐步的 `StepRecord` | 画 loss 曲线、定位发散的那一步 |

**词表必须随检查点落盘**——这与 day041 `EmbeddingResponse` 带 `provider` + `dimension` 是同一种纪律：**产物要自描述**。一个只有权重的目录，别人拿到手第一件事就是问"这是哪个分词器训的"。

### 8.2 实测：写过四个、保留三个

```text
检查点：
  写过 checkpoint-10
  写过 checkpoint-20
  写过 checkpoint-30
  写过 final
  落盘后实际保留：['checkpoint-20', 'checkpoint-30', 'final']
  （save_total_limit=2，最旧的中间检查点已被清理）
回读：args.max_length=320  updates=30  records=30  metrics.total_steps=30
```

末次检查点写在 `output_dir/final`，中间检查点写在 `output_dir/checkpoint-{step}`（与 HF 的命名习惯一致），按 `save_total_limit` 删除最旧的中间项——**`final` 永远不删**，它是这次实验的交付物。磁盘不是无限的，而"训练跑了两天因为磁盘满而崩"是最令人沮丧的失败方式。

### 8.3 检查点的失败路径必须显式

`load_checkpoint` 缺任何一个必需文件都抛 `CheckpointError`——**不返回"部分可用的对象"**。一个缺了 `tokenizer.json` 的检查点看着能用，实际会在推理时给出完全错误的文本（id 与字符错位），这比直接报错危险得多。

测试覆盖了四条失败路径：目录不存在、文件不完整、JSON 损坏、`train_log.jsonl` 某行损坏（报出行号）。另外还有一条"容错路径"：`train_log.jsonl` 里的空行会被跳过（写日志时追加是常态）。

### 8.4 端到端入口

`train_reference(train, eval)` 是一行跑通全流程的便捷入口：建词表 → 建模型 → 训练 → 返回 `(报告, 模型, 分词器)`。其中两个细节值得记：

1. **词表从训练集与评估集的全部文本构建**。必须包含评估集——否则评估集里的字符会全部落到 `<unk>`，评估就失去了意义（这是真实项目里很常见的一个错误，测试里有一条专门守它）。
2. **缺省参数必须对最小输入也成立**：`gradient_accumulation_steps=1`（不做累积），这样即使只有 4 条样本也能切出完整的更新窗口。**累积机制由 `SFTTrainer` 的循环与专门用例覆盖，不必写进缺省值**——这条规则让"便捷入口在小数据上直接报错"这类问题不会发生。

## 第九章：接入 API 与配置

### 9.1 三个只读端点

```python
@router.get("/finetune/sft/defaults", response_model=SFTDefaultsResponse)
@router.post("/finetune/sft/plan", response_model=SFTPlanResponse)
@router.post("/finetune/sft/preview", response_model=SFTPreviewResponse)
```

**训练本身不进 HTTP 端点**：一个需要 GPU 的长任务不该由一个同步 `def` 路由承载。三个端点都是"算账"与"看数据"：

| 端点 | 回答什么 |
|------|---------|
| `GET /finetune/sft/defaults` | 默认超参（与 `TrainingArguments` 同名）+ SFT 专属项 + 依赖清单 |
| `POST /finetune/sft/plan` | 派生量（步数 / warmup / 有效批）+ 风险告警 + **长度分布与 `max_length` 建议值** |
| `POST /finetune/sft/preview` | 一条样本的监督切分与 label mask |

`/finetune/sft/plan` 有一个设计取舍值得说：它把 `length` 与 `suggested_max_length` 一起返回，是为了让"`max_length` 该取多少"这个判断**可被复核**——调用方能看到 p50/p90/p95/max，再决定是接受建议值还是按自己的口径取。

实测（空请求体，走配置缺省 + 真实数据集）：

```text
train_size=30  eval_size=7
micro=15  steps_per_epoch=3  total_steps=30   ← 配置缺省是 10 个 epoch
warmup_steps=0  effective_batch_size=8
length: {count: 37, min: 219, p50: 248, p90: 276, p95: 302, max: 320, mean: 250.9}
suggested_max_length = 320  （分位 0.95，向上取整到 32 的倍数）
```

把 `num_train_epochs` 覆盖回 day049 用的 3.0，接口就会复现那六个数字（`total_steps=9`、`warmup_steps=0`）——**测试里就是这么断言的**。

### 9.2 `/finetune/sft/preview` 里最有价值的字段

```python
prompt_fully_masked = bool(prompt_labels) and all(v == IGNORE_INDEX for v in prompt_labels)
```

这是"label mask 真的生效了吗"的**可执行答案**。只要它为 `false`，这条样本就不该进训练集。把一句设计原则变成一个布尔字段，是本课"每个环节都要可观测"这条纪律的最小实现。

### 9.3 错误码延续既有契约

| 情况 | 状态码 | 理由 |
|------|--------|------|
| 超参非法（含 `overrides` 类型不对） | **400** | 请求语义与能力不匹配 |
| 未知 `template` | **400** | 同 day048 未知 `format` |
| 答案放不下 `max_length` | **400** | 参数组合不可行，调用方要改参数 |
| 样本缺 `output` / `output` 全空白 | **400** | 数据不合格（与 day048 `validate` 同构） |
| `train_size=0` / `eval_size=-1` / `max_length<2` | **422** | Pydantic 在进路由前拦下 |
| 正常 | 200 | — |

这与 day038 建立、day040/day041 沿用、day046 扩展到 `/pipeline/*`、day048 延伸到 `/finetune/*` 的错误码语言完全一致。

### 9.4 九个配置项

全部在 `config.py`（`.env.example` 同步）。它们的注释里写清了一件容易混淆的事：**配置里的默认值按"参考模型 + 本课程数据集"标定，而 `SFTTrainingArgs` 的字段缺省值按"7B 全参 + AdamW"标定**——两者的 `learning_rate` 相差四个数量级，混用会得到一条水平的 loss 曲线。

```text
sft_output_dir                    = "outputs/sft"
sft_max_length                    = 384     # 渲染后 p100=320，留余量
sft_num_train_epochs              = 10.0
sft_learning_rate                 = 8.0     # 参考模型量级
sft_per_device_train_batch_size   = 2
sft_gradient_accumulation_steps   = 4
sft_warmup_ratio                  = 0.03
sft_lr_scheduler_type             = "cosine"
sft_seed                          = 42
```

## 结语：三条可以带进 M5 的工程结论

1. **SFT 的全部机制落在一个整数上。** `-100` 写在哪里，决定了 loss 学的是什么。整章的数据准备（模板渲染 → 字符偏移 → 分别编码 → mask → padding → collate）都只是为了把这三个数字放进正确的位置。理解了这一点，"换框架"就只是换一层皮。

2. **能算的账必须在训练之前算完。** `total_steps=9`、`warmup_steps=0`、`max_length=320`、`effective batch=8`——这四个数字不需要 GPU、不需要框架，只需要数据规模与超参。day049 算过一遍，今天在运行时逐一验证，接口与脚本也从同一份 `SFTTrainingArgs` 派生。**"先算再跑"把"跑了才知道"的试错成本降到了零。**

3. **阈值必须与规模匹配，否则告警会变成噪声。** 本课写了两个学习率区间（7B 全参 vs 参考模型），相差四个数量级。同一组超参在错误的区间里会永久误报——而**天天误报的告警一定会被忽略**。这与 day046 性能基线的判定下限、day048 "500 条以下先补数据"的规则是同一条纪律：**规则的有效性取决于它的适用范围是否被写清楚。**

> **诚实的说明**：本课的训练结果（`loss 6.3212 → 5.4760`）来自一个 557×557 的 bigram 参考模型，在一份 30 条样本的教学数据集上。**它不是一个可用的模型，也无意成为。** 它的价值是让"数据 → token → mask → 梯度 → loss"这条链路的每个环节都被打印出来、可核对、可复现。真正有意义的微调需要真实语料（线上 bad case、人工标注、领域问答）、`max_length` 按真实长度分布标定、以及一个按模型规模标定过的学习率。另外，本章生成的 `transformers` 训练脚本**没有在本机真正运行过**（无 GPU、无权重下载），它由 26 个测试用例守住语法与参数同源——这一点必须说清，而不是让读者以为它已经跑通。

明天（day051）进入 **LoRA / QLoRA 微调**：把今天"全参更新"的思路换成"只训一个低秩增量 `ΔW = B @ A`"。今天定下的三件事会在那一天直接复用：**label mask 完全不变**（它是数据准备的事，与微调方法正交）、**`plan_training` 的步数算术完全不变**（LoRA 不改变优化器步数）、**`SFTTrainingArgs` 通过 `to_trl_dict()` 加一个 `peft_config` 就能接上 PEFT**。而 day049 复核过的那四个 LoRA 比例（`4096/r8 = 0.3906%`、`4096/r16 = 0.7812%`、`2048/r8 = 0.7812%`、`11008/r16 = 0.2907%`）会在那天被重新算一遍——它们正是"LoRA 能把参数量从平方级降到线性级"的算术基础。
