## 第一章：从骨架到循环 —— ReAct 的状态机视角

### 1.1 回顾：骨架缺了什么

day003 的 `ReactAgent` 骨架是这样的：

```python
def run(self, task: str) -> str:
    """执行任务的主入口（day006 实现完整 ReAct 循环）."""
    logger.info("接收到任务: %s", task)
    raise NotImplementedError("ReAct 循环将在 day006 实现")
```

它有组件（llm、tools、history），有入口（run），但没有**循环**。骨架回答的是"Agent 由什么组成"，今天要回答的是"**Agent 如何运转**"。

### 1.2 ReAct 循环的本质：一个五态状态机

很多教程把 ReAct 描述成"Thought → Action → Observation 的交替"，这没错，但不够工程化。工程视角下，ReAct 循环是一个**显式状态机**：

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
                    ▼                                          │
  ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
  │ 感知输入 │──▶│ LLM 推理│──▶│ 解析输出 │──▶│ 执行工具 │──▶│回填观察 │
  │ (任务)  │   │(生成文本)│   │(结构化) │   │(行动)   │   │(反馈)   │
  └─────────┘   └─────────┘   └────┬────┘   └─────────┘   └─────────┘
                                   │
                    Final Answer? ─┴─ 是 ──▶ ┌─────────┐
                                             │ 终止返回答案 │
                                             └─────────┘
```

每一圈循环经历五个状态转换：

| 状态 | 输入 | 输出 | 失败时的行为 |
|------|------|------|-------------|
| 感知输入 | 任务文本 + 历史消息 | 拼装的 messages | —— |
| LLM 推理 | messages | 一段自由文本 | 网络/限流异常（今天不处理，M4 处理） |
| 解析输出 | 自由文本 | `ReActStep` 结构体 | 抛 `ReActParseError` |
| 执行工具 | action + action_input | 结果字符串 | 错误转成 Observation，**不中断** |
| 回填观察 | observation | 追加到 messages | —— |

状态机视角的价值在于：**每个状态都可以单独测试，每个失败都有明确的处置策略**。这就是把"AI 玄学"变成"软件工程"的关键一步。

### 1.3 为什么是循环，而不是一次调用

一次性调用 LLM 回答复杂问题的根本局限：**模型的知识是静态的，而任务需要动态的、来自环境的信息**。

"2024 年诺贝尔文学奖得主的代表作有多少页？"——这个问题需要：

1. 先搜索得主是谁（动态信息）；
2. 再查代表作（依赖第一步结果）；
3. 再查页数（依赖第二步结果）。

每一步的输入都依赖上一步的输出，这是**串行依赖链**，单次调用在原理上就无法完成。循环结构让 Agent 能在每一步把环境的真实反馈（Observation）纳入推理，逐步逼近答案。这就是 ReAct 论文（Yao et al., 2022）的核心洞察：**推理（Reasoning）和行动（Acting）必须交织，互相提供上下文**。

> 思考题：为什么不一次性让 LLM 生成完整的"行动计划"，然后批量执行所有工具？  
> 提示：想想第二步的工具输入在计划时是否已知。这正是 day010 Planner-Executor 架构要面对的权衡，届时我们会正式对比两种范式。

### 1.4 一次循环的完整走查：逐消息视角

抽象讨论不如一次具体走查。假设任务是"2+3 等于几？"，LLM 按协议输出。我们跟踪 `messages` 列表在循环中的演化：

**循环开始，初始消息（2 条）：**

```text
[0] system:    你是一个使用 ReAct 范式解决问题的智能助手。严格按照以下格式……
               可用工具：- calculator: 计算数学表达式……
[1] user:      任务: 2+3 等于几？
```

**第 1 步：LLM 返回行动步。**

```text
Thought: 需要先计算 2+3
Action: calculator
Action Input: 2+3
```

解析器产出 `ReActStep(thought="需要先计算 2+3", action="calculator", action_input="2+3", final_answer=None)`。因为 `final_answer is None`，进入执行分支：`registry.get("calculator")` 命中，`execute(expression="2+3")` 返回 `"5"`。然后回填两条消息：

```text
[2] assistant: Thought: 需要先计算 2+3\nAction: calculator\nAction Input: 2+3
[3] user:      Observation: 5
```

**第 2 步：LLM 带着 4 条消息再次推理，返回终止步。**

```text
Thought: 已得到结果
Final Answer: 2+3 等于 5
```

解析器产出 `final_answer="2+3 等于 5"`，循环命中终止条件，`run()` 返回答案。

把这个走查和代码对照，你会发现 `run()` 里每一行都对应消息列表的一次确定变化——**循环没有魔法，只有消息列表的确定性演化**。这也是 ReAct 系统可调试的根本原因：出问题时，把 `messages` 完整打印出来，答案就在里面。

## 第二章：System Prompt 工程 —— 格式契约必须写死

### 2.1 为什么格式契约是循环的生命线

ReAct 循环里有一个角色错位：**LLM 输出的是自由文本，而程序需要的是结构化数据**。解析器（parser）是两者之间的翻译官，但它能翻译的前提，是 LLM 的输出遵守约定格式。

这个约定不能靠"暗示"，必须**写死在 System Prompt 里**：

```python
SYSTEM_PROMPT = """你是一个使用 ReAct 范式解决问题的智能助手。

严格按照以下格式交替输出：

Thought: 你对当前情况的分析与下一步打算
Action: 要调用的工具名（必须是可用工具之一）
Action Input: 工具的输入参数

当你已经有足够信息回答时，输出：
Thought: 总结性思考
Final Answer: 最终答案

可用工具：
{tools}
"""
```

[完整代码](../源码/smart-research-agent/smart_research_agent/agent/react_agent.py)

为什么必须如此强硬？因为 LLM 是**概率模型**，不给硬约束时它会"自由发挥"：有时用 Markdown 加粗，有时把 Action 写成中文"行动："，有时在 Thought 前加一段寒暄。每一种自由发挥都是解析器的一次崩溃。**Prompt 里的格式契约，本质上是人机之间的接口协议**——和 HTTP 协议、JSON Schema 是同一种东西，只不过约束对象从程序换成了模型。

### 2.2 三字段设计的考量

为什么是 `Thought / Action / Action Input` 三个字段，而不是把 Action 和参数合并成一行？

| 设计选择 | 我们的方案 | 替代方案 | 为什么选前者 |
|----------|-----------|----------|-------------|
| Thought 是否独立 | 独立字段 | 省略 Thought | Thought 是推理痕迹，提升决策质量（CoT 效应），也是调试日志 |
| Action 与参数 | 分离两个字段 | `Action: calculator("2+3")` 一行 | 函数调用式容易被模型写错语法；纯文本参数更鲁棒 |
| 参数格式 | 纯字符串 | JSON 对象 | JSON 转义引号常被模型写错；字符串先跑通，day004 的工具契约已约定 |

还有一个隐藏设计：**终止信号与行动信号共用同一个解析框架**。`Final Answer:` 只是另一种"字段组合"，解析器不需要为终止逻辑写一套独立机制。这降低了协议复杂度——LLM 需要学习的格式只有两种形态。

### 2.3 工具清单为什么注入 System Prompt

注意 prompt 末尾的 `{tools}` 占位符，它由 `registry.describe()` 动态填充：

```
可用工具：
- calculator: 计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'
```

这就是 day004 坚持给每个工具写 `description` 的回报：**工具的自然语言描述直接成为 LLM 选择工具的依据**。LLM 没有见过你的代码，它对工具的全部认知都来自这段文本。description 写得差（"一个工具"），LLM 就不知道怎么用；写得好（含示例、含边界说明），工具选择准确率立刻提升。

这也解释了 day005 的架构决策：Agent 不直接持有工具列表，而是持有 `ToolRegistry`——注册表既管路由（`get`），又管描述生成（`describe`），两件事天然是一体的。

### 2.4 常见 Prompt 反模式对照

格式契约写不好，循环就会在解析器上反复翻车。以下是教学中总结的典型反模式：

| 反模式 | 示例 | 后果 | 修正 |
|--------|------|------|------|
| 只说意图不给格式 | "请用工具解决问题" | LLM 自由发挥，解析必挂 | 逐字段给出标签与顺序 |
| 给格式不给示例 | 只有字段名 | 模型对 `Action Input` 该写 JSON 还是纯文本举棋不定 | 附 1~2 个完整输出示例（few-shot） |
| 格式与自然语言混杂 | "先想想再行动哦" | 措辞越软，模型越不当真 | 用"严格按照""必须是"等强约束措辞 |
| 工具清单缺失 | 不写可用工具 | 模型幻觉出不存在的工具名 | 动态注入 `registry.describe()` |
| 终止条件不明 | 不说何时输出 Final Answer | 模型无限调用工具 | 显式声明"信息足够时输出 Final Answer" |

今天的 `SYSTEM_PROMPT` 已经避开了其中四条（强措辞、明确格式、注入工具清单、声明终止条件），唯独没有给 few-shot 示例——这是有意的教学取舍：示例会让 prompt 变长，先把协议主干讲清楚。习题第 6 题会让你评估"加 few-shot 示例"对解析成功率的影响。

## 第三章：输出解析 —— 正则的脆弱性与分层设计

### 3.1 为什么解析器必须是独立函数

一个常见的初学者写法是把解析逻辑直接塞进 `run()` 的循环体里。我们坚决反对，而是抽成独立模块 `agent/parser.py`：

```python
def parse_react_output(text: str) -> ReActStep:
    """解析单步 ReAct 输出."""
```

[完整代码](../源码/smart-research-agent/smart_research_agent/agent/parser.py)

独立分层带来三个工程收益：

1. **可测试性**：`tests/test_parser.py` 里的 5 个测试不需要 LLM、不需要 Agent，直接喂字符串验结果。如果解析逻辑埋在循环里，测一次解析错误就得驱动整个 Agent。
2. **可替换性**：未来要换成 JSON 输出格式、换成 function calling，只需替换 parser 模块，`react_agent.py` 的循环结构不变。
3. **单一职责**：parser 只负责"文本 → 结构体"的映射，不知道工具怎么执行、不知道循环怎么终止。职责越单一，出错面越小。

### 3.2 解析结果的结构化：ReActStep

```python
@dataclass
class ReActStep:
    """一步 ReAct 推理的结构化结果."""

    thought: str
    action: str | None = None
    action_input: str | None = None
    final_answer: str | None = None
```

注意三个可选字段的语义设计：

- `final_answer is not None` → 本步是**终止步**，循环该停了；
- `action is not None` → 本步是**行动步**，需要执行工具；
- 两者互斥，由解析函数保证（见下）。

用一个数据类承载"二选一"的形态，比返回元组或字典好：字段名自带文档性，`ReActStep` 还能直接进 `agent.history` 成为推理痕迹。

### 3.3 正则实现与它的脆弱性

核心正则：

```python
_PATTERN_THOUGHT = re.compile(r"Thought:\s*(.+?)(?=\n(?:Action|Final Answer):|\Z)", re.S)
_PATTERN_FINAL = re.compile(r"Final Answer:\s*(.+?)\s*\Z", re.S)
```

两个值得展开的细节：

**（1）`(.+?)(?=...|\Z)` 的非贪婪 + 前瞻。** `Thought` 的内容可以是多行的（思考过程往往很长），所以用 `re.S` 让 `.` 匹配换行；但必须停在下一个字段开头，所以用前瞻断言 `(?=\n(?:Action|Final Answer):|\Z)`——要么遇到下一个字段标签，要么遇到文本结尾（`\Z`）。这就是 `test_multiline_thought` 测试覆盖的场景：

```python
def test_multiline_thought(self):
    text = "Thought: 第一步分析\n第二步分析\nAction: calculator\nAction Input: 1+1"
    step = parse_react_output(text)
    assert "第二步分析" in step.thought
```

[完整测试](../源码/smart-research-agent/tests/test_parser.py)

**（2）Final Answer 优先判断。** `parse_react_output` 先查 `Final Answer`，找到就直接返回终止步，不再找 Action。为什么？因为 LLM 偶尔会输出"既有 Action 又有 Final Answer"的矛盾文本。给定优先级规则，解析行为就是**确定的、可预测的**——工程系统最怕的是"看情况"。

但我们必须诚实：**正则解析是脆弱的**。以下输出都会让解析失败或出错：

- `Thought：需要计算`（中文全角冒号）；
- `**Action:** calculator`（Markdown 加粗）；
- Thought 内容里恰好包含一行以 `Action:` 开头的文字（前瞻被"骗"）。

教学项目里我们用正则，因为它直观、零依赖、足以演示协议概念。生产系统的演进方向是：**让模型输出 JSON，或直接使用厂商的 function calling 协议**，把格式约束从"正则匹配文本"升级为"schema 校验结构"。这条路我们会在后续阶段走。今天的取舍是：**用脆弱但透明的方案，配严格的容错策略**。

### 3.4 容错策略：解析失败怎么办

`parse_react_output` 在两种情况下抛 `ReActParseError`：

```python
if not thought_m:
    raise ReActParseError("缺少 Thought 字段")
...
if not action_m or not input_m:
    raise ReActParseError("缺少 Action 或 Action Input 字段")
```

抛异常而不是返回 `None`，是刻意的：**解析失败是协议违例，应该显式暴露**，让上层决定策略。可选的上层策略有：

| 策略 | 做法 | 适用场景 |
|------|------|---------|
| 重试 | 把错误信息反馈给 LLM，让它按格式重新输出 | 生产系统首选（自愈） |
| 降级 | 解析失败时直接把原文当 Final Answer 返回 | 兜底，保证用户总能拿到回复 |
| 熔断 | 连续 N 次解析失败则终止循环 | 防烧 token |

今天的教学实现选择"显式抛出"，保持循环主干的清晰；习题里你会亲手实现"重试反馈"策略。

## 第四章：工具执行与 Observation 回填 —— 自愈循环的心脏

### 4.1 run() 主循环完整走一遍

```python
def run(self, task: str) -> str:
    logger.info("接收到任务: %s", task)
    messages = [
        Message(role="system", content=SYSTEM_PROMPT.format(tools=self.registry.describe())),
        Message(role="user", content=f"任务: {task}"),
    ]
    for step_no in range(1, self.max_steps + 1):
        raw = self.llm.chat(messages)
        logger.info("第 %d 步原始输出:\n%s", step_no, raw)
        step = parse_react_output(raw)
        self.history.append(step)
        if step.final_answer is not None:
            logger.info("得出最终答案")
            return step.final_answer
        observation = self._execute_tool(step)
        messages.append(Message(role="assistant", content=raw))
        messages.append(Message(role="user", content=f"Observation: {observation}"))
    return "达到最大步数限制，未能得出最终答案"
```

[完整代码](../源码/smart-research-agent/smart_research_agent/agent/react_agent.py)

逐行拆解关键设计：

**（1）消息列表就是状态。** `messages` 承载了循环的全部上下文：system 定协议，user 给任务，之后每一步追加 `assistant`（LLM 的原始输出）和 `user`（Observation 反馈）。LLM 本身是无状态的——**"记忆"完全是客户端通过重放消息列表模拟出来的**。这一点至关重要，day008/day009 的记忆系统就是在给这个消息列表加管理能力。

**（2）Observation 伪装成 user 消息。** 工具的执行结果以 `Observation: ...` 前缀塞进一条 user 角色消息。为什么不用 tool 角色？因为我们要保持对任何 OpenAI 兼容端点的最小假设——system/user/assistant 三角是所有端点都支持的公约数。

**（3）原始输出原样回填。** `messages.append(Message(role="assistant", content=raw))` 回填的是 `raw` 原文，不是解析后的结构。这样 LLM 在下一轮能看到自己上一步说了什么，形成连贯的"内心独白"链条。

### 4.2 错误也是 Observation：自愈循环

整个 ReAct 循环里最重要的工程决策在 `_execute_tool`：

```python
def _execute_tool(self, step: ReActStep) -> str:
    tool = self.registry.get(step.action or "")
    if tool is None:
        return f"错误：不存在名为 {step.action} 的工具"
    ...
    try:
        return tool.execute(**kwargs)
    except Exception as exc:  # noqa: BLE001
        logger.warning("工具执行异常: %s", exc)
        return f"工具执行失败: {exc}"
```

注意它**从不抛异常**：

- 工具不存在 → 返回错误描述字符串；
- 工具执行炸了 → 捕获一切异常，返回失败描述字符串。

为什么不让异常传播、中断循环？回想状态机视角：LLM 是概率模型，**调用一个不存在的工具、传一个非法参数，是模型行为的正常分布，不是系统故障**。把这些"模型的错"转成 Observation 反馈回去，LLM 下一轮读到"错误：不存在名为 time_machine 的工具"，通常会自我纠正——改用合法工具，或承认无法完成。

这就是**自愈循环（self-healing loop）**：系统的鲁棒性不来自"永不出错"，而来自"把错误变成信息，让循环继续"。对比一下两种架构：

```
中断式设计：                        自愈式设计：
LLM 输出 ──▶ 执行 ──✗ 异常          LLM 输出 ──▶ 执行 ──✗ 异常
                     │                                    │
                     ▼                                    ▼
               程序崩溃/返回 500                    Observation: "错误：..."
                                                          │
                                                          ▼
                                                    下一轮 LLM 读到错误
                                                          │
                                                          ▼
                                                    自我纠正，继续推理
```

我们的端到端测试 `test_unknown_tool_feeds_error_back` 验证的正是这条路径：

```python
def test_unknown_tool_feeds_error_back(self):
    agent = _make_agent([
        "Thought: 试试不存在的工具\nAction: time_machine\nAction Input: now",
        "Thought: 工具不存在，直接回答\nFinal Answer: 无法使用工具",
    ])
    answer = agent.run("现在几点？")
    assert answer == "无法使用工具"
    # 第二次调用 LLM 时，消息里应包含错误 Observation
    second_call = agent.llm.calls[1]
    assert any("不存在" in m.content for m in second_call)
```

[完整测试](../源码/smart-research-agent/tests/test_react_loop.py)

这个测试不只断言最终答案，还**断言了错误确实作为 Observation 进入了第二次 LLM 调用的消息**——闭环被完整验证。

### 4.3 Schema 驱动的参数注入

工具怎么知道自己的参数名？回看这段：

```python
required = tool.parameters.get("required") or []
if not required:
    kwargs: dict = {}
else:
    kwargs = {required[0]: step.action_input or ""}
```

这里复用了 day004 工具契约里的 `parameters`（JSON Schema 形式）：从 `required` 数组取出第一个必填参数名，把 LLM 给的 `action_input` 字符串注入进去。对 `CalculatorTool` 来说，`required = ["expression"]`，于是调用变成 `tool.execute(expression="2+3")`。

这是**schema 驱动（schema-driven）**设计的雏形：Agent 不需要硬编码"计算器工具的参数叫 expression"，参数名是从工具自描述的 schema 里读出来的。新增任何工具，只要遵守 BaseTool 契约，Agent 自动就会调用它——**对扩展开放，对修改封闭**（开闭原则）。

当然，今天的实现是简化版：只支持单个必填参数。多参数工具需要把 `action_input` 解析成 JSON 再展开成 `**kwargs`，这是留给你的编程题（见习题第 10 题），也是 function calling 时代的标准做法。

### 4.4 双轨记录：history 与 messages 的分工

细心读代码会发现 Agent 同时维护了两份"历史"：

```python
self.history: list[ReActStep] = []   # 结构化的推理痕迹
messages = [...]                      # 给 LLM 看的对话消息
```

为什么要双轨？因为它们服务不同的读者：

| | `messages` | `history` |
|---|---|---|
| 读者 | LLM（下一轮推理的上下文） | 人类 / 程序（调试、审计、评估） |
| 内容 | 原始文本，含 system prompt、Observation | 结构化 `ReActStep`，只有解析结果 |
| 生命周期 | 单次 `run()` 的局部变量 | Agent 实例属性，跨调用保留 |
| 增长方式 | 每步 +2 条（assistant + observation） | 每步 +1 条 |

分开维护的好处：评估和调试代码不需要再从自由文本里重新解析一遍（`history` 直接给出 `action` / `final_answer` 字段）；而 LLM 拿到的上下文保持它"自己说过"的原始口吻，推理连贯性更好。M3 评估阶段统计"平均几步得出答案""工具失败率"时，消费的就是 `history` 这份结构化数据。

## 第五章：熔断与终止 —— 循环必须能停下来

### 5.1 两个终止条件

一个 `while True` 式的推理循环是危险的：LLM 可能反复调用同一个工具、反复犯同一个错，每一次调用都在烧 token 和钱。我们的循环有两道刹车：

**（1）正常终止：Final Answer。**

```python
if step.final_answer is not None:
    logger.info("得出最终答案")
    return step.final_answer
```

LLM 判断"信息足够"时主动给出最终答案，循环立即退出。这是协议层面的终止，是最理想的路径。

**（2）熔断终止：max_steps。**

```python
for step_no in range(1, self.max_steps + 1):
    ...
return "达到最大步数限制，未能得出最终答案"
```

`max_steps`（默认 10）是**熔断器（circuit breaker）**：循环次数耗尽时，无论 LLM 是否得出结论，强制返回一句明确的失败说明。注意这个返回值也是"信息而非异常"——调用方能区分"有答案"和"没跑出来"，并拿到可读的原因。

对应的测试 `test_max_steps_guard` 用 `max_steps=3` 加上三段永远行动的脚本，验证循环确实在第 3 步后停下，`history` 恰好 3 条。

### 5.2 为什么默认 10 步

`max_steps` 的取值是一个成本与能力的权衡：

| 取值 | 风险 |
|------|------|
| 太小（如 3） | 复杂任务（多跳检索）走不完，答案质量差 |
| 太大（如 100） | 死循环时烧钱烧时间，失去熔断意义 |
| 10 左右 | 覆盖绝大多数单任务推理链，失控成本可接受 |

工程实践中，熔断还应该叠加更多维度：**累计 token 上限、累计耗时上限、重复 Action 检测**（连续两次相同的 action+input 大概率是卡住了）。这些我们会在 M3 评估阶段和 M4 服务化阶段逐步补上。

### 5.3 熔断返回值的设计：失败也要可消费

注意熔断返回的不是异常、不是 `None`，而是一句人话：`"达到最大步数限制，未能得出最终答案"`。这个细节遵循与自愈循环相同的哲学——**失败是信息，不是事故**：

- 对终端用户：拿到一句可读的说明，而不是一堆 traceback；
- 对上游调用方（比如未来的 Planner）：字符串返回值可以原样拼进上下文，成为下一步推理的输入；
- 对日志与评估：熔断事件可以通过 `history` 长度达到 `max_steps` 且无 `final_answer` 来精确统计。

一个可对照检查的断言组合（`test_max_steps_guard` 已覆盖）：返回值包含"最大步数"、`len(agent.history) == max_steps`、`history` 中每一步的 `final_answer` 都是 `None`。三者同时成立，才能确认走的是熔断路径而非提前终止。

> 思考题：除了"步数耗尽"，还有什么信号可以判断 Agent 陷入了死循环？  
> 提示：观察 `history` 里相邻步骤的 `(action, action_input)` 是否重复。这正是"重复 Action 检测"的思路。

## 第六章：端到端测试 —— MockLLM 驱动完整循环

### 6.1 为什么能离线测试整个 Agent

回头看我们前五天埋下的伏笔，今天全部兑现：

- day004 的 `BaseTool` 契约 → 工具可独立实例化、独立执行；
- day005 的 `BaseLLM` 抽象 + `MockLLM` → LLM 可脚本化替换；
- day005 的 `ToolRegistry` → 工具组装只需两行代码。

于是端到端测试的搭建异常简洁：

```python
def _make_agent(responses: list[str], max_steps: int = 10) -> ReactAgent:
    registry = ToolRegistry()
    registry.register(CalculatorTool())
    return ReactAgent(llm=MockLLM(responses=responses), registry=registry, max_steps=max_steps)
```

MockLLM 的 responses 列表就是一份"剧本"：第一次调用 LLM 返回第一条，第二次返回第二条。**我们把模型变成了确定性的状态机输入**，整个循环的行为就完全可预测、可断言。这再次验证了依赖倒置的价值：`ReactAgent` 依赖的是 `BaseLLM` 抽象，所以测试里换 MockLLM、生产里换 OpenAICompatibleLLM，Agent 代码一行不动。

### 6.2 最核心的端到端用例：先行动后作答

```python
def test_full_loop_action_then_answer(self):
    agent = _make_agent([
        "Thought: 需要先计算 2+3\nAction: calculator\nAction Input: 2+3",
        "Thought: 已得到结果\nFinal Answer: 2+3 等于 5",
    ])
    answer = agent.run("2+3 等于几？")
    assert "5" in answer
    assert len(agent.history) == 2
```

这个测试虽然只有几行，但它走过的路径就是真实 Agent 的全部生命：

```
任务 ──▶ 拼 system+user ──▶ MockLLM 第1次返回(行动步)
    ──▶ parser 解析出 action=calculator, input="2+3"
    ──▶ registry.get("calculator") ──▶ execute(expression="2+3") ──▶ "5"
    ──▶ 回填 assistant 原文 + Observation: 5
    ──▶ MockLLM 第2次返回(终止步) ──▶ parser 解析出 final_answer
    ──▶ 返回 "2+3 等于 5"
```

注意一个微妙的细节：断言写的是 `assert "5" in answer`。最终答案里的 "5" 来自**真实计算**——CalculatorTool 真的执行了 AST 求值得到 "5"，它作为 Observation 进入了消息流。MockLLM 的剧本只是"复述"了这个结果。如果工具链断了（比如计算器没注册），Observation 会变成错误信息，这个测试的行为就会不同。**这就是端到端测试与纯单元测试的区别：它验证的是零件之间的连接，而不只是零件本身。**

### 6.3 测试矩阵：三个用例的分工

`tests/test_react_loop.py` 的三个测试各管一段：

| 测试 | 验证的状态机路径 | 对应设计 |
|------|-----------------|---------|
| `test_full_loop_action_then_answer` | 行动步 → 终止步（happy path） | 循环主干 + Observation 回填 |
| `test_unknown_tool_feeds_error_back` | 行动步（失败）→ 错误 Observation → 终止步 | 自愈循环 |
| `test_max_steps_guard` | 行动步 × 3 → 熔断 | 熔断机制 |

加上 `test_parser.py` 的 5 个解析用例，状态机的每个状态、每条边、每种失败都有了测试守护。今天全套测试共 **39 个**，全部离线、毫秒级跑完——这就是 FIRST 原则在 Agent 系统上的延续。

### 6.4 接入真实 LLM（可选练习）

今天的所有测试都是离线的，但骨架已经支持随时换成真实模型——这正是依赖倒置的回报：

```python
from smart_research_agent.agent.react_agent import ReactAgent
```

把 `OPENAI_API_KEY` 填进 `.env` 即可运行（[配置说明](../源码/smart-research-agent/.env.example)）。建议跑同一个任务多试几次，观察日志里每一步的原始输出——你会直观感受到第三章说的"LLM 输出的不稳定性"，也会理解为什么解析器、熔断器、自愈循环一个都不能少。**真实模型的每次翻车，都是今天某个设计决策存在的理由。**

## 第七章：今日总结 —— 闭环背后的工程思想

今天我们把五天的零件组装成了能运转的 ReAct Agent，核心思想一览：

| 思想 | 落地体现 |
|------|----------|
| **状态机视角** | 感知→推理→解析→执行→回填 五态循环，每个状态可独立测试 |
| **格式即协议** | System Prompt 写死 Thought/Action/Action Input/Final Answer 契约 |
| **解析分层** | 独立 `parser.py` 模块，`ReActStep` 结构化结果，显式抛 `ReActParseError` |
| **自愈循环** | 工具错误不中断，转成 Observation 反馈给 LLM 自我纠正 |
| **schema 驱动** | 参数名从工具自描述的 `parameters.required` 读取，新增工具零改动 Agent |
| **熔断设计** | `Final Answer` 协议终止 + `max_steps` 强制熔断，双保险 |
| **离线端到端** | MockLLM 剧本驱动完整循环，39 个测试毫秒级跑完 |

今天留下的已知局限（也是后续课程的伏笔）：

- 解析器是正则的，对 Markdown 加粗、全角冒号等变体脆弱 → 后续走向 JSON / function calling；
- 只支持单参数工具 → 习题第 10 题先练，后续正式支持；
- 消息列表无限增长，没有截断 → day008 短期记忆解决；
- 没有跨会话的知识沉淀 → day009 长期记忆（向量检索）解决；
- 单 Agent 顺序执行，不会先规划 → day010 Planner 模块解决。

最后退一步看：今天的 `ReactAgent` 只有约 70 行代码，但它已经具备了一个 Agent 的全部本质要素——**感知（消息）、推理（LLM）、行动（工具）、反馈（Observation）、终止（协议 + 熔断）、记忆（history）**。后续几十天的课程，本质上都是在这个内核上做加法：记忆更长、工具更强、规划更稳、评估更严。把今天这 70 行吃透，后面的每一次扩展你都能认出它在状态机里的位置。
