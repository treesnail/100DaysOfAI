## 第一章：为什么"可发布"不等于"已上线"

### 1.1 day059 留下的伏笔

day059 的结语里写着：

> 下一阶段进入 **M6：RAG 应用开发**（day060 起）——文档解析、分块策略、
> 向量数据库、混合检索、重排序与生产化部署。届时 `evaluation`
> 里的 RAG 评估器会与今天这条流水线的门禁相遇。

课程索引里 day060 是 **M5-D11「专属模型部署替换」**（M6 从 day061 开始，
本课按索引执行）。M5 的最后一天要回答的正是那条流水线的**下游**问题：

```text
day059：这份产物够格发布吗        → 门禁通过，注册表里多一条 stable
day060：发布之后，线上跑的是它吗  → 这一步没有任何自动化在保证
```

### 1.2 三条不会报错的部署事故

"线上跑的不是我以为的那一版"有三种完全不同的发生路径：

| 路径 | 具体表现 | 为什么不会报错 |
|------|---------|---------------|
| **路径指错** | `adapter_dir` 指到了旧目录 | 服务起得来、答得出来，只是答的是上一版 |
| **基座被换** | 训练用 8B、线上挂到 14B 上 | 适配器能挂上（day052 写过一次），输出"莫名其妙" |
| **副本不一致** | 多副本里某一个 Pod 还是旧配置 | 大部分请求正确，少数请求错误——最难定位的一种 |

三条路径的共同点是：**证据都在，只是没有人把它们放在一起比对**。
注册表说"1.1.0 是 stable"，适配器清单说"这一份的哈希是 `5c6d7e8f9012`"，
端点说"我加载的是 `deadbeef0000`"——三份事实各自都对，
但它们**指向的不是同一个东西**，而这只有在被并排放在一起看时才会暴露。

### 1.3 三条贯穿全包的纪律

| 纪律 | 具体表现 | 反例（如果没有它） |
|------|---------|------------------|
| **"哪个模型"必须能被证伪** | 五条一致性检查，每条指向一种"不报错但答错"的故障 | 事后从推理结果反推"当时跑的到底是哪一份" |
| **降级只向一个方向** | 专属失败可回落云端；云端失败**绝不**回落专属 | 云端故障时把流量交给未验证模型，两个故障叠加 |
| **缺失就是缺失** | 端点没自述 → 不一致；策略没给延迟倍数 → 未检查；云端成本为 0 → 节省比例 `None` | "因为没测延迟所以延迟检查通过" |

第二条值得多说一句。它看起来像是"少做了一半的容错"，其实是本日最反直觉的
一处设计：

```text
专属模型（新路径）失败 → 回落到云端（已验证路径）    修复：用户拿到正确答案
云端（已验证路径）失败 → 回落到专属模型（新路径）    事故：一个未验证的模型接管了全部流量
```

反向降级的坏处不只是"可能答得差"，而是**第二个故障的根因会被第一个掩盖**：
云端为什么挂、专属接管期间发生了什么，两件事会混在同一次事故复盘里。

## 第二章：部署形态 —— 必填字段由形态决定

### 2.1 三种形态

三种形态在**协议层完全一样**（都是 OpenAI 兼容端点，day045 的 `LocalModel`
一行都不用改），差异全部在**运维层**。实测（demo 第 1 节）：

```text
  base     必填 （无）            不需要额外运行时
           换业务：（无业务可换）
  adapter  必填 adapter_dir    需要 peft 在推理时挂载适配器
           换业务：换业务只换十几 MB 的适配器文件
  merged   必填 merged_dir     不需要额外运行时
           换业务：换业务要换一份与基座同量级的完整权重
```

这张表由 `spec_table()` 现场读出，因此"文档说 adapter 需要 `adapter_dir`、
代码却允许它为空"这类漂移会立刻可见。

### 2.2 一个在构造期被拦下的部署

`ServingSpec.__post_init__` 把"形态"与"必填字段"用一张表绑在一起：

```python
KIND_REQUIRED_FIELDS: dict[str, tuple[str, ...]] = {
    KIND_BASE: (),
    KIND_ADAPTER: ("adapter_dir",),
    KIND_MERGED: ("merged_dir",),
}
```

实测：

```text
声明 adapter 却没给目录被拒：形态 adapter 缺少必填字段 adapter_dir：
声明了形态却没给路径的部署不会报错，它只会安静地服务别的东西
```

这句话的后半段是本模块存在的**全部理由**。一个 `adapter_dir` 为空的部署
不会抛异常、不会返回 500，它只会安静地把基座的答案当成"专属模型的答案"
交出去——而那正是"专属模型上线了却没生效"最真实的一种发生方式。

**同一条纪律在 day060 出现了第三次**：day050 把词表随检查点落盘（产物要自描述）、
day052 校验 `base_model` 是否匹配（基座不匹配不报错）、今天把形态与必填字段绑定。
三次的形态不同，理由完全相同：**把"静默失效"提前成"构造期失败"。**

### 2.3 形态建议的两条规则

`recommend_kind` 只做两条判断，每条都来自"代价在哪一侧"：

```text
业务数 1 / 需热插拔 False → merged   只有一个业务且不需要热插拔：合并形态的部署链路
                                    与普通模型一致，而完整权重本来就只有一份
业务数 1 / 需热插拔 True  → adapter  需要热插拔：适配器形态换业务只换十几 MB，
                                    合并形态要重新加载完整权重
业务数 4 / 需热插拔 False → adapter  有 4 个业务：一个基座 + N 个适配器省下
                                    3 份完整权重，代价由清单与绑定校验承担
```

注意最后一句的措辞：省下的 3 份权重**不是免费的**，代价是"运行时挂载 +
基座与适配器的配对校验"。这条代价在 day052 由 `AdapterManifest` 承担、
在今天由 `binding` 模块承担——两天的产物在这里接上了。

`needs_hot_swap` 单独列出来的原因是它会在**只有一个业务时**也推翻第一条：
需要毫秒级切回基座做对照实验时，`merged` 形态要重新加载一份完整权重。

### 2.4 显存算术：三块分开列

自建推理的显存里有两块完全不同的东西，它们的决定因素也不同：

```text
权重      = 参数数 × 每参数字节数              与上下文无关，开机就占满
KV 缓存   = 2 × 层数 × KV头数 × head_dim × 字节数 × 上下文长度 × 并发数
适配器    = 十几 MB 到几十 MB                换业务时唯一变动的部分
```

实测（demo 第 3 节，结构参数取自 Qwen3-8B 的公开配置：36 层 /
8 个 KV 头 / head_dim 128 / 约 8.2B 参数，bf16 即每值 2 字节）：

```text
ctx 4096 × 并发 1：权重 15.2737 GiB + KV 576.00 MiB + 适配器 48 KiB = 15.8362 GiB
ctx 4096 × 并发 4：权重 15.2737 GiB + KV 2304.00 MiB + 适配器 48 KiB = 17.5237 GiB

每 token 每序列的 KV 缓存：147456 字节 = 144 KiB
算式：2 × 36 层 × 8 个 KV 头 × head_dim 128 × 2 字节（bf16）= 147456
并发 1 → 4 会在权重之外多要 1.69 GiB，而它不提升任何质量。
4-bit 权重 3.8184 GiB（下界标记：True）
```

三个细节值得单独说：

1. **算式里的第一个 2 是 K 与 V**。漏掉它会让估算整整少一半，而"少一半"
   在显存估算里意味着一次 OOM，不是一次警告；
2. **并发是最贵也最容易被忘掉的一个开关**。Ollama 官方 FAQ 把它写在
   `OLLAMA_NUM_PARALLEL` 的说明里（默认 1，并发会把上下文与内存分配按
   并发数放大）。本课把它做成了一个可复算的函数，而不是留在文档里当提醒；
3. **4-bit 给的是下界**（不含量化常数、未量化层与张量对齐），
   因此报告里有一个 `weights_is_lower_bound` 字段把它标出来——
   **"下界"与"以为精确"是两件事**。

顺带说清一处容易混淆的地方：`/serving/targets` 返回的 `spec.base_model` 是
**训练侧基座**（版本三元组的第一项），而显存算术用的结构参数来自
`ARCH_QWEN3_8B`。两者不是同一个东西，因此响应里显式带一句
`architecture_note` 说明用了哪份结构——**一个不说清来源的显存数字，
比没有数字更危险**。

### 2.5 一处被删掉的恒假分支

第一版的 `chat` 里有一段"防御性代码"：

```python
if record.shadow:
    # 走专属的请求不再另打影子
    record.shadow = False
```

它的意图是好的，但它是**恒为假**的：`_decide` 里走到专属分支时返回的
`shadow` 永远是 `False`（"打影子"只在云端分支上判定）。于是这段代码
一次也不会执行，却让人以为存在"走了专属但被标成影子"这种情形需要兜底。

按 day059 记过的那笔账——**一条永远为真的断言不是保护，而是噪声**——
它被删掉了，同时留下一条把不变式钉住的测试：

```python
def test_shadow_is_never_set_on_a_dedicated_route():
    ...
    assert all(item.route == ROUTE_DEDICATED for item in switcher.switch_log)
    assert switcher.shadow_calls == 0
    assert not any(item.shadow for item in switcher.switch_log)
```

**删掉代码的同时留下"为什么可以删"的证据**，这样将来谁改了 `_decide`
的返回约定，测试会立刻变红。

## 第三章：部署绑定 —— 三处版本必须指向同一份产物

### 3.1 五条检查与它们挡住的故障

实测（demo 第 2 节）：

```text
  五条一致性检查挡住的故障：
    [阻塞] serving_name         部署脚本改错了目标服务（改了 A 却以为改了 B）
    [阻塞] base_model           基座与适配器不匹配：能挂上，但输出与训练行为无关
    [阻塞] adapter_hash         线上加载的是上一份适配器（adapter_dir 指到了旧目录）
    [阻塞] kind_shape           形态与自述矛盾：合并形态却自述挂了适配器
    [告警] registry_head        绑定版本不是注册表 head：有人提升了新版本却没部署（或反过来）
```

四条阻塞项排在一起读，会发现它们有一个共同结构：
**每一条都把"一个文件里的声明"与"另一个地方的自述"对上**。

```text
serving_name    配置里的服务名        ↔ 端点自述的 id
base_model      部署单元声明的基座     ↔ 端点自述的基座
adapter_hash    版本三元组的内容哈希   ↔ 端点自述的适配器短哈希
kind_shape      形态声明               ↔ 端点自述里有没有适配器
```

第四项（`kind_shape`）检的不是"值相不相等"，而是**形态与证据是否自洽**：
合并形态不该自述适配器（自述了就说明端点加载的其实是别的目录），
适配器形态则必须自述。

### 3.2 为什么"不是 head"不阻塞

`registry_head` 是五条里唯一的非阻塞项，理由是具体而非宽容：

> **灰度发布的本质就是"部署的不是 head"**——先把新版本部署上去，
> 再逐步切流量；或者说先给 5% 流量试跑，跑稳了才提升阶段。

把它设成阻塞会发生什么？团队为了过校验会**先去提升阶段**，于是"提升"
变成一个为了过门禁而做的动作，而不是一个基于证据的决定。这比不做校验更糟。

它与 day059 的两个布尔开关（`require_traceability` / `require_artifacts`）
的差别在于：那里是"要不要检查"，这里是"要不要强制"——两个不同的开关。

### 3.3 `passed` 与 `consistent` 是两个结论

```text
端点自述与记录一致              passed=True  consistent=True  阻塞失败=无
线上挂的是上一份适配器            passed=False consistent=False 阻塞失败=['adapter_hash']
绑定版本不是注册表 head         passed=True  consistent=False 阻塞失败=无
严格模式：必须部署 head         passed=False consistent=False 阻塞失败=['registry_head']
```

第三行是关键：**`passed=true` 而 `consistent=false` 是灰度期间最正常的状态**。
把这两个布尔量合成一个，就再也表达不出"我放行了，但我知道它不是 head"。

这与 day059 把门禁结果分成三类（阻塞失败 / 告警 / 跳过）是同一种思路：
**一个布尔量只能表达"能不能继续"，表达不了"我为什么继续"。**

### 3.4 缺自述时：绝对判定那一侧

端点没自述基座或适配器哈希时，结论是**不一致**，而不是"跳过"：

```text
"端点没有自述适配器哈希：这是唯一能证明「线上跑的是哪一份」的证据，
 缺了它就只能相信部署脚本"
```

这与 day059 门禁的 `when_missing` 一列站在同一侧（缺证据不能发布）。
但本模块同时提供了一个开关 `require_self_report`，把它关掉之后：

```text
"策略关闭了自述要求：这是一次有意的关闭，不是「一致」（...）"  → 落进 warnings，不阻塞
```

**关闭一项检查不是通过**——这条在 day059 已经写过一次，今天在另一个子包里
被重新执行了一遍。

### 3.5 一处被删掉的冗余判定

第一版的 `bind_version` 里有第三个前置条件：

```python
if spec.kind == KIND_ADAPTER and not version.adapter_sha256.strip():
    raise ServingError("v... 没有适配器哈希，无法绑定到 adapter 形态的部署单元")
```

它同样是**不可达**的：`VersionTriple` 已经在入口保证 `adapter_sha256` 非空
（长度下限 16 位十六进制）。再判一次就是一条恒为真的检查。

删掉之后，那段 docstring 里留下了一句话说明为什么可以删，以及
**哪条路径由谁守**：`ServingBinding.__post_init__` 里那道判定守的是
`from_dict` 这条路径（从 JSON 还原出来的记录可能没有哈希）。
**同一件事在不同入口各守一次是合理的，在同一个入口守两次不是。**

## 第四章：流量切换 —— 确定性分桶与单向降级

### 4.1 与 day033 的分工

day033 的 `ModelRouter` 与今天的 `ModelSwitcher` 都在"选一个模型"，
但它们选的是**两个不同的东西**：

| | `ModelRouter`（day033） | `ModelSwitcher`（今天） |
|---|---|---|
| 选什么 | **候选**：同一个任务交给哪个模型 | **流量**：这一批请求里哪些走新模型 |
| 判据 | 任务复杂度 vs 模型能力 | 部署阶段（灰度 5% → 50% → 100%） |
| 目标是 | 省钱（别用大炮打蚊子） | **换模型**：让新模型逐步接管生产 |
| 失败时 | 沿降级链换更强的模型 | 回落到**已验证的旧路径**（云端） |
| 生命周期 | 长期存在 | **过渡态**：切完 100% 就该被删掉 |

最后一行是本类唯一的"短命"设计目标：`ModelSwitcher` 是**灰度期间的
基础设施**，它的终点是 `dedicated_ratio=1.0` 之后再被摘掉。
因此 `route_table()` 里专门有一行提醒："永远留在 100% 的切换器是一层
没有收益的间接层"。

### 4.2 分桶为什么用哈希

```python
bucket = sha256(f"{salt}\0{text}").digest()[:4] / 2**32    # 落在 [0, 1)
```

三条理由，一条代价。理由：

1. **同一个 prompt 永远去同一个模型**。用户重复问同一个问题时，
   两次得到的不会一会儿来自云端、一会儿来自专属——**线上体验的抖动
   本身就是一种事故**；
2. **可复现**。测试与 demo 里没有随机数，"这次分流到了哪些 prompt"
   可以逐条复现，也可以人工指定"就这一个 prompt 走专属"来复现线上问题；
3. 与 day058 的 `run_id`、day059 的 `tracking.run_id_for` 同一条纪律：
   **确定性让"这个数字是哪来的"可以被回答**。

代价必须说清楚，而且它被写进了 `route_table()` 的 `cost` 一列：

> **哈希分桶不是随机分流。** `dedicated_ratio=0.05` 的含义是"哈希落在
> 前 5% 的**那些 prompt**"，而不是"随机 5% 的请求"。同一句话被问一万次，
> 它要么全在专属侧、要么全在云端侧。

这也是本课**明确排除**的用法之一：不能把它当 A/B 实验平台，
因为两侧的用户构成不可比。要做统计意义上的 A/B，必须引入随机数——
本课程刻意不引（它会让每天的实验结果不可复现）。

demo 第 7 节把这条限制做成了可执行的证据：**先用 `split_summary` 算一遍，
再真跑一遍**，两个数字必须相同：

```text
  ① 影子 ratio=0.0   shadow=0.05  200 个不同问题 → 专属服务 0    影子 16   已切完 False
       先算一遍会分走 0 条（不调用任何模型）；再跑一遍结果相同：True
  ② 小流量 ratio=0.05  shadow=0.0   200 个不同问题 → 专属服务 11   影子 0    已切完 False
       先算一遍会分走 11 条（不调用任何模型）；再跑一遍结果相同：True
  ③ 半量 ratio=0.5   shadow=0.0   200 个不同问题 → 专属服务 90   影子 0    已切完 False
       先算一遍会分走 90 条（不调用任何模型）；再跑一遍结果相同：True
  ④ 全量 ratio=1.0   shadow=0.0   200 个不同问题 → 专属服务 200  影子 0    已切完 True
       先算一遍会分走 200 条（不调用任何模型）；再跑一遍结果相同：True
```

注意 ② 那一行：设定 5%，200 条里实际分走 **11** 条（5.5%）。
换一批 prompt 会得到另一个数（可能 8、可能 13）——它围绕 5% 波动，
但**同一个批次的答案永远不变**。这就是"稳定分桶"与"随机分流"在数字上的
可见差别。

### 4.3 降级只向一个方向（再说一次，因为它最反直觉）

实测（demo 第 4 节）：

```text
fail_open=True ：第 1 次 [云端] 参考答案
                第 2 次 [专属] 参考答案
                影子调用 0／降级次数 1
                服务计数：专属 1 / 云端 1（合计 = 请求数 2）
                ↑ 第 1 次其实是云端兜住的：**fail_open 会让「一切正常」变成一个假象**

fail_open=False：专属模型调用失败且策略为 fail_open=False（严格模式）：dedicated 暂时不可用
                云端被调用 0 次（严格模式不兜底）
```

两行合起来读才完整：`fail_open=True` 时**从成功率上看不出任何异常**
（请求全部成功），只有 `fallback_count=1` 这一行暴露了真相。因此
`describe()` 必须同时暴露两者：

> 只看成功率会得出"专属模型很稳"的结论，而它其实一次都没成功过。

`fail_open=False`（严格模式）的存在理由也在这里：**切换之前用它测一次
真实成功率**。缺省打开是为了可用性，严格模式是为了一次诚实的测量。

### 4.4 影子流量：先看再切

`shadow_ratio` 决定的请求会**同时调用专属模型，但只返回云端结果**：

```text
影子模式返回：[云端] 参考答案
影子调用 1 次（付两次成本），用户看到的仍是云端答案
```

它是灰度之前的一步：在真实请求上测专属模型的表现，而用户完全不受影响。
两处刻意的设计：

1. **影子比率与灰度比率是两个独立的数字**，不是"影子是灰度的一部分"。
   影子请求的服务结果来自云端、灰度请求的来自专属——它们的**用户可见
   行为完全不同**，混成一个数字就再也说不清"现在有多少用户已经真正在
   用专属模型了"；
2. **影子失败必须被吞掉**（`_run_shadow` 里 `except Exception`）。
   影子路径的唯一职责是提前发现问题，**一次影子失败导致用户请求 500，
   是把观测手段变成了故障源**。失败次数由 `shadow_failures` 单独暴露。

### 4.5 流式：已产出片段之后不再降级

这是与 day033 `ModelRouter.stream` 的一处**刻意差异**。那里在异常时直接
换下一个模型重新流式，代价是调用方可能已经收到前 20 个字——于是最终输出
变成"两个模型的两段话拼在一起"，而**它不会报错**。切换器的语义更严格：

```python
if produced or not self.policy.fail_open:
    raise ServingError(
        "专属模型流式失败（已产出片段，不再降级："
        "拼接两段回答不会报错，只会答错）：..."
    )
```

```text
首片未产出即失败     → 沿单向降级换云端（用户什么都没看到，切换是干净的）
已产出片段后失败     → 抛明确错误（宁可报错，也不产出一段看不出问题的拼接文本）
```

### 4.6 两处真实的计数缺陷

**第一处：影子请求在计数上不属于任何一侧。**

第一版的两个属性是这么写的：

```python
sum(1 for item in self.switch_log
    if item.served_by == self.cloud_name and not item.shadow)      # 错
```

于是影子请求既不算"专属服务"也不算"云端服务"，两侧之和对不上请求总数。
而影子请求恰恰是**最需要被数清楚**的一类（它付了两次钱）。
修法是把 `not item.shadow` 从 `cloud_served` 上移除，并留下一条断言：

```python
def test_served_counters_add_up_to_the_finished_requests():
    ...
    assert switcher.dedicated_served + switcher.cloud_served == len(switcher.switch_log)
```

**第二处：视觉路径漏了影子调用，却把记录标成了"影子"。**

`chat_vision` 第一版从 `_decide` 拿到 `shadow=True` 就直接记进 `switch_log`，
但**根本没有执行那次影子调用**。于是 `shadow_calls` 虚高——而它回答的问题
是"有多少请求付了两次推理成本"。修法是在视觉路径上补齐影子调用，
并在能力不足时（专属模型不支持视觉）**把标记改回 False**：

```python
if shadow and dedicated_ok:
    self._run_shadow(messages, record, lambda leaf: call(leaf))
elif shadow:
    record.shadow = False   # 影子调用根本没有发生 → 不能计入
    record.reason = f"{record.reason}；专属模型不支持视觉，本次没有打影子"
```

两处缺陷的共同特征是：**它们不会报错，只会让一个数字悄悄地不对**。
而这两个数字（"有多少请求真的在用专属模型"与"付了多少次额外推理成本"）
恰好是灰度期间唯一的决策依据。

同一个文件里还删掉了另外两处恒真的条件（`if record.shadow: ... = False`
与 `if shadow and not self.policy.is_fully_cut_over`）——理由见 2.5 节。

## 第五章：上线验证 —— 两个推理臂放在同一批用例上

### 5.1 五条检查

day053 已经有一套领域评估（18 条用例、六分量合取判定），day059 又把它接进了
发布门禁。今天的问题不是"再评估一次"，而是回答一个**部署特有的**问题：

> 同一批真实问题上，专属模型与现在正在服务的云端模型，**差在哪里**？

```text
cases       验证用例数必须大于 0                    阻塞
pass_rate   专属合格率 >= 下限                      阻塞
regression  相对云端不出现超出容忍的退步            阻塞
errors      专属侧不允许出现调用失败                阻塞（可由策略关闭）
latency     专属/云端延迟中位数倍数 <= 上限          **缺省不检查**
```

第三条的**方向**与 day059 的门禁一律：`delta = 专属 − 云端`，
**退步是负值**，因此判定式是 `delta >= -max_regression`。同样留下了
一条方向回归断言（`test_a_positive_delta_passes_the_regression_check`），
理由与 day059 完全一样：方向写反的表现是"所有候选都被拦下"，
而它看起来很像"门槛很严格"。

### 5.2 延迟为什么缺省不检查

```text
"多慢算慢"取决于部署形态：本地 CPU 推理与 A10G 上跑的差异是十倍量级，
给一个全局缺省只会让它被无脑放宽——然后被关掉。
```

把它设成 `None`（不检查）让调用方**显式给出**倍数，这与 day033 的
`compare_runs` 坚持 "`mode` 必须显式给出" 是同一条纪律：
**一个全局缺省会被忘记，而忘记的后果是结论反向。**

报告里这一项会明确写成"未检查（策略未给出倍数）"，而不是留空、
也不是记成"通过"——**"没测"与"没达标"必须分开报**（`skipped_checks`
与 `warnings` 两个属性）。

### 5.3 实测：逐项检查

同一批 4 条用例，专属侧有一条退步（demo 第 5 节）：

```text
上线验证 不通过 | 4 条用例 | 云端 1.0000 → 专属 0.7500（-0.2500）| 延迟 2.333× | 阻塞失败 ['regression']
跳过的检查 ['latency']（延迟中位数 云端 180ms / 专属 420ms = 2.333×）
逐项：
  [通过/阻塞] cases        实际 4 / 阈值 > 0
  [通过/阻塞] pass_rate    实际 0.75 / 阈值 0.5
  [不通过/阻塞] regression   实际 -0.25 / 阈值 >= -0.0
  [通过/阻塞] errors       实际 0 / 阈值 0
  [不通过/告警] latency      实际 None / 阈值 未给出倍数
```

显式要求延迟倍数之后，同一份数据得到两个阻塞项：

```text
上线验证 不通过 | 4 条用例 | 云端 1.0000 → 专属 0.7500（-0.2500）| 延迟 2.333× | 阻塞失败 ['regression', 'latency']
```

再让专属侧有一条调用失败：

```text
上线验证 不通过 | 4 条用例 | 云端 1.0000 → 专属 0.5000（-0.5000）| 延迟 1.000× | 阻塞失败 ['regression', 'errors']
失败用例：[('warmup', 'TimeoutError: 专属服务在 warmup 用例上超时')]
```

**"调用失败"与"答得不对"必须分开计数**：前者是部署问题（进程没起来、
显存不够、超时），后者是模型问题（训得不够、数据不对）。
把它们合成一个"不通过"，运维能做的唯一动作是"重跑一次看日志"。

### 5.4 一个真实的浮点缺陷：1e-9 容差

单测里出现了这样一条断言失败：

```text
assert report.delta == -0.05
E   assert -0.050000000000000044 == -0.05
```

`19/20 - 20/20` 在 IEEE 754 双精度下的值是 `-0.050000000000000044`，
它**比阈值 `-0.05` 小**。于是判定式 `delta >= -0.05` 得到 `False`：

> "退步 5 个百分点、容忍 5 个百分点"被判成失败。

更麻烦的是这个结论**随分母翻转**：同样的 5 个百分点，40 条用例里差 2 条
得到的是 `-0.049999999999999996`（判通过），20 条用例里差 1 条是上面那个值
（判不通过）。**同一件事因为用例数不同得到相反结论**，这是最坏的一类不稳定。

修法是给比率比较加一个显式容差：

```python
RATE_EPSILON = 1e-9   # 远小于 18 条评估集的最小分辨率 1/18 ≈ 0.0556
```

并留下两条把边界钉死的断言：一条确认 `delta < -0.05` **却仍然通过**
（先证明这条测试测的是真东西），另一条确认多退一条用例
（`-0.10`）**仍然被拦下**——**容差不是放宽门槛**。

> **可以带走的判断**：只要阈值是"十进制的"（0.05 / 0.5 / 0.9），
> 而参与比较的量是"两个整数相除"，就必须想一次浮点边界。
> 这类缺陷不会抛异常，只会让某个边界情形偶尔给出相反结论。

### 5.5 判定用片段，不用 LLM 打分

`must_contain` 是确定性判定：回复里必须出现全部片段（大小写不敏感、
顺序不限）。理由与 day026 的 LLM-as-a-judge 形成一个对照：

```text
LLM-as-a-judge（day026）  评估**质量**：回复好不好、有没有帮上忙
片段判定（今天）          回答**是否退化**：这次切换有没有让行为变差
```

后者的方差必须接近 0，否则"今天比昨天差 0.3 分"这句话永远给不出稳定结论。
片段为空的用例会**永远通过**（它退化成一条"只测连通性"的探针），
这是有意的用法而不是漏洞。

同时也必须承认它的局限（写进了 `SERVING_LIMITATIONS` 第 3 条）：

> 它只能发现"该出现的东西没出现"，**发现不了"多说了不该说的"**——
> 事实正确性与安全性仍要走 day031 的红队与 day044 的审核。

## 第六章：成本 —— 固定成本与可变成本

### 6.1 两个不同的成本模型

"专属模型部署到本地能省钱"是一句**没有主语就不成立**的话。本模块要做的事
只有一件：把两侧写成各自的式子，然后让数字说话。

```text
云端 API   = 可变成本 × 请求数        不调用就不花钱，调用越多花越多
自建推理   = 固定成本 × 开机时长      开机就在花钱，与调用量无关（吞吐上限之内）
```

### 6.2 实测：四个请求量档

价格取自公开按需时价（AWS g5.xlarge $1.006/h），吞吐按缺省占位值
250 token/s，每次请求 1500 入 + 500 出 token（demo 第 6 节）：

| 月度请求量 | 云端 | 自建 | 机器数 | 利用率 | 结论 |
|-----------|------|------|--------|--------|------|
| 10,000 | $5.25 | $734.38 | 1 | 3.04% | 云端更省 |
| 100,000 | $52.50 | $734.38 | 1 | 30.44% | 云端更省 |
| 1,000,000 | $525.00 | $2,937.52 | 4 | 76.10% | 云端更省 |
| 10,000,000 | $5,250.00 | $22,765.78 | 31 | 98.20% | 云端更省 |

四档全是"云端更省"，而且**差距随请求量先扩大再收窄**：
10000 请求时差 140 倍（一台机器的钱被 3% 的利用率摊），
1000 万请求时差 4.3 倍（利用率已到 98.2%）。

这张表最重要的不是最后一行，而是**第一行**：

> 0 请求时云端花 $0，自建照付 $734.38。

### 6.3 四个派生数字

结论字段 `cheaper_side` 只是副产品。真正该看的是另外四个数：

```text
100000 请求这一个月的四项数字：
  用掉的算力      222.2222 GPU·h
  为之付费的时长  730.0000 GPU·h（1 台 × 730h）
  实际利用率      30.44%
  盈亏平衡调用量  1398819 请求/月
```

它们回答的是四个不同的问题：

| 数字 | 回答的问题 |
|------|-----------|
| `required_gpu_hours` | 处理这批请求**用掉**了多少算力 |
| `deployed_gpu_hours` | 你**为之付费**了多少时长（`machines × 730h`） |
| `utilization_actual` | 这台机器是"在工作"还是"在待机" |
| `breakeven_requests` | 调用量要到多少，自建才真正更省 |

第二行的 `machines` 是一个容易被跳过的步骤：**用掉的算力时长超过一台机器
能提供的时长时，就得开第二台**——而第二台同样按月付费。
不做这一步会算出"用一台机器的时价承接十台机器的负载"这种**算得出来
但部署不出来**的方案（1000 万请求那一行需要 31 台）。

### 6.4 空转的 GPU 是最贵的

利用率那一列是这张表的灵魂。`utilization_actual = required / deployed`，
而自建成本的式子**不含利用率的分母**——它只乘时长：

```text
cost = usd_per_hour × deployed_hours
```

于是利用率减半，单位成本正好翻倍。这不是一个比喻，它有一个直接的算术后果：
**把利用率从 30% 提到 60%，等于把单位成本砍半**，而这件事不需要换模型、
不需要改代码——只需要把更多请求导进来（或者把机器关掉几台）。

这也是本课回答"值不值"的方式：不是一个"是/否"，而是
**"在什么调用量、什么吞吐、什么利用率下"**。

### 6.5 一条互相校验的恒等式

报告里最容易出错的几个乘数是：机器数、月时长、时价、每请求 token。
把盈亏平衡点的定义代进单位成本，可以证明：

```text
breakeven_requests / 当前请求量  ==  自建单位成本 / 云端单位成本
```

实测 100000 请求/月时两者都是 **13.99**：

```text
自建 $0.0036719/1K ÷ 云端 $0.0002625/1K = 13.99
1398819 ÷ 100000                        = 13.99
```

于是"盈亏平衡点是我现在请求量的 14 倍"与"我的单位成本是云端的 14 倍"
是同一句话的两种说法。**两个数字互相校验，任何一个乘数算错都会立刻暴露**——
这条断言被写进了测试（`test_breakeven_and_unit_cost_ratio_are_the_same_number`）。

### 6.6 价格是外部事实：只有一个出处

价格数字集中放在两个常量里（`GPU_HOURLY_USD` / `CLOUD_PRICING`），
出处写进模块 docstring 与 `price_book()` 的 `note` 一列：

```text
[gpu  ] aws-g4dn-xlarge-t4       0.526    USD/GPU·h
[gpu  ] aws-g5-xlarge-a10g       1.006    USD/GPU·h
[gpu  ] gcp-t4-gpu-only          0.35     USD/GPU·h
[gpu  ] lambda-a10               1.29     USD/GPU·h
[gpu  ] runpod-pod-l4            0.49     USD/GPU·h
[cloud] gpt-4o                   0.0125   USD/1K tokens
[cloud] gpt-4o-mini              0.00075  USD/1K tokens
```

三处刻意的处理：

1. **未知机型键必须响亮**：`gpu_pricing("my-laptop")` 抛错并列出全部可选项。
   否则会用一个 0 元时价算出一份"自建完全免费"的报告；
2. **吞吐没有缺省值**（`GpuPricing.tokens_per_second` 是必填字段）。
   它取决于模型、量化、批大小与序列长度，公开资料给不出"你这套配置"的数字。
   本课配置里的 250 token/s 是**待替换的占位值**——本模块存在的意义就是
   强迫把它填成一个测出来的数；
3. **打印用合计值时四舍五入到 8 位**：`0.00015 + 0.0006` 的双精度结果是
   `0.0007499999999999999`，而**一个看起来像 bug 的数字会让人去查代码，
   而它其实是浮点加法的正常结果**。

### 7.1 四个端点

| 端点 | 方法 | 回答什么 |
|------|------|---------|
| `/serving/targets` | GET | 三种形态、显存分解、流量策略、五条检查、价格表、**不能做什么** |
| `/serving/binding/verify` | POST | 三处版本是不是同一份产物 |
| `/serving/verify` | POST | 同一批用例上两个推理臂的对比 |
| `/serving/cost/compare` | POST | 两侧成本与四个派生数字 |

实测（demo 第 8 节）：

```text
GET  /serving/targets          → 形态 3 种 / 流量项 4 条 / 上线检查 5 条 / 绑定检查 5 条 / 价格 7 行
     显存 KV 缓存 576.0 MiB / 权重 15.2737 GiB
     形态建议 merged（与配置一致：False）
POST /serving/binding/verify   → passed=False 阻塞失败=['adapter_hash']
POST /serving/verify           → 上线验证 不通过 | 1 条用例 | 云端 1.0000 → 专属 1.0000（+0.0000）| 延迟 3.000× | 阻塞失败 ['latency']
POST /serving/cost/compare     → 100000 请求 | 云端 $52.5000 vs 自建 $734.3800 → 云端更省（省 $-681.8800）
```

四个端点全部**只读或纯计算**：不写磁盘、不联网、**不加载任何模型**、
不用随机数。与 day059 的取舍同源——**一个需要 GPU 的流程不该挂在一个
HTTP 请求上**；真正加载模型、量延迟、切流量由 `scripts/serving_demo.py`
与部署脚本承担。

`/serving/targets` 里有一处值得模仿的表达：`recommendation` 里带一个
`matches_configured` 字段。缺省配置是 `adapter` 形态，而"只有一个业务"
的建议是 `merged`——两者不一致。**把这个不一致显式打印出来**，
比让读者自己去比对两张表要诚实得多。

### 7.2 延迟是"请求里送来的观测值"

`/serving/verify` 需要两个推理臂的延迟，但端点不跑模型。做法是把延迟
做成**可注入的确定性时钟**：`run_verification` 会在每个用例的开始与结束
各调一次 `clock()`，因此一个按 `[0, l1, l1, l1+l2, ...]` 依次返回的时钟，
就能让报告里的延迟**精确等于**请求里送上来的毫秒数：

```python
def serving_clock(latencies_ms: list[float]) -> Callable[[], float]:
    values = [0.0]
    running = 0.0
    for value in latencies_ms:
        running += value / 1000.0
        values.extend([running, running])
    ...
```

这是"把不可复现的测量变成可注入的输入"这条纪律的第三次出现
（day059 的 dry-run 参考回调、day050 的参考模型、今天的确定性时钟）。
收益很具体：**延迟检查这条分支可以被逐位复现地测到，而不是只能跳过**。
实测 `100ms` 与 `300ms` 的观测值得到 `延迟 3.000×`。

### 7.3 错误码语言

| 情况 | 错误码 | 例子 |
|------|--------|------|
| **请求形状**不对 | 422 | `gpu_utilization: 1.5`、`requests: -1`、缺 `bound_version` |
| **业务规则**不允许 | 400 | 未知机型键、未知计价方案、版本不存在、产物不完整、基座不匹配、非法策略值 |

与 day050~day059 一致。"非法策略值一律 400（不是 422）"这一条同样在路由层
显式写出，因为 Pydantic 的 `ge`/`le` 很容易顺手把业务规则也吃掉，
而**两份会漂移的规则比一份好规则更糟**。

还有一种情况**既不是 400 也不是 422**：缺数据。用例缺回复、被标记为
调用失败的用例，都走**正常报告路径**——缺数据是结论，不是错误。
只有"调用方忘了填 `case_id` 之外的东西"（例如空 `prompt`）才是 400。

### 7.4 配置项（16 个，分四类）

```python
serving_dir: str = "outputs/serving"                    # 部署记录落盘目录
serving_name: str = "smart-research-qwen3-8b"           # 部署单元名（须与 /v1/models 一致）
serving_kind: str = "adapter"                           # 部署形态
serving_dedicated_ratio: float = 0.0                    # 专属模型直接服务的流量比例
serving_shadow_ratio: float = 0.0                       # 影子流量比例
serving_fail_open: bool = True                          # 专属失败是否回落到云端
serving_min_pass_rate: float = 0.5                      # 上线验证：合格率下限
serving_max_regression: float = 0.0                     # 上线验证：允许的退步
serving_max_latency_ratio: float | None = None          # 上线验证：延迟倍数（None = 不检查）
serving_gpu_key: str = "aws-g5-xlarge-a10g"             # 成本：机型键
serving_gpu_tokens_per_second: float = 250.0            # 成本：实测吞吐（占位值）
serving_gpu_utilization: float = 1.0                    # 成本：GPU 利用率
serving_cloud_pricing_key: str = "gpt-4o-mini"          # 成本：云端计价方案
serving_input_tokens_per_request: int = 1500            # 成本：每请求输入 token
serving_output_tokens_per_request: int = 500            # 成本：每请求输出 token
serving_monthly_requests: int = 100000                  # 成本：月度请求量
```

分四类是因为它们的**可调性完全不同**，混在一起会被误调：

```text
部署档案（dir / name / kind）：改一次要重新部署，属于变更管理
流量策略（ratio / shadow / fail_open）：**每天可调**，是灰度发布的操作面
上线验证（min_pass_rate / max_regression / max_latency_ratio）：切流量之前问一次
成本参数（gpu_key / tokens_per_second / ...）：**唯一必须实测的一组**
```

1. `test_shadow_is_never_set_on_a_dedicated_route` —— 2.5 节那个恒假分支的
   替代品。**删掉代码的同时留下"为什么可以删"的证据**；
2. `test_served_counters_add_up_to_the_finished_requests` —— 4.6 节那个计数

3. `test_a_regression_exactly_at_the_tolerance_is_accepted` —— 5.4 节那个浮点

   再断言判定通过；配套的 `test_just_over_the_tolerance_is_still_blocked`
   确认容差不是放宽门槛；
4. `test_breakeven_and_unit_cost_ratio_are_the_same_number` —— 把
   `盈亏平衡/请求量` 与 `单位成本之比` 绑在一起：**一个能解释另一个的数字，
   才值得被相信**。

为覆盖率做过的四处**设计调整**（它们各有不同的教训）：

1. **删掉三处恒真/恒假的分支**（2.5 / 3.5 / 4.8 节），并用测试把不变式钉住——
   而不是给它们标 `pragma: no cover`。**覆盖率报告的价值不只是"补测试"，
   它还会告诉你哪些代码是多余的**；
2. **修掉两处计数缺陷后补上回归断言**（4.6 节）——而不是只改代码。
   这两个数字是灰度期间唯一的决策依据；
3. **给浮点边界加显式容差并留下两条边界断言**（5.4 节）——
   一条证明"恰好等于容忍度"通过，一条证明"超过一条用例"仍然被拦；
4. **把延迟做成可注入的时钟**（7.2 节）——否则"延迟检查"这条分支只能
   靠"跳过"来通过，那等于没有测。

## 第九章：今日总结 —— 三条可以带走的判断

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|---------|
| 形态决定必填字段 | 声明了形态却没给路径的部署不会报错，只会安静地服务别的东西 | `spec.KIND_REQUIRED_FIELDS` |
| 显存三块分开列 | 它们的决定因素不同（量化 / 上下文与并发 / 挂哪个业务） | `spec.memory_breakdown` |
| KV 算式里的第一个 2 | 漏掉它会让估算整整少一半，而少一半意味着一次 OOM | `ModelArchitecture.kv_bytes_per_token` |
| 并发是最贵的开关 | 并发 1 → 4 多要 1.69 GiB，且不提升任何质量 | `memory_breakdown` 的 `max_parallel` |
| 4-bit 权重是下界 | "下界"与"以为精确"是两件事 | `weights_is_lower_bound` |
| 五条绑定检查 | 每一条都把"一个文件里的声明"与"另一个地方的自述"对上 | `binding.binding_table` |
| `serving_name` 也要比 | 多副本里"某一个 Pod 还是旧配置"是最难定位的一种 | `binding.verify_binding` |
| 形态与自述要自洽 | 合并形态自述适配器 = 端点加载的其实是别的目录 | `CHECK_KIND_SHAPE` |
| "不是 head"不阻塞 | 把灰度逼成"先提升阶段再过校验"比不校验更糟 | `BindingPolicy.require_registry_head` |
| `passed` 与 `consistent` 分开 | 一个布尔量表达不了"我放行了，但我知道它不是 head" | `BindingVerification` |
| 缺自述 = 不一致 | 缺证据不能算一致（绝对判定那一侧） | `_self_report_check` |
| 关掉检查不是通过 | "有意的关闭"必须落进 warnings 被看见 | `BindingPolicy.require_self_report` |
| 分桶用哈希不用随机数 | "同一句话被问一万次也只会走同一侧"——体验不抖动、可复现 | `switch.bucket_of` |
| 但要写出它的代价 | 它不是随机分流，因此不能当 A/B 平台 | `route_table` 的 `cost` 列 |
| 降级只向一个方向 | 反向降级 = 云端故障时把流量交给未验证模型 | `ModelSwitcher.chat` |
| `fallback_count` 必须暴露 | fail_open 会让"一切正常"变成一个假象 | `describe()` |
| 影子失败必须被吞掉 | 观测手段不能变成故障源 | `_run_shadow` |
| 流式已产出片段后不降级 | 拼接两段回答不会报错，只会答错 | `ModelSwitcher.stream` |
| 计数必须能加起来 | 影子请求不属于任何一侧时，决策依据就悄悄变小了 | `cloud_served` |
| 影子没发生就不能计数 | `shadow_calls` 回答的是"付了几次额外成本" | `chat_vision` |
| 延迟缺省不检查 | "多慢算慢"取决于部署形态，全局缺省只会被无脑放宽 | `VerifyPolicy.max_latency_ratio` |
| 比率比较要带容差 | `19/20 - 20/20` 比 `-0.05` 小，结论还会随分母翻转 | `RATE_EPSILON` |
| 判定用片段不用打分 | 要回答的是"有没有退化"，方差必须接近 0 | `verify.judge` |
| 固定成本 vs 可变成本 | "自建更便宜"缺了主语：调用量、吞吐、利用率 | `cost.compare_costs` |
| 机器数要上取整 | 不做这一步会算出"算得出来但部署不出来"的方案 | `compare_costs` 的 `machines` |
| 盈亏平衡与单位成本互为校验 | 一个能解释另一个的数字才值得被相信 | `breakeven_requests` |
| 价格只有一个出处 | "这个 $1.006 是哪来的"不该变成一次考古 | `GPU_HOURLY_USD` / `CLOUD_PRICING` |
| 吞吐没有缺省值 | 它取决于模型、量化、批大小与序列长度 | `GpuPricing.tokens_per_second` |
| 延迟做成可注入时钟 | 否则这条分支只能靠"跳过"通过，等于没测 | `serving_clock` |
| 删掉恒真的分支 | 一条永远为真的检查不是保护，而是噪声 | 2.5 / 3.5 / 4.8 节 |

M5 阶段到此结束（day048~day060 共 13 个日历日，其中 day049 / day056 是
两个缓冲复习日）。回头看这十三天留下的东西：

```text

day049  中场缓冲：把账算清（9 步更新 / 2500 token）
day050  SFT：模板渲染 + label mask + 步数超参核算
day051  LoRA/QLoRA：参数量与显存算术、NF4 量化
day052  PEFT 实践：适配器生命周期、多卡分片、合并门禁
day053  微调模型评估：领域评估集 + 六分量合取判定
day054  RLHF/DPO 原理：偏好数据与对齐目标
day055  DPO 实践：偏好构造 + TRL 配置镜像 + 损失自检
day056  M5 中场缓冲：六天地图与三本账
day057  领域数据：六阶段流水线 + 两级去重 + 可复现版本链
```
