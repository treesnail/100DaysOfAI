## 第一章：为什么用 FastMCP，而不是手写 JSON-RPC

### 1.1 手写协议服务器的隐性成本

MCP 的线上格式确实"只是"JSON-RPC 2.0：每条消息一个 JSON 对象，带 `jsonrpc`/`id`/`method`/`params` 字段。理论上你可以起一个循环，`stdin` 读一行、`json.loads`、分发到处理函数、`json.dumps` 写回去。demo 五十行就能跑。

但一个**能给别人用**的 Server 远不止消息收发。它至少要处理：

- **握手状态机**：客户端必须先 `initialize`，Server 校验协议版本、记下客户端能力，回自己的能力声明；客户端再发 `notifications/initialized` 确认，之后才允许正常请求。顺序错了怎么办？没握手就 `tools/call` 怎么办？
- **协议版本协商**：客户端说"我会 2025-06-18 版"，服务端说"我会 2025-06-18 和 2024-11-05 版"，双方要收敛到一个共同版本，谈不拢要干净地拒绝。
- **Schema 推导与校验**：每个工具的入参是 JSON Schema。手写意味着你为每个工具维护一份 schema，并保证它和函数签名永远同步——改一个参数忘改 schema，客户端传参就会莫名其妙地失败。
- **错误映射**：业务代码抛异常时，要按 JSON-RPC 规范包装成带 `code`/`message` 的错误响应，不能让异常 traceback 直接泄到线上，更不能让进程直接挂掉。
- **传输适配**：stdio 和 SSE 的读写循环、帧边界、并发模型完全不同，业务逻辑不该感知这些差异。

这些全是**协议工程**而非**业务逻辑**。每一家自己写一遍，既重复又容易在边界情况上翻车——这正是框架存在的意义。

### 1.2 FastMCP 的分层：装饰器是协议处理的语法糖

`mcp` 官方 SDK（1.29）提供了两层 API：

- 底层是 `mcp.server.lowlevel.Server`：你自己注册 `list_tools`/`call_tool` 等请求处理器，完全控制，也完全自理。
- 上层是 `FastMCP`：用装饰器声明能力，框架负责握手、schema 推导、错误包装、传输适配。

对照一下 FastMCP 把哪些事收走了：

| 协议职责 | 手写 JSON-RPC | FastMCP |
|----------|--------------|---------|
| initialize 握手与版本协商 | 自己实现状态机 | 框架内置 |
| 能力声明（capabilities） | 自己拼响应 JSON | 按注册的装饰器自动生成 |
| 工具入参 JSON Schema | 手工维护、易与签名漂移 | 从类型标注自动推导 |
| 业务异常 → 错误响应 | 自己 try/except 包装 | `ToolError` 自动转 `isError=true` |
| stdio / SSE 传输 | 各写一套 I/O 循环 | `app.run(transport=...)` 一行切换 |

我们的业务代码因此只剩"一个 Python 函数 + 一个装饰器"。**框架的价值不在于少打字，而在于把协议的正确性从"你的责任"变成"框架的责任"。**

### 1.3 为什么还要自己建 protocol.py

既然 FastMCP 全包了，为什么我们还在 [mcp_server/protocol.py](../源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py) 里用 pydantic 手写了一遍 JSON-RPC 消息和三类 Descriptor？

三个理由：

1. **学习锚点**。框架把协议藏起来是双刃剑——用久了会忘记线上跑的到底是什么。`protocol.py` 把协议的关键消息（请求、成功响应、错误响应）和三类能力描述符用 pydantic 显式建模，是项目内**可导入、可实例化、可测试**的协议规格文档。
2. **静态能力清单**。`full_server.py` 的 `capability_descriptors()` 用这些模型声明了 Server 的能力清单。它与运行时 `tools/list` 等接口返回的内容对应，可被文档生成、客户端预检消费，不必启动服务就能知道"这个 Server 有什么"。
3. **未来扩展点**。M2 后续如果要写自己的网关、代理或测试桩（day023 的协议测试会用到），这些模型就是现成的消息契约。

一句话：**框架负责运行时，protocol.py 负责认知与文档**。两者不矛盾。

### 1.4 包名为什么必须是 mcp_server

今天新建的包叫 `smart_research_agent.mcp_server`——注意，绝不能叫 `smart_research_agent.mcp`。如果叫 `mcp`，在项目根目录下运行时，Python 的模块解析可能把绝对导入 `from mcp.server.fastmcp import FastMCP` 解析到项目内部的 `mcp` 包上，遮蔽官方第三方包，出现极其诡异的导入错误。这是 Python 工程里经典的"命名遮蔽"陷阱：标准库和第三方包名是公共财产，业务包名必须避让。

## 第二章：Server 生命周期 —— initialize 握手与能力协商

### 2.1 生命周期的四个阶段

一个 MCP 会话不是"连上就能调"，它有明确的生命周期：

```text
┌──────────┐   initialize 请求     ┌──────────┐
│          │ ───────────────────▶  │          │
│  Client  │                       │  Server  │
│          │ ◀───────────────────  │          │
│          │   serverInfo +        │  校验协议版本
│          │   capabilities +      │  记录客户端能力
│          │   instructions        │  生成能力声明
└──────────┘                       └──────────┘
      │
      │ notifications/initialized（客户端确认：握手完成）
      ▼
═══════════ 正常交互阶段 ═══════════
  tools/list  tools/call
  resources/list  resources/read
  prompts/list  prompts/get
  （以及 ping、日志、进度通知等）
      │
      │ 连接关闭 / 进程退出
      ▼
   shutdown：stdio 下 stdin 关闭即结束；SSE 下 HTTP 会话终止
```

四个阶段各司其职：

1. **initialize（能力协商）**：客户端自报家门——协议版本、自己的能力（如 roots、sampling）、客户端实现名与版本。Server 回应自己的协议版本、`serverInfo`（名称/版本）、`capabilities`（我支持 tools/resources/prompts 中的哪些）、以及 `instructions`（给模型看的使用说明）。
2. **initialized（确认）**：客户端发一条通知，表示"我收到并接受了你的协商结果"。此后 Server 才开始接受正常请求。
3. **正常交互**：所有能力的列出、读取、调用都发生在这个阶段。
4. **shutdown**：MCP 没有定义专门的"再见"消息——**传输层的结束就是会话的结束**：stdio 下 stdin 关闭、SSE 下 HTTP 连接断开。这也解释了为什么 Server 必须能容忍客户端随时消失。

### 2.2 能力协商到底协商了什么

"握手"听起来像仪式，实际上交换了四类实打实的信息：

**（1）协议版本。** MCP 协议在演进（2024-11-05、2025-03-26、2025-06-18……），版本差异意味着消息结构差异。协商保证双方说同一种方言。客户端与服务端版本不一致时，服务端应尝试回退到双方都支持的版本，做不到就拒绝——**宁可拒连，不可误解析**。

**（2）能力声明（capabilities）。** Server 明确告诉客户端"我支持 tools、resources、prompts"。客户端据此决定可以发哪些方法——没声明 prompts 的 Server，客户端就不该发 `prompts/list`。这是**向后兼容的基石**：未来新增能力类型时，老客户端看到不认识的声明可以安全忽略，老服务端遇到不支持的方法返回标准错误码 `-32601 Method not found`。对比一下 Web 世界的同类设计：HTTP 的 `Accept`/`Content-Type` 协商、TLS 的密码套件协商，思想完全一致——**分布式系统的双方必须显式交换"我会什么"，而不是猜测对方会什么**。

**（3）实现信息（serverInfo / clientInfo）。** 名称与版本号，用于日志、调试与兼容性判断。我们的 Server 自报名为 `smart-research-agent`——客户端日志里出现连接问题时，这个名字就是定位线索。

**（4）instructions（使用说明）。** 这是 MCP 相对一般 RPC 框架的独特设计：一段给**模型**读的文本，描述这个 Server 是干什么的、能力怎么用。因为 MCP 的终极消费者是 LLM——客户端（如 Agent）会把 instructions 连同工具清单一起放进模型上下文，模型靠它决定"什么时候该调这个 Server 的工具"。**写 instructions 本质上是写一段给模型的产品文档。**

### 2.3 握手在代码里如何被验证

FastMCP 把握手收进了框架内部，但握手的结果是可观察的。我们的测试用内存会话验证它（[tests/test_full_server.py](../源码/smart-research-agent/tests/test_full_server.py)）：

```python
async def test_server_metadata(self):
    server = create_server()
    async with create_connected_server_and_client_session(server) as session:
        result = await session.initialize()
        assert result.serverInfo.name == SERVER_NAME
        assert result.instructions == SERVER_INSTRUCTIONS
```

`session.initialize()` 返回的就是 initialize 响应的完整内容。`create_connected_server_and_client_session` 是 mcp 官方提供的测试工具：它在**同一进程内**用内存流把客户端和服务器接起来，走完整的协议状态机，但不经过任何真实传输——测试既真实（协议逻辑全跑）又离线（零网络、零子进程），这正是 FIRST 原则在协议测试上的体现。

> 思考题：为什么 MCP 选择"客户端先 initialize、再发 initialized 通知"的两步握手，而不是一步完成？提示：想一想通知（notification）和请求（request）在 JSON-RPC 里的区别，以及"谁有权宣布协商结束"。

## 第三章：FastMCP 装配三类能力

### 3.1 工厂函数 create_server

完整代码见 [mcp_server/full_server.py](../源码/smart-research-agent/smart_research_agent/mcp_server/full_server.py)。骨架是：

```python
def create_server() -> FastMCP:
    """创建并装配完整的 FastMCP Server 实例."""
    app = FastMCP(name=SERVER_NAME, instructions=SERVER_INSTRUCTIONS)
    # ... 装饰器注册三类能力 ...
    return app
```

两个设计决策：

**（1）用工厂函数而不是模块级单例。** 如果 `app = FastMCP(...)` 写在模块顶层，import 即构建，测试之间共享同一个实例，注册状态互相污染。工厂函数让每个测试拿到全新实例——这是 day002 讲的 fixture 隔离思想在对象创建上的应用。

**（2）name 与 instructions 就是元数据配置。** `FastMCP(name=..., instructions=...)` 的两个参数分别对应第二章讲的 `serverInfo.name` 和握手响应里的 `instructions`。框架把它们自动接进握手流程，我们一行协议代码都不用写。

### 3.2 Resources：用 URI 模板暴露知识库

```python
@app.resource("research://knowledge/{doc_id}")
def read_knowledge(doc_id: str) -> str:
    """按 doc_id 读取本地知识库中的 Markdown 文档."""
    if not _SAFE_DOC_ID.match(doc_id):
        raise ValueError(f"非法的 doc_id: {doc_id!r}，仅允许小写字母、数字与下划线")
    path = _KNOWLEDGE_DIR / f"{doc_id}.md"
    if not path.is_file():
        raise ValueError(f"知识库文档不存在: {doc_id}")
    return path.read_text(encoding="utf-8")
```

读法有三个层次：

**URI 即地址。** MCP 的 Resource 借鉴了 REST 的思想：每份内容有一个 URI。我们自定义 `research://` scheme，`{doc_id}` 是路径参数——带参数的 URI 叫**资源模板（Resource Template）**，它会出现在客户端的 `resources/templates/list` 里，而不是 `resources/list`（后者只列无参数的静态资源）。客户端拿到模板后，把具体 doc_id 填进去再 `resources/read`。

**函数签名即参数协议。** FastMCP 把 URI 模板里的 `{doc_id}` 映射到同名函数参数。框架替你做了 URI 解析与参数绑定。

**安全校验是 Resource 实现的本职。** 注意 `_SAFE_DOC_ID = re.compile(r"^[a-z0-9_]+$")` 这道白名单。没有它，客户端传 `doc_id = "../../.env"`，路径拼接后就可能读到知识库目录之外的文件——这就是经典的**路径穿越（Path Traversal）**攻击。MCP 客户端背后是 LLM，LLM 生成的参数不可信程度不亚于用户表单输入，day015 学的注入防御思想在这里同样适用：**凡是进入文件系统路径的外部输入，必须白名单校验。**

知识库内容是两个示例 Markdown（[data/knowledge/rag_overview.md](../源码/smart-research-agent/smart_research_agent/mcp_server/data/knowledge/rag_overview.md) 与 [agent_architecture.md](../源码/smart-research-agent/smart_research_agent/mcp_server/data/knowledge/agent_architecture.md)），内容正是 M1 阶段学过的 RAG 与 Agent 架构——知识库服务于"智研"主题，示例数据也该言之有物。

### 3.3 Tools：包装而不是重写 CalculatorTool

```python
_calculator = CalculatorTool()

@app.tool()
def calculate(expression: str) -> str:
    """计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'."""
    try:
        result = _calculator.execute(expression=expression)
    except Exception as exc:  # 兜底：任何意外异常都不能让 Server 崩溃
        logger.exception("calculate 工具内部错误")
        raise ToolError(f"计算工具内部错误: {exc}") from exc
    if result.startswith("计算失败"):
        raise ToolError(result)
    return result
```

**（1）包装（Adapter），不是重写。** day004 的 `CalculatorTool` 已经实现了基于 AST 白名单的安全求值。MCP 工具函数只是它的适配层：把 MCP 调用翻译为 `execute()` 调用。业务逻辑只有一份，协议层薄薄地包在外面——和 day001 以来"关注点分离"的主线一脉相承。如果哪天计算器逻辑要修，只改 `tools/calculator.py` 一处。

**（2）docstring 与类型标注即 schema。** FastMCP 从签名推导 JSON Schema：`expression: str` 变成 `{"type": "string"}`，docstring 变成工具的 `description`——而 description 会进模型上下文，**直接决定模型会不会正确使用这个工具**。所以 MCP 工具的 docstring 不是写给人类维护者的内部注释，而是写给模型的公开文档，要认真写。

**（3）两种失败，两种表达。** `CalculatorTool.execute` 的设计是用返回字符串 `"计算失败: ..."` 表达业务失败；到了 MCP 层，我们把它转成 `raise ToolError(...)`。为什么要转？因为 MCP 的工具结果有结构化的 `isError` 标志：抛 `ToolError` 会让框架返回 `isError=true` 的 CallToolResult，客户端（和它背后的模型）能**程序化地区分**"算出了 14"和"算不了"。如果只回一段以"计算失败"开头的文本，模型只能靠自然语言理解去猜——把结构化信息降级成文本，是协议适配层的失职。

错误处理的完整原理下一章展开。

### 3.4 Prompts：把提示词模板变成可共享的能力

```python
@app.prompt()
def research_report(topic: str) -> str:
    """生成一份针对指定主题的结构化调研报告提示词."""
    return (
        f"你是一名资深行业研究员。请围绕主题「{topic}」撰写一份调研报告，要求：\n"
        "1. 先给出 3~5 个调研维度的提纲；\n"
        ...
    )
```

Prompts 是 MCP 三类能力里最容易被误解的一个：**它不是给模型直接执行的，而是给客户端用户/应用选用的提示词模板**。语义接近 IDE 里的代码片段（snippet）——客户端列出可用模板，用户选了 `research_report`、填入 `topic`，得到渲染好的提示词文本，再交给模型。

为什么提示词也值得走协议共享？因为**好的提示词是稀缺资产**。一份打磨过的调研报告模板，与其复制粘贴散落在各个 Agent 项目里，不如由一个 MCP Server 统一托管、版本化演进。这呼应了 day010 讲的"提示词是迭代出来的"——迭代成果需要载体，MCP Prompts 就是跨项目的载体。

### 3.5 三类能力的职责边界

| 维度 | Resources | Tools | Prompts |
|------|-----------|-------|---------|
| 本质 | 数据（只读内容） | 行为（可执行的函数） | 模板（参数化的文本） |
| 驱动方 | 应用/用户挑选 | 模型自主决定调用 | 用户显式选择 |
| 类比 | GET 接口 | POST 接口 | 代码片段库 |
| 本项目的实例 | `research://knowledge/{doc_id}` | `calculate` | `research_report` |
| 失败表达 | 抛异常 → 协议错误 | `ToolError` → `isError=true` | 参数校验错误 |

设计一个新能力时先问"它是数据、行为还是模板"，答案决定该用哪类——选错类别会让客户端模型困惑（比如把"执行计算"做成 Resource，模型不知道该何时"读"它）。

## 第四章：错误处理 —— 为什么工具失败不能是进程崩溃

### 4.1 MCP Server 的故障模型

先想清楚 Server 挂掉的代价。stdio 传输下，Server 是客户端拉起的子进程，stdout 是唯一的协议通道。**进程崩溃 = 连接死亡 = 客户端手里所有能力瞬间消失**，而且客户端无法区分"网络抖动"和"Server 有 bug"，只能整个重连。SSE 下稍好（HTTP 连接可重建），但一次未捕获异常照样打断当前会话。

所以 MCP Server 的错误处理第一原则是：**单个请求的失败必须被包含在单个响应里。** 这和普通 Web 服务的"一个请求 500 不能拖垮整个站点"同理，但在 stdio 场景下后果更严重——Web 服务 500 只是这个请求失败，MCP stdio 崩溃是所有请求的通道都没了。

### 4.2 三层错误防线

`calculate` 工具的错误处理实际是三层结构：

```text
客户端 ──tools/call──▶ FastMCP 框架层
                         │  调用业务函数
                         ▼
                       calculate()
                         │  try: CalculatorTool.execute()
                         │    ├─ 业务失败（除零/语法错）→ "计算失败: ..." 字符串
                         │    │    → 转为 raise ToolError(result)
                         │    └─ 意外异常 → logger.exception 记录
                         │         → raise ToolError(f"内部错误: {exc}")
                         ▼
                       框架捕获 ToolError
                         │  包装为 CallToolResult(isError=true, content=[错误文本])
                         ▼
客户端收到结构化错误，连接完好，可继续下一个调用
```

**第一层：业务层的本地化处理。** `CalculatorTool.execute` 内部把 `SyntaxError/ValueError/ZeroDivisionError` 转成失败字符串（day004 的设计），适配层再把失败字符串升级为 `ToolError`——每层用自己合适的方式表达失败。

**第二层：兜底 catch-all。** `except Exception` 捕获一切意外。注意它做了两件事：`logger.exception` 把完整 traceback 留在**服务端日志**里（调试者需要），而返回给客户端的只有一句摘要（调用者不需要也不该看到内部 traceback——那既无助于排查，还可能泄露路径等敏感信息）。**对内详尽、对外节制，是错误信息设计的通用法则。**

**第三层：框架的协议包装。** FastMCP 捕获 `ToolError`，生成 `isError=true` 的结构化结果。框架默认 `raise_exceptions=False`：即使业务函数抛的是其他异常，框架也会转成错误结果而不是让 Server 任务崩掉——但显式抛 `ToolError` 仍然必要，因为它保证了**错误消息是我们精心设计的那句话**，而不是原始异常的原文。

### 4.3 测试如何锁定错误路径

错误处理的价值要靠测试钉死，否则下次重构很容易被顺手"优化"掉：

```python
async def test_calculate_error_returns_iserror(self):
    async with create_connected_server_and_client_session(server) as session:
        await session.initialize()
        result = await session.call_tool("calculate", {"expression": "1 / 0"})
        assert result.isError is True
        assert "计算失败" in result.content[0].text
        # 会话未被错误破坏，后续调用依然可用
        ok = await session.call_tool("calculate", {"expression": "1 + 1"})
        assert ok.isError is False
```

注意最后两行——这是本章核心论点的可执行版本：**错误之后会话必须仍然可用**。只断言 `isError is True` 只能证明"这次失败了"，再发一个成功调用才证明"失败被正确隔离了"。测试 LLM 应用时，错误路径（sad path）与正常路径同等重要，因为模型的奇异输入是常态而非边角。

资源侧同理：`read_knowledge` 对不存在的 doc_id 和路径穿越尝试抛 `ValueError`，框架将其转为协议错误响应，测试用 `pytest.raises(Exception, match="不存在")` 锁定这一行为。

> 思考题：`except Exception` 兜底会不会掩盖 bug，让问题更难发现？我们是如何避免这个副作用的？提示：看 `logger.exception` 那一行，想一想"可观测性"和"容错"的分工。

## 第五章：stdio 与 SSE —— 两种传输的模型差异

### 5.1 入口：一个参数切换两种世界

```python
def main() -> int:
    parser = argparse.ArgumentParser(description="智研 AI 助手 MCP Server")
    parser.add_argument("--transport", choices=["stdio", "sse"], default="stdio")
    args = parser.parse_args()

    app = create_server()
    if args.transport == "stdio":
        # stdout 是协议通道，任何日志都会污染它，必须把控制台日志让路到 stderr
        for handler in logging.getLogger().handlers + logger.handlers:
            if isinstance(handler, logging.StreamHandler) and handler.stream is sys.stdout:
                handler.setStream(sys.stderr)
        app.run(transport="stdio")
    else:
        app.run(transport="sse")
```

业务装配（`create_server()`）与传输选择完全解耦——同一个 `app`，两种跑法。这是 FastMCP 分层设计的红利：协议逻辑不感知传输。

### 5.2 stdio：进程模型

stdio 传输的本质是**父子进程间的管道通信**：

```text
┌──────────────── Client 进程（如 Agent / Claude Desktop）───────────────┐
│                                                                        │
│   spawn ──▶ ┌──────────── Server 子进程 ────────────┐                  │
│   stdin  ◀──│  stdout（纯 JSON-RPC 消息流，逐行）     │                  │
│   stdout ──▶│  stdin（客户端请求）                    │                  │
│   stderr ◀──│  stderr（日志、诊断，随便写）           │                  │
│             └───────────────────────────────────────┘                  │
└────────────────────────────────────────────────────────────────────────┘
```

关键性质：

- **生命周期绑定**：Server 由 Client 拉起，Client 退出则子进程被回收。没有"服务管理"问题——不用注册、不用守护、不用端口。
- **零网络面**：不监听任何端口，天然免疫网络攻击，也没有鉴权负担。安全性来自进程边界。
- **一对一**：一个 Client 一个 Server 实例，天然隔离，但也意味着能力无法共享给多个客户端。
- **stdout 是神圣的**：这是 stdio 模式最容易踩的坑——stdout 上只允许出现 JSON-RPC 消息。任何 `print`、任何指向 stdout 的日志 handler，都会污染消息流，客户端解析直接报错。我们开发时就实测踩中：项目 logger 默认把控制台日志写 `sys.stdout`，stdio 客户端一握手就收到 GBK 编码的日志行，协议解析立刻 `UnicodeDecodeError`。修复方式就是入口里那段 `handler.setStream(sys.stderr)`。**stdio 服务的铁律：日志只去 stderr 或文件，stdout 永远干净。**

### 5.3 SSE：网络模型

SSE（Server-Sent Events）传输的本质是 **HTTP 长连接 + 回调端点**的双通道：

```text
Client A ──┐
           │  GET /sse（长连接，Server → Client 推送消息）
Client B ──┼──▶ ┌──────── MCP Server（HTTP 服务，127.0.0.1:8000）────────┐
           │     │  /sse：SSE 流，下发响应与通知                          │
           └──▶  │  /messages/：POST 端点，Client → Server 上行请求       │
                 └───────────────────────────────────────────────────────┘
```

为什么需要两个通道？SSE 本身是单向的（服务器→客户端），客户端的 JSON-RPC 请求没有回路可走，所以 MCP 的 SSE 方案补一个 HTTP POST 端点负责上行：**下行用 SSE 流，上行用 POST**，两个通道靠会话 ID 关联。

关键性质恰好与 stdio 互补：

- **独立服务**：Server 是长期运行的网络服务，生命周期与任何客户端无关，需要部署、监控、健康检查（day022 的 Docker 化就是为此准备）。
- **多客户端共享**：一个实例服务多个客户端，知识库等状态的更新对所有客户端即时可见。
- **网络面带来新责任**：监听端口就意味着要考虑绑定地址（默认 `127.0.0.1` 仅本机）、鉴权（MCP 支持 OAuth，本阶段不展开）、传输加密——SSE 的灵活性是用运维复杂度换来的。

### 5.4 选型对照

| 维度 | stdio | SSE |
|------|-------|-----|
| 拓扑 | 一对一，父子进程 | 多对一，C/S 网络 |
| 生命周期 | 随客户端生灭 | 独立常驻服务 |
| 网络暴露 | 无 | 监听端口，需考虑鉴权 |
| 延迟 | 进程间管道，极低 | 本地 HTTP，略高；远程视网络 |
| 部署成本 | 零（客户端拉起即用） | 需要服务化管理（Docker/systemd） |
| 日志约束 | stdout 必须纯净 | 无特殊约束 |
| 典型场景 | 桌面助手、IDE 插件、本地 Agent | 团队共享服务、远程工具、云端能力 |

经验法则：**同机、单用户、能力随用随起 → stdio；跨机、多用户、能力常驻共享 → SSE。** 我们的智研助手作为本地 Agent 的附属能力，stdio 是默认项；SSE 留给了未来"知识库服务化"的演进方向。

### 5.5 为什么测试不真起 SSE 服务

SSE 测试要起真实 HTTP 端口：端口占用、防火墙、异步服务回收都会让测试变脆，而且重复验证的是 uvicorn 而非我们的代码。**测试的黄金位置是协议逻辑层**——`create_connected_server_and_client_session` 的内存会话覆盖了握手、能力列表、工具调用、错误路径的全部业务逻辑；传输层的差异交给框架，框架自己有测试。这是我们一次次强调的原则的又一个实例：**测自己的逻辑，信任并隔离外部依赖。**

### 6.2 pytest-asyncio 的 auto 模式

MCP 客户端 API 全是异步的，测试函数自然是 `async def`。pytest 本身不会执行协程——收集到一个协程函数只会跳过并警告。`pytest-asyncio` 负责把它们跑在事件循环里，两种用法：

- 严格模式（默认）：每个异步测试都要标 `@pytest.mark.asyncio`；
- **auto 模式**：`asyncio_mode = "auto"`，所有 `async def test_*` 自动视为异步测试。

我们选 auto：本项目的异步测试将越来越多（day020 客户端、day023 协议测试全是异步），逐函数打标记是纯重复劳动。这是"配置优于分散标注"的取舍——和 day002 用 `conftest.py` 集中管理 fixture 是同一思想。

### 6.3 内存会话测试的读法

所有集成测试共享同一个三段式结构：

```python
server = create_server()                                    # ① 工厂创建全新实例
async with create_connected_server_and_client_session(server) as session:  # ② 内存连接
    await session.initialize()                              # ③ 显式握手
    ...  # list_tools / call_tool / read_resource / get_prompt
```

每一段都对应本章的一个知识点：①对应 3.1 的工厂隔离；②对应 2.3 的"真实协议状态机 + 零网络"；③对应第二章——握手不是可选项，是交互的前置条件（漏掉 `initialize()` 直接调用，客户端库会先报错）。

## 第七章：今日总结 —— FastMCP Server 的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 用 FastMCP 而非手写 JSON-RPC | 协议正确性交给框架，业务只写函数+装饰器 | `full_server.py` |
| 保留 `protocol.py` 模型 | 框架管运行时，显式模型管认知与文档 | `mcp_server/protocol.py` |
| 包名 `mcp_server` | 避免遮蔽官方 `mcp` 包 | 目录命名 |
| `create_server()` 工厂 | 测试隔离，实例互不污染 | `full_server.py` |
| `instructions` 元数据 | 写给模型的产品文档，握手时分发 | `SERVER_INSTRUCTIONS` |
| 工具包装而非重写 | 业务逻辑单点维护，协议层只做适配 | `calculate()` |
| 失败字符串 → `ToolError` | 用 `isError=true` 让错误结构化、可程序化判断 | `calculate()` |
| catch-all + `logger.exception` | 对内详尽留 traceback，对外节制只给摘要 | `calculate()` |
| doc_id 白名单正则 | 路径穿越防御，外部输入不信任 | `read_knowledge()` |
| stdio 下日志让路 stderr | stdout 是协议通道，必须纯净 | `main()` |
| 内存会话做集成测试 | 覆盖协议逻辑，隔离传输依赖，离线可跑 | `tests/test_full_server.py` |
