## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：视觉请求与纯文本请求的协议分水岭，正是 `user` 消息的 `content` 从"纯字符串"升级为"**部件数组**"（content parts array）：

```json
{"role": "user", "content": [
    {"type": "text", "text": "这张图里有什么？"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBOR..."}}
]}
```

数组里每个元素是一种模态，模型按顺序理解它们的关系。A 错——没有"独立的顶层图像字段"这回事，图像必须作为 content 的部件；C 错——图像部件挂在**最后一条 user 消息**上（见 `openai_compatible.py` 的 `user_idx` 逻辑），system 消息原样透传；D 错——图像恰恰用 **data URL**（`data:image/png;base64,...`）内嵌，自包含、无额外请求，这是离线测试能跑通的前提。

### 第 2 题

**答案：C**

**解析**：10 MB 上限的三个依据是：① base64 膨胀约 1/3（3 字节编码为 4 字符）；② VLM 对超高清大图按 tile 切块计费，体积越大 token 成本越高；③ 因此限制体积"既是传输保护，也是成本保护"。C 提到的"TCP 分包错误"不是设计依据——HTTP 层面对大文件有分块传输等成熟机制，这不是我们设上限的理由。

### 第 3 题

**答案：A**

**解析**：magic bytes 是每种文件格式**在内容开头**的固定字节序列，由格式规范定义（如 PNG 是 `\x89PNG\r\n\x1a\n`、JPEG 是 `\xff\xd8\xff`），伪造成本远高于改扩展名。服务端校验永远以**自己读到的字节**为准，不信任客户端声称的任何信息。B 是干扰项（速度不是设计动机）；C 错——magic bytes 是服务端**读取**内容识别出的，不是自己生成的；D 错——扩展名同样能区分 PNG/JPEG，问题在于它**可以被伪造**。

### 第 4 题

**答案：B**

**解析**：三种异常分别对应三种失败语义（空、超限、格式不支持），设计意图是让**不同消费方按类型分支处理**：API 层在 `routes.vision_describe` 里用 `except (EmptyImageError, ImageTooLargeError, UnsupportedImageTypeError)` 统一转成 422 并携带各自 detail；工具层则捕获一切异常统一转成"图像分析失败: 原因"文案。A 错——`chat_vision` 不捕获图片错误；C 错——拆分的是**异常类型**而非模块；D 错——模型不读异常类型，消费方是服务端代码。

## 第二部分：判断题

### 第 5 题

**答案：对**

**解析**：`supports_vision` 默认 `False`、`chat_vision` 默认抛 `NotImplementedError`，两层含义：① **向后兼容**——所有只实现了 `chat` 的旧实现无需任何改动，就保持"不支持视觉"的诚实声明；② **绝不静默忽略图像**——如果默认实现是"假装没看见、直接走 chat 返回文本"，会造成"模型根本没看图却回答了"的危险假象，显式抛错把"不支持"做成明牌。

### 第 6 题

**答案：错**

**解析**：`ModelRouter.chat_vision` 遍历降级链时，对不支持视觉的模型是 `continue`（**跳过**），而不是报错——把"该模型没有视觉能力"当成**路由层可规避的事实**，而不是一次失败。全部候选都不支持视觉时，才抛 `候选模型均不支持视觉，无法处理图像请求`；若有视觉候选但全部调用失败，抛 `所有视觉模型均调用失败: ...`（汇总各候选原因）。

### 第 7 题

**答案：对**

**解析**：工具是 Agent 循环里的"动作执行者"，返回文本拼回上下文供模型继续推理。失败以业务文案返回（`图像分析失败: 原因`），模型能据此调整策略（换参数、换工具、如实告知用户）；若抛异常则可能让整轮推理崩溃。这与 `CalculatorTool` 的错误契约完全一致。

## 第三部分：简答题

### 第 8 题

**参考答案要点**：

- **两个问题的分离**："这个模型看得见吗？"是能力声明（`supports_vision`），"怎么让它看？"是调用实现（`chat_vision`）。前者是路由层/API 层**做决策的依据**，后者是各实现类**执行动作的细节**。
- **路由层消费 `supports_vision`**：`ModelRouter.chat_vision` 用 `getattr(spec.llm, "supports_vision", False)` 过滤降级链——决策层不关心模型怎么看图，只关心"它能不能看"。
- **API 层消费 `supports_vision`**：`/vision/describe` 对解析出的 `target` 检查 `getattr(target, "supports_vision", False)`，为 False 时返回 400（请求语义与能力不匹配）。
- **调用实现被两者共用**：路由层、API 层最终都调 `chat_vision` 完成图像问答。
- **向后兼容**：默认 `False` + 抛错，让引入视觉协议不需要改动任何旧 LLM 实现；默认值的设计同时保证了"不支持"是明牌而非静默错误。

### 第 9 题

**参考答案要点**：

| 场景 | 状态码 | detail |
|------|--------|--------|
| 图片为空 | 422 | `图片为空` |
| 图片超限 | 422 | `图片过大：...超过上限...` |
| 图片格式不支持 | 422 | `无法识别的图片格式...` |
| 点名的模型没有视觉能力 | 400 | `模型 xxx 不支持图像输入（缺少视觉能力）` |
| 点名的模型不存在 | 404 | `未知模型: xxx，可用模型: ...` |

**400 与 404 的区别**：404 表示**资源不存在**——模型名是"合法字符串但不在候选集里"，这是资源层面的问题；400 表示**请求语义错误**——模型存在，但它的能力（不支持视觉）与请求要求不匹配。这个区分延续 day039 的契约哲学：客户端拿到 404 应修正模型名或查询 `/models`；拿到 400 应换一个支持视觉的模型（或接受默认路由自动过滤）。

## 第四部分：编程题

### 第 10 题

**参考答案**（可直接追加到 `tests/test_router.py`）：

```python
class TestRouterVision:
    """day040：视觉请求路由——图像请求只发给支持视觉的候选."""

    def make_mixed_models(self) -> list[ModelSpec]:
        """文本模型更便宜（会被成本策略首选），但视觉链必须跳过它."""
        return [
            ModelSpec("text", TextOnlyLLM(), capability=2, cost_per_1k=0.001),
            ModelSpec("vision", MockLLM(default="视觉模型的回答"), capability=4, cost_per_1k=0.05),
        ]

    def test_chat_vision_skips_text_models(self):
        """路由决策首选便宜的文本模型，但视觉链跳过它、落到视觉模型."""
        router = ModelRouter(self.make_mixed_models())
        reply = router.chat_vision(
            [Message(role="user", content="图片里有什么")],
            image_data_url="data:image/png;base64,AAAA",
        )
        assert reply == "视觉模型的回答"
        decision = router.decision_log[-1]
        assert decision.chosen == "text"      # 成本策略仍选了文本模型
        assert decision.fallback_used == "vision"  # 视觉链实际落到 vision
```

**关键点说明**：

1. **构造**：文本模型成本更低（0.001 < 0.05），任务"图片里有什么"短且无复杂关键词（复杂度=1），因此 `CostFirstStrategy` 的决策是 `chosen="text"`；
2. **执行**：`chat_vision` 遍历降级链 `[text, vision]`，`text` 的 `supports_vision` 为 False 被跳过，`vision` 调用成功返回；
3. **`fallback_used` 的意义**：它把两条**正交的维度**汇合到同一条决策记录里——**路由决策**（成本策略按复杂度选模型，该选谁还选谁）与**视觉能力**（模型属性决定图像请求实际落到谁）。`chosen="text"` 说明"按成本本应选文本模型"，`fallback_used="vision"` 说明"视觉链实际生效的是 vision"，两者并存让"为什么最终是 vision 回答的"有案可查——这正是 day033 设计 `RouteDecision` 时预留的可观测性在 day040 的回报。

**验证**：运行 `python -m pytest tests/test_router.py -q`，新增用例通过（day040 快照全量 651 个测试、覆盖率 94.33% 全绿）。
