## 一、速答

**1.** 四份：`demo` 演示剧本（这一次运行能不能被别人原样重放）、
`summary` 课程清单 + 总结（这门课交付了哪些子包、各有多少东西）、
`assessment` 能力自评（八项能力分别建到哪一步、证据是什么）、
`roadmap` 后续规划（按真实缺口排，下一步该补什么）。
它们被写在 `types.DELIVERABLE_ORDER` 里，四份合起来不重不漏。

**2.** 含：**问题 / 九段读数 / 汇总行 / 归档行**。
不含：时间戳、uuid、耗时、日志文本。
"不含"才是要点——把它们放进读数，"两次重放逐位相同"这条性质会**永远失败**，
而失败的原因与剧本无关，于是这条性质就会被人关掉。这与 day096 把时钟做成可注入、
day099 把时间移出复算口径是同一条纪律：**可复现的前提是先把"不确定的东西"挪出去**。

**3.** 运行摘要覆盖"问题 / 九段记录 / 答案 / 四条指标 / 费用 / token / span 条数"；
剧本摘要覆盖"问题 / 九段读数 / 汇总行 / 归档行"。
不复用运行摘要的原因：**"运行没变"与"剧本没变"是两件事**——
有人改了剧本的抬头或归档行时，运行摘要不会变，交付物却已经变了。

**4.** 无 `__all__` 时改用**文件系统口径**：数它目录下有多少个子模块（`pkgutil.iter_modules`）。
不用 `vars()` 的原因只有一个——**确定性与导入顺序无关**：
`vars()` 会随着别的模块把子模块 import 进来而"长"出新名字，
于是同一次运行里"先数"与"后数"会给出两个数（6 与 7 这种）。
按目录数只取决于磁盘上有哪些文件，因此两次调用逐位相同。

**5.** 检查 **发现集合 == 记录集合**。能抓到两类错误：
**漏项**（某个子包没进名册）与**重复**（同一个子包被数了两遍）。
漏掉的包既不会出现在名册里、也不会被任何人负责；重复计数会让汇总数虚高。

**6.** "数出来"的是 `subpackages`（52）、`modules`（379）、`symbols`（4767）——
它们来自 `InventoryReport`；"折出来"的是 `capabilities`（8，来自 `capstone.types`）、
`stages`（9）、`properties`（7）、`deliverables`（4）。
唯一"声明"的是 `days`（100）：这个仓库里没有日期，100 天是里程碑的定义，
因此它是一条被复述的常量（并由 `CourseSummary` 的护栏逐位钉住）。

**7.** 四档：

```text
0 未建     有承担子包不在场（证据：在场数 < 承担数）
1 已建     承担子包全部在场，但公开名字数 < 门槛 8
2 可用     前两项成立，但端到端链上那一段 ok=False
3 已交付   在场 / 符号 / 阶段三项全过
```

**8.** 第二条闭合检查是：**`level` 必须等于由同一批证据重算出来的那一档**
（`level_for(...)`）。它拒掉了"手写的分"——一个没有证据的满分，
与"我猜的满分"在报告里长得一模一样。

**9.** 两种缺口：`unclaimed_package`（无人认领的子包，来自 `Manifest.unclaimed`）、
`capability_below`（没到最高级的能力，来自 `Assessment.below`）。

**10.** 下界是 ⑥ `assessment_has_evidence`（最少证据条数 >= 1）；
上界是 ⑤ `assessment_within_scale`（最高评级 <= 3）。
下界不能写成相等：证据越多越好，写成 `== 1` 会在补了一条证据时误报失败。
上界不能写成相等：8 项能力不可能都恰好是 3 分才合格——本课真实状态就是
"7 项 L3 + 1 项 L1"，而这一项已被第 ④ 条（规划覆盖缺口）兜住。

## 三、对照

**14.**

```text
A: SystemRun.comparable()（day099）
   口径：问题 / 九段记录 / 答案 / 四条指标 / 费用 / token / span 条数
   用途：证明"同一次端到端调用两次运行逐位相同"——即"链本身是确定性的"
   读数：跑一次链，比较两次运行的元组

B: DemoTranscript.comparable()（day100）
   口径：问题 / 九段读数 / 汇总行 / 归档行
   用途：证明"这一份**产物文本**两次生成逐位相同"——即"剧本是可重放的"
   读数：由 A 的读数折成一行行文本，再比较两份文本
```

一句话：A 管"运行"，B 管"产物"；B 依赖 A，但覆盖的是 A 覆盖不到的那一部分（剧本文本）。

**15.** "两条独立路径给出同一个数"消除了**单一来源的盲区**：

```text
总结 vs 清单   总结给人读（一条 `line()`），清单给程序读（一次遍历计数）
记账 vs 手算   CostTracker 走价格表，hand_cost_formula 走一行公式
```

如果只有一个来源，你只是在**复述**那个来源：价格表写错一档、或清单扫描少一个包，
报告都不会变红。两条独立路径都给出同一个数时，"这个量可信"才成为一个
**可被反驳**的结论（读数就是"差异项数"）。这正是本课把它做成第 ⑦ 条性质的理由。

**16.** 因为两者回答的是**不同的问题**：

```text
① 七条性质    "这次交付本身成立吗"（四份非空 / 重放一致 / 清单闭合 / 规划对上 / 量程与证据）
② 全部到 L3   "八项能力是否都做到了最高档"
```

本课的真实状态是 7×L3 + 1×L1：`tool_execution` 停在"已建"（`tools` 包公开面 5 < 门槛 8）。
把两者绑在一起，会让"有一条能力在 L1 **且已经被规划兜住**"这种合法状态被当成失败，
从而逼着人把自评的分数往上写——那就毁掉了自评的意义。
因此 `require_ok` 只查七条性质，`require_delivered` 是**可选**的更严那条路。

## 四、诊断

**17.** 他错在把"承担子包全部在场"当成了"已交付"。题目这组参数里
`symbols = 5 < SYMBOL_FLOOR = 8`，因此按照量程定义：

```text
owners_present == owners_total → 不是 0（未建）
symbols(5) < 8                 → 命中"已建但公开面太薄" ⇒ LEVEL_BUILT (1)
```

**必须**返回 1 而不是 3，因为评级是"由证据重算出来的"，而证据说这项能力的公开面
还没达到"可用"。若允许返回 3，`CapabilityScore.__post_init__` 的第二条闭合检查会当场拒绝
（`评级 3 与证据重算出的 1 不一致`）——也就是说，**这个错误在构造期就被拦住了**，
不可能悄悄出现在报告里。本课真实的 `tool_execution` 就是这一档。

**18.** 最可能的三处病因（都属于"混进了一个没有固定的量"）：

```text
① 时间 / uuid：脚本里把 time.time() 或 uuid4() 写进了某一行读数
② 采样：模型带随机性（真实 LLM 而不是 MockLLM），或用了未固定的随机种子
③ 字典序 / 集合序：某一行是由 dict/set 直接迭代出来的，而它们的顺序不稳定
```

`DemoTranscript.comparable()` 能帮他定位，是因为它**只取四个字段**
（问题 / 九段读数 / 汇总行 / 归档行），而 `diff_count` 逐项比对这四个字段：

```text
差异项数 == 3，说明这四个字段里有 3 个不同
→ 若四段读数不同   ⇒ 病在链（② 采样）
→ 若汇总行不同     ⇒ 病在汇总（可能带了时间戳）
→ 若问题/归档行不同 ⇒ 病在剧本抬头（可能带了 uuid 或生成时间）
```

把"哪个字段变了"缩小到四选一，比对着整份文本找不同快得多——
这就是"复算口径要写死"的实用价值。

## 五、推导

**19.** 逐项算（名字数 = 承担子包的公开名字数之和）：

```text
能力                  名字数                              评级
input_guard           8 + 12   = 20                       L3（在场 2/2、>=8、plan 前的 guard ok=True）
task_planning         11 + 12  = 23                       L3（plan ok=True）
hybrid_retrieval      124 + 95 = 219                      L3（retrieve ok=True）
context_packing       124      = 124                      L3（pack ok=True）
grounded_generation   124 + 12 = 136                      L3（generate ok=True）
offline_evaluation    20       = 20                       L3（evaluate ok=True）
cost_and_tracing      8 + 12   = 20                       L3（account ok=True）
tool_execution        5        =  5                       L1（5 < 门槛 8）
```

因此 `Assessment.line()` 里的三个数是：

```text

最少证据条数 = 3（每一项都挂了三条证据：在场 / 名字 / 阶段）
```

完整一行：

```text
自评：最高 L3 / 最低 L1 | 已交付 7/8 项 | 最少证据 3 条
```
