## 今日目标

1. **理解视觉-语言模型的输入格式**——content 从"纯字符串"升级为"部件数组"，图像以 data URL 内嵌，这是多模态与纯文本协议的分水岭。
2. **实现图像进入模型的三道工序**——校验（magic bytes 识别真实类型）、编码（base64 + data URL）、组装（文本与图像部件数组）。

4. **在 FastAPI 暴露图片上传接口**——multipart 表单接收图片，错误按类型映射为稳定的状态码契约。

到今天为止，我们的 Agent 是个"文盲"：它能推理、能调工具、能流式回答，但**看不见**。用户给它一张截图、一张报表、一张产品图，它只能读到文件名。这一课给 Agent 装上眼睛——多模态输入。核心不是调用某个 API（那只是几行代码），而是理解三件事：**图片以什么格式进模型、谁负责把它变成那个格式、哪些模型"看得见"而哪些不能**。

## 第一章：为什么需要多模态 —— 纯文本模型的边界

### 1.1 看不见的代价

纯文本模型（如 gpt-3.5-turbo）的输入只有一个通道：字符串。世界的信息大部分不在字符串里——UI 截图里的布局、表格图片里的数据、手写笔记、商品实拍图。要让模型理解这些，以前只有两条笨路：

1. **人工转述**：人把图片内容"翻译"成文字再喂给模型——信息丢失、成本高、不可扩展；
2. **OCR 预处理**：用专门的 OCR 服务把图片转成文字——只解决了"文字图片"，遇到图表、物体、场景就无能为力。

视觉-语言模型（VLM，Vision-Language Model）把图像通道直接接入模型：输入是「文本 + 图像」的混合，模型在同一份上下文里理解两者的关系。今天实现的，就是让我们的服务具备这条通道。

### 1.2 协议层面的分水岭：content 从字符串变成部件数组

纯文本请求里，`user` 消息的 `content` 是一个字符串：

```json
{"role": "user", "content": "这张图里有什么？"}
```

视觉请求里，`content` 升级为**部件数组**（content parts array）：

```json
{"role": "user", "content": [
    {"type": "text", "text": "这张图里有什么？"},
    {"type": "image_url", "image_url": {"url": "data:image/png;base64,iVBORw0KG..."}}
]}
```

数组里的每个元素是一种**模态**（modality）：文本部件、图像部件。模型按数组顺序理解它们的关系——先读问题、再看图、再回答。这个格式是 OpenAI 兼容协议的标准，我们实现里的组装函数（见第二章）输出的正是这种结构。

### 1.3 图像的载体：data URL

图像部件里的 `url` 不是 `https://...`，而是 **data URL**——把图片字节编码进 URL 自身：

```text
data:<MIME 类型>;base64,<图片字节的 base64 编码>
```

为什么不用普通 URL？三个理由，且都指向"自包含"：

1. **无额外请求**：服务端不用再发起一次 HTTP 去拉图片，省一次网络往返，也少一个失败点；
2. **无托管依赖**：不需要把图片传到图床/对象存储拿到 URL，私密图片也不会外泄；
3. **离线可测**：测试里用 `data:image/png;base64,AAAA` 就能模拟一张图，不需要起文件服务——这是我们的测试能全离线跑通的关键。

代价是体积：base64 会把字节膨胀约 1/3（3 字节编码为 4 字符），这也是第二章设置图片大小上限的原因之一。

## 第二章：图像进入模型的三道工序 —— 校验、编码、组装

图像从"用户上传的字节"到"模型认识的部件数组"，中间是三道工序。它们收敛在新增模块 `multimodal/image.py`，模块只做「图像字节 → 协议消息」，不做网络传输，因此全程可离线、可测试。

### 2.1 第一道：校验 —— 用 magic bytes 识别真实类型

第一道防线是**类型校验**。为什么不能信文件扩展名？因为扩展名可以被随手伪造——把一个文本文件改名为 `pic.png`，扩展名是 `.png`，内容还是文本。服务端校验永远以**自己读到的字节**为准。

识别方式用 **magic bytes**：每种文件格式在内容开头有固定字节序列，由格式规范定义，伪造成本比改扩展名高得多：

```python
_IMAGE_MAGIC: tuple[tuple[str, bytes], ...] = (
    ("image/png", b"\x89PNG\r\n\x1a\n"),
    ("image/jpeg", b"\xff\xd8\xff"),
    ("image/gif", b"GIF87a"),
    ("image/gif", b"GIF89a"),
)

def detect_mime(data: bytes) -> str | None:
    """用 magic bytes 识别图像真实 MIME 类型（不信任文件扩展名）."""
    for mime, magic in _IMAGE_MAGIC:
        if data.startswith(magic):
            return mime
    if data.startswith(b"RIFF") and len(data) >= 12 and data[8:12] == b"WEBP":
        return "image/webp"
    return None
```

注意 WebP 的特殊处理：WebP 的容器头是 `RIFF`，真正的类型标识藏在偏移 8 处的 `WEBP` 四字节，所以要多判断一步。这个例子说明：**格式识别是逐格式的领域知识**，没有万能银弹。

### 2.2 校验的顺序与错误细分

`validate_image` 按"空 → 超限 → 类型"的顺序检查，并且**每种失败抛不同的异常类型**：

```python
class EmptyImageError(ValueError): ...
class ImageTooLargeError(ValueError): ...
class UnsupportedImageTypeError(ValueError): ...

def validate_image(data: bytes, max_bytes: int | None = None) -> str:
    if not data:
        raise EmptyImageError("图片为空")
    limit = max_bytes or MAX_IMAGE_BYTES
    if len(data) > limit:
        raise ImageTooLargeError(f"图片过大：{len(data)} 字节超过上限 {limit} 字节")
    mime = detect_mime(data)
    if mime is None:
        raise UnsupportedImageTypeError("无法识别的图片格式，仅支持 PNG/JPEG/GIF/WebP")
    return mime
```

错误类型细分的设计意图在第六章显现：API 层要按**类型**把三类失败映射到不同的 HTTP 状态码（422/422/422 在本次都是 422，但语义不同，客户端可按 `detail` 区分）；而 `ImageAnalysisTool` 则把任何异常统一转成业务失败文案。**同一套错误类型，在不同层有不同的消费方式**——这就是"按类型分支而不是解析文案"的收益。

大小上限 `MAX_IMAGE_BYTES = 10 * 1024 * 1024`（10 MB）的选择有技术依据：base64 膨胀 1/3，10 MB 图片编码后约 13.3 MB 字符；且 VLM 对超高清大图按 tile 切块计费，体积越大 token 成本越高——限制体积既是传输保护，也是成本保护。

### 2.3 第二道：编码 —— base64 与 data URL

```python
def encode_image_base64(data: bytes) -> str:
    return base64.b64encode(data).decode("ascii")

def build_data_url(data: bytes, mime: str | None = None) -> str:
    resolved = mime or validate_image(data)
    return f"data:{resolved};base64,{encode_image_base64(data)}"
```

`build_data_url` 不传 `mime` 时会**自动校验并识别**——这保证任何进入 data URL 的字节都先过了一遍校验，编码和校验耦合在同一个入口。

反向的 `decode_data_url` 用于工具层（第五章）：把 data URL 还原成字节，且 base64 段用 `validate=True` 严格校验，畸形内容绝不静默解出错误字节。

### 2.4 第三道：组装 —— 视觉消息的部件数组

```python
def build_vision_payload(prompt: str, image_data_url: str) -> list[dict]:
    return [
        {"type": "text", "text": prompt},
        {"type": "image_url", "image_url": {"url": image_data_url}},
    ]
```

这就是第一章讲的协议分水岭：content 从字符串变为部件数组。组装函数很小，但它把"协议格式"这个容易写错、写散的知识点收敛到了一个可测试的入口——测试可以直接断言它的结构，而不必等真实 HTTP 请求。

## 第三章：LLM 层的视觉协议 —— 能力声明与调用实现

### 3.1 能力声明（supports_vision）与方法实现（chat_vision）分离

多模态能力有两个不同的问题要回答：

- **"这个模型看得见吗？"** —— 这是**能力声明**，是路由层做决策的依据；
- **"怎么让它看？"** —— 这是**调用实现**，是各实现类的协议细节。

两者分开设计，在 `llm/base.py` 里对应一个属性和一个方法：

```python
@property
def supports_vision(self) -> bool:
    """是否支持图像输入（day040）."""
    return False  # 默认：纯文本模型不需要任何改动就保持诚实的"不支持"

def chat_vision(self, messages, image_data_url, temperature=0.7, max_tokens=1024) -> str:
    raise NotImplementedError(
        f"{type(self).__name__} 不支持图像输入，请改用纯文本 chat 协议"
    )
```

默认值的设计有两个深意：

1. **向后兼容**：所有旧实现（只写了 `chat` 的模型）默认 `supports_vision=False`、`chat_vision` 抛错，不需要为引入视觉协议而改动任何旧代码；
2. **绝不静默忽略图像**：如果 `chat_vision` 的默认实现是"假装没看见、直接走 chat 返回文本"，那会造成**"模型根本没看图却回答了"**的假象——在图像问答场景这是最危险的错误。显式抛错让"不支持"成为明牌。

### 3.2 真实实现：OpenAICompatibleLLM.chat_vision

```python
def chat_vision(self, messages, image_data_url, temperature=0.7, max_tokens=1024) -> str:
    user_idx = None
    for i, m in enumerate(messages):
        if m.role == "user":
            user_idx = i
    if user_idx is None:
        raise ValueError("视觉消息至少需要一条 user 消息")
    built: list[dict] = []
    for i, msg in enumerate(messages):
        if i == user_idx:
            built.append(
                {"role": "user", "content": build_vision_payload(msg.content, image_data_url)}
            )
        else:
            built.append(msg.to_dict())
    resp = self._client.chat.completions.create(
        model=self._model, messages=built,
        temperature=temperature, max_tokens=max_tokens,
    )
    return resp.choices[0].message.content or ""
```

两个协议细节值得注意：

- **图像部件挂在哪条消息上**：只挂在**最后一条 user 消息**上（`user_idx` 循环取最后一个匹配），其余消息（system、历史轮次）原样透传——图像属于"当前这轮提问"，不该污染系统提示；
- **`supports_vision` 固定返回 True 的前提**：当前配置的 `settings.default_model`（`gpt-4o-mini`）是视觉模型。教程把这条写进注释：**能力声明是配置问题，不是写死的问题**——若将来配置换成纯文本模型，这里要改成按配置判断，否则会"声称看得见却看图失败"。

### 3.3 模拟实现：MockLLM 的视觉与成本口径

离线测试不能发网络请求，MockLLM 用脚本模拟视觉调用，并且**把图像成本也模拟出来**：

```python
IMAGE_TOKEN_BUDGET = 85  # multimodal/image.py：OpenAI 视觉计费的最低档（低细节，每图约 85 token）

def chat_vision(self, messages, image_data_url, temperature=0.7, max_tokens=1024) -> str:
    self.calls.append(messages)
    reply = self._take_reply(temperature)
    prompt_tokens = sum(estimate_tokens(m.content) for m in messages) + IMAGE_TOKEN_BUDGET
    completion_tokens = min(estimate_tokens(reply), max_tokens)
    self.usage_log.append({"prompt_tokens": prompt_tokens, "completion_tokens": completion_tokens})
    self.total_prompt_tokens += prompt_tokens
    self.total_completion_tokens += completion_tokens
    return reply
```

`IMAGE_TOKEN_BUDGET = 85` 不是随便写的数字：OpenAI 视觉计费里，低细节（low detail）模式每张图固定约 85 token。MockLLM 用它让**离线统计的成本口径贴近真实协议**——后续成本追踪（day043 的 `cost_tracker.py`）不需要区分文本/视觉两种调用，因为它们已经按同一套口径记账。

## 第四章：路由层的视觉处理 —— 图像请求只发给看得见的模型

### 4.1 问题：模型池是"混合视力"的

day033 的 `ModelRouter` 管理一池模型：便宜的文本模型、贵的强模型。day040 之后池子里还可能混着"看得见的"和"看不见的"。如果视觉请求按普通 `chat` 路由，发到一个纯文本模型，得到的是 `NotImplementedError`——把"该模型没有视觉能力"当成了一次随机失败，既浪费降级机会，错误信息也误导人。

正确做法：**把"没有视觉能力"当作路由层可规避的事实**，而不是一次失败。视觉路由只挑选支持视觉的候选：

```python
@property
def supports_vision(self) -> bool:
    """是否有可用模型支持视觉（day040）."""
    return any(getattr(spec.llm, "supports_vision", False) for spec in self.models)

def chat_vision(self, messages, image_data_url, temperature=0.7, max_tokens=1024) -> str:
    decision, chain = self.route(self._last_user_task(messages))
    errors: list[str] = []
    for spec in chain:
        if not getattr(spec.llm, "supports_vision", False):
            continue  # 文本模型：跳过而非报错
        try:
            reply = spec.llm.chat_vision(
                messages, image_data_url, temperature=temperature, max_tokens=max_tokens
            )
        except Exception as exc:
            errors.append(f"{spec.name}: {exc}")
            continue
        if spec.name != decision.chosen:
            decision.fallback_used = spec.name
        return reply
    if errors:
        raise RuntimeError(f"所有视觉模型均调用失败: {'; '.join(errors)}")
    raise RuntimeError("候选模型均不支持视觉，无法处理图像请求")
```

`getattr(spec.llm, "supports_vision", False)` 用 `getattr` 带默认值而非直接访问属性，是为了兼容**任何** LLM 对象——即使它没有实现 `supports_vision`（比如测试桩），也按"不支持视觉"处理，不炸出 `AttributeError`。

### 4.2 一个值得品味的场景：路由决策与视觉能力的正交

考虑 `TestRouterVision.test_chat_vision_skips_text_models` 这个用例：模型池里文本模型更便宜（cost 0.001 < 视觉模型 0.05），任务是"图片里有什么"（短、无复杂关键词，复杂度=1）。成本策略的决策是：

```
chosen = "text"（满足能力要求的最便宜模型）
chain  = [text, vision]
```

但 `chat_vision` 遍历降级链时：`text` 不支持视觉 → **跳过**；`vision` 调用成功 → 返回。决策记录里：

```
chosen = "text"        # 路由决策没变，它只负责"选模型"
fallback_used = "vision"  # 视觉链实际生效的模型
```

这个结果很优雅：**路由决策（cost 策略）与视觉能力（模型属性）是两条正交的维度**。路由该选谁还选谁，视觉链自己过滤掉"看不见的"——两者通过 `fallback_used` 字段汇合到同一条决策记录里，"为什么最终是 vision 回答的"有案可查。这正是 day033 设计 `RouteDecision` 时预留可观测性的回报。

### 4.3 降级语义与 chat 完全对称

视觉首选失败（网络错误、API 500）时，沿降级链找**下一个支持视觉的**候选重试；全部视觉候选失败才抛错，且错误里汇总每个候选的失败原因（`超时`、`限流`……），与 `chat` 的"所有候选模型均调用失败"惯例一致。失败方向也是失败安全的：**降级只向上（更强），绝不向下（更弱）**——视觉任务答错比多花钱严重。

## 第五章：ImageAnalysisTool —— 把视觉能力变成 Agent 的工具

### 5.1 为什么需要工具封装

Agent 的推理循环只会调用"工具"，不会直接调用 LLM 方法。把视觉能力封装成工具 `image_analysis`，Agent 就能在推理中说"我需要看一张图"，然后模型以标准 function calling 格式给出参数、工具负责执行。封装同时承担了**输入格式的兼容层**：模型的工具参数只是字符串，怎么变成图像字节，是工具的内部细节。

### 5.2 三种输入形态与优先级

```python
def _resolve_image_bytes(self, image: str) -> bytes:
    if image.startswith("data:"):
        return decode_data_url(image)              # ① data URL
    if image.startswith(("http://", "https://")):
        raise ValueError("不支持远程图片 URL，请使用本地路径、base64 或 data URL")
    path = Path(image)
    if path.is_file():
        return path.read_bytes()                   # ② 本地文件路径
    try:
        return base64.b64decode(image, validate=True)  # ③ 裸 base64
    except (ValueError, binascii.Error) as exc:
        raise ValueError("无法解析图片参数：既不是文件路径、也不是合法的 base64") from exc
```

三个形态按优先级判断：data URL 开头特征最明确，最先识别；**远程 URL 显式拒绝**——服务端组件发任意外网请求是 SSRF（服务端请求伪造）的边界，这一步把风险挡在工具层（day044 的安全专题会系统展开）；本地路径用 `pathlib.Path.is_file()` 判断（不存在的路径不会误判成 base64）；最后尝试裸 base64 严格解码，失败给出人可读的错误。

### 5.3 错误契约：失败是"业务文案"而不是异常

```python
def execute(self, image: str = "", question: str = "描述这张图片的内容", **kwargs: Any) -> str:
    try:
        data = self._resolve_image_bytes(image)
        mime = validate_image(data)
        data_url = build_data_url(data, mime)
        reply = self._vision.chat_vision(
            [Message(role="user", content=question)], image_data_url=data_url
        )
    except Exception as exc:
        return f"图像分析失败: {exc}"
    return reply
```

与 `CalculatorTool` 完全一致的约定：**任何失败都以 `图像分析失败: 原因` 的字符串返回，而不是抛异常**。Agent 循环（day011 的 ReAct / day037 的 function calling）把工具返回值当作可读文本拼回上下文，异常则可能让整轮推理崩溃。工具是"动作的执行者"，把失败转成文本反馈给模型，模型可以据此调整策略（换参数重试、换工具、如实告诉用户）。

### 5.4 视觉模型注入与注册

视觉模型通过构造器注入（`ImageAnalysisTool(vision=llm)`），缺省时按 `default_llm()` 构建——离线环境得到 MockLLM 占位，配了 API Key 得到真实视觉模型。工具注册进 `ToolRegistry` 后，`FunctionCallingAgent` 就能看到 `image_analysis` 并调用它：**Agent 的"眼睛"就此接上**。

## 第六章：/vision/describe 接口 —— multipart 上传与错误码契约

### 6.1 为什么图片不走 JSON

day038 的请求体都是 JSON（Pydantic 模型校验）。但图片是二进制，塞进 JSON 字符串既低效（base64 膨胀 1/3）又不规范。文件上传走 **multipart/form-data**：请求体里 `file` 字段是二进制流、`question`/`model` 是普通表单字段。FastAPI 用 `UploadFile` + `File`/`Form` 声明接收：

```python
@router.post("/vision/describe", response_model=VisionDescribeResponse)
def vision_describe(
    file: UploadFile = File(...),
    question: str = Form("描述这张图片的内容"),
    model: str | None = Form(None),
    llm: BaseLLM = Depends(get_llm),
    models: dict[str, BaseLLM] = Depends(get_models),
) -> VisionDescribeResponse:
    data = file.file.read()
    try:
        mime = validate_image(data)
    except (EmptyImageError, ImageTooLargeError, UnsupportedImageTypeError) as exc:
        raise HTTPException(status_code=422, detail=str(exc)) from exc
    data_url = build_data_url(data, mime)
    target = resolve_model(model, llm, models)
    if not getattr(target, "supports_vision", False):
        raise HTTPException(
            status_code=400,
            detail=f"模型 {model or '默认'} 不支持图像输入（缺少视觉能力）",
        )
    reply = target.chat_vision(
        [Message(role="user", content=question)], image_data_url=data_url
    )
    return VisionDescribeResponse(description=reply)
```

注意这里 Pydantic 角色的分工：请求侧的文件/表单不走 Pydantic 模型（`UploadFile`/`Form` 由 FastAPI 处理），但**响应侧**用 `VisionDescribeResponse` 序列化——客户端拿到的仍是稳定的 JSON 契约，`/openapi.json` 与 Swagger UI 里也能自动生成文档。

### 6.2 错误码契约：一张表说清所有失败

| 场景 | 状态码 | detail 示例 | 判定依据 |
|------|--------|------------|----------|
| 文件为空 | 422 | `图片为空` | `EmptyImageError` |
| 超过大小上限 | 422 | `图片过大：...字节超过上限...` | `ImageTooLargeError` |
| 不是支持的图片格式 | 422 | `无法识别的图片格式...` | `UnsupportedImageTypeError` |
| 点名的模型没有视觉能力 | 400 | `模型 xxx 不支持图像输入` | `supports_vision` 为 False |
| 点名的模型不存在 | 404 | `未知模型: xxx，可用模型: ...` | `resolve_model`（day039） |

三处 422 共用状态码、detail 区分语义：客户端要么按"重试/裁剪/换格式"分支处理（读 detail），要么统一提示用户图片不合规。400 与 404 的区分延续 day039 的契约哲学——**模型名是"合法字符串但不在候选集"→ 404（资源不存在）；模型存在但能力不匹配 → 400（请求语义错误）**。

### 6.3 与路由层的配合

`resolve_model` 返回的 `target` 可能是：显式点名的单模型（能力检查直接生效，不匹配就 400）、或默认的 `ModelRouter`（它自己实现了 `supports_vision` 过滤与降级，永远不会走到 400 分支）。所以这个 400 分支**只在调用方点名了纯文本模型时触发**——这正是错误码契约里"请求语义与能力不匹配"的精确场景。

### 6.4 测试怎么覆盖这一切

`test_api.py` 的 `TestVisionDescribe` 用 `TestClient` 直接 POST multipart（`files={"file": (filename, content, "image/png")}`），覆盖：正常返回、带问题与显式模型、空文件 422、超限 422、格式 422、纯文本模型 400、未知模型 404、OpenAPI 文档包含新端点。配合 `test_multimodal.py`（模块级 20 个用例）与 `test_router.py`（视觉路由 7 个用例），三层各有一组独立防线——**模块层测工序、路由层测过滤与降级、API 层测协议与契约**。
