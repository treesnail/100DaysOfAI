## 第一部分：选择题

### 第 1 题 —— B

同一句话 `"分块预算决定索引规模。"`（11 个字符）实测：`chars` 给 11，
`cl100k_base` 给 13——**差 18%，而参数名完全一样**。所以单位必须显式化。

但"用哪个单位"与"哪个更准"无关，它们的差别在**确定性**：

```text
chars     只调用 len()                          → 任何机器结果一致
tiktoken  依赖本机是否有词表缓存（day034 的 TokenCounter 会退化成字符级估算）
          → 有缓存 13、没缓存 11，两套结果
```

为什么确定性这么重要：`chunk_id = sha256(doc_id | strategy | index | text)`，
而知识库按 `chunk_id` 去重。同一份文档在两台机器上切出两套 id →
"这条知识为什么重复了两份"变成一个查不出来的问题。

代价是"与计费单位不一致"。要按真实 token 预算时显式切到 `tiktoken`，
并且它会跟着产物走（`ChunkSet.token_measurer`）；本机词表不可用时
`resolve_measurer` **直接报错**，不做静默降级。

顺带记住：`A` 不成立（chars 的实现就是 `len`，但 tiktoken 的慢不在计数本身，
而在首次加载词表）；`C` 是错的（中文按字符算是**高估** token 数还是低估，
取决于编码与模型，本模块不做这种假设）；`D` 是错的（tiktoken 是开源的，本地即可用）。

### 第 2 题 —— C

`chunk_id` 的四个输入缺一不可：

```python
def chunk_id_for(doc_id: str, strategy: str, index: int, text: str) -> str:
    payload = f"{doc_id}|{strategy}|{index}\n{text}".encode("utf-8")
    return hashlib.sha256(payload).hexdigest()[:16]
```

- `A` 成立：四个输入相同 → hash 相同；
- `B` 成立：`doc_id` 是内容指纹（day061 的 `sha256(规范化全文)[:16]`），
  改一个字节它变，于是所有块的 id 都变——这正是"索引要能整批失效重来"的依据；
- **`C` 不成立**：`doc_id` 进了 hash，因此**同一段话在两份文档里得到不同的
  `chunk_id`**。要跨文档识别"同一段内容"，用的是另一个字段
  `Chunk.fingerprint = sha256(text)[:16]`；
- `D` 成立，而这正是把 `index` 放进 id 的理由：只按文本算 id 时，
  工程文档里反复出现的"注意"小节会得到同一个 id，向量库按 id 覆盖，
  "命中了 3 次"在库里只剩 1 条。

两个问题、两个字段：

```text
chunk_id     「这一块是谁」（位置身份，向量库主键）
fingerprint  「这是哪段内容」（内容身份，跨文档去重）
```

`ChunkSet.knowledge_records()` 里 `doc_id` 位置放 `chunk_id`，
`fingerprint` 放进 `metadata`；`ChunkReport.duplicate_chunks()` 用后者
回答"这批块里有多少是重复内容"。

### 第 3 题 —— C

```python
if self.policy.overlap_tokens:
    raise ChunkingError(
        "结构策略不支持重叠（overlap_tokens 必须为 0）："
        "标题边界就是语义边界，跨边界重叠会把上一节内容灌进下一节，"
        "而块的 heading_path 会让它看起来本来就属于这一节"
    )
```

结构策略的块带 `heading_path`，这是它最有价值的产物（检索时靠它补语境）。
而重叠会让一块包含上一节的尾巴——**那条尾巴会挂着新一节的路径**：

```text
块 #3  heading_path = ("检索手册", "成本")
       text 以「…阈值用分位数标定，换 embedding 模型必须重新标定。」开头   ← 属于「检索」节
```

于是引用会指向一个**错误的、而且看起来很合理**的来源。这类错误比"没有来源"
更糟：没有人会去核对一条自洽的引用。所以这里不是"忽略参数"，
而是**报错**——而且报错信息必须说清"为什么"，否则下一个人会去调小 overlap
把它绕过去。

另外三点补充：

- `A` 不对（成本不是理由，报错里没有一个字提钱）；
- `B` 不对：重叠确实会让 `total_chars > doc_chars`（`duplication_ratio > 0`），
  但覆盖率的不变量只要求"原文的非空白字符至少属于一个块"，与重叠无关；
- `D` 不对：标题边界处的重叠长度是可以算的，只是**不该算**。

`base.DEFAULT_POLICIES` 因此是**按策略**给出的表：

```python
STRATEGY_STRUCTURAL: {"max_tokens": 320, "overlap_tokens": 0, "min_tokens": 0},
```

### 第 4 题 —— B

```python
ATOMIC_KINDS: tuple[str, ...] = (BLOCK_CODE, BLOCK_TABLE)
```

超预算的原子块**整块保留**并标记 `oversized`。取舍的依据是两种代价不对称：

```text
切开会得到两块「都不对」的文本     ← 错误隐蔽：两半各自语法不完整、语义不成立，
                                    却会被各自编码、各自检索、各自拼进提示词
不切会得到一个超出预算的块         ← 错误可见：oversized_count 是一个能被统计、
                                    能被报告打印、能进监控的数字
```

实测（同一份文档，预算压到 40）：

```text
structural | 5 块 | 覆盖 98.53% | 重复 0.00% | max 210 chars | 超预算 1
  ! #6 210 字（reason=atom:code）—— 整块保留，不切出残码
```

注意 `oversized` 这个字段的**含义必须唯一**：它表示"不可切且超预算"，
而不是"超过了任何阈值"。本日的缺陷一（见教程第七章）就是它被重叠
占用过——**同一个字段表达两件事，报告就再也说不清是哪种**。

其余选项为什么错：`A` 错（代码块的 token 数当然能算，`token_count` 就是）；
`C` 错（表格渲染是 day061 的事，与这里的取舍无关）；`D` 错
（`oversized` 的块照样入库，它只是需要被看见——**被看见**正是它存在的意义）。

### 第 5 题 —— C

```python
threshold = percentile(similarities, self.policy.similarity_percentile)
breaks = {i for i, s in enumerate(similarities) if s < threshold}
```

`0.7` 这个绝对值在换一个 embedding 提供方之后就换了一个含义：

```text
text-embedding-3-small  上的 0.7 可能是"非常相似"
char-ngram（离线）      上的 0.7 可能是"完全不相干"（它的取值范围与尺度都不同）
另一种语言的语料        上又是另一个含义
```

余弦相似度的绝对值依赖模型的训练目标、向量维度、是否归一化，以及语料语言。
分位数把参数变成**相对判据**：`0.25` 表示"在相似度最低的那 25% 的缝上切"，
它在任何提供方上都表示同一件事。

实测（同一份文档，只改 `similarity_percentile`）：

```text
percentile=0.10 → 5 块 | 阈值 -0.1568 | 断层 4
percentile=0.25 → 5 块 | 阈值 -0.1018 | 断层 6
percentile=0.50 → 5 块 | 阈值  0.0062 | 断层 6
percentile=0.75 → 6 块 | 阈值  0.0492 | 断层 8
```

`A` 错（分位数要排序，反而更贵一点，代价可以忽略）；`B` 错
（浮点数表示与这件事无关）；`D` 错——注意"相对判据"并不随文档长度自动调整，
它随**相似度分布**调整，这两者不是一回事。

## 第二部分：判断题

### 第 6 题 —— 对

```python
@dataclass(frozen=True)
class Span:
    """切分器交给收尾器的中间产物：一段**原文的字符区间** + 切在这里的理由."""
    start_char: int
    end_char: int
    reason: str = ""
    heading_path: tuple[str, ...] = ()
    start_block: int = -1
    end_block: int = -1
    oversized: bool = False
```

`Span` 只带区间，**文本只能由 `document.text[start:end]` 现取**：

```python
def _make_chunk(self, document: Document, span: Span, index: int) -> Chunk:
    text = document.text[span.start_char : span.end_char]
```

于是"块文本是原文的连续子串"这条不变量**没有第二个地方可以违反**——
收尾六步里只有"修剪"和"重叠"会移动区间，而两者都只改 `start_char` / `end_char`，
不改文本。

这与 day061 `make_document` 删掉 `text` 参数是同一种做法：
**让错误的东西无处可写。** 一个可以被写进去的错误值，迟早会被写进去。

### 第 7 题 —— 错

覆盖率判定的是**非空白字符**：

```python
missing = [i for i, ch in enumerate(text) if not covered[i] and not ch.isspace()]
if missing:
    raise ChunkingError("…没有被任何块覆盖…")
```

因此它**允许**略低于 1，差额来自"块首尾的空白被修剪"（两个块之间的空行既不属于
前一块的结尾，也不属于后一块的开头）。这不是放松标准，而是：
**块首尾的空白是噪声，剪掉它是对的。**

而且这个差额有**上界**，所以它是可核对的：

```text
doc_chars - total_chars ≤ 2 × (块数 - 1) + 1
                            ↑ 块间空行      ↑ 原文结尾的换行
```

实测：

```text
fixed      11 块，614 → 612 字符   差额 2（上界 21）
structural  5 块，614 → 605 字符   差额 9（上界 9，正好用满）
```

如果哪天差额远超上界（例如 4 块差 40），那就真的是丢了内容——
**"覆盖率 98% 是否正常"从一个感觉问题变成了一个算术问题。**

另外注意"丢内容"本身是被接口拒绝的：`_assert_spans` 一旦发现未被覆盖的
非空白字符就抛 `ChunkingError`，**不是给一个 `coverage=0.94` 的报告**。
这是 day061「只分类不丢弃」在切分层的对应物。

### 第 8 题 —— 错

去掉 `。`、`，` 这两档的后果不是"效果差不多"，而是**一路退到按字符硬切**——
而且不会有任何报错：

```text
separator_histogram（本项目文档）
  段落      → 10
  换行      → 28
  中文句号   → 9      ← 去掉这一档，段内就没有断点了
  中文逗号   → 10
  英文句号   → 0
```

一份中文技术文档的段落经常有 200~400 字，超过 `max_tokens=320` 的段落并不少。
如果 `。` 不在表里，那些段落就只能：

```text
按 "，" 切 → 有些段落连逗号都很少（图表说明、命令示例）
按 " " 切  → 中文句子之间没有空格
按 "" 切   → 硬切，**每 320 字一刀，与固定长度策略完全一样**
```

也就是说：**递归策略退化成了固定长度策略**，而它的全部卖点（不切在句子中间）
都没了。这种退化的表现只是"块边界变差"，用"sentence in block"之类的
粗糙指标都看不出来。

所以本模块做了两件事：

1. 表里中英标点并列（`。！？；` 与 `. ! ? ;` 都在）；
2. 提供 `separator_histogram()` 让"这份文档为什么退化了"**当场可核对**——
   块长分布告诉你"结果不好"，直方图告诉你"为什么"。

## 第三部分：简答题

### 第 9 题

**1）为什么判定"非空白"字符？**

因为收尾的第一步是**修剪**：每一块的首尾空白都会被去掉（`_trim`），
否则块文本会以 `"\n\n"` 开头——它在 embedding 里贡献不了任何语义，
却会让"引用里显示的那段话"看起来像是从半空中开始的。

修剪必然在块之间留下空白缝隙（两个块之间的空行既不属于前一块的结尾，
也不属于后一块的开头）。如果判定"全部字符"，那么**任何一次正确的修剪都会
被报成丢内容**，于是只有两个选择：不修剪（块文本带空行），或者关掉这条检查
（丢内容就再也发现不了）。两个都更糟。

因此契约的准确表述是：

> 原文里每一个**非空白字符**都必须至少落在一个块里。

**2）差额为什么可核对？上界是什么？**

上界来自"能被修剪掉的空白只有两类"：

```text
doc_chars - total_chars ≤ 2 × (块数 - 1) + 1
                            ↑                  ↑
                     块之间的空行（最多 2 个换行）  原文结尾的换行（规范化补的 1 个）
```

用一份 5 块、614 字符的文档说明：上界 = `2 × 4 + 1 = 9`。

```text
structural   5 块，614 → 605 字符   差额 9 → 用满上界，正常
fixed       11 块，614 → 612 字符   差额 2 → 远小于上界（60 字一块切得密，被剪的都是单换行）
```

所以"覆盖率 98.53%"不再需要凭感觉判断：把 `doc_chars - total_chars` 与
上界比一下就知道。实测数字写进了教程第六章与
`docs/chunking_strategies.md` 第 6 节。

**3）起点严格递增这条检查为什么必须存在？**

它挡的是"窗口没有前进"——切分器切出一块之后，下一块的起点没有往右走。
真实成因有两类：

- 步长 ≤ 0（`overlap_tokens >= max_tokens`）：窗口原地踏步。这条已经在
  `ChunkPolicy.__post_init__` 里被拦下，因此它到不了这里；
- 更隐蔽的一类：**重叠回带 + 修剪的顺序问题**（本日缺陷三）。重叠把下一块的
  起点往回挪，挪过之后落进空白；紧接着的修剪又把两块各自往前推到同一位置：

```text
块的起点必须严格递增，收到 [0, 1, 11, 22, 32, 38, 38, 38, 47, 67, 67, 67, 78, 84]
```

如果去掉这条检查，最坏的结果是"两块起点相同、内容几乎相同"：
表现为**块数暴涨、重复率接近 50%**，而每一个块的字段都合法，
报告里每个数字都"看起来正常"。**那是一种谁都不会去查的回归。**

**4）`_dedupe_starts` 与第 2 条检查是不是重复了？**

不重复，它们守的是两件不同的事：

```text
_dedupe_starts   处理"修剪/回带造成的合法碰撞"——自愈，并记一条 warning
_assert_spans    处理"切分逻辑本身出错"——报错
```

`_dedupe_starts` 只自愈一种情形：**后一块完全包含前一块**。

```python
if (cleaned
        and span.start_char <= cleaned[-1].start_char
        and span.end_char >= cleaned[-1].end_char):
    dropped = cleaned.pop()
    logger.warning("块起点重复（%d），丢弃被包含的那一块 [%d:%d]", …)
```

因为这种情形下丢掉前一块是**安全**的：它的内容被后一块完整覆盖（区间有序、
终点递增），留着它只会带来重复内容与一次多余的 embedding 调用。

其它情形（起点倒退、后一块更短）**必须让 `_assert_spans` 响亮地报错**——
自愈会把"窗口没有前进"这种病变成一堆悄无声息的短块，
那正是第 3 问里说的、最难发现的一类回归。

能自愈不等于不该知道：触发时会记一条 warning，如果它频繁出现，
说明真正的病因在重叠比例（`2 × overlap >= max_tokens`），而不是这一层。

本文给出一套可复现的检索参数。中文标点必须在分隔符表里，否则会退化成硬切。

## 分块

```python
def plan(doc_chars, max_tokens, overlap_tokens):
    step = max_tokens - overlap_tokens
    return 1 if doc_chars <= max_tokens else -(-(doc_chars - max_tokens) // step) + 1
def helper_a():
    return 1
def helper_b():
    return 2

    return 3

@pytest.mark.parametrize("strategy", STRATEGIES)
def test_invariants_hold_for_every_strategy(strategy: str) -> None:
    document = default_registry().load_bytes(
        RICH_MARKDOWN.encode("utf-8"), source="docs/rich.md", media_type="text/markdown"

    policy = ChunkPolicy(strategy=strategy, max_tokens=64, overlap_tokens=0)

def test_budget_scaling_visible_in_the_response() -> None:

要点说明：

- 第 1 组用 `@pytest.mark.parametrize` 扫过四个策略——**同一条不变量写一次、
  在四个判据上各验一遍**，将来新增策略时它会自动覆盖；
- 第 2 组故意让两种策略"打架"：一边必然切碎、一边必然整块保留。
  互补行为被并排钉住之后，"谁把原子块保护去掉了"会立刻变红；
- 第 3 组的四条护栏里，`2 × overlap >= max_tokens` 那一条最值得留意：
  它的两个数各自都合法（`64` 与 `32` 都很正常），只有合起来才是错的；
- 第 4 组走真实端点而不是直接调函数：**要断言的不只是"算出来的参数对"，
  还有"生效的参数能被人看见"**（`stats.metadata.policy`）。

**为什么"未知策略名要列出可选值"值得单独断言？**

因为这两件事在真实使用中的差别是"一分钟"与"一小时"：

```text
KeyError: 'semantic_v2'
  → 用户只知道这个名字不存在。他要去找文档、翻代码、猜正确的名字，
    而且很可能猜错（猜成 semantic_chunk / semantic_splitter / topic …）

UnsupportedStrategy: 没有名为 'semantic_v2' 的分块策略，当前可用：fixed, recursive, structural, semantic
  → 用户当场知道自己写错了哪个词，并拿到四个正确选项
```

这与 day045"未配置密钥时退回 Mock 并告警"、day061"注册表找不到加载器时
列出当前可用的加载器"是同一条纪律：

> **报错信息的第一读者是正在排障的人，而不是写这段代码的人。**

而且它是一条**会被测试守住**的性质：如果哪天有人把 `UnsupportedStrategy`
改成直接抛 `KeyError`（比如把 `registry.get` 换成 `self._chunkers[strategy]`），
这条断言会立刻变红——**这比在注释里写"记得列出候选"可靠得多。**
