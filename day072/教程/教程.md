## 第一章：这一课不是"再写一份 docker-compose.yml"

day022 已经交付过一份 `docker-compose.yml`（MCP Server 那一套）。今天为什么还要一层？

### 1.1 三件 day022 做不到的事

```text
① 那份 yml 没有校验      "容器起来了，但库是空的""镜像不可追溯""探针永远绿"
                         —— 三类事故都能在提交时查出来，却都被留到了部署时
② 没有"该不该动"的判据   语料一份没变也要整库重建一遍（或者反过来：变了却没发现）
③ 没有"能不能服务"的账   容器活着 ≠ 这个实例答得出问题
```

### 1.2 规格、判据、渲染：三者分离

```text
ComposeSpec（数据）→ validate_spec（11 条判据）→ render_compose（确定性文本）
                                                        ↓
                                      docker-compose.rag.yml（进 git，被测试守着）
```

手工写 yml 会得到两种结局：要么它逐渐与事实脱节，要么有人写一个脚本去"猜"
它合不合规——而那种检查永远在报"可能不一致"，会在三天内被人静音。

### 1.3 十步的运行顺序（`pipeline.py`）

```text
① 读账本        SyncLedger.load          （账本不存在 = 首次运行，不是错误）
② 判调度        schedule.decide          （没到点就**结束**，一次编码都不做）
③ 扫语料        snapshot.scan_corpus     （文件只读一遍：快照与文档一起拿）
④ 算差集        sync.plan_sync           （文件级的账：谁变了）
⑤ 定模式        sync.resolved_mode       （变更比例高 → 整库重建）
⑥ 重建索引      indexer.build_from_documents  ← day065 的块级增量在这里
⑦ 落盘          store.persist + versions.persist
⑧ 前进水位      ledger.mark_success / mark_failure
⑨ 体检 + 采样   health.build_health_report / metrics.collect_samples
⑩ 写报告 + 账本 OpsReport.save / ledger.save
```

**十步的顺序不能换**，其中第 ⑦ 步是最容易被省掉、代价最大的一步：
day064 的 `FlatVectorStore` 默认**不落盘**（这是刻意的），而容器化世界里
"进程重启"是常态。因此"重建完索引之后把它写下来"必须发生在编排层——
它是唯一知道"这一次重建是不是完整成功"的那一层。

## 第二章：两级增量 —— 这一课的核心新概念

### 2.1 同一个词，两个问题

"增量"在 M6 里出现过两次，而它们比的**不是同一样东西**：

```text
文件级（今天）   两份语料快照的差集       → "要不要跑这一趟"
                 语料一份没变 → 一行都不写（连解析与分块都不做）

块级（day065）   planner 的四条判据        → "要重算哪些向量"
                 一份文档改一行 → 只重算变了的块（其余判 unchanged，不重新编码）
```

两者缺一不可，理由是一道简单的算术题：

```text
只有块级增量   每天都要把语料全部解析、全部切块，才能知道"哪些块变了"
               —— 省下的是编码，浪费的是解析与分块（这一层最贵的一段）
只有文件级增量 一份 4000 字的文档改一个字，它的十几块全部重新编码
```

### 2.2 差额本身是一条读数（实测）

演示脚本第 5、6 节把这条读数打了出来（3 份语料、共 71 字，全部离线）：

```text
改一份：  文件级 [+0 ~1 -0] 变更比例 33.3%   → 块级 写入 1 / 未变 2 / 删除 1 / 编码 1
改两份：  文件级 [+0 ~2 -0] 变更比例 66.7%   → 块级 写入 3 / 未变 0 / 删除 2 / 编码 2（缓存命中 1）
```

两行数字说的不是一回事：**文件级回答"这次改了几份"，块级回答"这次动了几块"**。
只看前者会以为"改动很小"，只看后者会以为"语料大改"。

### 2.3 差集是纯函数，但它的完备性在构造期校验

```python
def plan_sync(previous: CorpusSnapshot | None, current: CorpusSnapshot) -> SyncPlan:
    ...
    added   = sorted(set(after_map) - set(before_map))
    removed = sorted(set(before_map) - set(after_map))
    for source in sorted(set(before_map) & set(after_map)):
        if before_map[source].fingerprint == after_map[source].fingerprint:
            unchanged.append(source)
        else:
            updated.append(source)
```

四条判据都平凡，真正重要的是 `SyncPlan` 在**构造期**校验的那两条恒等式：

```python
        expected_previous = groups["removed"] | groups["updated"] | groups["unchanged"]
        if expected_previous != set(self.previous_sources):
            raise SyncError(
                "差集没有完全解释上一份快照：…漏掉的来源会静默地留在库里（没人删它），"
                "而它的表象只是“这次改得不多”。"
            )
```

少了这一条会怎样：**漏掉一份来源 = 库里少一条记录**，而没有任何一处报错。
它的表象是"这次改得不多"——与"真的没改多少"长得一模一样。

### 2.4 变更比例的分母是并集

```python
        union = {*self.previous_sources, *self.current_sources}
        if not union:
            return 0.0
        return round(self.changed_count / len(union), 6)
```

为什么不用"当前来源数"做分母：一个"删光了"的目录会得到 `5/0`，
而用并集得到 `1.0`（"这一趟全变了"）——后者才是要传给"要不要整库重建"的数字。

### 2.5 换挡：`suggest_mode` 与 `resolved_mode`

```python
def suggest_mode(plan: SyncPlan, *, threshold: float | None = None) -> str | None:
    limit = settings.rag_ops_churn_full_rebuild if threshold is None else float(threshold)
    if not 0.0 <= limit <= 1.0:
        raise SyncError(f"整库重建阈值必须落在 [0, 1]，收到 {limit}：…")
    if plan.empty:
        return None
    if plan.churn_ratio > limit:
        return BUILD_MODE_FULL
    return None
```

它与 day065 的 `indexing_full_rebuild_threshold` 是**同一个口径的两个使用点**，
而不是重复：那边按**块**算（要不要清空重写库），这边按**文件**算
（要不要连解析与分块都省掉）。实测里两级换挡真的会给出不同答案：

```text
改两份（3 份语料）   文件级 66.7% > 阈值 0.5   → 本层建议整库重建
                     块级  3 条里 2 条要重算（66.7%）→ day065 的换挡看到的是同一件事
```

第 6 节的实测输出把这个决定与它的理由一起打了出来：

```text
变更比例 66.7% 超过阈值，本次按**整库重建**（逐条 upsert 的开销在高变更比例下反而高于清空重写）
```

**建议必须带理由**：报告里读不到"为什么这次走全量"的话，
"走全量"与"忘了换挡"长得一样。

## 第三章：水位与账本

### 3.1 三个时间字段，三种含义

```python
@dataclass(frozen=True)
class SyncLedger:
    snapshot: CorpusSnapshot | None = None   # 水位本体：上一份**成功**的快照
    last_run_at: str = ""                    # 上次**尝试**（成功或失败都写）
    last_success_at: str = ""                # 上次**成功**（只有成功才前进）
    last_index_version: str = ""
    consecutive_failures: int = 0
    runs: int = 0
    failures: int = 0
    last_error: str = ""
```

分不清这三个的后果是具体的：`health` 的"语料新鲜度"检查如果用了 `last_run_at`，
一个"每小时都在跑、每次都失败"的实例会看起来**非常新鲜**。

### 3.2 失败不推进水位

```python
    def mark_failure(self, *, at: str, error: str) -> SyncLedger:
        """记一次失败：**水位不动**、连续失败数 +1、原因留下."""
        if not error:
            raise SyncError("记录失败必须带一条原因：只记'失败了'的账本没有可执行的下一步。")
        return SyncLedger(
            snapshot=self.snapshot,          # ← 关键：水位原样保留
            ...
            consecutive_failures=self.consecutive_failures + 1,
        )
```

一次失败如果推进了水位，失败的那批来源会被**永久跳过**（"已经处理过了"），
而库里少的记录没有任何地方会提醒你。代价是"失败之后同一批来源会被再处理一次"，
而这笔代价可以承受——**重跑幂等，漏更新不幂等**。

### 3.3 账本不进 git（与 day071 的基线相反）

```text
RagBaseline.load   文件不存在 → **报错**   "没有基线"与"基线全是零"是两回事
SyncLedger.load    文件不存在 → 空账本     "没有账本"就是**首次运行**，本来就该全量
```

```python
    @classmethod
    def load(cls, path: str | Path) -> SyncLedger:
        target = Path(path)
        if not target.exists():
            return cls.empty()
        try:
            payload = json.loads(target.read_text(encoding="utf-8"))
        except json.JSONDecodeError as exc:
            raise SyncError(
                f"账本 {str(target)!r} 不是合法 JSON（第 {exc.lineno} 行）："
                "坏账本比没有账本危险——没有账本会全量重跑，坏账本会被当成水位。"
            ) from exc
```

"读不到"与"读不懂"必须分开处理：**前者是首次运行**（正常），
**后者是有一份假账**（危险）。因此 `.gitignore` 里加了一条：

```text
# 账本进了 git 的后果很具体：一次全新的部署会以为"我已经同步过了"，
# 于是第一次运行只做增量——而增量在空库上等于什么都没做。
data/ops/
# day065 的 indexing_dir：清单、版本表与备份（落盘时机由运维层决定）
data/index/
```

## 第四章：调度 —— 四条规定

### 4.1 抖动是算出来的

```python
def jitter_seconds(policy: SchedulePolicy, *, anchor: str, run_index: int) -> int:
    if policy.jitter_seconds <= 0:
        return 0
    digest = hashlib.sha256(f"{anchor}|{int(run_index)}".encode()).hexdigest()
    return int(digest[:8], 16) % (policy.jitter_seconds + 1)
```

用 `random` 的坏处不是"不够随机"，而是**同一次判定的两次调用会给出两个"下一次"**
（报告里一个、端点里一个），而那种不一致会被读成"调度自己改了主意"。
第二个分量用"运行序号"而不是机器名，是为了**可重算**：
换一台机器跑同一份账本，应当得到同一个抖动。

### 4.2 错过窗口只补跑一次，且下一个计划点不漂移

```python
    lag = (now - planned_moment).total_seconds() / 60.0
    missed = int(lag // policy.interval_minutes)
    ...
        notes.append(
            f"其间错过了 {missed} 个计划点（滞后超过一个间隔）：**只补跑这一次**，"
            "不连续补跑——补跑 N 次会连着重建 N 次索引，而语料只需要最新那一份"
        )
    ...
        next_run_at=_next_run_at(
            policy, anchor=anchor, run_index=ledger.runs, intervals=missed + 2
        ),
```

`missed + 2` 这个式子值得盯一眼：当前的触发点是第 `missed + 1` 个间隔，
因此下一个计划点是第 `missed + 2` 个。**关键在于锚点仍然是"计划"**
（`anchor` = 上次尝试时间），而不是"本次实际运行时间"——
否则每次迟到都会把整个调度往后推，几天之后计划时间就漂出了凌晨。

### 4.3 失败退避：指数增长 + 封顶

```python
    def backoff_seconds(self, consecutive_failures: int) -> int:
        if consecutive_failures <= 0:
            return 0
        exponent = min(consecutive_failures - 1, 20)
        return min(self.backoff_base_seconds * (2**exponent), self.backoff_max_seconds)
```

`min(..., 20)` 不是随手加的：无脑左移在 `n` 稍大时就会算出一个天文数字，
而那个数字会被 ceil 成一个"永远不重试"的等待——比退避本身更糟。
封顶（缺省 3600 秒）的意义是"**永远会重试**"。

### 4.4 "没到点"是一个结论，不是失败

```text
not_due    没到计划时间（连语料目录都没碰，账本也不写）
no_change  到点了，但一份来源都没变（一行都没写，水位照常前进）
synced     至少一份来源发生了变化
failed     跑了但失败了（水位不动，原因留在账本与报告里）
```

四档都是**正常返回**而不是异常。把它们实现成异常会逼每个调用点写一次 `try`，
而那些"正常的空转"本来就该出现在报告里——与异常处理混在一起之后，
"这个月跑了 30 次、其中 28 次没变化"这种结论就再也统计不出来。

## 第五章：健康与监控

### 5.1 探活不许跑评估

```text
vector_store        库里有几条记录        0 条 → 它答不了任何知识库问题
index_integrity     清单与库对不对得上     复用 day065 的 verify_index
corpus_freshness    距上次**成功**同步多久  用 last_success_at，不是 last_run_at
quality_regression  质量相对基线退没退化     只读 day071 的结论，一行都不评
```

容器探针每 30 秒被调一次，而一次端到端评估要跑检索 + 生成。把评估挂进探针的后果是：
**提供方一抖动，全部实例会被同一条探针一起摘掉**——一次外部故障变成一次全站故障。

### 5.2 "跳过"永远不是 `ok`

```python
    if manifest is None:
        return HealthFinding(
            check=CHECK_INDEX_INTEGRITY,
            state=STATE_WARN,
            message=(
                "没有清单可比对：这个实例不知道库里的记录是哪一版、由谁建的——"
                "跑一次同步会生成清单（POST /rag/ops/sync）"
            ),
            ...
```

四种"缺输入"都给 `warn`：没有清单、没有基线文件、没有评估结果、没有账本。
与 day071 的"不下结论 ≠ 通过"同源：报告里不许出现一个**看起来没问题**的空洞。

### 5.3 只有"这一秒就在骗人"的事才 `fail`

```text
fail   库是空的 / 清单与库对不上 / 质量门禁判定为回归
warn   从未成功同步过 / 语料偏旧 / 缺清单 / 缺基线 / 缺评估结果
```

`fail` 会让退出码变成 1（`HEALTH_STATE_EXIT_CODES`），编排层据此停止导流量。
把 `warn` 也塞进 `fail`，只会让一个"还没灌库"的新实例永远起不来。

### 5.4 空报告当场报错

```python
    def __post_init__(self) -> None:
        if not self.findings:
            raise HealthError(
                "健康报告不能是空的：'一项都没查'与'全绿'的 state 都是 ok，"
                "交出一份空报告等于宣称这个实例健康。"
            )
```

### 5.5 监控：11 个指标，量不到就不报

```python
def samples_from_quality(quality: RagBaseline | None, *, at=None) -> tuple[MetricSample, ...]:
    """质量侧的四个采样（``None`` 时**返回空**，不是四个 0）."""
    if quality is None:
        return ()
```

这一处最容易被"顺手补全"。一份没有评估过的部署如果上报
`hallucination_rate = 0`，看板会显示"幻觉率 0"——而那句结论没有任何一次测量支撑它。
演示脚本第 8 节把这件事打了出来：7 行指标，`quality_*` 四个**缺席**。

单位由指标名决定（`OPS_METRIC_UNITS`），不由调用方填：同一个指标不可能在
两次采样里带两个单位。方向也一样，且刻意只有两类：

```text
lower_better   同步年龄 / 连续失败数 / 幻觉率 / 坏例率
higher_better  检索召回率 / 接地率
neutral        语料份数 / 变化数 / 写入块数 / 同步耗时 / 库记录数
```

语料份数与库记录数**不给方向**：它们多可能是内容更全，也可能是在灌噪声。
把"多就是好"写进监控，等于给一条迟早会被人手动忽略的告警线。

## 第六章：编排 —— 规格、判据、渲染

### 6.1 三个服务与四个卷

```text
vector-store   chromadb/chroma:1.5.3    卷 chroma-data:/data         探针 /api/v2/heartbeat
rag-api        本项目镜像:<tag>          卷 rag-index:/app/data/index + rag-ops-state:/app/data/ops
                                        + 语料只读卷            探针 /rag/ops/health
rag-ops-sync   本项目镜像:<tag>          同一个索引卷与账本卷；无 HTTP 端口 → 写明探针豁免理由
```

账本刻意挂在**独立的一个卷**（`rag-ops-state`）上，而不是顺手写进索引卷：
两者都能"重建容器后保住"，但生命周期不同——索引可以被整库重建，
而账本一旦丢了，下一次同步就会退化成一次全量（幂等，但昂贵）。

### 6.2 11 条静态判据

```text
R1  三个服务角色齐全                  R7  卷挂载点不覆盖镜像自带的路径
R2  探针与豁免理由二选一              R8  chroma 后端必须 depends_on 向量库
R3  持久卷被挂载且在顶层声明          R9  depends_on 指向真实服务
R4  镜像 tag 可追溯（不得 latest）     R10 命令不得为空串
R5  宿主端口不重复                    R11 顶层卷名合法
R6  环境变量名全大写、值可安全渲染
```

两条判据的取舍值得单独说：

**R2 的形态是"要么有探针、要么写明豁免理由"**，而不是"每个服务都要有探针"：

```python
        if not has_probe and not exempted:
            problems.append(
                f"R2 服务 {service.name!r} 既没有健康探针，也没有写明豁免理由："
                "没有探针的容器在编排层看来永远'活着'，它坏了没人知道。"
            )
        if has_probe and exempted:
            problems.append(
                f"R2 服务 {service.name!r} 同时给了探针与豁免理由："
                "两者只能有一个——同时存在时，读的人不知道该信哪个。"
            )
```

批处理容器（本例的 `rag-ops-sync`）确实没有可探活的 HTTP 面。硬塞一个
`CMD true` 的探针等于把"没有探针"伪装成"探针永远绿"。因此纪律是：
**缺失必须是有意的，并且写下来**。

**R7 不许写成"路径深度 ≥ 2"**：那种规则会把官方 Chroma 镜像推荐的
`/data` 一起拦掉。正确的判据是"不许覆盖镜像自带的路径"：

```python
RESERVED_MOUNT_PREFIXES: tuple[str, ...] = (
    "/bin", "/boot", "/dev", "/etc", "/lib", "/lib64",
    "/proc", "/sbin", "/sys", "/usr", "/var/run",
    "/app/smart_research_agent",
)
```

### 6.3 渲染必须是确定性的

```python
def render_compose(spec: ComposeSpec) -> str:
    """把规格渲染成一份确定性的 compose 文件（**同一份规格永远同一份文本**）."""
```

键按名排序、没有时间戳、没有随机名。收益不是"好看"，而是**可被守住**：

```python
def check_committed_compose(spec: ComposeSpec, path: str | Path) -> str:
    ...
    for index in range(max(len(expected_lines), len(actual_lines))):
        if left != right:
            return (
                f"{str(target)!r} 第 {index + 1} 行与规格渲染结果不一致：\n"
                f"  仓库里：{right}\n"
                f"  规格算：{left}\n"
            )
```

不一致时给出**第一处不同的行号与两行内容**：只报"不一致"的消息
会让人去逐行 diff 一份上百行的 yml，而那条消息本身就该指出现场。

### 6.4 镜像与探针的三个坑

**坑一：镜像 tag 不能是 `latest`。** Chroma 官方文档明确建议固定 tag
（"Avoid relying on latest for production or repeatable environments"），
理由是今天与明天拉到的是两个镜像，而配置看起来一模一样。

**坑二：容器里的启动命令不能照抄本地入口。** `python -m smart_research_agent.api.app`
的 `main()` 绑的是 `127.0.0.1:8000`——本地开发的正确默认值，而在容器里
宿主机的端口转发**一个包都进不来**。表现是"容器 healthy、端口开着、请求超时"，
日志里什么都没有。因此容器用 uvicorn 的 factory 模式：

```python
API_COMMAND: tuple[str, ...] = (
    "python", "-m", "uvicorn",
    "smart_research_agent.api.app:create_app", "--factory",
    "--host", "0.0.0.0", "--port", str(API_CONTAINER_PORT),
)
```

**坑三：探针路径要探"能不能服务"，而不是"进程活没活"。**
`/health` 答后者，`/rag/ops/health` 答前者——容器编排关心的是前者。

## 第七章：接入与实测

### 7.1 三个端点的状态码约定

| 端点 | 状态码 | 说明 |
|------|--------|------|
| `GET /rag/ops/status` | 200 | 四块只读内容，0 次模型调用、0 次写盘 |
| `GET /rag/ops/health` | **200 / 503** | `fail` → 503（探针靠它工作） |
| `POST /rag/ops/sync` | 200 / 400 / 503 | 200 = 有结论（含 `failed`）；400 = 跑不了；503 = 没装配流水线 |

**`/rag/ops/health` 必须用状态码表达失败**：

```python
    report = pipeline.health_report()
    if report.state == STATE_FAIL:
        response.status_code = 503
```

理由很朴素：`docker-compose.rag.yml` 里的探针是 `curl -f`，而 `curl -f`
**只看状态码**。永远返回 200 的探针等于没有探针。

**`/rag/ops/sync` 的运行失败仍然是 200**：四档状态塞进状态码会让
"没到点"与"同步失败"在监控里长得一样，而它们的处置完全不同。
真正的"跑不了"（账本损坏、语料目录没配对）走 400——那才是调用方要改的东西。

### 7.5 顺带修了一个"有保质期"的测试

全量回归第一次跑出 **6 个失败**，全部在 `tests/test_registry_api.py`
（day058 的模型版本注册表端点），而它们的报错是：

```text
FAILED tests/test_registry_api.py::test_candidate_gain_above_threshold_promotes
  AssertionError: assert 'hold' == 'promote'
  → 被拦下：候选年龄 185.56h 超过 168.0h 上限
```

这与今天的改动无关，`day071` 的快照里同样失败（在 `day071/源码` 下单独跑
那个文件也是 `6 failed, 44 passed`）。根因是一行常量：

```python
FRESH = "2026-09-16T00:00:00+00:00"          # ← 写死的日期
```

候选版本的"新鲜度"由 `settings.retrain_max_candidate_age_hours = 168`（7 天）
判定，而这个常量在 **2026-09-23 之后就过期了**——从此所有"应当 promote"的
用例都会变成 `hold`，报错看着像产品代码出了问题。

修法是让它相对当前时刻算：

```python
FRESH = (datetime.now(timezone.utc) - timedelta(hours=1)).isoformat()
```

**可以带走的结论**：一个按真实时钟判定的测试有一个**保质期**，
而写死的日期把这个保质期藏进了字面量里。凡是"相对时间"的判据，
测试里的时间基准就必须相对当前时刻算——这与本课 `FakeClock` 的取舍是同一条：
**让时间成为入参，而不是环境**。

## 第八章：这一课踩到的三个坑

### 8.1 两个 `IndexVersionStore` 指向同一目录（不报错）

第一版装配是这样的：`default_indexing_pipeline()` 给构建器建一份版本表，
运维层**又**建了一份指向同一目录的版本表，用来回答"当前生效的是哪一版"。

```text
构建器 register 到**它自己**内存里的表  →  运维层那份仍然是空的
→ current_manifest() 永远返回 None（"清单丢了"）→ 体检只会报"没有清单"
而磁盘上其实躺着一份完整的清单
```

它不报错、只让体检的结论偏保守，因此几乎没有症状。修法是让运维层
**从构建器手里取**那份版本表：

```python
    versions = resolved_indexer.versions   # 不是 IndexVersionStore(path=...)
```

为此给 `IndexingPipeline` 加了一个只读属性：

```python
    @property
    def versions(self) -> IndexVersionStore | None:
        """构建器手里的那份版本表（**只读用途**：运维层要读"当前生效的是哪一版"）."""
        return self._versions
```

**可以带走的结论**：当两个对象"指向同一个东西"时，它们迟早会分家。
把它变成**同一个引用**，是唯一不需要靠人记得同步的写法。

### 8.2 `Path("")` 等于 `Path(".")`（会把整个仓库当语料）

```python
    raw = str(root or "").strip()
    if not raw or raw == ".":
        raise SyncError(
            f"语料根目录不能是空串或 '.'（收到 {raw!r}）：请显式给一个目录，"
            "或配置 rag_ops_source_dir——否则同步会拿进程当前目录当语料。"
        )
```

第一版的检查是 `if not str(path)`，而 `Path("")` 的字符串是 `"."`——**永远为真**。
于是在仓库根目录跑一次同步，`pyproject.toml`、测试文件与文档会被一起灌进库里
（它们全都是合法的 markdown 与文本）。这个坑是在写测试时才被发现的：
一条"空目录应该报错"的用例，实际跑了十几秒（它在扫整个仓库）。

### 8.3 一条规则不许有两处实现

R7 最初包含了"挂载点不能是容器根目录 `/`"。而 `VolumeMount` 的构造期
已经拒绝了它——`if self.target.endswith("/")` 会先命中 `/`。

两处实现并存时，`validate_spec` 里那一段是**死代码**：它永远不会触发，
但会让"这条规则由谁负责"变成一个需要读两个文件才能回答的问题。
修法是删掉重复的那一处，并在原处留一句说明：

```python
    # R7 挂载点不能覆盖镜像自带的目录
    # （挂到根目录 "/" 在 VolumeMount 的**构造期**就被拒了，因此这里不重复判它：
    #  同一个规则有两处实现时，两处迟早会对同一份输入给出不同的结论。）
```

这与 day071 的"指标口径只有一份实现"是同一条纪律，只是这次触发它的
不是"两个函数算同一个指标"，而是"两个层次判同一条规则"。

## 第九章：今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 增量分两级 | 文件级回答"要不要跑"，块级回答"重算哪些" | `sync.plan_sync` + day065 `planner` |
| 差集的完备性在构造期校验 | 漏一份来源 = 库里少一条记录，而没有报错 | `SyncPlan` 的两条恒等式 |
| 变更比例用并集做分母 | "删光了"的目录用当前数做分母会得到 5/0 | `SyncPlan.churn_ratio` |
| 换挡建议必须带理由 | "走全量"与"忘了换挡"长得一样 | `sync.resolved_mode` |
| 抖动是算出来的 | 两次调用给出两个"下一次"会被读成"调度改了主意" | `schedule.jitter_seconds` |
| 下一个计划点按计划算 | 从实际运行时间起算会让计划点逐日漂移 | `decide` 的 `missed + 2` |
| 退避指数增长且封顶 | 无脑左移会算出一个"永远不重试"的等待 | `SchedulePolicy.backoff_seconds` |
| 失败不推进水位 | 推进了就会永久跳过一批来源（漏更新不报错） | `SyncLedger.mark_failure` |
| 账本不进 git | 进了 git 的全新部署会以为"我同步过了" | `.gitignore` + `SyncLedger.load` |
| 读不到 ≠ 读不懂 | 前者是首次运行，后者是有一份假账 | `SyncLedger.load` 的两条分支 |
| 空转不覆盖证据 | `last_report` 要是"上次真实运行"的结果 | `_finish(persist=False)` |
| 探活不跑评估 | 否则提供方一抖动会摘掉全部实例 | `health.build_health_report` |
| 跳过不是通过 | 缺输入给 warn，不假装 ok | 四项检查的四种"缺输入" |
| 空报告当场报错 | "一项都没查"与"全绿"都是 ok | `HealthReport.__post_init__` |
| 没量到不写 0 | 0 会被读成"幻觉率 0，很好" | `samples_from_quality` 返回空 |
| 单位由指标名决定 | 同一个指标不许在两次采样里带两个单位 | `OPS_METRIC_UNITS` |
| 描述性指标不给方向 | 把"多就是好"写进监控 = 一条迟早被忽略的告警 | `MetricSample.direction` |
| 探针用状态码表达失败 | `curl -f` 只看状态码 | `/rag/ops/health` 的 503 |
| 运行失败仍是 200 | 四档状态塞进状态码会让"没到点"与"失败"同形 | `/rag/ops/sync` 的注释 |
| 缺失必须是有意的 | 批处理容器没有探针，但必须写明理由 | `ServiceSpec.probe_exempt` |
| 判据不许写成"路径深度" | 那种规则会拦掉官方镜像推荐的 `/data` | `RESERVED_MOUNT_PREFIXES` |
| 渲染必须确定性 | 否则"与仓库文件不一致"这条检查会永远在报 | `render_compose` |
| 编排文件由规格渲染 | 手改 yml 会当场变红，而不是带着偏配置上线 | `check_committed_compose` |
| 容器入口不能照抄本地 | 绑 127.0.0.1 的入口在容器里一个包都进不来 | `API_COMMAND` |
| 状态必须落盘且顺序不能反 | 版本表是"库应该长什么样"的声明 | `_persist_state` |
| 一条规则只有一处实现 | 两处实现迟早对同一份输入给出不同结论 | R7 与 `VolumeMount` 的分工 |
| 同一个东西只有一个引用 | 两个 `IndexVersionStore` 会让运维层永远读不到清单 | `IndexingPipeline.versions` |
| 时间基准必须相对当前时刻 | 写死日期的测试有一个藏在字面量里的保质期 | `tests/test_registry_api.py` 的 `FRESH` |
