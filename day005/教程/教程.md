## 第一章：问题引入 —— 散件状态的两大痛点

### 1.1 现状盘点

经过前两天，我们手里有：

```text
smart_research_agent/
├── agent/
│   └── react_agent.py      # ReactAgent 骨架（day003）
└── tools/
    ├── base.py             # BaseTool 契约（day004）
    └── calculator.py       # CalculatorTool（day004）
```

看起来不错，但如果现在要写 Agent 的主循环，马上会遇到两个具体的问题。

### 1.2 痛点一：Agent 怎么知道自己有哪些工具？

ReAct 循环里，Agent 要做两件与工具相关的事：

1. **告诉 LLM 有哪些工具可用**——把工具名和描述拼进 system prompt；
2. **根据 LLM 输出的工具名找到对应工具并执行**——`Action: calculator` 这行文本要能路由到 `CalculatorTool` 实例。

最直觉的写法是硬编码：

```python
# 反例：硬编码工具路由
from smart_research_agent.tools.calculator import CalculatorTool


def execute_action(action: str, action_input: str) -> str:
    if action == "calculator":
        return CalculatorTool().execute(expression=action_input)
    elif action == "search":
        return SearchTool().execute(query=action_input)
    # ... 每加一个工具就要回来改这个函数
    raise ValueError(f"未知工具: {action}")
```

这种写法在 demo 里能跑，但作为要迭代 100 天的系统，它有四个结构性缺陷：

- **违反开闭原则**：每新增一个工具，都要修改 Agent 的核心路由代码。"对扩展开放、对修改关闭"被反过来写了。
- **无法动态生成工具清单**：prompt 里的工具列表和路由里的 `if/elif` 是两份手写代码，迟早不同步——prompt 里说有 `search` 工具，路由里忘了加，LLM 一调用就报错。
- **没有去重防线**：两个人各写了一个叫 `search` 的工具，后写的悄悄覆盖语义，排查起来极其痛苦。
- **无法测试**：想测试"Agent 只有一个计算器工具时的行为"，得改源码注释掉别的分支。

### 1.3 痛点二：LLM 调用写死在业务代码里

另一个直觉写法是直接调 SDK：

```python
# 反例：Agent 直接依赖具体 SDK
from openai import OpenAI


class ReactAgent:
    def run(self, task: str) -> str:
        client = OpenAI(api_key="sk-xxx")
        resp = client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": task}],
        )
        return resp.choices[0].message.content
```

问题同样明显：

- **换模型 = 改业务代码**：明天想换成 DeepSeek 或本地 vLLM 部署的开源模型，要翻遍所有 `OpenAI(...)` 出现的地方。
- **无法离线测试**：每次跑测试都真实调 API——慢（秒级延迟）、花钱（按 token 计费）、不确定（模型输出每次不同，断言没法写）。
- **配置泄露风险**：`api_key` 硬编码进代码，day001 讲的配置管理全部白做。

这两个痛点的解法，就是今天的两个主角：**注册表模式**解决工具管理，**依赖倒置 + Mock** 解决 LLM 调用。我们逐一来看。

## 第二章：注册表模式 —— 工具的集中管理

### 2.1 什么是注册表模式

注册表（Registry）模式的思想一句话就能说完：**用一个中心化的容器保存"名字 → 对象"的映射，所有存取都经过这个容器。**

它在软件工程里无处不在：

| 系统 | 注册表 | 注册的"名字 → 对象" |
|------|--------|---------------------|
| DNS | 域名服务器 | 域名 → IP 地址 |
| pytest | fixture 注册表 | fixture 名 → 工厂函数 |
| Web 框架 | 路由表 | URL 路径 → 视图函数 |
| 我们的 Agent | `ToolRegistry` | 工具名 → `BaseTool` 实例 |

注意 pytest 你其实已经用过这个模式了：day002 讲过，测试函数签名里写 `monkeypatch`，pytest 去它的注册表里找到同名 fixture 并注入。今天我们自己实现一个。

### 2.2 硬编码路由 vs 注册表

在写代码前，先把两种范式摆在一起对比，理解我们到底买到了什么：

| 维度 | 硬编码 if/elif 路由 | 注册表模式 |
|------|---------------------|-----------|
| 新增工具 | 修改 Agent 路由代码 | `registry.register(NewTool())`，一行 |
| 工具清单（给 LLM 看） | 手写第二份，易与路由不一致 | `registry.describe()` 自动生成，永远同步 |
| 重名工具 | 静默覆盖或分支冲突 | 注册时抛 `ValueError`，失败趁早 |
| 非法对象混入 | 无防护 | 注册时抛 `TypeError`，类型校验前置 |
| 测试隔离 | 要改源码 | 每个测试新建一个 `ToolRegistry()` |
| 运行时插件化 | 不可能 | 未来可从配置/入口点动态加载 |

核心收益：**工具集合从"编译期写死"变成"运行期数据"**。一旦工具集合是数据，遍历它生成 prompt、校验它、按测试需要定制它，都是自然而然的事。

### 2.3 ToolRegistry 实现

[完整代码](../源码/smart-research-agent/smart_research_agent/tools/registry.py)

```python
class ToolRegistry:
    """集中管理 Agent 可用的工具."""

    def __init__(self) -> None:
        self._tools: dict[str, BaseTool] = {}

    def register(self, tool: BaseTool) -> None:
        if not isinstance(tool, BaseTool):
            raise TypeError("只能注册 BaseTool 的实例")
        if tool.name in self._tools:
            raise ValueError(f"工具重复注册: {tool.name}")
        self._tools[tool.name] = tool
        logger.info("注册工具: %s", tool.name)
```

三个设计决策值得细看：

#### （1）内部就是一个 dict

不要小看这个"普通"的实现。`dict[str, BaseTool]` 给了我们 O(1) 的名字查找，这正是注册表存在的意义。工程里大量"模式"落地后都是朴素的数据结构，价值在于**约束了所有访问必须经过统一入口**，而不在于数据结构本身多精巧。

#### （2）注册时校验，而非使用时校验

两道防线都放在 `register` 里：

- `isinstance(tool, BaseTool)`：保证注册进来的东西一定满足 day004 定义的契约——有 `name`、有 `description`、有 `execute`。不满足？现在就知道，而不是等 Agent 在 ReAct 循环第 7 步调用时才 `AttributeError`。
- 重名检查：工具名是 LLM 输出路由的唯一依据，重名等于让 LLM 的 `Action: search` 变得有歧义。直接在注册时拒绝。

这是 day001 学过的**失败要趁早（Fail Fast）**原则的又一次应用：错误暴露的位置离错误产生的位置越近，调试成本越低。

#### （3）注册动作写日志

```python
logger.info("注册工具: %s", tool.name)
```

一行日志，换来的是"系统启动时到底加载了哪些工具"的完整可观测性。将来工具多到十几个、从配置文件动态加载时，你会感谢这行日志。

### 2.4 查询与导出接口

注册表对外提供四个只读接口：

```python
def get(self, name: str) -> BaseTool | None:
    return self._tools.get(name)

def list_tools(self) -> list[BaseTool]:
    return list(self._tools.values())

def schemas(self) -> list[dict]:
    return [t.to_schema() for t in self._tools.values()]

def describe(self) -> str:
    """生成给 LLM 阅读的工具清单文本."""
    return "\n".join(f"- {t.name}: {t.description}" for t in self._tools.values())
```

注意分工：

- `get` / `list_tools`：**给代码用**——ReAct 循环用 `get(step.action)` 路由工具调用。找不到时返回 `None` 而不是抛异常，因为"LLM 输出了一个不存在的工具名"是运行时常态（模型会幻觉），应该由调用方决定如何处理（day006 会把这个错误信息喂回给 LLM 让它自我修正）。
- `schemas` / `describe`：**给 LLM 用**——`describe()` 生成纯文本清单拼进 prompt，`schemas()` 导出 JSON Schema 列表，将来 M4 迁移到原生 Function Calling 接口时直接用。

`describe()` 的实际输出长这样：

```text
- calculator: 计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'
```

每一行都来自工具自己的 `name` 和 `description`——**工具自我描述，注册表负责聚合**。新增工具时 prompt 内容自动更新，这就是 2.2 节说的"永远同步"。

> 思考题：`get()` 为什么返回 `None` 而不是抛 `KeyError`？对比一下 day008 将要学的 `SessionManager.get_memory()`，它对未知会话选择抛 `KeyError`。同为注册表式查询，设计为何不同？  
> 提示：想一想两种"查不到"各自的来源——一个来自不可信的 LLM 输出（常态、可恢复），一个来自调用方自己的代码错误（异常、应暴露）。

## 第三章：依赖倒置原则 —— Agent 不认识任何具体模型

### 3.1 依赖倒置原则（DIP）

SOLID 五大原则中的 D，定义是：

> 高层模块不应该依赖低层模块，两者都应该依赖抽象；抽象不应该依赖细节，细节应该依赖抽象。

翻译到我们的场景：

- **高层模块**：`ReactAgent`——它关心的是"把消息发出去，拿回文本回复"这个能力。
- **低层模块**：OpenAI、DeepSeek、本地 vLLM……具体怎么发 HTTP 请求、怎么鉴权，Agent 根本不关心。
- **抽象**：`BaseLLM`——一个 `chat(messages) -> str` 的承诺。

没有抽象时，依赖方向是"高层 → 低层"：Agent 直接 import OpenAI SDK，换模型就得改 Agent。引入抽象后，低层模块反过来依赖抽象（要实现 `BaseLLM` 定义的接口），依赖方向被"倒置"了：

```text
没有抽象（依赖自上而下）：

  ReactAgent ──依赖──▶ OpenAI SDK ──依赖──▶ OpenAI API
      │ 换模型 = 改这里

依赖倒置后（双方都依赖抽象）：

  ReactAgent ──依赖──▶ BaseLLM ◀──实现── OpenAICompatibleLLM
                            ▲
                            ├──实现── MockLLM（测试）
                            └──实现── 未来：LocalModelLLM（M4）
```

"倒置"指的就是右边那个朝上的箭头：具体实现不再是被依赖的终点，而是反过来去满足抽象定义的契约。

### 3.2 为什么这让替换模型零成本

关键在于：**`BaseLLM` 归我们所有，不由任何厂商定义。**

因为抽象是我们定义的，它就稳定——`chat(messages, temperature, max_tokens) -> str` 这个签名不随任何厂商的 SDK 升级而变化。于是：

- 换模型供应商：新写一个 `BaseLLM` 子类，Agent 一行不改；
- M4 做模型路由：实现一个 `RouterLLM(BaseLLM)`，内部按策略转发给不同后端，Agent 依然无感；
- M5 微调出专属模型：实现 `FinetunedLLM(BaseLLM)` 指向自己的部署端点，即插即用。

这就是"零成本替换"的准确含义：**替换的成本被收敛到"新增一个文件"，而不是"修改所有调用方"。**

### 3.3 BaseLLM 与 Message 的定义

[完整代码](../源码/smart-research-agent/smart_research_agent/llm/base.py)

```python
class BaseLLM(ABC):
    """大模型调用的统一抽象.

    Agent 层只依赖 BaseLLM，不关心底层是哪家模型（依赖倒置原则）。
    """

    @abstractmethod
    def chat(
        self,
        messages: list[Message],
        temperature: float = 0.7,
        max_tokens: int = 1024,
    ) -> str:
        """发送对话消息，返回模型的文本回复."""
```

接口设计的取舍：

- **入参是 `list[Message]` 而不是一个 prompt 字符串**：对话是有结构的（system/user/assistant），压平成字符串会丢失角色信息，也就无法支撑多轮 ReAct 循环。
- **返回 `str` 而不是厂商的响应对象**：`resp.choices[0].message.content` 是 OpenAI 的结构，别的厂商结构不同。在抽象边界上就把响应"归一化"成纯文本，上层永远不需要知道响应体长什么样。
- **`temperature` / `max_tokens` 带默认值**：这是所有主流 LLM API 的最大公约数参数。不暴露 `top_p`、`frequency_penalty` 之类的参数——抽象接口只保留所有实现都能满足的部分，特殊参数将来可以通过子类构造函数注入。

## 第四章：Message —— 对话即协议

### 4.1 三种角色的语义

```python
@dataclass
class Message:
    """一条对话消息.

    role 取值: "system" | "user" | "assistant"
    """

    role: str
    content: str

    def to_dict(self) -> dict[str, str]:
        return {"role": self.role, "content": self.content}
```

为什么恰好是三种角色？因为它们对应一次人机协作中的三个信息来源：

| 角色 | 语义 | 谁写的 | 类比 |
|------|------|--------|------|
| `system` | 行为契约：你是谁、遵守什么格式、有哪些工具 | 开发者 | 给员工发的岗位说明书 |
| `user` | 任务与反馈：用户提问、工具执行结果（Observation） | 用户 / 系统回填 | 客户提需求、同事反馈进展 |
| `assistant` | 模型的历史回复 | 模型自己（的历史输出） | 员工之前说过的话 |

关键洞察：**`assistant` 消息是模型自己输出的回放**。多轮对话中，模型并没有"记住"自己说过什么——是我们在每次请求时把它之前说过的话原样带回去。理解了这一点，就理解了为什么 ReAct 循环要把每一轮的原始输出 append 进 messages（day006 会做）：

```text
第 1 轮请求: [system, user(任务)]
第 2 轮请求: [system, user(任务), assistant(LLM第1轮输出), user(Observation)]
第 3 轮请求: [system, user(任务), assistant(...), user(...), assistant(...), user(...)]
              ────────────────── 上下文单调增长 ──────────────────
```

也由此可以推出两个重要结论：

1. **上下文长度就是成本**：每多一轮，请求体就变大，token 计费随之上涨。这正是 day008 短期记忆要做截断的原因。
2. **Observation 伪装成 user 消息**：工具执行结果以 `user` 角色回填给模型。这是 ReAct 的标准做法——对模型来说，"工具的输出"和"用户说的话"都是外部输入。

### 4.2 为什么用 dataclass 而不是 dict

OpenAI API 本身接受的就是 dict，为什么我们多包一层 `@dataclass`？

- **类型安全**：`Message(role="user")` 少了 `content` 会立刻报错；dict 少个 key 要到 API 返回 400 才知道。
- **IDE 友好**：`message.content` 有自动补全；`message["contnet"]` 拼错了运行时才发现。
- **演进锚点**：将来消息要携带工具调用信息（M4 的 function calling）、token 计数（M4 的成本追踪），dataclass 上加字段即可，dict 则要全局搜索所有构造点。
- **`to_dict()` 是防腐层**：只在调用厂商 SDK 的边界上才转成 dict，内部流转始终是强类型对象。

> 思考题：`Message.role` 的类型注解是 `str`，意味着 `Message(role="systme")`（拼写错误）也能构造成功。如果想让这种错误在构造时就暴露，你会怎么改进？（提示：`Literal` 类型或枚举。为什么规格里没这么做？想想 M2 阶段 MCP 协议可能引入的新角色。）

## 第五章：OpenAI 兼容 API —— 一次实现，处处可用

### 5.1 "OpenAI 兼容"为什么成为事实标准

OpenAI 的 Chat Completions API 结构已经成为行业事实标准。DeepSeek、通义千问、Moonshot、智谱，以及 vLLM / Ollama 等本地推理框架，全都提供与之兼容的端点。这意味着：

**只要我们的代码面向"OpenAI 兼容协议"写，换一个 `base_url` 就能切换到几乎所有主流模型。**

核心请求结构：

```json
POST {base_url}/chat/completions
{
  "model": "gpt-4o-mini",
  "messages": [
    {"role": "system", "content": "你是一个..."},
    {"role": "user", "content": "2+3 等于几？"}
  ],
  "temperature": 0.7,
  "max_tokens": 1024
}
```

响应里取 `choices[0].message.content` 即模型回复。我们前面把 `Message.to_dict()` 设计成恰好输出 `{"role", "content"}`，就是为了无缝喂给这个结构。

### 5.2 配置注入：新增 openai_base_url

要支持"切换 base_url 即切换供应商"，配置层先加一个字段。day001 的 `Settings` 新增一行（[完整代码](../源码/smart-research-agent/smart_research_agent/config.py)）：

```python
openai_api_key: str | None = None
openai_base_url: str | None = None   # 新增：None 表示使用 OpenAI 官方端点
default_model: str = "gpt-4o-mini"
```

环境变量 `OPENAI_BASE_URL` 会自动映射到这个字段（Pydantic Settings 的默认行为）。于是切换供应商变成了纯配置操作：

```text
# .env —— 使用 DeepSeek 时
OPENAI_API_KEY=sk-deepseek-xxx
OPENAI_BASE_URL=https://api.deepseek.com/v1
DEFAULT_MODEL=deepseek-chat
```

代码零改动。这正是 day001"配置与代码分离"原则今天结出的果实。

### 5.3 OpenAICompatibleLLM 实现

[完整代码](../源码/smart-research-agent/smart_research_agent/llm/openai_compatible.py)

```python
class OpenAICompatibleLLM(BaseLLM):
    """通过 OpenAI SDK 调用任何 OpenAI 兼容端点."""

    def __init__(
        self,
        api_key: str | None = None,
        base_url: str | None = None,
        model: str | None = None,
    ):
        self._client = OpenAI(
            api_key=api_key or settings.openai_api_key or "sk-missing",
            base_url=base_url or settings.openai_base_url,
        )
        self._model = model or settings.default_model
```

构造函数体现了清晰的**配置优先级链**：

```text
显式传参  >  环境变量/配置文件（settings）  >  兜底默认
```

为什么要允许显式传参覆盖全局配置？两个场景：

1. **测试**：`OpenAICompatibleLLM(api_key="sk-test", model="test-model")` 可以脱离环境变量构造对象，测试不被本机环境污染（day002 讲的 Repeatable 原则）。
2. **多模型并存**：M4 做模型路由时，同一个进程里可能同时存在两个实例——一个指向便宜模型处理简单任务，一个指向强模型处理难题。全局单一份配置不够用。

`chat` 方法是直接的协议翻译：

```python
def chat(self, messages, temperature=0.7, max_tokens=1024) -> str:
    resp = self._client.chat.completions.create(
        model=self._model,
        messages=[m.to_dict() for m in messages],
        temperature=temperature,
        max_tokens=max_tokens,
    )
    return resp.choices[0].message.content or ""
```

两个细节：

- `[m.to_dict() for m in messages]`：强类型 `Message` 在边界处转为 dict，内部世界与厂商协议的翻译只发生在这一行。
- `or ""`：模型有时返回 `content=None`（比如只返回工具调用时）。归一化成空字符串，保证抽象承诺的 `-> str` 返回值永远成立，上层不必处理 `None`。

## 第六章：MockLLM —— 可测试性的地基

### 6.1 为什么单元测试绝不能依赖真实 LLM

假设我们的测试真的去调 OpenAI API，会发生什么：

| 问题 | 具体表现 | 违反的原则（day002） |
|------|----------|----------------------|
| 慢 | 每次调用 1~10 秒网络往返，几十个测试跑几分钟 | **F**ast |
| 花钱 | 每次 CI 跑测试都消耗 token，日积月累是真金白银 | 成本失控 |
| 不确定 | 模型输出是概率性的，同一个输入今天说"等于 5"明天说"答案是五" | **R**epeatable |
| 依赖外部环境 | 没网、没 API Key、供应商宕机时测试全红 | **I**ndependent |
| 无法构造边界场景 | 想测"LLM 输出格式错误时 Agent 怎么办"？你没法命令真实模型故意犯错 | 测试覆盖不全 |

结论：**真实 LLM 属于集成测试/E2E 测试的范畴，单元测试必须用假的。** 这就是测试金字塔里"单元测试要快要稳"在 AI 项目里的具体含义。

### 6.2 脚本式 Mock 的设计

[完整代码](../源码/smart-research-agent/smart_research_agent/llm/mock.py)

```python
class MockLLM(BaseLLM):
    """按预设脚本回复的 LLM，用于无网络、无 API Key 的测试环境."""

    def __init__(self, responses: list[str] | None = None, default: str = "mock response"):
        self._responses = list(responses or [])
        self._default = default
        self.calls: list[list[Message]] = []

    def chat(self, messages, temperature=0.7, max_tokens=1024) -> str:
        self.calls.append(messages)
        if self._responses:
            return self._responses.pop(0)
        return self._default
```

三个机制各有用途：

#### （1）`responses`：剧本队列

每次 `chat` 弹出队列头部的一条作为回复。这让测试可以**精确导演一场多轮对话**：

```python
llm = MockLLM(responses=[
    "Thought: 需要先计算\nAction: calculator\nAction Input: 2+3",   # 第 1 轮：决定调工具
    "Thought: 已得到结果\nFinal Answer: 2+3 等于 5",                # 第 2 轮：给出答案
])
```

day006 的 ReAct 循环端到端测试，靠的就是这个机制——测试完全确定，跑一万次结果都一样。

#### （2）`default`：剧本耗尽后的兜底

队列空了还继续调用，返回固定兜底串而不是抛异常。理由：测试"达到最大步数"这类场景时，我们关心的是循环的终止行为，不想为每一步都写剧本。

#### （3）`calls`：交互记录器

每次调用都把入参 `messages` 存下来。这让测试可以断言**过程**而不仅是**结果**：

```python
def test_records_calls(self):
    llm = MockLLM()
    llm.chat([Message(role="user", content="你好")])
    assert llm.calls[0][0].content == "你好"
```

day006 会用它验证"工具报错后，错误信息确实被喂回给了 LLM"——断言第二次调用的 messages 里包含错误 Observation。这种"验证系统间交互"的能力，是普通返回值断言做不到的。

### 6.3 Mock 是依赖倒置的试金石

注意一个顺理成章的事实：`MockLLM` 能存在，恰恰因为 `BaseLLM` 抽象存在。如果 Agent 直接依赖 OpenAI SDK，测试时就得用 monkeypatch 去替换 SDK 内部的 HTTP 层——脆弱且啰嗦。

这给了我们一个经验法则：**一段代码好不好测试，是检验其抽象设计好坏的最快方法。** 写不出干净的 Mock，往往说明依赖方向错了。测试不是开发的附属品，而是架构的探针。

## 第八章：今日总结

| 能力 | 原理核心 | 落地位置 |
|------|----------|----------|
| 工具注册表 | 注册表模式、注册时校验（Fail Fast）、自我描述聚合 | `tools/registry.py` |
| LLM 抽象 | 依赖倒置原则、接口归一化（进 `Message` 出 `str`） | `llm/base.py` |
| 会话协议 | system/user/assistant 三角色、上下文单调增长 | `llm/base.py` 的 `Message` |
| 兼容 API 接入 | 配置优先级链、base_url 切换供应商 | `llm/openai_compatible.py`、`config.py` |
| 离线可测试 | 剧本队列 + 兜底 + 交互记录 | `llm/mock.py` |

今天的主线是一句话：**把"会变的东西"（工具集合、模型供应商）关进抽象的笼子里，让"不变的骨架"（Agent 循环）对变化免疫。**

明天（day006）是 M1 阶段的第一个高潮：把今天的 `ToolRegistry` 和 `BaseLLM` 接进 `ReactAgent`，实现完整的 ReAct 循环——Thought → Action → Observation，并用 `MockLLM` 的剧本机制做端到端测试。今天所有的"为什么"，明天都会变成"原来如此"。
