## 第一部分：选择题

### 第 1 题（评估即测试）

LLM 项目的 CI 为什么必须在单元测试之外再加评估门禁？最根本的原因是：

- A. 单元测试运行太慢，需要评估脚本分担压力
- B. 单元测试验证机制的正确性，但无法发现提示词修改、模型更换导致的行为品质退化

- D. GitHub Actions 要求至少包含一个评估步骤才能通过检查

### 第 2 题（成本归因的时机）

`CostTracker` 的归因维度（model、endpoint）是 `UsageRecord` 的字段，在记录时打上，而不是月底从账单或日志里事后解析。这种设计的主要价值是：

- A. 节省存储空间
- B. 让 record() 方法运行得更快
- C. 记录时的上下文信息最完整，事后解析既不可靠也不可行；结构化数据要在产出的时刻就结构化
- D. 这只是个人编码偏好，两种方式效果相同

### 第 3 题（trace 与 log）

关于 log 与 trace 的分工，下列哪一项描述是**错误**的？

- A. log 是离散的文本事件流，回答"系统发生了什么"

- C. span 自带起止时间与状态，可以做"llm.chat 平均耗时"这类聚合分析
- D. 有了 trace 之后就可以删除所有日志，因为 trace 是 log 的超集

`CostTracker.record()` 遇到价格表里没有的模型时抛 KeyError 而不是按 0 元记账，因为成本数据漏算（显示 0 元）会让报表一切正常，直到真实账单到来才暴露，是最危险的错误模式。（对 / 错）

## 第四部分：编程题

### 第 10 题（给一次 Agent 运行算一笔账）

**功能要求**：

1. 在项目根目录新建 `scripts/trace_and_cost_demo.py`，用 `run_with_trace` 带 trace 地跑一次 ReactAgent（MockLLM 驱动、装配 calculator + web_search，可参考 `scripts/run_agent_eval.py` 的 `make_agent`），同时用 `CostTracker` 以 `gpt-4o-mini` 的价格给这次运行记账（提示：agent 跑完后 `tracker.record_from_llm(agent.llm, model="gpt-4o-mini")`）。
2. 打印：trace_id、各 span 的名称/耗时/状态、本次运行的 prompt/completion token 数与折算费用。
3. 验证 trace 的落盘与回放：把 tracer 指向 `data/eval/traces.jsonl`，程序末尾用 `Tracer.load()` 读回文件，确认读回的 span 数与内存中一致。
4. 断言自测：root span 状态为 `"ok"`，其 `answer` 属性等于 `agent.run` 的返回值；`llm.chat` span 数等于 MockLLM 的调用次数。

**提示**：两次 LLM 调用（先 Action 后 Final Answer）需要给 MockLLM 准备两条响应；`run_with_trace` 内部会临时替换 `agent.llm`，记账要在运行结束、llm 换回来之后做。
