## 第一部分：选择题

### 第 1 题

**答案：D**

**解析**：D 错误且恰好说反——function calling **不强制**模型外露推理过程，模型的"思考"隐含在 tool_calls 的选择里；反而是 ReAct 文本协议强制每步输出 `Thought`，推理过程天然可见，可调试性更好。这是两条路线的真实权衡之一，也是"需要强制外露推理过程时文本协议仍是正确 fallback"的原因。A 是两条路线的本质差异（求来的格式 vs 协议保证的格式）；B 指出循环骨架同构（FunctionCallingAgent 是 ReactAgent 在结构化通道上的等价物）；C 是 function calling 的协议优势（tool_calls 是数组）。

### 第 2 题

**答案：D**

**解析**：D 错误——模型决定传什么参数时能看到的信息**只有** tools 字段里的 name/description/parameters，参数名 `expression` 只能传达"这是个表达式"，传达不了"支持哪些运算符、要不要括号、什么格式"。模糊或缺失的 description 几乎等于让模型猜，选参错误率随之上升。A、B、C 都是正确实践：A 强调 description 的受众是模型；B 对应"缺必填"这一最高频的选参错误；C 是同源原则——schema 与工具实现共用一份元数据，漂移在结构上被消除（`FunctionSpec.from_tool`）。

### 第 3 题

**答案：B**

**解析**：这是典型的"模型的错"——参数类型不符属于 schema 类错误，模型有能力据此自我修正，因此正确处置是**把错误详情回填并占重试预算**。反馈文本会明确写出"应为 string，实际为 int"，模型下一轮补上正确类型即可（测试 `test_schema_error_fed_back_and_retried` 演示了完整回路）。A 过度反应（一次可修正的错误不该终止任务）；C 危险——静默修改模型意图会掩盖问题且可能与工具语义冲突（42 与 "42" 对某些工具含义不同），纠错决策应交还模型；D 让模型永远不知道调用没发生，后续推理会建立在虚构前提上。

## 第二部分：判断题

### 第 4 题

**错。**

Python 的类型层次与 JSON Schema 的类型语义在这里**冲突**：`isinstance(True, int)` 为 True（bool 是 int 的子类），但 JSON Schema 里 `boolean` 与 `number`/`integer` 互不相容。不特判的话，模型给数字参数传 `true` 会漏过校验。`validate_arguments` 显式拦截：期望值是 integer/number 而实际值是 bool 时抛 `SchemaValidationError`（测试 `test_bool_rejected_for_number` 守护此行为）。这是"Python 实现 JSON Schema 校验"的经典坑。

### 第 5 题

**错。**

两类失败的处置刻意不同。schema 校验失败是"模型的错"——模型能自我修正，计入连续失败计数（占重试预算）。工具执行异常是"环境的错"——参数合法，失败发生在工具内部，重试模型无意义；正确处置是把失败事实作为观察结果回填（模型可据此换工具或放弃），但**不占重试预算**。`_execute` 返回三元组 `(结果文本, 是否失败, 是否占重试预算)` 把这个决策显式化，测试 `test_execution_error_fed_back_without_retry_budget` 用 `max_retries=1` 下连续三次执行异常仍未放弃来验证这一点。

### 第 6 题

**对。**

`parse_tool_calls` 在生产中处理的是 OpenAI 线上格式（arguments 为 JSON 字符串、带 id/type 字段）。如果 Mock 直接输出"已解析的 dict"，测试走的就是一条 Mock 专用的简化路径——线上格式特有的失败模式（坏 JSON、缺 id）在测试里根本不会出现，测试通过也无法证明生产路径正确。`_normalize_tool_response` 把简写脚本规整为线上格式，测试覆盖的才是真实协议路径；脚本用尽后的兜底、usage 统计等既有行为完全不受影响（旧测试零改动）。

## 第三部分：问答题

### 第 7 题

（1）有效的重试反馈应包含三要素：**错误类型**（参数校验失败）、**具体定位**（哪个参数、缺了还是类型错了）、**schema 期望**（要求什么）。模型拿到"缺少必填参数 expression（schema 要求：expression）"后，下一步该做什么是完全确定的——补上 expression；而一句"调用失败"没有任何可操作信息，模型只能瞎猜哪里错了，可能改错地方、甚至编造新的错误参数。这与 day036 的约束要素同理：反馈越具体，修正越准；模糊的反馈等于把 token 浪费在猜测上。

（2）`max_retries` 防的是**反馈回路死循环**：模型可能在"缺参 → 反馈 → 还是缺参"上空转，每轮都是一次真实的 LLM 调用，无上限等于烧 token 的漏斗。超过上限（默认 2 次连续失败）即放弃并返回明确说明，把失败暴露给上层而不是无限掩盖。计数**连续**而非累计的原因：一次成功的调用证明模型回到了正轨，历史错误不应再惩罚后续行为——重试预算约束的是"正在持续的故障"，不是"模型的历史表现"。实现上即成功调用时把 `consecutive_failures` 清零。

### 第 8 题

（1）`tool` 是 OpenAI 协议的专用角色，它把"函数返回的事实"与"用户说的话"在协议层分开。模型据此知道这段文本是工具输出而非新指令——这对抗"经工具结果注入的间接提示词攻击"（day031）有结构性帮助：工具返回里混入的恶意指令，其角色权重与真正的用户指令不同。ReactAgent 用 user 消息包 `Observation: ...` 是文本协议没有专用角色时的妥协。

（2）回填 tool 消息需要与调用配对（`tool_call_id`），而坏 JSON 意味着连工具名和调用 id 都不可信——`parse_tool_calls` 在解析阶段就抛 `SchemaValidationError`，拿不到合法的配对信息。此时降级为 user 消息反馈（"你的函数调用格式有误……请重新发起调用"）是协议无法配对时的体面兜底：错误信息仍然进了上下文，模型仍然有机会修正。

（3）省掉 assistant 决策入史，消息历史里就只剩 tool 结果而没有"是谁、以什么参数发起的调用"——模型看到的上下文断裂：突然冒出一段工具结果，却没有对应的调用记录。后果有二：模型无法从自己的错误中学习（看不到上次传错了什么参数）；多步调用时丢失调用序列，模型可能重复调用同一函数。把 tool_calls 序列化为 assistant 消息（`json.dumps(response["tool_calls"])`）保持了"决策 → 结果"的交替结构完整。

### 第 9 题

（1）"把 tools 拼进提示词再调 chat"本质上就是 ReAct 文本协议——它没有 function calling 的任何核心收益（结构化输出通道、解码层约束），却伪装成同一个接口，会让上层误以为拿到了协议级可靠性。抛 `NotImplementedError` 是**能力检测即路线切换点**：上层捕获后明确降级到 ReactAgent 文本路线，错误信息里直接写明退路（"请改用 chat 走文本协议"）。显式失败优于静默降级——静默降级让"可靠性差异"变成隐形炸弹。

（2）生产系统的选择逻辑：LLM 实现支持 `chat_with_tools`（OpenAI 兼容厂商、支持工具调用的自研模型）→ 走 `FunctionCallingAgent`，结构化可靠性优先，这是默认路线；不支持（纯文本小模型、未对齐工具调用的模型）→ 走 `ReactAgent` 文本协议兜底；需要强制外露推理过程（审计、教学、调试）时也选文本路线，因为 `Thought` 字段天然可见。

（3）共享注册表与元数据是同源原则的延伸：`BaseTool` 的 `name`/`description`/`parameters` 一处定义，`to_schema()` 供文本提示词（渲染进"可用工具"段落）、`FunctionSpec.from_tool` 供 function calling（下发 tools 字段）。若两条路线各自维护工具描述，同一个工具在两份描述里措辞不同，模型行为就会因路线而异——迁移时的行为一致性无从谈起。一处定义、两种投影，工具层零改动即可被两种 Agent 壳复用。

## 第四部分：编程题

### 第 10 题

参考实现见 `../源码/smart-research-agent/scripts/function_calling_demo.py`，核心结构：

```python
def demo_spec_and_parse() -> None:
    registry = ToolRegistry()
    registry.register(CalculatorTool())
    spec = specs_from_tools(registry.list_tools())[0]
    payload = spec.to_openai_tool()
    assert payload["type"] == "function"
    assert payload["function"]["parameters"]["required"] == ["expression"]

    raw_response = {"tool_calls": [{
        "id": "call_abc", "type": "function",
        "function": {"name": "calculator",
                     "arguments": json.dumps({"expression": "(1 + 2) * 3"})},
    }]}
    calls = parse_tool_calls(raw_response)
    assert calls[0].id == "call_abc"
    assert calls[0].arguments == {"expression": "(1 + 2) * 3"}

    validate_arguments(spec, calls[0].arguments)          # 合法参数通过
    try:
        validate_arguments(spec, {"expression": 123})     # 类型错误应被拦截
        raise AssertionError("类型错误应被拦截")
    except SchemaValidationError:
        pass

def demo_agent_retry() -> None:
    llm = MockLLM(tool_call_responses=[
        {"tool_calls": [{"name": "calculator", "arguments": {}}]},                        # 漏参
        {"tool_calls": [{"name": "calculator", "arguments": {"expression": "(1 + 2) * 3"}}]},  # 修正
        {"content": "(1 + 2) * 3 = 9"},                                                   # 最终答案
    ])
    agent = FunctionCallingAgent(llm, registry, max_retries=2)
    assert agent.run("计算 (1 + 2) * 3") == "(1 + 2) * 3 = 9"
    (call1, result1, ok1), (call2, result2, ok2) = agent.call_history
    assert not ok1 and "缺少必填参数" in result1
    assert ok2 and result2 == "9"
    assert any(m.role == "tool" and "参数校验失败" in m.content for m in llm.calls[1])
    assert any(m.role == "tool" and "[calculator] 9" in m.content for m in llm.calls[2])
```

**踩坑点提示**：

1. **Mock 脚本的两种形态**：`{"tool_calls": [...]}` 表示模型决定调工具，`{"content": "..."}` 表示直接回答——`FunctionCallingAgent` 靠"有没有 tool_calls"判断循环是否终止，脚本顺序写错会导致循环行为完全偏离预期。
2. **call_history 的记录粒度**：每次工具执行记一条 `(call, 结果, 是否成功)`，schema 失败也记录——它反映的是"执行层发生的事"，与"LLM 调用轮数"（`llm.calls`）是两个维度，断言时注意区分。
3. **导入路径**：与 day036 相同，脚本顶部必须 `sys.path.insert(0, ...)` 以导入本快照内的包。
