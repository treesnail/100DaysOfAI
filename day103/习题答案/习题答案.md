## 一、速答

**1.** 节点是**每一个 `.py` 文件**。命名规则：`smart_research_agent/foo/bar.py` → `smart_research_agent.foo.bar`；
而 `smart_research_agent/foo/__init__.py` → `smart_research_agent.foo`（`__init__.py` 折成**包节点**，
包节点这一身份在 `ModuleGraph.packages` 里单独记着，并参与"包 / 模块"的读数）。

**2.** `absolute` 的目标写全了（`from smart_research_agent.tools.base import BaseTool`）；
`relative` 的目标要按 `level` 算（`from .base import X`）。算的规则是**减掉 `level - 1` 层点**：

```text
在 smart_research_agent/foo/bar.py 里，所在包 = smart_research_agent.foo
  level = 1 ⇒ 用所在包本身
  level = 2 ⇒ 用所在包的父（smart_research_agent）
```

之所以要减 `level - 1`（而不是 `level`），是因为一个点已经代表"所在包"了。

**3.** 两条好处：
- **不被掩盖**：`import` 会把包真的执行一遍，一个语法错或一个缺失的可选依赖会被 `ImportError` 掩盖；
  `ast` 只读文本，语法错会被当场点名（`ParseError`）。
- **看得见延迟导入**：`tools/image_analysis.py` 在**函数体内部**写
  `from smart_research_agent.api.app import default_llm`，只在运行时才会执行；
  `import` 式扫描或运行时工具都看不见它，而 `ast` 看得见——它正是 `api ↔ tools` 那个环的另一半。

**4.** `sccs()` 返回**全部**强连通分量（包含单点分量）；`cycles()` 只挑出成员数 > 1 的那些（真正的环）。
`topological_order()` 的长度是**分量数**：环上的多个模块被凝缩成一个点之后才存在线性序，
所以它小于（或等于）模块数——当前快照是 446 个分量 vs 457 个模块。

**5.** `closure(x, "down")` 回答"我依赖谁"（少一个就跑不起来）；
`closure(x, "up")` 回答"动了我，谁受影响"。两个方向的答案**极不对称**：
`smart_research_agent.utils.logger` 当前读数是 **down 2 / up 150**。
坚持写方向的原因：不写就取一个默认值，会让报告里两个完全不同的数长得一模一样。

**6.** 回来的族是 `AssemblyError`（`RETURNED_FAMILY`）：它由 day080 第一次命名，
此后被 `arch_variants` / `encoder_decoder` / `hf_source` / `transformer_stack` / `capstone` 各写一遍，
是本仓库里被跨包重写最多的族名之一；day102 没有它，本课要把 450 个模块"装成一张图"，
于是"零件装不成一个整体"重新需要一次控制流事件。
缺席的族是 `GradientError`（`ABSENT_FAMILY`）：本课是纯静态分析，连一次 import 都不执行。

## 二、对照

**7.** 同一句话的三条：① 覆盖（day102 是"每份 `errors.py`"，本课是"每个 `.py`"）、
② 可复算、⑤ 未解析目标数为 0（day102 是"未解析基类名"，本课是"未解析 import 目标"）。
本课**特有**的四条：③ 线性序合法、④ 环是真的、⑥ 闭包含自己、⑦ 存在依赖链。
其中 ③④ 是"图"这件事独有的：台账没有"顺序"与"环"的概念。

**8.** 是同一条纪律：**把并列 / 未固定的顺序显式消掉，让"两次运行逐位相同"成为一条 `==`。**
- day101 防的是 `dict` 插入序（倒排表里文档名必须排序）；
- day102 防的是集合序（族按"包名升序 × 源码顺序"排）；
- day103 防的是**排序键并列**——`sorted(key=len, reverse=True)` 在等长候选上会回到 `set` 的迭代序，
  而 `set` 的迭代序随进程（`PYTHONHASHSEED`）变化。
  因此本条测试用**两个不同哈希种子的子进程**比对摘要，直接钉住"跨进程可复算"。

**9.** `topological_order()` 给的是**凝缩图**的线性序（永远存在）；
`require_acyclic()` 是"拒绝交付"的那条路——它检查**原始图**有没有环，有就抛 `CycleError`。
独立成族的原因：把"你要线性序、但图里有环"记进 `GraphBuildError` 会让人以为图画错了，
而真相是**调用点问错了问题**（该先凝缩，或者该改层去真正拆环）。

## 三、诊断

**10.** 三种可能：
- **相对导入的层数算错**（少减 / 多减了一层点）⇒ 改解析规则；
- **别名 / 属性形式的写法没被覆盖**（例如 `from smart_research_agent.foo import bar` 里
  `bar` 是一个包而不是模块）⇒ 改解析规则；
- **源码里真的写错了一个模块名**（或引用了还不存在的模块）⇒ 改源码。
三者都会让 `import_targets_resolve`（上界判据）失败。

**11.** 例子：`from . import a, b`，其中 `a.py` 与 `b.py` **同长**且都存在。
- 正确写法 `sorted(key=lambda item: (-len(item), item))`：永远先挑 `a`；
- 错误写法 `sorted(key=len, reverse=True)`：`a` 与 `b` 等长，顺序回退到 `set` 的迭代序，
  **两次运行会挑到不同的目标**——图照样画得出来、照样能排序、`sccs()` 也照样跑完，
  只有**摘要**（和那条子进程测试）会发现"这次编出来的图与上次不是同一张"。

**12.** 因为那一行写在**函数体内部**：模块被 import 时，函数体不执行，
所以 `tools/image_analysis` 在导入期不会真的去 import `api.app`，环被"延迟"到了第一次调用。
但依赖图读的是 **import 语句的文本**，不是运行期行为——它看得见那两条边，
于是把它如实记成一个环。这正是本课选择"不做 import"的直接后果：
**运行期看不见的东西，静态图看得见；静态图看得见的东西，运行期不一定发生。**

**13.** `smart_research_agent.foo.bar` 的所在包是 `smart_research_agent.foo`；
`level = 3` ⇒ 减 `2` 层 ⇒ 只想保留 `smart_research_agent` 的前 0 段 = 空串
（因为 `foo` 已经在包根，再往上就出界了）。
此时 `ImportRef.internal` 应当是 **`True`**：一句相对导入想指的**永远是本包内部**，
落到包根之外不是"外部导入"，而是一条**解析不出来的包内 import**——
它必须被性质 ⑤（未解析目标数 <= 0）抓住。本仓库当前没有这种写法（读数 0）。

## 四、推导与动手

**14.** `a → b`、`b → c`、`c → a`：
- `sccs()`：只有一个分量，成员排序后是 `("a", "b", "c")`；
- `condensation_edges()`：分量内部没有跨分量的边 ⇒ `()`；
- `topological_order()`：只有 1 个分量 ⇒ `("a",)`，长度为 **1**（不是 3）。

**15.** 证明：图无环 ⇒ 每个强连通分量恰好是一个单点（一个节点自己与自己互达，
但若两个节点互相可达就构成环）。因此分量数 = 节点数；
`topological_order()` 每个分量取一个键，长度就等于节点数。∎

**16.**

```python
from smart_research_agent.import_graph import build_graph
graph = build_graph()
node = "smart_research_agent.utils.logger"
print(len(graph.closure(node, "down")), len(graph.closure(node, "up")))
```

当前读数：**down 2 / up 150**。不对称的原因：`utils.logger` 只依赖 `utils` 自己那一两个模块，
而它被几乎每一个子包依赖（`logging` 是横向的公共设施）。这也是为什么"动工具函数要跑全量回归"。

**17.** 建议写成：

```text
id          utils_is_widely_depended_on
criterion   lower_bound
检查量       utils 的上游闭包里出现的**不同顶层子包**个数
下界          5
失败意味着   这个仓库里几乎没人用共享的工具模块——要么 utils 被绕过了，
            要么这次的扫描把 utils 的依赖边整片漏掉了（例如相对导入解析错）。
```

（当前快照下这个量是 **32** 个子包，远大于下界 5。）

**18.** 两个真实例子：
- **day102 的"18 个子包没有 `errors.py`"**：它被印成一个**读数**，而不是一条失败性质。
  因为"没有 `errors.py`"完全合法（`agent` / `llm` / `api` 都有自己的错误处理），
  一条会在仓库**合理地**变化时变红的性质，最后一定会被人关掉。
- **day101 的"金标准材料不是第一名"**：那条性质写成"金标准材料被命中 >= 1 次"，
  而不是"它必须排第一"。因为名次是排序规则的结果，
  把"名次"和"是否命中"混在一起，会在多召回一条同样相关的材料时误报失败。

一句话总结：**当一个现象是"仓库的真实状态"而不是"仓库的缺陷"时，它应当被印出来；
只有当一个现象是"我们承诺过的东西没做到"时，它才应当是一条失败性质。**
