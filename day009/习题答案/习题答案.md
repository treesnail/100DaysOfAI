## 第一部分：选择题

### 第 1 题

**答案：C（注入）**

解析：长期记忆三步模型的划分标准是「数据流向」：

- **存储（remember）**：文本 → embed → 写入向量库。方向是「进库」。
- **检索（recall）**：问题 → embed → 相似度排序 → 取 top-k。方向是「出库」。
- **注入（inject）**：把检索结果拼进发给 LLM 的消息。方向是「进上下文」。

题目描述的动作发生在检索完成之后、LLM 调用之前，目的是让模型「看到」这些知识，属于注入。容易混淆的是 B——recall 只负责把结果从库里取出来，放到 prompt 里是另一个决策（放哪、放多少、要不要放），因此单独成一步。

### 第 2 题

**答案：C（余弦相似度为 1.0，因为方向完全一致）**

解析：直接套公式：

- 点积 = 1×3 + 1×3 = 6
- |A| = √2，|B| = √18 = 3√2
- cos = 6 / (√2 × 3√2) = 6 / 6 = **1.0**

B 的向量模长是 A 的三倍，但方向完全相同（都在 y=x 这条射线上）。余弦相似度只衡量方向，对长度不敏感，所以判定「完全相同」——这正确反映了「同一句话重复三遍，语义没变」的事实。A 错：欧氏距离 = √(2²+2²) ≈ 2.83，反而认为它们差很远，这正是文本检索不用欧氏距离的原因。D 错：余弦公式对任意非零模长都适用。

### 第 3 题

**答案：B**

解析：暴力精确搜索每次查询要与库中全部 N 条记录计算相似度，复杂度 O(N)。百万级数据、1536 维向量意味着单次查询约 15 亿次浮点运算，数据量翻倍成本就翻倍，生产上不可接受。ANN（如 HNSW）通过预先建立索引结构，把查询降到近似 O(log N)，代价是召回率略降（比如 99%）。

A 错：精确搜索结果才是最准确的，「暴力」指的是计算方式而非结果质量。C 错：ANN 仍然要存储向量（索引是额外的结构）。D 错：精确搜索可以处理任意维度，只是慢。关键点：top-k 检索服务于上下文注入，第 1 名与第 2 名差 0.001 的相似度对最终答案几乎无影响，用约 1% 的精度换百倍速度是稳赚的交易。

### 第 4 题

**答案：C（该说法错误，故为本题答案）**

解析：C 的说法恰恰是 MockEmbedding **不具备**的能力。SHA-256 是密码学哈希，雪崩效应保证输入差一个字节、输出就面目全非，所以「猫」和「狗」的伪向量相似度与「猫」和「微积分」的一样随机——它没有语义结构，只能可靠召回完全相同的文本。

其余选项都是 MockEmbedding 的真实优点：

- A 对：确定性哈希 → 同一文本永远得到同一向量，测试才能写出「recall 精确文本必然排第一」的断言。
- B 对：纯标准库实现，无网络、无 Key、无费用。
- D 对：生产环境应实现 `EmbeddingProvider` 接口接入真实服务（如 OpenAI embedding），上层 `LongTermMemory` 无需改动。

## 第二部分：判断题

### 第 5 题

**答案：对**

解析：暴力搜索对库中**每一条**记录都计算余弦相似度并完整排序，因此返回的 top-k 就是数学意义上的全局最近邻，不存在「漏掉更相似的记录」的可能。它的问题从来不是准确性，而是成本——O(N) 的查询复杂度在数据量大时不可接受。ANN 才是「牺牲精确换速度」的那一方；教学版用暴力搜索，恰恰因为结果精确、便于测试断言。

### 第 6 题

**答案：对**

解析：余弦相似度公式为 `cos = (a·b) / (|a|·|b|)`。若两个向量都已归一化（|a| = |b| = 1），分母恒为 1，于是 `cos = a·b`。点积只需 N 次乘加，省掉了两次模长计算和除法，在大规模检索中差距可观。这就是很多 embedding 服务直接返回单位向量的工程动机之一。注意前提：「归一化后点积等于余弦」只在**两个**向量都是单位向量时成立。

### 第 7 题

**答案：错**

解析：「链路跑通」只证明数据能从存储流到检索再到注入，不证明检索结果有语义价值。今天的 `MockEmbedding` 就是反例：整条链路完整、测试全绿，但它的哈希向量没有语义，「猫」和「狗」不会比「猫」和「微积分」更近。语义能力来自真实的 embedding 模型（用对比学习在海量语料上训练出来的语义空间），不来自向量库和检索代码。判断一个检索系统是否具备语义能力，要看语义相近但不相同的文本能否互相召回。

## 第三部分：问答题

### 第 8 题

**参考答案：**

**（1）计算过程**

对 `q = [1, 2, 2]` 与 `a = [2, 4, 4]`：

- 点积：1×2 + 2×4 + 2×4 = 2 + 8 + 8 = 18
- |q| = √(1+4+4) = √9 = 3
- |a| = √(4+16+16) = √36 = 6
- cos(q, a) = 18 / (3×6) = **1.000**

对 `q` 与 `b = [1, 0, 0]`：

- 点积：1×1 + 2×0 + 2×0 = 1
- |b| = √(1+0+0) = 1
- cos(q, b) = 1 / (3×1) ≈ **0.333**

**（2）top_k=1 返回 a。**

几何解释：注意 `a = [2,4,4] = 2 × [1,2,2] = 2q`——a 与 q 在同一条从原点出发的射线上，**夹角为 0°**，所以余弦相似度取最大值 1（a 只是模长翻倍，方向完全一致）。而 b 指向 x 轴正方向，与 q 的夹角约 70.5°，方向偏离明显，相似度只有 0.333。余弦相似度只比较「指向哪里」，不比较「走多远」，因此 a 必然排在 b 前面。这也再次说明：对文本检索而言，语义编码在方向上。

### 第 9 题

**参考答案：**

**（1）两种注入位置的权衡**

| 注入位置 | 优点 | 缺点 |
|----------|------|------|
| 拼进 system 消息 | 位置固定、全程生效；模型对 system 通常赋予更高权重 | system 应当稳定（工具清单、角色设定）；历史知识每次不同，拼进去会污染它，也不利于 prompt 缓存 |
| 任务前的 user 消息 | 与当次任务强绑定，语义清晰；system 保持纯净 | 会被短期记忆的 FIFO 截断丢弃；多轮后「记忆的记忆」失效 |

**（2）与 FIFO 截断的冲突及缓解**

day008 的 `ShortTermMemory` 在超限时按 FIFO 丢弃最老的非 system 消息。注入的「相关资料」消息位于消息列表**最前面**（仅次于 system），因此它是最先被丢弃的那批——对话稍长，Agent 就「又忘了」。

缓解思路（答出合理者即可）：

- **每轮重新 recall**：每次用户发新消息，都重新检索并注入最新相关资料，旧注入随截断丢弃也无所谓。代价是 embedding 调用次数增加。
- **修改截断策略**：像 system 一样把「相关资料」消息标记为不可丢弃（例如用 metadata 或专门 role）。
- **升级而非保留**：被截断前，把关键结论用 `remember` 写回长期记忆，下次需要时还能再检索出来——让短期记忆和长期记忆形成「降级存储 / 按需复活」的循环。

要点：没有唯一正确答案，核心是意识到「注入的记忆」与「窗口容量」争夺的是同一个稀缺资源，任何方案都是在成本、及时性、实现复杂度之间取舍。

## 第四部分：编程题

### 第 10 题

**参考实现：**

在 `InMemoryVectorStore` 中新增（`search` 保持不变）：

```python
def search_with_threshold(
    self, query_vector: list[float], top_k: int = 5, min_score: float = 0.0
) -> list[tuple[VectorRecord, float]]:
    """相似度检索，但只返回 score >= min_score 的记录."""
    return [(r, s) for r, s in self.search(query_vector, top_k=top_k) if s >= min_score]
```

要点：复用已验证的 `search`（排序、top-k 截取逻辑不重写），再按阈值过滤。注意过滤发生在 top-k **之后**——先取前 k 个再筛掉低分的，语义是「最相关的 k 条里达标的」，这符合「宁缺毋滥」的注入需求。

参考测试（加入 `tests/test_long_term.py` 的 `TestVectorStore`）：

```python
def test_search_with_threshold_filters_low_scores(self):
    store = InMemoryVectorStore()
    store.add(VectorRecord(id="a", text="A", vector=[1.0, 0.0]))
    store.add(VectorRecord(id="b", text="B", vector=[0.0, 1.0]))
    # 查询 [1, 0]：a 得 1.0，b 得 0.0；阈值 0.5 应剔除 b
    results = store.search_with_threshold([1.0, 0.0], top_k=2, min_score=0.5)
    assert [r.id for r, _ in results] == ["a"]

def test_search_with_threshold_zero_matches_search(self):
    store = InMemoryVectorStore()
    store.add(VectorRecord(id="a", text="A", vector=[1.0, 0.0]))
    store.add(VectorRecord(id="b", text="B", vector=[0.9, 0.1]))
    # 两条记录与查询都是正相似度，min_score=0 不过滤任何记录
    plain = store.search([1.0, 0.0], top_k=2)
    filtered = store.search_with_threshold([1.0, 0.0], top_k=2, min_score=0.0)
    assert [r.id for r, _ in filtered] == [r.id for r, _ in plain]
```

验证：在项目根目录运行

```bash
python -m pytest tests/ -q --no-cov
```

全部通过即完成。注意第二个测试用 `0.9, 0.1` 保证两条记录对查询 `[1,0]` 的相似度都为正（若存在负相似度记录，`min_score=0.0` 也会将其过滤，与 `search` 行为不同——这正是提示中「注意余弦相似度可能为负值」的含义）。
