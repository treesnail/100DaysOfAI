## 今日目标

1. **把适配器做成一个可交付物**——一个适配器是**三个文件**（配置 / 权重 / 训练状态），外加一份**含内容哈希的清单**。参考模型上实测 274 678 B；哈希只覆盖配置与权重，不含"训到哪了"。
2. **算清多卡之后的账**——全局批 = `per_device × accum × devices`；每设备显存取决于**分片策略**而不是设备数；学习率要按法则缩放（`linear` / `sqrt` / `none`）。
3. **记住一条反直觉的实测**：LoRA 场景下 `zero2` **几乎不省显存**（12.65 → 12.59 GiB，省 1.00 倍），只有 `zero3` 省 4 倍——代价是每步通信量放大**三个数量级**（0.025 GB → 26.98 GB）。
4. **把配置变成数据**——accelerate 的 YAML 与 DeepSpeed 的 ZeRO JSON 都由代码生成，字段名与官方一致，可以被 review、被测试。
5. **让训练循环只保留一份**——`SFTTrainer` 加一个 `on_step` 回调，`LoRATrainer` 用它把"落适配器"插进循环；**循环逻辑一行没有复制**。
6. **把"合并前后逐位一致"变成部署门禁**——`verify_merge` 在 557 个上下文上逐位比较，并**必须有一条"失败时会怎样"的用例**（一个永远不会失败的门禁不是门禁）。
7. **记两个会真正炸掉的坑**：多卡脚本里重复的关键字参数会让脚本 `TypeError`（而 `compile()` 通过），显式传 `system_prompt=None` 被吞掉会让训练数据与推理输入不一致。

昨天留下的三件事今天逐一兑现：**`LoRAReferenceModel` 的接口**（训练器直接接上）、**`merged_by_context` 的合并语义**（落盘必须选对那一个矩阵）、**`plan_memory` 的六项预算**（多卡与混合精度改的正是这几项）。

## 第一章：适配器是一个"可交付物"

### 1.1 三个文件，缺一不可

一次 LoRA 训练结束后，要交付的东西不是"一堆权重"，而是三件彼此独立的信息：

```text
adapter_config.json     r / alpha / dropout / target_modules / 基座参数量 / 缩放公式
adapter_model.json      A 与 B 两个矩阵（**只有它们**）
training_state.json     步数、学习率、loss、超参快照、词表大小、参考模型的账
```

参考模型上实测的体量：

```text
adapter_config.json           435 B
adapter_model.json         272918 B
training_state.json          1325 B
合计                       274678 B（268.2 KiB）
```

**缺任何一个都不该被加载**，而 `load_adapter` 就是这么做的——缺文件直接抛 `AdapterCheckpointError`，不返回"部分可用的对象"。这三条失败路径各有各的后果：

| 缺什么 | 后果 |
|--------|------|
| `adapter_config.json` | 加载时用默认 `alpha`，**缩放悄悄变了一个倍数** |
| `adapter_model.json` | 无权重可用，无法推理 |
| `training_state.json` | 续训从第 0 步开始，**学习率调度被重置**，loss 曲线从此不可解释 |

这与 day050"检查点必须包含词表"是同一条纪律：**产物要自描述**。一个只有 `A` / `B` 的目录，别人拿到手第一件事就是问"这是哪个 `r`、配哪个基座"。

### 1.2 内容哈希：只覆盖配置与权重

```python
def adapter_content_hash(*, config: dict, model: dict) -> str:
    digest = hashlib.sha256()
    digest.update(_canonical_bytes({"config": config}))
    digest.update(_canonical_bytes({"model": model}))
    return digest.hexdigest()
```

两个设计点：

1. **规范化序列化**（`sort_keys=True` + 紧凑分隔符）。同一份数据换了键顺序就会得到不同的哈希，那么"线上跑的是哪个适配器"这个问题就仍然答不出来；
2. **刻意不含 `training_state.json`**。同一个适配器续训一步之后权重没变、但"训到哪了"变了——**哈希要回答的是"权重是不是同一份"**，把步数/时间戳混进去会让这个答案随无关量漂移。测试里有一条用例专门守它：改变训练状态不改变哈希，改变权重才改变哈希。

参考模型上 `r=8`、训练 4 步后的适配器哈希是 `sha256:4aa1b146abb3…`（完整 64 位留在 `content_sha256`）。

### 1.3 清理策略：`adapter-final` 永不删除

```text
落盘 3 个中间适配器后：['adapter-final', 'adapter-step-2', 'adapter-step-4', 'adapter-step-6']
prune_adapters(limit=2) → 删除 ['adapter-step-2']
剩余：['adapter-final', 'adapter-step-4', 'adapter-step-6']
```

中间目录按步号排序、保留最后 `limit` 个，`adapter-final` 不在清理范围内。与 day050 的 `save_total_limit` 同一条纪律——**磁盘不是无限的**；差别只是这里要清的是几十 KB 到十几 MB，而全参微调的检查点是十几 GB。

### 1.4 发布动作：重新生成清单

`repackage_adapter` 把三件套复制到发布目录，并**重新生成清单**（而不是原样拷贝）：

```text
发布目录：['adapter_config.json', 'adapter_manifest.json', 'adapter_model.json', 'training_state.json']
发布清单：published | 基座 Qwen/Qwen3-0.6B | r=8 alpha=16 targets=['weight'] | step 4 | 274678 B | sha256:4aa1b146abb3
```

复制的是三个文件而不是整个目录，所以发布目录里不会留下训练过程中的临时文件；而"实验目录里的那一份"与"发布出来的那一份"各自带着自己的哈希与元信息——**发布是一次显式的动作，不是 cp 一个文件夹**。

清单里刻意保留 `base_model`：**基座不匹配的适配器不会报错，只会给出莫名其妙的结果**。推理脚本会把这条不一致打印成警告（见第五章）。

## 第二章：多卡之后的账

### 2.1 全局批有三个乘数

```text
global_batch_size = per_device_train_batch_size × gradient_accumulation_steps × devices
```

单卡上把有效批调到 8（`per_device=2 × accum=4`），在 4 卡上默认变成 **32**。于是跟着变的有三样：**学习率**（见 2.2）、**warmup 步数**、**总步数**。

总步数的口径与 day050 一致（`drop_last`）：

```text
micro_batches_per_epoch = train_size // (per_device × devices)
steps_per_epoch         = micro_batches_per_epoch // accum
total_steps             = steps_per_epoch × num_train_epochs
```

实测（`llama-2-7b` / 4 卡 / 1000 条 / `per_device=2` / `accum=4`）：全局批 32、`micro=125`、`steps_per_epoch=31`、`total_steps=93`、`warmup=2`。

### 2.2 学习率：三条法则与它们的边界

```python
ratio = new_global_batch_size / base_global_batch_size
linear → lr × ratio          sqrt → lr × sqrt(ratio)          none → lr × 1
```

实测（有效批 8 → 32，`lr=2e-4`）：`linear` 给 **8e-4**（4 倍）、`sqrt` 给 **4e-4**（2 倍）、`none` 给 **2e-4**。

为什么要缩放：批大小变大意味着梯度是更多样本的平均，**梯度噪声变小、步长可以更大**。线性法则来自"批大小翻倍时梯度方差减半"的直觉，工程上在中小规模最常用；平方根法则更保守。

`none` 不是"错"的选项，但它会命中一条告警：

```text
全局批从 8 放大到 32（4 个设备），但 lr_scaling_mode=none：梯度噪声变小而步长不变，
训练会明显变慢。批大小翻倍时通常把学习率同倍放大（线性法则），并重新标定。
```

**把"不缩放"显式化，比让它悄悄发生好**——这正是本课反复用的那种手法：用一个配置项把隐含的假设挖出来。

### 2.3 每设备显存：分片规则决定一切

四种策略的差别**不是"除以设备数"**，而是"切哪几项"：

```text
ddp     每个设备一份完整副本（权重 + 梯度 + 优化器状态）
zero2   优化器状态 + 梯度按设备数分片，**参数不分片**
zero3   参数也分片（每层前向/反向各 all-gather 一次）
```

全参微调（`llama-2-7b` / bf16 / AdamW fp32 状态 / 4 个设备）：

| 单项（每参数） | 全模型 | ddp | zero2 | zero3 |
|--------------|--------|-----|-------|-------|
| 权重 2 B | 12.55 GiB | 12.55 | 12.55 | 3.14 |
| 梯度 2 B | 12.55 GiB | 12.55 | 3.14 | 3.14 |
| 优化器状态 8 B | 50.20 GiB | 50.20 | 12.55 | 12.55 |
| **合计** | **75.30 GiB** | **75.31** | **28.24** | **18.83** |

优化器状态（8 字节/参数）是最大的一项，所以 `zero2` 这一步就省掉 2.67 倍；`zero3` 再切参数与梯度，到 4.00 倍。**"同一份配置，DDP 要 80 GB 卡、ZeRO-3 只要 24 GB 卡"** 这句话的出处就在这里。

### 2.4 一条反直觉的实测：`zero2` 对 LoRA 无效

同样的四个设备，换成 LoRA（`attention_all` / `r=8`）：

| 策略 | 每设备显存 | 相对单卡 | 每步通信量 |
|------|-----------|---------|-----------|
| ddp | 12.65 GiB | 1.00× | 0.025 GB |
| zero2 | **12.59 GiB** | **1.00×** | 0.025 GB |
| zero3 | 3.16 GiB | 4.00× | **26.979 GB** |

`zero2` 只省了 0.46%。原因一眼可见：**它切的是优化器状态与梯度，而 LoRA 的优化器状态只有适配器那一百来 MB**；占大头的（12.55 GiB）是**冻结的基座权重**，而它只有 `zero3` 才会切。

**"分片策略的收益取决于'哪一项占用最大'"**——这句话在 LoRA 上比在全参微调上更明显，因为两者的"最大项"根本不是同一项。这也是本课把 `per_device_memory` 的实现写成"按项分片"而不是"总量除以 D"的原因。

### 2.5 通信量：`zero3` 的代价

同一张表右列是通信量。`zero3` 要 `all-gather` 的是**被分片的参数**（整个基座），而它每步的通信量因此比 `zero2` 高三个数量级：

```text
LoRA / 4 卡：zero2 0.025 GB/步 → zero3 26.979 GB/步（1072 倍）
全参 / 4 卡：zero2 20.215 GB/步 → zero3 47.169 GB/步（2.33 倍）
```

注意两行的反差为什么这么大：全参微调的**梯度**本来就是 6.7B 个参数，`zero2` 的梯度通信已经把量级抬上去了；而 LoRA 的梯度只有 8.4M 个参数（0.025 GB），于是"再一次搬整个基座"显得格外贵。

这条代价被写成一条告警（**每一条都对应一个真实代价**）：

```text
zero3 的每步通信量是 zero2 的 1072 倍（26.98 GB vs 0.025 GB），而每设备显存只从
12.65 降到 3.16 GiB。zero3 的显存收益来自切分参数，而它的通信代价正是每层前向
都要 all-gather 一遍参数——这笔交换是否值得要用实测吞吐来判断，不能只看显存表。
```

实现时这条告警的第一版写的是"显存省不到 1.2 倍就告警"，结果它**几乎不可达**（`zero3` 把六项全按设备数分片，节省倍数恒为设备数）。测试里那条用例因此也变成了"用 `devices=1` 硬凑"——**一条只能靠硬凑才触发的告警，等于没有**。改成"通信量 vs 显存收益"之后，它每次都会命中，而且指出的是真实代价。

### 2.6 混合精度：`bf16` 与 `fp16` 差在指数位

两者字节数完全一样（2 字节），差别在**指数位**：

| | 指数位 | 尾数位 | 需要 loss scaling | 特点 |
|---|-------|-------|------------------|------|
| `bf16` | 8 | 7 | **不需要** | 动态范围与 fp32 相同，几乎不会溢出 |
| `fp16` | 5 | 10 | **需要** | 精度略高，但容易溢出为 `inf` |

这就是"Ampere 及之后优先用 bf16"的全部理由。`MixedPrecisionProfile.needs_loss_scaling` 把这条差异写成了字段，而 `plan_distributed` 在 `fp16` 下会告警提醒动态范围窄。

## 第三章：把配置变成数据

### 3.1 accelerate 的配置是代码生成的

`accelerate config` 是一个交互式问答，最后写出一份 YAML。本课把它做成数据：

```python
accelerate_config(devices=4, strategy="zero2", mixed_precision="bf16",
                  deepspeed_config_file="ds_zero2.json")
```

渲染结果（实测）：

```yaml
compute_environment: LOCAL_MACHINE
distributed_type: DEEPSPEED
num_processes: 4
machine_rank: 0
main_training_function: main
mixed_precision: bf16
use_cpu: false
gpu_ids: all
deepspeed_config:
  deepspeed_config_file: ds_zero2.json
  zero3_init_flag: false
```

字段名与官方逐字对齐（`distributed_type` / `num_processes` / `machine_rank` / `main_training_function` / `use_cpu`），因此可以被真实 `accelerate launch --config_file` 消费。`ddp` → `MULTI_GPU`，`zero2` / `zero3` → `DEEPSPEED` + 一份 DeepSpeed 配置。

**为什么必须是数据**：交互式问答产出的配置**没法被测试、也没法被 review**。这里的版本会被测试用 `yaml.safe_load` 解析回来、与生成它的字典逐键比对——**渲染与读回必须是同一份东西**。

### 3.2 DeepSpeed 的 ZeRO 配置：三个 `"auto"`

```json
{"zero_optimization": {"stage": 2, "offload_optimizer": {"device": "none"}},
 "train_batch_size": "auto", "train_micro_batch_size_per_gpu": "auto",
 "gradient_accumulation_steps": "auto", "bf16": {"enabled": true}}
```

三个 `"auto"` 是刻意的：这三项由 `accelerate` 在运行时从 `TrainingArguments` 推导，**手写死值会让"配置里的批大小"与"训练日志里的批大小"对不上**——一个非常常见、而且非常难查的不一致。

`stage=3` 时多两处：`offload_param`，以及 `stage3_gather_16bit_weights_on_model_save: true`。后者只在 ZeRO-3 下有意义：权重被分片了，保存时必须先聚合——**不开这一项，落盘的模型是"半份"的**。

### 3.3 YAML 1.1 的 `no` 陷阱（本课踩的坑）

```text
mixed_precision: no        ← 语义上是字符串
yaml.safe_load(...)        → {'mixed_precision': False}   ← 读回来变成布尔！
```

`no` / `yes` / `on` / `off` / `true` / `false` / `null` / `~` 都是 YAML 1.1 的布尔别名。渲染时不给它们加引号，**渲染出去的配置与读回来的配置就不一致，而两边都不会报错**。

修法是在 `_yaml_scalar` 里显式枚举这些保留字并加引号。测试里有一条：**用 `mixed_precision="fp32"`（YAML 里渲染成 `no`）时，`yaml.safe_load(render_config_yaml(cfg)) == cfg` 必须成立**。

这条经验的一般形式：**序列化格式的"隐式类型转换"必须被当成接口的一部分来对待**——它与 day048 的"JSONL 用 `ensure_ascii=False`"、day050 的"检查点写 UTF-8"是同一类问题。

### 3.4 启动命令与配置同源

```text
accelerate launch --config_file accelerate_config.yaml --num_processes 4 train_lora_zero2.py
```

`devices=1` 时**不带** `--num_processes`（单卡不需要它）。命令与配置由同一组 `devices` / `strategy` 派生，因此不会出现"脚本里的设备数与命令里的不一致"。

## 第四章：训练循环只保留一份

### 4.1 一个回调而不是一份副本

day052 给 `SFTTrainer` 加了一个可选参数：

```python
def __init__(self, ..., on_step: Callable[[int, Any, Sequence[StepRecord]], None] | None = None)
```

循环里在"记录已经写进 `records`、间隔落盘也已做过"之后调用它：

```python
if self.on_step is not None:
    self.on_step(global_step, self.model, records)
```

`LoRATrainer` 用它把"落适配器"插进循环，**循环本身一行没有复制**。

为什么不复制：循环里每一步都有 day050 辛苦钉住的口径——累积分母、warmup 第 0 步的空更新、`drop_last` 的步数算术。复制一份的代价不是那 60 行代码，而是**那些口径会各自漂移**。

### 4.2 回调的时序契约

回调拿到的是 `(step, model, records)`，其中 `records` 的**长度等于 `step`**——也就是说，回调整点之前的每一步记录都已经写进去了。测试里把这条写成断言：

```python
assert len(records_at_call) == step      # 回调整点一致
assert report.sft["optimizer_steps"] == final_checkpoint.step
```

第二条断言把"回调看到的快照"与"报告里的步数"绑在一起。**一个拿不到完整快照的回调，写出来的检查点就是残缺的**——而残缺的检查点在被加载之前不会暴露任何问题。

### 4.3 回调失败的语义：不静默

回调抛异常会让训练整体失败。这是刻意的：落盘失败（磁盘满、权限、序列化 bug）属于**必须立刻中止**的情况——静默跳过会让"以为存了"变成一颗雷。测试里有一条：回调抛出异常时 `fit` 必须把它抛出来。

### 4.4 续训：加载一个小矩阵

```python
trainer.restore("outputs/lora/adapters/adapter-final")
```

`restore` 只加载适配器（三个文件里的两个），**不加载基座权重**；`r` / `alpha` 与当前模型不一致时直接抛 `AdapterCheckpointError`。

这里有一处必须说清的语义差异：**全参微调的续训是"加载整份权重"，LoRA 的续训是"加载一个小矩阵"**。两者失败的后果完全不同——后者错了只会得到一份错的增量，不会毁掉基座；但它的错误也更难发现（一个缩放被改了的适配器依然能跑出"看起来合理"的输出）。

## 第五章：合并与部署门禁

### 5.1 两种部署形态

```text
形态 A：一个基座 + N 个适配器（推理时动态加载）
形态 B：合并成一个完整模型（merge_and_unload → save_pretrained）
```

选择的关键是"适配器要不要热插拔"。实测（`llama-2-7b` 基座）：

| | 体积 |
|---|---|
| 基座（bf16） | 13 476 831 232 B（12.55 GiB） |
| 适配器 | 274 678 B（0.2620 MiB） |
| 适配器 / 基座 | 2.038e-05（约 49 064 分之一） |
| 10 个合并模型 | 134 768 312 320 B |
| 1 个基座 + 10 个适配器 | 13 479 578 392 B |
| **节省** | **10.00×** |

**"一个基座 + N 个适配器"省掉的正是"每个业务一份完整权重"这件事**——而它的代价（多两次小矩阵乘法、以及"哪个适配器配哪个基座"的运维）在表里看不到。这正是清单里必须有 `base_model` 的原因。

### 5.2 `merge_and_unload` 是不可逆的

```python
model = PeftModel.from_pretrained(model, adapter_dir)   # 先挂上适配器
model = model.merge_and_unload()                        # 再合并（就地替换权重）
model.save_pretrained(output_dir)                       # 落盘成普通模型
```

合并会**就地替换**权重并丢弃适配器，因此它必须发生在"所有需要适配器的动作之后"。生成的合并脚本在合并前打印适配器的内容哈希——**合并是一个不可逆动作，落盘的模型必须能指回它是由哪一份适配器产生的**。

### 5.3 `verify_merge`：把不变式变成门禁

```python
verification = verify_merge(model, eval_batches)   # tolerance 缺省 0.0（逐位一致）
```

实测（557 个上下文）：

```text
检查 557 个上下文 | 逐位一致 True | 最大 logits 差 0.000e+00
loss 6.3136913150 vs 6.3136913150（差 +0.000e+00）| 通过 True
```

`tolerance=0.0` 是缺省，而且这不是苛刻：两条路径做的是同一批浮点运算（`W[i][j] + ΔW[j][i]` 一次算完 vs 每次前向现算一次），结果本就应当相同。**本课实测差值是 `0.00e+00`。**

如果调用方要容忍正数容差，那必须显式给出——因为"合并错了"与"合并对了但有浮点重排"在数值上只差量级：**约定错误带来的是 O(1) 的差异（day051 实测 0.0381），浮点重排带来的是 O(1e-7)**。

**本课为这条门禁专门写了一条"失败时会怎样"的用例**：把 `merge()` 换成"差 0.5"的结果，断言 `bitwise_identical is False`、`max_logit_difference == 0.5`、`passed is False`，并且把 `tolerance` 放宽到 0.5 时同一个结果变成通过。

这条用例守的是一条纪律：**一个永远不会失败的门禁不是门禁**。合并恰好是逐位一致的，所以这条路径只能靠构造偏差来触发——但不写它，将来有人把 `passed` 改成恒真时，所有测试仍然全绿。

### 5.4 生成的脚本

| 脚本 | 行数 | 关键片段 |
|------|------|---------|
| 多卡训练（Accelerate） | 280 | `Accelerator(...)` / `accelerator.prepare(...)` / `if accelerator.is_main_process` |
| 合并（`merge_and_unload`） | 76 | `PeftModel.from_pretrained` / `merge_and_unload` / `save_pretrained` |
| 推理（适配器形态） | 56 | 加载时多一行 `PeftModel.from_pretrained`，并打印清单哈希 |

多卡脚本里必须出现的三处，对应多卡训练的三个真实坑：

1. **`Accelerator` 负责混合精度**——不要把 `TrainingArguments.bf16` 与 `accelerate` 的 `mixed_precision` 同时打开（两套开关会各做一次 autocast 与缩放）；
2. **`accelerator.prepare(...)` 必须在构造 `Trainer` 之前调用**（它负责 DDP 包装、分片与设备放置）；
3. **只在主进程保存**：`if accelerator.is_main_process`——四个进程同时往一个目录写适配器，轻则相互覆盖、重则文件损坏。

## 第六章：一个会在运行时崩的脚本

### 6.1 重复的关键字参数

多卡脚本里这一行是本课踩到的坑：

```python
training_args = TrainingArguments(
    output_dir=args.output_dir,
    gradient_accumulation_steps=1,     # 注释说：累积交给 Accelerator，这里留 1
    **TRAINING_ARGUMENTS,              # 但这份 JSON 里也带这个键
)
```

而 `TRAINING_ARGUMENTS` 来自 `args.to_hf_dict()`——它**包含** `gradient_accumulation_steps`。Python 语义下：

```text
f(x=1, **{"x": 4})  →  TypeError: got multiple values for keyword argument 'x'
```

**脚本语法合法、`compile()` 通过、所有文本断言通过，只有真正运行时才崩。**

修法是在渲染时把那个键从内嵌 JSON 里删掉：

```python
training_arguments = args.to_hf_dict()
training_arguments.pop("gradient_accumulation_steps", None)
```

### 6.2 为什么 `compile()` 拦不住它

`compile()` 检查的是**语法**，而这是一个**求值期的错误**：关键字参数在调用发生时才会被匹配。所有"生成脚本 + compile 验证"的测试都拦不住它——除非有一条用例专门断言"**那个键不在 JSON 里**"。

本课因此加了两条互补的用例：

```python
assert "gradient_accumulation_steps=1" in call_block(script, "TrainingArguments(")
assert "gradient_accumulation_steps" not in extract_json_payload(script, "TRAINING_ARGUMENTS")
```

**两条都要有**：只断言前者，重复键的问题依然存在；只断言后者，累积被漏掉的问题没人发现。

### 6.3 第二类坑：显式 `None` 被吞掉

`LoRATrainer` 的构造里，第一版是这样转发两条缺省的：

```python
if template is not None: sft_defaults["template"] = template
if system_prompt is not None: sft_defaults["system_prompt"] = system_prompt
```

而 day050 的 `system_prompt=None` 有**明确语义**——"不要 system 轮"。把 `None` 与"没传"混为一谈，意味着调用方传 `None` 想训"无 system"的数据时会被静默换成默认提示词：

```text
训练时看到的 prompt ≠ 推理时给的 prompt
```

这是 day050 第 2.1 节列在最隐蔽一类里的缺陷——**它不会报错，只会让效果莫名变差**。本课用自己的测试发现它（断言 `trainer._sft_defaults["system_prompt"] is None` 时拿到 `KeyError`），修法是用一个哨兵值区分两种情形：

```python
_UNSET: Any = object()
if system_prompt is not _UNSET:
    sft_defaults["system_prompt"] = system_prompt
```

### 6.4 这两条坑的共同点

两个都是**"配置转发"环节的缺陷**：一层包装（多卡脚本包装 `TrainingArguments`、`LoRATrainer` 包装 `SFTTrainer`）在转发参数时改变了语义。而这一层恰恰是测试最容易漏掉的地方——因为它看起来"只是在转发"。

这与 day051 第九章的端点 500 是同一条经验的第三次出现：**"每个零件都对"不等于"装起来对"**；而**包装层必须有自己的用例**，尤其是"参数被完整转发"这一类。

## 第七章：接入 API 与配置

### 7.1 两个新端点

```python
@router.post("/finetune/lora/distributed", response_model=LoRADistributedResponse)
@router.post("/finetune/lora/deploy", response_model=LoRADeployResponse)
```

| 端点 | 回答什么 |
|------|---------|
| `/finetune/lora/distributed` | 多卡的派生量（全局批 / 步数 / 学习率缩放 / 每设备显存 / 通信量）+ 可用的 accelerate 与 DeepSpeed 配置 + 启动命令 + 告警 |
| `/finetune/lora/deploy` | 走一遍"保存适配器 → 生成清单 → 验证合并 → 体积对照"，返回门禁结果与两种形态的体积 |

`deploy` 是本课唯一一个**会写磁盘**的端点，而且写的是临时目录（请求结束即删除）——它要演示的正是"一个适配器 = 三个文件 + 一份清单"，所以产物必须是真的。`train_steps=0`（缺省）时适配器未训练，响应里 `adapter_trained=false` 会如实标注这一点；传一个正数就会先在参考模型上真跑几步。

### 7.2 一个"缺省值自相矛盾"的修正

`deploy` 端点最初要求 `target_modules="bigram"`（它用参考模型演示），而全局缺省预设是 `attention`——于是**空请求体必定 400**，与"不传参数就能走完整流程"的意图自相矛盾。

修法是缺省时把预设置为 `bigram`，但**显式**传 `attention` 仍然必须被拒绝：

```python
overrides = dict(req.overrides)
overrides.setdefault("target_modules", "bigram")
```

这条区分很关键：**调用方的显式配置是真实的错误，不该被悄悄改写**；而缺省值是我们自己的选择，应该选择一个能跑通的。

### 7.3 错误码

| 情况 | 状态码 |
|------|--------|
| 未知模型规格 / 未知策略 / 未知精度 / 未知优化器 / 配置非法 | **400** |
| `devices` / `train_size` / `train_steps` 的取值越界，或类型不对 | **422**（Pydantic 在进路由前拦下） |
| 正常 | 200 |

与 day038 建立、day040/041/046/048/050/051 沿用的错误码语言完全一致。

### 7.4 七个配置项

```text
peft_adapter_dir                = "outputs/lora/adapters"
peft_adapter_save_steps         = 0       # 0 = 只在训练结束时落盘一次
peft_adapter_save_total_limit   = 2
peft_devices                    = 1
peft_sharding_strategy          = "ddp"   # ddp / zero2 / zero3
peft_mixed_precision            = "bf16"  # no / fp16 / bf16
peft_lr_scaling_mode            = "linear" # linear / sqrt / none
```

`peft_adapter_save_steps` 缺省是 **0**（只在结束时落盘）：中间适配器是"续训与回滚"才需要的东西，缺省打开只会让产物目录变乱。

## 结语：三条可以带进 M5 的工程结论

1. **可交付物不是权重，是"权重 + 配置 + 状态 + 清单"。** 一个适配器是三个文件加一份含哈希的清单；哈希只覆盖"权重是不是同一份"，清单负责回答"配哪个基座"。**产物要能指回它的来源**——这与 day050 把词表随检查点落盘是同一条纪律，只是今天的产物更小、更容易被随手 cp 而丢掉元信息。

2. **分片策略的收益取决于"哪一项占用最大"。** 全参微调的大头是优化器状态（8 字节/参数），所以 `zero2` 就省掉 2.67 倍；LoRA 的大头是冻结的基座权重，所以 `zero2` 几乎是 0、只有 `zero3` 有用——而 `zero3` 的通信量要比 `zero2` 高三个数量级（LoRA 场景）。**"能不能多卡跑"与"多卡跑得值不值"是两个问题，第二问的答案在这一课里是算术，不是感觉。**

3. **包装层的缺陷最难发现，因为它看起来只是在转发。** 重复的关键字参数会让脚本在运行时崩（而 `compile()` 通过），显式 `None` 被吞掉会让训练数据与推理输入不一致（而 loss 曲线完全正常）。两个都不是算法问题、都是"转发语义"问题。**给包装层写用例时，重点不是"它有没有跑通"，而是"参数有没有被完整、正确地传下去"。**

> **诚实的说明**：本日所有"多卡"数字都是**算术结果**，不是真机实测——`per_device_gib`、通信量、全局批与步数都由公式算出，环境里没有多卡也没有 GPU。生成的 accelerate / DeepSpeed 配置在测试里做了**往返核对**（渲染 → 解析 → 与来源逐键比对）与字段名核对，但它们**没有在真实集群上跑过**：真实的吞吐取决于通信拓扑、算子融合与重叠策略，本课的通信量是一个刻意保守的量级估计（"梯度通信 + 两倍参数规模的 all-gather"），**不做精确建模**，因为精确建模需要知道层数、拓扑与重叠策略，而本课要传达的结论只需要量级。另外，合并验证与部署体积对照是在 557×557 的参考模型上做的，`llama-2-7b` 的体积数字来自公开参数量规格（6 738 415 616，day051 已逐项核对）。
