## 第 1 题

**答案：C**

解析：A、B、D 是教程第一章归纳的失控模式——原样重试（没有诊断的重试只是在消耗步数配额）、Panic 式乱撞（局部应激反应，无人全局复盘）、耗尽步数（无声的失败，没有任何异常抛出）。C"静默成功"在逻辑上自相矛盾：工具失败后模型即使输出答案，那也只是碰巧或编造，属于 B 的"编答案收场"，而不是一种真实的"成功"模式。更何况 ReAct 循环里模型看到的 Observation 就是错误文本，它无法"无视错误还保证正确"——它根本没有独立的真相来源。

## 第 2 题

**答案：B**

解析：尝试总数 = 1 次原始尝试 + `max_retries` 次重试 = 3 次，每轮尝试恰好调用 Agent LLM 至少一次（本题设定每轮一步即失败），所以 Agent LLM 共 3 次。Reflector 只在"失败且还有重试机会"时被调用：第 1、2 次失败后各反思一次，第 3 次（最后一次）失败后 `attempt == max_attempts` 直接返回，**不再反思**——产出的建议无人消费，调了也是白调。所以 Reflector 共 2 次。这正是教程 4.1 节"不为无人消费的结果付费"的编排细节，`test_max_retries_limits_attempts` 用 `len(agent_llm.calls) == 3` 和 `len(reflector_llm.calls) == 2` 把这个承诺钉死成了可执行断言。

## 第 3 题

**答案：C**

解析：走一遍 `parse_reflection` 的逻辑：`find("{")` 能找到左括号，但 `rfind("}")` 找不到（或位置在 `{` 之前），`end > start` 不成立，直接跳过 JSON 分支，落入兜底 `return cleaned or "LLM 未给出有效复盘", ""`。即使 `}` 存在但 JSON 损坏，`json.loads` 抛出的 `JSONDecodeError` 也被 `except` 捕获、`data` 置 None，同样落入兜底。**`parse_reflection` 不抛任何异常**——这是与 `parse_plan` 刻意相反的设计：反思是建议性数据，容错机制自身绝不能成为新的故障源（软着陆 / 优雅降级）。A、B 错在抛异常；D 错在丢掉了原文里的信息——原文虽然没结构，但整段作为 `reason` 至少保留了审计价值。

## 第 4 题

**答案：错**

解析：这正是教程 2.1 节的关注点分离——**Reflector 只在"已被判定为失败"的轨迹上工作，失败检测是 ReactAgent（执行层）的职责**。证据在代码里：`Reflector.reflect(task, trajectory)` 的入参没有任何"请帮我判断是否失败"的语义，`REFLECT_PROMPT` 里写的也是事实陈述"该次执行已经失败"，而不是提问"这次是否失败"。`Reflection.failed` 恒为 True，是调用方传入的事实，不是 LLM 的判断。为什么这样切？执行层最清楚自己走到哪一步、工具返回了什么（它手里有 Observation 原文）；让反思器再做一次检测，等于把同一份判断逻辑放两处，迟早不一致。

## 第 5 题

**答案：对**

解析：向后兼容由两道守卫保证。其一，`max_attempts = 1 + (self.reflector.max_retries if self.reflector is not None else 0)`——不传 reflector 时恒为 1，`run()` 只跑一轮。其二，快速失败分支的条件是 `if self.reflector is not None and observation.startswith(_ERROR_PREFIXES)`，`reflector is None` 时短路求值，整个分支被跳过，错误 Observation 照旧 `messages.append` 回喂、循环继续。`tests/test_react_loop.py` 是 day006 的回归测试，今天一字未改、全部通过——兼容性的可执行证明。这也是"新能力以可选参数接入"的标准手法：**默认路径零变化，新行为全靠显式装配激活。**

## 第 6 题

**答案：错**

解析：注入处有 `if suggestion:` 守卫：

```python
if suggestion:
    system_content += REFLECTION_HINT.format(suggestion=suggestion)
    user_content += f"\n\n上一次失败的教训（来自反思模块）：{suggestion}"
```

suggestion 为空串时（比如反思输出不是 JSON、软着陆兜底后 `suggestion == ""`），两处都不注入，下一轮的 prompt 与首轮完全相同——系统从"反思增强"优雅降级为"普通重试"。`test_parse_error_in_reflection_output_still_retries` 验证的正是这条路径。如果没有这个守卫，prompt 里会出现"上一次失败的教训："后面跟着一片空白的怪异文本，反而可能误导模型。

## 第 7 题

**参考答案**：

**为什么策略相反**：两种输出的**关键性**不同。

`parse_plan` 解析的是**负载数据**：整个执行流程都建立在计划之上——没有计划，执行器无事可做。解析失败意味着"系统此刻无法工作"，此时唯一诚实的选择是抛异常、快速失败，把问题暴露给调用方（未来由 RePlanner 兜底重规划）。任何兜底（比如"解析不出来就返回空计划"）都会把故障推迟到更下游、以更诡异的形式爆发。

`parse_reflection` 解析的是**建议数据**：有建议则重试更聪明，没建议则退化为普通重试，系统依然能工作。反思本身就是容错机制，如果它解析失败也抛异常，就会出现"任务失败 → 调反思 → 反思再抛异常"的连环故障——**容错机制自身成了新的故障源**，这是容错设计的大忌。

**判断依据**：问一个问题——"这份输出拿不到时，系统还有合理的降级路径吗？"有（反思 → 普通重试）就软着陆兜底；没有（计划 → 无任务可执行）就快速失败抛异常。同一条原则也适用于别处：配置加载失败该抛异常（没有配置无法运行），缓存未命中该兜底（本来就是可选加速）。

## 第 8 题

**参考答案**：

**优点**：快速失败把"模型没看懂错误"的时刻显性化了。模型一旦开始原样重试，说明错误 Observation 里的信息不足以让它自我纠正——继续在循环里空转，每一步都是一次 LLM 调用的纯浪费，而且失败步骤堆积在 messages 里污染后续上下文。中断后转入专门的复盘通道，换来的是带诊断的重启：原因 + 可操作的建议，新一轮还从干净的消息列表开始。

**代价**：丢掉了循环内自愈的机会。浅层错误（Observation 里已写明正确用法）或一次性抖动（网络超时）本来模型当场就能改，现在却要付出"一次反思调用 + 全新一轮"的固定成本；对某些工具错误类型，这是杀鸡用牛刀。

**为什么这个折中合理**：两种策略服务的是深浅两级错误，本就不矛盾。把选择权交给组装者——不传 reflector 时走 day006 的自愈路径（适合错误浅、工具可靠的场景），传了才走快速失败 + 反思（适合错误需要诊断、追求可靠性的场景）——既没有强迫所有用户为反思付费，也没有删除已验证的自愈能力。生产系统里更精细的做法是按错误类型分流（可重试错误自愈、语义错误反思），那就是这个折中的下一级演进。

## 第 9 题

**参考答案**：

**盲区**：只注入最新一条建议，假设了"每一轮犯的是同一个错误"。如果模型第 1 轮败在"工具输入格式错"，第 2 轮修好了格式却败在"调错了工具"，那么第 3 轮拿到的只有"别调错工具"的建议——**"格式要用阿拉伯数字"这条教训被遗忘了**，模型完全可能在第 3 轮把格式错误再犯一遍。修正了错误 B 又复活了错误 A，乒乓式打转。

**改进**：把 `run()` 里的 `suggestion` 从单条字符串改为累积列表，每轮注入全部历史教训：

```python
lessons.append(reflection.suggestion)
# 注入时拼成编号清单：
# 1. 请使用阿拉伯数字表达式
# 2. 只调用可用工具清单内的工具
```

`Reflector.reflections` 已经天然持有全部历史，改动很小。

**代价**：上下文成本随重试次数线性增长，每轮注入的文本越来越长，稀释模型对任务本身的注意力；而且历史教训之间可能相互矛盾（早期建议基于早期错误现场），全部堆上去可能造成混淆。更精致的版本是给教训做去重/压缩，或只保留最近 N 条——但那就引入了新的调参面。这正体现了"注入上下文的每一个 token 都要有明确目的"这条原则的另一半：**注入得越多，目的就越模糊。**

## 第 10 题

**参考实现**：

**（1）`smart_research_agent/tools/base.py` 新增 ToolResult：**

```python
from dataclasses import dataclass


@dataclass
class ToolResult:
    """工具执行的结构化结果：成功标志由工具自己声明."""

    success: bool
    output: str
```

**（2）`CalculatorTool.execute` 改为返回 ToolResult：**

```python
def execute(self, expression: str = "", **kwargs: Any) -> ToolResult:
    try:
        result = _safe_eval(ast.parse(expression, mode="eval"))
    except (SyntaxError, ValueError, ZeroDivisionError) as exc:
        return ToolResult(success=False, output=f"计算失败: {exc}")
    return ToolResult(success=True, output=str(result))
```

**（3）`ReactAgent._execute_tool` 与 `_attempt` 改造：**

```python
def _execute_tool(self, step: ReActStep) -> ToolResult:
    tool = self.registry.get(step.action or "")
    if tool is None:
        return ToolResult(success=False, output=f"错误：不存在名为 {step.action} 的工具")
    required = tool.parameters.get("required") or []
    kwargs: dict = {} if not required else {required[0]: step.action_input or ""}
    try:
        return tool.execute(**kwargs)
    except Exception as exc:  # noqa: BLE001
        logger.warning("工具执行异常: %s", exc)
        return ToolResult(success=False, output=f"工具执行失败: {exc}")
```

`_attempt` 循环体内：

```python
result = self._execute_tool(step)
observation = result.output
trajectory.append(
    f"第{step_no}步 Thought: {step.thought} | "
    f"Action: {step.action}({step.action_input}) | Observation: {observation}"
)
if self.reflector is not None and not result.success:
    logger.warning("检测到工具执行失败，中断本轮转入反思: %s", observation)
    return f"尝试失败：{observation}", True, trajectory
```

同时删除 `_ERROR_PREFIXES` 常量。Observation 文本格式不变，故既有断言（`"不存在" in m.content`、`"失败" in answer`）无需改动。

**（4）新增误判防护测试：**

```python
class _OddEchoTool(BaseTool):
    """正常输出恰好以『计算失败』开头的工具：旧机制必误判."""

    @property
    def name(self) -> str:
        return "odd_echo"

    @property
    def description(self) -> str:
        return "回显词条"

    @property
    def parameters(self) -> dict:
        return {"type": "object", "properties": {}, "required": ["q"]}

    def execute(self, q: str = "", **kwargs) -> ToolResult:
        return ToolResult(success=True, output=f"计算失败率词条：{q}")


def test_no_false_positive_on_error_like_text():
    registry = ToolRegistry()
    registry.register(_OddEchoTool())
    agent_llm = MockLLM(responses=[
        "Thought: 查词条\nAction: odd_echo\nAction Input: 定义",
        "Thought: 拿到了\nFinal Answer: 已查到",
    ])
    reflector_llm = MockLLM()
    agent = ReactAgent(llm=agent_llm, registry=registry, reflector=Reflector(llm=reflector_llm))

    assert agent.run("查一下计算失败率") == "已查到"
    assert reflector_llm.calls == []  # 旧机制下这里会被误触发一次反思
```

**思考题**：成功标志由工具自己声明，因为**工具是唯一知道自己执行语义的一方**——Agent 看到的只是输出文本，文本里出现"失败"二字和执行真的失败是两回事。这与"解析 LLM 输出必须锁定结构"是同一条原则的两面：凡是需要程序消费的输出，都要用显式结构传递语义，而不是让消费方从自由文本里猜。对 LLM 我们用提示词锁定（`Thought:/Action:` 标记、JSON 数组），对工具我们用类型锁定（`ToolResult.success`）——**自由文本是给人读的，程序之间要用契约说话。**
