## 第一部分：选择题

**第 1 题答案：A**

解析：套公式前先数清楚两个集合。

- 相关文档全集 `relevant` 共 4 个，命中 3 个 → **召回率 = 3/4 = 0.75**（"相关的找回了几成"，分母是 relevant）。
- 返回结果 `retrieved` 共 5 个，其中 3 个相关 → **精确率 = 3/5 = 0.60**（"端上来的有几成是对的"，分母是 retrieved）。

选 B 是把两个分母弄反了；选 C/D 是没分清两个分母不同。记忆口诀：**召回看"全集"，精确看"结果集"**。

**第 2 题答案：B**

解析：逐项分析。

- A 错：RR **只看第一个命中**的位置，第一个命中之后的相关文档完全不产生贡献。
- B 对：两种情况第一个命中（`a`）都在第 1 位，RR 都是 1.0。这正是 MRR"只看首个命中"的体现，也是 `tests/test_rag_eval.py` 中 `test_only_first_hit_matters` 固化的行为。
- C 错：收集型查询关心"找全"，主指标是召回率；MRR 适合导航型查询（用户心里只有一个正确答案）。
- D 错：RR = 1/rank，第 4 位 → 0.25，不是 0.75。注意没有"1 - 1/rank"这种变形。

**第 3 题答案：B**

解析：NDCG 三步各有分工，别混淆：

- **分级相关**（增益 `2^rel - 1`）解决"相关程度有差别"——对应 D 的干扰项，但 D 描述错了（等级是输入不是输出）。
- **位置折损**（`1/log2(i+1)`）解决"排越后贡献越小"——C 描述的是折损，不是归一化。
- **归一化**（除以 IDCG）解决"不同查询的相关文档数量不同，裸 DCG 无法横向比较"。除以该查询的理想 DCG 后，任何查询的分数都落在 [0, 1]，求平均才有意义。

A 是干扰项：除零保护只是实现的边界处理，不是设计动机。

## 第二部分：判断题

**第 4 题答案：召回率部分对，精确率部分错（整体判"错"）**

解析：

- **召回率：对。** Top-K 扩大后，原来的 Top-3 结果仍是 Top-10 的子集，命中的相关文档不会减少，只可能新增 → 召回率单调不减。
- **精确率：错，"一定下降或不变"不成立。** 精确率 = 命中数 / K。反例：Top-3 命中 1 个（精确率 0.33），扩到 Top-10 后新增的 7 个里有 5 个相关 → 命中 6/10 = 0.60，精确率反而上升。直觉上"K 越大精确率越低"只在"新增结果大多不相关"时成立，这不是数学必然。经验趋势可以谈，"一定"二字就是错的——判断题里看到"一定/必然/只"要特别警惕。

**第 5 题答案：错**

解析：端到端准确率是**结果指标**，检索评估是**诊断指标**，两者解决不同问题：

1. **归因**：答案错了可能是召回失败、排序失败或生成失败三种病灶，修复动作完全不同（调 embedding/分块 vs 加 rerank vs 改 Prompt）。只有端到端分数，定位全靠猜。
2. **成本**：生成评估要调 LLM，检索评估是纯本地计算。迭代检索参数时只跑检索评估，快几个数量级。
3. **容错掩盖**：LLM 有时会"蒙对"（检索没返回关键文档，模型靠参数化知识答对了），端到端达标会掩盖检索的真实缺陷，换个问题就露馅。

分段评估的价值在于把"系统好不好"拆解成"哪一段不好"。

## 第三部分：问答题

**第 6 题答案**

已知等级 `{a: 2, b: 1}`，实际排序 `["b", "a"]`。

第 1 步算各位置增益（`2^rel - 1`）：

```text
b: rel=1 → 增益 1
a: rel=2 → 增益 3
```

第 2 步算折损系数（`1/log2(i+1)`）：

```text
第 1 位: 1/log2(2) = 1.0000
第 2 位: 1/log2(3) ≈ 0.6309
```

第 3 步 DCG（按实际排序 b 在前）：

```text
DCG = 1×1.0000 + 3×0.6309 = 1 + 1.8928 = 2.8928
```

第 4 步 IDCG（理想排序 a 在前，增益 3 吃满第 1 位折损）：

```text
IDCG = 3×1.0000 + 1×0.6309 = 3.6309
```

第 5 步归一化：

```text
NDCG = 2.8928 / 3.6309 ≈ 0.7967
```

排反一对文档，损失约 0.20。对照实现：`tests/test_rag_eval.py::TestNdcg::test_inverted_pair` 断言的正是这个数。

**第 7 题答案**

核心逻辑是**两段式链路的容错不对称**：

- **检索漏了（召回失败）→ 无药可救。** 相关文档没进 Top-K，生成器看到的上下文里就没有这个事实。LLM 不可能检索它没见过的知识，只能要么拒答要么编造（幻觉）。召回缺口会 1:1 传导成生成错误。
- **检索混入噪声（精确率低）→ 有一定缓冲。** Top-K 里混进一两篇无关文档，LLM 的注意力机制通常能识别并忽略它们，答案质量未必受损。

所以 RAG 检索的常见调优目标是"在精确率可接受的前提下把召回率顶上去"——宁可多喂两篇噪声，也不能漏掉关键文档。这也是工程上常用"Top-K 放大召回 + rerank 精排"两段式检索的原因：第一段全力保召回，第二段把排序修好。

注意边界：这个结论不是"精确率无所谓"。噪声太多会挤占上下文窗口、稀释注意力、推高 token 成本，超过生成器容错阈值后答案同样崩坏。

**第 8 题答案**

**MockEmbedding 缺了什么**：它用 SHA-256 哈希生成伪向量，只保证"同文本同向量"的确定性，**不保证"语义相近则向量相近"**。两个只差一个字的文本，哈希向量也毫无相关性。用它做检索，排序近似随机，期望值无法手算——断言只能写"值在 [0,1] 之间"，验证不了排序逻辑。

**ToyEmbedding 补上了什么**：词表到标准基的映射（"向量"→[1,0,0,1] 中的第 0 维等），让每篇语料、每个查询的向量完全透明，余弦相似度和 Top-K 排序可以在纸上逐步算出，从而断言**精确的**检索顺序与四个指标值。

**体现的原则**：测试替身（test double）要模拟被依赖物的**哪些性质**，取决于被测逻辑依赖哪些性质。检索排序依赖的是"语义相关性 → 向量相似度"这条性质，MockEmbedding 恰好把它丢掉了。这时正确的做法不是降低断言精度凑合，而是造一个抽象层级正确的假实现。这也呼应依赖注入的价值：`RagEvaluator` 只依赖 `EmbeddingProvider` 抽象，替换实现零成本。

## 第四部分：编程题

**第 9 题参考答案**

在 `smart_research_agent/evaluation/rag_metrics.py` 末尾追加：

```python
def hit_rate(retrieved_ids: list[str], relevant_ids: list[str]) -> float:
    """命中率（Hit Rate）：Top-K 中至少命中一个相关文档则记 1.0，否则 0.0.

    与 recall 的区别：recall 衡量"相关文档找回了多大比例"（0~1 连续值），
    hit_rate 只问"有没有找到至少一个"（二值）。它对"用户只要一个入口
    就能继续"的场景（如客服知识库、FAQ 导航）更贴切，也比 recall
    对标注不完整（relevant_ids 标少了）更鲁棒。
    """
    if not relevant_ids:
        return 1.0
    return 1.0 if set(retrieved_ids) & set(relevant_ids) else 0.0
```

在 `tests/test_rag_eval.py` 中追加：

```python
class TestHitRate:
    def test_hit(self):
        assert hit_rate(["x", "a"], ["a", "d"]) == 1.0

    def test_miss(self):
        assert hit_rate(["x", "y"], ["a"]) == 0.0

    def test_empty_relevant(self):
        assert hit_rate(["x"], []) == 1.0
```

要点：空 relevant 的约定与 recall 保持一致（1.0，没有欠账）；用集合交集判断而不是逐个比较，重复 id 不影响结果。跑 `pytest tests/test_rag_eval.py -k hit_rate -q --no-cov` 应 3 个用例全绿。

**第 10 题参考答案**

`scripts/compare_topk.py`：

```python
"""Top-K 对比实验：观察四个指标随 K 变化的趋势."""

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from smart_research_agent.evaluation.rag_eval import RagEvaluator, load_jsonl
from smart_research_agent.memory.vector_store import InMemoryVectorStore
from scripts.eval_rag import CharBagEmbedding

DATA_DIR = Path(__file__).resolve().parent.parent / "data" / "eval"


def main() -> None:
    corpus = load_jsonl(DATA_DIR / "rag_corpus.jsonl")
    eval_set = load_jsonl(DATA_DIR / "rag_eval.jsonl")

    evaluator = RagEvaluator(vector_store=InMemoryVectorStore(), embedding=CharBagEmbedding())
    evaluator.index_documents(corpus)

    print(f"{'K':>3} {'recall':>8} {'precision':>10} {'mrr':>8} {'ndcg':>8}")
    for k in (1, 3, 5):
        r = evaluator.evaluate_retrieval(eval_set, top_k=k)
        print(f"{k:>3} {r.mean_recall:>8.4f} {r.mean_precision:>10.4f} "
              f"{r.mean_mrr:>8.4f} {r.mean_ndcg:>8.4f}")


if __name__ == "__main__":
    main()
```

实际输出（已用项目评测集验证）：

```text
  K   recall  precision      mrr     ndcg
  1   0.7500    0.8333   0.8333   0.7465
  3   0.9167    0.3333   0.9167   0.8623
  5   1.0000    0.2333   0.9167   0.9176
```

趋势解读：

- **召回率单调上升**：K 越大覆盖的相关文档越多，必然不减（0.75 → 0.92 → 1.00）。
- **精确率单调下降**：分母 K 增大而命中数增长变慢，被稀释（0.83 → 0.33 → 0.23）。这一对就是教科书上的召回-精确权衡。
- **MRR 基本不变**：K=3 之后不再变化（0.9167 → 0.9167）。只要相关文档本来排得靠前，K 加大不改变第一个命中的位置；MRR 对 K 不敏感正是它"只看首个命中"的直接推论。
- **NDCG 随 K 上升**：0.75 → 0.86 → 0.92。注意 NDCG **对 K 不保证单调**——本评测集标了 1 级的"边缘相关"文档，K 增大把它们收了进来，增益增加；如果新增位置全是零相关文档，NDCG 也会因折损被挤占而下降。读 NDCG 要结合标注密度看。

一句话总结：**K 改变的是"覆盖"与"纯度"的配比，而首个命中的位置由排序质量决定、与 K 无关**——这就是为什么 MRR 要看、但绝不能只看 MRR。
