## 第一部分：选择题

### 第 1 题

**答案：D**

**解析**：D 错误——subword 分词的词表是**从语料自动学出来的**（BPE 合并最高频对、WordPiece 选似然提升最大对、Unigram 裁剪大词表），没有任何人工构词法规则表，这正是它能处理新词、错拼、任意语言的原因。`encode("deeply")` 演示了这一点：算法从未见过 "deeply"，但靠学到的 `deep` 片段加字符兜底完成切分，全程无人工介入。A、B 分别准确描述了词级与字符级两个极端的缺陷；C 是 subword 的核心思想。

### 第 2 题

**答案：B**

**解析**：BPE 每轮选**按词频加权后频率最高的相邻符号对**合并。我们的演示里第一轮 `("d","e")` 与 `("e","e")` 并列 12 次（deep×4 + deeper×3 + deepest×5），靠字典序 tie-breaking 选出 `("d","e")`——这个细节同时说明 BPE 是纯频率驱动的贪心算法，不涉及任何语义（C 错）；长度（A）与随机性（D）都不是选择标准。贪心意味着 BPE 不保证全局最优词表，但工程上足够好且训练极快。

### 第 3 题

**答案：B**

**解析**：`freq(pair) / (freq(a) * freq(b))` 是点互信息的变体：分母是"两符号若相互独立时的期望共现频率"，分子是实际共现频率。比值高说明这对符号**结合得比偶然更紧密**——例如 "un" 与 "##able" 各自都常见，但它们黏在一起的倾向远超独立假设下的期望，这种片段语言学上更有意义。等价表述：选使训练语料似然提升最大的合并。A 描述的正是 BPE 而非 WordPiece；C、D 都不在 WordPiece 的目标函数里。

## 第二部分：判断题

### 第 4 题

**错。**

BPE 没有任何专门的 OOV 处理机制——OOV 是贪心合并的**自然副产品**。编码按合并规则的产生顺序套用，未见过的词会一路拆到已学片段乃至单个符号（工业版是字节）。演示：`encode("deeply")` 在只学过 deep/deeper/deepest/learning 的词表上得到 `["deep", "l", "y", "</w>"]`——`deep` 是学过的高频片段，没学过 `ly` 就退回字符，编码照样完成。对比词级分词才需要 `<UNK>` 回退表（且 `<UNK>` 是信息丢失而非"解决"）。

### 第 5 题

**错。**

tiktoken 的 Python 包只含编码逻辑，BPE 词表文件（cl100k_base 约 1.7 MB）在**首次使用时从公网下载**，之后缓存在本地（Windows 默认 `%LOCALAPPDATA%\Temp\data-gym-cache`，可用 `TIKTOKEN_CACHE_DIR` 改位置）。所以"刚装好包的机器"若无网络且无缓存，首次 `get_encoding` 会失败——这正是 `TokenCounter` 必须实现字符估算降级路径、并用 `backend` 属性显式暴露当前路径的原因。本机实测两个词表均已缓存，断网可加载，但这属于"缓存命中"而非"包内自带"。

### 第 6 题

**对。**

实测（cl100k_base）：语义等价的 "The quick brown fox jumps over the lazy dog"（43 字符）是 9 tokens，中文 "敏捷的棕色狐狸跳过了懒惰的狗"（14 字符）是 27 tokens——**约 3 倍**。原因：词表训练语料以英文为主，汉字覆盖不足，部分汉字退回字节级编码（一个 UTF-8 汉字 3 字节，最差 1 字 = 2~3 tokens）。直接工程推论：中文场景的上下文预算、max_tokens 都要打 2~3 倍余量；新词表在改善（o200k_base 下同句中文降到 16 tokens），选型时"对中文更便宜"是真实存在的考量维度。

## 第三部分：问答题

### 第 7 题

（1）**词级分词**：词表无法覆盖词形变化、复合词、新造词与错拼，未登录词只能记 `<UNK>` 信息全丢；且词表越大，模型输出层参数越多。**字符级分词**：词表极小、永不 OOV，但序列长度爆炸——注意力计算随长度平方增长，单字符几乎无语义，模型要从零学"字符拼词"。

（2）subword 让**频率决定粒度**：高频词（"the"、"deep"）整体进词表，获得词级的短序列；低频/未见词拆成常见片段（"un"+"belie"+"vable"），获得字符级的覆盖率。三个指标（词表大小、序列长度、OOV 风险）都落在两个极端之间的甜点位。

（3）以 256 个字节为初始符号是**覆盖率的终极兜底**：任何 UTF-8 文本都是字节序列，汉字、emoji、控制字符、乱码全都可编码，OOV 在定义上被消除（不存在"没见过的字节"）。若以 Unicode 字符为初始符号，词表要先枚举十几万个码点，仍可能遇到训练语料里没出现过的生僻字。代价是高频汉字若没学进合并表会退回多字节编码（这正是第 6 题中文 token 膨胀的机制），收益是普适性与实现简洁——初始词表固定 256，与语言无关。

### 第 8 题

（1）对中文、日文、泰文等**书写上不用空格分词**的语言失效——整句话是一个"词"，预分词直接退化。

（2）SentencePiece **取消预分词假设**：直接从原始字符流训练，把空格当作普通字符（用 `▁` 表示）参与合并与统计。空格不再是分隔符，分词管线对所有语言统一，"▁世界" 与 " 世界" 可以学出不同的片段。

（3）构造方向相反：BPE **自底向上**（从字符/字节逐轮合并到目标词表大小），Unigram **自顶向下**（从超大的候选词表出发，用 EM 估计片段概率，反复删除"删掉后语料总似然下降最小"的片段直到达标）。Unigram 的概率化带来独特能力：同一句子存在多种合法切分且各自带概率，训练时可按概率**采样不同切分**（subword regularization）——等价于对输入做数据增强，模型见过同一句子的多种 token 化方式，对噪声与罕见表达的鲁棒性更好；BPE/WordPiece 的切分是唯一确定的，没有这层正则化。

### 第 9 题

（1）窗口按 **token** 计而非字符。128K tokens 对英文约 9.6 万词，但 cl100k_base 下中文 1 字常需 2~3 tokens，128K 窗口实际只装得下 4~5 万汉字。RAG 塞检索结果、长文档总结等场景的截断点比中文用户的直觉早得多——必须先用 `count_tokens` 量过再塞。

（2）预估与记账是**同一条成本时间轴的两端**：事前 `estimate_cost` 说"这次调用大约 $0.0001"，事后 `CostTracker` 记"实际花了 $0.0001"。若两者价格表不同（预估用旧价、记账用新价）或计数口径不同（预估按字符、记账按 BPE），预算与账单系统性对不上，"是否超预算"的判断失去意义，成本归因报表也会失真。共用 `DEFAULT_PRICE_TABLE` 与同一个 `TokenCounter` 是让两个工具可交叉验证的工程纪律。

（3）max_tokens 是硬截断（day033：生成没有"说完才停"的内在保证）。中文回答 token 消耗是英文的 2~3 倍，按英文经验设的 max_tokens 会把中文回答**拦腰截断**；Agent 场景的回答常是 JSON/结构化输出（ReAct 的 `Action:` 行），截断导致解析失败 → 触发重试 → 重试重新消耗全部输入 token 加一轮输出。省下的几十个输出 token，换来一整轮调用的成本与延迟——"省小钱亏大钱"，且在中文场景被 2~3 倍的 token 膨胀进一步放大。

### 第 10 题

**参考代码**（`scripts/token_budget_demo.py`，已加入 day034 快照）：

```python
"""day034 习题第 10 题参考解答：迷你 BPE 训练 + token 预算对比实验."""

from __future__ import annotations

import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).resolve().parent.parent))

from smart_research_agent.llm.bpe_demo import encode, train_bpe
from smart_research_agent.llm.tokenizer import TokenCounter


def demo_bpe() -> None:
    corpus = {"deep": 4, "deeper": 3, "deepest": 5, "learning": 6}
    merges, vocab = train_bpe(corpus, 16)
    print("== 迷你 BPE 合并规则表（前 16 轮）==")
    for i, m in enumerate(merges, 1):
        print(f"  {i:>2}. {m.pair} -> {m.merged!r}")

    # (a) 第一条规则：("d","e") 与 ("e","e") 频率并列 12，字典序小者胜出
    assert merges[0].merged == "de", merges[0]
    # (b) 最高频整词 deepest（词频 5）进入词表，编码为单个符号
    assert encode("deepest", merges) == ["deepest</w>"]
    # (c) 未见词 "deeply" 被拆成已知片段 deep + 字符兜底 —— OOV 的现场演示
    assert encode("deeply", merges) == ["deep", "l", "y", "</w>"]
    print(f"最终词表: {vocab}")
    print(f"encode('deepest') = {encode('deepest', merges)}  (高频整词 -> 单 token)")
    print(f"encode('deeply')  = {encode('deeply', merges)}  (未见词 -> 已知片段 + 字符兜底)")


def demo_token_count() -> None:
    samples = [
        "请用三句话总结 Transformer 的核心思想。",
        "帮我比较一下 BPE 和 WordPiece 两种分词算法的差异。",
        "Summarize the core idea of the Transformer architecture in three sentences.",
        "Explain the difference between BPE and WordPiece tokenization.",
    ]
    precise = TokenCounter()
    fallback = TokenCounter(prefer_tiktoken=False)
    print(f"\n== token 计数对照（精确路径 backend={precise.backend}）==")
    for text in samples:
        n_precise = precise.count_tokens(text, "gpt-4o")
        n_fallback = fallback.count_tokens(text)
        print(f"  精确 {n_precise:>3} | 估算 {n_fallback:>3} | {text[:24]}…")
        assert n_precise > 0 and n_fallback > 0


def demo_cost() -> None:
    prompt = "请详细分析 RAG 与微调各自的适用场景，并给出选型建议。"
    counter = TokenCounter()
    mini = counter.estimate_cost(prompt, "gpt-4o-mini", expected_completion_tokens=200)
    full = counter.estimate_cost(prompt, "gpt-4o", expected_completion_tokens=200)
    print("\n== 成本预估（同一提示词，预计输出 200 token）==")
    print(f"  gpt-4o-mini: ${mini['total_cost_usd']:.6f}  (输入 {mini['prompt_tokens']} token)")
    print(f"  gpt-4o     : ${full['total_cost_usd']:.6f}  (输入 {full['prompt_tokens']} token)")
    assert full["total_cost_usd"] > mini["total_cost_usd"]


def main() -> int:
    print(f"本机计数路径: {TokenCounter().backend}")
    demo_bpe()
    demo_token_count()
    demo_cost()
    print("\n全部断言通过")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

**解析**：

1. **频率决定一切**：观察合并表的走向——`deep` 家族（合计词频 12）在第 1~4 轮就合并成 `deep`，而词频 3 的 `-er` 后缀到 16 轮仍未合并，`deeper` 在最终词表里是 `('deepe', 'r', '</w>')` 三个符号。词频高低直接翻译成"切分粒度粗细"，这就是"常见词整体成 token、罕见词拆片段"的算法实现。
2. **tie-breaking 是正确性的一部分**：第一轮 `("d","e")` 与 `("e","e")` 同为 12 次，若无字典序规则，结果取决于字典遍历顺序，测试就无法断言。工程教训：**"可重复的确定性"本身就是功能**，尤其教学与 CI 场景。
3. **OOV 演示**：`deeply` 不在语料中，编码结果是 `deep`（学过的片段）+ `l`、`y`（退回字符）。词表永远可以"拼"出未知词，区别只在用几个 token。
4. **估算路径的偏差方向值得读**：两条中文样本精确值（10/18）低于估算值（16/21）——`estimate_tokens_chars` 按 CJK 1 token/字，而 o200k_base 词表对常见中文词组（"总结"、"比较"）已有整词 token，比"一字一 token"更省；英文样本估算值偏高是因为空格与标点摊薄了"4 字符 1 token"的密度。**估算的价值在数量级正确，精确值必须来自真实分词器**。
5. **成本对比的量级感**：同一提示词，gpt-4o 的预估费用是 gpt-4o-mini 的约 17 倍（输入单价 0.0025 vs 0.00015、输出 0.01 vs 0.0006）——这就是 day033 `CostFirstStrategy` 省钱空间的来源，也是事前 `estimate_cost` 存在的理由：看到 17 倍的差价，你才会认真考虑这条提示词值不值得用强模型。
