## 第 1 题

**答案：B**

解析：MCP 的核心是**协议标准化**：工具供给方实现一次 MCP Server，任何实现了 MCP Client 的 Agent 都能消费它，双方各自只写一次协议实现，N×M 降到 N+M。A 错——MCP 恰恰是为"工具不在本地进程"设计的，改成本地类违背初衷；C 错——让 LLM 读源码生成调用既不可靠也不安全；D 错——MCP 是 RPC 协议（JSON-RPC 2.0 over stdio/sse），与消息队列无关，且"统一队列"本身仍是另一种点对点拓扑的包装。

## 第 2 题

**答案：D**

解析：D 说反了。随用随连把建连、握手这两个**固定成本**摊到每一次工具调用上，子进程启动是数百毫秒级开销，生产环境无法接受；而"无状态"在这里是伪优点——MCP 会话本来就是有状态的（握手时协商的协议版本、能力声明都活在连接里）。A、B、C 都是正确描述：C 尤其值得注意，随用随连确实"代码好写"，这正是它被新手首选、又被性能现实否决的原因——**简单性和效率经常在连接管理上打架，常驻连接是付出代价换来的效率**。

## 第 3 题

**答案：B**

解析：会话底层的 anyio 流（内存流或套接字流）把通知原语（事件、锁、回调）注册在创建它的循环 A 上。`asyncio.run` 结束即关闭循环，原语全部作废；循环 B 拿这些"死原语"发数据，`send_nowait` 直接抛 `ClosedResourceError`。A 错（流与循环强绑定）；C 错（anyio 没有跨循环迁移机制）；D 错（故障是显式抛错，不会静默——这其实是好事，静默失败才可怕）。这个实验正是教程 2.2 节的内容，也是 `McpClient` 要自带常驻循环的直接原因。

## 第 4 题

**答案：对**

解析：这是今天桥接设计的核心机制。`asyncio.run(client.call_tool(...))` 创建的临时循环里，`call_tool` 协程只做一件事：通过 `run_coroutine_threadsafe` 把真正的 I/O 协程提交到常驻循环，再 `await wrap_future(...)` 等结果。临时循环是"传声筒"，常驻循环才是"干活的"——会话流绑定在常驻循环上，常驻循环不关闭，跨次调用复用同一条流完全合法。所以同步 ReAct 循环里 `asyncio.run(...)` 逐次调用是安全的；反过来，若公开方法直接操作会话（见第 7 题），才会踩跨循环的坑。

## 第 5 题

**答案：错**

解析：MCP 协议把"工具内部出错"建模为**合法的调用结果**：Server 捕获工具函数异常，返回 `CallToolResult(isError=True, content=[错误说明])`，连接本身完好，后续调用照常。这是刻意的协议决策——工具是外部世界的代理，失败是常态，不能让一次业务失败撕裂传输层。我们的 `McpClient.call_tool` 检测到 `isError=True` 抛 `McpToolCallError`，`tests/test_mcp_client.py` 里 `test_call_tool_server_error_raises` 之后其他测试继续用同一 fixture 的 client 正常调用，就是"连接没断"的直接证据。真正会断连的是**连接层故障**（子进程崩溃、管道断开），那是另一类问题。

## 第 6 题

**答案：错**

解析：`McpToolAdapter` 的 `name`/`description`/`parameters` 全部**原样透传** `ToolDescriptor`，不做任何改写。理由有二：其一，工具描述本就该由工具提供方书写——Server 作者最清楚自己的工具怎么用，Client 端润色只会引入信息失真（改丢关键约束、改出歧义）；其二，透传保证了"Server 端改描述 → 下次连接 LLM 即见新描述"的自描述闭环，任何中间改写层都会成为同步负担。如果未来确实需要风格统一，正确位置是 Server 端的写作规范，或注册前的显式策略层，而不是藏在适配器里隐式改写。

## 第 7 题

**参考答案：**

**（1）两个调用各自解决的问题：**

- `asyncio.run_coroutine_threadsafe(coro, loop)` 解决**跨线程提交**：主线程（或调用方线程）不能直接把协程塞进另一个线程正在运行的循环，这个 API 是 asyncio 官方提供的线程安全入口，它把协程包装成任务排进目标循环，并立刻返回一个 `concurrent.futures.Future` 供提交方等待结果。
- `asyncio.wrap_future(...)` 解决**跨循环等待**：上一步返回的是并发 Future，不是 asyncio Future，调用方循环里的 `await` 不认它。`wrap_future` 把它桥接成绑定到调用方循环的 asyncio Future，于是 `await client.list_tools()`（异步场景）和 `asyncio.run(client.call_tool(...))`（同步场景）都能正常工作。

**（2）为什么不能直接 `await self._session.list_tools()`：**

会话底层的 anyio 流绑定在**创建它的常驻循环**上。若公开方法在调用方循环里直接操作会话，就等于在循环 B 里使用绑定循环 A 的流：两个循环同时活着时行为未定义（通知原语错乱），调用方是 `asyncio.run` 的临时循环时，循环一关流即失效，下次调用抛 `ClosedResourceError`。桥接把"操作会话的代码"固定调度回常驻循环执行，调用方循环只负责等待结果——**I/O 永远发生在流所属的循环上**，这是 anyio 时代跨循环协作的基本纪律。

## 第 8 题

**参考答案：**

**（1）Client 为什么不直接返回错误字符串：** Client 是通用组件，**无权替上层决定失败策略**。重试、降级、熔断、终止任务、把错误喂回 LLM——这些是不同上层的不同选择，且随场景变化。如果 Client 返回字符串，上层就无法区分"这是工具的真实输出"和"这是失败信息"（字符串语义模糊），策略选择被提前锁死。抛语义化异常（`McpToolCallError`，携带 Server 的错误文本）把"发生了什么"表达清楚，把"怎么办"留给上层——与 day010 `PlanParseError(ValueError)` 是同一套异常哲学。

**（2）宽 `except Exception` 为什么合理：** Adapter 的契约是"`execute` 永远返回字符串"，它是 Agent 与外部世界之间的**最后一道防线**。在这里，任何漏网的异常——连接层 anyio 错误、协议层解析错误、业务层 `McpToolCallError`、甚至 `asyncio.run` 在错误上下文里的 `RuntimeError`——都会向上打进 ReAct 循环把 Agent 打崩。防线组件的职责就是兜底一切，宽捕获是契约要求而非懒惰；同时它配了 `logger.warning` 保证故障可观测，不是静默吞掉。

**（3）错误字符串如何被消化：** `ReactAgent._execute_tool` 把 `execute` 的返回值（此时是错误说明）当作普通 Observation 追加进消息列表，下一轮 LLM 调用时读到"远程工具 xxx 调用失败： ..."。LLM 据此调整策略：换工具、换参数、或基于已有信息直接作答。故障从"打断循环的异常"被**降维成循环可消化的一条观察**——Agent 的行为从"崩溃"变成"绕路"，这就是回退设计的目标。

## 第 9 题

**参考实现：**

```python
import sys

from mcp import StdioServerParameters

from smart_research_agent.mcp_server.client import McpClient
from smart_research_agent.tools.calculator import CalculatorTool
from smart_research_agent.tools.mcp_tool import discover_mcp_tools
from smart_research_agent.tools.registry import ToolRegistry


def build_registry_with_mcp(command: str, args: list[str]) -> tuple[ToolRegistry, McpClient]:
    """连接 MCP Server，把远程工具与本地工具注册进同一份注册表.

    注意：返回的 client 必须保持存活，适配器的 execute 依赖这条常驻连接。
    """
    client = McpClient(StdioServerParameters(command=command, args=args))
    client.run(client.connect())                       # 同步桥接：建连 + 握手
    registry = ToolRegistry()
    registry.register(CalculatorTool())                # 本地工具
    for adapter in client.run(discover_mcp_tools(client)):  # 远程工具本地化
        registry.register(adapter)
    return registry, client
```

**测试：**

```python
def test_build_registry_with_mcp():
    registry, client = build_registry_with_mcp(
        sys.executable, ["-m", "smart_research_agent.mcp_server.demo_server"]
    )
    try:
        assert registry.get("calculator") is not None
        assert registry.get("search_docs") is not None
        result = registry.get("search_docs").execute(query="测试")
        assert "检索结果" in result
    finally:
        client.shutdown()
```

**要点解析：**

- 返回值从单一 `ToolRegistry` 改成 `tuple` 是**资源所有权**问题：适配器内部持有 client 引用，Python 的 GC 不会替你关连接；显式返回 client 把"谁负责 shutdown"说清楚。题目要求"函数返回前不能断开连接"，正是逼你面对这个所有权设计。
- `client.run(...)` 是同步桥接的正确用法：同步函数里没有事件循环，`asyncio.run` 也能用，但 `run` 语义更直白（提交到常驻循环并等结果）。
- 测试的 `finally: client.shutdown()` 不可省：守护线程虽不阻止进程退出，但规范的资源收尾是好习惯，也避免子进程泄漏。

## 第 10 题

**参考实现：**

```python
import asyncio
import threading

from mcp.shared.memory import create_connected_server_and_client_session

from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.mcp_server.client import McpClient
from smart_research_agent.mcp_server.demo_server import build_demo_server
from smart_research_agent.tools.mcp_tool import McpToolAdapter, discover_mcp_tools
from smart_research_agent.tools.registry import ToolRegistry


def test_react_survives_repeated_tool_failure():
    client = McpClient()
    holder: dict = {}
    ready, stop = threading.Event(), threading.Event()

    async def _session_lifecycle():
        async with create_connected_server_and_client_session(build_demo_server()) as s:
            holder["session"] = s
            ready.set()
            await asyncio.get_running_loop().run_in_executor(None, stop.wait)

    future = client.submit(_session_lifecycle())
    assert ready.wait(timeout=10)
    client.attach_session(holder["session"])
    try:
        adapters = client.run(discover_mcp_tools(client))
        registry = ToolRegistry()
        for a in adapters:
            if a.name == "unstable_tool":     # 只注册必挂的工具
                registry.register(a)
        llm = MockLLM(responses=[
            "Thought: 先试工具\nAction: unstable_tool\nAction Input: 第一次",
            "Thought: 报错了，再试一次\nAction: unstable_tool\nAction Input: 第二次",
            "Thought: 工具确实不可用\nFinal Answer: 基于已有知识作答",
        ])
        answer = ReactAgent(llm=llm, registry=registry).run("任意任务")
        assert answer == "基于已有知识作答"
        # 第二次、第三次 LLM 调用的最后一条消息各带一次"调用失败"的 Observation
        observations = [call[-1].content for call in llm.calls[1:]]
        assert len(observations) == 2
        assert all("调用失败" in obs for obs in observations)
    finally:
        stop.set()
        future.result(timeout=10)
        client.shutdown()
```

**第 5 问的思考（注释）：** 这个实验暴露了纯字符串回退的核心风险——**LLM 可能无限重试同一个坏工具**。错误字符串只说"失败了"，没说"别再试了"；只要 LLM 判断"也许这次能成"，循环就会一边烧钱一边原地踏步，直到 `max_steps` 兜底。生产上应加**熔断器**：同一工具连续失败 N 次后，Adapter 直接返回"该工具已熔断"（或从注册表临时摘除），把"是否还值得试"的决策从 LLM 的概率判断变成系统的确定性规则。这也是教程 5.4 节提到的系统性故障处理方向。
