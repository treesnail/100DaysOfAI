## 一、本课只承诺一件事：**账**，不承诺性能

```text
承诺      三笔账都能被逐项算出来：
          缓存（字节）、量化（误差与上界）、批（步数与槽位）、预算（三项之和）
不承诺    真实推理引擎的加速比（显存分配器、kernel 融合、页式注意力都不在其中）
```

因此本课的量化是"量化 → 反量化"、用浮点算**误差**；
本课的缓存是纯 Python 的逐步 decode；本课的批是**静态**批的计数。
三样都能量出"省了多少"，一样都量不出"快了多少"——那条边界写在手册最后一节。

还有一条边界要写在最前面：

```text
量化是不可微的：round(x/scale) 的导数几乎处处为 0、在跳变点不存在。
真实世界的做法是前向用量化权重、反向用直通估计（STE）——而那是**训练**的事。
本课只做推理，因此连续第三天**没有** GradientError 那一族。
```

## 二、缓存不是"变快"，而是"换"

自回归生成的第 t 步只需要**一个新位置**的 hidden state，而它的注意力要看前面 t 个位置的 K/V。

```text
不缓存    每步把前面 t 个位置重算一遍 ⇒ 打分次数 1 + 2 + … + T = T(T+1)/2
缓存      每步只算新位置对前面 T 个位置 ⇒ 打分次数每步 T ⇒ 总共 T
```

演示读数（`T = 9`）：

```text
注意力打分次数（重算, 缓存）= (45, 9)
```

45 与 9 都是整数，因此"省了多少"是一个能被算出来、而不是被形容出来的数。
但收益的另一面是代价：

```text
缓存把每步的计算量从 O(T) 降到 O(1)，代价是 **O(T)** 的显存。
⇒ 显存紧的时候，"缓存一定更好"是错的。
```

## 三、缓存账的公式：`2 · L · T · h · bytes`

```text
缓存里存的是**两**张表（K 与 V），因此每一条缓存公式前面都有一个 2。
L = 层数、T = 已处理的 token 数、h = 隐藏维、bytes = 每个元素占几字节
```

演示读数（`L=2, h=16, fp32` ⇒ 每步 256 字节）：

```text
T=0   总量 0       == 每步 256 × 0
T=1   总量 256     == 每步 256 × 1
T=5   总量 1280    == 每步 256 × 5
T=16  总量 4096    == 每步 256 × 16
T=32  总量 8192    == 每步 256 × 32
```

四个长度各核一次，而不是核一次了事：只核一次的话，
"把 K 与 V 只算了一份"（差一半）与"漏乘层数"（差一个整数倍）都只会在**某一个长度**上碰巧对。

## 四、缓存路径与整段重算必须**逐位**相同

这是本课最强的一条对账。两条路径的算术**逐字相同**（都走 day085 的
`project` / `split_heads` / `row_softmax` / `merge_heads`），差别只有一处：

```text
整段路径    K/V 从输入现场投影出来
缓存路径    K/V 从参数传进来（老的行来自缓存、新的行刚算出来）
```

因此下面的等式必须成立，而且**不是"数值相近"**：

```python
cached, full = compare_with_recompute(card, weights, prompt_ids, new_token)
assert cached == full          # 逐位
```

它抓的错法是"缓存在归一化之前取"（形状全对、数值全变）或"K/V 弄反"。
两者都不会报错——只会让生成结果**偏掉**。

## 五、位置必须由缓存长度决定（本课最容易踩的一个坑）

```text
整段路径   第 5 个 token（下标 5）拿到位置表第 5 行
decode     必须**显式**告诉它"你在第 5 位"，否则它会拿第 0 行
```

这是第一版实现里真实撞上的一次：decode 复用了 day086 的 `embed_tokens`，
而那个函数按行内下标编号位置（`range(len(row))`）——一步只喂一个 token 时，
它会把这个新 token 当成**位置 0**。形状完全合法、不报错，而这一步的输入
**整块被换掉了**（本机实测：位置 5 与位置 0 的嵌入最大差 `3.658558e-01`），
于是它与整段路径的 logits 立刻分家。

修法是一个只服务于单行的 `_embed_at(card, weights, token_id, position)`：
它把"位置"变成一个**必须显式给出**的参数，而那个参数来自**缓存长度**。
这条纪律在真实实现里的说法是"缓存必须带一个 `position_ids`"。

## 六、量化：定标 / 取整 / 打包是**三件事**

```text
① 定标     找一个 scale（对称）或 scale + zero（非对称），把浮点映射到整数格
② 取整     q = round(x / scale) —— **误差只发生在这一步**
③ 打包     int4 两个数挤进一个字节 —— **无损的位运算**，一位都不丢
```

把"打包"和"取整"混在一起说，就会出现"4 位量化精度是 8 位的一半"这种话——
而真正决定精度的是**格数**：8 位 256 格、4 位 16 格。

### 6.1 一条可推导的上界

```text
|x − x̂| = |x − round(x/scale)·scale| ≤ 0.5 · scale = scale/2
```

它不是经验，是推导。它有**两条前提**，而两条都要当场检查：

```text
前提 ①  每个元素都落在 [-max_abs, max_abs] 内   ⇒ 出现 inf/nan 时前提就破了
前提 ②  scale ≠ 0                             ⇒ 整块同值时 scale = 0（本包当场拒绝）
```

演示读数（`L=2, h=16` 的权重分块，8 种组合全部满足上界）：

```text
int8  absmax     per_tensor  最大 9.508e-04 ≤ 9.526e-04 ✓ | SNR 47.86 dB
int8  absmax     per_channel 最大 9.271e-04 ≤ 9.526e-04 ✓ | SNR 48.31 dB
int8  zero_point per_tensor  最大 9.160e-04 ≤ 9.163e-03 ✓ | SNR 49.53 dB
int4  absmax     per_tensor  最大 1.664e-02 ≤ 1.728e-02 ✓ | SNR 23.57 dB
...
```

**注意判据的写法**：上面每一行都是"实测 ≤ 上界"，而不是"两个数相等"。
本课的 `CrossCheck` 因此多了一个 `upper_bound` 字段——有它时判据是"≤"，
没有它时才是"=="。把两类混成一个判据，就会出现"实测误差恰好是 0
（因为输入全是 0）被当成通过"这种事。

### 6.2 两个端点必须出现在样本里

```text
有符号 4 位：[-8, 7]      无符号 4 位：[0, 15]
同一个字节 120 → 有符号解出 0、无符号解出 120   （补码的两个端点）
```

"负数的低 4 位会串到高位"这类错误**只在负数上**出现——
用一组非负样本试，永远试不出来。

### 6.3 粒度买精度，位宽买空间

```text
per_tensor   整块共用一个 scale ⇒ **一个离群值抬高所有人的台阶**
per_channel  每一行一个 scale   ⇒ 离群值只抬高它自己那一行
```

演示读数（样本**带离群值**：只有一行有一个放大 80 倍的元素）：

```text
int8 absmax     per_tensor 8.016e-04 vs per_channel 4.143e-04 ⇒ 1.9 倍
int8 zero_point per_tensor 4.179e-04 vs per_channel 1.984e-04 ⇒ 2.1 倍
int4 absmax     per_tensor 1.605e-02 vs per_channel 7.427e-03 ⇒ 2.2 倍
int4 zero_point per_tensor 7.551e-03 vs per_channel 4.017e-03 ⇒ 1.9 倍
对照（每行分布相同的权重）：int8 的收益只有 1.2 倍
```

三条值得单独指出的：

```text
① 这个收益只在**行与行的动态范围差得很大**时才出现：
   在每行分布相同的权重上，两种粒度的读数降到 1.2 倍（本课量过）
② 表里用的是**均值**误差而不是最大值：最大值被那个离群的那一行占住，
   而两种粒度下它都是同一行 ⇒ 最大值会把收益完全掩盖
③ 粒度与位宽不能互换：粒度买精度、位宽买空间
```

## 七、批的账：静态 vs 连续

```text
静态批       把请求按 max_batch 分好组，一组一起跑到底 ⇒ 总步数 = Σ 每组的最长
连续批       一条算完就把它那个位置让给新的一条
```

演示读数（长度 `[9, 2, 5, 1, 7]`、批大小 3）：

```text
组 [0, 1, 2]：宽 9 ⇒ 9 步；组 [3, 4]：宽 7 ⇒ 7 步
静态批 16 步 / 连续批下界 9 步 | 槽位效率 50.0%（有效 24 / 机会 48）
连续批的处理表：10 步 × 3 槽位 = 30 | 占用 24（80.0%）
每条请求在表里出现的次数 [9, 2, 5, 1, 7] == 各自的长度 [9, 2, 5, 1, 7] ✓
```

### 三个必须写下来的细节

```text
① "连续批的总步数 = 最长的那条"只在 len(lengths) <= max_batch 时成立；
   请求比槽位多时实际步数会更长（上面 10 > 9 就是这一条：
   第 5 条请求只有等第 3 条腾出位置才进得来）
② 每一条请求在表里必须出现**恰好它的长度**次——这是"它每一步都在算"的唯一证据
   少了这个核对，"某一条被提前扔掉"与"它算完了"在表里长得一样
③ 槽位效率的分母是"总步数 × max_batch"（**有机会**算的 token 数），
   分子是"真的算了有意义工作的那部分"
```

第 ② 条是本课抓到的一个真实错误：第一版处理表忘了把 `remaining` 减 1，
于是**没有一条请求会结束**——表看起来完全合法（槽位都占着、步数也对），
而第 5 条请求只出现了 6 次而不是 7 次。

## 八、预算的账：三项必须能被逐项相加

```text
权重       参数量 × 每元素字节          —— 与序列长度**无关**
缓存       2·L·T·h·bytes               —— 与序列长度**线性相关**
激活       一次前向最宽的那个中间张量    —— 与批大小**线性相关**（本课按 ffn 估）
```

第三样的口径必须写死，否则它会变成一个可以随便取值的数
（换成 `hidden` 会小 `ffn/h` 倍、换成"所有层一起"会大 `L` 倍）。

演示读数（同一个 64 KiB 预算、同一个 32 个位置）：

```text
fp32  | 权重 46144 + 缓存  8192 + 激活  8192 =  62528 / 65536 ✓ | 余量  3008 | T_max 37
fp16  | 权重 23072 + 缓存  4096 + 激活  4096 =  31264 / 65536 ✓ | 余量 34272 | T_max 165
int8  | 权重 11536 + 缓存  2048 + 激活  2048 =  15632 / 65536 ✓ | 余量 49904 | T_max 421
int4  | 权重  5768 + 缓存  1024 + 激活  1024 =   7816 / 65536 ✓ | 余量 57720 | T_max 933
```

### 一个能被整除算出来的答案

缓存与激活都**线性**于序列长度，因此"预算内最长能做多少 token"是一个一次方程的整数解：

```text
weights + T·(batch·ffn·bytes + 2·L·h·bytes) ≤ budget
⇒ T_max = ⌊(budget − weights) / (batch·ffn·bytes + 2·L·h·bytes)⌋
```

而且**两侧都要查**：

```text
fp32 下最多 37 个位置：T=37 合计 65088 ✓、T=38 合计 65600 ✗
```

只查"放得下"的话，一个**偏小**的 `T_max` 也会通过——
而"保守"与"算错"读起来一样。

## 九、两个总数不一定是"和"

本课有四处"总数"，而每一处的"总数"都值得单独说清它到底是不是和：

```text
缓存总量        == 逐层相加                    （是，N 层 × 每层 2 表）
处理表的总槽位   == 步数 × max_batch            （是，但"占用"要用 >= 0 数出来）
连续批的总步数   不一定是"最长的那条"           （槽位不够时更长：11 > 9）
预算总量        == 权重 + 缓存 + 激活           （是，而且必须是）
```

第二处与第三处是同一类陷阱：一个"看起来是定义"的数其实是一个**只在某个条件成立时**
才等于定义的数。把它们当成定义，就会在边界上给出**看起来正常**的错读数。

## 十、五条边界（**这一课明确不承诺的事**）

```text
① 本包复现的是账（字节数、误差上界、吞吐计数），不是真实推理引擎的性能
② 本包不做真正的 8 位/4 位算术：量化是"量化 → 反量化"，用浮点算误差
③ 本包不安装、也不调用 bitsandbytes / accelerate：它们只出现在"对接对象"与笔记里
④ 本包的批处理是**静态**批；连续批处理只在计数层面被算出来
⑤ 本包的缓存不跨请求复用（没有前缀共享），也没有分页
```

第 ④ 与第 ⑤ 条是这一课留下的两个悬念，而它们都是**推理优化里最赚钱的两块**：

```text
连续批        真正的收益来自"不等"——而本课只算出了"省了几步"
前缀共享      多条请求共用同一段前缀时，缓存可以只存一份——本课不做
```

它们值得在 day088 的"原理 → 应用"提纲里各占一行。
