## 第一部分：选择题

### 第 1 题（预算单位）

同一句话 `"分块预算决定索引规模。"`（11 个字符）在 `chars` 与 `tiktoken`
两个度量器下分别得到 11 与 13。本模块**默认**用 `chars`，核心理由是：

- A. 字符计数更快（省掉一次分词）
- B. **因为分块结果必须可复现：`chunk_id` 是知识库的去重键，而 `tiktoken` 依赖本机词表缓存，换台机器可能切出另一套 id**
- C. 因为中文按字符算更准
- D. 因为 `tiktoken` 需要付费

### 第 2 题（`chunk_id` 的构成）

`chunk_id = sha256(doc_id | strategy | index | text)[:16]`。下列哪一条**不是**
它成立的性质？

- A. 同一份文档用同一策略切两次，得到同一批 `chunk_id`
- B. 文档内容变一个字节，全部 `chunk_id` 都变（`doc_id` 进过 hash）
- C. **同一段话在两份不同文档里会得到同一个 `chunk_id`**
- D. 同一段话在同一份文档里出现两次时，两个块各有各的 `chunk_id`

### 第 3 题（结构策略与重叠）

`StructuralChunker` 对非零 `overlap_tokens` 直接**报错**而不是忽略它。理由是：

- A. 结构分块的块本来就短，重叠会浪费钱
- B. 重叠会让覆盖率超过 100%，破坏不变量
- C. **跨标题回带会把上一节的内容灌进下一节，而该块的 `heading_path` 会让这些内容看起来本来就属于这一节——一条错误的来源标签比没有标签更糟**
- D. 标题边界处无法计算重叠长度

### 第 4 题（原子块）

代码块与表格超预算时"整块保留并标记 `oversized`"，而不是切开。这个取舍的
依据是：

- A. 代码块的 token 数无法计算
- B. **切开会得到两块语义都不成立的残码，而不切只得到一个可见、可统计的超预算块——两种代价不对称**
- C. 表格切开后无法渲染成 Markdown
- D. 因为 `oversized` 的块不会进知识库

### 第 5 题（语义阈值）

语义策略的阈值用"相似度分布的分位数"而不是绝对值（如 0.7），因为：

- A. 分位数计算更便宜
- B. 绝对值无法用 Python 精确表示
- C. **余弦相似度的绝对值依赖 embedding 提供方的训练目标、维度、归一化方式与语料语言；换一个提供方，同一个绝对阈值就换了一个含义**
- D. 分位数能自动适应文档长度

## 第二部分：判断题

### 第 6 题

`Span` 只携带 `(start_char, end_char)` 而不携带文本，块文本只能由
`document.text[start:end]` 现取。因此"块文本是原文的连续子串"这条不变量
**在构造上不可能被违反**。（对 / 错）

### 第 7 题

覆盖率（`ChunkSet.coverage`）必须严格等于 100%，否则说明切分丢了内容。
（对 / 错）

### 第 8 题

递归策略的分隔符表里去掉 `。`、`，` 这两档也没关系——`\n\n` 已经能切开
绝大多数段落，剩下的长段落按字符硬切即可，效果差不多。（对 / 错）

## 第三部分：简答题

### 第 9 题（那条不变量为什么这么写）

本模块的核心不变量由 `Chunker._assert_spans` 逐字符核对，它同时检查三件事：

```python
# 1. 区间合法
if span.start_char < 0 or span.end_char > len(text): raise ChunkingError("越界…")
# 2. 起点严格递增
if any(later <= earlier for earlier, later in zip(starts, starts[1:])): raise …
# 3. 非空白字符全覆盖
missing = [i for i, ch in enumerate(text) if not covered[i] and not ch.isspace()]
if missing: raise ChunkingError("…没有被任何块覆盖…")
```

请回答四个问题：

1. 第 3 条为什么判定"**非空白**字符"而不是"全部字符"？如果改成判定全部字符，
   会发生什么？
2. 覆盖率因此可能略低于 1。为什么说这个差额是"可核对的"而不是"差不多"？
   请写出那个上界，并用一份 5 块、614 字符的文档说明它怎么用。
3. 第 2 条为什么必须存在？如果去掉它，一个"窗口原地踏步"的切分器会产出什么
   样的结果，而那种结果为什么很难被发现？（提示：想想块数与 embedding 调用量）
4. 收尾里还有一步 `_dedupe_starts`（起点相同的块只保留包含者）。它与第 2 条
   检查是不是重复了？为什么它只自愈"后一块完全包含前一块"这一种情形？
