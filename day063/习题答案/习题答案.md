## 第一部分：选择题

### 第 1 题 —— B

```python
def chunk_id_for(doc_id: str, strategy: str, index: int, text: str) -> str:
    payload = f"{doc_id}|{strategy}|{index}\n{text}".encode("utf-8")
    return hashlib.sha256(payload).hexdigest()[:16]
```

```text
chunk_id     「这一块是谁」——位置身份：向量库主键、按 id 覆盖与更新
fingerprint  「这是哪段内容」——内容身份：跨文档去重、重复内容统计
```

实测（见第 11 题答案）：同一段文本 `'甲\n\n乙丙丁戊己庚辛壬癸。'` 在两个策略下
`fingerprint` 完全相同（`87c0a6c476b7c5f5`），而 `chunk_id` 完全不同
（`f1338cfd15686ed1` vs `beb86a2f8bf3d189`）。

`A` 是错的（两者都用于存储，区别在"回答什么问题"）；
`C` 说反了（`doc_id` 是文档的内容指纹，不是"这段内容属于哪份文档"）；
`D` 错——**两者混用会出现两种失效，而且都不报错**：
只留 `chunk_id` → 跨文档去重失效；只留 `fingerprint` → 同一段话出现两次时互相覆盖。

### 第 2 题 —— B

```python
MEASURER_CHARS = "chars"        # 1 个字符 = 1 个预算单位（默认）
MEASURER_TIKTOKEN = "tiktoken"  # 1 个 token（依赖本机词表缓存）
```

实测：`"分块预算决定索引规模。"`（11 个字符）在 `cl100k_base` 下是 **13 个 token**。

选 `chars` 做默认不是"更准"，而是**更可复现**：`chunk_id` 是知识库的去重键，
而 `tiktoken` 的可用性依赖本机是否有词表缓存（没有时 day034 的 `TokenCounter`
会退化成字符级估算）——**同一份文档在两台机器上切出两套 id**，
"这条知识为什么重复了两份"就变成一个查不出来的问题。

`A` 错（默认不是 tiktoken）；`C` 错（"320 个汉字"与"320 个字符"只在
"全部是汉字且无标点"时才重合，标点、数字、英文都算一个字符）；
`D` 错（`chars` 是字符不是字节，中文一个字 3 个字节）。

### 第 3 题 —— C

语义分块的第一步是"把原文按**空行**切成自然段"，然后比较**相邻**自然段的相似度。
一整份没有空行的长日志只有一个自然段：

```python
if len(units) < 2:
    # 只有一个自然段：语义判据没有施展空间。
    self.stats = {"units": str(len(units)), "breaks": "0", "threshold": "n/a"}
    return self._group_spans(text, units, boundaries=set(), positions=[])
```

此时它在**退化路径**上跑：一个自然段装不下预算就直接按预算回切
（`reason="topic-overflow"`）。也就是说，**它在日志上等价于固定长度分块**，
而且这次退化是"结论"不是"报错"——报告里的 `units=1` 就是它。

另外三种语料都能吃到语义判据：技术文档有多个自然段与标题
（标题处还会额外断开）、QA 集合每问每答各自成段、中英混排会体现在相似度上
（`char-ngram` 只认字面相似，但至少能分出"话题换了"）。

### 第 4 题 —— B

这是 day062 第七章的缺陷三，实测报错长这样：

```text
块的起点必须严格递增，收到 [0, 1, 11, 22, 32, 38, 38, 38, 47, 67, 67, 67, 78, 84]
```

成因有两步：**重叠把下一块的起点往回挪**，挪过之后可能落进两个块之间的空白；
紧接着的**修剪**又把两块各自往前推到同一个位置。修法有两条，都保留：

1. 把顺序固定为"修剪 → 重叠 → 合并 → 校验"（`finalize` 的注释写着为什么）；
2. 加 `_dedupe_starts`：起点相同时**只丢弃"被包含"的那一块**，
   其它情形（起点倒退、后一块更短）照样让 `_assert_spans` 响亮报错。

`A` 错（重叠确实会让覆盖率超过 100%，但那与顺序无关）；
`C` 错（双重回带是另一个缺陷——`window_overlap` 与 `policy.overlap_tokens`
分工不清导致，与本条的顺序问题无关）；`D` 错（面包屑属于 `retrieval_text`，
与收尾顺序无关）。

`A` 错（它恰恰让报告更啰嗦）；`B` 错（写进元数据不减少 `if`，

### 第 7 题 —— 对

```python
missing = [i for i, ch in enumerate(text) if not covered[i] and not ch.isspace()]
```

"非空白"是刻意的：收尾第一步会修剪掉每块首尾的空白，如果判定"全部字符"，
**任何一次正确的修剪都会被报成丢内容**。因此覆盖率允许略低于 1，而差额有上界：

```text
doc_chars - total_chars ≤ 2 × (块数 - 1) + 1
                            ↑ 块间空行     ↑ 原文结尾的换行（规范化补的）
```

实测：`structural` 5 块、614 → 605 字符，差额 **9**，上界也是 **9**——用满但不超。

注意这条上界**只在差额为正时有意义**：`fixed` 那行的差额是 −93，
负号表示"块文本总量超过原文"，那是重叠贡献的。**重叠与丢内容是方向相反的两件事，
用同一个数看会看反。**

### 第 8 题 —— 错

理由不是成本，而是**来源标签的正确性**：

raise ChunkingError(

跨标题回带之后，上一节的尾巴会挂在**新一节的 `heading_path` 下**：

成本只是附带好处（结构策略的 `duplication_ratio` 恒为 0），不是理由。

## 第三部分：简答题

### 第 10 题

**1）`doc_id` 位置放什么？为什么安全？**

```text
day061  doc_id = 文档内容指纹（sha256(规范化全文)[:16]）
day062  doc_id = chunk_id（sha256(doc_id | strategy | index | text)[:16]）
```

安全的原因是：**下游只依赖三件事，而这三件事都不关心"这条记录代表文档还是片段"**。

```text
① 一个稳定的唯一键          ← doc_id 位置永远放唯一键
② 一段要被编码/引用的文本    ← text 位置永远放"要处理的那段文本"
③ 一个自由扩展的元数据口袋   ← metadata 只增不改
```

反过来说：如果哪天下游开始依赖"`doc_id` 一定是文档级 id"，
那才是真正的破坏性变更——**接口契约的核心是"位置的语义"，
不是"位置的名字"。** day062 的做法（换身份、不改名、把差异放进 metadata）
恰好把这件事讲清楚了。

**2）不写出 `retrieval_text` 会在什么时候暴露？**

先明确两者的分工：

```text
text           原文片段（能在 document.text 里逐字核对，用于展示与引用）
retrieval_text heading_path 面包屑 + text（用于做 embedding）
```

如果不写出来（文档只说"向量化用 `text`"），所有人都会按字面实现：
**编码 `chunk.text`、库里存 `chunk.text`。** 它在演示里完全正常——
检索照样返回结果，分数也照样有高低。暴露的时机是：

```text
用户问："缓存相似度阈值怎么配？"
命中片段："阈值设为 0.85，超过两周未命中的条目会被清掉。"
        ← 这段文字里没有"缓存"两个字，标题路径才是唯一的桥
```

于是那一刻起，"标题里有的词、正文里没有"的查询会**系统性地检索不到**，
而现象只是"有些问题答得不好"——**没有任何报错、指标也不会突变**，
因为错误的做法与正确的做法产生的是同一种形状的结果。

这正是 day062 把它写成 `/chunking/records` 的一个显式字段
（`embedding_input = "metadata.retrieval_text"`）的原因：
**"存的"和"embed 的"不是同一段文本，这一条必须被写出来。**

**3）把 `fingerprint` 放到 `doc_id` 位置会怎样？**

具体失败场景——**工程文档里的"注意"小节**：

```text
docs/a.md   第 3 节有一句："注意：阈值设为 0.85，超过两周未命中的条目会被清掉。"
docs/b.md   第 7 节有一句完全一样的话
```

- 正确做法（`doc_id` 位置放 `chunk_id`）：两条记录有**不同的主键**，各自入库，
  各自可被检索、可被引用到正确的出处；
- 错误做法（`doc_id` 位置放 `fingerprint`）：
  两条记录的内容指纹相同 → **向量库按主键覆盖，只剩一条**。

后果有两层，第二层更糟：

```text
第一层：少了一条记录 —— 检索"b.md 里那句话"时找不到出处
第二层：**没有任何报错**，而且"覆盖"看起来像"去重成功"
```

也就是说，**把内容身份当主键，会把"同一段话出现两次"这个正常事实
误判成"重复数据"**，而 chunk 级的重复是常见的（命令示例、模板段落、免责声明）。
反过来，把 `chunk_id` 当去重键也不行——它包含 `index`，
同一段话在文档里出现两次时 id 不同，**去重会完全失效**。

**4）"搜不到那份 PDF"的排查顺序**

四个东西正好两天各提供两个：

```text
第 1 步（day061，类型层）：detect_media_type 的 decided_by / conflict
    → 这份文件到底是什么？后缀说 .txt、内容说 %PDF，是按谁解析的？

第 2 步（day061，内容层）：Document.metadata 的
    pdf_cid_font_detected / encoding_confident / pdf_warnings
    → 解析出来的是空文本还是乱码？如果是 CID 字体，那就是规范级不可确定
      （§9.10.2），不是 bug——**这一步能立刻把"我们的问题"与"PDF 的问题"分开**

第 3 步（day062，分块层）：ChunkSet.metadata.policy 与覆盖率
    → 切的时候用的是哪个策略、什么参数？coverage 是否远低于上界？
      （差额远超 2×(块数-1)+1 才说明切丢内容）

第 4 步（day062，索引层）：块的 retrieval_text 与 fingerprint
    → 被编码的到底是不是 retrieval_text？检索词是否只出现在标题里
      （那正是"该用面包屑"的信号）？
```

四步的共同点是：**每一步都在回答"证据是什么"，而不是"猜哪里错了"。**
这也是这两天所有元数据字段存在的唯一理由。

### 第 11 题

```python
"""day063 复习日第 11 题：用一条不变量把 day061 与 day062 串起来."""

from __future__ import annotations

from smart_research_agent.chunking import (
    STRATEGY_FIXED,
    STRATEGY_STRUCTURAL,
    ChunkPipeline,
    ChunkPolicy,
    build_chunker,
)
from smart_research_agent.documents import DocumentIngestor, default_registry
from smart_research_agent.llm.embedding import MockEmbedding
from tests.chunking_samples import chars

MARKDOWN = """# 检索手册

本文给出一套可复现的检索参数。

## 分块

固定长度分块每 320 个字符切一刀，重叠 48 个字符。它不认识标点。

```python
def plan(doc_chars, max_tokens, overlap_tokens):
    step = max_tokens - overlap_tokens
    return 1 if doc_chars <= max_tokens else -(-(doc_chars - max_tokens) // step) + 1
```

## 检索

默认返回前 5 条，相似度低于 0.35 的直接丢掉。
"""

SHORT = "# 甲\n\n乙丙丁戊己庚辛壬癸。\n"


def test_day061_to_day062_end_to_end() -> None:
    # 1) day061：入库（去重 + 三类状态）
    ingest = DocumentIngestor().ingest_bytes(
        [
            ("docs/guide.md", MARKDOWN.encode("utf-8")),
            ("docs/guide-copy.md", MARKDOWN.encode("utf-8")),
            ("docs/broken.txt", b"\x00\x01\x02"),
        ]
    )
    assert ingest.status_counts() == {"ok": 1, "duplicate": 1, "error": 1}
    assert ingest.unique_documents == 1
    assert ingest.duplicates()[0].duplicate_of == "docs/guide.md"

    # 2) day062：分块（两个策略），逐块核对不变量
    document = ingest.documents[0]
    pipeline = ChunkPipeline(measurer=chars(), embedding=MockEmbedding())
    fixed = pipeline.chunk(
        document,
        STRATEGY_FIXED,
        ChunkPolicy(strategy=STRATEGY_FIXED, max_tokens=60, overlap_tokens=0),
    )
    structural = pipeline.chunk(document, STRATEGY_STRUCTURAL)

    for chunk_set in (fixed, structural):
        assert chunk_set.count >= 1
        for chunk in chunk_set.chunks:
            assert document.text[chunk.start_char : chunk.end_char] == chunk.text
        assert chunk_set.doc_chars - chunk_set.total_chars <= 2 * (chunk_set.count - 1) + 1
        assert [chunk.index for chunk in chunk_set.chunks] == list(range(chunk_set.count))
        ids = [chunk.chunk_id for chunk in chunk_set.chunks]
        assert len(set(ids)) == len(ids)

    # 3) 两个身份：文档 id 与块 id 不重合
    assert document.fingerprint not in {chunk.chunk_id for chunk in fixed.chunks}

    # 跨策略：同一段文本的 fingerprint 相同、chunk_id 必然不同。
    # 构造保证：文档足够短，四个策略都只切出一块，且文本与全文一致。
    short = default_registry().load_bytes(
        SHORT.encode("utf-8"), source="docs/short.md", media_type="text/markdown"
    )
    per_strategy = {}
    for strategy in ("fixed", "recursive", "structural", "semantic"):
        policy = ChunkPolicy(
            strategy=strategy, max_tokens=96, overlap_tokens=0, similarity_percentile=0.0
        )
        if strategy == STRATEGY_STRUCTURAL:
            policy = ChunkPolicy(strategy=strategy, max_tokens=96, similarity_percentile=0.0)
        result = build_chunker(
            strategy, policy, measurer=chars(), embedding=MockEmbedding()
        ).split(short)
        assert result.count == 1
        per_strategy[strategy] = result.chunks[0]
    assert len({chunk.fingerprint for chunk in per_strategy.values()}) == 1
    assert len({chunk.chunk_id for chunk in per_strategy.values()}) == 4

    # 4) 记录形状
    for record in structural.knowledge_records():
        assert set(record) == {"doc_id", "source", "text", "metadata"}
        assert record["metadata"]["parent_doc_id"] == document.fingerprint
```

实测输出（四个策略各切出一块，文本完全相同）：

```text
text        = '甲\n\n乙丙丁戊己庚辛壬癸。'
fingerprint = 87c0a6c476b7c5f5   ← 四个策略完全相同
chunk_id    = f1338cfd15686ed1   fixed
              a4638a33cc56dbd4   recursive
              beb86a2f8bf3d189   structural
              60f15c06e9d872cb   semantic
```

**"同一段文本的 `fingerprint` 相同而 `chunk_id` 不同"为什么在两种策略之间
比在同一个策略内部更值得检验？**

因为在同一个策略内部，这两条断言几乎不会同时成立得"有意义"：

```text
同一策略内部：文本相同的两块 → 它们的差别只有 index
             → fingerprint 相同（✓ 但这是显然的）
             → chunk_id 不同（✓ 但只证明了"index 进了 hash"）
```

而跨策略的比较同时钉住了**三条**互相独立的性质：

1. `fingerprint` **不含** `strategy`：内容是内容，判据是判据——
   如果哪天有人把 `strategy` 也塞进 `fingerprint`，
   "同一段话在两个策略下被存了两份"这个事实就统计不出来了；
2. `chunk_id` **含** `strategy`：换判据 = 换一批块 = 换一批主键。
   这条性质正是"改分块参数会让历史索引全部失效"的技术依据；
3. 两者**不能合并**：把 `fingerprint` 当主键会让同一段话覆盖（第 10 题第 3 问），
   把 `chunk_id` 当去重键会让去重失效。**跨策略样本是唯一能同时触发
   "内容相同、身份不同"的构造**——同一策略内部的样本永远做不到。

顺带一个工程理由：跨策略比较用的是**同一次切分**里的产物，
因此它不依赖"两个策略切得一样"这种脆弱的巧合——
短文档 + 四策略各出一块的构造是**构造保证**的，而不是碰运气。

### 第 12 题

```python
"""day063 复习日第 12 题：两条"会变红"的一致性断言."""

from __future__ import annotations

from smart_research_agent.chunking import (
    STRATEGY_STRUCTURAL,
    ChunkPolicy,
    build_chunker,
)
from smart_research_agent.documents import default_registry
from smart_research_agent.llm.embedding import MockEmbedding
from tests.chunking_samples import chars

MARKDOWN = """# 检索手册

本文给出一套可复现的检索参数。

## 分块

固定长度分块每 320 个字符切一刀，重叠 48 个字符。它不认识标点。

```python
def plan(doc_chars, max_tokens, overlap_tokens):
    step = max_tokens - overlap_tokens
    return 1 if doc_chars <= max_tokens else -(-(doc_chars - max_tokens) // step) + 1
```

## 检索

默认返回前 5 条，相似度低于 0.35 的直接丢掉。
"""


def _document():  # type: ignore[no-untyped-def]
    return default_registry().load_bytes(
        MARKDOWN.encode("utf-8"), source="docs/guide.md", media_type="text/markdown"
    )


# --------------------------------------------------------------------------- #
# 断言一：加载器与媒体类型一一对应
# --------------------------------------------------------------------------- #


def test_loader_and_media_type_are_one_to_one() -> None:
    registry = default_registry()
    table = registry.table()
    assert len(table) == len(registry.media_types)
    loaders = [row["loader"] for row in table]
    # 每个加载器在表里恰好出现一次 —— 也就是"一个加载器只对应一种媒体类型"
    assert len(set(loaders)) == len(loaders)


# --------------------------------------------------------------------------- #
# 断言二：max_tokens 在四种策略下含义统一
# --------------------------------------------------------------------------- #


def test_max_tokens_means_the_same_in_all_four_strategies() -> None:
    document = _document()
    for budget in (40, 96):
        overlap = budget // 5
        policies = {
            "fixed": ChunkPolicy(
                strategy="fixed", max_tokens=budget, overlap_tokens=overlap
            ),
            "recursive": ChunkPolicy(
                strategy="recursive", max_tokens=budget, overlap_tokens=overlap
            ),
            "structural": ChunkPolicy(strategy="structural", max_tokens=budget),
            "semantic": ChunkPolicy(
                strategy="semantic", max_tokens=budget, overlap_tokens=overlap
            ),
        }
        for strategy, policy in policies.items():
            result = build_chunker(
                strategy, policy, measurer=chars(), embedding=MockEmbedding()
            ).split(document)
            for chunk in result.chunks:
                if chunk.oversized:
                    continue
                assert chunk.token_count <= budget, (strategy, budget, chunk.index)

    # 而"不可切且超预算"的原子块必须存在，且**只有它**允许超预算
    tight = build_chunker(
        STRATEGY_STRUCTURAL,
        ChunkPolicy(strategy=STRATEGY_STRUCTURAL, max_tokens=40),
        measurer=chars(),
    ).split(document)
    assert tight.oversized_count >= 1
    assert all(chunk.oversized for chunk in tight.chunks if chunk.token_count > 40)
```

**为什么必须同时断言两件事？**

只断言"普通块不超预算"（前半段）会漏掉**另一半契约**：

```text
规则：普通块 ≤ max_tokens      ← 防止"重叠把块撑过预算"（day062 缺陷一）
例外：原子块可以超预算，但必须标记 oversized   ← 防止"切出残码"（缺陷的另一面）
```

漏掉"例外"那一半，会发生两件都不报错的事：

1. **保护被悄悄去掉**：有人把 `ATOMIC_KINDS` 改成空元组，
   代码块就会被从中间切开。前半段断言**依然全绿**（切出来的每一块都很小），
   而"函数被切成两半"这件事没有任何测试会发现；
2. **字段含义被悄悄改掉**：`oversized_count` 一旦可以因为"重叠"而 > 0，
   报告里那一列就不再能回答"有多少块注定被模型截断"（这正是 day062 缺陷一：
   **同一个字段表达两件事，报告就再也说不清是哪种**）。

所以这组断言的价值不在"检查上限"，而在**把"例外"也变成契约的一部分**：

```text
超预算只允许发生在 oversized=True 的块上
→ 反过来说：oversized=True 的块必须真的超预算（或至少真的是原子块）
```

第二层含义还能推出一条更硬的检查：如果哪天有人让 `oversized` 与
`token_count > budget` 脱钩（例如把重叠造成的超预算也标成 `oversized`），
**这条断言会立刻变红**——它同时守住了"上限"与"例外"，而这两者正是
day062 缺陷一被修好的标志。
