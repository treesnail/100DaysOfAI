## 第一章：CI/CD 对 ML/LLM 项目的特殊性 —— 评估即测试

### 1.1 传统软件的 CI 在 LLM 项目里不够用了

传统软件的 CI 门禁很简单：编译通过 + 单测全绿。这两个判定都是**确定性**的——同一个输入永远产生同一个输出，断言可以精确到字节。

LLM 项目打破了这个前提。把系统提示词里"请简明回答"改成"请详细回答"，全部 418 个单测可能依然全绿——单测验证的是**机制的正确性**（ReAct 循环转不转、解析器认不认格式），而改提示词损害的是**行为的品质**（答案变得啰嗦、工具选择变糟）。品质退化是确定性测试的盲区。

这就是为什么 LLM 项目的 CI 必须多一层：**评估即测试（evaluation as test）**。把评估指标（任务完成率、拦截率）当作和单测一样的门禁指标，跌破阈值就判这次提交不合格：

```text
传统 CI:  编译 ──▶ 单元测试 ──▶ ✅ 通过
LLM CI:   单元测试 ──▶ 功能评估 ──▶ 安全评估 ──▶ ✅ 通过
             │           │            │
          机制对不对   行为好不好    防线牢不牢
```

### 1.2 评估能进 CI 的两个前提

评估脚本要进 CI，必须满足两个前提，这两个前提我们其实已经铺垫了一周：

1. **确定性**：同一个 commit 跑一百次结果必须相同，否则 CI 会随机失败（flaky），团队很快就会学会无视红灯——比没有门禁更糟糕。这就是 day030/031 坚持 MockLLM 驱动、把模型随机性排除在评估之外的根本原因，今天的门禁是那条设计决策的回报。
2. **无外部依赖**：CI 环境没有 API Key、不能联网（也不该为每次提交花真实的 API 费用）。全程离线意味着评估可以在 PR 阶段就跑，而不是合并后才发现问题。

### 1.3 门禁不是越严越好：阈值怎么定

门禁阈值是工程权衡，不是道德表态。定高了，正常重构动不动触发红灯，团队会想办法绕过它；定低了，门禁形同虚设。实用的定法：

- **从现状出发**：先跑出当前基线（我们的 Agent 评估 completion_rate = 0.62），门禁设在基线略低处（0.6）——**门禁的初始职责是防退化，不是逼优化**；
- **安全类指标从紧**：红队拦截率针对的是"已知攻击集"，已知攻击都拦不住没有任何借口，直接定 1.0；
- **想提标准就改阈值，别改数据**：优化防线后想宣布"我们达到了新水平"，做法是提交一个 PR 把阈值从 0.6 提到 0.8——阈值变更本身就是一次可评审的质量决策。

### 1.4 快照里的 CI 配置为什么"不会触发"

本日新增的 `.github/workflows/ci.yml`（见 `../源码/smart-research-agent/.github/workflows/ci.yml`）位于教学快照目录 `day032/源码/smart-research-agent/` 内。GitHub Actions 只识别**仓库根目录**下的 `.github/workflows/`，而本项目每天的快照是仓库根 `autocreatemd/` 下的子目录，所以这份配置在快照里不会被真正触发——它是"准备好随时上岗"的完整配置。

在真实项目中启用它有两种方式：

1. 把 `smart-research-agent/` 单独作为一个 Git 仓库推送到 GitHub（本目录即仓库根），配置原样生效；
2. 在已有仓库根目录放置 `.github/workflows/ci.yml`，若项目在子目录，给每个 `run` 步骤加 `working-directory: smart-research-agent`。

本地则完全不需要 GitHub：`scripts/run_all_checks.sh` 把同一套门禁串成本地一键流水线，与 CI 的判定逻辑严格一致（第五章）。

## 第二章：成本追踪 —— 从账单到归因

### 2.1 为什么 LLM 项目需要专门做成本追踪

传统服务的成本大头是机器：多少台服务器、多少核时。LLM 应用的成本模型完全不同——**每一次 API 调用都按 token 计费**，成本与"用户怎么用"强相关：一个爱追问的用户成本是另一个的十倍；一次失控的 ReAct 循环（day006 的 max_steps 为什么存在）可能把一轮对话的 token 消耗放大几十倍。

更要命的是**账单的滞后与笼统**：厂商账单只告诉你"本月 gpt-4o 花了 $312"，回答不了真正重要的问题——

- 哪个功能在烧钱？（规划模块还是反思模块？）
- 哪类任务成本最高？（简单问答还是多步调研？）
- 上次重构让成本涨了还是跌了？

回答这些问题需要**归因（attribution）**：在每一次调用发生时就给它打上标签（哪个模型、哪个接口），而不是月底对着总账猜测。

### 2.2 归因原理：标签打在记录时，不是聚合时

成本追踪的数据模型非常简单——每次 LLM 调用产生一条 `UsageRecord`（见 `../源码/smart-research-agent/smart_research_agent/observability/cost_tracker.py`）：

```python
@dataclass
class UsageRecord:
    """一次 LLM 调用的用量记录（归因的最小单元）."""
    model: str
    endpoint: str           # 接口名，如 "chat" / "embedding"
    prompt_tokens: int
    completion_tokens: int
```

关键设计是**归因维度在记录时就是字段**，不是事后从日志文本里解析出来的。这呼应 day015 审计日志的经验：结构化的观测数据要在一产出的时刻就结构化。

费用由可配置的价格表折算：

```python
DEFAULT_PRICE_TABLE: dict[str, dict[str, float]] = {
    "mock-model":  {"input": 0.0,     "output": 0.0},
    "gpt-4o-mini": {"input": 0.00015, "output": 0.0006},
    "gpt-4o":      {"input": 0.0025,  "output": 0.01},
}
```

注意两点：输入与输出单价**不同**（输出 token 几乎总是更贵——自回归生成要逐 token 串行解码，day033 讲原理）；价格表是**构造参数而非全局常量**，换模型、厂商调价只需换一张表。

`CostTracker` 上还刻意安排了一个"坏味道"设计：`record()` 遇到价格表里没有的模型时**抛 KeyError 而不是按 0 元记账**。成本数据归零看起来无害，实则是最危险的错误——它让一切报表绿油油，直到月底真实账单到来。**宁可报错，不可漏算**。

### 2.3 MockLLM 也要产生 token 计数

成本追踪的测试需要 token 用量数据，但 MockLLM（day005）过去只返回文本。本日给它加上了确定性的用量统计（`../源码/smart-research-agent/smart_research_agent/llm/mock.py`）：

```python
def estimate_tokens(text: str) -> int:
    """粗略估算文本的 token 数（约 4 个字符 1 token，至少为 1）."""
    return max(1, len(text) // 4)

class MockLLM(BaseLLM):
    def chat(self, messages, temperature=0.7, max_tokens=1024) -> str:
        ...
        prompt_tokens = sum(estimate_tokens(m.content) for m in messages)
        completion_tokens = min(estimate_tokens(reply), max_tokens)
        self.usage_log.append({"prompt_tokens": prompt_tokens,
                               "completion_tokens": completion_tokens})
        ...
        return reply
```

三个设计要点：

1. **向后兼容**：`chat` 的签名与返回值完全不变，用量统计是纯增量——旧测试一行不用改（418 个测试原样全绿验证了这一点）；
2. **`max_tokens` 计入估算**：completion 用量被 `max_tokens` 截断，模拟真实 API 的行为——真实的 token 计费就是这样被截断的；
3. **与真实客户端同构**：OpenAI 兼容 API 的每次响应自带 `usage` 字段（`prompt_tokens`/`completion_tokens`），MockLLM 的 `usage_log` 与之一一对应。这意味着在 MockLLM 上写通的 `CostTracker.record_from_llm()` 接线，换真实模型时不用改。

真实分词（BPE、为什么中文一个字往往不止一个 token）是 day034 的主题；今天用 `len(text)//4` 的粗略估算即可——它满足成本测试唯一真正需要的性质：**确定且与长度正相关**。

### 2.4 增量消费：record_from_llm 的游标

`CostTracker.record_from_llm(llm, model=...)` 有一个容易写错的细节：它把 LLM 实例的 `usage_log` 登记进追踪器，但**重复调用不能重复计费**。实现用了一个游标（`_cost_consumed`），每次只消费自上次以来的增量：

```python
consumed = getattr(llm, "_cost_consumed", 0)
new_entries = llm.usage_log[consumed:]
...
llm._cost_consumed = len(llm.usage_log)
```

这是日志/队列消费里反复出现的模式（Kafka 的 offset、shell 的 `tail -f`）：**生产者只管追加，消费者记住自己读到哪了**。相比"读完清空"，追加式日志保留了完整的原始记录，别的消费者（比如 debug 工具）还能从头读。

## 第三章：trace 与 log —— 一次请求的结构化账本

### 3.1 日志回答不了的问题

day015 我们有了完善的日志：每次工具调用、每条防线决策都有 log。但线上排查"刚才那次调研为什么花了 40 秒"时，纯日志的体验是这样的：在几千行日志里 grep 出相关的几十行（多个用户的请求是交错打在一起的！），然后心算每两行的时间戳差。

日志缺两样东西：

1. **归属**：这条日志属于哪一次请求？（trace_id）
2. **层级**：这个操作是谁的子步骤？（parent span）

### 3.2 trace 的数据模型：span、trace_id、parent_id

trace 把"一次请求"建模为一棵 **span 树**（`../源码/smart-research-agent/smart_research_agent/observability/tracing.py`）：

```python
@dataclass
class Span:
    """一次操作的结构化记录：名称、起止时间、状态、父子关系与自定义属性."""
    name: str
    trace_id: str            # 同一次请求的所有 span 共享
    span_id: str
    parent_id: str | None    # 父子关系 -> 树
    start: float
    end: float | None
    status: str              # "ok" | "error"
    attributes: dict         # 自定义键值（消息数、回复长度……）
```

一次 `agent.run` 产生的 trace 形如：

```text
trace_id=7f3a…
└── agent.run        212ms  ok     task="计算 2+3*4"
    ├── llm.chat      98ms  ok     messages=2, reply_chars=45
    └── llm.chat     105ms  ok     messages=4, reply_chars=30
```

log 与 trace 的分工至此清晰：**log 是离散的文本事件流，回答"系统发生了什么"；trace 是单次请求的结构化账本，回答"这一次请求经历了什么"**。前者适合告警与审计（day015），后者适合性能归因与单请求复盘。两者都落盘 jsonl，但 span 自带起止时间与层级，可以被聚合分析（"llm.chat 平均耗时"），自由文本日志做不到。

> 工程对照：这正是 OpenTelemetry 的核心数据模型。我们的 `Span` 是它的教学简化版——学会概念后，接入 OTel SDK 只是换一套 API。

### 3.3 零改造插桩：run_with_trace 的代理模式

给 ReactAgent 加 trace 有个约束：day030 定过规矩——**被测对象不为观测做改造**。但如果不在 `agent.run` 里埋点，怎么拿到每次 LLM 调用的耗时？

答案是**代理（proxy）插桩**：`run_with_trace` 在运行前把 `agent.llm` 临时换成一个计时代理，跑完再换回来：

```python
def run_with_trace(agent, task: str, tracer: Tracer) -> str:
    with tracer.start_trace("agent.run", task=task) as ctx:
        original_llm = agent.llm
        agent.llm = _TimedLLMProxy(original_llm, ctx)   # 包一层计时
        try:
            answer = agent.run(task)
        finally:
            agent.llm = original_llm                    # 无论如何换回来
        ctx.set_attribute("answer", answer)
    return answer
```

`_TimedLLMProxy` 只实现 `chat`（把每次调用包在一个 span 里计时），其余属性经 `__getattr__` 全部透传——所以 MockLLM 的 `calls`、`usage_log` 等观测点照常工作，Agent 完全不知道自己被观测了。这种模式在工程上用途极广：装饰器、缓存层、限流器都是同一个思想。

### 3.4 异常路径：span 状态是错误分析的索引

`TraceContext.span()` 用 contextmanager 实现，异常时先给 span 标 `status="error"` 落盘、**再继续抛出**：

```python
@contextmanager
def span(self, name, parent=None, **attributes):
    span = self._tracer._start_span(name, self.trace_id, parent or self.root, attributes)
    try:
        yield span
    except Exception:
        span.finish(status="error")
        self._tracer._write(span)
        raise            # 观测绝不吞掉业务异常
    span.finish(status="ok")
    self._tracer._write(span)
```

"先落盘再抛出"是观测代码的铁律：如果异常导致 span 丢失，恰恰是最需要排查的那次请求没有数据——**观测系统的价值在故障时最大，所以故障路径必须一等公民**。有了状态标记，事后分析就是一句 `tracer.query(status="error")`。

## 第四章：GitHub Actions 流水线解剖

`../源码/smart-research-agent/.github/workflows/ci.yml` 的完整配置如下，逐段拆解：

```yaml
name: ci
on:
  push:
    branches: [main]
  pull_request:        # PR 阶段就拦截，而不是合并后才发现
```

触发策略：`push` 到 main 与所有 PR 都跑。PR 触发是"质量左移"——问题在进入主干前被拦下，评审者看到的是带着质量结论的代码。

```yaml
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip               # 缓存 pip 依赖，CI 从分钟级降到秒级
      - name: Install dependencies
        run: |
          pip install -e ".[dev]"
          pip install -r requirements.txt
```

环境准备三件事：检出代码、装 Python、装依赖。注意整个流水线**没有任何 secrets**——评估全程 MockLLM 离线驱动（1.2 节的前提二），CI 不需要任何 API Key，也就没有任何密钥泄漏面。

```yaml
      - name: Unit tests with coverage gate
        run: python -m pytest tests/ -q
      - name: Agent evaluation gate
        run: python scripts/run_agent_eval.py --min-completion-rate 0.6 --min-step-efficiency 0.7
      - name: Red team gate
        run: python scripts/run_redteam.py --min-block-rate 1.0
```

三级门禁串行执行，任何一步退出码非零，后续步骤跳过、整个 job 标红。覆盖率门禁（`fail_under = 80`，day030 配置在 `pyproject.toml`）已经内嵌在 pytest 里——它是第一级，因为单测挂了评估没有意义。

```yaml
      - name: Upload evaluation reports
        if: always()               # 失败时更要传，报告是复盘的第一手材料
        uses: actions/upload-artifact@v4
        with:
          name: eval-reports
          path: data/eval/*.md
```

`if: always()` 是个关键细节：默认情况下前序步骤失败后后续步骤不执行，但**恰恰是失败时的评估报告最有价值**——它告诉你哪个指标跌破阈值、哪些用例漏网。

## 第五章：告警判定与本地流水线

### 5.1 告警 = 指标 × 阈值，两者必须解耦

告警模块（`../源码/smart-research-agent/smart_research_agent/observability/alerting.py`）只有几十行，核心是两个函数：

```python
def check_thresholds(metrics: dict[str, float],
                     thresholds: dict[str, float]) -> list[Alert]:
    """逐项比对指标与阈值，指标缺失时跳过，不臆造告警."""

def render_alerts(alerts: list[Alert]) -> str:
    """渲染为 Markdown 红色告警段；无告警返回空字符串."""
```

设计原则一句话：**评估器只管算数，告警器只管比大小**。day030 的 `AgentEvaluator` 不知道阈值存在，`check_thresholds` 不知道指标怎么算出来的。这样阈值是纯粹的配置——CI 里改一个命令行参数就调了门禁，不动一行评估代码。

接入点是两个评估脚本各加一个参数：`run_agent_eval.py --min-completion-rate 0.6`、`run_redteam.py --min-block-rate 1.0`。有告警时做三件事：打印 `[告警] …`、往报告末尾追加红色告警段（`<span style="color:red">🔴 …</span>`）、`return 1`。效果（真实运行）：

```text
$ python scripts/run_agent_eval.py --min-completion-rate 0.99
[告警] 指标 completion_rate = 0.6250，低于阈值 0.9900
…
报告已写入: data/eval/report.md
$ echo %ERRORLEVEL%   # Windows；bash 用 $?
1
```

报告末尾出现：

```markdown
## ⚠️ 告警

- <span style="color:red">🔴 指标 completion_rate = 0.6250，低于阈值 0.9900</span>
```

**退出码是 CI 的通用语言**：GitHub Actions、本地脚本、crontab 都只看退出码判定成败。这就是为什么告警的最终落点必须是退出码非零——打印得再红，退出码是 0 就等于没说。

### 5.2 run_all_checks.sh：与 CI 严格一致的本地副本

`../源码/smart-research-agent/scripts/run_all_checks.sh` 把三级门禁串成本地一键流水线：

```bash
set -uo pipefail
PYTHON="${PYTHON:-python}"        # 可用 PYTHON=... 指定解释器

python -m pytest tests/ -q          || { echo "❌ 单元测试失败"; exit 1; }
python scripts/run_agent_eval.py --min-completion-rate 0.6 --min-step-efficiency 0.7 \
                                    || { echo "❌ Agent 评估未过门禁"; exit 1; }
python scripts/run_redteam.py --min-block-rate 1.0 \
                                    || { echo "❌ 红队评估未过门禁"; exit 1; }
```

为什么有了 ci.yml 还要本地脚本？三个理由：

1. **反馈速度**：提交前本地 15 秒跑完，比 push 后等 CI 快一个数量级；
2. **同一套判定**：脚本与 ci.yml 用**完全相同的命令与阈值**——本地过了 CI 就一定过，不存在"我本地是好的"；
3. **CI 配置本身也要被测试**：本地脚本就是流水线逻辑的"单测"，改 ci.yml 前先改脚本验证。

`PYTHON` 环境变量的设计是为了跨环境：学生的机器上 `python` 指向激活的 venv（day001 的环境约定）；没激活时显式指定 `PYTHON=.venv/Scripts/python.exe bash scripts/run_all_checks.sh`。

### 5.3 可观测性三支柱全景

至此三支柱在本项目的落位齐了，值得回头总览：

| 支柱 | 回答的问题 | 本项目落地 | 引入日 |
|------|-----------|-----------|--------|
| Log 日志 | 系统发生了什么？（离散事件流） | `utils/logger.py` + `security/audit.py` | day004 / day015 |
| Metric 指标 | 系统整体健康吗？（可聚合的数） | `evaluation/metrics.py` + `observability/cost_tracker.py` | day015 / day032 |
| Trace 追踪 | 这一次请求经历了什么？（结构化账本） | `observability/tracing.py` | day032 |

告警（alerting）不是第四支柱，而是**指标的下游消费者**：指标负责度量，告警负责在度量越界时叫醒人（或叫醒 CI）。

### 5.4 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 评估脚本进 CI 门禁 | LLM 项目品质退化是确定性单测的盲区，评估即测试 | `ci.yml` 三个门禁步骤 |
| 评估全程 MockLLM 离线 | 进 CI 的前提：确定性 + 无密钥 + 零费用 | day030/031 既有设计 |
| 门禁阈值从基线略低处起步 | 门禁初始职责是防退化，不是逼优化 | `--min-completion-rate 0.6` |
| 红队拦截率阈值定 1.0 | 已知攻击集必须全拦，安全指标从紧 | `--min-block-rate 1.0` |
| 归因维度是记录的字段 | 标签打在记录时，聚合不猜测 | `UsageRecord.model/endpoint` |
| 未知模型抛 KeyError | 宁可报错不可漏算，0 元是最危险的错误 | `CostTracker.record()` |
| usage_log 追加 + 游标消费 | 生产者只管追加，消费者记住读到哪 | `record_from_llm()` |
| trace = span 树共享 trace_id | log 回答"发生了什么"，trace 回答"这次请求经历了什么" | `Span` / `Tracer` |
| 代理插桩计时 | 被测对象不为观测做改造 | `_TimedLLMProxy` |
| 异常路径先落盘再抛出 | 观测系统的价值在故障时最大 | `TraceContext.span()` |
| 告警最终落点是退出码 | 退出码是 CI 的通用语言 | `return 1 if alerts else 0` |
| 本地脚本与 CI 同命令同阈值 | 本地过了 CI 就一定过 | `run_all_checks.sh` |

明天进入 M4（大模型原理与 API 调用），day033 会深入 GPT 类模型的自回归生成原理——今天 `CostTracker` 里"输出 token 比输入贵"的定价现象，明天会从解码原理上得到解释；同时给 Agent 加上多模型路由能力，届时 `CostTracker` 的按模型归因正好用来度量路由策略省下了多少钱。
