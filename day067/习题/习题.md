## 第一部分：选择题

### 第 1 题（CJK 免分词的 2-gram 方案）

关于 `lexical.tokenize` 的切分规则与"为什么不引入 `jieba`"，下面哪一句是**对的**？

- A. 关键词一路应当换成 `jieba` + `rank_bm25`：分词质量决定 BM25 的上限，而"零依赖"只是课程偏好；一旦换上分词库，`词表 274 / avgdl 34.3` 这类数字会明显变小，精确率随之上升
- B. 只留 2-gram 更干净：单字粒度会把"语义"与"义语"混在一起（它们共享 语/义/义/语），因此单字是噪声，`tokenize("语义缓存")` 应该只给 `["语义", "义缓", "缓存"]`
- C. 按空格切再删标点就够了：中文虽然没空格，但入库正文里的标点与英文单词已经把句子切得足够碎，`"语义缓存"` 会被切成两个词元，比 2-gram 更接近"真正的分词"
- D. **先按 `[a-z0-9_]+ | [\u4e00-\u9fff]+` 切段（标点、空白、连字符都是分隔符），拉丁段原样保留（大小写先折叠）、汉字段长度 1 保留该单字、长度 ≥2 则「单字 + 相邻 2-gram」：实测 `tokenize("语义缓存") == ["语", "义", "缓", "存", "语义", "义缓", "缓存"]`、`tokenize("ERR-2043") == ["err", "2043"]`、`tokenize("retry_budget") == ["retry_budget"]`；单字与 2-gram 各补一件事（单字让"重算"与"重新计算"共享 重/算，2-gram 把"缓存"与"存缓"区分开），而 2-gram 只在同一个汉字段内生成，因此 `tokenize("  语义  缓存  ")` 里**没有**跨空白的 `义缓`；不用 `jieba`/`rank_bm25` 的两条理由缺一不可：不新增依赖（本节产物要在"只有 Python + 标准库"的机器上复现，而 `jieba` 还带约 5 MB 词典）、评估要可复现（分词器有版本，换版本会切出不同的词，于是同一天同一份语料给出不同的 BM25 分数；相邻 2-gram 没有版本）**

### 第 2 题（IDF 恒正、k1 与 b 的方向）

关于 BM25 的打分公式与两个参数，下面哪一句是**对的**？

- A. 经典写法 `log((N - df + 0.5) / (df + 0.5))` 更好：本模块的 `log(1 + …)` 把 IDF 整体抬高了，而 `df > N/2` 时给出负权重其实是合理的——"到处都出现的词"本来就该给文档减分
- B. **`idf(t) = log(1 + (N - df + 0.5) / (df + 0.5))` 里的那个 `1 +` 是刻意的：经典写法在 `df > N/2` 时会变成负数，于是"分数越靠近 0 越不相关"与"负分意味着减去相关性"两件事混在一起，而本模块用 `0 分` 当"完全没有共同词元"的哨兵（`search` 只返回 `score > 0` 的文档），恒正的 IDF 让"0 分"只有一个含义；实测 `_idf(10, 1) = 1.992430`（手算 `log(1 + 9.5/1.5)`）、`_idf(10, 10) = 0.046520`；`k1=1.5` / `b=0.75` 的缺省出自 Robertson & Zaragoza（2009）的经典取值，**不是本课标定出来的**；两个参数的方向在受控语料上单调——`k1` 扫描（`b` 固定 0.75）时 `heavy/light` 的分数比是 `1.0000 → 1.0549 → 1.1268 → 1.1883 → 1.2852`（`k1=0` 时词频完全不参与、两篇同分），`b` 扫描（`k1` 固定 1.5）时比值 `1.8182 → 1.5710 → 1.1268 → 0.9264` 单调下降（`b=1` 时"长文档里的同一个词更不值钱"，`heavy` 反而**低于** `light`）**
- C. 两个参数可以合成一个"文档长度惩罚"：`k1` 与 `b` 都是让长文档打折，同时调大就能同时得到"词频收益更大"与"长文档更不值钱"，因此扫描时应当一起调
- D. `b` 越大长文档越占优：`b` 是"长度归一化强度"，`b=1` 表示完全归一化，而完全归一化之后长文档里的词频被放大得更厉害，所以 `heavy/light` 的比值在 `b=1` 时达到最大

### 第 3 题（量纲不可比与 weighted 的两个细节）

关于"为什么要有两种融合策略"与 `weighted` 的实现细节，下面哪一句是**对的**？

- A. 直接加权求和就够，只要把 `alpha` 调小：两个数字都是浮点数，`0.82` 与 `7.31` 相加在数学上没问题；`alpha` 就是用来压住 BM25 那一侧的
- B. `min == max` 时应当归一化成 `0.0`：这一路没有区分度（只有一条命中，或多条同分），归一化成 0 才诚实地表达"它没提供信息"
- C. 归一化应当对**合并之后**的分数做：先两路合并成一张分数表再 min-max，这样"最大值"是全局最大值，`alpha` 调整的就是整张表的重心，比逐路归一化更省事
- D. **向量路是余弦 ∈ [-1, 1]、关键词路是 BM25 ∈ [0, ∞)，两个区间的数字直接相加是类型错误而 `sorted` 不会报错，于是"加权求和"会把量纲差当成相关性差——实测同一批输入下向量路分数 `[1.0, 0.0, 0.0]`、关键词路 `[4.0006]`，直接相加时后者单方面说了算；因此 `weighted` 必须**在每一路内部**做 min-max（对合并后的分数做，`alpha` 调的是"混在一起之后的重心"，仍然不是权重），且 `min == max` 必须定义为 **1.0** 而不是除零或 0（一路只有一条命中时它必然是该路第一名，归 0 会让"唯一的那条证据"被 `0 × weight` 乘没）；实测 alpha 扫描里两条"各自的第一名"的分数恰好是 `alpha` 与 `1 - alpha`（`alpha=0.25` 时 `h-c-01=0.2500`、`h-t-01=0.7500`；`alpha=0.5` 时两者都是 `0.5000`，第一名按 `record_id` 升序落到 `h-c-01`），`alpha=0.0/0.25` 时关键词路那份第一、`0.75/1.0` 时向量路那份第一——权重**确实**在起作用**

### 第 4 题（RRF 只看名次与第三排序键）

关于 `rrf` 策略，下面哪一句是**对的**？

- A. RRF 也需要分数，只是要先把两路各自归一化：`score = Σ 归一化分数 / (k + rank + 1)`，这样"差多少"与"排第几"都进了公式
- B. `k` 越小越稳：`k` 是平滑常数，`k` 越大头部权重越集中（`k=1` 时第 1 名只有 `1/61`），因此缺省应当取 1，让排名第一的那条更突出
- C. **`score = Σ_channels 1 / (k + rank + 1)`（`rank` 从 0 起，`k` 缺省 60 出自 Cormack、Clarke & Buettcher（2009）的原文），它**完全不看分数**：实测 `ERR-2043` 在深度 3 时向量路三名 `h-c-01(rank 0)/h-c-02(rank 1)/h-c-03(rank 2)`、关键词路 `h-t-01(rank 0)`，手算与引擎逐位一致 `h-c-01 = 1/61 = 0.016393443`、`h-t-01 = 1/61`、`h-c-02 = 1/62 = 0.016129032`、`h-c-03 = 1/63 = 0.015873016`；`h-c-01` 与 `h-t-01` 分数**精确并列**，次序由第三排序键决定（`_assemble` 的键是 `(-score, best_rank, record_id)`，`h-c-01 < h-t-01`）——这不是"向量路赢了"，而是"分数并列时必须有确定的第三键"，没有它同一份数据两次运行会给出不同的 top-1；而"不看分数"的可核对形态是：把某一路的分数整体放大 100 倍，融合结果逐位不变**
- D. RRF 的代价是"抗不住异常值"：某一路给出一条分数虚高 100 倍的记录时，它会因为分数大而被排到第 1 名，这正是 `weighted` 存在的理由

### 第 5 题（两个落刀位置与空结果口径）

关于混合模式下 `where` 与 `min_score` 各自落在哪一刀，下面哪一句是**对的**？

- A. 过滤只在一路落刀就够：融合会按 `record_id` 去重，被过滤条件排除掉的记录反正会被向量路剔掉，关键词路多返回的那几条不会进入最终名单
- B. `min_score` 应当对两路都生效才一致：既然向量路有阈值，关键词路也给它一个同样的数字，两边的门槛就对齐了；BM25 的分数虽然尺度不同，但"越大越近"这个口径是一致的
- C. 阈值把向量路清空就等于空结果：单路检索里 `min_score` 切光即是 `below_threshold`，混合模式沿用同一条规则即可，不必再看关键词路
- D. **`where` 必须在两路都落刀、而且是**同一份**子句（`hybrid.py` 第 5 步把 `combine_where` 的调用放在两路取候选**之前**、只调一次，同一个变量交给两个调用点——这是代码结构上的保证）：只过滤向量路时，关键词路会把已被排除的记录重新抬进名单，实测 `where={"parent_doc_id": "doc-concept"}` 的反面对照里融合名单出现 1 条不满足条件的记录 `[('h-t-01', 'doc-trouble')]`，而报告里 `filter_applied=True`、没有任何异常——**"多而不报"比"少而不报"更难发现**；而 `min_score` **只作用于向量通道**（在融合前落刀）：实测 `min_score=1.0` → 向量路候选 1 条、切掉 9 条、名单 2 条（`h-c-01`、`h-t-01`），`min_score=1.5` → 向量路候选 0 条、切掉 10 条、名单仍有 1 条 `h-t-01`（它的 `channels == ('bm25',)`）；"min_score=X 只作用于向量通道"这句话**即使一条都没切、即使阈值是 `-1.0` 也必须进 `notes`**，因为它是一个"被忽略的参数"（假的安全感，与 `retrieval_min_score` 缺省 `None` 同源）；随之而来的是混合模式下 `below_threshold` 的新口径——它必须**同时**满足"关键词路本来就没召回"（阈值不可能清空关键词路）：实测 `QUERY_SEMANTIC + min_score=1.5` 是 `below_threshold`，而 `ERR-2043 + min_score=1.5` **不是空结果**

## 第二部分：判断题

### 第 6 题

`LexicalIndex.search` 只返回 `score > 0` 的文档是"丢召回"：BM25 会给完全不相关的文档一个 0 分，
把它们排除在名次之外等于关键词路主动放弃了一批候选；既然 RRF 只看名次，多给一路几条"第 N 名"
的证据只会让融合更稳，因此 0 分文档也应当带着 0 分进入名次。（对 / 错）

### 第 7 题

`RetrievalHit.channels[0]` 与 `RetrievalHit.channel` 永远相等不是巧合：
前者由 `fusion._ordered_channels` 给出（按名次好坏排序，**名次相同时向量优先**，
再按名字兜底），后者由 `hybrid._dominant_channel` 给出（**贡献最大者，并列时
`CHANNEL_VECTOR` 优先**）——两处必须是同一条规则，因为它们本来就是同一个问题的
两个问法；同理 `sum(contributions.values()) == score` 在 `rrf` 与 `weighted`
两种策略下都成立（证据必须能解释分数）。（对 / 错）

### 第 8 题

混合检索缺省就是开着的：`retrieval_hybrid_enabled` 的缺省值只需要写成 `True`，因为多一路候选
只是"更全"；而且开关关着时 `POST /retrieval/hybrid` 应当**静默退回单路**（照常返回 200，
只是结果里没有关键词路的证据），这样调用方不必改代码就能先把链路跑通。（对 / 错）
