## 第一部分：选择题

### 第 1 题 → **B**

三项各自的"缺了会怎样"是本课第一个需要记住的对照表：

| 字段 | 缺了它会怎样 |
|------|-------------|
| `base_model` | 同名同格式的适配器挂在不同基座上会给出**完全不同**的输出，而且不会报错（day052 的推理脚本专门为此打了警告） |
| `adapter_sha256` | 分不清"调了学习率重训"与"同一个权重" |
| `dataset_fingerprint` | 分不清"同一份数据多训了两轮"与"换了一批数据"；而这两件事的效果差异通常比调参大得多 |

A 是错的：缺一项确实会抛 `RegistryError`，但那是**形式**上的后果，
而不是这项设计存在的理由；C 是错的：合并只用基座与适配器的权重；
D 是错的：版本号由注册表里的历史推出，与三元组的内容无关。

### 第 2 题 → **C**

归一化**不会**让版本键变短——键的长度恒为 16 位十六进制
（`VERSION_KEY_LENGTH`），归一化只是保证**同一份产物得到同一个键**。

A、B、D 都是真实理由，而且各自对应一个人工事故：终端复制带换行、
日志里印的是 `sha256:5c6d7e8f9012` 这种带前缀形式、`hexdigest()` 给小写
而人常写大写。归一化之后**立刻做十六进制校验**：一个含 `g` 的"哈希"是抄错了，
而它如果混进键里，只会表现为"版本总是不匹配"，不会有任何报错。

### 第 3 题 → **A**

```text
| 步骤 | 变化项 | 递增位 | 新版本号 |
|------|--------|--------|----------|
| 首版 | （首版） | minor | v1.0.0 |
| 同数据重训 | adapter_sha256 | patch | v1.0.1 |
| 换数据集 | dataset_fingerprint | minor | v1.1.0 |
```

递增位由 `bump_kind_for(previous, base_model=..., dataset_fingerprint=...)` 推出，
判据只有两项（基座、数据集指纹）：

- 基座变了 → `major`（旧适配器挂不上新基座，整条适配器链作废）；
- 只有数据集指纹变了 → `minor`；
- 两项都没变（只有适配器变了）→ `patch`。

B、D 把"重训"当成 `minor`：那会让版本号迅速失去区分度——
**重训是持续微调里最高频的动作**，v1.9 → v2.0 只因为多跑了一次同样的数据。
C 把"换数据集"当成 `major`：换数据的候选虽然与上一版**不可比**
（见第 4 题），但模型谱系是连续的，`major` 的语义要留给基座替换。

顺带一个容易踩的坑：递增某一位时右边的位**必须归零**，否则会得到
`1.9.3 → 2.9.3` 这种"跨了大版本却还带着小版本号"的怪号。

### 第 4 题 → **B**

`-0.1600` 是 **0.4400 − 0.6000**，两个数来自**两套不同的评估分布**：

```text
缺省（require_comparable=True）: action=hold gain=未计算
  被拦下：不可比且未达绝对门槛：候选 0.4400 < 0.5
关掉可比性要求                 : action=hold gain=-0.1600
  被拦下：增益 -0.1600未达到采纳门槛 0.02；本次差值不可作为提升证据
```

它既不是提升也不是退步。之所以危险，是因为下游会把它当**提升量**使用
（"候选比当前低 0.16，所以不能换"听起来完全合理，但它比较的其实是两份
不同的卷子）。这正是 day057 那句"同一份数据在两套口径下得到两个结论，
是数据治理最忌讳的事"的另一种形态。

A 是错的：它没有解释任何东西；C 是错的：量级（0.16）远大于任何浮点误差，
而且是系统性的（换数据集必然改变分数分布）；D 是错的：无法从两个数字
判断"哪份数据更难"——这也是为什么缺省策略改用**绝对值门槛**而不是去
猜测一个换算关系。

### 第 5 题 → **B**

回滚是**不可逆动作**，因此第一步必须确认"有退路"：

```text
rollback | 1.0.2 → 1.0.1 | 4 步（阻塞 2）
  1. [verify] 校验目标 v1.0.1 产物齐全（阻塞）
  2. [freeze] 把 v1.0.2 置为 rolled_back（阻塞）
  3. [record] 写入审计事件（非阻塞）
  4. [observe] 按 24.0h 观察窗口监控（非阻塞）
```

反过来写也能通过绝大多数测试，代价只在最坏情况下暴露：先冻结当前版本、
再发现目标不可部署，结果是**生产上没有任何可服务版本**。这与 day046 的
六阶段、day057 的六阶段是同一种推理方式——每一步的位置都有理由，
换位只在某些输入下才出错，而那种错误最难在测试里被发现。
所以它被写成代码里的固定顺序，并有一条断言直接钉住 `steps` 数组。

A 是错的：`verify` 只读一份 JSON，两边都不是瓶颈；C 是错的：两者参数独立；
D 是错的：可实测两种顺序在"目标不可部署"的输入下结果完全不同。

## 第二部分：判断题

### 第 6 题 → **对**

两个性质都在 `ModelRegistry._insert` 里，实测（demo 第 3 节）：

```text
非法迁移被拒：非法状态迁移 stable → candidate（1.0.0）；允许的目标：archived, rolled_back
版本号冲突被拒：版本号 1.0.0 已属于键 abef9265dd96544e（…），不能再给键 9a8b309ccd09837f 使用；
              版本号是人写的叙事，两份不同产物写同一个号是常有的事，静默覆盖会让索引少掉一份真实产物
  幂等重登记：1.0.0
```

幂等（返回已有记录、不写重复事件）只覆盖"三元组键与版本号**都**相同"，
即 CI 重跑同一个任务的情形。把幂等放宽到"版本号相同就覆盖"是危险的：
**版本号是人写的叙事**，两个人给两份不同的产物写同一个 `1.2.0` 是常有的事。

冲突信息里给出**具体哪些字段不同**也是必需的：只报 "conflict" 的话，
运维唯一的动作就是去翻索引文件。`VersionConflict.fields` 正是为此存在。

### 第 7 题 → **错**

`prune()` **只清理候选**，而且 `head()` 与所有 `stable` 版本都不会被归档：

> **`stable` 是回滚目标，归档一个 stable 版本等于删掉一条退路。**

`prune` 的两条保护都写在代码里（不是注释里的建议）：
① 只收集 `stage == candidate` 的记录；② `head()` 必然是 stable，
因此第 ① 条已经覆盖它，但仍然显式写出这个推论——`prune` 的调用方不该
需要自己记住它。

要下线一个 stable 版本，必须显式走 `rolled_back` 或 `archived`：
**那是一次有理由的运维动作，而不是磁盘清理的副作用。**

只清理候选的理由同样具体：候选是"跑完还没通过门禁"的中间态，数量增长最快、
生命周期最短，而且**每一个都能由三元组重新算出键**——真需要它们回来，
重新登记一次即可，丢失的信息只有"当时分数多少"。

### 第 8 题 → **对**

两条都是"**缺失与 0 是两件事**"这条纪律的实例，而后果可以精确算出来：

```text
hours_since_last_train = None → 当成 0 → 0 < 24 → veto
```

把缺失当 0，会让"从未训练过"的新仓库被冷却期**永久**拦住——
而它恰恰是最该训练一次的那种状态。同理，把
`online_pass_rate=None` 当成 0 会让每一次判定都触发一次"质量下降"重训。

实现上还有一个细节：`TriggerEvaluation.actual` 允许为 `None`
（而不是用 `-1` 或 `0` 当哨兵），因为"没有观测值"与"观测值是 0"
在报告里不能打印成同一个样子——**一个显示为 0 的缺失值，
会被读报告的人当成一次真实的观测。**

## 第三部分：简答题

### 第 9 题

#### (1) 会丢失哪一条信息

把 veto 改写成"触发器的反向条件"之后，判定规则变成
`should_retrain = all(t.fired for t in triggers)`。此时下面两种状态
**被压成同一种**（都表现为 `should_retrain=False`）：

```text
状态甲：fired = []                            → 没有理由训练
状态乙：fired = [data_growth, dataset_change] → 有理由，但冷却期未过
```

要区分它们，报告里必须**同时**保留两份信息：**"有没有理由"**与
**"时机允不允许"**。本课的写法是：

```python
should_retrain = bool(fired) and not vetoed       # 两个量各自独立记录
```

两者的运维动作完全不同：

| 状态 | 报告给出的信号 | 运维动作 |
|------|---------------|---------|
| 甲 | `fired=[]`，`notes="没有任何触发理由：去看数据与线上评估，而不是调冷却期"` | **去查**：数据流水线是不是没跑？线上评估窗口是不是没开？ |
| 乙 | `fired=[…]`，`vetoed_by=[cooldown]`，`notes="这是'再等等'而不是'不需要'"` | **等**：什么也不用做，24 小时后同一次判定会自动放行 |

把两者压成一种，运维看到 "False" 之后的第一个动作通常是**去调冷却期**——
而在状态甲里调冷却期什么也解决不了。

#### (2) 为什么允许 `actual` 为 `None`

因为 `-1` 或 `0` 这类哨兵值**会被下游当成真实观测值**：

- `online_pass_rate` 的合法区间是 `[0, 1]`，`0` 是**合法值**（合格率为 0）。
  用一个合法值当"缺失"的哨兵，等于把"从没评估过"与"评估结果是全错"
  混为一谈——而后者需要立刻告警，前者只是还没开始；
- `-1` 更糟：它落在合法区间之外，任何"顺手打印一下"的地方都会显示出
  一个明显荒谬的数字，而**荒谬的数字会被人忽略**（"这肯定是缺失"），
  于是它既丢掉了语义、又污染了报表。

允许 `None` 还有第二个好处：类型层面就能看出这个字段是可空的，
调用方**必须**显式处理"没有观测值"这条分支。这与
`ModelVersion.pass_rate` 返回 `None` 是同一条纪律。

#### (3) 为什么判定顺序必须等于展示顺序

因为报告是给人看的，而"读报告的人"与"改代码的人"往往不是同一个人。
顺序不同步会带来两个具体问题：

1. **定位成本**：报告里第 4 行写着 `cooldown`，而代码里它是第 5 个被评估的
   项——当有人想加一条"为什么这里会否决"的日志时，他得先在脑子里做一次
   重排。一次重排不出错，但每次都重排一定会出错；
2. **版本漂移无法被发现**：如果有人把某条评估挪到前面，报告顺序会跟着变
   （因为 `render_markdown` 直接遍历 `evaluations`），
   于是"顺序变了"这件事本身没有任何提示。而顺序在这里是有语义的——
   前三条是触发器、后两条是否决项。

因此本课用一条用例把它钉住：

```python
def test_evaluation_order_is_triggers_then_vetoes():
    decision = evaluate_triggers(TriggerState())
    assert [item.name for item in decision.evaluations] == [
        TRIGGER_DATA_GROWTH, TRIGGER_DATASET_CHANGE, TRIGGER_QUALITY_DROP,
        VETO_COOLDOWN, VETO_ACTIVE_RUN,
    ]
```

## 第四部分：编程题

### 第 10 题

```python
"""day058 习题 10 参考实现：事件流折叠 + 回滚顺序（离线、确定性）."""

from __future__ import annotations

import tempfile
from pathlib import Path

from smart_research_agent.registry import (
    STAGE_CANDIDATE,
    STAGE_STABLE,
    ModelRegistry,
    ModelVersion,
    RegistryError,
    VersionTriple,
    apply_rollback,
    plan_rollback,
)


def hexdigest64(seed: str) -> str:
    """由字符串派生 64 位十六进制串（确定性适配器哈希，避免用 random）."""
    raw = "".join(f"{byte:02x}" for byte in seed.encode("utf-8"))
    return (raw * 8)[:64]


def make(version: str, **kwargs) -> ModelVersion:
    """构造一条版本记录（默认产物齐全、有一个可比的合格率）."""
    artifacts = kwargs.pop(
        "artifacts", {"adapter": f"a/{version}", "merged": f"m/{version}"}
    )
    return ModelVersion(
        triple=VersionTriple(
            base_model="Qwen3-8B",
            adapter_sha256=hexdigest64(version),
            dataset_fingerprint="3f1b0c9d7e5a2468",
        ),
        version=version,
        parent_version=kwargs.pop("parent", ""),
        stage=kwargs.pop("stage", STAGE_CANDIDATE),
        artifacts=artifacts,
        metrics={"eval_pass_rate": 0.6},
    )


# --------------------------------------------------------------------- 第 1 件事


def part_one(index: Path) -> None:
    """事件流折叠：确定性、幂等性、失败动作不留事件."""
    registry = ModelRegistry(index)
    registry.register(make("1.0.0"))
    registry.set_stage("1.0.0", STAGE_STABLE, reason="首次上线")
    registry.register(make("1.0.1", parent="1.0.0"))

    # 1) 写入方与重载方的审计流必须逐条相等（教程 3.4 节那个缺陷的回归测试）
    reloaded = ModelRegistry(index)
    assert len(registry.events()) == len(reloaded.events()) == 3
    assert registry.events() == reloaded.events()

    # 2) 折叠幂等：reload 两次状态不变
    before = reloaded.counts()
    reloaded.reload()
    reloaded.reload()
    assert reloaded.counts() == before

    # 3) 失败的动作不能留下事件
    lines_before = len(index.read_text(encoding="utf-8").splitlines())
    try:
        reloaded.set_stage("1.0.0", STAGE_CANDIDATE)  # stable → candidate 被禁止
    except RegistryError as exc:
        print(f"非法迁移被拒：{exc}")
    lines_after = len(index.read_text(encoding="utf-8").splitlines())
    assert lines_after == lines_before, "失败的动作写进了索引"


# --------------------------------------------------------------------- 第 2 件事


def part_two() -> None:
    """回滚计划的顺序与三处边界."""
    registry = ModelRegistry()
    registry.register(make("1.0.0", stage=STAGE_STABLE))
    # v1.0.1 缺 merged —— 它不可部署，回滚必须跳过它
    registry.register(
        make("1.0.1", parent="1.0.0", stage=STAGE_STABLE, artifacts={"adapter": "a/1.0.1"})
    )
    registry.register(make("1.0.2", parent="1.0.1", stage=STAGE_STABLE))

    plan = plan_rollback(registry, "1.0.2", reason="演练")
    assert plan.action == "rollback"
    assert plan.target_version == "1.0.0"
    assert [step.action for step in plan.steps] == ["verify", "freeze", "record", "observe"]
    assert [step.blocking for step in plan.steps] == [True, True, False, False]

    # 没有退路：首个 stable 版本
    lonely = ModelRegistry()
    lonely.register(make("1.0.0", stage=STAGE_STABLE))
    hold = plan_rollback(lonely, "1.0.0")
    assert hold.action == "hold"
    assert hold.steps == ()
    assert hold.should_execute is False
    try:
        apply_rollback(lonely, hold)
    except RegistryError as exc:
        print(f"hold 计划被拒绝执行：{exc}")


if __name__ == "__main__":
    with tempfile.TemporaryDirectory() as tmp:
        part_one(Path(tmp) / "versions.jsonl")
    part_two()
    print("全部断言通过")
```

#### 为什么"失败的动作不能留下事件"必须被单独断言

因为"它会抛异常"与"它没留下事件"是**两件独立的事**，而后者才是我们真正需要的性质。

`set_stage` 的实现顺序是：

```python
def set_stage(self, version, stage, *, reason="", record=None):
    current = self.get(version)
    if record is not None:
        ...                       # ① 校验 record 与目标版本一致
    updated = current.with_stage(stage, note=reason)   # ② 这里会抛 RegistryError
    self._records[current.version] = updated           # ③ 内存折叠
    self._append({...})                                # ④ 落盘
    return updated
```

抛异常发生在 ②，因此 ④ 不会执行——**这个顺序是刻意的**，
而它是可以被无声改坏的：把 `_append` 提前到 `with_stage` 之前
（"先记账再改状态"，看起来很合理），异常照抛、测试里那条
`pytest.raises(RegistryError)` 照样通过，**只有"索引里多了一行"这件事没人发现**。

那一行事件的后果不是"多了一条日志"，而是**下一次 `reload()` 会失败**：

```text
stage 事件指向一个与当前状态冲突的阶段
→ 折叠时 with_stage 抛 RegistryError
→ 整个注册表从此读不出来（load 阶段就崩）
```

也就是说：**一个"多余的事件"会把一份本来能用的索引变成一份读不出来的索引。**
这正是"先折叠再落盘"这条顺序在 `register` 的 docstring 里被写成纪律的原因
（"折叠会抛异常，抛出时不该在文件里留下一行'事件已经写了、但状态没建立'的记录"）。

同样的推理适用于另外两处：

1. **`register` 的幂等命中不写事件**：重复写会让索引膨胀，而语义上什么都没发生；
2. **`_fold` 遇到未知事件类型直接抛错**：跳过不认识的事件会丢状态，
   而丢状态的表现只是 `head()` 变成 `None`——查的人根本不会想到是
   索引里有一行没读懂。

> 可带走的判断：**当一段代码有"先改内存、后写外存"的形状时，
> 一定要单独断言"外存没被改"。** 异常路径的测试通常只断言"抛了什么"，
> 而真正会被静默破坏的是"抛之前已经做了哪些不可逆的事"。
