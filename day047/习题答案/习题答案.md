# day047 课后习题答案

---

## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：单看"哪个模型贵"不足以做决策——同一个模型，`/agent/run` 的多轮 tool calling 与 `/chat` 的单轮问答成本能差一个数量级。`CostTracker` 因此提供 `breakdown(key)`（可按任意维度分组）与 `top_cost_paths(top_n)`，把 `model × endpoint` 组合成"调用路径"，才能回答"钱花在哪条业务线上"、优先优化哪条。A、C、D 都不是设计动机（token 数与模型统计本身无关）。

### 第 2 题

**答案：B**

**解析**：语义匹配返回的是"相近但不相同"的旧回复——语义相近不等于语义相同。而字面完全一样的两个请求，其答案高度可信可以复用。所以 `SemanticCache.get` 的顺序是**先精确匹配（规范化后查键）、未命中再比语义（余弦 ≥ 0.85）**，顺序本身即优先级。C 是次要收益而非根本原因；A、D 无据。

### 第 3 题

**答案：B**

**解析**：银行卡号是 16~19 位纯数字，与订单号、时间戳（如 `2026091215300012`）同形。纯正则只能回答"格式对不对"，无法回答"内容真不真"，会把大量正常长数字串误脱敏。Luhn 校验（模 10 校验和）能筛掉约 90% 的随机长数字串，因此采用"正则取候选 → Luhn 校验 → 通过才替换"的两步走。A、C、D 都不是理由。

### 第 4 题

**答案：B**

**解析**：审核结果（`ModerationInfo`：是否安全、命中哪些敏感词/PII 类型）要随响应体返回给客户端。中间件的 `dispatch` 能拿到 request/response 对象，但拿不到响应体、也无法往响应体里加字段，只能"拦"不能"改语义"。所以审核放在 `/chat`、`/agent/run` 的路由函数里，构造响应时把审核报告一并写入。D 错——`Depends`/`request.app.state` 在中间件里同样可用。

### 第 5 题

**答案：B**

**解析**：`estimate_vram_gb` 的显存 = **权重项 + KV 缓存项**。权重随参数量与量化档位（`bytes_per_parameter`）固定；KV 缓存随**上下文长度与 batch 线性增长**，长上下文常常才是真正的瓶颈。所以 `HardwarePlan`/`fitting_quantizations`/`max_context_tokens` 要从"卡有多少显存"反推"能用哪些量化档、上下文能开多长"。A、C、D 均为无据干扰项。

### 第 6 题

**答案：B**

**解析**：若 `store` 先于 `moderate`，含 PII 的原始回复会被写入记忆/缓存，之后被反复命中并反复返回——**缓存把"一次性泄漏"变成"持续性泄漏"**。因此 `moderate` 必须在 `store`（以及缓存写入）之前，且缓存键要包含系统提示词。这是 day046 教程中重点剖析的"顺序陷阱"。

### 第 7 题

**答案：B**

**解析**：`percentile` 的文档明确写了"实现刻意不做插值：小样本下插值会造出'观测不到的耗时'，而性能门禁的结论必须能回溯到某一次真实请求"。因此用最近秩法返回**样本中真实存在**的那个值（`q=0` 取最小、`q=100` 取最大）。A、C、D 不是设计理由。

### 第 8 题

**答案：C**

**解析**：day046 之前 `evaluation/` 覆盖检索指标（`metrics.py`）、红队（`redteam.py`）、Agent 评估、RAG 评估、Prompt 评估、输出质量——都是"答得对不对"的质量尺子。day046 新增 `perf_baseline.py`，第一次补上"跑得快不快、有没有变慢"的**性能尺子**（`PerfBaseline`/`PerformanceGuard`/`Regression`）。所以答案是 C。

## 第二部分：判断题

### 第 9 题

**答案：错**

**解析**：命中率必须与"语义阈值是否被滥用"一起看。把阈值调低确实会提升命中率，但会把**不相关**的请求也命中，省了钱却答错了——这是"用错误的答案换来的命中率"。而且阈值与 embedding 质量绑定：0.85 是给神经向量的经验值，换成 `CharNgramEmbedding` 这种字面重叠型向量，同一阈值会大面积误命中。命中率是体检指标，不是越大越好。

### 第 10 题

**答案：对**

**解析**：`25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d` 四段交替恰好枚举 0~255 的所有取值（250~255 / 200~249 / 100~199 / 0~99），于是 `999.999.999.999` 因"没有一段能匹配 999"而整体失配。这是把"格式精确约束"写进正则，属于误报防护——与银行卡号用 Luhn 是同一类思路（一个用正则约束、一个用校验和约束）。

### 第 11 题

**答案：对**

**解析**：`/agent/run` 的 `answer` 过审核脱敏，但 `tool_calls` 保留原始参数与结果。因为工具调用轨迹是**审计证据**，要求"原文是什么就是什么"；脱敏会破坏可追溯性。需要对外展示时由消费方决定如何脱敏。这体现了"审核"（关心输出安全，可改文本）与"审计"（关心证据完整，不可改文本）两种相反诉求的边界。

### 第 12 题

**答案：对**

**解析**：Ollama（默认端口 11434，api_key 占位 "ollama"）与 vLLM（默认端口 8000，未加 `--api-key` 时不校验密钥）都暴露 **OpenAI 兼容接口**，所以 `LocalModel` 继承 `OpenAICompatibleLLM`，只需要 `normalize_base_url` 规范化地址、补上探活（`is_available`）与清单（`list_served_models`）等本地特有动作。重新封装一套 SDK 只会制造第二个契约，与"协议兼容胜过 SDK 封装"的结论相悖。

### 第 13 题

**答案：错**

**解析**：day046 集成实测暴露的真实缺陷正是"包装器不透传可观测属性"——`ModelRouter` 包装叶子模型后，成本追踪器按 `llm.usage_log` 归集会在这里断链，抛 `AttributeError` 把请求打成 500。修复是新增 `router.last_used_llm`，让计费落到真正干活的叶子上。教训：**包装器必须透传可观测性**，否则所有依赖观测的下游（计费、追踪）都会断链。

## 第三部分：简答题

### 第 14 题

**参考答案要点**：

**四天各自留下的产物**：

- **day043（成本）** 留下 `CostTracker`（账单口径）与 `SemanticCache`/`CachedLLM`（省钱手段）；
- **day044（合规）** 留下 `PromptInjectionDetector`（输入护栏）、`ContentModerator`（输出审核 + PII 脱敏）、`AccessLogStore`/`AccessLogMiddleware`（HTTP 层审计）；
- **day045（部署）** 留下 `LocalModel`（本地模型实例，与云端同一套 `BaseLLM` 接口）与 `local_runtime`（显存预算）、`local_eval`（换模型前的度量）。

**day046 的汇合方式**：

- `IntegratedPipeline` 把**护栏（day044）+ 缓存（day043）+ 模型/路由（day039/045）+ 计费（day043）+ 审核（day044）+ 记忆**装配成一条**有序**六阶段流水线（`STAGE_ORDER = guard → cache → generate → account → moderate → store`）；
- `build_hybrid_router(local, cloud, ...)` 把 **day045 的本地模型** 与云端模型标上不同的 `capability`/`cost`，复用 **day039 的 `CostFirstStrategy`**，不写一行 if 就实现"简单题走本地、复杂题走云端、本地宕机自动升级"；
- `_account` 用生成前后 `CostTracker.total_cost` 的**差值**做单次请求归因，把 day043 的账单口径落到"每一次请求花了多少"。

**day046 新增（前三天没有的）**：① 一体化的**有序装配**与 `PipelineResult`（每阶段的账）；② **性能基线门禁** `perf_baseline.py`（`PerfBaseline`/`PerformanceGuard`/`Regression`，最近秩法分位数 + 判定下限防抖动）——这是评估体系里第一次出现"性能尺子"；③ `router.last_used_llm` 修复"包装器计费断链"；④ `/pipeline/run` 与 `/pipeline/baseline` 两个端点。

## 第四部分：编程题

### 第 15 题

**参考答案**（可直接追加到 `tests/test_pipeline.py`）：

```python
class TestStageOrder:
    def test_moderate_runs_before_store_and_masks_pii(self):
        """输出审核必须先于记忆写入，否则 PII 会被缓存反复返回."""
        llm = MockLLM(default="我的手机号是 13812345678，请联系我")
        pipeline = IntegratedPipeline(
            llm,
            moderator=ContentModerator(),
            detector=PromptInjectionDetector(),
        )
        result = pipeline.run("帮我查一下 RAG 相关资料")

        # ① 正常路径走完整阶段序列
        names = result.stage_names
        assert names == list(STAGE_ORDER)

        # ② moderate 必须排在 store 之前
        assert names.index(STAGE_MODERATE) < names.index(STAGE_STORE)

        # ③ 最终答复已脱敏，手机号不再出现
        assert "13812345678" not in result.reply
        assert "***手机号***" in result.reply

        # ④ moderate 阶段记录里带审核结果
        assert "手机号" in result.moderation.pii_types
        record = result.stage(STAGE_MODERATE)
        assert record is not None
        assert "手机号" in record.detail
```

**关键点说明**：

1. **导入**：`from smart_research_agent.integration.pipeline import STAGE_MODERATE, STAGE_STORE, STAGE_ORDER, IntegratedPipeline`；`MockLLM` 来自 `smart_research_agent.llm.mock`，`ContentModerator`/`PromptInjectionDetector` 来自 `smart_research_agent.security`。
2. **构造**：`IntegratedPipeline` 的协作者全部可注入且可为 `None`（`None` = 该层不启用），因此测试可以只开"审核 + 护栏"两层，把变量降到最少。
3. **阶段记录**：`_moderate_detail` 在未通过时返回 `f"flagged={...} pii={...}"`，所以 `record.detail` 里能直接读到 `手机号`——阶段记录不是空壳，它承载了审核结论。
4. **如果调换成 `store` 先于 `moderate` 会怎样**：含手机号的原始回复会被写入记忆/缓存，后续相同或语义相近的请求**命中缓存直接返回未脱敏的旧回复**，且**不再经过审核**（缓存命中路径止于 `moderate` 之前的流程会被改写）——泄漏从"一次"变成"持续、可复现"。这正是 day046 强调"顺序即策略"的原因：装配顺序不是实现细节，而是安全语义的一部分。

**验证**：运行 `python -m pytest tests/test_pipeline.py -q`；day046 快照全量 **956 个测试通过、覆盖率 95.99%**（其中 `integration/pipeline.py` 100% 覆盖）。
