## 第一部分：选择题

### 第 1 题（多模态协议）

关于视觉-语言模型的输入格式，下列哪一项说法是**正确**的？

- A. 视觉请求里 `user` 消息的 `content` 仍是纯字符串，图像作为独立的顶层字段传给模型
- B. `content` 升级为部件数组，如 `[{"type": "text", ...}, {"type": "image_url", ...}]`，模型按顺序理解各模态的关系
- C. 图像必须放在 `system` 消息里，否则模型会忽略它
- D. 图像部件里的 `url` 必须是 `https://` 开头的远程地址，data URL 不被视觉模型接受

### 第 2 题（data URL 与体积）

项目把单张图片的体积上限设为 10 MB。下列哪个原因在教程中**没有**被列为依据？

- A. base64 编码会把字节膨胀约 1/3，10 MB 图片编码后约 13.3 MB 字符
- B. VLM 对超高清大图按 tile 切块计费，体积越大 token 成本越高
- C. 超过 10 MB 的图片在传输过程中更容易触发 TCP 分包错误
- D. 限制体积既是传输保护，也是成本保护

### 第 3 题（类型识别的可靠性）

服务端校验图片类型用 magic bytes 而不是文件扩展名，原因是：

- A. magic bytes 由格式规范定义在内容开头，扩展名可以被随手伪造，所以校验要基于内容而非声称
- B. magic bytes 校验比扩展名校验更快
- C. 扩展名是客户端传来的，magic bytes 是服务端自己生成的
- D. 只有 magic bytes 才能区分 PNG 和 JPEG

### 第 4 题（错误类型细分）

`multimodal/image.py` 定义了 `EmptyImageError` / `ImageTooLargeError` / `UnsupportedImageTypeError` 三种异常。这样设计的主要好处是：

- A. 让 `chat_vision` 能捕获所有图片错误并静默跳过图像
- B. 让不同消费方（API 层按类型映射状态码、工具层统一转业务文案）都能按类型分支处理，而不是解析错误文案
- C. 让图片校验逻辑能够被拆分成三个独立模块
- D. 让模型能直接读懂异常类型并调整回答策略

## 第二部分：判断题

### 第 5 题

`BaseLLM.supports_vision` 默认返回 `False`、`chat_vision` 默认抛 `NotImplementedError`，这样的设计保证旧实现无需改动就保持"不支持视觉"的诚实状态，且绝不静默忽略图像。（对 / 错）

### 第 6 题

`ModelRouter.chat_vision` 在遍历降级链时，遇到不支持视觉的模型应当**抛错**，好让调用方尽快知道"这个池子里有模型看不了图"。（对 / 错）

### 第 7 题

`ImageAnalysisTool` 把任何失败都以"图像分析失败: 原因"字符串返回而不是抛异常，与 `CalculatorTool` 的约定一致，是为了让 Agent 循环能把这句文案当作可读反馈拼回上下文、据此调整策略。（对 / 错）
