### 第 1 题 → **B**

纯文本丢掉了 M6 后面七天要用的全部信息：

| 信息 | 谁需要它 |
|------|---------|
| 标题层级 | day062 的结构分块（按标题切）、day069 的 RAG 提示（把标题当上下文） |
| 代码块与其语言 | day062 不该把代码从中间切开 |

A、C、D 都不是理由。顺带说清一件容易混淆的事：**`text` 与 `blocks` 是同一份
内容的两种视图，而不是两份数据**。`make_document` 里全文**只能**由块拼出：

```python
kept = [block for block in blocks if not block.is_empty]
body = normalize_text("\n\n".join(block.text for block in kept))
```

一开始它接受一个覆盖用的 `text` 参数，理由是"加载器可能有更准确的全文"。
那个参数被删掉了——**它的存在本身就是在允许两份内容不一致**，
而一旦不一致，两份都会有人依赖：分块器按 `blocks` 切、检索器按 `text` 找，
于是"检索命中的段落"与"引用到的原文"会长期对不上，且不会报错。

### 第 2 题 → **C**

C 是错的，而且是**反过来的**：`doc_id` **完全不包含**文件名与路径。
`content_id(规范化文本)` 只看文本内容，因此：

```text
docs/guide.md 与 docs/guide-copy.md（内容相同）→ 同一个 doc_id
重命名文件                                    → 同一个 doc_id
```

A、B、D 都成立，而且各有具体用途：

- A 支撑**去重**：同一份规范从两个渠道各下了一份，入库时被认成同一份；
- B 支撑**内容寻址**：与 day058 的三元组、day060 的部署绑定同一种设计；
- D 是设计的边界：文件名与路径回答的是"这份内容放在哪"，
  把它们混进 id 会让同一份内容因为换了个目录就变成两份，而去重也就失效了。

实测（demo 第 6 节）：

```text
docs/guide.md            → 2de1fccfba62a249
docs/guide-copy.md       → [重复]（与 docs/guide.md 内容相同）
renamed.md（同内容）     → 2de1fccfba62a249（同一个指纹）
```

### 第 3 题 → **C**

```python
def test_detection_prefers_content_and_reports_the_conflict():
    detection = detect_media_type("fake.txt", b"%PDF-1.4\n")
    assert detection.media_type == MEDIA_PDF
    assert detection.decided_by == DECIDED_BY_MAGIC
    assert detection.conflict is True
    assert detection.suffix_type == MEDIA_TEXT
```

实测的那一行：

```text
fake.txt → application/pdf（**冲突**：后缀说 text/plain、内容说 application/pdf；按内容处理）
```

A 是最常见的错答，也是真实系统里最常见的做法：
**只信后缀的代价非常具体**——导出工具改名不改内容、下载器按 URL 猜后缀、
磁盘上有人手工改过扩展名。按后缀处理会得到一个"解析成功但内容全空"的文档，
而那种结果最容易被当成"这份文件本来就没内容"。

B 是另一个极端：抛异常会让一份**本来能解析**的文件失败。
冲突不是错误，它是一个**需要被记录的事实**——它往往是"文件被人改过"
的第一手证据，因此进文档元数据（`media_type_conflict`）。

D 比 B 更糟：把决定权推回给用户，而用户往往只知道文件名。

### 第 4 题 → **C**

```python
    ...
    return DecodedText(
        text=data.decode("latin-1"),
        encoding="latin-1",
        decided_by=ENCODING_FROM_LATIN1,
        confident=False,     # ← 关键：它必须被标记
    )
```

latin-1 的性质是"任何字节序列都是合法的"——**这既是它的价值，
也是它必须排最后的原因**：

- 价值：它保证函数总能返回一个字符串，调用方需要处理的是
  `confident=False` 这种情形，而不是异常；
- 危险：**它永不失败**，因此如果排在前面，它会把所有 UTF-8 与 GB18030 的
  中文文档都"成功"解成乱码，而那个乱码会一路通过分块、向量化与检索，
  最后以一个"模型答非所问"的形式出现在用户面前。

A 是错的（latin-1 只覆盖 256 个码位）；B 是错的（中文旧文档的兜底是
**gb18030**，它是 GBK 与 GB2312 的超集）；D 与设计无关。

顺带记住测试里踩到的那个坑：`b"\xff\xfe\xfd"` 看起来像"随机字节"，
但它**以 UTF-16-LE 的 BOM 开头**，会被第 1 步接走。
真正走投无路的样本是 `b"\x80\x80"`——`0x80` 在 utf-8 与 gb18030 里都是非法起始字节。

### 第 5 题 → **B**

三个状态的含义是**三件不同的事**：

| 状态 | 含义 | 后续动作 |
|------|------|---------|
| `ok` | 解析成功且首次出现 | 进知识库 |
| `duplicate` | 与前一份内容相同 | **数据治理**：确认是不是同一份规范的两份拷贝 |
| `error` | 不在支持范围 / 解析失败 | **工程**：去看那一份文件 |

合成一个"成功/失败"之后，运维看到"有 2 项失败"时无法判断该去**补数据**
还是该去**查错误**——而这两件事的动作完全不同。

这与 day059 把门禁结果分成三类（阻塞失败 / 告警 / 跳过）、
day060 把 `passed` 与 `consistent` 分开是同一条思路：

> **一个布尔量只能表达"能不能继续"，表达不了"我为什么继续"。**

A、C、D 都不是理由。事实上重复文件通常**不占额外空间**（它们本来就是
同一份内容的两次出现），而 D 把因果说反了：三个键恒存在是为了报告可比较，
不是为了让状态分类显得整齐。

## 第二部分：判断题

### 第 6 题 → **对**

`normalize_text` 只管四件事，**都不涉及字符层面**：

```text
\r\n / \r → \n              换行统一
去掉每行行尾空白           尾随空格
连续空行折叠到 1 个        多余空行
去掉首尾空白 + 结尾补 \n   有无结尾换行
```

它**不做** Unicode 规范化（不把全角标点换成半角、不折叠空格）。
因此：

```python
content_id(normalize_text("第一，第二")) != content_id(normalize_text("第一,第二"))
```

这是刻意的。理由是一个具体判断：**中英文混排的技术文档里，
全角逗号与半角逗号经常是内容差异而不是格式差异**——例如代码片段里的
半角逗号与正文里的全角逗号在语义上不同。把它们合并会改变检索结果，
而这类"看起来更干净"的规范化最难被发现：它不会报错，
只会让某次检索命中了一份它不该命中的文档。

代价也要说清楚：同一段文字用不同标点风格写两遍，会得到两个 `doc_id`。
**这是一个已知的取舍，不是遗漏**——把它写进 docstring 而不是留给读者去猜。

### 第 7 题 → **对**

```python
BOMS: tuple[tuple[bytes, str], ...] = (
    (b"\x00\x00\xfe\xff", "utf-32-be"),
    (b"\xff\xfe\x00\x00", "utf-32-le"),
    (b"\xef\xbb\xbf", "utf-8-sig"),
    (b"\xfe\xff", "utf-16-be"),
    (b"\xff\xfe", "utf-16-le"),
)
```

表是**顺序敏感**的，而且顺序被写进了对照表的第一条理由：

```text
1. BOM（utf-32-be / utf-32-le / utf-8-sig / utf-16-be / utf-16-le）
   有 BOM 就是明示，不需要猜；UTF-32 必须排在 UTF-16 之前
```

写反的后果：一份 UTF-32-LE 的文件以 `FF FE 00 00` 开头，如果先匹配
`FF FE`（UTF-16-LE），BOM 会被切掉 2 字节，剩下 `00 00` 加上正文一起
按 UTF-16-LE 解码 —— 结果是**每个真实字符后面跟一个 NUL**。
那种乱码看起来很像文件损坏，于是排查会从"文件是不是坏了"开始，
而真正的原因只是**我们查表的顺序**。

配套的测试直接钉住这一点：

```python
def test_utf32_bom_must_be_checked_before_utf16():
    decoded = decode_bytes(b"\xff\xfe\x00\x00" + "宽字符".encode("utf-32-le"))
    assert decoded.text == "宽字符"
    assert decoded.encoding == "utf-32-le"
```

### 第 8 题 → **错**

`docx_parts_not_read` 是本模块最重要的几个字段之一。理由是一个具体的场景：

> 有人问"为什么知识库里搜不到那份 Word 里的附表？"
> 如果答案只是"文档解析成功了"，那么排查会从"是不是没入库"开始，
> 一个个环节试过去；而元数据里如果写着
> `docx_parts_not_read = word/header*.xml, word/footer*.xml, ...`，
> 第一个要确认的问题就是"那张附表在页眉里，还是在一个嵌入的 OLE 对象里"。

**"没读到的部分"最容易被当成"文档里没有"** —— 这两件事在结果里长得一样
（都表现为"检索不到"），而它们的后续动作完全不同：

```text
文档里没有   → 无需处理（或去问内容作者）
没读到       → 要么换解析方式，要么在文档里反映这个缺口
```

这与 day059 的模型卡要写"已知限制"、day060 的部署要写 `fallback_count`
是同一条纪律：**把"我没看到"做成一个字段，而不是一个沉默。**

## 第三部分：简答题

### 第 9 题（能力边界为什么必须写下来）

#### 1. 为什么"返回一堆乱码"比"拒收"更糟

因为**乱码会一路走下去，而每一站都不会拦它**：

```text
解析       → 得到一串"看起来是文本"的字符串（实际上每个字符都是错的）
规范化     → 忠实地把这串乱码规范化（换行、空白都处理得好好的）
doc_id     → 忠实地为这串乱码算一个指纹（稳定、可复现、毫无用处）
分块       → 忠实地把乱码切成片段（每个片段都精确到 token 上限）
Embedding  → 忠实地把乱码片段编码成向量（向量本身完全正常）
向量库     → 忠实地存进去（检索得到最近邻，而它们只是"乱得像"）
检索       → 命中一段乱码，返回给生成器
生成       → 模型看着一段乱码，给出一个自信的瞎猜答案
用户       → 看到"模型答非所问"，而永远不会想到源头是编码
```

关键在最后三行：**排查要从用户反馈倒推回编码，中间隔着九天的工作量**。
而拒收的代价只是"这一份没进库"——它是**可发现、可定位、可修**的。

同类处理在别处也出现过：

| 位置 | 拒收 / 声明的对象 |
|------|-----------------|
| `decode_bytes` | 头 8 KiB 出现 NUL → 拒收（改名为 `.txt` 不会让它变成文本） |
| `extract_pdf_text` | `/Encrypt` 出现 → 拒收（而不是给乱码） |
| `DocxLoader` | 不是 ZIP、缺 `word/document.xml`、无 `w:body` → 拒收 |
| `detect_media_type` | 后缀与内容冲突 → **不拒收**，但把冲突记下来 |

注意最后一行的对比：**冲突不拒收**（内容更可信，还能继续），
**乱码拒收**（没有任何可信的东西可用）。**"能不能继续"是拒收与否的唯一判据**，
而不是"这个文件有没有问题"。

#### 2. `pdf_cid_font_detected` 三个月后回答的问题

它回答的是：**"这份 PDF 抽出来的文本为什么是空的/乱的？"**

- 如果没有这个字段：排查会从"解析器是不是坏了"开始 ——
  拿别的 PDF 试一次（发现正常），于是怀疑这份文件（打开一看明明有字），
  然后进入"是不是加密了/是不是扫描件/是不是权限"的逐项试验，
  **最后才会想到字体编码**；
- 有它：第一个动作就是看元数据：

  ```text
  pdf_cid_font_detected = true
  pdf_warnings = 检测到 Identity-H 编码（字符码 = 字形索引） | ... §9.10.2 ...
  ```

  结论立刻是"这份文件不在支持范围内，需要换一种抽取方式"，而不是
  "我们的解析器有问题"。

**这两个结论的后续动作完全不同**：前者是换工具或换输入，
后者是查代码。而这正是这一字段存在的全部价值——**它把一次排查
从"探索"变成"确认"。**

把这条边界摆在明面上还有一个副作用：它把"要不要支持 CID 字体"
变成一个**可决策的问题**（要做就得实现 CMap 解析或引入 pypdf），
而不是一个藏在失败里的隐形成本。

#### 3. 为什么同一条边界写在三个地方

三处各有各的消费面，谁也替代不了谁：

| 位置 | 谁在读 | 回答什么问题 |
|------|--------|-------------|
| 元数据字段 `pdf_cid_font_detected` | 批量入库的后续流程、排查 | **这一份**文件是不是这种情况 |
| 告警文本（含 `§9.10.2`） | 人（日志、报告） | 为什么抽不到，**依据是什么** |
| `pdf_boundaries()["not_supported"]` | 开工前读文档的人、`/documents/loaders` 端点 | 这个格式**整体**的边界在哪里 |

三处**会不会不一致**？会 —— 如果它们各自独立维护的话。
因此有一条测试同时断言三者：

```python
def test_cid_fonts_raise_a_loud_warning():
    data = build_pdf(["x"], extra=b"/Type0 /Identity-H /ToUnicode")
    document = _load(data)
    assert document.metadata["pdf_cid_font_detected"] == "true"
    assert "§9.10.2" in document.metadata["pdf_warnings"]
    assert document.metadata["encoding_confident"] == "false"
    assert any("Identity-H" in item for item in pdf_boundaries()["not_supported"])
```

更根本的保证是**字段名与告警都来自同一份常量**：

```python
CID_MARKERS: tuple[tuple[bytes, str], ...] = (
    (b"/Identity-H", "Identity-H 编码（字符码 = 字形索引）"),
    (b"/Type0", "Type0 复合字体"),
    (b"/ToUnicode", "内嵌 ToUnicode CMap（本模块不解析它）"),
)
```

检测与描述读的是**同一个元组的同一项**，因此"检测到了 A 却描述了 B"这类
漂移不可能发生。这与 day059 的门禁表 / 阶段表 / CI 摘要从代码常量现场读出、
day060 的价格表只有一个出处是同一个做法：

> **同一份事实在仓库里只该有一处权威**，其余都是渲染。

#### 4. "我们自己的 bug"的例子

`ingest_bytes` 的 `except` **只捕 `DocumentError`**：

```python
            try:
                document = self.registry.load_bytes(data, source=source, media_type="")
            except DocumentError as exc:
                # 只有"我们认识的失败"被记进报告；其余异常向上抛
                entries.append(IngestEntry(source=source, error=str(exc)))
                continue
```

于是以下两类事件被**分开处理**：

| 事件 | 类型 | 处理 |
|------|------|------|
| 一份 `.txt` 其实是二进制 | `UnsupportedDocument`（`DocumentError` 的子类） | 记进报告，整批继续 |
| 一个文件是加密 PDF | `UnsupportedDocument` | 记进报告，整批继续 |
| `render_table` 里一个 `IndexError`（我们写错了） | `IndexError` | **向上抛出**，整批失败 |

如果第二类也被吞掉，后果是具体的：

> 报告看起来"只是一份文件失败了"，于是没有人去看那个 `IndexError`。
> 而它其实会影响**所有含表格的文档**——只是恰好这一次的输入让那个分支跑了。

这与 day059 把 `blocked`（预期内的结论）与 `failed`（有东西坏了）分开、
day060 把"未知机型键"（输入错误）与"策略关闭检查"（有意为之）分开，
是同一条纪律的第三次出现：

> **"做不到"要被记成结论，"出错了"要响亮。**

判断标准也很清楚：**这个异常是不是我预期过的？**
预期过的（文件格式不支持、编码定不下来）→ 记结论；
没预期过的（索引越界、类型错误）→ 让它冒出去。

    # 0x80 在 utf-8 与 gb18030 里都是非法起始字节 → 只能回退 latin-1，且标记不可信
    fallback = decode_bytes(b"\x80\x80")
    assert fallback.encoding == "latin-1"
    assert fallback.confident is False
    print("2. 类型识别与编码链          OK")

def build_docx_sample() -> bytes:
    document = (
        '<?xml version="1.0" encoding="UTF-8" standalone="yes"?>'
        f'<w:document xmlns:w="{WORDML}"><w:body>'
        '<w:p><w:pPr><w:pStyle w:val="Heading1"/></w:pPr><w:r><w:t>标题</w:t></w:r></w:p>'

    buffer = io.BytesIO()

    return buffer.getvalue()


def build_raw_pdf() -> bytes:
    """手工造一份**未压缩**的最小 PDF（内容流里只有一行 Hello）."""
    content = b"BT /F1 12 Tf 72 720 Td (Hello) Tj ET"
    objects = [
        b"<< /Type /Catalog /Pages 2 0 R >>",
        b"<< /Type /Pages /Kids [3 0 R] /Count 1 >>",
        b"<< /Type /Page /Parent 2 0 R /Contents 4 0 R >>",
        b"<< /Length "
        + str(len(content)).encode()
        + b" >>\nstream\n"
        + content
        + b"\nendstream",
    ]
    out = bytearray(b"%PDF-1.4\n")
    for index, body in enumerate(objects, start=1):
        out += str(index).encode() + b" 0 obj\n" + body + b"\nendobj\n"
    out += b"trailer\n<< /Root 1 0 R >>\n%%EOF\n"
    return bytes(out)

#### 为什么"顺序反转后 `doc_id` 集合不变"值得单独断言

它保护的是一条**容易被"优化"掉的契约**：

```text
去重的结果与遍历顺序**无关**（有哪些内容），
但"谁被留下"与顺序**有关**（哪一份是原件）。
```

这两件事必须分开看，而它对应未来的三类改动：

| 未来的改动 | 没有这条断言时会发生什么 | 有它时会发生什么 |
|-----------|----------------------|-----------------|
| 换成并发遍历（多线程 / `asyncio`） | "先看到的留下"变成"谁先跑完谁留下"，而**结果每次不同** | `doc_id` 集合仍不变 → 断言仍绿，但重复项归属的测试会红，提示需要显式排序 |
| 换成按文件大小/修改时间排序 | 内容集合可能无意中变化（例如过滤规则一起被改） | 集合断言把"内容变了"与"归属变了"分开暴露 |
| 给 `ingest_bytes` 加缓存 | 缓存键若含顺序，同内容不同顺序会得到不同结果 | 缓存实现被迫保持内容等价 |

它保护的核心是 day057/058/060 反复出现的那条纪律：

> **同一份输入要在任何机器上得到同一份输出。**

注意这条断言**只断言集合**，而不去断言"重复项归属"——
后者本来就依赖于顺序，是最合适的显式契约。**把断言写在该断言的地方**，
才能让失败信息直接指向出问题的契约；写成"整份报告逐字节相等"
只会在任何一处顺序变化时给出一条无用的红。
