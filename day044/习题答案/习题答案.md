## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：银行卡号是 16~19 位纯数字，与订单号、流水号、时间戳（如 `2026091215300012`）同形。如果像手机号那样"正则匹配就脱敏"，任何一段 16 位数字都会被误杀成银行卡。所以银行卡号走**两步走**：正则取候选（`BANK_CARD_PATTERN`）→ 逐候选 Luhn 校验（`_luhn_valid`）→ 通过才替换。Luhn 是"确认这是卡号"的数学依据。A 错——不是正则写不出来，而是正则只能回答"格式对不对"、回答不了"内容真不真"；C 错——银行卡号是高危 PII；D 错——Luhn 是纯整数运算，标准库 `re` + 手写十几行即可。

### 第 2 题

**答案：B**

**解析**：`25[0-5]|2[0-4]\d|1\d\d|[1-9]?\d` 四段交替恰好枚举了 0~255 的所有取值（250~255 / 200~249 / 100~199 / 0~99）。把"每段上界 255"编码进正则，`999.999.999.999` 因"没有一段能匹配 999"而整体失配。这是把"格式精确约束"而不是"宽松的 `\d{1,3}`"写进规则，属于误报防护。A、C、D 都不对——D 恰恰是我们要挡在门外的。

### 第 3 题

**答案：B**

**解析**：审核结果（脱敏了哪些 PII、命中了哪些敏感词）要随响应体返回给客户端，这需要路由函数把 `ModerationInfo` 塞进响应模型。中间件的 `dispatch` 只能拿到请求/响应对象、无法读取响应体、也无法往响应体加字段，所以只能"拦"不能"改语义"。A、C、D 均为无据干扰项。

### 第 4 题

**答案：B**

**解析**：`AccessLogStore` 记的是 HTTP 接入层的请求（`method`/`path`/`status_code`/`duration_ms`/`client_ip`），`AuditLogger` 记的是 Agent 内部每次工具调用（`tool_name`/`arguments`/`result`/`status`）。两者一外一内，共同构成完整审计链路。A 错——不是重写，是分工；C 把两者记反了；D 错——两者没有继承关系。

## 第二部分：判断题

### 第 5 题

**答案：对**

**解析**：Luhn 把最后一位替换成任意数字（0~9 共 10 种），只有 1/10 的概率仍然通过"总和能被 10 整除"的校验，所以能筛掉约 90% 的随机长数字串。这正是 `test_pii.py` 用 `4111111111111111`（有效）与 `4111111111111112`（无效）相邻两个数字验证的边界。

### 第 6 题

**答案：错**

**解析**：`moderation` 字段**始终返回**（即使回复干净也返回 `is_safe=True`、空列表）。原因是**契约稳定性**——字段永远存在，客户端不用写"先判断有没有 moderation 字段"的分支。省那点响应体积，换来的是契约的确定性和客户端代码的简单。

### 第 7 题

**答案：对**

**解析**：`/agent/run` 的 `answer` 过审核脱敏，但 `tool_calls` 保留原始参数与结果。因为工具调用轨迹是**审计证据**，要求"原文是什么就是什么"，脱敏会破坏可追溯性。需要对外展示时再由消费方决定如何脱敏。这是"审核"（关心输出安全）与"审计"（关心证据完整）两种诉求的边界。

## 第三部分：简答题

### 第 8 题

**参考答案要点**：

- **输入侧**：守"用户想害系统"这道门——拦截恶意注入（"忽略之前指令""泄露系统提示词"），在请求**进入模型之前**把关。对应 `PromptInjectionDetector`。
- **输出侧**：守"系统无意泄露"这道门——拦截模型复述训练数据里的 PII（手机号/身份证/银行卡号），在回复**离开系统之前**把关。对应 `ContentModerator`。
- **不能互相替代**：输入侧防的是"有人主动攻击"，输出侧防的是"模型被动说漏嘴"。两者的威胁模型、发生位置、检测手段都不同——注入检测看的是"指令模式"，内容审核看的是"敏感词与 PII 格式"。只做输入侧，模型复述一条手机号照样泄露；只做输出侧，恶意注入照样能套出系统提示词。

### 第 9 题

**参考答案要点**：

- **内存记录**：让测试无需碰文件系统就能断言——测试注入内存 `AccessLogStore` 后，用 `query()` 直接回放已记录请求，`test_middleware.py` 全程不建临时文件。
- **可选 JSONL 落盘**：给了 `log_path` 才追加写 JSONL，满足生产的长期留存与离线分析需求（与 `AuditLogger` 的落盘策略一致）。
- **两者的结合点**：`record()` 同时写内存和（可选的）文件，一条代码路径同时服务"可测试"与"可持久化"两个诉求。这正是本项目一贯的"依赖注入让测试可换血"思想在存储层上的体现——测试注入内存版，生产注入文件路径版。

## 第四部分：编程题

### 第 10 题

**参考答案**（可直接追加到 `tests/test_pii.py`）：

```python
class TestBankCardMasking:
    def test_luhn_invalid_long_number_preserved(self):
        """Luhn 不过的长数字串（如订单号）不应被误脱敏."""
        order = "订单号 4111111111111112 请核对"
        text, hits = _mask_bank_cards(order)
        assert hits is False
        assert "4111111111111112" in text  # 原样保留
        assert "***银行卡号***" not in text
```

**关键点说明**：

1. **为什么用 `4111111111111112`（Luhn 无效）而不是 `4111111111111111`（Luhn 有效）**：`_mask_bank_cards` 对每个正则候选先做 Luhn 校验，只有校验通过才替换。`...111` 是 Luhn 有效的经典 Visa 测试卡号，`...112` 改最后一位破坏了校验和（校验和无法被 10 整除）。用 `...112` 才能构造出"格式像卡号、但校验不过"的订单号场景。
2. **换成 `...111` 后断言怎么变**：`_mask_bank_cards("订单号 4111111111111111 请核对")` 会返回 `hits is True`、文本中 `4111111111111111` 被替换成 `***银行卡号***`——因为它是 Luhn 有效的真卡号。此时断言应改为 `assert hits is True` 且 `assert "4111111111111111" not in text`。
3. **这条测试守的是什么**：误报防护——审核系统"该脱的脱、不该脱的绝不脱"。Luhn 用"最后一位之差"把卡号与订单号区分开，这正是"校验型 PII"相对"纯正则 PII"的价值所在。

**验证**：运行 `python -m pytest tests/test_pii.py -q`，新增用例通过（day044 快照全量 753 个测试、覆盖率 94.82% 全绿）。
