## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：B 说反了——成本恰恰是**唯一不需要主观判断**的指标，不需要 LLM-as-judge 打分。A、C、D 正是教程第一章的三层论述：token 数是协议自带的客观事实、单价是厂商公开定价，二者相乘即费用（A）；它不需要裁判与标注集，误差只来自价格表是否及时更新（C）；"会看账单"的系统比"只会跑"的系统多一双眼睛（D）。需要 LLM-as-judge 的是答案质量（day026/027），那是另一类指标。

### 第 2 题

**答案：B**

**解析**：成本结构由「模型 × 接口」共同决定——同一个模型走 chat（输入输出都计费）与走 embedding（只计输入）的账单完全不同；只看模型会漏掉"这个模型在 embedding 上烧钱"，只看接口会漏掉"这个接口用的是最贵的模型"。A 是把实现细节当成了原因；C 是无稽之谈；D 逻辑不通——按接口聚合本来就不会"重复统计"同一模型，问题在于它无法区分同接口下的不同模型。

### 第 3 题

**答案：A**

**解析**：精确匹配是 `strip` 后字典查找，O(1)；语义匹配要 embedding 编码 + 对全部 n 条条目做余弦，O(n) 次点积。先廉价后昂贵是自然的工程顺序。B 错——语义匹配不更"准确"，它更"宽松"，可能张冠李戴；C 错——顺序有意义，精确命中就不该再付语义匹配的代价；D 错——语义匹配纯本地点积，无网络请求。

### 第 4 题

**答案：A**

**解析**：char-ngram 的相似度来自**字面重叠**。"机器学习是什么/什么是机器学习"共享大量字符 n-gram，相似度约 0.55；而"什么是 RAG / RAG 是什么"里的空格把"RAG"从连续字符流里切开，n-gram 重叠锐减，相似度掉到 0.36。这暴露了 char-ngram 对中英混排文本的局限——它统计的是字符片段，不是语义。B 错——char-ngram 不做任何"理解"；C 错——差异是确定性的字面重叠差异，不是哈希碰撞；D 错——与编码长度无关。

## 第二部分：判断题

### 第 5 题

**答案：对**

**解析**：`report()` 只在原有字段之外**新增**了 `top_paths`，未改动任何既有字段名与语义。已有测试断言 `total_calls`、`total_tokens`、`by_model`、`by_endpoint` 等键，新增键不影响它们——这正是"向后兼容增强"的含义。day043 快照里 day032 的 `TestCostTracker` 全部原样通过。

### 第 6 题

**答案：错**

**解析**：`CachedLLM` **没有**覆写 `stream()`。它只覆写了 `chat()`，而 `BaseLLM.stream` 的默认实现是 `yield self.chat(...)`——因此继承的 `stream` 会自动调用被覆写的 `chat`，流式路径天然走缓存，与非流式行为一致。这正是"包装器只改一个入口、协议层自动受益"的设计收益，也是教程第五章强调的继承收益。

### 第 7 题

**答案：错**

**解析**：价值排序恰恰相反——**正确 > 省钱**。阈值过低会让无关查询命中缓存，出现"问晚饭吃什么却答机器学习"的正确性事故；阈值过高只是漏命中、多花一次钱。错命中的代价（污染答案质量、诱导模型胡说）与漏命中的代价（多一次 API 调用）完全不对等，因此宁可漏命中、不可错命中。这与 day041 `min_score` 过滤"宁缺毋滥"是同一套价值观。

## 第三部分：简答题

### 第 8 题

**参考答案要点**：

| 维度 | 精确缓存 | 语义缓存 |
|------|----------|----------|
| 匹配机制 | `strip` 后字符串相等（字典键） | 余弦最近邻达到阈值 |
| 代价 | O(1) 字典查找 | O(n) 次点积（n 为条目数） |
| 失效条件 | 字面一变即失效 | 相似度低于阈值才失效 |

- **为什么引入语义匹配**：真实流量里大量重复是"同义改写"而非"字面重复"——用户把"什么是 RAG"换成"RAG 是什么"，精确缓存就放走了一次本可复用的调用。语义匹配借助 day041 的 embedding，让"意思相近"也能命中，把缓存的省钱潜力从"字面重复"扩展到"语义重复"。
- **顺序**：精确匹配优先，因为它更廉价、更无歧义；语义匹配兜底，只在精确未命中时付出 O(n) 的代价。

### 第 9 题

**参考答案要点**：

| 维度 | 语义缓存（day043） | 长期记忆（day009） |
|------|--------------------|--------------------|
| 复用范围 | 会话内/近期的短期复用 | 跨会话的长期复用 |
| 失效策略 | LRU 按"最近最少使用"淘汰，容量上限 128 | 知识持续积累，需显式删除 |
| 存储内容 | 「查询 → 回复」成对缓存 | 事实/知识/历史对话的向量化条目 |

- **机制同源**：两者都是"向量化 + 相似度召回"——缓存的"够像"与记忆的"相关"用的是同一把 `cosine_similarity` 尺子。
- **共享基础设施**：day064 接入 ChromaDB/FAISS 时，长期记忆需要一个持久化向量索引，语义缓存的"查询向量 → 命中判断"也可以复用同一套索引与 `EmbeddingProvider` 抽象——缓存查得快（近邻检索），记忆存得久（持久化），底层索引统一，上层语义各自保留。

## 第四部分：编程题

### 第 10 题

**参考答案**（可直接追加到 `tests/test_cache.py`）：

```python
class TestLruOrdering:
    def test_lru_evicts_least_recently_used(self):
        cache = SemanticCache(CharNgramEmbedding(), max_size=3)
        cache.put("a", "ra")
        cache.put("b", "rb")
        cache.put("c", "rc")
        assert cache.get("a") == "ra"  # 访问 a，刷新其使用时间到队尾

        cache.put("d", "rd")  # 容量 4 > 3，淘汰最久未用的 b

        assert cache.size == 3
        assert cache.get("a") == "ra"   # a 因访问被保留
        assert cache.get("b") is None   # b 被淘汰
        assert cache.get("c") == "rc"
        assert cache.get("d") == "rd"
        assert cache.evictions == 1
```

**设计问答**：`SemanticCache` 用 `OrderedDict` 作底层存储，因为它**同时提供"有序"与"O(1) 键查找"**两个性质——这正是 LRU 需要的：插入顺序就是使用顺序，队头是最久未用的、队尾是最近使用的。`_touch(key)`（把 key 移到队尾）是 `pop` + 重新赋值，均摊 O(1)；淘汰 `popitem(last=False)`（弹出队头）也是 O(1)。若用普通 `dict`，Python 3.7+ 虽也保序，但缺少 `popitem(last=False)` 这类"从头部弹出"的便捷接口；若用 `list`，精确匹配就得 O(n) 线性查找。`OrderedDict` 让"精确匹配 O(1) + 淘汰 O(1)"同时成立。
