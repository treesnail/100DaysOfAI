# day023 习题答案：MCP 协议测试与文档

## 一、选择题

**1. 答案：B**

解析：内存传输测试（`create_connected_server_and_client_session`）只替换了一样东西——传输介质，从"进程间管道"换成"内存流"。其余全是真的：真实的 initialize 握手（A 错）、真实的 JSON-RPC 序列化、真实的 Server 路由，三类能力（Tools/Resources/Prompts）全能测（C 错）。D 错在 LLM 与 MCP 传输测试无关，MockLLM 是 M1 阶段 Agent 测试的工具。这正是"每一层引入一样真实的东西"的分层原则：中层付出不起进程的便宜代价，换来协议栈行为的高密度验证。

**2. 答案：B**

解析：stdout 污染是**传输通道层**的失效——`print()` 把非 JSON 字节混入 stdio 管道，Client 的帧解析器收到垃圾直接报协议错误。内存传输测试的"管道"是纯内存流对象，不经过进程的 stdout，这个 bug 在它的世界里不存在。A、C、D 都是行为层或契约层问题，内存传输测试甚至协议模型单测就能发现。这个题目对应教程第一章的事故场景，也是"为什么还要保留最贵的顶层测试"的标准答案。

**3. 答案：B**

解析：`sys.executable` 是当前 Python 解释器的绝对路径。测试进程跑在 `.venv` 里，`sys.executable` 就指向 `.venv/Scripts/python.exe`，子进程因此继承完全相同的解释器与全部依赖。如果写死 `"python"`，子进程会走 PATH 查找，可能命中系统 Python——没有装 mcp 包，测试报 `ModuleNotFoundError`，且这种失败在别的机器上可能又不复现。A、C 是无关表象；D 错误，解释器路径与权限无关。这是"环境一致性"问题的标准解法：**不显式选择解释器的子进程，都是潜在的依赖漂移源**。

## 二、判断题

**4. 答案：错误（×）**

解析："哑对象不需要测"是测试领域最常见的误解之一，在协议场景下尤其危险。三个反理由：

1. **模型即契约**：`jsonrpc: Literal["2.0"]` 不是数据，是"本系统讲 JSON-RPC 2.0"的可执行声明。没有测试守护，一次重构把默认值改成 `"1.0"` 都不会有人发现，直到线上对端报错。
2. **序列化往返需要验证**：协议消息的宿命是被序列化、传输、再反序列化。`model_dump() → model_validate()` 的 round-trip 测试验证信息无损——这不是"逻辑"，是协议对象的核心职责。
3. **成本极低、收益确定**：纯内存毫秒级，10 个用例零点几秒跑完，却永久锁死了消息结构的回归。

测试金字塔的底层之所以是"大量"，正因为这一层便宜到没有理由不写。

**5. 答案：错误（×）**

解析：自动生成 ≠ 自动提交。把文档重写挂到 Server 启动钩子里有三个具体问题：

1. **污染版本历史**：任何一次本地调试启动都会重写文档，工作区凭空多出 diff，开发者被迫频繁处理无关变更。
2. **职责错位**：Server 的职责是"提供能力"，不是"维护自己的文档"。运行时副作用让启动变慢、变脆弱（文档目录不可写时 Server 要不要拒绝启动？）。
3. **失控**：文档变更应该伴随明确的提交意图，由人决定何时纳入版本。

正确做法是"半自动"：生成自动、提交人工把关；若要强约束，在 CI 里加"运行脚本并 diff，不一致则构建失败"的校验，而不是在运行时偷偷改写。

## 三、问答题

**6. 参考答案：**

两者的本质区别在于**失败发生在协议的哪一层**：

- **工具级失败（`isError=False` + 错误文本）**：协议层面一切正常——请求合法、路由成功、工具函数被执行完毕并返回了结果，只是结果的*内容*是"计算失败"。失败属于业务语义，属于"工具正常履职，但答案是失败"。
- **协议级错误（异常）**：请求本身无法完成——`research://knowledge/not-exist` 指向的资源不存在，Server 无法产出任何有意义的结果，只能以 JSON-RPC error 响应告知"这次调用失败了"。

calculator 选择前者的原因：`CalculatorTool.execute` 从 day003 起的设计就是"容错求值器"——非法表达式是**预期的用户输入场景**（LLM 可能生成错误表达式），调用方（Agent 循环）需要把这个失败当普通 Observation 消化、继续推理，而不是当异常中断。knowledge 选择后者的原因：读取不存在的资源不是"答案为空的正常结果"，而是**URI 寻址失败**，请求语义上就不成立；让 Client 收到明确异常，调用方才知道"这个 doc_id 是错的"，而不是误以为"这篇文档的内容恰好是一段错误文本"。

一句话总结：**能被调用方当普通结果继续处理的失败，用返回值；请求本身不成立的失败，用协议错误。** 混用两者（比如让不存在资源返回"不存在"文本）会让调用方无法区分"内容"与"事故"。

**7. 参考答案：**

解决的问题是**依赖隔离与演进自由**：

- **SDK 升级影响面收敛**：官方 `mcp` 包在快速演进，能力对象的字段名、类型（如 `uriTemplate` 从 str 变 AnyUrl）都可能变。如果上层业务直接依赖 SDK 类型，一次 SDK 升级要改动所有使用点；有了防腐层，只需改 `discover_capabilities()` 一处适配代码。
- **类型稳定性即 API 稳定性**：`ToolDescriptor` 等项目自有类型构成对内稳定契约，测试、能力文档脚本、未来的 Agent 工具接入层都建立在它之上，不受外部库版本颠簸影响。
- **语义裁剪**：SDK 类型携带很多我们用不到的字段（icons、annotations 等），自有描述符只保留项目关心的字段，降低认知负担。

代价也真实存在：

- **转换代码要维护**：`discover_capabilities()` 本身就是适配成本，字段映射写错会引入 bug（所以集成测试断言了描述符内容）。
- **信息有损**：SDK 新增有用字段时，描述符不会自动获得，需要显式扩展。
- **多一层抽象的心智负担**：新人要理解"为什么有两套类型"。

取舍逻辑：MCP SDK 是**演进快的外部依赖**，项目能力面是**需要长期稳定的内部契约**——两者变化速率不同，中间放一层防腐层是标准解法（与 day005 用 `BaseLLM` 隔离 openai SDK 是同一思想）。

**8. 参考答案：**

理性选择的经济学本质是**验证成本与失败定位成本的双重优化**：

- **运行成本**：三层耗时比约 1:5:30。假设要为 calculator 穷举 20 个边界表达式——放中层约 10 秒，放顶层约 60 秒。中层把"协议栈真实性"的价格打到了接近单元测试的水平，穷举行为细节几乎免费。
- **失败定位成本**：顶层测试挂了，可疑范围是"整个进程间链路"（序列化？管道？子进程？业务逻辑？）；中层测试挂了，可疑范围收敛到"协议行为"；底层挂了，精确到某个字段。同一类断言放的层越低，红灯亮起时的排查半径越小。
- **稳定性**：顶层涉及操作系统进程管理，天然有偶发失败（端口、句柄、时序）。把大量断言堆在顶层等于把测试套件的信噪比押在最不稳定的基础上——结果是开发者开始无视红灯（"又是环境问题"），测试体系信用破产。

反过来做的后果：一是慢，每次提交等几十秒甚至几分钟，开发者开始跳过测试；二是脆，大量用例因环境问题随机失败；三是定位难，业务逻辑错误和进程事故混在同一种失败信号里。金字塔倒置（冰淇淋蛋筒反模式）是测试体系崩溃的经典路径。

但注意另一面：顶层不能为零。stdout 污染、进程生命周期这类失效点只有顶层能守。正确比例是：**行为穷举在中层，顶层只保留"链路是通的"的抽查**（本日 4 个用例）。

## 四、编程题

**9. 参考答案：**

在 `smart_research_agent/mcp_server/server.py` 的 `app` 定义之后追加：

```python
@app.tool(description="统计文本的字符数与词数")
def word_count(text: str) -> str:
    """返回文本的字符数与按空白分隔的词数."""
    return f"字符数: {len(text)}, 词数: {len(text.split())}"
```

在 `tests/test_mcp_server_unit.py` 追加测试类：

```python
class TestWordCountTool:
    async def test_word_count_normal_text(self):
        async with _connect() as session:
            result = await session.call_tool("word_count", {"text": "hello mcp world"})
        assert result.isError is False
        assert result.content[0].text == "字符数: 15, 词数: 3"

    async def test_word_count_empty_string(self):
        async with _connect() as session:
            result = await session.call_tool("word_count", {"text": ""})
        assert result.content[0].text == "字符数: 0, 词数: 0"
```

重新生成文档：

```bash
python scripts/dump_capabilities.py
```

生成的 `docs/mcp_capabilities.md` 的 Tools 表格会自动多出 `word_count` 一行——这正是"文档跑出来"的价值：新工具注册后，能力文档零手工成本同步。

评分要点：工具函数实现（3 分）；两个内存会话测试覆盖正常与空输入（4 分）；能力文档确实被重新生成且包含新工具（3 分）。注意空字符串测试的意义：`"".split()` 返回 `[]` 而非 `[""]`，词数为 0——边界行为被测试固定，避免未来有人"优化"实现时改出 `[""]` 的回归。

**10. 参考答案：**

```python
class TestCapabilityInvariants:
    async def test_capability_invariants_over_stdio(self):
        async with McpClient.stdio() as client:
            for tool in client.tools:
                assert tool.input_schema.get("type") == "object"
                assert "properties" in tool.input_schema

            for resource in client.resources:
                assert resource.uri.startswith("research://")

            for prompt in client.prompts:
                assert prompt.arguments is not None
```

互补价值在于**断言对象从"点"变成"面"**：

- 单个能力测试（如 `test_call_tool_over_stdio`）验证"**这一个**能力的行为正确"，它对新注册的能力完全无感——明天有人加一个 schema 写坏的 Tool，所有单能力测试照样全绿。
- 不变式测试遍历能力面整体，断言"**所有**能力都满足结构性约束"。它不关心每个能力具体算什么，只守护"能力面永远处于可消费状态"（schema 合法、URI 规范、参数声明完整）。

两类测试的失败信号语义也不同：单能力测试红 = "某个能力坏了"；不变式测试红 = "能力面的整体契约被破坏了"，往往指向注册/声明环节的系统性问题（比如改了一个公共的 schema 生成逻辑）。理想测试套件两者兼备：点状测试保证深度，面状不变式保证广度。这与协议模型单测的 round-trip 思想一脉相承——**把"永远应该为真"的性质写成代码，让回归无处藏身**。

评分要点：三类不变式断言正确（6 分）；互补价值的论述能说出"点 vs 面"及失败信号语义差异（4 分）。
