## 第一章：LLM 是无状态的 —— "记忆"其实是一个错觉

### 1.1 一个让人意外的实验

打开任何一个大模型聊天产品，连续发两条消息：

```text
你：我叫小明。
AI：你好小明，很高兴认识你！
你：我叫什么名字？
AI：你叫小明。
```

看起来 AI"记住"了你的名字。但真相是：**第二次请求里，服务端把第一条问答也一起发给了模型。** 模型本身什么都没记住。

我们用项目里的 `MockLLM` 模拟一下 API 视角看到的东西：

```python
# 第二次请求时，发送给模型的 messages 实际上是：
[
    {"role": "user", "content": "我叫小明。"},
    {"role": "assistant", "content": "你好小明，很高兴认识你！"},
    {"role": "user", "content": "我叫什么名字？"},
]
```

模型看到的不是"第二次提问"，而是一份**完整的对话记录**。它从记录里"读"出你叫小明，然后回答。

### 1.2 无状态（Stateless）是设计选择，不是缺陷

为什么 LLM 服务要设计成无状态的？因为无状态是分布式系统的黄金性质：

| 性质 | 说明 |
|------|------|
| **可水平扩展** | 任何一台服务器都能处理任何请求，不需要"找到存着你状态的那台机器" |
| **容错简单** | 服务器宕机重启后不需要恢复会话状态 |
| **负载均衡自由** | 请求可以路由到任意空闲节点 |

代价是：**状态管理的责任被转移给了调用方（客户端/应用层）**。你（应用开发者）必须在每次请求时，把"模型需要知道的全部背景"打包进 messages 里。

```
        你以为的聊天                    API 实际发生的
┌──────────────────┐          ┌──────────────────────────────┐
│ 你 ──► AI         │          │ 请求1: [msg1]          ──► LLM│
│   "记得吗？"      │          │ 请求2: [msg1, r1, msg2] ──► LLM│
│ AI "当然记得"     │          │ 请求3: [msg1, r1, msg2, r2,   │
└──────────────────┘          │         msg3]           ──► LLM│
                              └──────────────────────────────┘
        记忆是连续的                    每次请求都是全量重放
```

> 思考题：既然每次都要重放全部历史，为什么聊天产品不直接把整份聊天记录永久保存、每次全发？——因为**上下文窗口是有限的，而且按 token 计费**。这正是本章后面截断策略存在的原因。

### 1.3 "记忆"的工程定义

所以我们今天实现的"记忆"，准确说不是模型的记忆，而是：

> **应用层维护的消息历史缓冲区，负责在每轮请求前组装出一份"恰到好处"的上下文。**

"恰到好处"意味着三件事：

1. **完整性**：包含回答当前问题所需的关键历史（如 system 指令、用户刚提供的信息）。
2. **有界性**：不超出模型的上下文窗口，也不让 token 成本失控。
3. **隔离性**：张三的对话历史绝不能出现在李四的请求里。

这三个要求分别对应今天的三节：数据结构（完整性）、截断策略（有界性）、会话管理（隔离性）。

### 1.4 上下文窗口：记忆的天花板

为什么"有界性"这么重要？因为每个模型都有一个硬性物理限制——**上下文窗口（Context Window）**，即单次请求能处理的 token 总量上限：

| 模型代际 | 典型窗口 | 约合中文内容 |
|----------|----------|--------------|
| 早期 GPT-3 | 4k tokens | 约 2000~3000 汉字 |
| GPT-4 代际 | 8k~128k tokens | 数千到数万汉字 |
| 新一代长上下文 | 200k~1M tokens | 一本书的量级 |

窗口再大，也有两个绕不过去的现实：

1. **窗口是"输入 + 输出"共享的**。128k 窗口如果塞了 120k 历史，只剩 8k 给模型作答。历史越满，回答空间越小。
2. **成本随输入线性增长**。API 按 token 计费，每轮重放 100 条历史消息，意味着每一轮都在为全部历史重新付费。一个聊 50 轮的会话，最后几轮的单次调用成本是第一轮的几十倍。

还有一个更隐蔽的问题——**"中间遗忘"（Lost in the Middle）**：研究表明，模型对上下文开头和结尾的内容利用率高，对埋在中间的长篇内容利用率显著下降。也就是说，无脑塞满窗口不但贵，效果反而可能变差。**更多历史 ≠ 更好回答**，精挑细选的历史才是。

这三条共同决定了今天的工程目标：**主动管理历史的长度与构成，而不是被动地把一切塞给模型。**

```text
无管理的记忆                     有管理的记忆（今天实现）
┌─────────────────────┐        ┌─────────────────────┐
│ 历史无限增长          │        │ 长度封顶 max_messages │
│ 成本逐轮膨胀          │   →    │ system 永远保留       │
│ 最终撞上窗口上限报错   │        │ 最老对话 FIFO 淘汰    │
│ 中间信息被模型忽视    │        │ 上下文始终"新鲜且完整" │
└─────────────────────┘        └─────────────────────┘
```

## 第二章：短期记忆的数据结构设计

### 2.1 为什么是 list，而不是别的？

短期记忆的核心操作只有三个：**追加一条消息、取出全部消息、超长时丢弃最老的消息**。

对比一下候选数据结构：

| 结构 | 追加 | 保序 | 丢弃最老 | 结论 |
|------|------|------|----------|------|
| `list` | O(1) append | 天然有序 | 切片 `[-k:]` | ✅ 最合适 |
| `deque(maxlen=n)` | O(1) | 有序 | 自动丢弃 | 可用，但无法"保住 system 消息" |
| `dict` | O(1) | 3.7+ 有序 | 麻烦 | 消息没有天然 key，不合适 |
| `set` | O(1) | ❌ 无序 | — | 直接排除，顺序即语义 |

对话顺序就是语义的一部分——把问答对调序，模型会完全误解上下文。`deque(maxlen=n)` 看似完美（自动丢最老），但它一刀切：连 system 消息也会被挤掉，而 system 消息是我们**永远不想丢**的。所以选择 `list` + 自己实现截断，多写几行代码换来策略的完全可控。

### 2.2 为什么 system 消息必须特殊保留

回顾 day006 的 ReAct Agent，system 消息里装着 Agent 的"人设与规则"：

```python
SYSTEM_PROMPT = """你是一个使用 ReAct 范式解决问题的智能助手。
严格按照以下格式交替输出：
Thought: ...
Action: ...
可用工具：
{tools}
"""
```

system 消息和其他消息的地位不对等：

- **user/assistant 消息**：对话内容，时间越久价值越低，可以被淘汰。
- **system 消息**：行为契约，一旦丢失，模型立刻"忘记格式要求、忘记可用工具、忘记角色设定"，后续输出全面崩坏。

类比：开会时，前几分钟的闲聊可以忘，但**会议规则**不能忘。所以截断策略的第一铁律是：**system 消息钉在头部，永不淘汰。**

### 2.3 max_messages 的权衡：记忆长度 vs 成本 vs 遗忘

`max_messages` 是今天最重要的一个参数。设大了和设小了各有代价：

```
max_messages 小 ←──────────────→ max_messages 大

  token 成本低                    token 成本高（每条消息都计费）
  响应延迟低                      上下文处理慢
  容易"失忆"：                    记忆长：早期信息仍可被引用
  用户三分钟前说的话已丢失        
  超出窗口风险低                  可能撞上下文窗口上限，API 报错
```

具体怎么选？几个参考视角：

1. **按任务类型**：ReAct 单任务循环，一轮 Thought/Action/Observation 占 2~3 条消息，`max_steps=10` 最多约 20~30 条。闲聊型对话可以更短。
2. **按 token 反推**：假设平均每条约 200 token，窗口 8k token 的模型，扣掉 system 与输出预留，安全上限约 25~30 条。
3. **工程默认值**：我们取 `max_messages=20`，覆盖一次完整 ReAct 任务的典型长度，留有余量。

> 思考题：为什么不用"最大 token 数"而"最大消息条数"做截断标准？  
> 答：条数是确定性的、测试友好的、实现简单的。token 数需要调用 tokenizer（依赖具体模型、还要额外计算开销），属于更精细的优化——day009 之后你会看到更高级的上下文管理手段。先把简单正确的版本做扎实。

### 2.4 设计定型

综合以上，短期记忆的规格：

```text
ShortTermMemory
├── max_messages: int          # 容量上限（≥2，构造时校验）
├── add(message)               # 追加 → 立即检查截断
├── get_all() -> list[Message] # 返回副本（防止外部篡改内部状态）
├── clear()                    # 清空（开启新话题时用）
└── _truncate()                # 私有：保留 system + FIFO 丢弃最老的其余消息
```

两个细节值得强调：

- **`get_all()` 返回 `list(self._messages)` 副本而不是本体**：否则调用方拿到引用后随手 `append`，就绕过了截断逻辑，封装形同虚设。这是防御性拷贝（Defensive Copy）。
- **截断在 `add()` 内立即执行**：不变量"长度 ≤ max_messages"在每次写操作后就恢复成立，读取方永远不需要操心。这叫**在写入侧维护不变量**，比在读取侧临时裁剪更可靠。

## 第三章：截断策略对比 —— 没有银弹，只有取舍

超限的历史消息怎么处理？业界有三种主流策略：

### 3.1 FIFO 丢弃（我们今天采用的）

最老的消息直接扔掉：

```text
容量=4:  [sys, m1, m2, m3] → 加入 m4 → [sys, m2, m3, m4]
                                          ↑ m1 被丢弃
```

- **优点**：实现 5 行代码、O(n) 一次完成、行为完全确定可测试。
- **缺点**：被丢弃的信息永久消失。用户在第 1 条消息里说"我对花生过敏"，聊到第 30 条时 Agent 会推荐花生酱。
- **适用**：任务型对话、单轮目标明确的 Agent 循环——这正好是 SmartResearch Agent 的场景。

### 3.2 滑动窗口（Sliding Window）

严格保留"最近 N 条"，与 FIFO 本质相同，只是更强调"窗口"的隐喻。很多框架（如 LangChain 的 `ConversationBufferWindowMemory`）就是它了。可以视为 FIFO 的别名，不再单列。

### 3.3 摘要压缩（Summarization）

不直接丢弃老消息，而是**再调一次 LLM，把老消息压缩成一段摘要**，替换掉原文：

```text
[sys, m1..m10, m11, m12]  →  [sys, "摘要: 用户询问了RAG与微调的区别……", m11, m12]
                                ↑ 一次额外 LLM 调用的产物
```

- **优点**：信息不"硬丢失"，长对话仍保留早期要点。
- **缺点**：每次压缩是一次**真金白银的 LLM 调用**（成本+延迟）；摘要本身可能丢细节、引入幻觉；实现复杂度高出一个数量级。
- **适用**：长时陪伴型对话、客服会话——早期事实（用户姓名、偏好）有长期价值的场景。

### 3.4 横向对比

| 维度 | FIFO 丢弃 | 摘要压缩 |
|------|-----------|----------|
| 实现复杂度 | 极低 | 高（需额外 LLM 调用 + prompt 设计） |
| 额外成本 | 零 | 每次截断一次 LLM 调用 |
| 信息保留 | 硬丢失 | 软保留（有损） |
| 确定性/可测试性 | 完全确定，易测试 | 依赖模型输出，难测试 |
| 适用场景 | 任务型 Agent、短会话 | 长对话、陪伴型产品 |

**架构决策记录**：SmartResearch Agent 是研究任务型 Agent，一次会话聚焦一个任务，FIFO 的损失可控。我们选 FIFO，但把 `_truncate()` 收敛为一个私有方法——未来要换成摘要压缩时，只需替换这一个方法，对外接口（`add`/`get_all`）零变化。这就是把易变的决策封装在最小面积内。

### 3.5 截断策略与 ReAct 循环的相互作用

把 FIFO 截断放进 day006 的 ReAct 循环里，有一个值得推演的细节：ReAct 的一轮"行动"会向历史里追加**两条**消息（assistant 的 Thought/Action + user 角色的 Observation）。这意味着容量会被成对消耗：

```text
max_messages=20，其中 system 占 1 条、初始任务占 1 条
→ 剩余 18 条可容纳 9 轮完整的 Action/Observation
→ 恰好覆盖 max_steps=10 以内的绝大多数任务
```

这也解释了为什么默认值是 20 而不是 10——`max_steps=10` 的 ReAct 任务若用 `max_messages=10`，跑到第 5 步左右就会开始**丢弃早期的 Observation**，模型会忘记自己刚查到的资料，推理质量骤降。

反过来推演：如果任务确实超过了记忆容量，会发生什么？最早的 Observation 被丢弃，模型可能会**重复调用已经查过的工具**（它看不到"已经查过"的证据）。这是 FIFO 记忆在 ReAct 场景下的典型退化模式。应对之策有两个，分别对应后续两天：

- **day009 长期记忆**：把已经获得的关键结论向量化存起来，即使原始 Observation 被淘汰，结论仍可被检索召回。
- **day010 Planner**：用规划把大任务拆小，每个子任务一次新的会话/记忆，单会话内的历史自然就短了。

看，记忆系统不是孤立的组件，它的容量参数和 Agent 的步数上限、任务规划方式是**联动设计**的。

## 第四章：会话隔离 —— 为什么记忆必须分房间

### 4.1 串扰事故：一个全局列表的灾难

假设我们图省事，整个应用只用一个全局 `ShortTermMemory`：

```python
# 反例：全局共享的记忆
GLOBAL_MEMORY = ShortTermMemory()

def handle_request(user_id: str, text: str) -> str:
    GLOBAL_MEMORY.add(Message(role="user", content=text))
    ...
```

用户 A 刚告诉 Agent"我的银行卡号是 6222…"，用户 B 随后问"刚才聊了些什么？"——**A 的卡号就躺在发给模型的 messages 里**，模型很可能原样复述给 B。这不是理论风险，真实产品事故里，会话串扰（Context Bleeding）导致的信息泄露屡见不鲜。

即使不谈隐私，**上下文污染**也足以致命：A 在调研"新能源汽车"，B 在问"红烧肉做法"，混在一起的上下文会让模型精神分裂，两头都答不好。

### 4.2 隔离的粒度：为什么是"会话"而不是"用户"

隔离按什么 key？候选：按用户 ID、按会话 ID。

| 隔离粒度 | 优点 | 缺点 |
|----------|------|------|
| 按用户 | 实现简单，一人一记忆 | 同一用户并行开两个话题会互相污染 |
| **按会话** | 话题级纯净隔离；同一用户可多会话并行 | 需要会话生命周期管理 |

选**会话（session）**：一个用户可以同时进行"调研 RAG"和"调研 MCP"两个独立会话，互不干扰。这和浏览器开两个无痕窗口是同一个思想。

### 4.3 SessionManager 的设计：一个字典就够了

```text
SessionManager
  └── _sessions: dict[str, ShortTermMemory]
        "a1b2c3d4e5f6" ──► ShortTermMemory(会话A的消息)
        "f6e5d4c3b2a1" ──► ShortTermMemory(会话B的消息)
```

四个操作对应会话的生命周期：

```text
create_session() ──► [会话活跃中：add/get] ──► close_session()
      │                                              │
      ▼                                              ▼
 生成 uuid，建空记忆                          从字典移除，记忆释放
```

### 4.4 session_id 为什么用 uuid

`create_session()` 里的 ID 生成：

```python
session_id = uuid.uuid4().hex[:12]
```

为什么不用自增整数（1, 2, 3…）？

1. **不可猜测性**：自增 ID 意味着我可以遍历 `session_id=1,2,3` 试探别人的会话。uuid 的随机性让"撞中别人会话"在实际上不可能（12 位十六进制 ≈ 281 万亿种）。
2. **无协调成本**：自增需要全局计数器（分布式下还要加锁/用数据库），uuid 本地生成零协调。
3. **无状态兼容**：uuid 生成不依赖任何存储，和第一章"无状态易扩展"的精神一致。

`uuid4().hex` 是 32 位十六进制，我们截取前 12 位——碰撞概率对教学项目可忽略（生日悖论下，需要上千万个会话才有可观碰撞概率），生产环境可用完整 32 位或加用户前缀。

> 思考题：截断 uuid 会不会有安全隐患？  
> 答：要区分两种需求。**防碰撞**（两个会话 ID 不撞车）12 位绰绰有余；**防猜测**（攻击者枚举 ID 窃取会话）取决于攻击者能尝试多少次——若接口有限流，12 位（约 2.8×10¹⁴ 空间）也足够；若完全不限流，应使用完整 32 位并配合鉴权（session_id 只标识会话，访问控制应由登录态负责，ID 本身不该是唯一防线）。这叫**纵深防御**：不把安全押在单一机制上。

### 4.5 两个防御性设计

- **`get_memory()` 对未知 ID 抛 `KeyError` 而不是静默新建**：拼错的 session_id 如果静默创建新会话，用户会发现"我的历史丢了"却无从排查。**失败要趁早、要响亮**（呼应 day001 的 Fail Fast）。
- **`close_session()` 用 `pop(session_id, None)` 容忍重复关闭**：关闭是清理动作，重复清理应当无害（幂等性，呼应 day002）。注意这两个方法的不同哲学：**读取要严格，清理要宽容。**

## 第五章：动手实现 ShortTermMemory

完整代码见 [memory/short_term.py](../源码/smart-research-agent/smart_research_agent/memory/short_term.py)，这里逐段讲解关键设计。

### 5.1 构造与参数校验

```python
def __init__(self, max_messages: int = 20):
    if max_messages < 2:
        raise ValueError("max_messages 至少为 2")
    self.max_messages = max_messages
    self._messages: list[Message] = []
```

为什么下限是 2？因为最小有意义的记忆 = 1 条 system + 1 条对话。`max_messages=1` 意味着连一轮问答都存不下，这种配置只可能是笔误，直接拒绝。

### 5.2 核心：截断逻辑

```python
def _truncate(self) -> None:
    if len(self._messages) <= self.max_messages:
        return
    system_msgs = [m for m in self._messages if m.role == "system"]
    others = [m for m in self._messages if m.role != "system"]
    keep = max(self.max_messages - len(system_msgs), 0)
    self._messages = system_msgs + others[-keep:] if keep else system_msgs[: self.max_messages]
```

逐行拆解：

1. **快路径**：没超容量直接返回——大多数 `add()` 调用走这里，开销为零。
2. **分拣**：把消息分成 system 与非 system 两堆。列表推导保持了原有相对顺序（Python 列表推导是保序的）。
3. **`keep = max(上限 - system数, 0)`**：非 system 消息还能留几条。`max(..., 0)` 防御极端情况（比如有人塞了 5 条 system 而容量只有 4）。
4. **重组**：system 钉在头部，其余只留最新 `keep` 条——`others[-keep:]` 这个负数切片就是 FIFO 丢弃的全部魔法。

最后一行的三元表达式处理退化情形：`keep=0` 时 `others[-0:]` 是**整个列表**（Python 切片陷阱！`-0 == 0`），所以必须显式分支，改为只留 system（且自身也要截到容量内）。

> 思考题：`others[-0:]` 为什么是全部元素而不是空列表？  
> 答：`-0` 就是 `0`，`others[0:]` 当然是从头到尾。负数切片里"0"没有负值形式，这是切片语法的一个著名边角，写截断逻辑时极易踩中。

### 5.3 写入侧维护不变量

```python
def add(self, message: Message) -> None:
    self._messages.append(message)
    self._truncate()
```

每次写入后立即恢复"长度 ≤ 上限"的不变量。调用方永远拿到合法状态，`get_all()` 里不需要任何防御逻辑。**约束集中在一处执行，是整个类可靠性的根基。**

### 5.4 一次完整的截断走查

光看代码不过瘾，我们用纸笔把一次真实的截断过程走一遍。设 `max_messages=4`，依次加入 1 条 system 和 5 条 user 消息：

| 操作 | 内部状态（追加后、截断后） | 是否触发截断 |
|------|---------------------------|--------------|
| add(sys) | `[sys]` | 否（1 ≤ 4） |
| add(u1) | `[sys, u1]` | 否 |
| add(u2) | `[sys, u1, u2]` | 否 |
| add(u3) | `[sys, u1, u2, u3]` | 否（4 ≤ 4，恰好满） |
| add(u4) | 追加后 `[sys, u1, u2, u3, u4]` → 截断后 `[sys, u2, u3, u4]` | **是**：system 保留，u1 淘汰 |
| add(u5) | 追加后 `[sys, u2, u3, u4, u5]` → 截断后 `[sys, u3, u4, u5]` | **是**：u2 淘汰 |

逐格验证 `_truncate()` 在 `add(u4)` 时刻的计算：

1. 长度 5 > 4，进入截断分支；
2. `system_msgs = [sys]`，`others = [u1, u2, u3, u4]`；
3. `keep = max(4 - 1, 0) = 3`；
4. `others[-3:] = [u2, u3, u4]`；
5. 重组：`[sys] + [u2, u3, u4]`，长度回到 4。✓

注意两个性质在这个走查中清晰可见：**system 的位置始终在第 0 位**（模型最看重上下文开头，钉在这里效果最好）；**任何时刻长度都不超过 4**（不变量从未被打破，哪怕一瞬）。

### 5.5 常见误区

- **误区一：在 `get_all()` 里截断。** 读侧截断意味着内部状态可以无限膨胀（内存照涨），只是"看起来"短。写侧截断才是真截断。
- **误区二：直接返回 `self._messages` 省一次拷贝。** 省下的微秒换来的是封装破洞——调用方一次意外的 `append` 就绕过全部截断逻辑。防御性拷贝是廉价的保险。
- **误区三：给 system 消息也设 FIFO。** 有的实现图省事统一丢弃，结果第 N 轮后 Agent 忘记输出格式，ReAct 解析器（day006）开始疯狂抛 `ReActParseError`。system 是契约，不是对话。
- **误区四：认为截断是"有损的坏设计"。** 恰恰相反——结合第一章的"中间遗忘"现象，主动丢弃低价值的陈旧消息，往往比硬塞全部历史效果更好。截断是特性，不是妥协。

## 第六章：动手实现 SessionManager

完整代码见 [memory/session.py](../源码/smart-research-agent/smart_research_agent/memory/session.py)。

### 6.1 生命周期四操作

```python
class SessionManager:
    def __init__(self, max_messages: int = 20):
        self._max_messages = max_messages
        self._sessions: dict[str, ShortTermMemory] = {}

    def create_session(self) -> str:
        session_id = uuid.uuid4().hex[:12]
        self._sessions[session_id] = ShortTermMemory(max_messages=self._max_messages)
        return session_id

    def get_memory(self, session_id: str) -> ShortTermMemory:
        if session_id not in self._sessions:
            raise KeyError(f"会话不存在: {session_id}")
        return self._sessions[session_id]

    def close_session(self, session_id: str) -> None:
        self._sessions.pop(session_id, None)

    def active_sessions(self) -> list[str]:
        return list(self._sessions.keys())
```

设计要点回顾：

- **配置透传**：`max_messages` 由管理器持有，统一注入每个新建的记忆——策略集中在一处调整。
- **字典映射**：`dict` 的 O(1) 查找天然适合"按 ID 取会话"，十万级会话也无压力。
- **严格读取 + 宽容清理**：`get_memory` 抛 `KeyError`；`close_session` 用带默认值的 `pop`，重复关闭不报错。

### 6.2 与 Agent 的接线（预告）

今天两个模块是独立交付的，明天（day009 长期记忆）及之后，它们会这样接入 Agent：

```python
# 未来形态预览（本日不要求实现）
mgr = SessionManager()
sid = mgr.create_session()

memory = mgr.get_memory(sid)
memory.add(Message(role="system", content=SYSTEM_PROMPT))
memory.add(Message(role="user", content=task))

# ReAct 循环里，每次调 LLM 前：
messages = memory.get_all()      # 有界、隔离、保序的上下文
answer = llm.chat(messages)
```

今天的 `ReactAgent`（见 [agent/react_agent.py](../源码/smart-research-agent/smart_research_agent/agent/react_agent.py)）还在自己持有 `messages` 列表——那是一个"一次性的内置记忆"。`ShortTermMemory` 就是把那段逻辑**提炼成可复用、可测试、可隔离的正式组件**。

### 6.3 从"散落的列表操作"到"记忆组件"：一次典型的重构抽象

值得停下来体会一下今天做的事在架构上的意义。day006 的 ReAct 循环里，`messages` 列表的追加、传递散落在 `run()` 方法各处：

```python
# day006 的形态：记忆逻辑与推理逻辑混在一起
messages.append(Message(role="assistant", content=raw))
messages.append(Message(role="user", content=f"Observation: {observation}"))
```

它有三个隐患，恰好被今天的组件一一化解：

| day006 散落写法的问题 | ShortTermMemory 的化解 |
|----------------------|------------------------|
| 无长度控制，长任务会撑爆上下文 | `add()` 内置截断，不变量自动维持 |
| 无会话概念，Agent 实例即会话，无法多用户复用 | `SessionManager` 按 session_id 隔离 |
| 追加逻辑不可独立测试，只能端到端跑 Agent | 记忆组件有 7 个专属单元测试 |

这是一次教科书式的**职责提取**：把"上下文管理"这个横切关注点从推理循环里抽出来，单独成组件。推理循环以后只关心"思考与行动"，记忆组件负责"记住该记的、忘掉该忘的"。后面的长期记忆（day009）、反思模块（day011）都会复用这套边界。

### 6.4 生产级会话管理还要补什么

今天的 `SessionManager` 是内存版教学实现，思路正确但离生产还差几块拼图，这里明确列出来，让你知道边界在哪：

1. **过期回收（TTL）**：当前实现里，不调用 `close_session()` 的会话会永远占着内存。生产实现要给每个会话记"最后活跃时间"，由后台任务定期清理超时会话——否则内存泄漏只是时间问题。
2. **持久化**：进程重启，所有会话蒸发。生产环境通常把消息历史落到 Redis（带 TTL，天然匹配会话语义）或数据库。
3. **分布式共享**：多实例部署时，会话状态要放在共享存储里，否则负载均衡把同一用户的两次请求打到不同机器，记忆就断了。
4. **并发安全**：同一 session_id 的两个请求同时 `add()` 时，当前实现没有锁。单进程内可用 `threading.Lock`，跨进程则依赖存储层原子操作。

这些问题都不改变今天的核心设计（字典映射 + 生命周期四操作），只是在同一骨架上叠加运维能力。**先把语义做对，再把规模做大**——顺序不能反。

## 第七章：测试 —— 把三条设计承诺变成断言

完整测试见 [tests/test_memory.py](../源码/smart-research-agent/tests/test_memory.py)。测试不是走形式，每一条都对应前文的一条设计承诺：

### 7.1 承诺一：截断时 system 不死、最老的先死

```python
def test_truncation_keeps_system_and_drops_oldest(self):
    mem = ShortTermMemory(max_messages=4)
    mem.add(Message(role="system", content="sys"))
    for i in range(5):
        mem.add(_msg("user", i))
    all_msgs = mem.get_all()
    assert len(all_msgs) == 4            # 不变量：长度有界
    assert all_msgs[0].role == "system"  # system 钉在头部
    contents = [m.content for m in all_msgs]
    assert "msg-user-0" not in contents  # 最老的被丢弃
    assert "msg-user-4" in contents      # 最新的保留
```

这个测试用 1 条 system + 5 条 user 灌进容量 4 的记忆，一次性验证三个行为：容量封顶、system 保留、FIFO 顺序。

### 7.2 承诺二：非法配置当场拒绝

```python
def test_invalid_max_messages(self):
    with pytest.raises(ValueError):
        ShortTermMemory(max_messages=1)
```

### 7.3 承诺三：会话之间互不泄露

```python
def test_sessions_are_isolated(self):
    mgr = SessionManager()
    s1 = mgr.create_session()
    s2 = mgr.create_session()
    mgr.get_memory(s1).add(_msg("user", 1))
    assert len(mgr.get_memory(s1).get_all()) == 1
    assert len(mgr.get_memory(s2).get_all()) == 0  # s2 完全不受 s1 影响
```

这是全文件最重要的一条断言——它守护的是**隐私底线**。

```bash

# 46 passed
```

46 个测试全部通过，其中本日新增 7 个（test_memory.py），此前各日的 39 个（配置、日志、计算器、注册表、LLM、解析器、ReAct 循环）全部保持绿色——**新组件的引入没有破坏任何既有行为**。

### 7.5 为什么是"承诺式"测试

注意本章测试的组织方式：不是按"代码有哪些函数"来列测试，而是按"设计做了哪些承诺"来列。两者的差别在重构时会显现出来——

- 按函数列测试：重构改了内部结构（比如把 `_truncate` 改名或拆分），测试就得跟着大片重写。
- 按承诺列测试：只要"system 保留、最老先丢、会话隔离"这三条对外承诺不变，内部实现随便改，测试无需动。

这正是 day002 FIRST 原则里 "Repeatable + Self-validating" 的深层应用：**测试锁定的是契约，不是实现细节。** 未来如果 `_truncate()` 从 FIFO 升级成摘要压缩（第三章说过这是预留的演进方向），只有截断细节相关的断言需要调整，隔离性、容量校验等测试照常工作。

## 第八章：今日总结

| 主题 | 核心原理 | 落地位置 |
|------|----------|----------|
| LLM 无状态 | 记忆 = 每次请求全量重放历史消息 | 第一章的概念模型 |
| 数据结构选型 | 顺序即语义；防御性拷贝；写入侧维护不变量 | `ShortTermMemory._messages` |
| system 保留 | 行为契约永不淘汰，闲聊可以丢 | `_truncate()` 分拣逻辑 |
| 截断策略 | FIFO 简单确定，摘要压缩有损但保留要点；按场景取舍 | `_truncate()` 单点封装 |
| 会话隔离 | 按 session 而非按 user；串扰是隐私事故 | `SessionManager._sessions` |
| session_id | uuid 不可猜测、零协调 | `uuid.uuid4().hex[:12]` |
| 严格读宽容清 | `get` 抛错 Fail Fast；`close` 幂等 | `get_memory` / `close_session` |

今天的一个总线：**Agent 的"记忆"不在模型里，而在应用层的工程里。** 我们什么也没让模型变聪明，只是把"该给模型看什么历史"这件事做对了——上下文完整、有界、隔离。明天 day009 将解决另一个维度的问题：超出短期记忆容量、但有长期价值的信息，用向量检索存进长期记忆，按需召回。
