## 第一部分：选择题

### 第 1 题（工具调用的本质）

关于"工具调用"扩展 LLM 能力边界的说法，哪一项是**正确**的？

- A. 接入计算器工具后，LLM 的乘法运算准确率提升了，因为模型内部学会了精确计算
- B. 工具让 LLM 能直接访问互联网，突破了训练数据截止日期的限制，模型权重被实时更新
- C. LLM 负责决策"调用哪个工具、传什么参数"，精确计算等执行工作交给外部程序完成
- D. 工具调用的主要价值是减少 LLM 生成的 token 数量，从而节省 API 费用

### 第 2 题（抽象基类）

关于 Python 抽象基类（ABC），下列说法**错误**的是：

- A. 含有抽象方法的类不能直接实例化
- B. 子类如果没有实现全部抽象方法，实例化时会抛出 `TypeError`
- C. ABC 只能在运行时发现契约违反，无法配合静态类型检查工具
- D. 抽象基类中也可以包含有完整实现的普通方法（如 `to_schema()`），供所有子类复用

### 第 3 题（eval 与 AST）

为什么 `ast.parse(expression)` 之后做白名单校验比直接 `eval(expression)` 安全？

- A. `ast.parse` 会自动删除表达式中的危险代码
- B. `ast.parse` 只做语法解析、不执行代码，生成的语法树让我们可以在执行前逐节点甄别，只放行数字与运算符节点
- C. `ast` 模块是标准库，标准库代码经过安全审计
- D. 白名单校验会把所有字符串转成数字，恶意代码因此失效

## 第四部分：编程题

### 第 9 题（实现新工具）

参照 `CalculatorTool` 的实现方式，在 `smart_research_agent/tools/` 下实现一个 `StringLengthTool`：

1. 继承 `BaseTool`，`name` 为 `"string_length"`；
2. `description` 要面向 LLM 写作，清楚说明用途与参数（可以参考计算器的写法）；
3. `parameters` 为 JSON Schema，必填参数 `text`（string 类型）；
4. `execute` 返回 `f"字符串长度为 {len(text)}"`，`text` 缺失或为空时返回 `"错误: 缺少 text 参数"`；
5. 在 `tests/test_string_length.py` 中写测试，覆盖：正常计算、空参数报错、`to_schema()` 导出正确。

提示：回顾第二章——`description` 的读者是谁？写描述时应该包含哪些信息？

### 第 10 题（扩展白名单）

当前 `_safe_eval` 支持 `+ - * / ** %` 六种运算。请扩展 `CalculatorTool` 使其额外支持：

1. 整除运算 `//`（对应 AST 节点 `ast.FloorDiv`，运算函数 `operator.floordiv`）；
2. 在 `tests/test_calculator.py` 中补充至少 2 组参数化用例验证整除行为（如 `"7 // 2"` → `"3"`）；
3. 同步更新 `description`，让 LLM 知道工具新增了整除能力。

思考：完成这个扩展时，你改了求值函数 `_safe_eval` 本身的代码吗？这体现了什么设计原则？
