## 第一章：为什么需要多 Agent —— 单体 Agent 的三堵墙

### 1.1 先复现问题：让一个 Agent 完成整条调研流水线

到目前为止，我们的 SmartResearch Agent 是**单体架构**：一个 `ReactAgent`、一份 system prompt、一个 LLM，完成所有工作。假设我们要求它"调研 RAG 技术并写一篇科普短文"，理想的单体 system prompt 大概长这样：

```text
你是一个全能助手。请先收集资料，再提炼要点，最后写成文章。
收集资料时要客观全面；提炼要点时要犀利精准；写文章时要生动流畅。
```

这句话读起来没问题，但实际运行中单体 Agent 会撞上三堵墙。

**墙一：上下文稀释（Context Dilution）。** 收集资料阶段会产生大量原始文本——搜索结果、网页片段、数据表格。这些内容全部堆在同一个对话上下文里。等到"写文章"阶段，模型的注意力要在几千字的原始资料噪声中找到"现在该写作了"这个信号。day010 我们说过 ReAct 会"迷失方向"，原因就是局部上下文淹没了全局目标；单体流水线把这个问题放大了一个数量级——**调研的噪声直接污染了写作的判断**。

**墙二：角色冲突（Persona Interference）。** "客观全面地罗列事实"和"生动流畅地讲故事"是两种互相拉扯的写作风格。放在同一份 system prompt 里，模型要么折中（资料不够全面，文章也不够生动），要么漂移（写着写着把资料清单当成了正文）。一个提示词同时定义多个互相冲突的行为准则，本质是**让模型自己解决我们没解决的架构矛盾**。

**墙三：失败不可定位。** 最终文章质量差，问题出在哪一环？是资料没查全、要点没抓准，还是文笔不行？单体 Agent 的中间过程隐没在一条连续的思维流里，没有明确的阶段边界，**你无法对"哪个环节最差"做出断言，也就无法针对性改进**。

```text
单体 Agent 流水线:
┌────────────────────────────────────────────┐
│  system: 你是全能助手（收集+分析+写作）      │
│  user:   调研 RAG 并写文                    │
│  ...资料...资料...资料...要点...文章...      │  ← 所有阶段共享一个上下文
└────────────────────────────────────────────┘
   噪声累积 ↑      风格冲突 ↑      边界模糊 ↑
```

### 1.2 人类组织早就给出了答案：分工

面对同样的任务，人类社会的解法是分工。一份调研报告的诞生流程：

```text
研究员 ──收集整理──▶ 资料清单 ──▶ 分析师 ──提炼──▶ 要点列表 ──▶ 撰稿人 ──成稿──▶ 报告
（广而全）                    （准而精）                      （美而顺）
```

为什么分工有效？三个层面的原因：

1. **认知带宽**：每个角色只需在有限的上下文里做好一件事。研究员不需要管文笔，撰稿人不需要重新读原始资料——它拿到的是分析师提炼过的要点。
2. **目标单一**：每个角色的评价标准清晰。资料全不全、要点准不准、文章顺不顺，分别由三个人负责，质量可分别考核。
3. **接口明确**：角色之间交接的是**标准化产物**（资料清单、要点列表），不是一团混沌的思考过程。接口清晰，替换任何一个角色都不影响其他人。

多 Agent 协作就是把这套组织学原理搬进软件架构：**把一个"什么都要做"的大 Agent，拆成若干"只做一件事"的小 Agent，用明确的接口把它们串起来。**

### 1.3 多 Agent 的收益与代价

分工不是免费的。诚实地列出两端：

| 维度 | 收益 | 代价 |
|------|------|------|
| 上下文 | 每个角色上下文小而聚焦，注意力不稀释 | 上游产出需要显式传递，传递中可能丢信息 |
| 提示词 | 每个角色的 system prompt 短而专，风格不冲突 | 要维护 N 份提示词，语义需保持一致 |
| 可观测性 | 阶段边界清晰，每环产出可单独检查 | 系统整体行为更复杂，需要消息轨迹来还原 |
| 可测试性 | 每个角色可独立用 MockLLM 测试 | 需要额外测试协作链路本身 |
| 成本 | —— | LLM 调用次数 = 角色数 × 每角色调用次数 |

关键判断是：**当任务可以自然地分解为"输入输出明确的阶段"时，分工的收益大于代价**。"调研 → 分析 → 写作"恰好是这样的任务——每个阶段的产出（资料清单、要点列表、文章）都是边界清晰的标准化产物。反过来，如果任务阶段之间纠缠不清（比如边写边改、反复回头的创作），硬拆角色反而制造沟通成本。今天的任务属于前者。

> 思考题：既然每个角色背后都是同一个 LLM，为什么说拆分角色能减少"角色冲突"？提示：冲突发生在**同一份上下文内部**，拆分后每份上下文只剩一种行为准则。

### 1.4 多 Agent 系统的三种协作拓扑

今天的流水线只是多 Agent 协作的最简单形态。把视角放宽，常见拓扑有三种：

```text
(a) 流水线（Pipeline）—— 今天实现
    A ──▶ B ──▶ C        固定顺序，单向传递，无回环

(b) 中心调度（Hub-and-Spoke）
        ┌──▶ B ──┐
    A ──┼──▶ C ──┼──▶ A   中心 Agent 分派任务、回收结果、决定下一步
        └──▶ D ──┘        （如 AutoGen 的 GroupChat、Manager 模式）

(c) 对等网络（Peer Network）
    A ◀──▶ B
    ▲      ▲             任意 Agent 可互相通信，涌现协作
    └──────┘             （如多智能体辩论、社会模拟）
```

复杂度从左到右递增，可控性从左到右递减。流水线**顺序固定、数据流向明确、行为完全可预测**，是入门与生产中最常用的形态；中心调度引入了"谁来做决策"的灵活性；对等网络最强大也最难以调试。我们先在（a）上把"消息传递与结果交接"这个基本功练扎实，day013 的 LangGraph 会给我们表达（b）（c）的图结构能力。

## 第二章：角色设计 —— system prompt 即角色契约

### 2.1 角色拆分的原则：按"产出物"划分，而不是按"能力"划分

设计角色时最容易犯的错误是按能力拆："搜索 Agent""计算 Agent""翻译 Agent"——这是**工具视角**，拆出来的其实是工具调用器，不是角色。正确的拆法是按**产出物**拆：

| 角色 | 输入 | 产出物 | 评价标准 |
|------|------|--------|----------|
| 研究员 ResearcherAgent | 话题 | 资料清单 | 全面、客观、标注可信度 |
| 分析师 AnalystAgent | 资料清单 | 要点列表 | 精准、有取舍、指出矛盾 |
| 撰稿人 WriterAgent | 要点列表 | 成稿文章 | 结构完整、通顺、不引入新事实 |

每个角色的**产出物就是下一个角色的输入**，这条"产出物链"定义了流水线的形状。判断角色拆得好不好的尺子很简单：**能不能用一句话说清每个角色交付什么？** 说不清，就是职责边界没划对。

### 2.2 system prompt 的三段式结构

看研究员的 system prompt（完整代码见 [agent/roles.py](../源码/smart-research-agent/smart_research_agent/agent/roles.py)）：

```python
class ResearcherAgent(BaseRoleAgent):
    """研究员：围绕话题检索、收集资料."""

    role = "researcher"
    system_prompt = """你是一名研究员。你的职责是围绕给定话题收集、整理资料。

要求：
1. 列出与话题直接相关的事实、数据与背景信息
2. 标注每条资料的来源或可信度
3. 只输出资料清单，不要下结论、不要写观点
"""
```

三段式结构，每一段都有明确职责：

1. **身份声明**（"你是一名研究员"）：锚定角色，让模型调用与之相关的行为模式。
2. **正向要求**（第 1、2 条）：定义产出物的内容标准——要有什么。
3. **负向约束**（第 3 条"不要下结论、不要写观点"）：定义职责边界——**不做什么和做什么同样重要**。研究员一旦开始写观点，就越界做了分析师的工作，下游拿到的是夹生的资料。

第 3 条是多 Agent 提示词区别于单体提示词的关键。单体提示词不需要"不要写观点"这种约束，因为它什么都得做；角色提示词必须**显式封住越界的出口**，否则相邻角色的职责会互相渗透，分工形同虚设。

对照分析师和撰稿人的第 3 条：

- 分析师："只输出要点列表，**不要展开成文章**"——封住向撰稿人越界的出口。
- 撰稿人："不引入要点之外的**新事实**"——封住向研究员越界的出口（不能自己编资料）。

三条负向约束合起来，构成了一条单向流动的数据纪律：**每个角色只加工上游的产出，不回头重做上游的工作。**

### 2.3 为什么是"轻量封装"而不是复用 ReactAgent

`BaseRoleAgent.work()` 的实现轻得惊人——拼 system + user 两条消息，调一次 `llm.chat`，返回文本：

```python
class BaseRoleAgent:
    """角色基类：独立 system prompt + 单次 LLM 调用的轻量封装."""

    role: str = "role"
    system_prompt: str = ""

    def __init__(self, llm: BaseLLM, name: str | None = None):
        self.llm = llm
        self.name = name or self.role

    def work(self, task: str, context: str = "") -> str:
        prompt = f"任务：{task}" if not context else f"任务：{task}\n\n上游产出：\n{context}"
        result = self.llm.chat(
            [
                ChatMessage(role="system", content=self.system_prompt),
                ChatMessage(role="user", content=prompt),
            ]
        )
        return result
```

一个自然的疑问：为什么不让每个角色都是 `ReactAgent`，自己跑完整的工具循环？

答案是**按当前职责选当前形态，给未来升级留好接口**：

- 今天三个角色的工作都是"一次性转换"——输入一段文本，输出一段文本，不需要工具、不需要多步推理。用 ReactAgent 意味着每个角色内部都要消耗 1~N 步循环、承担解析失败和步数耗尽的失败模式，收益为零。
- 但研究员是**最可能需要升级**的角色：真实的"收集资料"离不开搜索工具。等 M2 阶段 MCP 工具接入后，ResearcherAgent 内部可以换成 ReAct 循环，只要 `work(task, context)` 的签名不变，编排层一行不改——这就是 day010 说的"执行原语可替换"。

这也呼应了 `__init__` 里的依赖注入：构造函数接收 `BaseLLM`，测试注入 MockLLM，生产注入真实模型。三个角色类加起来不到 80 行，但"角色 = 提示词契约 + 一次 LLM 调用"这个抽象，是后面所有复杂协作的基石。

> 思考题：`work()` 的 `context` 参数为什么是字符串而不是上游 `Message` 对象？提示：想一想角色层和编排层的依赖方向——角色应该知道"消息"这个编排概念的存在吗？

## 第三章：消息传递 —— 显式交接 vs 共享黑板

### 3.1 Message：协作的最小数据单元

角色之间的交接需要一个数据载体。我们定义 `agent/message.py` 中的 `Message`：

```python
@dataclass
class Message:
    """一条 Agent 间的协作消息."""

    sender: str
    receiver: str
    content: str
    metadata: dict = field(default_factory=dict)

    def to_dict(self) -> dict:
        """序列化为 dict，便于日志输出与持久化."""
        return {
            "sender": self.sender,
            "receiver": self.receiver,
            "content": self.content,
            "metadata": dict(self.metadata),
        }
```

四个字段，各有不可省略的理由：

- **sender / receiver**：消息的**路由信息**。今天的流水线里路由是写死的，但字段必须从一开始就存在——未来中心调度拓扑里，Orchestrator 要根据 receiver 决定把消息派给谁；消息轨迹里也要靠它还原"谁把什么交给了谁"。
- **content**：交接的内容本体。今天是纯文本（资料清单、要点列表、文章），保持简单。
- **metadata**：结构化附注。我们用它记录 `stage`（消息属于哪个阶段）。为什么要单独的 metadata 而不是塞进 content？因为 content 是给**下游角色**读的（会拼进提示词），metadata 是给**程序**读的（过滤、统计、审计）——两类消费者，两条通道，互不污染。

注意它和 `llm/base.py` 里的 `Message`（role + content）是**两个不同层次的概念**：`llm.Message` 是"对 LLM 说的一句话"，`agent.Message` 是"Agent 之间的一次交接"。前者是传输层，后者是应用层。分层清晰，所以我们在 `roles.py` 里用 `from smart_research_agent.llm.base import Message as ChatMessage` 做了显式别名，避免同名混淆——**同名不同义的概念共处一个系统时，命名上就要拉开距离。**

### 3.2 两种交接模型：共享黑板 vs 显式消息

多 Agent 系统的信息交换有两种经典模型：

| 维度 | 共享黑板（Blackboard） | 显式消息（Message Passing） |
|------|----------------------|---------------------------|
| 机制 | 所有角色读写同一块共享状态 | 角色间点对点传递消息 |
| 数据可见性 | 所有人看到所有东西 | 只看到你收到的 |
| 上下文控制 | 差：黑板无限膨胀 | 好：每环只传递必要产出 |
| 轨迹审计 | 难：要 diff 黑板历史 | 天然：消息序列就是轨迹 |
| 典型代表 | 早期专家系统、AutoGen 群聊 | Actor 模型、微服务 |

我们选显式消息，核心理由是第一章的"墙一"：**上下文稀释问题在协作层同样存在**。如果用共享黑板，撰稿人能"看到"全部原始资料，它的上下文又脏了——分工在架构上做了，在数据上没做，等于没做。显式消息强制每环只传递**加工后的最小必要产出**：分析师只收到资料清单，撰稿人只收到要点列表。信息在每一次交接时被主动压缩，这正是流水线质量优于单体的数据层原因。

> 思考题：撰稿人只看要点列表，会不会丢失资料里的重要细节，导致文章写得浅？这个风险的缓解手段是什么？提示：要点列表的质量由谁负责？负向约束"不引入新事实"在这里起了什么作用？

### 3.3 message_log：让协作可审计

`MultiAgentOrchestrator` 每发生一次交接，就把消息追加进 `message_log`。一次完整运行产生 4 条消息：

```text
[1] orchestrator ──▶ researcher   (stage=dispatch_research)  下发任务：话题
[2] researcher   ──▶ analyst      (stage=research)           交接资料清单
[3] analyst      ──▶ writer       (stage=analysis)           交接要点列表
[4] writer       ──▶ orchestrator (stage=article)            交回成稿
```

为什么连"orchestrator 下发任务"和"writer 交回成稿"也要记录？因为 message_log 的目的是**完整还原一次协作的全部信息流动**，而不是只记"角色之间"的部分。少了第 1 条，你无法从日志里看出这次协作是为哪个话题发起的；少了第 4 条，你无法断言成稿是在哪个阶段产生的。**审计日志的完整性原则是：只看日志就能重建整个系统的行为，不需要任何系统外信息。**

这个设计的回报立竿见影——测试里我们可以直接断言整条轨迹：

```python
pairs = [(m["sender"], m["receiver"]) for m in log]
assert pairs == [
    ("orchestrator", "researcher"),
    ("researcher", "analyst"),
    ("analyst", "writer"),
    ("writer", "orchestrator"),
]
```

第一章"墙三"说的失败不可定位，到此被根治：文章不好？查 `stage=analysis` 的消息看要点准不准；要点不准？查 `stage=research` 的消息看资料全不全。**每一环的产出都是日志里一条可检查的记录。**

## 第四章：编排器 —— 不调 LLM 的指挥者

### 4.1 run() 的完整实现

`MultiAgentOrchestrator.run()` 是整个协作的大脑（完整代码见 [agent/orchestrator.py](../源码/smart-research-agent/smart_research_agent/agent/orchestrator.py)）：

```python
def run(self, topic: str) -> dict:
    self.message_log.clear()

    # 阶段一：研究员检索资料
    self._record("orchestrator", self.researcher.name, topic, stage="dispatch_research")
    research = self.researcher.work(task=f"围绕话题收集资料：{topic}")
    self._record(self.researcher.name, self.analyst.name, research, stage="research")

    # 阶段二：分析师提炼要点
    analysis = self.analyst.work(task="从研究资料中提炼核心要点", context=research)
    self._record(self.analyst.name, self.writer.name, analysis, stage="analysis")

    # 阶段三：撰稿人成稿
    article = self.writer.work(task=f"根据要点撰写关于「{topic}」的短文", context=analysis)
    self._record(self.writer.name, "orchestrator", article, stage="article")

    return {
        "topic": topic,
        "research": research,
        "analysis": analysis,
        "article": article,
        "message_log": [m.to_dict() for m in self.message_log],
    }
```

### 4.2 设计点一：编排器本身不调用 LLM

整个 `run()` 没有一次 `self.llm.chat`——编排器甚至不持有 LLM。这是刻意的：**调度逻辑是确定性的程序，不该把"下一步给谁"交给概率模型决定**。

对照一下两种编排思路：

- **程序化编排（今天）**：顺序写死在代码里，`研究 → 分析 → 撰稿`，100% 可预测、可测试、可复现。
- **LLM 驱动编排（中心调度的极端版）**：每完成一步，问 LLM"下一步该让谁做"。灵活，但调度本身变成了不可预测的黑盒，还需要解析 LLM 的调度输出。

当流水线拓扑固定时，程序化编排完胜——灵活性是为"拓扑会变"付出的税，拓扑不变就不该交这笔税。day013 的 LangGraph 会让我们用图结构表达更复杂的拓扑，但**图的结构（节点与边）依然是程序定义的**，变的只是表达方式。

### 4.3 设计点二：任务文本的构造是编排器的职责

注意三个阶段传给 `work()` 的 `task` 各不相同：

```python
researcher.work(task=f"围绕话题收集资料：{topic}")                       # 携带话题
analyst.work(task="从研究资料中提炼核心要点", context=research)          # 固定指令 + 上游产出
writer.work(task=f"根据要点撰写关于「{topic}」的短文", context=analysis)  # 两者都要
```

**"怎么向角色描述任务"是编排器的知识，不是角色的知识。** 角色只负责"给我任务和上游产出，我交付结果"；任务文本怎么措辞、要不要重复话题、产出放在哪个参数里，都由编排层决定。这个边界让角色保持纯粹——换一个话题、换一条流水线（比如调研后只要要点不要文章），角色类一行不用改，只改编排器的调用序列。

### 4.4 设计点三：message_log 的清理时机

```python
def run(self, topic: str) -> dict:
    self.message_log.clear()
```

`clear()` 放在 `run()` 开头而不是 `__init__` 里，语义是：**message_log 描述的是"最近一次协作"的轨迹**。这样同一个 Orchestrator 可以连续跑多个话题，每次的日志互不混淆（测试 `test_message_log_reset_between_runs` 固化了这个语义）。另一种设计是持续累积、全局审计——那需要给每条消息加时间戳和话题字段，属于生产化阶段的增强，今天先用最简语义。

### 4.5 协作时序全景

把三个模块串起来，一次 `orchestrator.run(topic)` 的完整时序：

```text
调用方        Orchestrator        Researcher        Analyst        Writer        LLM
  │ run(topic)  │                  │                │              │             │
  │────────────▶│ log: dispatch    │                │              │             │
  │             │ work(task)       │                │              │             │
  │             │─────────────────▶│ chat(sys+user) │              │             │
  │             │                  │──────────────────────────────────────────────▶│
  │             │                  │◀──────────────────────────────────────────────│
  │             │ log: research    │                │              │             │
  │             │ work(task, ctx)  │                │              │             │
  │             │──────────────────────────────────▶│ chat ──────────────────────▶│
  │             │ log: analysis                     │                             │
  │             │ work(task, ctx) ───────────────────────────────▶│ chat ────────▶│
  │             │ log: article                                    │               │
  │  dict       │                  │                │              │             │
  │◀────────────│                  │                │              │             │
```

LLM 恰好被调用 **3 次**，每个角色一次。这个次数是流水线拓扑的直接推论：N 个角色、每角色单次调用，就是 N 次。和 day010 的"规划 1 次 + 每子任务 M 次"对比着看，你能直观感到不同架构的成本结构差异。

### 4.6 与既有模块的关系图

```text
day005  BaseLLM / MockLLM ────────────── 被注入 ▶ 三个角色
day006  ReactAgent ────────────────────── 执行原语（未来研究员内部可升级复用）
day010  Planner ───────────────────────── 上游可接：先规划话题维度，再交给流水线
```

### 5.2 组装一条流水线只需五行

```python
from smart_research_agent.agent.orchestrator import MultiAgentOrchestrator
from smart_research_agent.agent.roles import AnalystAgent, ResearcherAgent, WriterAgent
from smart_research_agent.llm.mock import MockLLM

llm = MockLLM(responses=["资料清单……", "要点列表……", "成稿文章……"])
orchestrator = MultiAgentOrchestrator(
    researcher=ResearcherAgent(llm=llm),
    analyst=AnalystAgent(llm=llm),

result = orchestrator.run("RAG 检索增强生成技术")
```

三个角色共享同一个 MockLLM 是安全的：流水线串行执行，MockLLM 按顺序弹出响应，消费顺序与执行顺序天然一致。生产环境把 `build_llm()` 里的 MockLLM 换成 `OpenAICompatibleLLM` 即可（见 [main.py](../源码/smart-research-agent/smart_research_agent/main.py)），流水线代码不动。

### 5.3 测试设计：四层断言

`tests/test_multi_agent.py` 分三个测试类，对应今天三个模块，其中编排器的测试分四层递进：

**第一层：产出正确**（happy path）——最终产出包含各阶段结果：

```python
def test_pipeline_produces_article(self):
    orchestrator, _ = _make_orchestrator(_SCRIPT)
    result = orchestrator.run("RAG 技术")
    assert result["research"] == _SCRIPT[0]
    assert result["analysis"] == _SCRIPT[1]
    assert result["article"] == _SCRIPT[2]
```

**第二层：角色被依次调用**——利用 MockLLM 记录的 `calls`，检查三次调用的 system prompt 分属三个角色：

```python
def test_three_roles_called_in_order(self):
    orchestrator, llm = _make_orchestrator(_SCRIPT)
    orchestrator.run("RAG 技术")
    assert len(llm.calls) == 3
    assert "研究员" in llm.calls[0][0].content
    assert "分析师" in llm.calls[1][0].content
    assert "撰稿人" in llm.calls[2][0].content
```

注意这个断言的技巧：`llm.calls[i][0]` 是第 i 次调用的第一条消息（system），通过检查 system prompt 里的角色名，我们**不依赖角色类的内部实现**就验证了"调用顺序正确"——测试的是行为契约，不是实现细节。

**第三层：上游产出流向下游**——验证结果交接真实发生：

```python
def test_upstream_output_flows_downstream(self):
    orchestrator, llm = _make_orchestrator(_SCRIPT)
    orchestrator.run("RAG 技术")
    assert _SCRIPT[0] in llm.calls[1][1].content  # 分析师收到了研究员的产出
    assert _SCRIPT[1] in llm.calls[2][1].content  # 撰稿人收到了分析师的产出
```

**第四层：消息轨迹完整**——验证 message_log 的 sender/receiver 序列与阶段标记：

```python
def test_message_log_records_full_trace(self):
    ...
    pairs = [(m["sender"], m["receiver"]) for m in log]
    assert pairs == [
        ("orchestrator", "researcher"),
        ("researcher", "analyst"),
        ("analyst", "writer"),
        ("writer", "orchestrator"),
    ]
```

四层断言从"结果对不对"逐步深入到"过程对不对"。只测第一层，消息传递断了也可能蒙混过关（比如角色不看上游产出直接自说自话）；加上三、四层，**协作链路本身的正确性**也被钉死了。

## 第六章：今日总结 —— 多 Agent 协作的设计要点

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| 三角色分工 | 上下文稀释、角色冲突、失败不可定位是单体的三堵墙 | `agent/roles.py` |
| 按产出物划分角色 | 产出物链定义流水线形状，评价标准随之清晰 | 三角色职责表 |
| system prompt 三段式 | 身份 + 正向要求 + 负向约束（封住越界出口） | 各角色 `system_prompt` |
| 轻量封装而非 ReactAgent | 按当前职责选形态，留好 `work()` 升级接口 | `BaseRoleAgent` |
| 显式 Message 传递 | 交接时主动压缩信息，每环只传最小必要产出 | `agent/message.py` |
| content / metadata 双通道 | 内容给下游角色读，附注给程序读，互不污染 | `Message` 四字段 |
| message_log 全量记录 | 只看日志就能重建整个协作行为 | `Orchestrator._record` |
| 编排器不调 LLM | 拓扑固定时调度逻辑用确定性程序，不交税给灵活性 | `Orchestrator.run` |
| 任务文本由编排器构造 | 角色保持纯粹，换话题换流水线角色零改动 | `run()` 中的 `task=` |

今天埋下的三个伏笔，后续阶段回收：

- **研究员的工具化**：ResearcherAgent 目前是"凭模型记忆做调研"，接入搜索/MCP 工具（M2 阶段）后才具备真实检索能力，内部可升级为 ReAct 循环。
- **协作拓扑升级**：流水线无法表达"分析不合格打回研究员重来"这类回环，day013 的 LangGraph 状态图将解决这个问题。
- **质量门控**：当前各环节产出无人验收。M1-D11 的评估与 M3 的 Harness 框架会给流水线加上质量闸门。
