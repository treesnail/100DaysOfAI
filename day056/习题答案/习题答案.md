## 第一部分：选择题

### 第 1 题 → **B**

`IGNORE_INDEX = -100` 是"前缀与答案**分别 tokenize 再拼接**"这条实现的配套约定：拼接之后，前缀段的每个 token 的 label 都被置成 `-100`，交叉熵只在答案 token 上计算。这就是"同一个模型，为什么 SFT 能学会跟随指令"的工程答案——**如果不在 prompt 段屏蔽 loss，模型学到的会是"把问题复述一遍"**。

A 是错的：分词失败会让 tokenize 直接抛错，不会用 `-100` 标记；C 是错的：超长样本由 `max_length` 截断处理；D 是错的：`-100` 与 padding mask 是两件事（前者决定"算不算 loss"，后者决定"注不注意"）。

### 第 2 题 → **B**

两条口径的具体数字（本文第七章实测）：

```text
day048 画像口径（字符 → token 估算）：平均约 84.2 token/条，输出长度 67~165 字，median=78
day050 渲染分词口径（真实 token）：     p95 = 302、max = 320
```

day049 的预算是"用当时能拿到的最好的口径"算的，**没有错**；但 day050 拿到的是**渲染并分词之后**的真实长度分布，于是缺省 `max_length` 取 384（向上取整到 32 的倍数）。A、C 都不是理由（32 的倍数只是工程惯例；384 与上下文窗口无关）；D 是错的——这是一次**口径升级**，不是算错。

### 第 3 题 → **B**

实测（`compare_strategies` 的输出）：

```text
strategy='qlora'  base_weight_bytes=3 476 140 673  base_bits_per_parameter=4.126953125
```

`4.126953125 = 4 + 0.126953125`，多出来的部分来自**二级量化**（每 64 个权重一个 absmax 常数，`block=64`）与一级量化常数。若按 4.0 bit 估算，7B 模型的权重会算成 `6 738 415 616 × 4 / 8 = 3 369 207 808` 字节，比真实的 `3 476 140 673` **少算约 107 MB（≈100 MiB）**。

A 是"教科书答案"但不是本课实测值；C 是 int8；D 属于 2-bit 档位。

### 第 4 题 → **B**

```text
lr=2.0 : 训练集 421.76 → 290.49           （欠拟合）
lr=8.0 : 训练集 421.82 → 14.46，评估集 587.64（泛化间隙 573.24，过拟合）
lr=20.0: 发散（困惑度 inf）
```

训练集困惑度降到 14.46 单独看像"学得极好"，**只有把训练集与评估集放在一起看，过拟合才显形**。这正是 day053 引入白盒探针的原因：文本分量在"看起来差不多"的微调输出上区分度有限，困惑度能给出一个更锐利的信号。

### 第 5 题 → **C**

三种损失的起点值（本文第三章实测，`beta=0.1`）：

```text
sigmoid → 0.693147
hinge   → 1.0
ipo     → 25.0   = 1/(4 × 0.1²)
```

A 对应 `sigmoid`；B 对应 `hinge`；D 不是任何一档。**起点自检值不是"都用 ln2"**——沿用 `ln2` 去检查 `ipo`，会漏掉真实的接线错误（25.0 与 0.693 的差远超任何浮点容差）。

## 第二部分：判断题

### 第 6 题 → **错**

两者**不矛盾，因为它们分属两个对象、两层口径**：

| 层级 | 对象与字段 | 本课实测 |
|------|-----------|---------|
| 清洗器 | `DatasetCleaner` → `FilterReport.drop_reasons` | `{'output_too_short': 2}` |
| 偏好构造 | `PreferenceBuildReport.drop_reasons`（两条体检） | `{}`（零丢弃） |

`build_preferences` 的流程是"**清洗 → 造候选 → 自洽体检 → 区分度体检**"，18 条种子先被清洗掉 2 条（`output_too_short`），剩 16 条；这 16 条**全部通过了偏好对的两条体检**，所以构造层面的丢弃是 0。

**这道题考的是"同名键分属不同对象"这个陷阱**：只看到两个 `drop_reasons` 里一个是 2、一个是 0，很容易得出"账对不上"的结论。正确做法是先看它们属于哪个 dataclass，再看口径。

### 第 7 题 → **对**

LoRA 合并是纯矩阵加法 `W + (alpha/r) · B @ A`，**没有任何近似**。给一个宽容差（例如 1e-3）反而会让"合并时少加了一项"这类真错误被放过去——而那正是一个"看起来合了、其实没合"的静默缺陷。实测差 `0.00e+00`。

这与 day031 立的"安全门禁零容忍、质量门禁留裕度"是同一条纪律：**门禁的宽容度应该由"物理上有多少噪声"决定，而不是由"怕误报"决定。** 这里噪声是 0，所以容差是 0。

### 第 8 题 → **对**

实测：

```text
warmup_floor(3)   = 0.333333   重算 warmup_steps = int(3 × 0.333333)   = 1
warmup_floor(12)  = 0.083333   重算 warmup_steps = int(12 × 0.083333)  = 1
warmup_floor(30)  = 0.033333   重算 warmup_steps = int(30 × 0.033333)  = 1
warmup_floor(100) = 0.010000   重算 warmup_steps = int(100 × 0.010000) = 1
```

并且把比例**略小一档**（`floor - 1e-6`）时，四组全部退化为 0：

```text
3   → 0.333332 → int(3 × 0.333332)   = 0
12  → 0.083332 → int(12 × 0.083332)  = 0
30  → 0.033332 → int(30 × 0.033332)  = 0
100 → 0.009999 → int(100 × 0.009999) = 0
```

所以 `warmup_floor = 1/total_steps` 是**恰好让 warmup 生效一步的下界**，边界是"取整"而不是别的——**这不是玄学，是一条可以被断言的算术事实**。

### 第 9 题 → **错**

day053 的实测结果是：合格率 `33.33% → 83.33%`，配对自助法区间 `[+0.1994, +0.4059]` 不含 0，但 **McNemar 精确检验的 `p = 0.25`，并不显著**。

原因很直接：18 条用例里**只有 3 个不一致对**（翻转的那两格），样本量根本不足以支撑显著性。三个统计口径给出的是**互补**的信息：

- 自助法区间回答"效应量大概在哪个范围"；
- McNemar 回答"在只看翻转对的前提下，这个方向有多少可能是巧合"。

**"看起来涨了 50%"与"统计上证明涨了"是两件事。** 结论应该是"方向可能是对的，但需要更多用例才能做上线决策"——这正是 day053 把 `finetune_eval_bootstrap_samples` 与 `finetune_eval_alpha` 做成可配置项、并在报告里同时给出三种口径的原因。

## 第三部分：简答题

### 第 10 题（三本账）

**第一本账：步数账（day050）**

- **回答什么**：这次训练会做多少次参数更新？分几个 epoch？warmup 真的生效了吗？
- **落点**：`sft/args.py` 的 `SFTTrainingArgs` + `plan_training`（八类风险告警）、`dpo/config.py` 的 `DPOTrainingConfig.step_plan` 与 `warmup_floor`。
- **为什么不依赖显卡**：`micro_batches = 样本数 // batch`、`steps_per_epoch = micro // 累积`、`total_steps = steps_per_epoch × 完整 epoch 数`——**全是整数除法**，输入只有"样本条数"与"超参"。
- **最容易拍脑袋的一项**：`warmup_ratio`。**机制**：`warmup_floor(total_steps)` 给出"至少生效一步"的比例下界，`step_plan` 直接在返回值里给出 `warmup_degenerate` 布尔量。实测 7/16/32 条偏好对的 `total_steps` 分别是 3/12/24，**三组的 `warmup_degenerate` 全为 `True`**。

**第二本账：资源账（day051 + day052）**

- **回答什么**：要训多少参数？占多少显存？多卡下每设备多少、每步要通信多少？
- **落点**：`peft/layers.py`（`lora_delta` / `matrix_rank`）、`peft/targets.py`（`MODEL_SPECS` / `parameter_check`）、`peft/qlora.py`（NF4 码本 + 分块 + 二级量化 → 每参数字节数）、`peft/memory.py`（`plan_memory` / `compare_strategies` 六项明细）、`peft/accelerate.py`（`plan_distributed`）。
- **为什么不依赖显卡**：显存 = 字节数之和，而字节数 = 参数量 × 每参数字节数。**参数量由模型规格决定，字节数由优化器与精度决定**，两者都是纯算术。
- **最容易拍脑袋的一项**：**优化器状态**。实测 `llama-2-7b` 全参策略里 AdamW 的优化器状态是 **53 907 324 928 字节**，占 75.3 GiB 总需求的约三分之二——比权重（13.5 GB）大四倍。**机制**：`plan_memory` 把它作为独立的一项列出来（`base_optimizer_bytes`），而不是揉进一个总数；`notes` 里明说"换成 `adamw_bnb_8bit` 可降到 2 字节/参数"。一个被单独列出来的数字才会被质疑，被揉进总数的数字只会被接受。

**第三本账：证据账（day053）**

- **回答什么**：这份适配器值不值得上线？涨了多少、有多少可能是巧合？
- **落点**：`finetune_eval/metrics.py`（六个文本分量）、`finetune_eval/compare.py`（Wilson / McNemar 精确 / 配对自助法）、`finetune_eval/model_probe.py`（白盒探针）、`finetune_eval/report.py`（`verify_manifest_binding` + 三项门禁）。
- **为什么不依赖显卡**：六个文本分量是字符级统计；探针用的是那套 557×557 参考模型；三种统计口径只有几十次浮点运算。
- **最容易拍脑袋的一项**：**样本量**。18 条用例、3 个不一致对，McNemar `p = 0.25`——**样本量决定了"能证明什么"，而它最容易被"多写几条用例就好"这种说法糊过去**。
- **机制**：
  1. `finetune_eval_suite_ratio` 按能力桶**分层**切分（保证每个桶都有评估用例），而不是随机切；
  2. 报告同时输出**三种口径**，让"效应量"与"显著性"分开展示；
  3. 三项门禁里有一条是 `execution`——**先保证评估本身能跑通**，再谈分数；
  4. 报告绑定评估集指纹，因此"换了一批用例所以分数变了"这种事不可能被误读成"模型变好了"。

**三本账的共同点**：**先立口径，再下结论。** 每一步都要能被手算复核（`37 // 2 = 18`、`r*(in+out)/(in*out)`、`int(3 × 0.03) = 0`），凡是能从公式独立算出来的数字就不要从实现里抄。

### 第 11 题（"没有绑定信息的分数不是证据"）

**1. 只写分数会出什么具体问题**

一个能真实发生的场景：team 里两个人各自跑了一次评估，报告里都写着"合格率 83.33%"，但：

- A 用的是 day050 那版评估集（18 条），B 用的是后来补到 24 条的版本；
- A 的适配器是 `checkpoint-120`，B 的是 `checkpoint-240`；
- 两人都不是恶意的，都只是在按当时的习惯跑脚本。

于是"83.33%"这个数字**无法被归因**：它既可能是"同一份文件被读了两次"，也可能是"两次不同的实验碰巧得到同一个分数"。更糟的情况是**评估集泄漏**：B 的评估集里混进了 A 的训练样本，分数被抬高，而报告上看不出任何异常。

**绑定信息就是把"分数"变成"证据"的那一步**：适配器哈希回答"是不是同一份权重"、基座与步数回答"是不是同一棵树上的同一个节点"、评估集指纹回答"是不是同一把尺子"。

**2. `adapter_content_hash` 为什么只覆盖配置与权重**

哈希要回答的问题是**"权重是不是同一份"**。训练状态（优化器动量、已完成步数、随机数状态）**随训练推进本来就会变**——把它算进哈希，会让"同一份权重"在不同步数下得到不同哈希，绑定信息当场失效。

反过来，训练状态是**续训与回滚**需要的东西，它由 `load_checkpoint` 消费，走的是另一条路径。两件事的消费者不同，就不该挤进同一个哈希。

**3. 在 day057 的领域数据集里的继承形式**

| day053 的绑定项 | day057 的对应字段（`DomainDataManifest`） |
|----------------|------------------------------------------|
| 适配器内容哈希 | `fingerprint`（数据集内容指纹：逐条 prompt 精确键按顺序拼接后的 SHA-1 前 16 位） |
| —（新增） | `parent_fingerprint`（父版本指纹，把版本串成链） |
| 基座名 | `config` 里的全部参数快照（含 `snapshot` 标签、"用哪一版代码生成的"） |
| 步数 | `stages` 六个阶段的进/出/丢弃/新增计数 |
| 评估集指纹 | `counts` / `groups` / `quality`（来源分布、配比与实际占比、质量分分布） |

**同一个思想的第三次出现**：day032 的成本报告要能归因到"哪次调用"、day053 的评估报告要能绑定"哪份权重与哪把尺子"、day057 的数据集清单要能说清"哪一版、按什么参数生成的"。**边界说法不同，纪律是同一条——报告必须自带它的坐标。**

## 第四部分：编程题

### 第 12 题（重做一次步数算术并核对 `warmup_floor`）

#### 参考实现

```python
"""day056 习题：DPO 步数算术 + warmup_floor 语义核对."""

from __future__ import annotations

from smart_research_agent.dpo.config import (
    DEFAULT_ACCUMULATION_STEPS,
    DEFAULT_BATCH_SIZE,
    DEFAULT_EPOCHS,
    DEFAULT_WARMUP_RATIO,
    DPOTrainingConfig,
    warmup_floor,
)


def hand_calc(train_pairs: int) -> dict:
    """按公式手算步数（不复用实现的返回值）."""
    micro = train_pairs // DEFAULT_BATCH_SIZE
    steps_per_epoch = micro // DEFAULT_ACCUMULATION_STEPS
    total_steps = steps_per_epoch * int(DEFAULT_EPOCHS)
    return {
        "micro": micro,
        "steps_per_epoch": steps_per_epoch,
        "total_steps": total_steps,
        "warmup_steps": int(total_steps * DEFAULT_WARMUP_RATIO),
        "effective_batch_size": DEFAULT_BATCH_SIZE * DEFAULT_ACCUMULATION_STEPS,
    }


cfg = DPOTrainingConfig()
print(f"默认配置：batch={cfg.per_device_train_batch_size} 累积={cfg.gradient_accumulation_steps} "
      f"epochs={cfg.num_train_epochs} warmup_ratio={cfg.warmup_ratio}")

for pairs in (7, 16, 32):
    plan = cfg.step_plan(pairs)
    manual = hand_calc(pairs)
    same = (
        plan["micro_batches_per_epoch"] == manual["micro"]
        and plan["optimizer_steps_per_epoch"] == manual["steps_per_epoch"]
        and plan["total_steps"] == manual["total_steps"]
        and plan["warmup_steps"] == manual["warmup_steps"]
        and plan["effective_batch_size"] == manual["effective_batch_size"]
    )
    print(f"{pairs:>3} 条：micro={plan['micro_batches_per_epoch']} "
          f"步/epoch={plan['optimizer_steps_per_epoch']} total={plan['total_steps']} "
          f"warmup={plan['warmup_steps']} 有效批={plan['effective_batch_size']} "
          f"退化={plan['warmup_degenerate']} 手算一致={same}")

print("\nwarmup_floor 语义核对：")
for total_steps in (3, 12, 30, 100):
    floor = warmup_floor(total_steps)
    assert int(total_steps * floor) >= 1, total_steps             # 下界：恰好生效一步
    just_below = max(0.0, floor - 1e-6)
    assert int(total_steps * just_below) == 0, total_steps        # 略小一档：退化为 0
    print(f"  total_steps={total_steps:>3} floor={floor:.6f} "
          f"重算={int(total_steps * floor)} 略小一档={just_below:.6f} → 0")
```

#### 实测输出

```text
默认配置：batch=2 累积=2 epochs=3.0 warmup_ratio=0.03

 train_pairs  micro  步/epoch  total  warmup    有效批     退化      手算一致
           7      3        1      3       0      4   True      True
          16      8        4     12       0      4   True      True
          32     16        8     24       0      4   True      True

warmup_floor 语义核对：
 total_steps       floor   重算 warmup   >=1      略小一档     退化为0
           3    0.333333           1  True  0.333332     True
          12    0.083333           1  True  0.083332     True
          30    0.033333           1  True  0.033332     True
         100    0.010000           1  True  0.009999     True

边界：total_steps 个位数时，3% 的 warmup_ratio 必然退化
    7 条偏好对 → total_steps=  3，int(3 × 0.03) = 0，退化=True，下限 = 0.3333
   16 条偏好对 → total_steps= 12，int(12 × 0.03) = 0，退化=True，下限 = 0.0833
   32 条偏好对 → total_steps= 24，int(24 × 0.03) = 0，退化=True，下限 = 0.0417
```

三点值得注意：

1. **三组数据的 `warmup_degenerate` 全为 `True`**——包括 32 条偏好对、24 步的那一组。这说明"小数据集上 warmup 不生效"不是个位数步数的特例，而是**步数在两位数量级时也依然成立**（下限 4.17% > 缺省的 3%）。
2. **`effective_batch_size` 恒为 4**（batch 2 × 累积 2）：它只取决于超参，与样本量无关。这正是"有效批大小"这个量的意义——**它描述的是"一次参数更新看多少条数据"，而不是"一共看了多少条"**。
3. **32 条偏好对时 `micro = 16`、`steps/epoch = 8`**：`16 // 2 = 8`，没有余数。但 7 条那一组 `3 // 2 = 1`、余 1，`pairs_dropped_per_epoch = 1`——**每 epoch 有 1 条偏好对被丢掉**（`drop_last`）。这也是 `step_plan` 会把 `pairs_dropped_per_epoch` 单独输出的原因：一条被丢掉的样本不会报错。

#### 为什么"`warmup_degenerate` 是一个布尔量"比"文档里写一句"更有价值"

三个层次：

1. **文档是"人读的"，布尔量是"机器可断言的"。** 写在文档里的句子无法进入 CI，也无法在**别的数据集**上自动重新判断。布尔量让"这次训练 warmup 生效了吗"变成一个能在每次计划里被检查的字段。
2. **布尔量把判断的执行者从"读文档的人"换成"写代码的人"。** 文档里那句话要求调用方**记得去读**；`step_plan` 的返回值要求调用方**看到它**——它就在你要消费的同一个对象里。**把结论放在消费点上，而不是放在参考文献里**，是接口设计的一条通用原则。
3. **它把一条"经验"变成了一条"可复核的算术"。** `warmup_degenerate = (int(total_steps × warmup_ratio) == 0)`，配上 `warmup_floor = 1/total_steps` 的下界，任何人两分钟就能验算一遍。day055 把**数值梯度核对**放进生产代码而不是测试文件，用的是同一条理由：

> **能在报告里被打印出来、被学员复现的断言，比只在 CI 里静默通过的断言更有价值。**
