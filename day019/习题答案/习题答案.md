## 第 1 题

**答案：C**

解析：initialize 响应携带四类信息——协议版本（双方收敛到共同版本）、`serverInfo`（实现名与版本号）、`capabilities`（能力声明）、`instructions`（给模型的使用说明）。**知识库内容绝不会在握手里下发**：握手的目的是交换"我会什么"的元数据，具体数据要等客户端按需 `resources/read` 时再取。这体现了一个普遍的协议设计原则——握手只交换协商所需的最小信息，载荷传输留给交互阶段，否则握手的成本会随数据量膨胀，客户端还没决定要不要用这些资源就已经被迫接收了它们。

## 第 2 题

**答案：C**

解析：MCP 把资源分两类列出：

- **静态资源**（无参数 URI，如 `research://knowledge/rag_overview` 这种固定地址）出现在 `resources/list`；
- **资源模板**（含 `{doc_id}` 这类参数）出现在 `resources/templates/list`，客户端拿到模板后自行填充参数再 `resources/read`。

这样分层的原因是：`{doc_id}` 的取值空间理论上无限，`resources/list` 如果要把所有实例列全，既不可能也无意义。模板机制让客户端先知道"地址长什么样、能填什么"，再按需实例化。我们的测试 `test_list_resource_templates` 验证的正是这一点。注意：Server 端**可以**额外为每个已知文档注册静态资源，让它们在 `resources/list` 里直接可见——这是体验优化，但模板本身永远只在 templates 列表里。

## 第 3 题

**答案：C**

解析：这正是教程第四章的核心设计。`calculate` 内部把 `CalculatorTool` 返回的 `"计算失败: ..."` 升级为 `raise ToolError(...)`，FastMCP 捕获后包装成 `CallToolResult(isError=true, content=[错误文本])`。三个要点：

- **A 错**：进程崩溃是 stdio 场景下最严重的故障——进程即连接，崩溃意味着客户端所有能力瞬间消失。Server 设计的第一原则就是"单个请求的失败被包含在单个响应里"。
- **B 错**：只回文本会让"算不了"和"算出了字符串"在协议上无法区分，客户端（及其背后的模型）只能靠自然语言猜测。`isError` 标志存在的意义就是让错误**结构化、可程序化判断**。
- **D 错**：框架不做自动重试。重试策略属于客户端或上层编排（比如未来 ReAct 循环可以捕获 `isError` 后换个表达式重试），Server 的职责是如实、清晰地报告失败。

测试 `test_calculate_error_returns_iserror` 还用"错误之后再成功调用一次"锁定了更强的性质：失败被隔离，会话未被破坏。

## 第 4 题

**答案：错**

解析：stdio 模式下 stdout 是**唯一的协议通道**，客户端对 stdout 的处理不是"区分日志和消息"，而是把每一行都当作 JSON-RPC 消息解析——混入任何日志行都会直接产生解析错误，握手都无法完成。本项目实测踩过这个坑：项目 logger 默认把控制台日志写 `sys.stdout`，stdio 客户端一连就收到 GBK 编码的日志行，协议解析立刻抛 `UnicodeDecodeError`。

正确做法是 `full_server.py` 入口里的让路逻辑：stdio 模式启动前把指向 stdout 的 `StreamHandler` 重定向到 `sys.stderr`。stderr 在 stdio 传输中完全自由——客户端通常把它接到自己的日志面板，是诊断信息的合法出口。铁律：**stdio 服务的 stdout 永远纯净，日志只去 stderr 或文件。**

## 第 5 题

**答案：对**

解析：MCP 的会话生命周期里，shutdown 阶段没有专门的应用层消息，**传输层的结束就是会话的结束**：stdio 下 stdin 关闭（或子进程退出）即结束，SSE 下 HTTP 连接断开即结束。这个设计的推论是：Server 必须能容忍客户端**随时、无预告地消失**——不能假设会收到"再见"通知才做清理。这与 TCP 的设计哲学相通：连接可能因断电、断网在任何时刻中断，依赖优雅告别消息的协议是脆弱的。对服务端编码的实际影响是：不要依赖析构时机做关键操作，状态要能承受会话的突然终止。

## 第 6 题

**答案：错**

解析：`create_connected_server_and_client_session` 的名字里有"connected"，但它建立的是**同进程内的内存流**（memory streams）——客户端对象和服务器对象通过 anyio 的内存管道直接相连，没有子进程、没有 stdio、没有任何真实传输层。这是刻意的取舍：

- **它验证了**：完整的协议状态机（握手、能力协商、方法分发、错误包装）和我们的业务逻辑——因为消息走的仍是真实的 JSON-RPC 序列化与协议处理代码。
- **它不验证**：stdio 的管道行为（如 stdout 污染问题）、SSE 的 HTTP 语义、端口监听、子进程生命周期。

所以两种测试互补而非替代：内存会话测试快速、离线、确定性地覆盖协议逻辑（FIRST 原则）；真实 stdio 冒烟（如第 10 题）覆盖传输集成。教程 5.5 节讲过这个原则：**测自己的逻辑，信任并隔离外部依赖**——传输层的正确性是框架的责任，框架自己测过。

## 第 7 题

**参考答案**：

**（1）维护性好处**：业务逻辑保持**单点存在**。算术求值的安全规则（AST 白名单、允许的运算符集合）只写在 `tools/calculator.py` 一处。未来修复计算 bug、增加运算符、收紧安全策略，都只改这一个文件，ReAct Agent 和 MCP Server 两个消费方同时受益，不存在两处实现漂移的风险。同时职责清晰：`calculator.py` 不知道 MCP 的存在，`full_server.py` 不知道 AST 的细节——协议层薄薄地包在业务层外面，这是 day001 以来关注点分离主线的延续。

**（2）为什么转成 ToolError**：核心是**保住错误的结构化语义**。`"计算失败: ..."` 是一段自然语言文本，客户端收到后无法程序化地区分"这是结果"还是"这是失败"——模型只能靠阅读理解去猜。`ToolError` 让框架返回 `isError=true` 的 CallToolResult，客户端代码可以直接写 `if result.isError: ...` 走失败分支（比如让模型换个表达式重试，或在报告中标注"该数据未能核算"）。一句话：**协议适配层的职责是把业务语义无损地翻译成协议语义，把结构化信息降级成文本是适配层的失职。** 反过来，错误文本本身仍然重要——它会进模型上下文，所以 `ToolError` 携带的是那句精心设计的人话，而不是原始 traceback。

## 第 8 题

**参考答案**：

**（1）选 stdio。** 理由逐条命中 stdio 的特性：同机、单客户端、生命周期与 Agent 绑定——"随 Agent 启动、随 Agent 退出"正是 stdio 的父子进程模型天然提供的语义，零部署成本（不需要服务注册、端口管理、守护进程）；不监听任何端口，零网络攻击面，无需鉴权；进程间管道延迟最低。用 SSE 反而要引入一整套本不需要的运维负担。

**（2）选 SSE。** 逐条命中 SSE 的特性：多客户端共享同一实例（十几个人的 Agent 连接同一个服务端点）；知识库实时更新要求"一份数据、全员可见"，stdio 的一对一模型会让每个 Agent 拉起一个带本地副本的 Server，数据一致性无从谈起；独立常驻服务的生命周期与任何客户端无关，知识库可以后台持续更新。同时要意识到代价：监听端口带来了新的责任——至少要约束绑定地址、评估鉴权需求（MCP 支持 OAuth，更后期的内容），并用 Docker 等手段把服务运维化（day022 的主题）。

经验法则收尾：**同机、单用户、随用随起 → stdio；跨机、多用户、常驻共享 → SSE。**

## 第 9 题

**参考实现**：

在 `create_server()` 中、`research_report` 之后新增：

```python
    @app.prompt()
    def compare_frameworks(frameworks: str) -> str:
        """对逗号分隔的多个框架做四维度对比分析."""
        return (
            f"请对以下框架做系统的对比分析：{frameworks}\n"
            "要求：\n"
            "1. 从易用性、生态、文档质量、社区活跃度四个维度逐一评估；\n"
            "2. 每个维度给出具体证据，不要泛泛而谈；\n"
            "3. 最终结论用 Markdown 表格呈现，行是框架、列是维度；\n"
            "4. 表格之后给出一段选型建议。"
        )
```

`capability_descriptors()` 的 prompts 列表补充：

```python
            PromptDescriptor(
                name="compare_frameworks",
                description="对逗号分隔的多个框架做四维度对比分析",
                arguments=[{"name": "frameworks", "description": "逗号分隔的框架名", "required": True}],
            )
```

测试（`TestCapabilityListing` 中追加或新开类）：

```python
    async def test_list_prompts_includes_compare(self):
        server = create_server()
        async with create_connected_server_and_client_session(server) as session:
            await session.initialize()
            prompts = await session.list_prompts()
            names = sorted(p.name for p in prompts.prompts)
            assert names == ["compare_frameworks", "research_report"]

    async def test_get_compare_prompt(self):
        server = create_server()
        async with create_connected_server_and_client_session(server) as session:
            await session.initialize()
            result = await session.get_prompt("compare_frameworks", {"frameworks": "A,B"})
            text = result.messages[0].content.text
            assert "A,B" in text
            for dimension in ("易用性", "生态", "文档质量", "社区活跃度"):
                assert dimension in text
```

解析：本题练的是三类能力中最轻量的一类的完整闭环——**声明（装饰器）、文档（静态 Descriptor）、验证（列出 + 获取两个测试）**。两个细节值得注意：其一，`prompts/list` 只验证名字的集合，而 `prompts/get` 验证渲染结果包含入参与关键约束——前者测"注册了对的能力"，后者测"参数真的被填进了模板"，缺一个都不算闭环；其二，测试中对四个维度逐个断言，而不是只断言 `"A,B" in text`，因为 prompt 模板最容易在后续编辑中丢约束，维度断言把"四维度对比"这个业务需求固化成了回归守卫。

## 第 10 题

**参考实现**（`scripts/mcp_stdio_smoke.py`）：

```python
"""MCP Server 的真实 stdio 链路冒烟脚本：以子进程拉起 Server 并走完整握手."""

from __future__ import annotations

import asyncio
import sys

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client


async def main() -> int:
    params = StdioServerParameters(
        command=sys.executable,
        args=[
            "-m", "smart_research_agent.mcp_server.full_server",
            "--transport", "stdio",
        ],
    )
    async with stdio_client(params) as (read, write):
        async with ClientSession(read, write) as session:
            result = await session.initialize()
            print(f"serverInfo.name = {result.serverInfo.name}")
            print(f"instructions = {result.instructions[:30]}...")

            tools = await session.list_tools()
            print(f"tools = {[t.name for t in tools.tools]}")

            ok = await session.call_tool("calculate", {"expression": "6 * 7"})
            assert ok.isError is False and ok.content[0].text == "42"
            print("calculate 6*7 -> 42  ✓")

            bad = await session.call_tool("calculate", {"expression": "1 / 0"})
            assert bad.isError is True
            print(f"calculate 1/0 -> isError=True ({bad.content[0].text[:20]}...)  ✓")
    return 0


if __name__ == "__main__":
    raise SystemExit(asyncio.run(main()))
```

在项目根目录（`smart-research-agent/`）下运行 `python scripts/mcp_stdio_smoke.py`，输出握手信息、工具列表和两行 `✓`，退出码 0。

解析：这个脚本与内存会话测试的差异就是第 6 题论证的互补关系，此处亲手验证一遍：

- **内存会话测试**验证协议逻辑——握手内容、能力列表、错误路径，快速、离线、确定性，适合进 CI 全量跑；
- **stdio 冒烟脚本**额外验证**传输集成**——子进程真的能被拉起、stdout 协议通道真的纯净（如果有人在代码里加了一句往 stdout 的 `print`，内存测试不会发现，这个脚本会在握手时立刻炸掉）、模块入口的 argparse 真的接对了参数。

两者都不能省：只有内存测试，传输层的回归无人看守；只有冒烟脚本，协议逻辑的细节断言（比如 `instructions` 的精确内容）在子进程场景下写起来笨重且慢。工程上的常见配比是：**大量内存/单元测试 + 少量真实链路冒烟**——这正是 day002 测试金字塔在协议项目上的具体形态。
