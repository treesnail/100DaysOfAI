## 第一部分：选择题

### 第 1 题（反思的必要性）

以下哪一项**不是**纯 ReAct 循环面对工具失败时的典型失控模式？

- A. 原样重试：不理解失败原因，把几乎相同的输入再发一遍
- B. Panic 式乱撞：反复失败后换不存在的工具或编造答案
- C. 静默成功：工具失败后模型无视错误直接输出正确答案
- D. 耗尽步数：在"合理但无效"的打转中用完 max_steps

### 第 2 题（重试次数语义）

`Reflector(max_retries=2)` 装配到一个任务上，该任务每一轮尝试都失败。整个 `agent.run()` 过程中，Agent 的 LLM 和 Reflector 的 LLM 分别被调用多少次？

- A. Agent 2 次，Reflector 2 次
- B. Agent 3 次，Reflector 2 次
- C. Agent 2 次，Reflector 3 次
- D. Agent 3 次，Reflector 3 次

### 第 3 题（软着陆解析）

LLM 的反思输出为 `"复盘如下：{\n 不合法的 JSON"`（有 `{` 但内容损坏且没有配对的 `}` 在后）。`parse_reflection` 的行为是：

- A. 抛出 `ReflectionParseError`
- B. 抛出 `json.JSONDecodeError`
- C. 返回 `(原文整段, "")`，不抛任何异常
- D. 返回 `("", "")`

## 第三部分：问答题

### 第 7 题（两种解析哲学）

day010 的 `parse_plan` 解析失败会抛 `PlanParseError`，今天的 `parse_reflection` 解析失败却用原文兜底、绝不抛异常。请解释：为什么同一个项目里对两种 LLM 输出采用截然相反的解析策略？判断"该抛异常还是该兜底"的依据是什么？

### 第 8 题（快速失败 vs 循环内自愈）

启用 reflector 后，工具一旦报错就立即中断本轮、转入反思，不再给模型循环内自愈的机会。请说出这个设计的一个优点和一个代价，并说明为什么"不传 reflector 走自愈、传了走快速失败"是合理的工程折中。

### 第 9 题（建议注入策略）

当前实现中，第 3 轮尝试只注入第 2 次反思的 suggestion，不累积历史反思。如果模型"每一轮犯不同的错误"，这个策略会有什么盲区？你会怎么改进？改进的代价是什么？

## 第四部分：编程题

### 第 10 题（用结构化工具结果替代文本前缀嗅探）

教程 2.4 节坦白了一个工程妥协：`_ERROR_PREFIXES` 靠字符串前缀嗅探工具失败，可能误判。请动手修正它，要求：

**功能要求**：

1. 在 `smart_research_agent/tools/base.py` 中新增 `@dataclass ToolResult`，字段为 `success: bool` 和 `output: str`。
2. 修改 `CalculatorTool.execute`，让它返回 `ToolResult`：计算成功时 `ToolResult(success=True, output=str(result))`，失败时 `ToolResult(success=False, output=f"计算失败: {exc}")`。
3. 修改 `ReactAgent._execute_tool`：工具不存在时返回 `ToolResult(success=False, ...)`；调用 `tool.execute` 拿到 `ToolResult` 后，把 `output` 作为 Observation 文本，把 `success` 作为失败判定的依据，`_attempt` 中的 `observation.startswith(_ERROR_PREFIXES)` 嗅探改为直接使用这个布尔值。
4. 修改后 `_ERROR_PREFIXES` 常量应被删除。

**兼容性提示**：`run()` 的返回值和 Observation 的文本格式保持不变，这样 `tests/test_react_loop.py` 和 `tests/test_reflexion.py` 里基于文本的断言（如 `"不存在" in m.content`、`"失败" in answer`）不需要改动。

**测试要求**：

- 新增一个用例：构造一个"正常输出文本恰好以'计算失败'开头"的工具（模拟教程 2.4 节的误判场景），验证在新机制下它**不会**被误判为失败。
- 跑全部测试确认无回归。

**提示**：

- `_execute_tool` 的返回类型要从 `str` 改成 `ToolResult`，它的调用方 `_attempt` 里取 `observation = result.output`、`tool_ok = result.success`。
- 思考：为什么"成功标志"应该由工具自己声明，而不是由 Agent 猜测？这和"解析 LLM 输出必须锁定结构"是不是同一条原则？
