## 第一部分：选择题

### 第 1 题（下游只认识一种东西）

`Document` 里同时保留了 `text`（全文）与 `blocks`（块序列）。为什么不只留全文？

- A. 为了让报告看起来更详细
- B. **因为下游需要"结构"**：day062 要按标题切、代码块不能被切开、表格要保留行列
- C. 因为全文的计算成本太高，块序列是缓存
- D. 因为 `text` 可能被截断，`blocks` 才是完整的

### 第 2 题（`doc_id` 的性质）

`doc_id = sha256(规范化全文)[:16]`。下列哪一条**不是**它成立的性质？

- A. 同一份内容从两个路径读进来会得到同一个 `doc_id`
- B. 改一个字节，`doc_id` 就变
- C. **`doc_id` 相同就说明两份文件的文件名也相同**
- D. `doc_id` 不包含文件名、路径与时间，因此它回答的是"这是哪份内容"而不是"它放在哪"

### 第 3 题（类型识别）

一份名为 `report.txt` 的文件，头四个字节是 `%PDF`。本模块的处理是：

- A. 按后缀当成纯文本解析，并在日志里记一条警告
- B. 抛 `UnsupportedDocument`（后缀与内容矛盾）
- C. **按内容当成 PDF 解析，并把 `conflict=True` 记进文档元数据**
- D. 拒绝解析并要求用户改名

### 第 4 题（编码探测链）

`latin-1` 排在编码探测链的最后一步，原因是：

- A. 它的编码表最完整
- B. 它是中文文档的常见编码
- C. **它永不失败（任何字节序列都是合法 latin-1），因此只能最后一步，且结果必须标记 `confident=False`**
- D. 它的解码速度最快

### 第 5 题（三类状态）

入库报告把"与前一份文档内容相同"记成 `duplicate` 而不是 `ok`，核心理由是：

- A. 重复文件会占用更多磁盘
- B. **"这一批里有几份是重复内容"是一个数据治理问题，不是一个失败问题**；分开才能回答"该去补数据还是该去查错误"
- C. 重复文件一定是上传错误
- D. 为了让 `status_counts` 的三个键都有值

## 第二部分：判断题

### 第 6 题

`normalize_text` 不做 Unicode 规范化（不把全角逗号换成半角）。
因此 `"第一，第二"` 与 `"第一,第二"` 会得到**两个不同的 `doc_id`**，
而这是刻意的：中英文混排的技术文档里全角标点常是内容差异而不是格式差异。（对 / 错）

### 第 7 题

UTF-32-LE 的 BOM 是 `FF FE 00 00`，它以 UTF-16-LE 的 BOM（`FF FE`）开头。
因此 BOM 的匹配表**必须把 UTF-32 排在 UTF-16 之前**；写反的表现是
"每个字符后面跟一个 NUL"的乱码。（对 / 错）

### 第 8 题

`Document.metadata` 里的 `docx_parts_not_read` 记录了"本模块读不到的部件"
（页眉页脚、脚注、批注……）。这条信息可以省略，因为使用者只要知道
"文档解析成功了"就够了。（对 / 错）

## 第三部分：简答题

### 第 9 题（能力边界为什么必须写下来）

本模块有好几处刻意的"拒绝"与"声明"：

```text
加密 PDF        → 抛 UnsupportedDocument（而不是返回一堆乱码）
Identity-H 字体 → 元数据里 pdf_cid_font_detected=true + 一条 §9.10.2 的告警
编码没把握      → encoding_confident=false
DOCX            → docx_parts_not_read 列出读不到的部件
```

请回答四个问题：

1. 为什么"返回一堆乱码"比"拒收"更糟？请用**乱码会经过哪些环节**来说明；
2. `pdf_cid_font_detected` 这条字段会在三个月后回答什么问题？
   如果没有它，排查会从哪里开始、又会在哪里卡住？
3. 为什么同一条边界要写在**三个地方**（元数据字段、告警文本、`pdf_boundaries()`
   的 `not_supported` 列表）？三处的内容会不会不一致？靠什么保证它们一致？
4. 请举一个**不属于**"能力边界"而属于"我们自己的 bug"的例子，
   并说明为什么这两者必须被分开处理（提示：批量入库的 `except` 只捕一类异常）。

## 第四部分：编程题

### 第 10 题（用"会变红的机制"钉住四件事）

在 day061 快照的基础上写一个脚本或测试文件（离线、确定性，不联网、
不写盘、不依赖第三方库），完成四件事：

1. **验证归一化与内容指纹**
   - 断言 `normalize_text("a\r\nb") == normalize_text("a\nb\n") == "a\nb\n"`；
   - 断言 `"第一，第二"` 与 `"第一,第二"` 的 `content_id` **不同**（不做 Unicode 规范化）；
   - 断言 `make_document` 的调用签名里**没有** `text` 参数（用 `inspect.signature`），
     并断言文档的 `text` 等于按块拼出的结果；
2. **验证类型识别与编码链**
   - 构造 `("fake.txt", b"%PDF-1.4\n")`，断言 `media_type == "application/pdf"`、
     `conflict is True`、`decided_by == "magic"`；
   - 断言 `detect_media_type("a.docx", b"PK\x03\x04x")` 的 `conflict is False`；
   - 断言 `decode_bytes("中文".encode("gb18030")).encoding == "gb18030"`；
   - 断言 `decode_bytes(b"\x80\x80").confident is False`，且
     `decode_bytes(b"\xff\xfe" + "小端".encode("utf-16-le")).encoding == "utf-16-le"`；
3. **验证五个加载器各自的最小样本**
   - Markdown：`"# 标题\n\n正文\n\n- 项\n\n> 引\n\n```python\nx=1\n```\n"` →
     块类型必须是 `[heading, paragraph, list_item, quote, code]`，
     且代码块的 `language == "python"`；
   - HTML：`"<body><script>bad</script><h1>标题</h1><p>正文 &amp; 实体</p></body>"` →
     文本里**不含** `bad`、含 `&`（实体已解码）、首块是 `heading` 且 `level == 1`；
   - DOCX：用 `zipfile` 手工造一份含 `word/document.xml` 的包
     （一个 `w:pStyle=Heading1` 的段落 + 一个普通段落），断言块类型是
     `[heading, paragraph]` 且 `level == 1`；
   - PDF：用手工构造的未压缩 PDF（`BT /F1 12 Tf 72 720 Td (Hello) Tj ET`），
     断言文本里含 `Hello`，且 `pdf_inflated_streams == "0"`、`pdf_warnings == ""`；
   - 断言一份 `b"\x00\x01"` 的 `.txt` 抛 `UnsupportedDocument`；
4. **验证批量入库的三类状态**
   - 用同一个内容、两个文件名 + 一份二进制 + 一份假 PDF 组成 4 个文件；
   - 断言 `status_counts() == {"ok": 1, "duplicate": 1, "error": 2}`；
   - 断言 `unique_documents == 1`，且重复条目的 `duplicate_of` 指向第一个文件名；
   - 断言把同一批文件**顺序反转**时，去重后的 `doc_id` 集合不变
     （即"顺序只影响谁被留下，不影响有哪些内容"）。

要求给出完整可运行的代码，并回答：**第 4 条里"顺序反转后 `doc_id` 集合不变"
这条性质为什么值得单独断言？** 它保护的是哪一类未来的改动？
