## 第 1 题

**答案：B**

解析：LLM 是无状态的——每次 API 请求都是一次独立调用，模型本身不保存任何会话状态。"记住名字"的真相是：服务端把完整对话历史（你的第一条消息、AI 的回答、你的第二条消息）一起打包发给了模型，模型从历史中"读"出了答案。A 错误，模型权重在推理时不会被改写；C 错误，记忆数据库存在于应用层而非模型内部；D 混淆了 Web 会话机制与模型工作机制。

## 第 2 题

**答案：C**

解析：开场白里的订单号处在会话的**最老**位置，FIFO（A）和滑动窗口（B）都会最先把它丢弃——这正是教程中"用户说过对花生过敏，后来被推荐花生酱"的同类事故。摘要压缩（C）把老消息压缩成摘要，关键事实（订单号）能以摘要形式长期留存。D 在长会话下会撞上下文窗口上限且成本失控。注意：如果是 SmartResearch Agent 这种短任务场景，FIFO 才是更优解——**策略选择取决于信息的生命周期价值**。

## 第 3 题

**答案：B**

解析：system 消息与 user/assistant 消息地位不对等：它不是"对话内容"，而是 Agent 的行为契约——ReAct 的输出格式要求、可用工具清单、角色设定都在里面。一旦 FIFO 把 system 也淘汰，模型会立刻忘记格式，解析器开始抛 `ReActParseError`，整个循环崩坏。A 是结果不是原因；C 是无稽之谈；D 即使是某些 API 的约束，也只是表层原因，根本原因是契约不能丢。

## 第 4 题

**答案：C**

解析：`-0 == 0`，所以 `lst[-0:]` 等价于 `lst[0:]`，即从头到尾整个列表。负数切片里"0"没有负值形式，这是 Python 切片的著名边角。教程中 `ShortTermMemory._truncate()` 用 `if keep else ...` 显式分支处理 `keep=0` 的情形，正是为了避开这个坑——如果直接写 `others[-keep:]`，当 `keep` 为 0 时会把**全部**消息保留下来，截断彻底失效。

## 第 5 题

**答案：错**

解析：无状态是主动的**架构设计选择**，不是技术局限。无状态服务意味着任何请求可以被任意服务器处理，带来水平扩展自由、容错简单、负载均衡容易三大红利——这正是大模型服务支撑海量并发的基础。代价是状态管理责任转移给应用层，也就是我们今天实现的记忆系统。

## 第 6 题

**答案：对**

解析：这是防御性拷贝（Defensive Copy）。如果返回内部列表本体的引用，调用方拿到后可以直接 `append`/`remove`，绕过 `add()` 里的截断逻辑，"长度 ≤ max_messages"的不变量就被外部打破了，封装形同虚设。`list(self._messages)` 拷贝的是列表容器（元素 Message 是共享的，但 Message 是不可变风格的 dataclass，只读使用安全），成本极低，换来的是封装完整性。

## 第 7 题

**答案：错**

解析：三个理由。其一，窗口由输入输出共享，历史塞满意味着留给回答的 token 变少；其二，成本按输入 token 线性计费，每轮都在为全部历史重复付费；其三，也是最容易忽视的——"中间遗忘"（Lost in the Middle）现象：模型对上下文中间部分的信息利用率显著低于开头和结尾，无脑堆砌历史反而降低关键信息被注意到的概率。**更多历史 ≠ 更好回答，精挑细选的历史才是。**

## 第 8 题

**参考答案**：

用条数的好处：

1. **确定性**：条数是整数，截断行为完全可预测，测试断言可以直接写"长度 == 4"。
2. **零依赖零开销**：不需要 tokenizer，数列表长度是 O(1)。
3. **模型无关**：同一份代码服务任何后端模型。

用 token 数的代价：

1. 需要引入**具体模型对应的 tokenizer**（如 tiktoken），且不同模型词表不同——token 计数必须与目标模型严格匹配，换模型就要换计数器。
2. 每次截断都要对所有消息编码计数，增加**计算开销和代码复杂度**。
3. 边界情况变多：一条超长消息（如贴入一整篇文档）可能独占大半个窗口，截断策略需要处理"单条超限"这种条数方案里不存在的问题。

值得切换的场景：消息长度方差极大时（如 Agent 经常把整份文档、长网页正文塞进 Observation），"条数"与真实 token 消耗严重脱钩，20 条短消息和 20 条长文档对窗口的压力天差地别——此时按 token 预算截断才是对成本和窗口的诚实管理。

## 第 9 题

**参考答案**：

按 user_id 隔离的两个具体问题：

1. **同一用户的多话题污染**：用户同时开两个窗口，一个调研 RAG、一个问红烧肉做法，两份上下文混在一起，模型会在 RAG 问题里带出红烧肉的语境（上下文串扰），两个话题的回答质量都受损。
2. **会话生命周期缺失**：按 user_id 的记忆没有"开始/结束"概念——昨天的对话和今天的对话堆在一起，越长越臃肿，且用户无法获得"开一个新对话"的清爽体验；也无法单独清理某次会话的历史（隐私合规要求"删除某次对话"时做不到）。

按 session_id 隔离如何解决：

- 每个话题/对话一个独立 session，天然按话题隔离，同一用户可并行多会话互不干扰；
- 会话有明确生命周期（`create_session` → 活跃 → `close_session`），可单独销毁、可单独导出，配合 uuid 的不可猜测性，还顺带获得了会话级的访问边界。

一句话：**用户是"谁在说"，会话是"在说什么"——隔离应该按话题（说什么）而不是按身份（谁）。**

## 第 10 题

**参考答案**：

`smart_research_agent/memory/pairwise.py`（或在测试文件中就地实现）：

```python
"""成对淘汰的短期记忆：ReAct 场景下 Action/Observation 必须同生共死."""

from __future__ import annotations

from smart_research_agent.llm.base import Message


class PairwiseMemory:
    """截断时 system 保留，其余消息按 user/assistant 对从最老开始淘汰."""

    def __init__(self, max_messages: int = 20):
        if max_messages < 2:
            raise ValueError("max_messages 至少为 2")
        self.max_messages = max_messages
        self._messages: list[Message] = []

    def add(self, message: Message) -> None:
        self._messages.append(message)
        self._truncate()

    def get_all(self) -> list[Message]:
        return list(self._messages)

    def _truncate(self) -> None:
        if len(self._messages) <= self.max_messages:
            return
        system_msgs = [m for m in self._messages if m.role == "system"]
        others = [m for m in self._messages if m.role != "system"]
        keep = max(self.max_messages - len(system_msgs), 0)
        keep -= keep % 2  # 只保留整数对，保证成对淘汰
        self._messages = system_msgs + others[-keep:] if keep else system_msgs[: self.max_messages]
```

`tests/test_memory_pair.py`：

```python
"""成对淘汰记忆测试."""

from __future__ import annotations

from smart_research_agent.llm.base import Message


def _pair(mem, i: int) -> None:
    """加入一对 user/assistant 消息."""
    mem.add(Message(role="user", content=f"u{i}"))
    mem.add(Message(role="assistant", content=f"a{i}"))


class TestPairwiseMemory:
    def test_under_capacity_no_truncation(self):
        from smart_research_agent.memory.pairwise import PairwiseMemory

        mem = PairwiseMemory(max_messages=6)
        mem.add(Message(role="system", content="sys"))
        _pair(mem, 0)
        assert len(mem.get_all()) == 3  # 未满容量，原样保留

    def test_pairwise_eviction(self):
        from smart_research_agent.memory.pairwise import PairwiseMemory

        mem = PairwiseMemory(max_messages=5)
        mem.add(Message(role="system", content="sys"))
        for i in range(3):
            _pair(mem, i)  # sys + 3 对 = 7 条，超出容量
        all_msgs = mem.get_all()
        assert len(all_msgs) == 5  # sys + 2 对
        contents = [m.content for m in all_msgs]
        assert "u0" not in contents and "a0" not in contents  # 最老一对整对淘汰
        assert "u1" in contents and "a1" in contents
        assert "u2" in contents and "a2" in contents

    def test_system_always_first(self):
        from smart_research_agent.memory.pairwise import PairwiseMemory

        mem = PairwiseMemory(max_messages=3)
        mem.add(Message(role="system", content="sys"))
        for i in range(4):
            _pair(mem, i)
        assert mem.get_all()[0].role == "system"
        assert len(mem.get_all()) == 3  # sys + 1 对
```

要点解析：

- 与原版 `_truncate()` 的唯一差异是 `keep -= keep % 2`：把保留条数向下取整到偶数，保证 `others[-keep:]` 切出来的必然是完整的若干对，不会留下"半对"孤儿消息。
- `if keep else ...` 分支依然必须保留——`others[-0:]` 是整个列表的切片陷阱（第 4 题）。
- 测试用 `_pair()` 辅助函数表达"成对加入"的语义，比裸写六次 `add()` 更能传达意图；三个用例分别锁定：未满不截断、超量成对淘汰且总数封顶、system 钉在头部。
- 这道题的现实意义：day006 的 ReAct 循环每步恰好追加"assistant 的 Thought/Action + user 角色的 Observation"两条消息，成对淘汰才能保证任何时刻上下文里的 Action 和 Observation 都成对完整。
