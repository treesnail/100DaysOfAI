## 第一章：为什么"能跑"不等于"成体系"

### 1.1 day058 留下的伏笔

day058 的结语里写着：

> **实验追踪**：现在的指标散在 `ModelVersion.metrics` 与各阶段的报告里，
> day059 会把它们收进一个追踪器（实验参数、指标、产物的统一记录）；
> **流水线集成**：今天的手动/脚本触发会在 day059 变成一条端到端 MLOps
> 流水线，并接入 GitHub Actions。

今天兑现它。先看清楚"散"在哪里：

| 证据 | 谁产生的 | 存放在哪 |
|------|---------|---------|
| 超参与数据指纹 | `SFTTrainingArgs` / `DomainDataManifest` | `outputs/sft/*/training_args.json` |
| 逐步 loss | `SFTTrainer` 的 `StepRecord` | `train_log.jsonl` |
| 适配器内容哈希 | `peft.trainer` | `adapter_manifest.json` |
| 合格率与门禁结论 | `finetune_eval` | `outputs/finetune_eval/*.json` |
| 版本记录 | `registry`（day058） | `outputs/registry/versions.jsonl` |

五份证据各自可复现，但它们回答不了跨实验的问题：**"这两次训练差在哪、
哪一次更好、能不能发"**。

### 1.2 三条贯穿全包的纪律

| 纪律 | 具体表现 | 反例（如果没有它） |
|------|---------|------------------|
| **"出错"与"做不到"分开报** | 门禁拦下发布时 `publish` 是 `blocked`，`failed` 为 `False` | CI 的红灯掩盖真正需要看的那份门禁报告 |
| **缺失就是缺失** | `Run.metric` 返回 `None`；门禁缺指标时判**不通过** | "因为没测延迟所以延迟门禁通过" |
| **文档与实现同源** | 门禁表/阶段表/CI 摘要现场读出，**仓库里的 workflow 由渲染器生成** | YAML 里的阈值悄悄漂移，没人知道谁是权威 |

第二条有一处必须说清的**反直觉**细节：同样面对"缺数据"，两类判定的结论
**相反**。

```text
相对判定（day058 evaluate_candidate）：缺数据 → 只能说"不知道"（gain = None）
绝对判定（今天 evaluate_gates）：      缺数据 → 必须说"不行"（不通过）
```

理由：相对判定问的是"候选比当前更好吗"，缺一个分数就没有可比的基准；
绝对判定问的是"这份产物够格发布吗"，**没有证据本身就是不发布的理由**。
把两者合并的那一天，就会出现上面那个"没测延迟所以通过"的事故。

## 第二章：阶段表 —— 把"顺序即策略"变成可校验的结构

### 2.1 六阶段的声明

day046 的 `integration/pipeline.py`、day057 的 `domain_data/pipeline.py`、
day058 的 `registry/retrain.py` 都讲过"顺序即策略"，但三处都只是
**注释里的约定**。今天把它做成数据结构：

```python
@dataclass(frozen=True)
class StageSpec:
    name: str
    description: str
    requires: tuple[str, ...] = ()
    produces: tuple[str, ...] = ()
```

实测（demo 第 1 节）：

```text
  1. ingest    依赖 ['（无）'] → 产出 ['dataset_fingerprint']
     确认数据集指纹与基线：没有指纹的产物三个月后说不清来路
  2. train     依赖 ['dataset_fingerprint'] → 产出 ['adapter_sha256']
     调用训练回调，产出适配器（内容哈希是版本三元组的一半）
  3. evaluate  依赖 ['adapter_sha256'] → 产出 ['metrics']
     在领域评估集上评估适配器，产出指标（门禁唯一的判据来源）
  4. gate      依赖 ['metrics', 'adapter_sha256'] → 产出 ['gate_report']
     按发布门禁策略做绝对判定：不通过则 publish 被阻塞
  5. package   依赖 ['metrics', 'gate_report'] → 产出 ['model_card']
     生成模型卡与发布清单（产物要能自描述）
  6. publish   依赖 ['adapter_sha256', 'model_card', 'gate_report'] → 产出 ['version']
     把版本登记进注册表并提升为 stable（**上线是显式动作**）

主链：ingest → train → evaluate → gate → package → publish
依赖表自检：通过
```

### 2.2 `validate_stage_order` 抓住两类错误

它逐条检查"每个 `requires` 都能在**它之前**的 `produces` 里找到"。
实测能抓住顺序写错：

```text
  依赖写错的表被拒：阶段 publish 依赖了尚未产出的 adapter：顺序即策略——
  把产出它的那一步挪到前面，或者把依赖写对
```

**第二类错误更值钱：依赖漏写。** 给 `package` 加一个对 `metrics` 的依赖、
却忘了写进 `requires`，平时不会报错——只会在某次运行时出现 `KeyError`，
而那时的堆栈指向阶段内部的某一行，不是"依赖表漏了一项"。

一次构造期校验把这两类问题都变成**启动即失败**。

### 2.3 主链的取法：多个上游时取**最靠后**的那一个

`publish` 同时依赖 `adapter`（train）、`gate_report`（gate）与
`model_card`（package）。若取"第一个上游"，主链会变成
`ingest → train → publish`——**它漏掉了评估与门禁**。

因此 `critical_path` 在多个上游里取序号最大的那个：

```python
upstream = [produced_by[item] for item in spec.requires if item in produced_by]
current = max(upstream, key=lambda name: order[name]) if upstream else None
```

这条规则被一条断言直接钉住（`test_critical_path_uses_the_latest_upstream`），
它同时断言 `path != ["ingest", "train", "publish"]`——**把错误答案也写进断言**，
这样将来有人"简化"这段代码时会立刻变红。

### 2.4 一处被删掉的检查

第一版还有第五条判据："至少要有一个无依赖阶段，否则流水线永远开不了头"。
覆盖率报告指出它**不可达**：第一个阶段的 `requires` 必须落在空集里，
因此它必然为空。于是它被删掉了，理由写进了 docstring：

> **一条恒为真的断言不是保护，而是噪声。** 它会让人以为存在某种未被覆盖的
> 情形，从而在别处写出多余的兜底代码。

这一条与 day058 里"为覆盖率把 `verify_data` 提到模块级"是同一枚硬币的两面：
覆盖率报告的价值不只是"补测试"，它还会告诉你**哪些代码是多余的**。

## 第三章：门禁 —— 六项检查与三类结果

### 3.1 与 day058 的采纳判定分工

两个函数都在判"行不行"，但它们**判的不是同一件事**：

| | `evaluate_candidate`（day058） | `evaluate_gates`（今天） |
|---|---|---|
| 问题 | 候选比当前**更好吗**？ | 这次产物**够格发布吗**？ |
| 判据 | 相对（与当前版本比差值） | **绝对**（与固定阈值比） |
| 输入 | 两个 `ModelVersion` | 一次 run 的指标 + 产物清单 |
| 缺指标时 | 无法判定（gain 无从计算） | **门禁不通过**（缺证据不能发布） |
| 结论 | promote / hold | passed / failed |

### 3.2 单因素对照（实测）

| 改动 | 结果 | 阻塞失败 |
|------|------|---------|
| 全项达标 | 通过 | 无 |
| 合格率 0.42 | 不通过 | `pass_rate` |
| 相对基线 -0.03 | 不通过 | `regression` |
| 适配器 80 MiB | 不通过 | `adapter_size` |
| 缺数据集指纹 | 不通过 | `dataset_traceability` |
| 缺合并产物 | 不通过 | `artifact_completeness` |
| 加了成本指标 0.09 | 不通过 | `cost` |

这张表的存在意义是**先看拦在哪一项，再决定改什么**——把六项合成一个
`passed` 布尔值，运维能做的唯一动作就是重跑一次看日志。

### 3.3 三类结果必须分开命名

| 类别 | 判据 | 含义 |
|------|------|------|
| `blocking_failures` | 阻塞且未通过 | 决定 `passed`——发布被拦下 |
| `warnings` | 非阻塞且未通过 | 有人**显式关掉了**这项检查（一个值得被看见的决定） |
| `skipped_checks` | 非阻塞且没有观测值 | 缺证据（例如首次训练没有基线） |

如果不分开，运维看到"有 2 项没通过"时无法判断该去**补数据**还是
该去**把开关打开**。

其中"关掉一项检查不是通过"是刻意的：`require_traceability=False` 会把该项
置为 `passed=False, blocking=False`，于是它落进 `warnings` 而不是静默通过。
第一版把它写成 `passed=True`，被这条区分"逼"出来了——**接口报"通过"等于
宣称查过，而我们其实没查**。

### 3.4 `when_missing`：最容易出事的一列

六项门禁里有三项"缺指标即不通过"、三项"缺指标则降级"：

| 门禁 | 缺指标时 | 理由 |
|------|---------|------|
| `pass_rate` | **不通过** | 合格率是核心结论，缺了它整次评估没有意义 |
| `adapter_size` | **不通过** | 体积不可知就决定不了部署成本 |
| `artifact_completeness` | **不通过** | 只有适配器、没有合并模型不算交付完成 |
| `regression` | 跳过（告警） | 首次训练没有基线 |
| `cost` | 跳过（告警） | 离线训练不产生推理成本 |

`gate_table()` 把这一列渲染出来，因为**它是这张表里最容易被忽略、也最容易
出事的一列**——把两类混在一起读，就会出现"因为没测延迟所以延迟门禁通过"。

### 3.5 一个写反过的方向（本课最值得记住的缺陷）

`delta = 候选 − 基线`，**退步是负值**，因此 `max_regression=0.0` 的含义是
`delta >= 0`（一处都不许掉），而**不是** `delta <= 0`。

实现时写反过一次，表现是**所有改进都被拦下**：

```python
# 错的：把"提升 5 个百分点"判成失败
passed = value <= resolved.max_regression
# 对的
passed = value >= -resolved.max_regression
```

可怕之处在于"所有候选都被拒绝"看起来很像"门禁很严格"，不会有人立刻
怀疑方向写反。因此修完之后**立刻加了一条专门的回归断言**：

```python
def test_positive_delta_passes_the_regression_gate():
    report = evaluate({**BASE_METRICS, "eval_pass_rate_delta": 0.05})
    assert report.check(GATE_REGRESSION).passed is True
    assert report.check(GATE_REGRESSION).threshold == ">= -0.0"
```

> **可以带走的判断**：方向类缺陷（大小/正负/包含与排除）不会抛异常，
> 只会让结论整体反向。修掉之后**必须留下一条能把方向钉死的断言**，
> 因为"看起来更严格"和"看起来更宽松"都不足以让人怀疑方向。

## 第四章：实验追踪 —— 确定性 run_id 与"不能覆盖历史"

### 4.1 与 MLflow / W&B 的对应关系

本模块刻意照着 MLflow 的概念形状设计，换到真框架时是一次机械替换：

| 本模块 | MLflow | Weights & Biases |
|--------|--------|------------------|
| `ExperimentTracker` | `mlflow`（模块级） | `wandb.init()` |
| `Run` | `mlflow.start_run()` | `wandb.Run` |
| `log_params` | `mlflow.log_params` | `run.config` |
| `log_metrics(step=)` | `mlflow.log_metric(key, value, step)` | `wandb.log({...}, step=)` |
| `log_artifact` | `mlflow.log_artifact` | `wandb.Artifact` |
| `finish(status)` | `mlflow.end_run(status)` | `run.finish()` |
| `runs.jsonl` | 后端数据库 | 云端存储 |

**为什么不直接用真框架**：本课程的硬纪律是"离线、可复现、零外部依赖"。
引入 MLflow 需要一个长期运行的追踪服务（测试里就得起容器）；引入 W&B
需要联网与账号。两者都会让"每天 2 小时"变成"每天先解决环境问题"。

### 4.2 两处与 MLflow 的刻意差异

实测（demo 第 4 节）：

```text
  第一次：97fa8e5a0da1 lora-ablation [running] 3 参数 / 0 指标（无指标）| 0 产物 | 0.00s
  reuse=True  → 同一个 run_id：True
  reuse=False → 新 id（同参数第二次运行）：97fa8e5a0da1-2
  改一个参数 → 全新 id：d6be7bb3c8b0
```

1. **`run_id` 是确定性的**：`sha256(name + canonical(params))[:12]`。
   于是"两次实验的 id 相同 ⟺ 参数完全相同"这条性质成立——而这正是
   "这个数字是哪次跑出来的"能被直接回答的原因。MLflow 用随机 id，
   因此重跑永远产生一个新 run；
2. **同一个 `(指标名, step)` 不能重复记录**：

```text
  step 冲突被拒：指标 train_loss 在 step=42 已记录过（旧值 0.3187）：
  覆盖会让曲线变成'最后一次写入的曲线'，要记录第二次请换一个 step
```

第 2 条听起来苛刻，但覆盖写正是"loss 曲线"最容易失效的方式——**它不会
报错，只会让历史安静地变成最后一次写入的样子**。

两个细节：`run_id` **只覆盖 params、不覆盖 metrics**（指标是这次运行的
结果，算进去会让"同一次实验的两条记录"分裂成两个 id）；
无 step 的标量指标落在 `-1` 槽位而**不是 0**（step 0 是一个真实的训练步，
day050 的 warmup 就从第 0 步开始）。

### 4.3 三种比较关系与"没测过不算更差"

```text
  compare(mode=max): left=0.5493 right=0.58 delta=0.0307 → better
  compare(mode=min): left=0.5493 right=0.58 delta=0.0307 → worse
  缺指标时：comparable=False relation=None
```

`mode` 必须显式给出（`max` / `min`），**没有一个全局缺省**：同一个数字
（例如 loss）在监督微调里越小越好、在奖励模型里越大越好，给一个全局缺省
会诱导调用方忘记它，而忘记的后果是**结论反向**。

前两行是同一个 delta 得到相反结论——这正是"方向参数真的被用上了"的证据。
第三行是另一条纪律：**"没测过"不是"更差"，也不是"相等"**。

### 4.4 落盘方式：一次运行写多行

`runs.jsonl` 里每条 run 会被**多次**追加（开启时一行、每次 log 一行、
结束时一行），读的时候按 id 折叠成最后一行。

这与 day058 的版本索引选择"事件流"的原因不同，值得对照：

| | `registry/versions.jsonl` | `mlops/runs.jsonl` |
|---|---|---|
| 数据形状 | 版本很多、单条很小，阶段变更是**稀疏事件** | "一次实验一个对象"，单条不大 |
| 写法 | 只追加事件（register / stage） | 追加整条快照 |
| 读法 | 折叠事件流 | 读最后一行即得终态 |

**选择取决于数据形状，而不是"哪一种更先进"**——day058 的事件流是为了
不丢"什么时候变的、为什么变"，而这里的 run 快照字段少、体积可忽略，
写整条让 `reload` 的实现简单到没有出错空间。

```text
    [blocked] publish      0.00 ms  dry_run / publish=False：只演练到打包，未写注册表
    版本表规模 1，head=1.0.0
■ dry_run=False：ecca78533a34 | 全部完成 | 已发布 v1.1.0 | 门禁 通过
    …
    [ok     ] publish      0.89 ms  v1.1.0 已发布并置为 stable（键 14dceb829e28ce44）
    版本表规模 2，head=1.1.0
```

两次运行的 `run_id` **相同**（`ecca78533a34`）——因为参数一字未改。
但 `dry_run` 不同，于是 `publish` 的结论不同。这不是矛盾：
`run_id` 由参数（输入）决定，而"发不发"是**本次执行的选择**，
它记录在阶段结果里而不是 run_id 里。

### 5.2 `blocked` ≠ `failed`（本课的核心区分）

实测（demo 第 6 节）：

```text
  4f59b38146fe | 全部完成 | 未发布 | 门禁 不通过/未执行
    [blocked] gate      发布门禁 不通过 | 5/6 项通过 | 阻塞失败 ['artifact_completeness']
    [ok     ] package   模型卡 v1.1.0（patch）| 5 个指标 | 4 条已知限制
    [blocked] publish   门禁不通过，未写注册表：阻塞失败 ['artifact_completeness']
  failed=False（**blocked 不算失败**）
  追踪器里的 run 状态：finished
```

四处一致的表达，缺一不可：

| 位置 | 值 | 含义 |
|------|-----|------|
| `gate` 阶段 | `blocked` | 上游判定不允许继续 |
| `publish` 阶段 | `blocked` | 同上 |
| `outcome.failed` | `False` | **没有任何东西坏了** |
| run 状态 | `finished` | 这次实验正常跑完了 |

把它报成 `failed` 的代价是具体的：CI 会标红，而**那份门禁报告就在同一个
构建产物里**，被一个"失败"的标签挡住了。

这与 day058 把"回滚没有退路"输出成 `hold` 而不是抛异常是同一条纪律——
**一个悄悄违反自己约束的护栏，比没有护栏更糟**。

### 5.3 门禁不通过**仍然打包**

`package` 阶段在两条路径上都是 `ok`。理由：那份报告与模型卡正是要给人看的
东西——"这一版为什么不能发"必须是一个可下载的结论，而不是一句
"流水线失败了"。

### 5.4 卡片版本号必须等于注册表版本号

同一份产物重跑时，`propose_version` 会算出下一个号（例如 `1.1.1`），
而注册表里那条记录是 `1.1.0`——两者指向**同一条记录**（day058 的
"三元组复用"）。

修法是把三元组**在打包前**就算出来，若已存在则卡片用已有版本号：

```python
triple = VersionTriple(base_model=..., adapter_sha256=..., dataset_fingerprint=...)
existing = self.registry.find(triple.key)
if existing is not None:
    version_number = existing.version
    bump_kind = existing.tags.get("bump_kind", bump_kind)
```

这类"同一个东西两个编号"的缺陷不会报错，只会让追溯失效，所以它有一条
专门的断言（`test_rerun_card_version_matches_the_registry_record`）。

### 5.5 回调契约：只强制一样东西

```python
train(params) -> {"adapter_sha256": ...,            # 必填
                  "adapter_mebibytes": ..., "train_loss": ..., "step": ...,
                  "metrics": {...}, "artifacts": {...}}     # 全部可选
evaluate(artifacts) -> {"eval_pass_rate": ...}      # 必填
```

两处"必填"各有理由，而且它们的**失败必须响亮**：

- 训练回调缺 `adapter_sha256`：没有它就算不出版本键；
- 评估回调缺 `eval_pass_rate`：门禁第一项就是合格率——若允许缺，
  "评估器写错了"会被伪装成"效果不达标"，而后者会让人去调超参。

其余字段全部可选，因此有一条用例专门走"只给必填字段"的路径
（`test_train_callback_with_only_the_required_field_works`）——
**契约只强制一样东西，那么其余路径都必须能被走通**。

### 5.6 失败也要留档

任何阶段抛异常都会被捕获，并把 run 标为 `failed`、错误写进 `run.tags["error"]`：

```python
outcome = build_pipeline(train=boom).run(...)
assert outcome.run.status == STATUS_FAILED
assert "CUDA out of memory" in outcome.run.tags["error"]
```

**失败那次 run 的参数才是复现问题所需要的东西**——只留一行 CI 日志而不留
参数，等于每次都要靠记忆重建现场。

失败被记在"下一个该执行的阶段"上（`_next_stage_name`）。没有这个辅助函数，
失败会被记在一个"名字随便取"的阶段上，而 `StageResult` 会因未知阶段名
直接抛 `MLOpsError`——那是"处理异常时又抛异常"，最难查的一类。

## 第六章：模型卡 —— 第四段才是它存在的理由

### 6.1 四段结构

```text
身份      版本 / 基座 / 适配器哈希 / 数据集指纹 / 实验 id / 提交号
指标                              ← 取 run 的最终值
发布门禁  通过与否 + 三类名单
产物      适配器目录 / 合并模型目录
适用场景 / 明确不适用 / 已知限制    ← **这一节是它存在的理由**
```

前三段在 day058 的注册表里已经能回答，而"它**不能**做什么从来没有人
写下来——于是每一次"模型答错了"的讨论都要从头争一遍"这算不算预期内"。

### 6.2 四条限制，每条带一个可核对的数字

| 限制 | 数字依据 |
|------|---------|
| 领域评估集只有 18 条用例，合格率的最小可分辨变化是 `1/18 ≈ 0.0556` | day053 的评估套件 |
| 参考模型是 557×557 的双字符 bigram（约 31 万参数） | day050 的参考模型 |
| 训练数据来自单一来源、单一语言（中文技术问答） | day048/day057 的数据画像 |
| 质量门禁只覆盖格式与治理，不覆盖事实正确性 | day057 的五维质量分 |

**把限制写成"可能在某些情况下表现不佳"是没有用的**，因为它无法被用来
否掉任何一个结论。而"小于 0.0556 的差异不可作为提升证据"可以——它能
**否掉一个结论**。

这条性质被一条用例钉住：断言四条限制里分别出现 `1/18`、`557`、
`单一来源`、`事实正确性`。

### 6.3 一处刻意的过滤

`gate_` 前缀的指标**不进卡片的指标表**：

```python
if not name.startswith(GATE_METRIC_PREFIX)
```

它们是门禁自己的结论（`gate_pass_rate=1.0`），而卡片有专门的"发布门禁"
一节。把同一份事实在一份文档里写两遍且措辞不同，是让评审产生不信任的
最快方式——**读者会开始怀疑哪一处才是对的**。

这与 day027 的"分数用于聚合、问题清单用于诊断"是同一种思路：
一份文档里每一个数字都要有唯一的出处。

### 6.4 清单与卡片：两份产物，用途不同

`release_manifest.json` 给机器读（字段平铺、可直接取用），
`MODEL_CARD.md` 给人读（五分钟内判断"能不能用"）。

只留一份的后果是总有一方要去解析对方的格式——因此有一条断言保证
**两份产物里的版本号 / 哈希 / 指纹 / 指标完全一致**
（`test_manifest_and_card_are_two_renderings_of_the_same_facts`）。

## 第七章：接进 GitHub Actions —— workflow 是**生成**的

### 7.1 与 day032 的 `ci.yml` 的分工

| | CI（day032） | 持续微调（今天） |
|---|---|---|
| 触发 | push / PR（事件驱动） | 定时（cron）+ 手动 |
| 耗时 | 分钟级 | 十分钟级以上（真实训练更久） |
| 输入 | 代码 | 代码 + 数据 + 上一版模型 |
| 失败意味着 | "这次提交不能合" | "这一版不值得上线" |

最后一行是关键的语义差异，也是为什么两条流水线不能合并。

### 7.2 三个地方只有一份权威

```text
settings.mlops_*  →  ReleaseGates  →  render_github_actions()  →  .github/workflows/finetune-nightly.yml
                                          ↓
                                    workflow_commands()（同时出现在 YAML、教程与终端里）
```

`tests/test_mlops_ci.py::test_committed_workflow_matches_the_renderer` 断言
**仓库里那份文件与渲染器的输出逐字相同**。因此"改门禁阈值"会同时在三个
地方生效，而它们之间只有一份权威；忘了重新生成，测试立刻变红。

实测（demo 第 8 节）：

```text
  文件：.github/workflows/finetune-nightly.yml
  cron：0 20 * * *（GitHub Actions 的 schedule 一律按 UTC 解释）
  超时：30 分钟 | Python 3.11
  门禁命令：python scripts/mlops_demo.py --min-pass-rate 0.5 --max-adapter-mebibytes 64.0
            --max-cost-per-1k-tokens 0.05 --max-regression 0.0
  仓库里的 finetune-nightly.yml 与渲染结果逐字相同：True
  yaml 行数 57，仓库文件存在 True
```

手写 YAML 的问题是反过来的：阈值会在 YAML 里悄悄漂移，而
**YAML 里那个数字没有任何东西在守护它**——它与
`settings.mlops_min_pass_rate` 谁是权威，取决于读的人先看到哪一份。

### 7.3 六步与两处细节

```text
checkout → setup-python → 装依赖 → 测试（代码没坏） → 门禁（该不该发） → 上传产物
```

- **产物上传必须是 `if: always()`**：失败时那份报告才是最需要看的；
- **cron 必须按 UTC 写**：GitHub Actions 的 `schedule` 一律按 UTC 解释，
  写成本地时间会出现"配的凌晨 2 点、跑在下午 2 点"。

### 7.4 YAML 1.1 的 `on` 陷阱

`yaml.safe_load` 会把裸 `on:` 解析成**布尔** `True`，因此
`payload["on"]` 会 `KeyError`，`payload[True]` 才对：

```python
payload = parse_workflow(render_github_actions())
assert "on" not in payload
triggers = payload[True]
assert triggers["schedule"][0]["cron"] == "0 20 * * *"
```

这不是本课的 bug，而是所有解析 GitHub Actions workflow 的脚本都会撞上的
一件事——所以它被写成一条可运行的证据，而不是留在注释里。

## 第八章：接入 API 与配置

### 8.1 四个端点，一个共同的取舍

| 端点 | 方法 | 回答什么 |
|------|------|---------|
| `/mlops/stages` | GET | 六步怎么走、门禁查什么、CI 怎么跑、**不能做什么** |
| `/mlops/gates/evaluate` | POST | 这份指标与产物够不够格发布（三类名单） |
| `/mlops/pipeline/dry-run` | POST | 用确定性参考回调演练整条流水线 |
| `/mlops/ci/workflow` | GET | 生成的 workflow 与摘要 |

四个端点**全部只读或纯计算**：不写磁盘、不联网、不做真实训练、不用随机数。
真正的"训练 + 发布"由 `scripts/mlops_demo.py` 与 GitHub Actions 承担——
**一个需要十分钟的流程不该挂在一个 HTTP 请求上**。

`dry-run` 端点用**确定性的参考回调**驱动六阶段：它回答的问题是
"如果现在发，门禁会不会放行？"——在花十分钟真训一次之前先把这个问题
问清楚，是 dry-run 存在的全部理由。适配器哈希由 `sha256` 派生而不是随机数，
因此同一个请求体永远得到同一个响应。

### 8.2 错误码语言

| 情况 | 错误码 | 例子 |
|------|--------|------|
| **请求形状**不对 | 422 | `pass_rate: 1.5`、`adapter_mebibytes: 0` |
| **业务规则**不允许 | 400 | 非法策略阈值、空数据集指纹 |

与 day050~day058 一致。**"非法策略值一律 400（不是 422）"这一条在路由层
显式写出**，因为 Pydantic 的 `ge`/`gt` 很容易顺手把业务规则也吃掉，
而两份会漂移的规则比一份好规则更糟。

### 8.3 配置项（9 个）

```python
mlops_dir: str = "outputs/mlops"                  # runs.jsonl / 模型卡 / 清单
mlops_min_pass_rate: float = 0.5                  # 门禁：合格率下限
mlops_max_regression: float = 0.0                 # 门禁：允许的退步
mlops_max_adapter_mebibytes: float = 64.0         # 门禁：适配器体积上限
mlops_max_cost_per_1k_tokens: float = 0.05        # 门禁：单位成本上限
mlops_ci_python_version: str = "3.11"             # CI：Python 版本
mlops_ci_schedule: str = "0 20 * * *"             # CI：cron（UTC）
mlops_ci_timeout_minutes: int = 30                # CI：超时
```

值得单独说一句的是 `mlops_max_adapter_mebibytes=64.0`：它是本课程参考模型上
LoRA 适配器体积的**约 1000 倍余量**（实测几十 KiB）。它拦的不是日常调优，
而是"挂错了目标模块导致适配器暴涨"这类事故——**安全网档的阈值就该定在
"明显错了才会撞上"的地方**，否则它会天天误报，然后被关掉。

## 第十章：今日总结 —— 三条可以带走的判断

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|---------|
| 阶段依赖表可程序校验 | 把"顺序写错"与"依赖漏写"变成启动即失败 | `stages.validate_stage_order` |
| 主链取最靠后的上游 | 取第一个上游会漏掉评估与门禁 | `stages.critical_path` |
| 删掉恒为真的检查 | 噪声会诱导写出多余的兜底代码 | `stages` 的 docstring |
| 绝对判定 ≠ 相对判定 | 缺数据时一个说"不知道"、一个说"不行" | `gates` 模块 docstring |
| 三类结果分开命名 | "补数据"与"把开关打开"是两件事 | `GateReport` 三个属性 |
| 关闭检查记为告警 | 接口报"通过"等于宣称查过，而其实没查 | `evaluate_gates` 两个开关分支 |
| `when_missing` 一列 | 最容易被忽略、也最容易出事 | `gate_table` |
| 确定性 run_id | "id 相同 ⟺ 参数相同"让"哪次跑出来的"可答 | `tracking.run_id_for` |
| 同 step 指标不可覆盖 | 覆盖会让曲线变成最后一次写入的样子 | `tracking.log_metrics` |
| `mode` 无全局缺省 | 同一数字在不同任务上的好坏方向相反 | `tracking.compare_runs` |
| 快照写而事件流留给 registry | 选择取决于数据形状，不是"谁更先进" | `tracking._persist` |
| `blocked` ≠ `failed` | 红灯会掩盖真正需要看的门禁报告 | `pipeline.PLAN_STAGES` 语义 |
| 门禁不通过仍打包 | "为什么不能发"必须是可下载的结论 | `pipeline` 的 package 阶段 |
| 卡片版本 = 注册表版本 | "同一个东西两个编号"会让追溯失效 | `pipeline` 打包前的三元组查询 |
| 回调只强制一样东西 | 必填字段的失败必须响亮，其余路径都要能走通 | `TRAIN_REQUIRED_FIELDS` |
| 失败留档 | 失败那次 run 的参数才是复现问题所需的东西 | `pipeline` 的 except 分支 |
| 四条限制带数字 | 无法否掉结论的限制等于免责声明 | `packaging.LIMITATIONS` |
| 过滤 `gate_` 指标 | 同一份事实在一份文档里只该出现一次 | `packaging.build_model_card` |
| workflow 由渲染器生成 | 让"同源"变成一条会变红的机制 | `ci.render_github_actions` |
| `if: always()` 上传产物 | 失败时那份报告才是最需要看的 | `ci.render_github_actions` |

M5 阶段到此结束（day048~day059 共 12 个日历日，其中 day049 / day056 是两个
缓冲复习日）。回头看这十二天留下的东西：

```text
day048  数据工程：格式收敛 + 七条硬规则 + 可复现切分
day049  中场缓冲：把账算清（9 步更新 / 2500 token）
day050  SFT：模板渲染 + label mask + 步数超参核算
day051  LoRA/QLoRA：参数量与显存算术、NF4 量化
day052  PEFT 实践：适配器生命周期、多卡分片、合并门禁
day053  微调模型评估：领域评估集 + 六分量合取判定
day054  RLHF/DPO 原理：偏好数据与对齐目标
day055  DPO 实践：偏好构造 + TRL 配置镜像 + 损失自检
day056  M5 中场缓冲：六天地图与三本账
day057  领域数据：六阶段流水线 + 两级去重 + 可复现版本链
day058  版本管理：三元组内容寻址 + 事件流版本表 + 采纳与回滚
day059  MLOps：实验追踪 + 发布门禁 + 六阶段流水线 + CI 集成
```

十二天的产物合起来回答了一个完整的问题：
**"从一批数据到一个敢上线的模型版本，中间每一件事凭什么可信"**——
而 day059 的这条流水线正是那个答案的可执行形式。

下一阶段进入 **M6：RAG 应用开发**（day060 起）——文档解析、分块策略、
向量数据库、混合检索、重排序与生产化部署。届时
`evaluation`（day025~day032）里的 RAG 评估器会与今天这条流水线的门禁
相遇：**检索质量将成为门禁里的一项，而不再只是一份离线报告**。
