## 第一章：短期记忆的局限 —— 为什么需要长期记忆

### 1.1 回顾：短期记忆做了什么

day008 的 `ShortTermMemory` 是一个消息列表：新消息追加到尾部，超过 `max_messages` 时保留 system 消息、按 FIFO 丢弃最老的消息。完整代码见 [memory/short_term.py](../源码/smart-research-agent/smart_research_agent/memory/short_term.py)。

这个设计对「当前对话的近期上下文」是完美的——但它回答不了这些问题：

- 用户三周前告诉过 Agent「我对花生过敏」，这次聊天第 30 轮时，那条消息早就被 FIFO 丢弃了。
- 用户上传过一份 200 页的研究报告，其中的关键结论不可能全部塞进上下文窗口。
- 一个全新的会话开始时（新的 session_id），短期记忆是空白的，Agent 对这个用户一无所知。

问题的本质是：**短期记忆是「按时间保留」，而人类需要的是「按相关性取回」**。

### 1.2 上下文窗口是稀缺资源

LLM 的上下文窗口（比如 128K tokens）看似很大，但它是**按 token 计费、按注意力稀释**的：

| 做法 | 成本 | 效果 |
|------|------|------|
| 把所有历史都塞进 prompt | token 费用线性增长，迟早爆窗口 | 「中间迷失」：模型对中间内容注意力下降 |
| 只保留最近 N 条（短期记忆） | 便宜 | 旧知识永久丢失 |
| 全部持久化，用时按相关性检索 top-k | 只花 top-k 的 token | 旧知识可以复活 |

第三种做法就是长期记忆的核心思想：**窗口里只放「现在需要的」，其余的存起来，需要时再取**。

### 1.3 长期记忆的三步模型

今天实现的所有代码，都围绕一个三步模型：

```
        ┌──────────────────────────────────────────────┐
        │              LongTermMemory                  │
        │                                              │
  写入──▶│  ① 存储(remember)                            │
        │     文本 ──Embedding──▶ 向量 ──▶ 向量库       │
        │                                              │
  查询──▶│  ② 检索(recall)                              │
        │     问题 ──Embedding──▶ 向量 ──▶ 相似度排序    │
        │                                ──▶ top-k 文本 │
        │                                              │
        │  ③ 注入(inject)                               │
  LLM◀──│     top-k 结果拼进发给 LLM 的消息里           │
        └──────────────────────────────────────────────┘
```

注意一个类比：

| 人类记忆 | Agent 记忆 |
|----------|-----------|
| 工作记忆（正在想的事） | 短期记忆（上下文窗口里的消息） |
| 长期记忆（记住的知识） | 向量库（持久化的向量记录） |
| 回忆（想起相关的事） | 相似度检索（recall） |

### 1.4 写入策略：记什么、什么时候记

长期记忆不是「把所有消息都向量化存一份」——那是日志系统，不是记忆系统。不加筛选的写入会带来三个问题：

1. **噪声淹没信号**：「嗯」「好的」这类消息也入库，检索时稀释真正有价值的记录。
2. **存储膨胀**：每条记录都要 embed 一次（真实 embedding 是付费 API），无脑写入就是无脑烧钱。
3. **隐私风险**：敏感信息一旦入库，就可能在未来某个会话被检索出来注入上下文。

合理的写入策略通常是三选一或组合：

| 策略 | 做法 | 适用场景 |
|------|------|----------|
| 显式指令 | 用户说「记住：我周五要交报告」才写入 | 个人助手，用户掌控感强 |
| 规则抽取 | 每轮对话结束后，用规则或小模型抽「事实型陈述」入库 | 全自动场景 |
| 会话摘要 | 会话关闭时让 LLM 总结要点，把摘要入库 | 长对话、研究型任务 |

今天我们的 `remember` 是显式 API——调不调用、传什么文本，由上层策略决定。记忆系统分层（底层存取机制 + 上层写入策略）是刻意的：**机制要稳定，策略要可演进**。

> 思考题：为什么长期记忆的检索必须用「语义相关性」而不是「关键词匹配」？用户问「我吃什么会起疹子」，能匹配到三周前那句「我对花生过敏」吗？关键词匹配做不到（两句话没有共同关键词），而语义向量可以——这正是 Embedding 存在的理由。

## 第二章：Embedding 原理 —— 把语义装进向量

### 2.1 从「文字」到「数字」的鸿沟

计算机不能直接比较两段文字的「意思」。`"猫"` 和 `"狗"` 在字符层面完全不同，但任何人类都知道它们比 `"猫"` 和 `"微积分"` 更接近。

Embedding（嵌入）要做的就是：**训练一个模型，把任意文本映射为一个固定长度的浮点数向量，使得语义相近的文本，其向量在空间中也相近**。

```
"猫"     ──Embedding 模型──▶  [0.21, -0.53, 0.87, ..., 0.12]  ┐
"狗"     ──Embedding 模型──▶  [0.19, -0.48, 0.81, ..., 0.09]  ├─ 距离很近
"微积分" ──Embedding 模型──▶  [-0.66, 0.33, -0.14, ..., 0.55] ─┴─ 离上面两个都很远
```

这背后的直觉来自语言学的**分布假设（Distributional Hypothesis）**：「词的意义由它的上下文决定」。出现在相似语境中的词（猫/狗都常出现在「宠物」「喂」「毛」附近），其向量自然被训练得相近。

### 2.2 维度：向量有多长

Embedding 模型的输出维度是固定的超参数：

| 模型 | 维度 | 说明 |
|------|------|------|
| 我们今天的 MockEmbedding | 64（可调） | 教学用，足够演示原理 |
| OpenAI text-embedding-3-small | 1536 | 生产常用 |
| OpenAI text-embedding-3-large | 3072 | 精度更高、更贵 |

维度的权衡：

- **维度太低**：表达力不足，不同的语义被迫挤在一起，检索精度下降。
- **维度太高**：存储和计算成本线性增长；而且「维度灾难」会让高维空间里的距离越来越趋同，边际收益递减。

生产实践中 768~3072 是常见的甜点区。

### 2.3 归一化：为什么很多向量长度为 1

很多 embedding 服务返回**单位向量**（模长为 1）。这不是巧合，而是刻意的工程选择：

1. 归一化后，余弦相似度退化为**点积**（见第三章推导），计算更快。
2. 向量的「方向」承载语义，「长度」往往只反映文本长度、词频等噪声——归一化把噪声抹掉，只留方向。
3. 相似度分数被约束在 `[-1, 1]` 区间，便于设阈值（比如「相似度 > 0.8 才注入上下文」）。

我们今天的 `MockEmbedding` 不做归一化，因为 `cosine_similarity` 函数内部会处理模长——这也让我们有机会在代码里看清归一化到底发生在哪一步。

### 2.4 Embedding 模型是怎么训练出来的（概念性理解）

我们不需要自己训练 embedding 模型，但理解其训练目标能帮你判断「什么场景它擅长、什么场景它会翻车」。

现代文本 embedding 模型（如 OpenAI 的 embedding 系列、开源的 BGE、E5）大多用**对比学习（Contrastive Learning）**训练：

```
训练样本：(锚点文本, 语义相似的正例, 语义无关的负例)
   例如：("如何煮米饭", "煮饭的步骤", "量子力学发展史")

训练目标：
   cos(embed(锚点), embed(正例)) ↑ 越大越好
   cos(embed(锚点), embed(负例)) ↓ 越小越好
```

模型在海量这样的三元组上反复调整参数，最终学会把「语义相似」编码为「方向相近」。注意这个目标函数里**直接出现了余弦相似度**——模型就是朝着「让余弦相似度等于语义相似度」的方向优化的，这是第三章选择余弦的又一个理由：度量方式和训练目标一致。

由此也能推出它的盲区：

- **训练数据里罕见的领域**（如极小众方言、内部黑话），向量空间里的「语义结构」不可靠。
- **精确匹配类需求**（订单号、身份证、代码标识符），embedding 反而不如关键词检索——「O-12345」和「O-12346」语义上没有任何区别，但业务上完全不同。生产系统常用「向量检索 + 关键词检索」的混合方案（hybrid search），M6 阶段会详细展开。

## 第三章：余弦相似度 —— 方向比长度重要

### 3.1 几何意义：夹角

把两个文本的向量画在二维平面上：

```
        y
        │      ╱ b（"狗"）
        │     ╱
        │    ╱  θ  ← 夹角越小越相似
        │   ╱╲
        │  ╱  ╲ a（"猫"）
        │ ╱
        │╱___________ x
        O
```

**余弦相似度 = 两个向量夹角的余弦值**：

- 夹角 0°（方向完全一致）→ cos = 1，最相似
- 夹角 90°（正交，互不相关）→ cos = 0
- 夹角 180°（方向相反）→ cos = -1，最相反

### 3.2 公式推导

从点积的定义出发。两个向量的点积有两种等价表达：

```
代数定义：a · b = Σᵢ aᵢ·bᵢ
几何定义：a · b = |a| · |b| · cos(θ)
```

把两式联立，解出 cos(θ)：

```
                 a · b              Σᵢ aᵢ·bᵢ
cos(θ) = ───────────────── = ─────────────────────────
              |a| · |b|       √(Σᵢ aᵢ²) · √(Σᵢ bᵢ²)
```

分子是点积，分母是两个模长的乘积。这正是我们代码里的实现（[memory/vector_store.py](../源码/smart-research-agent/smart_research_agent/memory/vector_store.py)）：

```python
def cosine_similarity(a: list[float], b: list[float]) -> float:
    """余弦相似度：值域 [-1, 1]，1 表示方向完全一致."""
    if len(a) != len(b):
        raise ValueError("向量维度不一致")
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    if norm_a == 0 or norm_b == 0:
        return 0.0
    return dot / (norm_a * norm_b)
```

注意两个防御性细节：

1. **维度检查**：两个向量维度不一致说明调用方用错了 embedding 模型，直接报错比 silently 算出错结果好（fail fast，day001 的原则）。
2. **零向量保护**：模长为 0 时分母为 0，约定返回 0.0（既不相似也不相反）。

> 推论：如果向量已经归一化（|a| = |b| = 1），分母恒为 1，余弦相似度就等于点积——这就是 2.3 节说的「归一化后点积即余弦」。

### 3.3 为什么不用欧氏距离

欧氏距离（直线距离）看似更直觉，但对文本检索有一个致命问题：**它对向量长度敏感**。

举个例子。假设文档 A 是「猫是宠物」的向量，文档 B 是「猫是宠物，猫是宠物，猫是宠物」（同一句话重复三遍，词频翻三倍）的向量。语义上 A 和 B 应该几乎一样，但：

```
A = [1, 1]           B = [3, 3]（词频×3，方向不变，长度×3）

欧氏距离 = √((3-1)² + (3-1)²) ≈ 2.83   ← 看起来「差很远」
余弦相似度 = (1·3+1·3) / (√2·√18) = 6/6 = 1.0   ← 正确识别「完全相同」
```

| 度量 | 衡量什么 | 对文本长度/词频 | 文本检索适用性 |
|------|----------|----------------|----------------|
| 欧氏距离 | 空间中的直线距离 | 敏感（长文本向量模长大） | 差 |
| 余弦相似度 | 方向的夹角 | 不敏感（归一化掉模长） | 好 |

**文本的语义在方向上，不在长度上**——这是信息检索领域几十年实践沉淀下来的结论，也是几乎所有向量数据库默认用余弦相似度的原因。

### 3.4 手算练习（先算再看答案）

给定向量 `q = [3, 4]`，`d = [4, 3]`：

- 点积：3×4 + 4×3 = 24
- |q| = √(9+16) = 5，|d| = √(16+9) = 5
- 余弦相似度 = 24 / 25 = **0.96**

今天的习题里有更多手算题，建议亲手算一遍——余弦相似度是 M6 RAG 阶段还会反复出现的基础。

## 第四章：向量库本质 —— 从暴力搜索到 ANN

### 4.1 教学版实现：暴力最近邻

向量数据库（Vector Database）剥掉所有工程外壳，核心只做三件事：**存向量、算相似度、按相似度排序取 top-k**。我们的 `InMemoryVectorStore` 就是这核心逻辑的最小实现：

```python
class InMemoryVectorStore:
    """内存向量库：暴力最近邻搜索."""

    def __init__(self) -> None:
        self._records: dict[str, VectorRecord] = {}

    def add(self, record: VectorRecord) -> None:
        self._records[record.id] = record

    def search(self, query_vector: list[float], top_k: int = 5) -> list[tuple[VectorRecord, float]]:
        scored = [(r, cosine_similarity(query_vector, r.vector)) for r in self._records.values()]
        scored.sort(key=lambda x: x[1], reverse=True)
        return scored[:top_k]
```

`search` 的过程一目了然：

```
查询向量 q
    │
    ▼
对库中每一条记录 r：计算 cos(q, r)     ← O(N) 次相似度计算
    │
    ▼
按分数降序排序                        ← O(N log N)
    │
    ▼
取前 top_k 条                         ← 这就是「召回」
```

这叫**暴力最近邻搜索（Brute-force kNN / Exact kNN）**：结果精确（找到的真的是全局最相似的 top-k），但每次查询都要扫全库。

### 4.2 暴力搜索的扩展性问题

算一笔账。假设库里有 100 万条记录，向量维度 1536：

- 每次余弦相似度约 1536 次乘加 → 一次查询 ≈ 15 亿次浮点运算
- 单次查询延迟在秒级，QPS 稍高就撑不住
- 数据量翻 10 倍，查询成本也翻 10 倍——**线性增长在生产上是不可接受的**

教学版用暴力搜索是因为：我们的库只有几条到几十条记录，O(N) 毫无压力，而且**精确结果便于测试断言**。理解暴力版是理解一切优化的前提。

### 4.3 生产级方案：ANN 与 HNSW

生产向量数据库的答案是 **ANN（Approximate Nearest Neighbor，近似最近邻）**：牺牲一点点精度（比如召回率从 100% 降到 99%），换取数量级的速度提升。

核心思想是**索引**：像书的目录一样，预先组织好数据结构，查询时不用翻遍每一页。

主流索引算法概览（概念性了解即可，M6 阶段会深入）：

| 索引 | 直觉 | 类比 |
|------|------|------|
| **IVF**（倒排文件，FAISS 支持） | 先把向量聚类成 K 个桶，查询只搜最近的几个桶 | 查字典先按拼音首字母定位 |
| **HNSW**（分层可导航小世界图） | 把向量组织成多层图，从稀疏顶层跳到稠密底层，逐步逼近最近邻 | 找朋友：先找同省→同市→同小区 |
| **PQ**（乘积量化） | 把高维向量分段压缩成短码，用码本近似距离 | 用邮编近似地理位置 |

HNSW 是目前最流行的方案（ChromaDB、Qdrant、Milvus 默认或推荐都用它），查询复杂度从 O(N) 降到近似 O(log N)，且召回率通常保持在 95% 以上。

| 维度 | 我们的教学版 | 生产级（ChromaDB / FAISS） |
|------|-------------|---------------------------|
| 数据规模 | 几十条 | 百万~亿级 |
| 搜索方式 | 暴力精确 kNN，O(N) | ANN 索引，近似 O(log N) |
| 持久化 | 无（进程退出即丢） | 落盘、崩溃恢复 |
| 元数据过滤 | 存了 metadata 但检索不用 | 支持「先过滤再检索」 |
| 分布式 | 无 | 分片、副本 |

> 思考题：为什么「近似」在检索场景里是可以接受的？因为 top-k 检索本来就服务于 LLM 上下文注入——第 1 名和第 2 名差 0.001 的相似度，对最终答案质量几乎没有影响。工程上用 1% 的精度换 100 倍的速度，是稳赚的交易。

### 4.4 HNSW 的直觉图

HNSW 值得多看一眼，因为它是当前事实标准。把向量组织成多层图：

```
第 2 层（最稀疏）   A ─────────────── M              ← 高速公路：大步跳跃
                    │               │
第 1 层（中等密度） A ── E ── I ── M ── Q           ← 国道：中步逼近
                    │    │    │    │    │
第 0 层（全量数据） A B C D E F G H I J K L M N O P Q  ← 小巷：精细定位
```

查询过程类似「扶梯下降 + 贪心游走」：

1. 从最顶层随机入口出发，在当前层贪心走向离查询向量最近的邻居，走不动了就下一层。
2. 逐层下降，每层步长更细，直到第 0 层找到最近的若干个向量。

因为每层只访问极少数节点，总访问量约为 O(log N) 级别——100 万条记录，实际比较的向量只有几百个，这就是「近似」的来源和代价。

## 第五章：Embedding 抽象与 MockEmbedding 的教学价值

### 5.1 接口先行：EmbeddingProvider

和 day005 的 `BaseLLM` 一样，我们先定义抽象，再给实现（[llm/embedding.py](../源码/smart-research-agent/smart_research_agent/llm/embedding.py)）：

```python
class EmbeddingProvider(ABC):
    """文本向量化提供方抽象."""

    @abstractmethod
    def embed(self, text: str) -> list[float]:
        """把文本编码为定长向量."""

    @property
    @abstractmethod
    def dimension(self) -> int:
        """向量维度."""
```

这是**依赖倒置原则**的又一次应用：`LongTermMemory` 只依赖 `EmbeddingProvider` 接口，不关心底层是 Mock、OpenAI 还是本地开源模型。想换实现？写一个新的子类，注入处改一行，其余代码不动。

### 5.2 MockEmbedding：确定性的哈希向量

```python
class MockEmbedding(EmbeddingProvider):
    """基于 SHA-256 哈希的确定性伪向量."""

    def embed(self, text: str) -> list[float]:
        digest = hashlib.sha256(text.encode("utf-8")).digest()
        return [(digest[i % len(digest)] / 255.0) * 2 - 1 for i in range(self._dimension)]
```

工作原理：

1. 对文本做 SHA-256，得到 32 字节的哈希摘要。
2. 把字节循环映射到 `[0, 255]`，再线性变换到 `[-1, 1]`，拼成 `dimension` 维向量。

教学价值：

- **完全离线**：无网络、无 API Key、无费用，CI 里随便跑。
- **确定性**：同一文本永远得到同一向量——这让 `recall` 的测试可以写出精确断言（见 `test_long_term.py`：相同文本的伪向量完全一致，recall 精确文本必然排第一）。
- **可复现**：任何人 clone 仓库跑测试，结果都一样。

### 5.3 必须诚实说明的局限

**MockEmbedding 没有语义。** SHA-256 是密码学哈希，设计上就是要让输入的微小变化导致输出的剧烈变化（雪崩效应）。所以：

- `"猫"` 和 `"狗"` 的 MockEmbedding 向量，相似度和 `"猫"` 与 `"微积分"` 的一样随机。
- 用 MockEmbedding 的 `LongTermMemory` 只能可靠地召回**完全相同的文本**。

这不影响今天的学习目标——向量库的排序逻辑、top-k 截取、注入流程，都可以用确定性向量验证。但请不要误以为「向量检索能跑通」等于「语义检索有效」。**语义能力来自真实的 embedding 模型，不来自向量库。**

### 5.4 真实接入 OpenAI Embedding 的位置

得益于 `EmbeddingProvider` 抽象，接入真实服务只需要新增一个实现类（示意代码，不在今天快照中）：

```python
class OpenAIEmbedding(EmbeddingProvider):
    def __init__(self, api_key=None, model="text-embedding-3-small"):
        from openai import OpenAI
        self._client = OpenAI(api_key=api_key or settings.openai_api_key)
        self._model = model

    @property
    def dimension(self) -> int:
        return 1536

    def embed(self, text: str) -> list[float]:
        resp = self._client.embeddings.create(model=self._model, input=text)
        return resp.data[0].embedding
```

注意它和 day005 的 `OpenAICompatibleLLM` 是同一个模式：配置从 `settings` 读取，网络调用收敛在实现类内部，上层无感知。这正是抽象层存在的意义。

## 第六章：组装 LongTermMemory —— 存储与检索

### 6.1 组合而非继承

`LongTermMemory` 把一个 `EmbeddingProvider` 和一个 `InMemoryVectorStore` 组合起来（[memory/long_term.py](../源码/smart-research-agent/smart_research_agent/memory/long_term.py)）：

```python
class LongTermMemory:
    """长期记忆 = Embedding 编码 + 向量库存储 + 相似度检索."""

    def __init__(self, embedding: EmbeddingProvider, store: InMemoryVectorStore | None = None):
        self._embedding = embedding
        self._store = store or InMemoryVectorStore()

    def remember(self, text: str, metadata: dict[str, Any] | None = None) -> str:
        record_id = uuid.uuid4().hex[:12]
        vector = self._embedding.embed(text)
        self._store.add(VectorRecord(id=record_id, text=text, vector=vector, metadata=metadata or {}))
        return record_id

    def recall(self, query: str, top_k: int = 3) -> list[str]:
        query_vector = self._embedding.embed(query)
        return [r.text for r, _score in self._store.search(query_vector, top_k=top_k)]
```

两个方法对应三步模型中的前两步：

- `remember`：文本 → embed → 存库，返回记录 ID（外部可用 ID 做删除、更新）。
- `recall`：问题 → embed → 相似度检索 → 返回 top-k 原文。

`store or InMemoryVectorStore()` 是一个小设计：默认给你内存库，但允许注入任何同接口的存储——未来换成 ChromaDB 客户端时，`LongTermMemory` 一行都不用改。

### 6.2 metadata 的作用

`VectorRecord` 上挂了 `metadata: dict`。今天我们没有用它参与检索，但它是生产系统的关键扩展点：

```python
mem.remember("用户花生过敏", metadata={"user_id": "u123", "type": "health"})
mem.remember("项目截止日是周五", metadata={"user_id": "u123", "type": "work"})
```

生产向量库支持「先按 metadata 过滤、再做相似度检索」，例如「只在 u123 这个用户的记录里找」。这解决了多租户隔离问题——回忆一下 day008 的 `SessionManager` 用 session_id 隔离短期记忆，长期记忆同样需要按用户隔离，只是隔离键放进了 metadata。

### 6.4 写入时机与去重

还有两个实现层面的小决策，今天的代码给出了最简答案，但要知道权衡在哪：

**写入时机**：`remember` 在被调用时**立即 embed 并入库**。这意味着调用方要承担 embed 的延迟（真实服务是网络往返）。生产系统常用异步写入——对话先继续，记忆写入走后台队列——教学版保持同步，逻辑更可预测。

**去重**：我们的 `remember` 每次都生成新 UUID，同一段文本写两次就会有两条记录。暴力版里这只会浪费一点内存；但配合真实 embedding 时，重复记录会在 top-k 里占位挤掉其他知识。生产做法是先按文本哈希查重，或者用「相近度超过阈值则更新而非新增」的 upsert 策略。`VectorRecord.id` 的存在就是为这类更新操作预留的。

### 6.5 测试如何保证正确性

看 `tests/test_long_term.py` 的几个关键断言：

```python
def test_remember_and_recall_exact(self):
    mem = LongTermMemory(embedding=MockEmbedding())
    mem.remember("Python 是一种编程语言")
    mem.remember("今天天气不错")
    # 相同文本的伪向量完全一致，recall 精确文本必然排第一
    results = mem.recall("Python 是一种编程语言", top_k=1)
    assert results[0] == "Python 是一种编程语言"
```

注释里那句话很重要：这个测试能精确断言，**正是因为 MockEmbedding 的确定性**。如果接入真实 embedding 服务，测试就必须改成「断言结果包含某文本」之类的模糊断言，或者干脆用 mock 替换网络层——这是「测试替身」设计的又一处收益。

## 第七章：注入 —— 把检索结果放进 Agent 上下文

### 7.1 三步模型的最后一步

存储和检索都有了，最后的问题是：**检索出的文本放在 prompt 的什么位置？**

回顾 day006 的 ReAct 循环（[agent/react_agent.py](../源码/smart-research-agent/smart_research_agent/agent/react_agent.py)），发给 LLM 的消息结构是：

```
[system]   SYSTEM_PROMPT（含工具清单）
[user]     任务: ...
[assistant] Thought/Action（第 1 轮）
[user]     Observation: ...
...
```

检索结果有两个常见注入点：

| 注入位置 | 做法 | 优点 | 缺点 |
|----------|------|------|------|
| **拼进 system** | 在 SYSTEM_PROMPT 后追加「已知事实：...」 | 全程生效，位置固定 | system 通常应该稳定；历史知识每次变会污染它 |
| **拼进首条 user 之前** | 在任务消息前加一条「相关资料」user 消息 | 与任务强绑定，逻辑清晰 | 多轮后会被短期记忆截断丢弃 |

业界实践（包括 ChatGPT 的记忆功能）多采用第二种的变体：**recall 结果作为一条上下文消息，紧跟在任务描述前后**。示意（组合代码，非快照文件）：

```python
# 伪代码：在 ReactAgent.run 开头注入长期记忆
recalled = long_term_memory.recall(task, top_k=3)
context_block = "\n".join(f"- {text}" for text in recalled)
messages = [
    Message(role="system", content=SYSTEM_PROMPT.format(tools=registry.describe())),
    Message(role="user", content=f"相关资料（来自长期记忆）:\n{context_block}"),
    Message(role="user", content=f"任务: {task}"),
]
```

为什么今天不把它写进 `ReactAgent`？因为注入策略涉及截断优先级、相关性阈值、与短期记忆的配合（注入的 recall 结果占用了 `max_messages` 额度）——这些设计决策需要在你亲手调试过完整循环后再做，day010 的 Planner 接入时会统一处理记忆与 Agent 的组装。今天的目标是把**存储、检索、接口**这三块地基打牢并测透。

### 7.3 一次完整的数据流走查

把今天所有模块串起来，看一条知识从写入到影响回答的全过程：

```
写入阶段（三周前）
  用户: "记住，我对花生过敏"
    └─▶ remember("用户花生过敏", metadata={"type": "health"})
          └─▶ embed() → [0.13, -0.77, ...] (64 维)
                └─▶ VectorRecord(id="a1b2...", ...) 存入 InMemoryVectorStore

检索阶段（今天，新会话）
  用户: "帮我规划一周的健身餐"
    └─▶ recall("帮我规划一周的健身餐", top_k=3)
          └─▶ embed() → 查询向量
                └─▶ 与库中每条记录算余弦相似度，降序取前 3
                      └─▶ ["用户花生过敏", ...]（真实 embedding 下它会排前列）

注入阶段
  检索结果拼成 "相关资料" 消息，置于任务消息之前
    └─▶ LLM 看到 "用户花生过敏"，规划餐单时自然避开花生
```

注意整个链条里 Agent 的推理代码（ReAct 循环）**没有任何改动**——长期记忆是在消息组装层接入的。好的架构让新能力以「插件」而非「手术」的方式接入。

### 7.4 注入的两个工程细节

真要落地时，有两个细节必须先想清楚：

1. **相关性阈值**：如果 recall 结果的最高相似度都很低（比如 < 0.3），说明长期记忆里根本没有相关知识，此时注入只会干扰模型。正确做法是设阈值，低于阈值就不注入。
2. **token 预算**：top-k 不是越大越好。每条注入的记忆都占上下文窗口、都花 token 费用，top_k=3~5 通常是甜点区——和「短期记忆要截断」是同一个稀缺资源问题的两面。

> 思考题：recall 结果注入后，如果用户连续追问，这条注入消息会随短期记忆的 FIFO 被丢弃。这合理吗？什么时候应该重新 recall，什么时候应该复用之前的注入结果？（提示：可以按「话题是否切换」来决定，这正是生产记忆系统的难点。）

## 第八章：今日总结 —— 长期记忆的最小完备实现

| 概念 | 今天的落地 | 生产级对应 |
|------|-----------|-----------|
| 长期记忆三步模型 | remember / recall / 注入设计 | 记忆系统通用架构 |
| Embedding | `EmbeddingProvider` 抽象 + `MockEmbedding` | OpenAI / 开源 embedding 模型 |
| 相似度度量 | 手写 `cosine_similarity` | 向量库内置，归一化后用点积 |
| 向量库 | `InMemoryVectorStore` 暴力 kNN | ChromaDB / FAISS + HNSW 索引 |
| 记忆组装 | `LongTermMemory`（组合模式） | 带 metadata 过滤、持久化的记忆服务 |
| 上下文注入 | 注入位置与阈值的设计分析 | RAG 系统的上下文组装 |

今天最重要的三个认知：

1. **长期记忆 = 持久化 + 按相关性取回**，它解决的是短期记忆「按时间保留」解决不了的问题。
2. **语义在方向上**——余弦相似度衡量方向、对长度不敏感，这是文本检索选择它的根本原因。
3. **抽象先行**：`EmbeddingProvider` 和 `InMemoryVectorStore` 的可替换设计，让教学版到生产版的迁移只改注入处一行。

明天（day010）我们将实现 Planner 模块，让 Agent 学会先规划再执行——届时长期记忆将作为规划时的「背景知识来源」派上用场。
