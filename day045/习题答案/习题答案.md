## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：公式 `2 × batch × seq × layers × kv_heads × head_dim × 精度字节数` 里的 "2" 是 **Key 与 Value 两份张量**——注意力需要缓存每个历史位置的 K 和 V，所以是两份而不是一份。`KV 头数` 是 GQA/MQA 架构里的 KV 头数，来自 `config.json` 的 `num_key_value_heads`，**不是** `num_attention_heads`：Qwen3-8B 有 32 个注意力头但只有 8 个 KV 头，写错这个数会让估算偏高 4 倍（源码注释里专门提醒了这一点）。A 错（不是推理次数，且 KV 头数≠注意力头数）；C 错（2 不是字节数，`head_dim` 才是维度）；D 错（与内存副本无关，且 KV 缓存与上下文长度是**线性正相关**，这正是第六章要反解的对象）。

### 第 2 题

**答案：B**

**解析**：GGUF 的 k-quant 是**混合量化**——关键张量（注意力输出、FFN 下投影等对精度敏感的部分）保留更高位宽，其余压到 4 位，加权平均约 4.5 bpw。所以 `QUANTIZATION_BITS["q4_k_m"] = 4.5`，`bytes_per_parameter("q4_k_m") = 0.5625`。按 4.0 估算会低估约 12% 的权重显存，压着显存上限部署就会 OOM——低估比高估危险得多。A、C、D 均无据：这不是舍入误差，也不需要与 FP16 对齐，`q4_k_m` 的 0.5 来自混合位宽而非 embedding 开销。

### 第 3 题

**答案：B**

**解析**：Ollama 提供 `http://localhost:11434/v1/` 的 OpenAI 兼容端点（api_key 传 `"ollama"`，官方文档原话是 "required but ignored"），vLLM 默认在 8000 端口提供同样协议的端点。因此 `chat`/`stream`/`chat_vision` 全部可以复用 `OpenAICompatibleLLM` 的实现，本地与云端的差异被压缩到"部署与运维"这一层——继承不是省代码，而是**声明这个架构事实**。A 低估了设计意图；C 错（`BaseLLM` 是抽象基类，继承具体实现是可选的设计决定，不是语法强制）；D 错（`ModelRouter` 只依赖 `BaseLLM` 接口，与是否继承 `OpenAICompatibleLLM` 无关）。

### 第 4 题

**答案：B**

**解析**：`normalize_base_url` 只在 `path` 为空或 `"/"` 时补 `/v1`；一旦路径里已经有内容（如反向代理的 `/proxy/llm`），就原样保留。理由是**不做画蛇添足的改写**：用户显式配置的路径说明他知道自己在做什么（可能是网关的挂载点），自作聪明地拼接只会产生 404。A 错（这是有意设计，不是 bug）；C 错（函数无法判断前缀是否"已经完整"）；D 错（与密钥无关）。

## 第二部分：判断题

### 第 5 题

**答案：对**

**解析**：两个方法的**语义不同**，所以失败行为必须相反。`is_available` 回答"现在能不能用"——探活的语义是**返回事实**，调用方据此决定是否降级到云端模型，抛异常会让"探活"变成"必须 try 的调用"，用起来更容易出错。`list_served_models` 回答"有哪些模型"——用户明确要清单，拿不到就必须**抛 `RuntimeError`**，且错误信息里带上端点地址（如 `无法访问本地 ollama 服务（http://localhost:11434/v1）`），否则"服务没起来"会被误读成"本机一个模型都没有"。`test_local_model.py` 里的 `test_is_available_false_on_connection_error` 与 `test_list_served_models_raises_with_endpoint_hint` 正是这两条语义的守卫。

### 第 6 题

**答案：错**

**解析**：本地 embedding 模型的输出维度**取决于权重文件**，没有权威常量表可查：`nomic-embed-text` 是 768 维、其他模型各异。所以 `OllamaEmbedding` 的 `dimension` 做成**惰性探测**属性——未显式传入且尚未调用过时，先发一次极短文本的探测请求，从响应里回填维度并缓存。维度虽然不属于"协议"，但它**决定向量库与语义缓存能否对齐存储**：维度不一致的向量混进同一个库，检索结果会静默错乱（不报错，只变笨）。所以处理方式不是写死常量，而是"显式传入优先、否则探测一次"。

### 第 7 题

**答案：对**

**解析**：空样本时返回 `0.0`（而不是 `1.0`）是刻意的：如果返回 1.0，那么"任务集为空 → 一致性 100% → 判定可替代"这条错误链路就会自动成立，"没测过"会被当成"测过且达标"。同理，`verdict()` 在无样本时返回"无评估样本，无法给出结论"，`worst_case()` 返回 `None`——三个地方一起保证"空输入必须表现为信息缺失，而不是表现为通过"。

## 第三部分：简答题

### 第 8 题

**三种取值的语义与场景**：

| 取值 | 语义 | 适用场景 |
|------|------|---------|
| `"5m"`（默认） | 请求结束后模型在显存里再待 5 分钟，超时自动卸载 | 开发机与低频服务：既避免频繁重载，又不长期占显存 |
| `-1` | 常驻不卸载 | 生产预热：把首字延迟从"加载权重的十几秒"压到"纯推理的几百毫秒" |
| `0` | 请求返回后立即卸载 | 显存要与别的服务（如另一个模型、训练任务）共享时"用完即走" |

**请求体**：`load_model` 会向 `POST http://localhost:11434/api/generate` 发送

```json
{"model": "qwen3:8b", "keep_alive": -1, "options": {"num_ctx": 8192}}
```

三个字段各有来源：`model` 是必填的模型名；`keep_alive=-1` 来自参数覆盖（未传时用 `OllamaRuntime.keep_alive` 的默认 `"5m"`）；`options.num_ctx=8192` 来自 `context_length` 参数——**这是把 Ollama 默认 4096 上下文调大的唯一入口**。注意文档给出的预热方式就是"发一个只有 `model` 字段的 `generate` 请求"：Ollama 加载权重后立即返回，不产生任何 token，所以这里不需要 `prompt` 字段。

### 第 9 题

**为什么必须量一致性**：延迟和成本是"效率"指标，它们无法回答"换了模型之后，Agent 还答不答得对"。本地小模型在复杂推理、长上下文、严格格式（比如工具调用的 JSON 参数）上会退化，而这种退化**不会报错**，只会表现为"回答变短、变泛、格式偶尔不合法"。如果只看延迟与成本，最容易犯的错是：**把一个明显变笨的模型替换上线，把产品降级当成成本优化**——省下的钱远抵不上回答质量下降带来的损失。

**结合实测数字的决策**：一致性 0.3383 远低于阈值 0.8，说明本地模型的回答与云端在语义上已经"不是一回事"；同时延迟比 3.75（本地 1.5s / 云端 0.4s）意味着本地**更慢**；每条只省 $0.00034。三项加起来是明确结论：**不该直接替换**。正确的做法是混合路由——把"召回型/摘要型"这类简单任务交给本地（`ModelSpec.cost_per_1k=0`、能力档位按实测一致性标定），把"分析/推理/多步工具调用"这类复杂任务留给云端，让 day033 的 `ModelRouter` 按复杂度自动分流。

## 第四部分：编程题

### 第 10 题

**完整代码**（放在项目根目录下执行即可，无需 Ollama 服务）：

```python
"""16GB 显存跑 Qwen3-8B 的部署账本."""

from smart_research_agent.llm.local_runtime import (
    fitting_quantizations,
    max_context_tokens,
    plan_deployment,
)

#: Qwen3-8B 的公开架构参数（config.json）
ARCH = {"num_layers": 36, "kv_heads": 8, "head_dim": 128}
VRAM = 16.0
PARAMS_B = 8.0


def main() -> None:
    print(f"=== {PARAMS_B}B 模型 @ {VRAM}GB 显存（ctx=4096）===")
    for quant in ("fp16", "q8_0", "q5_k_m", "q4_k_m"):
        plan = plan_deployment(PARAMS_B, VRAM, quant=quant, **ARCH)
        flag = "装得下" if plan.fits else "装不下"
        print(
            f"  {quant:<7} 权重 {plan.weights_gb:>6.2f}GB + KV {plan.kv_cache_gb:.2f}GB"
            f" = {plan.total_gb:>6.2f}GB → {flag}（余量 {plan.headroom_gb:+.2f}GB）"
        )

    fitted = fitting_quantizations(PARAMS_B, VRAM, **ARCH)
    print(f"\n按质量从高到低能装下：{fitted}")
    print(f"建议档位：{fitted[0]}（质量最高且装得下）")

    ctx = max_context_tokens(PARAMS_B, VRAM, quant="q4_k_m", **ARCH)
    print(f"q4_k_m 下最大上下文：{ctx} token")


if __name__ == "__main__":
    main()
```

**实测输出**：

```
=== 8.0B 模型 @ 16.0GB 显存（ctx=4096）===
  fp16    权重  14.90GB + KV 0.56GB =  17.01GB → 装不下（余量 -1.01GB）
  q8_0    权重   7.92GB + KV 0.56GB =   9.33GB → 装得下（余量 +6.67GB）
  q5_k_m  权重   5.12GB + KV 0.56GB =   6.25GB → 装得下（余量 +9.75GB）
  q4_k_m  权重   4.19GB + KV 0.56GB =   5.23GB → 装得下（余量 +10.77GB）

按质量从高到低能装下：['q8_0', 'q5_k_m', 'q4_k_m']
建议档位：q8_0（质量最高且装得下）
q4_k_m 下最大上下文：74752 token
```

**结论文字**：16GB 显存下，FP16 装不下（需 17.01GB，缺 1.01GB），**首选 q8_0**（9.33GB，余量 6.67GB，量化损失最小）；若还要给 KV 缓存留更多空间或与其他服务共享显存，再降到 `q5_k_m` / `q4_k_m`。选 `q4_k_m` 时，单序列上下文可开到 **74752 token**（按 1024 向下取整）。

**为什么 fp16 必然装不下（算式）**：

```
权重 = 参数量 × 每参数字节数
     = 8e9 × (16 / 8) 字节
     = 16e9 字节
     = 16e9 / 1024³ GiB
     ≈ 14.901 GiB

总需求 = (权重 + KV) × (1 + overhead)
       = (14.901 + 0.5625) × 1.1
       ≈ 17.010 GiB  >  16 GiB
```

关键在两点：**FP16 每参数 2 字节**，8B 参数光权重就 16e9 字节 ≈ 14.9GiB；再叠加 0.56GB 的 KV 缓存与 10% 的框架开销（激活值、CUDA context、显存碎片）就突破 16GB。所以"16GB 卡跑 8B 模型"必须走量化——这正是第二章"先算再跑"的价值：**花两行代码算一次，省下几小时的 OOM 排查**。
