## 第一章：自回归生成 —— GPT 到底在算什么

### 1.1 next-token prediction：一切的原子操作

GPT 类模型暴露给世界的全部能力，归结为一个原子操作：**给定一段文本，预测下一个 token 的概率分布**。

```text
输入: "中国的首都是"
模型内部: 对词表中每个 token 算一个分数（logit）
输出:  P("北京")=0.92  P("上海")=0.03  P("首都")=0.01  …  (词表十万个 token 的分布)
```

注意输出的不是一个词，而是**词表上的完整概率分布**。"生成一句话"是这样完成的：从分布里选一个 token 追加到文本末尾，把新文本重新喂给模型，再选下一个——如此往复，直到产出结束标记。这就是**自回归（autoregressive）**：模型的输出（已生成的 token）会回归为自己的输入。

```text
第 1 步: "中国的首都是"        → 选 "北京"
第 2 步: "中国的首都是北京"      → 选 "。"
第 3 步: "中国的首都是北京。"    → 选 <end>，停止
```

### 1.2 原理解释经验现象

自回归原理能解释我们此前遇到的许多"经验事实"，这就是学原理的回报：

- **为什么输出 token 比输入贵**（day032 价格表）：读输入时可以并行（所有输入 token 同时进注意力计算），而生成必须逐 token 串行——第 N 个 token 没算出来，第 N+1 个就无法开始。串行解码的算力占用时间远长于并行预填充，定价如实反映了这一点。
- **为什么幻觉是结构性的**：模型每步都在选"概率上合理的下一个 token"，而不是在"查事实"。"拿破仑的宠物龙叫什么名字"这个问题里没有概率合理的拒答 token 序列——顺着问题的分布走，编一个名字反而概率更高。
- **为什么 ReAct 的格式约束有效**（day006）：我们在系统提示词里给出 `Thought:/Action:` 模板，本质是把后续 token 的概率分布**塑造**成我们想要的样子——模型没有"遵守规则"的概念，只有"这个上下文后面通常接这种格式"。
- **为什么 max_tokens 是硬截断**：生成没有内在的"说完才停"保证，只有概率上的结束倾向；`max_tokens` 是调用侧的安全带，到数就断。

### 1.3 从 logit 到概率：softmax

模型最后一层为词表中每个 token 输出一个实数分数，称为 **logit**。logit 不是概率（可为负、和不为 1），要经 softmax 归一化：

```text
p_i = exp(z_i / T) / Σ_j exp(z_j / T)
```

公式里多出的 **T 就是 temperature**——它不是什么神秘黑话，就是 softmax 分子里对 logit 的缩放因子。我们的实现（`../源码/smart-research-agent/smart_research_agent/llm/sampling.py`）：

```python
def softmax_with_temperature(logits: list[float], temperature: float = 1.0) -> list[float]:
    scaled = [z / temperature for z in logits]
    peak = max(scaled)                     # 数值稳定：减最大值再取 exp，防止溢出
    exps = [math.exp(z - peak) for z in scaled]
    total = sum(exps)
    return [e / total for e in exps]
```

### 1.4 从概率到 token：采样

有了分布，最后一步是**选一个 token**。两种极端策略：

- **贪心（argmax）**：总取概率最大者——确定、稳定，但容易陷入复读（"好的好的好的…"）；
- **纯采样**：按分布掷骰子——多样、有惊喜，但长尾上的烂 token 也可能被抽中。

temperature 与 top_p 就是在这两个极端之间调参的工具，这是第二章的主题。

## 第二章：采样参数的数学含义

### 2.1 temperature：温度缩放

把 logit 除以 T 再 softmax，效果是：

| T | 数学效果 | 行为效果 |
|---|----------|----------|
| T → 0 | logit 差异被放大，分布趋于 one-hot | 近似贪心：总选最优 token，输出确定 |
| T = 1 | 原始分布 | 按模型本有的置信度采样 |
| T → ∞ | 差异被抹平，分布趋于均匀 | 近乎随机选词，输出混乱 |

用我们的函数实测（`logits = [0, 1, 4]`，第三个 token 的概率）：

```text
T=0.5 → 0.9972   尖锐：几乎锁定最优
T=1.0 → 0.9362
T=2.0 → 0.7361   平坦：其他选项开始有机会
```

注意一个边界：`T = 0` 在数学上是除零，**它不是"很低的温度"，而是另一种解码算法（贪心）**。我们的 `softmax_with_temperature` 显式拒绝 T=0 并提示改用 argmax；`SamplingParams` 允许 `temperature=0.0` 是因为 API 语义里 0 就表示"走贪心路径"。

### 2.2 top_p：核采样的累积概率截断

temperature 改变分布的**形状**，top_p 改变采样的**候选集**。核采样（nucleus sampling）的算法（`nucleus_filter`）：

```text
① 按概率降序排列候选 token
② 从最大者开始累加概率，累积和达到 top_p 即截断
③ 截断线外的 token 概率置零，核内重新归一化
④ 只在核内采样
```

例：`probs = [0.4, 0.35, 0.25]`，`top_p = 0.5`：0.4 不够 0.5，加上 0.35 后累积 0.75 ≥ 0.5，截断——核 = 前两个 token，归一化为 [0.533, 0.467, 0]。

核采样相对 top-k（固定保留 k 个）的关键优势是**自适应**：分布尖锐时（模型很确定）核里只有一两个候选，分布平坦时（模型拿不准）核里有一大串。测试 `test_candidate_set_adapts_to_shape` 用 `[0.9, 0.05, 0.05]` 与 `[0.34, 0.33, 0.33]` 两个分布验证了这一点——同样的 `top_p=0.9`，前者核内 1 个候选，后者 3 个。

### 2.3 max_tokens：成本与截断的双重含义

`max_tokens` 不影响分布，它管的是**何时硬停**。两个实践含义：

1. **成本上限**：按 token 计费意味着 max_tokens 就是单次调用的费用天花板（day032 的 CostTracker 记账时 completion 用量被它截断）；
2. **截断风险**：答案被拦腰截断的 JSON 解析不了、ReAct 格式认不出。Agent 场景的 `Final Answer:` 如果出现在第 max_tokens+1 个 token，这次调用就白费了——**max_tokens 要按"最长合理答案"而不是"平均答案长度"来设**。

### 2.4 为什么 Agent 场景要 temperature=0

这是最常被问的经验法则，现在可以从原理推导了。Agent 与聊天机器人的根本区别：**LLM 的输出不是给人看的，是给解析器看的**（day006 的 `parse_react_output`）。

- 解析器要求输出严格匹配 `Action: xxx\nAction Input: yyy` 格式。高 temperature 会时不时从长尾里抽出不合格式的 token——不是模型"变笨"，而是采样本来就会选中低概率 token；
- Agent 的每一步都是后续步骤的输入（Observation 回喂），早期的一个随机波动会被循环**放大**——单轮对话的温度噪声只影响一句话，Agent 里的温度噪声影响整条轨迹；
- 评估与 CI（day030~032）要求行为可复现，temperature=0 的贪心解码是同输入同输出的前提。

反过来，什么时候该调高温度？**输出本身就是目的**的场景：创意写作、头脑风暴、生成多样化候选（比如给红队造攻击话术）。原则一句话：**温度是给"欣赏多样性的人"准备的，不是给"执行精确格式的机器"准备的**。

### 2.5 MockLLM 的采样模拟：离线观察参数效果

没有 API Key 怎么"看见" temperature 的作用？day033 给 MockLLM 加了候选集机制（`../源码/smart-research-agent/smart_research_agent/llm/mock.py`）：

```python
llm = MockLLM(candidates=["候选A", "候选B", "候选C"])
llm.chat(msgs, temperature=0.0)   # 恒为 "候选A"（贪心近似）
llm.chat(msgs, temperature=1.5)   # "候选A" -> "候选B" -> "候选C" -> "候选A"（轮换）
```

低温度恒取第一个候选（近似贪心解码），高温度在候选间轮换（模拟采样的多样性）。轮换当然是**确定性**的——测试可断言、CI 可复现的底线不破。它与真实模型的对应关系：候选集 ≈ 核内的 token 序列，轮换 ≈ 采样抽到不同候选。教学上它足够演示"同样的输入，温度不同，输出从固定变多样"；工程上它让采样参数的下游逻辑（比如重试换候选）也能离线测试。

## 第三章：多模型路由 —— 成本与质量的权衡

### 3.1 为什么需要路由

假设我们接入了三档模型：

| 模型 | 能力 | 价格（$/1K token） |
|------|------|--------|
| 轻量版 | 2/5 | 0.001 |
| 标准版 | 3/5 | 0.01 |
| 旗舰版 | 5/5 | 0.1 |

一个调研 Agent 的真实流量里，"2+3 等于几"和"对比分析 RAG 与微调的取舍"混在一起。全部走旗舰版，简单任务在为用不上的能力付 100 倍的钱；全部走轻量版，复杂任务翻车。这就是路由要解决的**成本/质量权衡**：**让每个任务恰好为它需要的能力付费**。

这与缓存、索引是同一类工程思想——没有一种资源配比适合所有负载，于是按请求特征分流。

### 3.2 路由三要素：能力、成本、可用性

`ModelSpec`（`../源码/smart-research-agent/smart_research_agent/llm/router.py`）把路由所需的全部信息建模为三个属性：

```python
@dataclass
class ModelSpec:
    name: str
    llm: BaseLLM
    capability: int       # 能力档位 1~5：它能胜任多复杂的任务
    cost_per_1k: float    # 综合成本：用它要花多少钱
    available: bool = True  # 可用性：它现在活着吗（熔断/下线时置 False）
```

第三个属性容易被忽略，但生产环境里**模型是会挂的**——限流、区域故障、版本下线。可用性进路由表，意味着故障处置从"半夜改代码"变成"改一个标志位"。

### 3.3 复杂度估计：路由的输入特征

路由需要回答"这个任务有多复杂"。我们用的是确定性启发式（长度 + 复杂关键词）：

```python
def estimate_complexity(task: str) -> int:
    score = 1
    if len(task) > 50:  score += 1
    if len(task) > 200: score += 1
    hits = sum(1 for kw in COMPLEX_KEYWORDS if kw in task)  # 分析/对比/推理/证明…
    score += min(2 * hits, 3)
    return min(score, 5)
```

启发式当然粗糙——但它在测试里完全确定、零成本、可解释，这对教学与 CI 是特性不是妥协。真实系统可以换成分类模型或历史表现回流（哪种任务在哪档模型上成功率高），**策略接口不变，只换估计器**。

### 3.4 成本优先策略与降级链

`CostFirstStrategy` 的规则一句话：**首选"满足能力要求的最便宜模型"，降级链按能力从强到弱**：

```python
capable = [m for m in available if m.capability >= complexity]
primary = min(capable, key=lambda m: m.cost_per_1k)     # 够用就好，不为过剩能力付费
rest.sort(key=lambda m: m.capability, reverse=True)     # 兜底永远向上
```

注意降级方向的设计：首选失败时往**更强**的模型切，而不是更便宜的。降级到更弱模型可能答错（质量风险），降级到更强模型只是多花钱（成本风险）——失败安全应该偏向多花钱的那一侧。

如果所有可用模型的能力都不够（`capable` 为空），策略降级为"最强可用模型"并在理由里如实记录——路由决策**不许沉默地妥协**。

### 3.5 决策可观测：为什么选了这个模型

day032 立过规矩：一切重要行为都要有结构化记录。路由每次决策都落一条 `RouteDecision`：

```python
@dataclass
class RouteDecision:
    task: str
    complexity: int
    chosen: str
    reason: str              # 人类可读的决策理由
    fallbacks: list[str]     # 当时的降级链
    fallback_used: str | None  # 实际发生降级时，最终生效的模型
```

`reason` 字段是路由器的灵魂。两个月后成本账单异常，你要能回答"为什么这条简单查询走了旗舰模型"——是复杂度估计误判？可用性标志被误关？还是 capable 集合为空？没有决策日志，这些都只能猜。结合 day032 的 `CostTracker`，路由策略的收益可以直接度量：同一份任务集，分别跑 `CostFirstStrategy` 与 `QualityFirstStrategy`，费用差就是路由省下的钱（本日习题第 10 题就做这个实验）。

### 3.6 透明的抽象：ModelRouter 就是一个 BaseLLM

`ModelRouter` 实现 `BaseLLM` 接口，意味着它可以**原位替换** ReactAgent 里的任何单一模型：

```python
router = ModelRouter([
    ModelSpec("cheap",  cheap_llm,  capability=2, cost_per_1k=0.001),
    ModelSpec("strong", strong_llm, capability=5, cost_per_1k=0.1),
])
agent = ReactAgent(llm=router, registry=registry)   # Agent 不知道路由的存在
```

这是 day005 依赖倒置设计的又一次回报：Agent 只依赖 `BaseLLM` 抽象，于是"换一个模型"与"换一层路由"对它是同一件事。`router.chat` 内部用最近一条 user 消息做路由依据、沿降级链依次尝试、全部失败才抛 `RuntimeError`（附带每个模型的错误详情）——Agent 侧的 ReAct 循环、安全防护、评估接线一概不用动。

一个细节：`ModelRouter.chat` 的默认 temperature 是 **0.0** 而不是 `BaseLLM` 的 0.7——路由层是 Agent 场景的入口，默认就该按 Agent 的规矩来（2.4 节）。

### 3.7 今日总结

| 设计决策 | 背后的原理 | 落地位置 |
|----------|-----------|----------|
| next-token prediction 是原子操作 | 自回归：输出回归为输入，逐 token 串行 | 第一章 |
| 输出 token 定价更贵 | 串行解码 vs 并行预填充的算力差异 | day032 价格表的原理注释 |
| temperature 是 softmax 的缩放因子 | T→0 趋 one-hot，T→∞ 趋均匀 | `softmax_with_temperature` |
| T=0 在函数里报错 | 贪心是另一种解码算法，不是"很低的温度" | `ValueError(... argmax ...)` |
| top_p 截断候选集 | 核大小随分布形状自适应，优于 top-k | `nucleus_filter` |
| Agent 场景 temperature=0 | 输出给解析器看，随机波动被 ReAct 循环放大 | `ModelRouter.chat` 默认值 |
| MockLLM 候选集轮换模拟采样 | 离线演示参数效果，且保持确定性可进 CI | `MockLLM(candidates=...)` |
| 路由 = 按请求特征分流 | 让每个任务恰好为它需要的能力付费 | `CostFirstStrategy` |
| 降级链永远向上（更强） | 失败安全偏向多花钱一侧，不偏向答错一侧 | `rest.sort(capability, reverse=True)` |
| 决策理由必须落日志 | "为什么选了这个模型"要永远有案可查 | `RouteDecision.reason` |
| ModelRouter 实现 BaseLLM | 依赖倒置：路由对 Agent 透明 | `class ModelRouter(BaseLLM)` |
