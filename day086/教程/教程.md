### 1.1 前十一天各交出了一件事，今天换了一个动作

```text
day075   一层可训练的自注意力        回答"怎么混合"
day076   把它切成 heads 份          回答"看什么"
day078   把"第几位"加进输入          回答"在哪"
```

读与装的区别，是一件很具体的事：

```text
读的时候     你可以只承诺"行为"——给同样的权重与输入，算出同样的数
装的时候     你必须承诺"解析"——文件在哪、哪个键叫哪个量、token 怎么切
```

因此今天引入的失败族里有三个是全新的，而它们**与算术无关**：

```text
ConfigError   "这份配置描述的模型不成立"     n_embd=16 而 n_head=5
HubError      "东西根本不在本地"             local_files_only=True 而缓存里没有这个 revision
TokenError    "词表对不上"                  merges.txt 引用了词表里没有的片段
```

### 1.2 今天的架构是"十一个模块"

```text
errors.py     七个失败族（**缺席的仍是 GradientError**，理由换了一条）
types.py      缓存布局 / 键名映射 / 池化三法 / 两条管线 / 十条性质 / 十二条生态笔记 / 五条边界
hub.py        名字 → commit → 文件 → 实体：四段结构与**逐文件命中**
config.py     config.json → ModelCard，并由配置**算出**参数量
tokenizer.py  byte-level BPE：两个文件 + 一个循环 + 一个被复刻的怪癖
forward.py    按卡片把 day079~085 的零件串成一次真前向
features.py   池化三法 + 那个**只差一个分母**的 bug
pipeline.py   两条管线（零数学的编排层）
bridge.py     接进 local_model：八项方法面 + 三条路线的客观事实

study.py      六张表
```

### 1.3 三条纪律

```text
① 每一行都要带两个数      命中/下载、配置/库、真实长度/总宽度、safe/naive
② "不适用" ≠ "通过"       今天有**两条**性质真的会走到"不适用"
③ 不可能失败的判据不算判据  逐文件缓存那条判据必须**从空缓存开始跑**
```

第 ③ 条是今天新学的。写"第二次解析时下载 0 个"时，最容易犯的错是
拿一个**已经填好的缓存**去跑——那样"第一次"本身就是一次命中，
于是这句话**不可能失败**。它看起来是一条判据，实际上是报告里的一行装饰。

### 2.1 一处被说反的默认值

在真库上跑一条 `GPT2Config()` / `BertConfig()` 立刻会看到：

```python
>>> transformers.GPT2Config().tie_word_embeddings
True
>>> transformers.BertConfig().tie_word_embeddings
True
```

**两个架构都共享词嵌入**，而真实 `bert-base-uncased` 的 `config.json` 里
**根本没有这个键**——于是全局默认生效。这一条常被说反，而它有一个整数的代价：

```text
带共享    109 482 240
不共享    109 482 240 + 30522×768 = 132 923 136     （多出 23 440 896）
```

本包因此把缺省值写成常量 `config.DEFAULT_TIE = True`，并让两边都用它：

```text
parse_config            读不到这个键时取 True
forward.make_weights    tied = card.tie_word_embeddings（**是配置的属性，不是架构的属性**）
```

第二行是刻意的修正：一开始我把 `tied` 写成 `card.model_type == "gpt2" and ...`，
那会让"BERT 不共享"这个错误假设**藏在代码里**——而它与"BERT 共享"在
一次 `head is word` 的检查上不会报错，只会让参数量差出整整一张词表。

## 第三章：把文件找齐

### 3.1 三段结构

```text
① 名字 → commit      refs/<revision> 里存着一串 commit hash（"main" 只是一个可读别名）
② commit → 文件      快照目录 snapshots/<commit>/ 里的相对路径**与仓库一致**（平铺）
③ 文件 → 实体        blobs/<sha256> 存实体；快照里的路径与实体之间是"两个名字"
```

本包把它建成**内存里的三段结构**（对应磁盘上的 `$HF_HOME/hub`）：

```python
CacheStore.refs       = {"models--org--tiny/main": "1f2e…"}       # 名字 → commit
CacheStore.snapshots  = {"models--org--tiny/1f2e…": {path: sha}}  # commit → 文件表
CacheStore.blobs      = {sha: b"…"}                               # 实体
```

### 3.2 "逐文件"这三个字有代价

```python
for path in sorted(manifest):
    digest = sha256_of(data)
    cached = snapshot_map.get(path) == digest and digest in self.store.blobs
    if not cached:
        self.store.blobs[digest] = data
    snapshot_map[path] = digest
    entries.append(CacheEntry(path=path, size=len(data), cached=cached))
```

演示读数（同一个缓存、两轮 + 一次离线）：

```text
第1次  config.json    387 B  新下      第2次  config.json    387 B  命中
第1次  vocab.json    2860 B  新下      第2次  vocab.json    2860 B  命中
……                                      离线解析：下 0 个 / 命中 4 个
```

把它写成 `all-or-nothing`（一个文件缺失就整仓重下）在单次调用上**看不出区别**——
区别只在第二次调用上，而第二次调用在开发机上很少被执行到。

### 3.3 为什么 `HubError` 不继承 `ParameterError`

```text
参数全对 + 缓存里没有   →  HubError        （本包的）
参数全对 + 网络断了     →  同样一句连接错误  （也是 HubError）
参数写错（max_length=0）→  ParameterError
```

三者的出路不同：前者要**改环境**（联网、换 revision、补缓存），
后者要**改调用**。把前者归进后者，就会有人把 `local_files_only` 改成 `False` 再试——
而网络那一步的失败**长得完全一样**。因此 `HubError` 继承的是本族基类
`IntegrationError`，**不是** `ParameterError`：

```text
ValueError
└── IntegrationError
    ├── ShapeError / NumericError / ParameterError   （多继承：既是 day075 族、也是本族）
    ├── HubError                                      （本层独有：它不是参数错）
    └── ConfigError → ParameterError                  （配置也是一种调用参数）
        TokenError  → ParameterError                  （词表也是一种入参）
        AssemblyError → ParameterError                （组装不成立也是一种参数失败）
```

## 第四章：配置即形状

### 4.1 同一个量的两个键名

```python
SIZE_KEYS = {
    "gpt2": {"hidden": "n_embd", "heads": "n_head", "layers": "n_layer",
             "positions": "n_positions", "ffn": "n_inner",
             "activation": "activation_function", "ln_eps": "layer_norm_epsilon"},
    "bert": {"hidden": "hidden_size", "heads": "num_attention_heads",
             "layers": "num_hidden_layers", "positions": "max_position_embeddings",
             "ffn": "intermediate_size", "activation": "hidden_act",
             "ln_eps": "layer_norm_eps"},
}
```

**这张表只有一处**：`parse_config` 读它，`test_hf_real_bridge.py` 拿它去
`hasattr(真 *Config())`——写错一个字母时，本包会安静地取到默认值，
而"取到默认值"与"这份配置没写"读起来一样。

### 4.2 一处"看起来一样、其实不一样"

与真库对账时冒出来的一条：**前馈中间维的缺省规矩，两个架构不同**。

```python
>>> transformers.GPT2Config().n_inner
None                      # 缺省 ⇒ 按 4·hidden 推
>>> transformers.BertConfig().intermediate_size
3072                      # 缺省 ⇒ 就是 3072，与 hidden 无关
>>> transformers.BertConfig(hidden_size=16, num_attention_heads=2).intermediate_size
3072                      # 一个 hidden=16 的 BERT 前馈宽度是 3072
```

于是"两个架构的前馈都是 4 倍"这句话只对 `bert-base-uncased` 那种尺寸成立：

```text
bert-base-uncased   hidden=768  intermediate=3072  ⇒ 比例恰好 4.0
一个 hidden=16 的小 BERT                            ⇒ 比例 192.0
```

这条**不是推理出来的**，是读出来的。它值一个测试，因为一句"两个架构都是 4 倍"
听起来完全合理——而它是错的。本包的写法：

```python
@property
def ffn(self) -> int:
    if self.intermediate is not None:
        return self.intermediate              # 配置里有就用配置里的
    if self.model_type == ARCHITECTURE_BERT:
        return BERT_DEFAULT_INTERMEDIATE      # 3072
    return FFN_RATIO * self.hidden             # GPT-2 的规矩
```

### 4.3 头数必须整除隐藏维：同一个条件，两个族

```python
if hidden % heads != 0:
    raise ConfigError(f"{keys['hidden']}={hidden} 不能被 {keys['heads']}={heads} 整除："
                      "head_dim = 16/5 不是整数，这个模型**没有定义**。")
```

同一个条件在 `hf_source.split_heads` 里报的是 `ShapeError`。这不是不一致，
而是**按谁去修分族**这条纪律的第二次兑现：

```text
hf_source.split_heads      要改的是**这次调用的 heads**          → ShapeError
hf_integration.parse_config 要改的是**那份配置文件**（或换模型）  → ConfigError
```

报错点离出错点越近，修起来越便宜：真实装载会在某一次 `reshape` 上失败，
而本包在**解析配置的那一刻**就拒绝。

## 第五章：参数量是算出来的

### 5.1 两个整数

```text
gpt2（124M）  vocab=50257 n_embd=768 n_head=12 n_layer=12 n_positions=1024 tie=True
              → 124 439 808
bert-base     vocab=30522 hidden=768 heads=12 layers=12 positions=512 type=2
              → 109 482 240
```

两者都能在真库上复核：

```python
sum(p.numel() for p in transformers.GPT2LMHeadModel(GPT2Config(**tiny)).parameters())
```

**"我理解了这个架构"是一句无法反驳的话**，而一旦写成"给定这几个整数，
参数量必须等于某个数"，它就变成一条能失败的判据。两条公式的差别集中在三处：

```text
LN 的个数       GPT-2 每层 2 个 + 栈尾 1 个；BERT 每层 2 个 + 嵌入后 1 个
嵌入的三张表     BERT 多一张 token_type（type_vocab × hidden）与一次**带参数**的嵌入后 LN
池化            BERT 多一个 pooler（hidden² + hidden）
```

### 5.2 差值必须被逐项解释

本包的前向**省略了注意力的偏置**（day075 的四个投影都不带偏置），
因此它的真实参数量比配置口径少。差值可以被算出来：

```text
配置口径的每一层    12h² + 13h
本包权重每一层      12h² +  9h
差                 4h        = 注意力的偏置
```

而 4h 在两边的**拆法不同**：

```text
GPT-2   c_attn 的偏置 3h  +  c_proj 的偏置 h            （一次融合投影，分成两段）
BERT    query/key/value 各 h  +  output.dense 的 h      （四次独立投影，各一）
```

演示与测试里的读数：`配置 11536 / 权重 11408 / 差 128 = 4·16·2`。
于是 `weights_gap_is_explained` 是一条**可失败**的断言——而它抓住的错法是
"偏置被漏算或错算"（那时差值就不再是一个可拆的数）。

## 第六章：两个文件加一个循环

### 6.1 字节级是什么意思

```python
def bytes_to_unicode() -> dict[int, str]:
    direct = (list(range(ord("!"), ord("~") + 1))      # 33..126 可见 ASCII
              + list(range(ord("¡"), ord("¬") + 1))    # 161..172
              + list(range(ord("®"), ord("ÿ") + 1)))   # 174..255
    ...
```

先把文本编成 UTF-8 字节，再把每个字节映射成一个**可打印字符**（256 ↔ 256 一一对应）。
于是这一族里**没有 unknown token 这件事**——任何字节串都能被切出来。

真库那一侧有同一个函数，而它是 byte-level BPE 的地基：

```python
assert bytes_to_unicode() == transformers.models.gpt2.tokenization_gpt2.bytes_to_unicode()
```

映射错一个键，某一段字节就会切错——而它只在**含那个字节的文本**上出错，
因此"随手试几条都正常"是可能的。

### 6.2 一个汉字几个 token 是**词表的性质**

```text
本包的玩具词表：256 个基元 + 20 条合并 ⇒ 一个汉字**恰好 3 个 token**（UTF-8 三字节）
真实 GPT-2：50257 个 token            ⇒ 常见汉字常被合并成 1~2 个
```

两边都没错。本包在文档与笔记里都写清了这句限定——因为一句"汉字很费 token"
如果不带"在什么词表下"，它就是一句不可反驳的话。

### 6.3 预分词：两条容易读错的地方

```text
① 四条分支的**顺序即优先级**
   缩写 → "可选空格 + 字母串" → "可选空格 + 数字串" → "可选空格 + 其他" → 空白串
   因此 "hello world" → ("hello", " world")   ← 词首空格与词绑在一起
   而   "  leading"   → ("  ", "leading")     ← 两个空格是另一个 piece

② 缩写识别**区分大小写**（真实实现的模式里没有 IGNORECASE）
   "don't" → ("don", "'t")     而     "I'M" → ("I", "'", "M")
```

### 6.4 一个被复刻的怪癖

真实 `Encoder.__init__` 里是 `dict(zip(bpe_merges, range(len(bpe_merges))))`。
`dict` 的构造会让**后出现的重复键覆盖先出现的**——因此一份含重复合并对的
`merges.txt` 里，是**最后一次**出现决定名次，而不是第一次：

```python
>>> merge_ranks((("a", "b"), ("c", "d"), ("a", "b")))
{('a', 'b'): 2, ('c', 'd'): 1}
```

本包逐字复刻这条行为，并给它配一条测试——因为"第一次生效"是一个很自然的直觉，
而真实实现里它是反的。

## 第七章：一次真前向

```text
GPT-2    embed = wte[id] + wpe[pos]                      （不加 LN）
         L ×      x = x + attn(ln_1(x)); x = x + mlp(ln_2(x))
         ln_f     最后一次 LayerNorm；lm_head 与 wte **共享**
BERT     embed = LN(wte[id] + wte_type[0] + wpe[pos])     （多一次 LN）
         L ×      x = ln_1(x + attn(x)); x = ln_2(x + mlp(x))
         pooler   tanh(W·x[0] + b)
```

本包的层执行函数 `forward.run_one_block` 与 day085 的 `gpt2_block` **逐字相同**，
只多了一个参数：一张**显式掩码**。这条扩展是必需的，原因在下一章。

写法上有一处刻意的复用：layer norm、残差、前馈、四个投影全部来自
day079~085 的既有实现，因此"本包的块与 day085 的块落在同一个值上"
是一条**真的**对账，而不是两份格式不同的东西互相看一眼：

```python
mine      = run_one_block(card, weights, 0, states, causal=True)
reference = gpt2_block(block, attention, states, shape, activation=card.activation, causal=True).output
assert mine == reference           # **逐位**，不是容差
```

两条路径的差别只有一处：`gpt2_block` 内部**造一张加性偏置**，
本包**给一张显式掩码**。它们在每一个浮点数上相同——这才是"接线没有走散"的证据。

## 第八章：填充什么时候是惰性的（本课最值钱的一章）

### 8.1 单条样本内的结论

```text
因果侧：填充排在真实位置**之后**，因果掩码让它们一格都传不回来  ⇒ 填充是惰性的 ✔
双向侧：填充会真的改写真实位置那一行的输出                    ⇒ 必须先切开再跑
```

本包把它写成两个策略：

```text
safe    因果：整批一次跑，掩码是**段内下三角**
        双向：按真实长度切开，逐条跑
naive   一律整批一次跑（因果侧漏掉"段"、双向侧漏掉"切开"）
```

### 8.2 但"因果 ⇒ 填充惰性"只在**单条样本内**成立

这是本课最值钱的一条工程结论，而它是被**测试逼出来的**。第一版实现里，
因果侧的批量就是"整批跑 + 一张 `(n, n)` 的下三角"，然后我写了这条断言：

```python
assert batch.rows == singles        # 批量与逐条必须逐位相同
```

它**红了**。原因不是浮点，而是语义：

```text
三条样本首尾相接之后，第 2 条样本的第 0 个 token 落在第 1 段的末尾之后，
  因此在"整条长序列的下三角"之内 ⇒ 它能看到第 1 条样本的**全部** token
```

它不报错、也不给出异常读数：第 2 条的输出只是**偏了**，
而偏的方向取决于同一批里前面那条样本的内容。正确做法是把掩码升级成
**段内下三角**（真实实现里那张 `(batch, 1, seq, seq)`）：

```text
三条各 2 长的样本：
  0: 1 1 . . . .
  1: 1 1 . . . .
  2: . . 1 1 . .
  3: . . 1 1 . .
  4: . . . . 1 1
  5: . . . . 1 1
```

而**第 1 条样本在 naive 下碰巧是对的**——这正是这类 bug 最难被发现的地方：
拿一条样本试，永远试不出来。演示读数：

```text
gpt2：批量与逐条逐位一致：True；naive 策略与 safe 的最大差 3.657138e+00
      （归因：跨样本串味（漏掉'段'））
bert：批量与逐条逐位一致：True；naive 策略与 safe 的最大差 1.6…e+00
      （归因：填充污染（没有切开））
```

**两种架构的 naive 错法不同**，而这一点必须写下来，否则读到的差无法归因。

### 8.3 池化：只差一个分母

```text
mean_correct = sum(真实位置) / 真实长度     # ← 分母是真实长度
mean_buggy   = sum(全部位置) / 总宽度       # ← 分母是总宽度：填充越多，向量越"短"
```

手算锚点（`states = (1,1) (3,3) (5,5) (9,9)`、`mask = 1 1 1 0`、`mean`）：

```text
正确版 (3.0, 3.0)   真实 3 格之和 ÷ 3
违反版 (4.5, 4.5)   4 格之和 ÷ 4
```

演示读数（三条真实长度 `[5, 2, 9]`）：

```text
正确池化在两种填充宽度下的最大差 0.000000e+00   ← **逐位**要求 0
违反 mask 的代价：宽 12 时 1.451731e+00（填充占比 55.6%）、宽 16 时 1.524318e+00
```

两个读数放在一起才有意义：**没有填充时两版逐位相同**——
因此"我本地测过没问题"与"它在线上是错的"可以同时成立。
本包把违反的那一版也实现出来（`pool_masked(..., ignore_mask=True)`），
理由与 day082 的探针一样：**一条规矩如果没有一个读数，它就无法被反驳。**

## 第九章：两条管线

```text
text_generation     逐条跑（长度不齐、各自停在 eos）；settings **原样**透传给 day085
feature_extraction  可以合批；池化按 mask；双向侧**先切开**
```

### 9.1 为什么生成不能合批

生成是自回归的：第 t 步的输出是第 t+1 步的输入。合批之后两条样本的第 t 步
落在同一个矩阵乘法里，而其中一条可能已经该停了：

```text
一起停      另一条被提前截断（它的 token 序列少了一截，而结果看起来完整）
不停        撞上 eos 的那条继续生成（输出里多了一段本该结束的内容）
```

本包因此逐条跑，并把每条的长度印出来（`GenerationOutput.generated_lengths()`）。

### 9.2 解码只解"新生成的那一段"

```python
texts.append(tokenizer.decode(result.generated, skip_special_tokens=skip_special_tokens))
```

把 prompt 一起拼回去会让"模型生成了什么"消失在字符串里——
而"它是不是把 prompt 原样吐了回来"恰恰是最需要被看见的一种失败。

### 9.3 "换管线不改模型"的可断言形式

`run_both` 的两份结果来自**同一份权重对象**（一次都没重新造过参数）：

```python
generation, features = run_both(card, weights, tokenizer, prompt, settings)
```

这条纪律在报告上的样子是"两条管线共用一次装载"，而在代码里它就是
"两个函数收的是同一个 `weights`"。

## 第十章：接进 `local_model`

### 10.1 接的不是代码，是**接口面**

day045 的 `LocalModel` 走的是**协议**路线（Ollama / vLLM 的 OpenAI 兼容端点）。
今天出现第三条路线：模型就在这个进程里。三条路线并存时，上层代码凭什么一行不改？

答案写在**一张清单**里：

```python
PROTOCOL_SURFACE = ("chat", "stream", "chat_with_tools", "is_available",
                    "describe", "model_name", "backend", "context_length")
```

`verify.check_protocol_surface_matches` 逐名核对两边——一条能被失败的对账。
反过来，少一个 `describe` 的后果是监控里安静地少一行读数，
而"少一行"与"这一项没问题"读起来一样。

### 10.2 三条路线各自的**事实**

| | 服务端 | 离线 | 视觉 | 工具调用 | 上下文窗口来自 |
|--|-------|------|------|---------|---------------|
| `in-process` | 不需要 | 是 | 由模型 | **不支持** | 位置表长度（写死在配置里） |
| `ollama` | 需要 | 是 | 支持 | 支持 | `OLLAMA_CONTEXT_LENGTH`（默认 4096） |
| `vLLM` | 需要 | 是 | 按模型 | 支持 | `--max-model-len` |

第四条差别最容易被忽略而后果最大：**上下文窗口的来源不同**。
在进程模型的窗口是"模型的硬上界"（本课的玩具卡片是 32），
而 Ollama 的默认 4096 是"我们的一个选择"——同一段长文本在两条路线上的
"够不够用"是两个不同的答案。

### 10.3 一处"明确不支持"胜过"静默降级"

```python
def chat_with_tools(self, messages, tools, temperature=0.7, max_tokens=1024):
    del messages, tools, temperature, max_tokens
    raise NotImplementedError("在进程模型不实现 function calling：本包的玩具主干没有工具调用头。")
```

day045 的 `LocalModel` 之所以实现它，是因为 Ollama 的兼容端点**真的支持** `tools` 字段。
本包的玩具主干没有工具调用头，因此"假装支持"的后果是：调用方以为会拿到 `tool_calls`，
实际拿到一段自由文本，而 Agent 会带着这段文本继续跑——
它看起来像"模型决定不调工具了"。

### 10.4 工厂与四条硬规则

```python
def choose_backend(*, offline_required=True, needs_tools=False, needs_vision=False,
                   needs_batching=False, multi_user=False, long_context=False) -> BackendChoice
```

两条硬规则先判（需要工具 ⇒ 不是 in-process；需要视觉 ⇒ 只有 ollama），
然后是三条软规则（多用户/批量 ⇒ vLLM；要长上下文 ⇒ 能调窗口的那条；其余 ⇒ in-process）。
每一条都带上理由——因为"选了哪条"与"为什么选它"必须一起被印出来。

## 第十二章：边界与后续

### 12.1 五条边界（**本课明确不承诺的事**）

```text
① 本包复现的是解析与装箱语义，不是 huggingface_hub 的内部实现
   （并发下载、断点续传、符号链接与 xet 存储都不在其中）
② 本包不下载任何东西：网络侧由一个可注入的 Hub 客户端承担，测试里它是内存假仓库
③ 参数量公式覆盖两个架构，不覆盖专家混合、跨层共享、量化权重
④ byte-level BPE 不含 tokenizer.json 里的正规化与预分词规则 ⇒ 中文切法只是"可复现"
⑤ 块只支持**因果 / 全双向**两种掩码，不支持 padding 掩码；
   双向侧处理填充的办法是**先切开**
```

第 ⑤ 条是这一课留下的最大悬念：本包没有"给注意力塞一张 padding mask"这条路径，
而 day087 要接的是**推理优化**——KV Cache 与量化都只作用于推理，
那时"一张 `(batch, 1, seq, seq)` 的掩码"会变成 cache 的一部分。

### 12.2 三条纪律的第四次兑现

```text
① 每一行都要带两个数        命中/下载、配置/库、真实长度/总宽度、safe/naive
② "不适用" ≠ "通过"         两条性质真的走到了"不适用"
③ 不可能失败的判据不算判据    逐文件缓存那条判据从**空缓存**开始跑
```

第 ③ 条是今天新学的，而它有一个副产品：它也让"第二次解析"这件事必须
**共用同一个缓存**——否则"命中"永远不会发生，而两轮看起来都正常。

### 12.3 与后续的接缝

```text
day087  高效推理与量化：KV Cache 与量化都只作用于**推理**，
        而今天的 hidden_states 正是那条推理路径；
        "段内掩码"会成为 cache 的一部分（缓存的是一整段还是逐条？）
day088  项目底层原理串联：用今天这六张表写"原理 → 应用"的提纲
```

今天最值得带走的一句话与 day085 那句对着看：

```text
day085  "分头"发生在**投影内部**         —— 读源码读出来的结构事实
day086  "因果 ⇒ 填充惰性"只在**单条样本内**成立 —— 装进来才撞上的工程事实
```

两句都是"一句话 + 一个能失败的判据"，而第二句是被测试逼出来的。
