## 第一部分：选择题

### 第 1 题

**答案：B**

**解析**：流式最直接的收益是**首字延迟（TTFT）**的下降：总耗时几乎不变（模型生成的总字数、总 token 数没有减少），但用户从"盯几秒空白"变成"1 秒内看到第一个字、边看边等"，感知性能大幅提升。A 错在因果——流式不省模型计算的耗时，只省了"攒满整段再发"的延迟；C 属于臆测，流式/一次性走的是同一模型同一推理，内容质量与是否流式无关；D 直接违反本日的协议契约：流式与一次性拼接后**内容相等**，只是传输方式不同（`test_stream_equivalent_to_one_shot` 守护这一点）。

### 第 2 题

**答案：D**

**解析**：A、B、C 都是本日 `routes.py`/`test_api.py` 的真实设计（空行分隔事件、`delta` 是增量、`[DONE]` 哨兵区分正常结束与异常中断）。D 错误——SSE 协议只规定了 `data:` 字段和空行分隔这类**报文骨架**，`data:` 后面跟什么**内容**（裸文本、JSON、自定义结构）完全由服务自定义。我们选 `{"delta": "..."}` 只是自选的客户端约定，OpenAI 的流式用的就是另一种更复杂的 JSON 结构。协议框架与载荷结构是两层，不能混为一谈。

### 第 3 题

**答案：B**

**解析**：`resolve_model` 的语义是"`model is None` 时直接返回默认 `llm`"——这个 `llm` 是 `create_app(llm=...)` 注入的 `app.state.llm`，它可以是单模型也可以是 `ModelRouter`（取决于调用方怎么装配）。A 错：不携带 `model` 时**根本不查注册表**，走的是独立的 `app.state.llm`，它与注册表是两套东西（`test_default_model_when_not_specified` 精确验证了这一点）。C 错：`model` 是可选字段，缺省不是错误。D 错：是否路由取决于注入对象是什么，注入 `MockLLM` 就是普通单模型，不会凭空变成 Router。

## 第二部分：判断题

### 第 4 题

**对。**

`BaseLLM.stream` 的默认实现就是 `yield self.chat(...)`——把完整回复作为一个片段产出。因此一个只重写了 `chat`、完全没有流式概念的旧实现，调用 `stream` 也能工作：协议上它是流式（返回一个生成器、可逐片迭代），只是只有一片。这让流式能力**向后兼容**，加流式不需要所有实现立即跟进。`test_base_default_stream_yields_single_chunk` 用一个只实现 `chat` 的 `_ChatOnlyLLM` 验证了"单片段、内容完整"。

### 第 5 题

**错。**

原理与 day038 第三章完全一致：`/chat/stream` 内部的 `target.stream` 是**同步阻塞**的生成器（底层是同步 `llm.chat` 的 HHTP 调用），必须声明为普通 `def`，让 Starlette 把它丢进**线程池**里迭代——事件循环在等待 LLM 的增量时不至于被冻结。若声明为 `async def` 并直接在函数体里遍历这个同步生成器，事件循环会在每一个阻塞的 `chat` 调用上停摆。`async def` 只在"生成器本身是异步可迭代（`async for`）"时才正确。

### 第 6 题

**对（在"正确性"的意义上）。**

流式是一次性的另一种传输方式，不是另一种模型。把"片段按序拼接 == 一次 chat 的完整回复"固化为契约，意味着：流式实现**不该**改变内容，测试也**只需**断言这一条不变量就能覆盖流式正确性。`test_llm.py` 的 `test_mock_stream_reassembles_to_chat`、`test_router.py` 的 `test_stream_reassembled_equals_chat`、`test_api.py` 的 `test_stream_equivalent_to_one_shot` 分别在 LLM 层、路由层、API 层各自验证了这条等价性。需要补一个限定：这条契约管住的是"内容正确"，管不住"分片节奏/时延"这类性能维度——后者需要单独的性能测试。

## 第三部分：简答题

### 第 7 题

**参考答案**：

`/agent/run` 的响应不是"一段纯文本"，而是结构化的三部分：`answer`（最终答案）、`steps`（消耗了几轮 LLM 调用）、`tool_calls`（每次工具调用的审计轨迹）。这个结构决定了它不适配流式，原因有三：

1. **中间步骤没有"可用输出"**：Agent 内部是多轮"决策 → 工具执行 → 回填"，每一轮 LLM 输出要么是 `tool_calls`（结构化决策，必须**整体拿到**才能解析工具名与参数去执行），要么是最终答案。等最终答案出来之前，`tool_calls` 这种结构化结果对等待中的客户端没有展示价值——推半截 JSON 没意义。
2. **审计轨迹必须完整**：`steps` 和 `tool_calls` 是任务**结束后**才能统计完整的（尤其 `steps` 是 `run()` 前后取差值）。流式推"进行到一半的轨迹"既不准确也无用。
3. **语义上它是"整体交付"的接口**：调用方要的是"跑完一次任务拿到完整结论 + 可审计的轨迹"，这是批处理语义，不是"边生成边读"的对话语义。

一句话：**流式适配的是"纯文本、人直接消费、可增量理解"的场景**；`/agent/run` 适配的是"结构化、机器消费、整体可用"的场景。二者边界清晰，所以只给 `/chat` 加了 `/chat/stream`。

### 第 8 题

**参考答案**：

- **422 Unprocessable Entity**：请求**语法可理解但语义不符合契约**——字段类型错、缺必填、超范围（如 `message: ""`、`temperature: 3.0`）。它回答的是"这**不是一个**合法请求"。
- **404 Not Found**：请求是**合法的**，但它指向的**资源不存在**。`model="nope"` 是一个合法字符串，只是这个模型名不在候选集里——"合法但不存在"。

客户端据此分支：

- 拿到 422：是**我发错了**，需要改请求体再发；
- 拿到 404：是**我点的资源不在**，应该调 `/models` 拿合法清单、换一个再发。

我们还在 404 的 `detail` 里附上了可用的模型名清单（`未知模型: nope，可用模型: fast, mock`），让错误信息本身给出**下一步行动**——这是 day038"错误也是契约"的延续：状态码负责机器分支，`detail` 负责人类可读与可行动。对应测试 `test_unknown_model_returns_404` 同时断言状态码与 `detail` 内容。

## 第四部分：编程题

### 第 9 题

**参考实现**（与 day039 快照 `tests/test_router.py` 的 `test_stream_fallback_on_failure` 一致）：

```python
import pytest

from smart_research_agent.llm.base import BaseLLM, Message
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.llm.router import ModelRouter, ModelSpec


class FailingLLM(BaseLLM):
    """只重写 chat，stream 走 BaseLLM 默认实现 -> 遍历时调 chat -> 抛异常."""

    def __init__(self, error: str = "connection refused"):
        self.error = error
        self.calls: list = []

    def chat(self, messages, temperature=0.7, max_tokens=1024) -> str:
        self.calls.append(messages)
        raise ConnectionError(self.error)


def test_stream_fallback_on_failure():
    models = [
        ModelSpec("cheap", FailingLLM(), capability=2, cost_per_1k=0.001),
        ModelSpec("mid", MockLLM(default="中档模型的回答"), capability=3, cost_per_1k=0.01),
        ModelSpec("strong", MockLLM(default="强模型的回答"), capability=5, cost_per_1k=0.1),
    ]
    router = ModelRouter(models)

    chunks = list(router.stream([Message(role="user", content="2+3 等于几")]))

    assert "".join(chunks) == "强模型的回答"   # 降级链按能力从强到弱：strong 先生效
    decision = router.decision_log[-1]
    assert decision.chosen == "cheap"          # 首选仍是 cheap
    assert decision.fallback_used == "strong"  # 实际生效的是 strong
```

**要点解析**：`FailingLLM` 只重写了 `chat`，它的 `stream` 是 `BaseLLM` 默认实现——默认实现是个生成器函数（含 `yield self.chat(...)`），**调用时不执行**，只有在路由器 `for chunk in spec.llm.stream(...)` 的迭代过程中才真正触发 `chat`、抛出 `ConnectionError`。这个异常发生在路由器 `try` 覆盖的范围内，于是被捕获、沿降级链换下一个模型重新流式。这反向证明了第二章"默认 stream 是惰性生成器"这一设计对降级语义的支撑：如果默认实现是"调用即执行"，异常会提前抛在路由器的迭代之外，降级照样能捕获，但失败点不同——两种情况下"首选失败换下一个"的语义都成立，本测试锁定的是其中一种路径。

### 第 10 题

**参考实现**（契约检查 + 语义辨析）：

```python
def test_openapi_has_stream_models_and_model_field():
    resp = make_client().get("/openapi.json")
    assert resp.status_code == 200
    spec = resp.json()

    # 1. 新端点进入 paths
    assert "/chat/stream" in spec["paths"]
    assert "/models" in spec["paths"]

    # 2. ChatRequest 的 model 字段进入 properties（且可空）
    chat_req = spec["components"]["schemas"]["ChatRequest"]
    assert "model" in chat_req["properties"]
    model_prop = chat_req["properties"]["model"]
    # pydantic v2 对 str | None 生成 anyOf: [{type:string},{type:null}]（或含 $ref）；
    # 这里只断言"可空字符串"这一语义成立即可
    assert model_prop.get("anyOf") is not None or model_prop.get("type") == "string" \
        or "null" in str(model_prop)
```

（更简洁的断言可写成：`openapi.json` 的 `ChatRequest.properties` 里存在 `model`，且 `month` 之上的 `temperature` 仍在；路径集合包含 `/chat/stream`、`/models`。）

**语义辨析**（schema 能表达什么、表达不了什么）：

- **schema 能直接表达**的：① `model` 存在且为字符串类型；② 它**可空/可选**（`str | None` 反射为 `anyOf`/`null`，`None` 默认值反映为"非 required"）——即"不传也合法"。`required` 列表里**没有** `model`，机器即可判定它是可选字段。
- **schema 表达不了**的：① `model=None` 时走默认 `llm` 还是走注册表第一个模型（这是 `resolve_model` 的运行时逻辑）；② 未命中返回 404 且 `detail` 附带可用清单（状态码与错误载荷约定）；③ 注册表里有哪些名字（由 `default_models`/注入决定，不在静态 schema 里）。这些属于**运行时行为契约**，只能靠测试（`test_default_model_when_not_specified`、`test_unknown_model_returns_404`、`test_list_models`）守护。

这恰好呼应 day038 的结论：OpenAPI/Pydantic 给出的是**结构与类型**的单一事实源，保证的是"不漂移"；**语义层**（业务分支、状态码、错误信息）仍需要人写描述与测试——机器保证结构同步，保证不了所有语义。
