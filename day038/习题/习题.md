## 第一部分：选择题

### 第 1 题（服务层的必要性）

关于"为什么 Agent 需要 HTTP 服务层而不是继续用脚本形态"，下列哪一项理由是**错误**的？

- A. 脚本要求调用方 import 你的 Python 包，语言、依赖环境、机器三者都被锁死；HTTP 把调用换成跨进程消息，实现解耦
- B. 脚本是"跑完就退"的批处理模型，无法持续驻留并并发受理多个请求
- C. HTTP 服务可以借助 API 契约在框架层校验请求，业务代码无需写防御性校验
- D. 脚本形态下 Python 函数调用比 HTTP 请求慢，服务化主要是为了提升单次调用的性能

### 第 2 题（422 的产生机制）

客户端向 `/chat` 发送 `{"message": "hi", "temperature": 3.0}`，收到的响应是 422。关于这个 422，下列说法**正确**的是：

- A. 422 由路由函数里的校验代码主动抛出，表示业务逻辑拒绝了请求
- B. FastAPI 在校验失败时抛出 `RequestValidationError`，由框架内置处理器转为 422；路由函数从头到尾没有执行
- C. 422 表示请求体不是合法 JSON，服务器无法理解语法
- D. 之所以是 422 而非 400，是因为 400 已被 `/health` 端点占用

### 第 3 题（同步代码与异步框架）

我们的三个端点全部声明为普通 `def` 而非 `async def`。这样做的原因是：

- A. `def` 路由性能更好，因为省去了协程调度的开销
- B. `async def` 路由不支持 Pydantic 请求校验
- C. Agent 循环内部是同步阻塞代码（多次 LLM HTTP 调用），声明为 `def` 时 FastAPI 把它丢进线程池执行，事件循环不被阻塞；若塞进 `async def` 会在执行期间冻结整个事件循环
- D. uvicorn 只支持 `def` 路由
