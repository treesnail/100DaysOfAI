## 第一章：从 LLM 到 Agent —— "说"与"做"的鸿沟

### 1.1 LLM 的本质：一台极其博学的"文本续写机"

先用一句不严谨但有用的话概括大语言模型（LLM）的工作方式：

> 给它一段文本，它预测"接下来最可能出现的文本"。

这意味着 LLM 的全部能力边界是**输入一段文字，输出一段文字**。它博学、能推理、会写代码，但它**不能改变世界，也不能感知世界的当前状态**。

看一个具体的场景。你问 LLM：

> "北京今天气温多少度？我出门要不要带伞？"

LLM 会怎么回答？它可能说"建议您查看天气预报应用"，也可能煞有介事地编一个"今天北京 28℃，多云"——后者就是**幻觉（Hallucination）**。无论哪种，问题都一样：

- LLM 的训练数据有截止日期，它**不知道"今天"是哪天**，更不知道今天北京的实时气温；
- 即使知道气温，它也不能替你**做任何事情**——不能帮你下单买伞、不能把提醒写进你的日历。

```
        ┌──────────────────────────────┐
        │            LLM               │
        │                              │
 文本 ─▶│  输入文本 ──▶ 预测 ──▶ 输出文本 │─▶ 文本
        │                              │
        │   无感知：不知道现在几点        │
        │   无行动：不能查天气/发邮件     │
        │   无记忆：每次调用从零开始      │
        └──────────────────────────────┘
```

一句话总结：**LLM 只会"说"，不会"做"。**

### 1.2 Agent 的定义：LLM + 感知 + 行动 + 记忆

Agent（智能体）就是为了跨越这条鸿沟而生的系统。一个被广泛接受的定义是：

> **Agent 是一个能够感知环境、进行推理决策、采取行动影响环境，并通过记忆积累经验的自治系统。LLM 在其中扮演"大脑"（推理引擎）的角色。**

对应到工程上，一个 LLM Agent 由四个核心组件构成：

```
                        ┌─────────────┐
                        │   Memory    │
                        │   记忆       │
                        └──────┬──────┘
                               │ 读写上下文
                               ▼
┌─────────────┐      ┌─────────────────┐      ┌─────────────┐
│ Perception  │─────▶│   Reasoning     │─────▶│   Action    │
│   感知       │ 信息  │  推理（LLM 大脑）│ 决策 │   行动       │
└─────────────┘      └─────────────────┘      └──────┬──────┘
      ▲                                               │
      │                环境反馈（Observation）          │
      └───────────────────────────────────────────────┘
```

这四个组件不是学术装饰，每一个都直接对应我们项目里将要写的代码模块。逐一展开：

### 1.3 组件一：感知（Perception）

**职责：把外部世界的信息转化为 Agent 可处理的输入。**

对人类来说，感知是眼睛、耳朵；对 LLM Agent 来说，感知是"信息的入口"，常见形态：

| 感知形态 | 例子 | 在我们项目中的位置 |
|---------|------|------------------|
| 用户输入 | 对话框里的任务描述 | `ReactAgent.run(task)` 的参数 |
| 工具返回结果 | 搜索 API 返回的网页摘要 | 工具的 `execute()` 返回值（day004） |
| 文件/环境状态 | 读取本地文件、查询数据库 | 后续 RAG 阶段的检索器 |

关键认知：**LLM 的"知识"是静态的，感知是让它接触动态世界的唯一通道。** 没有感知，"北京今天气温"永远无解。

### 1.4 组件二：推理（Reasoning）

**职责：分析感知到的信息，决定"下一步该做什么"。**

这是 LLM 的主场，也是 Agent 的"大脑"。推理组件要回答的问题是：

- 当前我已经知道了什么？
- 还缺什么信息？
- 缺的信息能通过哪个工具获得？
- 信息够了，可以直接回答了吗？

注意推理的产出**不是最终答案，而是"下一步行动的决策"**。这是 Agent 与普通对话的本质区别：对话的目标是"说得好"，推理的目标是"选得对"。

在我们项目中，推理引擎就是 `llm` 组件（day005 接入），而"如何组织推理过程"正是本章 ReAct 要解决的问题。

### 1.5 组件三：行动（Action）

**职责：把推理的决策落地为对环境的真实操作。**

行动是 Agent "会做"的那一半。常见形态：

| 行动形态 | 例子 | 风险级别 |
|---------|------|---------|
| 只读查询 | 调搜索 API、查数据库、算一算 | 低：不改变世界 |
| 本地写操作 | 写文件、改配置 | 中：可回滚 |
| 外部副作用 | 发邮件、下单、调支付接口 | 高：不可逆 |

这个风险分级很重要，它直接决定了工程设计的严格程度。我们在 day004 实现的 `CalculatorTool` 是最安全的只读行动；到后期接入网络搜索、文件写入时，就需要日志审计（day001 打的地基在这里兑现）和更严格的参数校验。

### 1.6 组件四：记忆（Memory）

**职责：跨越单次调用保存状态，让 Agent"记得"之前发生了什么。**

LLM 本身是无状态的——每次 API 调用都是一张白纸，它之所以"记得"你上一句话，是因为你把整段对话历史都重新发给了它。记忆组件管理的就是这份历史：

- **短期记忆**：当前会话的对话与推理轨迹（day008 实现 `ShortTermMemory`）；
- **长期记忆**：跨会话沉淀的知识与经验，用向量检索按需召回（day009 实现 `LongTermMemory`）。

没有记忆的 Agent 每做一步都"失忆"；有了记忆，它才能做多步推理、记住用户偏好、从过去的任务中学习。

### 1.7 四组件如何组装成一个循环

把四个组件连起来，就是 Agent 的运行本质——**一个持续的循环**：

```
      ┌────────────────────────────────────────────┐
      │                                            │
      ▼                                            │
  感知环境 ──▶ 大脑推理："现在该怎么办？" ──▶ 选择并执行行动
      ▲                                            │
      │                                            ▼
  记忆更新 ◀── 记录这一步的所见所行 ◀── 行动产生结果（观察）
      │
      └── 循环，直到任务完成或达到终止条件
```

这个图值得记住，因为 ReAct 就是它的一个具体实例化：把"推理"显式写成 Thought，把"行动"写成 Action，把"观察"写成 Observation。

> 思考题 1：导航软件算不算 Agent？  
> 提示：对照四组件检查——它感知 GPS 位置（感知）、规划路线（推理）、给你语音指令（它的"行动"是影响你，而非直接控制方向盘）、记住你的家和公司地址（记忆）。这个边界案例能帮你看清"Agent 程度"是一个光谱，而不是非黑即白。

## 第二章：为什么需要推理-行动协同 —— ReAct 的诞生逻辑

### 2.1 纯推理路线的代表：Chain-of-Thought（思维链）

2022 年提出的 Chain-of-Thought（CoT，思维链）提示法发现：只要在提示词里加一句"让我们一步一步思考"，让 LLM **把推理过程写出来再作答**，数学和逻辑题的正确率会大幅提升。

```text
问题：小明有 3 箱苹果，每箱 12 个，送给同学 8 个，还剩几个？

CoT 输出：
先算总数：3 × 12 = 36 个。
再减去送出的：36 - 8 = 28 个。
所以还剩 28 个。
```

CoT 的思想深刻影响了后续所有 Agent 设计：**显式的中间推理步骤，是提升复杂任务正确率的关键杠杆。** 但它有一个无法自愈的硬伤。

### 2.2 纯 CoT 的两大局限

**局限一：无法获取外部信息——推理链是封闭的。**

CoT 的每一步推理都只能基于两样东西：模型训练时记住的知识 + 当前对话里的文本。对于"北京今天气温"这类问题，训练数据里没有答案，对话里也没有答案，推理链再长也只是在**封闭的信息空间里打转**。推理得再精彩，前提错了（或者前提根本不存在），结论就是空中楼阁。

**局限二：幻觉计算与幻觉事实——越长的链条越容易出轨。**

LLM 并不真的"会算数"，它只是模仿计算的文字形式。复杂运算（比如 `123456 × 789`）它经常算错，而且**错得理直气壮**——幻觉不会因为"一步步来"而消失，反而可能一步错、步步错，整条推理链朝着错误方向越滚越远，中途没有任何机制把它拉回现实。

一句话：**CoT 只有 Thought，没有 Action 和 Observation，推理过程与现实世界之间没有反馈回路。**

### 2.3 纯行动路线的局限：没有推理的行动是僵化的

另一个极端是传统的"工具调用流水线"：预先写死流程——第一步调搜索 API，第二步调天气 API，第三步生成报告。这在流程固定的场景没问题，但真实任务充满意外：

- 搜索结果为空怎么办？
- 用户的问题需要先算一道算术再决定搜什么关键词怎么办？
- 中途发现方向错了，能不能换条路走？

固定流水线对这些问题无能为力，因为**行动序列在运行前就被焊死了，运行中没有"想一想"的环节**。

### 2.4 ReAct 的核心思想：把推理和行动交织成一条轨迹

2022 年，Google Brain 的 Yao 等人在论文《ReAct: Synergizing Reasoning and Acting in Language Models》中提出了一个简洁而强大的方案：

> **让 LLM 交替输出"思考"（Thought）和"行动"（Action），每次行动的结果（Observation）再回到上下文中，供下一轮思考使用。**

```
Thought: 我现在知道什么？下一步该做什么？
Action: 调用哪个工具？
Action Input: 给它什么参数？
   │
   ▼ （系统真正执行工具）
Observation: 工具返回的真实结果
   │
   ▼ （结果回到上下文）
Thought: 基于刚才的观察，现在该怎么想？
Action: ...
   │
   ▼
... 如此交替 ...
   │
   ▼
Final Answer: 信息足够，给出最终答案
```

ReAct 的精妙之处在于它同时吸收了 CoT 和工具调用的长处，并且两者**互相成就（Synergy）**：

- **推理引导行动**：Thought 决定"调哪个工具、传什么参数"，行动不再是写死的，而是每一步由大脑动态决策；
- **行动反馈推理**：Observation 把真实世界的信息注入推理链，幻觉有了"现实的锚点"——算错了？工具会返回正确结果。不知道今天天气？查一下就有了。

### 2.5 走一遍"带伞"的例子

用"查北京今天气温再决定是否带伞"这个任务，把三种范式放在一起对比，你会看得最清楚。

**纯 CoT 的轨迹（悲剧版）：**

```text
Thought: 北京这个季节一般二十多度，降水概率不高。
Thought: 所以我判断不用带伞。
Final Answer: 不用带伞。（实际上今天北京雷阵雨 19℃——幻觉，全错）
```

**固定工具流水线的轨迹（僵硬版）：**

```text
Step 1: 调用 weather_api("北京")        ← 写死的
Step 2: 如果结果含"雨"则建议带伞        ← 写死的
（如果用户改问"上海呢？"或者 API 返回格式变了，流程就崩了）
```

**ReAct 的轨迹（协同版）：**

```text
Thought: 用户想知道北京今天的气温以及是否带伞。这两个信息我都不知道，
         需要先用天气工具查询真实数据。
Action: weather_search
Action Input: 北京今天天气

Observation: 北京今天雷阵雨，气温 16~19℃，东北风 3 级。

Thought: 已获取真实天气：有雷阵雨，气温偏低。根据常识，有雨应该带伞，
         且 16~19℃ 偏凉，可以顺便提醒加衣。信息足够，可以作答了。
Final Answer: 北京今天有雷阵雨，16~19℃，建议带伞，并适当添衣。
```

注意 ReAct 轨迹里的几个关键瞬间：

1. **第一段 Thought 是"元认知"**——它先意识到"我不知道"，然后才决定"去查"。这种"知道自己不知道"的能力，正是纯 CoT 缺失的；
2. **Observation 是真实世界的数据**，不是 LLM 编造的。推理从此有了事实地基；
3. **第二段 Thought 完成了"信息 → 决策"的转化**，并在确认信息足够后主动终止循环。

> 思考题 2：ReAct 的每一步 Thought 都由 LLM 生成，它也可能"想错"——比如决定调用一个完全不相干的工具。相比纯 CoT，ReAct 凭什么能从这个错误中恢复？  
> 提示：错误的 Action 会产生真实的 Observation（哪怕是一条"工具不存在"的报错），这条真实的坏消息会进入下一轮上下文，LLM 有机会看到它并改弦更张。**反馈回路是纠错能力来源。**

### 2.6 论文里的证据：ReAct 真的更好吗

设计思想再漂亮，也要有实验支撑。ReAct 论文在两个差异很大的基准上做了对照实验：

- **HotpotQA / FEVER**（知识问答与事实核查）：ReAct 与纯 CoT 正确率相当，但 ReAct 的**幻觉率显著更低**——因为它的事实来自真实检索结果，而不是模型记忆。论文还发现一个实用组合：让 CoT 和 ReAct 互补，先让 ReAct 查资料、查不到再退回 CoT 内部推理，效果优于任何单一范式。
- **ALFWorld / WebShop**（交互式决策环境：在虚拟房间里找东西、在模拟电商里下单）：ReAct 的绝对成功率比"模仿学习/强化学习"出身的专用方案高出 10 个百分点以上。这类任务**无法预先知道行动序列**，正是"边做边想"的主场。

从这两个实验可以提炼出一条选型经验：**任务中"未知信息的占比"越高、"行动路径的不确定性"越大，ReAct 相对其他范式的优势就越明显。** 这也再次印证了我们第三章的结论——研究调研类任务（智研 AI 助手的主场景）恰好在 ReAct 的优势区间中央。

### 2.7 ReAct 为什么成为事实标准

ReAct 论文发表于 2022 年 10 月，之后几乎所有主流 Agent 框架（LangChain Agent、AutoGPT 家族、各类 Function Calling 循环）都是它的变体或演进。它成为事实标准的原因可以归结为三点：

1. **简单**：不需要训练新模型，纯靠提示词约定格式就能跑起来；
2. **通用**：任何"需要外部信息或外部操作"的任务都能套这个循环；
3. **可解释**：每一步 Thought 都是自然语言，Agent 的"心路历程"完全可读、可审计——配合我们 day001 的日志系统，整条轨迹可以被完整记录和复盘。

## 第三章：三种范式的正面对比 —— CoT vs 纯工具调用 vs ReAct

### 3.1 对比总表

| 维度 | 纯 CoT | 固定工具流水线 | ReAct |
|------|--------|--------------|-------|
| 推理过程 | 显式、灵活 | 无（流程写死） | 显式、灵活 |
| 获取外部信息 | ✗ 做不到 | ✓ 但只能按预定方式 | ✓ 按需动态决定 |
| 幻觉防护 | 无反馈，错误会累积 | 无推理可错，但无法应变 | Observation 提供现实锚点 |
| 应变能力 | 高（但无处施展） | 几乎为零 | 高（每步重新决策） |
| 可解释性 | 好 | 中（流程固定故可读） | 好（Thought 全程可读） |
| 实现成本 | 极低（一句提示词） | 低（写流程代码） | 中（需要解析器 + 循环 + 工具层） |
| Token 消耗 | 低 | 低 | 较高（多轮调用，历史越来越长） |

### 3.2 适用场景分析

没有银弹，只有匹配：

- **纯 CoT** 适合：封闭的、信息齐全的推理任务。数学题、逻辑题、代码改写——所有需要的信息都在提示里，不需要看世界。
- **固定流水线** 适合：流程稳定、高频重复的生产任务。比如"每天早上抓取固定的 10 个数据源生成简报"——确定性反而是优点，便宜、快速、可预测。
- **ReAct** 适合：开放域、路径未知的任务。研究调研、问答客服、数据分析——下一步依赖上一步的结果，必须边做边想。

我们的主线项目叫**智研 AI 助手（SmartResearch Agent）**，核心场景是"帮用户做研究调研"——这正是 ReAct 的主场：查什么资料取决于已经查到了什么，路线不可能预先写死。

### 3.3 ReAct 的代价与我们的应对

选 ReAct 也要正视它的代价：

1. **成本**：每一步都是一次 LLM 调用，且对话历史单调增长，token 消耗是 CoT 的数倍。→ 应对：记忆截断（day008）、成本控制（day001 的配置与日志）。
2. **失控风险**：LLM 可能陷入"反复调用工具、永不收手"的死循环，token 费用爆炸。→ 应对：**max_steps 熔断**，本章第四节细讲。
3. **格式脆弱**：LLM 输出不一定严格符合 `Thought:/Action:` 格式，解析会失败。→ 应对：专门的解析器与容错（day006）。

这些代价决定了我们今天骨架设计的每一个字段。

## 第四章：ReactAgent 骨架设计 —— 每个字段背后的"为什么"

### 4.1 为什么今天只写骨架，不直接写完整循环？

软件工程里有一个反模式叫"大爆炸式开发"：一口气写完 200 行循环逻辑，然后发现解析器有 bug、提示词格式不对、工具接口设计反了，所有问题纠缠在一起无法定位。

正确的节奏是**先立接口，再填实现**：

```
day003（今天）: 定义 ReactAgent 的"形状"——有哪些组件、接口是什么
day004:        实现"行动"——BaseTool 抽象与第一个工具
day005:        实现"感知与推理的原料"——工具注册表 + LLM 调用层
day006:        实现完整 ReAct 循环，把散件组装成会跑的 Agent
```

骨架的价值在于：**它把"架构决策"从"实现细节"中剥离出来，让架构决策可以被单独审视、测试和讨论。** 接下来逐个字段审视。

### 4.2 依赖注入：为什么 llm 和 tools 从构造函数传入

骨架的构造函数签名：

```python
def __init__(self, llm=None, tools=None, max_steps: int = 10):
```

为什么不在 `__init__` 内部直接创建 LLM 客户端和工具列表？比如：

```python
# 反例：内部自建依赖
def __init__(self):
    self.llm = OpenAI(api_key="sk-...")   # 焊死了具体实现
    self.tools = [CalculatorTool()]       # 焊死了具体工具集
```

对比两种设计：

| 维度 | 内部自建（反例） | 构造函数注入（我们的选择） |
|------|----------------|--------------------------|
| 换 LLM 厂商 | 改 ReactAgent 源码 | 换一个参数，Agent 代码不动 |
| 单元测试 | 会发起真实网络请求 | 传入 MockLLM，完全离线 |
| 工具扩展 | 每加一个工具改 Agent | 工具自注册，Agent 无感知 |
| 配置来源 | 散落在类内部 | 集中在调用方，一目了然 |

这就是**开放封闭原则（Open-Closed Principle）**：对扩展开放（新 LLM、新工具随便加），对修改封闭（`ReactAgent` 的代码不需要动）。它也是依赖倒置原则的体现：`ReactAgent` 依赖的是"LLM 的抽象"和"工具的抽象"，而不是任何具体实现。

day002 我们讲过 pytest 的 fixture 是"测试的依赖注入"——同一个思想，今天用在生产代码上。到 day005 你会看到 `MockLLM` 如何让整个 ReAct 循环在不花一分钱、不联网的情况下被完整测试，那是依赖注入回报的兑现时刻。

### 4.3 max_steps：熔断器，Agent 的"安全气囊"

```python
self.max_steps = max_steps  # 默认 10
```

回忆 ReAct 循环的结构：LLM 决定何时停止（输出 Final Answer）。这意味着**循环的终止条件掌握在一个不可预测的概率模型手里**。如果 LLM 状态不佳、提示词没写好、或者任务本身无解，循环可能永远转下去——每一步都在烧钱。

`max_steps` 就是熔断器（Circuit Breaker）：**无论 LLM 怎么想，循环最多转 max_steps 圈，到点强制停车。**

为什么默认 10？这是个经验值，背后的权衡：

- 太小（如 3）：复杂任务（查 5 个资料源再综合）走到一半就被掐断；
- 太大（如 100）：失控时浪费的 token 费用失控；
- 10 对"研究调研"类任务是个合理起点，且**它是可配置的**——调用方可以根据任务复杂度调整。

熔断的思想在分布式系统里很常见（超时、重试上限、速率限制），把它引入 Agent 设计是同一个直觉：**对不可控组件（网络服务 / 概率模型）的调用，必须有确定性的上限兜底。**

### 4.4 history：Agent 的"黑匣子"

```python
self.history: list[dict] = []
```

`history` 的职责是记录 ReAct 循环每一步的结构化结果（Thought、Action、Observation）。为什么需要它？

1. **可解释性**：当 Agent 给出奇怪答案时，`history` 是复盘整条推理链的唯一依据——哪一步想错了、哪个工具返回了垃圾数据，一目了然；
2. **调试与评估**：M3 阶段做 Agent 评估时，评估的原材料就是大量任务的 `history` 轨迹；
3. **审计**：行动类操作（尤其后期有写操作后）必须有可追溯的记录，这是 day001 说的"安全合规"在 Agent 层的落地。

今天它是 `list[dict]`——一个刻意简单的占位类型。day006 解析器落地后，它会升级为 `list[ReActStep]`（强类型数据类）。骨架阶段不追求完美类型，追求**把"要记录轨迹"这个架构意图表达出来**。

### 4.5 run() 为什么 raise NotImplementedError

```python
def run(self, task: str) -> str:
    """执行任务的主入口（day006 实现完整 ReAct 循环）."""
    logger.info("接收到任务: %s", task)
    raise NotImplementedError("ReAct 循环将在 day006 实现")
```

三个设计细节都值得说：

**（1）用 NotImplementedError 而不是 pass 或 return ""。**

这是"诚实的 API"原则：调用一个尚未实现的功能，应该得到一个**明确的、可搜索的异常**，而不是一个看起来"正常但什么都没做"的假结果。空字符串返回值会让上层误以为任务执行成功，错误被掩盖；异常则让问题立即暴露。而且注意异常信息里写了 "day006"——**错误信息本身就是文档和路标**。

**（2）run() 里依然打了日志。**

虽然只有一行，但它确立了契约：**Agent 的每个入口动作都要留痕。** day006 填充循环体时，日志只会增不会减。

**（3）参数名叫 task 而不是 prompt 或 query。**

命名反映世界观：`prompt` 是 LLM 调用层的词汇，`query` 是检索系统的词汇，而 `task` 是 Agent 层的词汇——它暗示这是一个**需要多步协作才能完成的目标**，不是一次性的问答。

### 5.2 骨架类全文

[完整代码](../源码/smart-research-agent/smart_research_agent/agent/react_agent.py)

```python
"""ReAct Agent 骨架：定义 Agent 的核心组件与运行接口."""

from __future__ import annotations

from smart_research_agent.utils.logger import get_logger

logger = get_logger(__name__)


class ReactAgent:
    """基于 ReAct（Reasoning + Acting）范式的 Agent 骨架.

    核心组件（后续逐日接入）：
      - llm: 推理引擎（day005 接入）
      - tools: 行动能力（day004/day005 接入）
      - memory: 记忆系统（day008/day009 接入）
    """

    def __init__(self, llm=None, tools=None, max_steps: int = 10):
        self.llm = llm
        self.tools = tools or []
        self.max_steps = max_steps
        self.history: list[dict] = []

    def run(self, task: str) -> str:
        """执行任务的主入口（day006 实现完整 ReAct 循环）."""
        logger.info("接收到任务: %s", task)
        raise NotImplementedError("ReAct 循环将在 day006 实现")
```

对照第四章的设计，逐行验证：

- `llm=None`：今天还没有 LLM 抽象层（day005 才有 `BaseLLM`），先用 `None` 占位，类型注解留给接入那天；
- `tools or []`：防御性写法——调用方传 `None` 时保证 `self.tools` 是空列表而非 `None`，避免后续遍历时 `TypeError`。这是"让非法状态不可表示"思想的轻量版；
- `max_steps: int = 10`：熔断器，带类型注解和默认值；
- `history: list[dict]`：轨迹记录，今天就用类型注解标注意图。

注意文档字符串里明确写了**每个组件的接入日程**。这是骨架代码的重要修养：留白的地方要告诉读者"这里将来是什么、哪天来填"，否则三个月后没人知道 `llm=None` 是"还没做"还是"故意允许为空"。

### 5.3 为骨架写测试：测"现状"，也测"承诺"

[完整代码](../源码/smart-research-agent/tests/test_react_agent.py)

```python
"""ReactAgent 骨架测试."""

from __future__ import annotations

import pytest

from smart_research_agent.agent.react_agent import ReactAgent


class TestReactAgentSkeleton:
    def test_default_init(self):
        agent = ReactAgent()
        assert agent.max_steps == 10
        assert agent.tools == []
        assert agent.history == []

    def test_run_not_implemented_yet(self):
        agent = ReactAgent()
        with pytest.raises(NotImplementedError, match="day006"):
            agent.run("任意任务")
```

两个测试各有分工，值得琢磨：

**`test_default_init` 测的是"架构契约"。** 它把第四章的三个设计决策（默认 max_steps=10、tools 默认为空列表、history 从空开始）固化为可执行的断言。将来任何人改动这些默认值，测试会立刻报警，迫使他确认"这是有意为之"。

**`test_run_not_implemented_yet` 测的是"诚实的未完成"。** 它验证了 `run()` 确实抛出 `NotImplementedError`，并且用 `match="day006"` 校验异常信息里带着路标。这个测试是**临时的**——day006 实现真循环后，它会被真实的行为测试取代。临时测试也是测试：在骨架阶段，它防止有人误以为 `run()` 已经可用。

`pytest.raises(..., match=...)` 的用法是今天的测试新知识点：`match` 参数接受正则表达式，断言异常消息匹配该模式。只断言异常类型不够精确（`NotImplementedError` 可能从任何地方抛出），加上消息匹配，才锁死"是我们故意抛的那个异常"。

## 第六章：今日总结 —— 概念与设计决策一览

| 主题 | 核心结论 | 落地位置 |
|------|----------|----------|
| Agent 定义 | LLM（大脑）+ 感知 + 推理 + 行动 + 记忆，四组件构成循环 | 本章第一、四节 |
| CoT 的局限 | 推理链封闭、无外部信息、幻觉无反馈锚点 | 本章第 2.2 节 |
| ReAct 思想 | Thought/Action/Observation 交替；推理引导行动、行动反馈推理 | 本章第 2.4 节 |
| 范式选择 | 封闭推理用 CoT、固定流程用流水线、开放任务用 ReAct | 本章第三章对比表 |
| 依赖注入 | llm/tools 从构造函数传入，满足开放封闭原则，天然可测试 | `ReactAgent.__init__` |
| max_steps | 对不可控的 LLM 设置确定性熔断上限，防死循环与费用失控 | `ReactAgent.max_steps` |
| history | Agent 的黑匣子：可解释、可调试、可审计 | `ReactAgent.history` |
| 诚实的 API | 未实现的功能用 NotImplementedError 明确表态，错误信息带路标 | `ReactAgent.run()` |
| 骨架先行 | 先立接口与架构决策，再逐日填实现，每天测试保持绿色 | 本章第五章 |

明天（day004）我们给"行动"组件注入第一块血肉：设计 `BaseTool` 抽象基类——工具的 name/description/parameters/execute 四件套契约，并实现第一个真实工具 `CalculatorTool`。你会看到今天的 `tools` 列表参数如何与那个抽象基类严丝合缝地对接。

### 展望：day006 的完整循环将长什么样

最后用一段伪代码预览 ReAct 循环的完整形态，让今天的骨架和未来的实现之间不再有悬念：

```text
def run(task):
    messages = [系统提示词(含工具清单), 用户任务]
    循环最多 max_steps 次:
        raw = llm.chat(messages)          # 推理：产出 Thought + Action/Final Answer
        step = parse(raw)                 # 解析文本为结构化步骤
        history.append(step)              # 黑匣子记录
        如果 step 含 Final Answer:
            return 答案                    # 正常终止
        observation = 执行工具(step.action, step.action_input)
        messages += [raw, Observation]    # 观察反馈回上下文，进入下一轮
    return "达到最大步数限制"               # 熔断终止
```

对照今天的骨架：构造函数注入的 `llm`、`tools` 在这里被使用；`max_steps` 在这里兑现熔断承诺；`history` 在这里逐步积累。你现在看不懂的两处空白——`llm.chat` 怎么调、工具怎么执行——正是 day004、day005、day006 三天的内容。**骨架的意义就是让未来每一天的功课都有明确的"坑位"可填。**
