## 第一部分：选择题

### 第 1 题 —— B

**考点**：两个身份（`fingerprint` 与 `vector_key`）各自回答什么问题，以及"只比其中一个"会漏掉哪一整类变更。

**解析**：

`indexing/__init__.py` 把本课要解决的核心矛盾写成一句话：

> **"有没有变"与"该不该重算向量"是两个问题。**

```text
内容身份（fingerprint）   这段文本是不是另一段了   → 决定"要不要更新这条记录"
向量键（vector_key）      这个向量还能不能用        → 决定"要不要重新编码"
```

两个字段各自由**不同的那段文本**算出，这一点是本题的关键（`planner.entry_from_record`）：

```python
return IndexEntry(
    record_id=record_id_of(record),
    fingerprint=_fingerprint_of(record),          # metadata["fingerprint"]，取不到才 content_id(**原文** text)
    vector_key=vector_key(
        identity.provider, identity.model, identity.dimension,
        embedding_text(record),                   # **编码文本**（retrieval_text 优先，回落 text）
    ),
    token_count=_token_count_of(record),
)
```

`planner.plan_index` 的判据是**两条分别判**，任一不同即 `updated`：

```python
if before is None:
    added.append(record_id)
elif before.fingerprint != entry.fingerprint:
    updated.append(record_id)
elif before.vector_key != entry.vector_key:
    updated.append(record_id)
else:
    unchanged.append(record_id)
```

两处 docstring 把"少比一个"的后果写成了表（`planner.py` 模块 docstring）：

| 只比 | 漏掉的变更 | 症状 |
|------|-----------|------|
| `fingerprint` | 换了编码器（身份变了，原文没变） | 新旧向量混在一个库里，排序整体错乱 |
| `vector_key` | 内容变了但编码文本没变（覆盖写场景） | 库里留着旧内容的向量，命中的却是新原文 |

这两条各有一条**已存在**的用例钉住，且都构造得恰到好处：

```text
tests/test_indexing_planner.py::test_fingerprint_change_without_vector_key_change_is_updated
    before = "内容甲乙"    + retrieval_text="检索视图（固定）"
    after  = "内容甲乙丙"   + retrieval_text="检索视图（固定）"
    → fingerprint 变、vector_key 不变 → 必须判 updated

tests/test_indexing_planner.py::test_vector_key_change_without_fingerprint_change_is_updated
    before = "内容甲乙" + retrieval_text="检索视图 一"
    after  = "内容甲乙" + retrieval_text="检索视图 二"
    → fingerprint 不变、vector_key 变 → 必须判 updated
```

演示脚本第 3 节的 ② 与 ③ 是"计数可以重合但 id 分组完全不同"的证据（`updated=1/unchanged=7`
与 `removed=1/unchanged=7`）；而"只比一个"的漏判之所以致命，是因为**它不报错**：
命中了、写入了、查询也返回了，只是"谁更近"变了或新内容查不到。

**其余选项为什么错**：

- `A` 错（本课第一个误区）："内容没变 ⇒ 向量还能用"在**换模型**时直接失效。原文一个字节没改、
  `fingerprint` 相同，旧模型的向量却被继续使用。`types.py` 的模块 docstring 把这句代价写在最前面：
  "新旧向量混在同一个库里 → 检索结果整体错乱，而这个过程**不会有任何异常**"。
- `C` 错：`vector_key` 覆盖的是"该编码的那段文本 + 编码器身份"，它**看不到原文**。
  `fingerprint` 用的是原文、`vector_key` 用的是编码文本，两者是两段不同的文本；
  当 `retrieval_text` 固定而原文改了（或反过来），只有一个字段会变——这正是上面两条用例的形状。
  `planner.py` 的原话是"两条文本分别对应'内容'与'该编码什么'，混用会让'只改检索视图'被误判成'内容变了'"。
- `D` 错：把结构保证退化成"人肉约定"。`types.py` 里"身份进键"的全部价值恰恰是**不靠自觉**：
  "想漏判都漏判不了"。而且"清缓存"也救不了这个判断——`IndexPlan` 仍会把全部条目判成 `unchanged`，
  库里的旧向量也仍然在；`indexing/__init__.py` 的纪律一写得很清楚：换配置要"**必然**让旧向量作废"。

**结论**：两个身份都要有、都要比，因为它们由两段不同的文本算出、回答两个不同的问题；
"只比一个"的两类漏判表现完全不同（"检索质量下降" vs "新内容查不到"），但**都不报错**。

### 第 2 题 —— C

**考点**：键的四个输入、版本号的四个输入、`created_at` 的位置，以及"重放不产生新版本"。

**解析**：

`types.py` 里三个函数/属性是这道题的全部依据：

```python
def vector_key(provider: str, model: str, dimension: int, text: str) -> str:
    payload = f"{provider}|{model}|{dimension}\n{text}".encode()
    return hashlib.sha256(payload).hexdigest()[:VECTOR_KEY_LENGTH]       # VECTOR_KEY_LENGTH = 16

def index_version_id(*, identity_key: str, metric: str, backend: str, digest: str) -> str:
    payload = f"{MANIFEST_VERSION}|{identity_key}|{metric}|{backend}|{digest}".encode()
    return hashlib.sha256(payload).hexdigest()[:VECTOR_KEY_LENGTH]

# EmbeddingIdentity.key —— 进向量键与版本号的就是它
@property
def key(self) -> str:
    return vector_key(self.provider, self.model, 0, f"dimension={self.dimension}")
```

**四个输入里三个是编码器身份**（`provider` / `model` / `dimension`）。演示第 1 节对同一段编码文本
`'索引手册 > 缓存\n缓存键里必须含编码器身份，否则换模型之后会命中旧向量。'` 的实测：

```text
现状：      model='default'      / 256d | 身份 95df00b1373d4b1b | 向量键 b213ef25c724c42c
只换 model：model='char-ngram-2-3'/ 256d | 身份 33dc151f42b9724a | 向量键 d46048eb2a6d2285
只换维度：  model='default'      / 384d | 身份 9486942d12a1e2d3 | 向量键 a1d74e61bf7d29ee

三个向量键两两不同：True
```

缓存键与向量键是**同一个函数**（`cache.EmbeddingCache.key → types.vector_key`），实测
`cache.key(同一段文本) == 上面那个向量键 → True`、`cache.identity_key == identity.key → True`。
于是换编码器之后**旧缓存条目永远不会命中**，而不是"命中了旧模型的向量、检索结果只是变得不太对"。

版本号这边，`build_manifest` 是**唯一**算出 `version_id` 的地方，`created_at` / `parent_version` /
`metadata` 都不参与：

```text
parent_version   血缘是"谁接在谁之后"，与"这一版是什么"无关
created_at       时间戳进版本号 → 同一份内容在两台机器上得到两个版本号
metadata         给人看的备注（构建耗时、触发人等），不是身份
```

最直接的证据是演示第 4 节的"重放"：

```text
首次构建：version_id=7a19694afcc814e8 / parent=（首版）
重放同一批：version_id=7a19694afcc814e8 / parent=7a19694afcc814e8
版本号与首次逐位相同：True
版本表：1 版（重放没有产生新版本——版本号由内容算出）
```

**其余选项为什么错**：

- `A` 错：这正是本课第五个误区（"缓存键只取文本"）。换一次模型之后"文本没变 → 键没变 →
  **命中旧向量**"，于是新旧向量混进同一个库、检索结果整体错乱，而且**不抛任何异常**。
  "手工清缓存"也不是结构保证：它同样挡不住 `planner` 把全部条目判成 `unchanged`。
- `B` 错：时间戳进版本号会让"同一份内容"在两台机器上得到两个版本号，
  于是"这个版本在哪台机器上建的"变成一个**必须回答**的问题，而它本来不该是一个问题。
  `types.py` 把它与 day062 用 `chars` 而不是 `tiktoken` 作默认度量并列——同一条纪律。
- `D` 错：让调用方传 `version_id` 等于把"版本号等于内容"这条纪律交给每个调用点去遵守。
  `build_manifest` 的 docstring 写着后果："只要有一个调用点算错（或图省事传了个时间戳），
  版本表里就会出现**两个内容相同、版本号不同**的版本，而它在报告里只表现为'凭空多出一版'。"

**结论**：键里必须有身份、版本号里必须没有时间。前者让"换配置"变成结构上漏不掉的事，
后者让"同一份内容在任何机器上算出同一个版本号"成立——两者合起来，才让
"重建一次不该凭空多出版本"（`7a19694afcc814e8` 逐位相同）成为可核对的事实。

### 第 3 题 —— B

**考点**：`entries_digest` 自排序、`IndexManifest` 强制"升序且不重复"、摘要取哪三个字段。

**解析**：

`types.entries_digest` 的排序是**函数内部**做的，不依赖调用方：

```python
lines = [
    f"{entry.record_id}|{entry.fingerprint}|{entry.vector_key}"
    for entry in sorted(entries, key=lambda item: item.record_id)
]
payload = "\n".join(lines).encode()
return hashlib.sha256(payload).hexdigest()[:VECTOR_KEY_LENGTH]
```

`IndexManifest.__post_init__` 再补一道：

```python
ordered = tuple(sorted(self.entries, key=lambda entry: entry.record_id))
object.__setattr__(self, "entries", ordered)
seen: set[str] = set()
for entry in ordered:
    if entry.record_id in seen:
        raise ManifestError(f"清单里出现重复的 record_id {entry.record_id!r}："
                            "重复通常意味着两次构建的结果被拼在了一起")
    seen.add(entry.record_id)
```

`build_manifest` 的 docstring 把结论写成了承诺："条目顺序不影响结果……
因此**同一份内容按任何顺序传进来都得到同一个版本号**（这条有专门用例）。"

这条纪律是被冒烟自检逼出来的（`entries_digest` 的 docstring）：最初它按入参顺序拼字符串，
于是同一份内容按不同顺序算得两个版本号，**重建一次索引就凭空多出一个版本**。演示第 4 节
"重放 → 版本号逐位相同 + 版本表 1 版"就是这条纪律的可核对形态：
摘要取的是"内容集合"，`created_at` 不进版本号，条目顺序也不进。

**其余选项为什么错**：

- `A` 错："这批条目是分几次构建出来的"是一个**过程事实**，不是"这一版是什么"。版本号要能被任何人
  重算，而"谁先谁后"与内容无关；把过程写进身份，就正好制造出那个"凭空多出来的版本"。
- `C` 错：`token_count` 明确**不进摘要**（`entries_digest` 的 docstring："它们的变化不需要重建索引，
  进了摘要就会让'改一个统计字段'变成'整库失效'——这种'过度敏感'的版本号比不准的版本号更麻烦"）。
  同一个判断在体检里也出现过：`tokens_match` 为假不影响 `ok`。day062 有一个同构的例子——
  `oversized` 是报告字段，**不进 `chunk_id`**。
- `D` 错：把排序推给调用方，只要有一个调用点忘了排就多出一个版本。"身份必须是内容的函数，
  而不是传入方式的函数"这条纪律要挂在那条**任何人都会经过的路**上——`IndexManifest` 的构造
  （以及 `entries_digest` 内部）。而且 `__post_init__` 还顺手拒绝了重复 id，这也不是可选的装饰：
  重复通常意味着两次构建的结果被拼在了一起。

**结论**：摘要自排序 + 清单强制升序去重，是"版本号可被任何人重算"的前提；
否则同一份内容会有两个身份，而两个身份在报告里**看不出来**（条目集合完全相同）。

### 第 4 题 —— B

**考点**：`batch_size` 只改"分几次送"、`batches` 才是成本、`提供方调用次数 == batches`、
`<= 0` 报错而不是猜成 1、空批不免费。

**解析**：

`encoder.BatchEncoder.encode` 的分批循环决定了 `encoded` 与 `batches` 的口径：

```python
for start in range(0, len(pending), self._batch_size):
    chunk = pending[start : start + self._batch_size]
    returned = self._embedding.embed_batch(list(chunk))
    batches += 1
    ...
encoded = len(pending)
```

`encoded` 是"送了几条"，只由 `pending` 的长度决定；`batches` 是"分几次送"，由批大小决定。
演示第 2 节的实测正好把两者分开（8 条文本、每次用全新编码器 + 全新缓存）：

```text
batch_size | encoded | batches | cache_hits | 提供方调用 | 命中率
        32 |       8 |       1 |          0 |          1 |    0%
         4 |       8 |       2 |          0 |          2 |    0%
         1 |       8 |       8 |          0 |          8 |    0%
```

`batches == 提供方调用次数` 逐位相同——脚本自己数了每一次 `embed_batch`，所以报告里的
`batches` 不是估算，**两个数字相等才是一份证据**。`batch_size=1` 就是 day064 那条基线
（"库没变，钱照花"）。`encoder.DEFAULT_BATCH_SIZE = 32`，真实取值走 `settings.indexing_batch_size`。

两端各有代价：太小退化成逐条调用（`batches == encoded`，批处理收益全部消失）；
太大则一次请求体积大，且**一次失败要重试一整批**。

**其余选项为什么错**：

- `A` 错：表里 `encoded` 恒等于 8。批大小只改变"分几次送"，不改变"送了几条"——
  这是 `batch_size` 被称作**成本参数而不是正确性参数**的全部含义。
- `C` 错：顺序是"先查缓存、再决定要不要发调用"。全命中时的实测是
  `8 份文本 → 命中 8 / 编码 0 | 0 批 | 命中率 100.00%`，提供方调用次数"2 → 2（本次新增 0）"。
  反过来先发一批空调用，在真实 API 上**也是一次真实账单**，某些提供方还会把"零条的请求"判为错误。
  源码里那句话很直白："空批不是免费的。"
- `D` 错：`_resolve_batch_size` 对 `<= 0` 抛 `IndexingError`，理由写在错误消息里：
  "批大小是成本参数：0 或负数一定是配置写错了，本模块不会替你猜成 1——
  **那会让逐条调用伪装成批量调用**。" 这一条有专门用例
  `test_non_positive_batch_size_is_rejected`（参数化 `0` 与 `-1`）。

顺带一条与本题同源、也常被漏掉的账（`cache.py` 模块 docstring 与
`tests/test_indexing_encoder.py::test_duplicate_texts_are_encoded_only_once`）：
同一批里的重复文本（`[A, B, A]`）只编码一次，`encoded == 2`、`cache_hits >= 1`、
`vectors[0] == vectors[2]`——它省下的确实是一次调用，只是省下的方式与"上次已经存过"不同。

**结论**：看 `encoded` 知道"送了几条"，看 `batches` 知道"分几次送"，看"提供方调用次数"知道
`batches` 有没有说谎；三者合起来才把"这次花了多少"说清楚。

### 第 5 题 —— B

**考点**：换挡换的是"怎么写库"、它的四个前置条件、"严格大于"、以及为什么只有装配层说得了。

**解析**：

`builder._apply_rebuild_threshold` 的判据与四个前置条件：

```python
if mode != BUILD_MODE_INCREMENTAL or parent is None or plan.total <= 0:
    return mode, ""
ratio = plan.changed / plan.total
threshold = float(settings.indexing_full_rebuild_threshold)
if ratio > threshold:                      # 严格大于：等于阈值时不换
    return BUILD_MODE_FULL, (
        f"变更比例 {ratio:.1%} 超过阈值 {threshold:.2f}，已从 incremental 切到 full："
        "增量不是永远更省——变更比例很高时，逐条 upsert 加逐条 delete 的开销"
        "反而高于清空重写"
    )
```

演示第 5 节的实测（阈值调到 `0.1`、8 条里改 4 条）：

```text
计划（只读）：新增 0 / 更新 4 / 删除 0 / 未变 4 | 复用率 50.00%
            changed=4 / total=8 → 比例 50.0% > 阈值 0.10
实际构建：  full 构建 | a8d699e98d8a35e1 ← 7a19694afcc814e8 |
            8 条 → 写入 8 / 未变 0 / 删除 0 | 编码 4（命中 4，1 批） | 复用率 50.00%
report.note：变更比例 50.0% 超过阈值 0.10，已从 incremental 切到 full：增量不是永远更省——
            变更比例很高时，逐条 upsert 加逐条 delete 的开销反而高于清空重写
```

三个要点：

1. **`encoded=4` 而不是 8**：换挡只改"怎么写库"（`clear()` + 整批写回，取代逐条 `upsert` 与
   逐条 `delete`），不改"要不要编码"——没改的那 4 条仍然靠缓存免掉了编码；
2. **只有装配层说得了**：`planner` 看不到"写库要花多少"，后端也不知道"这批数据相对上一版变了多少"，
   两边各缺一半，所以判据落在 `builder` 里；
3. **两套 `unchanged` / `reuse_ratio` 口径**（`builder.py` 模块 docstring 的表）：

```text
written      两模式一致：本次真正写进库的条数（added + updated）
unchanged    增量：plan.unchanged 的条数（这些条目一条都没碰库）
             全量：恒为 0 —— clear() 之后库里没有"没动过"的东西
removed      增量：delete() 实际删掉的条数；全量：plan.removed 的条数（clear() 顺带删的）
reuse_ratio  增量：plan.reuse_ratio；全量：cache_hits / requested（这一次请求里多少条靠缓存免掉）
```

**其余选项为什么错**：

- `A` 错：这是本课第十个误区（"以为全量重建等于重新编码"）。全量下真正决定成本的是缓存命中率，
  实测 `encoded=4`、`cache_hits=4`；`reuse_ratio` 报的是 `0.5`（缓存命中率）而不是 `plan.reuse_ratio`。
- `C` 错：阈值是"**严格大于**才换"。`builder._apply_rebuild_threshold` 的 docstring：
  "等于阈值时不换挡：阈值是'超过它才换'的那条线"。"等于就换"会让阈值这个数字变成**下限**。
- `D` 错：`_apply_rebuild_threshold` 的 docstring 原文——"换挡只改'怎么写库'，不改'写了什么'：
  条目集合、版本号都不受影响（`full` 与 `incremental` 写完之后库的内容相同，差别只在过程与成本）"。
  如果两种模式"写出来的东西"不同，那么"哪种更省"这个问题就不再是一个成本问题，而是一个正确性问题。

另外三个前置条件也值得记：模式必须是 `incremental`（`full` 不需要换挡）、
上一版必须存在（否则"变更比例"没有分母）、`plan.total > 0`（空记录集时两种模式等价，
不换挡也不报错——`test_empty_records_neither_switch_mode_nor_fail`）。

**结论**：阈值换挡是一个**成本决策**，不是正确性决策；它改变的只是"把同一批内容怎么写进库"。

## 第二部分：判断题

### 第 6 题 —— 错

**考点**：`encoded=0` 与 `cache_hits=0` 的关系；增量是"不问"、缓存是"问了才省"。

**解析**：

演示第 4 节的实测把四个数字两两成对地摆开：

```text
首次构建：incremental 构建 | 7a19694afcc814e8 ← （首版） |
        8 条 → 写入 8 / 未变 0 / 删除 0 | 编码 8（命中 0，1 批） | 复用率 0.00%

重放同一批：incremental 构建 | 7a19694afcc814e8 ← 7a19694afcc814e8 |
        8 条 → 写入 0 / 未变 8 / 删除 0 | 编码 0（命中 0，0 批） | 复用率 100.00%
        提供方调用次数：两次构建之间增加了 0 次

encoded    8 → 0     第二次一条都没算
batches    1 → 0     第二次一批都没发
written    8 → 0     第二次一条都没写库
unchanged  0 → 8     第二次 8 条全都没碰库
cache_hits 0 → 0     ← 第二次连缓存都没问
```

第二次 `cache_hits` 仍然是 `0`，但这一次**确实省下了 8 次编码**。两件事同时为真，
因为它们是两条不同的路径（`builder` 与 `encoder` 的分工）：

```text
增量是"不问"     plan_index 直接判定 8 条 unchanged → plan.to_encode 为空 →
                 builder 的 target_ids 为空 → _encode 直接 return（缓存一次都没查）
缓存是"问了才省"  查了没命中 → 编码；查了命中 → 省一次调用
```

`builder._encode` 的第一行就是答案：

```python
if not pending:
    return {}, cache_hits, encoded, batches, notes     # 四个数全是 0，且不碰缓存
```

所以"缓存累计命中率 0%"与"这次省下 8 次编码"可以同时为真。把这两件事混成一句话，
就会得出题干的结论——"缓存没生效，所以增量是假的"。

**题目两处错**：

- 把 `cache_hits=0` 读成"缓存没生效"：这一批**根本没有进缓存查询**，
  `EmbeddingCache` 的 `hits` / `misses`（`cache.py` 里"命中与未命中都要计数"的那两个计数器）
  在重放里**一次都没有被触碰**。要证明缓存生效，应该看的是"第一次构建之后、
  第二次构建之前，提供方调用次数有没有新增"——实测新增 `0` 次；
- 把"省不省钱"归到 `cache_hits` 上：省钱的证据是 `encoded` / `batches` / `written`
  从 `8` 掉到 `0`（以及 `unchanged` 从 `0` 涨到 `8`）。`cache_hits` 只在"这一批真的
  去问了缓存"时才有意义——它是**缓存**那个省钱机制的数，不是**增量**那个省钱机制的数。

顺带一条口径：`EmbeddingCache.reset_counters()` 单独存在，是因为"一次构建的命中率"与
"这份缓存实例累计的命中率"是两个数；不清零，第二次构建的命中率会被第一次的命中累加进去。

**结论**：错。`encoded=0` 说明"这次没花编码"，`cache_hits=0` 说明"这次没走缓存那条路"；
两者可以同时为真，而且**同时为真恰恰是增量最省钱时的样子**。

### 第 7 题 —— 错

**考点**：三处降级的正确形状（"先整批、失败再逐条"）、"非认识的异常一律上抛"。

**解析**：

`builder.py` 模块 docstring 把三处降级写成明文，它们的共同形状是"**先整批、失败再逐条**"：

```text
文本为空/全空白    直接进 failures，**一小段编码都不发起**（它本来就不该进编码器）
一批编码抛错       对该批逐条重试，真正失败的那几条进 failures，其余照常写入
一次 upsert 抛错    逐条重试，故障被定位到具体 record_id，其余照常写入
```

**题目第一处错**：失败时不是"把整批记进 `failures`"，而是**逐条重试**。收益写在同一段里：
"反过来（整批失败就整批放弃）会让一份 1000 条的批次里 1 条坏数据带走 999 条好数据，
而报告上只写着'失败'。"两条现成的用例：

```text
tests/test_indexing_builder.py::test_encoding_error_falls_back_to_per_record_retry
    embedding.batch_calls == 4（1 次整批 + 3 次逐条重试）
    report.batches == 2（失败的那条没有产出报告，因此不计入）
    report.failed == 1、report.written == 2、"逐条重试" in report.note

tests/test_indexing_builder.py::test_upsert_error_falls_back_to_per_record_retry
    backend.upserted == [[ID_A, ID_B, ID_C], [ID_A], [ID_B], [ID_C]]
    → 先整批（三条一起），失败之后逐条——**包括那条坏的**（它要再响一次，
      否则"到底哪一条写不进去"就只能靠猜）
```

逐条重试是**有界的**：每一条最多被重试一次，不存在重试风暴。代价也必须写在明面上——
失败的那条不计入 `encoded` / `batches`（编码器在抛出之前没有产出报告），
所以出错时的报告里编码成本**偏低**，这一条由 `note` 说明：
"（失败的那条不计入 encoded / batches，这次报告的编码成本偏低）"。

**题目第二处错**：非认识异常**必须上抛**，不许记进 `failures`。这是 day061 那条纪律的
第三次复用（day061 的 `except VectorLoaderError`、day062 的 `except ChunkingError`、
今天的 `except (IndexingError, VectorStoreError)`）：

```python
except VectorStoreError:      # 只有"我们认识的失败"被记进报告
    ...
                              # 其余异常**向上抛**
```

源码的原话是："报告只能收留我们认识的失败，不认识的失败必须让调用栈把它喊出来。"
一个宽泛的 `except Exception` 会把"后端实现里有个 `TypeError`"这种真 bug 记成一行
`failed=1`，于是它**永远不会被修**——因为报告看起来"只是有一条数据没过"。
两条用例直接钉住这件事：

```text
test_unexpected_upsert_error_propagates     → pytest.raises(RuntimeError)，且 backend.count() == 0
test_unexpected_encoding_error_propagates   → pytest.raises(RuntimeError)，且 backend.count() == 0
```

**题目唯一说对的地方**：`IndexingReport.ok` 确实"只看 `failed` 是否为 0"
（`return self.failed == 0`），这一点与 day064 的 `IngestReport.ok`（`skipped == 0 and failed == 0`）
**不同**。而它与本题的结论正好相反：正因为 `ok` 只看 `failed`，
把不认识的异常也塞进 `failed` 会让"报告是绿的/红的"这件事彻底失去判断力。

顺带一条同族的边界：后端自己护栏跳过的条数（`write.skipped`）**不并进 `failed`**，
只在 `note` 里说一声并把差额留给 `verify()`——"我们没有它的逐条 id，
编一个 id 出来只会让 `failures` 变成一份不可信的名册"。用例见
`test_backend_guardrail_skips_are_noted_and_left_to_verify`。

**结论**：错。窄捕获（只吞 `IndexingError` / `VectorStoreError`）+ 失败时逐条重试 +
其余异常上抛，三者缺一不可。

### 第 8 题 —— 错

**考点**：`register` 与 `adopt` 分开、"回滚沿血缘而不是按登记顺序"、以及这个错误为什么不报错。

**解析**：

`versioning.py` 的模块 docstring 把这个反例画成了图：

```text
v1 ─► v2（采纳） ─► v3（构建失败，从未采纳）
                    ▲
        按时间倒序，v3 是"最新的一版" → 回滚会回到 v3
        按血缘，从 current=v2 回溯      → 回滚回到 v1
```

演示第 6 节的实测（连续构建三版、每版只改一条原文）：

```text
#1 7a19694afcc814e8 ← （首版）
#2 fa3967020368edc1 ← 7a19694afcc814e8
#3 2f60e07f3a3a0170 ← fa3967020368edc1
current=2f60e07f3a3a0170（构建成功即采纳）

现在采纳第二版：
  versions.adopt(v2) → current=fa3967020368edc1
  血缘链（从 current 回溯）：7a19694afcc814e8 → fa3967020368edc1

再回滚一步：
  versions.rollback(steps=1) → current=7a19694afcc814e8     ← 回到 v1
```

注意此时 `latest()`（最近**登记**的一版）仍然是 `2f60e07f3a3a0170`，
而回滚问的是"从**当前生效**的那一版往回看"——`lineage()` 的最后一版就是 `current`，
`steps=1` 取 `chain[-2]`：

```python
chain = self.lineage(self._current)
if len(chain) <= steps:
    raise VersionError(...)
target = chain[-1 - steps]
self._current = target.version_id
```

**题目三处错**：

- "按登记顺序倒着数取上一版"：会把 `current` 变成一个**从没生效过**的版本。
  `versioning.py` 的取舍表第一条就写着放弃"按时间回滚"，因为"那正是本模块要修的错"；
- "构建成功即采纳，所以最后一行就是最新的一版"：这句话**恰好把两个不同的事实合成一个**。
  `latest()` 的 docstring 明确区分："它说的是'最近登记的'而不是'当前生效的'（后者是 `current`）：
  这两者在本模块里刻意分开，因为'最新的'与'已采纳的'不是同一件事——
  两者合一的实现会让下面那个反例（v3 未采纳）无法被表达。" `register`（登记）与
  `adopt`（采纳）分开是刻意的："登记的版本可能从未生效过（构建失败、验证不过、被人工否决）。"
  真实的失败更普遍：**v3 构建失败时根本不会被登记**，
  于是按时间倒序会回到一个从没生效过的版本，而它之所以没被采纳，通常就是因为失败了；
- "是否被采纳过对回滚没有影响"：这正是错误的核心。这个错误在报告里**完全看不出来**——
  `current` 从一个合法的版本号变成另一个合法的版本号，没有异常、没有告警，
  只有下一次检索开始给出另一批结果。

顺带两条同族的硬约束：`lineage()` 遇到血缘断裂或成环都直接抛 `VersionError`，
而不是"能走多远走多远"（成环只能从磁盘上来，`test_lineage_detects_a_cycle_in_a_crafted_history`
用一份手工拼过的 JSONL 构造它）；回滚时"血缘不够"也**不**退而求其次地退回能退到的最远那一版——
"一次'想退 3 步但只退了 1 步'的回滚如果静默成功，调用方会以为自己在一个自己没打算去的版本上"。

**结论**：错。回滚必须沿 `parent_version` 走；`current` 与 `latest()` 是两个不同的概念，
把它们合成一个就表达不出"v3 未采纳"这个真实且常见的局面。

## 第三部分：简答题

### 第 9 题

**考点**：体检的四类不一致、`problems` 的措辞纪律、`tokens_match` 为什么不参与判定、
`builder.verify()` 无参为什么必然为真、以及 `compare_with_store` 与 `planner` 的分工。

**解析**：

**1）四类不一致的症状与处置。**

体检有两个检查点：`manifest.compare_with_store(manifest, backend)` 给原始字段，
`verify_index(manifest, backend)` 收敛成 `{"ok", "checks", "problems"}`，
`builder.verify(manifest=None)` 是它在装配层的入口。四类不一致（`verify_index` 的五段文案归并成四类）：

```text
① 清单有、库里没有   missing_in_store 非空
   症状：上一次构建半途失败，或有人手工删过记录
   处置：**先重建清单**（或用这些 id 补回向量），**不要在这份清单上做增量**
② 库里有、清单没有   orphan_in_store 非空
   症状：有人绕过索引流程直接写了库
   处置：同上——它们不会被增量更新覆盖，同样先重建清单
③ 维度不符           manifest.identity.dimension != backend.dimension
   症状：这份清单描述的是**另一个编码器**建的库
   处置：用当前编码器重建（build(..., mode='full')），或换回建库时那个编码器
④ 度量 / 后端不符     manifest.metric / backend 与库不一致
   处置：用清单的度量**新建实例**（metric=清单里那个），而不是让一个已有实例改度量；
        换后端可以重建，但**不能与旧版共用一份清单**
```

`problems` 原文（一句能直接照做的话，实测 `problems` 共 1 条）：

```text
清单里有 1 条记录在库里找不到：['a3e81f5c20d97b46']——上一次构建可能半途失败，
或有人手工删过记录；请先重建清单（或用这些 id 补回向量），不要在这份清单上做增量。
```

为什么 ③ 与 ① 的处置不同：**它们不是一个层面的问题**。① 是"同一套口径下账与库对不上"
（账少了一条或库少了一条），处置是**先修账**——因为在错的账上做增量，
差集会把那条缺失判成 `added`（于是静默地把它写回去）或判成 `removed`（于是删掉库里还有的东西）。
③ 是**口径本身不符**：这份清单描述的是另一个编码器建的库，拿它算差集会得到一份
"看起来正常、实际上完全不相干"的计划——所有 `vector_key` 都不同 → 全部重算，
于是"清单与库对不上"被**伪装成"数据全变了"**。所以它的处置是"改库或改编码器"（重建），
不是"改账"。

`problems` 为什么是句子而不是错误码：读它的人是运维，而上面那一句里已经包含
**现象（清单里有 1 条在库里找不到）、数量（1 条）、具体 id、下一步做什么（先用这些 id 补回向量，
不要做增量）**。`manifest._ids_preview` 只列前 3 个并补 `…`（`[..., …]`），
而数量写在句首的"清单里有 N 条……"，所以截断不会让人误以为"只有 3 条"——
这是"报告要能被人读完，细节由数量与出路承担"的同一条纪律。

**2）`tokens_match = False` 为什么不影响 `ok`。**

`entries_digest` 只取三个字段：

```text
record_id     哪一条
fingerprint   内容有没有变（day062 的内容身份）
vector_key    该不该复用向量（编码器身份 + 该编码的那段文本）
```

`token_count` 只用于统计（成本估算、报告），**不进摘要**（`types.entries_digest` 的 docstring）。
所以"改一个统计字段"不需要重建索引，`token_count` 随手改、`total_tokens` 随手变，
`tokens_match` 都会是 `False`——把它当成问题会让检查结果**过度敏感**，
而"一个过度敏感的检查项比一个不准的更麻烦"（教程第七章的原话）。
`compare_with_store` 的 docstring 也明写了："`tokens_match` 单独给出，
但**它不参与 `verify_index` 的判定**。"

实测里 `extra_tokens = {'manifest': 209, 'store': 178, 'diff': -31}`：清单 8 条共 209 token、
库里 7 条共 178 token、差额 `-31`，而 `ok=False` 只来自 `missing_in_store` 那一条。

day062 的同构例子：`oversized` 是报告字段、**不进 `chunk_id`**——同一条纪律
"报告字段不参与身份"。反过来也有 day064 的例子：`VectorRecord.metadata` 里加一个
"仅用于展示"的字段（例如入库时间），会让整条记录的比较**静默地永远不相等**，
于是每次重放都报 `updated`。

**3）`builder.verify()` 无参为什么必然为真。**

`IndexBuilder.verify` 的 docstring：

```text
manifest 为空时用 manifest_from_store 现算一份：那是"清单丢了、库还在"时的补救路径。
注意现算出来的清单是**"从现在起"的基线**，不是历史的那一版——所以"库里被人删了一条"
这种问题只有拿**原来那份清单**来对账才看得出来（verify() 无参调用必然对得上，
因为清单是从库现算的）。
```

现算用的是 `manifest.manifest_from_store(backend, identity=self.identity, created_at=self._clock())`：
它遍历 `backend.ids()`、对每条 `backend.get(record_id)` 折成 `IndexEntry`
（`fingerprint` 取 `metadata["fingerprint"]`，缺了才 `content_id(record.text)` 现算；
`vector_key` 取 `vector_key(身份, embedding_text(...))`），再交给 `build_manifest` 算版本号。
**清单的每一条都来自库本身**，两者不可能对不上，所以 `ok=True`、`problems=[]` 是**恒等式**。

它不能用来证明"库没问题"，理由有两条：

- 这份清单不是历史那一版。`manifest_from_store` 的 docstring 写着"这一版与真正的那一版
  可能不同（原文不在了、`retrieval_text` 不在 metadata 里，都会让算出来的指纹与当初不同）"，
  并且"**重建出来的清单是'从现在起'的基线，不是历史的那一版**"。
  实测里"库里被人删了一条"之所以能被发现，正是因为我们拿的是**构建时那份清单**
  （它记录着 8 条），而不是现算的这份；
- `verify` **不做任何修复**（"本方法的名字是 verify，不是 repair"）。顺手补一条缺失的记录，
  会让"库与清单不一致"这件事**下一次也查不出来**——它的成因（半途失败的构建、人工改库）
  才是要修的东西。

顺带一条容易踩的边界：`manifest_from_store` 在"原文为空且 `metadata` 里也没有 `fingerprint`"时
抛 `ManifestError` 而不是猜一个指纹——"这条记录无法回答'它的内容变了没有'，因此不能进清单"。

**4）差集为什么只比 id；`extra_tokens` 为什么返回三个键。**

`compare_with_store` 的 docstring 说得很直接："为什么差集只比 id、不比 `vector_key`：
那一层判断属于 `planner.plan_index`（它要分'内容变了'与'该不该复用向量'）。
本函数回答的是更粗也更硬的问题——**'清单与库说的是不是同一批记录'**。
两者分开，报告里的结论才不会混在一起。"

换句话说：体检回答"**谁多谁少、口径是不是同一套**"（集合级、口径级），
`planner` 回答"**哪些块要重算**"（记录级、逐条级）。把两者合并，
`problems` 就会同时包含"有两条记录不见了"和"有七条的向量键变了"，
而这两句话的处置完全不同（前者先重建清单，后者要看是不是换了编码器）——
混在一份结论里，运维就不知道该先做哪一步。

`extra_tokens` 返回三个键（`manifest` / `store` / `diff`）而不是一个合计值：
"两边的 token 合计"要对账，就必须能看出**差额是哪一边多出来的**。
实测 `{'manifest': 209, 'store': 178, 'diff': -31}` 一眼能读出"是库这边少了"；
若只给一个"对不上"的总数，就只能在发现对不上之后再拆一次——
而"拆一次"意味着这一次的报告没有任何结论。

**结论**：体检的结论分两层——`ok` 是"能不能用这份清单驱动增量"，
`problems` 是"照着做就能修"；`tokens_match` 这类统计字段故意不参与判定；
而 `verify()` 无参是"清单丢了怎么补救"，**它的全绿只证明它等于它自己**。

### 第 10 题

**考点**：备份为什么必须有保留上限、账本 / `list()` / `load()` 三个口径的差别、
`backup_id` 里为什么没有时间、序号为什么不随份数走，以及端点状态码 400。

**解析**：

**1）`keep <= 0` 直接报错，以及"不设上限最讽刺的失败方式"。**

`IndexBackupStore.__init__` 里就拦：

```python
self._keep = _resolve_keep(keep)
if self._keep <= 0:
    raise BackupError(
        f"备份保留份数必须 >= 1，收到 {self._keep}："
        "一个不保留任何备份的备份机制是自相矛盾的——"
        "它在报告里显示'备份成功'，而真出事时没有任何东西可以回去"
    )
```

`_resolve_keep` 用 `None` 作哨兵：**只有显式传值才覆盖配置**，缺省取
`settings.indexing_backups_keep`（默认 `3`）；常量 `backup.DEFAULT_KEEP = 3` 是
"配置读不到时"的兜底，也是文档引用的那个数。

`backup.py` 的模块 docstring 把"为什么不是日志"写成一句可以直接背的话：

```text
日志可以无限追加，因为它的价值在"完整"；备份的价值在"能回去"，
而"能回去"这件事只需要最近几份。不设上限的备份目录会一直长到吃满磁盘，
而吃满磁盘的那一刻，正在写库的那次构建会失败——**备份把主流程搞挂了**，
这是备份机制最讽刺的失败方式。
```

也就是说：不设上限的后果不是"磁盘满了备份写不进去"，而是**备份把主流程（写库的那次构建）
拖垮了**——一个本来用来防事故的机制，自己变成了事故源。

**2）三个数字的口径。**

```text
账本 backups.jsonl 里 3 行      create 是**追加写**：三份各写一行 → 账本记的是"曾经发生过什么"
内存里的 list() 2 条            prune 删掉目录的同时，把那条记录也从内存表里清掉
backups.load() 返回 2          **实际可用**份数（目录还在的），不是记录条数
```

`load` 的 docstring 把返回值的取舍写清楚了：

```text
记录说存在但目录没了 → 不报错（prune 与人工删除都会造成这种状态，
                      而它不该让整个账本读不出来）
                      但必须**如实计入返回值**——
                      否则 load() 说"读了 3 份"，restore 却只成功 2 次
```

`load` 之后 `list()` 又变回 3 条，是因为 `load` 把账本**整体读回**（`self._records = records`），
"这一版曾经备份过"这条事实不会丢。此时被裁掉的那一份：

```text
backups.get(被裁的那份) → 仍然取得到（账本里有记录）
(base / backup_id).is_dir() → False
restore(被裁的那份) → BackupError："备份目录不存在：……账本里有记录不代表目录还在
                      （prune 或人工删除都会这样）"
```

`latest()` 之所以跳过目录已丢的记录，因为它要保证 `restore(latest())` 这条最自然的写法可用：
"让 `latest()` 返回一个必然失败的记录，会把'备份目录被人删了'伪装成'恢复功能坏了'。"

`read_manifest` 是第三条路——"我想看看那一版是什么，但不想动现在的库"：
它只读快照里的 `manifest.json` 并 `verify_version_id()`，实测读它之后
**库仍是 8 条（读之前 8）、账本仍是 3 条（读之前 3）**。没有这个入口，
人就会用 `restore` 去"看一眼"，而 `restore` 会覆盖现在的库。
真正的 `restore` 实测恢复出两个文件：`manifest.json`（1750 B）与 `store_v2.json`（40767 B）
——**清单跟着一起回去**，因为"没有账的库，下一次增量会当它'没有上一版'而整库重算"。
另外两条硬约束：`restore` **不动**目标目录里已有的其它文件（避免"恢复备份顺带清库"）；
`create` 在动手前**校验全部源文件**（缺一个就拒绝，"少备份一个文件而报告说成功"
是备份机制最不该有的行为）。

**3）`backup_id` 里为什么没有时间；序号为什么不随份数走。**

`backup_id` 只由 `(version_id, backend, 序号)` 决定，`created_at` 不进 id：

```text
时间戳进 id → 同一份内容在同一台机器上备份两次得到两个 id
            → "这两个备份其实是同一版"这件事再也说不清
            → 而清理与对账正是靠"哪些备份是同一版"来做的
```

代价是"两次创建得到同一个 id 前缀"，于是补一个**四位序号**（`_SEQ_WIDTH = 4`）区分：
同一份内容备份两次得到 `…-0001` 与 `…-0002`——**id 不同、`version_id` 相同**，
前者是存储位置，后者才是身份。`created_at` 只作为记录字段（由注入的 `clock()` 提供），
它是给人看的；演示脚本甚至把它钉成固定值 `2026-01-02T03:04:05+00:00`，
因为"`created_at` 不进版本号，钉死它不会让任何身份变假，只是让这份输出可以被逐字节复现"。

序号取"现有最大序号 + 1"而不是"份数 + 1"：

```python
def _next_seq(self) -> int:
    # **不能用"现有份数 + 1"**：裁剪之后份数会变小，于是下一次创建会得到
    # 一个**仍然存在**的 id，把上一份快照原地覆盖掉。
    return max((_seq_of(record.backup_id) for record in self._records), default=0) + 1
```

这是"序号只增不减"的关键。`keep=2` 时的实际轨迹：

```text
create#1  records=[]          → 最大序号 0 → seq 1 → …-0001，list=[1]
create#2  records=[1]         → 最大序号 1 → seq 2 → …-0002，list=[2,1]
create#3  records=[2,1]       → 最大序号 2 → seq 3 → …-0003，prune 把 0001 删掉 → list=[3,2]
create#4  records=[3,2]       → 最大序号 3 → seq 4 → …-0004   ← 正确
         若改用"份数 + 1"     → 份数是 2 → seq 3 → …-0003
                             ← 那是一个**仍然存在**的 id：mkdir(exist_ok=True) 不会拦，
                               新快照会**原地覆盖**掉那份还没被裁掉的旧快照
```

所以演示里"建三份"这一步两种写法都会得到 `0001/0002/0003`（撞车要到第四次才出现），
但纪律必须一开始就写对——这正是源码注释里那句"路径永不重号"的意思。

**4）端点状态码。**

```text
POST /indexing/backup   indexing_dir 为空 → **400**
    detail 说明"本实例没有配置索引目录（indexing_dir 为空）：备份需要一个……一起带走。
    请在 create_app 时传入 indexing_dir=settings.indexing_dir"
    不是 500，也不在请求里偷偷建目录
POST /indexing/plan     mode 非法 → 400，消息里列出 full / incremental
POST /indexing/build    mode 非法 → 400，消息里同样列出 full / incremental + 收到的是什么
POST /indexing/build    records 为空 → 400
POST /indexing/*        请求体形状不对 → 422（与业务规则的 400 分开）
```

`/indexing/backup` 那条是"本组最硬的一条约定"（`tests/test_indexing_api.py` 的说明）：
它失败的典型方式是"跑一次测试就在仓库里留下一个 `backups` / `data/index` 目录"。
因此 `create_app(..., indexing_dir="")` 的缺省是**空串**（与 day064 的
`vector_persist_path = ""` 同一理由：默认行为必须是"明确不落盘"），
而"没配置目录"这个前置条件在**进 `create()` 之前**就被判成 400——
既不 500（那不是环境不可用的语义，是配置缺失），也不在请求里替调用方建一个目录
（那会让"这份备份存在哪"变成一个事后才发现的问题）。

`mode` 非法之所以也走 400 且消息必须列出可选值：`builder._validate_mode` **不做大小写与别名的宽容**
（`"Full"` / `"rebuild"` 一律拒绝），因为"模式决定的是'要不要清空整个库'，
一个靠猜解析出来的模式一旦猜错，代价是一次全量重建"；而 400 的消息里带上
`full / incremental`、收到的是什么，写错的人当场就能改对（
`test_plan_rejects_an_unknown_mode` 与 `test_build_rejects_an_unknown_mode_with_the_choices`
都断言了这三个片段）。

`/indexing/build` 的 `records` 为空返回 400 的理由写在端点 docstring 里：
"增量模式下它会删掉上一版的全部条目（计划里全是 `removed`），而一次**清库**不该由一次空请求触发。"
这一条与 `/indexing/plan` 的空批 400 是同一个形状："一次'什么都不变'的计划会被读成'数据没问题'，
而真相是没看。"

最后一条同样属于"端点纪律"：`/indexing/plan` 调用之后**库与版本表都必须原样**
（`test_plan_does_not_touch_the_store_or_the_version_table`）——计划是"看"，不是"做"；
`/indexing/build` 才是**本组唯一真正改状态的端点**，它把最近一次报告挂在
`app.state.indexing_last_report`（常量 `INDEXING_LAST_REPORT_STATE_KEY`），
而换一个 app 实例它必须是 `None`——写操作不跨实例泄漏。

**结论**：备份的三个数字各回答一个问题（账本 = 历史、`list()` = 内存里的登记、
`load()` = 现在还能恢复几份）；`backup_id` 用"身份 + 序号"而不是时间；
而端点上的 400 都对应"改一个参数/改一次配置就能修好"的那类问题——
它们与 200（缺依赖折成一行报告）、422（请求形状）各管一段。

### 第 11 题

**考点**：缓存键里含身份带来的两件事——"全命中时一次调用都不发"与"换 model 后旧缓存条目永不命中"；
以及这两件事为什么是**结构性**的（不靠"向量碰巧不同"，靠键不同）。

**解析（代码 + 期望输出）**：

把下面这份文件放到 `day065/源码/smart-research-agent/tests/test_exercise_day065_cache.py`：

```bash
cd day065/源码/smart-research-agent
python -m pytest tests/test_exercise_day065_cache.py -q --no-cov -p no:cacheprovider
```

```python
"""day065 习题第 11 题：缓存键里含身份 —— 全命中零调用、换身份零命中.

离线、确定性、不联网、不写盘。提供方是被数过的（``CountingEmbedding``），
因此"一次调用都没发生"是一个可断言的期望值，而不是一种感觉。
"""

from __future__ import annotations

import hashlib

from smart_research_agent.indexing.cache import EmbeddingCache
from smart_research_agent.indexing.encoder import MODEL_LABEL_FALLBACK, BatchEncoder
from smart_research_agent.indexing.types import EmbeddingIdentity, vector_key
from smart_research_agent.llm.embedding import EmbeddingProvider

#: 假提供方的维度。取 4 而不是 256：期望值能手算，向量也一眼能看完。
DIMENSION = 4

#: 三段"编码文本"（真实链路里通常是 retrieval_text = 面包屑 + 正文）。
TEXTS = (
    "索引手册 > 缓存\n缓存键里必须含编码器身份。",
    "索引手册 > 批量编码\n同一批里的重复文本只编码一次。",
    "索引手册 > 版本与血缘\n回滚必须沿血缘走，不能按登记顺序倒着数。",
)

#: 两个"provider 相同、model 不同"的身份。真实场景里这就是"换了模型"。
IDENTITY_A = EmbeddingIdentity(
    provider="CountingEmbedding", model=MODEL_LABEL_FALLBACK, dimension=DIMENSION
)
IDENTITY_B = EmbeddingIdentity(
    provider="CountingEmbedding", model="char-ngram-2-3", dimension=DIMENSION
)


def vector_for(text: str, dimension: int = DIMENSION) -> list[float]:
    """由文本确定性地造一个非零、有限的向量（每个分量落在 [0.1, 0.9]）."""
    digest = hashlib.sha256(text.encode("utf-8")).digest()
    return [((digest[index % len(digest)] % 9) + 1) / 10.0 for index in range(dimension)]


class CountingEmbedding(EmbeddingProvider):
    """确定性编码器：把 ``embed`` / ``embed_batch`` 的调用次数记下来."""

    def __init__(self, dimension: int = DIMENSION) -> None:
        self._dimension = dimension
        self.embed_calls = 0
        self.batch_calls = 0

    @property
    def dimension(self) -> int:
        return self._dimension

    def embed(self, text: str) -> list[float]:
        self.embed_calls += 1
        return vector_for(text, self._dimension)

    def embed_batch(self, texts: list[str]) -> list[list[float]]:
        self.batch_calls += 1
        return [self.embed(text) for text in texts]


def make_cache(identity: EmbeddingIdentity) -> EmbeddingCache:
    """按身份建一份缓存（键里含的就是这三个字段）."""
    return EmbeddingCache(
        provider=identity.provider,
        model=identity.model,
        dimension=identity.dimension,
    )


def test_warm_cache_makes_the_second_encoder_call_free() -> None:
    """全命中时提供方**一次都没被调用**（换一个编码器实例、共用同一份缓存）."""
    cache = make_cache(IDENTITY_A)

    warm = CountingEmbedding()
    warm_encoder = BatchEncoder(warm, batch_size=32, cache=cache, identity=IDENTITY_A)
    warm_vectors, warm_report = warm_encoder.encode(list(TEXTS))

    assert warm_report.encoded == 3
    assert warm_report.batches == 1
    assert warm_report.cache_hits == 0
    assert warm.batch_calls == 1
    assert warm.embed_calls == 3

    cold = CountingEmbedding()
    cold_encoder = BatchEncoder(cold, batch_size=32, cache=cache, identity=IDENTITY_A)
    vectors, report = cold_encoder.encode(list(TEXTS))

    # 结果逐位相同：缓存只省调用，不改变结果
    assert vectors == warm_vectors
    # encoded=0 且 batches=0 —— 一次调用都不该发（空批不是免费的）
    assert report.encoded == 0
    assert report.batches == 0
    assert report.cache_hits == 3
    assert report.hit_ratio == 1.0
    assert cold.batch_calls == 0
    assert cold.embed_calls == 0


def test_changing_the_model_changes_every_key() -> None:
    """换 model 之后，同一段文本的向量键**逐条全变**，身份指纹也变了."""
    old_keys = [
        vector_key(IDENTITY_A.provider, IDENTITY_A.model, IDENTITY_A.dimension, text)
        for text in TEXTS
    ]
    new_keys = [
        vector_key(IDENTITY_B.provider, IDENTITY_B.model, IDENTITY_B.dimension, text)
        for text in TEXTS
    ]

    assert all(old != new for old, new in zip(old_keys, new_keys))
    assert IDENTITY_A.key != IDENTITY_B.key

    cache_a = make_cache(IDENTITY_A)
    cache_b = make_cache(IDENTITY_B)
    assert cache_a.identity_key == IDENTITY_A.key
    assert cache_b.identity_key == IDENTITY_B.key
    assert cache_a.key(TEXTS[0]) != cache_b.key(TEXTS[0])


def test_old_cache_entries_never_hit_after_switching_the_model() -> None:
    """旧缓存条目**永不命中**新模型：键不相交，于是差集只能全部重算."""
    cache_a = make_cache(IDENTITY_A)
    warm = CountingEmbedding()
    BatchEncoder(warm, cache=cache_a, identity=IDENTITY_A).encode(list(TEXTS))
    assert sorted(cache_a.keys()) == sorted(
        vector_key(IDENTITY_A.provider, IDENTITY_A.model, IDENTITY_A.dimension, text)
        for text in TEXTS
    )

    # "新模型会去查的那些键"与旧缓存里的键没有一处相交
    cache_b = make_cache(IDENTITY_B)
    new_keys = {
        vector_key(IDENTITY_B.provider, IDENTITY_B.model, IDENTITY_B.dimension, text)
        for text in TEXTS
    }
    assert set(cache_a.keys()).isdisjoint(new_keys)

    fresh = CountingEmbedding()
    encoder_b = BatchEncoder(fresh, batch_size=32, cache=cache_b, identity=IDENTITY_B)
    vectors, report = encoder_b.encode(list(TEXTS))

    # 一条都没命中：全部走真实编码
    assert report.cache_hits == 0
    assert report.encoded == 3
    assert report.batches == 1
    assert fresh.embed_calls == 3
    # 注意：这个假提供方对两个 model 给出的是**同一批向量**，
    # 而旧缓存依然一条都不命中——保护来自"键里含身份"，不来自"向量碰巧不同"。
    assert vectors == [vector_for(text, DIMENSION) for text in TEXTS]
```

**这两条断言守的是什么**（为什么它们必须会变红）：

```text
若把 EmbeddingCache.key 改成 sha256(text)[:16]（丢掉身份）
    → test_changing_the_model_changes_every_key 会红（新键等于旧键）
    → test_old_cache_entries_never_hit_after_switching_the_model 会红
      （换 model 后 cache_hits 变成 3 而不是 0 —— 这正是"命中旧模型的向量"）

若改成"先发一批空调用、再查缓存"（顺序反了）
    → test_warm_cache_makes_the_second_encoder_call_free 会红
      （cold.batch_calls == 1、report.batches == 1，而期望是 0）

若给 BatchEncoder 传一份与 identity 不匹配的缓存（键错位）
    → 本题的第三条用例会当场红：那一份缓存算出的是 A 的键，
      而 encoder 声明的身份是 B —— 这正是 builder 的 docstring 反复提醒的
      "cache 与 identity 必须一起考虑"
```

最后一条特别值得记住：**假提供方对两个 model 给出的是同一批向量**，
所以"旧缓存不命中"这件事**不是**因为向量不同，而是因为**键不同**。
这正好说明"身份进键"是一个**结构性**保证：它不依赖"两个模型碰巧算出不同向量"这个偶然事实。

**结论**：把"提供方一次没被调用"与"两份缓存的键集合不相交"写成断言，就把
`cache.EmbeddingCache.key → types.vector_key` 与 `encoder.encode` 的
"先查缓存、再决定要不要发调用"这两条纪律锁在了一起——其中任何一处松动，pytest 立刻变红。

```python
"""day065 习题第 12 题：回滚沿血缘 + 重放零写入.

离线、确定性、不联网、不写盘（``FlatVectorStore`` 不带 ``path`` 就只活在内存里）。
用真实的 ``IndexBuilder`` + ``FlatVectorStore`` + ``IndexVersionStore`` 造出
"v1 → v2 采纳 → v3 登记但未采纳"的局面，钉住两件事：

1. ``rollback(steps=1)`` 回到 v1（沿血缘），而不是回到 v3 的上一版（按登记顺序）；
2. 重放同一批时 ``written == 0 and encoded == 0 and batches == 0``。
"""

from __future__ import annotations

import hashlib
from typing import Any

from smart_research_agent.documents.types import content_id
from smart_research_agent.indexing.builder import IndexBuilder
from smart_research_agent.indexing.cache import EmbeddingCache
from smart_research_agent.indexing.encoder import describe_embedding
from smart_research_agent.indexing.types import EmbeddingIdentity
from smart_research_agent.indexing.versioning import IndexVersionStore
from smart_research_agent.llm.embedding import EmbeddingProvider
from smart_research_agent.vectorstore.flat import FlatVectorStore

DIMENSION = 4

#: 八个 16 位十六进制 id（形态取自 day062 的 ``chunk_id``）。
IDS = tuple(f"{index:016x}" for index in range(1, 9))

#: 每条 id 对应一段原文（八条互不相同，因此八个 vector_key 互不相同）。
TEXTS = {
    record_id: f"第 {index} 块：增量不是永远更省，变更比例超过阈值时改走全量重建。"
    for index, record_id in enumerate(IDS, 1)
}

HEADING = "索引手册 > 习题"


def vector_for(text: str, dimension: int = DIMENSION) -> list[float]:
    """由文本确定性地造一个非零、有限的向量."""
    digest = hashlib.sha256(text.encode("utf-8")).digest()
    return [((digest[index % len(digest)] % 9) + 1) / 10.0 for index in range(dimension)]


class CountingEmbedding(EmbeddingProvider):
    """确定性编码器 + 一份"提供方被调用了几次"的台账."""

    def __init__(self, dimension: int = DIMENSION) -> None:
        self._dimension = dimension
        self.embed_calls = 0
        self.batch_calls = 0

    @property
    def dimension(self) -> int:
        return self._dimension

    def embed(self, text: str) -> list[float]:
        self.embed_calls += 1
        return vector_for(text, self._dimension)

    def embed_batch(self, texts: list[str]) -> list[list[float]]:
        self.batch_calls += 1
        return [self.embed(text) for text in texts]


def knowledge_record(record_id: str, text: str) -> dict[str, Any]:
    """造一条 day062 ``knowledge_records()`` 形状的记录（四个键）."""
    return {
        "doc_id": record_id,
        "source": "docs/embedding_index.md",
        "text": text,
        "metadata": {
            "heading_path": HEADING,
            "token_count": 24,
            "fingerprint": content_id(text),
            "retrieval_text": f"{HEADING}\n{text}",
        },
    }


def base_records() -> list[dict[str, Any]]:
    """八条记录（每次调用返回一份新列表，因此改动不会串到别的用例）."""
    return [knowledge_record(record_id, TEXTS[record_id]) for record_id in IDS]


def with_text(
    records: list[dict[str, Any]], record_id: str, text: str
) -> list[dict[str, Any]]:
    """改一条原文，并**同时**更新它的两个派生字段（fingerprint 与 retrieval_text）."""
    updated: list[dict[str, Any]] = []
    for record in records:
        payload: dict[str, Any] = {**record, "metadata": dict(record["metadata"])}
        if payload["doc_id"] == record_id:
            payload["text"] = text
            payload["metadata"]["fingerprint"] = content_id(text)
            payload["metadata"]["retrieval_text"] = f"{HEADING}\n{text}"
        updated.append(payload)
    return updated


def make_rig() -> tuple[FlatVectorStore, CountingEmbedding, IndexVersionStore, IndexBuilder]:
    """装配一份"完全离线"的构建器：内存后端 + 假编码器 + 内存版本表."""
    backend = FlatVectorStore(metric="cosine")
    embedding = CountingEmbedding()
    identity: EmbeddingIdentity = describe_embedding(embedding)
    cache = EmbeddingCache(
        provider=identity.provider,
        model=identity.model,
        dimension=identity.dimension,
    )
    versions = IndexVersionStore()
    builder = IndexBuilder(
        backend,
        embedding,
        cache=cache,
        identity=identity,
        batch_size=8,
        versions=versions,
    )
    return backend, embedding, versions, builder


def test_rollback_follows_lineage_not_registration_order() -> None:
    """v1 → v2 采纳 → v3 登记未采纳：``rollback(steps=1)`` 回到 v1，不是 v2."""
    backend, _embedding, versions, builder = make_rig()
    records = base_records()

    v1, report1 = builder.build(records)
    v2, report2 = builder.build(with_text(records, IDS[0], "第一版之后改写的第一条。"))
    v3, report3 = builder.build(with_text(records, IDS[0], "第二版之后又改写了一次第一条。"))

    # 三次构建各自成功 → 各自被采纳；三版的内容不同 → 三个版本号互不相同
    assert len({v1.version_id, v2.version_id, v3.version_id}) == 3
    assert versions.current == v3.version_id
    assert [manifest.version_id for manifest in versions.history()] == [
        v1.version_id,
        v2.version_id,
        v3.version_id,
    ]
    # 血缘是显式连起来的
    assert v2.parent_version == v1.version_id
    assert v3.parent_version == v2.version_id
    assert report2.parent_version == v1.version_id
    assert report3.parent_version == v2.version_id

    # 现在把第二版标为"生效"：v3 仍然登记着，但**没有被采纳**
    versions.adopt(v2.version_id)
    assert versions.current == v2.version_id
    assert versions.latest().version_id == v3.version_id

    rolled = versions.rollback(steps=1)

    # 反事实：按"登记顺序倒着数"，从最新登记的 v3 往回一步会得到 v2
    history_ids = [manifest.version_id for manifest in versions.history()]
    naive = history_ids[history_ids.index(v3.version_id) - 1]
    assert naive == v2.version_id

    # 沿血缘：current 是 v2，它的 parent_version 是 v1
    assert rolled == v1.version_id
    assert rolled != naive
    assert versions.current == v1.version_id
    # 回滚只改版本指针，不动库与数据
    assert backend.count() == 8


def test_replaying_the_same_batch_writes_nothing_and_encodes_nothing() -> None:
    """重放同一批：``written == 0 and encoded == 0 and batches == 0``."""
    backend, embedding, versions, builder = make_rig()
    records = base_records()

    first, first_report = builder.build(records)
    assert first_report.mode == "incremental"
    assert first_report.seen == 8
    assert first_report.written == 8
    assert first_report.unchanged == 0
    assert first_report.encoded == 8
    assert first_report.batches == 1
    assert backend.count() == 8
    calls_after_first = embedding.batch_calls

    second, second_report = builder.build(records)

    assert second_report.written == 0
    assert second_report.encoded == 0
    assert second_report.batches == 0
    assert second_report.unchanged == 8
    assert second_report.reuse_ratio == 1.0
    # 增量是"不问"：这一次的 cache_hits 仍然是 0（连缓存都没查）
    assert second_report.cache_hits == 0
    # 一次提供方调用都没发生（连空批都没有）
    assert embedding.batch_calls == calls_after_first
    # 重放不产生新版本：版本号由内容算出，四条输入逐位相同
    assert second.version_id == first.version_id
    assert second.parent_version == first.version_id
    assert len(versions) == 1
    assert backend.count() == 8
```

三条读数值得单独看一眼：

```text
v2 与 v3 的 report 都是"写入 1 / 未变 7 / 编码 1（命中 0，1 批）"
    → 这与演示第 3 节 ② 的 updated=1/unchanged=7 是同一个形状；
      而 cache_hits=0 说明这 7 条**根本没进缓存查询**（增量是"不问"）
重放的第二次 cache_hits 仍然是 0，而 encoded/batches/written 都是 0
    → 这是第 6 题那个判断的实时证据
提供方调用增量=0
    → "省下了 8 次编码"这句话的可核对形态（batches == 提供方调用次数 == 0）
```

**为什么第 2 步那个"反事实"比只断言 `rollback(steps=1) == v1` 更能守住这条契约？**

因为"返回值等于 v1"只是一个**值**，它可能被错误实现"恰好也对"地满足：

```text
沿血缘（正确）              current=v2 → parent 是 v1            → v1
按登记顺序倒着数（错）       latest=v3 → 上一行是 v2             → v2
另一个同样错的实现           return history()[0].version_id      → v1（在这个样本上"恰好"通过）
```

第三种实现（"直接返回第一版"）在这个样本上会让 `rolled == v1` 全绿——
但它不是沿血缘，换一个形状（例如 `current=v3`、三版线性登记）它就会给出错误答案。
把反事实也算出来，就把"两种实现的差别"本身写进了断言：

```text
naive（登记顺序下的答案）必须**确实是 v2**，
    → 否则这个用例根本没有测到那条纪律（样本前提失效，先红为敬）
rolled 必须**不等于** naive
    → 一旦有人把 rollback 改成"按登记顺序取上一行"，这条立刻红，
      而且报错信息直接指出反事实是谁（8b71ebe9cbc38a72）
```

这与 day064 第 12 题"必须把'先取 top-k 再筛'的反事实算出来"是同一条纪律：
**把契约的反面也写进断言**——只断言"正确时应该是什么"，
就永远抓不到"错误时会变成什么"。另外 `assert naive == v2.version_id` 这一行还顺带钉住了
"v3 确实登记在 v2 之后"这个样本前提：哪天有人调整了构建顺序让这个前提失效，
它会先红，提示"这个用例已经不再测那件事了"。

最后一条边界也写在这里：`rollback` **只改版本指针**，不动库与数据
（实测回滚后 `backend.count() == 8`）。要真正把库重建回某一版，得再调用一次
`builder.build(...)`——回滚是运维动作，不自动重建索引。

**结论**：`rollback` 的目标是 `lineage(current)` 这条链上的 `chain[-2]`，
而不是 `history()` 的倒数第二行；把"按登记顺序会得到谁"这个反事实也写进断言，
才能让"有人把它改成按登记顺序"这件事本身变红——这与第 11 题"把契约的反面写进断言"
是同一条纪律。
