## 一、选择题

**第 1 题：B**

`max_steps` 的本质是**终止性保险丝**。LLM 是概率模型，"何时输出 Final Answer"没有硬保证——它可能在工具结果之间无限兜圈子。循环上限把"可能不收敛"的概率行为变成"必然在 N 步内结束"的工程承诺。A（省钱）是附带收益而非根本原因——如果只为了省钱，按 token 计费即可，不需要步数上限；C 是上下文管理的职责（day008 的截断策略），即使窗口无限大，不收尾的循环仍是灾难；D 工具超时是单次调用层面的事，与循环步数无关。参考 [../../day006/教程/教程.md](../../day006/教程/教程.md)。

**第 2 题：C**

`eval` 会把字符串当任意 Python 代码执行，`__import__("os").system(...)` 这样的载荷可以执行系统命令——Agent 的工具输入来自 LLM 输出，而 LLM 输出可能被 Prompt 注入污染，因此工具输入是**不可信输入**。AST 白名单的思路是"解析后逐节点检查类型，只允许数字常量与运算符节点"，从机制上杜绝代码执行。A、B、D 都是正确性问题，`eval` 同样能"正确"处理它们——它们不是换 AST 的理由，安全才是。参考 [../../day004/教程/教程.md](../../day004/教程/教程.md) 与 [tools/calculator.py](../../day010/源码/smart-research-agent/smart_research_agent/tools/calculator.py)。

**第 3 题：B**

短期记忆 = 每次请求重发的历史消息列表 + 最大长度/截断策略（因为 LLM API 无状态，"记忆"是代码模拟的）；长期记忆 = 文本经 Embedding 向量化入库，按与查询的语义相似度召回 top-k。A 说反了两者的存储形态；C 错误——模型权重在对话中不更新，什么都"记不住"；D 错在"精确"与"必然"——向量检索是模糊匹配，相似度排序只保证"可能相关"，且受截断与索引质量影响。参考 [../../day008/教程/教程.md](../../day008/教程/教程.md)、[../../day009/教程/教程.md](../../day009/教程/教程.md)。

**第 4 题：C**

MCP 在传输层复用 JSON-RPC 2.0：请求 `{"jsonrpc": "2.0", "id": ..., "method": ..., "params": ...}`，响应携带 `result` 或 `error`。项目里用 pydantic 把 `JsonRpcRequest`/`JsonRpcResponse`/`JsonRpcError` 建模（见 [../../day016/源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py](../../day016/源码/smart-research-agent/smart_research_agent/mcp_server/protocol.py)）。复用成熟标准而非自造协议，换来现成的错误码语义、批量请求语义和各语言实现。参考 [../../day016/教程/教程.md](../../day016/教程/教程.md)。

**第 5 题：B**

"提供文档读取"是**只读、无副作用**的语义，正是 Resource 的定义：URI 寻址（如 `kb://docs/rag-intro`），客户端可以安全地预取、缓存、索引。选 A 的问题不在"能不能做"（Tool 确实也能返回文本），而在**语义承诺**：Tool 声明的是"可能有副作用的动作"，客户端不敢对其做缓存等优化；选 C 则混淆了"数据"与"提示词模板"——文档内容可能被放进提示词，不等于文档本身是 Prompt。三原语的价值就在于把语义承诺写进协议类型。参考 [../../day017/教程/教程.md](../../day017/教程/教程.md)。

## 二、判断题

**第 6 题：×**

提示词约束是**软约束**——它只降低坏输出的概率，不能归零。LLM 可能在 JSON 前后加客套话、包 Markdown 代码块、输出合法但语义不对的 JSON。解析层的容错与校验是**硬约束**：`parse_plan` 的四道防线（find/rfind 定位边界 → `json.loads` 语法校验 → 字符串数组类型校验 → 非空语义校验）保证任何不听话的输出都变成明确异常而非坏数据流入下游。两者的关系是"提示词降失败率、解析器兜底安全网"，缺一不可。参考 [../../day010/教程/教程.md](../../day010/教程/教程.md)（[agent/planner.py](../../day010/源码/smart-research-agent/smart_research_agent/agent/planner.py)）。

**第 7 题：×**

LangGraph 重构的是**编排**，不是推理。迁移后，"决定继续行动还是收尾"的 `add_conditional_edges` 判断依据仍然是节点内 ReAct 逻辑的产出（LLM 输出了 Action 还是 Final Answer）；节点函数内部照样要调 LLM、解析输出、执行工具、写回状态。变的是控制流的表达方式（while 循环 → 状态图），换来持久化（checkpointer）、会话隔离（thread_id）、断点续跑；不变的是 Thought → Action → Observation 的推理范式本身。参考 [../../day013/教程/教程.md](../../day013/教程/教程.md)（[graph/react_graph.py](../../day013/源码/smart-research-agent/smart_research_agent/graph/react_graph.py)）。

**第 8 题：×**

把自建包命名为 `mcp` 会造成**包遮蔽（shadowing）**：Python 导入 `mcp` 时会先命中本地包，官方 SDK 的 `from mcp.server.fastmcp import FastMCP` 将拿到你自己的模块，报出一堆莫名其妙的 AttributeError，排查极其痛苦。这是项目共享规格里明确的红线：包名固定为 `smart_research_agent.mcp_server`。同类教训在 Python 生态屡见不鲜（如本地文件命名 `json.py` 遮蔽标准库）。参考 [../../day016/教程/教程.md](../../day016/教程/教程.md)。

**第 9 题：×**

恰恰相反——内存内测试走的是**真实的协议路径**：客户端请求被序列化为 JSON-RPC 消息、经内存流传输给 Server、Server 路由到对应处理函数、响应再序列化回来。被 Mock 掉的只是"传输介质"（内存流替代 stdio 管道/网络），而传输介质恰恰是协议正确性测试中**最不需要关心**的部分。这与 MockLLM 的思想完全同构：**Mock 最不确定的依赖（网络/模型输出），保留要验证的逻辑（协议路由/业务代码）**。因此它是真测试，而且比真起子进程的集成测试快两个数量级、零 flake。真子进程冒烟测试留少量即可。参考 [../../day023/教程/教程.md](../../day023/教程/教程.md)。

## 三、问答题

**第 10 题：**

三大失控模式（参考 [../../day010/教程/教程.md](../../day010/教程/教程.md)）：

1. **迷失方向**：沉浸在某步细节里，忘了全局目标——ReAct 每步只看当前上下文做局部决策，没有全局目标牵引；
2. **步骤冗余**：忘记已经搜过的内容，重复行动——没有"已完成清单"；
3. **提前收场**：查了三分之二就下结论——局部每步都"合理"，全局任务没完成。

**Planner 是事前补偿**：在执行的"时间轴起点"之前，用一次 LLM 调用产出显式的全局计划（Plan）。提纲同时缓解三困境——方向有提纲牵引、进度有清单可查、完成有兜底标准。它扩展的是单步推理**向前看**的视野。

**Reflexion 是事后补偿**：在执行失败之后，把失败轨迹蒸馏成"原因 + 改进建议"的自然语言文本，注入下一轮重试的上下文。它扩展的是单步推理**向后看**的视野——不重试同样的输入赌采样，而是让模型"知道自己上次错在哪"，本质是用自然语言更新上下文（而非权重）。

**不能互相替代**：Planner 管"出发前有没有地图"，但对地图之外的环境变化（子任务失败、新信息）无能为力——它没有反馈回路；Reflexion 管"撞墙后怎么调整"，但一份反思只修正局部行为，无法保证全局目标的完整性。生产级系统需要两者配合（计划牵引方向 + 失败时反思重试，甚至触发重规划），这正是后续 RePlanner 机制的方向。

**第 11 题：**

`BaseLLM` 抽象 + 构造注入（`Planner(llm=...)`、`ReactAgent(llm=...)` 都接收抽象基类）带来的红利至少包括：

1. **测试离线且确定**：所有涉及 LLM 的逻辑用 `MockLLM`（按预设脚本弹出回复）驱动，满足 FIRST 原则——Fast（毫秒级）、Repeatable（任何机器结果一致）、不消耗 API 额度。后续 day006 的循环测试、day010 的规划测试、day011 的反思测试全部建立在此基础上；
2. **失败路径可测试**：`MockLLM(responses=["我不知道怎么拆解"])` 一行就能制造"模型不听话"的场景，验证 `PlanParseError` 等 sad path——真实模型几乎无法按需复现失败；
3. **生产实现可替换**：换模型供应商只需换注入的实现（`OpenAICompatibleLLM` 换成任何 OpenAI 兼容端点），上层模块一行不动；M2 阶段 Client 包装层出错时的回退策略也依赖这个边界。

如果当初让 `ReactAgent` 直接 `import OpenAICompatibleLLM`：每次跑测试都要真实网络请求 + API Key——测试慢（秒级/次）、不稳定（网络抖动、模型输出漂移）、有成本、CI 跑不了；且模型输出不可控，无法构造"恰好输出坏 JSON"的测试用例，第三、四章的防御式解析防线将永远无法被测试守护。参考 [../../day005/教程/教程.md](../../day005/教程/教程.md)（[llm/mock.py](../../day010/源码/smart-research-agent/smart_research_agent/llm/mock.py)）。

**第 12 题：**

合拢路径：MCP Client 连接 Server 并完成握手后，调用 `list_tools()` 做**能力发现**，拿到每个工具的 `ToolDescriptor`（name/description/input_schema）；然后为每个远程工具创建一个**本地代理对象**——它实现 M1 的 `BaseTool` 契约（name/description/parameters/execute），但 `execute()` 内部是发起 MCP `tools/call` 请求；最后把这个代理 `registry.register()` 进 day005 的 `ToolRegistry`。

说这是架构胜利，因为 ReAct 循环只依赖注册表的 `get(name)` / `describe()` 抽象——工具背后是进程内函数还是跨网络的 MCP 调用，对循环完全透明。day005 埋下的"注册表而非硬编码工具列表"设计，在 day020 兑现了回报：**新增一整类能力来源，上层代码零改动**。这是开闭原则的实例。

Client 包装层必须做的关键事情：**把 JSON-RPC error / 网络异常翻译成 Agent 能消化的 Observation 错误文本**（如 `"工具执行失败: <原因>"`），而不是让异常击穿 ReAct 循环。这与 `ReactAgent._execute_tool` 内部 `try/except` 返回错误文本的设计一致——工具失败对循环而言是"一次结果不好的观察"，而不是"系统崩溃"。参考 [../../day020/教程/教程.md](../../day020/教程/教程.md)。

**第 13 题：**

- **stdio**：Client 把 Server 作为子进程拉起，通过标准输入输出交换 JSON-RPC 消息。适合**本地场景**：桌面 Agent 接入本地工具、单机开发调试。优点是零网络配置、零端口管理，进程边界天然就是隔离边界；缺点是一对一（一个 Client 一个 Server 进程）。
- **SSE**：Server 作为 HTTP 服务常驻，多个远程客户端通过长连接收发消息。适合**网络场景**：团队共享的工具服务、跨机器调用。优点是一对多、可集中部署运维；缺点是要处理网络认证、超时、断线。

容器化 stdio Server 时，**stdout 是协议信道**：JSON-RPC 消息一条一条从 stdout 流过。任何写进 stdout 的日志（print、logging 默认 StreamHandler 写 stdout 的配置）都会混进消息流，Client 端解析到非 JSON 行直接协议错误。因此日志必须写 stderr（或文件），保持 stdout 的纯净——这是 stdio 类协议（LSP 同理）的通用纪律。Docker 化不改变这个约束，只是把"拉起子进程"换成了"拉起容器"。参考 [../../day019/教程/教程.md](../../day019/教程/教程.md)、[../../day022/教程/教程.md](../../day022/教程/教程.md)。

**第 14 题参考解答**

`plan_execute_memory_pipeline.py`（已基于 day010 快照实测通过）：

```python
"""规划 -> 执行 -> 记忆 流水线：Planner 拆任务，ReactAgent 逐个执行，结果记入日志."""
from __future__ import annotations

from typing import Callable

from smart_research_agent.agent.planner import Planner
from smart_research_agent.agent.react_agent import ReactAgent
from smart_research_agent.llm.base import BaseLLM
from smart_research_agent.tools.registry import ToolRegistry

FAILURE_MARK = "未能得出最终答案"


class PlanExecuteMemoryPipeline:
    def __init__(
        self,
        planner: Planner,
        registry: ToolRegistry,
        agent_llm_factory: Callable[[str], BaseLLM],
        max_steps: int = 5,
    ) -> None:
        self._planner = planner
        self._registry = registry
        self._agent_llm_factory = agent_llm_factory  # 每个子任务一个独立 LLM（测试可控）
        self._max_steps = max_steps
        self.memory_log: list[str] = []

    def run(self, goal: str) -> dict:
        plan = self._planner.plan(goal)  # 非法输出在此抛 PlanParseError，直接向上传
        results = []
        for step in plan.steps:
            agent = ReactAgent(
                llm=self._agent_llm_factory(step),
                registry=self._registry,
                max_steps=self._max_steps,
            )  # 每子任务新建 Agent：history 不跨任务累积，保持隔离
            output = agent.run(step)
            status = "failed" if FAILURE_MARK in output else "ok"
            results.append({"step": step, "status": status, "output": output})
            self.memory_log.append(f"{step} => {output}")  # 模拟写入长期记忆
        return {"goal": goal, "results": results, "memory_log": list(self.memory_log)}
```

测试 `test_pipeline.py`：

```python
import pytest

from plan_execute_memory_pipeline import FAILURE_MARK, PlanExecuteMemoryPipeline
from smart_research_agent.agent.planner import Planner, PlanParseError
from smart_research_agent.llm.mock import MockLLM
from smart_research_agent.tools.calculator import CalculatorTool
from smart_research_agent.tools.registry import ToolRegistry


def make_registry() -> ToolRegistry:
    registry = ToolRegistry()
    registry.register(CalculatorTool())
    return registry


def action_then_answer(expression: str, answer: str) -> MockLLM:
    """构造一个"先调计算器、再给最终答案"的 MockLLM."""
    return MockLLM(responses=[
        f"Thought: 需要计算 {expression}\nAction: calculator\nAction Input: {expression}",
        f"Thought: 已得到计算结果\nFinal Answer: {answer}",
    ])


def make_pipeline(plan_json: str, llm_by_step: dict, max_steps: int = 5) -> PlanExecuteMemoryPipeline:
    planner = Planner(llm=MockLLM(responses=[plan_json]))
    return PlanExecuteMemoryPipeline(
        planner=planner,
        registry=make_registry(),
        agent_llm_factory=lambda step: llm_by_step[step],
        max_steps=max_steps,
    )


def test_happy_path_all_ok():
    pipeline = make_pipeline(
        '["计算 2+3", "计算 10-4"]',
        {"计算 2+3": action_then_answer("2+3", "5"),
         "计算 10-4": action_then_answer("10-4", "6")},
    )
    result = pipeline.run("算两个数")
    assert result["goal"] == "算两个数"
    assert [r["status"] for r in result["results"]] == ["ok", "ok"]
    assert result["results"][0]["output"] == "5"
    assert len(result["memory_log"]) == 2
    assert "计算 2+3 => 5" in result["memory_log"]


def test_failed_step_does_not_abort_plan():
    stuck = MockLLM(responses=[
        "Thought: 再想想\nAction: calculator\nAction Input: 1+1",
    ] * 3)  # 永远不给 Final Answer，跑满 max_steps
    pipeline = make_pipeline(
        '["计算 2+3", "永远答不完的子任务", "计算 10-4"]',
        {"计算 2+3": action_then_answer("2+3", "5"),
         "永远答不完的子任务": stuck,
         "计算 10-4": action_then_answer("10-4", "6")},
        max_steps=3,
    )
    result = pipeline.run("含失败子任务的目标")
    assert [r["status"] for r in result["results"]] == ["ok", "failed", "ok"]
    assert FAILURE_MARK in result["results"][1]["output"]
    assert result["results"][2]["output"] == "6"   # 失败子任务没有中断后续计划
    assert len(result["memory_log"]) == 3


def test_invalid_plan_raises():
    pipeline = make_pipeline("我不知道怎么拆解", {})
    with pytest.raises(PlanParseError):
        pipeline.run("任意目标")
```

**解析**：

- **编排层薄如纸是对的**：`run()` 只做三件事——规划前置、逐个下发、收集结果。它不含任何规划逻辑（归 Planner）也不碰工具细节（归 ReactAgent/Registry），这正是 day010 第四章职责边界的落地检验。
- **每子任务新建 ReactAgent** 是为了隔离 `history`；`agent_llm_factory` 注入而非直接传 MockLLM 列表，让测试能精确控制"哪个子任务收到哪份脚本"——这是 day005 依赖注入思想在编排层的延续。
- **失败检测用契约文本**而非异常：`ReactAgent.run` 跑满步数返回的是提示文本而非抛异常（见 [react_agent.py](../../day010/源码/smart-research-agent/smart_research_agent/agent/react_agent.py)），所以用 `FAILURE_MARK in output` 判定。生产中更稳妥的做法是让 `run` 返回结构化结果（含成功标志），本题为了不改基座代码采用文本匹配。
- **失败不中断**是"跳过并标记"策略：结果里带 `"status": "failed"`，调用方（未来的汇总层/RePlanner）可以据此决定重试或降级。对比"中断"策略：简单但一个失败拖垮整份计划。
- 实测：`pytest test_pipeline.py` → **3 passed**（基于 day010 快照，全程离线）。

`mcp_calc_server.py`（已在 mcp 1.29.1 上实测通过）：

```python
"""把 M1 的安全计算逻辑暴露为 MCP Tool + Resource."""
from __future__ import annotations

import ast
import operator

from mcp.server.fastmcp import FastMCP

# 与 day004 CalculatorTool 同款的 AST 白名单求值
_BIN_OPS = {
    ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
    ast.Div: operator.truediv, ast.Pow: operator.pow, ast.Mod: operator.mod,
}
_UNARY_OPS = {ast.UAdd: operator.pos, ast.USub: operator.neg}


def _safe_eval(node: ast.AST) -> float:
    if isinstance(node, ast.Expression):
        return _safe_eval(node.body)
    if isinstance(node, ast.Constant):
        if isinstance(node.value, (int, float)):
            return node.value
        raise ValueError("仅支持数字常量")
    if isinstance(node, ast.BinOp) and type(node.op) in _BIN_OPS:
        return _BIN_OPS[type(node.op)](_safe_eval(node.left), _safe_eval(node.right))
    if isinstance(node, ast.UnaryOp) and type(node.op) in _UNARY_OPS:
        return _UNARY_OPS[type(node.op)](_safe_eval(node.operand))
    raise ValueError("不支持的表达式")


app = FastMCP("calc-server")


@app.tool()
def safe_calculate(expression: str) -> str:
    """计算数学表达式，支持 + - * / ** % 与括号，例如 '2 + 3 * (4 - 1)'."""
    try:
        result = _safe_eval(ast.parse(expression, mode="eval"))
    except (SyntaxError, ValueError, ZeroDivisionError) as exc:
        return f"计算失败: {exc}"   # 错误翻译成文本，而非让异常击穿调用方
    return str(result)


@app.resource("guide://usage")
def usage_guide() -> str:
    """计算器使用说明."""
    return "safe_calculate(expression)：输入算术表达式字符串，返回计算结果文本；非法表达式返回'计算失败'原因。"


if __name__ == "__main__":
    app.run(transport="stdio")
```

```python
import pytest
from mcp.shared.memory import create_connected_server_and_client_session
from pydantic import AnyUrl

from mcp_calc_server import app


@pytest.mark.asyncio
async def test_capabilities_and_calls():
    async with create_connected_server_and_client_session(app) as session:
        await session.initialize()

        # (a) 能力发现：Tool 与 Resource 都可见
        tools = await session.list_tools()
        assert "safe_calculate" in [t.name for t in tools.tools]
        resources = await session.list_resources()
        assert "guide://usage" in [str(r.uri) for r in resources.resources]

        # (b) happy path：2 + 3 * 4 = 14
        ok = await session.call_tool("safe_calculate", {"expression": "2 + 3 * 4"})
        assert ok.content[0].text == "14"

        # (c) 注入载荷被 AST 白名单拦截，返回错误文本而非异常
        bad = await session.call_tool("safe_calculate", {"expression": "__import__('os')"})
        assert bad.content[0].text.startswith("计算失败")

        # (d) 读取 Resource
        guide = await session.read_resource(AnyUrl("guide://usage"))
        assert "safe_calculate" in guide.contents[0].text
```

**解析**：

- **跨阶段的接缝就在这道题里**：`_safe_eval` 是 M1（day004）的执行内核，`@app.tool()` 是 M2（day018）的协议外衣——内核不管协议、协议不管内核实现，各演各的。FastMCP 依据函数签名（`expression: str`）与 docstring 自动生成 input schema 和描述，所以 **docstring 不是文档而是给 LLM 的使用说明书**。
- **错误翻译**体现了 day020 Client 包装层的思想：工具侧把异常收敛为 `"计算失败: ..."` 文本，协议层就不会产生 JSON-RPC error，调用方（Agent 循环）拿到的是可消化的观察结果。注意 `"__import__('os')"` 在 `ast.parse` 阶段是合法语法（它是个 Call 节点），是 `_safe_eval` 的白名单检查抛出 `ValueError("不支持的表达式")`——白名单防的是"语义"而非"语法"。
- **内存内测试走真实协议**：`create_connected_server_and_client_session` 在 mcp 1.29 中可直接接收 `FastMCP` 实例并产出已连接的 `ClientSession`，请求-响应全程经过 JSON-RPC 序列化与路由，只有传输介质换成了内存流——与 MockLLM 同构的"Mock 最不确定的依赖"。
- `read_resource` 的参数必须是 `AnyUrl` 而非裸字符串（pydantic 类型约束）；`session.initialize()` 不可省略——MCP 握手交换双方能力声明，跳过它后续调用会直接报错。
- 实测：`pytest test_mcp_calc.py` → **1 passed**（离线，毫秒级）。
